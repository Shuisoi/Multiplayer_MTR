# 02 任务驱动的客货运服务器 —— 可行性分析与技术路线

> 目标：以“任务(Task)”对象驱动整台服务器运行的 MTR 客货运玩法改造；
> 列车按“车底/编组类”重做牵引与制动（有级/无级/降保升）；加入 MTR 没有的货运与“主副节点”连解挂；UI 全面重构。
> 倾向：基于 MTR 源码（MIT）直接派生独立模组。
> 本文件结论均基于对 MTR 4.0.5/1.20.4 与 TSC（Transport Simulation Core）源码的实读取证（详见文末“证据清单”）。
>
> **决策更新（2026-09）：产品定名 MMTR（Multiplayer MTR）、平台 Fabric/1.20.4、引擎进程化路线 —— 见 `docs/03-MMTR-架构决策与里程碑.md`。**

---

## 0. 结论速览（TL;DR）

- **技术可行性：高，但工程量大。** 不存在阻碍性技术障碍；关键不是“能不能”，而是“范围和排序”。
- 必须动“三层”代码，只改 MTR mod 不够：**车辆物理与数据在 TSC 引擎内**，mod 只负责渲染/方块/输入/UI。
- **推荐路线：分层派生（fork TSC 引擎 + fork MTR mod + fork 映射库），组成自研 monorepo；引擎源码级参与构建（不再用 libs 里的预编译 jar）**；对外命名空间/ mod id 改为自研名，内部包名建议保留 `org.mtr.*` 以把改动集中在功能层。
- 第一版保持“MC 服务端进程内嵌引擎”的现有架构（改动面最小、同步/存档管线现成可用）。
- 预计：单人全职做到可玩的 MVP 约 **5–8 个月**；建议先砍出最小闭环：**1 条线 + 2 种车底 + 客运任务 + 货运任务 + 连解挂 + 基础 HUD**。

## 1. 现状盘点（谁在做什么，改哪里）

### 1.1 代码分层（已核实）

| 层 | 仓库/角色 | 许可 | 关键内容 |
| --- | --- | --- | --- |
| 引擎 TSC | `Minecraft-Transit-Railway/Transport-Simulation-Core`（master，无 tag） | MIT | 车站/线路/时刻/调车场/信号/车辆**物理与调度**；可脱离 Minecraft 单测（自带 JUnit） |
| 内容+平台层 | `Minecraft-Transit-Railway/Minecraft-Transit-Railway`（master = 4.0.5/1.20.4） | MIT | 方块/物品/实体渲染/输入/网络包/本地 Web（运输图+资源包创建器）；把 TSC 打成 jar 发布 |
| 跨平台抽象 | `Minecraft-Mappings`（含 1.20.4 各 loader 版） | MIT | `org.mtr.mapping.*` 屏蔽 Fabric/Forge 差异 |
| 注册/事件库 | `Minecraft-Mod-API-Tools`（jonafanho） | MIT | `Registry/RegistryClient`、命令、事件 |

**构建事实**：MTR 用 `libs/` 里的预编译 jar（flatDir）把 TSC、Mappings、工具库**整体 shadow 进发布 jar**（relocate 只做三方库）；车辆等数据对象由 **JSON Schema → 生成 Java/TS 代码**的管线产生（TSC 与 MTR 的 buildSrc 都有 `SchemaParserJava/TypeScript`），所以**改持久化数据结构＝改 schema json＋重新生成**，这是本项目最该学会的“第一课”。

### 1.2 你要的能力 vs MTR/TSC 现状

| 需求 | 现状（源码证据） | 差距 |
| --- | --- | --- |
| 任务对象驱动 | 只有 `Route/Trip/Siding/Depot 指令`、ATO 自动到站 | **无 Task**：需新建任务图/调度器/执行状态机 |
| 玩家与 AI 无缝 | 已有 手动/自动 驾驶切换（`manualCooldown`、掉线即回自动）、服务器权威 + 客户端快照回放（`Vehicle.isClientside`） | 需把“司机”抽象成角色（Human/AI 统一 Actor）并纳入任务执行 |
| 车底/编组牵引制动 | 现为固定 7 级功率（`MAX_POWER_LEVEL=7`，含紧急制动到 `-8`），加减速常量（`Siding.ACCELERATION_DEFAULT/MAX_ACCELERATION`、`VehicleExtraData.acceleration/deceleration/maxManualSpeed`） | **无“车底特性”数据模型**：需按车底定义有级曲线/无级控制/降保升空气制动等可插拔动力学 |
| 货运 | `train_cargo_loader/unloader` **只是传感器**（`BlockTrainSensorBase`，按车次/停走触发），无货物数据 | 需完整货运模型：货物类型/容量/装卸终端/经济闭环 |
| 主副节点连解挂 | 只有静态 `couplingPadding` 几何；一列 `Vehicle` 即固定编组，无车钩对象、无运行时重组 | 需 Coupler/Consist 重组 + 同步渲染更新 + 调车任务 |
| UI 重构 | 原版风格屏幕（`org.mtr.mod.screen`）＋渲染实体 | 需自研 HUD/司机台/任务/调度 UI（客户端 mod 重做） |
| 防掉线 | TSC 仿真在服务端，不依赖玩家在场；席位由玩家实体驱动 | 补：玩家离开→AI 接管的形式化规则 |

## 2. 产品/领域模型草案（先定概念再写码）

以任务为核心的最小域模型（所有对象在引擎内定义并持久化，mod 侧只是“交互视图”）：

- **TaskDef（任务定义/模板）**：类型（客运/货运/调车连挂/调车解挂/回库/整备）、起点终点（站/股道/装卸点）、车底要求、时刻/顺序、奖励/费用、前置条件。
- **TaskInstance（任务实例）**：指派给某 Consist，状态机：`等待→准备→出库→区间运行→站内作业(停车/装卸/连挂/解挂)→完成/取消/超时`。
- **ConsistType（车底/编组类，服务端配置数据）**：车辆组合模板、**动力分布（动车/拖车/动力车头）、控制方式（有级 N 档 / 无级 / 降保升空气制动）、牵引力-速度曲线、阻力、自重/载重、货舱配置**、制动类型（电空/空气）。
- **Consist（运行中的车列）**：由若干引擎既有 `VehicleCar` 组成，但改为**可变编组**；车钩链 Coupler[] 显式建模（节点 = 主/副端，即你说的“主副节点”）。
- **Actor（司机角色）**：Human / AI 双实现；同一时刻一个 Consist 只允许一个“有效控制源”，任务引擎总能介入（安全层兜底）——天然解决抢控/掉线。
- **Freight（货物）**：货物条目（类型/重量/来源/去向/货票）+ 车辆货舱占用 + 装卸事件。
- **Dispatcher / TaskRunner**：服务器核心循环，决定“下一个任务给谁、何时发车”，玩家与 AI 在它面前完全一致。
- **RailNode/Station/DeliveryPoint**：沿用 MTR 的 Station/Platform/Siding，新增“作业点”概念。

“任务驱动”执行模型一句话：**列车不自己决定去向，一切移动与作业由 TaskRunner 派发的指令（order）驱动**；玩家司机驾驶的是“建议指令”，安全/信号层与 ATO 一致，防止乱开与脱轨式玩法破坏。

## 3. 技术路线（推荐 A，含备选与理由）

### 3.1 方案对比

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A. 分层派生（推荐）** | fork TSC(引擎)＋MTR(内容/平台)＋Mappings/工具库，做成 composite 源码依赖的 monorepo；在引擎内实现车底物理/任务/货运/连解挂，mod 侧实现方块与 UI | 改动受控、可无头单测、同步/存档/发布管线现成；工作量主要在功能本身 |
| B. 不动源码，用 Mixin/反射钩子改发布 jar | 尝试注入已 shade 的 `org.mtr.core.*` | **不推荐**：类是 final、包被 shade、API 不稳定；只能做 UI/输入等小钩子，物理/任务做不了 |
| C. 完全自研（不用 MTR/TSC） | 另起炉灶 | 不推荐：轨道/信号/寻路/调度/渲染同步全要重造，工期翻数倍 |

### 3.2 方案 A 的具体拆解

**① 仓库与构建策略（第一周）**
- 建 monorepo：`engine`（TSC fork）+ `game`（MTR fork，fabric 优先）+ `mappings`（fork，按需）。
- **把 `libs/Transport-Simulation-Core-0.0.1.jar` 换成源码级参与**（composite build 或 includeBuild），彻底解决“每次改引擎要手工打 jar 进 libs”的问题。
- 锁定引擎基线：MTR 4.0.5 打包的 TSC 是 0.0.1（TSC 上游现为 1.0.2、无 tag），**需从 MTR 发布日（2026-06 前后）附近的 TSC 提交取基线**，避免夹带 1.0.2 的未知变更。
- 命名策略：**mod id、资源命名空间、lang key、方块/物品 id 改成自研名**（如 `frt`）；**内部 Java 包保留 `org.mtr.*`**（大幅缩小 diff、降低出错面），代价是与官方 MTR 不能同实例共存——对本项目（替换式服务器 mod）可接受；若日后要共存再全量改包名（IDE 重构可机械化）。
- 保留 Schema 代码生成管线，新增字段走 `buildSrc/src/main/resources/schema/**` 修改 + 重新生成。

**② M1 引擎层：车底对象 + 可插拔牵引/制动（约 3–5 周）**
- 在 `Vehicle` 的 `simulateMoving/Stopped/InDepot` 处做**动力学策略化**：`DriveController` 接口 + 实现：
  - 有级：档位→牵引力曲线（保留现 7 级并参数化每车底可配）；
  - 无级：目标牵引力/恒速控制（含加速限制、粘着限制可选）；
  - 降保升（空气制动）：列车管压力状态机（缓解/保压/制动）+ 制动缸建压/缓解速率、紧急制动；
  - 阻力（可选 Davis 或简化常数）+ 坡度/曲线附加阻力（如需）。
- 新增 `ConsistType` 数据对象（schema 定义），物理参数由服务端配置/资源包提供。
- **可无头验证**：TSC 自带 JUnit（已有 `DepotDepartureTests` 等），在纯 JVM 上回归，不必每次开 Minecraft。

**③ M2 任务引擎 + AI 司机 + 连解挂（约 4–6 周）**
- Task 图/调度器（服务器权威、持久化：复用 serializer，或 JSON/NBT；二期可上数据库）。
- `Actor`（Human/AI）与席位、掉线接管规则（接入现有 `isCurrentlyManual/manualToAutomaticTime` 机制）。
- **连解挂**：给 Consist 引入显式 Coupler（主/副节点）与“可变编组”，涉及渲染同步与车辆间相对运动（长度/间距在 `VehicleExtraData.totalVehicleLength` 与位置更新中现成可扩展），改动中等风险，做专项测试。
- 与信号/ATO 关系：任务的“区间运行/站内停车”继续走 TSC 现有路径与闭塞逻辑，只把“何时停/开哪个门/停几秒”改由任务指令决定。

**④ M3 货运闭环（约 4–6 周）**
- 车辆货舱（schema 加 `cargo` 字段/独立 `FreightCar` 派生），货物清单与重量影响动力学（载重对加速的影响接入 M1 的动力学）。
- 装卸：把现有 `train_cargo_loader/unloader` 传感器**升级/替换为真实终端方块**（装卸台＋仓储容器＋到站自动装卸），任务中定义装卸点与货单。
- 基础经济/记分（若服务器需要）：接任务获得“运单/报酬”，最小闭环即可。

**⑤ M4 客户端/UI（约 4–6 周）**
- 输入重构：驾驶台（有级档把/无级推杆/降保升三态/紧急），可沿用键盘或手柄。
- 信息 HUD/界面：当前任务与下一步、速度/信号/下一站、功率/制动状态、编组与货物、司机接管状态（AI/玩家）。
- 管理面：任务列表/创建/调度 GUI；可选 Web 调度台（引擎现有 Jetty servlet 可扩展）。
- 渲染：车辆外观沿用资源包 .bbmodel/OBJ（MTR4 数据驱动，改模组后依然有效）。

**⑥ M5 服务器运营（随开发持续）**
- 权限（司机/调度/管理）、反作弊（防飞天/瞬移兜底沿用原版）、备份与存档迁移（**破坏性玩法改动需设计存档迁移器或直接开新档 beta**）、性能调优（线程化仿真与异步文件加载已有开关，配置化）、部署文档与自动化。

## 4. 需要你拍板的关键决策（我的默认建议）

1. **平台**：Fabric 先行（环境已就绪），Forge 二期 → 默认 Fabric。
2. **MC 基线**：锁定 **1.20.4 + MTR 4.0.5**（fork 冻结），不追上游；未来是否迁 `stonecutter`（4.1 beta 多版本线）另议 → 默认冻结 1.20.4。
3. **命名**：对外改 `frt`，内部保留 `org.mtr` → 默认采纳（不要求与官方 MTR 共存）。
4. **引擎形态**：第一版沿用“服务端进程内嵌引擎”；二期评估独立引擎进程（TSC 已支持无头 Simulator，利于性能隔离）→ 默认内嵌先行。
5. **任务范围 MVP**：一条线、两个站对、两种车底（客运电力动车组 + 货运机车+敞/棚车）、任务链含连挂/解挂/装卸 → 请确认或调整。
6. **多人规模假设**：决定是否需要分区/线程化优化级别与网络带宽考虑（建议按 20–50 并发在线起步设计）。

## 5. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 范围失控（最常见死因） | 强制 MVP 定义；每个里程碑给“可玩验收点” |
| TSC/MTR 数据与 schema 生成改动引发连锁 | 先吃透 codegen 管线；数据字段走 schema 修改而非手改生成类 |
| 连解挂/变编组破坏渲染与闭塞 | 专项原型（M2 前先做 1 周 spike）验证后再全线开发 |
| 存档不兼容 | beta 阶段明示“开新档”；数据结构稳定后再出迁移器 |
| 上游(含 TSC)不追更 | 冻结基线 + 自己的回归测试集（JUnit 无头） |
| 与资源包类 addon 兼容 | 保留 `assets/mtr` 命名空间的兼容读取层或说明约束 |

## 6. 里程碑与粗排期（单人全职）

| 阶段 | 交付 | 估计 |
| --- | --- | --- |
| M0 派生与跑通 | monorepo、改名、双端(单机+服务器)能跑、schema 改一字段全链路生效 | 1–2 周 |
| M1 车底与物理 | 两种控制方式(有级/无级)+降保升原型、参数化车底、JUnit 回归 | 3–5 周 |
| M2 任务与连解挂 | Task 图/调度/AI 接管/连解挂 spike→落地 | 4–6 周 |
| M3 货运 | 货舱/装卸终端/任务闭环 | 4–6 周 |
| M4 UI/输入 | HUD/司机台/调度 GUI | 4–6 周 |
| M5 运营化 | 权限/经济/备份/性能/文档 | 3–6 周 |
| **合计** | **可玩 MVP（含运营基础）** | **约 5–8 个月** |

（有经验的多人小团队可压缩到 3–4 个月到 MVP；估算不含美术/音效外包。）
