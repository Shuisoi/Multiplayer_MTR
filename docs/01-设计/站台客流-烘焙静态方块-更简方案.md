# 站台客流：只针对 Human Era 的静态烘焙（读 jem → 网格 → 批量绘制）

> **一句话**：**只服务 Human Era 这一份包**，所以不需要通用适配、也不需要"录渲染"——
> 直接把 `HumanEra_Villagers.zip` 的 `villager.jem`（几何）与它的三层贴图（皮 / 群系 / 职业）读出来，
> 烘成**网格模板**，用批量网格绘制；读的时机放在**资源重载之后**（毫秒级、内存里、不写盘、不二次重载）。
> 现在的两条在制代码（录制 594 行 + 反推成方块模型 937 行）**整条删掉**。

本文替换前几版方案（同名文件的旧内容）。相关：`站台客流-村民实体与客量属性-设计.md`、
`notes/414`（标记与走动人流）、`notes/398/401`（钢轨烘焙：后台烘 + 合桶 + 每 pass 预算，本文复用的管线）。

## 3 只针对 Human Era 之后，哪些问题自动消失

| 上一版的难题 | 现在 |
|---|---|

### 3.1 读什么（Human Era 的固定约定，已实测）

```
HumanEra_Villagers.zip
  assets/minecraft/optifine/cem/villager.jem        ← 几何：9 个原版部件 + 自定义人形子树（32 盒，成年 28）
     └ 挂点写死：bodywear/player/{player, lreg, rreg, left_arm2, right_arm2, head2}
       盒子全部轴对齐；textureSize = [128,128]；rotate 只有 bone2/bone3 的 [90,0,0]
  assets/minecraft/optifine/random/entity/villager/*.png   ← 底层皮（72 张 128×128）
  assets/minecraft/textures/entity/villager/type/*.png     ← 群系层（7 张）
  assets/minecraft/textures/entity/villager/profession/*.png ← 职业层（16 张）
```

### 3.2 ★ 必须画**三层**，只画底层皮 = 裸体（本机实测）

| 文件 | 尺寸 | 不透明像素 | 外套区 (16,32)-(40,48) |
|---|---|---|---|
| `optifine/random/entity/villager/villager10.png`（底皮） | 128×128 | 15% | **11 / 384** |
| `optifine/random/entity/villager/aaaaa.png`（底皮） | 128×128 | 7% | 0 / 384 |
| `textures/entity/villager/type/plains.png` | 128×128 | 7% | 0 / 384 |
| `textures/entity/villager/profession/librarian.png` | 128×128 | 7% | 0 / 384 |

- 探针：[he_layers.py](sandbox/tmp/he_layers.py)。底层皮在外套区几乎是空的 ⇒ **衣服在叠加层**。
- 与 `MmtrCrowdVillagers` 里的旧记录一致：「Human Era 的底板人皮是**裸体**的（外套区 (16,32)-(40,48) 全透明）」。
- 所以雕像的**层集合照抄实体**：`base + type + profession`（实测有效层 3，第 4 层是空的），
  用**同一套四边形**逐层画一遍（多 2 次 draw，仅此而已）。
- 顺带解释了为什么"方块模型"这条载体更贵：方块模型里每多一层就要**复制一遍几何**
  （派生包 112 elements = 28 盒 × 4 层，就是这么来的）。

## 4 方案

### 4.1 数据流

```
Human Era 的字节（底皮 / type / profession / villager.jem）
        │  ① 读：资源重载后读一遍（两条已知路径：emf/cem 与 optifine/cem）
        ▼
  ② 烘（纯函数、可单测）：jem → 四边形（位置/UV/法线）；档位 → (皮, type, profession) 三元组
        ▼
  ③ 绘制：网格模板 × 实例矩阵（格子位置 + 朝向），每层一次 draw
        │     （复用钢轨烘焙那条路：后台烘 + 合桶 + 每 pass 预算 + LRU + 剔除 + 失败回退）
        ▼
  ④ 谁站哪：引擎给 crowdLevel + 闸门；客户端算格子/朝向/档位（纯视觉）
```

### 4.2 为什么要烘成网格，而不到处画实体

| # | 理由 |
|---|---|
| 1 | **一条站台 1–2 次 draw**（钢轨那条路的账：767 draw → 每材质 1 次，`notes/398`） |
| 2 | **客量/半径变化不重建区块网格**（方格块模型的话，每改一次客量 = 站台那几段区块重烘 = 真卡顿） |
| 3 | **任意贴图 id**（不碰方块图集）；**任意角度**（不需要 22.5° 两层拆） |
| 4 | 层数天然支持（每层一次 draw），不用为每层复制几何 |

### 4.3 时机 = "无感"

| 项 | 现在（在制代码） | 本版 |
|---|---|---|
| 什么时候读 | 进世界 40 tick 后录渲染 | **资源重载之后**（下一帧读一次文件，解析 JSON） |
| 开销 | 派生 + 写包 + **二次重载** + 自校验 | 解析 ≈6 KB JSON + 读 3 张 PNG（**毫秒级**） |
| 落盘 | 派生包 11.58 MB | **无** |
| 玩家感受 | 进世界可能卡一下 / 多一次重载 | **感受不到** |
| 换皮/换版本 | 要重进世界/重启 | **他自己那次重载后立刻生效** |

退化：读不到 / 解析失败 ⇒ 一条日志 + 用模组内置基线（随 jar 出货的一份 Human Era 派生模板）⇒ 不空、不崩、不二次重载。

### 4.4 档位、姿势、走动

| 项 | 方案 |
|---|---|
| 档位 | **4 组显式指定的 (底皮, 群系, 职业)**；不再去猜 ETF 的随机结果 |
| 姿势 | **静止姿势**（jem 的盒子声明，忽略 `animations` 表达式）；朝向由实例矩阵给（16 向随便给） |
| 走动的人流 | 同一套网格 + 按走道挪位置；要"腿在摆"，就**手工烘 2 帧**（腿 ±25°、臂反向）按位移切帧 —— 不实现表达式求值器 |

### 4.5 治根第二步：客流 = 引擎给数、客户端画

| 关注点 | 谁 | 怎么做 |
|---|---|---|
| 客量 | 引擎（**权威，不动**） | `crowdLevel` 已在下发；`platform set/station/all` 不动 |
| 闸门 | 引擎（**不动**） | `cap / radius / rows / force` 照旧，改成**渲染侧**闸门 |
| 谁站哪/朝哪/哪档 | 客户端 | 本地标记格 + `crowdLevel` + 闸门 → 同一套确定性算法（splitmix64 排序取前 N，notes/414 §3） |
| 走动人流 | 客户端 | 按走道挪渲染位置（纯视觉） |
| 标记方块 | 玩家（**不动**） | `crowd_mark_*` 仍是布局编辑器 |

## 8 取舍与边界（写清，别再回头改口径）

| 放弃 | 换来 |
|---|---|
| 支持 Human Era 以外的包 | 不用写通用适配层；不用录渲染；路径与部件名写死、可单测 |
| Human Era 的**动画表达式**（呼吸/眨眼/跟随原版动作） | 静止姿势 + 手工 2 帧走路；不需要实现 CEM 表达式求值器 |
| ETF 的"随机挑皮" | 4 组显式档位（确定性、可复现） |
| "方块"这个载体 | 任意角度/任意贴图/不碰图集/层数不复制几何/客量变化不重建区块 |
| 站定客流是"世界里的东西" | 引擎仍是唯一权威，客流只是画面（它本来也不影响玩法逻辑） |

**边界**：静止姿势 = 雕像不呼吸不眨眼（这是"固定方块/固定网格"的语义本身）；
换 Human Era 版本后若部件名/层数改了，读法要跟着改一行（写死的是约定，不是代码结构）。

## 11 第二刀：座位方块回退 + "雕像一个都看不见"的根因（2026-10-11）

### 11.1 用户口径（原话）

> 标记方块依旧需要原本的逻辑啊，我们只不过是查询标记方块并生成村民模型。

第一刀把"这一格站着人"做成了**换方块**（标记 → `crowd_seat_*`），于是：

* 用户手放的**一级/二级标记**全被换走 ⇒ 手持标记时原地看不到任何标记（"根本不显示红色十字型"）；
* 那条路还多出两个方块、1024 个状态、一个方块操作队列和"谁顶替谁"的账 —— 全是自找的复杂度。

**回退**：`occupied`（标记自己的属性）就是"这一格站着人"，方块种类与摆放朝向不动；
客户端扫 `occupied=true` 的一级/二级标记格，每格画一个人。座位方块**停止写入**，只保留"认出老格并迁回"这一步。

### 11.2 根因：图集 Identifier 少了 `textures/` 前缀与 `.png`

```
Failed to load texture: mtr:crowd/crowd_atlas
java.io.FileNotFoundException: mtr:crowd/crowd_atlas   (ResourceTexture$TextureData.load)
```

`RenderLayer.getEntityCutoutNoCull(Identifier)` 要完整贴图路径 ⇒ 必须是
`mtr:textures/crowd/crowd_atlas.png`。这一个字符级错误就是"顶点写下去了（日志里
`本帧雕像 220/739 个 ｜ 147840 顶点`）、画面里却一个人都没有"的全部原因。

### 11.3 删 / 改清单

| 对象 | 处置 |
|---|---|
| `MmtrCrowdModule.applySeatOp` | 改成 `BlockCrowdMarker.withOccupied(state, true/false)`；`isSeat` → `hasStatue` |
| `MmtrCrowdModule.bodyStepOf/headStepOf/variantOf/HEAD_SALT` | **删**（姿势与外观由格子哈希算，服务端不再写进方块状态） |
| `RenderCrowdMarker` | 回到原样：手持任意标记 ⇒ 全部标记现形（贴地色块 + 十字矮柱） |
| `MmtrCrowdStatues` | `ATLAS_ID` 修正；只画 `occupied=true`（老座位格亦算，过渡）；朝向/外观改由格子哈希 |
| `BlockCrowdMarker` | `withOccupied(state, boolean)`、`markerStateOf(kind)`、`isLegacySeat` |
| `BlockCrowdSeat` + `crowd_seat_*` 注册/blockstate/模型/物品 | **留一届**（过渡识别，见 §5）；`crowd dump` 的"雕像格台账"不再出现座位格时删 |

### 11.4 这一刀之后的判定口径（别再混）

| 问题 | 一个数/一眼就够 |
|---|---|
| 服务端认不认这些格 | RCON：`execute if block <x> <y> <z> mtr:crowd_mark_1[occupied=true] run say OK` |
| 客户端扫到几格 | 客户端日志 `[MMTR-CROWD] 扫到雕像格 N 个`（半径 8 区块 ⇒ 一条站台约 1100 格） |
| 贴图加载成功没有 | 日志里**不该有** `Failed to load texture: mtr:crowd/crowd_atlas` |
| 画了几个人/多贵 | `MMTR_STATUES_DEBUG=true` ⇒ `本帧雕像 N/M 个 ｜ Q 四边形 ｜ 写顶点 X ms ｜ 下一帧上限 C` |

### 11.5 渲染路径与规模（实机定论，2026-10-11）

| 路径 | 结论 |
|---|---|
| 自己往实体批次写顶点（`AFTER_ENTITIES`） | **钉在屏幕上**（变换不对）⇒ 废弃 |
| `MainRenderer.scheduleRender` + `IDrawing.drawTexture`（`BEFORE_ENTITIES` 排队） | **位置正确** ⇒ 现行方案（与车厢/钢轨/标记现形同一条路） |

代价：一个人 672 个四边形 ≈ **60 µs**；8 区块内 1075 人全画 ≈ 64 ms/帧。**已改成 VBO 批次**（§11.6）。

### 11.6 最终方案：烘进 MTR 优化渲染器的 VBO 批次（2026-10-11）

| 项 | 做法 |
|---|---|
| 载体 | 每 32 格一块的 `OptimizedModel`（`RawMesh` + `RawModel.triangulate()` + `upload(MAPPING)`），与钢轨同一条路 |
| 缓存 | 每块一个签名（格坐标 + 朝向 + 四个外观下标）；扫描（100 tick）后只把签名变了的块标脏，每帧最多重烘一块 |
| 每帧 | `push / translate(块原点 − 相机) / OPTIMIZED_RENDERER_WRAPPER.queue(model) / pop`，照抄 `RenderRails` |
| 释放 | 不再出现的块 `close()`（显存还给 GPU） |
| 回退 | 优化渲染器不可用 / 建块抛异常 ⇒ 回到"逐帧写顶点 + 自调预算"，画面一致只是人数要闸门 |

实机读数：**1280/1280 人全画**，每帧排队 **0.02–0.07 ms**，`[MMTR-LIGHT]` 里
`mtr:textures/crowd/crowd_atlas.png=14.0(1.00批)` 确认进了同一条优化批。
两个必须在映射库字节码里确认过的坑：**四边形必须三角化**（索引缓冲按每面 3 个下标分配）、
**失败后要清干净**（净迭代器 + 立刻停手）。建块 35–94 ms 仍在渲染线程，欠一条"挪到工作线程"。
