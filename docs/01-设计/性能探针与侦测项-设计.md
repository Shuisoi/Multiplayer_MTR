# 服务端性能探针与侦测项（设计）

> 起因：**地图一大就落后 40 s**（notes/336 §3），严重时被看门狗直接杀掉（notes/335 §4）。
> 但"是谁吃掉的"一直只能靠两样东西回答：崩溃栈（只有崩了才有）与 JFR 采样（要停机、要人来读）。
> 结果每加一座站，都只能"感觉更卡了"。
>
> 这篇定的是**怎么把"是谁"变成常驻、可开关、可点名的数字**，以及**哪些数字一越线就该动手**。
> 怎么跑、怎么读数看 [`02-运行与作业/性能探针-运行手册.md`](../02-运行与作业/性能探针-运行手册.md)。
>
> ⚠️ **本篇只覆盖服务端**（引擎模拟 tick + MC 服务端 tick）。**客户端渲染帧**是另一套：
> `MmtrFrameProbe` / `[MMTR-FRAME]`，开关与读数口径见运行手册 **§8**。
> 它沿用本篇的三条设计约束（只记账不改行为 / 关掉近似零成本 / 不许淹没日志），
> 但段名分 `main.` 与 `shadow.` 两套 —— 因为开光影时一个视觉帧会被**渲染两遍**，
> 而阴影那一遍的开销与屏幕分辨率无关（这正是"分辨率调低也没用"的机制）。

---

## 1. 三条设计约束（每一条都对应一个踩过的坑）

| 约束 | 为什么 |
| --- | --- |
| **只记账，不改行为** | notes/328 §R 已把"允许做的优化"钉死为**逐位相同**（不许改采样步长、不许换近似算法、不许跳过计算）。探针若顺手缓存/短路，就等于把行为改了却没人知道。所以探针的返回值**只**表示"要不要计时"，绝不参与任何判断。 |
| **关掉就近似零成本** | 默认关闭，唯一开销是每个测量点一次 `volatile` 读（`MmtrProbe.on()`）。`System.nanoTime()` 只在开着时才调，且计时点埋在**一段工作的边界**（一次投影、一个 tick 阶段），不埋在循环体里。 |
| **不许淹没日志** | notes/77 的教训：诊断输出一旦每 tick 一行，真正要看的行就被埋掉。所以输出是**窗口汇总**（默认每 100 tick = 5 s 一行）+ 一个**有界**的最坏帧榜（12 条）。 |

## 2. 三层模型

```text
① 帧（frame）      引擎一次模拟 tick  /  MC 一次服务端 tick         ← 一次 tick 多长？掉帧没有？
② 段（section）    帧内的一段工作（rails.tick2 / sections.rebuild / server.mirror.*）
                   ＋ 跨帧的重复劳动（projection.solve 的次数）      ← 时间花在哪一段？
③ 计数（event）    缓存命中/清空、重建次数、跳过次数、峰值           ← 次数本身就是结论
```

三层缺一不可，理由：

- **只有 ①** ⇒ 只知道"卡了"，不知道查哪；
- **只有 ②** ⇒ 会被"每 tick 全量重算"骗过去：单次看起来不贵（0.05 ms），乘上 250 灯 × 294 轨就是几十毫秒；
- **只有 ③** ⇒ 知道"次数爆炸"，但不知道那值多少毫秒。

### 2.1 帧为什么要分槽

嵌入式运行时同一个线程上有**两个时钟**：引擎的模拟 tick（50 ms 一步）与 MC 的服务端 tick（20 TPS）。
两者不是一回事 —— 一次服务端 tick 里可能跑 0…N 次模拟 tick（掉帧时还会追帧）。混在一张表里两边都读不懂，
所以帧预算按**帧槽**分开：`frame=sim` 与 `frame=server`，分段计时共用。

### 2.2 服务端帧被拆成三段（`MmtrTickProbe`）

只用 `START_SERVER_TICK → END_SERVER_TICK` 量"整帧"是不够的：MMTR 的每-tick 钩子挂在 `END` 上，
而 `END` 事件本身在整帧**之后**才发 —— 单看那个数会得出"我们没花时间"的**错误结论**。所以量三段：
`server.tickSpan`（完整帧间隔）｜`server.vanillaAndEngine`（原版）｜`server.mmtrHooks`（三个钩子合计）。
再减去 `server.routeMirror` / `server.signalSync` 两个单点，剩下就是指令执行器与开销本身。

## 3. 探针清单（埋在哪、看什么）

### 3.1 引擎模拟 tick（`Simulator.tick`）

| 段名 | 位置 | 越线意味着 |
| --- | --- | --- |
| `rails.tick1` / `rails.tick2` | 逐轨 tick | 轨数 × 每轨成本；现场最大的一段 |
| `vehicles.simulate` | `sidings.simulateVehicles` | 车多才贵；空世界应当≈0 |
| `points.syncPhysical` / `points.syncPhysical2` | 道岔跟着授权扳岔（每 tick 两次） | 幂等但要遍历全部道岔；道岔多则贵 |
| `points.retryQueues` / `points.defaults` | 位置队列自愈 / 默认位 | 排队反复重试 = 有车在抢岔 |
| `signal.aspectView` | 信号显示视图重建门 | 轨图签名变了才重建；频繁重建=轨图在动 |
| `plan.dispatchers` / `jobs.scheduler` | 时刻表派发 / 作业步进 | P 系列的每-tick 成本 |
| `clients.sendUpdates` | 每客户端差量同步 | ∝ 在线人数 × 脏对象。**无头环境恒 0，量不到** |
| `save.auto` | 自动落盘 | 落盘那一拍会顶掉一整个 tick |
| `web.runs` + `web.queue` / `web.shed` / `web.skipSlowTick` | 网页任务时间片 | 网页把 tick 吃掉时这里会亮；让开次数说明它在挨饿 |

### 3.2 区间层与几何（真正的地雷区）

| 段名 | 位置 | 越线意味着 |
| --- | --- | --- |
| `sections.rebuild` | `MmtrSectionService.rebuild()` | 整层重建：全世界的轨×灯几何 |
| `sections.rebuildCount`（事件） | 同上 | 每 tick 重建几次；>1 就是缓存失效在抖 |
| `sections.signatureCheck`（事件） | `refreshIndexes` | **每一次公开查询都会问一遍世界签名**（notes/172 实测 ~25 µs/次）。次数 ÷ tick 数 = 放大倍数 |
| `projection.solve` | `MmtrSectionGeometry.project` 冷算 | 单次 = 整根轨按 0.25 m 采样；`max` 与均值差得远 ⇒ 个别长轨在拖 |
| `projection.hit`（事件） | 投影缓存命中 | 与 `solve` 的比 = **命中率** |
| `projection.evict`（事件） | `MAX_ENTRIES` 撑爆后整体 `clear()` | **非零就是危险信号**：清一次之后每一对 (灯,轨) 回到冷算 |
| `projection.entries`（峰值） | 缓存条目数 | 逼近 200 000 就说明下一轮会更卡 |

### 3.3 游戏端每-tick 钩子（`END_SERVER_TICK` 上的三个）

| 段名 | 位置 | 说明 |
| --- | --- | --- |
| `server.routeMirror` | `MmtrRouteMirror.tick` | **已知头号热点**：看门狗的栈顶就是它（notes/335 §4） |
| `server.mirror.nextRails` / `.pendingEntries` / `.restrictedNodes` / `.lampAspects` / `.lampRails` / `.sectionBands` / `.signature` / `.broadcast` | 同上，逐段 | 一行读出"这五步里哪一步贵" |
| `server.mirror.changed` / `.unchanged`（事件） | 同上 | **能不能改脏标记的前置读数**：unchanged ÷ tick 数 ≈ 1 ⇒ 绝大部分 tick 算完发现没变 |
| `server.signalSync` / `signalSync.syncChunk` / `signalSync.chunks` | `MmtrSignalSync` | 每 tick 的固定成本（排队区块 + 每 20 tick 轮转） |
| `server.commandExecutor` | `MmtrCommandExecutor` | 应当≈0；有毫秒读数就是**指令本身**贵（扫描/铺轨在这一格里） |
| `world.loadedChunks` / `world.signalBlocks`（峰值） | 同上 | 规模自变量：灯数与区块数是所有读数的**主语** |
| `server.tickSpan` / `server.vanillaAndEngine` / `server.mmtrHooks` | `MmtrTickProbe` | 见 §2.2 |

## 4. 侦测项（什么算"有问题"）

探针只给数字；**判据**在这里。每条都写明"读到什么就说明什么"，不写"应该优化"。

| # | 侦测项 | 判据 | 指向 |
| --- | --- | --- | --- |
| D1 | 单帧耗时 `frame=server max` | 反复 > 1000 ms（20 个 tick） | 尖峰：施工/区块生成/存档；看最坏帧标签 |
| D2 | `server.tickSpan` 的 p50 | ≈ 50 ms = 没掉帧；持续 > 60 ms | 稳态就跑不动 20 TPS |
| D3 | `server.vanillaAndEngine` ÷ `tickSpan` | > 80% 且 `mmtrHooks` 不大 | 锅在原版（区块/实体）或落在里面的引擎 tick |
| D4 | `server.mmtrHooks` | 持续 > 10 ms | 三个每-tick 钩子之一；用 `.routeMirror` / `.signalSync` 二分 |
| D5 | `server.mirror.unchanged` ÷ 总 tick 数 | > 0.8 而 `server.routeMirror` 又贵 | **每 tick 重算了没变的东西** ⇒ 脏标记/节流的方向（不是"算得更快"） |
| D6 | 投影命中率 `hit/(hit+solve)` | < 0.9（稳态） | 缓存没在起作用：键不命中或被清空 |
| D7 | `projection.evict` | **> 0** | `MAX_ENTRIES` 撑爆后整体 `clear()`；这是"突然更卡一档"的机制 |
| D8 | `projection.solve` 次数 ÷ tick 数 | 与「灯数 × 候选轨数」同量级 | 每 tick 全量重算；次数本身就是结论 |
| D9 | `sections.signatureCheck` ÷ tick 数 | > 50 | 有公开查询被放在每灯/每轨的循环里 |
| D10 | `sections.rebuildCount` ÷ tick 数 | > 1 | 签名在抖（轨图/道岔/进路/灯绑定每 tick 都在变） |
| D11 | `web.shed` + `web.skipSlowTick` | 持续增长 | tick 已经慢到网页整队挨饿（这是**症状**，不是病） |
| D12 | `save.auto` | 单次 > 50 ms | 落盘吃掉整帧；autosave 要摊开 |
| D13 | `world.loadedChunks` / `world.signalBlocks` | 随施工单调增长 | 规模自变量；与所有读数一起看才能比"前后" |
| D14 | 客户端 `已量段合计 ÷ 帧间隔 p50` | 稳态明显 < 1（实测见过 8.5 / 18 ms） | 时间在**没被埋点的每帧钩子**（`MainRenderer.render` 的"模拟 + 钩子"那半边，见 §5）或别的线程/GC ⇒ 转 JFR，**不要继续给渲染段加计时**（2026-10-08 就是靠这条差额找到 notes/404） |
| D15 | `[MMTR-FRAME]` 的 `兜底轨 现建` | 持续 > 0（实测每 5 s 窗口 2 万–7 万次） | 车辆位置查询在**重复造曲线**（notes/404）。健康的稳态应当是**个位数**，`复用` 才是大的那一格 |
| D16 | `[MMTR-FRAME]` 的 `车辆位置查询` | 与「视野里的列车数 × 真的需要位置的调用点」同量级 | 若它相对"车数"涨了，说明又有**只要车节 id** 的调用点去走了位置查询（notes/405：`modelCarIndex` / `vehicleIdFor` 一类必须为 0） |

**升级路径（什么时候不该再加探针）**：D6/D7/D8 同时亮 ⇒ 问题已经定位到投影放大，直接改结构（脏标记 / LRU / 按轨索引候选灯），
不要再加测量点；反过来，如果所有段加起来只占 `tickSpan` 的一小半，那锅在**没被埋点的代码**里 ——
这时才轮到 JFR/async-profiler 去找新的埋点位置（方法见运行手册 §5）。

## 5. 不变量与已知边界

- **只在开着时计时**：`begin()` 返回 0 ⇒ `end()` 直接返回。所以关掉探针后**没有任何行为差异**。
- **异常路径也收帧**：`Simulator.tick` 的 `finally` 里收帧，否则一次异常之后每帧耗时都算错。
- **最坏帧榜有界**：12 条；窗口汇总的段数上限 24（多的折叠成一行计数）。
- **量不到的（写在明处）**：
  - **32 个客户端**：`clients.sendUpdates` ∝ 在线人数 × 脏对象，无头环境恒 0；
  - **原版世界活**：只能在真实服务端上由游戏端读数回答；
  - **JIT 冷启动**：一次投影的冷热差可以到 30 倍（见运行手册 §4 的表），所以任何对照实验都要先预热。
- **帧探针只覆盖"渲染段"**：一个视觉帧在 `MainRenderer.render` 里被分成两半 —— 前一半是**模拟 + 每帧钩子**
  （`MmtrCoupleInteraction.tick`、`VehicleExtension` 的平滑位置、`ModelPropertiesPart` 之类都在这里），
  后一半才是被 `main.*` / `shadow.*` 埋点的渲染。**前半段没有计时**，所以
  D14 的差额不是噪音而是线索：2026-10-08 那 8.0 ms/帧（占活跃窗口 42–69%）全在段外
  （notes/404 §4）。⇒ 差额大就去 JFR，别在渲染段里找。
- **JFR 的叶子归属会被 JIT 内联改变**：同一个函数在两次 run 里可能一次显示为 `World.getChunk` 叶子、
  一次显示为它内部的 `PalettedContainer.get`。**跨 run 比"叶子"不可靠**；能跨 run 比的是
  "栈上出现过某函数"的采样占比、以及探针自己的计数（例：notes/405 §2.3 那次按叶子判读改动的尝试，
  实测不出差别就回退了）。

## 6. 验收（这套东西自己怎么被验）

| 用例 | 验什么 |
| --- | --- |
| `MmtrTickBudgetTests` | 真实世界存档上量 ① 引擎 tick ② 游戏端每-tick 链；断言各阶段埋点都在、引擎单步不超天花板（默认 5 ms）、重复调用后投影命中率 ≥ 50% |
| `MmtrProjectionKillCurveTests` | 投影缓存的击杀曲线：同一批 (轨,点) 投 N 轮，冷算/命中/耗时的形状；硬断言"同一 (轨,点) 投两次只冷算一次" |

两条都**只打印**性能数字（不设"必须更快"的断言），硬断言只针对**结构**：埋点失联、缓存失效、
引擎悄悄变成整帧瓶颈。理由：性能数字随机器与 JIT 抖动，把它写成闸门只会让人学会跳过测试。
