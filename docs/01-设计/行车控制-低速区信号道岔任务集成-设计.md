# 低速区整体行车控制系统：信号 × 道岔 × 任务（英铁式联锁，设计 v1）

> 状态：设计 v1（2026-09-08）。现实基准：docs/01-设计/参考-英铁AWS与TPWS机制.md（AWS/TPWS/
> 联锁边界）；任务体系：docs/01-设计/任务系统-任务派生与任务单时间表-设计.md。
> 目标：低速区（AWS 制式，≤100 km/h 轨段）上，任务（进路意图）驱动道岔自动扳动，
> 信号显示 = 进路状态 × 闭塞空闲，AWS 触发绑定信号/限速，形成闭环行车控制。

## 1. 角色分配（英铁语义 → MMTR 组件）

| 现实角色 | MMTR 组件 | 现状 | 缺口 |
|---|---|---|---|
| 进路意图（车要去哪） | `MmtrTask` / mission 计划（MmtrRunPlanner nodes+forkOps） | 已有（每车现算路线） | 无"进路"状态对象，信号读不到 |
| 联锁/道岔锁闭 | `MmtrPointAuthority`（(节点,进向) holder/queue/lock） | 出发时**整条进路预占** | 接近式授予 + approach-lock + 信号联动 |
| 信号显示（四显示） | mmtr-trains signals[]（占用链红黄绿） | 只按占用 | 需并入"进路已设/锁闭" |
| AWS（点式告警+确认） | S3 状态机 | 固定提前量触发 | 绑定信号"非绿"/限速 + 未确认制动对齐 |
| 闭塞（一区段一车） | S1 每轨一区段占用 | 已有 | — |

## 2. 核心改造（分步）

### A1. 接近式岔权（本片）
- `MmtrRunPlanner.Plan` 增加 `forkMeters`：每个岔口 op 在 walker 距离空间的绝对位置
  （与 stopCumulativeM 同坐标系）；
- `Vehicle`：任务武装/刷新时**只请求距车 ≤ APPROACH_METERS（120 m）的岔口**：
  - 出发时不预占远处岔口 → 后车不再占前车将用的岔；
  - 车接近岔口才 request：前方无车占时即 GRANTED（英铁：车到信号前，进路为它设）；
  - 被前车占用/已持 → QUEUED（英铁：在信号外排队），前车 passed() 后自动递补；
  - mission 终了/删除 → releaseAll（孤儿清理保留窗口过期兜底）。
- 取消语义：接近中取消=立即释放 + 由信号红等待（approach-lock 延时后续按需加）。

### A2. 信号 = 进路 × 闭塞（低速区显示）
- 对**有任务**的列车：其进路首岔口已设并授权 → 该信号按 UK 四显示链给绿/单黄/双黄；
  未设/敌对/接近车未授权 → 红；
- 对**无任务自由驾驶**（玩家手动作业）：维持现占用链显示（红黄绿），不参与联锁；
- WEB 信号层同规则；feed 附带每个任务车的"当前进路"摘要（首目标+已授权岔）。
- **进展（2026-09-09，notes/79）**：引擎侧已交付——`MmtrSignalAspect` 成为单一真源
  （闭塞链为底；SET 的 MAIN 进路收窄分岔；PENDING 进路把入口轨压红；SHUNT 不清主灯；无进路退回原链），
  `SystemMapServlet` 的重复链走行已删除。**剩余**：游戏内渲染器（fabric `RenderSignalBase.mmtrChainDepth`）
  改读同一规则，需要把进路状态镜像到客户端（notes/79 §4 的 R3）。

### A3. AWS 挂点（低速区）
- AWS 触发条件从"固定距离"改为与**信号显示/限速对象**绑定：本信号非绿（红/黄）或前方
  限速起点 → 进 AWS 警示（含双黄/单黄），绿灯 clear（复位）；
- 未确认窗口按现实对齐（2~2.5 s 语义 → 引擎参数），未确认 → 紧急制动直至停稳（与现有
  保护层协同，防 SPAD 由占用+保护兜底，文档注明与 TPWS 的差异）。

### A4.（后置）进路对象与 OP/玩家视图
- 任务进路可观察（当前任务+已授权岔+信号状态）供 OP 时间表/信号控制台引用；
- Vehicle 派生后 COUPLE 进路（DriveToConsist）进入同一联锁框架。
- **进展（2026-09-09，notes/78）**：`MmtrRoute`/`MmtrRouteRegistry` 已交付——进路成为一等对象
  （rails + 道岔需求 + SET/PENDING，状态由 `MmtrPointAuthority` 每 tick 派生），每列车 feed 带 `route`、
  顶层 `routes[]`；这是 A2 信号显示与 S5 联锁的读源。A2/A3 待做（见 notes/78 §4 的 R2–R5）。

## 3. 边界（本系统 v1 不做）
- 高速区 LZB 连续列控并入（同架构第二制式，后续）；
- 多列车进路冲突的全局优化（路由重排）——v1 靠接近式排队+信号红解决；
- TPWS 等效硬防护——v1 用 S1 占用+保护制动兜底并在文档标注。

## 4. 实施记录（2026-09-08）：信号灯登记 + 覆盖绑定工具 + 指令驱动扫描

落地切片（真实存档联调前置）：先把"信号灯 = 摆放出来的 MTR 灯光块"这件事登记到引擎，
后续 A2 显示/进路 × 闭塞才读得到信号机。

- 登记表：引擎 Simulator.mmtrSignals（持久化 mmtr-signals.json），条目 = (x,y,z,
  angle, aspects, mode, target)。mode AUTO = 按摆放自动推断读取对象；BOUND = 覆盖绑定，
  target 为被读轨道 hex。绑定不替代几何推断，只是给"放不开/放不下/要读别的信号"的灯
  一条显式通道（用户场景：第一盏灯读正线 160 限速信号，第二盏灯放 2 格外读另一侧）。
- 覆盖绑定工具（游戏内）：新物品 mtr:signal_binder（外观套用木铲，非放置类，注册
  CreativeModeTabs.CORE）。两击流程：第一击必须是信号灯块（BlockSignalBase 全家族，含
  2/3/4 灯与臂板信号机），第二击必须是铁道节点（BlockNode，含其内连续移动子类）。
  角取自灯块 state（FACING/IS_22_5/IS_45 → 与渲染同规则），aspects 按灯族类名（4Aspect=4,
  3Aspect=3, Semaphore2=3, 其余 2）。上行 op：engine MmtrSignalsOp（hasNode=true）→
  Simulator.mmtrSignalBindAtNode：在点击节点邻接轨道中挑与灯朝向最贴合的轨道并登记
  BOUND。灯与节点的 90° 偏移语义是活调点，实机验证时如读错轨翻转 bind 的 ±90。
- 指令驱动扫描（WEB 指令栏 → 无周期扫描）：WEB 推送指令到引擎队列（mmtr-command），
  fabric 端 MmtrCommandExecutor（END_SERVER_TICK 轮询，每世界对应 sim）执行
  signals scan：遍历已加载区块的方块实体找信号灯，AUTO 登记/更新（BOUND 条目保留
  不动）。已加载区块集合由 MmtrChunkTracker 的 CHUNK_LOAD/UNLOAD 事件维护（vanilla
  不直接暴露"当前加载区块"列表），只在指令到达时读取。玩家不在线则只扫在线时的加载区。
- 反馈：指令结果写回引擎 mmtrCommandLog（WEB 指令栏可见），如
  "[signals] 扫描完成: 找到 N 个信号灯, 新增 M 个 AUTO 条目"。
- 手工获取：/give @s mtr:signal_binder；WEB 面板指令栏输入 signals scan。
