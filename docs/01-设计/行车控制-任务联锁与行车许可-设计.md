## 1. 结论摘要（先读这段）

1. 三者结合的**链条已经存在**并已在跑：任务 → planner → `MmtrRoute` → `MmtrPointAuthority`
   → 走行闸门 → 物理道岔 → 灯显 → 镜像/网页。**不需要新建架构。**
2. 但链条上有**两处断裂**，它们正是"三者没有真正互相约束"的全部原因：
   - **断裂一：信号不控车。** 灯色在全仓库只有一个消费者是"影响行车"的 —— AWS 告警
     （`Vehicle.java:3033-3037`）。停车一律由 `computeMmtrBlockStopM`（`Vehicle.java:3098`）的
     四条规则决定，**没有一条读灯色**。红灯目前是一块显示屏。
   - **断裂二：道岔许可按"进向"发，物理上互斥的两份许可能同时成立。**
     `MmtrPointAuthority` 的键是 `(节点, 进向轨)`（`:58-60`），而 `MmtrRouteRegistry.refresh`
     判 SET 只看 `isGrantedTo(...)`（`:79-88`）。两列车从不同进向申请同一处道岔 → 两个键 →
     **都 GRANTED → 两条互斥进路同时报 SET**；而物理位置只有一个，
     `Simulator.mmtrSyncTurnoutPositionToGrant`（`:787-802`）按固定数组顺序 `{stem, far, branch}`
     取第一个有授权的进向 —— **仲裁权落在数组下标上，而不是计划或到达顺序**。
     走行侧靠 `continuationFrom(...) == null` 的闸门兜住（车停在岔前，**不会脱轨**），
     所以症状不是碰撞，而是**咽喉僵持 + 进路状态说谎**（两条互斥进路都说自己 SET）。
3. 因此选定**方案 A**：先把断裂二的物理唯一性补上（这是现存真 bug），
   同时把断裂一补成"信号 → 行车许可"（`MmtrMovementAuthority`），让红灯第一次真正让车停下来。
   顺带做**方案 C** 的收口（新增语义写成显式阶段，避免 notes/114·115 那类"三层各持一份视图"复发）。
   方案 B（时刻表预排进路）是"任务固定"真正的红利，**后置**。
4. **多车争一处道岔**的解法不在"仲裁得更聪明"，而在三点（2026-09-13 拍板）：
   **咽喉原子获取**（咽喉区内道岔一次全拿到，否则全部退回）+ **离线敌对进路表** + **全自动裁决**。
   现状是**逐岔申请且失败不回滚**（`MmtrRunPlanner.java:768-781`）+ 授权每 tick 续期
   （`Vehicle.java:481-487`）⇒ **hold-and-wait + 循环等待 = 永久死锁**，比"状态说谎"严重得多。
   **且因为玩家只有司机一个角色、没有调度员，裁决链上不允许存在"等人工"的环节。** 见 §5。

## 2. 现状：链条已在，两处断裂

### 2.1 已经通的链条（每环都有代码锚点）

```
作业单 MmtrConsistJob.steps[]
  └─ MmtrJobScheduler（每 tick 推进步骤，实例化 MmtrMission）
       └─ Vehicle.mmtrMotionSelfArmMission            (Vehicle.java:506)
            └─ MmtrRunPlanner.planToRail               → Plan{routeRailHexes, forkOps, forkMeters, stopCumulativeM}
                 └─ Vehicle.armMmtrPointRun            (Vehicle.java:589)
                      ├─ 清本车 fork 的人工位          (:611-613)
                      ├─ 发布 MmtrRoute（先发布→后申请，申请期=PENDING）(:625-630)
                      └─ MmtrRunPlanner.requestForkOps → MmtrPointAuthority.request
                                                       (MmtrRunPlanner.java:763-776 / MmtrPointAuthority.java:68)
                           └─ 每 tick 刷新授权窗口      (Vehicle.java:481-497)
                                └─ MmtrRouteRegistry.refresh → SET / PENDING   (:58-89)
  ── 走行 ──
  MmtrForkElection.elect                                (MmtrForkElection.java:60-138)
       ├─ Simulator.mmtrSyncTurnoutPositionToGrant（联锁扳动，同步调用）(:787-802)
       ├─ 物理闸门 continuationFrom(via, position) == null → 停在岔前 (:94-96, :130-136)
       └─ 取值顺序：人工位 → 本次授权 → 任务目标 → 唯一续行 (:105-129)
  ── 显示 ──
  MmtrDirectionalBlockService（v2 灯到灯区间，读物理道岔位置）→ MmtrSignalAspect（进路×闭塞投影）
       └─ 镜像 PacketMmtrRoutes → 客户端 RenderSignalBase ／ 网页 mmtr-signals ／ signal why
  ── 停车 ──
  Vehicle.computeMmtrBlockStopM 的 min 链 (Vehicle.java:3098-3160)
       (1) 同轨/编组体遮挡  (2) 下一闭塞区间被占 nextSectionStopM (:3347)
       (3) ① 区间出口是选不出腿的道岔 nextSectionAuthorityStopM (:3233)
       (4) ② 岔区清限 junctionClearanceStopM (:3167)
```

### 2.2 断裂一：信号不控车

`MmtrSignalAspect.Aspect`（`RED / SINGLE_YELLOW / DOUBLE_YELLOW / GREEN`）在全引擎的消费点：

| 消费点 | 用途 | 是否影响行车 |
| --- | --- | --- |
| `SystemMapServlet:565` | 网页灯色 | 否（显示） |
| `Vehicle.java:3033-3037` | **AWS 触发**（非绿且进入 75 m 触发带） | 半 —— 只影响告警/SPAD |
| `MmtrInterlockReport:68` | `interlock` 诊断 | 否 |

**结论：灯色不进入任何停车规则。** 红灯之所以"看起来能停住车"，是因为闭塞占用规则 (2) 恰好
与"保护区间被占 → 红灯"同源；而**因进路未设、道岔位置不对而变红的那些灯，对车没有任何约束力** ——
车会一路开到岔前才被闸门 (3) 挡住。这正是"任务没有被信号约束"的准确含义。

### 2.3 断裂二：权限层按进向发许可

| 事实 | 位置 |
| --- | --- |
| 授权键 = `x,y,z\|viaRailHex`（**方向视图**） | `MmtrPointAuthority.java:58-60` |
| 进路 SET 判据 = 每个 fork 的 `isGrantedTo(node, via, owner)` | `MmtrRouteRegistry.java:79-88` |
| 物理位置仲裁 = 按 `{stem, far, branch}` 顺序取第一个有授权的进向 | `Simulator.java:787-802` |
| 物理闸门（兜底，安全侧） | `MmtrForkElection.java:94-96, 130-136` |

**可达场景**（dev 世界 8 处单开道岔上真实存在）：
A 车从正线来要"去岔股"（需要位置 1）、B 车从岔股来要"回根部"（需要位置 0）。
两者进向不同 → 两个键 → **都被 GRANTED → 两条进路都 SET**；物理位置只能是一位，
数组顺序里 `stem` 在前 → A 赢。B 的 `continuationFrom(branch, 0) == null` → B 停在岔前。

- 安全侧：**没有脱轨/碰撞风险**（闸门兜住了）。
- 一致性侧：**B 的进路仍然报 SET、仍然占着授权**，运营台/`mmtr-rails.aspects` 投影说两列车都有进路；
  `MmtrRouteRegistry` 的 SET 与物理事实矛盾。
- 症状：咽喉僵持（谁赢由数组下标决定，不由计划决定）+ 诊断说谎。
  notes/115 §5.1 那个"侧线 2 的出库车停在库门口 23.18 m 处 awaiting operator/task"就是这条路径的影子。

## 3. 方案与取舍

### 方案 A：信号升级为行车许可 + 道岔物理唯一持有者（**选定**）

| 件 | 内容 |
| --- | --- |
| A-1 | `MmtrPointAuthority` 加**物理层**：一处道岔只有一个持有者，进向请求先翻译成"位置需求"，互斥需求在该道岔上排队 |
| A-2 | `MmtrRouteRegistry.refresh` 判 SET **追加**"每个岔的物理位置就是我这条腿要的那一位"，PENDING 理由点名"物理道岔被 vX 按在位置 N" |
| A-3 | 新增 `MmtrMovementAuthority`（行车许可，纯派生）：`aspect → {目标轨, 目标距离, 目标速度}`，进 min 链 |
| A-4 | `computeMmtrBlockStopM` 新增规则 **(5) 行车许可停车点**：目标速度 0 → 停在目标前 ε |
| A-5 | 任务侧接线：`MmtrRoute.Kind` 由**任务类型**决定（不再由"有没有调车授权"反推）；`MmtrShuntAuthority` 并入同一联锁 |
| A-6 | **咽喉原子获取 + 敌对进路表**：咽喉区内的道岔一次**原子**申请（全拿到才 SET，否则**全部退回**），互斥关系由**离线算好的敌对进路表**判定；分段释放保留 |

- **代价**：中。改 4 个类 + 1 条停车规则 + 1 个新对象；动 S1 会碰到既有用例期望值。
- **收益**：修掉现存真 bug；信号第一次真正控车；"三者互相约束"闭环成立。
- **风险**：新增停车规则可能让"手动自由驾驶"也被红灯管住（见 §9 开放问题 1、2；其中问题 1 是本设计最大的未定项）。

### 方案 B：时刻表预排进路（"任务固定"的红利，**后置**）

既然任务集与计划时刻**静态已知**，就不必运行时抢道岔：

1. 新增 `MmtrTimetablePlan`：作业集 → 每车每步的 `{进路轨序, 岔需求, 计划时间窗}`（`MmtrTask.earliestMs/dueMs`
   已经带着时刻，`:31-34`，数据现成）；
2. **在道岔上解冲突**（道岔=机器，任务=工件）：同岔冲突按 `(计划时刻, jobId)` 定序，给每车一个预约槽；
3. 授权接口从"逐岔机会式申请"（`MMTR_APPROACH_LOCK_METERS = 120 m`，`Vehicle.java:201`）改为
   `reserve(进路, 时间窗)`；SET = "在窗口内已排定 **且** 物理位置就位"；
4. 运营台天然得到"**计划进路 vs 实际进路**"对照（`任务系统…设计.md §4` 的时间表视图已经写好）。

- **代价**：大 —— 要写冲突求解 + 晚点重排。
- **收益**：仲裁从"数组下标"变成"计划"；确定性、可复现、可优化咽喉利用率。
- **风险**：晚点漂移 → 必须定"计划优先 + 到达序兜底"的退化策略，否则会僵。

### 方案 C：把隐式顺序写成显式阶段管道（**随 A 做**，防复发）

今天同一件事在四处互相穿插：`Vehicle.armMmtrPointRun`（:589）、`Vehicle.replenishForkRequests`（:642）、
`Simulator.mmtrSyncTurnoutPositionToGrant`（:787，**还被走行内联调用**）、`Vehicle.tick` 里的
`routes.refresh`（:495-497）。notes/114 与 115 反复踩的"三层各持一份视图"就是它造成的。

把每个 tick 写成一个声明式阶段序列，每阶段产出下一阶段的输入：

```
任务意图 → 进路规划 → 道岔预约 → 物理位置 → 进路 SET/PENDING
        → 灯显 → 行车许可 → 停车点 → 走行
```

- **代价**：重构而非新功能；必须保证 541 例不破。
- **收益**：这类 bug 不再复发；`signal why` / `interlock` 可按阶段输出（诊断说谎已被 notes/115 记为
  "比没有诊断更坏"，且已发生三次）。

### 对比与选择

| | A | B | C |
| --- | --- | --- | --- |
| 修掉现存真 bug | ✅ | ❌（只在 B 完成后才被覆盖） | ❌ |
| 信号真正约束任务 | ✅ | ✅ | ❌ |
| 利用"任务固定" | ❌ | ✅✅ | ❌ |
| 改动量 | 中 | 大 | 中 |
| 现在就能做 | ✅ | 需 A 的地基 | 建议随 A |

**选择：A（本片）+ C 的显式阶段（随 A）+ B 后置。**
理由：没有 A，B 只是把"任意仲裁"换成"计划仲裁"，而信号仍然不控车 —— 三者互相限制还缺一角。

## 4. 方案 A 的设计

### A-1 道岔：物理唯一持有者

现状 `MmtrPointAuthority` 是**纯方向视图**（键含 `viaRailHex`）。物理位置已由
`MmtrTurnout`（notes/115）唯一化，但**权限层还没跟上**。

改法：

- 授权表新增节点级条目：`(节点) → {holder, position}`，与现有 `(节点,进向) → {holder, leg, queue}` 并存；
- `request(x,y,z,via,owner,leg,...)` 内部先把 `(via, leg)` 经 `MmtrTurnout.positionForLeg(via, leg)`
  翻译成**位置需求**（`Simulator.java:939-948` 已有同源实现）；
- 同一道岔上第二个持有者的**互斥**需求 → `QUEUED`（在道岔上排队，不是在各自进向上排队）；
  "相容"需求（同一位置）→ `GRANTED`；
- `passed()` 推进道岔队列，`releaseAll(owner)` 一并清节点级持有；
- 物理位置由**持有者**决定，不再由 `{stem,far,branch}` 数组顺序决定（改 `mmtrSyncTurnoutPositionToGrant`）。

> 说明：`positionForLeg` 对"物理上不存在的组合"返回 `Integer.MIN_VALUE`（notes/115 §9），
> 这类请求在本层**直接拒绝**，不再进队列。

### A-2 进路：SET 判据纳入物理位置

`MmtrRouteRegistry.refresh` 现在只问"我的每个岔有没有授权给我"。追加一条：

```
SET ⟺ ① 每个未越过的 fork 都 grantedTo(myOwner)
     ∧ ② 每个未越过的 fork 的物理位置 == 我这条腿需要的那一位
```

- ② 让"两条互斥进路同时 SET"在结构上不可能；
- PENDING 理由分类点名（复用 notes/76 的点名风格）：
  `物理道岔 -67,-60,-139 被 v12 按在位置 1（岔股开放），本车需要位置 0（正线贯通）`；
- `crossedForkKeys` 的分段释放语义（`MmtrRoute.java:126-146`）不变 —— 越过的岔不再参与 ①②。

### A-3 信号 → 行车许可（`MmtrMovementAuthority`）

新增 `org.mtr.core.mmtr.signal.MmtrMovementAuthority`，**纯派生、不持有状态**（与 `MmtrRoute`
"只读派生"同一纪律）：

- **输入**：本车 + 它的 `MmtrRoute` + 灯显（`MmtrDirectionalBlockService` / `MmtrSignalAspect`）
  + 闭塞（`nextSectionStopM` 已有）；
- **"下一架管我的信号"** = 沿本车进路走，第一盏 FACING 本车行进方向的灯（复用 v2 的
  `resolveLegByPointState` 选腿 + `headingOf` 角度语义，notes/104/114，不另写一套）；
- **输出**：`{aspect, targetRailHex, targetDistanceM, targetSpeedKmh, reason}`；
- **出口**：feed 每车 `authority{}`；驾驶室 HUD；网页；`signal why` 增一节。

**映射规则**（用户口径，§6 有行为表）：

| Aspect | 目标 | 目标速度 |
| --- | --- | --- |
| `RED` | 该信号所在位置（进路入口/保护区间起点） | **0** |
| `SINGLE_YELLOW` | **下一架**信号位置 | 该信号允许速度（通常 0 ⇒ 能停住） |
| `DOUBLE_YELLOW` | **再下一架**信号位置 | 同上（预告，不强制限速） |
| `GREEN` | 无约束 | 轨限速 |

**与 LZB 的关系**：上游设计 §1.2 已定"运行时允许速度永远 = `min(轨限速, 动态约束, 目标距离制动曲线)`
—— **信号配合发生在 min 链**"，并把"信号降级（红灯=目标速度 0）"列为**动态约束**这一层的首个成员。
本设计就是把它真正落地成一个对象；LZB 连续曲线是 min 链的另一支，**不合并、自然取小**。

### A-4 走行：`computeMmtrBlockStopM` 新增规则 (5)

在 `Vehicle.java:3098-3160` 的 min 链末尾加：

```
(5) 行车许可停车点 signalAuthorityStopM()
      authority.targetSpeedKmh == 0 → stop = min(stop, 到 target 的距离 - MMTR_BLOCK_NODE_EPS_M)
      authority.targetSpeedKmh  > 0 → 作为速度钳制（min 链速度侧）—— 本片可先只做 0 的情况
```

并像 `mmtrSectionAuthorityHold`（`:151-155`）那样存一个新的标志与理由串，供 HUD/诊断读出
"为什么停"。

> **诚实的边界**：规则 (2)（下一闭塞区间被占）在功能上**已经**实现了"占用类红灯停车"。
> 规则 (5) 的真正增量是**非占用类红灯**：进路 PENDING、道岔物理位置不对、灯色因进路而降级。
> 换句话说，"红灯停车"有一半早已以闭塞形式存在；本片补的是**联锁那一半**。

### A-5 任务侧接线

现在"任务 → 进路"是**隐式**的：`MmtrJobScheduler` 造 `MmtrMission`，
`Vehicle.mmtrMotionSelfArmMission`（:506）里 planner 算完，
`armMmtrPointRun`（:589）**顺带**发布 `MmtrRoute`，而 `Kind` 是由"有没有调车授权"**反推**的
（`:627-629`）。改成显式：

1. **任务层产出进路意图**（`targetRef` + 期望的动作类型），planner 只负责几何与岔需求拆分；
2. **`Kind` 由任务类型决定**：`DriveToConsistTask` / `CoupleTask` / `UncoupleTask` → `SHUNT`；
   `DriveToPlatformTask` / `DriveToSidingTask` → `MAIN`；不再反推；
3. **`MmtrShuntAuthority` 并入同一联锁**：SHUNT 进路同样要过物理道岔预约与 A-2 的 SET 判定，
   区别只在"灯显走副显示、可越过闭塞占用"。现在它是**绕过 S1 占用的第二套授权**
   （`Vehicle.java:551-562` 的 `grantRoute`），与主进路并行 —— 这是三者结合里第二处需要收口的地方。

### A-6 咽喉原子获取与敌对进路表（**多车争用的正解**）

**问题**：大系统里多车争一处道岔是常态。但真正的失败模式不是"谁先走"，而是：

1. **状态说谎**（断裂二）：互斥的两份许可同时成立，两条进路都报 SET；
2. **永久死锁**（更严重）：`requestForkOps`（`MmtrRunPlanner.java:768-781`）逐个岔申请、
   失败的只置标志**不回滚**，配合 `Vehicle.armMmtrPointRun` 把接触窗口内（120 m）的岔**一次申请**
   （`:597-605`）与每 tick 续期（`:481-487`，`untilMillis = now + 10 min`）⇒
   **部分持有 + 等待其余（hold-and-wait）+ 授权永不超时**。
   具体：A 车进路要 `[P, Q]`、B 车进路要 `[Q, P]` ⇒ A 持 P 等 Q、B 持 Q 等 P，**两列车永久卡死，不会自解**。

**真实铁路的做法**（照抄即可）：联锁**不在道岔这一级仲裁**，它的仲裁单位是**进路**，且进路是**原子**的。

| 机制 | 作用 |
| --- | --- |
| 仲裁单位 = 进路 | 信号员排列一条进路，联锁把它当**一件事**完成 |
| **原子性** | 任何一处道岔要不到 ⇒ 整条进路不设、已锁的**全部退回**、信号保持红 ⇒ **构造上不存在 hold-and-wait** |
| **敌对进路表** | 哪些进路互斥是**离线算好的表**，运行时只查表不推理 |
| 同向跟随不算敌对 | 交给闭塞与间隔解决（notes/82 已定），不进联锁 |
| **分段释放** | 越过一处道岔即释放该处，进路在车前方保持 SET（`crossedForkKeys` 已有） |
| 接近锁闭 | 列车接近后进路不许取消（或延时）——保护"已给出的许可不被突然收回"，**不用于减少争用** |
| **队列在信号外** | 拿不到进路的车停在**保护这条进路的信号外**，不进入咽喉 |
| 人工最高 | 保留，但**降级为运维通道**（见 §5） |

**本设计的取法**（用户 2026-09-13 拍板：**咽喉原子**）：

- **咽喉区**（度 ≥ 3 节点的净空区及其中间的道岔）内的道岔需求：**一次原子申请**
  —— 全 GRANTED ⇒ SET；任一处 QUEUED ⇒ **全部退回**，进路 PENDING，灯红，车停在信号外排队；
- **咽喉外**：仍按接近窗口逐段申请（不提前占远端岔，保住利用率）；
- **分段释放**保留：越过即释放，咽喉尽快腾出；
- 互斥判定走**敌对表**，判据三条（第四条交给闭塞）：
  ① 同一道岔需要不同位置；② 共用任一根轨；③ 侧面防护区（`MMTR_JUNCTION_CLEARANCE_M = 10 m`）重叠；
- **回滚必须在同一 tick 内完成**（原子性不能跨 tick，否则又会退化成 hold-and-wait）；
- 效果：**断裂二与死锁同时消失**，而且是结构性消失，不是"检测到再解开"。

### A-6 的规模上限与真正的规模化答案

运行时仲裁只能决定**顺序**，**不能创造通过能力**。大系统里咽喉与单线区段是瓶颈资源，
所以层 5 才是规模化的真答案：**用时刻表把冲突提前消掉**（同向最小间隔、咽喉无冲突径路分配、
单线交会点预先定）。对固定任务集这只是个很小的调度问题（几十处道岔 × 几十列车），完全可解
—— 这就是方案 B / T5。届时运行时的"抢"退化为**偏差处理**：正常按计划走、不争；
只有晚点才动用 §5 的自动裁决链。

## 5. 无调度员约束：玩家只有司机一个角色

**用户 2026-09-13 拍板**：`人工锁 > 计划时刻 > 到达序 > 防饿死` 里"人工"这一档**保留**，
但**我们不能有调度员——玩家仅有司机这一个角色**。这条约束的连带后果必须写清：

### 5.1 裁决链（定稿）

```
人工锁（运维/排障通道，默认不存在）
  > 计划时刻（任务固定 ⇒ 主裁决）
  > 到达序（FIFO 兜底）
  > 防饿死（等待超时提升优先级）
```

**关键：链上不允许存在"等人工"的环节。** 没有调度员 ⇒ 任何"需要人来解锁才能继续"的状态
都是**永久停摆**。

### 5.2 必须清查的死等（无调度员就解不开）

| 位置 | 现状 | 要求 |
| --- | --- | --- |
| `Vehicle.java:563-577` | self-arm 失败 ⇒ 任务停在 ASSIGNED，**每 tick 重试直到 grants 到位**（注释点明"operator unlock / the other train's release"） | "另一列车释放"是自动的（`passed()` 推进队列）✅；"operator unlock"这条路**不存在了** ⇒ 必须保证所有阻塞源都能自动解开 |
| `Vehicle.java:1397` | 日志与状态文案 `awaiting operator/task` | 文案与语义都要改：等待理由只能是"等前车越岔 / 等计划时刻 / 等信号"，不能是"等 operator" |
| `MmtrPointAuthority.java:244` | `operator park holds the point; queue waits for unlock` —— 被锁的道岔**队列永不动** | 人工锁降级为**排障通道**：必须（a）状态可见、（b）可一键全清、（c）建议加 TTL；否则一次遗留的锁 = 永久停摆 |
| `MmtrJunctionState.java:92-94` | 非单开岔口（度 4 交叉 / 三岔口）的"岔口没人决定"规则，靠**引擎默认预置行**或授权来满足 | **引擎默认预置就是那个"决定"**，是这套无调度员世界的关键兜底，**不得删除**（单开道岔已在 notes/115 §6.1 跳过该规则） |

### 5.3 司机角色的边界（需要落到玩法层）

- **准入门槛（新，由"玩家行为全在任务内"直接推出）**：**无任务不得操纵**。
  现在 `MmtrDriveAccess.canControl`（`:58-70`）只看"坐司机座 + override 归属"，
  不看任务 ⇒ 任何人都能开一辆没有任务的车。必须补这道闸，否则"行为限制在任务内"只是意图。
  与之配套：玩家执行任务时，引擎要把该任务**转成进路意图**并走同一条
  planner → 授权 → 进路 → 灯显 的路径（= T4 的要求 A）。
- **玩家不扳岔，联锁扳岔** —— 与立项时定的"任务判定该往哪走 → 直接操作相关道岔"一致。
  现在网页有「0 正线贯通 / 1 岔股开放」按钮、游戏内有 `point set` 指令
  （`tools/check-web-turnout.ps1` 就是在测这条路径），这些应**明确定位为调试/运维通道**，
  而不是玩家能力。
  <br>**已实现（notes/130，2026-09-14）**：意图（人工位 / 授权 / 任务目标）与道岔位置不一致时，
  联锁**按意图扳岔**（`MmtrForkElection` → `Simulator.mmtrThrowTurnoutForIntent`；人工锁着不扳、
  有人物理持有不扳）。调度通道的 `point set` 同时**锁定**该道岔（重启仍生效，`point unlock` 释放）——
  这正是 `道岔系统-方向感知与多级控制-设计.md` §R3 早就写的"人工可覆盖自动设置并锁定"。
- 玩家作为司机唯一的人为干预面是**驾驶行为本身**（开/停/执行任务内的作业），不是排列进路。
- 注意现存机制 `Vehicle.java:611-613`：任务武装时会**清掉本车进路各岔的人工位**。
  在无调度员的世界里这是**正确**行为（任务优先于遗留的人工设置），保留。

1. ~~无任务的手动/自由驾驶，怎么过岔？~~ → **已解决（用户裁定 2026-09-13）**：
   **玩家的一切行为都在任务内**，不存在无任务的自由驾驶，所以"没任务就没进路"的空洞**不成立**。
   —— 但这句话**现在还没在代码里成立**，它拆成两条必须落地的前置要求：
   - **要求 A：进路/授权必须接玩家任务。**
     `mmtrMotionSelfArmMission` 目前**只在 `Executor.AUTOPILOT` 时调用**（`Vehicle.java:425-427`），
     `MmtrMissionControl.java:77` 同样只对 AUTOPILOT 规划 ⇒

   - **要求 B：准入必须设闸。** `MmtrDriveAccess.canControl`（`:58-70`）的判据只有

     **设计意图，不是被强制的规则**：任何人拿到钥匙坐进驾驶室，就能开一辆没有任务的车 ⇒ 又回到自由驾驶。

2. **手动驾驶是否也受红灯约束？** → 在"玩家行为全在任务内"的前提下**自动成立**：
   **受约束**——玩家开的车一定有进路，进路 PENDING 就等于红灯 = 停车。
   （调车授权 / 副显示内仍豁免；车场无灯区段天然不受影响。）
3. **人工锁要不要加 TTL？** 无调度员的世界里一次遗留的锁 = 永久停摆。
   建议：TTL + 一键全清 + 状态可见（见 §5.2）。
4. **黄灯要不要限速？** 本设计按用户口径只做"确认"。
5. **晚点漂移的重排策略**（T5）：计划优先 + 到达序兜底，还是到点重排整张表？
