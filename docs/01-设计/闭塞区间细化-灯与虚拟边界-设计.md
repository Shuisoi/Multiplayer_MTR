# 闭塞区间细化 · 信号灯与虚拟边界（设计 v1 · 待拍板）

> 触发：2026-09-09 用户选定方向 A（承接「区间是以信号灯划分的么」一问）。
> 现状一句话：**一根轨 = 一个闭塞分区**；本设计把它升级为**由信号灯/虚拟边界切分的区间**。
> 状态：**设计待拍板**（§8 三个问题），拍板后按 §6 分片实施。

## 2. 问题（为什么值得改）

1. **长轨粒度粗**：实机 aassdd 有一根 187 m 的轨；它被占就整段关闭，后车被拦在上一根轨末端——保守到浪费，且与司机看到的"两灯之间"无关。
2. **灯与区间脱钩**：灯放在哪、照哪条轨，都不影响分区；运营台/司机无法把"这一段"与"那架灯"对应起来。
3. **下游连带保守**：AWS 的告警边界、LZB 的目标距离都取 `mmtrBlockStopM`，整轨封锁让这两个数都偏保守。
4. **进路释放也按轨**：S5 的进路锁虽然按轨序，但"车尾清岔/清轨"的判定同样是整轨。

## 3. 目标 / 非目标

**目标（v1）**
- 区间 = **同一方向上相邻两盏灯之间的轨段**；无灯处退化为整轨；
- **长轨**在无灯处按阈值切**虚拟边界**，得到固定长度的短区间；
- S1 停车判定、信号显示、AWS 告警边界、LZB 目标距离**改读区间**；
- 区间可被运营台观察（feed），便于实机核对。

**非目标（v1 明确不做）**
- 不把道岔权威、进路锁、调车授权的**单位**从"轨+节点"改成区间（它们依赖轨几何与节点语义；区间只做**占用/显示**的粒度）；
- 不做"按灯位几何投影到任意弧长"的完整版（见 §5，v1 用节点绑定，几何投影留 B4）；
- 不改 MTR 的轨/方块数据，不动存档格式。

## 4. 数据模型

```text
MmtrBlockService（Simulator 持有，rails-signature + signals-signature 双门控缓存）
  ├─ MmtrBlockBoundary { railHex, arcFromEntryM, kind = NODE | SIGNAL | VIRTUAL, sourceKey }
  ├─ MmtrBlock         { id, railHex, arcFromM, arcToM, entryNode, exitNode }
  └─ 查询
       blockAt(railHex, arcM)                  → 该点所在区间
       nextBlockAhead(railHex, arcM, toward)   → 前方第一个区间的边界距离（walker 空间）
       occupant(blockId)                       → 占用者（读现有 per-rail 占用树投影）
```

**边界来源（按优先级，同一轨内按弧长排序）**

| 来源 | 何时产生 | 说明 |
| --- | --- | --- |
| `NODE` | 总是 | 轨两端节点（现状语义，保证岔区/站台/股道各自成段） |
| `SIGNAL` | 该轨被某盏登记灯绑定（`MmtrSignalRegistry.target`）时 | v1 取**灯绑定的那个节点**作为边界（见 §5 方案 B） |
| `VIRTUAL` | 轨长 > `LONG_RAIL_M` 且相邻边界间距 > `MAX_BLOCK_M` 时 | 按 `MAX_BLOCK_M` 等分（末段可短），保证最小段长 `MIN_BLOCK_M` |

**占用投影**：沿用现有 per-rail 占用树（不改写入端），区间占用 = 该区间弧长窗口与树上外部区间相交。这样**写入端零改动**，只有读取端换粒度。

## 5. 灯 → 区间的映射（本设计的关键取舍）

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **B（推荐 v1）节点绑定** | 灯通过 `MmtrSignalRegistry.target` 绑定到轨；区间边界取**该轨的入口/出口节点**（由灯朝向决定） | 与现有登记表语义一致、零几何歧义、实现小；覆盖"灯放在岔/站台旁"的实机常态 | 灯若摆在轨中段，效果等同现状（该轨不切分） |
| A（几何投影） | 灯位投影到绑定轨的弧长（最近点），朝向决定方向 | 最贴近现实：灯摆哪就切哪 | 灯可能离轨很远/朝向模糊/一轨多灯；需要容差、去重、回退策略；区间随灯移动而变，缓存失效面更大 |

**v1 建议 B**：先把"长轨虚拟切块 + 区间化读端"这套基础设施落地（收益立刻可见：跟车距离、LZB 目标距离），A 作为后续增量（B4）——它只影响 `SIGNAL` 边界的弧长来源，不影响其它部分。

## 7. 兼容与回归清单（改之前先跑）

- `MmtrMotionBlockingTests`（S1 跟车/对向/手动等待）——**B2 实测：无灯轨图期望值不变**（一根轨=一个区间，
  与改前完全一致）；只有**登记了灯**的轨会变，且方向与本文原先的猜测相反：后车停在**灯前**（区间边界），
  比改前的"贴尾 2 m"更**远**——这正是闭塞的意义（一区间一列车）。"更贴近前车"只在**同一区间内**成立

- `MmtrAwsWarningTests`（告警边界来自 `mmtrBlockStopM`）、`MmtrLzbSupervisionTests`（目标距离）；

## 8. 拍板结果（2026-09-09 用户）

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 长轨虚拟切分阈值 | **不按长度切**：区间一律按**信号灯**切，"不用管他长"（300 m 无灯轨 = 1 个区间） |
| 2 | 灯-区间语义 | **直接实现几何投影**（它是"节点绑定"的超集：灯贴节点时投影=节点，二者一致） |
| 3 | 区间是否成为进路锁/调车授权单位 | **否**，v1 只用于占用/显示/AWS/LZB |

据此修订：§4 的 `VIRTUAL` 边界**不做**（`BoundaryKind` 只有 `NODE` / `SIGNAL`）；§5 直接走方案 A。
