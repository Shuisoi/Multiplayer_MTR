# 闭塞区间：两层模型（L1 轨道区间 + L2 行车区间）· 设计

> 状态：**当前唯一有效的闭塞区间模型**（2026-09-15 用户拍板，实施记录见 `notes/166`）。
> 本文**取代**：`闭塞区间-灯到灯跨轨有向模型-设计.md`（v2）与
> `闭塞区间细化-灯与虚拟边界-设计.md`（v1）。两份旧文档只作历史。

## 1. 一句话

> **轨道本身不带方向。**
> **Level 1 轨道区间**：切点**只由信号灯**产生，无方向、双向共用，**占用判定只在它上面做**。
> **Level 2 行车区间**：按行车方向、从一架灯到下一架**同向**的灯；**没有任何信号灯的连通块整块作为一个大区间**。

用户原话（触发起因）：

> 「单根轨道是双向的，也就是说轨道区间是双向的，但实际上在逻辑层面，无论是上行信号灯还是下行信号灯，
> 都可以将轨道切成"轨道区间"，每个轨道区间端点都会在上行或下行有一个信号灯，这时候就可以根据行车方向
> 以及带有同向信号灯的端点组成行车区间。」

现实对照（铁路通识，用户确认"基本思想相同"）：

| 本文 | 现实 |
| --- | --- |
| L1 轨道区间（无方向） | **检测区段**（轨道电路/计轴区段）：谁压上都报占用，与方向无关 |
| L2 行车区间（有方向） | **闭塞分区**（block section）：边界是**停车信号机**，灯立在**分区入口** |

细节差异（现实比模型多的东西，写下来免得被当成缺陷）：现实里检测分界的来源**不只是灯**
（绝缘节、道岔区段、道口、长分区内的中间区段都可能无灯）；**预告/远方信号机不是分界**；
还有 **overlap（过走保护距离）**；**半自动/移动闭塞**根本没有固定分区。

## 2. 三条裁定（2026-09-15）

| # | 问题 | 裁定 |
| --- | --- | --- |
| 1 | 旧的两套实现怎么办 | **v1（`MmtrBlockService`/`MmtrBlockReport`）与 v2（`MmtrDirectionalBlockService`）整层删除**，不留任何回退分支 |
| 2 | L1 的切点由什么产生 | **只由灯**（上行灯、下行灯都算） |
| 3 | 没信号灯的地段 | **整块作为一个大区间**（"之后编程不按当前世界来看"）；这条**反转**了 notes/157 的"无灯轨不属于任何区间" |

## 3. Level 1：轨道区间（`MmtrSectionService.TrackSection`）

**切点 = 灯在它保护的每根轨上的投影**（`NODE_CUT_TOLERANCE_M = 1 m` 之内算"站在那个节点上"，
切的是节点而不是轨内一点；实测：MTR 灯方块中心 = 方块坐标 + 0.5，立在接头上的灯投影落在弧 0.5 处）。

段沿**唯一续轨**推进，遇三类情况收口：

1. 切点；2. 分叉/合流节点（度 ≠ 2）；3. 线路尽头。
第 2、3 条**不是新增的切点来源**，而是"段是线性的、不能分叉"的推论（现实里也如此：道岔区段自成一段）。

**不变量**：每一点**恰好**属于一个轨道区间（真正唯一划分，双向共用同一份）。
既有用例原来只断言 `owners <= 1`（名字却写着 `WithoutGapsOrOverlaps`）—— 天窗抓不到，本层补齐为 `== 1`。

**占用**：`isOccupied(TrackSection, trees, excludeVehicleId)` —— 判据在全仓只有这一份实现
（`overlapsEnough`：重叠要占到**车长的一半**再减一格松弛）。占用是物理事实，**与行车方向无关**。

### 3.1 占用粒度：在 L1 判定，**再扩大到 L2**（用户 2026-09-15 的口径）

> 「虽然区间层面是双向的铁路，但是铁路只有一根，所以区间的"占用"判断粒度是依据**轨道区间**的，
> 然后**扩大至行车区间**。」

- **物理事实**：一根轨就是一根轨，两个方向共用它 —— 所以"被占/没被占"这件事**只在 L1 上成立**，
  判据里没有任何"朝哪走"的入参（`isOccupied(TrackSection, …)` 没有 direction 参数）。
- **L2 的被占 = 它的成员（轨道区间）里任意一段被占**：`MmtrSectionService.isOccupied(Section, …)`
  先把每个 span 归到它所在的 L1 段（`trackSectionsOf(Section)`，边界对齐所以每 span 恰好一段），
  再问那一段 —— 这就是"扩大"。多个成员里任一段被占 ⇒ 整段行车区间被占。
- 因此：**同一段物理轨在两个方向的区间里读数一致**（同一份 L1 状态），不会出现"东行说被占、西行说空"。
- 附带后果（刻意）：一个 L1 段**被压住就是被占**，哪怕车只压住它的一部分 —— 这正是"占用按物理区段判定"
  的含义；要把粒度做细，就得在 L1 里切得更细（切点来源只有灯）。
- 用例：`MmtrTrackSectionTests.occupancyIsDecidedAtLevelOneAndWidenedToLevelTwo`（岔口处 L1 必然收口 ⇒
  一个 L2 由多段 L1 拼成，占任一段都算被占）与 `occupancyIsDirectionNeutralAcrossBothDirections`
  （东行/西行两段同时被占）。

## 4. Level 2：行车区间（`MmtrSectionService.Section`）

- 从一架朝方向 D 的灯起，沿 D 走到下一架朝 D 的灯（**不含**）为止；跨轨，节点不切分；
- = **连续若干个轨道区间的并**（L2 边界一定是 L1 边界，所以是 L1 的一个加粗划分）；
- 同一段弧在两个方向上各属一个行车区间（"方向是区间的第一属性"，`SectionView.direction` / `bySpan.dirOfTravel`）；
- **无灯大区间**：把"灯到灯区间"没盖到的弧窗（做**差集**，因此不漏不重叠）补成区间，
  **每块两段**（两个方向各一段），id `无灯#<L1 id>` / `无灯#<L1 id>·逆`，`entrySignalKey` 为空。

**链（`followingBySection`）**：灯到灯的段按**出口灯**连；**任何没有后继的段**再用**位置判据**补一次
（最后一根轨沿行进方向到远端节点 → 取所有前向腿 → 找"那根轨上从这一点起朝我这个方向"的段）。
链深（红/单黄/双黄）用**跨所有分支的 BFS**（与显示层 `depthAt` 同一套走法），不要在岔口只跟一条。

沿用 v2 的现场修正（这些都是实测修出来的，不属"两套模型"）：
走行不许掉头（`MMTR_REVERSAL_DOT = -0.5`，只对唯一续段生效）、岔口多腿（一盏灯守整个咽喉）、
进路收窄（SET/PENDING MAIN）、走不到的腿**守住但不判断路**、道岔禁行侧 ⇒ 该段按红、
轨中段的灯切分、占用树键序两个方向都认、灯 → (保护轨, 方向) 的解析（人工绑定 > 目标轨 > 节点选腿 > 中段投影）。

## 4.1 灯的状态**绑定在它开的那一段上**（用户 2026-09-15）

> 「然后需要将行车区间状态绑定至信号灯上。」

- **绑定对象**：`MmtrSectionService.LampBinding` —— 每一盏登记灯一条：它守的轨、**它开出的行车区间**
  （一灯多腿 ⇒ 多条）、这些段的**占用**、由段状态推出的**显示**、以及"**未接入闭塞**"这个显式状态。
- **读法**：网页（`/mmtr-signals` 的 `section` / `sections` / `nextSections` / `occupied` / `aspect` /
  `unbound`）与游戏（指令 `lamps`，`lamps-v2` 为别名）读的都是这一份，不再各算一套。
- **删掉的回路**：BOUND 灯原来按 `target` 那条轨去查 **per-rail 显示表** —— 那是"状态绑在轨上"的读法，
  于是同一盏灯"网页看轨、游戏看段"，两边可以不一致。现在**所有灯**一律读绑定。
- **一灯多腿取最不利**：任一条腿的段被占 ⇒ 该灯红。
- **两个字段不要混**（实测钉住）：`occupied` 是**物理事实**（它守的段上真有车，含被道岔切断的那条腿），
  `aspect` 是**显示结论**（被切掉的腿"不算进路"，不参与颜色计算 —— 既有铁律 `blockedAtDeparture`）。
- **未接入闭塞的灯**（守不到任何轨）：`unbound=true`、`aspect=""` —— 网页/游戏显示"未知"，
  不给一个**看起来正常**的绿。
- 用例：`lampStateFollowsTheSectionItOpensNotTheRailItStandsOn`（灯脚下那根轨被占 ≠ 它的段被占）、
  `aMultiLegLampReportsEverySectionItOpensAndTakesTheWorstAspect`、
  `aLampThatReachesNoRailIsReportedUnbound`。

## 4.2 Web 接口（三层各一个，字段含义只有一种）

| 接口 | 图层 | 关键字段 |
| --- | --- | --- |
| `GET /mtr/api/map/mmtr-track-sections` | **L1 轨道区间**（占用单位） | 每条 `id / length / occupied / spans[{hex,from,to,points[]}]`；顶层 `count / busyCount / railCount` |
| `GET /mtr/api/map/mmtr-block-sections` | **L2 行车区间**（授权单位） | 每条 `id / entrySignal / exitSignal / next / aspect / occupied / length / direction{angle,label,dx,dz} / uncovered / members[] / memberCount / spans[{hex,from,to,dirOfTravel,reachable,points[]}]`；顶层 `count / busyCount / lampCount` |
| `GET /mtr/api/map/mmtr-lamps` | **信号灯状态**（绑定） | 每盏 `key / x,y,z / angle / aspects / mode / target / boundExplicit / aspect / occupied / unbound / section / sections[] / nextSections[] / protectedRails[]`；顶层 `count` |
| `GET /mtr/api/map/mmtr-total-sections` | **总区间**（地图一条带 = 一个位置 ＋ 各方向归属） | 每条 `id / length / occupied / directions / staggered / covers[{section,entrySignal,exitSignal,next,aspect,occupied,uncovered,length,direction{angle,label,dx,dz}}] / spans[{hex,from,to,points[]}]`；顶层 `count / busyCount / staggeredCount`（见 §4.4） |

- `points[]` 是**成对**的 `x,z` 采样点（一趟 9 个点），前端直接画那一段弧窗，不必自己实现 MTR 的轨道数学。
- `members[]` 把两层连起来：**这一段行车区间由哪些轨道区间拼成**（占用是在 L1 判定、再扩大上来的）。
- `uncovered=true` = 补出来的**无灯大区间**（没有入口灯）—— 前端应画成"无信号区段"，不要当绿灯画。
- `unbound=true` = 这盏灯守不到任何轨（未接入闭塞），`aspect` 为空 —— 画"未知"。
- `reachable=false` = 这条腿被道岔当前位切掉（**守着但不判断路**，见 §6）。
- 另有综合包 `/mmtr-sections`（运营台在用：`sections` + 多值 `byRail` + `trackSections`）、
  格对齐的区间图 `/mmtr-schematic`、道岔图层 `/mmtr-points`、轨拓扑 `/mmtr-topology`。
- 契约用例：`SystemMapSectionApiTests`（钉字段名与形状 —— 缺字段前端会**静默画不出来**）。

## 4.3 道岔在两层模型里的位置

| 层面 | 道岔怎么进来 |
| --- | --- |
| **L1 划分** | 不按"道岔"这个身份切，而是**结构使然**：段是线性的、不能分叉 ⇒ 度 ≠ 2 的节点必然收口（现实依据同构：道岔区段自成一段、绝缘节在警冲标外方） |
| **L2 走行** | 岔口**跟每一条朝前腿走**（用户 2026-09-10「一盏灯守整个咽喉」）；设了 MAIN 进路则收窄到进路那条腿（`nextLegs(narrowToRoute)`）；道岔**当前位置禁行**的那条腿照样收进守卫集合，但标 `reachable=false`（**守着、但不判断路**）；走行**撞在禁行侧**⇒ 这一段 `blockedAtArrival` ⇒ 显示**红**（"没有进路"比"前方有车"更硬） |
| **缓存** | **道岔位置进签名**：扳一次岔就重建两层（否则位置 0 建好的段会带着旧的"禁行侧"结论继续用） |
| **显示（④）** | 岔区**清限区**（`MMTR_JUNCTION_CLEARANCE_M = 10 m`：汇于该节点的每根轨靠近节点的那 10 m）里"够算占用"有车，或该岔口**没人定**（没有一个进向有人工位）⇒ `MmtrJunctionState.unclearedNodeKeys` 报该节点"清不掉"，显示层把跨过该节点的那一步当**占用**（红） |
| **运动与联锁** | 道岔有自己的权威层：`MmtrPointAuthority`（物理唯一持有者 + 排队 + 拒绝不存在的组合）、`MmtrTurnout`（纯几何：`(节点, 盆轨)` 一个物理位置 0/1，默认 0，不存在"未知态"）、进路 `MmtrRoute`/敌对进路表。区间层**不做**这些判断，只在"这一段还能不能走"上如实反映（`blockedAtArrival` / `reachable` / 清限节点） |

> 一句话：**区间层不定义道岔，只如实反映它的三个后果** —— 段在这里收口、这条腿走不走得到、以及这个岔口现在清不清得掉。
> 道岔的"谁持有 / 什么时候扳 / 扳到哪一位"在权威层与联锁层，区间层不参与。

## 4.4 总区间：地图上"一条带"（用户 2026-09-15）

用户原话：

> 以**错开**的一段轨道区间为例，一辆车在其中间，代表着这辆车**既在上行区间中，也在下行区间中**，
> 那么这时候就需要引出下一层了，叫做**总区间**，用于显示在地图上。

问题是真的：L2 是**有方向**的，两个方向的边界并不重合（灯错开布置），所以一辆车可能同时落在
"上行某段"和"下行某段"里；地图上按 L2 画就是**两条带叠在一根轨上**（现场实测 140 轨里 62 根属于
2 个以上 L2 区间、最多 5 个），画出来既重叠又说不清"这一段现在归谁"。

**为什么它是 L1 而不是第三层划分**（这一点必须写死，否则以后会有人再去划一遍）：

1. 两个方向的行车区间各自都是"若干 L1 段的并"（L2 的边界必是灯位 = L1 的切点）；
2. 所以它们的交、并、按"覆盖配对"分组，结果**都还是 L1 段的并**；
3. 而相邻两个 L1 段之间**必有一盏灯** —— 是上行灯就换掉上行区间、是下行灯就换掉下行区间 ——
   于是"覆盖配对相同"的最大连段**恰好就是 L1 段本身**；
4. 想更粗就只能放弃某一个方向的灯当界，那与"切点只由灯产生"（§2）冲突。

所以总区间的 **几何 = L1**（同一批 id、同一批 span），它多出来的是**归属**这一半信息：

| 字段 | 含义 |
| --- | --- |
| `id / length / spans[]` | 位置：就是那一段 L1（`/mmtr-track-sections` 里同一条） |
| `occupied` | 这一段**被占**了吗 —— L1 那**唯一**一条判据的答案（不是各 cover 的或；两者恒等） |
| `directions` | 覆盖它的**行车方向数**（2 = 上下行都照到这一处；1 = 只有一侧有灯） |
| `staggered` | **错开**：两个方向都照到，但两段区间**不是同一段路**（起止不重合） |
| `covers[]` | 覆盖它的每条行车区间：`section / entrySignal / exitSignal / next / aspect / occupied / uncovered / length / direction` |

- **一处一条带**：地图按 `spans[]` 画（不再按 L2 画方向带），卡片里展开 `covers[]` 说清
  "它同时是上行 X 段、下行 Y 段"。
- **"既在上行、也在下行"是可查的**：错开处车压在同一根轨上，`covers[].occupied` **两条都报 true**
  —— 这就是用户那句话在数据里的形状（用例 `aCarOnAStaggeredStretchSitsInBothDirectionalSectionsAtOnce`）。
- **"同一段路"按集合比，不按顺序比**：上行段从西往东数、下行段从东往西数，同一段路的 `spans` 表
  顺序正好相反；按顺序比会把**成对布置**的灯误判成错开（用例 `lampsPairedAtTheTwoEndsAreNotStaggered`）。
- **`covers` 里空 `entrySignal` = 补出来的无灯大区间**（§6.1）：无灯就没有显示、`aspect` 为空，
  前端必须画成"无信号区段"。
- **放在服务端而不是网页**（用户问过"是在 web 设计逻辑还是在服务端设计逻辑比较好"）：几何是引擎的
  结论，归属（哪条区间覆盖哪一段、它现在什么显示）也只有引擎算得对；网页自己求交必然与引擎的容差
  漂移（notes/113 的 web 侧划分出过 137 片 / 64 处重叠；notes/158 记过 3 m 与 4 m 容差不一致）。
  网页/HUD 都读同一份结论。
- 位置层与归属**不许互相推导**：网页不得自己按"上下行都照到"重划一遍带（那会与 L1 对不上，
  用例 `everyPlaceHasOneTotalSectionWhoseGeometryIsTheTrackSection` 钉的就是这条数量关系）。
- 网页落点：`engine/website` 的区间地图上多了一层 `TotalSectionsLayer`（正中的"这一处"），
  与 L2 的两条方向带**横截面互补**（方向带 0.4 格 / 偏 0.25 格、总区间带 0.1 格居中）；纯函数与用例
  在 `website/src/domain/TotalSection.ts` 与 `website/scripts/total-sections.test.ts`。

## 5. 消费方（全部只读新层）

| 消费方 | 读什么 |
| --- | --- |
| S1 停车 / ①②岔前扣车 | L1 弧窗（`trackSpanAt`）+ L2 边界（`sectionBoundaryAheadM`） |
| 信号显示与链深 | `chainDepth`（BFS，占用树 + 受限节点 + 排除自身） |

| 网页 feed `/mmtr-sections` | L2 `sections[]` + 多值 `byRail[]` + **L1 `trackSections[]`** |
| 地图图层 `/mmtr-total-sections` | 总区间（L1 几何 ＋ 各方向归属，见 §4.4） |
| 游戏端指令 | `tracks [<轨>]`（L1 逐段）/ `totals`（总区间）/ `blocks-v2 [all\|<轨>]`（某轨属于哪几段 L2）/ `lamps` / `occ` —— **只在游戏端/被 push 时可用** |
| 网页指令栏 | `query totals`（总区间概况；网页走的是**引擎分发器**，游戏端那几条敲不到，见 notes/167 §7）|
| 客户端镜像 | 引擎给**结论**（`lamps` = 每盏灯的显示、`lampRails` = 每盏灯守的轨）；客户端**不再自己数区间** |
| 绑定工具 | `resolveProtectedRail(s)`（与区间模型同源） |

> 已删除的通道：**每区间一个预留信号色**（B3b）整条链路 —— 它让"占用"多了一份认不出是谁的来源，
> 正是"列车被自己的影子扣住"（notes/112 §4 / notes/152）的载体。现在占用只有**占用树**一份。

## 6. 已知取舍

1. **无灯区整块一个大区间 ⇒ 长走廊会被整块锁**（一列车在里面，同方向后车停在块外）。
   这是用户明确选定并接受的（"不按当前世界来看"）。
2. **段不能分叉 ⇒ 道岔节点必然收口**，即"切点只由灯"在分叉处必然多出边界；这是"段"这个概念本身的推论。
3. **两层显示同一段路**：网页要按 L2（方向带）画授权、按 L1 画占用；两者在同一条轨上**重叠是正确的**
   （现场实测：140 轨里 62 根属于 2 个以上 L2 区间、最多 5 个）。
4. **总区间只解决"画法"，不改变"事实"**：错开处的两条 L2 区间依然存在、依然各自算授权；总区间给的是
   地图上的一条带 ＋ 归属表（§4.4）。它**不能**用来替代 L2 做授权判断（授权必须看方向）。
5. **`staggered` 只在两个方向都有灯时才有意义**：一处如果只有单侧有灯（另一侧是无灯大区间），
   它报 `directions=1`、`staggered=false` —— 那是"半边无灯"，与"错开"是两件事，前端别混。
