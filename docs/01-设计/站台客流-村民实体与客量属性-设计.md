# 站台客流：客量属性 + 村民实体（MMTR）

> 一句话：引擎里每个站台有一个 **0–100% 的客量**（`crowdLevel`，落盘、下发、可指令改），
> 游戏侧按它把**真村民实体**放到**站台面**上（站台方块后面那几排，以及用标记方块画出来的人流区）
> 表示客流：一级格站着排队、二级格站着候车、流动格上的人**沿走道来回走**；
> 渲染整条交给原版渲染器 + **Fresh Animations**（EMF/ETF），模组不写一行实体渲染代码。

## 1 口径（用户拍的，别再自己发明）

| 口径 | 值 | 原话 / 出处 |
|---|---|---|
| 客量粒度 | **每个站台一个** 0–100% | 2026-10：「每个车站的站台有客量 0-100% 属性」 |
| 人站哪 | **站台方块那一排不站人**（贴轨的安全线块），站台方块**后面**那几格才是人流区 | 「站台方块本身不能站人，所以外扩二格即可」 |
| 默认自动区 | 站台方块往站台里数 **2 格**（`platform rows <n>`，0 = 彻底不自动铺）；**这条站台只要有标记就只认标记**，自动区不参与 | 同上（现场量过上水村：站台方块 z=1798、人站的那层地面 z=1797/1796）+ 2026-10-10「村民乱站，在无标记位置也站」 |
| 分级 | **两级**：一级=贴边排队、二级=往里候车 | 「分 2 级，因为现实人会靠近屏蔽门排竖队，所以需要分级的客流方块」 |
| 未满时的分配 | 一级 : 二级 = **7 : 3**（在站定的人里分；走动人流另占一份，最多满员的 20%） | 「1 级方块朝站台方向排队，未满时比例为 7：3」 |
| 100% 是什么 | **满员站满**（满员 = 单站台上限）；上限抬到"候选总格数"时才是每格一人的真·全站满 | 「100% 时无论几级全站满」（2026-10-10 修正，见下面「客量与人数」） |
| 流动人流 | 走道上的人**真的会走**（沿标记朝向来回） | 「真的走来走去」 |
| 标记方块 | 一级/二级/流动/归属锚四种，**平时看不见，手持任意一种标记物才现形** | 「设计一系列透明方块（手持现形）……放置在站台方块上以确认归属站台的方块」+「手持任意标记物显示三类全部」 |
| 载体 | **真村民实体**，不是方块/方块实体 | 「非实体仅方块即可」→「还是需要点动态的……fresh animations 那个」 |
| 单站台上限 | 默认 **48** 人（`platform cap <n>`）= **这个站台的满员人数**：人数 = 满员 × 客量% | 「不然村民起步就是大概 2-300 只在一个站台上」+ 2026-10-10「村民数量没有增多」 |
| 玩家半径 | 默认 **96 格**（`platform radius <n>`）；勘测模式可临时忽略（`platform force on`） | 同一条：看不见的人纯白花性能 |
| 朝向 | 一级/二级面朝**自己那条轨**；流动沿标记朝向 | 「等车的人都看着车来的方向」 |
| 花色 | **群系类型 7 种**随机（plains/desert/jungle/savanna/snow/swamp/taiga） | 用户要原版村民 → 花色差异用原版就有的维度，不自己画皮 |

> **客量与人数（2026-10-10 口径修正）**：`人数 = 满员人数 × 客量%`，**满员人数 = `platform cap`**。
>
> 旧口径是"客量 × 全站候选格数"（那等于"每格一人"）：TEST 站台铺了 850 个标记格
> （一级 300 + 二级 460 + 流动 180），50% 就是 470 人，而上限默认 48 —— 上限一咬住，
> **客量 10% 与 100% 铺出来完全一样**（实测：客量改成 50% 之后报告仍旧写"应有 一级=8 二级=2 流动=2"，
> 与 100% 一字不差；用户当场指出"村民数量没有增多"）。旧代码里那段"截断时二级与流动各保底 2 个"
> 就是为这个口径打的补丁 —— 补丁只保住了"分级看得见"，没救回"客量看得见"。
>
> 新口径下（`MmtrCrowdModule.select`）：站定的人 = `满员 × 客量% − 流动`，再按 **一级 7 : 二级 3** 分；
> 走动人流 = `min(流动格数, 满员 × 20%) × 客量%`（至少 2 只）；把上限抬到候选总格数
> （TEST 站台 940）就与旧口径**完全等价**（100% = 每格一人）。
> 实测（cap 220 ｜ 客量 50% ｜ TEST 站台）：一级 62 / 二级 26 / 流动 22 = **110 人**，
> 与引擎 `platform list` 自己报的"≈110人"逐位对上。

> 为什么客量不做成"自动跟乘客仿真挂钩"：用户 2026-10 明确「暂时留接口和指令就行」。
> 接口已经留好：`MmtrCrowd.setModulator(...)`（引擎侧调制器，默认没有 = 客量就是存下来的数）。
>
> **2026-10-13 补（notes/425）**：用户接着提「车站人流系统，这个需要一个系统进行自动动态设置」，
> 于是有了《[车站人流系统-自动动态客量-设计.md](车站人流系统-自动动态客量-设计.md)》。
> 它**没有用** `setModulator` —— 那个钩子只改 `getEffectiveCrowdLevel()`，而**有效值不跨端**
> （游戏侧推给客户端的是 `crowdLevel` 字段，见 notes/416）；系统直接按
> `曲线[小时] × 基准% × 班次因子 × 事件 + 停站冲量` 写 **`crowdLevel` 本身**，
> 于是落盘 / 跨端推送 / 渲染 / 读数整条链路一行没改。本文 §2 的数据流图里
> "引擎 `Platform.crowdLevel`" 那一格现在由那个系统自动填（默认关，`crowd on` 开）。

## 2 数据流（谁是真源）

```
引擎 Platform.crowdLevel（权威，落盘 platforms/<末两位hex>/<hex>）
   ├─ 指令：platform set / station / all / cap / radius        （中控指令栏）
   ├─ 仪表盘：站台屏 0–100 滑杆（关屏时随 PacketUpdateData 一起发回）
   ├─ 下发：DataResponse → 客户端 MinecraftClientData
   └─ 读数：/mtr/api/map/mmtr-platforms 的 crowdLevel / effectiveCrowdLevel
                    ↓ 每个核对节拍（5 秒，或客量一改的下一拍）
游戏侧 MmtrCrowdModule：扫站台边缘 → 按客量+闸门选格 → 生成/拉回/收走村民实体
                    ↓
世界：村民实体，身份写在实体 tag 里（见 §4）—— 唯一的账本
```

引擎侧还会在 `platform list` / `mmtr-platforms` 里报出**闸门**（上限、半径），
因为"设了 100% 为什么只有 48 个人"这个问题必须在读数里自答。

## 3 选点算法（站台面，不只是站台边那一排）

站台实体只有两个轨道端点，**没有"站台面在哪、多宽"**，所以候选格有两个来源：

**A. 自动区**（没打标记时的默认）

1. 沿站台轨每 **1 格**取一个点（`rail.railMath.getPosition`，曲线也照走）；
2. 在该点的**法线两侧**从近到远找**第一块 MTR 站台方块**（`PlatformHelper`：full/slab/indented 都算）
   —— 找到的那块就是站台边缘（岛式站台两侧都有站台面时按位置哈希定一侧）；
3. **站台方块那一格不站人**（贴轨的安全线块）：从它往站台里数第 1..`autoRows`（默认 2）格，
   每格要求"脚下是**同一层**的实心地面（顶面高度差 ≤ 0.26 格：容得下内缩站台 13/16，
   挡得住半砖与台阶）且这一格没有碰撞箱" —— 墙、长椅、柱子、售货机自然被筛掉；
4. 第一格的实际地面当后面几格的基准（站台方块可能比站台面高一点点）。

**B. 标记区**（玩家画的，比自动识别权威）

5. 同一趟法线继续往里扫到第 `MARKER_WINDOW`（12）格，认**标记方块**（§4）；
   地面高度一变就停 —— 于是"两条站台之间隔着轨道"时，往轨道那侧扫会自然停住，不会抢邻台的人流区。

> **候选只有一份来源（2026-10-10 修正）**：这条站台扫到**任何一个标记** ⇒ 候选 = **标记格**
> （自动区整段不参与）；一个标记都没扫到 ⇒ 候选 = 自动区那几排。
> 曾经是"自动区 ∪ 标记（同一格标记优先）"，于是**标记没画到的格子被自动区补进来站人** ——
> 用户看到的就是"**村民乱站，在无标记位置也站**"。TEST 站台实测对得上账：
> 候选一级 300 = 标记画的 180 + 自动区补的 **120 个无标记格**
> （120 = 30 个门洞 × 门洞内 2 格 × 自动区 2 排）。改成"只认标记"后候选一级 = **180**，
> 实有 = 应有、多出 = 0、漂移 = 0。
> 注意副作用：**一格遗留的标记就会让整条站台变成"只认标记"**（上水村那种早期试验标记就是），
> 读数里表现为候选数量骤降 —— 不想要就把那几格敲掉（或把 `platform rows` 设回默认）。

**选择（客量 → 目标集合）**

6. 候选按级分成三组（一级 / 二级 / 流动），**按位置哈希排序取前 N 个**：
   - 为什么不是"阈值筛"（`hash < fraction`）：阈值筛出来的人数是**二项分布**的 ——
     220 格、上限 12 时实测铺出 **18** 个，上限形同虚设（那是客户端帧率的闸门，必须硬）；
   - 排序取前 N 既保持随机散列（挑哪几格由哈希决定，看上去是自然空档），人数又精确等于目标；
   - `hash01` 用 splitmix64 收尾（两次乘法）：短写法实测均值偏到 **0.478**，于是"设 60%"会铺出 62–64% 的人。
7. 目标数（口径见 §1「客量与人数」）：`总人数 = 满员 × 客量%`（满员 = `platform cap`）；
   站定的人按 **一级 0.7 / 二级 0.3** 分（某一级格不够就整份补到另一级）；
   走动人流另分一份：`min(流动格数, 满员 × 20%) × 客量%`，至少 2 只 ——
   走动的人最贵（每 tick 一次 `setPosition` + 客户端走路动画），不设份额上限的话
   180 格的走道按客量能要到 90 只；
8. **上限即满员**：抬上限 = 把站台铺得更满（上限 ≥ 候选总格数时，100% = 每格一人）。
   实测 cap 220 ｜ 客量 50% ⇒ 一级 62 / 二级 26 / 流动 22 = **110 人**（旧口径在这个上限下会铺成
   216 / 2 / 2 —— 一级挤满、分级与流动几乎看不见，这正是旧"保底 2 个"补丁的副作用）；
9. **半径闸门按整条站台判**：站台上**任意一格**在半径内 → 整条站台按上面算；否则整条收走。
   判"任意一格"而不是"站台中心"：220 格站台站在一端时中心离玩家 110 格，按中心判会整条空掉 ——
   玩家明明就站在站台上。按整条判也避免了"半条有人半条空"的半截画面。
   `platform force on`（勘测模式）可临时忽略这道闸门；
10. 只处理**已加载区块**（读方块前必查；`getBlockState` 会把未加载区块从磁盘拉起来甚至生成地形）。

## 4 标记方块（"透明方块，手持现形"）

| 方块 | id | 含义 |
|---|---|---|
| 客流标记·一级 | `mtr:crowd_mark_1` | 贴站台边排队的格（未满时 7 成的人） |
| 客流标记·二级 | `mtr:crowd_mark_2` | 往里一层的候车格（未满时 3 成的人） |
| 客流标记·流动 | `mtr:crowd_flow` | 人流走道；格里的人沿**放方块时的朝向**来回走 |
| 客流归属锚 | `mtr:crowd_anchor` | 放在**站台方块上**，声明它周围一片标记区归哪条站台 |

- **平时完全看不见**：方块本身 `getRenderType2 = ENTITYBLOCK_ANIMATED`、blockstate 指到空模型，
  世界里不留痕迹；**手里拿着任意一种标记方块**（主手或副手）时 `RenderCrowdMarker` 才画出来
  （贴地色块 + 中间一根矮柱，颜色按种类分；渲染距离 128 格，站台端头也看得清）。
- **不挡路**：碰撞箱为空 —— 标记格就是"人站的那一格"，村民实体站在方块里面，玩家也能穿过去。
- **归属怎么判**：谁扫到归谁（记着离站台边几格）；两条站台都扫到同一格（岛式站台两面都往中间扫）
  时按"离站台边更近"判；**归属锚**把它周围 8 格内的标记连同连通的整片改判到它所在的那条站台 ——
  岛式站台"中间那一片到底算哪条站台的客流"就靠它拍板。
- 铺完 **15 秒内**生效（重扫节拍）；急的话 `platform refresh`。

## 5 流动人流（走道上的人真的在走）

- 走道 = **整条流动标记**铺出来的格，按 (x,z) 两列索引 —— 半砖/内缩站台上人脚下会矮一点点，
  按三维格判会把他每 tick 拽回格心，看上去原地抽搐、永远走不动（实测踩过）；
- 每 tick 沿所在格的朝向挪 `0.045` 格（≈0.9 格/秒，闲逛速度）；下一格不在走道上就**掉头**；
- 位置用 `setPosition`（相对移动包）而不是传送：客户端插值着走，**原版那套走路动画
  （也就是 Fresh Animations 的走路动画）自动生效**；
- 台账与站定客流不同：走动人流只记"属于哪条站台"（tag `mmtr_crowd_flow`），**不记记忆格** ——
  他本来就该离开那一格；人数按客量收敛，"这一步往哪走"是易失状态（重启后按格坐标重新哈希）。

## 6 实体账本：身份放 tag，不放内存

每只村民三个 tag（走动人流把第三个换成 `mmtr_crowd_flow`）：

| tag | 作用 |
|---|---|
| `mmtr_crowd` | 这是我铺的人（枚举用） |
| `mmtr_crowd_p_<平台hex>` | 属于哪个站台（站台拆了/删了按它回收） |
| `mmtr_crowd_at_<x>_<y>_<z>` | **它应该站哪一格**（记忆格；走动人流没有这一条） |

每个核对节拍做四件事，全部**从世界读事实**（不信任任何内存账本）：

| 动作 | 判据 | 为什么这样做 |
|---|---|---|
| 生成 | 目标格上没有人，且没有任何人"记忆"着这一格 | 新的人 |
| **拉回** | 有人记忆着这一格，但它实际不在这一格（高度容差半格） | 村民会被玩家/别的实体推走；拉回而不是"删了重生成"——后者每拉一次发一次生成包，玩家眼前的队伍会闪。容差半格是因为内缩/半砖站台上人脚下会矮一点点，按整数格判会每拍把人往上拽一次（上下抖） |
| 收走 | 记忆格不在目标里（客量降了 / 出半径了 / 站台面被改 / 平台没了） | 客量一降人就该少 |
| 纠朝向 | 人在位但被推转了 | 让人都朝着轨 |

> **为什么不用内存记账**：服务端一重启、区块一卸载重载，内存账本就没了，而世界里的人还在 ——
> 上一版（方块方案）实测就这样留下过 **113 个永远清不掉的孤儿**（世界 354 个 vs 应有 241 个）。
> tag 跟着存档走，重启后照样认得这批人、各自该站哪。

## 7 指令与读数

| 指令（中控指令栏 `POST /mtr/api/map/mmtr-command`） | 作用 |
|---|---|
| `platform list [--station=<id\|hex\|名>]` | 逐站台报 客量/有效/长度/折合人数（含"被上限截断"标注）+ 闸门现值 |
| `platform set <站台hex\|id> <0-100>` | 改一个站台 |
| `platform station <车站id\|hex\|名> <0-100>` | 改该站所有站台（最常用） |
| `platform all <0-100>` | 全图 |
| `platform refresh` | 立刻重铺（不改客量；人被杀/被清掉时用） |
| `platform scan` | **让游戏端数一遍世界里实际站着几个人**（下一条） |
| `platform cap <n\|show>` | 单站台上限（1–400，默认 48） |
| `platform radius <n\|show>` | 玩家半径（16–512，默认 96） |
| `platform rows <n\|show>` | 自动区宽度（0–8，默认 2；0 = 关掉自动区，站台上只认手动标记） |
| `platform force <on\|off\|show>` | **勘测模式**：忽略玩家半径，所有已加载区块的站台都铺人（布景/截图用，用完关掉） |

`platform scan` 的读数（逐站台一行，名词在报告里就写清）：

| 字段 | 含义 |
|---|---|
| `候选` | 已加载区块里找到的站台边缘格数（`候选 × 客量%` 就是"想要几个人"） |
| `应有` | 按客量与上限算出来的目标人数（`min(客量% × 候选, 上限)`） |
| `实有` | 这些格里**真的站着我们的人**的格数（差值 = 还没生成完 / 被杀 / 被推走） |
| `多出` | 世界里我们的人比"实有"多出来的部分（下一拍会被收走） |
| `站位漂移` | 人还在、但不在自己记忆格上的只数（下一拍被拉回） |
| `排队` | 还没做完的实体/方块操作数（每 tick 2 ms 预算，做不完接着做） |
| 尾注 | `（客量要 N 人，被上限 M 截断）` / `（本拍半径内没玩家 ⇒ 整条站台收走；不是没铺出来）` |

闸门的持久化：引擎侧是权威值（指令当场生效），游戏侧把当前值**镜像**到
`<世界存档>/mtr/mmtr-crowd.properties`，服务端启动时读回来再灌回引擎 —— 单一权威，又活得比进程长。

## 8 客户端要装什么（Fresh Animations）

| 要装 | 版本（**实测能用的那套**，2026-10-05） | 装哪 / 怎么接 |
|---|---|---|
| Entity Model Features (EMF) | `entity_model_features_1.20.4-fabric-3.0.7.jar` | `vendor/mods/` → `build.gradle` 的 `modLocalRuntime files(...)` |

## 9 已知边界（不该惊讶的事）

1. **没玩家在线 ⇒ 整条站台收走**（半径闸门）。这是有意的：没人看的人纯白花客户端与网络。
   读数里会写清"是半径收走的、不是没铺出来"；要"人不在场也铺"用 `platform force on`（勘测模式）。
2. **站定的人是 `NoAI` ⇒ 没有走路动作**（待机动画照常播）。放开 AI 它们会自己寻路走下站台掉到轨道上；
   要"走动"只有流动标记那条路：我们每 tick 驱动位置，不碰寻路（见 §5）。
3. **村民会被推动**（玩家挤、别的实体推）⇒ 每拍按记忆格拉回；`站位漂移` 计数就是它。
4. **职业 = 无业**（`VillagerProfession.NONE`）⇒ 右键**不开交易界面**；也是静音 + 无敌 + 不消失。
5. **方块 `mtr:crowd_villager` 还在**（手动摆放 / 对照用），但生成器不再使用它；
   升级到实体方案时，世界里遗留的旧方块会被自动扫掉（目标格每拍查一次 + 扫描时登记其余格）。
6. **上限是"同屏人数"的闸门，不是"站台容量"**：想让站台更挤就抬 `platform cap`。
   实测量级（2026-10-05）：**≤500 只服务端无感**、**95 只连客户端都量不出差别**；
   而一次性 5951 只时连服务端都会 `Can't keep up`（290 ticks behind）。所以"要不要更挤"是体感问题，不是性能问题。
   上限咬住时**二级与流动各保底 2 个**（否则整类被砍光，分级与流动都看不见）。
7. **同位置的帧数落差先别归因给村民**：实测在同一个站位把 95 只全收走，帧数没有变化 ——
   110（空旷地）→ 30（站台）的落差是**车站方块 + 光影**的账。要判断任何"新东西吃不吃帧"，
   都得在**同位置、镜头不动**的条件下做 A/B。
8. **标记只扫站台面附近**：从站台方块往站台里最多 12 格（`MARKER_WINDOW`），且地面高度一变就停。
   所以站厅/扶梯口那种**离站台面十几格远**的标记区扫不到；站台特别宽（>12 格）时外圈也扫不到。
9. **归属锚只管周围 8 格**：它把这一片连通标记改判到"锚所在的那条站台"（锚放在站台方块上），
   更远的地方得再放一个锚。
10. **流动人数 = `客量% × 走道格数`**：走道铺得短、客量又低时可能只有 1 个人在走（正常）；
    上限截断时流动至少留 2 个（前提是铺了流动标记）。

## 12 客流村民的"简化"：没有碰撞箱的人形贴片

用户口径（2026-10-10）："**村民导致帧数暴跌，我们也不需要这个村民有什么碰撞箱，能不能简化一下**"。

| 开关 | 值 | 为什么 |
|---|---|---|
| NoAI | 开 | 不寻路、不选目标、不 tick 大脑（LivingEntity.tick 里 isImmobile() 直接跳过 	ickNewAi），否则会自己走下站台掉到轨道上 |
| Silent | 开 | 一个站台两百多只村民的"哼哼"声 |
| Invulnerable + PersistenceRequired | 开 | 打不死的装饰 / 不参与生物消失逻辑 |
| 速度 | setVelocity(0,0,0) | 不被任何陈年冲量推着走 |
| isCollidable() / canHit() / isPushable() | **false** | **"没有碰撞箱"本体**：不再进入任何实体碰撞的候选列表（EntityPredicates.CAN_COLLIDE、准星射线、活塞与实体挤压都问这三个）。站台上几百只挤在一格宽的地方，原版每只每 tick 都要跟周围上百只做一次两两相交（每次都新建候选列表）—— 候选列表空了，这条最贵的路径整体消失 |
| 自定义名字 mmtr_crowd | 设上但**不显示** | 给客户端一个身份判据：命令 tag 不进实体数据、不随生成包同步，客户端手里那份永远是空的 |
| 重力 | **不动**（保持开） | 内缩站台（13/16）、半砖站台上人脚下会矮一点点，靠重力落到真实地面上；关掉会浮在半空 |

**为什么不用 
oClip = true**（看着最省的那一条）：它把**方块**碰撞也一起关掉 —— 而客流是靠"站在地板上"
定位的，关了之后重力会把人穿过站台面掉下去（onGround 永远不置位）。所以只关**实体之间**那一半：
isCollidable/canHit/isPushable 一律 false 之后，碰撞求解的候选列表是空的，而方块碰撞一个字没动。

实现：MmtrCrowdVillagers#simplify（两条生成路径都走它；nsureSimplified 在收编老存档里那批人时补一次）
+ MmtrCrowdEntityMixin（Entity#isCollidable）+ MmtrCrowdLivingEntityMixin（LivingEntity#canHit / #isPushable）。
两个 mixin 挂在 mtr.mixins.json 的 **mixins** 段（**两侧都装**，不是 client 段）：玩家能不能穿过一只村民
是**客户端**算的（本地 Entity.move → EntityView.getEntityCollisions(玩家, 箱子) 拿 CAN_COLLIDE 筛候选），
只在服务端关掉是没用的。

## 13 帧率：实测到的那两条硬数据

测量条件：4K 客户端、TEST 两条站台（共 220 只客流）、同一机位。

| 状态 | fps | GPU | 说明 |
|---|---|---|---|
| 客流 0 只 | 113–118 | — | 空站台基线 |
| 客流 220 只 | 68–83 | 61% | 用户的"暴跌"现场 |
| 客流 220 只、**全部隐身**（Invisible:1b） | 72–77 | **14%** | 不画模型了，帧数**没变** |

结论：**瓶颈不是"画模型"，而是每只实体的固定开销**（每只每 tick 的碰撞求解/挤压检测等）。
GPU 从 61% 掉到 14% 而 fps 不动 ⇒ 渲染不是瓶颈，隐身省下的全在 GPU 空闲上。
所以这一版的"简化"砍的正是这条路径；数量仍然是线性的旋钮（platform cap <n>）。


## 14 帧率闸门：逐格人流半径（2026-10-10 口径变更）

用户口径："帧数 50，不行，正常帧数 100 多"、"更加激烈"。实测（见 §13）锁定了成本口径：
**每多一只"进入视锥"的村民 ≈ 0.06–0.1 ms/帧**，且与"画不画模型"无关（全隐身帧数不变）——
贵的是 EMF 为每只村民做的自定义模型/动画处理。

于是把 platform radius 的口径从**整条站台**（半径内有一格 ⇒ 整条 220 格全铺）改成**逐格**：
只有玩家周围 
adius 格里的格子才站人，走出圈的人下一拍被收走。
MmtrCrowdModule#select 里就是 populate 判完之后对三个候选表按 hasPlayerNear 过一遍。

- 旧口径留下的"整条站台要么有人要么没人"（当时为了让画面不出现半截空）**为了帧数让位**；
- 默认 32 格；platform radius <n> 现场可调（调大更热闹、更吃帧），值与其它闸门一起镜像进存档；
- 走动人流也一起被这道闸门裁（走道 = 半径内的流动标记），所以走动的人只在你附近来回走。

配套（客户端侧、不进这个仓的代码，写在 notes/414 续 4）：EMF 的 nimationLODDistance 6、

etainDetailOnLowFps false、
etainDetailOnLargerMobs false —— 这三键只掉远处动画细节、不掉模型，
是"保住 FA 观感"前提下能拿到的最大一笔。


### 14.1 结果与定案（2026-10-10）

用户口径随后变了两步："**不要对视距以及村民数量进行限制，站台上该多少就多少**" ⇒ 逐格半径撤回
（platform radius 512，闸门等于关；cap 220 不动）。帧数改从**单只成本**上要，最终 **50 → 110+ fps**、客流 176 只全在：

1. **村民不吃 FA 的自定义模型**（EMF modelsNamesDisabled: ["villager","villager2"]）—— 这是那笔钱的正主；
2. **配套把纹理也换回原版**（自建小资源包 MMTR_vanilla_villagers.zip，排在资源包列表最后 = 最高优先级；
   ETF propertiesDisabled 关掉 FA 的村民 properties）。**只关模型不关纹理 = 村民没眼睛**，两半必须一起关；
3. 其余生物仍吃 FA（站台附近只有 4 只非客流实体，"整个卸载 FA"没有额外收益）；
4. EMF 的 nimationLODDistance 6 / 
etainDetailOnLowFps false 保留（只影响非村民的远处动画）。

口径上的取舍写清楚：**客流村民从此是"原版外观"**（有眼睛、群系配色、走路腿摆，但没有 FA 的呼吸/眨眼/精细模型）。
若哪天要把 FA 的村民观感拿回来，就得接受每只 0.06–0.1 ms/帧的账，或者给客流单独写一套更省的渲染路径。
