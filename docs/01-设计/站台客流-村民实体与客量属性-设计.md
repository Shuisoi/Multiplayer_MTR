# 站台客流：客量属性 + 村民实体（MMTR）

> 一句话：引擎里每个站台有一个 **0–100% 的客量**（`crowdLevel`，落盘、下发、可指令改），
> 游戏侧按它把**真村民实体**站到"站台边缘那一排"上表示客流；人不会乱走（`NoAI`），
> 渲染整条交给原版渲染器 + **Fresh Animations**（EMF/ETF），模组不写一行客户端渲染代码。

## 1 口径（用户拍的，别再自己发明）

| 口径 | 值 | 原话 / 出处 |
|---|---|---|
| 客量粒度 | **每个站台一个** 0–100% | 2026-10：「每个车站的站台有客量 0-100% 属性」 |
| 100% 是什么 | 原本「站台边缘 1 格一人」，**现在被两道闸门截断** | 「站台边挤，1 格一人」→ 后加「需要减少实体数量」 |
| 载体 | **真村民实体**，不是方块/方块实体 | 「非实体仅方块即可」→「还是需要点动态的……fresh animations 那个」 |
| 单站台上限 | 默认 **48** 人（`platform cap <n>`） | 「不然村民起步就是大概 2-300 只在一个站台上」 |
| 玩家半径 | 默认 **96 格**（`platform radius <n>`） | 同一条：看不见的人纯白花性能 |
| 朝向 | 面朝**自己那条轨** | 「等车的人都看着车来的方向」 |
| 花色 | **群系类型 7 种**随机（plains/desert/jungle/savanna/snow/swamp/taiga） | 用户要原版村民 → 花色差异用原版就有的维度，不自己画皮 |

> 为什么客量不做成"自动跟乘客仿真挂钩"：用户 2026-10 明确「暂时留接口和指令就行」。
> 接口已经留好：`MmtrCrowd.setModulator(...)`（引擎侧调制器，默认没有 = 客量就是存下来的数）。

## 2 数据流（谁是真源）

```
引擎 Platform.crowdLevel（权威，落盘 platforms/<末两位hex>/<hex>）
   ├─ 指令：platform set / station / all / cap / radius        （中控指令栏）
   ├─ 仪表盘：站台屏 0–100 滑杆（关屏时随 PacketUpdateData 一起发回）
   ├─ 下发：DataResponse → 客户端 MinecraftClientData
   └─ 读数：/mtr/api/map/mmtr-platforms 的 crowdLevel / effectiveCrowdLevel
                    ↓ 每个核对节拍（5 秒，或客量一改的下一拍）
游戏侧 MmtrCrowdModule：扫站台边缘 → 按客量+闸门选格 → 生成/拉回/收走村民实体
                    ↓
世界：村民实体，身份写在实体 tag 里（见 §4）—— 唯一的账本
```

引擎侧还会在 `platform list` / `mmtr-platforms` 里报出**闸门**（上限、半径），
因为"设了 100% 为什么只有 48 个人"这个问题必须在读数里自答。

## 3 选点算法（站台边缘那一排）

站台实体只有两个轨道端点，**没有"站台面在哪、多宽"**，所以：

1. 沿站台轨每 **1 格**取一个点（`rail.railMath.getPosition`，曲线也照走）；
2. 在该点的**法线两侧**从近到远找**第一块 MTR 站台方块**（`PlatformHelper`：full/slab/indented 都算）
   —— 找到的那块就是站台边缘；人放在它**上面那一格**（岛式站台两侧都有站台面时按位置哈希定一侧）；
3. 候选格 × 客量 → 目标集合。**阈值写法**：
   `fraction = min(客量%/100, 上限 / 候选数)`，然后 `hash01(平台id, 格) < fraction` 的格子站人。
   - 期望人数 = `fraction × 候选数 = min(客量% × 候选数, 上限)` —— 正好是"按客量比例，但不超过上限"；
   - 为什么不用"选满 N 个再砍尾巴"：那样人会挤在站台一端，看起来像排队而不是人群；
   - `hash01` 用 splitmix64 收尾（两次乘法）：短写法实测均值偏到 **0.478**，于是"设 60%"会铺出
     62–64% 的人 —— 而"六成格子有人"正是对外承诺的口径，偏差会直接在 `platform scan` 的"应有"里露出来。
4. **半径闸门按整条站台判**：站台上**任意一格**在半径内 → 整条站台按上面算；否则整条收走。
   判 "任意一格"而不是"站台中心"：220 格站台站在一端时中心离玩家 110 格，按中心判会整条空掉 ——
   玩家明明就站在站台上。按整条判也避免了"半条有人半条空"的半截画面。
5. 只处理**已加载区块**（读方块前必查；`getBlockState` 会把未加载区块从磁盘拉起来甚至生成地形）。

## 4 实体账本：身份放 tag，不放内存

每只村民三个 tag：

| tag | 作用 |
|---|---|
| `mmtr_crowd` | 这是我铺的人（枚举用） |
| `mmtr_crowd_p_<平台hex>` | 属于哪个站台（站台拆了/删了按它回收） |
| `mmtr_crowd_at_<x>_<y>_<z>` | **它应该站哪一格**（记忆格） |

每个核对节拍做四件事，全部**从世界读事实**（不信任任何内存账本）：

| 动作 | 判据 | 为什么这样做 |
|---|---|---|
| 生成 | 目标格上没有人，且没有任何人"记忆"着这一格 | 新的人 |
| **拉回** | 有人记忆着这一格，但它实际不在这一格 | 村民会被玩家/别的实体推走；拉回而不是"删了重生成"——后者每拉一次发一次生成包，玩家眼前的队伍会闪 |
| 收走 | 记忆格不在目标里（客量降了 / 出半径了 / 站台面被改 / 平台没了） | 客量一降人就该少 |
| 纠朝向 | 人在位但被推转了 | 让人都朝着轨 |

> **为什么不用内存记账**：服务端一重启、区块一卸载重载，内存账本就没了，而世界里的人还在 ——
> 上一版（方块方案）实测就这样留下过 **113 个永远清不掉的孤儿**（世界 354 个 vs 应有 241 个）。
> tag 跟着存档走，重启后照样认得这批人、各自该站哪。

## 5 指令与读数

| 指令（中控指令栏 `POST /mtr/api/map/mmtr-command`） | 作用 |
|---|---|
| `platform list [--station=<id\|hex\|名>]` | 逐站台报 客量/有效/长度/折合人数（含"被上限截断"标注）+ 闸门现值 |
| `platform set <站台hex\|id> <0-100>` | 改一个站台 |
| `platform station <车站id\|hex\|名> <0-100>` | 改该站所有站台（最常用） |
| `platform all <0-100>` | 全图 |
| `platform refresh` | 立刻重铺（不改客量；人被杀/被清掉时用） |
| `platform scan` | **让游戏端数一遍世界里实际站着几个人**（下一条） |
| `platform cap <n\|show>` | 单站台上限（1–400，默认 48） |
| `platform radius <n\|show>` | 玩家半径（16–512，默认 96） |

`platform scan` 的读数（逐站台一行，名词在报告里就写清）：

| 字段 | 含义 |
|---|---|
| `候选` | 已加载区块里找到的站台边缘格数（`候选 × 客量%` 就是"想要几个人"） |
| `应有` | 按客量与上限算出来的目标人数（`min(客量% × 候选, 上限)`） |
| `实有` | 这些格里**真的站着我们的人**的格数（差值 = 还没生成完 / 被杀 / 被推走） |
| `多出` | 世界里我们的人比"实有"多出来的部分（下一拍会被收走） |
| `站位漂移` | 人还在、但不在自己记忆格上的只数（下一拍被拉回） |
| `排队` | 还没做完的实体/方块操作数（每 tick 2 ms 预算，做不完接着做） |
| 尾注 | `（客量要 N 人，被上限 M 截断）` / `（本拍半径内没玩家 ⇒ 整条站台收走；不是没铺出来）` |

闸门的持久化：引擎侧是权威值（指令当场生效），游戏侧把当前值**镜像**到
`<世界存档>/mtr/mmtr-crowd.properties`，服务端启动时读回来再灌回引擎 —— 单一权威，又活得比进程长。

## 6 客户端要装什么（Fresh Animations）

| 要装 | 版本（**实测能用的那套**，2026-10-05） | 装哪 / 怎么接 |
|---|---|---|
| Entity Model Features (EMF) | `entity_model_features_1.20.4-fabric-3.0.7.jar` | `vendor/mods/` → `build.gradle` 的 `modLocalRuntime files(...)` |
| Entity Texture Features (ETF) | `entity_texture_features_1.20.4-fabric-7.0.6.jar` | 同上（EMF 硬依赖 ETF ≥7.0.0） |
| Fresh Animations（资源包） | `FreshAnimations_v1.10.2.zip` | `fabric/run/resourcepacks/`，已在 `options.txt` 的 `resourcePacks` 里启用 |

**版本为什么钉死**（两条独立的硬约束，**升级前先读 `notes/393`**）：

1. **Loom 版本闸**：本工程钉 Loom **1.10.5**，而 loom 会拒绝"用更新 loom 构建的 mod"——
   `IllegalStateException: Mod was built with a newer version of Loom (1.15.48)`。
   这个戳在 jar 的 `META-INF/MANIFEST.MF` 的 `Fabric-Loom-Version:`，**离线可筛**：
   EMF 3.0.17/3.0.16/3.0.15=1.15.48 ✗、3.0.12/3.0.11=1.13.44 ✗、3.0.10/3.0.9=1.11.38 ✗、**3.0.7=1.9.32 ✓**；
   ETF 7.0.13=1.15.48 ✗、7.0.9=1.13.44 ✗、7.0.8=1.11.38 ✗、**7.0.6=1.9.32 ✓**。
   要升 EMF 就得先升本工程 loom —— 那是另一件事，别顺手做。
2. **启动方式**：**必须用 `mmtr\game\run-client.bat`（或任何工作区外的 JDK）**，
   **不要在 IDEA 里跑**——IDEA 装在 `env\idea`（工作区内 ⇒ 低完整性令牌）：
   - 走 `fabric.addMods`（运行时 remap）会 `IOException: …\.fabric\processedMods\…jar can't be written`；
   - 走 loom 构建会 `Failed to setup Minecraft, java.nio.file.ReadOnlyFileSystemException`（notes/349）。

服务端**不需要**装这三个（EMF/ETF 都是 `environment=client`，资源包只影响客户端渲染）。

## 7 已知边界（不该惊讶的事）

1. **没玩家在线 ⇒ 整条站台收走**（半径闸门）。这是有意的：没人看的人纯白花客户端与网络。
   读数里会写清"是半径收走的、不是没铺出来"。
2. **`NoAI` ⇒ 没有走路动画**。客流是装饰：放开 AI 它们会自己寻路走下站台掉到轨道上。
   要"走动"得另做（给站台内的往返路径 + 我们自己的移动逻辑，或加护栏）。
3. **村民会被推动**（玩家挤、别的实体推）⇒ 每拍按记忆格拉回；`站位漂移` 计数就是它。
4. **职业 = 无业**（`VillagerProfession.NONE`）⇒ 右键**不开交易界面**；也是静音 + 无敌 + 不消失。
5. **方块 `mtr:crowd_villager` 还在**（手动摆放 / 对照用），但生成器不再使用它；
   升级到实体方案时，世界里遗留的旧方块会被自动扫掉（候选格每拍查一次 + 扫描时登记非候选格）。
6. **上限是"同屏人数"的闸门，不是"站台容量"**：想让站台更挤就抬 `platform cap`。
   实测量级（2026-10-05）：**≤500 只服务端无感**、**95 只连客户端都量不出差别**；
   而一次性 5951 只时连服务端都会 `Can't keep up`（290 ticks behind）。所以"要不要更挤"是体感问题，不是性能问题。
7. **同位置的帧数落差先别归因给村民**：实测在同一个站位把 95 只全收走，帧数没有变化 ——
   110（空旷地）→ 30（站台）的落差是**车站方块 + 光影**的账。要判断任何"新东西吃不吃帧"，
   都得在**同位置、镜头不动**的条件下做 A/B。

## 8 实机验证记录（2026-10-05，真 dev 服务端 + RCON）

| 验的什么 | 怎么验 | 读数 |
|---|---|---|
| 客量落盘跨重启 | 设 60% → RCON `stop` → 起服 → `platform list` | 仍 `客量=60%`（`platforms/<hex>` 里读回来的） |
| 人数随客量缩放 | 60% → 40% | 应有 241 → 162；`/fill ... replace mtr:crowd_villager` 独立数也是 **162** |
| 自愈（被清掉会补回） | `/fill` 清掉 162 → 等一拍再数 | 又是 162 |
| 孤儿/残留清理 | 手动 `/setblock` 一个"不该有人"的格子 → `platform scan` | 报告 `残留=1` → 12 秒后被自动收走（`Test passed`） |
| 旧方块清理 | `/fill 792 66 1798 1032 66 1798 air replace mtr:crowd_villager` | 清出 114 + 127 = 241 个旧方块；已加"候选格每拍查"防复发 |
| 上限截断 | `platform station 上水村 100` | 候选 220 → **应有 48**（报告写明"客量要 220 人，被上限 48 截断"） |
| 半径闸门 | 无人上线时 `platform scan` | `实有=0`，并写明"半径 96 格内没玩家 ⇒ 整条站台收走" |
| 实体账本（按 tag 回收） | 手动 `/summon` 一只带 `mmtr_crowd*` tag 的村民 → 等一拍 | 被收走（`execute if entity @e[tag=mmtr_crowd]` → Test failed） |
| **真实规模到位（有玩家在线）** | 玩家（Shuisoi）站在上水村，`platform scan` + RCON `execute if entity` | 应有 48/47 = **实有 95**，多出 0、漂移 0；RCON 独立数也是 `count: 95` |
| **服务端成本 vs 实体数**（`/debug start|stop` 读 TPS，无人在线） | 0 / 100 / 300 / 500 只 NoAI 村民 | 20.02 / 20.03 / 20.02 / 20.03 —— **≤500 只服务端无感** |
| **客户端成本（同位置 A/B）** | 玩家在上水村原地不动：`platform station 上水村 0`（0 只）↔ `100`（95 只） | **帧数没区别** ⇒ 95 只村民的客户端代价量不出来；该站 110→30 的落差是**车站方块 + 光影**本身的账，不是客流 |
| 反面数据（别这么干） | 一次性 summon **5951** 只测试村民 | 连**服务端**都追不上（日志 `Can't keep up! ... 289 ticks behind`）—— 四位数实体时服务端还要为在线玩家做实体跟踪，这条量级的闸门是必须的 |

> 结论：**闸门（48/站台）不是为了压客户端帧率才存在的**（95 只量不出来），
> 而是为了给"病态输入"（超长站台、全图 100%、脚本误设）兜底。
> 想让站台更挤可以抬 `platform cap`；抬之前记住上面那条反面数据。

**待人工目视**（自动化验不到的部分）：玩家在半径内时村民实体的**外观与站位**
（原版模型 + FA 动画、朝向轨道、7 种群系花色、不会乱走、穿过人群不被卡）。
