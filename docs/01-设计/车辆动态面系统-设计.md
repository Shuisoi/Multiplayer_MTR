# 车辆动态面系统 · 设计（MMTR Dynamic Vehicle Faces）

> 状态：**F0 地基 / F1 作者可用 / F2 工作室 / F3 复杂业务 已落地**；
> **F4 曾做过的那条第三方代码扩展路径已按用户口径整条删除**（作者路径全部内置，
> 见 §2、§8、§9 与 notes/363；过程记录在 notes/361，仅存记录）；
> 面文档格式的权威表在 [`车辆动态面-面文档格式.md`](车辆动态面-面文档格式.md)。
> 口径来源：用户 2026-10-02「动态的东西会很多，需要构建一个子系统专门处理这些动态面的显示以及绘制器，
> 否则其他构建者或者车体作者难以制作车辆资源包」；方案选定为**方案 A**。

## 1. 这个子系统解决什么

一块"动态面"= 车体上的一块平面 + 上面**随车状态变化**的内容（水牌、下一站牌、车厢 PIS 内屏、
司机台综合屏、灯箱、故障提示……）。在它之前，这类东西每来一个需求就得改一次客户端 Java：
版式写死、条件只能"有值就画"、动画没有、车体作者想加一块屏也无从下手。

这个系统要把三件事分开，且**每一件都有稳定的接口**：

| 谁 | 只负责 | 产物 | 需要会什么 |
| --- | --- | --- | --- |
| 车体作者 | 牌**多大、在哪、朝哪** | Blender 里的 `mmtr_*` 锚点 | Blender |
| 资源包作者 | 牌上**画什么、什么时候画** | 锚点 JSON 里的 `faces` 段 | JSON（逻辑用 JSONLogic） |
| 引擎维护者 | 内置能力（画法 / 算子 / 过滤器 / 字段）与数据**镜像** | 内置元素与字段 + 稀疏补丁 | 引擎 |

**作者侧只有前两行**：写数据的人**永远不需要装任何模组、永远不写 Java**（见 §2）。

## 2. 信任边界（★ 方案 A 的核心决定）

**资源包是不可信内容**：它会从服务器、从别人的整合包进到玩家客户端。所以：

- 资源包里**只有声明式数据**（JSON + 贴图），由本系统的求值器解释：没有反射、没有 I/O、
  没有类加载、有预算上限（≤512 节点 / ≤24 层）。**客户端从不执行资源包里的任何代码**，
  恶意资源包能做到的最坏情况是"这块牌画歪了"；
- **代码级能力只由 MMTR 自己内置**：9 种元素、32 个算子、8 个模板过滤器、内置字段表就是全部，
  都由引擎与模组自己实现（加一个要改哪些文件、代价多少，见 §8）；
- **作者侧不引入任何代码**：车体作者 / 资源包作者只写 `faces` 段与贴图，因此**不需要装任何模组、
  不需要写 Java**。缺什么就按 §8 提需求，由引擎把它做成内置；
- **这条边界是单向的**：越界的东西（第三方代码）**不进**这套系统 —— 既没有"作者自己加一个"，
  也没有"装个模组来补"这一级。明确**不做**：在资源包里执行 JS/脚本（那是把资源包变成
  任意代码执行通道）。

## 4. L0 · 数据接口

字段登记表就是**给外人看的接口**，一行一个量：名字 / 类型 / 单位 / 来自哪个镜像字段 / 更新节拍 / 说明。
导出的 `tools/face-studio/fields.json` 供 web 工作室做自动补全，并由用例**逐字**比对（防漂移）。

**四方核对**（`MmtrFaceFieldsTests`）：登记表 ↔ 取值口 `case` ↔ 引擎 `DYNAMIC_KEYS`（节拍）↔ 导出文件。

**加一个新量 = 四步曲**：
1. 引擎侧算出来并进镜像（`schema/data/vehicle.json` 加字段；写的地方标脏；每 tick 变的量必须进
   `VehicleSyncPatch.DYNAMIC_KEYS`，否则客户端只在整份快照时更新 —— notes/257 的"读数不实时"）；
2. `MmtrVehicleFaceSource` 加一个 `case`；
3. `MmtrFaceFields` 加一行；
4. 重生成 `fields.json`（用例不一致时会写出 `fields.json.actual`）。

**两条口径**：取不到 = 不放进去；空串也算没有。于是 `var`／`missing`／模板三个用法对"没有这个量"的理解一致。

## 5. L1 · 面文档（作者写的东西）

```json
"faces": {
  "<锚点名>": {
    "background": "#FF101418",      // 缺省透明（牌底交给模型）
    "textColor":  "#FFF2F4F6",      // 文本元素没写 color 时用它
    "pxPerMetre": 512,              // 缺省 512
    "side":       "normal",         // normal（朝读它的人，默认）/ driver（仪表面板）/ both
    "require":    {"!!": [{"var": "pid.service"}]},   // 整块面画不画
    "vars":       {"arriving": {"<": [{"var": "lzb.targetM"}, 200]}},
    "elements":   [ … ]
  }
}
```

**★ 面名 = 锚点名**：模型里那个锚点叫什么，文档就写在 `faces.<锚点名>` 下。由此：

- 再加一块牌**不用改客户端**（打包器给锚点 + JSON 写文档）；
- "哪块牌归谁画"有唯一答案：**有文档的锚点归面系统，没文档的仍归老渲染器**
  （`MmtrPidBoard` 会跳过有文档的锚点）⇒ 把水牌切到面文档是**纯资源包动作**。

### 5.1 元素（9 种；键与缺省的权威表见 `车辆动态面-面文档格式.md` §5）

| type | 键 | 说明 |
| --- | --- | --- |
| `text` | `text`（模板）、`x,y,size`、`align`、`color`、`shrinkToFit`（默认 0.9）、`when` | 取不到内容 ⇒ 不画（不是画空位） |
| `rect` | `x,y,w,h,color` | 实心矩形 |
| `roundRect` | 同上 + `radius` | 圆角矩形 |
| `line` | `x,y,x2,y2,width` | 直线（圆头） |
| `circle` | `x,y,radius` | 实心圆 |
| `arc` | `x,y,radius,start,end,width` | 圆弧（角度逆时针从 +X 起） |
| `gauge` | `x,y,radius,start,end,max,ticks,labelEvery,lineWidth,needle,needleColor,needleWidth,needleLength` | 表盘 + 指针；指针值来自 `needle` 表达式（默认车速） |

几何一律**比例**：`x/w` 乘牌宽，`y/h/size/radius` 乘牌高 ⇒ 同一份文档贴到任何尺寸的牌上都等比。

### 5.2 模板与过滤器

`"开往 {pid.terminus}"`；过滤器：`upper / lower / trim / int / num:N / pad:N / len / default:文本`。
`{{` `}}` 是花括号转义。数字默认不写小数点后缀（`1.0` 写成 `1`）。

## 6. L2 · 逻辑层：JSONLogic 子集

- 算子：`var`（点号路径 / 数组下标 / 缺省值）、`if`、`and`、`or`、`!`、`!!`、`==`、`!=`、`===`、`!==`、
  `<`、`<=`、`>`、`>=`、`+`、`-`、`*`、`/`、`%`、`min`、`max`、`cat`、`substr`、`in`、`missing`、
  `missing_some`、`?:`、`some`、`all`、`none`、`filter`、`map` —— 就是全部（清单以
  `MmtrFaceLogic.operators()` 为准，加一个要走 §8 那条内置改动）。
- 口径：真值 = `null`/false/0/空串/空数组为假（`"0"`、`"false"` 是**真**）；两边可数字化按数字比；
  **有一边 null ⇒ 比较一律假**（不把缺数据当 0）；类型不匹配的算术 ⇒ null。
- 预算：≤512 节点、≤24 层（超了抛，调用方跳过那一个元素）。
- **共享测试向量** `tools/face-studio/conformance/logic.json`（68 条）：Java 端两种数据形态各跑一遍，
  web 工作室的 JS 端跑同一份文件 —— "浏览器里试出来的条件进游戏还是那个结果"因此可证伪。

## 7. L3 · 绘制器

- **节拍**：数据每帧每车一份（同一帧十几块面读同一份）；贴图只在"文档身份 + 数据 + 牌面尺寸 + 像素密度"
  签名变化时重画；四边形每帧照画。
- **画在哪一侧**由文档的 `side` 说（`MmtrPanelQuad.drawSide`）——notes/357 那个"背面剔除让整块牌看不见"
  的坑从此是数据可配的。
- **错一处不毁一块面**：条件求值抛异常 / 类型不认识 / 模板写坏 ⇒ 跳过那一个元素 + 记一次日志。
- 元素画法就是"缺画法"的落点：`MmtrFaceElements` 里的 `PAINTERS` 是**内置的 9 种**（`text`/`rect`/
  `roundrect`/`line`/`circle`/`arc`/`gauge`/`image`/`foreach`），画不出新东西时的唯一出路是
  **提需求让引擎加一种内置元素**（改动点与代价见 §8）。

## 8. 升级阶梯（"复杂 UI"卡住时走哪条）

**先把口径钉死**：作者**只写数据**（`faces` 段 + 贴图），**不装任何模组、不写 Java**。
能力只有内置那一套 —— 9 种元素、32 个算子、8 个模板过滤器、内置字段表。
所以"卡住"只有一个出口：**向引擎提需求，由引擎把它做成内置**。没有"自己加一个"，
也没有"装个模组来补"这一级 —— 第三方代码不进这套系统（理由见 §2）。

| 级 | 卡在哪 | 找谁 | 做法 | 判据 |
| --- | --- | --- | --- | --- |
| 1 | 能用现成元素/条件表达 | 你自己 | 写 JSON | 面文档用例 + 自检 P1..P9 |
| 2 | 缺**算子/过滤器** | 引擎 | 做成内置算子/过滤器（见下面「新增一个内置算子/过滤器」那条） | 共享向量**含负例** + 工作室清单与 Java 同序一致 |
| 3 | 缺**画法** | 引擎 | 做成内置元素类型（见下面的改动点清单） | 元素用例 + 离线出图 + 自检认得这个类型 |
| 4 | 缺**取值** | 引擎 | 走**加字段四步曲**（§4）：引擎算出来并进镜像 → 取值口加 `case` → `MmtrFaceFields` 加一行 → 重生成 `fields.json` | 四方核对用例绿 |
| 5 | 跨面协同（整列车同步翻页等） | 引擎 | 需要面级 state + 数据提供者 | **还没有这条路**，只有"文档级 `vars` + 数据字段" |

每一级都**不改资源包格式**：做出来之后，作者侧仍然只是 JSON 里多一个字段名、一个算子名或一个 `type`。
第 2 级的"缺字段"与第 1 级的区别值得写清：第 1 级里作者**可以拿已有字段在文档里算**
（`vars` + 算子，纯 JSON，谁都不用动）；第 2 级是"**引擎里多一个权威量**"（数据从服务器来，
要动同步与镜射），**不是**同一件事。

**加一个内置的东西要改哪些文件、代价多少**：

| # | 改哪 | 改什么 |
| --- | --- | --- |
| 1 | [`schema.json`](../../tools/face-studio/schema.json) | `elementTypes` 加名字 + `sections` 加这个类型的键表（键名 / 类型 / 缺省） |

| 3 | [`MmtrFaceElements.java`](../../game/fabric/src/main/java/org/mtr/mod/render/panel/MmtrFaceElements.java) | `PAINTERS` 加一条 + 写一个 `paintXxx(...)` 画法 |
| 4 | 工作室 JS：[`painter.mjs`](../../tools/face-studio/painter.mjs) · [`schema.mjs`](../../tools/face-studio/schema.mjs) · [`app.mjs`](../../tools/face-studio/app.mjs) | 依次是 `ELEMENT_TYPES`、内嵌兜底缺省、属性面板（多数情况跟着 `schema.json` 自动出来） |

  `MmtrFaceText.filters()` 的实现、[`verify_face.js`](../../tools/anchor-check/verify_face.js)
  里那两张清单（必须**逐字一致**，`MmtrFaceToolingTests` 钉着）、工作室
