# 07 驾驶输入与列车控制模型（三手柄规格 v2）

> 状态：**规格定稿（2026-09-19）**，本轮落地"输入侧 + 引擎控制模型"，客户端键位已接、HUD/面板仍留 B6。
> 上一版（v1，单手柄 notch + HID 轴）见文末 §12 附录；本版是 BR101 这类**三手柄机车**的语义真源。
>
> 用户口径（本轮逐项确认）：
> ① 原逻辑是 legacy 单手柄 **P7 B8**（7 牵引档 / 8 制动档，见 `MmtrSupport.controlFromLegacyPowerLevel`）；
> ② 新列车**三根手柄**＝定速巡航 + 油门（牵引与电阻制动集成、双向）+ 气制动；
> ③ 定速巡航：**步长 5 km/h、量程 0–160**（33 个定位），**AFB 只能削减牵引（不提升功率）+ 超速反向电阻制动/补气来保速**（LZB 只做向下限定，见 §2、§2.1）；
> ④ 油门：**1% 一档**，中央"关闭"、两侧各有独立"最小"档、其后 5%…100%（两侧镜像：牵引 / 电阻制动）；
> ⑤ 制动：**运行 / 1A / 1B / 2 / 3 / 4 / 5 / 6 / 7 / 8 / EB**（1A、1B 是弱档，力按档位查表）；
> ⑥ 换向仍是独立换向器，沿用引擎红线"只在停稳时可动"；三手柄不含它。

## 1. 三根手柄总览

| # | 手柄 | 取值 | 定位 | 谁说了算 |
| --- | --- | --- | --- | --- |
| H1 | 定速巡航（AFB） | `cruiseSpeedKmh` 0…160，**步长 5** | 33 位：0 = 关闭 | 设定值＝目标速度；AFB 只削手柄那份牵引（越接近削得越狠）、超速时反向电阻制动、必要时补气；LZB 向下限定 |
| H2 | 油门（Fahrschalter，牵引＋电阻制动） | `driveHandle` **−97…+97** | 中央 0 = 关闭；±1 = 最小；±2…±97 = 5%…100% | 定速关闭时＝司机要的牵引力/电阻制动力；定速在岗时 AFB 只削手柄那份牵引（**手柄关闭 = 牵引 0**），手柄的电阻制动侧仍是手动干预 |
| H3 | 制动（气制动） | `brakeNotch` 0…10（＝位置下标） | 0 运行 / 1 = 1A / 2 = 1B / 3…9 = 2…8 / 10 = EB | 气制动缸压力，按查表比例 + 建/缓解速率 |
| — | 换向器（独立小杆） | `reverser` −1/0/+1 | 后退 / 中立 / 前进 | 只在停稳时可动（引擎红线，`applyMmtrTravelReversed`） |

三根手柄互不排斥但在引擎里按**固定优先权**合成，见 §5。

## 2. H1 定速巡航（AFB）

- 量程 0…160 km/h，**每档 5 km/h**；`0` = 关闭（不干预）。客户端键位：**数字键 9 = −5、0 = +5**（暂定）。
- **语义（2026-09-23 第五轮修订 = 最终口径）**：
  - **AFB 只能削减，不能提升功率**（现场原话：「AFB 只能限制功率，不能提升功率，为什么现在一上车手柄为 0
    就会直接往前开」）⇒ **手柄关闭 = 牵引 0**，车不许自己走；手柄 20% = 最多 `300 kN × 20%`；
  - **动力手柄决定当前输出的力**：`牵引 = min(手柄牵引比例, clamp(afbGainPerMps × error, 0, 1))`
    —— AFB 越接近设定值削得越狠，但永远不会超过手柄那一份；
  - **定速的作用是限速/保速，不是自动驾驶起步**：要起步/加速必须司机推手柄（这是刻意的取舍：
    旧口径"AFB 自己加牵引"会让上车手柄为 0 的车自己开走）；
  - **超过设定速度时反向**：先电阻制动（`afbBrakeDecelPerMps × |error|` = 要的减速度），
    压不住的部分**由它补气制动**；补气与气制动手柄**取大耦合**（谁要得多听谁的，不合并也不吞掉司机的手柄）；
    这一半 AFB 可以"自己动手"（它只让车变慢，不违反"不提升功率"）；
  - 手柄的**电阻制动侧**仍是司机的手动干预（它一有诉求就走制动支）；想完全手动开车把定速关到 0；
  - `afbUsesHandleAsCap=false` 是**非符合口径的历史模式**（AFB 自己加牵引）—— 只作兼容保留，
    现场配置一律 `true`，缺省也是 `true`（notes/256）。
- 生效条件：`cruiseSpeedKmh > 0` ∧ 非紧急。保护/紧急由既有监督层（`evaluateMmtrProtection`、LZB 天花板）
  在控制器**之上**执行，AFB 不复制这套判断。
- **牵引联锁（两条都要）**：① 气制动手柄离开"运行"位（**刚拉到 8 档那一拍缸压还是 0**，不能让它偷一会儿牵引）；
  ② 缸压还没排空（手柄已回"运行"、或 AFB 自己补的气）—— 残余缸压是真在刹车，不能丢。
  这两条同时实现了"司机一拉闸就没有牵引"。
- 调节律汇总（`ThreeHandleDriveController`，纯比例，`error = target − v`，`门限 = afbBrakeThresholdMps`）：
  - `error > 门限` → 牵引 `= min(手柄牵引比例, clamp(afbGainPerMps × error, 0, 1))`（手柄关闭 ⇒ 0）；
  - `error < −门限` → 要的减速度 `a = afbBrakeDecelPerMps × |error|`；电阻制动出 `min(需要, 可用)`，
    缺口折成缸压补气：`缸压 = (a×惯性质量 − 电阻制动力) / 常用制动力`；
  - 其余（|error| ≤ 门限）→ 惰行（只受运行阻力）。
  - 旋钮：`afbGainPerMps`（默认 1.0 /(m/s)）、`afbBrakeDecelPerMps`（默认 0.5 (m/s²)/(m/s)）、
    `afbBrakeThresholdMps`（默认 0.05 m/s = 0.18 km/h）、`afbUsesHandleAsCap`（默认 **true**）。
- AFB **会**用气制动（"Fahr- **und Brems**steuerung"）：定速低于当前速度、电阻制动一个人压不住时它补气；
  想停车仍由司机拉制动手柄（AFB 只保速，不会替你停）。

### 2.1 定速与 LZB 的耦合（2026-09-23 现场补）

- **定速值是正常设定，LZB 只做"向下限定"**（用户口径：「AFB 速度正常设置，需要 LZB 来进行向下限定」）：
  `有效天花板 = min(LZB 天花板（= min(线路限速, 车底限速)）, 定速设定值)`。
  - 定速低于线路限速 ⇒ 车稳在**定速**，LZB 不干预；
  - 定速高于线路限速 ⇒ 由 **LZB** 把它压到线路限速（下一段限速更低时，照旧由 LZB 包线提前收）。
- **为什么必须有这一条**：LZB 区段（限速 ≥101 km/h 的轨）的**手动**驾驶走的是"包线 + 天花板"的**简化模型**，
  不经过 `ThreeHandleDriveController`（AFB 那套）。缺了这句，定速 20 + 手柄 97 的车在 120 的 LZB 轨上
  会一路涨到 91.5 km/h 还在涨 —— 现场原话就是"定速没用"。
  用例：`MmtrLzbSupervisionTests.theSetSpeedAndTheLzbCeilingAreCoupled`（定速 60 → 稳在 60；定速 150 → 不超过 120）。

## 3. H2 油门手柄（牵引＋电阻制动，双向）

位置 p ∈ [−97, +97]，1% 一档：

| p | 位置 | 牵引比例 | 电阻制动比例 |
| --- | --- | --- | --- |
| 0 | **关闭** | 0 | 0 |
| +1 | **最小** | `driveMinRatio`（默认 0.02） | 0 |
| +2 … +97 | 5% … 100% | `(p + 3) / 100` | 0 |
| −1 | **最小** | 0 | `driveMinRatio` |
| −2 … −97 | 5% … 100% | 0 | `(|p| + 3) / 100` |

- 校验：`p = +2 → 5%`，`p = +97 → 100%`；`+1` 的 2% 低于 5%，这就是"最小"独立成一档的原因。
- 牵引：`MmtrPhysics.tractionAcceleration(type, ratio, v)`（恒力矩到折点、其后恒功率 1/v、再减运行阻力）。
- 电阻制动：`a = rheostaticBrakeDecelerationMps2 × ratio × fade(v)`，
  `fade(v)` 在 `rheostaticFadeKmh`（默认 10 km/h）及以上为 1，往下降到**其一半**（5 km/h）线性归零，
  再低**完全失效**。
  **低速失效是刻意的**：真车电阻制动在低转速下建立不了力矩，想停住必须用气制动 ——
  这也是"两根手柄要配合"的根据。若把衰减写成 `a ∝ v`，列车会以指数律渐近停住，这条就成了一句空话。
- 电阻制动与气制动**叠加**，但**没有自动补气**（电阻制动衰减时不会自动代以气制动）——那是司机的活。
- **牵引力增速控制（2026-09-25 口径，notes/265）**：牵引力**上升与下降**都受一个斜率上限约束，
  缺省 **30 kN/s**（`tractionRampNPerSecond`，`0` = 不限速）—— 用来消掉"一推杆就满推力"的冲力：
  BR101 推满档要 10 s 才到 300 kN（`300 kN ÷ 30 kN/s`），不再是第一拍就满。
  - 限的是**力**：把目标比例折成目标力（`TrainPhysics.tractiveEffortN`）再限斜率，所以高速恒功率段
    也是 30 kN/s（同一比例的力在 200 km/h 只有 115 kN）；
  - **方向不豁免**：回杆、AFB 削力、气制动联锁、紧急制动都按同一斜率回落；回落期间残余牵引**真的在推车**，
    所以合力改成 `牵引 − 气制动 − 电阻制动 − 运行阻力`（四力同号相加）—— 旧的"按分支只算一支"会把
    残余牵引整段丢掉；
  - 后果写明：满牵引（300 kN）时拉闸/EB，头几秒合力仍是**正的**（牵引还没退完），这是本口径的直接结果
    （要立刻切零就把速率配成 0）；
  - 状态量与"等效比例"：`ThreeHandleDriveController.getAppliedTractiveEffortN()` 是本拍真正施加的力，
    `getLastTractionRatio()` 由它反解（`F / F(1,v)`，比例在牵引曲线里是一次齐次的，反解无损），
    于是 HUD/日志/镜像看到的仍是"实际出力"；
  - 上一拍的力是**控制器状态**：客户端镜像/换端后从 0 起爬，头几秒与服务端略有出入（与气制动种子同类问题）。

## 4. H3 制动手柄（气制动）

位置表（下标即 `brakeNotch`，比例可配 `brakeRatios`）：

| 下标 | 位置 | 制动缸目标比例 | 备注 |
| --- | --- | --- | --- |
| 0 | 运行 | 0.00 | 缓解：管压回充、缸压排空 |
| 1 | 1A | 0.05 | 弱档（低速微调） |
| 2 | 1B | 0.12 | 弱档 |
| 3 | 2 | 0.20 | |
| 4 | 3 | 0.32 | |
| 5 | 4 | 0.44 | |
| 6 | 5 | 0.56 | |
| 7 | 6 | 0.68 | |
| 8 | 7 | 0.80 | |
| 9 | 8 | 1.00 | 全常用制动 |
| 10 | **EB** | 紧急 | 忽略速率直接按 `emergencyDecelerationMps2`，并置 `emergency` 标志 |

- **建压/缓解不是瞬时的**：缸压按 `airBrakeApplyRatePerSecond` / `airBrakeReleaseRatePerSecond` 追目标值，
  管压同步镜像（供 HUD 与镜像种子）；这与既有 `AirBrakeController` 的"降保升"同一套参数、同一套口径。
- **制动减速度 = `serviceBrakeDecelerationMps2 × 缸压 + 运行阻力`。**
- **气压口径（2026-09-25，notes/266，设计见 `制动系统-气压与制动力模型-设计.md`）**：
  三手柄机车改走**真 bar 语义**（`PneumaticBrakeSpec`，随车底 JSON + 镜像串下发）：
  - 档位 → **列车管目标**：运行 5.2 / 1A（初制动）4.6 / 1B 4.4 / 2 4.2 / 3 4.05 / 4 3.9 / 5 3.8 /
    6 3.7 / 7 3.6 / 8 3.5 / EB 3.0 bar（定压标称 5.0 bar）；
  - 分配阀：`缸压 = clamp(2.5333 × (5.2 − 管压 − 0.2 灵敏限), 0, 3.8 bar)`（EB 4.2）；缸簧 0.30 bar
    以下不出力；
  - 时间：充风 0.35 / 排风 0.85 bar/s、缸压建/缓 1.30 / 0.95 bar/s（**实测 8 档建压 3.1 s、
    松闸到牵引联锁放开 3.9 s**）；
  - **制动力锚改成 UIC 制动重率反推**（`F = m_equiv·(0.0065λ + 0.12)`，λ = 制动重量/车底质量 × 100%）：
    BR101 = 102.2 kN（旧铭牌 150 kN）、P1 客车 = 43.7 kN（旧 70 kN）；
  - 闸片摩擦随速衰减 `μ_b = 0.39 − 0.00045·v_kmh`（200 km/h ⇒ 0.30）⇒ 8 档在 200 km/h 只剩 78.6 kN；
  - 电制动补上**高速恒功率**段：150 kN 到 153.6 km/h，之上按 6.4 MW/v（200 km/h ⇒ 115 kN）；
  - **电空混合（P3，默认开）**：管压那份是司机诉求，**电制动先吃饱、机械补缺口、EP 阀只削不加**
    （司机电阻制动手柄与自动电制动**取大不相加**）—— 总力不变，但**缸压会被削低甚至到 0**，
    所以"缸压不等于分配阀那档"是正常的（那是*诉求*，不是最终缸压）；
  - **黏着截断 + WSP（P4）**：制动力合计过 `μ_brake(v)=7.5/(v_kmh+44)+0.161`（与天气/撒砂取小）的上限；
    WSP 恒开（钳到上限），关掉则断崖到 `wheelSlipMu`。新标定下干轨/湿轨**吃不穿**，只有落叶/油污才截。
  旧的 `brakeRatios` / `airPipe*RatePerSecond` / `airBrake*RatePerSecond` 仍在，只喂 legacy 模式
  （NOTCHED / STEPLESS / AIR_BRAKE）与逐车气路：**不写 bar 键的车底逐位走旧模型**（零回归）。
- **档位只是数据（notes/270，P6）**：三种控制方式（三手柄 / 有级 / 无级）都把档位折算成**同一个归一化诉求**
  交给同一个制动模型：三手柄 = `档位/(档位数−1)`（级位表逐位，含紧急位）；有级 = `档/档数`；
  无级 = 制动轴 0…1 —— 后两者再乘 `getServiceDemandLimit()`（级位表"全常用"那一档的位置比例，
  默认 0.9），因为**表尾的 3.0 bar 是紧急/快排级，不该被"连续制动诉求"够到**：无级手柄推到底、
  货车最后一档都停在全常用 3.5 bar，紧急由保护层或三手柄的紧急位显式给。
  实测三种方式在同一诉求下逐位同一个力（20.8/35.6/…/102.2 kN，`MmtrBrakeModelReuseTests`）。
- **手柄到 EB 位与"外部紧急"（保护层）同一个出口**：两者都走紧急减速度，`DriveOutput.emergencyBrake = true`。

## 5. 合成优先权（每 tick，从上到下第一条命中即生效）

| 序 | 条件 | 结果 |
| --- | --- | --- |
| 1 | 紧急（EB 位 / 保护层） | 紧急减速度，牵引与电阻制动全部封锁 |
| 2 | 气制动 > 运行 位 | 气制动生效；AFB **暂停**（设定值保留）；电阻制动仍可叠加（司机手柄） |
| 3 | AFB 生效（§2） | AFB 调牵引/电阻制动；牵引受油门手柄上限约束 |
| 4 | 加油门（p > 0） | 纯牵引（含"最小"） |
| 5 | 拉电阻制动（p < 0） | 纯电阻制动，**低速衰减**（§3） |
| 6 | 都没有 | 惰行（只减运行阻力） |

## 6. 状态与配置字段

### 6.1 `ControlState`（引擎侧统一输入状态）

| 字段 | 含义 | 备注 |
| --- | --- | --- |
| `driveHandle` | H2 位置 −97…+97 | **新增** |
| `cruiseSpeedKmh` | H1 设定值 0…160（步长 5） | **新增** |
| `brakeNotch` | H3 位置下标 0…10 | 复用：THREE_HANDLE 按查表解释，NOTCHED 仍按 `notch/brakeNotches` |

  引擎把它落到被占用那一端的镜像（`mmtrLightA` / `mmtrLightB`），渲染侧只查表。

### 6.2 `ConsistType`（服务端 JSON，新增 `THREE_HANDLE` 控制模式）

**车底是按车选的，不是按维度**（`MmtrCarTypeResolver`）。两条来源，按优先级：

1. 车厢**声明的**车底 id（资源包的 `mmtrConsistTypeId`，随 OBJ 车列元数据进来）；
2. 注册表里的**车型映射** `carTypeIds`：`{"br101": "br101_three_handle"}` —— 不必重打包就能把已有车型接到新车底上；
3. 都解析不出来 → 维度缺省 `defaultConsistTypeId`（**零回归**：没配过的车一个字节不变）。

一列车是一个刚体、纵向动力学只有一套参数，所以**第一节能解析出车底的动力车说话**（机车/动车组），
没有动力车才取第一节能解析出的车厢；连挂/解挂换了说话的车，控制器与气制动状态会重解一次
（判据是"决定车底的那节车的型号|车底|动力位"）。

### 6.3 谁能操纵（准入判据，2026-09-19 放宽）

| 判据 | 内容 |
| --- | --- |
| 引擎权威 | `Vehicle.canTakeMmtrControl(uuid)`：**骑在这辆车上、并且是司机位**（ride 包的 `isDriver`） |
| ~~钥匙~~ | **不再是前提**：`holdsMmtrCabKey` 从操纵判据里去掉（用户口径「操作手柄不需要手里握着钥匙」）。它保留下来只回答"钥匙在谁手里"（system 钥匙 / 乘务员钥匙的区分） |
| 占用锁 | 一列车上同时只有一个司机：没人持有 override 时谁先动手谁拿到；持有者**还在司机位上**时别人抢不走 |
| 交还判据 | **司机位空了才交还**（人走开 / 下车 / 断线）。拔钥匙**不再**断牵引 —— 否则站在司机位上、车正在走的人会因为"钥匙被人拔了"而突然失去制动 |
| 任务闸门 | 无任务不得操纵（T4 策略开关，默认关） |
| 客户端上报 | `isDriver = mmtrCabConfirmed \|\| MmtrDriverSeat.isAtControls()`，**只在变化时**发包 |

- 客户端的"我在司机位"判据与雨刷的 `driverOnBoard` 共用 `MmtrVehicleAnchors.nearestCab`（**唯一一份**），
  所以"雨刷会动的地方"和"能操作手柄的地方"永远指同一个驾驶室。
- **"离哪个驾驶室最近"还要加一道沿车长的距离门槛**（`MmtrDriverSeat.CONTROLS_RADIUS_M = 2.0 m`，
  量到该驾驶室座位点）：否则车厢里任何地方都算"坐在司机位上"，乘客在车厢里按 A/D 会被摘键（走不动）
  还会去推手柄。实测：整间司机室都在 2.0 m 内（SAF420 风挡离座位 1.53 m、BR101 1.28 m），
  车厢中部离座位 7.7–8.2 m。见 notes/353 §5。

## 7. 键位（本轮；可在控制菜单改）

> **2026-09-29 改版（用户指定）**：键位换成"左手油门、右手制动"的模拟器布局，并加灯光键。
> 与原版同键的那些（A/D 平移、Q 丢弃、F 交换副手、L 进度页）由 `ClientInputDecoupleMixin` **只在坐在司机位上时**
> 从原版动作上摘下来 —— 详见 notes/352 与本文档 §7.3。
>
> **2026-10-01 补课（notes/353）**：原版的键盘事件**一个物理键只发给一个绑定**（`KEY_TO_BINDINGS`，
> 赢家由 HashMap 顺序决定）—— 于是撞键里"输掉"的那一个**收不到按键**：实机表现为"在车外按 A 走不动"
> （A 的赢家是 MMTR 的油门键）与"按 L 弹进度页、灯光却没换"（L 的赢家是原版的进度页）。
> 现在由 `MmtrKeyEventFanout` 在 `setKeyPressed` 上把事件补发给全部同键绑定，两个动作都能收到。

| 键 | 动作 |
| --- | --- |
| A | 油门手柄往**牵引**侧一步（+1%，长按 >0.25 s 后按 20 步/秒扫） |
| D | 油门手柄往**电阻制动**侧一步（−1%，同样长按扫） |
| ' | 气制动 **+1 档**（施加；一直按到 10 = EB） |
| ; | 气制动 **−1 档**（缓解，最低回"运行"） |
| R | 定速巡航 **+5 km/h** |
| F | 定速巡航 **−5 km/h**（到 0 = 关闭） |
| Q | 响应键（AWS 确认 / 解除闯信号触发的紧急制动） |
| L | **灯光开关**：循环本端档位（动车组 尾→日→夜；机车 关→尾→日→夜） |
| **W / S** | 换向器 **上（前进）/ 下（后退）**（±1，停稳才生效）——2026-10-01 用户从 ←/→ 改过来（JourneyMap 的全屏地图也占着 ←/→） |
| G | 进/出驾驶室（既有，B2） |
| J | 雨刷（既有，W4） |
| K | 连挂/解挂（既有，C7） |

- "1% 一档 + 96 档"必须能长按扫，否则推满要按 96 次 —— 单击 1 档、长按 0.25 s 后 20 档/秒。
- **单手柄车底（有级 / 无级 / 降保升 / 缺省兜底）：A/D 就是那根杆的键**（A 往牵引侧一步、D 往制动侧一步，
  推到底再一格是 EB）；`'` / `;` **也作用在同一根杆上**（`'` 往制动、`;` 往牵引，与真车"施加/缓解"同向）
  —— 两对键都能推它，是为了避免"换了一辆车底，按了半天没反应"。
  判据：`isSingleHandle()` = **除 `THREE_HANDLE` 之外的一切**（含"镜像还没到"），见 notes/352 §3.3。
- **操作不需要钥匙**（用户口径 2026-09-19）：键位在**坐在司机位上**时即产生控制意图，
  判据是 `MmtrDriverSeat`（沿车长的位置离哪个驾驶室的玻璃最近 **+ 离该驾驶室座位点 ≤ 2.0 m**，
  与雨刷 `driverOnBoard` 同一条"哪个驾驶室"的规则），
  **不要求按 G 申领驾驶室、也不要求手里握着钥匙**；引擎侧对应地不再要求 `holdsMmtrCabKey`（见 §6.3）。
- 坐在司机位上**第一次动手柄**时会自动把该驾驶室接管过来（`MmtrCabInteraction.claimSeatWhenDriving`，
  就是 G 键那条命令）—— 因为"哪一端在前"由被占用的驾驶室决定，不接管的话坐在 A 端的人会倒着开。
  刻意不在"坐下"时就接管：那会让"坐到 AI 车的驾驶室里看看"把自动运行停掉。
- 离开司机位时客户端把三手柄归到 **关闭 / 运行 / 定速 0** 并发最后一次状态，避免"人走了车还带着旧手柄"；
  **换向器不动**，**灯光开关也不动**（灯是世界的状态，由引擎在司机位空了时把白灯落回尾灯，见 §7.3）。

### 7.3 驾驶室里的按键解耦（2026-09-29）

| 项 | 内容 |
| --- | --- |
| 判据 | `MmtrDriverSeat.isAtControls()`（与"能不能推手柄"同源：骑车 + 沿车长离该驾驶室座位点 ≤ `CONTROLS_RADIUS_M`）+ 没有界面打开，100 ms 缓存 |
| **摘谁** | **按"撞键"判，不点名**：一个绑定被摘掉 ⇔ 它不是 `key.mmtr.*` **且**它**当前**绑定的键位与 MMTR 某个键相同（`MmtrInputDecouple.blocks`） |
| 实现 | `ClientInputDecoupleMixin`（注入 `KeyBinding.isPressed` / `wasPressed` 的 HEAD，读 `getTranslationKey()` + `getBoundKeyTranslationKey()`） |
| 为什么不是点名法 | 第一版只点了 left/right/drop/swapHands 四个原版键，**实机当场漏掉 `key.advancements = L`（按 L 弹出进度页面）**；对实机 `options.txt` 一核，还撞着 JourneyMap 的一整排默认键（B/J/N/H/←/→）。见 notes/352 §3.1 |
| 缓冲 | 被摘掉的点按键连 `timesPressed` 一起清 —— 否则人一下车就把驾驶室里按下的那一次迟发出来 |
| 界面开着 | 一律不摘（打字优先）；同时 `MainRenderer` 在界面开着时不 tick 那些字母交互键（K/G/B/Y/U/N/H/J），`MmtrDriveInput` 也跳过"读键"（但保留每秒补发，占用锁靠它维持） |
| 可见性 | 每种被摘的绑定**说一次**（`[MMTR-KEY]`），第一行报 MMTR 现在的键位表 —— 否则"驾驶室里 L 不弹进度页面"看起来和"按键坏了"一模一样 |
| **事件流** | 原版一个物理键只把事件发给 `KEY_TO_BINDINGS` 里的那一个绑定 ⇒ 撞键里输掉的那个**收不到**。`MmtrKeyEventFanout` 在 `KeyBinding.setKeyPressed` 的 HEAD 上把状态写给 `GameOptions.allKeys` 里**所有**同键绑定（`setPressed` 是公开 setter，赢家随后被原版再写一次同样的值）；点按计数 `timesPressed` 私有，**不碰**，改由 mixin 在 `wasPressed` 上用补正过的 `pressed` 造一次上升沿（每次按键只报一次）。见 notes/353 |
| **灯光开关是边沿型** | 引擎按**来源**（司机 UUID / 引擎内部）记住最后一次请求的档位，只有它**变了**才写灯（`Vehicle.applyMmtrLightSwitch(requested, driverUuid)`，调用点在 `applyMmtrControl`）。若改成"每拍把当前活动控制状态的档位写一遍"，两个来源（自动运行 + 坐进驾驶室的玩家）会以 tick 频率互相覆盖 —— 实机 2026-10-01：`[MMTR-LIGHT]` 每秒正好 20 条、在尾灯↔夜间之间来回。见 notes/353 §5.2 |
| 缓存 | `MmtrDecoupleCache.fresh(now, cachedAt)`：**哨兵 `Long.MIN_VALUE` 只参与等式比较**。第一版写成 `now - cachedAtMillis < 窗口`，减法溢出成负数 ⇒ 条件永远成立 ⇒ 判据一次都没跑过（实机症状：解耦完全没生效）。有可执行的离线用例 |
| **读原始键码的模组** | 有的模组不问 `isPressed()`，而是拿**原始键码**和它自己那条绑定的 `getKey().getCode()` 比（JourneyMap 的 `KeyBindingAction.isActive(int, …)` 就是；实机按 J 仍弹全屏地图）。摘状态对它无效 ⇒ `MmtrKeyNeutraliser` 在驾驶室里把**别的模组的**撞键绑定临时挪到 `InputUtil.UNKNOWN_KEY`（原键位用 `InputUtil.fromTranslationKey` 记下，走公开 `setBoundKey`，不反射），离开驾驶室/打开界面/**写 `options.txt` 之前**（`GameOptionsWriteMixin`）原样放回；原版绑定不挪（摘状态够用，少碰一次玩家的 options.txt） |

> ⚠️ **操作注意（实机 2026-09-29）**：代码里改键位只改**默认值**，原版把玩家改过的绑定存在
> `run/options.txt` 里且**存档优先** —— "键位不是新版的"就是这个。改键用一个脚本
> `sandbox/set-mmtr-keys.ps1`（客户端在跑时会拒绝写入，因为退出时会用内存里的值整份覆盖）。

## 7.2 HID（手柄 / 摇杆）：DirectInput 的 X / Y / Z

| 轴 | 手柄 | −1 端 | +1 端 |
| --- | --- | --- | --- |
| **X** | 定速巡航 AFB | 0（关闭） | 车型上限（BR101 = 160，步长 5 km/h） |
| **Y** | 油门手柄（双向） | 满电阻制动 | 满牵引（**中位 = 关闭**，含死区） |
| **Z** | 气制动手柄 | 运行（缓解，含死区） | EB（末尾吸附） |

- 换算全在引擎的 `MmtrHidMapping`（纯函数 + 真值表单测：中央关闭 / 两端吸附 / 逐轴可反转 / 镜像对称）；
  客户端 `MmtrHidInput` 只做"找设备、读 GLFW 轴、按启动参数校准"三件事。
- **键盘与 HID 并存**：轴是绝对量，所以它**压在键盘之后**（有真杆时以杆位为准）。没插手柄时 `poll` 返回
  `null`，纯键盘照常 —— 零回归。
- 开机（或换设备/重连）打一行 `[MMTR-HID]`，写明设备名、轴号、生效方向与死区 —— "手柄没反应"
  不该再是一种只能靠猜的现场。
- **校准不改代码**（实物千差万别）：

  ```
  -Dmmtr.hid.joystick=0          选 GLFW 手柄号（0 = GLFW_JOYSTICK_1）；默认第一个连着的手柄
  -Dmmtr.hid.axis.x/y/z=0,1,2    轴号（DirectInput 惯例 X/Y/Z）
  -Dmmtr.hid.invert.x/y/z=true   逐轴反转（推杆方向与预期相反时）
  -Dmmtr.hid.deadzone=0.05       死区
  ```

- **两处有意的不对称**（写下来，免得当成 bug 查）：
  1. 模拟轴上**"最小"档（位置 ±1，2%）不可达** —— 它落在死区里，一出死区就是 5%。要 2% 就用键盘单击 ↑/↓；
  2. 死区只做**中央吸附**（油门）与**两端吸附**（制动），不做量程缩放 —— 否则"最小档"会被死区吃掉一整段。

## 8. 客户端输入链

```
KeyBindings (键盘) ─┐
                    ├─ MmtrDriveInput.tick()   每客户端 tick：MmtrDriverSeat 判定 + 状态机 + 长按扫描 + HID 绝对量
MmtrHidInput (GLFW) ┘        ├─ MmtrCabInteraction.claimSeatWhenDriving(seat)   第一次动手柄 ⇒ 自动接管该驾驶室（定方向）
                             └─ PacketDriveControl (C2S)   仅在值变化时发；坐着期间每秒补发一次（自愈）
                                  └─ MmtrDriveControl (op) 引擎权威入口（occupation lock：只有坐在司机位的玩家算数）
                                       └─ Vehicle.applyMmtrControl → MmtrDriveAccess.sanitize（钳位）
                                            └─ ThreeHandleDriveController.compute（每 tick / 每子步）
```

- **只在变化时上报**：手柄状态是"保持型"，不按不耗流量；每秒补发一次是为了引擎侧 override 被自动释放后能自愈。
- 引擎钳位是**外部守卫**（`driveHandle` ±100、`cruise` 0…320），按车型的精确范围由 spec 再钳一次 —— 恶意/有 bug 的客户端推不出物理范围外的值。

## 9. 镜像（客户端同物理）

- 客户端没有 `consist-types.json`：车型参数与手柄规格通过车辆快照镜像。
- 新增镜像字段：`mmtrDriveHandle`（整数）、`mmtrCruiseKmh`（整数）、`mmtrHandleSpec`（**紧凑字符串**，如
  `TH;0.02;96;0.9;10;160;5;1;0,0.05,…`；只有车型变化时才变，不必每帧传数组）。
- `mmtrBrakeNotch` 继续承载气制动位置；`createMirrorControlStateFromSync` / `createMirrorConsistTypeFromSync` 按规格重建，
  于是客户端与服务端跑的是同一个控制器、同一个手柄值 —— 与既有 AIR_BRAKE 的 `mmtrAirState` 种子同一套路。
- 增量同步白名单（`VehicleSyncPatch`）必须带上这三个字段，否则"改了手柄客户端不同步"（历史坑）。
- **控制方式与制动模型解耦（notes/270）**：三种操纵方式（三手柄 / 有级 / 无级）都把手柄折成同一个
  `BrakeCommand` 交给 `BrakeModel`（管压→缸压→逐车力→黏着）。配了 bar 键的车底，**无论哪种控制方式**
  都实现 `BrakeCarrier` + `AirBrakeStateful` ⇒ 镜像种子、HUD 的气压/气制动力读数走同一套；

  详见 `制动系统-气压与制动力模型-设计.md` §9。
