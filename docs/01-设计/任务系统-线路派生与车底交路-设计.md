## 1. 结论摘要（先读这段）

1. **任务词汇表已经完备，不需要造新词。** `MmtrTaskKind` 的九种类型
   （`DRIVE_TO_SIDING` / `DRIVE_TO_PLATFORM` / `STATION_SERVICE` / `DRIVE_TURNBACK` /
   `CHANGE_ENDS` / `DRIVE_TO_CONSIST` / `FREIGHT_WORK` / `COUPLE` / `UNCOUPLE`）
   正好覆盖 出库 · 到站 · 停站 · 折返 · 换端 · 回库 · 连挂 · 解挂 · 装卸。
   本设计**只负责拼装它们**，不扩类型。
2. **缺的是任务层"上面"的输入层、生成层，和"旁边"的事件层。** 现状是**手工作业单**
   （`MmtrJobRegistry.fromFile` 持久化的是**任务本身**）。本设计把它反过来：
   **持久化输入，不持久化派生** —— 计划是 `f(线路, 密度, 车底, 事件, 时钟)` 的纯函数结果。
   这同时回答了"任务不能死存在某个文件中"。
3. **生成器做成纯函数核心 + 服务层出入口**：核心可离线跑、可单测、可重放；服务层是
   Jetty servlet（跨平台、可远程、可脚本化）。**不新增独立进程**，逻辑也不放浏览器。
4. **关键模型修正（由"替补按现实做法"逼出）**：产物必须**两段式**——
   **服务计划（趟次表，与车无关，乘客看的）** 与 **车底运用（趟次分配给哪辆车）**。
   替补顶替只改第二层，时刻表不动。见 §3。
5. **事件层不只是编排的附属品**：其中的"降速"就是 `信号系统…设计.md §1.2` 早就写好的
   **动态约束**层的第一个真实成员，直接进第 1 份设计的 min 链。两份文档只在这一点相接。
6. 现成零件盘点（详见 §2.2）：**任务/执行层完备**；**定时源是个从没通电的空壳**
   （`MmtrPeriodicTaskSource` 被每 tick 调用但**从未被填充**）；**分段密度、线路定义、车底运用、
   事件层全缺**。

## 2. 定位与边界

### 2.1 四层流水线

```
① 输入层（静态 · 持久化的就是它 · 每天重启直接加载）
     线路     站序 / 每站停站时长 / 终点处理{换端 | 灯泡线 | 回库} / 环线闭合
     密度     分段：07:00–08:30 → 5 min，08:30–10:00 → 3 min，…
     车底     车辆数（固定）/ 替补集合 / 出库提前量
     事件规则 触发条件 → 影响（密度 / 加开车次 / 降速 / 下线）+ 持续 + 理由文案
     货运队列 到货与作业请求 + 时间限制
        │
        │  ② 生成层（纯函数核心 · 可离线 · 可单测 · 可重放）
        │     MmtrServicePlan  ← 分段密度 + 线路  ⇒ 趟次表（与车无关）
        │     MmtrDiagram      ← 趟次表 + 车底      ⇒ 每辆车一天的完整任务序列
        │
        ↓  ③ 派发层（到点了把任务挂到具体车列）
     现有 MmtrMission（Executor = AUTOPILOT | PLAYER）
        ↓
     ④ 执行层（已交付）
     T1/T1b 联锁 → 走行 → 停车/灯显/映像
```

## 3. 关键设计：两段式模型（服务计划 vs 车底运用）

**为什么必须两段**（由"替补按现实做法"直接推出）：现实里备用车顶上时，**趟次的时刻表不变，
换的是执行车辆** —— 乘客看到的时刻表不受影响。若像单层模型那样"每辆车一条任务序列"，
替补顶替就只能去改时刻表，越改越乱。

```
MmtrServicePlan（服务计划 · 与车无关 · 乘客看的）
   线路 → 有序趟次：[(车次, 发车时刻, 各站到 / 发时刻, 终点处理方式)]
        │
        │  分配（可被替补、事件、手工指派改变）
        ↓
MmtrDiagram（车底运用 · 每辆车一条）
   车辆 → 有序趟次 → 展开成有序 [MmtrTask...]（含首尾出库 / 回库）
```

由此得到三条干净的性质：

1. **替补顶替 = 只改 `MmtrDiagram`**，`MmtrServicePlan` 不动（§8.1）；
2. **事件的影响面清晰**：改"密度/加开车次" → 动计划；改"执行车辆/下线" → 动运用；
   改"降速" → 两者都不动，走动态约束（§6.4）；
3. **手工指派（WEB 的 `assign`）= 对运用层的覆盖**，需要一个"手工 > 自动"的优先级分层，
   与联锁那套 `人工锁 > 计划时刻 > 到达序` 同一种思路。

## 4. 输入模型（持久化 · 这是"每天重启直接加载"的东西）

### 4.1 线路 `MmtrLine`

| 字段 | 说明 |
| --- | --- |
| `lineId` / `name` | 线路标识 |
| `stops[]` | 有序站点：`{stationId, platformId, dwellMillis}` —— **每站停站时长** |
| `terminalTreatment` | 终点处理：`CHANGE_ENDS`（原地换端）\| `TURNBACK`（灯泡线掉头）\| `STABLE`（直接回库） |
| `loop` | 环线标志：终点即起点（同理同终），`terminalTreatment` 退化为"继续" |
| `yardSidingId` | 出库/回库的车场股道 |
| `leadTimeMillis` | **首发前移量**：从车场出发到站台等待出发所需时间 |

> 直接对应你的原话："由线路从起点首发时间**前移若干时间**用于从车厂出发到站等待出发"。
> 这个前移量就是交路的**第一个任务**（`DRIVE_TO_PLATFORM` 之前的那一段 `DRIVE_TO_SIDING`/出库）。

### 4.2 密度 `MmtrPattern`（分段）

```
线路 → [(fromMillis, toMillis, headwayMillis), ...]      // 同一天内、不重叠覆盖运营时段
例：07:00–08:30 → 5 min，08:30–10:00 → 3 min，…
```

- 校验：区间不得重叠、必须覆盖 `[运营开始, 运营结束]`、`headway > 0`；
- 事件可以**临时改写**这张表（`PeakSurge` → 局部 headway 变小），但不落盘回输入层
  （事件是运行时的扰动，见 §6.3）。

### 4.3 车底 `MmtrFleet`

| 字段 | 说明 |
| --- | --- |
| `consists[]` | 每条交路的车底：`{consistId, cars[], maxSpeedKmh}` |
| `spares[]` | **替补集合**（不排班，专供事件与晚点顶替） |
| `vehicleCount` | 车辆数 —— **固定**，是输入而不是结果 |

**校验（重要）**：加载时就算 "运营所需车底数 N"（§5.1），若 `available < N` 则
**加载即报错**，而不是运行到高峰才发现跑不动。这正是"车辆数固定要利用好"的落点。

## 5. 生成器（纯函数核心）

### 5.1 交路生成三步

```
① 周转时间  ring = 往程走行 + 沿途各站停站 + 终点处理 + 返程走行 + 沿途各站停站
                    （环线：ring = 一整圈，终点处理不计）
② 运营车底数 N = ceil(ring / 高峰最小间隔)      ← 按**高峰**取最大需求，平峰自然有富余
③ 排班     按分段密度展开"计划发车时刻表"（= MmtrServicePlan 的趟次），
           再用 N 辆车循环套上（round-robin）→ 每辆车的趟次序列 + 首尾出库/回库
           替补 N_备用 辆不参与套班
```

### 5.2 终点处理三态 → 已有任务类型（不需要新词）

| 终点处理 | 任务序列 | 已有类型 |
| --- | --- | --- |
| 原地换端 | `CHANGE_ENDS` | ✅ |
| 灯泡线掉头 | `DRIVE_TURNBACK` | ✅ |
| 直接回库 | `DRIVE_TO_SIDING` | ✅ |
| 环线 | 不处理，继续下一趟 | ✅ |

### 5.3 客运与货运同构（只差"趟次来源"）

| | 趟次从哪来 | 产物 |
| --- | --- | --- |
| 客运 | **分段密度表**（周期性） | `MmtrDiagram`：每辆车一天的交路 |
| 货运 | **到货 / 作业事件**（随到随干 + 时间限制） | `MmtrDiagram` 退化为每辆车的任务队列 |

⇒ **生成器只写一个**，"趟次来源"做成可插拔的两种实现（`ServicePatternSource` / `FreightQueueSource`）。
后面的排班、派发、重算、联锁约束全部共用。这是本设计里最大的复用点。

## 6. 事件层

### 6.1 抽象事件类

```
MmtrEvent（抽象）
  ├─ id / 类型 / 严重度
  ├─ target        目标：车站 | 区段(一组轨) | 车次 | 车列 | 全线
  ├─ startMillis   生效时刻
  ├─ endMillis     预计结束（可变；未知时为 -1，由人工或后续事件终止）
  ├─ reason        给人看的理由文案     ← 用户要求"赋予时间理由推送前台展示"
  └─ state         生效 / 衰减 / 结束
```

**每条事件都必须能回答三个问题**：影响什么、从何时到何时、为什么（理由文案）。
理由文案是**前台展示**的契约（网页事件条 / 游戏内 HUD / 站台显示屏皆可读）。

### 6.2 四类细分与影响

| 细分 | 目标 | 影响谁 | 怎么影响 |
| --- | --- | --- | --- |
| **临时高峰** `PeakSurge` | 车站 | 计划层 | 局部缩短 headway / **加开临时车次** |
| **延误** `Delay` | 车次 / 车列 | 运用层（或计划层） | **平移趟次时刻**（保车）**或换车保时刻**（见 §8.1） |
| **故障** `Fault` | 车列 \| 区段 | 运用层 / 执行层 | 车列**下线** → 触发替补顶替；区段不可用 → 进路不可达 |
| **降速** `SpeedRestriction` | 区段 | **动态约束** | 该区段允许速度下降，**直接进 min 链**（§6.4） |

> 用户原话："事件类型及其多，但无非就是恶劣天气降速、故障、卧轨、某站客流激增临时高峰期等，
> 说白了就是现实里那点事" —— 所以**抽象在前、细分在后**：新事件类型只需回答"目标 + 影响谁 + 理由"，
> 不必改生成器。

### 6.3 推前台展示

- 出口：`GET /mtr/api/mmtr/plan/events`（生效中 + 即将生效），字段 = `{类型, 目标, 开始, 预计结束, 理由}`；
- **时间**：剩余时长实时下发（"预计 12 分钟后恢复"），供 HUD / 网页 / 站台屏渲染；
- 事件**不落盘回输入层**：它是运行时扰动，只改"本次重算的输入"，不改变配置
  （配置文件里的 `MmtrEventRule` 是**规则**，不是事件实例）。

### 6.4 降速事件 = 动态约束 → min 链（与姊妹文档的唯一接合点）

`信号系统-AWS与LZB两制式-设计.md §1.2` 早已定下：

> 运行时允许速度永远是 `min(轨限速, 动态约束, 目标距离制动曲线)`——信号配合发生在 min 链。

它把"**动态约束**"列为"独立对象（不绑轨）：临时限速 TSR（发布/撤销/过期）、信号降级（红灯=目标速度 0）"。
**本设计的"降速事件"就是那个动态约束层的第一个真实成员**；《行车控制-任务联锁与行车许可-设计.md》
里的 `MmtrMovementAuthority`（信号降级）是第二个。两者同一层、同一条 min 链、互不耦合。

⚠️ **跨文档依赖**：`SpeedRestriction` 的落地依赖姊妹文档的**动态约束层**（其 T2/T3 会建立 min 链的接入点）。
若先做本文，`SpeedRestriction` 可先只做"事件存在于 feed、供前台展示"，**接线留到那一层就绪**。

## 7. 滚动重算协议

**触发**：事件发生 / 取消 · 晚点超阈值 · 跨时间带（如 08:30 换密度）· 定时兜底 · 手工指派。

**不可动区（冻结边界）** —— 否则会把正在开的车打断：

```
每辆车：frozenUntil = 它"当前任务的预计完成时刻"
  过去   ：不可改（已完成的任务是事实，也是时刻表"实际到发"的数据源）
  在途   ：不打断（当前任务保持，只重排它之后的）
  未来   ：全部重算
```

**与联锁的漂亮耦合**：联锁里的**授权持有**本身就是"在途"的物理表达 —— 一辆握着道岔、身在进路的车
就是不能被动的那辆。所以冻结边界可以直接从 `MmtrRouteRegistry` + `MmtrPointAuthority` 读出来，
**不必另建一套"谁在途"的状态**。

⚠️ **硬约束**：**重算产物绝不能去抢在途车已持有的道岔**。重算在联锁之后落地（先冻结、再申请），
顺序反了就会退化成第 3 轮讨论的 hold-and-wait 与死锁。

## 8. 替补与接管

### 8.1 替补顶替（按现实做法）

用户裁定：**按现实做法** ⇒ **趟次时刻不变，换执行车辆继续跑后续趟次**。

```
故障 / 晚点超阈值
  → 在 MmtrDiagram 上把该车的后续趟次转给替补车
  → MmtrServicePlan 一行不改（乘客时刻表不变）
  → 接续点 = "后续某站的某一趟次"，不是凭空开始：
     替补车需要一条"从它的停放位置开到接续站"的前置任务（DRIVE_TO_SIDING / DRIVE_TO_PLATFORM）
  → 若替补来不及（前置任务时长 > 可用窗口）→ 退化为"取消该趟"并对外发出事件（理由可见）
```

**"保车还是保表"是一个策略开关**：`Delay` 事件可选择平移趟次时刻（保车）或换车（保表）。
默认建议：**保表**（乘客体验优先），与"按现实做法"一致。

### 8.2 AI ↔ 玩家接管

底座已有（`Executor` + `MmtrDriveAccess` override），缺的是**移交协议**：

| 方向 | 移交内容 |
| --- | --- |
| AI → 玩家 | 停止自动运行（`mmtrMotionAuto` 关）、清自动停点、玩家控制接管；**交路与任务不变**（换的是执行者） |
| 玩家 → AI | 玩家控制释放（override 归还）、按当前任务目标重新自臂、从那一点续行 |

**原则：任务是作业，执行者可换。** 这与 §3 的两段式同源 —— 连"谁在开"也是可替换的一层。

## 9. 服务层 API 与 WEB 页

编排器 = **引擎 Web 服务层的模块**（用户裁定：纯 Java、跨平台、HTTP 出入口；浏览器只是客户端）。

```
GET/PUT  /mtr/api/mmtr/plan/lines        线路定义
GET/PUT  /mtr/api/mmtr/plan/patterns     分段密度
GET/PUT  /mtr/api/mmtr/plan/fleet        车辆数与替补
GET/POST /mtr/api/mmtr/plan/events       事件规则（配置） + 生效中的事件（运行时）
GET      /mtr/api/mmtr/plan/service-plan 趟次表（与车无关 · 乘客视角）
GET      /mtr/api/mmtr/plan/diagrams     车底交路（计划 vs 实际）
POST     /mtr/api/mmtr/plan/replan       强制滚动重算
POST     /mtr/api/mmtr/plan/assign       指定某辆车 / 批量的任务   ← 用户要的 WEB UI
```

WEB 分页（新）：

1. **线路**（站序 / 停站 / 终点处理 / 环线）；
2. **密度**（分段表 + 时间轴可视化）；
3. **车底**（车辆数 / 替补 / 出库提前量 + "所需 N vs 实际"校验提示）；
4. **事件**（规则编辑 + 生效中事件条，带理由与剩余时间）；
5. **交路**（每辆车一行的时间轴：计划 vs 实际，复用 `任务系统…设计.md §4` 的时间表设计）；
6. **指派**（选中车辆/批量 → 指定任务；手工覆盖优先级可见）。

## 11. 边界（本设计不做）

1. **不扩任务类型**：九种已够，产物只做拼装（§1.1）。
2. **不做浏览器端编排**：逻辑在服务层，浏览器只是客户端（用户裁定 1）。
3. **不新增独立进程**：纯函数核心 + 服务层已满足"独立"（可离线跑），不引入要运维的新进程。
4. **不把事件实例写回配置**：配置里是规则，事件是运行时扰动（§6.3）。
5. **不做跨线路的车底共享优化**：v1 一条线路一个车底池；跨线共用留给后续。
6. **不做货运装卸的场地形态细化**：`FREIGHT_WORK` 仍是占位，P7 只做生成器与排队。
7. **不动联锁**：本文只产出"进路意图"的上游；联锁改动全在姊妹文档（T1/T1b/T3/T4）。

## 12. 风险与开放问题

**风险**

- **R1（中）晚点与重算的抖动**：频繁重算会让计划跳变、玩家看不懂。
  缓解：重算有**节流**（最短间隔）+ **最小变更原则**（能平移就不换车），并向玩家展示"计划已调整"的事件。
- **R2（中）保表 vs 保车的默认策略**：默认保表会牺牲车辆运用效率。缓解：做成策略开关（§8.1），
  运营台可见当前策略与它的后果。
- **R3（中）跨文档顺序**：`SpeedRestriction` 依赖姊妹文档的动态约束层。缓解：本文 P5 先做"事件在 feed 可见"，
  接线留到那一层就绪（§6.4 已写明）。
- **R4（低）车底数校验过严**：`available < N` 直接报错可能在编辑配置时很烦。
  缓解：设为**警告 + 明确提示缺几辆**，只有明显不足才拒绝加载。
- **R5（低）性能**：生成是纯计算，量级 = 趟次数 × 站数（几十 × 几十），每 tick 不必重算
  （只在触发时算一次 + 派发器逐 tick 读计划）。

**开放问题**

1. **货运气氛组的最低活跃度**默认值（用户：看情况先，**保留动态设置**）—— 参数化 + 运行时可变已定，
   默认值待定；建议先设一个保守值（如"至少 1 列在干线活动"）并可即时改。
2. **运营时段的表达**：每天固定时段，还是支持"工作日/周末不同表"？影响 `MmtrPattern` 是否需要多套。
3. **环线与终点处理并存**：环线是否需要"套跑若干圈后回库"？若需要，`MmtrLine` 要加"圈数"或"回库趟次"。
4. **事件的人工干预**：玩家只有司机角色，所以事件的发布/终止应由**程序**定（规则自动）还是
   运维通道手设？建议：规则自动为主，运维通道可手设（与联锁的"人工锁仅运维通道"同一纪律）。
5. **接管时的任务状态**：玩家从 AI 手里接管后，如果他把车开离了交路（比方说开错方向），
   任务是自动重规划，还是先报"偏离任务"？建议先报偏离 + 提供重规划，避免静默改计划。
