## 1. 用户口径（本次修正，定案）

1. **换端 ≠ 列车转向**。现代列车普遍双驾驶室：换端时列车物理姿态完全不变，是**司机走到另一端的驾驶室**。
2. 换端是**司机动作**，标准序列：**列车停稳 → 拔出钥匙 → 走到另一端驾驶室 → 插回钥匙**。
   - 因此换端**不涉及运行中反向行驶**，与既有红线「火车不能倒车」（commit 748a349）不冲突；
   - 换端可在**任意位置、任意时刻发起**，但只有满足上述序列才生效。
3. 驾驶室抽象 = **把司机固定在列车某个点，直接写死**（不新增逐车配置声明）。
4. 本轮范围：**只重写 motion 分支**；legacy `immutablePath` 分支保持不动。
5. **整列占用 `[tail..head]` + 车尾清岔（rear-clear）+ 信号按整列**纳入本轮。

## 2. 问题定位（代码级根因）

现状把"编组体姿态"和"行进方向"混成了**一个单点状态**：

| 位置 | 事实 |
|---|---|
| `MmtrMotionWalker.java:30-35` | 只跟踪**一个点**（`rail / enteredFrom / ahead / offsetM`），**无车尾、无编组长度、无姿态** |
| `MmtrMotionWalker.java:359-377` | `flipDirection()` 交换 `enteredFrom/ahead` 并**追加一条反向 PathData 回段** |
| `Vehicle.java:1409-1415` | `refreshMmtrMotionLegs()` 把整条 leg 链（含反向回段）直接塞进客户端同步路径 `mmtrSetSyncPath` |
| `MmtrMotionSnapshot.java:110-123` | 快照报 `segStart=enteredFrom / segEnd=ahead`，且**硬编码 `segmentReversed = false`** |
| `Vehicle.java:1195-1205` | 换端执行点：停稳后调 `flipDirection()` |

→ 换端后车体位置其实没变，但**同步路径方向整体反转**，客户端沿路径重放时车体朝向翻转 180°。
**这是数据模型缺陷（单点表达不了双端编组），不是渲染 bug。**

## 3. 概念模型

### 3.1 编组体（MmtrConsistBody）

编组体 = 轨道图上的**有向区间**，是 Motion Core 位置状态的唯一来源。

```
spine      : 有序轨段链（rail + 入端节点 + 长度），从编组 A 端一侧向 B 端一侧
aEndArcM   : 沿 spine 的弧长坐标，标记编组 A 端所在位置
lengthM    : 编组总长（含车长与车钩间隙）
```

- **B 端弧长** = `aEndArcM + lengthM`；
- **第 k 辆车中心弧长** = `aEndArcM + Σ(len_0..len_{k-1}) + len_k/2` —— 车辆位置由 **A 端**度量，
  **与行进方向无关**（这是"换端不改变任何车辆位置"的数学保证）；
- **占用区间** = `[aEndArcM, aEndArcM + lengthM]` 与 spine 各轨段求交 → `(railHex, fromM, toM)` 列表（可跨多轨）；
- spine 随行进增长/裁剪：前端在行进方向延伸，后端裁掉已出清的轨段。

### 3.2 驾驶室（写死）与操纵端

**本轮写死为"编组两端各一个驾驶室"**：

| Cab | 位置 | 朝向（编组坐标系） |
|---|---|---|
| `CAB_A` | A 端（car0 外端） | A→B |
| `CAB_B` | B 端（carN-1 外端） | B→A |

- `activeCab ∈ { NONE, CAB_A, CAB_B }`；
- **行进方向 = activeCab 的朝向**；**前端 = 该方向那一侧的编组端**；
- `ControlState.reverser` 对 motion 车**继续忽略**（方向由 activeCab 决定，红线 748a349 保持）；
- **已知简化（显式记录）**：动力集中式双端机车"两个驾驶室同处第一节"本轮不支持（写死为两端）。
  同一 Cab 抽象后续可扩展为"沿编组的里程坐标"（`cabAtArcM`），届时 `CAB_A/CAB_B` 退化为两个默认值；本轮不做。

### 3.3 钥匙与操纵权

| 概念 | 语义 |
|---|---|
| 钥匙（Key） | 司机持有的物品（复用游戏内 MTR 司机钥匙）；**插在某驾驶室**才授予该车操纵权 |
| 插钥匙 `insertKey(cab)` | 前置：列车已停稳（`speed ≈ 0`）∧ 该驾驶室无钥匙 ∧ 司机实体在该驾驶室点 → `activeCab = cab` |
| 拔钥匙 `removeKey()` | 立即撤销操纵权（`activeCab = NONE`）；若此时仍在运动，**牵引归零并按服务制动停稳**（不允许继续牵引） |
| 换端 `changeEnds()` | **不是原子操作**，= `removeKey()` → 司机移动到另一驾驶室 → `insertKey(other)`；引擎只校验前置条件 |

### 3.4 换端状态机

```
MANNED_A ──removeKey──► UNMANNED ──insertKey(CAB_B)──► MANNED_B
   ▲                                                      │
   └────────────── removeKey / insertKey(CAB_A) ──────────┘

前置（insertKey）：速度 ≈ 0 ∧ 无其他钥匙 ∧ 司机位于目标驾驶室
非前置（removeKey）：任意时刻合法（运行时拔钥匙 = 失去牵引 → 服务制动停稳）
```

### 3.5 换端流程配合（运营侧，配套构建）

换端不是孤立的原子操作，而是一段**流程**：有人发起、有前置闸门、要占时间、之后必须重算进路。
B1–B7.1 只做了"换端本身"（几何零位移 + 钥匙状态机），下面是配套层。

| 环节 | 现有 | 需要新建 |
|---|---|---|
| ① 触发 | 无 | 作业单任务 `ChangeEnds`（终点站原地换端，区别于"经折返轨绕回"）；规划器"到达终点/死端→换端→续行"；OP 指令 `changeends <vehicleId>`；司机钥匙事件上行 |
| ② 闸门 | `changeEnds(stopped)` | 车门须关；车不得压在待搬岔上（rear-clear 已保证岔权不提前释放）；时刻表换端停时 |
| ③ 执行 | `MmtrCabState` | 驾驶室↔座位端映射（现 `hasMmtrDriverRiding` 只判"是否司机"，不区分头尾）；钥匙物品事件（MTR 钥匙无"拔钥匙"语义）；ATO 的"系统钥匙"与固定停时；HUD 引导 |
| ④ 换端后重算 | 无 | `Plan.forkOps/forkMeters/stopCumulativeM` 均为**旧前端方向**坐标：换端后必须释放旧岔权 → 以新前端重规划 → 重新申请岔权；停点目标重算 |
| ⑤ 展示 | 快照 `activeCab` | 时刻表"换端"行（计划/实际）；HUD 操纵端与"换端中"提示；OP 车辆卡片 |
| ⑥ 异常 | 无 | 司机掉线（钥匙自动拔出？）；双司机各占一端；单驾驶室车拒绝换端并提示需环线/转盘（§8 O1/O2） |

**切片归属**：B7.3 吸收 ①④ 的引擎侧（任务类型 + 规划器 + OP 指令 + 重规划）；新增
**B7.5 换端后重规划与岔权重申请**、**B7.6 游戏侧钥匙/座位映射 + HUD 引导**、
**B7.7 时刻表与 OP 展示**。

#### 3.5.1 定案（2026-09-08 用户拍板）

1. **玩家换端 = 物理走到另一端（真实形态）**：需要驾驶室↔座位端映射、钥匙插入/拔出事件，
   引擎必须校验"司机确实位于目标驾驶室"才允许 `insertKey`。简化倒计时方案**不采用**。
2. **作业单新增 `CHANGE_ENDS` 步骤**：与现有"经折返轨绕回"的 `DriveTurnback` 语义分开——
   原地换端不需要折返轨，是终点站折返的常规做法。
3. **ATO 换端 = 系统自动完成**：无人自动车到终点停稳后由系统持钥匙完成换端并续行
   （对应 §3.3 的"系统钥匙"形态）。
4. **换端不建模耗时**：`CHANGE_ENDS` 步骤**不带时长参数**；换端属"特殊情况、专用时刻表"，
   时刻表只记录**实际发生时刻**，不预留计划时长。因此 `MmtrCabState` 不引入 dwell 字段。

### 3.6 驾驶室交互与视角（用户提出的三个问题，设计）

> 前置事实（代码核对 2026-09）：MTR 模型部件类型含 `SEAT`（76 个内置车辆模型在用，坐标单位
> 1 格=16，z 沿车长）；`VehicleRidingEntity` 已带**车内本地坐标** `(ridingCar, x, y, z)`，
> z 沿车长、x 为横向；上车由"走进车门/地板包围盒"触发（`VehicleRidingMovement.startRiding`）；
> 引擎侧**没有** `PartType`/SEAT 概念（只有 `MmtrDriveAccess` 的"司机席"文字描述）。

#### 3.6.1 端的界定（已有，明确化）

- 编组坐标系由**车辆顺序**定义：**car 0 的外端 = A 端，car N-1 的外端 = B 端**；
- **端是编组体属性，不随换端改变**——换端只改"哪一端在前"（`MmtrCabState.leadingEnd()`）；
- 几何由 `MmtrConsistBody` 的 A 端弧长 + 车长给出（B1 已实现）。

#### 3.6.2 驾驶室识别：`Cab = (carIndex, facing)`

| 布局 | 驾驶室定义 | 说明 |
|---|---|---|
| 动力分散动车组 | cab1=(0, A)、cab2=(N-1, B) | 首尾各一，天然 |
| 动力集中式双端机车 | cab1=(0, A)、cab2=(0, B) | **同一辆车两端各一**，靠 `alongCar` 区分 |
| 推挽（机车+控制车） | cab1=(0, A)、cab2=(N-1, B) | 同动车组 |
| 单驾驶室机车 | 只有一个 Cab | 换端不可行 → 提示需环线/转盘 |

- `facing` = 该驾驶室朝编组坐标系的哪一端；**操纵该 cab 时列车向该端前进**（与 §3.2 一致）。
- **持久化用 `(carIndex, facing)`**，显示名"1 号 / 2 号驾驶室"按 `carIndex` 升序、同车 A 先于 B
  派生——避免编组变化导致编号漂移。
- 数据来源（**游戏侧**，引擎不读模型）：
  1. 模型 `SEAT` 部件位置（首选）：按 SEAT 在车内的 z 位置分类，靠车头端 = facing A、靠车尾端 = facing B；
  2. 无 SEAT 部件 → 回退 `alongCar = 0.08 / 0.92`；
  3. 特例覆盖：编组类型模板显式声明（同 `signal_binder` 的显式通道思路）。

#### 3.6.3 驾驶室视角（玩家位置）

- 复用 MTR 的**乘车实体本地坐标**：进入驾驶室 = 把玩家的 `(ridingCar, x, y, z)` 吸附到该 cab 的
  **视点** `viewPoint = { alongCar ∈ [0,1]（沿车长，自 A 端面起）, lateral ∈ [-0.5,0.5], eyeHeightM }`；
- 相机由 MTR 现有的乘车渲染自动跟随，无需新渲染层；朝向由 `facing` 决定，鼠标仍可自由看；
- **客户端对自己位置权威**（MTR 语义），服务端只校验权限与占用——引擎不需要驱动玩家坐标。

#### 3.6.4 UI 交互（对准门 → 提示 → 按键进驾驶室）

1. **客户端每帧**：相机射线命中车体/车门部件 → 得 `(vehicleId, carIndex)`，并据命中点在该车的
   哪一端推断目标 cab；
2. **提示**：有权限（持司机钥匙 / OP 白名单）且该 cab 可操纵 → HUD 显示
   "按 [K] 进入 1 号驾驶室"；无权限 → 显示"需要司机钥匙"；
3. **按键**：新增 MMTR 键绑定（默认 `K`），或复用司机钥匙右键（MTR 钥匙当前无 use 逻辑，
   推荐新键位以免与开门冲突）；
4. **服务端校验**：`(vehicleId, cabIndex)` → 车必须停稳 ∧ 该 cab 无钥匙 ∧ 玩家有权限 ∧
   玩家在对应车附近 → `MmtrCabState.insertKey` → 回执 → 客户端吸附视点；
5. **离开 / 拔钥匙**：再按一次键或走离驾驶室点 → `removeKey()`（运行时拔钥匙 = 失去牵引 →
   服务制动停稳，§3.3 已定）。

#### 3.6.5 完整换端流程（三者串起来）

> 到站停稳 → 按 `K` 下车（拔钥匙）→ 沿站台/车厢走到另一端 → 对准另一端的车门 →
> 按 `K` 进入 2 号驾驶室（插钥匙）→ 反向发车。

整条链路只用现成机制：MTR 的走行/车门包围盒 + 乘车实体坐标 + 司机钥匙；MMTR 只新增
"瞄准提示 + 键位 + 服务端校验 + 驾驶室定义"。

## 5. 三方位集成

### 5.1 Motion Core（重写主体）
- `MmtrMotionWalker` 单点 → **双端编组体行走器**：前端推进、后端拖尾、节点裁决在前端；
- `flipDirection()` 删除，由 `changeEnds()`（改 activeCab，不动几何）取代；
- `buildLegs()` 语义从"走过的路"改为"编组体脊柱 + 已行进轨迹"，供渲染/占用/规划共用；
- `MmtrMotionSnapshot` 增 `frontX/Z`、`rearX/Z`、`activeCab`、`cabManned`、真实 `segmentReversed`。

### 5.2 道岔（语义修正）
- hold 归属**列车**（owner = 车 id），不是"头端位置"；
- **release 时机 = 车尾出清岔区**（`MmtrMotionWalker.java:255-258` 现行"头过即释放"作废）；
- 岔区占用 = 编组区间 ∩ 岔区（含节点两侧）；接近式授予（A1，120 m 窗口）与 FIFO 队列语义不变。

### 5.3 信号（冻结新增设计，只做接线）
- 占用写入 = **整列区间**（替换现行"头端轨"）；
- 制式判据 / AWS 触发 / LZB 顶棚读 **操纵端所在轨**（推挽时可能是拖车，符合现实）；
- 换端**不改变占用、不改变灯色语义**；S1–S4 既有测试必须全绿不动。

## 6. 接口草案

```java
// 编组体（纯数据 + 纯函数，无世界依赖）
final class MmtrConsistBody {
    ObjectArrayList<SpineLeg> spine;   // railHex, entryNode, exitNode, lengthM
    double aEndArcM, lengthM;
    double[] carCenterArcM();                       // 逐车中心弧长（A 端度量）
    ObjectArrayList<OccupiedSegment> occupancy();   // (railHex, fromM, toM)
    boolean advanceFront(double deltaM, NodeElector elector);  // 前端推进 + 后端裁剪
    boolean slideBack(double deltaM);               // 拖尾
    double frontArcM(); double rearArcM();          // 由 activeCab 解析
}

// 换端状态机（服务器权威）
final class MmtrCabState {
    enum Cab { NONE, CAB_A, CAB_B }
    Cab activeCab;
    boolean insertKey(Cab cab, boolean stopped, boolean driverAtCab, boolean keyFree);
    boolean removeKey();
    boolean changeEndsLegal(boolean stopped);       // = 停稳 ∧ 司机可在两端间移动
}

// 行走器（重写）
final class MmtrConsistWalker {
    MmtrConsistBody body;
    MmtrCabState cabs;
    void advance(double deltaM);                    // 前端推进；节点处 elect（operator>grant>target>单续>halt）
    boolean changeEnds();                           // 仅停稳；几何不变
    ObjectArrayList<PathData> buildLegs();
}
```

## 8. 风险与开放问题

- **R1（中）spine 增长/裁剪的内存与确定性**：长跑车 spine 必须裁剪已出清轨段；裁剪以"后端已出清"为判据，与 I5 同源。
- **R2（中）换端与占用同时发生**：换端只改方向不改占用，故 S1 占用无需重算；但 `blockedWaiting` 的"前方"需按新方向重算。
- **R3（中）legacy 互操作**：legacy 车仍写共享占用树；整列占用区间必须与 legacy 的 `[tail..head]` 语义一致（S1 已有 `getBlockedBounds` 先例）。
- **R4（低）客户端镜像兼容**：`mmtrMotionMirror` 老字段保留（新增字段而非替换），避免旧客户端解析失败。
- **O1 动力集中式双驾驶室同车**：本轮写死为两端（§3.2），扩展点已预留（`cabAtArcM`），不阻塞。
- **O2 换端是否允许"另一端不在同一轨"**（编组跨岔换端）：几何上合法（司机走过去），
  但需确认道岔/信号不因此进入非法态——B5 用长编组跨岔用例验证。

## 9. 与既有红线的相容性

| 红线 | 本设计如何保持 |
|---|---|
| 火车不能倒车（748a349） | 换端必须先停稳；行进方向由 activeCab 决定，`reverser` 继续忽略 |
| 道岔 authority「绝不动车」 | 岔权只决定"往哪走"，换端与推进仍由驾驶/任务驱动 |
| 信号只投影不裁决 | 信号仍只读占用与制式，不参与运动决策 |
| 全量回归零新增失败 | 每片门禁；legacy 分支不动 |
