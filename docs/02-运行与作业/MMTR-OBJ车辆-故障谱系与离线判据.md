# MMTR OBJ 车辆：故障谱系（症状 → 一眼定性 → 真因 → 判据 → 修法）

> **这是什么**：把 notes/187–203 这几轮**实机踩过的坑**按"**你会看到什么**"重新排一遍。
> 工作流（`MMTR-OBJ车辆资源包-标准化工作流.md`）回答"**怎么做**"，本篇回答"**出了这个现象，是哪一类，
> 先去量哪个数**"。
>
> **为什么需要它**：MTR 的 OBJ 路径**大量失败是静默的** —— 组名互相覆盖、资源路径大小写被改写、
> 缺 UV 采到透明纹素、OBJ 路径不给地板盒、几何被 optimized 批量吞掉、异常打断整批渲染。
> 这些都不报错，只会表现为"东西没出来/没生效"。**同一个症状往往有 4~5 种互不相关的死法**
> （"车看不见"就有三种以上），所以排查的第一步永远是**量一个可测量的中间量**把范围切开，
> 而不是"我觉得是 X"。
>
> 时间范围：2026-09-18/19（BR101 入包 → 驾驶层 B2 → 仪表 → 实体雨刷 W4）。

## 1. 「看不见 / 显示不对」一族（最多、最像"打包没生效"）

### 1.1 整车看不见 A：组名被覆盖（notes/191）

- **症状**：车辆实体、锚点、properties 全在，OBJ 也在，就是渲染不出车体。
- **真因**：MTR 按**组名**建表（`nameToObjModels.put(name, model)`），**同名互相覆盖只剩最后一个**；
  而 `groupMap` 是**故意**把多个源组映射到同一角色的
  （BR101 的 `body = car_body + buffer_beam + buffers + bogies + wiper_motors`，5 个源组）。
  打包器只**改名**、没**合并** → 打包后 OBJ 里出现 5 个 `g body` → MTR 只留最后一个（`wiper_motors`，一小块）。
- **判据**：数 zip 里的同名组（修前 `body×5 / interior×3`，修后 `body×1`；组数 29→23，**面数 9154 不变**）。
- **修法**：打包时做一次**同名合并**（`mergeSameNamedGroups`）：顶点行全部提前（面索引是绝对的，仍然有效），
  每个名字只输出一次，面按原顺序、并把它当时的 `usemtl` 随面重放。
- **易混点**：这个症状**极像**"包没打进去"。所以先量组数，再怀疑落盘。

### 1.2 整车看不见 B：模型朝向（Y 不是"上"）（notes/192）

- **症状**：模型**成功加载**（日志 `obj=1006426 chars`、`body` 只出现一次 ✓、properties 组名吻合 ✓），
  但游戏里看不见车。
- **真因**：打包后 OBJ 的包围盒是 **Y=±16.19（=32 m，车长）、Z=−7.22..0（=高）**，
  即"长度沿 Y、高度沿 Z"，相对 MTR 的约定**绕 X 转了 90°**（在 Blender 里它是立着的）→ 车被立起来，
  大半在地下/天上 → 看着就是"不显示"。
  对照正常显示的 saf101：`Y=1..6（高）`、`Z=±8（长）`。
- **约定与判据**：MTR **Y 朝上、长度沿 Z**。导出后自检应为
  **`X ≈ ±宽/2 ≈ ±2.5`、`Y ≈ 1..6`（坐在轨面上）、`Z ≈ ±车长/2 ≈ ±15.5`**。
- **修法**：模型在 Blender 里就是按 MC/MTR 口径（Y 向上、Z 向前）建的，所以**动导出参数、不动模型**：
  `forward_axis="Y", up_axis="Z"`（= Blender 自身口径 → 恒等转换）。⚠️ 导出脚本的**兜底分支**也要保住这两个参数：
  它原来在 `TypeError` 时把 `forward_axis/up_axis` 一起 `pop` 掉 → 退回 Blender 默认值 → **又一次静默把车转歪**。
- **排除过的东西**（写在笔记里，避免重复怀疑）：`No floors or doorways found`（saf101 也报，不是原因）、孤立顶点（0 个）、
  同名组覆盖（已修）、服务端锁 zip（已修）。

### 1.3 整车看不见 C：分包 / 落盘（notes/191、193）

- **症状**：代码/模型都改了、打包器也跑了，游戏里**没变化**。
- **真因**：服务端运行时**占着 `run/resourcepacks/*.zip`** → 打包器 `unlink` 报 `EBUSY: resource busy or locked` →
  **zip 还是旧的**。`server stop` 之后 JVM 还可能没退干净（孤儿进程仍占文件）。
- **流程约定**：**先停服 → 打包 → 再起服。** 另一个变体是**盘上的包比模型旧**（19:17 vs 19:21）——比对 mtime 一眼可见。
- **教训**：这类"流程性坑"表现得和"代码没生效"一模一样，所以**打包日志有没有报错**必须看，别只看"命令跑完了"。

### 1.4 只有雨刷显示：MTR 读 OBJ 的三条硬约束（notes/194）

- **症状**：整车被"抠光"，只剩雨刷（雨刷恰好是没有 UV 层的那批）。
- **真因**（反汇编 `org/mtr/mapping/render/obj/ObjModelLoader` 得到，不是猜）：
  1. **第 i 个顶点强制配第 i 个 `vt`/`vn`** —— 面里写的 `v/vt/vn` 三元组**从来不读**；
  2. **每个面只读前 3 个角**（四边形/多边形会被截断）；
  3. Blender 默认导出两条都不满足。BR101 实测 `v=10482 / vt=2568 / vn=3092` + 四边形
     → **第 2568 号之后的顶点 UV 全变 (0,0)**；
  4. 再叠加 **`flipTextureV: false`** → 贴图上下颠倒 → 车体的 UV 落到那 58% 透明区。
- **修法（三处，缺一不可）**：
  1. 打包器新增 `toMtrObj()`：去焊接 + 耳切三角化 + 写盘前自检（保证 `#v==#vt==#vn`、全三角形、`f i/i/i`）；
  2. 新配置 `untexturedUv`（没有 UV 层的面采哪个纹素）；
  3. `flipTextureV` 改 **true**。
- **判据**：`tools/obj-mtr-packager/verify_mtr_obj.js`（布局 / 配对 / 面积 / 包围盒四层，喂坏包会红）。规范进工作流 **§1.5**。

### 1.5 单个部件整块不见：没有 UV 层（notes/194）

MTR 永远取 UV，缺省就是 (0,0) = 贴图左下角。雨刷这类件通常**没有 UV 层** → 采到透明纹素 → 整块不见。
用 `untexturedUv` 指到一个不透明纹素。**"没 UV"和"UV 错位"症状一样，量法不同**（看该组有没有 `vt` 引用）。

### 1.6 机构件整体消失：wrapper 是空的（notes/203 §8）

- **症状**：改了"部件批次"相关代码之后，雨刷**整体不见**。
- **真因**：`addObjModelPosition` 一身二职 —— 既把 ObjModel 放进批次表，**又调用 `objModel.addTransformation(...)`**；
  而 OBJ wrapper 的几何**只从登记过的变换里生成**（`OptimizedModel.fromObjModels` 按变换列表展开几何）。
  "不登记" = wrapper 空 = 什么都不画。
- **修法**：机构件**照旧登记**，但登记进一张**没人会拿去建整车模型的临时表**。
- **判据**：`tools/anchor-check/verify_plane_frame.js` 的源码守卫会报 `disappears`。

### 1.7 机构件多出一份：留在"关门态"批次里（notes/203 §8）

- **症状**：停位时只有一份，**一开雨刷就多出一个雨刷**（停位时两份重合、一动就分开）。
- **真因**：202 只把机构件剔出了**主** optimized 批次，忘了 **doors-closed** 那张 ——
  而**整车车身画的正是关门态那张**（`StoredModelResourceBase:51-52` 把 doors-closed 的 objModels 当整车模型建）。
  对**门**来说这不是 bug（门在关门态那份里的几何**就是关着的门**）；雨刷没有这种状态。
- **修法**：机构件两张批次表都不进，只由按部件那条路画一次（门与普通件行为一字未改）。
- **判据**：`tools/anchor-check/verify_plane_frame.js` 的源码守卫**同时**挡两个互为反面的错 ——
  查 `STATIC COPY`（多画一份）与查 `disappears`（漏登记消失）。**只查一边会把人从一边赶到另一边**
  （这正是本轮真实发生的事：先修成"消失"，再修回"多一份"，第三次才对）。

### 1.8 折面仪表拿不到 facet（notes/193）

- **症状**：折面仪表变成一块大平板 / 打包日志里 facet 数不对。
- **真因**：折面组的锚点法线曾取"组质心三点叉积"，折面组偏 **49°** → 客户端拿不到 facet 数据
  （顺带风挡 2D 域偏 5.8°）。
- **判据**：`tools/anchor-check/verify_facets.js`；打包日志 `hud facets: … faces=N`。
- **给模型的硬要求**：折面锚点**每块面必须是矩形**（相邻边 90°）；错切平行四边形客户端画不出来。
  （后来 201 让**仪表面**随台面错切，是在**客户端侧**用锚点基向量直接摆四角实现的，不违反这条——
  违反的是"期望客户端按矩形去猜"。）

### 1.9 面板画面本身的问题

花屏/碎块/镜像/上下颠倒/被底板盖住/文字方向 —— 归工作流 **§1.3**（一张贴图一个 bucket、`upload()` 不能改尺寸、
绕序朝 −Z、v2 才是上边、局部 +X 朝司机右手边、只画乘坐中那节）。验收症状对照工作流 **§4** 的表，
离线看画面用 `tools/panel-preview`（别拿游戏当画布）。

## 2. 「上车」一族（驾驶层 B2）

### 2.1 按 G 之后实体消失 / 视角被锁死 / 进不去（notes/198）

- **三个症状一个根因**：雨刷层的一行**诊断**在 `ridingPositionCacheOld` 还为空的帧上无条件解引用 →
  NPE 从 `MmtrWindshield.render` 抛穿 `RenderVehicles.iterateWithIndex` 的 lambda →
  **`movePlayer` 在雨刷渲染之后，永远轮不到** → 偏移永远算不出来 → 每帧再 NPE → 骑乘计时器超时 `leaveRide`；
  同一个 NPE 从实体渲染抛出还**打断整批实体渲染** = "所有实体瞬间消失又突然出现"。
- **第二个真因（我自己写的锁）**：上车锁跟了**本地请求**而不是**引擎判定** ——
  按下瞬间就 `mmtrIsInCab()=true`，引擎一拒绝就把玩家**冻在原地**（"视角被扭到固定位置"）。
- **修法**：① 渲染路径里的诊断**绝不允许抛异常**（两处解引用判空）；
  ② **上车与持钥匙拆开**：上车永远本地成立（不看权限），**司机锁只跟引擎镜像**
  （`getMmtrActiveCabFromSync` + 钥匙含 `crew`）。
- **教训**：渲染循环里的一行日志可以产生"实体消失"这种完全不相干的症状。
  失败必须留痕（新增 `[MMTR-CAB]` 请求/结果、`[MMTR-RIDE] 结束骑乘（原因）`，`leaveRide` 必须带原因）。

### 2.2 上不去车：OBJ 车**没有地板盒**（notes/199）

- **真因（三层）**：MTR 的**两个 `writeCache` 重载功能不对等** —— **OBJ 路径根本不收集 FLOOR/DOORWAY 盒**
  （只有 NORMAL）→ OBJ 车 `floors` 恒空 → `VehicleResource` 落到兜底：日志
  `No floors or doorways found in vehicle models` + **合成地板 `y = 1 + legacyRiderOffset`**；
  而 `VehicleRidingMovement.clampPosition` 要求盒在 Y 上包住骑手（兜底只容 `|盒顶−骑手Y| ≤ 1 m`）。
  101 骑手在 **y=3.13** 而默认合成地板在 **1.0** ⇒ 差 2.13 m ⇒ **一上车就被踢**。
- **修法（只改打包器）**：写 `legacyRiderOffset = (mmtr_seat 眼位 − 1.62) − 1`
  （现代包支持的 `VehicleResourceWrapperSchema` 字段）→ 101 得 **2.13 → 合成地板 3.13**，相机正好落在建模眼位。
  其他车型算出来是 −0.12（在容差内，不重打包也能用）。
- **判据**：`sandbox/cab_floor_check.js`（座位点 vs 打包 OBJ 的 floor 盒）；日志里那句 `No floors or doorways` 就是它。
  规则进工作流 **§1.6**。

### 2.3 人落在车厢外：**存档里的 `length` 引擎真的在用**（notes/197 坑A）

- 引擎走 `VehicleCar.getTotalLength`，用的是**世界存档里那份副本**，不是资源包声明。
  BR101 存档 `length 16.0(±8.0)` 而座位锚点在 **±12.53** → 按 G 会把人放到**车厢端部外 4.53 m**。
- **判据/修法**：`mmtr/scripts/fix-rolling-stock-dims.ps1`（默认 dry-run、**服务端在跑时拒写**、写前备份、
  逐键对比、幂等）。dry-run 实测 20 处不一致（br101 在两个车厂各一辆 + 8 辆 saf101/p1 的转向架位置）。

### 2.4 编组体**静默降级**（notes/197 坑B）

车长超过股道时 `mmtrConsistWalkerFromYard` 返回空，spawn 会**无声**退成"没有驾驶室的遗留整车"
（此后 `cab` 一律答"不是编组体车"）。**改完尺寸必须复查这一条**——它没有任何显式报错。

### 2.5 相机比眼位低（notes/198 §4 → notes/201）

`sandbox/cab_view_check.js` 量出**相机在 3.940 而模型眼位 4.750（差 0.81 m）**：MC 眼高固定 1.62，
与按真车建的台面高度不匹配。修法是把 `mmtr_seat` 眼位抬到 **5.12**（连 `SeatCam` 一起），
合成地板随之变 3.5。**眼位不是"看着差不多"，它是 `legacyRiderOffset` 的输入，直接影响能不能上车。**

## 3. 「雨刷」一族（W4 实体雨刷）

### 3.1 按 J 完全不动（notes/202）

- **真因**：几何**根本没进那次带旋转的绘制** —— OBJ 部件默认全进 optimized 主批次
  （`objModelsForPartConditionAndRenderStage`），部件级变换作用在空气上；而当时 W4 分支写在
  `if (OptimizedRenderer.hasOptimizedRendering())` 的 `else` 里，**默认（优化渲染开着）永不执行**。
- **修法**：给 `ModelPropertiesPart` 加 `isMechanism()`（`wiper*` 与门同路：走 `optimizedModelDoor`、
  从主批次剔除），`renderNormal` 的 W4 分支在旋转栈内 queue 该 wrapper。
- **判据**：`[MMTR-WSHLD] wiper part …` 单次日志（**"没动"与"档位没变"症状一样，日志能分开**）。

### 3.2 会动但"动得不对"（notes/203）

用户原话：**刀片向下弯、两根杆子飞到天上**。三个量，必须同时对：

| 量 | 错法 | 量级（BR101 实测） |
| --- | --- | --- |
| **轴** | 从 `up` 的分量猜欧拉角（`pitch=asin(-up.y())`） | 轴偏 **13.81°**（pitch 51.90 vs 正确 38.10），基向量最大偏差 0.170 |
| **支点** | 把平面坐标 `(u,v,0)` 当模型坐标平移 → 旋转轴穿过**模型原点** | 支点离玻璃中心 ~1.2 m（整块玻璃之外）→ 杆子飞天 |
| **比例** | 配置里 pin/pivot 是 **0..1 比例**，`pointAt` 要的是**相对玻璃中心的米**，漏了 `−0.5` | 右向 0.6475 m、上向 0.2782 m |

- **正确取角**（`M = Ry(yaw)·Rx(pitch)·Rz(roll)`，列 = `(right, up, normal)`）：
  `pitch = asin(-normal.y())`、`yaw = atan2(normal.x(), normal.z())`、`roll = atan2(right.y(), up.y())`。
- **正确姿势**：矩阵栈是**模型空间**，先 `plane.pointAt()` 把支点抬到玻璃上，再 `translate·旋转·反平移`；
  整块连杆运算统一到"相对玻璃中心"的米制系（**安全**：连杆运算只用点间差值，共同平移不改变结果）。
- **顺带一个近似**：杆（rod）是刚体，一端在自己的支点、另一端销在刀片上，**转角不是曲柄角 θ**
  （理想平行四边形才相等）。现在臂/杆/刀片共用一次连杆解算：臂转 θ、杆转 `∠(br−p2) − ∠(br0−p2)`、刀片转销对走过的角。
- **判据**：`tools/anchor-check/verify_plane_frame.js` —— **源码守卫**（断言从 `normal` 取角、支点先 `pointAt`、比例先减 0.5、
  机构件只画一次）+ **帧契约**（正交、`right == up × normal`、反解重建基、共轭轴=法线/转角=θ）+
  **桥梁断言**（`K` 作用在停位臂销上必须与"平面内绕法线转 θ"重合到 5e-6 m，且支点落在玻璃面上）。

### 3.3 两份几何 → 见 §1.7

### 3.5 一块玻璃两把雨刷：只有一把动 / 两把抢同一把配置（notes/279）

一块玻璃可以有多把雨刷（§1.4⑥），名字的**第三个索引**是"第几把"：`mmtr_wipersweep_1_1_2` +
`wiper_1_1_2`（同一块玻璃 `mmtr_windshield_1_1` 的第 2 把）。这一族错的共同点是**索引对不上**，
而且对不上时的表现都不是报错，而是"某一把不动"或"两把一起动"：

| 症状 | 先量什么 | 真因 | 判据 |
| --- | --- | --- | --- |
| **一块玻璃上只有一把动，另一把钉在停放位** | 模型里第二把的件名 | 件名漏了 `_2`（两把都叫 `wiper_1_1`）→ 打包器只认到一把，第二把没有部件；或第二把没有自己的 `mmtr_wipersweep_1_1_2`（没有扇形 = 没有该把的配置） | 打包器日志 `windshield windshield_1_1: 2 wipers on one glass (wipers 1, 2)`；`[MMTR-WSHLD] modelled wiper part … has no fitted wiper 2` |
| **两把按同一套参数动**（一起摆、同角度） | 锚点 JSON 里该玻璃的块 | 两个扇形重名（都叫 `mmtr_wipersweep_1_1`）→ 后一个覆盖前一个；打包器会打 WARNING | `verify_windshield.js`：同一 (玻璃, 把号) 被两个扇形认领即 FAIL |
| **第 2 把按第 1 把的参数动**（支点/停放角错位） | 配置里的 `wiperIndex` | 只按下标对齐配置与实体件；模型只画了第 2 把或编号不连续（1、3）时，下标会**静默**接错刀片 | 配置里 `wiperIndex` 是**显式**写出的（notes/279 §2），客户端按它查而不是按下标 |
| **水在行程中间被放下 / 两把互相把对方的积水带走** | 是否两把共用一份"谁在推水" | 每颗雨滴只能属于**一把**（`Drop.carriedByWiper`）；允许两把同时认领会让"到端释放"互相判反 | 客户端**顺序**跑两把，且另一把的通过**完全跳过**非自己的水（notes/279 §3） |
| 打包后**单雨刷车型配置变了** | 该玻璃有没有 `wipers` 键 | 单雨刷必须写**扁平**字段（与多雨刷之前逐字节一致） | `verify_windshield.js` 的单雨刷用例 + notes/279 §4 的对照探针 |

> **不要**用"把玻璃拆成两块"来绕多雨刷：那样会得到**两份雨**（两份雨滴/湿度/贴图），
> 两块之间会有可见的接缝与两倍开销，而实体上是一块玻璃。

### 3.4 刮拭区与刀片不一致（notes/187、193）

- 擦拭公式分两族（**单轴=扇形**、**平行连杆=带**），由几何自动选择（有没有第二支点），不是开关；
- `sweepSign` 写错会让刀片走**反方向**（真实连杆不是理想平行四边形，反向走过未装配区间 →
  会出现"89° 的刀片自转"和"带测试失败"这种假 FAIL）；
- 校验器曾有两处假 FAIL（没乘 `sweepSign`；band 要求"弦=弧"，而正确模型差 3.79 mm 的**弧凸**）。
- 现在刀片与刮拭**共用同一份动画状态**，且实体刀片的运动学与 `bladeSegmentM`（雨滴擦拭用）同源。

## 4. 「仪表」一族

### 4.1 角度差 68°（notes/200）

`MmtrPanelQuad` 一直在用**欧拉反解**摆面板，而这套解**只对竖直面板成立**
（它把 `up` 的竖直分量当成 pitch 的全部）：风挡差 **90°**、BR101 仪表实测差 **68°**。
**修法**：直接用锚点的**正交基**摆四个角（`centre + right·a + up·b + normal·lift`），只套车体变换、没有局部旋转 ——
面在不在建模的面上变成**按构造成立**，与缠绕/倾角/`up` 朝向无关（注意 `transform()` 会 push，必须 `pop()`）。
判据：`tools/anchor-check/verify_panel_frame.js`（全局镜像 `u→1-u` 既连续又铺满又合比例，**只有"u 朝司机右手增大"能发现**）。

### 4.2 仪表面与仪表台不贴合（notes/201）

用户要求"仪表面要和仪表台的流线贴合"：两侧翼板从**矩形**改成**随台面走的错切平行四边形**
（8 个外顶点吸附到台面 quad；翼板 85.695° vs 台面 85.696°，残差 1.0 mm 是既有的折痕偏移），中间板不动；
代价是画面被剪掉约 4.3°（用户已接受）。产物 `BR101_v6.zip`。

## 5. 「工具链 / 环境」一族

### 5.1 PowerShell 无 BOM → **静默丢行**（notes/196）

`.ps1` 全是 UTF-8 **无 BOM** + 中文注释 → Windows PowerShell 5.1 按 ANSI(GBK) 解码：
① 38 个文件直接**解析失败**（含 `env\workspace.env.ps1` → `JAVA_HOME` 指向机器上的 JRE 8，客户端起不来）；
② 更阴的：`dev-client.ps1` **解析报 0 错**，但错配的注释把第 7 行的 dot-source **整行吞掉**了 —— AST 里它根本不存在。
**"能解析"不等于"语句还在"。**
- 修法：给所有无 BOM 的 `.ps1` 加 UTF-8 BOM（`mmtr/scripts/add-utf8-bom.ps1`，幂等）。
- 判据：`sandbox/parse_audit.ps1`（5.1 解析审计）+ `sandbox/ast_probe.ps1`（AST 语句审计）。
- **纪律**：工作区脚本一律用 `pwsh` 跑。

### 5.2 zip 相关三类（工作流 §6 + notes/191）

- **条目名分隔符**：`Compress-Archive` 写反斜杠 → Java 读不到（打包器自己写 zip，条目名恒为 `/`）；
- **文件名必须全小写**：MTR 把资源路径整体转小写 → `HST_H.obj` 静默读到空串 → 模型不显示；
- **薄片索引偏移**：自动追加的 `doorway_*`/`floor` 薄片面索引必须是"已有顶点数 + 薄片内偏移"；
- **服务端锁 zip / 孤儿 JVM**：见 §1.3。

### 5.3 路径机相关 / 客户端起不来

- 脚本里禁止机器相关绝对路径，用 `${MC_ROOT}` 占位（判据：`mmtr/scripts/check-paths.ps1`）。
- 客户端起不来常见两个：`JAVA_HOME` 指向 JRE 8（见 5.1）；`config\iris.properties` 里
  `shaderPack=` 仍指向某个会让 Iris 在 `onLoadingComplete` 抛 `NoClassDefFoundError` 的包
  （`enableShaders=false` **不足以**避免，得把 `shaderPack` 也清掉）。

## 7. 横向教训（为什么这类问题反复出现）

1. **MTR 的 OBJ 路径失败以"静默"为主**：覆盖、空串、退化成默认、被批量吞掉、被异常打断。
   → 因此**每一类症状都要有一条离线判据**，而判据必须能在**喂坏数据时变红**（所以有 `selftest` 的故障注入）。
2. **同一症状常有多个独立死法**："车看不见"至少有 §1.1 / §1.2 / §1.3 三类，
   "雨刷不对"有 §3.1 / §3.2 / §3.3 三类。→ 排查流程是**量中间量、逐段切分**，
   而不是猜一个原因然后改代码（本轮"雨刷不转"就是这样逐环量出来的：档位 → 状态 → 部件名匹配 → 几何在不在那次绘制里）。
3. **两套坐标系的交界是 bug 高发区**：文件↔渲染（`(x,−y,−z)`）、渲染↔骑乘（`(−x,y,−z)`）、
   配置**比例**↔**米制**。每次跨界都要问一句"这一侧的量纲/原点是什么"。
   §3.2 的 `−0.5` 与"支点被当模型坐标"都是这一条。
4. **欧拉反解不要用来摆倾斜面**：从基向量"看着取角"在倾斜/退化面上必错（风挡 90°、仪表 68°、雨刷 13.81°）。
   正确做法只有两条：**用欧拉角必须从矩阵元取**（§3.2），或者**干脆不反解、直接用正交基摆点**（§4.1）。
5. **渲染路径里的诊断必须无异常**：一行日志能把"整批实体渲染"打断（§2.1），
   症状与原因看起来毫不相干。
6. **"优化渲染开着"是默认前提**：OBJ 车的几何在哪里被画（主批次 / 关门态批次 / 部件 wrapper）
   决定了"部件级变换能不能生效"。改动这一层要同时交代**几何从哪来**（登记变换）与**几何在哪画**（批次），
   少一个就"消失"，多一个就"多一份"（§1.6 / §1.7）。
7. **流程性坑与代码坑症状相同**：先停服再打包、包比模型旧、`Compress-Archive` 反斜杠、
   文件名大小写、`.ps1` 编码 —— 这些都不报错。**"命令跑完了"不等于"东西变了"。**
8. **数值要落进文档**：本篇记住了 13.81°、68°、90°、2.13 m、±12.53、16.0 vs ±8.0、32 m、
   `#v/#vt/#vn` 10482/2568/3092、20 处尺寸不一致…… 这些数就是下次一眼定性的依据；
   只写"角度不对"下次还得从头查。
9. **判据自己也会假 FAIL，而且比不判更坏**：它会把**正确的模型**报成坏的，让人去改一件没错的东西。
   这几轮真实踩到三处：`verify_windshield` 曾没乘 `sweepSign`、曾要求 band 的"弦=弧"
   （正确模型差 3.79 mm 的**弧凸**）；`verify_facets` 的 `outOfQuad` 用**交叉量的绝对阈值** `1e-12`，
   而顶点正好落在 quad 角点上时交于该角的两条边给出 ±1e-7 的**浮点噪声**、符号相反
   → 一个完美角点被报成"越界一整个宽度"（而且 `inQuad` 还没把容差传下去）。
   **规矩**：判据红了先问"是它错了还是模型错了"；容差按**可解释的量级**写（注释里写清为什么是这个数）；
   并且**每条判据都要有故障注入证明它有牙**（`tools/anchor-check/selftest.js`，当前 32/32）。
