# 性能探针运行手册

> 设计（有哪些探针、判据是什么）看 [`01-设计/性能探针与侦测项-设计.md`](../01-设计/性能探针与侦测项-设计.md)。
> 这篇只讲**怎么跑、怎么读、读完怎么动手**。
>
> 一句话：服务端"卡"的时候，先 `probe on` 看 30 秒的 `[MMTR-PROBE]` 行，**别急着改代码**。
>
> ⚠️ **1–7 节全是服务端**。客户端帧率看 **§8**（`[MMTR-FRAME]`）—— 那是另一套探针，开关与读数都不同。

## 1. 三十秒上手

### 1.1 已经跑着的服务端（推荐：不动进程）

网页指令栏（`mmtr-studio` / 引擎网页的指令输入）或游戏内控制台敲：

```text
probe on          ← 开（每 100 tick = 5 s 一行汇总）
probe dump        ← 立刻读一次（不打断统计）
probe off         ← 关
probe reset       ← 清零，做前后对照时先来这一下
```

读数的落点：服务端日志里搜 `[MMTR-PROBE]`（和 `[MMTR-HLTH]` 健康行同拍，两张表说的是同一个 5 s 窗口）。

### 1.2 从启动就开（要抓开机头几分钟 / 不想记得敲）

```bat
:: 服务端启动参数里加（game/fabric 的 run 配置或 dev-server 脚本）
-Dmmtr.probe=true
-Dmmtr.probe.interval=100        :: 每多少 tick 一行（抓尖峰调小，例如 20）
-Dmmtr.probe.warnMs=40           :: 单帧超过多少毫秒就进最坏帧榜（默认 40 ≈ 两个 tick）
-Dmmtr.probe.file=…              :: 明细追加到文件（默认只进 stdout）
```

引擎侧默认把明细写到 `<引擎数据根>/mmtr-perf-probe.txt`（启动那行 `[MMTR-PROBE] 探针已开…` 会打出全路径）。
**注意**：`game/fabric/run/` 下是存档与运行产物，不属于仓库；要留档请把 `-Dmmtr.probe.file=` 指到 `logs/<yyyy-MM>/`。

### 1.3 离线量（不开游戏，可重复，适合做前后对照）

```bat
cd mmtr\engine
set JAVA_HOME=..\..\env\jdk-21
gradlew.bat test --tests "org.mtr.core.mmtr.probe.MmtrTickBudgetTests" --offline
gradlew.bat test --tests "org.mtr.core.mmtr.probe.MmtrProjectionKillCurveTests" --offline
```

它把**运行中的存档整份复制**到 `engine/build/mmtr-tick-budget/`，在副本上跑（线上一个字节不动）。

## 2. 一行读数怎么读

```text
[MMTR-PROBE] minecraft/overworld frame=sim n=100 wall=100104ms busy=37ms avg=0.37ms p50=0ms p95=1ms p99=4ms max=6ms over40ms=0
[MMTR-PROBE] 分段（累计毫秒/次数，按累计耗时排序）—— rails.tick1=13ms/400 | projection.solve=41ms/865 max=3ms | projection.hit=0ms/0 ev=28224 | sections.rebuild=31ms/3 |
[MMTR-PROBE] 最坏帧（tick#=耗时）—— #18422=40685ms(world.fill×1108) #19011=2100ms(save)
```

| 字段 | 意思 |
| --- | --- |
| `frame=sim` / `frame=server` | 引擎模拟 tick / MC 服务端 tick。**两个时钟，别混着比** |
| `n` | 这一窗口跑了多少帧 |
| `wall` | 窗口首帧到末帧的墙钟跨度（`n=100` 而 `wall≈5000ms` = 正常 20 TPS；`wall=100000ms` = 落后了 95 s） |
| `busy` | 这些帧**忙的总时长**（`busy ÷ wall` = 占用率） |
| `avg / p50 / p95 / p99 / max` | 单帧耗时分布。p50≈0 而 max 很大 ⇒ **尖峰**；整条分布都抬起来 ⇒ **稳态慢** |
| `over40ms` | 超过 `warnMs` 的帧数（桶边界跟 `warnMs` 一起动，名字就是门槛） |
| `名字=累计ms/次数 max=单次最坏ms ev=事件数(Σ和) peak=峰值` | 分段。**次数比毫秒更早暴露放大**（每 tick 上万次 = 每 tick 全量重算） |
| 最坏帧榜 | `tick#=耗时(标签)`。标签是外面塞进来的活（施工/存档），用来分开"引擎的锅"与"外面的锅" |

## 3. 症状 → 先看哪几个读数

| 你会看到 | 先读 | 大概是什么 |
| --- | --- | --- |
| 日志里周期性 `Can't keep up! Running 40685ms / 813 ticks behind` | `server.tickSpan p99/max` + 最坏帧榜 | 尖峰。有 `world.fill` 标签 = 施工期；没有标签而 `mmtrHooks` 大 = 每-tick 钩子 |
| 一直卡、不是一阵一阵 | `frame=server avg` 与各段 | 稳态慢：`server.mmtrHooks` / `server.vanillaAndEngine` 谁大 |
| `vehicles=0` 却卡（现场就是这条） | `server.mirror.*` 各段 + `projection.*` | 每 tick 全量重算（notes/335 §4） |
| 加了一座站就明显更卡一档 | `projection.evict` + `projection.entries peak` + `projection.solve` 次数 | 缓存撑爆后整体 `clear()` |
| 网页打开就卡 | `web.runs` / `web.shed` / `web.skipSlowTick` / `webSlow`（健康行） | 网页重活落回 tick（notes/172 的预算闸在起作用吗） |
| 车一动就卡 | `vehicles.simulate` / `signal.aspectView` / `points.*` | 车辆走行或信号视图重建 |
| 一保存就顿一下 | `save.auto` 的单次毫秒 | 落盘吃掉整帧 |
| 客户端一多就卡 | `clients.sendUpdates` | ∝ 人数 × 脏对象；**无头环境量不到，只能在实机读** |

## 4. 冷启动 vs 稳态：先看这张表再解释任何数字

离线量到的真实读数（2026-09-27，`rails=294 lamps=250 sections=250 turnouts=28 vehicles=0`）：

| 量的是什么 | 第 1 次（冷） | 其后（热） | 说明 |
| --- | --- | --- | --- |
| 引擎 400 步（每步 50 ms 仿真） | — | **0.13 ms/步**（p50=0、max=7 ms） | 一次模拟 tick 只占 20 TPS 预算的 **0.3%** |
| `rails.tick1` | — | 13 ms / 400 次 | 引擎里最大的一段 |
| 游戏端每-tick 链（`lampAspectNames` + `lampBindings`） | **37 ms** | **13 ms** | 一个服务端 tick 走一次 = 26% 的 tick 预算 |
| 单次弧投影 | **0.045 ms** | **0.0017 ms** | 冷热差 **≈ 27×** |

两条结论直接可用：

1. **40 s 的落后不在模拟里**。引擎 tick 是 0.13 ms 级；而游戏端那条每-tick 链是 13–37 ms 级，
   813 个 tick 上就是几十秒 —— 与现场读数同量级。
2. **冷启动与稳态差一个数量级**。所以任何"前后对照"都要先预热（离线用 `-Dmmtr.budget.steps`，
   实机等 `probe on` 之后至少一个窗口），否则量到的是 JIT 与缓存冷启动。

## 5. 读到问题之后：动结构之前的三条纪律

1. **逐位相同**（notes/328 §R）。允许的加速只有"同一份输入上的重复劳动不要重复做"（记忆化、脏标记、按轨索引候选灯）；
   **不允许**改采样步长、换近似算法、跳过计算、改节拍。做完要用 golden trace 对拍。
2. **先做"能不能省"的实验，再改代码**。`server.mirror.unchanged ÷ 总 tick 数` 就是那个实验：
   如果 ≈1，说明绝大部分 tick 的结果与上一 tick 逐字相同 —— 脏标记/节流能省掉的正是这部分。
   这个比值要在**现场**读（离线量不到镜像链的 changed/unchanged，因为离线没有客户端与真实 tick 顺序）。
3. **改完必须能回到同一张表**。所以探针的段名是稳定的接口：改结构之后 `probe dump` 的那几行应当还在，
   数值应当按预期变化。**读数消失 = 埋点被重构掉了**，用例 `MmtrTickBudgetTests` 会在 CI 里红。

## 6. 想加新探针时

```java
final long probeT = org.mtr.core.mmtr.probe.MmtrProbe.begin();
try {
    doTheWork();                       // 一行都不许因为探针而改变
} finally {
    org.mtr.core.mmtr.probe.MmtrProbe.end("名字.子名字", probeT);
}
```

- **段名口径**：`子系统.动作`（`rails.tick2`、`server.mirror.lampAspects`）。游戏端加 `server.` 前缀。
- **不耗时的事件用 `hit()`**（命中、重建次数、跳过次数），带数值用 `event(名字, 值)`，峰值用 `peak()`。
- **别埋在循环体里**：埋在"一段工作的边界"。一次调用的纳秒级 `nanoTime()` 在 250 灯 × 294 轨的循环里就是灾难。
- **别加会淹没日志的输出**：要加就加段名（汇总行有界，最多列 24 段）。
- 加完顺手在 `MmtrTickBudgetTests` 的阶段断言里点名，防止它被静默重构掉。

## 7. 工具与环境备忘

| 事项 | 说明 |
| --- | --- |
| `JAVA_HOME` | 引擎/游戏编译都要 JDK 21（`env\jdk-21`）；系统默认若是 JDK 8 会直接 `JAVA_HOME is set to an invalid directory` |
| Gradle | 两个工程各自 `gradlew.bat`，离线加 `--offline`；引擎侧 `compileJava` 依赖 `generateVersion`/`generateSchemaClasses`/`setupWebserver` 三个生成任务 |
| 引擎 jar 同步 | 改了引擎要同步进 `game/libs`：`mmtr\scripts\sync-engine.bat`（或 `deploy-engine.ps1 -Build`，后者带停机检查） |
| 存档 | 离线用例只读副本；实机 `probe` 不改任何游戏数据（探针不写存档） |
| 崩溃取证 | 看门狗杀掉时先看 `crash-…-server.txt` 的栈顶，再用 `probe dump` 看同期的段读数（栈给出**位置**，探针给出**代价**） |
| **进服务器就闪退** | 先看 `fabric/run/logs/latest.log`（**是追加日志，必须按时间过滤**）里有没有 `ClassNotFoundException: org.mtr.mod.block.IBlock$1` 这类**合成的 `$1` 内部类**。那是 `build/classes/java/main` 残了（gradle 增量与磁盘不一致，且它还会报 `UP-TO-DATE` 假绿），**跟代码无关**：删掉 `mmtr\game\fabric\build\classes\java\main` 后 `.\gradlew.bat :fabric:compileJava --console=plain --no-daemon` 重编。`mmtr\scripts\check-java-compile.ps1` 会替你发现（它报"缺 N 个源文件的 class"）。详见 notes/281 |

## 8. 客户端帧率：`[MMTR-FRAME]`（`MmtrFrameProbe`）

> 上面 1–7 节全是**服务端**。客户端原先只剩两个总帧率 —— `[MMTR-PERF]` 的
> `帧=…（… FPS）` 与 `[MMTR-LIGHT] 性能` 的 `平均帧时`；两条互相印证，但**都不说时间花在哪一段**。
> 设计文档自己把这条写在"量不到的"里（[`01-设计/性能探针与侦测项-设计.md`](../01-设计/性能探针与侦测项-设计.md) §5），
> 于是现场只能靠"关掉一个特性看帧率动不动"去二分。§8 补的就是那一步。
>
> 默认**开**（与 `[MMTR-PERF]` / `[MMTR-LIGHT] 性能` 同口径：都是一直开着的客户端遥测），
> 每 5 秒一行。关掉：JVM 参数 **`-Dmmtr.frame=0`**（关掉后每次调用只剩一次 `volatile` 读）。

### 8.1 一行读数怎么读

**形状示例**（数字是编的，用来对齐字段；真实值以现场为准）：

```text
[MMTR-FRAME] 5.0s 窗口：帧=214（42.8 FPS）帧间隔 p50=23ms p95=31ms 最慢=57ms ｜ 已量段合计=18.40ms/帧
  ｜ 通行=2.00/帧（阴影 214 + 主 214） ｜ 阴影pass avg=8.10ms ｜ 主pass avg=10.30ms
  ｜ 分段（累计ms/次数 max=单次最坏ms，按累计耗时排序）—— main.vehicles=1204ms/214 max=9.80 | shadow.vehicles=980ms/214 max=7.20 | main.rails=612ms/214 max=8.10 | main.lightfield=430ms/214 max=12.40 | shadow.rails=520ms/214 max=6.90 | main.submit=180ms/214 max=2.10 | main.simulate=96ms/214 max=3.40 | main.tick=92ms/214 max=4.80 | …其余 3 段（累计更小，已折叠）
  ｜ 最坏帧（#帧号=耗时ms(最重段)）—— #1841=57ms(main.vehicles) #1792=54ms(shadow.vehicles)
  ｜ 说明：……
```

| 字段 | 意思 |
| --- | --- |
| `帧` / `（… FPS）` | 本窗口跑了几个**视觉帧**，以及由此算出的帧率 |
| `帧间隔 p50 / p95 / 最慢` | 相邻两个**视觉帧**之间真实隔了多久（= 1/FPS）。p50 小而最慢很大 ⇒ **尖峰型**卡顿（notes/177 那种"tick 还在跑、画面不出帧"） |
| `已量段合计=…ms/帧` | **不是帧时** —— 它是本探针埋了点的那些段在一个视觉帧里的合计。**与 p50 一比就是覆盖率**（见 §8.2 D3） |
| `通行=…/帧（阴影 N + 主 M）` | 一个视觉帧被渲染了几次。**2.00 = 光影包的阴影 pass 开着**（见 §8.2 D1） |
| `阴影pass avg` / `主pass avg` | 两遍各自的墙钟均值；`阴影pass avg` 就是"阴影那一遍花了多少" |
| `名字=累计ms/次数 max=单次最坏ms` | 分段。名字带 **`main.` / `shadow.` 前缀** —— 同一段 Java 在两遍里各跑一次，**只有前缀能告诉你是谁付的钱**。次数比毫秒更早暴露放大 |
| 最坏帧榜 | `#帧号=耗时ms(最重段)`。帧号与该窗口的 `[MMTR-PERF]` 对齐；括号里是这一帧累计最重的那一段 |

**段名清单**（`main.` / `shadow.` 各一套）：

| 段 | 量的是什么 |
| --- | --- |
| `simulate` | 客户端车辆/电梯模拟（**只在主 pass**） |
| `tick` | 每帧钩子链：面板过期、面快照失效、交互键、驾驶输入…（**只在主 pass**） |
| `vehicles` | `RenderVehicles` |
| `lifts` | `RenderLifts` |
| `rails` | `RenderRails`（手持轨道工具时那个 33³ 节点扫描另有 `nodes` 段） |
| `nodes` | `RenderRails` 里的 33³ = 35937 次节点扫描。**次数 ÷ 帧数 = 1 ⇒ 这一帧手里拿着轨道工具** |
| `queue` | 渲染队列拷贝 + 派发 |
| `lightfield` | `MmtrLightField.beginFrame`：采集切片 + LUT + 上传 + 采样器绑定 |
| `submit` | 优化渲染器真正提交（`OPTIMIZED_RENDERER_WRAPPER.render`）。**这一段里没有任何 GPU 同步点**（该路径上无 `glFinish`/`glFlush`/swap，grep 实证）⇒ 它量的是 draw 循环里的**逐 draw CPU 成本**，与分辨率**无关**、随 **draw 数**走。见 §8.2 D9 |
| `wiper` | 挡风玻璃雨滴模拟 + 绘制。**次数 ÷ 帧数 = 每帧几节车**（每节车每帧一次）。开销 ∝ 车数 × 挡风数，与分辨率、与是否在视锥内**都无关** |
| `faces` | 车辆动态面/仪表画布（Java2D 软件光栅 + 纹理上传）。次数 ÷ 帧数 = 每帧有几节车真的画了面 |

### 8.2 判据

| # | 读到什么 | 说明什么 / 往哪查 |
| --- | --- | --- |
| **D1** | `通行` 明显 > 1（通常正好 2.00） | 光影包的**阴影 pass** 在跑 ⇒ 整个帧预算要按两遍算，`阴影pass avg` 就是那一遍的价钱。⚠️ 阴影贴图有自己的分辨率（由包与 `iris.properties` 的 `maxShadowRenderDistance` 决定），**不吃屏幕分辨率** —— 但这**不是**"分辨率调到极低、帧率却几乎不动"的主因：那个现象的主因是**逐 draw 的 CPU 成本**（D9）。**别据此去调阴影距离** —— 2026-10-05 走过这个弯路，纠正过程见 §8.5 |
| **D2** | 某段 `次数 ÷ 帧数` > 1 | 这段每帧跑了不止一遍（`shadow.*` 与 `main.*` 各算一套，所以正常的"跑两遍"已经由前缀分开；这里是**同一前缀内**的次数异常） |
| **D3** | `已量段合计 ÷ 帧间隔 p50` | ≈ 1 ⇒ 帧时基本被表里的段解释完了；**明显偏小** ⇒ 时间在**没埋点**的代码、**别的线程**（区块构建 / 遮挡剔除 WorkerThread）或 **GC / 呈现**上 ⇒ 这时才转 `F3+L` 的分析器（§8.4） |
| **D4** | 某段均值不大但 `max` 很大 | **尖峰**，不是稳态慢。配合最坏帧榜看是哪一段 |
| **D5** | `nodes` 的次数 ÷ 帧数 ≈ 1，且累计不小 | 手持轨道类工具时那个 33³ 循环在花钱。**空手 vs 手持信号灯各测一段即可证伪** |
| **D6** | `wiper` 在下雨时明显抬头 | 雨滴模拟按"车数 × 挡风数"收费。`/weather clear` 前后对照 |
| **D7** | `faces` 抬头 | 面板是 **Java2D 软件光栅 + 逐像素写入 + `glTexSubImage2D`**。⚠️ **画布像素数与 `guiScale` 无关**：`MmtrPanelCanvas` 的像素数只由 `最长边 × pxPerMetre` 决定、并夹在 `MAX_PIXELS=512`（实测以 **461×204** 为主 ≈ 9.4 万像素）。`guiScale` 只影响**屏幕 HUD** 那条入口（`createExactPixels` / `MAX_HUD_PIXELS=4096`）⇒ **别为了 `faces` 去调 `guiScale`**（2026-10-05 更正；此处早先写反了）。真正决定它的是**重画率**，见 §8.8 |
| **D8** | `lightfield` 每帧都有固定毫秒数 | 光场的**每帧采集**（`COLLECT_LAYERS_PER_FRAME` 与采样点数）。对照 `run/mmtr-lightfield.properties` 的 `enabled=false` |
| **D9** | `submit` 大，且 `draws/frame ÷ batches/frame` 很大（实测 2487 ÷ 12.00 ≈ **每批次 207 个 draw**） | `submit` 是**逐 draw 的 CPU 成本**。判据：`submit 累计 ÷ draw 数` = **µs/draw**（2026-10-05 实测 **4.5 µs/draw**）。⚠️ 但**别以为削掉每次 draw 的固定开销就能救帧率** —— 实测那样只把单 draw 从 4.54 降到 4.01 µs（−12%），帧率不动。**决定帧率的是 draw 次数本身，见 D10**。注意 `draws/frame` 是**每 pass** 的，一个视觉帧要再乘 `通行` |
| **D10** | `draws/frame` 高（实测 900–2800） | 与 FPS **强相关**（308 个窗口 r = −0.781，分档严格单调：1000–1500→45.6 FPS、1500–2000→31.1、2000–2500→22.1、2500–3000→20.5）。⚠️ **但"相关"不等于"唯一杠杆"**：2026-10-05 用 §8.7 的拆分校准后发现，当时真正的瓶颈是**车辆侧的 Java 开销**（`main.vehicles` + `main.faces` = 16.6 ms/帧），而全部 MTR draw 的提交只有 6.5 ms/帧。**先看 §8.8 的三问，再决定砍 draw 还是砍 Java** |

### 8.3 与另外两条客户端读数的关系

| 读数 | 它回答什么 | 与 `[MMTR-FRAME]` 的分工 |
| --- | --- | --- |
| `[MMTR-PERF]`（`MmtrPlayerMotionTrace`） | **帧与 tick 两条线分开量** + 镜像车数 | ⚠️ **它数的是 pass，不是视觉帧**：`frame()` 挂在 `RenderVehicles.render` 上，而那个方法开光影时一个视觉帧跑**两遍** ⇒ 它的 `帧=` 与 FPS 都是真值的 **≈2 倍**。判据：`[MMTR-PERF] 帧 ÷ [MMTR-FRAME] 帧 ≈ 通行` |
| `[MMTR-LIGHT] 性能：平均帧时=…` | ⚠️ 同样是 **pass 间隔**，不是视觉帧间隔（它的累加在 `beginFrame` 里，而那也是每 pass 一次）⇒ 开光影时它报的 FPS 也是真值的 **≈2 倍**。想要真帧率看 `[MMTR-FRAME]` 的 `帧间隔 p50` | 判据：`[MMTR-LIGHT] 平均帧时 × 通行 ≈` `[MMTR-FRAME]` 的 p50 |
| `[MMTR-LAG]` | 只在异常时打：帧间隔 > 250 ms、tick 间隔 > 150 ms | **尖峰的证据**：`[MMTR-FRAME]` 的最坏帧榜告诉你"哪一帧多长"，`[MMTR-LAG]` 告诉你"那一刻时间戳" |

> **为什么要专门写这一段**：2026-10-05 实测，同一个 5 秒窗口里 `[MMTR-FRAME]` 报
> **21.6 FPS** 而 `[MMTR-PERF]` 报 **42 FPS**、`[MMTR-LIGHT]` 报 **43.0 fps** —— 比值正好 `通行=2.00`。
> 也就是说**在光影开着的前提下，前两条读数的 FPS 一直是真值的两倍**（`draws/frame` 同理由此变成"每 pass 的 draws"，
> 一个视觉帧要再乘 `通行`）。`[MMTR-FRAME]` 是唯一把 pass 与视觉帧分开计数的读数。

### 8.4 本探针量不到的（写在明处）

1. **GPU / 驱动侧真正的绘制时间** —— 要 GPU timer query（notes/340 §8.1③）。所以 `submit` 小**不代表** GPU 不忙。
2. **别的线程**：区块构建、遮挡剔除 `WorkerThread`。它们抢的是核与内存带宽，会表现为"所有段都正常但帧间隔很大"（那就是 D3 的形状）。
3. **GC 停顿**落在帧中间的那一段 —— 同样表现为 D3 的形状。`F3` 界面的 `Mem` / `Allocation rate` 可以旁证。
4. **原版地形渲染**（区块网格构建/上传）没有埋点 —— 它属于"没埋点的代码"，D3 会把你的注意力引过去。

> 要看 1–4 里的任意一条，就用 **`F3+L`**（原版调试分析器）或 Spark / async-profiler。

### 8.5 2026-10-05：`submit` 的构成 = 逐 draw 的光场/车灯钩子

**症状**：分辨率调到极低帧率几乎不动；`通行=2.00`；而 `main.submit` ≈ `shadow.submit`
（11.3 / 8.7 ms）—— 两遍的像素量差一个数量级以上，价钱却相当。

**判定**：这是 **CPU 逐 draw** 的形状，不是 fill/GPU 的形状。分辨率只减片元、**一个 draw 都不会少**。
且 `OPTIMIZED_RENDERER_WRAPPER.render` 内部**没有** `glFinish`/`glFlush`/swap（grep 实证）
⇒ `submit` 量的是 draw 循环里的 CPU 工作，不是"等 GPU"。
（这也纠正了 §8.2 D1 早先的措辞：阴影距离与这个现象没有主因关系。）

**当时每个 draw 的固定开销** —— 三个挂点**各查一次** `GL_CURRENT_PROGRAM`，共 3 次：

| 挂点 | 逐 draw 做的事 | 一个批次内会变吗 |
| --- | --- | --- |
| `VertexAttributeStateMixin` → `MmtrLightField.uploadPackModelMatrix` | `glGetInteger` + HashMap + `glUniformMatrix4fv` + 3× `glUniform1i` | program **不变**；3 个标量**不变**（源值 2 秒才重读一次 properties） |
| 同上 → `MmtrHeadlights.upload` | `glGetInteger` + HashMap | **不变** |
| `BatchManagerRenderCallMixin` RETURN → `MmtrLightField.clearPackModelMatrix` | `glGetInteger` + HashMap + `glUniformMatrix4fv`（清零哨兵） | **不变** |

实测 `draws/frame=2487`、`batches/frame=12.00` ⇒ **每批次 207 个 draw**。
乘 `通行=2.00` ⇒ 一个视觉帧 ~4974 个 draw：**同一个 program 被查了约 1.5 万次，而上限只需 24 次**
（两遍 × 12 批次）；那 3 个标量 uniform 每帧被写约 1.5 万次，**真正需要写的次数是 0**。

**改法**（`submit` 的语义与画面都不变）：

1. **program 按批次缓存** —— `setupShaderBatchState` **RETURN** 处取一次（`MmtrLightField.onBatchProgramBound`），
   批次 **HEAD**、优化渲染器退出（`MainRenderer`）、包重载（`clearPackSamplerCache`）三处作废；
   **批次外自动回落到真正的查询**，即完全等于改前行为。
   依据：`BatchManager$RenderCall.draw()` 只绑 VAO、传逐 draw 顶点属性、`glDrawElements`，**不重绑 program**。
   地形那一路（Sodium `GlProgram.bind()`）不在批次循环里 ⇒ `uploadForTerrainProgram()` **始终现查**，不吃这份缓存。
2. **三个开关标量"变化才传"** —— uniform 是 **program 的状态**（写一次就一直保持），
   所以按 program 记住上次写进去的值即可（`PackSamplerBinding`）。源值一变立刻上传 ⇒ 仍是"改 properties 不用重启"。
3. ⚠️ **矩阵去重做不了，别再试**：`draw()` RETURN 每个 draw 都把 `mmtrModelMat` 清成**全零哨兵**
   （`clearPackModelMatrix`，为的是让后面的原版实体不误用上一个 MTR draw 的矩阵），
   所以 GL 里那个 uniform 的真实值**每个 draw 都不一样** —— "和上次相同就跳过"会直接错。

**验收口径**：同一编组、同一视距、同一路线前后各取一个 5 秒窗口：

| 读数 | 期望 |
| --- | --- |
| `main.submit` / `shadow.submit`（`累计ms ÷ 帧`） | 明显下降（`main.submit` 是主要观察对象） |
| `已量段合计` ÷ `帧间隔 p50` | 覆盖率上升（改前 66–75%） |
| `optimizer draws/frame`、`batches/frame` | **必须不变** —— 改的是"上传次数"，不是 draw 数 |
| 画面 | 车厢明暗、车灯、光场占比与改前一致 |

**零代码上界对照**：`run/mmtr-lightfield.properties` 的 `enabled=false` 会**同时**短路上述三个挂点
（`uploadPackModelMatrix`/`clearPackModelMatrix` 的 `!isEnabled()` 与 `MmtrHeadlights.canUpload()`），
所以它给出的是这笔开销的**上界**（代价是同时失去光场视觉效果），**不等于**修完能省这么多。

### 8.6 2026-10-05 收盘：§8.5 那个修复**没有**救到帧率，真凶是 draw 次数

§8.5 的修复实测结果（同口径 `累计ms ÷ 帧数`）：

| | 改前 | 改后 |
| --- | --- | --- |
| `main.submit` | 1231/109 = **11.29 ms/帧** | 1221/111 = **11.00 ms/帧** |
| `shadow.submit` | 950/109 = 8.72 ms/帧 | 924/111 = 8.13 ms/帧 |
| `draws/frame` | 2487 | **2741** |
| **单 draw 成本** | 4.54 µs | **4.01 µs（−12%）** |

少掉的 ~3 万次 GL 调用是真实的（单 draw −12%），但它在 `submit` 里只占 12%
⇒ **`submit` 的主体是 draw 调用本身**，不是 uniform 上传。§8.5 的假设方向错了。

**真凶（D10）**：`draws/frame` 与 FPS 强负相关（308 窗口 r = −0.781，分档严格单调）。
拆解（由 `批次：钢轨=N 车辆=M` 与 `draws/frame` 交叉得出，`钢轨+车辆` 每帧恰等于 `batches/frame`）：

| 场景 | `draws/frame` | `batches/frame` | 构成 |
| --- | --- | --- | --- |
| 只有钢轨、无车 | **924** | **1.00** | **1 个钢轨批次里 ~924 个 draw** |
| 钢轨 + 车 | **2741** | **12.00** | 钢轨 1 + 车辆 11 ⇒ 车辆侧 ~1817 |

**已排除**：车灯灯罩逐 draw 染色（`染色draw` ≈ 3.6 次/**帧**）、动态面（`main.faces` 9 次/帧、1.26ms/帧）。

**先做这两个零代码实验**（都以 `draws/frame` 为准，**别只看 FPS**）：

| 实验 | 预期 |
| --- | --- |
| `renderDistance` 32 → 8（`run/options.txt`） | 钢轨与地形 draw 大幅下降 ⇒ `draws/frame` 塌下去。**这是"降分辨率没用、降视距有用"的直接验证** |
| `disableShadowsForShaders` 打开（MMTR 配置界面已有按钮） | 跳过 MTR 内容在阴影 pass 的绘制 ⇒ `draws/frame` 约减半 ⇒ FPS 接近翻倍。代价：车厢/钢轨不再投影 |

> ### ⚠️ 验收性能改动时的一条硬纪律
>
> `[MMTR-FRAME]` 的 **`已量段合计` 同时是"这个场景里有没有 MMT 的东西"的判据**。
> 实测它的稳态值：**有车有轨 28–50 ms/帧**，**无车无轨 0.15 ms/帧**（此时 `draws/frame=0.0`）。
>
> 本轮就踩过：用户在**空场景**测到 97–98 FPS 以为修复成功，而那个场景里
> `已量段合计=0.15ms/帧`、`draws/frame=0.0` —— **零 draw ⇒ 逐 draw 的优化一分钱都没省**。
>
> **所以：验收任何性能改动，必须同时贴 `[MMTR-LIGHT] optimizer draws/frame`。**
> 它才是"场景里有多少活"的度量；只看 FPS 会把空场景的高帧率当成改进。

细节与"接下来该动什么"见 `notes/395`（否定性记录）。

### 8.7 `[MMTR-LIGHT] optimizer` 行的 draw 拆分（2026-10-05 加）

§8.2 D10 指出帧率由 `draws/frame` 决定，但当时**只有一个总数**，无法回答"这些 draw 是谁发的" ——
只能靠"有车的窗口 vs 只有钢轨的窗口"凑对照，而场景一直在变，凑不出结论。这一版把总数按来源拆开：

```text
[MMTR-LIGHT] optimizer draws/frame=923.0 batches/frame=12.00 (窗口 319 帧)
  ｜ 拆分：钢轨 draws=890.2(1.00批) 非钢轨 draws=32.8(11.00批)
  ｜ 非钢轨 top4：mtr:models/vehicle/saf420car.png=20.1(3.00批) | … | … | … …另 N 个贴图（合计 X.X draw/帧）
```

| 字段 | 意思 |
| --- | --- |
| `draws/frame` | **每 pass** 的真 draw 数（`BatchManager$RenderCall#draw()`）。一个视觉帧要乘 `通行` |
| `拆分：钢轨 … 非钢轨 …` | 按批次来源分桶后的 draw 数与批次数 |
| `非钢轨 top4` | 非钢轨那一侧**按贴图**细分，只列累计最重的前 4 项，其余折叠成一行合计（有界输出） |

**口径与依据**（细节见 `MmtrOptimizerStats` 的类注释）：

- 归属点选在**批次 HEAD**：MTR 的批次循环是"每桶 `setupShaderBatchState` 一次 → 把这桶的 RenderCall 全画完"，
  而 `RenderCall.draw()` 不重绑材质 ⇒ **一个批次内的每个 draw 必然属于这一批**，归属是精确的，不是推断。
- "算不算钢轨"复用 `MmtrLightField.isRailTexture` —— 与光场分 LUT **同一份判据**，不写第二份实现。
- `批次` 数与 `[MMTR-LIGHT]` 另一行的 `批次：钢轨=N 车辆=M` **应当一致**（后者是光场侧的同类计数）。若不一致，
  说明有批次没走到 `setupShaderBatchState`，那本身就是个发现。

**怎么用**：拿到拆分后按桶决定方向 ——

| 读到 | 往哪走 |
| --- | --- |
| 钢轨占大头 | `RenderRails.renderWithinRenderDistance` 里的两处剔除缺口（见 §8.6 末）：**< 32 格完全不剔除**、**32 格外只判"在相机前方"而不判左右**。都在 `RenderRails.java`，改它不牵动 MTR 的映射库 |
| 非钢轨占大头且贴图是车辆模型 | 走 `PartCondition` / 模型部件数，即 `mmtr-train-modeling` 的领域；视距与剔除都帮不上 |
| 非钢轨里出现钢轨贴图名 | `isRailTexture` 漏判（资源包把钢轨贴图放在别处）⇒ 光场那边也在漏，一起修 |

### 8.8 2026-10-05 收盘（第二次修正）：draw 数是**相关**，不是唯一杠杆

§8.7 的拆分上线后第一次实测（`renderDistance=8`，用户实机）：

```text
draws/frame=922.2  batches/frame=12.00  ｜ 钢轨 draws=638.2(1.00批)  非钢轨 draws=284.0(11.00批)
非钢轨 top4：mtr:saf420car/saf420.png=112.0(2.00批) | .../saf420_glass.png=104.0(1.00批) | cab_b=21 | cab_a=21
```

**拆分本身很干净**：钢轨 **69%** 的 draw 全在**一个**材质批次里（`1.00批` 装 638 个 draw ⇒ 再次确认 MTR 不做实例化合批）。
非钢轨那一侧只有 6 个贴图，全是 `saf420car` 的车辆贴图 —— 分类判据工作正常。

**但结论跟预期相反。** 同一次会话里，出现过一个**纯钢轨、零非钢轨**的窗口：

| 场景 | `draws/frame` | FPS | 帧时 |
| --- | --- | --- | --- |
| 只有钢轨 | 638 | **82.4** | 12.1 ms |
| 钢轨 + 车辆 | 922 | **34.6 – 35.8** | 28.6 ms |

⇒ **638 个钢轨 draw 单独跑出 82 FPS。** 加 284 个车辆 draw（`draws` 只 +45%）却让帧时涨了 16.5 ms。
若按"每个 draw 一样贵"去算，那 284 个 draw 要 58 µs 一个 —— 但分段表说明了真相：

| 分段 | ms/帧 |
| --- | --- |
| `main.vehicles` | **8.93** |
| `main.faces`（6.8 次/帧 ⇒ **每次 1.13 ms**） | **7.70** |
| `main.submit` + `shadow.submit`（**全部** 922 个 draw 的提交） | 6.49 |
| `shadow.vehicles` | 1.18 |
| rails（两遍，Java 侧） | 0.34 |

**车辆侧 Java 16.6 ms vs 全部 draw 提交 6.5 ms。** 那 16.5 ms 的增量几乎正好等于
`vehicles` + `faces` —— **钱花在 Java 侧，不在 draw 上。**

所以 D10 要这样读：`draws/frame` 与 FPS 的相关是**真的**，但它混了两个共变的项 ——
①随视距增长的 draw 数（rd 32→8 削掉的那 1534 个），②与视距无关的车辆侧 Java 开销。
降视距只治①，治完就撞上②（35 FPS 的地板）。

**§8.7 拆分 + 分段表 = 每次遇到"帧率低"要问的三句**：

1. `draws/frame` 拆出来**谁占大头**？（钢轨 / 车辆 / 其他）
2. 那个大头在**分段表里对应哪个段**？（`submit` = draw 提交；`vehicles`/`faces` = Java 侧）
3. 若钱在 Java 侧，**砍 draw 是白费** —— 去看对应的那段代码。

**当前最可疑的一项**：`main.faces` 的**每次调用成本是"双峰"的，不是渐变**（392 个窗口实测）：

| 工况 | `faces` ms/次 | `vehicles` ms/帧 | 会话里如何交替 |
| --- | --- | --- | --- |
| 便宜 | **0.06 – 0.19** | 1.7 – 4.1 | 每次持续 **10–15 s** |
| 昂贵 | **1.1 – 2.7** | 7.6 – 33 | 每次持续 **15–25 s** |

**中间没有过渡值（约 13 倍跳变），而且两种工况的调用次数一样**（都 8–9 次/帧）⇒ 翻转的是**单价**，不是次数。
更有决定性的是：**两种工况下车数完全相同**（`画到的车=2 锚点=4`），批次数也相同 ⇒ **不是"车更多了"，
而是同一个东西每帧被重新做了一遍。**

⚠️ **不要把它读成"相比 13:53 那次 0.134 ms/次 的 8 倍回归"** —— 那是同一会话里两种工况的取值，
不是时间上的恶化。（2026-10-05 我先写错过这一句，此处更正。）

**形状像"某个可开关状态"**：昂贵工况与便宜工况以 10–25 s 为尺度交替、中间偶尔夹着
`vehicles=0.02 ms/帧`（一辆车都没画）的时段；`[MMTR-CL] 车辆包：整份=1`（7 千多字节的整车包，
相对于 357 字节的补丁）总是紧跟一次翻转。⇒ 待查方向：**面板/动态面是否只在某个距离或状态下才真正光栅化**。

另外 `shadow.vehicles max=79.71 ms`、最坏帧出现 `136ms(shadow.vehicles)`，说明 `RenderVehicles`
还有百毫秒级尖峰，且**尖峰集中在阴影 pass**（那里 `millisElapsed = 0`）。

### 8.9 2026-10-05：钢轨合并烘焙（`[MMTR-RAILBAKE]`）

§8.7/§8.8 把"钢轨桶 638–890 个 draw 装在一个材质批里"量清楚了。这一版**换掉那个结构**：
把一根轨的全部实例烘成一个模型，一个材质一次 draw。原理见 notes/398。

**读数位置**：每 ~5 秒（主 pass 300 帧）一条，与 `[MMTR-LIGHT] optimizer` 行相邻：

```text
[MMTR-RAILBAKE] 窗口 300 帧：新建烘焙 3 次、其中光照重建 1 次 ｜ 缓存 5/96 项
```

| 字段 | 正常值 | 异常值意味着 |
| --- | --- | --- |
| `新建烘焙 N 次` | 稳态 **0**；进新区域/点亮灯时偶发个位数 | 持续每窗口都有非零 ⇒ 键在不停变（几何被反复重建？看 `hexId`/AABB） |
| `其中光照重建 M 次` | 稳态 **0**；黎明/黄昏/开关灯时成串 | 持续非零 ⇒ 光照**离散档位**的假设不成立，去查 `walk` 里采光的那两行 |
| `缓存 n/96` | 大致等于"可见轨 × 样式数" | 长期贴 96 ⇒ 一直在淘汰重建，把 `MAX_ENTRIES` 调大。**注意：把它和"失败次数"并排看** —— 若 `缓存 n` 明显大于累计失败次数，说明有键走了**静默**的"暂时取不到源几何"分支（2026-10-05 就是这么发现 `UNBAKEABLE` 哨兵把懒加载未完成的键永久毒住了，见 notes/398 §11） |
| **`最近一次烘焙：N 个实例 → M 个材质（= M 次 draw）`** | **M 是个位数**（钢轨模型 1–2 个材质） | **M 很大 ⇒ 材质没合桶**（源网格按面拆成了多份），合并等于没做；N 应该接近"轨长 ÷ repeatInterval" |
| 结尾的**状态**后缀 | 无 | `被 -Dmmtr.railbake=false 关掉了` / `拿不到源几何，已停用` / `烘焙连续失败 N 次，已自动停用` ⇒ 已整体回退，**性能回到改前**（画面仍然对）。后者去看第一条 `[MMTR-RAILBAKE]` WARN 的堆栈 |

> `最近一次烘焙` 那一项是**直接证据**，不用只看 draw 总数去反推：映射库的 `RawModel.upload`
> 是"每个带面的 `RawMesh` 造一个 `VertexArray`"，而 `BatchManager.queue` 给每个 `VertexArray`
> 建一条 `RenderCall` ⇒ **draw 数 == VertexArray 数 == 带面的 RawMesh 数**。
> 离线已用真类跑过场景校验（1 材质 × 200 实例 → 1 次 draw；2 材质 → 2 次），见 notes/398 §8。

**要看的两条判据（缺一不可）**：

1. **`draws` 掉下来了没有** —— 同一行区域里的 `拆分：钢轨 draws=…`。
   改前 638–890/通行，改后应是**个位数**（一根轨 1–2 个材质 ⇒ 1–2 次 draw × 可见轨数）。
2. **画面一模一样** —— 逐像素级对照，重点看三处：
   - **黎明/黄昏**（天空光档位切换，最容易露出"光照没跟着变"）；
   - **隧道里**（方块光是唯一光源，最容易露出"光照全错"）；
   - **光照档位切换的那一帧**（重建预算用完时会**继续画旧的**，这是设计如此，不该看到闪烁）。

**怎么知道"逐顶点光照"那一步真的生效了**：故意把每 draw 的 `light` 传成"默认（全亮）"
（见 `RenderRails` 里那段注释）。所以：

| 看到的 | 结论 |
| --- | --- |
| 钢轨明暗随环境正常变化 | 逐顶点光照生效 ✅ |
| 钢轨**整根发白/全亮** | 顶点映射没生效（`UV_LIGHTMAP` 仍被当成 GLOBAL）⇒ 走"按光照值分组 + 光照走 GLOBAL"的退路 |

**它不是"又一条探针"，是行为改动。** 出问题时按顺序退：`-Dmmtr.railbake=false`（全关）→
确认 `[MMTR-RAILBAKE]` 报出停用状态 → 此时 `RenderRails` 走的就是改前那条逐实例路径（**原样保留，不是重写**）。

**为什么它可以"只建一次"**：钢轨是引擎数据（`Rail` + `RailMath` 曲线），世界里只有 `BlockNode` 方块，
**没有任何持久网格**；而它只在玩家编辑线路或世界光照变化时才变。所以失效判据只有两个
（键里的几何 + 光照哈希），不存在"每帧都得重建"的理由。这与原版区块网格同理。

**改前的等价性怎么证（不依赖游戏）**：烘进顶点的是矩阵，所以"只改性能不改画面"可以离线证。
工具 `sandbox/railbake-verify/VerifyRailBake.java`（工作区外，不入库），20 万随机实例、世界坐标 ±30000：

### 8.9.2 实机第一次跑就翻车：`GlStateTracker: Not protected`（2026-10-05）

第一次实机的读数长这样 —— **这不是"没生效"，是"烘焙抛异常后按设计整体回退了"**：

```text
[MMTR-RAILBAKE] 烘焙钢轨模型时抛异常（第 1 次，共 5 次后停用）
[MMTR-RAILBAKE] 窗口 300 帧：新建烘焙 0 次 … ｜ 状态：烘焙连续失败 5 次，已自动停用（逐实例渲染）
[MMTR-LIGHT] optimizer … ｜ 拆分：钢轨 draws=671.0(1.00批)     ← 又回到改前的量级
```

**怎么一眼分辨"回退"和"生效"**：看量级和状态后缀。

| 读到的 | 含义 |
| --- | --- |
| `钢轨 draws` 仍是 **数百**，且带 `已自动停用` / `已停用` 后缀 | **回退了**（画面正常，性能 = 改前）⇒ 去看第一条 `[MMTR-RAILBAKE]` WARN 的堆栈 |
| `钢轨 draws` 掉到 **个位数**，无状态后缀，且 `最近一次烘焙：N → M` 里 M 是个位数 | **生效了** |

**根因**：建 `VertexArray` 必须在 `GlStateTracker` 的保护区里（`VertexBuffer.bind()` 会 `assertProtected()`）。
`OptimizedRenderer.beginReload()` 恰好提供这个保护区，**但它同时会重新编译 3 个着色器程序**，
所以不能按需调用；正确做法是直接 `GlStateTracker.capture()`/`restore()`，且**必须先判断是否已受保护**
（`isStateProtected` 是布尔量不是嵌套计数，盲目 restore 会拆掉外层保护区）。完整推导见 notes/398 §10。

**这条为什么安全**：`OptimizedRenderer.render()` 本身就是
`capture() → BatchManager.drawAll() → restore()`，而它是 `MainRenderer.render()` 的最后一步、
**每个视觉帧都跑** ⇒ `capture/restore` 本来就是帧中间的常规操作，`restore()` 的那几个副作用
本来每帧就已经发生一次。保护只需要罩住 `upload()`（建/绑）；`VertexArray.draw()` 与 `close()`
都**不**要求保护。

⚠️ 另一个**既有**问题（不是本次引入，但查等价性时撞上，详见 notes/398 §7）：Minecraft 的 `RotationAxis.rotation` 走 JOML 的 `rotationX/Y/Z`，其 `cosFromSin` 在 θ≈π 附近把 `w` 压成 0；
而钢轨恒有 `ax = π − pitch` ⇒ **近水平段（pitch ≲ 5e-4 rad）的俯仰被整段丢掉，小 pitch 上还有量化台阶**。
本次**刻意复刻**这个行为以保证画面逐位不变（用欧拉写法会更准，但那就顺手改了观感）。
要修它得另开一片，并接受观感变化。

### 8.10 2026-10-05：车辆模型重建的卡顿（`ShaderManager.reloadShaders()` 计数）

车辆侧的模型重建（换资源包、资源包创作工具构建、模型缓存重建）会在**渲染线程**上同步做完
"解析 OBJ + 建 VBO"，原来的实现还会顺手把着色器**重编译 3 个程序**，而且一次重建会做 **5 遍**。
实测后果：`[MMTR-LAG] 帧间隔 562ms（渲染线程被卡住：掉帧）`。

**读法**：`[MMTR-LIGHT] ShaderManager.reloadShaders()` 这行由 mixin 打出，**它就是那次重编译**。
按"同一毫秒/同一秒里的条数"分组看：

| 一次模型重建里的条数 | 含义 |
| --- | --- |
| **1** | 正常（notes/399 修好之后：着色器只在资源重载时编译一次） |
| **4–5** | **回归**：说明 `OptimizedRendererWrapper.beginReload()` 又走了"每次都真重载"那条路 —— 去查 `shadersDirty` 是不是被什么东西提前置成了 false |
| **0，但 `loading model` 有** | 更糟：着色器可能**从未编译**（`isReady()` 为假 ⇒ 优化渲染器整片不画）。去查 `shadersDirty` 的初值是不是被改成了 false |

**配套看**：`[MMTR-DBG] loading model …` 的条数 = 这一波加载了几个模型；
`[MMTR-LAG] 帧间隔 …ms（渲染线程被卡住）` = 这一波的代价。

**修好之后的残留**（2026-10-05 实测）：着色器只编译 1 次了，但一次重建仍有 **284–455 ms** ——
大头是**解析 4.5 MB 的 OBJ + 建 VBO**，仍然在渲染线程上。切分点很干净：
`OBJ 文本 → RawMesh` 是纯 CPU（可搬走），只有 `upload()` 必须在渲染线程。

> **2026-10-08 把它量了并修了 —— 见 §8.14 / §8.15。** 结论：解析占一次重建的 **87–93%**，
> 已经搬到后台线程（§8.14）；几何那一段里的"归一化 + 合桶"也搬走了（§8.15），
> 渲染线程只剩 `addTransformation`（在 `建 VBO` 那一段里）与 GL `upload()`。
> 三条更正：① 不要用 `MainRenderer.WORKER_THREAD` —— 那是**遮挡剔除**的 worker
> （它的任务都要 `OcclusionCullingInstance`，塞一个 150 ms 的解析进去会把逐帧剔除拖住）；
> ② 模型重建**不是"每会话一次"**，稳态里是**每 ~100 s 一波**（§8.14）；
> ③ "渲染线程每轮的代价"要**分段**读（`[MMTR-MODEL]` / `[MMTR-REBUILD]`），
> 一次重建横跨好几个 tick，"总共多久"没有意义。

⚠️ **别把它读成"每次几分钟就会卡一次"**：2026-10-05 那个会话里模型加载**只发生了一波**
（`reloadShaders` 全会话仅 1 次）。**但 2026-10-08 三次会话都出现了多波**（相隔 ~100 s）——
成因不是"资源重载被反复触发"，而是 `CachedResource` 的寿命：车离开视野超过
`MODEL_LIFESPAN`（60 s）后缓存被清，再进视野就整辆车从头重建。详见 §8.14。

**车辆 draw 数怎么读**：`[MMTR-LIGHT] optimizer` 的 `非钢轨 top4`。车辆是 `mtr:<车型>/<贴图>.png` 的形状。
**一个部件一次 draw**（批次只有材质数）是结构性的，不是剔除没做好：

```text
非钢轨 draws=196.0(7.00批)
  ｜ mtr:saf420car/saf420.png=84.0(2.00批) | mtr:saf420car/saf420_glass.png=78.0(1.00批)
     | mtr:saf420cab_a/saf420.png=21.0(3.00批) | mtr:saf420cab_a/saf420_glass.png=13.0(1.00批)
```

判据：**`draws ÷ 批`** 就是"平均一个材质批次里塞了多少个部件"。这个比值大（这里 196/7 ≈ 28）
说明缺的是**合并**，不是剔除 —— 和钢轨当初 `767 draw / 1 批` 是同一个病。
机制与设计见 notes/399 §4。

### 8.11 2026-10-05：车辆按材质合并（**默认开启**；`-Dmmtr.vehiclemerge=false` 可关）

车辆那边实现了"把同一 `PartCondition` 下一批部件的几何按材质合并、一个材质只 upload 一次"。
它**先以默认关闭上线**、经实机验证后于 2026-10-06 翻成**默认开启**：

| | 值 |
| --- | --- |
| 实测收益 | **非钢轨 draws 284 → 40（−86%）**、`submit` 2.72 → **0.85–1.04 ms/帧**、稳态 **57–66 FPS** |
| 风险面 | **车辆外观 / 车门 / 车灯 / 雨刷** —— 目标里写死不许变的四项 |
| 风险处置 | 先默认关（行为逐位相同）→ 实测 → 用户肉眼确认四项 → 才翻默认 |

```powershell
# 回到改动前（逐部件 upload，一个部件一次 draw）
-Dmmtr.vehiclemerge=false
```

**怎么看它生效了**：

```text
[MMTR-VEHMERGE] 合并 N 个部件 → M 个材质（= M 次 draw）     ← M 应在个位数
[MMTR-LIGHT] optimizer … ｜ 非钢轨 draws=…                  ← 应大幅下降
```

| 读到的 | 含义 |
| --- | --- |
| 没有 `[MMTR-VEHMERGE]` 行 | 开关没生效（`-D` 没传进去，或类没重新加载 —— **必须重启进程**） |
| `M` 很大（几十） | 材质没合桶成功 ⇒ 源 ObjModel 的 `MaterialProperties` 每份都不同，得回去查 `writeToOptimizedModels` 收到的 bundle |
| 有 `[MMTR-VEHMERGE] … 停用` WARN | 合并抛异常、已自动回退逐部件 upload（画面正常，只是没省下 draw） |

⚠️ **画面须核对**（比看 draw 数重要）：**车门开关、雨刷动作、车灯光色**。
`optimizedModelDoor`（门与雨刷那一份）当时**不在**合并范围内 —— **2026-10-08 已纳入，见 §8.12**。
**2026-10-06 用户已肉眼确认这四项"都对"**，据此才翻成默认开。

⚠️ **据实记一句**：我检查的那个会话里 **门那一路一次都没被跑到**（`非钢轨 draws` 93 个窗口
一直钉在 40.0、`[MMTR-WSHLD]` 全程 `mode=OFF`）—— 用户的确认是他们自己看到的，
我这边**没有**日志证据显示门开过。**2026-10-08 补上了**：门开过之后 draw 数**确实上升**
（40 → 283–320），而且上升与**服务端的 `OPEN_DOORS` / `CLOSE_DOORS` 子任务逐次对齐** —— 见 §8.12。

⚠️ **A/B 必须同机同事位**。notes/398 §3 有前车之鉴：钢轨那次"改前 60 FPS / 改后 41 FPS"
其实是因为两次会话相机差了 64 格、人站到了车旁边（`vehicles` 段从 0.04 涨到 3.63 ms/帧），
对比根本不成立。开/关这个开关各测一次时，**站位和朝向都要一样**。

#### 实测结果（2026-10-05 00:10，合并开）

**这次不用换站位也能对照**：改前那次的**批次结构与这次完全一样**
（11 批、同样的 `2.00/1.00/3.00/3.00` 批、同样那 6 张贴图）⇒ 是同一批车辆。

| | 改前（关） | 改后（开） | 变化 |
| --- | --- | --- | --- |
| 非钢轨 draws/pass | 284 | **40** | −86% |
| 总 draws/pass | 290 | **46** | −84% |
| `saf420car/saf420.png` | 112 | **16** | −86% |
| `saf420car/saf420_glass.png` | 104 | **8** | −92% |
| `submit`（两 pass） | 2.72 ms/帧 | **1.04 ms/帧** | −1.68 |
| 已量段合计 | 7.76 ms | **4.60–4.78 ms** | −2.3 |
| 稳态帧率 | 41 FPS（p50 24ms） | **63–66 FPS（p50 14–15ms）** | — |

⇒ **单价仍然是 ~2.9 µs/draw**（244 个 draw × 2.9 µs × 2 pass ≈ 1.4 ms，实测 1.68）。
**这条最值得记住**：−86% 的 draw 只值 1.68 ms ⇒ 改后 `非钢轨 40 + 钢轨 6 = 46`，
**draw 数已经不是主要矛盾**（同期 `vehicles` Java 侧仍有 3.2 ms、未量到的约 10 ms）。

而 draw 数与异常数**证明不了画面** —— 所以流程是：先默认关（行为逐位相同）→ 实测拿数
→ 用户肉眼确认那四项 → 才翻默认。**要回退只需 `-Dmmtr.vehiclemerge=false`。**

### 8.12 2026-10-08：开门态的 draw（`[MMTR-VDRAW]`）—— 40 与 320 的跳变是服务端开门

**触发**：同一个客户端里「非钢轨 draws」在 **40** 与 **283–320** 之间来回跳，而
`[MMTR-VEHMERGE]` 只在模型构建时出现过一次、此后一条都没有，也没有"停用"warn。
模型是 `CachedResource` 缓存的 —— **没有重建就不该变**，这是当时解不开的矛盾。

**怎么解的**：把**服务端**的日志叠到客户端的 draws 上。专用 dev 服务器在跑引擎作业，
里面有 `[MMTR-SUB] ▶ 基础操作开始：OPEN_DOORS / CLOSE_DOORS`。对齐结果四次全中：

| 客户端 `非钢轨 draws` | 服务端事件 |
| --- | --- |
| 17:36:03–13 → 29.1 / 39.4 / **40.0** | 门关 |
| 17:36:18–33 → 212.5 / 283.2 / 314.4 / **320.0** | 17:36:08 / :14 / :15 `OPEN_DOORS` |
| 17:37:08–23 → **40.0** / 35.9 / 29.0 / 28.3 | 17:36:28 / :34 / :35 `CLOSE_DOORS` |
| 17:38:18–33 → 243.0 → **320.0** | 17:38:14 / :16 `OPEN_DOORS` |
| 17:39:08 → **40.0** | 17:39:11 `CLOSE_DOORS` |

⇒ **不是合并失效，是开门态**。链路：服务端 `OPEN_DOORS` → `persistentVehicleData` 门值/可开判定
→ `RenderVehicles` 收 `openDoorways` → `noOpenDoorways = openDoorways.isEmpty()` →
① 走哪个 bundle ② `matchesCondition(DOORS_CLOSED/DOORS_OPENED)` ③ 门几何由 `optimizedModelDoor` 逐位置画。

**那批 112 / 104 为什么和 §8.11 的"改前"逐位相同**：因为就是同一批门部件 ——
关门时门在 `…DoorsClosed` 桶里（已合并），开门时同一批门走 `optimizedModelDoor`
（`ModelPropertiesPart.java:214`，**从来没合并过**）。`fromObjModels` 一个部件一个
`VertexArray`，而 `BatchManager.queue` 一个 `VertexArray` 一次 `glDrawElements`。

**当时试过的修法**（`ModelPropertiesPart.writeCache` 里把 `optimizedModelDoor` 也按材质合并）——
**实测零收益、已回退**：`fromObjModels` 本来就按材质分桶（`javap`：
`lambda$fromObjModels$2` = 逐 ObjModel `generateNormals(); distinct();` 再 `upload(DEFAULT_MAPPING)`，
`upload` 每个材质返回一个 `VertexArray`）。瓶颈不在"材质"，在"这份模型是**一个部件组**的，
而开门时是**逐部件组**排队"。

**`[MMTR-VDRAW]` 探针**（`render/MmtrVehicleDrawProbe`，`-Dmmtr.vdrawprobe=false` 可关）：
按「门开/关 + 编组节数 + 匹配到的 `PartCondition` 集合」分桶，每 5 秒一行，
报**每次排队 draw 数**（各 `OptimizedModelWrapper.partCount()` 之和；该方法是反射
`OptimizedModel.uploadedParts`，已用 `javap` 核对是 `final List<VertexArray>`），
外加门/雨刷那条路的排队次数（`onDoorQueued`，挂在 `ModelPropertiesPart.renderNormal` 的两处
`OPTIMIZED_RENDERER_WRAPPER.queue` 上）。

```text
[MMTR-VDRAW] 5.0s 窗口：车·帧=1240（门关=1200 门开=40）｜ 每次排队 draw 数 avg=3.4 max=18
  ｜ 条件匹配数 avg=3.00 max=3 ｜ 门/雨刷逐位置排队=151776 次 draw avg=1.0 max=1 ｜ 签名：…
```

| 读到的 | 含义 |
| --- | --- |
| 两个桶**签名相同**、`draw avg` 不同 | 几何被换了（合并回退）⇒ 查 `[MMTR-VEHMERGE]` 的 warn |
| 两个桶**签名不同** | 状态驱动的正常差异（门开/关、在途/回库）⇒ 波动**不是 bug**，要做的是让那部分也能合并 |
| `partCount()` 报 `-1` | 反射没拿到 `uploadedParts`（映射库变了）⇒ 埋点退化，先修反射 |
| `门/雨刷逐位置排队` 的 `draw avg=1.0 max=1` | 门那一路"一次排队一次 draw、且恰好 1" ⇒ 想降 draw 只能**减少排队次数**，合并材质没用 |
| 签名里冒出一堆只差一位的桶 | `CHRISTMAS_LIGHT_*` 的相位每 500 ms 变一次，当噪声读 |

**怎么把这类问题更快定位**（本篇最值得记的一条）：draw 数跳变时，**先把服务端事件叠上去**。
车辆渲染的开关（门、在途、编组节数）全部是服务端镜像过来的，客户端单看日志只会看到
"模型没重建但几何变了"这种自相矛盾的现象。

### 8.13 2026-10-08：开门态门 draw 数 —— 按**动画类**合并（`[MMTR-DOORBATCH]`，**默认开**）

**为什么不是"再合并一次材质"**：`[MMTR-VDRAW]` 量出来开门态 ≈ **172 次排队/帧**、每次
`draw avg=1.0 max=1`；临时埋点 `[MMTR-DOORSHAPE]` 又量出**每个门部件组的位置数 = 1**
⇒ 43 次/节来自"43 个部件组"，只能**跨部件组**合并。判定实验
`-Dmmtr.doortranslate=false`（把门那次 draw 的 `translate` 摘掉）得到"**门位置照旧、只是不再滑动**"
⇒ 几何已经按位置烘好，draw 的 `translate` **纯粹是动画位移** ⇒ 同一个动画类的门可以共用一次 draw。

**做法**（`resource/MmtrDoorBatch.java`）：`ModelPropertiesPart` 在 `writeCache`（OBJ 路）
登记自己那组门的几何；第一次渲染这辆车时按
`doorXMultiplier|doorZMultiplier|DoorAnimationType|flipped|PartCondition|侧别` 分组，
把同一类里所有组的几何用 `MmtrVehicleMeshMerger` 合并成一份；每帧在
`DynamicVehicleModel.render` 的**逐部件渲染之前**对每个类**试算**一次位移，
全类一致就排一次队，并让 `renderNormal` 对这几组跳过门那次 draw。

**两个实机逼出来的坑**（第一版、第二版都是"一次都没合上"，判定日志一次抓出来的）：

| 坑 | 现象 | 判据 |
| --- | --- | --- |
| 类型键少了**侧别** | 资源包里 `door_r_1` 与 `door_l_1` 的 `doorZMultiplier` **完全相同**（都是 −14，左右门同一套动画）⇒ 左右门进了同一个类，而 `canOpen` 是逐 doorway 判的，一站台只在一侧就永远不一致 | 类里必须含"这一组门映射到的 doorway 的中线 x 符号"（也就是 `canOpen` 的判据来源）。再细到 doorway 就退化成一组门一个类，反而更贵 |
| 位移要求**逐位相等** | 同一扇门的门板与玻璃差 `0.028`：`getInterpolatedDoorValue` 是按 `System.currentTimeMillis()` 插值的，同帧内两次调用落在不同毫秒 | `x`/`y` 逐位相等；`z` 容差 `0.05`（1/16 格，≈3 mm）。真正要挡的状态差异是 `O(1)`–`O(20)` |

**安全阀**（这是"画面不变"的来源）：类里只要有一组位移不同、或者有一组这一帧
`shouldRender=false` / 条件不成立，**整类都不合**、一组都不画，退回改动前的逐组路径。
不成立的合并 = 改动前，不会出现"半个类被合并、位置对不上"。

**怎么开 / 怎么读**：

| | |
| --- | --- |
| 默认 | **开启**（2026-10-08 起，与 `mmtr.vehiclemerge` 同样的上线方式：先默认关、实机确认画面后翻默认） |

| 合并失败的类 | `[MMTR-DOORBATCH] 类 …（N 组门）这一帧不合并：…`（每个类最多一条、总数 8 条）—— **"什么都没变"时先看这一行**，它区分"开关没开/没门/只有一组"和"合并不成立" |

### 8.14 2026-10-08：模型重建的分段（`[MMTR-MODEL]`）与解析搬离渲染线程（默认开）

**为什么现在才动**：§8.10 那条"一次重建仍有 284–455 ms、大头是解析 4.5 MB 的 OBJ"当年只是推断。
本节先把它**量出来**，再按量出来的切分点修。

#### 1 三段读数（`VehicleModel.createModel`）

三段都是**直接量的**（不靠相减反推），只在**这一轮重建 ≥ 50 ms** 时打一条，总数封顶 60 条：

```text
[MMTR-MODEL] mtr:saf420cab_a/saf420cab.obj 这一轮重建 362 ms ｜ 读 - ｜ 解析 336 ms（本线程） ｜ 建 VBO 26 ms
[MMTR-MODEL] mtr:saf420car/saf420car.obj   这一轮重建 146 ms ｜ 读 - ｜ 解析 135 ms（本线程） ｜ 建 VBO 11 ms
[MMTR-MODEL] mtr:saf420cab_b/saf420cab.obj 这一轮重建 149 ms ｜ 读 - ｜ 解析 136 ms（本线程） ｜ 建 VBO 13 ms
```

| 字段 | 含义 |
| --- | --- |
| `读` | `ModelResourceLoader.createSource`：取 OBJ/MTL 文本 + 扫一遍找 `mtllib`。**留在渲染线程**（`CustomResourceLoader.RESOURCE_CACHE` 没有同步），实测 3–31 ms |
| `解析` | `ModelResourceLoader.parseSource`：OBJ 文本 → RawMesh。**可以搬**，实机 98–553 ms（JIT 冷的第一轮最贵） |
| `建 VBO` | `new DynamicVehicleModel(...)`。**只有** `writeCache` / `addTransformation`（把位置烘进几何）——`generateNormals` / `distinct` / 合桶 / `upload()` 都**不在**这一轮里，它们在下一层 `CachedResource`（`VehicleResource.writeToOptimizedModels`，晚一两个 tick，读数见 §8.15） |
| `这一轮重建` | 从进入 `createModel` 起的总时间 |

**改前判据**：解析占 **87–93%**，建 VBO 只占 7–9%。

#### 2 重建是**周期性**的（这一条以前记错了）

§8.10 写"每模型每会话一次"。2026-10-08 三份日志里都出现了**多波**（例：19:20:50–56 与 19:22:32–37，
相隔 102 s），成因在代码里：

* `VehicleModel.MODEL_LIFESPAN = 60000`；
* `CachedResource.getData` 只在**被调用**时才把 `expiry` 往后推，而它只由 `RenderVehicles` 对
  **视野内**的车节调用 ⇒ 车离开视野超过 60 s，`tick()` 就把 `data` 清掉，再进视野时整辆车从头重建。

⇒ 十节编组在世界里跑，**稳态里约每 100 秒一波、每波 2–3 个模型**的渲染线程停顿。
这才是这一项值得做的原因（不是"偶尔一次"）。

#### 3 修法与实测（`-Dmmtr.modelparseasync`，**默认开**）

读留在渲染线程，解析交给一个专用单线程 `MMTR-ModelParse`（daemon）：

```text
[MMTR-ModelParse] [MMTR-MODELASYNC] 后台解析 mtr:saf420cab_a/saf420cab.obj: 519 ms（线程 MMTR-ModelParse）
[Render thread]   [MMTR-MODEL] … 这一轮重建 166 ms ｜ 读 31 ms ｜ 解析 已在后台完成 ｜ 建 VBO 104 ms
```

| | 同步（改前） | 后台（改后） |
| --- | --- | --- |
| cab_a（最冷的一个） | 362 ms | **166 ms** → **−54%** |
| cab_b | 149 ms | **83 ms** → **−44%** |
| car | 146 ms | **< 50 ms**（没到打印阈值） → **≥ −66%** |
| 失败/兜底 | — | **0 条** |

⚠️ **别把"建 VBO"读成"变大了"**：改前 26/11/13 ms、改后 104/83 ms 是**同一段代码**在两种条件下的读数 ——
改后它和后台解析**同时在跑**，两者都吃内存带宽（4.5 MB 文本解析 + 约 1 MB 顶点拷贝）并一起触发 GC，
所以各自都慢一截（后台解析也出现过 519/553 ms）。诚实的结论是**渲染线程每轮 146–362 → 50–166 ms**。

`[MMTR-MODELASYNC]` 是无条件打的（每次解析一条，一个会话个位数量级），带**线程名**——
这就是"解析真的不在渲染线程上了"的证据。

#### 4 读法 / 开关 / 安全网

| | |
| --- | --- |
| 打开 | 默认开；`-Dmmtr.modelparseasync=false` 回到同步（便利脚本 `-I sandbox/dev-run/modelparse-sync.gradle`） |
| 后台解析失败 | `[MMTR-MODELASYNC] 后台解析 … 失败` + 一条 `[MMTR-MODEL]` 结尾注明"这一轮是后台失败后的同步兜底" |
| 解析还没好 | `createModel` 返回 `null`，车厢**晚一两个 tick** 出现（`CachedResource` 那条链本来就用 `null` 表示未就绪） |
| 离线复算 | `sandbox/railbake-verify/ObjParseBench`（真实解析器、跳过 `upload()`；见 notes/400 §7.1） |

#### 5 为什么不搬"读"、为什么解析要加锁、还剩下什么

* **读不搬**：`ResourceProvider` 背后是 `CustomResourceLoader.RESOURCE_CACHE`（**没有同步**的
  `Object2ObjectAVLTreeMap`）；从别的线程读会与渲染线程并发改同一个结构。读只要 3–31 ms，留着划算。
* **解析整段加锁**：`OptimizedModel$ObjModel.loadModel` 会动一个**静态**的
  `OptimizedModel.ATLAS_MANAGER`（字节码确认：`ATLAS_MANAGER.load(identifier)` +
  交给 `ObjModelLoader.loadModel` 去 `applyToMesh`），而它的两个容器是**普通 HashMap/HashSet**
  ⇒ 两个解析同时跑会把它写坏，而它是长生命周期静态对象。所以 `parseSource` 整段
  `synchronized`（后台解析与同步兜底共用这把锁）。
* **几何那一段**（`generateNormals` / `distinct` / 合桶）**本节之后也搬走了** —— 见 §8.15。
  留在渲染线程的是 `addTransformation`（`writeCache` 的一部分）与 `upload()`。
* **不覆盖**：MQO/MQOZ（要先转换）与 `.bbmodel`（小文件）都走原来的整条同步路。

### 8.15 2026-10-08：几何归一化 + 合桶搬到工作线程（`[MMTR-REBUILD]` + `[MMTR-MESH]`，**默认开**）

### 8.16 2026-10-08：钢轨烘焙的"走曲线 + 合桶"搬到 `MMTR-RailBake` 线程（默认开）

### 8.19 2026-10-09：驾驶输入本地闭环（`驾驶回路` 行，**默认开**；`-Dmmtr.localdrive=false` 可关）

notes/407。**这一条量的不是帧时间，是控制回路的死时间** —— 用户口径"接管后上传列车位置、
下载旁路到对账纠正路径"，目的是"防止客户端延迟导致列车操作、动画因网络原因卡顿"。

病因已确证（不是推测）：客户端跑的是同一套物理（`Vehicle.simulateMoving` 的镜像分支），
但它的输入严格只来自镜像（`createMirrorControlStateFromSync()`），而 `MmtrDriveInput.send(...)`
**只发包、不写本地** ⇒ 按键到车有反应要等
`C2S + 引擎下一 tick(≤50 ms) + ① 的下一帧(≤100 ms，边沿型) + 半个 RTT` ≈ **RTT + 150 ms**。

#### 1 新读数

```text
[MMTR-LOCAL] 驾驶回路：本地写=3 手柄变化=3 时延均值=0ms 最大=31ms 样本=3 开关=开
```

```text
[MMTR-MOTION] 运动流：… 本地闭环=41帧 跳回声=12 领先max=1.85m 对账=0
```

| 读数 | 读法 |
| --- | --- |
| **时延均值 / 最大** | **"我改了手柄" → "本地镜像的手柄值等于我这一份"** 的毫秒数。这就是死时间：本地物理的输入就是镜像。开关开应 ≤ 1 个客户端 tick（0–50 ms）；关掉就是 RTT+150 ms。**开/关用同一个读数，可直接 A/B** |
| `本地闭环=N 帧` | 有 N 个渲染帧处在"我在本地开车"状态（0 = 本地闭环根本没生效：`-Dmmtr.localdrive=false`、没坐在司机位上、或镜像里的 crew uuid 是别人的） |
| `跳回声=M` | 本地闭环期间丢掉了多少条 ① 的 `CONTROL`（那是同一批字段的稍旧值）。**长期为 0 而本地闭环 >0 帧 = 回声本来就没来** |
| `领先max=X m` | 我（本地）跑在服务端前面多少米。正常值 ≈ `speed × RTT`，是**设计内**的；持续 >> 这个量级 ⇒ 对账阈值该调 |
| `对账=K` | 本地闭环期间误差超过阈值、被硬对齐了几次。**持续增长 = 本地与服务端真的在分叉** |

#### 2 开关

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| `-Dmmtr.localdrive` | `true` | `false` = **逐位回退**到"手柄只在回声里到本地" |
| `-Dmmtr.localdrive.hold` | `600` | 本地写进镜像后不接受回声的窗口（ms）。只在"真的改了手柄"时刷新；窗口一到回声重成权威 ⇒ 引擎钳位/拒绝/换端/钥匙被抢最多错这么多 |
| `-Dmmtr.localdrive.correctm` | `8` | 本地闭环期间的对账阈值基数（m）；0 = 完全不纠正。阈值 = 基数 + `0.5 s × 速度`（半秒那一项盖住网络来回的正常领先） |

**副本 jar** ⇒ 必须先 `mmtr/scripts/deploy-engine.ps1 -Build`（**先停 dev 服务端**，见该脚本顶部的事故记录）。
在同步之前 `check-java-compile.ps1` 会报 `找不到符号: mmtrApplyLocalDriveControl` ——

| 读数 | 读法 |
| --- | --- |
| `长 tick N ms：区块载入=a ｜ 包 b 次 X ms（…）其余≈Y ms` | **三块归因**。`其余`包含 vanilla 的区块解析/光照/建模、实体生成、GC、别的线程 —— 那些我们插不进计时点，所以只能从"减掉已知的两块"里看出来 |
| `包 …（… 解析 Z, 字节）` | 每个包类名一行：**解析**（`parseJson`）与**落地**（`runClientInbound`）分开。字节大 + 次数少 ⇒ 突发（该切片）；次数多而每次小 ⇒ 稳态成本（该减频次） |
| `区块载入=… （最长一 tick n 个）` | n ≥ 4 就说明区块是**一串一串**进来的；与 `[MMTR-LAG]` 的节拍对照即可确认它是不是引信 |
| `前视拉取=n 次（半径 …, 平均前视 …m）` | 管线在干活：请求圆心在车前方多少米（`平均前视` 应当 ≈ `-Dmmtr.dynload.lead`）。0 次 = 没在动（速度 <1 m/s）或管线被关 |

#### 3 开关

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| `-Dmmtr.load` | `1` | `0` = 探针全关（每次调用只剩一次 boolean 读） |
| `-Dmmtr.dynload` | `1` | `0` = **整条前视管线关**，回到"只在区块加载后拉一次"的老路（老路一条都没删） |
| `-Dmmtr.dynload.lead` | `192` | 前视距离（米）：请求中心在相机运动方向上的提前量 |
| `-Dmmtr.dynload.radius` | `128` | 单次请求半径（米）＝切片大小 |
| `-Dmmtr.dynload.step` | `32` | 前视点每走这么多米才发下一次 |
| `-Dmmtr.dynload.period` | `250` | 两次请求的最小间隔（毫秒） |
