# 性能探针运行手册

> 设计（有哪些探针、判据是什么）看 [`01-设计/性能探针与侦测项-设计.md`](../01-设计/性能探针与侦测项-设计.md)。
> 这篇只讲**怎么跑、怎么读、读完怎么动手**。
>
> 一句话：服务端"卡"的时候，先 `probe on` 看 30 秒的 `[MMTR-PROBE]` 行，**别急着改代码**。

---

## 1. 三十秒上手

### 1.1 已经跑着的服务端（推荐：不动进程）

网页指令栏（`mmtr-studio` / 引擎网页的指令输入）或游戏内控制台敲：

```text
probe on          ← 开（每 100 tick = 5 s 一行汇总）
probe dump        ← 立刻读一次（不打断统计）
probe off         ← 关
probe reset       ← 清零，做前后对照时先来这一下
```

读数的落点：服务端日志里搜 `[MMTR-PROBE]`（和 `[MMTR-HLTH]` 健康行同拍，两张表说的是同一个 5 s 窗口）。

### 1.2 从启动就开（要抓开机头几分钟 / 不想记得敲）

```bat
:: 服务端启动参数里加（game/fabric 的 run 配置或 dev-server 脚本）
-Dmmtr.probe=true
-Dmmtr.probe.interval=100        :: 每多少 tick 一行（抓尖峰调小，例如 20）
-Dmmtr.probe.warnMs=40           :: 单帧超过多少毫秒就进最坏帧榜（默认 40 ≈ 两个 tick）
-Dmmtr.probe.file=…              :: 明细追加到文件（默认只进 stdout）
```

引擎侧默认把明细写到 `<引擎数据根>/mmtr-perf-probe.txt`（启动那行 `[MMTR-PROBE] 探针已开…` 会打出全路径）。
**注意**：`game/fabric/run/` 下是存档与运行产物，不属于仓库；要留档请把 `-Dmmtr.probe.file=` 指到 `logs/<yyyy-MM>/`。

### 1.3 离线量（不开游戏，可重复，适合做前后对照）

```bat
cd mmtr\engine
set JAVA_HOME=..\..\env\jdk-21
gradlew.bat test --tests "org.mtr.core.mmtr.probe.MmtrTickBudgetTests" --offline
gradlew.bat test --tests "org.mtr.core.mmtr.probe.MmtrProjectionKillCurveTests" --offline
```

它把**运行中的存档整份复制**到 `engine/build/mmtr-tick-budget/`，在副本上跑（线上一个字节不动）。

## 2. 一行读数怎么读

```text
[MMTR-PROBE] minecraft/overworld frame=sim n=100 wall=100104ms busy=37ms avg=0.37ms p50=0ms p95=1ms p99=4ms max=6ms over40ms=0
[MMTR-PROBE] 分段（累计毫秒/次数，按累计耗时排序）—— rails.tick1=13ms/400 | projection.solve=41ms/865 max=3ms | projection.hit=0ms/0 ev=28224 | sections.rebuild=31ms/3 |
[MMTR-PROBE] 最坏帧（tick#=耗时）—— #18422=40685ms(world.fill×1108) #19011=2100ms(save)
```

| 字段 | 意思 |
| --- | --- |
| `frame=sim` / `frame=server` | 引擎模拟 tick / MC 服务端 tick。**两个时钟，别混着比** |
| `n` | 这一窗口跑了多少帧 |
| `wall` | 窗口首帧到末帧的墙钟跨度（`n=100` 而 `wall≈5000ms` = 正常 20 TPS；`wall=100000ms` = 落后了 95 s） |
| `busy` | 这些帧**忙的总时长**（`busy ÷ wall` = 占用率） |
| `avg / p50 / p95 / p99 / max` | 单帧耗时分布。p50≈0 而 max 很大 ⇒ **尖峰**；整条分布都抬起来 ⇒ **稳态慢** |
| `over40ms` | 超过 `warnMs` 的帧数（桶边界跟 `warnMs` 一起动，名字就是门槛） |
| `名字=累计ms/次数 max=单次最坏ms ev=事件数(Σ和) peak=峰值` | 分段。**次数比毫秒更早暴露放大**（每 tick 上万次 = 每 tick 全量重算） |
| 最坏帧榜 | `tick#=耗时(标签)`。标签是外面塞进来的活（施工/存档），用来分开"引擎的锅"与"外面的锅" |

## 3. 症状 → 先看哪几个读数

| 你会看到 | 先读 | 大概是什么 |
| --- | --- | --- |
| 日志里周期性 `Can't keep up! Running 40685ms / 813 ticks behind` | `server.tickSpan p99/max` + 最坏帧榜 | 尖峰。有 `world.fill` 标签 = 施工期；没有标签而 `mmtrHooks` 大 = 每-tick 钩子 |
| 一直卡、不是一阵一阵 | `frame=server avg` 与各段 | 稳态慢：`server.mmtrHooks` / `server.vanillaAndEngine` 谁大 |
| `vehicles=0` 却卡（现场就是这条） | `server.mirror.*` 各段 + `projection.*` | 每 tick 全量重算（notes/335 §4） |
| 加了一座站就明显更卡一档 | `projection.evict` + `projection.entries peak` + `projection.solve` 次数 | 缓存撑爆后整体 `clear()` |
| 网页打开就卡 | `web.runs` / `web.shed` / `web.skipSlowTick` / `webSlow`（健康行） | 网页重活落回 tick（notes/172 的预算闸在起作用吗） |
| 车一动就卡 | `vehicles.simulate` / `signal.aspectView` / `points.*` | 车辆走行或信号视图重建 |
| 一保存就顿一下 | `save.auto` 的单次毫秒 | 落盘吃掉整帧 |
| 客户端一多就卡 | `clients.sendUpdates` | ∝ 人数 × 脏对象；**无头环境量不到，只能在实机读** |

## 4. 冷启动 vs 稳态：先看这张表再解释任何数字

离线量到的真实读数（2026-09-27，`rails=294 lamps=250 sections=250 turnouts=28 vehicles=0`）：

| 量的是什么 | 第 1 次（冷） | 其后（热） | 说明 |
| --- | --- | --- | --- |
| 引擎 400 步（每步 50 ms 仿真） | — | **0.13 ms/步**（p50=0、max=7 ms） | 一次模拟 tick 只占 20 TPS 预算的 **0.3%** |
| `rails.tick1` | — | 13 ms / 400 次 | 引擎里最大的一段 |
| 游戏端每-tick 链（`lampAspectNames` + `lampBindings`） | **37 ms** | **13 ms** | 一个服务端 tick 走一次 = 26% 的 tick 预算 |
| 单次弧投影 | **0.045 ms** | **0.0017 ms** | 冷热差 **≈ 27×** |

两条结论直接可用：

1. **40 s 的落后不在模拟里**。引擎 tick 是 0.13 ms 级；而游戏端那条每-tick 链是 13–37 ms 级，
   813 个 tick 上就是几十秒 —— 与现场读数同量级。
2. **冷启动与稳态差一个数量级**。所以任何"前后对照"都要先预热（离线用 `-Dmmtr.budget.steps`，
   实机等 `probe on` 之后至少一个窗口），否则量到的是 JIT 与缓存冷启动。

## 5. 读到问题之后：动结构之前的三条纪律

1. **逐位相同**（notes/328 §R）。允许的加速只有"同一份输入上的重复劳动不要重复做"（记忆化、脏标记、按轨索引候选灯）；
   **不允许**改采样步长、换近似算法、跳过计算、改节拍。做完要用 golden trace 对拍。
2. **先做"能不能省"的实验，再改代码**。`server.mirror.unchanged ÷ 总 tick 数` 就是那个实验：
   如果 ≈1，说明绝大部分 tick 的结果与上一 tick 逐字相同 —— 脏标记/节流能省掉的正是这部分。
   这个比值要在**现场**读（离线量不到镜像链的 changed/unchanged，因为离线没有客户端与真实 tick 顺序）。
3. **改完必须能回到同一张表**。所以探针的段名是稳定的接口：改结构之后 `probe dump` 的那几行应当还在，
   数值应当按预期变化。**读数消失 = 埋点被重构掉了**，用例 `MmtrTickBudgetTests` 会在 CI 里红。

## 6. 想加新探针时

```java
final long probeT = org.mtr.core.mmtr.probe.MmtrProbe.begin();
try {
    doTheWork();                       // 一行都不许因为探针而改变
} finally {
    org.mtr.core.mmtr.probe.MmtrProbe.end("名字.子名字", probeT);
}
```

- **段名口径**：`子系统.动作`（`rails.tick2`、`server.mirror.lampAspects`）。游戏端加 `server.` 前缀。
- **不耗时的事件用 `hit()`**（命中、重建次数、跳过次数），带数值用 `event(名字, 值)`，峰值用 `peak()`。
- **别埋在循环体里**：埋在"一段工作的边界"。一次调用的纳秒级 `nanoTime()` 在 250 灯 × 294 轨的循环里就是灾难。
- **别加会淹没日志的输出**：要加就加段名（汇总行有界，最多列 24 段）。
- 加完顺手在 `MmtrTickBudgetTests` 的阶段断言里点名，防止它被静默重构掉。

## 7. 工具与环境备忘

| 事项 | 说明 |
| --- | --- |
| `JAVA_HOME` | 引擎/游戏编译都要 JDK 21（`env\jdk-21`）；系统默认若是 JDK 8 会直接 `JAVA_HOME is set to an invalid directory` |
| Gradle | 两个工程各自 `gradlew.bat`，离线加 `--offline`；引擎侧 `compileJava` 依赖 `generateVersion`/`generateSchemaClasses`/`setupWebserver` 三个生成任务 |
| 引擎 jar 同步 | 改了引擎要同步进 `game/libs`：`mmtr\scripts\sync-engine.bat`（或 `deploy-engine.ps1 -Build`，后者带停机检查） |
| 存档 | 离线用例只读副本；实机 `probe` 不改任何游戏数据（探针不写存档） |
| 崩溃取证 | 看门狗杀掉时先看 `crash-…-server.txt` 的栈顶，再用 `probe dump` 看同期的段读数（栈给出**位置**，探针给出**代价**） |
