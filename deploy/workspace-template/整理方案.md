## 0. 一句话结论

现在的 `MC\` 把四类完全不同的东西平铺在同一层：

| 类别 | 例子 | 生命周期 |
|---|---|---|
| 可重装的工具链 | `tools/jdk-*`、`tools/idea`、`tools/ai3d` | 坏了重下 |
| 第三方只读输入 | `mods/`、`sources/`、`downloads/` | 按需重取 |
| 自有代码 | `mmtr/`（唯一 git 仓库）、`tools/obj-mtr-packager`、`creator-studio` | 必须版本控制 |
| 可再生的产物/日志/探针 | `build/`、`*.log`、`.launch-tmp`、`Create…导出版` | 随时可删 |

**整理动作 = 把四类拆成四层目录，并让 `mmtr` 重新成为唯一的源码真相。** 真正的自有源码不到 20 MB，却和 29.8 GB 的工具/副本/产物混在一起。

### 为什么这样分

- `env/` 与 `vendor/` 用同一条判断：**能不能用一行命令重新获得？** 能 → 不版本控制，不进备份。
- `assets/` 单独一层：`.blend` / `.glb` / 3D 扫描无法再生，必须备份，但不适合直接进 git（单文件 15 MB 级）。
- `mmtr/tools/obj-mtr-packager` 与 `mmtr/apps/creator-studio` 进仓库：它们各只有几十 KB 源码，却是流程的关键环节；进仓库后 `pack-vehicle.ps1` 不再需要"仓库的父目录"这种脆弱假设。
- `mmtr/.gitignore` 已有 `build/`、`.gradle/`、`run/`、`node_modules/` 等规则，`apps/creator-studio` 的产物会被自动忽略，无需额外配置。
