## 1. 入口

```
POST mmtr-plan-assign { fromConsistId, fromTripId（空 = 该车全部未跑趟次）, toConsistId }
```

- 指派**进输入签名**（与事件、输入同级）—— 否则"指派被接受了、却没生效"，与事件踩过的是同一个坑；
- 应用顺序：**输入 → 事件重算 → 手工指派** —— 人说了算排在最后一层（§3 的第三条性质）；
- 只登记一条（同 `from` + `fromTrip` 覆盖），`mmtr-plan-assign` 立即触发重算。

## 2. 现场读数（两次场景）

**场景 A（间隔 20 min → N=1）**：只有 `C1` 有班（`steps=434`），`C2` 是"配多了的闲置车底"（P3 的设计）。
指派 `C2 → C1` 如实回报 **0 条**：`事件改计划：人工指派：C2 全部 起的 0 条交给 C1（手工覆盖自动排班）`。

**场景 B（间隔压到 5 min → N=2）**：两个编组都上场，`C2` 有 289 条待跑；指派 `C2 → C1`：
```
事件改计划：人工指派：C2 全部 起的 289 条交给 C1（手工覆盖自动排班）
```
——**真的搬了 289 条**（不是 0），并且这条说明**进了服务端日志**。

## 3. 顺带解决的一件旧事 + 一件新发现

- ✅ **"事件改计划的说明没进日志"（notes/141 §5 的待查项）**：本轮同一条打印路径**打出来了** ——
  说明那段管道是通的，141 那次没出来是**那一次 `notes` 为空**（高峰那次为什么为空还要单独看，
  但已不是"日志出口坏了"）。**结论：待查项收窄到 PeakSurge 那一条路径。**
- ⚠️ **新发现（留给下一轮）**：指派之后 `GET mmtr-plan-diagrams` 的 `workings` 只剩 `C1`，
  且 `C1.steps` 没看到长（仍是 1731）。两个疑点：
  1. 来源车的 `DEPART_YARD` 也被搬走了 ⇒ 它不再"上场"（`scheduledWorkings()` 按"有出库那条"筛）——
     从"谁在跑"的角度这**也许是对的**（它今天确实没班了），但运营台会以为"这辆车消失了"；
  2. `C1.steps` 没长，与日志里"搬了 289 条"**对不上** —— 大概率是接口在**重算前后**取到了不同的那份
     `dispatcher`（`mmtr-plan-diagrams` 里 `mmtrRefreshPlanDispatchers()` 与读 `snapshot()` 的次序），
     属于**显示层口径问题**，不是搬没搬的问题（日志与 289 这个数是搬了的证据）。
  → 下一轮先把这两条查清（先看接口取的是哪一份，再决定"来源车要不要保留出库条目"）。
