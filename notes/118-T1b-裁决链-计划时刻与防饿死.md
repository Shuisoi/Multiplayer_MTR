# 118 - T1b（二）：裁决链 —— 计划时刻优先 / 到达序 / 防饿死

> 对应设计：`docs/01-设计/行车控制-任务联锁与行车许可-设计.md` §5.1（裁决链定稿）/ §6（T1b 第二半）。
> 前置：notes/117（T1b 一：咽喉原子获取）。触发：用户 2026-09-14「一路把T做完吧」。

## 1. 定稿的裁决链

```
人工锁（运维/排障通道，默认不存在）
  > 计划时刻（任务固定 ⇒ 主裁决）
  > 到达序（FIFO 兜底）
  > 防饿死（等待超时提升优先级）
```

**链上不允许存在"等人工"的环节** —— 用户 2026-09-13 裁定"玩家只有司机一个角色、没有调度员"，
所以任何"需要人来解锁才能继续"的状态都是永久停摆。

## 2. 交付

| 件 | 内容 |
| --- | --- |
| `Req.priorityMillis` | 计划时刻优先（越小越优先）。{@link Long#MAX_VALUE} = 没有计划 |
| `Req.enqueuedAtMillis` | 入队时刻，算等待时长用。**重复申请不刷新它**（否则每 tick 的重申请会让防饿死永不触发） |
| `MMTR_STARVATION_MILLIS` | 防饿死阈值（5 分钟） |
| `pickNext(q, now)` | 队列递补从"**取队首**"改成"**选最优**"：超时等待者先提一档，同档内按（计划时刻，到达序） |
| `requestAtomically(..., priorityMillis)` | 计划时刻的入口（3 参版委托，默认无计划） |

### 为什么这一改**没有**动到基线

排序机制从"取队首"变成了"选最优"，但**只要没人有计划时刻、也没人等超时**，比较键就退化成
入队时刻 —— 与修前逐位一致。这一条不是推理，是用例钉住的：
`withoutAPlanTheQueueStaysPureFifo`（三列车无计划排队 → 严格按到达序依次被服务）。

### 防饿死这一档的细节

- 超时的等待者**不再排在任何新来者后面**（哪怕新来者计划更早）；
- 同档内**只按等待时长**排序，计划时刻在这一档不再参与 —— 否则一个计划极早的老等者会把它后面的
  饿者一直压住，"防饿死"就只救了排在最前面的那一个。

## 4. 未结

1. **`priorityMillis` 目前没有任何调用方填** —— 计划时刻的输入源是 T5（时刻表预排）。
   本片把机制与时序做出来并测通，T5 只负责把值填进去（`requestAtomically` 的第 4 参）。
2. **物理道岔队列仍是纯 FIFO**：`physicalQueued` 没有接优先级/防饿死。
   物理队列只在"同岔互斥"时用，且互斥的赢家由逐进向层决定，所以暂按 FIFO 处理；
   若日后实测发现物理层有饿死，照 `pickNext` 的写法补一份即可。
3. **人工锁 TTL** 仍未做（设计 §5.2 建议项）—— 无调度员的世界里一次遗留的锁就是永久停摆，
   需要"可一键全清 + 状态可见"，建议随 T4 的准入闸门一起处理。
