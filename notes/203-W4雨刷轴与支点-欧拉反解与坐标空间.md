# 203 · W4 实体雨刷"动得不对"：两根轴都错了（欧拉反解 + 支点坐标空间）

> 承接 notes/202（"雨刷不转"的四个渲染环节修复）。202 之后雨刷**会动**了，但用户实测：
> **"动的不对"** —— 刀片向下弯、两根杆子飞到天上。202 附录里"旋转数学一行未改"的判断到此被推翻：
> 数学表达式没动，但它读到的**输入**是错的，而且错在两个互相独立的地方。两处都已修，并补了一条
> 能挡住回退的离线判据。

---

## 1. 症状 → 两根轴

| 症状 | 成因 | 量级（BR101 实测） |
| --- | --- | --- |
| 刀片不是"在玻璃面上扇形摆"，而是**向下弯** | 欧拉反解读错矩阵元，旋转轴不是玻璃法线 | 轴偏 **13.81°**（pitch 51.90° vs 正确 38.10°） |
| 两根杆子**飞上天** | `applyRotation` 把平面坐标 `(u,v,0)` 当模型坐标平移，旋转轴穿过**模型原点** | 支点离玻璃中心 ~1.2 m，即整块玻璃之外 |
| （同源第三处）刀片/杆子整体偏移约半屏 | 配置里的 `pivotU/pinAU` 是 **0..1 比例**，`pointAt()` 要的是**相对玻璃中心的米**，漏了 `−0.5` | 右向 0.6475 m、上向 0.2782 m |

用户看到的两个症状分别对应前两处；第三处是同一段代码里的同类错误，一起修掉了。

## 2. 根因一：欧拉反解（`MmtrWindshield.Plane` 构造函数）

`applyPlaneRotation` 做的是共轭 `M · Rz(θ) · M⁻¹`，其中 `M = Ry(yaw)·Rx(pitch)·Rz(roll)`，并且
**要求 `M` 的三列恰为 `(right, up, normal)`**。旧代码用"看向量猜角度"的方式取角：

```java
this.pitch = asin(clamp(-up.y()));          // ✗
this.roll  = atan2(up.x(), up.y());         // ✗
```

这不成立：`M` 的行是

```
row1 = [cp*sr, cp*cr, -sp]          col2 = (sy*cp, -sp, cy*cp)
```

所以正确取值只能来自矩阵元：

```java
this.pitch = asin(clamp(-normal.y()));      // 不是 up.y()
this.yaw   = atan2(normal.x(), normal.z()); // 这一条原本就对
this.roll  = atan2(right.y(), up.y());      // 不是 atan2(up.x(), up.y())
```

手算校验（yaw=roll=0、pitch=−30°）：正确解 `asin(−0.5)=−30°`；旧式 `up.y()=cos(−30°)=0.866`
给出 `asin(−0.866)=−60°`。**只有当玻璃完全不倾斜且 yaw=±90° 时两者才偶然同解**——这正好解释了为什么
夹具（`wipefix`：normal=(−1,0,0)、up=(0,1,0)）一路都是绿的（见 §5）。

## 3. 根因二：支点的坐标空间

`plane.pointAt(a, b) = position + right*a + up*b`，`position` 是**玻璃中心**（同文件 205-207 行用
`pointAt(±widthM/2, ±heightM/2)` 取四角，那条路径在游戏里已验证正确）。而 `applyRotation` 当时是

```java
graphicsHolder.translate(pivotX, pivotY, 0);        // ✗ 平面坐标当模型坐标
```

矩阵栈是**模型空间**的，于是旋转发生在"过模型原点、方向为玻璃法线"的轴上：杆子被整根甩出去。

## 4. 根因三：比例 → 中心的 `−0.5`

配置里所有 pin/pivot 都是"从玻璃左下起算的比例"（`verify_windshield.js` 用
`(pivotU − 0.5) * widthM` 还原米制偏移，同文件 1581 行的**已验证**路径也写的是
`config.pivotU * anchor.widthM - anchor.widthM / 2`）。修法：在 `pushPartTransform` 里**一次性**
把整组点平移到"相对玻璃中心"的坐标系再用。这样做是安全的，因为下面每一次运算
（`rotateAbout` / `followerEnd` / `handedness` / `carried` / pin-pair turn）**都只用到点之间的差值**，
共同平移不改变任何结果；只有 `pointAt` 例外——它要的正是绝对位置。

## 5. 新判据：`verify_plane_frame.js`（+ selftest 30/30）

三个验证器各管一层，之前缺的正是"二维拟合 → 三维客户端"这一跳：

| 文件 | 管什么 |
| --- | --- |
| `verify_windshield.js` | 玻璃二维域里的拟合：pivot/arm/park/sweep/pin/四杆闭合 |
| **`verify_plane_frame.js`（新）** | **客户端能不能把那套二维旋转在模型空间里重现** |
| `verify_panel_frame.js` | 仪表画布在客户端帧里的朝向/连续性 |

`verify_plane_frame.js` 两部分，因为它们各自会独立失效：

* **F1 源码守卫**：直接读 `MmtrWindshield.java`，断言 pitch 取自 `normal`（不是 `up`）、roll 取自
  `(right.y(), up.y())`、支点先 `pointAt` 再进矩阵栈、配置比例先转成中心米制；并断言三个旧式
  写法**不在**源码里。注释先被剥掉，所以文件里可以放心地写明错误写法。
* **F2 帧契约**（对每个玻璃锚点）：写法向量必须正交、且 `right == up × normal`（**这一条管扇形方向**：
  写反了刀片就往回扇，而逐块二维拟合永远看不出来）；反解重建的 `M` 三列必须等于 `(right, up, normal)`；
  共轭矩阵 `K = M·Rz(θ)·M⁻¹` 的轴必须等于法线、转角必须等于 θ；最后是**桥梁断言**——
  `K` 作用在停位臂销上的结果，必须与"在平面内绕法线转 θ"（即 `verify_windshield.js` 验证过的二维运动学）
  重合到 5e-6 m，且支点落在玻璃面上。

BR101 实测：

```

pane windshield_1_1: basis reproduced to 3.3e-16; the disproven extraction (pitch 51.90 instead of 38.10,
                     i.e. 13.81 deg of tilt) misses the basis by 0.170
pane windshield_1_1: conjugation about the normal by 92.60 deg agrees with the in-plane kinematics
                     to 2.0e-12 mm; pivot on the glass to 3.3e-13 mm
PASS: 4 wiper pane(s)
```

**selftest 从 26 条注入故障涨到 30 条，全中。** 其中两条注入的是**客户端源码**（不新增这一能力，
上面 §2/§3 的错误就没有任何离线东西能挡）。为此 `selftest.js` 的主循环改为统一走
`runWithMutation(suite, mutation, pristine)`，源码级注入的还原放在 `finally` 里——verifier 抛异常也必须
把 checkout 原样留下，否则"跑自检"就等于"改坏构建"。另外两条注入在锚点 JSON 上：把 `up` 取反
（`right ≠ up × normal`）、把 `up` 写成与法线不垂直。

### 夹具为什么一直是绿的

`wipefix` 的玻璃是**轴对齐**的（normal −X、up +Y）。在 yaw=±90° 处 pitch 与 roll 退化，旧解与正确解
构造出**同一个矩阵**，所以无论怎么改夹具数据都测不到 §2。这不是"夹具不够好"，而是"这个 bug 的
性质是倾斜"——判据必须覆盖真实倾斜玻璃（`vehicle.br101.json`），而回归必须打在源码上。这一段同时
写进了 `selftest.js` 的注释和 §5 的注入命名里。

## 6. 顺手修掉的判据崩溃（与雨刷无关但挡住了整条 selftest）

`verify_facets.js` 的 quad 分支一加进来就崩，链条两处：

1. 选面时 `candidatePoints.map(i => L.sub(vpos[i], centre))` —— `candidatePoints` 里已经是**点**，
   再拿它当索引读 `vpos` 得到 `undefined`。改为按点算。
2. `outOfQuad` 用**交叉量的绝对阈值** `1e-12` 判"这条边算不算"。被检顶点正好落在 quad 角点上时
   （HUD 角点已被吸附到桌面对应位置，这就是常态），交于该角的两条边给出的是 ±1e-7 的**浮点噪声**，
   符号相反 → 被判成"两侧都在外"，于是一个完美角点被报成"越界一整个宽度"。改为按**距离**
   `|cross| / edgeLength` 与容差比较，且 `inQuad` 必须把 `tol` **传进** `outOfQuad`（原来只用于事后
   比较，导致噪声阈值停在 1e-6 而调用方要的是 1e-3，1.1e-6 的噪声照样翻符号）。

修后 BR101：`PASS: 2 hud anchor(s) checked, 2 with facet data`。

## 8. 用户复测："运动正常了，但停位那份不消失，开雨刷又多出一个雨刷"

运动对了 ⇒ §2/§3 的修复成立。新症状（**两份几何**）是 202 那轮修复的**漏网**：

| 观察 | 含义 |
| --- | --- |
| 停位时只有一份 | 两份**重合**在停放位置 |
| 一开雨刷就出现第二个 | 一份跟着机构走，另一份**冻在建模位置** |

202 只把机构件从**主** optimized 批次里剔了出去，忘了**关门态**那张表。而整车车身画的正是
**关门态**那张（`StoredModelResourceBase:51-52` 把 doors-closed 的 objModels 当整车模型建；
`VehicleResource` 常态也是关门），所以雨刷的"第二份"一直在。

对**门**来说这不是 bug：门在关门态那份里的几何**就是关着的门**，所以门只需要"开门时再画一份动的"。
雨刷没有这种状态，两份必须只剩动的这一份。

修法（`ModelPropertiesPart` 的 OBJ `writeCache`）—— **分两步，中间踩了一个坑**：

**第一步（错）**：把机构件从两张批次表里都剔掉。结果用户报 **"雨刷没了"**。
原因在 `addObjModelPosition` 一身二职：它既把 ObjModel 放进批次表，又调用
**`objModel.addTransformation(...)`**；而 OBJ wrapper 的几何**只从登记过的变换里生成**
（`OptimizedModel.fromObjModels` 按 ObjModel 上的变换列表展开几何）。所以
"不登记" = wrapper 是空的 = 雨刷整体消失。顺带解释了当初为什么"会动的那一份"存在：
登记发生在 `partDetailsList.add(... optimizedModelDoor.get() ...)` **之前**，wrapper 建出来时几何已在。

**第二步（对）**：机构件**仍然登记**，但登记进一张**临时表**（没人会拿它建整车模型）：

```java
if (mechanism) {
    addObjModelPosition(objModels, new Object2ObjectOpenHashMap<>(), x, y, z, flipped, modelYOffset);  // 只要几何，不要出现在任何批次里
} else {
    if (!isDoor()) {
        addObjModelPosition(objModels, objModelsForPartConditionAndRenderStage, ...);
    }
    addObjModelPosition(objModels, objModelsForPartConditionAndRenderStageDoorsClosed, ...);
}
```

即：**门与普通件的行为一字未改**（普通件两张表都进、门只进关门态），机构件两张表都不进、
只由按部件那条路画一次。

同轮还修掉一个**近似**（同一处代码）：杆（rod）是刚体，一端在自己的支点 `p2`、另一端销在刀片上，
所以它的转角**不是**曲柄角 θ —— 用 θ 只对理想平行四边形精确，真实连杆会让杆销离刀片销偏
`|杆长| × 连杆残差`。现在臂/杆/刀片共用**一次**连杆解算（`m` = 曲柄销、`br` = 闭环求出的从动销）：
臂转 θ、杆转 `∠(br−p2) − ∠(br0−p2)`、刀片转销对走过的角。

判据同步扩到**两条**源码守卫（`verify_plane_frame.js`）：
① 玻璃帧（§2/§3 的写法）；② **机构件只画一次**（登记进临时表、且分支内不得出现任何整车批次表）。
第二条守卫的关键在于它**同时挡住两个反向错误**——查 `static copy`（多画一份）与查 `disappears`
（漏登记导致 wrapper 为空），因为这两个错正好互为反面，只查一边会把人从一边赶到另一边。
selftest 相应新增 3 条注入（杆角退回 θ、机构件退回关门态批次、机构件漏登记）——
**`selftest` 32/32**；`selftest.js` 也支持 `sourcePath` 了（这些注入改的是 `ModelPropertiesPart.java`）。

**用户复测结论：完美，雨刷搞定。**
