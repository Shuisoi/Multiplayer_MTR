# 170 = 车辆位置图层：引擎报"在轨上的弧长"，网页在自己画的那条线上取点

> 触发（2026-09-16，用户原话）：「然后也**设计个读取车辆位置**，**在地图页显示**。」
>
> 状态：**已实施**（引擎补字段 ＋ 前端图层 ＋ 用例 ＋ 探针 ＋ 文档）。
> 前置：同日刚在**区间地图**上画了站台（notes/169）；这一层按用户原话放在**地图页**。

## 1. 引擎本来就有车，只是位置不好用

`mmtr-trains`（运营台那套）早就有：`vehicleId / 当前轨 / headX,headZ / speedKmh / onRoute / moving /
doorsOpen / nextSection / 路线号 / 目的地 / 有人驾驶 …`。**但位置有两个问题**：

1. `headX/headZ` 是**引擎世界坐标**（采样那一套：方块中心），而「地图」页画轨时会把整条 path
   按每条轨自己的校正量**对齐到轨端点**（`railView` 的注释：采样走方块中心、节点坐标走方块角）——
   直接拿坐标落点，车会**偏半个方块**（与用户前一轮抓到的"信号灯左右分布不均匀"同一个坑）；
2. 即使补上校正量，也要先知道"车在这根轨的哪一段"，只给一个坐标就得自己往折线上投影。

**所以给的是读数，不是坐标**（新增四个字段，加在 `mmtr-trains` 的每辆车上）：

```json
"railHex": "FFFFFFFFFFFFFF56-…-FFFFFFFFFFFFFF5F",   // 规范形式：与 /mmtr-topology 的 rails[].hex 同一写法
"railArcM": 15.0,                                    // 车头在**那条折线**上的弧长
"railArcLengthM": 46.0,                              // 那条轨的长度
"arcIncreasing": false                               // 行进方向与折线方向是否一致（箭头朝向）
```

前端按 `railArcM / railArcLengthM` 在**自己已经画出来的折线**上按弧长取点（`pointAtLengthFraction`，
不是按"第几个点"），曲线轨也对得上 —— 与站台那层同一条思路（"画在这一页已经画出来的线上"）。

## 2. 踩到的三个坑（一个比一个深，都是探针逼出来的）

第一版用 `walker.currentRail()` + `enteredFromPosition()` + `offsetM()` 拼弧长。**表面上完全自洽**：
图层与探针用的是同一套公式，两边一比就是"全对"。是**另一条判据**把它揪出来的 ——
把引擎的 `headX/headZ` 投到那条轨的采样折线上，看它落在哪个比例：

| # | 坑 | 症状 |
| --- | --- | --- |
| ① | `walker.currentRail()` 可能是**方向被翻过**的副本（position1/2 与图里那条相反） | 弧从另一端量起 |
| ② | `enteredFromPosition()` 未必与轨的端点**逐位相等**（`Position.equals` 比 x/y/z），`mmtrArcOfEndNode` 于是返回 NaN，兜底分支又把方向当"弧增" | 同上 |
| ③ | **弧空间本身不是折线的空间**：`/mmtr-topology` 发 path 时从"位置图先遇到的那个端点"（`ends[0]`）开始走（`reversed` 标志），而 `railMath` 的弧零点在另一端 | 同一根轨**差一个整长** |

实测 7 辆车里 **2 辆**中招（探针一开始只报了"中位数对、最大值 31 画布单位"—— 15 格，正好是
"画到轨的另一头"的量）。**最终修法**：

- 位置靠**投影**：车头一定落在轨上（实测到采样折线距离 0.00 格），所以把车头投到轨的弧空间
  （`mmtrArcOfPoint`：粗扫 64 段 + 最近段内细扫 41 点，`railMath.getPosition` 是解析解、很便宜）；
- 方向也靠**投影**：前方节点（`aheadNode`）投出来的弧比车头大就是"弧增"，整条路不依赖任何身份判断；
- 最后按**拓扑那同一个判据**把弧翻到折线方向上：`mmtrRailFirstEnd()` 复刻 `getMmtrTopology` 收集
  `ends[0]` 的顺序，若该端点在弧空间里不是 0 就整条倒着量。
- 修完实测：7/7 辆的 `arcT` 与"把 headX/headZ 投到折线上"的比例一致（差 ≤ 0.001，来自取整）。

## 3. 画法

- **一辆车一个箭头**（三角形，长 2 格、宽 1.2 格），压在它所在的那根轨上、朝着行进方向；
  填充用主题强调色（全页唯一彩的东西）、描边用底色（从灰轨上分出来）。
  > **已被 notes/173 取代**：用户当天后续的指令「列车箭头以圆角箭头画，无动力车厢用矩形，货车用中空四边形」
  > 把这一层改成**一节车一个记号**、长按真车长、三种形状。本节其余部分（位置怎么算、刷新节拍）仍然有效。
- 朝向 = 该处切线（t±0.5% 两点）± `arcIncreasing`。
- **悬浮提示**（`<title>`）：车 id、速度、在不在运行、线路/目的地、车门、下一区间、车场、是否有人驾驶。
- **每 2 秒刷新一次**（`REFRESH_MILLIS`）：不刷新就等于"取一次快照"，车会定格。代价是运动中的车最多
  滞后一个周期（18 km/h ≈ 5 m/s ⇒ 2 秒最多 10 格），画出来仍在轨上、方向也对；要更贴就调这个数。
  轨网几乎不变，所以只有首轮取拓扑、之后每轮只取车（省一半请求）；计时器在卸载时清掉。

## 4. 这一轮顺手抽出来的共用件

`views/map/railAlignment.ts`：**"采样形状对齐到轨端点"这条规则只有一份**（原来是内联在
`RailNodesLayer` 里的）。现在轨道层与车辆层都用它 —— 车辆能落在**同一条线**上，靠的就是这个；
用例里也把"对齐不只是平移、它把采样没覆盖到的半格**拉伸**到端点上"钉住了（`vehicles.test.ts`）。

## 5. 实测（2026-09-16，活页面）

| 量 | 值 |
| --- | --- |
| 车 | **7 辆**（在运行 1、停着 6；速度 0–24 km/h） |
| 箭头 | 图上 7 个，与接口按 **id 一一对应**（id 写在 `<title>` 里） |
| 位置 | 停着的车逐辆**精确**等于"按弧长取点"（误差 < 1e-6 画布单位）；运动中的车仍落在**它那根轨的折线上** |
| 坐标系 | 落点与"headX/headZ 直接投影"差 1.35–1.47 画布单位（半个方块的对角 = 1.414）—— 直接用坐标就会偏 |
| 像素 | 箭头中心 `rgb(0,120,215)` = 主题强调色 |
| 探针 | `vehicle-layer-probe.mjs` **5/5**（notes/173 改成逐节之后是 **7/7**）；`vehicles.test.ts` **7/7** |

顺带修掉两条**探针自己**的问题（都是"世界里有车在跑"才暴露的）：
`signal-layer-probe` / `total-sections-probe` 改成**切走再切回**再读数（图层是挂载时取一次数，
不重挂会看到"单黄画成绿""带色差一条"这种**读数时间差**造成的假不一致）；
`map-zoom-probe` 的叠放断言放宽到允许车辆图层压在最上面；`section-track-probe` 补上 `switchView`
（它原来依赖"区间地图是默认页"）。

## 6. 刷新节拍（同日追加：用户「所有可变的都需要 0.5s 一次变动」）

原来只有车辆有定时器（2 秒），其余图层挂载取一次就不动了（区间地图是**完全没有**定时器）。
用户要求全部会变的都按 0.5 秒动，于是把"会变的"收成一个 store：**页面的 `views/map/liveFeeds.ts`**。

- **一个节拍、每路每拍只取一次**：`mapContext.LIVE_REFRESH_MILLIS = 500`（唯一读口）。
  地图页声明 `["points", "signals", "trains"]`、区间地图声明 `["points", "signals", "totalSections"]`。
  > 这个数当天晚些时候又调过：0.5 秒实测让服务端每拍多扛 ≈ 240 ms 的重活（日志 `Can't keep up!`），
  > **当前值 2000**；取数层与服务端 tick 的整套改法在 notes/172，记号那一轮的数字在 notes/173 §5。
- 为什么不是"每个图层各挂一个定时器"：原来地图页的 `RailNodesLayer` 与 `SignalLayer`
  **各取一次 `fetchMapNodes()`**（= 拓扑 + 道岔 + 灯，同一份数据发两遍）。按 0.5 秒刷会变成每拍 7 个请求，
  而且各层节拍不同步（"这层的车是新的、那层的灯是旧的"）。现在每拍 3 个请求、派生节点全页只算一次。
- **静态的不跟拍子**：拓扑（轨 + 节点）、L1 切点、站台挂载取一次 —— 它们是底图。
- **引擎侧也要跟**：`/mmtr-trains` 原来有 `LIVE_DATA_CACHE_MILLIS = 3000` 的缓存，页面每 0.5 秒问一次
  却每 6 拍拿到同一帧（看起来像"没刷新"）。已改成 **400 ms**（短于节拍）；其余图层接口本来不缓存。
- 实测（`sandbox/live-refresh-probe.mjs`，**5/5**，数 CDP 的 Network 事件）：3 秒窗口里地图页每路 **6 次**
  （= 2 Hz）、请求间隔中位数 **498 ms**；区间地图每路 6 次且**不取车辆**；静态的拓扑/站台/切点 **0 次**；
  隔 1.2 秒两次读 DOM，7 个车辆箭头的位置确实变了。稳态约 **6 请求/秒**。
