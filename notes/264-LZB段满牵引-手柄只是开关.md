# 264 — "牵引 20% 和 100% 加速度都是 +1.6"：LZB 段原来用的是**满牵引**，手柄只是个开关

用户口径（2026-09-23）：

> 牵引 20% 和 100% 加速度都是 +1.6

## 1. 现场数据（服务端日志 + 客户端 HUD，同一趟）

```
[MMTR-CONSIST] 19:12:53 手柄=65(68%) 牵引比=68% 电机=204kN 速度=9.2km/h
[MMTR-CONSIST] 19:12:55 手柄=65       牵引比=68% 电机=204kN 速度=17.2km/h   ← Δv=2.22 m/s / 2 s = 1.11 m/s²
[MMTR-CONSIST] 19:12:57 手柄=54       牵引比=57% 电机=171kN 速度=25.2km/h   ← 1.11 m/s²（预期 0.94 ✓）
         …24 s 一行 CONSIST 都没有（这一段没走控制器）…
[MMTR-CONSIST] 19:13:21 手柄=96       牵引比=38% 电机=114kN 速度=30.0km/h
[MMTR-CONSIST] 19:13:23 手柄=34       牵引比=37% 电机=111kN 速度=40.8km/h   ← Δv=3.0 m/s / 2 s = 1.5 m/s²（预期 0.63 ✗）
客户端 HUD： 19:13:17→19:13:22 加速度行 +1.63/+1.62/+1.66/+1.44/+1.62，而“快照”那一列是 -31 kN
```

两件事同时不对：

- **控制器段（AWS 轨）**：力与手柄吻合（68% → 204 kN → 1.11 m/s²，和算出来的一模一样）；
- **LZB 轨段**：加速度恒为满牵引那一条（1.5–1.66 m/s²），**与手柄无关**，而 `电机` 那行还显示着控制器上一次的残值
  （于是出现"在 +1.6 m/s² 加速、电机显示 -31 kN"这种自相矛盾的行）。

## 2. 根因：`simulateMmtrMotion` 的 LZB 分支把加速度写死成 `tractionAccelerationMps2(1, v)`

```java
} else if (overridden && !airBrakeConsist && mmtrConsistType != null && getMmtrRegime() == MmtrRegime.LZB) {
    // Signal S4 (LZB): 包线 + 天花板
    final double accelPerMs = siAccelerationToInternal(mmtrPhysics().tractionAccelerationMps2(1, ...));  // ← 满牵引
    ...
    } else if (wantPower) { speed = Math.min(ceiling, speed + accelPerMs * millisElapsed); }
```

- `wantPower` 只判"手柄 > 0"⇒ **手柄是开关，不是力的量**；
- 定速（AFB）在这一支里只是 `ceiling = min(线路限速, 定速)` —— 只**卡速度**，不削力；
- 这条线的轨限速是 **160 km/h**（`mmtr-topology`：95 条轨 `speedLimitKmh1/2 = 160`）≥ 101 ⇒
  **整条线都是 LZB 区段**，所以现场几乎所有时间都走这一支（`[MMTR-CONSIST]` 只在短 AWS 轨上才打）。

同一根杆：AWS 段 20% → 0.33 m/s²、100% → 1.63 m/s²；LZB 段**两者都是 1.63**。这就是用户看到的现象全貌，
也解释了 notes/256 那条"手柄 0 不许自己开"为什么在现场仍显得"车自己会跑"（手柄一旦非 0，LZB 段就是满牵引）。

## 3. 修法

LZB 只该管**天花板与包线**（限速、降速预告、超速回收），出力必须由控制器决定：

```java
final double controllerAccelMps2 = mmtrLzbControllerAccelMps2(control, millisElapsed);   // 每拍调一次控制器
final double accelPerMs = siAccelerationToInternal(Math.max(0, controllerAccelMps2));      // 牵引侧
final double driverDecelPerMs = siAccelerationToInternal(Math.max(0, -controllerAccelMps2)); // 电制动/气制动侧
final double decelPerMs = Math.max(mmtrMotionServiceDecelPerMs(), driverDecelPerMs);        // 司机的闸只会更强
```

- 控制器每拍**只调一次**（驾驶/包线两支互斥，不重复推进内部状态），
  于是控制器里的空气状态与驱动延迟在 LZB 段也照常演进（原来这一支**根本不碰控制器**，缸压/管压在 LZB 段是冻住的）；
- `mmtrLiveMotorForceN()` 报的力因此与真正施加的力一致 ⇒ HUD 的"电机"行不再说谎；
- 修完这一支顺带把**电阻制动**也接上了（原来手柄负侧在 LZB 段同样被忽略，只按惰行处理）。

## 4. 验证

新用例 `MmtrLzbSupervisionTests.theHandleSetsTheForceOnTheLzbBandToo`（三手柄机车在 120 km/h 的 LZB 轨上量单拍加速度）：

```
[TEST] LZB 段手柄 20% → 0.69 m/s²，100% → 3.06 m/s²      ← 单车 84 t/λ1.16：比例 23% 与 100%
```

修前两者都是 3.06（即"20% 与 100% 一样"）。既有 LZB 用例同时通过（天花板仍然强制、包线仍然刹车）：

```
[AFB+LZB] 定速 60：A 轨最高 60 km/h      （定速就是天花板）
[AFB+LZB] 定速 150：A 轨最高 107 km/h    （被线路 120 向下限定，功率到不了 120）
```

两处既有用例的油门档从 3 改成 7 是有意的：**LZB 段走控制器之后档位会缩放牵引力**，"推得动"就要给满档
（这正是这次修的东西，用例的口径跟着改）。

## 5. 同一类缺陷的另一处（未改，记在这里）

`simulateMmtrMotion` 的**自动走行**分支（`autoActive && !airBrakeConsist`）同样把加速度写成
`tractionAccelerationMps2(1, v)` —— 无人自动车不看 `autoNotch`，一路满牵引跑到线路限速。
它不是这次现场的原因（现场是手动车），但同一个形状：**"包线/巡航"这一层不该替车决定出多少力**。
