# 229 · 站台作业的子任务：进出站判定、双向确认、以及"引擎不再替司机刹车"

> 用户口径（2026-09-21，本轮全部依据）：
>
> > 「这个东西需要做子任务，比如说到某站台。首先不能干预玩家停车的行为，所以判定可以宽松点，
> > 在站台上停车就算完成停车目标，然后按键开门，等段时间，关门。这几个子任务完成后才算任务完成。
> > 现在需要完成进出站的判定，并且需要明确的双向确认任务和子任务完成」
>
> 三条后续裁定：① 到站**宽松到只要有车在站上就行**；② 停留**暂定 20 秒，但保留修改接口**；
> ③ 车门**司机手动与自动都保留**。

前一轮（notes/228）把"玩家与作业表相连"做通了：接管、进路、任务提示下发都能用。**这一步的完成判据**
当时只有一条 —— "到点停稳 + 停够 N 秒"。本轮把它换成**一张清单**，并把三处判据按用户口径重写。

---

## 1. 子任务模型：为什么它不塞进任务状态机

新类 `MmtrSubTask`（`org.mtr.core.mmtr`）：`Kind = ARRIVE | OPEN_DOORS | DWELL | CLOSE_DOORS`，
`State = PENDING | ACTIVE | DONE`，另外记两个时刻：完成时刻与**司机侧确认**时刻。

调度原语（"这一步走到哪一段"）与作业内容（"这一段里的活干完了没有"）是两件事：

* 状态机 `ASSIGNED→DISPATCHED→AT_TARGET→COMPLETE` 会 **FAILED**，子任务只会 PENDING/ACTIVE/DONE ——
  到站没停够不是失败（**停多久是司机说了算**），所以两者的失败语义不同，合在一起两个语义都会被拧歪；
* 清单要**发给客户端**、要被逐条判定，两者都需要一个稳定身份 ⇒ 链挂在 `MmtrMission` 上
  （同一次执行 = 同一张清单），而不是车、也不是作业单。

链由 `MmtrMission.ensureStationSubTasks(engineDefaultDwellMillis)` 建，**读的是 `StationServiceTask`**：
计划里的停留（`effectiveDwellMillis`）与引擎默认取**大者**，于是"计划说停 30 秒"仍然压得过默认值。
建链点放在 `Vehicle.mmtrMissionTick`（不是 `attachTask`）：默认值住在 `Simulator` 上，
而"两者取大"那一句必须发生在能同时看见两者、且能看见引擎默认值的地方。幂等，每 tick 调一次不花钱。

## 2. 到站判据：宽松口径只给玩家，而且必须与"不给停车点"一起改

**`mmtrAnyCarOnMissionStation()`**：判的是**占用段与站台轨有交集** + **停稳**（|v| ≤ 1e-5 m/ms ≈ 0.036 km/h）。

为什么不是"车头在站台轨上"：站台在物理上是一段轨，一列车停上去时**编组跨着几根轨** ——
车头早过了站台，车门却正对着站台。用户说的"只要有车在站上"正是这个意思。

站台轨从**目标对象**解析，三种写法都认：站台 →（它所属**车站**的全部站台轨，同一站多站台都算在站上）、
股道、车站；再把任务自己的目标轨 hex 兜底加进来（折返这类没有站台对象的目标靠它，
不至于一个目标都没解析出来时"永远到不了站"而卡死）。

**只对玩家放宽**（`mmtrArrivalIsLoose`：`executor == PLAYER && 有子任务链`）。判据的理由就是用户那句话的
**原因**本身：引擎不再给玩家的车设停车点，所以"停准了没有"它根本没资格判。自动车不换判据 ——
它的停车点是引擎按包线自己刹的，精确判据才是它真实的语义（换宽松判据会在"被信号按在站台轨上停着"
时误判到站）。

**一并撤掉玩家任务的停车点**（`mmtrMotionSelfArmMission` 的 PLAYER 分支）：这是本轮语义改动最大的一处。
修前（notes/228）为了让状态机能走到 AT_TARGET，玩家的车也被设了停车点，代价是
`autoBraking`（`Vehicle.simulateMmtrMotion` 的刹车包线）**每 tick 替司机刹车** ——
停车点一进刹车距离就压住牵引，司机想再往前挪半米对车门，车却被按住。用户明确要求不许干预，
所以撤掉它、换成宽松判据。**两件事是一体的**：撤掉刹车就必须换判据，否则步骤永远停在 DISPATCHED
（这正是当初加停车点的原因）。进路照发 —— 联锁、道岔、信号一个不少，区别只剩"油门与刹车归谁"。

## 3. 停留与车门：手动与自动都保留，靠**一条判据**分叉

时间：`Simulator.mmtrSubTaskDwellMillis`，默认 **20 秒**，接口 `mmtrSetSubTaskDwellSeconds(秒)`
（夹在 1–3600s），指令面 **`job dwell [秒数]`**（不带参数 = 查当前值）。
改它只影响**之后**建的链 —— 正在停的那一站照原时间停完，免得同一个司机眼皮底下时间变来变去。

门归谁：`mmtrDriverIsOperating(mission)` = `executor == PLAYER && mmtrManualOverride`（司机在操纵台上）。

| 情形 | 开门 / 关门 |
| --- | --- |
| 司机在操纵台上 | **引擎只等**（每 5 秒一句"等司机开门/关门（按…键）"）；他不动手就一直等 |
| 执行者是玩家、但司机不在操纵台上 | 宽限 15 秒后**引擎兜底**（免得司机下车/挂机把作业链卡死），日志写明"司机未操作，引擎兜底" |
| 自动执行 | **引擎立刻动手**（老行为逐位保留，实测每站一条 `引擎开门/关门（自动执行）`） |

判定全部是**观测**（门开着没有 / 时间到了没有），不向车发操作指令 —— 所以同一条链既能判自动车
也能判玩家：唯一的分叉是"谁动手"，不是"两套逻辑"。

**顺带补上一个缺件**：这一轮才发现在骑行层重建（notes/185）时，MTR 自带的那套门键被一起删掉了，
而 `PacketMmtrCabOp.Op.DOORS` 与引擎 `doors <车辆id> toggle [<side>]` 一直都在 ——
**司机手里根本没有能开门的键**。子任务化把这件事暴露了出来（链要求"门真的开了"）。
本轮补上：**Y = 本列车两侧门一起开/关**、**U = 只动右侧**（notes/50 的左/右分控）；
坐在车上就是"我在开的那列车"，没坐车时退回**瞄准的车门**
（`MmtrInteractPrompt.aimedDoorVehicleId()`，与交互提示那条 `[Y] 开门/关门` 同源 ——
"提示里写着按 Y"与"按 Y 真的有反应"因此永远是同一个目标）。

## 4. 进出站判定与双向确认：一条能查的数据，不是一句口号

**进站确认**：`Mission.markStationArrival` 在链开始的那一 tick 记下**实际到站时刻**，日志：
`[MMTR-SUB] 进站确认：车 … 已停在站台上（任务 PASSENGER，执行者 AUTOPILOT，停稳，占用车节在站台轨上=true）`。

**出站确认**：整条链全 DONE（= 门关好）才 `mission.complete()`，并记**实际发车时刻**、算出站停秒数：

```
[MMTR-SUB] 出站确认：车 … 本步作业完成（作业 TT-LOOP-1-3 第 4/16 步，
  实际到站 1789994028892 → 实际发车 1789994048924，站停 20s；
  引擎判定 ✔到站停稳 ✔开门 ✔停够 20s ✔关门；客户端确认 0 次，rev 9）
```

**双向确认**在数据上就是**一格里的两个字段**：`mmtrSubTasks` 的编码是
`KIND:STATE:ACK:人话`（`ARRIVE:DONE:A:到站停稳`），`A` = 客户端已确认这条。
上行由客户端回一个 `PacketMmtrCabOp.Op.TASK_CONFIRM`（载荷 `序号:版本号`）→
`Simulator.mmtrConfirmSubTask` → `Vehicle.mmtrConfirmSubTask`，
**带版本号是关键**：客户端确认的是"它当时显示的那一版"，引擎已经往前走了一版时，
日志会明说 **不一致**，而不是把过期的确认当成"确认了现在这一条"（静默接受会让双向确认退化成口号）。

确认只认**当前司机**（`mission.getExecutorPlayer().equals(crewUuid)`），非司机发来的确认被拒且写明理由。
客户端那半：**自动**回确认（看到某条"引擎已判完成而自己还没确认"就回一次，同一版只回一次，
不靠重发掩盖被拒），人工追加确认用 **N** 键（同一个包、同一个引擎入口）。
自动确认的**发信条件**也读镜像字段（`executor == PLAYER` **且** 驾驶室钥匙在本机玩家手里）——
乘客坐在自动车上时不该替司机回确认，否则每一条都会被引擎如实拒绝、把指令日志刷满。

HUD 两行：`子任务  ✔✔到站停稳 ▶开门 ✔?停够 20s ·关门`（**两个勾** = 引擎判定完成 + 客户端已确认，
**一个勾带问号** = 引擎说完成了、我这边还没确认）与 `提示  进站：把车停在站台上…`。
词全部由引擎按原话下发（notes/170 §8.4），客户端只拆开画；提示变化时往动作栏播一次（同"车被扣住"的规矩）。

## 5. 验证

**单元测试**：新增 `MmtrStationSubTaskTests`（3 例）——自动执行走完四步并记下进/出站时刻（计划 30 秒压过默认）、
玩家执行时引擎**不碰门**且没有停车点（连 15 秒兜底窗口过掉门也不开）、停留可改且越界被夹。
全量 **767 例 0 失败**。

两条红证（写进类注释）：

* `ensureStationSubTasks` 不用 `effectiveDwellMillis` ⇒ 30 秒那一段红；
* `mmtrDriverIsOperating` 恒 false ⇒ "过了兜底窗口门还关着"那一句红。

**实机**（引擎已部署，服务端重启后作业 `TT-LOOP-1-3` 以自动执行跑 1→2→3 站循环）：

```
进站确认 → ▶到站停稳 → ✔到站停稳 → ▶开门 → 引擎开门（自动执行）→ ✔开门
        → ▶停够 20s → ✔停够 20s → ▶关门 → 引擎关门（自动执行）→ ✔关门
        → 出站确认（第 4/16 步，实际到站 1789994028892 → 实际发车 1789994048924，站停 20s）
```

同一节拍在第 6/16 步复现（站停 20s），作业随后正常推进到第 7 步（折返轨换端）——
完成闸门没有把循环卡住。`job dwell` 在实机上回 **"当前站台停留 20s"**。
`[MMTR-SUB]` 整条链与 `job status <车辆id>` 的"子任务 4/4 / 现在该做 / 进站= 出站= 停留要求="两处读数同源。

## 6. 两个教训（都是这一轮真踩到的）

1. **同一 tick 里刚改过的读数不能用方法开头那一份**：第一版把 `doorsOpen` 在 `mmtrTickStationSubTasks`
   入口读一次，引擎在同一 tick 里把门开掉之后，停留那一条立刻报"司机提前关门（已停 0s）"——
   **假警报**。改成每次现读（`vehicleExtraData.mmtrDoorsOpen()`）。
2. **测试里的时钟不会自己走**：`siding.simulateVehicles(1000, null)` 只跑一拍、**不动 `currentMillis`**；
   推进会话时钟的是 `Simulator.step(millis)`（内部按 1 秒切片）。第一版用例的 `tick()` 用了前者，
   于是"停够 20 秒"永远停在"已停 0s"，断言全线红 ——排查看起来像链没被调用，
   实际是时间没动。**夹具的 `tick()` 必须用 `sim.step`**（写进用例注释）。

## 7. 还没做 / 需要人做的
* **客户端必须重启**（notes/228 §8.6 的老规矩）：HUD 的子任务两行、Y/U 门键、N 确认键、自动确认
  都是客户端类，**正在跑的游戏客户端不会重新加载它们**。引擎侧（子任务链、进出站判定、停留时长）
  已经实机验证；司机那一半要重启客户端之后才能看：坐进司机位 → B 接管 → 开到站台停稳 →
  Y 开关门 → 看 HUD 的两行与动作栏提示。
* 玩家任务的**到站精确度**现在完全交给司机：停歪了（站台轨上没有车）这一步就不完成，
  HUD 提示会一直说"进站：把车停在站台上"。这是口径要的，但值得实机看一眼司机的体感。
* 换端（`CHANGE_ENDS`）目前不在子任务链里（它没有门/停留的时间语义）；若要"换端也要确认"，
  应该给它自己的一种子任务，而不是硬塞进站台链。

## 8. 现场跟进（同日）：br101 没有客车门 ⇒ 作业编组挂一节 P1

用户口径：「我这个车没有客车门，你在后面挂个 P1 车吧」。

**先核实前提**（不是猜）：`BR101_v54.zip` 的 OBJ 分组只有 `body / interior / floor / cabdoor_* / doorway_cabdoor_* / wiper*`
—— **没有 `door_l_*` / `door_r_*` 客车门**，机车只有司机门。所以司机按 Y 时引擎的门状态会翻，
但**车上没有任何一扇客车门会动**；而子任务链要的正是"门真的开了"。用户的判断是对的。

**P1 是现成资产**：`MMTR_NewStock_v1.zip`（已在资源包列表里）含
`definition_p1.json` / `properties_p1.json` / `p1/p1.obj`，`properties` 里有 4 扇门
（`door_l_1/2`、`door_r_1/2` + 对应 doorway）。实测打包后的 OBJ 包围盒：**X 5.0 × Y 5.71 × Z 16.0**
（MTR 约定：Z = 车长、X = 车宽）。旧列车表 `mmtr-rolling-stock.json.bak-before-fix` 里 p1 的规格是
`length 16 / width 5 / bogie ±5 / capacity 400 / powered false`，与模型完全一致。

**挂法（改的是"生成模板"，不是给车打补丁）**：

1. 列车表 `mmtr-rolling-stock.json` 的股道 2（`L1-br101` → `L1-br101+p1`）编组改成
   `[br101(powered, mmtrCouplerAfter), p1(unpowered)]` —— 19.9652 + 16 ≈ 36 m ≤ 43 m 股道；
2. 作业单 `TT-LOOP-1-3` 的 `cars` 改成**同一条两节编组**（`mmtr-jobs-upsert`）——
   这一步不能省：作业调度器按 `job.cars` 生成并会**丢掉"不属于它"的停放车**，
   只改列车表会被它覆盖回单节；
3. `manifest reload` → `mmtr-manifest-reset`（引擎清掉全部生成车并按新表重铺）。
   实机：`模板=[br101+p1] 在场=[br101+p1]`，新车辆 id `2220195164110232565`，`cars=2`。

**为什么走"重铺"而不是"现场连挂"**：连挂（`MmtrCoupleSurgery`）要求两列车**同一根轨、车钩相对、
已靠到车钩距离**（自动车钩 C8 也要靠上去才吸合）。br101 当时在 1 站 2 台上、P1 只可能在车辆段股道上生成，
中间隔着整段调车进路 —— 现场连挂需要司机先把机车开回段里。改模板重铺是**一次操作、且持久**
（重启后照样是两节），代价是编组回到段里、作业从第 1 步重跑。

**一处要修的东西（资产问题，不是接线问题）**：P1 是按**旧比例**建的 —— 宽 5.0 / 高 5.71，
而 br101 是宽 3.08 / 高 3.97。两节挂在一起，客车会明显比机车"胖一圈"。
要修的是建模与重打包（按 br101 那一套比例重导 p1 的 OBJ，见 skill `mmtr-train-modeling` 铁律 0
"有实测数据就不许估"），不是引擎侧的尺寸字段 —— 引擎给的 `width` 只影响占位，模型本身多大就是多大。
