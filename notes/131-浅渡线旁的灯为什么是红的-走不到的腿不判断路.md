# 131 - 浅渡线旁那盏灯为什么是红的：区间"走不到的那条腿"不许把整段判成没有进路

> 触发：用户 2026-09-14「道岔节点 -170,-60,-289，在 -170,-60,-253 节点旁的灯为什么是红色，
> 不应该是绿色么？」
> 前置：notes/130（浅岔口判据修好之后，这些节点第一次有了物理模型）。

## 1. 现场事实（改前，引擎自己的诊断）

`mmtr-signals` 里那个位置的灯是 **`(-168,-60,-253)`，朝向 180°（朝北，即朝 `-170,-289` 那座道岔），
aspect = RED**。把它交给引擎自己的诊断（`signal why -168 -60 -253`）：

```
① 保护的轨 (-170,-289)↔(-170,-253)（长 36 m），起点弧 36 m，朝向 (0.0,-1.0)
②[1] 本灯区间 id=-168,-60,-253  段数=2  长=73 m  占用=否  出口灯=-167,-60,-289
      结束原因：撞在道岔 -176,-60,-253 的**禁行侧**（道岔位置 0：这条轨禁止通行）→ 这条进路走不出去，按红显示
      span 轨 (-170,-289)↔(-170,-253) 弧 0..36
      span 轨 (-176,-253)↔(-170,-289) 弧 0..37          ← 那条 9.5° 斜线
③ 结论：深度 1 → RED
```

也就是说：**区间在岔口没走直通那条正线，而是拐上了那条 9.5° 斜线**（位置 0 时它禁止通行），
走到斜线另一端又撞上 `-176,-60,-253` 的禁行侧 ⇒ 整段被判成"没有进路" ⇒ 红。
而直通那条正线（位置 0 = 正线贯通、占用=否）本来是通的 —— 用户的判断是对的。

## 2. 这是"浅岔口被认出来"之后的**副作用**

那两个节点以前**没有物理模型**，所以"禁行侧"这道墙根本不存在 ⇒ 区间拐上斜线也不会撞墙 ⇒
灯由占用/链深决定 ⇒ 绿。判据修好（notes/130）之后，斜线在位置 0 被正确地标成禁止通行，
于是 `walk()` 里"撞在道岔禁行侧 ⇒ 这段按红"这条规则被**误伤**了。

`walk()` 的规则本身是用户 2026-09-10 的裁定：**"岔口多腿"** —— 一盏灯守整个咽喉，
不能只守它正对着的那条腿（否则出口灯只保护了一条路）。它只检查了**进来的那条轨**是不是禁行侧，
**没区分"这次运行走得到哪条腿"** ⇒ 拐进物理上禁止通行的岔股，再撞上那边的墙。

## 3. 修法：区分"走得到的腿"与"要守住但走不到的腿"

保留多腿保护（岔股上可能停着扳岔之前就进来的车，那条腿照样要守住），但给 `walk()` 加一个
`reachableRoute`：

- 进入某条腿时算 `reachableLeg = （这个节点没有模型）|| 这条腿 == 模型当前开通的那一条`
  （`continuationFrom(到达轨, 位置)`）；
- 递归时把 `reachableRoute && reachableLeg` 传下去；
- 撞在禁行侧时：**只有 `reachableRoute` 才**判"没有进路"（`blockedAtArrival = true` ⇒ 红）；
  走不到的那条腿撞墙只停下它自己，并留一句说明（"本进路走不到那条腿，不判断路"），
  而且不覆盖已写下的结束原因。

于是：那条斜线**仍在区间里**（保护不变）、区间**没有被判成断路**、灯按直通那条正线正常显示。

## 4. 验收

新增用例 `theBranchOfAShallowCrossoverIsGuardedWithoutTurningTheLampRed`
（`MmtrDirectionalBlockServiceTests`，用实测世界的几何：两处道岔 + 中间那条横移 6 格/36 格的浅斜线）
把三件事一起钉住：

1. 岔股那条腿**仍在区间里**（多腿保护没被砍掉）；
2. `blockedAtArrival == false`（走不到的腿撞墙不再把整段判成没有进路）；
3. 位置 0、线路空闲 ⇒ **`GREEN`**；
   再把道岔扳到位置 1（灯自己那条轨被切断）⇒ 仍然 `RED` + `blockedAtArrival`（用户 2026-09-13
   的规格：进路被道岔切断的灯必须是红）。

实现前先用临时探针量过（灯立在直通轨上朝岔口）：

```
[PROBE] 灯在弧 5.0 朝 A → 守 <正线远端> <根部> <斜线>  | 段数=3 blockedAtArrival=false aspect=GREEN
```
