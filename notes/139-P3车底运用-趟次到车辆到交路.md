## 1. 怎么套班（设计 §5.1 ③ + §3）

```
N = ceil(ring / 高峰最小间隔)
第 i 个发车槽位 → 第 (i mod N) 辆车；**同一槽位的返程趟也归它**
每辆车：出库 → 往 0 → 返 0 → 往 N → 返 N → … → 回库
替补（fleet.spares）一个趟次都不占
```

"为什么是 i mod N"：一辆车跑完"往 + 终点处理 + 返"（一个 ring）回到起点，而发车每 headway 一次 ——
它下一个接得上的槽位就是 i + N（N × headway ≥ ring，向上取整留出的余量变成它在起点站台上的等待）。
这条关系就是 N = ceil(ring / 高峰间隔) 的物理含义，也是"车辆数固定要利用好"要盯的那个数。

**返程趟是 P3 必须自己生成的**（P2 只生成起点方向）：否则一辆车的两趟之间会凭空跳回起点 ——
交路连续性（验收 ①）根本无从谈起。为此 P2 的生成器加了方向参数：
`MmtrServicePlan.generate(line, pattern, times, BACK)`，
返程趟的发车时刻 = 对应往程趟的 `terminalDoneMillis`（终点站处理完就开回来）。

## 2. 本轮**修正了一处设计公式**（有实测依据，不是口味问题）

设计 §5.1 ①：`ring = 往程走行 + 沿途各站停站 + 终点处理 + 返程走行 + 沿途各站停站`
—— 停站按"每站两次"算，**终点处理只算一次**。

按它实现之后，P3 的连续性用例**直接红了**，而且是硬数字：

```
C1 第 8 趟 L1-B025 处理完 09:12 → 第 9 趟 L1-033 开 09:12（差几秒，装不下）
```

原因：车回到起点后**还要换一次端**才能发下一趟，那一次同样是占用 —— 高峰段 3 min × 8 = 24 min 的
间隔，装不下 25.5 min 的实际循环。所以 ring 改成按**车辆实际占用时间**算：

| | 旧（设计字面） | 新（实际占用） |
| --- | --- | --- |
| 停站 | 每站算两次（2 × Σ停站） | **属于"到达"**：每站每次到达算一次 |
| 终点处理 | 一次 | **两端各一次**（起点端换端也是占用） |
| 三站例（4 min 段 / 45+30 s 停 / 3 min 处理） | 22.5 min | **24.5 min** |
| N（3 min 高峰） | 8 | **9** |

顺带把"停站属于到达"这条落进 `buildTrip`：**这一趟的起点站不加停站**（车本来就在那儿，
`departureMillis` 就是车轮动的时刻 —— 时刻表那一栏本来也该是这个含义）。
`N = ceil(ring / 高峰间隔)` 这条关系不变（验收 ④ 就是拿它对的）。

> 这条是本轮最有价值的东西：**公式看着对、跑起来装不下**，而抓出它的是一个"连续性"断言。
> 断言不是形式，它是唯一会替你算账的东西。

## 3. 交路长什么样

`MmtrDiagram`：`lineId` / `ringMillis` / `peakHeadwayMillis` / `requiredConsists` / `workings[]` /
`idleConsistIds`（配多了、今天不上场的套班车底）/ `spareConsistIds` / `capacityProblem`。

每辆车 `Working.entries` 是有序的：
`DEPART_YARD`（出库，起点=首发 − `leadTimeMillis`，终点=首发站台）→ 若干 `TRIP`（往/返交替）→
`STABLE_YARD`（回库）。每条带 `startMillis` / `endMillis` / `waitBeforeMillis`（与上一条的空档 ——
套班取整、终点处理、站台等待全都表现成它），`TRIP` 那条还挂着完整的 `MmtrServicePlan.Trip`。
