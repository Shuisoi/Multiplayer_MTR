# 228 计划内接管：司机开车、作业表照走、提示发到客户端

用户口径（2026-09-21）：

> **「现在要完成的是计划内接管，也就是说比如在车辆还在等待发车，到站停站等静止状态时接管。
> 除了操作以外还需要有任务提示传送到客户端，并且要有任务完成判定。」**

三件事对应本轮的三片。断点在前一轮已定位（notes/227 的上下文）：**玩家执行的任务原先不设停车点，
而任务前进的唯一判据是"停在停车点上"，于是步骤永远停在 `DISPATCHED`、作业表永远不往下走**。

---

## 1. 任务完成判定（S1）：玩家任务也要有停车点

`Vehicle.mmtrMotionSelfArmMission` 的 PLAYER 分支原来只发布进路（T4），**不设停车目标**。
现在照样调 `setMmtrMotionStopTarget(...)`，与自动车**唯一的区别仍然只有油门**
（不 `setMmtrMotionAuto(true)`，牵引只可能来自司机的手柄）。

得到两样东西，两样都是要的：

1. **到站停得准** —— 共用同一套制动包线与"锚点校正"，不会冲过站台；
2. **到点就算完成** —— `isMmtrMotionStoppedAtTarget()` 与自动车同一条判据，不另写一套。

顺带：司机"推手柄离开停车点"那一支（`simulateMmtrMotion` 的 departed 分支）里补了
`mmtrPlayerRoutePublished = false`，让自臂闩跟着停车点一起清 —— 否则下一步（或重规划）
会因为闩还立着而不再自臂。

## 2. 作业表认司机（S2）

| 件 | 说明 |
| --- | --- |
| `JobInstance.driverUuid` | 这条作业单交给谁（`null` = 只是老式"人工保留"，没有执行者） |
| `MmtrJobScheduler.humanTakeover(jobId, uuid)` | 新增重载；旧的单参版本 = `(jobId, null)`，语义逐字不变 |
| `startOutbound` | 有司机绑定时**照常进入这一步**（建 mission、发进路、给停车点）；只有"人工保留且无司机"才让位 |
| `runManualStep` | 建 mission 时 `attachJobStep(...)` + `setExecutor(PLAYER, driver)` |
| `jobIdOfVehicle(vehicleId)` | 把"车"翻成"作业"，接管入口用它 |

**计划内接管 vs 老式人工保留**（这是本轮的分界，写清楚免得被当成改坏了）：

| | 谁开 | 作业表 |
| --- | --- | --- |
| 老式 `humanTakeover(jobId)` | AI 不发车、也没执行者 | **停在原地** |
| 本轮 `humanTakeover(jobId, driver)` | 司机 | **逐步推进**（到点即完成） |

## 3. 静止交接的闸门（S2/S3）

`Simulator.mmtrJobTakeover(vehicleId, driverUuid)`：

- **车必须静止**（`speed <= 1e-9 && !isMoving()`）—— 用户口径"等待发车 / 到站停站时接管"。
  不是偏好：车在动时换执行者，进路/道岔持有/protection 都还是"为自动车算出来的"那一份，
  交接窗口里每一拍都可能在两个执行者之间空转。
- **司机从驾驶室钥匙读**（`Vehicle.getMmtrCrewUuid()`，新增）—— 客户端那条路自带 uuid，
  控制台那条路（`job take <车id>`）不必让人把 uuid 抄一遍。两者都没有 ⇒ 拒绝"先上车再接管"。
- 交接时清掉"自动车那一份"停车点（`clearMmtrMotionStopTargetForHandover()`），下一 tick 按
  PLAYER 口径重新自臂 —— 于是司机接手时就有一份属于他的停车点与进路。

## 4. 任务提示发到客户端（S4）

**四个新同步字段**（`schema/data/vehicle.json` → 生成类；`Vehicle.updateMmtrSyncFields()` 写；
`VehicleSyncPatch.DYNAMIC_KEYS` 收）：

```
mmtrJobId  mmtrTaskNote  mmtrTaskStep  mmtrTaskSteps  mmtrMissionState  mmtrMissionExecutor
```

三个刻意的决定：

1. **引擎算好原话发过去**，客户端一个字段都不反查 —— 目标名要从站台/股道对象取、步骤的人话说明
   在作业单里，客户端两样都没有（notes/170 §8.4）。
2. **变了就主动标脏**（`vehicleMmtrMarkSyncDirty`）。车停在站台等发车时速度/门都不变，
   若靠"读数变了顺带带出去"，这几个字永远推不过来 —— 而"等发车"恰恰是最需要看到提示的时刻。
3. 提示就是**作业单步骤自己的 `note`**（"去程到 1 站 1 台"这种），引擎不改写：作业单是
   操作者写的，引擎替它润色就等于两处说法迟早分叉。

**客户端**：`MmtrDriverHud` 顶部两行（作业 k/n · 任务说明 · 执行者），**换步时往动作栏播一次**
（与"车被扣住"同一个规矩：只在变化时播）—— 司机在站台上等，如果只更新角落里的小字，人会一直等下去。

## 5. 入口（S3）

| 入口 | 用法 |
| --- | --- |
| 游戏内 | 坐在司机位上按 **B**（`key.mmtr.task`）接管 / 再按一下还回去 |
| 引擎指令栏 | `job take <车辆id> [司机uuid]` / `job release <车辆id>` / `job status [车辆id]` |

游戏内那条走 `PacketMmtrCabOp` 的两个新 op（`TASK_TAKE`/`TASK_RELEASE`）：它动的是**引擎侧的绑定**、
不是世界里的实体，所以不走那条"转交游戏端"的文本指令队列，而是在 `simulator.run(...)` 里直接改
（引擎状态都在模拟线程上）。

客户端**不复刻**"必须停稳"这条规则（复刻一遍必然与引擎分叉）；被拒的原因由引擎写进指令日志，
动作栏也会显示。

## 7. 本轮踩的坑（值得记：一个注解写错，看起来像"整棵树坏了"）

改到一半时全量编译报 **200 个错**，分布在 20+ 个**我没碰过**的文件上（`Main`/`ServletBase`/`Data`/
`UpdateSquaremap`…），几乎全是 `找不到符号: 变量 log`，另外还有 `找不到符号: 方法 getGameMillisPerDay`。
当时的结论是"源码树本来就编不过、Gradle 一直在靠增量编译过日子"——**这个结论是错的**。

真因是**我自己**两处手误叠在一起：

1. `@org.jspecify.annotations.Nullable java.util.UUID` —— jspecify 的 `@Nullable` 是 **TYPE_USE** 注解，
   不能注在**全限定名**上；javac 直接报错。**而 javac 一旦在第一轮就有错，就会中止注解处理轮**，
   于是 Lombok 的 `@Log4j2` **一个 `log` 都没生成** —— 23 个 `@Log4j2` 类连同它们的子类
   （`Simulator extends Data` 就是靠继承拿 `log`）全部报"找不到 log"。
2. 同一轮 `driverOf` 上出现了**两个 `@Nullable`**（一处是我早先写的方法注解、一处是后来字符串替换
   补进去的），报 `Nullable 不是可重复的批注接口` —— 又是一个第一轮错误。

而"`getGameMillisPerDay` 不见了"也是同一件事的下游：它是**Lombok `@Getter` 从字段生成的**
（修好之后编译器还特意提醒 `Not generating getGameMillisPerDay(): A method with that name already
exists` —— 说的是我一度手工补的那一份）。我据此写过一段"源码丢了这个口"的注释，**已删掉**。

教训：`log`/`getXxx` 这类"全仓库一起消失"的符号，先怀疑**注解处理被中止**，不要先怀疑树坏了；
以及**第一轮错误**（注解写法、重复注解）的代价会被放大成几十个不相干的报错。

## 8. 补记：驾驶室朝向 —— "该进哪一端"由行进方向定（用户现场报的）

用户口径（2026-09-21）：

> **「关于生成列车后的驾驶室朝向的问题，需要按首个任务的方向定驾驶室方向。本次传送正常但是
> 被传送至了与行进方向相反的驾驶室 1，需要一个逻辑用于识别正确的驾驶室。」**

### 8.1 为什么"第一个驾驶室"是错的

方向**恰恰是由被占用的驾驶室决定的**：

```
MmtrConsistWalker.towardB() = cabs.travelsToward(End.B) != travelReversed
MmtrCabState.leadingEnd()   = 被占用的那个驾驶室所在的端（没人 = null）
```

车场刷出来的车带着引擎的 **SYSTEM 占位钥匙**，方向已经定死；传送上车原来挑"第一个可用的驾驶室"
（车节 0 的 A 端 = `1A`）。人坐进另一端的驾驶室，结果只有两种，两种都是**司机坐在车尾往前看**：
要么把方向拧反，要么自臂发现规划不出来、把换向器翻过去反向行驶。

### 8.2 判据（与自臂同一条，不另立一套）

"任务要往哪边走"只有规划器知道，而且**方向是它的输入而不是输出**（同一条进路按当前方向规划；
规划不出来时自臂就翻换向器再试 —— `mmtrMotionSelfArmMission` 的 flip 分支）。所以照抄那条判据：

```
先按当前方向 planToRail(目的轨)：
  可行   ⇒ 任务方向 = 当前方向
  不可行 ⇒ 任务方向 = 当前方向的反面
需要的驾驶室 = cabFor(任务方向)          // 朝 B ⇒ 最后一节的 B 端；朝 A ⇒ 第 1 节的 A 端
并要求换向器归位（驾驶室朝前）            // 只在停稳时；滚行中翻换向器是红线
```

落在 `Vehicle.mmtrPreferredCabSpec()`；`Simulator.mmtrPreferredCabSpec(vehicleId)` 是取数口；
`MmtrBoardPlayer` 在调用方**没显式指定驾驶室**时问它（显式指定仍然优先）。
另有 `Vehicle.mmtrResetTravelDirectionForDriver()`，在传送上车与 `job take` 时把换向器归位
（自动运行为了走得通可能正反着跑）。

### 8.3 实测（跑一整圈，看它跟不跟着翻）

`job status <车辆id>` 现在把三件事一起打出来 —— **领先端**、**换向器**、**引擎认为该进哪个驾驶室**
（只报其中一样，"司机坐在车尾"这种现场是看不出来的）：

```
[19:15:24] 5/16 去程到 3 站 1 台      占用=CAB_A  该进=1A  朝 A 端（领先端=A·换向器=推）
[19:15:48] 7/16 南端折返轨…换端        占用=CAB_A  该进=1A  朝 A 端（领先端=A·换向器=推）
[19:16:25] 9/16 回程到 3 站 2 台      占用=CAB_B  该进=1B  朝 B 端（领先端=B·换向器=推）
[19:16:37] 10/16 3 站 2 台开关门       占用=CAB_B  该进=1B  朝 B 端（领先端=B·换向器=推）
```

去程 A 在前 ⇒ 该进 `1A`；中间那一步 `CHANGE_ENDS` 把钥匙移到另一端之后，**回程变成 B 在前 ⇒ 该进 `1B`**。
这正是"按任务方向定驾驶室"。

### 8.4 连带发现：引擎换端之后，**人**不会自己走过去

同一个问题的另一半：作业单在两端的折返点有一步 `CHANGE_ENDS`，引擎把钥匙从一端移到另一端
（`MmtrCabState.changeEnds` 只是换 `activeCab` —— "人走过去"是这句话的物理含义）。
但钥匙是引擎的，**坐在驾驶室里的人不会因此站起来走过去**：不跟过去的话，回程就变成
"车朝 B 开、司机还在 A 端往前看"，与用户报的那个症状是同一件事，只不过这一次是作业单自己造成的。

客户端新增 `MmtrCabInteraction.followEngineChangeEnds`，三道判据保证"不会跟错"：

1. **钥匙确实在我手里**（比镜像里的乘务员 uuid，不是"有 crew 就算"——那可能是别人）；
2. **只在镜像"变过去"的那一拍跟**（记上一次看到的镜像驾驶室）：否则会与"司机自己在另一端
   动了手柄"打架 —— 他申领了 B 端、引擎还没确认的那几拍里，本条会把他拽回 A 端；
3. 跟随动作走**同一段 `enterCab`**（与按 G、与被传送进来完全一致）。

### 8.5 修法与"为什么之前怎么选都反"

**真因**：锚点编号 ≠ 引擎的 A/B 端。车体局部的 **+Z 由 bogie1→bogie2 定义**
（`PositionAndRotation.getYaw` 取 `atan2(x2−x1, z2−z1)`），而 MTR 把 bogie1 放在脊柱的 **A 端**
（`Vehicle.getVehicleCarsAndPositions()` 从 A 端起算、先 bogie1 后 bogie2）⇒ **+Z = 引擎的 B 端**。
而 BR101 的 `mmtr_cabdoor_1` 座位点在 `z=+7.71`（B 端）、`mmtr_cabdoor_2` 在 `z=−7.71`（A 端）。
客户端原来把**锚点编号**当引擎端发（`cab == 2 ? "B" : "A"`）：要 `1B` 时引擎把钥匙放在 B 端（它没判断错），
客户端却把人放到编号 2 的座位 = **A 端** —— "引擎以为司机在车头、人实际在车尾"。**选哪一端都反。**

实测佐证（19:21，B 端在前那一段）：

```
mmtr-motion : front=(-175.5,-305.5)  rear=(-175.5,-325.47)  activeCab=CAB_B
clients     : 玩家 z=-324                      ← 落在 rear 一侧（towardB 时 rear = aEnd）
```

**修法**：一条规则，换算只有一处 —— `MmtrVehicleAnchors.engineEndOfSeat(seatZ)`：
**`z > 0` → 引擎 B 端，否则 A 端**（锚点编号不再当端用）。四个交接点全部改走它：

| 位置 | 作用 |
| --- | --- |
| `MmtrCabInteraction.enterCab` | 锚点 → 引擎 spec |
| `MmtrDriverSeat.Seat.cabSpec` | 动手柄时的自动申领 |
| `MmtrBoardRequest.pick` | 引擎 spec → 锚点 |
| `MmtrCabInteraction.followEngineChangeEnds` | 换端跟随，比**端**不比编号 |
| `MmtrInteractPrompt.CabTarget` | 新增 `engineEnd` 字段（由 `cabView(...).z` 算出） |

**不在模型里改编号**：这条规则从几何推出，对两种编号约定都成立；而 `mmtr_cabdoor_1` 落在 +Z 与
`docs/02-运行与作业/MMTR-OBJ车辆资源包-标准化工作流.md §1.1` 写的"1 = A 端"不一致，是资源包侧的
命名约定问题，留待决定是否统一（代码已不依赖它）。

### 8.6 ⚠️ 客户端改动必须**重启游戏客户端**，不是重启服务端

改完这一版后现象依旧（日志里还是 `驾驶室=1（1A）`、座位点 `z=+7.71`）。查进程才发现：

```
CLIENT PID 40488  启动于 19:19:50        ← 玩家那一侧，从那时起就没换过类
客户端类编译时间     19:26:14             ← 重启服务端时 gradle 重编的
```

`dev-server.ps1` 那一轮 gradle 会把 `build/classes` 重新编好，**但已经开着的游戏客户端进程继续用它已经
加载过的旧类** —— 引擎侧（走 jar）重启即生效，客户端侧（走 loom 的 classes）必须**重开客户端**。
上一轮"改完还是反的"就卡在这里：那一测用的是旧客户端。

排查口径：`Get-CimInstance Win32_Process` 里 `fabric.dli.env=client` 那个进程的**启动时刻**
与 `build/classes/.../client/Mmtr*.class` 的**修改时刻**比一比 —— 进程更早 = 它跑的是旧代码。
