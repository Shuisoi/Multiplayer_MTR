# 216 · 实机「车不动」的真因：运行中换了引擎 jar（+ 把静默失败变成日志）

日期：2026-09-21 · 车辆：BR101（模型 id `br101`）· 结论：**不是服务端的运动限制** —— 是我在
dev server 运行中重建并覆盖了 `game/libs/Transport-Simulation-Core-0.0.1.jar`，服务端懒加载到坏 zip，
于是**每一个驾驶包都在服务端抛异常**。已加护栏（运行中拒绝同步）并把三类静默失败改成日志。

## 1. 现场证据（服务端日志，15:31–15:33 那次会话）

| 证据 | 说明 |
|---|---|
| 295× `RuntimeException: Failed to load class file for 'org.mtr.core.mmtr.ControlState'!` | 每一次按手柄都中；栈底 `PacketDriveControl.runServer:63` |
| `Caused by: java.util.zip.ZipException: ZipFile invalid LOC header (bad signature)` | jar 内容与进程手里的 zip 句柄不一致 |
| `[MMTR-CAB] 上车结果：进入驾驶室 1B … 钥匙=CREW` **成功** | 上车走 `PacketMmtrCabOp`，那条路不加载 `ControlState`，所以"能进驾驶室" |
| `[MMTR-HLTH] … mmtrOverrides=0` | 引擎从未收到过任何操纵状态（override 一次都没建立） |
| 进程表 | **PID 36748 = dev server 起于 13:26**；PID 55080 = client 起于 15:31；jar 于 **15:28:58** 被我覆盖 |

时间线完全吻合：**运行中的服务端**（13:26 起）抓着旧 jar 的句柄，我在 15:28:58 覆盖了同一个文件，
它下一次需要新类（`ControlState`）时读到坏 zip。客户端后起（15:31），但它与服务端共用同一个 jar 文件，
同样有风险。

## 2. 为什么"能上驾驶室、却一动不动"

- `PacketMmtrCabOp.runServer` → 引擎 `cab …` 命令 → `enterMmtrCabAtCar`：**不碰** `ControlState`，所以成功；
- `PacketDriveControl.runServer` → `new ControlState()`：第一次需要这个类 → 读 jar → 炸 → 整条包被丢弃；
- 服务端的 `canTakeMmtrControl` / `applyMmtrControl` 从来没被调用过 ⇒ override 恒为 0 ⇒ 车当然不动。

**这不是运动限制，是类加载失败。** 其余"看起来一样"的服务端限制见 §4。

## 3. 做了两件事（一个护栏 + 三条日志）

### 3.1 护栏：`scripts/sync-engine.ps1` 拒绝在 looom 进程运行时同步

```powershell
$running = Get-CimInstance Win32_Process -Filter "Name='java.exe' or Name='javaw.exe'" |
  Where-Object { $_.CommandLine -match 'devlaunchinjector\.Main' }
if ($running) { throw "拒绝同步：还有 loom 开发进程在跑…" }
```

要强行换 jar 得显式 `-Force`（明确承担风险）。这与 `check-java-compile.ps1` 头部的告警同源
（那条讲的是 `gradlew compileJava` 会动 `build/classes`），只是这次踩的是 `game/libs/*.jar` 这条路径 ——
**两条路径都必须在进程停止时才动**。

### 3.2 日志：三类"按了没反应"不再静默

| 日志 | 什么时候打 | 为什么必须默认可见 |
|---|---|---|
| `[MMTR-DRV] 操纵被拒：车=… 理由=…` | 驾驶包被准入判据拒（不是司机位 / 无任务 / 占用锁） | 三种拒绝在客户端**长得一模一样** |
| `[MMTR-DRV] 手柄语义不匹配：车=… 本车底是 NOTCHED…` | 客户端送 `driveHandle`，但车底没有三手柄规格（`carTypeIds` 没配 / 配置改了没重启） | 控制器读 `throttleNotch`，`driveHandle` 被无声忽略 |
| `[MMTR-DRV] 车底解析：车=… 说话的车=br101\|br101_three_handle\|true → br101_three_handle/THREE_HANDLE` | 车底解析结果变化时（含"谁都没配 → 用维度缺省"） | 决定这台车用哪套操纵语义，是排查第一步 |
| `[MMTR-DRV] driver=… engaged override T0 B0 R1 三手柄[油门=97 制动=0 定速=100]` | 操纵权建立（既有行，补上三手柄字段） | 确认"引擎真的收到手柄了" |

限频 2 s（理由变化立刻打），并且**不放在 `mmtr.trace` 开关后面**：它们属于"人正在试图开车但没开成"的状态类消息。

## 4. 服务端真正会拦住车的判据（重启后按这个顺序查）

| # | 判据 | 看什么 |
|---|---|---|
| 1 | **类加载**（本次） | 日志里有没有 `Failed to load class file` / `ZipException`；有 ⇒ 停服、重新同步、重启 |
| 2 | **车底控制模式** | `[MMTR-DRV] 车底解析：…` 那一行必须是 `…/THREE_HANDLE`；若是 `NOTCHED` ⇒ `carTypeIds` 没配上（键是资源包车型 id，BR101 v54 包 = `br101`）或服务端没重启 |
| 3 | **操纵准入** | `[MMTR-DRV] 操纵被拒：理由=…`；三种理由各自怎么修见下表 |
| 4 | 运动层 | `motion … waiting for turnout authority` / `authority halt` / `endOfLine` / SPAD 保护 —— 这类是**进路/信号/停点**层面的停车，日志会点名（与"手柄无效"不同：车会显示已收到操纵但不动） |
| 5 | 任务闸门 | `mmtrRequireTaskToDrive`（T4）：开着则"无任务不得操纵"，理由行会直接说 |

拒绝理由 → 修法：

| 理由 | 含义 | 修法 |
|---|---|---|
| `请求者不在司机位上（ride 包的 isDriver 为假）` | 客户端没报"我是司机"，或座位判据没落在驾驶室 | 看客户端 `MmtrDriverSeat`（位置判据 = 最近的风挡锚点）与 `[MMTR-DRV] client seated at …`（需 `mmtr.trace`） |
| `另一名司机正持有操纵权（占用锁…）` | 别人先动手了，且他还在司机位上 | 让他走开，或自己走到另一端的驾驶室（占用锁按"人"不按"端"） |
| `无任务不得操纵（T4 闸门…）` | 服务端开了"无任务不得操纵" | 给车派任务，或关掉该策略 |

## 5. 重启的正确顺序（本次的处置）

```bat
:: 1) 停掉 dev server 与 dev client（两个 java 进程）
:: 2) 重新同步引擎 jar —— 现在它会在"进程还在跑"时直接拒绝
mmtr\scripts\sync-engine.ps1
:: 3) 再起 server / client
```

引擎全量 **753 通过 / 0 失败 / 5 跳过**（本次只改诊断与护栏，未动物理）。

## 6. 遗留

1. 诊断日志的限频是"每辆车每 2 s 一条"：同一辆车被两个人抢、或两类消息交替时会各打一条（可接受）；
2. `sync-engine.ps1` 的检测靠 `devlaunchinjector.Main` 关键字（loom 的开发启动器）；若将来换启动方式
   （如 `run` 目录下的 `java -jar`），这条护栏要跟着改 —— 判据写在脚本里，一处；
3. 客户端侧同样读这个 jar，所以**客户端也要重启**；本次只提示，不强制。

## 7. 第二次"车不动"：配置装在错的目录（同一批日志的第二条真因）

修完 jar 之后重启，车**还是不动** —— 但这次新加的诊断一行就定位了：

```
[MMTR-DRV] 车底解析：车=-8484453616098281161 说话的车=（谁都没配） → emu_8_notched/NOTCHED
[MMTR-DRV] 手柄语义不匹配：车=-3749722016069463122 本车底是 NOTCHED（emu_8_notched），
           没有三手柄规格：接收到的油门手柄/定速不驱动它（油门手柄=97 定速=25）
[MMTR-HLTH] … mmtrOverrides=1 …        ← 免钥匙那条路是通的：手柄确实到了引擎
```

即：**准入没问题、手柄也没丢，是车底类型不对**（`driveHandle` 被 NOTCHED 控制器无声忽略）。

### 真因：`apply-consist-config.ps1` 只装 `run\saves`，而 dev server 读 `run\world`

引擎自己的日志给出了权威路径：

```
[MMTR-DBG] dimension=minecraft/overworld savePath=.\world\.\mtr\minecraft\overworld
           config=.\world\.\mtr\minecraft\overworld\mmtr-consist-types.json
```

loom 的 `runServer` 工作目录是 `game\fabric\run\`，世界在 **`run\world\`**；而脚本默认 `SavesRoot=run\saves`
（存档目录）。更糟的是脚本的逻辑是"**文件已存在就跳过**"：

```powershell
if ($hasRails) { if (-not $hasConfig) { Copy-Item … } else { 'already present' } }
```

于是 `run\world` 里那份 **2026-09-05** 的老配置（三种车底、没有 `carTypeIds`）永远拿不到新条目 ——
我前两轮改的一直是 `saves\新的世界\...`（另一个世界），服务端一眼都没看过。

### 修法

1. **`scripts/apply-consist-config.ps1` 重写**：
   - 默认同时覆盖 `run\world` 与 `run\saves`（不再是只装存档）；
   - **增量合并**而不是"存在就跳过"：缺哪个车底就补哪个（按 `id` 认）、`carTypeIds` 按 key 合并、
     `defaultConsistTypeId` 只在原文没写时补 —— 现场调过的参数一律不覆盖；`-Force` 才整份覆盖；
   - 选择器不按目录层级硬判（两个位置的层级不同），只认路径里有 `\mtr\` 且非 `.bak`。
2. 跑一遍合并：**6 份配置**（`run\world` × 3 维度 + `saves\新的世界` × 3 维度）全部带上
   `br101_three_handle` 与 `carTypeIds.br101`，JSON 逐个可解析、无 BOM。
3. 重启服务端（**配置只在启动时读，没有热加载命令**；这次是纯配置改动，**不需要动 jar**）。

### 教训（写进 §4 的判据表）

- "配置改了没生效"优先怀疑**装到别的地方去了/被跳过**，而不是先怀疑引擎没读；
  引擎自己打印的 `config=…` 路径就是权威答案；
- 诊断日志的价值在这一轮体现得很直接：从"车不动"到"车底解析成 NOTCHED"只用了**一行日志**。
