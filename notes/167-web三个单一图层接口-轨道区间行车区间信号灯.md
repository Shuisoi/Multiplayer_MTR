# 167 = Web 三个"单一图层"接口：轨道区间 / 行车区间 / 信号灯状态（灯的显示只读它自己的绑定）

> 触发（2026-09-15，用户）：
> 1. 「现在给 web 暴露接口，用于指示轨道区间，行车区间，信号灯状态。然后道岔这件事是如何处理的？」
> 2. 「然后需要将行车区间状态**绑定至信号灯**上。」
>
> 状态：**已实施**（引擎侧）。契约用例 `SystemMapSectionApiTests`；
> 模型与取舍见 `docs/01-设计/闭塞区间-两层模型-设计.md` §4.1–§4.3。

## 1. 为什么是"一层一个接口"，而不是一个综合包

原来的 `/mmtr-sections` 是"区间图层"的综合包：`sections[]`（有方向）＋ `byRail[]`（**多值**：
一根轨属于好几个区间）＋ `trackSections[]`（无方向）。三份东西挤在一个响应里，前缀还都叫 `mmtr`，
于是**同一个词指三种东西**（"区间"到底是哪一层？），网页侧只能靠约定去猜。实测吃过一次真实破损：
控制台一直在读引擎**已经不发的** `node.block` 字段 —— 服务端看不出来，前端静默画不出来。

所以拆成三层、字段含义只有一种：

| 接口 | 图层 | 单位 | 关键字段 |
| --- | --- | --- | --- |
| `GET /mtr/api/map/mmtr-track-sections` | **L1 轨道区间** | **占用判定单位**（无方向、双向共用） | `id / length / occupied / spans[{hex,from,to,points[]}]`；顶层 `count / busyCount / railCount` |
| `GET /mtr/api/map/mmtr-block-sections` | **L2 行车区间** | **授权单位**（有方向、灯到灯、跨轨） | `id / entrySignal / exitSignal / next / aspect / occupied / length / direction{angle,label,dx,dz} / uncovered / members[] / memberCount / spans[{hex,from,to,dirOfTravel,reachable,points[]}]`；顶层 `count / busyCount / lampCount` |
| `GET /mtr/api/map/mmtr-lamps` | **信号灯状态** | **每盏灯的绑定** | `key / x,y,z / angle / aspects / mode / target / boundExplicit / aspect / occupied / unbound / section / sections[] / nextSections[] / protectedRails[]`；顶层 `count` |

`/mmtr-sections` **保留**（运营台在用），但它不再是新代码的入口。

## 2. 三条"网页不必自己算"的约定

1. **`points[]` 是成对的 `x,z`**（一段弧窗采 9 个点）：区间可以落在**一根轨的一段**上（灯把轨切开），
   所以点必须按弧窗取，不能整根轨画。前端不必实现 MTR 的轨道数学。
2. **`members[]` 把两层连起来**：这一段行车区间由**哪些 L1 段**拼成 —— 占用是在 L1 判定、再扩大上来的
   （notes/166 裁定），所以"这一段为什么被占"能追到具体是哪一段轨。
3. **`uncovered` / `unbound` 是"不画成正常"的信号**：
   - `uncovered=true`（补出来的**无灯大区间**，没有入口灯）⇒ 画"无信号区段"，**绝不能当绿灯画**；
   - `unbound=true`（守不到任何轨）⇒ 画"未知"，`aspect` 为空，也不给一个"看起来正常的绿"。

## 3. 灯的显示：绑定在**它开的那一段**上

用户第 2 句裁定的落地：`/mmtr-lamps` 读的是 `MmtrSectionService.lampBindings(...)`
—— **每一盏灯都读同一份绑定**（它开的段 + 那些段的占用 + 由段状态推出的显示），
不再按灯的 `target` 轨去查 per-rail 表。

删除的那条回路：`getMmtrSignals` 原来对 `BOUND` 灯走 `computeRailAspectMap(...)`（按轨查颜色）——
"灯脚下那根轨被占 ⇒ 这盏灯红灯"是**错的**（该读的是它开的段）。现在灯与段是**一对一/一对多**的
（一灯多腿时 `sections[]` 多条、取最不利显示），与 `lamps` 指令、与游戏内灯色**同一份结论**。

## 4. 道岔在这三个接口里的位置

区间层不定义道岔，只如实反映它的三个后果（见设计文档 §4.3）：

- **L1 划分**：段不能分叉 ⇒ 度 ≠ 2 的节点必然收口（`/mmtr-track-sections` 上看得到这个收口，但没有"道岔"字段）；
- **L2 走行**：岔口跟**每一条朝前腿**走（"一盏灯守整个咽喉"）；设了 MAIN 进路则收窄到进路那条腿；
  道岔当前位置**禁行**的那条腿照样在守卫集合里，但标 `reachable=false`（**守着、但不判断路**）；
- **显示（④）**：岔区清限区（每根汇入轨靠近节点的 10 m）里有车，或该岔口没人定 ⇒
  这些节点的区间当**占用**（红）；
- 道岔自己的权威（谁持有 / 什么时候扳 / 扳到哪一位）在 `MmtrPointAuthority` / `MmtrTurnout` / 进路表，
  **不出现在这三个接口里**（另见 `/mmtr-points`、`/mmtr-junction-legs`）。

## 5. 实施中发现并修掉的缺陷（R1）

**无灯大区间在所有 feed 里都不见了。** `sectionViews(...)`（`/mmtr-block-sections`、`/mmtr-sections`、
区间图都读它）只遍历 `sectionsBySignal` —— 而补出来的无灯大区间是按"窗口"生成的，**没有入口灯可作键**，
所以从来没进过那张表。后果：

- `/mmtr-block-sections` 上的 `uncovered` 字段**永远读不到 true**（死分支）；
- 无灯的世界在网页上等于"一段区间也没有"，而按用户裁定那里应该是**一整块大区间**。

修法：`sectionViews` 末尾如实追加无灯区间，`aspect` 给空串（无灯就没有显示）。
用例：`MmtrTotalSectionTests.everyPlaceHasOneTotalSectionWhoseGeometryIsTheTrackSection`
（无灯走廊 ⇒ 一条总区间、两条 cover、两条都是无灯、`aspect` 为空）。

## 6. 实施中发现的第二个缺陷（R2）：jar 里内嵌的那份控制台**永远不会更新**

`engine/build.gradle.kts` 的 `setupWebserver` 只声明了 `outputs.file(WebserverResources.java)`、
**没有声明前端产物是输入** —— 于是这个任务第一次生成过那个文件之后就一直 UP-TO-DATE。
后果：重新 `npm run build` 之后，jar 里内嵌的控制台**还是旧的**（实测：dist 是 09-16 13:48 的，
而 `WebserverResources.java` 停在 09-15 13:38，重新 `shadowJar` 只花了 1 秒、什么都没做）。

- 开发时看不出来：本机跑的是**磁盘上的 dist**（`-Dmmtr.web.root=<dir>` / `MMTR_WEB_ROOT`，见 `Main.resolveWebRoot`），
  只有**发布包**（没有那个属性）才走内嵌那份。
- 修法：`inputs.dir("website/dist/website/browser")`。修完 `setupWebserver` 会在 dist 变化时重跑
  （实测：重跑后 `WebserverResources.java` 里出现了新图层的字符串）。

## 7. 第三个缺陷（R3）：**游戏端的动词在网页指令栏里根本敲不到**

`tracks` / `lamps`（以及这轮加的 `totals`）住在**游戏端**的 `MmtrCommandExecutor` 里 —— 它只在
"有指令被 push 过来"时跑（`signals scan`、以及连挂/换端那些 packet 会 push）。而**网页指令栏**走的是
`mmtr-command` 的默认分支 = **引擎侧**的 `MmtrCommandDispatcher`（名词打头：`vehicle` / `train` /
`signal` / `point` / `manifest` / `query` / `world` / `server`）。所以：

```text
POST mmtr-command {"command":"totals"}  →  不认识的名词「totals」
```

**真机实测就是这样**（我按游戏端那条加完之后，从网页发过去得到上面这句）。补法是在引擎侧加**同名同义的**
`query totals`（与既有的 `query sections` / `query topology` 并列），并补两条用例
（`MmtrQueryTotalsCommandTests`）。规矩：**要在网页指令栏里用得上的诊断，必须落在引擎分发器里**；
游戏端那套只服务于"只有游戏端做得到"的事（枚举已加载区块等）。
