# 346 · 工作区里的可执行文件跑在 **Low 完整性**沙箱里（2026-09-29 实测）

日期：2026-09-29 · 承接 notes/281（"gradle 老说 UP-TO-DATE"那类怪事的真根因）

## 0. 一句话

**DSH 的沙箱把"镜像位于工作区内的一切可执行文件"以 Low 完整性令牌运行（`S-1-16-4096`）；
Low 只能写工作区（工作区是低标签），写不了 `%APPDATA%` / `%LOCALAPPDATA%` / `%USERPROFILE%\.gradle`。**

这一条同时解释了三件以前各自以为是"别的毛病"的事：

| 现象 | 真因 |
|---|---|
| `gradlew` 起手 `FileNotFoundException: ...gradle-8.14-bin.zip.lck（拒绝访问）` | wrapper 是 JVM（`env\jdk-21`）⇒ Low ⇒ 写不了 `%USERPROFILE%\.gradle\wrapper\dists` |
| IDEA 起不来：`AccessDeniedException: ...\JetBrains\IdeaIC2025.2\.lock` + `Permission denied: bind` | `idea64.exe` 住在 `env\idea\bin`（工作区内）⇒ Low ⇒ 写不了 `%APPDATA%`/`%LOCALAPPDATA%\JetBrains` |
| 目录 ACL / 陈旧锁看着"像权限坏了" | **ACL 完全干净**（用户对那两个目录是 FullControl，`Get-Acl` 实测），跟权限无关 |

## 3. 修法（全部只用工具自带的"改家目录"能力，不动沙箱、不动 ACL、不写工作区外一个字节）

1. **JVM 的"家"搬进工作区** —— `env\workspace.env.ps1` / `.bat`（单一真源，客户端与 IDEA 一起生效）：
   - `GRADLE_USER_HOME=%MC_ROOT%\sandbox\gradle-home`（wrapper 发行版 145 MB 已复制进去）
   - `GRADLE_RO_DEP_CACHE=%USERPROFILE%\.gradle\caches`：既有的依赖缓存**只读复用**，不复制
   - `TEMP`/`TMP=%MC_ROOT%\sandbox\tmp`：`java.io.tmpdir` 跟着走
   - loom 自己的缓存 `caches\fabric-loom`（**1 GB**）用 `robocopy /E /MT:16` 搬进 `sandbox\gradle-home\caches\`
     （`Copy-Item -Recurse` 只搬了 44 MB —— 这种大而深的树一律用 robocopy）
2. **IDEA 的家搬进工作区** —— 新增 `bin\_prepare-idea-home.bat`，由 `打开-Game-工程.bat` /
   `打开-Engine-工程.bat` `call`：
   - 建 `sandbox\idea-home\{config,system,log,tmp}`；首次运行把 `%APPDATA%\JetBrains\IdeaIC2025.2`
     **只读复制**过来（观感/插件不变，顺带删掉复制过来的陈旧 `.lock`）
   - 生成 `idea.properties`（config/system/log/plugins 四条，值用**正斜杠**——Java properties 里反斜杠是转义）
   - 生成 `sandbox\idea-home\env.cmd`，入口脚本 `call` 它来设置 `IDEA_PROPERTIES` / `TEMP` /
     `GRADLE_USER_HOME` / `GRADLE_RO_DEP_CACHE`，然后才 `start idea64.exe`
3. **清掉旧会话的产物**：`mmtr\game\build`、`mmtr\game\fabric\build`、`mmtr\game\.gradle\{8.14,buildOutputCleanup,vcs-1}`
   （旧文件虽然多数可写，但上面那个 `problems-report.html` 已经拒绝过一次，清掉最省事；`loom-cache` 保留）

## 5. `.bat` 三条教训（都是本轮踩出来的）

1. **内容必须纯 ASCII**：`.bat` 里放 UTF-8 中文（加不加 BOM 都一样，配 `chcp 65001` 更糟）会让 cmd 丢字节偏移、
   把注释行碎片当命令执行（报错长这样：`'va.nio.file.AccessDeniedException:' is not recognized`）。**文件名可以中文**（运行时数据）。
2. **`if (...)` 块里 echo 的圆括号会打断块解析**（`- was unexpected at this time`）⇒ 小脚本一律用标签 + `goto`。
3. **`endlocal & set "VAR=..."` 在 `call` 场景下不可靠**（本机实测变量没进调用者环境）⇒
   改成"脚本生成 `env.cmd`，调用方 `call` 它"。

## 7. ★ 不要给 IDEA 设 `GRADLE_USER_HOME`（本轮踩的坑）

**IDEA 的 Gradle 侧本来不受这个沙箱影响**：实测它的守护进程/工具链 JDK 是
`C:\Users\…\.gradle\jdks\eclipse_adoptium-21-amd64-windows.2\bin\java.exe` —— **在工作区之外 ⇒ High、不受限**，
`IDEA` 日志里也是 `GradleManager - Instructing gradle to use java from C:/Users/…/.gradle/jdks/…`。
所以 IDEA 应当继续用原来的 `%USERPROFILE%\.gradle`（那里 loom 的东西都是齐的、昨天就是好的）。

**坑**：我一开始在 `sandbox\idea-home\env.cmd` 里也给 IDEA 设了 `GRADLE_USER_HOME=<工作区>`，后果有两个：

1. IDEA 的 Gradle sync 只能去用**那个还没养好的工作区 home** ⇒ 用户看到"Gradle 读不到项目"；
2. IDEA 会在**自己的进程里**加载工作区 home 下的
   `native\<hash>\windows-amd64\native-platform.dll`（`Get-Process -Module` 实测），
   于是命令行的 gradle（同一个 home）报 `Could not initialize native services. > Could not extract native JNI library.`，
   底层是 `FileNotFoundException: …native-platform.dll（另一个程序正在使用此文件）` —— **两个"世界"抢同一个 home**。

⇒ 正确分工：
| 使用者 | JVM 来自 | Gradle home | 说明 |
|---|---|---|---|
| **IDEA**（用户起，`idea64.exe` 在工作区内 ⇒ **只有它自己被关**） | `~/.gradle/jdks/…`（工作区外 ⇒ 不受限） | **原来的 `%USERPROFILE%\.gradle`** | 只需要重定向 IDEA 自己的 config/system/log/temp |
| **命令行**（`dev-client.ps1` / `check-*` / AI 代跑；JVM = `env\jdk-21` ⇒ **被关**） | 工作区内 ⇒ Low | `sandbox\gradle-home` | 必须搬进来，且别和 IDEA 同时跑 |

`bin\_prepare-idea-home.bat` 生成 `IDEA_PROPERTIES` / `TEMP` / `TMP` / `GRADLE_USER_HOME` / `JAVA_HOME`
五条（**2026-09-29 17:4x 修正**：`GRADLE_USER_HOME` 与 `JAVA_HOME` 后来加回来了，见 §8）。

### 7.1 结论：**命令行 gradle 与 IDEA 的 gradle 不要同时用**

两者会抢同一批**工程内**输出（`mmtr/game/build`、`mmtr/game/.gradle/loom-cache`、`fabric/build`）：

- IDEA 的 Gradle **不受限**（JVM 来自 `~/.gradle/jdks/…`）⇒ 它写出来的文件是 Medium/High；
- 命令行的 Gradle（`env\jdk-21`）**受限**（Low）⇒ **改不动** IDEA 写出来的那些文件，报
  `java.nio.file.ReadOnlyFileSystemException`（zipfs 打不开写就退化成只读，栈里是
  `MinecraftJarMerger.add` → `createDirectories`），loom 于是说 `Could not merge JARs! … please re-run`；
  反过来，IDEA 能覆盖命令行写的文件（不往上写不受限制）。

⇒ **以 IDEA 为准**：起客户端用 IDEA 的 run 配置（`mmtr/game/.idea/runConfigurations/Minecraft_Client___fabric__fabric.xml`）。
命令行只跑**不依赖 gradle** 的检查（`check-java-compile.ps1`、`check-paths.ps1`、`glslcheck`、`sodium-terrain-probe`）。
`env\workspace.env.*` 里的 `GRADLE_USER_HOME=<工作区>` 保留给"必须在受限侧跑 gradle"的场合
（`dev-client.ps1` 等），但**用之前先确保 IDEA 没有在构建**，并且必要时先删掉不受限侧写下的旧产物。

## 8. ★★ 修正（2026-09-29 17:4x）：IDEA **必须**设 `GRADLE_USER_HOME`，§7 的立论是错的

## 9. ★★ 更深的坑（2026-09-29 17:5x 实测）：工作区里 `Files.isWritable()` 对 Low 恒为 false

修完 `.lck`（§8）之后，sync 走得通了，但构建停在 loom 的 JAR 合并：

```
Could not merge JARs! Deleting source JARs - please re-run the command and move on.
java.nio.file.ReadOnlyFileSystemException
  at jdk.zipfs/jdk.nio.zipfs.ZipFileSystem.checkWritable(ZipFileSystem.java:370)
  at jdk.zipfs/jdk.nio.zipfs.ZipFileSystem.createDirectory(ZipFileSystem.java:708)
  at java.base/java.nio.file.Files.createDirectories(Files.java:753)
  at net.fabricmc.loom.configuration.providers.minecraft.MinecraftJarMerger.add(MinecraftJarMerger.java:151)
  at net.fabricmc.loom.configuration.providers.minecraft.MergedMinecraftProvider.mergeJars(MergedMinecraftProvider.java:111)
```

### 9.1 实测：不是"写不了"，是"写权限探测被判否"

同一个目录、同一个类，只换 JVM 的镜像路径：

| 路径 | `env\jdk-21`（Low） | 工作区外 JDK（High） |
|---|---|---|
| `MC\` | `isWritable=false` | `true` |
| `sandbox\` | `false` | `true` |
| `sandbox\gradle-home` | `false` | `true` |
| `sandbox\gradle-home\caches\fabric-loom` | `false` | `true` |
| `mmtr\game`、`mmtr\game\build`、`sandbox\tmp`、`sandbox\idea-home` | `false` | `true` |

**整棵工作区无一例外。** 但**真的写是成功的**：同一个 Low JVM 里
`Files.write(fresh, …)` → OK，`new RandomAccessFile(f, "rw")` → OK，Gradle 能把
daemon 日志/registry 写进 `sandbox\gradle-home`。

⇒ 这是**权限探测**这一项被 DSH 的 ACE 组合判否（工作区根上有继承下来的
`Everyone:(I)(CI)(DENY)(DC)`，而 `S-1-4-*` 的工作区授权只给 `(W,D,DC)`）。
不是标签问题：**Low 自己刚创建的文件，问 `isWritable` 也返回 false**。

### 9.2 为什么这能把整个构建打死

`jdk.nio.zipfs` 在 `newFileSystem()` 时会问一句底层文件/目录能不能写，
答否就**把整个 zip 文件系统标成只读**（`isReadOnly=true`），之后任何写操作都直接抛
`ReadOnlyFileSystemException` —— 与真实权限无关。最小复现：

```java
Path zip = dir.resolve("fresh.zip");
FileSystems.newFileSystem(URI.create("jar:" + zip.toUri()), Map.of("create","true"))
  .getPath("net/minecraft/util") … Files.createDirectories(…);   // Low ⇒ ReadOnlyFileSystemException
```

`create=true` 与 `create=false`（对已存在的 zip）**都**失败，所以
"先把 jar 拷进去、让 loom 走已存在的分支"这条路**也不通**。

受害面不止 loom：**任何用 zipfs 的东西**（JAR/ZIP 任务、`jar:` 文件系统、部分 Gradle 内部
产物处理）在工作区里都可能踩到。本工程目前踩到的是 `MinecraftJarMerger`。

### 9.3 因此**不要**用"搬缓存"绕

从工作区**外面**（High 的 PowerShell / robocopy）把 `minecraft-client.jar` /
`minecraft-merged.jar` 拷进 `sandbox\gradle-home\caches\fabric-loom\1.20.4\` 是**无效**的，
而且会让人误判"是文件标签的锅"。实测两轮：拷进去 → loom 判定要合并 → 照样
`ReadOnlyFileSystemException`；清空重下 → 同样。**根因是目录探测，不是文件。**

### 9.4 结论：**换令牌，但 home 要留在工作区内——两半缺一不可**

**路径可以在工作区外，但令牌也必须来自工作区外。** 三种组合实测（同一份代码）：

| JVM 镜像 | 目标目录 | 普通写 | zipfs 写 |
|---|---|---|---|
| 工作区内（Low） | 工作区内 | OK | **FAIL** `ReadOnlyFileSystemException` |
| 工作区内（Low） | `%USERPROFILE%\.gradle` | **FAIL** `AccessDeniedException` | FAIL |
| **工作区外（High）** | `%USERPROFILE%\.gradle` | OK | **OK** ✅ |

注意 `isWritable=false` **不是**判据：连工作区外的 `.gradle` 和 `%TEMP%` 对 Low 也是 false
（是常量）。真正的判据只有"实际写"。

⚠ 把工作区外的 JDK **复制**进工作区没用——标签跟**镜像路径**走（§1），
`env\jdk-21\bin\java.exe` 就是 Low。要的是**在工作区外执行**那个 JDK。

⚠ `-Dorg.gradle.java.home` **确实**能指定 daemon JVM（实测 daemon 命令行里就是它），
所以**不要**把它写成工作区内的路径，否则 daemon 立刻变 Low，改撞
`%USERPROFILE%\.gradle\native\…\native-platform.dll.lock（拒绝访问）`。

**最终落地（两半，各治一层）**：

| 要治的 | 药 |
|---|---|
