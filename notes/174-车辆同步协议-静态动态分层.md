## 1. 立项前先量出来的四个数（都在 dev 世界上实测）

| 量 | 实测 |
|---|---|
| 一份 `VehicleUpdate` 的 JSON | **3,470 字符 ≈ 3.5 KB**（单节车、1 条 path） |
| `VehicleExtraData.copy(0)` | **54–60 µs/次**（实现是 **JSON 反射序列化 + 重新解析**：`new VehicleExtraData(new JsonReader(Utilities.getJsonObjectFromData(this)))`） |
| `copy()` 的**调用位置** | `Vehicle.java` 的 **"每辆车 × 每个可见客户端"** 循环里 → 10 个客户端看见同一列车就做 10 次**与客户端无关**的深拷贝 |
| 上行（客户端→服务端） | 移动中每 **0.5 s** 一个 `DataRequest`，里面带**"我已经有什么"的全量 id 列表**，其中 `existingRailIds` 是**字符串数组**（每条轨 hex ≈100 字符）⇒ 159 轨的世界约 **32 KB/s/人** |

三个结构性问题：①每次更新重发整份（其中九成是路线名/站名/终点/编组/path/限速这类**静态**字段）；
②线格式是 JSON 文本；③上行的 id 列表每 0.5 s 全量重传。

## 2. 这一轮做了什么：**两档同步**（notes/174 的核心）

```
客户端第一次看到这辆车 / 静态字段变了  →  整份快照（vehiclesToUpdate，建立镜像，含重建渲染缓存）
只有动态字段变了                        →  稀疏补丁（vehiclesToPatch，客户端原地合并）
什么也没变                              →  保活 id（vehiclesToKeep）
```

- **判据方向是刻意的**：`VehicleSyncPatch` 列的是**允许走补丁的动态字段白名单**，
  **没列到的一律当静态** ⇒ "漏字段"的后果是**多发一份快照**（慢一点），而不是
  "客户端某个字段永远停在旧值"（静默错，这个项目被咬过多次的那种）。
- **兜底**：每辆车每 **30 秒**强制发一次整份（`FULL_RESYNC_MILLIS`），
  于是白名单万一漏了东西，偏差最多存在 30 秒而不是永久。
- **客户端零新逻辑**：合并用的是 `VehicleExtension.updateData(JsonObject)` ——
  上游当初为"部分更新"留的那个口（此前是**死代码**，本轮第一次被用起来）。
- **`ridingEntities` 刻意留在整份那档**：客户端收到上下车要重建 `EntityHelper.HIDDEN_PLAYERS`
  与乘客插值（只在整份那条路上做），为它走补丁等于把省下的又花回去；而上下车是"每站一次"量级。

### 实测（真实车辆，同一次"停车点变了"）

```
[VEH-SYNC] 同一次「停车点变了」: 整份快照=3249 字符  vs  稀疏补丁=33 字符
           补丁内容={"data":{"stoppingPoint":1234.5}}
```

**约 100×**（3,249 → 33 字符）。再加上：

- `copy()` 出了客户端循环（**每辆车每脏 tick 一次**，所有可见客户端共享同一份）⇒
  CPU 省下"可见客户端数"倍；
- 静态没变时**不再深拷贝**（补丁不经过 `copy()`）；
- 线格式仍是既有那条 JSON 通道（`DynamicDataResponse`），**没有新增包、没有新增 op key**，
  所以这一层是"数据模型分层"，将来要把线格式换二进制只动传输、不动协议语义。

## 3. 用例（引擎侧，修完回归后 725/0/4）

`VehicleSyncPatchTests`（11 条）：

| 用例 | 钉住什么 |
|---|---|
| `anUnchangedSnapshotProducesAnEmptyPatch` | 没变 ⇒ 不发（不是"发整份"） |
| `aDynamicChangeProducesAPatchWithOnlyThatField` | 补丁里**只有**变了的那个字段 |
| `bothSectionsCanCarryAPatchAtOnce` | `vehicle`/`data` 两段各自只带变了的字段 |
| `aStaticChangeForcesAFullSnapshot` | 路线名/车列长度/限速变了、以及"从没发过" ⇒ 整份 |
| `aDisappearingFieldForcesAFullSnapshot` | 字段消失不猜语义 ⇒ 整份 |
| **`applyingThePatchEqualsApplyingTheFullSnapshot`** | **等价性**：补丁合并出来的状态 == 整份快照逐字段相同 |
| `everyFieldTheEngineTreatsAsDirtyIsInTheWhitelist` | 引擎 `checkForUpdate()` 认的字段必须在白名单（`ridingEntities` 是写明的例外） |
| `staticFieldsAreNotInTheWhitelist` | 明显静态的字段**不许**走补丁 |

## 4. 还没做（下一轮，按收益排）

1. **上行那 32 KB/s/人**：`DataRequest` 里 `existingRailIds` 等改成**每类一个 hash/版本**，
   服务端自己记"我给这个客户端发过什么"（`Client` 已经在那里）⇒ 稳态上行趋近 0，
   不匹配时才全量重传。**这是现在最大的一笔**，且与下行协议互不干扰。
2. **线格式换二进制 / 量化**：包缓冲（`Mapping` 那层）只有 `writeInt/Long/Double/String` 原语、
   **没有字节数组**，所以要么"Base64 套 msgpack"（+33%），要么把动态记录写成**定长原语序列**
   （~30 个数字 + 长度前缀字符串，约 120–150 B）。现在的 33 字符补丁已经很小，优先级低于第 1 条。
3. **频率与 LOD**：远车降频（客户端本来就在本地积分位置，快照只是校正），
   以及 `updateRadius`（现在是**客户端渲染距离 × 16 格**）分级。
4. **`VehicleUpdate` 里仍偏大的静态块**（3.2 KB/车/次，只在首次或换交路时发）：
   若要再压，可把 `path` 只发一次、或把静态块也切进二进制。

## 5. 实机验收清单（换 jar 之后）

1. 启动服务端 + 客户端（**两端必须同版本**：这是协议变更，旧客户端不认得 `vehiclesToPatch`）；
2. 车库里派一趟车，确认列车**照常显示、照常移动**（静态块 + 补丁都必须生效）；
3. 站台停车 → 开门 → 关门 → 起步：确认**门与停车点**（这几个是补丁字段）跟着变；
4. 上下车：确认玩家在车上看不到自己（`HIDDEN_PLAYERS` 那条路，走整份）；
5. 连挂/解挂（车列长度变）：确认**不崩、渲染正常**（这条必须走整份，是会重建渲染缓存的那条路）；
6. 关掉开关再跑一次：`-Dmmtr.sync.patches=false` 应当回到"每次都发整份"的旧行为（出问题时的一键回退）。

## 6. 实机回归（2026-09-16 当晚）：**补丁车被客户端删掉了**

上线后用户报「**客户端看运行中的车辆很卡**」。根因是**我漏了一条**，而且症状与原因离得很远：

- 客户端镜像有一条硬规则：**"这一条消息里没出现的车，就删掉"**
  （`PacketUpdateVehiclesLifts.updateVehiclesOrLifts` 里的
  `dataSet.removeIf(data -> !keepIds.contains(data.getId()))`，删的时候还会
  `VehicleExtension::dispose` 掉按节数缓存的渲染数据）。
- 而我把补丁车只放进了 `vehiclesToPatch`，**没放进 `vehiclesToKeep`** ⇒ 客户端**每收到一次补丁就把那辆车
  删掉并 dispose 渲染缓存**，直到 30 秒后的兜底整份才回来 —— 画面上就是"车一亮一灭、非常卡"。

**修法**（引擎侧一行，客户端不用改）：补丁**隐含保活** —— `Client.processVehicles` 在发补丁时
同时 `addVehicleToKeep(id)`。协议语义写成一句话：**"补丁 ⇒ 这个客户端仍然持有它"**。

**红证**：新增 `ClientVehicleSyncTests`（`org.mtr.core.data`）两条，先跑成红的那一条正是
`★ 补丁车必须同时在保活列表里 … expected: <1> but was: <0>`；修完 725/0/4 全绿。第二条钉的是
"车出视野 → 引擎发一条空消息（客户端据此删）→ 再回来必须发**整份**"（发补丁会静默丢更新）。

### 顺手修掉的另一处潜在崩溃（同一条链路）

写用例时抓到：`VehicleExtraData.copy(pathUpdateIndex)` 在 **path 为空**的车（比如还没排班的车底）上
会 `path.get(0)` 抛 `IndexOutOfBoundsException` —— 而它跑在**同步路径**上，异常被 tick 外层那个
`catch (Throwable)` 接住，**中断本 tick 剩下的全部工作**（不是"这条同步失败"，是"这一 tick 废掉"）。
改成 `i >= path.size()` 时不再取元素；行为对非空 path 逐位不变。

### 一条教训（写给下一次改协议）

"发什么"错了，**症状会长在另一端**：这次是"服务端少发一个 id 列表" → "客户端画面上车闪断"。
所以协议层必须有**组成层**的用例（这次补上了：主表 / 补丁表 / 保活表三者的关系），
而不能只测"补丁内容对不对"。

### 顺手撞出来的两条（都值得记）

1. **运行中替换 `game/libs` 的 jar，症状是"任何非空指令都挂住"**（本轮我自己踩的：`sync-engine.ps1`
   在服务端还在跑时覆盖了那个 jar）。现象很有迷惑性 —— 空指令（`{"command":""}`）225 ms 正常返回，
   而 `query totals` / `server stop` 一律 20 s 超时、什么也不发生；**停机标记也写不出来**，
   于是"优雅停机"这条路也断了，只能硬停。干净重启后同一条 `query totals` **335 ms** 正常返回。
   机理：JVM 的 jar 句柄指向被替换过的文件，**懒加载**的类读到错位字节。
   ⇒ 与 note/77 那条红线一致，补充它的**症状描述**：不是崩溃，而是"指令静默挂起"。
2. **引擎自己的 `log.*` 在模组里全部不可见**（实测：`Loading files` / `Server started with dimensions` /
   `loaded rolling-stock manifest` / 网页慢任务 warn / `[MMTR-SRV]` 五个特征串在服务端日志里**各 0 条**，
   而同为引擎输出的 `System.out.println` 行 `[MMTR-HLTH]`/`[MMTR-DBG]`/`[MMTR-MSG]` 都在）。
   机理：引擎 shadow 时把 `org.*` 整体重定位成 `org.mtr.libraries.org.*`，而打包进模组后
   **log4j 的 provider 找不到**（启动日志里有 `main ERROR Log4j API could not find a logging provider`）。
   ⇒ 后果是所有引擎侧的诊断日志（包括 notes/172 里那条"网页任务花了多少毫秒"的 warn）在现场都是哑的。
   **本轮的对策**：把"这一轮跑的是哪套协议"放进 `[MMTR-HLTH]`（System.out，能看见）。
   **建议的修法**（没做）：让模组把重定位后的 log4j-core 一起打包，或者给引擎加一个
   `System.out` 的桥（两者都比现在"日志看起来正常、其实全丢"要好）。
