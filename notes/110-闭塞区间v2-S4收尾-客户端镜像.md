# 110 - 闭塞区间 v2 · S4 收尾：客户端镜像（灯 → 显示）

> 承接 notes/109（引擎显示接线）。本片把 **引擎的 v2 结论送到客户端**，客户端渲染器按**灯**取数。
> 至此 **S4 全部完成**（引擎 + 客户端镜像/链）。

## 1. 问题与接法

- 引擎的 v2 是**按灯**的：一盏灯 = 一条有向区间 = 一个显示；
- 客户端渲染器是**按轨**的：它站在一个信号方块上，收集该节点朝向前方的那几根轨，再走链算深度；
- v1 的按轨读法在"同一根轨上两个方向属于不同闭塞"时必然出错（这正是 v2 要修的）。

**接法（选它而不是让客户端重走一遍区间）**：引擎把**自己的结论**按灯推过去，渲染器用**自己所在的方块坐标**查表。

理由：`RenderSignalBase` 手里本来就有 `blockPos`，而引擎注册灯用的就是方块坐标
（`MmtrCommandExecutor.scanSignals` 用 `pos.getX()/getY()/getZ()`，`SignalEntry.x/y/z` 原样保存）。
两边键一致 → **不可能不一致**，客户端也不需要复制任何走行/收窄逻辑（否则就是第二份真相）。

## 2. 交付

| 层 | 件 |
| --- | --- |
| 引擎 | `MmtrDirectionalBlockService.lampAspectNames(trees, restrictedNodes)` → `{灯key → RED/SINGLE_YELLOW/DOUBLE_YELLOW/GREEN}`；`depthAt` / `aspectName` 抽出复用（`describeLampAspects` 与它同源） |
| 镜像推送 | `MmtrRouteMirror`：每 tick 取 `lampAspectNames`，**并入原有签名**（变化才推），随 `PacketMmtrRoutes.contentOf(...)` 第五个参数发出 |
| 线格式 | `PacketMmtrRoutes`：新增 `lamps` = 扁平 `[灯key, aspectName] * n`；`runClientInbound` 解析后交给 `MmtrClientRoutes.update(..., lampAspects)` |
| 客户端存储 | `MmtrClientRoutes`：新增 `lampAspect(int x, int y, int z)` / `lampAspectCount()`；`clear()` 一并清空；防御性拷贝 |
| 渲染 | `RenderSignalBase.mmtrEngineAspect(pos, localDepth)`：**引擎有结论就用它**（RED→1 / SINGLE→2 / DOUBLE→3 / GREEN→0），没有（该灯不在 v2 区间里）就退回本地按轨链的读数 —— 无灯区段逐位不变 |

## 3. 用例与验证

| 项 | 结果 |
| --- | --- |
| 引擎全量 | **512/0/2**（未变：本片引擎侧只加了查询方法） |
| fabric 全量 | **22/0**（原 21，新增 1 例） |
| 新用例 | `MmtrClientRoutesTests.theEnginesPerLampAspectIsMirroredAndLookedUpByBlockPosition`：空镜像时返回 null（渲染器保持本地读数）、按方块坐标命中、未发送的灯返回 null、防御性拷贝、`clear()` 清空 |

## 4. 注意事项（实机目视的前提）

客户端 JVM 必须与服务器**同一 jar 版本**才能看到变化 —— `dev-client` 是要连服务端的那一端，
改了引擎/fabric 之后**客户端也要重启**。服务端侧本轮已同步并重启。
