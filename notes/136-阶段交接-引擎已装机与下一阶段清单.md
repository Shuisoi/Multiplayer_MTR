## 3. 🔴 新发现：一辆车**被自己的持有卡死**（下一阶段第一件事）

> **现状更新**：那辆车（在 `aassdd`）已按用户要求**连车带厂一起删掉**了，
> `point why -212 -60 -159` 现在报 `物理持有者 = （没有）` —— 死锁当场消失（删车会释放它的持有）。
> 但**缺陷本身没修**：下个阶段只要有车"先按了某个位置、又需要另一个位置"，同样的死锁会重演。
> 所以这条仍然是下一阶段第一件事。

现场（重启后仍然存在，观察了 3 分钟以上没变化）：

```
车 8431887902004786548（车场 aassdd / 股道 -5385228036074278397，调车任务 MANEUVER，SYSTEM 驾驶）
  head=(-211.5,-124.5)  速度 0  授权 RED  停在出发信号前
  进路状态 PENDING，planStale=true，reason：
    "物理道岔 -212,-60,-159 被 v8431887902004786548 按在位置 1（岔股开放），
     本车需要位置 0（正线贯通）—— 两条进路互斥"

point why -212 -60 -159：
  结论：单开道岔 —— 根部 (-212,-178) / 正线远端 (-212,-125) / 岔股 (-220,-125)
  物理位置 = 1，物理持有者 = v8431887902004786548，等待队列 = []
```

**持有者就是它自己**（v + 自己的车辆 id）。于是：

- `MmtrRouteRegistry` 看到"物理位置 1 ≠ 本车需要 0" → 判定进路拿不到 → 车停在出发信号前；
- 而 `Simulator.mmtrThrowTurnoutForIntent` 的第一道闸门是
  `物理持有者 != 无 → 不扳`（第 1006 行），**没有"持有者就是我"这一条豁免** → 谁也扳不动它。

结果是一处**死锁**：车的旧授权把道岔按在位置 1 且没有释放（它没跨过那处岔就停/被重新调度了），
新计划要位置 0，而联锁因为"有人物理持有"拒绝扳岔 —— 包括持有者本人。

**为什么这是下一阶段必须先解决的**：任务/时刻表阶段会反复"到达岔前 → 要另一个位置"，
只要有一处遗留持有，车就永远停在那儿。三条可能的修法（留待决策）：

1. `mmtrThrowTurnoutForIntent` 对**请求方本人**豁免物理持有闸门（同一 owner 可以改自己按的位）；
2. 车辆计划被替换/取消时**释放它的物理持有**（现在只在跨过岔口或清空净空区时释放）；
3. 两条都做：豁免是为了能改，释放是为了不留垃圾。

**注意安全性不能因此丢掉**：第三道闸门（`MmtrJunctionState.blockedThrowReason`：车压在岔区上不扳）
是独立的一条，豁免第 1006 行不会把道岔从车底下抽走。

**现在就能用的手动解法**（没擅自执行，等用户决定）：

```
point release -212 -60 -159 --via=<根部轨 hex> --owner=v8431887902004786548
```

注意 `point release` 是释放**车辆申请/持有**，`point unlock` 解的是**人工锁**，两者不是一回事。
