## 0. 一句话

设计的核心是**两段式**：**服务计划**（趟次表，与车无关，乘客看的）与**车底运用**（趟次分给哪辆车）。
P1 把"输入层"立起来（**持久化的是输入，计划永远是算出来的**），P2 把第一段算出来。
这两片合起来回答"几点几分发哪一趟"，而"哪辆车去跑"是 P3。

```
P1 输入层（持久化）         P2 服务计划（纯函数）              P3 车底运用
线路 / 密度 / 车底    →    趟次表：车次 × 发车 × 各站到发 × 终点处理   →   每辆车一天的完整任务序列
```

## 1. P1 输入层：`MmtrLine` / `MmtrPattern` / `MmtrFleet`（设计 §4）

新增包 `org.mtr.core.mmtr.plan`：

| 类 | 内容 | 关键判据 |
| --- | --- | --- |
| `MmtrLine` | `lineId` / `name` / `stops[]{stationId, platformId, dwellMillis}` / `terminalTreatment{CHANGE_ENDS\|TURNBACK\|STABLE}` / `loop` / `yardSidingId` / `leadTimeMillis` | **站序闭合性**：环线必须首尾同站同台；非环线**不许**首尾相同（"忘了勾 loop"的典型写法，放过去会生成一条永远不折返的交路） |
| `MmtrPattern` | 每线路一张：`segments[]{fromMillis, toMillis, headwayMillis}`（当天毫秒） | 重叠 / **未覆盖运营时段** / `headway<=0`；判据一律按**排序后相邻两段**（`prev.to > next.from` 重叠、`<` 是空档），所以作者写乱序也不会误报 |
| `MmtrFleet` | `consists[]`（套班）/ `spares[]`（替补，不排班）/ `vehicleCount`（声明车辆数）；编组内容**复用** `MmtrCarSpec` | `requiredConsists(ring, 高峰间隔) = ceil(ring/间隔)`；`validateCapacity` = **P1 验收 ③**（不够就跑不起来，加载期就报，点名"需要 N / 现在几个 / 缺几个"） |
| `MmtrPlanInputs` | 持久化根：`lines[] / patterns[] / fleet`，`<存档>/<维度>/mmtr-plan.json` | 三层校验：① 各自结构 ② **交叉引用**（线路上有密度表、密度表指向存在的线路、线路有出库股道） ③ "够不够跑"（要 ring，见下） |

**为什么"够不够跑"要单独一层**：ring（周转）= 往程走行 + 停站 + 终点处理 + 返程走行 + 停站 —— **走行时间要算轨图**，
所以 P1 只提供纯计算 `requiredConsists` / `validateCapacity(lineId, ringMillis)`，由 P3 把真实 ring 接进来；
P1 的用例显式传 ring（与 P3 接线后的调用形状一致）。**输入层不猜走行时间**，这是"纯函数核心"这条边界的直接推论。

**持久化方向的翻转**（设计 §1.2 的原话落地）：`mmtr-jobs.json` 持久化的是**任务本身**（手工作业单），
`mmtr-plan.json` 持久化的是**输入**。计划不落盘 ⇒ 改一个密度段，整天的趟次立刻重算，不会出现
"文件里的计划和配置对不上"。

**接口**（引擎 servlet 挂在 `/mtr/api/map/*`，所以按既有惯例给 `mmtr-plan*`；设计文档里写的是
REST 风格的 `/mtr/api/mmtr/plan/*`，这是同一批能力的两种写法，映射记在这里）：

```
GET  mmtr-plan                  → { lines, patterns, fleet, errors[], valid }
POST mmtr-plan-line-upsert      ← 线路对象（同 lineId 覆盖）
POST mmtr-plan-pattern-upsert   ← 密度表对象
POST mmtr-plan-fleet-upsert     ← 车底对象
POST mmtr-plan-line-delete      ← { lineId }（连带它的密度表）
```

写进去就回 `{ok, problems, errors[]}` —— **不在保存成功时回一个空洞的 ok=true**：坏配置当场看得见，
与"加载即报错"同一个口径（加载时把每条问题逐行写进服务端日志，`log.error`）。

## 2. P2 服务计划：`MmtrServicePlan`（设计 §5.1）

- `MmtrTravelTimes` 是**接口**：生成器不认识轨图，走行时间由调用方喂（P3 用 `MmtrRunPlanner` 的距离 +
  编组限速造实现；用例用 `uniform(legMillis, terminalMillis)` 造等速假世界）。
- `generate(line, pattern, times)` = 按密度段**左闭右开**展开发车槽位 → 每槽一趟，
  逐站累计"前站开车 + 走行 → 到点 → + 停站 → 开点"，终点处理另计（`terminalDoneMillis`）。
- `ringMillis(line, times)` = 往程 + 停站 + 终点处理 + 返程 + 停站（环线不计终点处理），
  返程按同一张腿表**反向**取，所以不对称线路也算得对。

### v1 的范围（写清楚，免得后人以为是漏了）

1. **只生成起点方向的发车序列**（`Trip.Direction.OUT`）。反方向的乘客时刻表是它的镜像
   （同样的间隔、偏移一个往程走行时间），乘客视图归 P6 的 WEB 页；"出去再回来"的返程已经算进 ring，
   由 P3 排进车底序列。
2. `Trip.Direction.BACK` 这个枚举值先留着（P3 排返程趟时用），P2 不生成。

## 3. 测试账（P2 验收四条逐条对上）

`MmtrPlanInputTests`（10 例）—— P1 三条：
① 落盘→读回**逐字段**一致（含嵌套车卡与段；另有一条 JSON 字符串解析与文件路径结果一致）；
② 四条校验各自报错：重叠（点名压在哪段时间）/ 未覆盖（点名空档）/ `headway<=0`（0 与负数）/
站序不闭合（**两个方向都测**：环线首尾不同、非环线首尾相同）；外加结构+交叉引用一批
（站数、负停站、没出库股道、没密度表、指向不存在的线路、车底为空）；③ 车底不足点名
"需要 N / 现在几个 / 缺几个 / 替补不算在套班里"，外加"ring 未知不误报"。

`MmtrServicePlanTests`（6 例）—— P2 四条：
① 07:00–08:30/5min + 08:30–10:00/3min **逐条**断言（18 + 30 = 48 趟，07:00…09:57）；
② 08:30 **只出现一次**且属后一段、序列严格递增、末班不越过 10:00；
③ 各站到发逐站手算核对（A 07:00→07:00:30、B 07:04:30→07:05:15、C 07:09:15→07:09:45、终点处理到 07:12:45）；
④ 环线每趟首尾同站、末趟终点 = 首趟起点、环线不计终点处理。另有 ring 手算核对与"坏段不生成无穷多趟"。

## 4. 本轮踩到的两处（都是自己的错，记下来免得重犯）

1. **`@Nullable` 标注位置**：`static @Nullable MmtrLine.Stop` 被判"无法用 type-use 批注批注确定作用域结构"，
   要写成 `static MmtrLine.@Nullable Stop`（限定嵌套类型时的写法）。
2. **用例里的手算错了两次**（`ceil(22.5/5)=5` 写成 4、四站环线按 4 段算），
   两次都是**断言替我把账算清**——这正是"先写期望值再写实现"的价值，不是浪费。
