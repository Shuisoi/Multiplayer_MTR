> 用户决定："**首先把原逻辑删除干净，然后慢慢构建新逻辑**"。
> 本文是执行前的依赖面清点与删除清单（紧接 `notes/184` 的现状分析）。
>
> 目标：**删到只剩一个空壳 + 能编译 + 能进游戏**，然后在新地基上重建。

---

## 1. 为什么不能"直接删文件"

`VehicleRidingMovement` 是 MTR 渲染管线的**必需件**（不是 MMTR 加的），被 73 处引用。
若整类删掉，MTR 原版渲染路径（`RenderVehicles` / `RenderLifts` / `MainRenderer` /
`DrivingGuiRenderer` / `VehicleExtension`）全部编译不过 —— 连"车都看不到"。

**所以"删干净"的正确形态是：保留 API 外壳，掏空行为。**

```
保留：类名 + 公开方法签名（全部变成 no-op / 中性返回值）
删除：所有 private static 状态、所有内部逻辑
```

这样得到一个**可编译、可进游戏、但完全不能上下车**的地基 ——
正是"从零重建"想要的起点，而且每一步都留下一个能验收的检查点。

## 5. 两个待你决策的点

### 决策 1：G 键"进驾驶室"这一层，本轮一起删吗？

| 选项 | 含义 | 后果 |
|---|---|---|
| **A. 一起删**（我倾向） | 删掉 `MmtrCabInteraction` 的认领/释放/对账 + `findAimTarget` + `placeAtCabView` | 最干净；但驾驶室相关的 HUD/权限/钥匙那套全部停用，重建时要一起做 |
| B. 先留 | 只删它的"写 riding"部分（`mmtrPlaceRiding` 等），保留认领与 HUD | 会留下"认领了但人不在车上"的半死状态，**正是这一轮的病根**，不推荐 |

### 决策 2：电梯（`RenderLifts`）怎么办？

| 选项 | 含义 |
|---|---|
| **A. 一并不动**（我倾向） | 电梯乘坐也停用（它共用 `startRiding`/`movePlayer`），与列车一起重建 |
| B. 给电梯单独留一条旁路 | 工作量大，且会把刚清空的 API 又搞复杂 |

## 6. 重建路线（清空之后再谈，先列骨架）

清空后的地基上，按"每步可验收"重建：

| 步 | 内容 | 验收 |
|---|---|---|
| **B1** | `RideSession` 对象 + 单一所有者 + 客户端状态机（OUTSIDE/INSIDE/CAB） | 能上车能下车，能走动，视角跟随 |
| **B2** | 入口：按 G 进驾驶室（锚点座位） + 走到门口自动上（锚点半径） | 两个入口有明确优先级，不互抢 |
| **B3** | 车内走动：只用资源包盒子做碰撞；**Y 只解析一次** | 走动正常，不再有"三种 Y" |
| **B4** | 门外下车：潜行、走到站台 | 下车单一出口 |
| **B5** | 与引擎对接：`PacketUpdateVehicleRidingEntities` + `ridingEntities` + 钥匙归属 | 服务端认可司机身份；驾驶可用 |
| **B6** | 驾驶 HUD / 面板 / 雨刷联动 | 回到本轮之前的可见功能 |

> 每一步都保留"能进游戏"的状态，避免再出现"一轮改 10 版、无法定位"的局面。
