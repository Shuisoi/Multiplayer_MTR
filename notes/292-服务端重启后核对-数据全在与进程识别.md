# 292 · 服务端重启后的收尾核对：数据全在，客户端已重新拉起

> 触发：后台任务 `pwsh-26`（`dev-client.ps1`）报完成。顺着查下去，发现是**服务端被重启过**，
> 而不是客户端自己出事。这篇把"重启/恢复"这条链路的事实钉下来，并记一个**进程识别的假警报**。

## 1. 到底发生了什么

| 时刻 | 事件 | 证据 |
| --- | --- | --- |
| 15:22 | 服务端第 1 轮启动（PID 17360） | `dev-server.out.log` |
| 16:26:21 | **引擎收到重启请求** | `[MMTR-SRV] restart marker written: …\run\mmtr-restart.request` + `shutdown requested, will stop in 2s` |
| 16:26:23–24 | 优雅停机 | `Stopping server` → `Saving players/worlds` → `All dimensions are saved` → `Thread RCON Listener stopped` |
| 16:26 | 第 1 轮 gradle 退出 | `BUILD SUCCESSFUL in 1h 4m 1s` |
| 16:26:2x | 启动器读到重启标记 | `pwsh-21`：`检测到重启标记（restart requested at …），3 秒后再启动一次…` → `=== 启动服务端（第 2 轮）===` |
| 16:27:03 | 服务端第 2 轮起来（PID 40624） | 8888 / 25565 / 25575 三端口都由它持有 |
| 16:28:00 | 客户端也重新起来了（PID 31820） | 16:28:14 `Sound engine started`（主菜单） |

**判据**：重启标记被启动器消费掉了（`run\` 下现在**没有** `mmtr-*.request` 残留），
且三端口都有人应答 —— 与 notes/286 §3 记的那套口径一致（"8888 上有人应答才算起来了"）。

## 2. 重启后数据全在（这才是本轮真正有价值的验证）

引擎的路网数据是从磁盘重读的，所以**重启 = 一次真实的持久化考试**：

| 项 | 重启前 | 重启后 |
| --- | --- | --- |
| 轨道 | 44 | **46** |
| 信号灯 | 36 | **36**（全部 `模式=AUTO`） |
| 道岔 | — | **28** |
| 区间 | — | **48** |

多出来的 2 条轨 + 4 盏灯是**用户自己加的**：两条牵出线南端（z≈292）的出口信号门架，
立柱 `(-109,65..67,292)` / `(-100,65..67,292)`，灯头在 y=67、z=291 朝南 / z=293 朝北。
（与 notes/291 那 16 套的差别：那套是 y=70 的高门架、灯头挂在轨正上方；这套是地面柱、灯头挂在柱顶。）

> 顺带发现一处**语义问题**（不是 bug，是几何）：两条牵出线目前**在 z=292 就是死头**，
> 所以朝南那个灯头"面朝方向上没有腿"，引擎退回全部腿，和朝北那个**落到同一段 50 m**
> （`(-107,242)→(-107,292)`）。等牵出线往南延伸出去，朝南那盏才会真正守到新轨。

## 3. ⚠️ 假警报：`gradlew` **包装进程**与游戏 JVM 会被误认成两套

排查时看到"两个 SERVER + 两个 CLIENT"，一度以为重复启动了。逐条看命令行才明白：

```
PID 39140  "…java.exe" -Xmx64m -Xms64m -classpath …gradle-wrapper.jar org.gradle.wrapper.GradleWrapperMain :fabric:runServer
PID 40624  …在 8888/25565/25575 上监听的那个才是真服务端
PID 52176  "…java.exe" -Xmx64m -Xms64m -classpath …gradle-wrapper.jar org.gradle.wrapper.GradleWrapperMain :fabric:runClient
PID 31820  …真正在跑游戏的客户端（工作集 1.6 GB）
```

**判据（记下来，别再被骗）**：

- 包装进程：堆只有 `-Xmx64m`、工作集 ~100 MB、CPU 近乎 0、类名是 `GradleWrapperMain`；
- 真游戏 JVM：命令行里含 **`KnotClient` / `KnotServer`**、工作集 GB 级、CPU 会涨；
- **端口归属是最终裁判**：`Get-NetTCPConnection -LocalPort 8888` 的 `OwningProcess` 就是服务端真身。
