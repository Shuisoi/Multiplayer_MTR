# 339 · 车体光照粒度：**别人是怎么做的**（NTE / Create / 上游）

日期：2026-09-28 · 承接 `notes/338`（MTR 车辆渲染管线）。
本轮只回答一件事：**"一辆车/一节车整体一个亮度"这件事，生态里别人是怎么处理的？有没有现成答案可以捡？**

结论先行：

1. **NTE（MTR 生态里唯一自研过车辆渲染器的模组）的做法和 MTR 4 一模一样** —— 一节车一个采样点一个光值；
2. 而且 **MTR 4 的"优化渲染器"就是 NTE 的 Sowcer 上游化** —— 这个限制是**血缘继承**的；
3. **但 NTE 把"每次 draw 带自己的 light"这个机制留出来了**，并且已经在贯通道上实践过（外皮用世界光、内装用全亮）
   ⇒ 我们想做的"分段/分部件各自取光"**在这个生态里有先例、是被验证过的机制**；
4. **更彻底的样本是 Create 的可移动装置**：它把可移动结构按**方块**重新烘焙（逐顶点光 + AO），
   并把材质的 `CardinalLightingMode.ENTITY` **强制改成 `CHUNK`**；
5. **上游 MTR 没有把这件事当成问题**（按 title 搜 issue/PR 无相关条目），没有现成补丁可捡。

## 1. NTE：和 MTR 4 一字不差

`RenderTrainD51.renderCar(...)`（[源码](https://github.com/zbx1425/mtr-nte)，`render/train/RenderTrainD51.java`）：

```java
final BlockPos posAverage = applyAverageTransform(train.getViewOffset(), x, y, z);
...
final int light = LightTexture.pack(
        world.getBrightness(LightLayer.BLOCK, posAverage),
        world.getBrightness(LightLayer.SKY,   posAverage));
...
modelD51.updateAndEnqueueAll(MainClient.drawScheduler, updateProp, pose, light);
```

- 采样点是 `applyAverageTransform(...)` 的**平均位置**（对应 MTR 的"节中心"），
- 得到**一个** `light`，交给整节车的模型 enqueue。

⇒ 与 MTR 4 的 `PositionAndRotation.getLight()` + `vehicleResource.queue(..., light, ...)` 是同一种设计。
**没有可捡的答案。**

### 1.1 为什么一样：同一个血缘

NTE 自带 `cn.zbx1425.sowcer` / `cn.zbx1425.sowcerext`；MTR 4 的 `org.mtr.mapping.render.*` 与它**逐类对应**：

| NTE（Sowcer） | MTR 4（mappings jar） |
|---|---|
| `sowcer/batch/BatchManager`（三个桶 + `RenderCall`） | `render/batch/BatchManager` |
| `sowcer/batch/MaterialProp` / `ShaderProp` / `EnqueueProp` | `render/batch/MaterialProperties` / `VertexAttributeState` |
| `sowcer/vertex/VertAttrMapping` / `VertAttrSrc` / `VertAttrState` | `render/vertex/VertexAttributeMapping` / `VertexAttributeSource` / `VertexAttributeState` |
| `sowcer/object/VertArray` / `VertBuf` / `IndexBuf` | `render/object/VertexArray` / `VertexBuffer` / `IndexBuffer` |
| `sowcerext/reuse/DrawScheduler` / `AtlasManager` / `ModelManager` | （调度在 `OptimizedRenderer`）/ `render/obj/AtlasManager` |
| `TrainModelCapture` + `SowcerModelAgent` | `OptimizedModel` + `CapturingVertexConsumer` |
| `sowcerext/multipart/animated` + `script/*` | `ModelPropertiesPart` 的动画/条件机制 |

⇒ **MTR 4 的"优化渲染器"是 NTE 的实验成果上游化**（NTE 是 MTR 贡献者 Zbx1425 的实验性扩展模组，
wiki 明说"把稳定的部分稍后合并入 MTR 本体"）。所以"整节车一个光值"不是 MTR 4 新引入的缺陷，
而是**从 NTE 那套批渲染架构里继承下来的性质**（`UV_LIGHTMAP` 是 GLOBAL 属性）。

来源：[NTE 仓库](https://github.com/zbx1425/mtr-nte) · [NTE wiki](https://wiki.minecrafttransitrailway.com/zh-tw:mtr_addon:nte:start)

## 2. ★ NTE 留出来的机制：**每次 draw 带自己的 light**

`render/scripting/AbstractDrawCalls.java`：

```java
public static class ClusterDrawCall {
    public void commit(DrawScheduler drawScheduler, Matrix4f basePose, int light) {
        Matrix4f finalPose = basePose.copy();
        finalPose.multiply(pose);
        drawScheduler.enqueue(model, finalPose, light);
    }
}
```

`render/scripting/train/TrainDrawCalls.java`：

```java
public void addCarModel(int car, ModelCluster model, Matrix4f pose) { ... }         // 只登记，不带光
public void commitCar(int car, DrawScheduler ds, Matrix4f basePose, Matrix4f worldPose, int light) {
    for (ClusterDrawCall c : carDrawLists[car]) c.commit(ds, basePose, light);
}
```

并且在该文件的 `commitConnImmediate(...)` 里**已经按部位给了不同的光**：

```java
VertexConsumer vertexConsumerExterior = vertexConsumers.getBuffer(MoreRenderLayers.getExterior(tex));
drawTexture(..., light);                       // 外皮：世界光
int lightOnLevel = LightTexture.FULL_BRIGHT;
VertexConsumer vertexConsumerSide = vertexConsumers.getBuffer(MoreRenderLayers.getInterior(tex));
drawTexture(..., lightOnLevel);                // 内装贯通道：全亮
```

⇒ **"同一节车里不同部位亮度不同"这件事，NTE 的解法就是"拆成多次 enqueue，每次带自己的 light"**。
这与我们提的"分段/分部件，各自取光"是同一个机制 —— **有先例，不是拍脑袋**。

> **逐层调用链、`VertAttrSrc` 五档、帧剖析器、细节距离、以及"照搬到 MMTR"的清单，见文末 §7。**

## 3. 更彻底的样本：Create 的可移动装置

`content/contraptions/render/ContraptionVisual.java`（1.20.1 / Flywheel）：

```java
// ① 按世界重新烘焙成"方块模型"（带 AO 与逐顶点光）
var model = new ForgeBlockModelBuilder(modelWorld, blocks.positions())
    .modelDataLookup(clientContraption::getModelData)
    .materialFunc((renderType, shaded, ao) -> {
        Material material = ModelUtil.getMaterial(renderType, shaded, ao);
        if (material != null && material.cardinalLightingMode() == CardinalLightingMode.ENTITY) {
            return SimpleMaterial.builderOf(material)
                .cardinalLightingMode(CardinalLightingMode.CHUNK)   // ★ 别用实体光照，用方块光照
                .build();
        } else return material;
    })
    .build();
```

```java
// ② 实现 ShaderLightVisual：把装置包围盒外扩 1 格涉及的所有 section 报给光影管线
public class ContraptionVisual<E extends AbstractContraptionEntity> extends AbstractEntityVisual<E>
        implements DynamicVisual, TickableVisual, ShaderLightVisual {
    protected int lightPaddingBlocks = DEFAULT_LIGHT_PADDING;   // = 1
    public void setSectionCollector(SectionCollector collector) { ...; checkAndUpdateLightSections(); }
}
```

**这里给出了这个问题在引擎层面的正式名字**：

| 概念 | 含义 | 谁在用 |
|---|---|---|
| `CardinalLightingMode.ENTITY` | **一个实体一个采样点**，逐面/整体同亮度 | 原版实体、**MTR 的车辆**、NTE 的车辆 |
| `CardinalLightingMode.CHUNK` | **方块光照**：逐顶点、带 AO 与平滑过渡 | 世界方块、**Create 的装置** |

⇒ "整节车一起亮"本质是 **ENTITY 光照被用在一个 20 米长的物体上**。
Create 的答案是**不用 ENTITY 光照**，而是把可移动结构当成方块几何重新烘焙。

来源：[ContraptionVisual.java](https://github.com/Creators-of-Create/Create/blob/mc1.20.1/dev/src/main/java/com/simibubi/create/content/contraptions/render/ContraptionVisual.java) ·
[Contraption Rendering（DeepWiki）](https://deepwiki.com/Creators-of-Create/Create/3.5-contraption-rendering)

## 5. 三条路各自在别人那里的先例

| 方案 | 别人做过吗 | 代价 / 阻塞点 |
|---|---|---|
| ① 只换采样点（整节仍一个值） | 无先例（等于没解决"粒度"） | 1 行 |
| ② **分段 / 分部件，各自 enqueue 带自己的 light** | ★ **有** —— NTE 的 `DrawScheduler` + `ClusterDrawCall.commit(..., light)` 就是这么设计的；NTE 已在贯通道上实践（外皮世界光 / 内装全亮） | 1 段 = 1 次 draw，**无材质切换**（同桶连续画）；须绕开 `PartCondition` 合并键（notes/338 §6） |
| ③ 逐顶点光（真正的 CHUNK 光照） | ★ **有** —— Create 的 contraption（按方块重烘焙 + AO + section collector） | 我们的顶点格式 `UV_LIGHTMAP: GLOBAL` 在**预编译的 mapping jar** 里，改不了 ⇒ 要拿 Minecraft-Mappings 源码自编，或自写渲染器 |

**取舍建议**：先做 ②（照 NTE 的机制），不碰 mapping jar、无材质切换、机制在同生态里已验证；
③ 虽然 Create 证明可行，但它要求我们拥有渲染器源码与自建顶点管线，是另一个量级的工程。

## 7. 附录：NTE 渲染架构逐层详解（照抄用）

读的是 NTE `master`（MTR **3** 时代；类名 `cn.zbx1425.sowcer.*` / `cn.zbx1425.mtrsteamloco.*`）。
MTR 4 已把这套上游化并改名，见 §1.1 的对应表。

### 7.0 全景调用链（`TrainRendererBase.renderCar` → `glDrawElements`）

```
MTR3 RenderTrains
└─ TrainRendererBase.renderCar(carIndex, x, y, z, yaw, pitch, doorLeftOpen, doorRightOpen)
   │  ← MTR 3 本来就留了"可插拔车辆渲染器"这个接口，NTE 插在这里
   ├─ ScriptedTrainRenderer.renderCar(...)                        render/scripting/train/ScriptedTrainRenderer.java
   │  ├─ posAverage = applyAverageTransform(train.getViewOffset(), x, y, z)   ← 平均位置（同时是可见性判据）
   │  ├─ worldPose（车在世界里的位姿） / drawPose（含父矩阵）
   │  ├─ light = LightTexture.pack(world.getBrightness(BLOCK, posAverage),
   │  │                             world.getBrightness(SKY,   posAverage))   ← ★ 一节车一个光值
   │  └─ scriptResult.commitCar(carIndex, MainClient.drawScheduler, drawPose, worldPose, light)
   │       └─ TrainDrawCalls.commitCar(...)
   │            for (ClusterDrawCall c : carDrawLists[car]) c.commit(ds, basePose, light)
   │              └─ DrawScheduler.enqueue(model, finalPose, light)
   │                   drawCalls.add(new ClusterDrawCall(model, pose, light))  ← ★ 光随【每一次 enqueue】入队
   └─（帧末）DrawScheduler.commit(vertexConsumers, drawContext)    sowcerext/reuse/DrawScheduler.java
        for (call : drawCalls) call.model.enqueueOpaqueGl(batchManager, call.pose, call.light, ctx)
          └─ ModelCluster.enqueueOpaqueGl(...)                     sowcerext/model/ModelCluster.java
               batchManager.enqueue(uploadedOpaqueParts, new EnqueueProp(
                   new VertAttrState().setColor(255,255,255,255).setOverlayUVNoOverlay()
                       .setLightmapUV(AttrUtil.exchangeLightmapUVBits(light))   ← ★ 光变成"全局顶点属性"的值
                       .setModelMatrix(pose)
               ), ShaderProp.DEFAULT)
                 └─ for (VertArray va : model.meshList)
                        batches[(materialProp, shaderProp)].add(new RenderCall(va, enqueueProp))
        DrawScheduler.commitRaw → BatchManager.drawAll(shaderManager, ctx)      sowcer/batch/BatchManager.java
```

### 7.1 光是怎么变成画面上的亮度的

`VertAttrState.applyGlobal()`（`sowcer/vertex/VertAttrState.java`）：

```java
case UV_LIGHTMAP:
    if (lightmapUV == null) continue;
    GL33.glVertexAttribI2i(attr.location, (short) (lightmapUV >>> 16), (short) lightmapUV);
```

配合 `VertAttrMapping.setupAttrsToVao`：`GLOBAL` 源 → `attrType.toggleAttrArray(false)`（**关掉数组**，用常量值）。

⇒ 光是一次 draw call 的**常量通用顶点属性**，不是逐顶点数据。
**一个 draw 只能一个光值** —— 与 MTR 4 的 `UV_LIGHTMAP: GLOBAL` 完全同构。

### 7.2 ★ NTE 比 MTR 4 多出来的四样（值得抄）

**① 属性来源可配：`VertAttrSrc` 五档**（`sowcer/vertex/VertAttrSrc.java`）

```java
public enum VertAttrSrc {
    GLOBAL,                 // 只在 MaterialProp / EnqueueProp 里 —— 每 draw 一个常量
    VERTEX_BUF,             // 在顶点 VBO 里 —— 逐顶点
    VERTEX_BUF_OR_GLOBAL,   // 给了 global 就用 global，否则读顶点
    INSTANCE_BUF,           // 在实例 VBO 里 —— 逐实例
    INSTANCE_BUF_OR_GLOBAL; // 同理
}
```
`VertAttrMapping.Builder` 默认全部 `VERTEX_BUF`，再逐项覆盖。

⇒ **"逐顶点光 / 逐实例光"在 NTE 是配置项，在 MTR 4 是写死的 `GLOBAL`。**
这就是为什么同样想做"真逐顶点光照"：NTE 改 mapping，MTR 4 得改源码（而源码在预编译 jar 里）。

**② 实例化渲染**：`InstanceBuf` / `VertArrays` / `InstancedRailChunk`（"立體軌道"就是实例化画的），
`VertAttrMapping` 里有独立的 `strideInstance` / `INSTANCE_BUF_OR_GLOBAL`，`DrawContext` 里还单列 `instancedFaceCount`。

**③ 帧剖析器是一等公民**（`sowcer/util/DrawContext.java`）

```java
public int drawCallCount, batchCount, singleFaceCount, instancedFaceCount, blazeFaceCount;
public void resetFrameProfiler() { /* 本帧/累计双缓冲交换 */ }
public void recordBatches(int n) { batchCountCF += n; }
public void recordDrawCall(RenderCall rc) { drawCallCountCF++; /* DEBUG 下逐 draw 记 "<material>: <faceCount>" */ }
```
⇒ 正好是"先量基线"要量的那几个量。**指标口径照它定：drawCallCount / batchCount / faceCount。**

**④ "细节距离"是一等公民**（`ScriptedTrainRenderer`）

```java
trainScripting.trainExtraWriting.isInDetailDistance |=
        posAverage.distSqr(camera.getBlockPosition()) <= RenderTrains.DETAIL_RADIUS_SQUARED;
```
把"这节车在不在细节距离内"作为字段交给渲染器/脚本，由它决定要不要画细节。

⇒ 正是我们上一轮提的**距离 LOD**（近处分段、远处整节一个光），NTE 已经把这个开关摆在台面上。

### 7.3 但要说清楚：NTE 的**策略**仍然是一节车一个光

`TrainDrawCalls.commitCar(car, ds, basePose, worldPose, light)` 的 `light` 是**整节车一次**传入，
摊给该节车的全部 draw call。NTE 只在贯通道上用到了"同一节车里两种光"
（外皮世界光 / 内装 `LightTexture.FULL_BRIGHT`，见 `commitConnImmediate`）。

**2026-09-28 补齐核实：NTE 的四个车辆渲染路径全是一车一光。**

| 路径 | 证据 |
|---|---|
| `RenderTrainD51.renderCar` | `posAverage` → 一个 `light` → `modelD51.updateAndEnqueueAll(drawScheduler, updateProp, pose, light)`（整车一个 multipart 模型一个光值） |
| `RenderTrainDK3.renderCar` | 同一个模式；**而且两个转向架也共用它**：`MODEL_BOGIE.render(matrices, vertexConsumers, light, ±bogiePosition)` —— 那两个转向架相距十几米 |
| `RenderTrainDK3Mini` | 继承 DK3，不改光照 |
| `ScriptedTrainRenderer.renderCar` | 一个 `light` → `commitCar(carIndex, drawScheduler, drawPose, worldPose, light)` |

**NTE 确实会切模型，但切分依据不是位置**：① multipart 语义（`StaticPart`/`AnimatedPart`/`MiPart` —— 轮、连杆、锅炉、门、乘务员）；
② 材质（`ModelCluster` 构造时分成 `opaqueParts` / `translucentParts`）。这些 draw 全部共用同一个光值。

⇒ 所以"**沿车长切段、每段各自取光**"在 NTE 里**没有先例**，是我们的设计。
我们能走通的原因是车型结构不同：NTE 的模型是语义 multipart，按 Z 硬切会跟动画部件打架；
我们的 OBJ 车体是一整块 `body`，按 Z 切是纯机械操作（打包器本来就要重写一遍 OBJ）。

### 7.3.1 ★★ 但"做不到"是错的：NTE 的机制**天然就是逐部件**的

`MultipartContainer.updateAndEnqueueAll`（`sowcerext/multipart/MultipartContainer.java`）：

```java
for (PartBase part : parts) {
    ModelCluster model = part.getModel(prop);
    if (model == null) continue;
    Matrix4f partPose = basePose.copy();
    partPose.multiply(part.getTransform(prop));      // ★ 每个部件有自己的位姿
    scheduler.enqueue(model, partPose, light);        // ★ 每个部件一次入队，light 是那次入队的参数
}
```

⇒ **NTE 本来就是"每部件一次 enqueue"**，`light` 已经摆在"逐部件参数"的位置上，
只是调用方 `renderCar` 把同一个整车光值传给了所有部件。

**NTE 要做分段/分部件光照 = 把那个常量换成"按 `partPose` 的世界位置采样"，几行代码，而且不需要切几何**
（每个部件已经是独立的 `ModelCluster`）。

**真正的差别在我们这一侧**：

| | NTE | MTR 4（我们） |
|---|---|---|
| 模型结构 | **multipart**：锅炉/驾驶室/煤水车/连杆/门… 本来就按位置分开 | 车体是**一整块 `body`**（`groupMap` 把 `car_body`+`buffers`+`bogies`+… 并成它），跨全车长 |
| 入队粒度 | **每部件一次 enqueue**，天然可分 | 按 `PartCondition` 把整车几何**合并成一个** `OptimizedModel`，每 condition 只发一次 |
| 做分段光照要改什么 | `updateAndEnqueueAll` 里 `light` 一行 | **① 几何必须切 ② 切完还得绕开 `PartCondition` 合并键**（走门/机制件那条独立 wrapper 路） |

⇒ 精确结论：**不是"别人做不到"，而是"别人有条件、没需要；我们有需要、还得多做一步切片"。**
机制上有参考（`enqueue(模型, 位姿, 光)` 两家完全同形），但**"切几何"这一步只有我们需要，没有先例**。

**可拆成两件独立的事**（代价与风险完全不同，可先后上、分别量）：

1. **免费的一半**：门 / 雨刷 / 内装 / 转向架**本来就是分开的部件** ⇒ "按部件取光"立刻可做；
2. **必须做的一半**：`body` 是一整块 ⇒ 16 段切片只能靠打包器按面心 Z 切。

⇒ 准确的结论：**NTE 提供了机制，但没有做过"沿车长分段取光"的实战。**
我们是第一个这么用它的人 —— 风险可控，因为这个机制本来就是为"每次 enqueue 一个光"设计的
（**光不参与批次键**，所以多段只多 draw、不多材质切换）。

### 7.4 照搬清单（映射到 MMTR 的类）

| NTE | MMTR 现状 | 结论 |
|---|---|---|
| `DrawScheduler.enqueue(model, pose, light)` | `OPTIMIZED_RENDERER_WRAPPER.queue(model, holder, light)` | 机制已有（`RenderVehicles:424/446/538`） |
| `ClusterDrawCall(model, pose, light)` / `EnqueueProp.attrState` | `VertexAttributeState(lightmapUV, matrix4f)` | 已有 |
| 批次键 `(MaterialProp, ShaderProp)` —— **不含光** | `MaterialProperties` —— **不含光** | 已有 ⇒ 分段只增 draw |
| `RenderCall.draw()` = bind + `applyGlobal()` + draw | 同名同形 | 已有 |
| `TrainDrawCalls`（每节一个 draw call 列表，`commitCar(..., light)`） | `VehicleResource.queue`（每节按 `PartCondition` 合成**一个** model） | ★ **改这里**：让每段成为独立 wrapper，各自 enqueue 带自己的光 |
| `TrainDrawCalls.addCarModel(car, model, pose)` 登记 / `commit` 带光 | 部件走 `ModelPropertiesPart.render` → `scheduleRender(TEXT)` | ★ 每段仿门/机制件那条路（`ModelPropertiesPart.java:211-224,415`） |
| `isInDetailDistance` + `DETAIL_RADIUS_SQUARED` | 无 | ★ 照它加"细节距离"：近处分段、远处退化成整节 |
| `DrawContext.drawCallCount / batchCount / faceCount` | 无 | ★ 照它加帧剖析，**先量基线再定段数** |
| `VertAttrSrc.VERTEX_BUF_OR_GLOBAL` | 固定 `UV_LIGHTMAP: GLOBAL` | 要做"真逐顶点光"才需要；需 rendering 层源码，**暂不做** |

## 7.5 ★ 这套架构的硬上限：**每个 draw 一个光值**（谁都逃不掉）

要回答"能不能做出**外部照明方块照在车长方向上的梯度**"，必须先钉住这条上限。

1. **光是一个"每次 draw 的常量顶点属性"**：MTR 4 的 `UV_LIGHTMAP: GLOBAL`、NTE 的
   `VertAttrState.applyGlobal()` → `glVertexAttribI2i(...)` + `toggleAttrArray(false)`。
2. **几何是构建期一次上传到 VBO 的**（`OptimizedModel.uploadedParts` / `ModelCluster.uploadedOpaqueParts`），
   每帧不重传。
3. ⇒ **想让光沿车长连续变化，就得逐顶点烘光 ⇒ 光一变就得重传顶点缓冲**。
   而这里光**每帧都会变**（车在动、玩家随时可能在旁边放/拆灯）⇒ 每帧重传整车几何，代价不可接受。
4. ⇒ **所以可达到的粒度上限 = 该物体被画成多少个 draw（或多少个实例）**。
   NTE、MTR 4、我们，三者完全一样。**这不是谁偷懒，是批渲染架构的性质。**

（Create 逃出了这条限制，是因为它**不用批渲染画装置**：把装置当**方块模型**从虚拟世界重烘（带逐顶点光与 AO）、
把材质的 `CardinalLightingMode.ENTITY` 强制成 `CHUNK`、再给光影报 section。
那套要求几何是"方块拼的"，对我们任意 UV 的 OBJ 车体不适用 —— 见 §3。）

### 7.5.1 那么"外部照明方块的反光"具体能做成什么样

方块光的规律是**每格衰减 1 级、上限 15 格**（火把 14、灯笼/海晶灯 15）。
所以"灯放在车头旁边"这件事，在不同粒度下的结果是**可算的**：

| 粒度 | 采样点距灯 | 读到的 blockLight | 效果 |
|---|---|---|---|
| **现状**（每节车 1 个采样点，取在**节中心**） | 节长 20 格 ⇒ 两端各距 10 格 | 约 **4** | **整节车同一个值** ⇒ "车头放灯、车尾跟着亮"（= 用户报的现象） |
| **16 段**（每段 1.25 格） | 1 ~ 19 格 | 约 **13 → 0** | 完整的车头→车尾梯度，台阶 1.25 格 |
| **8 段**（每段 2.5 格） | 1.25 ~ 18.75 格 | 约 **13 → 0** | 完整梯度，台阶 2.5 格 |
| 逐顶点（**做不到**） | — | — | 平滑无台阶 |

**能/不能的两个边界**：

- ✅ **能做**：沿车长成块的亮度梯度；灯只能影响"离它最近的一两节车"（15 格上限）；
  同一节车内**天然**就有梯度（这正是诉求）。
- ❌ **做不到**：① 单个 draw 内部的连续衰减（一个部件/一段跨过灯光边界时，它整体取采样点的值 ⇒ 亮区会"溢出"该部件）；
  ② 真正的镜面/反射高光（MC 没有这个）；
  ③ 比"部件/段"更细的任何东西。

**所以 NTE 的答案是**：`MultipartContainer` 每部件一次 `enqueue(model, partPose, light)` ⇒
把那个 `light` 换成"按 `partPose` 的世界位置逐部件采样"，**几行代码就能得到上面这一档效果，且不用切几何**。
唯一的问题是**粒度由部件划分决定**：NTE 的部件是语义的（锅炉/驾驶室/煤斗/连杆…），
某个部件若横跨大半节车，它内部仍然只有一个光值 ⇒ 梯度是**不均匀、成块**的。

而我们的车体是**一整块 `body`** ⇒ 按部件取光对它**完全无效**（永远一个值）⇒ 必须切片。

### 7.5.2 为什么"给一块车体多个光值"没有别的路（2026-09-28 定）

诉求是**同一块车体沿车长不同亮度**（外部照明方块照上去的梯度），不是"各部件不同亮度"。闭环论证：

1. MC 的 lightmap 是**"光级 → 颜色"的一维渐变贴图，不含任何空间信息**（不是"哪里亮"的地图）；
2. ⇒ 逐片元的空间光照需要"某点处光是多少"这个数据，客户端没有这种东西
   （原版是把光**烘进方块网格**的 —— 放置/更新时就烘好了）；
3. 我们是**移动物体**，几何**构建期一次上传到 VBO** ⇒ 逐顶点/逐片元就得**每帧重烘重传**，代价不可接受；
4. ⇒ 唯一的杠杆是 **per-draw 常量光值**，**粒度的唯一提升手段 = 把这块车体画成更多次 draw**。

⇒ 所以"16 段"**不是把车体拆成部件**，而是"**为了给同一块车体 16 个光值，把它画 16 次**"。
语义上仍是一块车体 ⇒ 命名按族（`body_z00..body_z15`），不听着像 16 个零件。

**切分可以做零几何改动**：按**整面归属**切（用三角形面心 Z 决定归属），**不是把面切开**。
打包器写 OBJ 时本来就把每个角去焊接成独立三元组 ⇒
**顶点位置 / UV / 法线一个字节不变、不产生裂缝**，纯粹是"这些面归第 k 段"。
代价只有：亮度台阶落在**面的边界**上（看不出来）。

### 7.5.3 一条必须一起做的连带项（否则产生新接缝）

一旦车体按段取光（车头那段读到约 13），而门/雨刷/内装仍沿用"**节中心**"的那一个值（约 4），
车头端就会出现**"车体很亮、旁边的门很暗"**的接缝 —— 比现状更难看出问题。

⇒ **"所有部件都按自己的包围盒中心取光"不是附加好处，而是分段的必要前提。**
mod 侧与打包器侧**必须一起上、一起重启**；单独上任何一半都会引入新接缝。

（这条推翻了本笔记早期"门/雨刷可以免费先做"的说法 —— 那一半单上是**有害**的。）

### 7.5.4 「按 1 格切 + 复用游戏内平滑光照」的裁定（2026-09-28）

**① 按 1 格切：可行，而且这就是最优粒度。**

方块光是**整数字段、每格恰好衰减 1 级**（`LightEngine` 的 BFS：走一步减 1）；
而 lightmap 只有 **16 级**（`LightTexture` 是 16×16）。⇒ **采样间隔细于 1 格不携带任何信息**
（相邻采样点会读到同一个整数）。所以 1 格 = 无信息损失的粒度上限，再细纯属浪费 draw。

按长度算段数（不写死）：BR101 19.9652 格 → **20 段**；SAF420 控制车 19.5 → **20 段**；拖车 16.95 → **17 段**。

**② "复用游戏内的平滑光照"：做不到。**

原版平滑光照（smooth lighting）有两个前提，我们一个都没有：

- 它作用在**逐顶点**上（`BlockModelRenderer` 用面四角各取相邻方块的光值做平均，同时出 AO）；
  而我们这套的 `UV_LIGHTMAP` 是 **GLOBAL**（每次 draw 一个常量）⇒ 顶点格式里根本没有逐顶点光这一项；
- 它是**烘方块网格时**从**方块网格邻域**算出来的；我们画的不是方块几何。

⇒ 段与段之间是**硬台阶**，只不过 1 格 = 1 级 = **lightmap 能表达的最小差**。
也就是说：我们做不到"平滑"，但把台阶压到了理论最小 —— 这是"用最优粒度掩盖"而不是"复用了平滑光照"。
（**唯一能让台阶真正消失的是光影**：Iris 下着色器按世界位置重算光照。但取决于光影包怎么用 `lmcoord`，
不能保证；要实地看。）

**③ 一个让人放心的点：采样点不需要"往外偏"。**

车是**实体**，而光照只由**方块的不透明度**决定 ⇒ **车不遮挡光照**。
所以采样点取在段中心（哪怕落在车壳内部）读到的就是那一带空气的光，与贴着车皮外面采一样。
⇒ 实现上不必为"内/外"做特殊处理。（`PositionAndRotation.getLight` 现在取在节中心 `y+1`，就是这个道理。）

**④ 代价（用 notes/340 的实测基线算）**

| 粒度 | 段数/节 | 车体 draws/节 | 10 节编组车辆 draws | 总 draws/帧 | 优化批次增量 |
|---|---|---|---|---|---|
| 现状 | 1 | ~1 个 model（含若干材质组） | **152**（实测） | ~1630 | — |
| 20 段（1 格） | 20 | 20 个 model | **~310–450**（待实测） | ~1800–2000（**+12%~+23%**） | **+约 0.04–0.08 ms**（占帧 0.5–1%） |
| 8 段 | 8 | 8 | ~250–350 | ~1700–1900 | 约一半 |

**梯度总范围与粒度无关**（都是从约 13 到 0），差别只在台阶粗细：1 格 = 理论最小台阶。
⇒ 代价放得下，**按 1 格切是对的**；唯一量不到的仍是 GPU/驱动侧的 per-draw 固定开销（notes/340 §8.1 第 3 条），
只能靠同机位 A/B 帧间隔来判。
