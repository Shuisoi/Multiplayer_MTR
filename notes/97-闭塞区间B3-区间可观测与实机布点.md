# 97 - 闭塞区间 B3：区间可观测（`blocks` 指令）+ 实机布点实测

> 承 notes/96（B2）。设计：`docs/01-设计/闭塞区间细化-灯与虚拟边界-设计.md`。
> 用户 2026-09-10 关键约束：**灯的位置一定是在轨道节点旁边的**。

## 1. 实机布点实测（本片最重要的发现）

把运行中的 dev 世界（`run/world/mtr`）快照到临时目录，用引擎直接读 134 轨 / 8 架灯，逐架算绑定：

| 实测项 | 结果 |
| --- | --- |
| 灯的落点 | **8 架全部落在轨端节点上**：投影弧 = `0.00` 或 = 轨长，`toNode = 0.00`；横向离轨中心线 **2.06 m**（"在节点旁边"就是横向偏移，不沿轨偏移） |
| 切分情况 | `blockCount = 134 = railCount`：**没有任何一根轨被灯切分** |
| 哑绑定 | 1 架 BOUND 灯（`-163,-60,-189`）target 指向某轨，但灯离该轨 > `SIGNAL_BIND_TOLERANCE_M = 8 m`（投影超差）→ 它不切分任何轨；此前这种"绑定写了、实际不生效"从数据里看不出来 |

结论：用户判断正确；也说明 **B1/B2 的区间机制在当前世界等价于"每根轨一个区间"**（行为零变化），
中段灯切分是**备用能力**（灯若真的摆在轨中段才会生效，B1/B2 的用例已钉死该路径）。

## 2. 交付

| 件 | 内容 |
| --- | --- |
| `MmtrBlockReport`（引擎，纯投影） | `describeAll`：轨数 / 区间数 / 被切分轨数 + **每架灯的分类**（贴节点（不切分） / 切分该轨 / 未绑定 / 投影超差）+ 每根被切分轨的区间明细；`describe(railHex)`：单轨的边界序列（`NODE@0.0` / `SIGNAL@100.0(x,y,z)`）与区间 |
| `MmtrBlockService.resolveRail(SignalEntry)` | 公开的绑定解析（与切分用的是同一套规则：target 优先、否则 8 m 内最近轨），报告直接复用，避免两套口径 |
| OP 指令 `blocks [all\|<railHex>]` | fabric `MmtrCommandExecutor`；输出进 OP 指令日志（网页指令栏可见），未知指令帮助行已更新 |

## 3. 用例（`MmtrBlockReportTests`，1 例 12 断言）

合成两轨三灯：中段灯（切分，`SIGNAL@100.0`、两段各 100 m）、节点旁 2 格侧向灯（`贴节点（不切分）`）、
离所有轨 380 m 的 AUTO 灯（`未绑定`）；汇总行钉死 `轨道 2 根 / 区间 3 个 / 被灯切分的轨 1 根` 与
`灯共 3 架：贴节点 1 / 切分轨 1 / 未生效 1`；另覆盖单轨明细、未知轨、缺参三种输出。

  ```
  [blocks] 轨道 134 根 / 区间 134 个 / 被灯切分的轨 0 根（灯都贴在节点旁：每根轨 = 一个区间）
  ```

  与离线快照的结论一致，且**这架哑绑定灯在实机上一眼可见**。

## 5. 为什么本片没动客户端"显示读区间"（写给下一个会话）

引擎/客户端的显示占用都读**每轨一个色**的权威通道（`Rail.mmtrSignalColor()` /
`currentlyBlockedVehicleIds`）。要让显示按区间走，必须先把该通道切成**每区间一个色**（车辆按所占区间预留），
否则只能用车辆足迹树——而足迹通道比信号色通道**窄**（老式 MTR 停放车不写足迹，会让停放车所在轨显示变绿）。
既然实测世界不存在切分轨，客户端与引擎在"每根轨一个区间"下**完全一致**，本片不做客户端改动；
等真有中段灯（或需要"一轨多灯各自显示"）时，按设计 §6 的 **B3b** 做每区间色 + 镜像区间边界。
