# 353 — 键盘事件被"撞键"偷走（车外按 A 走不动 / 按 L 弹进度页）

2026-10-01。上一轮（notes/352）做的是"进驾驶室后与游戏内操作解耦"，这一轮是它实机当场暴露的
**两个真 bug**：一个把解耦冻死，一个是原版自己的机制在撞键时只让一个绑定收到按键。

---

| --- | --- | --- |

## 2. 第一现场：解耦一次都没跑过（哨兵参与减法 ⇒ 溢出）

第一版的判据缓存：

```java
private static long cachedAtMillis = Long.MIN_VALUE;
...
final long now = System.currentTimeMillis();
if (now - cachedAtMillis < CACHE_MILLIS) {   // ← 这里
    return cachedDecoupled;                  //    初值 false
}
cachedAtMillis = now;
cachedDecoupled = compute();
```

`now - Long.MIN_VALUE` 数学上等于 `now + 2^63`，在 long 上**溢出成负数**（本文这一次：
`1.79e12 + 9.223372036854775808e18` 超过 `Long.MAX_VALUE`，回绕成 `-9.22337203e18`）。
于是条件**永远成立**：第一次就把 `cachedDecoupled` 的初值 `false` 返回，`cachedAtMillis` 再也不会被写 ——
`compute()`（真正的判据）**一次都没被调用过**。

证据（两处，都是可复算的）：

1. `logs/` 里从 09-29 23:23 到 10-01 11:41 的**每一份客户端日志**都搜不到一行 `[MMTR-KEY]`
   （解耦生效时第一行必然是"驾驶室按键解耦生效：MMTR 键位 = …"）。
2. 部署产物里那个哨兵就在 `<clinit>`：
   `javap -p -c … MmtrInputDecouple` → `static {}: 0: ldc2_w #184 // long -9223372036854775808l; putstatic cachedAtMillis`。

**修法**：把窗口算法搬进纯函数 `MmtrDecoupleCache.fresh(now, cachedAt)`，哨兵**只参与等式比较**：

```java
return cachedAtMillis != NEVER && nowMillis - cachedAtMillis < WINDOW_MILLIS;
```

并且它**零 Minecraft 依赖**，所以 `sandbox/light-switch-probe/check.ps1` 里真的编译并跑了一遍，
用例包含反例断言：`now - NEVER < 窗口` 在这台机器上**必须为真**（证明旧写法确实是坏的，
不是"看错了"）。

## 3. 真正的病因：原版一个物理键只把事件发给一个绑定

### 3.1 原版（1.20.4）的两条路都只查一张"一键一绑定"的表

反编译 `net.minecraft.client.option.KeyBinding`（yarn 命名）：

```
private static final Map<String, KeyBinding> KEYS_BY_ID;          // 按 id（每个绑定都在）
private static final Map<InputUtil.Key, KeyBinding> KEY_TO_BINDINGS; // 按物理键（一键只有一个赢家）

public static void setKeyPressed(InputUtil.Key key, boolean pressed) {
    KeyBinding b = KEY_TO_BINDINGS.get(key);   // ← 单次查表，只发给赢家
    if (b != null) b.setPressed(pressed);
}
public static void onKeyPressed(InputUtil.Key key) {
    KeyBinding b = KEY_TO_BINDINGS.get(key);   // ← 同上，timesPressed 也只加给赢家
    if (b != null) b.timesPressed++;
}
public static void updatePressedStates() {    // 只被 Mouse.lockCursor() 调（锁定鼠标那一刻），不是每 tick
    for (KeyBinding b : KEYS_BY_ID.values()) { ... b.setPressed(InputUtil.isKeyPressed(...)); }
}
```

而"赢家是谁"由 `updateKeysByCode()` 决定 —— 它 `clear()` 之后**遍历 `KEYS_BY_ID` 这个 HashMap**
逐个 `put`：

```
KEY_TO_BINDINGS.clear();
for (KeyBinding b : KEYS_BY_ID.values()) KEY_TO_BINDINGS.put(b.boundKey, b);
```

`GameOptions.load()` 的最后一行就调用它（`207: invokestatic KeyBinding.updateKeysByCode`）。
⇒ **赢家是"同键绑定里在 HashMap 里排在最后的那一个"，即由字符串哈希顺序决定，逐键独立、每次启动一样。**
与"谁先注册"无关。

### 3.2 Fabric 侧的两条相关事实

- `fabric-key-binding-api-v1` 的 `KeyBindingRegistryImpl.registerKeyBinding` **在 GameOptions 已经初始化时直接抛异常**
  ⇒ 模组的绑定一定先于原版构造；而 `GameOptionsMixin` 在 `load()` 的 HEAD 把模组绑定 append 进
  `GameOptions.allKeys`（`process(allKeys)`）⇒ **`allKeys` 里有模组绑定**，可以放心遍历它。
- 因为 3.1 的哈希顺序，撞键的赢家**不是注册顺序**：A 可以输给 MMTR，D 却没输 —— 这正是
  "只有 A 走不动"这种看上去不可能的不对称的来源。

### 3.3 于是现象闭合

| 键 | 撞键双方 | 实测赢家 | 现场表现 |
| --- | --- | --- | --- |
| A | `key.mmtr.drive.traction` + 原版 `key.left` | MMTR | **原版向左走彻底失效**（车外也失效） |
| D | `key.mmtr.drive.electric_brake` + 原版 `key.right` | 原版 | 向右走正常；MMTR 的电制动键收不到事件 |
| L | `key.mmtr.lights` + 原版 `key.advancements` | 原版 | 按 L 弹进度页；**灯光键收不到事件** |

也就是说 notes/352 里"按 L 弹进度页面"当时被解释成"解耦漏了 L"，其实是**反过来的**：
不是我们摘少了，是原版把 L 拿走了、我们的灯光键根本没收到按键（而解耦因为 §2 又完全没跑）。

## 4. 修法：把事件补发给所有同键绑定

`MmtrKeyEventFanout` + `ClientInputDecoupleMixin` 上新增的一个注入点：

| 事 | 做法 | 为什么这样 |
| --- | --- | --- |
| 按住/抬起 | 在 `KeyBinding.setKeyPressed` 的 **HEAD** 上，遍历 `GameOptions.allKeys`，把 `setPressed(pressed)` 写给**当前绑定键位相同**的每一个绑定 | `setPressed` 是公开的普通 setter（只写一个字段），赢家随后被原版再写一次同样的值，**幂等** |
| 点按计数 | **不碰**私有的 `timesPressed`；在 `KeyBinding.wasPressed` 的 HEAD 上，输家（`timesPressed == 0`）用**已经被补正的 `pressed`** 的上升沿自造一次（`@Unique` 一位记"这一按报过"） | 私有字段要反射或 accessor（映射名会变）；而 `pressed` 已经是对的，造上升沿没有映射风险 |
| 解耦 | 不变：撞了我们的键、且坐在司机位上 ⇒ `blocks()` 让 `isPressed/wasPressed` 返回"没按" | 补发与解耦是两条独立的闸门：先补发，再由位置决定谁听 |

结果：**撞键双方都能收到按键**（这正是原版"按键冲突"对话框承诺的行为），
"谁能动"重新只由位置决定 —— 车外按 A 走路、坐在司机位上按 A 推油门、按 L 弹进度页（车外）与换灯（司机位上）。

**代价**：每个键盘事件遍历一次 `allKeys`（约一百个绑定，字符串比较用的是 `InputUtil.Key` 里存着的
translation key，无分配）；键盘事件是每秒几十次的低频事件。

## 5. 附带修好的：解耦在车厢里摘多了（操纵位半径）

§2 一修，解耦就真的会跑了 —— 而它当时的判据是 `MmtrVehicleAnchors.nearestCab`：
**车厢里任何地方都"离某个驾驶室最近"**，于是一列车里除了司机，乘客按 A/D 也会被摘键（走不动）
并且顺手推手柄。用户口径是"坐在司机位上"，所以 `MmtrDriverSeat` 补一道**沿车长**的距离门槛
`CONTROLS_RADIUS_M = 2.0 m`（量到该驾驶室座位点；横断面不设限 —— 司机室本来只有 2–3 m 宽）。

取值来自 resourcepack 里锚点的实测（`assets/mtr/mmtr_anchors_*.json`，乘坐空间 = 文件空间绕 Y 转 180°）：

| 车型 | 座位 \|z\| | 司机门 \|z\| | 风挡 \|z\| | 司机室跨度 | 车厢中部离座位 |
| --- | --- | --- | --- | --- | --- |
| `saf420cab_a/b` | 8.200 | 7.502（离座 0.70 m） | 9.725（离座 1.53 m） | \|z\| 7.3–9.8 | **8.2 m** |
| `br101` | 7.707 | 7.303（离座 0.40 m） | 8.986（离座 1.28 m） | \|z\| 7.3–9.0 | **7.7 m**（另一端座位离 15.4 m） |

⇒ 2.0 m 装得下整间司机室（含"站在风挡前"那种站位），把走道排除在外。判不出距离的车型（没有
`mmtr_seat_`/`mmtr_cabdoor_` 锚点）沿用旧口径。判出局时说一次
（`[MMTR-SEAT] 离操纵位 X m（门槛 2.0 m）⇒ 不算坐在司机位上`，每辆车每一端一行）。

## 5.1 还有一类读者：拿**原始键码**比，摘状态对它无效（2026-10-01 实机第二次）

实机（重启后第一次进驾驶室）用户报："按 J 弹出旅行地图，雨刷无反应"。日志显示解耦**确实在跑**，
而且明确摘了那条绑定：

```
[12:24:16] [MMTR-KEY] 驾驶室按键解耦生效：MMTR 键位 = …key.keyboard.j…
[12:24:19] [MMTR-KEY] 解耦：摘掉 key.journeymap.map_toggle_alt（它绑在 key.keyboard.j，MMTR 有个键也是这个键位）
```

可它还是弹出了地图。反编译 JourneyMap（`journeymap-1.20.4-5.10.0-fabric.jar`）后原因很清楚：

```java
// KeyBindingAction.isActive(int keyCode, boolean pressed, InputUtil.Type type)
keyBinding.isActiveAndMatches(InputUtil.Type.createFromCode(keyCode))   // ← 拿的是原始键码
// UpdateAwareKeyBinding.isActiveAndMatches(InputUtil.Key key)
if (key == InputUtil.UNKNOWN_KEY) return false;
... key.equals(getKey()) ...                                            // ← 和"当前绑定键位"比
```

它**从不问 `isPressed()`**：原始键码来自它自己的键盘事件入口（`KeyEventHandler.onGameKeyboardEvent(int)`）。
所以"让绑定回答没按"这条路对它天然无效 —— 顺带也解释了"雨刷没反应"：J 同时打开了全屏地图（一个界面），
而雨刷的读取点在"没有界面"那一支里（`MainRenderer` 的守卫），那一拍它连键都没读到。

**修法**：`MmtrKeyNeutraliser` —— 在驾驶室里把**别的模组的**撞键绑定临时挪到"未绑定"
（`InputUtil.UNKNOWN_KEY`，键码 −1；JourneyMap 的 `isActiveAndMatches` 第一句就 false），
离开驾驶室立刻放回。规则与安全网：

| 事 | 做法 | 理由 |
| --- | --- | --- |
| 挪谁 | 撞了我们的键、**且不是** `key.mmtr.*`、**且分类不是原版分类**（用 `KeyBinding.MOVEMENT_CATEGORY` 等游戏自己的常量判，不写名单） | 实测撞上的都是模组键：JourneyMap 的 J/B/N/H/←/→、Iris 的 K/R。原版绑定靠"摘状态"已经安静，少碰一次玩家的 `options.txt` |
| 怎么记原键位 | `InputUtil.fromTranslationKey(getBoundKeyTranslationKey())`，走公开 `setBoundKey` 放回 | 不反射 Minecraft 的私有 `boundKey`（生产环境 remap 后字段名会变） |
| 何时放回 | 每 tick 检查：不坐在司机位上就放回（**界面一开就恢复** —— 聊天里 J 还得是 J）；以及 `GameOptionsWriteMixin` 在 `GameOptions.write()` 的 HEAD 无条件放回 | 写 `options.txt` 是唯一把内存键位落盘的地方：那一刻不放回，"未绑定"会被永久写进玩家文件 |
| 状态 | 被挪走的绑定在 `blocks()` 里仍按 `isNeutralised` 摘掉 | 有的模组读状态、有的读键码，两条路都得安静 |

顺带把**换向器从 ←/→ 改成 W/S**（用户 2026-10-01 口径，见 §7）：JourneyMap 的全屏地图也占着 ←/→，
换掉之后那一组撞键直接消失。

## 5.2 灯光开关"连续切换档位"：它被当成每拍的绝对量了（2026-10-01 实机第三次）

上一轮把 L 键修通之后，立刻冒出第三个 bug：**按一次 L，档位自己来回跳**。这次不用猜 ——
引擎自己在每次档位变更时打一行日志（`[MMTR-LIGHT] 车=… 灯光开关：A端 = …`），服务端日志里：

```
[MMTR-LIGHT] 车=5709141194114865570 灯光开关：A端 = 尾灯
[MMTR-LIGHT] 车=5709141194114865570 灯光开关：A端 = 夜间      ← 同一秒里成对翻转
…                                                            ← 每秒**正好 20 条** = 20 TPS，一拍翻一次
```

**根因**：`Vehicle.tick` 里每拍都做 `applyMmtrLightSwitch(mmtrActiveControl.getLightSwitch())`
—— 把"当前活动控制状态里的档位"当成绝对量重写一遍。而控制包每拍都在发，`mmtrActiveControl` 会
在**两个来源**之间轮换（自动运行的 SYSTEM 控制状态里档位是出厂值"尾灯"，坐进驾驶室的玩家那份是
"日间/夜间"），于是两边的值以 tick 频率互相覆盖。

**修法（引擎侧，边沿语义）**：灯光开关是**保持型开关**，"谁扳动了谁说话" ——

| 改动 | 内容 |
| --- | --- |
| 判据 | `applyMmtrLightSwitch(int requested, UUID driverUuid)`：按**来源**（{@code null} = 引擎内部/自动运行，否则司机 UUID）记住最后一次请求的档位，**只有它变了才真的去扳开关** |
| 调用点 | 从 `Vehicle.tick` 的每拍那一段**移到** `applyMmtrControl`（控制状态被接受的那一处） |
| 不清空 | 司机离开时**不**清 `mmtrLightSwitchRequests`：清空会让"客户端还记着旧档位、隔一拍又发一次同样的值"变成新的扳动，把 `releaseMmtrLightSwitch` 刚落回的尾灯又点亮 |
| 端 | 不变：仍然由引擎的占用状态决定写哪一端（客户端说了不算） |

**验收判据**（可自动量）：修好之后，按一次 L，服务端日志里应该**只多一行** `[MMTR-LIGHT]`；
修好之前是每秒 20 行。这条比"看着不闪了"可靠。

| 检查 | 结果 |
| --- | --- |
| 修前：`[MMTR-LIGHT]` 条数 | 每档 20 条/秒（12:43:30–41 每秒都是 20 条，在 尾灯 ↔ 夜间 之间成对翻转） |
| 离线判据 | `check.ps1` **125/125**（§G5 七条：带来源参数、按来源记最后请求、边沿判断、调用点在 `applyMmtrControl`、**反例**：每拍那一段不再调用它、注释点明边沿语义、司机离开不清空记录） |
| 引擎回归 | 针对性子集 `gradlew test`：73 个用例 0 失败（LightSwitch 9 / DriveAccess 5 / DriveSanitize 3 / CabState 11 / DriveController 7 / ThreeHandle 26 / MiniWorldDrive 1 / VehicleSyncPatch 9 / ClientVehicleSync 2）—— 全量套件里那个 DAY-LOOP 仿真要跑几十分钟，改成子集 |
| 修后 | 见 §7 实机验收第 9 条（判据：按一次 L，服务端只多一行 `[MMTR-LIGHT]`） |

## 5.3 还在抖：客户端"跟镜像走"是第二台振荡器（同日，同一个判据抓到的）

引擎侧改成边沿语义之后，服务端日志仍然每秒 2–20 行地翻（只是不再稳定 20 行/秒）。对着客户端那几行判据看，
第二台振荡器在**客户端**：

```java
// adoptLightCapability（每拍）
if (mirror != sentLightSwitch && isKnown(mirror) && mirror != lightSwitch) {
    lightSwitch = sanitize(mirror, lightHasOff);   // "跟着镜像走（别人改的）"
}
```

镜像要**一个来回**才回来。我按 L 发出"日间"之后，在自己这个值回来之前先看到的是**旧值**（尾灯）：
`mirror(尾灯) != sentLightSwitch(日间)` 成立、`mirror != lightSwitch` 也成立 ⇒ 退回尾灯并再发一次；
下一拍先前发出去的"日间"才到，又把它拉回日间 …… **这条规则本身成了自己跟自己打架的振荡器**，
频率就是镜像延迟（实测 2–20 次/秒，值在 日间/夜间/尾灯 之间混着翻 —— 因为两边的发送还在交错）。
用户口径"按 L 会连续切换档位 / 依旧无法正常切换"就是它。

**修法（客户端）**：自己刚扳过开关之后 {@code LIGHT_MIRROR_GRACE_MILLIS = 2000 ms} 内**不跟镜像走**
（`send()` 里只有"我这边档位真的变了"才刷新那个时刻）。窗口过后若镜像确实不同（别人改了、司机离开回落、
连挂灭尾灯），照样跟上 —— 那时它已经不是"我刚发出去那个值的回声"。

**诊断**：`send()` 的 trace 行现在把灯光档位也打出来（`-Dmmtr.trace=true` 时可见），
于是"客户端每拍发了什么"和"服务端收到了什么档位"可以逐行对上。

| 检查 | 结果 |
| --- | --- |
| 离线判据 | `check.ps1` **130/130**（新增五条：静默窗口存在、窗口内提前 return、刷新时刻的条件、**反例**：不再无条件跟镜像走、trace 行带灯光） |
| 实机 | 见 §7 第 9 条（按一次 L，服务端只多一行） |



`sandbox/light-switch-probe/check.ps1` 这一轮加了 §G/§G2/§G3 共 31 项，**101/101 全过**：

- 事件流：补发遍历 `allKeys`、用公开 `setPressed`、按"当前绑定键位"匹配、撞键表说一次；
  反例：代码里不出现 `@Accessor("KEY_TO_BINDINGS")` / 反射读那张私有表；
  部署产物里 `ClientInputDecoupleMixin` 确实注入了 `setKeyPressed` 且调用 `MmtrKeyEventFanout.fanOutPressed`。
- 缓存：`fresh` 的哨兵只参与等式；`MmtrInputDecouple` 用 `MmtrDecoupleCache.fresh`、初值是哨兵；
  **反例：`now - cachedAtMillis` / `CACHE_MILLIS` 必须已经从代码里消失**（注释里解释旧写法不算）。

## 8. 教训

1. **哨兵值不能参与算术**。`Long.MIN_VALUE` 做被减数是溢出陷阱；判据"永远成立"比判据写错更难发现 ——
   因为它的症状是"功能像没接线"，而日志里**什么都没有**。现在这条规则有可执行的反例用例。
2. **"按键没反应"要往下一层查**：我们用 `KeyBinding` 读键，而原版**一个物理键只有一个绑定收得到事件**。
   撞键不是"两个动作都触发"，而是"只有一个触发，且赢家由 HashMap 顺序决定" ——
   所以"只有 A 不动、D 正常"这种不对称是**正常输出**，不是观测错误。
3. **反例断言不能被注释绊倒**：这一轮两条反例断言第一次就 FAIL，因为我在 javadoc 里**解释了旧写法**。
   判据脚本现在有 `Read-Code`（剥掉注释）专门给反例用。
