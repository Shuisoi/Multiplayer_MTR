# 406 — 可重建性自检：把"车在哪"压成"一端 + 单元几何"，还差什么

> 2026-10-09。背景：网络层要往"**玩家自身一条上传 + 服务器一条下载**"收敛，列车那边只发
> "单元 + 位置 + 方向"（用户 2026-10-09 口径）。本条**不改任何生产代码**，只把"这样够不够"
> 从判断变成读数 —— 一个纯引擎的用例：`MmtrRebuildSelfCheckTests`（7 例，全绿）。
>
> 一句话结论：**"一端位置 + 单元几何"是无损的（逐位相同），但"只发头部 + 方向"不够** ——
> 缺的不是"道岔现在在哪一位"，而是"**这一列车当时走了哪条腿**"。

---

## 0 为什么先做这件事

新协议的前提是"更小的信息量足以重建几何"。这件事**可以纯引擎验证**，而且失败也不会有人看得见：

- 不碰网络层、不碰渲染、不改生产代码；
- 用的是**真的走行出来的**编组体（不是手工拼的脊线）—— 一列三节车跨在岔口上（车尾在根部轨、
  车头在岔股），这正是"只发头部位置"最容易出事的位置；
- 比的是**逐位相同**（车长 / 一端弧 / 逐节车中心 / 占用面 + 轨 hex），不是"看起来对"。

复现：

```powershell
. env\workspace.env.ps1
Set-Location mmtr\engine
.\gradlew.bat test --tests 'org.mtr.core.mmtr.consist.MmtrRebuildSelfCheckTests' --console=plain
```

## 1 读数（`[REBUILD]` 行，逐字）

夹具：根部轨 `rIn` 20 m，岔口分正线 `rStraight` 与岔股 `rDiverge`；三节 5 m 车、第 1 节之后一处
接缝；先在根部轨放下（`aEnd=2`），再给岔股发一次第 1 条腿的授权、朝 B 端开 8 m。

真身（两例共用）：

```
len=15.000000 aEnd=10.000000 c0=12.500000 c1=17.500000 c2=22.500000
  [根部轨 10.000000..20.000000] [岔股轨 0.000000..5.000000]
```

| # | 给重建方的信息 | 结果 |
| --- | --- | --- |
| ① | **脊线轨序**（每根轨 hex + 入端）+ A 端（轨/入端/轨内偏移）+ 逐车长 + 接缝 | **逐位相同**（真身 == 重建，含跨两根轨的占用面） |
| ② | 只有 A 端 + 几何，让 `MmtrConsistWalker.place` 自己选岔（道岔表为空） | **`null`（建不出来）** |
| ③ | A 端 + 几何 + **当时那一次岔决定**（节点+进向轨 → 第 1 条腿） | **逐位相同** |
| ④ | 同 ③，但先把模拟器的道岔**扳回正线**（现在=0，决定=岔股） | **仍然逐位相同** |
| ⑤ | 把**头部**（B 端 = 岔股@5 m）当起点去 `place` | **成功返回，但是另一条脊线**（`len=15 aEnd=5`，只占岔股 `5..20`）—— 安静地错 |
| ⑥ | 接缝在车体内的位置（从 A 端量）走行前/后 | **10.000000 → 2.000000**（漂移 8 = 走行 8 m） |
| ⑦ | 内部驾驶室在车体内的位置，走行 4 m | **2.500000 → −1.500000**（漂移 4 = 走行 4 m） |

## 2 三条协议结论

### 2.1 位置要发**命名端（A 端）**，不是"头部"

`MmtrConsistWalker.place` 只有"A 端朝 B 端铺"这一个方向（`extendSpine(towardB=true)` 写死在
`place` 的循环里，见 :121-127）。把头部当起点：

- 车头恰好是 A 端时（CAB_B 在岗、朝 A 开）—— 能用；
- 车头是 B 端时 —— 得到的是**方向相反**的脊线，而且**返回值不是 null**（⑤）。

所以线上要发的是 `(命名端 A 的轨, 该端的入端, 轨内偏移 m, 端别 A/B 哪个在前, 行进方向)`。
这与"取列车最头部"是**同一份信息量**（知道了 A 端在哪、车有多长、哪端在前，头部自然确定），
但它能被现有 API 直接消费；反过来则要新增一个"反向铺脊线"的入口。

### 2.2 必须带**当时那次岔决定**，而"知道道岔状态"不够

- ②：岔口上没有任何提示 ⇒ `place` 直接 `null`。**客户端光有几何建不出脊线。**
- ③：把"从根部轨进这个节点走第 1 条腿"给出来 ⇒ 逐位相同。
- ④：**先把道岔扳回正线**（车清岔之后联锁本来就会这么干），同一份决定**照样逐位相同** ——
  因为注入道岔表时 `MmtrForkElection.elect` 读的是这份表（`positionFromRows`），
  而不是模拟器当前的物理位置。

⇒ 用户 2026-10-09 的口径"客户端需要能知道道岔的状态"是**必要但不充分**：
**当前道岔位置 ≠ 这列车当时走的那条腿**。道岔会被扳回去（rear-clear 之后就是正常操作），
而车体还压在岔股上；此时按"现在的位置"重推必然分叉。线上要带的是**历史决定**。

两种等价的小载荷（都比现在的腿表小）：

| 形态 | 每条记录 | 说明 |
| --- | --- | --- |
| **轨序**（hex + 入端） | hex 101 字符 ≈ 109 B/腿（现状）→ 稳定 8 字节摘要 ≈ 9 B/腿 | 客户端**不选岔**，直接 `new MmtrConsistBody(...)`（①已证明逐位相同），且不依赖它自己的道岔数据 |
| **岔决定**（节点 + 进向轨 → 第几条腿） | 每过一处岔口 1 条 | 更省，但要求两端对"第几条腿"的**排序一致** —— 而排序受 `simulator.mmtrJunctionLegs`（进向表）影响，那份表**没有同步到客户端** |

**建议取"轨序"**：它自足（不要求两端同序、不要求道岔状态、不要求进向表），而代价只是每根腿
9 B。**岔决定**那条路在客户端缺"进向表"时会静默给出另一个腿号，属于本仓库反复吃亏的那类静默错。

### 2.3 单元边界按"**第 k 节之后**"表达，绝不发弧长

见 §3：接缝弧与内部驾驶室弧**都不随车体移动**。`carIndexAfterSeam` / `mmtrCouplerAfter`
是稳定的（⑥里走行 8 m 它不动），弧长不是。

⇒ 线上单元表的形状应该是
`[单元 A: 车型 id, 车数 n] [单元 B: 车型 id, 车数 m]`（或等价的"每节车 + 是否接缝"），
**逐节几何（车长/耦合余量/转向架位置）由单元 id 查表得到**，位置只发一个端点。

## 3 待确认的缺陷：接缝弧与驾驶室弧不随车体移动（**未修**）

### 3.1 读数

⑥ / ⑦ 就是最小复现：`MmtrConsistBody.slideBy(deltaM)` 只移动 `aEndArcM`，
**不移动 `seamArcMs`，也不移动 `MmtrCabState.cabArcM`**，而它们都是**脊线空间的绝对值**
（`MmtrConsistBodyCouplingTests:196` 用"相减"得到体内位置、`:243` 拿 `cabArcM` 与 `carEndArcM(1)`
直接比，都说明是绝对值）。于是"车走了多少米，它们在车体内的位置就漂多少米"。

### 3.2 生产路径

- 走行：`Vehicle.simulateMmtrMotion` 每 tick `mmtrMotionWalker.advance(integratedDistance)`
  （`Vehicle.java:2941`），编组体那一支（`:2952` 判 `instanceof MmtrConsistWalker`）就走 `slideBy`。
- 消费者 ① 解挂：`MmtrCoupleSurgery.uncouple` 把 `body.seamArcM(k)` **当作后段的 A 端弧**
  传给 `placeConsistHalf`（`:549`），而后者用它去找轨与轨内偏移（`:632-658`）。
- 消费者 ② 连挂：`MmtrCoupleSurgery.cabArcOf` 读 `cabs().cabArcM()` 决定"合并在哪一节"。

⇒ **"挂上之后开一段再解挂"这一支会切在错的地方**；`MmtrConsistBodyCouplingTests` /
`MmtrCoupleSurgeryTests` 都在"刚刚合并完、一步没开"的状态下切分（`MmtrCoupleSurgeryTests:333`），
所以既有的 7 个解挂用例都没覆盖到这一格。

### 3.3 为什么本条**不修**

修法有两条，方向相反，而选哪条取决于 §2.3 的线上形状：

- **A：让弧跟着车体走** —— `slideBy`/`prependLeg`/`trimOutsideLegs` 里一并平移接缝弧与驾驶室弧。
  改动落在运动核心的共享对象上，且 `trimOutsideLegs` 已经在改 `aEndArcM`（`prependLeg` 也改），
  要一次改全三处才算对；
- **B：改成车体相对** —— 构造器注释本来就说"arc position of each seam **from the A end**"，
  即**注释与实现已经不一致**，按注释改就等于把 `seamArcMsFrom(aEndArcM, ...)` 的 `aEndArcM`
  去掉，并修 `MmtrCoupleSurgery` 那三处调用。

两种都会动到"连挂/解挂的几何口径"，属于要单独一片、单独验收的改动。**先把读数记账**，
等协议形状定了再决定 —— 若线上按 §2.3 只发"第 k 节之后"，B 方向顺便把注释与实现对齐就更自然。

## 4 这一轮**没有**验证的

- **只有一处岔口、一次过岔**：多岔口连续过岔、岔股回根部、度 4 交叉/三岔口（没有物理道岔模型）
  未覆盖 —— 那几处的 `continuationFrom` 分支不同（`manualDrive` 兜底、`turnout == null` 分支）。
- **轨表裁剪**（客户端按渲染半径拿轨）只有在"缺轨"时才发作，本用例的轨都在手上；
  `MmtrLegAppender` 的 `UNKNOWN_RAIL` 那一档在客户端是真会发生的（10 节 SAF420 ≈ 200 m，
  而渲染距离 12 区块 ≈ 192 m）。
- **反向（B 端在前）走行时的重建**只测了"用头部当起点会错"，没测"发 A 端 + 端别在前"的完整回放。
- 接缝/驾驶室漂移的**后果**（解挂切错位置的具体表现）没有在真车场里跑过，只从代码路径推的
  （`:549` 的消费者是确定的，但错多少米取决于当时 epoch 内走了多远）。

## 5 下一步（按依赖排序）

1. **定协议形状**（本条的产出就是这张表的输入）：单元表按 `[车型 id, 车数]`、位置发**命名端 A**、
   脊线发**轨序（摘要化）**、单元边界发**"第 k 节之后"**。
2. 给 `place`（或一个新的构造入口）加"**按给定轨序直接建车体**"的公开入口 —— ①已经证明
   直接 `new MmtrConsistBody(...)` 就够，但那条路现在只能从 `mmtr.consist` 包内拼；
   客户端要有一步"轨序 → 车体"的正门。
3. 客户端要知道道岔状态这件事**独立于**上面的结论：即使脊线由服务端给，道岔状态对
   "进路显示 / 手动开车"仍然需要；但**它不能替代历史决定**（④）。
4. §3 的接缝/驾驶室弧单独一片，选择 A 或 B 并在同一片里补一个"开一段再解挂"的用例。
