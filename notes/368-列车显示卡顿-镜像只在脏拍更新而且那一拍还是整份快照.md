# 368 = 列车显示卡顿：**镜像只在"脏拍"更新，而脏拍的门控里没有驾驶本身**

> 触发（2026-10-03，用户，三条一起报）：
> ①「服务端和客户端之间配合渲染列车时，往往有一定的卡顿」；
> ②「自己驾驶列车时，客户端会在原地不动，然后突然瞬移到正常位置之后可以正常移动」；
> ③「AI 驾驶的列车会有明显的卡顿，表现为位移掉帧和出站进站不平滑等系统性的问题」→
> 用户判断「**我认为需要重构显示系统**」。
>
> 状态：**已定位到机制（本节 §2/§3）、有实测数字（§1）**；修法与重构范围**待用户拍板**（§5/§6）。

## 1. 先量出来的数（都是这一版实机日志里的原话）

日志：`mmtr/game/fabric/run/logs/latest.log`（现场那一份同时含客户端 `Render thread` 与服务端 `Server thread`）。
`[MMTR-CL] 车辆包：…` 这一行是**客户端收到包时**打的（`PacketUpdateVehiclesLifts`）。

| 量 | 实测 |
|---|---|
| 客户端收车辆包的间隔 | **1 s 一次**（1515/1711 个间隔正好 1 s；另有 170 个 2 s） |
| 包的形态 | **`整份=1 补丁=0 保活=0` 占 1191/1711**；真正的补丁只有 232 次 |
| 包大小 | 平均 **7313 B**，最大 **15079 B**（单节车的整份快照 ~3.5–7.4 KB，用户现场已 10 节车） |
| 客户端镜像车数 | `客户端镜像=1`（视野内 1 辆，与 `[MMTR-PERF] … 镜像车=1` 一致） |
| 服务端 | 20 tps（`tick=100/5s`）；`vehicleSync=patches`（补丁通道是开着的） |

**一句话**：客户端不是"每拍收到位置"，而是**大约每秒被塞一份 7 KB 的整份 JSON 快照**，
中间那 19 拍全靠客户端自己积分；而客户端积分用的输入（手柄/标记）也**只在那一份快照里**才更新。

## 2. 机制：四环相扣，缺一不可

### (1) "发不发"由一个**老字段门控**决定，而驾驶本身不在门控里

`VehicleExtraData.checkForUpdate()`（`engine/src/main/java/org/mtr/core/data/VehicleExtraData.java:441`）
看的只有这几项：

```
stoppingPoint / doorTarget / powerLevel / speedTarget / isCurrentlyManual /
mmtrDoorLeft / mmtrDoorRight / mmtrDoorManual / hasRidingEntityUpdate
```

`postPowerLevel` / `speedTarget` 是 notes/235 之后**已经死掉的 legacy 读数**（服务端每拍写
`setSpeedTarget(speed)`，而 `speed` 的单位是 blocks/ms：正常加速度下每拍只变 ~5e-5，
**永远越不过 0.01 的门限**）。于是上表里真正还会动的只剩门与停车点。

而**司机/自动的手柄输入不走这条门**：

- `Vehicle.applyMmtrControl(...)`（`Vehicle.java:3595`，客户端 `PacketDriveControl` 的落点）
  写了 `mmtrActiveControl` / `mmtrManualOverride` / `mmtrDriverUuid` / `mmtrControlApplySeq`，
  **一次都没有 `mmtrMarkSyncDirty()`**；
- `updateMmtrSyncFields()`（`Vehicle.java:4962`）把这些镜像进 `mmtrThrottleNotch` /
  `mmtrDriveHandle` / `mmtrActive` / `mmtrReverser` …，也**不标脏**。

⇒ **"我推了手柄"这件事，在最坏情况下永远不会被推给客户端**，除非刚好有门/停车点/任务提示之类
的事发生（`mmtrMarkSyncDirty()` 的 25 处调用点里没有任何一处在驾驶路径上）。

### (2) 而"发什么"在那一拍常常退化成**整份快照**，不是补丁

`VehicleSyncPatch.DYNAMIC_KEYS`（`engine/src/main/java/org/mtr/core/operation/VehicleSyncPatch.java:47`）
是**动态白名单**：没列到的一律当静态，静态一变 ⇒ `patchOf()` 返回 `null` ⇒ 发整份。而镜像**物理自己要用**
的三个字段**不在白名单里**：

| 字段 | 谁在写 | 变化频率 |
|---|---|---|
| `acceleration` / `deceleration`（= `setMmtrAccelerationSi/DecelerationSi`，`Vehicle.java:5065`） | 每 tick，且**随速度变** | 车一动就变 |
| `path`（`mmtrSetSyncPath` 灌进来的**腿阴影**，notes/235） | 走行器每长出一条腿 | 每 30–100 m |
| `vehicleCars` / `ridingEntities` … | 连挂/上下车 | 偶发 |

⇒ 车一开动，**每个脏拍都变成整份 7.4 KB**（白名单里缺 `acceleration/deceleration` 这一条，
等于把 notes/174 省下来的带宽又还回去了一半）。

**第二条通路（同一天用用例证实的）**：`VehicleSyncPatch.patchOf` 在"逐字段比对下来一处都没变"时
返回的是**空对象**（`patchOf` 里那句 `if (patch.size() == 0) return patch;`），而 `Client.update()`
（`Client.java:170`）用 `patch.size() > 0` 当"这是补丁"的判据 ⇒ **空对象掉进 else 分支 = 发整份**。
触发它的是 `checkForUpdate()` 里那一项 `hasRidingEntityUpdate` —— 也就是 `mmtrMarkSyncDirty()`
**标脏标志本身**：凡是"标了脏、但序列化字段其实一处都没变"的拍，都会白扔一份整份快照。
证据：用例 `ClientVehicleSyncTests.aDirtyButUnchangedVehicleIsKeptInsteadOfResentWhole`
（修之前那条是红的：`expected: <1> but was: <0>` 反过来 —— 实际发出了一条消息且是整份）。

### (3) 客户端是**逐帧本地积分 + 每秒被整份覆盖**

- 积分：`MainRenderer.render()` 每帧调 `vehicle.simulate(millisElapsed)`
  （`game/fabric/.../render/MainRenderer.java:100`）→ 引擎侧 `Vehicle.simulateMoving()` 客户端分支
  （`Vehicle.java:5293`）用**镜像里的**手柄跑同一份 `ConsistDynamics`；
  但开门条件是 `tryInitMmtrController() && mmtrConsistType != null && mmtrDriveController != null && mmtrActive`
  —— **`mmtrActive` 为假就直接 `speed = 0; return;`（车在客户端一动不动）**，而 `mmtrActive`
  正是"只在脏拍才更新"的镜像字段（§2(1)）。
- 覆盖：整份快照到达时 `railProgress` / `speed` 被**直接写成服务端的值**（没有误差缓冲），
  客户端这一秒积出来的偏差只能靠渲染侧的平滑去糊（见 (4)）。
- 另有两条客户端夹紧（`Vehicle.java:2121`）：`mmtrMotionMirror && railProgress > 0` 时，
  只要镜像的 `mmtrRunStopTarget` / `mmtrRunTotalDistance`（同样是脏拍才更新的旧值）已经落在车后，
  **每帧把 speed 钉成 0** ⇒ 镜像再次冻住。

### (4) 渲染侧的平滑**藏不住**这些跳变

`PersistentVehicleData`（`game/fabric/.../data/PersistentVehicleData.java:68`）：

```java
railProgressSmoothingAdjustment = newRailProgress - smoothedRailProgress;
if (Math.abs(railProgressSmoothingAdjustment) > totalVehicleLength - 1) railProgressSmoothingAdjustment = 0;  // ← 直接放弃平滑
...
// 每帧只吃掉这么多：millisElapsed * (speed / 10)，speed 是 blocks/ms
railProgressSmoothingAdjustment = max(adj - amount, 0);
```

- 修正量一超过"车长 − 1 m"（客车 ~25 m，**25 m**！）就**完全不平滑**，直接瞬移；
- 速度越低吃得越慢：进站 5 km/h 时每帧只吃掉 ~2 mm —— 一次 1 m 的修正要几百帧才吃完，
  于是"停不准、停稳前一直在爬"；出站反过来，命令已经给了车还没走 → **进站出站都不平滑**。

## 3. 三条症状各自对应哪一环

| 用户看到 | 机制 |
|---|---|
| 「自己驾驶：原地不动 → 突然瞬移到正常位置 → 之后正常」 | 推手柄不标脏（§2(1)）⇒ 客户端的 `mmtrActive`/手柄停在旧值 ⇒ `simulateMoving` 直接 return（§2(3)）⇒ 镜像**冻住**；直到下一次**无关的**脏拍（到站开门 / 自臂停车点 / 任务提示）才把 `mmtrActive`+手柄+`railProgress` 一起送到 ⇒ 一次性跳到正确位置；此后手柄已同步，本地积分与服务端一致 ⇒「可以正常移动」。**冻多久取决于下一个脏事件什么时候发生，所以"没规律、难复现"。** |
| 「AI 车位移掉帧、出站进站不平滑」 | AI（autopilot / 自臂运行）也在改手柄与停车夹紧，同样不标脏；再加上镜像**根本没有** `mmtrBlockStopM`（闭塞停车距离）与任务侧的减速意图 ⇒ 两边剖面不同，每秒被整份快照**拉回一次** ⇒ 看到的就是每秒一记"位移掉帧"，进站尤其明显（§2(2)(3)(4)）。 |
| 「服务端和客户端配合渲染时往往有卡顿」 | 每秒一份 **7.4 KB 整份 JSON**（§1）+ 收到后重建镜像（`new VehicleExtension`）+ 渲染侧平滑参数不匹配（§2(4)）。 |

## 4. 顺手记下的、**不是**本次原因的东西（省下一轮）

- 光场 / 车灯（notes/344/345/367）：只影响**颜色**，不产生位移，也不在积分路径上。
- `[MMTR-LAG] 单 tick 本地位移 0.6 格`（417 条）：那是玩家自己在跑/被车带着走时**每 tick 0.62 格**
  （≈12 m/s）的正常值，`STEP_WARN` 取得偏小；`骑乘车=0` 只是那一刻的骑乘登记不是车——
  与本节三条无关，别被它带偏。
- `[MMTR-PERF] … tick最慢=6x ms`：每 5 s 窗口恰有一条 60+ ms 的慢拍，与本节结论无因果关系，尚未定性。

## 5. 修法（分两层，**建议先落 P0 再做 P1**）

### P0 —— 止血（小改，改完就能实机验证）

1. **驾驶路径标脏**：`applyMmtrControl(...)` 在"镜像会读的字段真的变了"时 `mmtrMarkSyncDirty()`
   （`mmtrActive` / 手柄 / 换向 / 紧急 / 定速 / 灯光），并覆盖"占用锁建立与释放"那两处。
2. **白名单补全**：把 `acceleration` / `deceleration` / `path`（腿阴影）按需补进 `DYNAMIC_KEYS`，
   或者把判据反过来（**允许整份的原因必须显式列出**）——现在的方向是"漏一个字段就多发整份"，
   而实测已经在多发。补一条用例钉住"移动中的脏拍必须是补丁"。
3. **`acceleration`/`deceleration` 补进白名单**（车一动就不再整份）；
   腿阴影 `path` 不进白名单 —— 改按增量走运动流（notes/369 §4.4）。
4. **空补丁按"没有东西要发"处理**（`Client.update` 三支：没有这辆车⇒整份 / 有且真差东西⇒补丁 /
   有但一处都不差⇒与"没脏"同路），已修 + 用例钉住（notes/369 §10 S2）。
5. ~~**30 s 兜底整份改成定时器驱动**~~ **撤回**：非白名单字段一变就必然整份（`diffSection` 直接返回
   false），"漏字段"本来就是自纠的；改成定时器反而在车停着时白花 0.25 KB/s/车。
   真正缺的是"该标脏的地方没标脏"（§2(1)），而那一半交给运动流（notes/369 §3）。

### P1 —— 重构（用户要的"显示系统"）

把**"镜像要复现的物理输入"**与**"画面要用的东西"**彻底分开：

```
① 运动流（新，紧凑二进制 / 定长原语，10–20 Hz）：id、railProgress、speed、
   mmtrActive、手柄三元组、emergency、runStopTarget、闭塞停车距离、mirror 旗标 …   ~40–80 B
   ⇒ 取代"每秒 7.4 KB JSON 顺手把位置带过去"这条路；不再依赖脏拍。
② 状态流（沿用现有 JSON 快照/补丁，低频）：静态块、路径、车底、HUD 文本、任务提示 …（人眼级变化）
③ 客户端显示模型（新）：
   - 本地积分保留（逐帧），但接收 ① 时**不直接改 railProgress**，而是把差值塞进误差缓冲；
   - 误差按**固定时间常数**（例如 150–250 ms）指数收敛，只有"停车/瞬移级"（> 阈值且持续）才硬对齐；
   - 渲染位姿按 tick↔frame 插值（现在渲染直接读积分值）。
④ 诊断：`[MMTR-PERF]` 增列"镜像误差 m / 每秒跳变次数 / 插值残差 mm"，让"平滑了没有"可量化。
```

## 7. 验收配方（任一条改完都这么看）

1. `vehicleSync=patches` 且车开动时 `[MMTR-CL] 车辆包` 应当是 **`补丁=1`**，不再每秒 `整份=1 字节=7xxx`；
2. 司机推手柄后 **≤1 拍**内客户端镜像的 `mmtrActive`/手柄跟上（`-Dmmtr.trace=true` 看 `[MMTR-CL]`/`[MMTR-SYNC]`）；
3. 自己开车：车从静止起步时**画面上不出现"冻住再跳"**（对照 `enabled` 关掉时的观感）；
4. AI 车：进站停车曲线连续、站停起步无阶跃；`[MMTR-PERF]` 的镜像误差/跳变计数趋近 0。
