## 2. 坑 A：世界存档里的车身长度，引擎**真的**在用

判定链（反查得到，不是猜）：

```
Siding.spawnMmtrConsistVehicle → Siding.getTotalVehicleLength
   → VehicleCar.getTotalLength = couplingPadding1 + length + couplingPadding2
   → length 就是 mmtr-rolling-stock.json 每辆车里那个 "length"
```

而**司机座位锚点在骑乘空间的 z = ±12.53**。存档里 br101 是 `length 16.0`（引擎认为车体 ±8.0），
于是 **司机被放到自己车厢端部之外 4.53 m**：

| | 引擎认为的车 | 模型/锚点 |
| --- | --- | --- |
| 车长 | **16.0**（±8.0） | **32.3729**（±16.19） |
| 座位 z | —— | **±12.53** → 超出车端 **4.53 m** |

**所以按 G 之后人可能出现在车头外面**。这是存档数值，不是 G 的逻辑 —— 记下来免得白查一轮。

修复器 dry-run 实测（`fix-rolling-stock-dims.ps1`）：

```
== differences (20) ==
  L1-saf101  br101  length           16  ->  32.3729
  L1-saf101  br101  bogie1Position   -5.3333  ->  -9.2797
  ...
  1          br101  length           16  ->  32.3729      <- br101 在【两个】车厂里都有一辆
  L2-p1      saf101 bogie1Position   -5.3333  ->  -5       <- 另外 8 辆车也有偏差
  ...                                                       （saf101/p1 车长 16 对，但转向架位置不对）
```

> `saf101`/`p1` 的 **±5.3333 → ±5** 是**另一个**既有问题（转向架位置影响过曲线时的表现），

## 3. 坑 B：编组体**静默降级**（改完尺寸后必须复查）

`Siding.java:323-350` 的 spawn 顺序是：

```
consistWalker = mmtrConsistWalkerFromYard(...)
  ├─ 非空 → spawnMmtrConsistVehicle  ← 有驾驶室（cab 命令可用）
  └─ 空   → mmtrMotionWalkerFromYard  ← 退一级
             └─ 也空 → 打一行 "[MMTR-MFST] … could not stage a Motion-Core car"
                       然后 new Vehicle(...)  ← 【遗留整车，没有 consist walker】
```

`mmtrConsistWalkerFromYard` 有一条硬门槛：**车长必须放得下这条道岔股道**（`trainLength <= railLengthM`）。

于是把 br101 从 16 改成 32.3729 之后，**如果那条股道不够长**，车会**静默降级**成遗留整车 ——
面板照画、车照样看得见，**但 `cab` 命令会答「不是编组体车（无驾驶室模型）」，G 一律被拒**。
而且**只有两个 walker 都失败才会打日志**：只掉 consist walker 这一级时**一行日志都没有**。
（股道长度存在 `world/mtr/<dim>/rails/*` 的 MessagePack 里，长度是 railMath 算出来的，离线不好直接量。）

**验收判据**（改完尺寸、重生成/重停 之后按顺序看）：
1. 服务端日志有没有 `[MMTR-MFST] manual siding … could not stage`；
2. 用 OP 命令 `cab <车辆id> A` 试一次，回答是 `已进入驾驶室 1A` 还是 `不是编组体车`；
3. 都没问题再按 G。

## 6. 顺带修掉的一个诊断缺陷：提示日志每帧刷屏

上面那 44 行里，同一秒就打了 13 行 —— 而 `logProjection` 的注释写着它**只在"投影来源变化时"打一行**。
原因是**去重键取错了**：它比较的是 `projectionSource()` 的返回值，而那个串**拼进了每帧都在变的**
`scaleX/scaleY/FOV`，于是去重永远失败、每帧都打。

修法（`MmtrInteractPrompt.logProjection`）：**去重只用稳定的状态串 `lastProjectionSource`**，
每帧数字仍然打在同一行的消息里。

> 这条不在目标范围内，但它**直接妨碍验收**（看日志时被刷屏埋掉关键行），而且只改 4 行。
> **故意没有重编译**（避免打扰正在跑的客户端）：下次重启客户端时由 Gradle 自动编入。
> `check-java-compile` 已过（432 文件）。

### 8.3 把"未生效"改成会说人话（本轮改代码）

原来的失败文案是 `未生效：需停稳 / 驾驶室空闲 / 编组体车（引擎日志有原因）` ——
**最后半句是假的**：§3 那个"静默降级"恰恰**一行日志都没有**，照着去翻日志只会白翻。
现在按引擎镜像状态分级报告，并点名唯一那个不写日志的可能：

```
未生效（驾驶室=无·钥匙=SYSTEM·速度=0km/h）：这里只可能是①别的乘务员拿着钥匙 ②该驾驶室不空闲，
或 ③这列不是 MMTR 编组体车。③ 是不会写日志的（车长超过股道时 spawn 会静默退成没有驾驶室的遗留整车）
——用 OP 命令 `cab <车辆id> A` 复查，答"不是编组体车"就是它 / no effect
```

车速用的是**仪表同一处来源**（`vehicle.getSpeed()*3600`），所以两者永远不会互相矛盾；
车还在动时直接说"车没停稳 —— 停稳后再按 G"，而不是让玩家去猜三个闸门哪个是关的。
