## 1 我做了什么，以及为什么是错的

在处理「V25 雨水面变曲面」时，我为了撤掉自己刚加的一段（"按几何决定雨水面内外侧"）而用了**按行号删除**：

```powershell
$start=(... Select-String "WHICH WAY THE CAB INTERIOR IS" ...).LineNumber   # 模式没匹配到 -> $start 为空
$end2=$end+1
$out = $lines[0..($start-2)] + $lines[$end2..($lines.Count-1)]
```

`$start` 为空时 `0..($start-2)` 在 PowerShell 里等于 `0,-1,-2`（**只有 3 个元素**），
于是 `pack_vehicle.js` 被写成「第 1 行 + 最后两行 + 第 792 行之后的全部内容」——
**文件开头约 790 行被丢弃**。

**这是本仓已经写过的一条规则的直接违反**（见 `MMTR-OBJ车辆-故障谱系与离线判据` 的横向教训）：
**永远不要用模式匹配/行号去删代码，用 `edit` 做字面替换，并且每步之后编译。**
我在同一轮里刚教育过自己，又犯了一次。

发现写坏后我用 `git checkout` 恢复——但 **`mmtr` 的 HEAD 停在 notes/192 时代**
（`6746b9a 打包器"刀片落在端边上"的残差门槛 5 mm -> 30 mm`），工作树里有 **89 个未提交文件**。

**教训**：这份仓库长期不提交代码，`git checkout` 在这里是**危险操作**而不是安全网；
要回退一个文件，先确认 HEAD 与工作树的差距。

## 5 恢复（已完成，且可证明）

用户没有备份，所以只能自己重建。关键在于**这个仓库里存在一份黄金参照**：
`BR101_v46.zip`（写坏之前由完好打包器打出的包）里有那份打包器产出的
**OBJ（3986630 字节）、锚点 JSON、properties、mtl、png**。于是"重建对不对"不再需要猜：

1. **拼接**：把 git 前缀与坏文件里幸存的**真实尾部**（`function buildAnchors(){` 起、到文件末尾，约 1140 行）拼起来。
2. **重建唯一缺失的函数 `toMtrObj`**。契约有四处独立来源，我全部对齐：
   - `notes/194` 的表：MTR **按顶点下标**把第 i 个顶点焊到第 i 个 UV/法线，且**只读面的前 3 个角**
     （所以源 OBJ 的 `v/vt/vn` 三元组**从来不读**，四边形会丢第 4 角）；
   - `verify_mtr_obj.js` 的 L1/L2/L3/L4 判据（布局 / (位置,UV) 对 / 面积 / 包围盒）；
   - `check_pack.py` 的 `v == vt == vn` 检查；
   - 黄金 OBJ 的**实际排版**：`mtllib` 在最前 → 全部 `v` → 全部 `vt` → 全部 `vn` → 按原序的 `g`/`usemtl`/`f`；
     行数正好 = 3×36064 + 19475 + 23 + 24 + 1。
     还从里面读出一个不显眼但关键的事实：`vn` 行**两种格式混用**（`vn 1.000000 0.000000 0.000000` 与 `vn 0 0 1`），
     所以 `toMtrObj` 必须是**原样搬运池中文本**、只重新编号与三角化，**不重新格式化**数值——
     自己格式化成统一 6 位小数就会把几何再悄悄改一遍。

## 7 代价的具体后果：用恢复版打包器打出来的包**仪表会扭曲**（用户实测）

用户装上 v53 后报「仪表面扭曲、雨滴消失」。逐字段 diff v53 与黄金 v46 后，差异**只有一处**——
丢失前缀里的 `buildFacetFields` 是旧版，它对**绕 `up` 折叠**的仪表把 **v 轴也切开了**：

| 字段 | 黄金 v46（健康版） | v53（恢复版） |
|---|---|---|
| `hud_1.canvasHeightM` | **0.283** | **0.3431** |
| 三个折叠面的 `v` 区间 | 每个都是 **`[0,1]`**（共享轴不切） | `[0.589,1]` / `[0.240,0.589]` / `[0,0.240]` |
| 每个面的 `heightM` | 都是 0.283（共享） | 0.3431 / 0.283 / 0.3181 |

仪表贴图按错的 v 窗口画 → **纵向压错、扭曲**。日志里能直接看出这个数：
恢复版打印 `hud facets: ... canvas=1.943 x 0.343m`，健康版是 **0.283m**。
（我上一轮看到 `hud facets` 那行**出现了**就以为恢复了——**"功能出现"不等于"数值正确"**，
应该拿黄金包逐字段比。这是这次判断失误的直接原因。）

**修法（未做）**：`foldAboutUp` 分支的 v 区间应是共享轴的全量 `[0,1]`，`u` 才是被切的那一轴；
`sharedSpan` 也应取共享坐标的整体范围（0.283），而不是各面自身高度的最大值（0.3431）。
**判据是现成的**：修完必须让产出的锚点 JSON 与黄金 v46 的 `hud_*.faces` **逐字段相同**。

## 8 这一轮的交付方式：绕开打包器，只改一个数

既然只有 `waterOffsetM` 需要动，就不要让恢复版打包器碰仪表。做法是
**拿黄金 v46 的包、只改那一个数字、用工程自己的 `zip.js` 重新打包**（`sandbox/_repack_offset.js`），
于是 HUD 折叠面与所有几何**逐字节保持黄金版**。产物 **`BR101_v54.zip`**，与 v46 的对比：

| | |
|---|---|
| 文件清单 / OBJ / MTL / PNG / properties / definition / mcmeta | **逐字节相同** |
| `mmtr_anchors_br101.json` | 唯一不同，其中只有 `windshield.*.waterOffsetM`：−0.05 → **−0.024** |
| `hud_*.faces` / `canvasHeightM` | **完全相同**（0.283）✓ |

**取值依据（射线-三角形求交实测）**：沿司机方向从雨水面出发，最后一道可见玻璃交点的深度
= **中位 18.6 mm、最深 19.2 mm**（68 个顶点）。所以

- **0 mm**（用户最初的想法"曲面就是雨水面"）：水落在玻璃壳里侧 → **看不见**；
- **3 mm**：58/68 个顶点仍在玻璃后面 → **雨滴消失**（v53 的实测）；
- **24 mm**：最坏处留约 5 mm 余量 → 既贴在玻璃上、又稳定在玻璃前面。

也就是说：雨水面被画在玻璃的**外表面**上，而司机要透过约 19 mm 的玻璃看它，
所以"零偏移"在渲染上不可行——**若想真正做到零偏移，应把 `mmtr_windshield_*` 挪到玻璃内表面**（模型侧的改法）。
