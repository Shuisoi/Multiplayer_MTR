| `-147,-60,-169` | 248.2 / 270 / 90 | 21.8° | ✅ 但**模型倒置**：正线远端 = 岔股那条，岔股 = 正线那条 |

**几何说完了一切**：两片区域是两条平行正线（沿 z，`x=-170` 与 `x=-176`，相距 6 格），中间由两条
很浅的斜线相连 —— 一条是两线之间的**渡线**（`-170,-60,-289` ↔ `-176,-60,-253`，两端各一处道岔），
一条是 `x=-176` 那条线**并入** `x=-170` 的汇入（`-170,-60,-199` ↔ `-176,-60,-222`）。
6 格横移要在 23~36 格内走完 ⇒ 岔股夹角**必然**只有 9.5°~14.6°。用户确认：「就是真道岔，只是画得长」。

## 2. 根因：`COS_STRAIGHT = 0.9` 让浅岔股自己也够"直"

老 `MmtrTurnout.resolve` 找直股对的办法是"遍历腿表，遇到互为直股的一对就记下来" ——
**最后遇到的那一对获胜**，而外层是 `Object2ObjectOpenHashMap`（键 = 轨 hex，遍历顺序由哈希槽位决定）。

以 `-170,-60,-289` 实测几何代入（南 17 格 / 北 36 格 / 岔股在 36.5 格处横移 6 格）：

| 进向 | 腿表 |
| --- | --- |
| 南股 | `北(cos 1.00) STRAIGHT`、**`岔股(cos 0.986) STRAIGHT`** |
| 北股 | `南(cos 1.00) STRAIGHT`（岔股 cos −0.986 在身后被排除） |
| 岔股 | `南(cos 0.986) STRAIGHT`（北股被排除） |

三对都"互为直股"：真共线 `(北,南)` 互直度 1.00；含岔股的 `(南,岔股)` 0.986。于是谁最后被遍历到谁赢：

- 含岔股的一对赢 ⇒ **模型倒置**（把岔股当正线、把正线一端当岔股）—— 实测 `-147,-60,-169` 就是这个；
- 赢的那一对恰好"岔股看不见正线另一端"（`legs(岔股)` 里没有北股）⇒ 找不到根部 ⇒ **返回 null**
  （网页退化成 legacy 卡片，**T1 的物理互斥在这一处完全不生效**）—— 实测 `-155,-60,-189` 就是这个。

两个节点几何完全镜像却一认一不认，就是这个顺序运气。**这不是显示问题，是安全缺口**。

## 3. 判据修正（`MmtrTurnout.resolve`）

1. **直股对 = 互直度最大的那一对**：对三根轨两两算 `min(cos(X 看 Y), cos(Y 看 X))`，
   取最大的（要求 ≥ `COS_STRAIGHT`）。真共线 1.00 > 浅岔 0.986，所以答案由几何决定，
   **不再依赖任何遍历顺序**；并列时按轨 hex 定序（仍然确定）。
2. **根部的判定要看两个正线进向**：浅岔口上"另一个正线进向"会因为岔股几乎在正后方（cos ≈ −0.99 < −0.9）
   而根本看不见它 —— 只判一个进向就会把整处道岔判成不存在。现在取"能看见岔股且 cos 更大"的那一侧，
   并要求 cos > 0.1（直角三岔口仍然拒绝，现实里那是两组道岔背靠背）。
3. 三根轨先按 hex 定序，所有"取哪一个"的选择都不再看哈希顺序。

**修后判据只增不减**：能建模的节点集合是旧集合的超集（模型可能从"倒置"变成"正确"，不会从"有"变"无"）。

### 实测：新用例确实抓得住旧缺陷

`MmtrTurnoutResolveTests`（6 例）用**实测世界的真实坐标**：
9.5° 渡线两端、21.8° 那一对镜像、直角三岔口与 120° 三角线仍拒绝、
**遍历顺序无关**（1..24 容量 × 3 种插入次序，每种都断言显式期望几何）、`point why` 的两种结论。

把判据临时改回旧语义（"最后一个够格的获胜"）跑一遍：**6 例里 3 例失败**，
其中包括遍历顺序那条 —— 即**旧代码在不同哈希顺序下真的给出不同答案**（不只是理论推演）。
新语义下 6 例全绿。这条实验是本次"测试有没有牙齿"的证据，不是推测。

## 4. 诊断入口：`point why <x> <y> <z>`

判定过程本身写成一条指令（与 `resolve` 走**同一段代码**，不会与实际生效的模型走偏）：

```
—— 道岔模型（节点 -170,-60,-289）——
结论：认成 1 处单开道岔 —— 根部 … / 正线远端 … / 岔股 …
  轨 … → (-176,-60,-253) 距 36.5 格，离开方向 (-0.16,0.99)
  进向 … 能续行到：STRAIGHT …(cos 1.0) STRAIGHT …(cos 0.99)
  候选直股对 (…, …)：互直度 0.99
  直股对 = (…, …)，互直度 1.0（最直，所以是正线）
  岔股 = …；根部 = …（它看岔股 cos 0.99 > 0 = 迎着开过去看得到岔股分出去），正线远端 = …
—— 当前状态 ——
物理位置 = 0（正线贯通），物理持有者 = （没有），等待队列 = []
  行 … = 腿 0 （位置 0 = 正线贯通）
—— 闭塞归属（这个节点被算在哪条区间里）——
  候选轨 … 是低端=false 是高端=true 节点弧=0.0 离开方向=(0.0,-1.0)
    区间 … 弧[0.0,36.0) 同向=true
```

用户不用再像本次这样从 `mmtr-points` 的 JSON 反推"为什么这条是 legacy 卡片"。

## 5. 连带的两条现场规则（用户 2026-09-14 的选择）

判据修好之后，**5 个既有用例红了** —— 逐个追根，全都是同一个原因：
**这些夹具的岔口此前根本没有物理模型，所以它们编码的是"没有模型时"的语义**。
| 失败用例 | 夹具岔股偏角 | 无模型时的旧语义 | 有模型后的真相 |
| --- | --- | --- | --- |
| `taskTargetIsTheAuthorityOnAnUnsetFork` | 9.9° | "岔口没人决定"⇒ 目标轨直接可走 | 位置默认 0 ⇒ 岔股禁止通行 |
| `taskTakesOverOnceTheOperatorClearsTheBranchBeforeTheFork` | 9.9° | 同上 | 同上 |
| `manualOperatorBranchOutranksTheVehiclesOwnGrant` | 9.9° | 人工设的行没人覆盖 | 逐进向授权兜底每 tick 把位置扳回 0，并顺手重写行 |
| `theLampKeepsItsOwnLegsWhenThePointsMove` | 13.5° | 老模型把岔股叫 `far` | 归属没变，变的是名字 |
| `aMovementIsHeldAtTheJunction...` | 16.7° | S 侧未禁止通行 ⇒ 车能进岔前 | 位置 0 ⇒ S 侧禁止通行 |

前两类是**设计取舍**，因此请用户当场定：

### 5.1 联锁按意图扳岔（选择 ①）

**规则**：人工位 / 授权 / 任务目标这条"想走哪条腿"的意图一旦确定，就把道岔扳到它要的那一位。
实现 `MmtrForkElection.elect` → `Simulator.mmtrThrowTurnoutForIntent`，**两道闸门**：

- **人工锁着的不扳**（人工优先，见 5.2）；
- **有人物理持有也不扳**（T1：不许把道岔从列车脚下抽走）。

与设计 §5.3"玩家不扳岔，联锁扳岔"一致。之前缺这一步的后果是：任务目标指向岔股时列车在岔前干等
（旧世界靠"没有模型"蒙过去了）。

### 5.2 人工搬岔 = 覆盖 + 锁定（选择 ②）

**规则**：`point set` / 网页搬岔 = 设位置**并锁住**该道岔（三个进向一起锁，一处道岔只有一个位置）。
因为"人工 operator > 显式任务/进路申请"，不锁的话在途授权下一个 tick 就把位置扳回去了。

- 入口：`Simulator.mmtrOperatorSetTurnoutPosition`（`mmtrSetPoint` 的 branch ≥ 0 走这里）。
- **锁随存档落盘**（`mmtr-points.json` 新增 `locks` 段）：只存位置的话，重启后自动进路会把位置
  按授权扳回去，"人工优先"只在当前进程里成立 —— 用户要的是"永久生效直到解锁"。
- **`branch < 0`（清掉人工位）不锁**：那是"没有人工意见"，不是"人工把它锁在 0"。
  （`MmtrPointDefaultZeroTests` 就是测这条的，语义保持不变。）
- 解锁：既有的 `point unlock`。
- 副作用（实测踩到并已处理）：**测试夹具会互相污染**（上一跑留下的锁让下一跑从一开始就锁着），
  所以用例收尾必须 unlock + 归位；`build/` 下已被污染的夹具目录已清。

### 5.3 车压在岔上 ⇒ 拒绝人工扳岔（选择 ③，用户 2026-09-14 追加）

**规则**：岔区净空被占时，人工扳岔**被拒**并给出可读原因（`MmtrJunctionState.blockedThrowReason`）。

- 判定与**灯显示"岔区净空被占"读同一段代码**（`foulingRail`）：否则会出现"这盏灯说岔区被占、
  道岔却照样能扳"这种自相矛盾的状态。指令层把这句话**原话**回给操作者
  （`Simulator.mmtrLastOperatorThrowBlockedReason` → `point set` 的失败文案）。
- 同一道闸也加在**意图扳岔**那条路上（`mmtrThrowTurnoutForIntent`）：任务目标/授权也不许把道岔
  从车下抽走。于是"扳岔"的三条路上有两条有闸（人工、意图），**自动授权同步那条还没有**（见 §8）。
- "压在岔上"用的是显示层同一条量纲：车体与 10 m 净空区的重叠要达到**半车长**
  （`foulsZone` 的松弛，notes/101 —— 不让"尾巴刚擦到边"误报）。所以它拦的是**骑在岔上**的车
  （车体盖住净空区），不是尾巴刚过节点的车；后者由走行侧那道更敏感的闸（走行器自己的 10 m 判定）拦。
- 被拒**不算人工位**，不留下锁（不然一次误操作就把道岔永久锁死了）。
- 这条规则有个漂亮的推论：**"另一条进路上的车被清空区挡住"这种场景在有模型的岔口上已经没有可能**
  —— 因为清空区被占时道岔根本扳不过去，第三进路无从出现。清空区规则真正守的是**同一进路上的后续车**。
  `MmtrJunctionClearanceTests` 因此按这个形状重写（见 §6）。

  先断言显示层说"岔区被占"，再断言扳岔被拒（两者必须一致）、原因是可读的、位置没动、**没留下锁**；
  车开出净空区后同样的扳岔照常受理（证明闸门不是"一律不许扳"）。
