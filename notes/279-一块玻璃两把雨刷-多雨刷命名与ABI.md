# 279 - 一块玻璃两把雨刷：多雨刷命名、ABI 与执行顺序

> 用户口径（本会话）：「先改第一项，使其能够在一个车窗上应用 2 个雨刷」。
> 起因：SAF420 控制车的风挡模型里已经画了**两把**实体雨刷（`wiper_1_1` / `wiper_1_2`）与两个作用面，
> 但游戏侧当时是**一把雨刷 = 一块玻璃**（`MmtrWindshield` 的注释原文：*"ONE wiper per anchor. A pair of
> wipers is two mmtr_windshield_<cab>_<pane> quads"*），于是"一块玻璃两把雨刷"这件事**表达不出来**。
> 本文冻结新口径，改的是**逻辑**（打包器 + 客户端），模型命名随后按这个口径调整。

## 1. 结论（新口径）

**一块玻璃可以有多把雨刷**，语法是在原有索引后面**再加一个索引**：

```
mmtr_windshield_<驾驶室>_<玻璃>              玻璃，仍然只有一个锚点
mmtr_wipersweep_<驾驶室>_<玻璃>[_<第几把>]   该玻璃第 <第几把> 把雨刷的作用面；缺省 = 1
wiper_<驾驶室>_<玻璃>[_<第几把>]             该把的刀片
wiperarm_<…> / wiperrod_<…>                  该把的臂 / 拉杆
```

- **第三个索引只在不是 1 的时候写**，所以老模型（`wipersweep_1_1`、`wiper_1_1`）**逐字节不变**。
- `mmtr_wipersweep_1_2` 仍然是"驾驶室 1、第 2 块玻璃、第 1 把"——第三个索引是**追加**的，不抢原有的两位。
- 一块玻璃两把雨刷 **≠** 两块玻璃：玻璃锚点（下雨的平面）只有一个。

## 2. 打包出来的配置形状（ABI）

按**该玻璃的扇形个数**自动决定，人不写：

| 扇形数 | `windshield["windshield_<cab>_<pane>"]` 的形状 |
| --- | --- |
| 1 个（索引 = 1） | **扁平**：`pivotU/pivotV/armM/parkAngleDeg/sweepDeg/sweepSign/…` —— 与多雨刷出现之前逐字节一致 |
| ≥2 个 | 玻璃级字段扁平 + `"wipers": [ { "wiperIndex": 1, … }, { "wiperIndex": 2, … } ]` |

- 字段被**分成两层**（这是整件事的关键，也是唯一的结构性改动）：
  - **每把雨刷一份**：`wiper`、`drawBlade`、`dualWiper`、`armM`、`parkAngleDeg`、`sweepDeg`、`sweepSign`、
    `periodS`、`pivotU/V`、`bladeWidthM`、`colour`、`armColour`、`pivot2U/V`、`bladeAU/AV/BU/BV`、`pinAU/AV/BU/BV`
  - **玻璃一份**（两把共用）：`raindrops`、`fallMps`、`maxStreakM`、`snow`、`waterOffsetM`、雨滴物理
    （`creepMps`…`runoffMps`）、`pushM`、`mergeDistanceM`、`collectZoneM`、`densityCellM`、`densityThresholdPerM2`
- `wiperIndex` **显式写进每个元素**，不靠数组下标。理由与"编号不连续"这一族坑同源：
  模型只画了第 2 把、或编号 1/3 时，按下标对齐会**静默**把配置接到另一把刀片上。
- ≥2 把时**不写**扁平的那份 per-wiper 字段（避免"到底哪份生效"的歧义）；
  作者在车型 JSON 里写的扁平 per-wiper 字段此时是**每一把的默认值**，而 `"wipers": [..]` 按下标覆盖。

## 3. 客户端做了什么（`MmtrWindshield.java`）

- `WindshieldConfig` 拆成 **玻璃配置 + `WiperConfig[]`**；`WiperConfig` 容纳原来散在玻璃配置里的
  per-wiper 字段与其方法（`armM` / `usesBandWipe` / `bladeSegmentM` / `followerEndFor` / `assemblyMode`）。
- `State` 的**单份**雨刷状态（角度/相位/行程方向）变成 `WiperState[]`（每把一份）；
  水滴场仍然是**每块玻璃一份**——雨是玻璃的属性，不是雨刷的属性。
- 每帧顺序：`advanceWipers()` → `applyWipe()`（**两把依次**跑同一片水滴场）。
- **水归把它推走的那把**：`Drop.carriedByWiper` 记录归属，另一把的通过**完全跳过**该雨滴。
  没有这一条，两把的"到端释放"会互相判反，水会在行程中间被放下（等于把 206/208 修好的水带模型重新打坏）。
- 实体件：`wiper_<cab>_<pane>[_<n>]` 的正则加了可选第三索引，按 **`wiperIndex`** 取那把的配置
  （找不到就**留在停放位**并打一条 `[MMTR-WSHLD]` 日志，绝不驱动另一把）。
- 部分改动是**同名不同物**：`drop.carriedByBlade` 保留为"是否被某把推着"，新增 `carriedByWiper` 记录归属。

## 7. 落地：SAF420 的第一次真机打包（同轮后续）

### 7.1 模型侧改名（`saf420cab.blend`）

`mmtr_wipersweep_1_2` / `wiper_1_2` / `wiperarm_1_2` → **`mmtr_wipersweep_1_1_2` / `wiper_1_1_2` / `wiperarm_1_1_2`**
（纯改名，几何一行未动；同时改了同名的 mesh datablock 与 action）。

**为什么确定"这是一块玻璃两把雨刷"而不是两块玻璃**（`_rename_wipers.py` 量的，玻璃域米制）：
两个扇形**各自 26 个顶点全部落在 `mmtr_windshield_1_1` 的平面上（离面 0.0000 m）**；
刀片离面 21.3 mm（骑在玻璃表面上，正常）、臂离面 80.9 mm（主轴在屏下，正常）——
两把的这两个数**逐位相同**，正是镜像成对的样子。

### 7.2 打包（`SAF420_v1.zip`，3 个 vehicle）

`mmtr/tools/obj-mtr-packager/consist/saf420.json`：`saf420cab_a`（`rotationDegY: 0`）+
`saf420cab_b`（**180**，`groupRename` 把锚点与雨刷件全部改到 2 号）+ `saf420car`。

- **`rotationDegY` 必须是 0，不是 −90**：`-90` 是给 Create/MineToMesh 那种"车长沿 X"的 OBJ 的；
  本工程的 OBJ（`forward_axis="Y", up_axis="Z"` 导出、Blender 里车长沿 Z、车头 −Z）与 BR101 同族
  （`vehicle.br101.json` 用的就是 **0**）。用 −90 打出来的锚点会**沿 X 排开**（`windshield_1_1 x=+9.70`），
  车在游戏里就是横着的 —— 而且没有任何报错。改 0 之后：cab A 的 `hud_1 z=−9.312`、cab B 的 `hud_2 z=+9.312`。
- `couplingPadding1/2 = 0.525`（两节车之间 1.05 m）—— 用户口径"车门间距与 cab 相接时为 4 m"：
  两端门洞到车端的余量各 1.475 m，1.475 + 1.05 + 1.475 = **4.000 m**。
- `extraDoorways: ["cabdoor_1_1","cabdoor_1_2"]`（司机门不在 `door_l*`/`door_r*` 命名族里，
  不点名就没有 DOORWAY，机组上不了车）。
- 反向车**没有**翻门滑向（`doorSlideByGroup`）：`rotationDegY` 是把顶点**烘进 OBJ** 的，
  所以门叶与门洞一起转，收纳槽方向相对车体不变。notes/46 当年翻了，但那份备注自己写着"待目视确认"，
  且与本条推理相反 —— 实机若发现尾车门开反，改的是这里。

### 7.3 两个工具的真缺陷：**停放位那条边会冒充"远端盖"**

第一次跑 `verify_windshield.js` 对 cab 报了 **`sweepDeg 88.8 != 0.250`** 的 FAIL，而打包器写的是 88.80。
两边的候选边集合都没问题（都是"只属于一个面的边"）；错在**选择规则**：

> 停放位的刀片**就躺在那条盖边上**，所以把它转动 0.25° 仍然离那条边只有 4.7 mm ——
> 比真正的远端盖（90.00°，26 mm）更"像"。两边原本都用 `|phi| > 0.2` 这个阈值排除停放位，0.25 正好溜过去。

独立实测（`_wiper_caps.py`，按"只属于一个面"取边界）证明**模型是对的**：
两个扇形的两条盖边分别与"刀片"和"刀片绕配置支点转 90.000°"重合到 **10.6 mm / 26.1 mm**（都是刀片半厚量级），
**两条盖边的方向正好相差 90.000°**。

修法（两个工具同改）：先把"最靠近 phi = 0 的那条匹配边"认作**停放位盖**并**按身份剔除**，
再在剩下的边里选远端盖；剩下的必须 `|phi| > max(2°, 极点+1°)`。
- BR101 回归：四条玻璃的行程**逐位不变**（80.55°，残差 4.4 mm），现在多打一行 "park cap … dropped"。
- `selftest.js` 37/37 仍全绿（我的改动没有削弱任何注入用例）。
- 顺带把 `verify_windshield.js` 教会了 `groupRename`：反向车是"同一个 OBJ + 打包时改名"，
  不认这件事的话 cab B 会满屏 "no mmtr_wipersweep_2_1 object in the source OBJ"，看着像模型坏了。

## 8. 控制模式：单手柄 P5+B8+EB 的客户端半（同轮）

引擎早就支持有级（`NotchedDriveController` 读 `ControlState.throttleNotch` / `brakeNotch`，
档数来自车底配置），缺的是**客户端发不出这两个字段**：`MmtrDriveInput.send()` 里
`throttleNotch` **硬编码 0**、`emergency` 恒 false（注释原文："老车底（NOTCHED/STEPLESS/AIR_BRAKE）
本轮不由新键位驱动"）。于是有级车底在游戏里**只有制动、永远没有牵引**。

现在按镜像的 `mmtrMode` 分流：

| 车底 | 客户端发什么 |
| --- | --- |
| `THREE_HANDLE` | 照旧：`driveHandle` + 制动位（11 位手柄），`throttleNotch = 0` |
| 其它（NOTCHED / STEPLESS / AIR_BRAKE） | **一根杆**：`+1…+P` 牵引、`0` 惰行、`−1…−B` 制动、`−(B+1)` **EB**，折成 `throttleNotch` / `brakeNotch` / `emergency` |

- 档数 `P` / `B` 来自镜像里**已经存在**的静态字段 `mmtrPowerNotches` / `mmtrBrakeNotches`
  （`VehicleSchema`；故意不在增量补丁白名单里，随整份快照下发 —— 见
  `VehicleSyncPatchTests.staticFieldsAreNotInTheWhitelist`），客户端加两个 getter 即可，**不动引擎、不用重同步 jar**。
- 键位：牵引键与制动键**推同一根杆**（牵引键往牵引侧、制动键往制动侧，另一侧回退）——
  真车单手柄就是一根杆，两对键都给，玩家不会"按了没反应"；`handleChangedThisTick` 照旧驱动"动操纵即接管司机位"。
- HUD：单手柄车底只显示**一行**「手柄」（并排两行会让人以为有两根杆）。
- 离开司机位时单手柄归 0（惰行），与三手柄的"关闭/运行/定速 0"同一个道理。
- 编译：`check-java-compile.ps1` 448 源 / 658 类 **OK**。

车底配置（`mmtr/config-example/consist-types.json`，已 `apply-consist-config.ps1` 合并进 4 份世界/存档）：
新增 `saf420_trailer` / `saf420_motor`，两者都是 `controlMode: NOTCHED` + **`powerNotches: 5` +
`brakeNotches: 8`**（换端后同一根杆档数不变），`carTypeIds` 把三个 vehicle id 都指向拖车口径
（动车要在编组里逐车显式给 `powered: true` + `consistTypeId: saf420_motor`，写错也不会误牵引）。
⚠️ **力学量级是占位值**（用户还没给 SAF420 的牵引/制动数据表）：操纵口径是真的，加减速手感与制动距离不可信。

## 9. 车底数据（E235 口径 → 一节车）

用户给的参考是 **E235系0番台（山手线 11 节 6M5T）的整列口径**：空车 349 t、100% 满载 444～452 t、
200% 超员 540～555 t；整列最大起动牵引力 310～420 kN、常用最大制动 440～580 kN、紧急峰值 540～720 kN，
且说明现代通勤电车有**应荷重控制**（力随载重自适应，不是固定机械力）。

MMTR 的模型是**逐车**质量/力再求和（`MmtrComposition`），所以整列口径要折成一节车。**全部推导写在
`mmtr/config-example/consist-types.json` 的两个 `saf420_*` 条目的 `_comment` 里**（那是这些数字的真源），要点：

| 量 | 取值 | 来源 |
| --- | --- | --- |
| 质量 | M 34.0 t / T·Tc 29.45 t | 349 t ÷ 11 = 31.73 t/车 → 12 节 380.7 t，按 M 比 T 重 4.5 t 拆 |
| 最大起动牵引力 | 60.8 kN × 6 = **364.8 kN** | 用户区间中值 365 kN ÷ 6 节动车 |
| 功率 | 676 kW × 6 = 4.06 MW | **假设**：保持起动牵引力到 40 km/h（P = F·v），用户没给功率 |
| 常用制动 | 逐车 47.1/45.6 kN → **556.4 kN** | 用户中值 510 kN × 12/11（我们多一节拖车） |
| 紧急制动 | **687.3 kN** | 用户中值 630 kN × 12/11 |
| 制动重量 | 60.8 t / 紧急 76.5 t（每车同口径） | 用 `BrakeSpec` 的 UIC 反推式 `a = 0.0065λ + 0.12` **解**出来的，不是按 kN/t 拍的 |
| 定员 | `payloadKg` 18000 | 100% ≈ 9 t/车、200% 超员 ≈ 18 t/车 ⇒ `loadRatio` 0.5 = 定员、1.0 = 超员 |

**没有应荷重控制**：模型里质量是"整备 + loadRatio × 定员"，司机只能靠 `loadRatio` 逐车设载重，
所以用户说的"空车到超员都保持恒定加减速"这一点**当前模型做不到**（要做就是另一件事：按载重缩放牵引/制动力）。
唯一凭假设填的是**功率**（由"折点 40 km/h"反推），真车折点更高就把 `maxPowerW` 调大。

## 10. 车门：两叶门被"整侧一个滑向"打坏（同轮发现并修）

打包器给门叶的滑向默认是**按车侧**定的：`door_l* → +slide`、`door_r* → −slide`。对"一个门洞一片叶"
的车型（MTR 自带模型、HST_B）这是对的；**本车每个门洞两片叶**（両開き 通勤门，实测：每侧 3 个门洞、
每洞 2 片 0.990 m 的叶），于是**每对叶里有一片朝自己的门洞里面滑**——开门时两片叠在半边门上。

新判据 `mmtr/tools/anchor-check/verify_doors.js`（`--config`）从**打包后的几何**判：

- D1 每个 `door_l*/door_r*` 组在 properties 里**各自是一个部件**（否则它动不了）；
- D2 按间距把叶片归成门洞（同洞两叶相距 ~0.1 m，下一个洞隔 6 m，所以 0.15 m 分界无歧义）；
- D3 每片叶的 `doorZMultiplier` 必须把它送**离门洞中心**。符号口径：MTR 把偏移加在部件的
  **打包后 Z** 上（`ModelPropertiesPart:399`），而本工程的模型 `+Z = 车尾/B 端`（锚点自证：cab 的
  `hud_1 z=−9.31`、`hud_2 z=+9.31`），所以 −Z 侧那片取 −、+Z 侧那片取 +。

实测（修之前）**三节车各 6 片叶反向**（每洞每侧一片）；修法是在 `consist/saf420.json` 里逐叶写
`doorSlideByGroup`。**反向车（cab_b）的符号是正向车逐叶取反**——`rotationDegY` 把顶点烘进 OBJ，
同一片叶在打包后落到镜像位置（`door_l_1` 从 z −5.2 变 +5.2），所以同一套符号不能照抄。
修后三节车 `verify_doors` 全 PASS，`selftest` 新增一条门叶套件（3/3 抓到，总数 **40/40**）。

顺带修了 `verify_mtr_obj.js` 的一处路径不一致：它只对 `sourceObj` 解 `${MC_ROOT}`，
`stagingDir` 里的占位符被当成字面路径（于是"打包好的 OBJ 找不到"）。同时新增
`example/vehicle.saf420cab_a.json` —— 控制车的**单车型配置**（稳定 staging 目录，不进 `%TEMP%`），
离线判据与 selftest 都对着它跑。

## 11. 控制模式实跑（离线，真引擎 + 真配置）

`sandbox/Saf420ControlProbe.java` + `sandbox/run-saf420-probe.ps1`：**用引擎自己编译好的类**
（`mmtr/engine/build/classes/java/main`）+ gradle 缓存里的 gson/fastutil/jspecify，`javac`/`java` 直接跑
—— 不碰 gradle（dev 会话占着项目锁，notes/195），也不碰游戏。它读**真的** `consist-types.json`、
按**世界清单里那 12 节**（Tc-M-M-T-T-M-M-T-T-M-M-Tc）建 `MmtrComposition`，然后把单手柄逐位推一遍。

| 手柄位 | 实际加速度 | 折算力 | 用户给的 E235-0 区间 |
| --- | --- | --- | --- |
| +5（满牵引） | 0.886 m/s² | **364.8 kN** | 310～420 ✓ |
| −8（全常用） | −1.374 m/s² | **556.4 kN** | 440～580 ✓ |
| EB（−9） | −1.696 m/s² | **687.4 kN** | 540～720 ✓ |

逐位均匀（牵引每档 73.0 kN、制动每档 69.5 kN），牵引联锁也验了（P5+B8 同时给 ⇒ 加速度不为正）。
整备 380.7 t 与推导逐位一致。

**跑出来一个引擎侧的空档（未改，报备）**：`brake model: pneumatic=false perCar=true aggregate bar spec: ABSENT`。
多节编组时 `Vehicle:4468-4472` 会把车底换成 `MmtrComposition.toConsistType(...)` 的**等效车底**，
而它**不传 `PneumaticBrakeSpec`**（`Vehicle:4491` 倒是把逐车 `brakeCars()` 塞进了制动模型，
`BrakeModel.ensure` 也确实会用逐车列表 —— 但没有 bar 口径就整段不接管）。后果：

- 制动力**是对的**（等效车底带着按车求和的 UIC 制动重量，`NotchedDriveController` 走减速度那一支）；
- 但**没有管压/缸压动态、没有尾车滞后**，HUD 的管压/缸压行显示的是归一化读数而不是 bar；
- 我给 `saf420_*` 填的 bar 键目前因此是**惰性的**（对三手柄车底不是这样：三手柄的位置表里带着 bar 规格）。

一行修法（**没有替你改**，它影响全项目所有有级/无级多节编组）：
`MmtrComposition.toConsistType` 的构造函数最后一个参数由 `null` 改成 `lead.getBrakes()`。
要不要动、什么时候动，你定。

## 12. 登车面：门洞箱与地板（同轮补进 D4）

`verify_doors.js` 现在连"门开了但上不去车"这一族一起判（**D4**）：打包器为**每片叶**生成一个
`doorway_<叶名>` 箱 + 一块 `floor`，而"某片叶没有门洞箱"是一扇**开在实心墙上**的门 —— 门叶会动、
门洞什么也不做，且没有任何地方会说。判据：每片叶都有自己的门洞箱且**箱的 z 跨度盖住该叶**，
有门洞的车必须有地板。

实测（三节车）：`doorway_*` 14 个（12 片客车门叶 + 2 扇司机门，后者靠 `extraDoorways` 点名）、
`floor` 1 块；每片叶的门洞箱都盖住自己 ✓ `PASS`。
