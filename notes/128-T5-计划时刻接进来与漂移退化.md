## 1. 计划时刻的来源：**本来就有，只是没人接**

上一轮说 T5 剩余部分"缺输入：趟次表来自 P 系列"。这轮先核实了一遍，发现**计划时刻在代码里已经存在**，
只是没有一路接到进路/道岔上：

| 环节 | 事实 |
| --- | --- |
| 任务 | `MmtrTask.earliestMs` / `dueMs` 已有时刻字段（任务系统设计 §1「任务 = 某时 × 某地 × 某操作」） |
| 作业单 → 任务 | `MmtrJobScheduler` 用 `MmtrTaskFactory.fromStep(step, …)` 实例化任务，`MmtrJobStep.dueTimeOfDayMs` 带时刻 |
| 任务 → mission | `MmtrJobScheduler:748` `mission.attachTask(task)` —— **生产路径确实挂了** |
| mission → 进路 | ❌ 修前**断在这里**：发布进路时没人读它 |

所以本片不需要造趟次表，只需要把**已有的那一段**接上：

```java
// Vehicle.armMmtrPointRun
publishedRoute.setPlannedMillis(mmtrPlannedMillis());   // ← 新
// Vehicle.mmtrPlannedMillis(): task.earliestMs > 0 ? task.earliestMs : task.dueMs
//                               两者都没有(0) ⇒ Long.MAX_VALUE = 无计划
```

同一时刻也交给**道岔申请**（`requestAtomically(…, priorityMillis)`，T1b 二 早就留好的入口）——
于是**两处仲裁（进路 SET、道岔队列）用的是同一个计划时刻**。

## 2. 裁决链（现在三档齐了）

```
计划时刻（有效）> 到达序 > 防饿死（道岔队列那一侧）
```

- `MmtrRoute.plannedMillis` **不进** `sameMovement`：计划随晚点变化，不该换掉进路对象（身份不churn，
  notes/78），但值要刷新 —— 有专门用例钉住（`replanningTheTimeKeepsTheRouteObjectButUpdatesItsPlannedTime`）。
- **没有计划的进路排在最后**。

## 3. 漂移退化策略（T5 的第三条验收）

判据**不需要时钟**：这条进路**申请的时刻**晚于它自己的**计划时刻** ⇒ 计划槽在它来要之前就过了 ⇒
计划作废，退回到达序。

```java
private static boolean hasLivePlan(MmtrRoute route) {
    final long planned = route.getPlannedMillis();
    return planned != Long.MAX_VALUE && planned >= route.getRequestedMillis();
}
```

**没有这一条，"计划优先"会变成"僵尸优先"**：晚点很久的车计划时刻仍在过去，于是永远"更早"、永远赢。
退化不惩罚它，只是不再让它靠计划占先。

> 这条规则立刻**反噬了我上一轮写的用例**：`plannedTimeDecidesConflictsNotArrivalOrder` 里我给一列车设的
> "计划时刻"（500）早于它自己申请的时刻（2000）—— 按新定义那就是**过期计划**，用例红了。
> 红得对：那本来就是"申请时槽已经过了"的不可能局面。改成两条**未来**槽（先申请的槽更晚、后申请的槽更早）
> 之后才表达出我真正想断言的东西。**第五次被验证改写结论。**

## 4. 计划 / 实际对照（T5 第二条验收）

feed 的每车 `route{}` 并排给出两个钟点：

```
requestedMillis —— 实际申请的钟点（实际）
plannedMillis   —— 计划时刻（计划，-1 = 无计划）
planStale       —— 该计划是否已经漂移
```

运营台据此就能做"计划 vs 实际"的对照（数据已齐，画表面板属网页层，见 §6）。
