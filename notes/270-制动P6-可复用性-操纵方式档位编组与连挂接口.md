# 270 — 制动 P6：把制动模型做成可复用的（操纵方式 / 档位 / 编组 / 连挂接口）

用户口径（2026-09-26）：

> 「尽量使其更加可复用，因为不同列车逻辑不同，操作也不同，手柄档位也不同，车体连挂形式也不同
> （需要留连挂接口）」

## 1. 拆之前是什么样

P1–P5 把气压模型做进了 `ThreeHandleDriveController`：管压/缸压状态、分配阀、电空混合、逐车传播、
黏着截断、连挂接口（`encodeAirState`/`applyAirStateString`/`seedAirStateAfterCoupling`）**全在这一个类里**。
后果：

- 有级/无级控制器想用同一套气压模型，只能把 `ensureBrakeSystem`/`syncNormalizedFromSystem`/
  `encode/apply/seed` 抄一遍 —— 抄完就有三份"气路"要同步维护；
- `Vehicle` 的连挂接口（解挂切分 / 连挂播种）**写死了 `instanceof ThreeHandleDriveController`**，
  换一种操纵方式就静默失效（连挂不再保气压）；
- `BrakePipeNetwork`（notes/268 P5）只有三手柄在用，其它模式是"另一条路"。

## 2. 拆成四层（"不同"各有一个落点）

| 不同 | 落点 | 说明 |
| --- | --- | --- |
| 列车逻辑 | `PneumaticBrakeSpec` / `AdhesionSpec` / `BrakeSpec` | 已是配置；每节车还可各自覆盖（`BrakeCar.spec`） |
| 操纵方式 | `DriveController` + **`BrakeCommand`（新）** | 控制器只做"手柄 → `demandRatio/assistRatio/emergency`" |
| 手柄档位 | `ThreeHandleSpec` / `ConsistType.brakeNotches` / `airPipeTargetsBar` | 档数、级位表都是数据 |
| 连挂形式 | **`List<BrakeCar>`（新）** + 状态串 | 一列车就是一串车；合并/切分就是拼接/切分 |

新增/改动的类：

| 文件 | 作用 |
| --- | --- |
| `mmtr/brake/BrakeSystem.java`（新） | 与操纵方式无关的那一层：逐车管压 → 分配阀 → 缸压 → 电空混合 → 逐车力（`BrakePipeNetwork` 整体并入，旧文件**删除**） |
| `mmtr/brake/BrakeCar.java`（新） | 一节车的制动能力：锚（常用/紧急）、是不是动力车、自己的气压口径 |
| `mmtr/brake/BrakeCommand.java`（新） | 与操纵方式无关的诉求：`demandRatio` / `assistRatio` / `emergency`（`notched(...)` / `ofRatio(...)`） |
| `mmtr/brake/BrakeModel.java`（新） | **模型宿主**：任何一个控制器挂一件 ⇒ 归一化读数、整列气制动力、牵引联锁、逐车 bar 读数、连挂状态串 |
| `mmtr/BrakeCarrier.java`（新） | "带制动模型"的能力接口（与 `AirBrakeStateful` 同一手法：按能力分派，不按具体类型） |
| `NotchedDriveController` / `SteplessDriveController` | 配了 bar 键就走同一个 `BrakeModel`；实现 `BrakeCarrier` + `AirBrakeStateful` |
| `MmtrComposition.brakeCars()`（新） | 连挂形式的装配点：逐车锚/动力/口径（旧的三个 `carXxx()` 数组访问器删除） |

## 3. 顺手钉死的一条口径：紧急级不该被"连续诉求"够到

级位表的**表尾是紧急/快排级**（默认表 `5.2…3.6,3.5` 之后还有 `3.0`）。三手柄的档位本来就含紧急位
（由 `ThreeHandleSpec.isEmergencyPosition` 判定），但**无级手柄推到底、货车最后一档都应该是全常用 3.5 bar**。
所以新增 `PneumaticBrakeSpec.getServiceDemandLimit()`（= 表里"全常用"那一档的位置比例，默认 `0.9`）：

- 三手柄：`demand = 档位/(档位数−1)`（逐位不变，P1 起的数一个不动）；
- 有级：`demand = 档/档数 × 0.9`（最后一位 = 全常用）；
- 无级：`demand = 制动轴 × 0.9`；
- 紧急一律走 `BrakeCommand.emergency`（快排 + 紧急限压 + 紧急力锚）。

`Vehicle` 的分派也一并改成按能力：

- 连挂接口（快照/灌回/连挂播种）：`BrakeCarrier` + **车底有没有 bar 键**（判据用车底而不是"模型里有没有系统"，
  因为连挂手术常发生在"新车还没人开"的那一拍）；
- `getMmtrPneumaticBrakeForceN()`：任何 `BrakeCarrier` 只要在跑气压口径就取模型的逐车求和。

**"迟到的状态串"**：`BrakeModel.applyState()` 在系统还没建时先存进 `pendingState`，第一拍建系统时灌进去 ——
否则解挂切分留下的那段半充气车列会在重建瞬间被当作满管。

## 4. 抓到的缺陷（已进用例）

**常用制动支路忘了记整列气制动力** ⇒ `getLastPneumaticBrakeForceN()` 在服务制动时恒为 0
⇒ 镜像给客户端的"气"那份为 0 ⇒ **HUD 在司机拉闸时只显示电制动**，正是 notes/269 现场那个症状的另一个入口
（修好之后 `MmtrPneumaticBrakeTests` 的现场场景重新打出 44.6 kN）。修法：服务支路写入逐车求和的结果，
读数按 `BrakeCarrier` 分派（有级/无级现在也有这一份）。

另外 `BrakeModel.isPerCar()` 的语义从"系统建起来没有"改成看**连挂形式**（车列长度）：装配完车列、
还没跑第一拍时也该是 true（连挂手术就发生在那一拍）。

## 5. 验证（`MmtrBrakeModelReuseTests`，dt = 50 ms）

```
全常用位：机车第 9 位 = 3.50 bar，常用诉求上限 0.90
诉求 0.1…0.9：三手柄 = 有级 = 无级（20.8 / 35.6 / 50.4 / 61.5 / 72.6 / 80.0 / 87.4 / 94.8 / 102.2 kN）
逐车口径：机车缸压 3.80 bar、客车 2.00 bar（客车自己的上限 2.0）
迟到的状态串：建系统后管压 2.098 bar、缸压 1.965 bar
```

- **同一诉求 ⇒ 同一个力**：三种操纵方式逐位相同（7 条断言 × 9 个诉求）；
- **档位只是数据**：`notched(8, 11)` 与 `ofRatio(0.8)` 逐位相同，且落在级位表第 8 位（管压 3.6 ⇒ 缸压 3.55 bar）；
- **每节车可以有自己的口径**：客车按自己的缸压上限 2.0 bar 封顶；
- **连挂接口**：状态串往返（切分 → 各自跑 → 重新合并）后逐车缸压跟着走；`seedAfterCoupling` 只把新车清零、
  动力车不受影响；系统没建时收到的状态串不丢；
- **零回归**：没配 bar 键的车底三种操纵方式都不接管（`isPneumatic()` 假、bar 读数 0），有级那一支逐位等于
  `serviceBrakeDecelerationMps2(档/档数, v)`；
- **牵引联锁与灯**：闸没排空时推牵引"一份力都不加"（与不推牵引逐位相同），惰行不许点亮制动灯。

全量：**845 条，失败 3 条**（仍是那 3 条预先存在的世界存档漂移：`MmtrConsistMultiCarPlacementTests` ×2、
`MmtrTrainCarsJsonTests` ×1，都在找存档里一个不存在的 sidings，与本轮无关）。

## 6. 还剩哪些"没解耦"（写在明处）

- 系数仍是硬编码（UIC 0.0065/0.12、Curtius-Kniffler 7.5/44/0.161、闸片形状）；
- 单管模型：没有空重车调整、分配阀两段动作、闸瓦间隙；
- 没有轮对滑移状态（S3）、没有车钩多体（S5）；
- 逐车充排气速率用的是**说话那节车**的口径；
- 异型重联的电制动仍是编组级一个数；
- `AirBrakeController`（AIR_BRAKE 模式）与 `MmtrComposition` 仍在旧的归一化气路上 —— 本次没有搬它，
  因为那条路是"另一个车型族的操纵语义"，要搬得先有它的实机口径。
