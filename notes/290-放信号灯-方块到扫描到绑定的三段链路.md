# 290 · 放信号灯：方块 → 扫描登记 → 绑定，三段缺一不可

> 用户口径（2026-09-25）：**「你能放信号灯吗」**。
> 答案是**能**，而且本轮已经真放了一盏并绑好（见 §5）。这篇是把"放灯"这条链路的契约钉下来。

## 1. 关键事实：`signal set` **不摆方块**

引擎指令面里 `signal set <x> <y> <z> [--angle=] [--aspects=]` 只做一件事 ——
`Simulator.mmtrSignalOp(..., "set", ...)` 往**信号登记表**（`mmtr-signals.json`）写一条。

而登记表会被**逐区块**跟世界对账：`MmtrSignalSync.syncChunk` 把"这一块已加载、世界里却没有这盏灯"
的条目删掉（注释写得很明白：那就是被玩家敲掉的灯）。
⇒ **只在引擎里 `signal set`、世界里没有灯方块，下一次区块核对就会被清掉。**

所以"放灯"必须**先有方块**。MTR 的灯是一族普通方块（`Blocks.java`）：

| 方块 id | 类型 |
| --- | --- |
| `mtr:signal_light_1` … `mtr:signal_light_4` | 2 灯位（4 种外观） |
| `mtr:signal_light_3_aspect_1` / `_2` | 3 灯位 |
| `mtr:signal_light_4_aspect_1` / `_2` | 4 灯位 |
| `mtr:signal_semaphore_1` / `_2` | 臂板信号机 |
| `mtr:signal_pole` | 信号杆 |

## 2. 方块状态契约（`BlockSignalBase`）

```
facing   ∈ north|south|east|west      ← Direction.asRotation(): south=0, west=90, north=180, east=270
is_22_5  ∈ "false"|"true"             ← 注意是 EnumBooleanInverted，值是字符串
is_45    ∈ "false"|"true"
power    ∈ 0..15
```

灯朝向角（引擎与渲染共用同一个式子）：

```java
getAngle(state) = FACING.asRotation() + (is_22_5 ? 22.5 : 0) + (is_45 ? 45 : 0)
```

**朝向怎么定**：解析灯守哪条轨时用的是 `want = 角度 + 90°`，与"从节点出去的轨的方位"比。
沿 Z（+Z 南）的轨方位 = 90°，所以 `角度 = 0` ⇒ `facing=south`。
本轮那盏就是 `facing=south` → 引擎报 `朝向=0.0°`，`signal why` 里 `面朝方向单位向量 (0.0, 1.0)`（+Z）✅。

## 3. 三段式流水线（脚本放灯的完整通路）

| 步 | 动作 | 谁执行 |
| --- | --- | --- |
| ① | `setblock <x> <y> <z> mtr:signal_light_1[facing=south,is_22_5=false,is_45=false,power=0]` | RCON |
| ② | `world scan-signals`（引擎指令） | 游戏端枚举已加载区块里的灯方块 → 写登记 |
| ③ | `signal bind <x> <y> <z> --rail=<轨hex>` | 引擎 |

**为什么必须显式跑 ②**：`BlockSignalBase.onPlaced2` 里有"放下即登记"的钩子（notes/284），
但那是**物品放置**事件 —— `/setblock` **不触发** `onPlaced2`。自动轮转扫描一分钟一圈，
要立刻可查就得手打一次 `world scan-signals`。

**为什么推荐显式跑 ③**：不绑定时引擎按几何推断 —— 灯要在
`SIGNAL_BIND_TOLERANCE_M = 8.0` 格内、且离最近节点在 `NODE_BIND_RADIUS_M`（约 3 格）内，
然后取"**从那个节点出发、朝灯面朝方向**的那条腿"。规则很绕（`MmtrSectionService` 里那段注释
记录了"朝向相符 ≠ 该守它"的坑）。`signal bind --rail=<hex>` 直接把 `target` 写死，
`resolveProtectedRailInternal` 第一段就是"有 target 就绑这条轨"，**绕过全部方向推断**。

## 4. 两个安全性质（都核过源码）

- **`world scan-signals` 不会误删远处（未加载）的灯**：`syncChunk` 的 stale 清理带
  `if (chunkKey(entry.x >> 4, entry.z >> 4) != chunkKey) continue;` —— 只清"刚扫的这一块"。
- **人工绑定能活过重复扫描**：`syncChunk` 对 `mode == "BOUND"` 的条目只刷新朝向/灯位数，不重建绑定
  （`result.skippedBound++`）。

## 5. 本轮真放了一盏（可作模板）

```
方块  (-141, 65, -153)  mtr:signal_light_1[facing=south,is_22_5=false,is_45=false,power=0]
       ↓ 下面是石砖平台（y=64），上面是空气
邻居  (-142, 65, -153)  mtr:rail[...]      ← 第 1 条侧线的北端节点，灯离它 1.0 格
引擎  信号灯 -141,65,-153  朝向=0.0°  状态=GREEN  模式=BOUND
绑定  → 第 1 条侧线（长 220 m），区间从弧 0 开始向南
```

`signal why -141 65 -153` 的原话（可作日后核对的样板）：

```
①[人工绑定] 登记 1 条轨（模式=BOUND）
① 保护的轨 FFFFFFFFFFFF…（长 220 m），起点弧 0 m，朝向 (0.0, 1.0)
   投影点离灯 1.0 格；轨的两端 (-142,-153) 与 (-142,67)；灯在 (-140.5,-152.5)
   区间从弧 0 开始，南(+z) 走
```

**注意**：这盏是**能力验证用的样本**，位置是"第 1 条侧线北端"。
16 条侧线只放了 1 盏 —— 真正要放哪些灯（数量/位置/灯位数/守哪条轨）等用户口径。

## 6. 顺带记一笔

- `signal list [--state=红|黄|绿]`、`signal why <x> <y> <z>` 是核对灯的主力（`why` 会把"为什么没绑定"
  逐条讲出来，比看状态有用得多）。
- 灯的方块是**一格**、模型两格高；`setblock` 只放一格即可（本轮实测渲染正常、登记正常）。
- 本轮为了扫描临时 `forceload add -150 -160 -60 70`（105 区块），**跑完已经 `forceload remove all`**。
