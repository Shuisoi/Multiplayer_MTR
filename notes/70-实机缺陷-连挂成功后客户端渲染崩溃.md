# 70 - 实机缺陷：连挂成功后客户端渲染崩溃（车与轨道"全消失"）

> 实机（2026-09-09 18:09:54，用户手动开 1 道机车连挂 2 道两节客车）：**连挂本身成功了**——
> 引擎日志 `[MMTR-COUP] 连挂完成: 7706126963531990152 + 5519287253737297475 -> 7706126963531990152（3 节，48.0 m，车钩间隙 0.3 m）`。
> 但用户看到的是"车、轨道这些实体全消失了"。

## 症状：渲染线程每帧抛异常

客户端日志在连挂成功后立刻开始刷：

```
[18:09:54] [MMTR-CL] mirror created id=7706126963531990152 cars=3 path=3 progress=0.0 doors=-1
[18:09:54] [Render thread/ERROR] (MinecraftMappings)
java.lang.ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1
	at org.mtr.mod.render.RenderVehicles.lambda$render$16(RenderVehicles.java:116)
	at org.mtr.mod.render.RenderVehicles.iterateWithIndex(RenderVehicles.java:625)
```

`RenderVehicles.java:116` 是 `vehicle.persistentVehicleData.rayTracing[carNumber]`。镜像已经是 3 节，
数组却只有 1 个元素，`carNumber = 1` 越界 → 整个世界渲染（车辆 + 轨道都在同一帧里画）每帧失败，
看起来就像"实体全没了"。**这不是连挂失败，也不是数据丢失，是渲染线程崩溃。**

## 根因：按车辆 id 缓存的车节数据没有随节数失效

`VehicleExtension` 构造时会先查缓存：

```java
final PersistentVehicleData temp = MinecraftClientData.getInstance().vehicleIdToPersistentVehicleData.get(getId());
if (temp == null) { new PersistentVehicleData(vehicleExtraData.immutableVehicleCars, ...); }
else { persistentVehicleData = temp; }
```

`PersistentVehicleData` 的 `rayTracing[]` / `longestDimensions[]` 在**构造时**按 `immutableVehicleCars.size()`
定长（MTR 上游假设"一个车辆 id 的车节数不会变"）。连挂手术恰恰打破了这个假设：机车 id 不变，节数 1 → 3，
镜像重建了，但缓存实例被原样复用，数组还是长度 1。

## 修法

`PersistentVehicleData.matchesCarCount(carCount)` + 构造时按节数校验：

```java
if (temp == null || !temp.matchesCarCount(vehicleExtraData.immutableVehicleCars.size())) {
	if (temp != null) { temp.dispose(); }   // 旧缓存里的音效/显示资源一并释放
	persistentVehicleData = new PersistentVehicleData(vehicleExtraData.immutableVehicleCars, getTransportMode());
	MinecraftClientData.getInstance().vehicleIdToPersistentVehicleData.put(getId(), persistentVehicleData);
} else { ... }
```

解挂（同一 id 少节）同样走这条路：数组偏长不会越界，但 `longestDimensions` 会错位，一并重建。
