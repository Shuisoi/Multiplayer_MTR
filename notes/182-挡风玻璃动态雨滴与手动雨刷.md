# 182 · 挡风玻璃：动态雨滴 + 手动雨刷（离屏自检工具）

接 `notes/179`。179 解决的是"雨层根本不在玻璃上"（欧拉反解，见其 §10）；本轮把它从**一个静态贴图 + 一条时间曲线**做成**有物理的雨滴场 + 有档位的雨刷**。

## 1. 手动雨刷：一个键，三个档位（**没有自动档**）

### 1.1 语义（用户拍板）

**天气不再参与雨刷速度。** 原来的实现是 `periodS * (1.45 - 0.75 * intensity)`——雨越大扫得越快。
现在 `intensity` 只决定**玻璃有多湿**（雨滴数量与生长），雨刷完全由司机决定。

| 档位 | `periodS`（一个来回的秒数） | 端点停顿 | 说明 |
|---|---|---|---|
| **关 OFF** | — | — | 刀停在**当前位置**（不会自己归位），且**什么都不擦** |
| **慢 SLOW** | 1.55 s | 1.0 s | 停顿让刀刃有"格一下"的节奏 |
| **快 FAST** | 0.78 s | 2.0 s | |

### 1.2 按键

```java
MMTR_WIPER = registerKeyBinding("key.mmtr.wiper", GLFW.GLFW_KEY_J, CATEGORY_MTR_KEYBINDING);
```

- 键位：**`J`**。第一版选了 `'`（紧挨 MTR 的制动键，最顺手），**但那是 `MMTR_BRAKE_RELEASE`**——
  同一个键挂两个功能，司机想刮水的时候会把制动缓解掉。已改 `J`。
  已占用：`Z` 电梯菜单、`↑/↓` 油门/制动、`R` 车门、`;` `'` 制动施加/缓解、`G` 驾驶室、`K` 连挂、
  `H` AWS 确认、`Y/U` 左/右门、小键盘若干。（MTR 本体还有 `B` 列车菜单、`Z` 电梯。）
- 边沿检测：`isPressed()` + `lastPressed`（`MmtrCabInteraction` 的现成写法），按一下切一档，动作条提示 `雨刷 关 / 慢 / 快`。
- **只有持着驾驶室的客户端能切**：`MmtrCabInteraction.holdsAnyCab()` 判定，否则提示 `需要先坐上驾驶位`。乘客按键不会去动别人的车。

### 1.3 只画在"我在开的那台车"上

`MmtrWindshield.render` 里：

```java
final WiperMode mode = driverOnBoard(vehicleId) ? wiperMode : WiperMode.OFF;
```

`driverOnBoard(resourceId)` 要**跨两套 ID**：按键持有的是**数字车辆 id**，渲染路径带的是**模型资源 id**，
所以它拿 `MmtrCabInteraction.holdsCab(vehicle.getId())` 找到那台车，再遍历 `vehicleExtraData.immutableVehicleCars`
比对 `getVehicleId()`。**一台编组可以混用多个模型**，所以必须按车比对，不能只看"我有没有驾驶室"。

### 1.4 换档不回跳

相位是 `0..2` 的**三角波**，`0` = 停放位：

```
angle = parkAngleDeg + sweepUnit(wiperPhase) * sweepDeg
sweepUnit(p) = p % 2 <= 1 ? p % 2 : 2 - (p % 2)
```

刀以**恒定角速度**走（真车连杆大致线性；之前那版是 `0.5 - 0.5*cos(...)`，两端爬、中间糊），
走完一程后在停放位**停顿** `dwellS` 再走下一程。

**关键**：任何档位切换都只是**改速率**，从不重置 `wiperPhase`。所以
- 慢 → 快：刀从当前位置加速，不跳；
- 快 → 关：刀**就地停住**（这是真车现象，不是 bug）；再开 慢，从那里继续。

### 1.5 擦水的定义：**从停放角到刀刃**

`wipeFactor(pointX, pointY, pivotX, pivotY)` 返回 `1`（已擦干净）/ `0`（没碰）/ `-1`（超出臂展）：

```
fromPark = signed(angle - parkAngleDeg) * sweepSign
swept    = signed(wiperAngleDeg - parkAngleDeg) * sweepSign
fromPark < 0 或 > swept + WIPE_FADE_DEG  -> 0
fromPark <= swept                        -> 1
否则                                      -> 1 - (fromPark - swept) / WIPE_FADE_DEG   // 前缘渐隐
```

**这个写法是踩了两次坑之后才定下来的，两种错法方向相反**：

| 错法 | 症状 |
|---|---|
| "上一次重绘角 ~ 当前角之间" | 只覆盖**一帧**的进展。重绘间隔 90 ms，快档一帧十几度——刀后面的玻璃**立刻回湿**，永远看不出被擦过 |
| "刀刃前后 N 度以内" | 角度差**分不清前缘和后缘**（都在 10° 外），刀一离开停放位就擦了半圈玻璃 |

"从停放角到刀刃"没有这两个问题：**不需要任何符号判断**，就是刀走过的区域，
而且在**换向瞬间**（扫掠范围在两端都是整个弧）也自洽。

### 1.6 雨刷拖出的水膜（不是"橡皮擦"）

被刀扫过的雨珠**不删除**，而是压到 `RE_WET_INK = 0.30` 然后按 `0.8/s` 重新长回来：

```java
if (wipe > 0) {
    final double target = RE_WET_INK + (1 - RE_WET_INK) * (1 - wipe);
    drop.trail = 0;
    drop.ink = Math.min(drop.ink, target);
}
```

- 前缘（`wipe` 从 0 到 1）→ `target` 从 1 渐变到 0.3，所以刀**到来时**珠子是渐隐的，不是"啪"一下没了。
- 刀后面 → 0.3，约 **0.9 s** 长回满值。这就是真车刮过之后那道慢慢回湿的痕。
- 另外画一条**水膜扇区**（`fillSector`，从 `wipedFromDeg` 到 `wiperAngleDeg`，`+2°` 余量）作为刀**正在拖**的湿痕。

> `MmtrPanelCanvas` 为此新增了 `fillSector(cx, cy, radius, startDeg, endDeg, color)`：扇形填充（先画心再沿弧连点、闭合）。
> 它不是 `arc`（那是描边），也不是 `fillPolygon` 直接给弧点（会把弦当边，切成弓形）。

## 2. 动态雨滴

### 2.0 算法选型：**毛细钉扎 + 水膜场**（第三版，覆盖下面 §2.1–§2.4 的早期设计）

用户要求"雨滴需要动态的从上往下运动，类似现实，有没有比较好的粒子算法"。
第一版是**串珠式下落**（每颗珠子每帧都动），问题不是不好看，而是**不像雨**。

现实的雨落在玻璃上是**三个阶段**，缺一个都不像：

| 阶段 | 物理 | 视觉 |
|---|---|---|
| **钉扎** | 表面张力顶住重力。小雨珠**完全不动** | 玻璃上一层静止的斑点，能挂几分钟 |
| **生长** | 雨里继续吸水，变大 | 斑点缓慢变胖 |
| **流失** | 超过临界半径，表面张力撑不住 | 开始下滑、加速、**在身后留下水膜** |

所以算法核心是**临界半径**（`staticThresholdM`）：超过它才动。而且它**按每颗珠子自己的个性缩放**
（`1.1× ~ 1.8×`），所以场里永远有一部分钉着、一部分在流 —— 这才是"天气"而不是"动画"。

**另外两个关键机制**：

1. **轨迹是"水膜场"，不是珠子拖的尾巴。**
   滑动中的珠子往一张粗网格（`wetness`，48×48）里**沉积**水分，水分按蒸发速率衰减。
   轨迹属于**玻璃**，所以珠子滑出画面后轨迹还在；雨刷也有**一个**东西要擦，而不是去追一百条尾巴。
2. **珠子会"掐断"（pinch-off）。**
   滑动中的珠子每走 `0.035 m` 就在身后**留下一个小珠子**。这既是真实溪流尾迹的成因，
   也**免费补足了钉扎种群**，不用凭空在玻璃中间生成珠子。

**空间哈希做合并**：掐断让珠子数量翻几倍，原来的 O(n²) 全配对不再划算。
按"合并距离"大小的格子分桶，每颗只查自己与邻格（3×3），退回 O(n)。

> 这三条合起来回答"有没有更好的粒子算法"：**不是"更好的粒子"，而是"把粒子从主角降级为水膜的搬运工"**。
> 单颗珠子的动画再精细，也不会像雨；**让玻璃自己记住水**才会。

#### 标定过程（**用离屏工具做的，不是在游戏里试**）

参数之间是**耦合**的：`staticThresholdM` 只有和 `growthMps` 一起才有意义 ——
珠子钉扎的时长是 `(阈值 − 起始半径) / 生长速度`。第一版把阈值设成 5.5 mm、
生长速度 4 mm/s，**穿越时间 0.5 秒**，于是"钉扎"这一档根本不存在（实测 `pinned=0.02`）。

| 阈值带 | 测得 `pinned`（20 s） | 结论 |
|---|---|---|
| `0.35×..1.0×` | 0.18 | 几乎全部在流 → 没有斑点 |
| `1.5×..2.5×` | **0.89** | 几乎全部钉住、**完全没有轨迹** |
| **`1.1×..1.8×`** | **0.58** | ✅ 混合：多数钉住、少数在流 |

最终参数：`staticThresholdM=0.0045`、`growthMps=0.0008` → 钉扎 **2.4 ~ 7.7 s**。
`[calib] 60s pinned=0.62 wetness coverage=0.817` —— 水膜**铺满 82% 的玻璃**。

**还有两个只能靠工具发现的坑**：

- **重生必须给随机尺寸**。原来 `respawn` 固定回到最小半径，稳态下**整个种群收敛成小点**、玻璃越来越稀
  （实测覆盖率 0.0006）。改为从同一尺寸分布抽取。但**上限必须卡在阈值以下**，
  否则新珠子"落地即流动"，斑点又没了 —— 写成 `min(maxBeadRadius, staticThreshold)` 就永远不会越界。
- **水膜沉积率要够大**。只有少数珠子在流，按最初的 1.6/s 沉积，60 s 覆盖率只有 0.005（看不见）。
  提到 6/s、蒸发降到 0.03/s，才有 0.817。

### 2.1 珠子是**物体**，不是精灵

`Drop` 现在有：位置（面坐标 0..1）、`radiusM`（**真实米数**）、`trail`（米）、`directionX/Y`（上次运动方向）、
`lateralVelocity`、`ink`（0..1 的"成形度"）、`variation`（0..1 的个性）、**每颗自己的 `Random`**。

尺寸默认 `minBeadRadiusM = 0.0035` → `maxBeadRadiusM = 0.011`，`growthMps = 0.004`。
一颗珠子在雨里**会变大**，大了流得快，撞上别的珠子**会合并**。

### 2.2 受力模型（三种力）

```java
gravityDown     = fallMps * (snow ? 0.35 : 1) * (0.6 + 0.9 * intensity);
airflow         = AIRFLOW_COEFFICIENT * speedMps * speedMps;          // 0.02
surfaceClimb    = clamp(airflow - gravityDown, -gravityDown, creepMps); // 正 = 向上爬
climbSpeed      = surfaceClimb * (0.25 + 0.75 * variation);            // 大珠子先流
```

1. **重力**：沿玻璃**下坡**（`panelDown()` = 世界下方向在玻璃平面内的投影），所以斜坡风挡天然比垂直的流得慢。
2. **气流**：与**车速平方**成正比，把珠子往**上**推。`AIRFLOW_COEFFICIENT = 0.02` 是**选出来的**：
   它让"气流 = 重力"的平衡点落在 **约 22 m/s（80 km/h）**。于是
   - 停车/低速 → 珠子往下流；
   - 80 km/h → 珠子**钉住不动**；
   - 更高 → 珠子**缓缓向上爬**（`creepMps = 0.09` 封顶）。
   这是"停着的车"和"跑起来的车"看起来不一样的唯一原因。
3. **横向**：加速度从**镜像车速差分**得到（`trackAcceleration`），沿玻璃 `right` 轴甩珠子。
   注意用的是**标称 0.35 s 暴露时间**而不是帧时间——一帧 16 ms，1.2 m/s² 只有 2 cm/s，看不见。
   再加一点 `jitterMps = 0.02` 的随机游走当走行品质。

> **玻璃法线不用来定方向**：`down` 是"世界下"在玻璃里的投影，不是"本地 -Y"。用本地轴会让雨**横着滑**（179 §1 就写过）。

### 2.3 雨珠画法

- **拖尾**：从珠心向**它自己上次运动的反方向**延伸 `trail` 米，两道线（宽 1.7× / 0.95× 半径）做出软边。
  - **必须是珠子自己的运动方向**，不是"顺着玻璃往下"：120 km/h 时珠子在**向上爬**，尾巴必须朝下，否则整个气流模型看起来就是噪点。
  - 贴图空间 x/y 每格米数不同（3.0 × 1.56 m），所以方向要先按 `(dirX*widthM, dirY*heightM)` 归一，不然宽风挡上拖尾会**斜着飘**。
- **珠体**：`circle` 主体 + `arc(0,360)` 内圈做出透镜感 + 一小块 `0xCC` 白的**高光**（偏右上，天在上、光从司机肩后过来）。
- **雪**：不透明白色小圆，不拉尾（`snow` 时 `trail` 不增长），下沉速度 ×0.35。

### 2.4 合并与种群

- `mergeDrops()`：每步一趟 O(n²)（几十颗珠子，可忽略）。距离 < 0.012 m 时**大的吸收小的**，
  `radius = hypot(ra, rb)`（面积相加），`ink` 部分叠加，小的重新入场。
- `spawnForWeather()`：**珠子是种群不是粒子流**。目标数量 = `raindrops * (0.35 + 0.65 * intensity)`，
  只有当被刀打掉的珠子让存活数掉到目标以下时，才按 `spawnPerSecond` 补。
  - **默认 `spawnPerSecond` 从 18 降到 2**：18/s 意味着 90 颗珠子每 5 秒全换一遍，
    以 `0.8/s` 的回湿速度，**每颗珠子都还没长成就在重生了**，玻璃永远是一层灰。
  - 补进来的珠子 `ink` 直接给 ≥0.55（**落地就是湿的**）；`0.3 → 1` 的渐长只属于**被刮过的**珠子。

### 2.5 重绘门（`needsRedraw`）

`MmtrPanelTexture` 本来就有 `needsRedraw(signature)`，但**签名里没有珠子**——
只有 `角度:强度:雪:数量`。刀一停，签名恒定，于是 Canvas 每 90 ms 重建一次**一模一样**的图，
**雨看起来是冻住的**。

`signature()` 现在把珠子场也粗量化进去：

```java
hash = hash * 31 + round(y*40)*7 + round(x*40) + round(ink*8);
```

粗量化是故意的：11 Hz 下珠子移动远小于一个像素。

## 3. 离屏自检工具（**不用开游戏就能验物理**）

`mmtr/tools/wiper-preview/WiperPreview.java` —— 纯 Java2D，**逐常量镜像** `MmtrWindshield` / `MmtrPanelCanvas`
（同样的力、同样的珠形、同样的水膜、同样的 v 翻转）。跑法：

```powershell
. env\workspace.env.ps1
& "$env:JAVA_HOME\bin\javac.exe" -d mmtr\tools\wiper-preview mmtr\tools\wiper-preview\WiperPreview.java
& "$env:JAVA_HOME\bin\java.exe" -cp mmtr\tools\wiper-preview WiperPreview
```

它输出 **24 项断言** + 4 张 PNG（`logs/2026-09/wiper-preview-*.png`：停放/停车刮/40 km/h/120 km/h）。

> **为什么值得留着**：这个工具在本轮抓出了 **6 个**只靠看游戏根本定位不了的问题——
> ① 擦水扇区在错误的一侧；② 擦水带覆盖整圈 357°；③ 珠子场因为签名缺项而冻住；
> ④ `spawnPerSecond=18` 让玻璃永远长不成；⑤ 阈值与生长速度不匹配导致"钉扎"这一档不存在；
> ⑥ 重生固定在最小半径让种群收敛成小点。每一项都是**数值**判定，不是"看着不对"。

### 调参用的取样（`[calib]` 行）

标定阈值带时是**打印分布再决定**，不是猜：

```
[calib] 20s pinned=0.58 running=0.42  半径分布 3.4-4.5mm:6 4.5-5.6mm:32 5.6-6.7mm:20 6.7-7.9mm:4 7.9-9.0mm:14
[calib] 60s pinned=0.62 wetness coverage=0.817 max=1.00
```

**这一步是必须的**：前两次失败是**方向相反**的（全在流 / 全钉住），
只看最终画面无法区分"阈值太低"和"阈值太高"，而分布图一眼就能看出珠子卡在阈值的哪一侧。

### 关键断言（改物理时先跑它）

| 断言 | 它守的是什么 |
|---|---|
| 120 km/h 时 `climbing=1.00` | 气流项确实盖过重力 |
| 120 km/h 时表面速度 < 0.06 m/s | 平衡点位置（不是"越快越动"） |
| 15 km/h 时 `climbing=0` | 低速不该有上爬 |
| 刀扫过时已清扇区**没有任何珠子存活**（`ink ≤ 0.31`） | 擦水**每一帧**都成立，不只是在收尾那一刻 |
| 水膜基线 ≥ 0.29 | 擦过之后玻璃是**湿的**，不是干玻璃 |
| 擦水带宽度在 `(5°, 半程+渐隐]` | 是**一条带**，不是整圈 |
| 停放位刀尖 `=(±arm, 0)` | `parkAngleDeg = 0` = 贴着玻璃 right 轴（建模侧的契约） |

## 4. 新增/变更的配置项（`windshield` 块，打包器会自动列出）

| 键 | 默认 | 说明 |
|---|---|---|
| `creepMps` | 0.09 | 线速下气流造成的上爬速度上限 (m/s) |
| `jitterMps` | 0.02 | 走行品质抖动 (m/s) |
| `minBeadRadiusM` | 0.0035 | 最小珠半径 (m) |
| `maxBeadRadiusM` | 0.011 | 最大珠半径 (m) |
| `growthMps` | 0.004 | 珠子吸水长大速度 (m/s) |
| `spawnPerSecond` | 2 | 补珠速率（**别调大**，见 §2.4） |
| `staticThresholdM` | 0.0045 | **核心参数**：超过这个半径表面张力就撑不住（米）。**必须和 `growthMps` 一起调**，见 §2.0 |
| `wetnessCells` | 48 | 水膜场每边的格数（越大轨迹越细，开销越大） |
| `wetnessDepositPerSecond` | 6 | 滑动珠子每秒沉积的水量 |
| `wetnessDryPerSecond` | 0.03 | 水膜每秒蒸发量（**必须小于沉积率**，否则永远积不起来） |
| `mergeDistanceM` | 0.012 | 珠子合并距离（米），**同时是空间哈希的格子尺寸** |
| `periodS` | 1.6 | **已不再被客户端读取**（档位在 `WiperMode` 里）。保留只为兼容旧包 |

> ⚠️ `periodS` 和 `parkAngleDeg`/`sweepDeg`/`sweepSign`/`pivotU`/`pivotV` 是**两组不同用途**：
> 前一组（`periodS`）已经作废；后一组仍然有效，因为它们是**几何**（刀怎么摆），不是**节奏**。

> ⚠️ **打包器白名单要跟上**：`pack_vehicle.js` 的 `WINDSHIELD_FIELDS` 必须包含上面这些新键，
> 否则它们会被静默丢掉——这正是 179 §9.4 #3 那个"配了 `sweepSign` 却不生效"的同款坑。

## 5. 待实机确认 / 已知取舍

1. **臂展**默认 = 玻璃短边一半（0.78 m），圆心在**底沿中点**。3.0 × 1.56 m 的风挡上，
   **只有下中部在臂展内**，上半部分永远擦不到——物理上正确，但视觉上要确认能不能接受（真车连杆确实如此）。
   （这一条是自检工具量出来的：45 颗已长成的珠子里，一个行程只有 4 颗落在臂展内。）
2. `sweepSign` 旋向仍未实机确认（179 §9.3 的存疑项）。
3. `driverOnBoard` 是**按车**判定（不是按驾驶室），所以双头机车两端会**同时**动。要按驾驶室区分需要
   `anchor.cab` ↔ 统一驾驶室编号的映射（179 §8 记过这个映射问题）。
4. 雨滴**不随车速在玻璃上产生位移错觉**（真车高速下雨是"横着抽"的）——本轮没做，需要时会加。
5. 雨刷形状仍然粗糙（两根矩形），用户已明确"这个事情再说吧"。
6. `periodS` 配置项已作废但仍在打包器白名单里，会被写进锚点 JSON 却无人读取。清理它需要同时改
   `pack_vehicle.js` 的 `WINDSHIELD_FIELDS`（本轮没动，避免与旧包不兼容）。
