# 215 · 开车不再需要钥匙 + 右上角简略 HUD

日期：2026-09-19 · 车辆：BR101 · 结论：**操纵判据从"手里有钥匙"改成"骑在司机位上"**（引擎 + 客户端一起改），
并加了屏幕右上角的简略操作 HUD；引擎全量 **753 通过 / 0 失败 / 5 跳过**（两条旧契约用例按新契约改写），
客户端 435 源 / 639 类 javac 通过。

用户口径（原话）：「**不需要手握钥匙才能操作**，外加在屏幕右上角 HUD 上**简略显示操作信息**」。

## 1. 为什么原来"按了没反应"

上一轮（notes/214）把三手柄输入接上时，客户端是**等钥匙**的：

```
MmtrDriveInput.tick()
  └─ if (mmtrCabVehicleId() != 0 && mmtrIsCabConfirmed())   ← 必须先按 G 申领驾驶室，且引擎确认
```

而引擎侧更硬：`Vehicle.canTakeMmtrControl(uuid)` 要求

```java
final boolean senderIsRidingDriver = hasMmtrDriverRiding(uuid) && holdsMmtrCabKey(uuid);
```

`holdsMmtrCabKey` 对编组体车 = 「**你的钥匙真的插在这个驾驶室里**」。于是常见现场是：
车从车场出来时引擎自己插了一把 **system 钥匙**（占位，用来定"哪一端在前"、也用于自动运行），
人坐进司机位、按手柄 —— `hasMmtrDriverRiding` 为真、`holdsMmtrCabKey` 为假 ⇒ 一条一条全被丢掉，
屏幕上什么都不动。这正是用户报的那件事（notes/48 记过同一类抱怨："开车必须手持钥匙"）。

## 2. 改法：判据回到"位置"

**引擎**（`Vehicle`）两条判据去掉钥匙项：

| 位置 | 旧 | 新 |
|---|---|---|
| `canTakeMmtrControl` | `hasMmtrDriverRiding && holdsMmtrCabKey` | **`hasMmtrDriverRiding`** |
| `simulate` 的自动交还 | `hasMmtrDriverRiding && holdsMmtrCabKey` | **`hasMmtrDriverRiding`** |

仍然拦着的：无任务不得操纵（T4 策略开关）、**占用锁**（一列车上同时只有一个司机：先动手的人拿到，
持有者还在司机位上时别人抢不走）。`holdsMmtrCabKey` 保留但**不再参与操纵判据**——它回答的是另一个问题
（"钥匙在谁手里"，驾驶室界面与运维查询用）。

**客户端**：谁是司机的唯一判据抽成 `MmtrDriverSeat`（新增）：

```java
MmtrDriverSeat.current()   // 骑在哪辆车的哪节车 + 沿车长的位置离哪个驾驶室的玻璃最近
MmtrDriverSeat.isAtControls()
```

- 位置判据用的是 `MmtrVehicleAnchors.nearestCab(...)`（**新增，唯一一份**）；雨刷的 `driverOnBoard`
  改为调用它 —— 于是"雨刷会动的地方"和"能操作手柄的地方"永远指同一个驾驶室（这类判据一分为二的先例见 notes/189 §7）。
- `VehicleRidingMovement` 里报给引擎的 `isDriver` 改为 `mmtrCabConfirmed || MmtrDriverSeat.isAtControls()`，
  并且**只在变化时**发包（位置每帧都在动，这一位回答的是"我是不是司机"，不是坐标）。
- `MmtrDriveInput` 的闸门与发送目标都改为 `MmtrDriverSeat`（不再看 `mmtrCabConfirmed`、不再看 G 键）。

## 3. 连带挖出来的两件事（都不是可选项）

### 3.1 拔钥匙会不会把牵引掐掉？

旧代码里"拔钥匙 ⇒ 下一拍自动交还 override ⇒ 没牵引"。放宽之后这条消失了，于是**必须明确**交还判据是哪一个：
现在只有**司机位空了**才交还（人走开/下车/断线）。这是有意的：站在司机位上、车正在走的人不该因为
"钥匙被人拔了"而突然失去制动。用例 `theCrewTakesTheStagedCabFromTheSystemKeyAndThenOwnsTheThrottle`
把新旧两半都钉住了（拔钥匙 → 操纵权仍在；下车 → 交还）。

### 3.2 方向从哪来 ⇒ "动手柄即接管驾驶室"

方向由**被占用的驾驶室**决定（`MmtrCabState.leadingEnd`：A 端驾驶室 ⇒ A 端在前）。没人接管时
`travelsToward(End.B)` 恒为 false ⇒ 退回"朝 B 端"，坐在 A 端驾驶室的司机就成了**倒着开**。

所以客户端加了一条自动接管：`MmtrCabInteraction.claimSeatWhenDriving(seat)` ——
**坐在司机位上第一次动手柄时**，替玩家把 `cab <id> <car><A|B>` 那条命令发出去（就是 G 键那条路）。
两个刻意的取舍：

- **不在"坐下"时就接管**：那会让"坐到 AI 车的驾驶室里看看"把自动运行停掉（接管会顶掉 system 钥匙）。
  只有真的动了手柄才算"我要开这列车"；
- 引擎的闸门照旧（停稳、一个驾驶室一把钥匙），被拒就隔 3 秒再试 —— 车停下来那一次就会成功。
  就算一直没抢到，**仍然能开**（第 2 节放宽的就是这一层），只是方向退回默认。

## 4. 右上角 HUD（`MmtrDriverHud`，新增）

```
                    ┌───────────────┐
                    │ 速度   87 km/h │
                    │ 油门 牵引 45%  │   ← 牵引蓝 / 电阻制动橙 / 关闭灰
                    │ 制动        2  │   ← 非运行位橙、EB 红
                    │ 定速 100 km/h  │   ← 开着青、关闭灰
                    │ 换向      前进 │
                    └───────────────┘
```

- 两列（标签 + 右对齐的值），五行；没有表盘/刻度 —— 那套是资源包的 `mmtr_hud_*` 面板（重建步 B6 的另一条路）。
- 注册走 GUI 钩子（`InitClient.registerGuiRendering`），与交互提示同一条路；有界面打开时（背包/聊天）不画。
- **只在坐在司机位上时显示**：判据与"能不能操作手柄"同源（`MmtrDriverSeat`），
  所以永远不会出现"HUD 在、按键没反应"这种最费解的组合；乘客与站台上的人看不到。
- 数值来源：手柄位置 = 客户端输入层自己持有的状态（`MmtrDriveInput`，它才是这三根手柄的本地真值）；
  速度 = 车辆镜像（与服务端权威同源）。

## 6. 实机验收清单（下一轮进游戏时按这个顺序看）

1. 上车走到司机位 → 右上角 HUD 出现（不必按 G）；
2. 按 ↑（油门）→ 车动、HUD 的"油门"变蓝、日志出现 `[MMTR-DRV] client handles → …`；
3. 按 `;` 到 8 → 停住；再按到 EB → HUD "制动 EB" 变红、紧急减速度；
4. 按 9/0 → "定速"在 0…160 之间按 5 跳；
5. 按 `'` 回"运行" → AFB 恢复接管（HUD 定速值仍在）；
6. 走开（离开司机位）→ HUD 消失、车交还操纵权（不再带着旧手柄跑）；
7. 坐在 A 端驾驶室动一下手柄 → 日志 `[MMTR-CAB] 自动接管司机位：… 驾驶室=1A`，车头朝 A 端开。

## 7. 遗留

1. **HUD 还没有面板刻度/指针**（资源包 `mmtr_hud_*` 那条路），也还没显示限速/AWS/LZB 这些监督信息；
2. `MmtrDriverSeat` 的松紧度：车厢中部也算"离某个驾驶室最近"（BR101 车厢短，实际等于"站在机车中部也能开"）。
   要收紧就在 `MmtrVehicleAnchors.nearestCab` 加距离门槛，箱位只有那一处；
3. 自动接管是**客户端**行为：如果将来要做"票务/权限"（谁能开哪列车），闸门应该落在引擎的
   `insertKey`/`canTakeMmtrControl` 那一层，而不是客户端的 `claimSeatWhenDriving`。
