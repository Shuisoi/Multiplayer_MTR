## 3. 判据顺序（唯一真源）

`MmtrLightSwitch.lampState(本端档位, 换向器)`：

1. 本端开关 = **关闭** ⇒ 灭（**压过 N**：机车的关闭档就是为了挂车时灭尾灯，而挂车时换向器多半是 N）；
2. 换向器 = **N** ⇒ 固定红尾灯（无视档位）；
3. 否则按本端档位（尾灯 / 日间 / 夜间）。

## 3.1 按键解耦：第一版点名法在实机上当场漏了

实机第一次按键就报回来一条：**"按 L 出来进度页面"** —— 原版的 `key.advancements` 默认就是 **L**，
而我第一版只点名摘了 `leftKey`/`rightKey`（A/D）、`dropKey`（Q）、`swapHandsKey`（F）四个。

顺着这条线把玩家自己的 `run/options.txt` 与 MMTR 的键位对了一遍，漏的远不止 L：

| 撞 MMTR 键的非 MMTR 绑定 | 键 |
| --- | --- |
| `advancements`（原版进度页面） | **L** = 灯光 |
| `left` / `right`（原版平移） | A / D = 油门 |
| `drop` / `swapOffhand` | Q / F = 响应 / 定速 |
| `journeymap.map_toggle_alt`（全屏地图） | **J** = 雨刷 |
| `journeymap.create_waypoint` / `fullscreen_create_waypoint` | **B** = 接管作业 |
| `journeymap.fullscreen_waypoints` | **N** = 子任务确认 |
| `journeymap.fullscreen.disable_buttons` | **H** = 重拉数据 |
| `journeymap.fullscreen.east` / `.west` | ← / → = 换向器 |

**点名法必然会漏**：原版有几十个绑定、每个模组还有自己的，而玩家还能把任何一个挪到我们的键上
（这份 `options.txt` 里就有 12 条撞键）。所以判据换成结构性的：

> 一个绑定被摘掉 ⇔ ①它不是 MMTR 自己的绑定（`key.mmtr.*`）**且** ②它**当前**绑定的键位与 MMTR 某个键撞了。

实现要点（`MmtrInputDecouple`）：
- MMTR 的键位**反射读 `KeyBindings` 的公开字段**得到（不是手写表）⇒ 加键/玩家改键都不会过期；
- `key.keyboard.unknown`（未绑定）不算撞键；
- 先问 100 ms 缓存的"我在不在司机位上"，再碰字符串（`isPressed()` 每 tick 被原版问几十次）；
- 每种被摘的绑定**说一次** `[MMTR-KEY]`，第一行报 MMTR 现在的键位表 —— 否则"驾驶室里 L 不弹进度页面"
  看起来和"按键坏了"一模一样。

## 3.3 单手柄车的 A/D（实机修：镜像还没到时不再猜成三手柄）

用户口径：**"对于单手柄车而言，A/D 则为控制那个手柄的键位"**。查下来这里有一个**静默失败**：

| 事实 | 出处 |
| --- | --- |
| 三手柄控制器读 `control.getDriveHandle()` 与 `getBrakeNotch()`，**不读** `getThrottleNotch()` | `ThreeHandleDriveController` |
| 有级/无级/降保升/缺省控制器读 `getThrottleNotch()` + `getBrakeNotch()` | `NotchedDriveController` / `SteplessDriveController` / `AirBrakeController` / `DefaultDriveController` |
| 客户端只在**单手柄**那一支里填 `throttleNotch`（三手柄那一支恒 0） | `MmtrDriveInput.send` |
| 而 `isSingleHandle()` 原来是 `!activeMode.isEmpty() && !THREE_HANDLE && !DEFAULT` | 同上 |

于是两处都会让 A/D "没反应"：

1. **镜像还没到**（刚坐上车的一两拍）：`activeMode` 空 ⇒ 判成三手柄 ⇒ A/D 去改 `driveHandle`，
   而 NOTCHED 车底不读它 ⇒ **按 A/D 什么都不发生**；
2. **跨车沿用**：`activeMode` 是**跨车**留着的 —— 上一辆是 BR101（THREE_HANDLE），
   坐进 SAF420 的头一两拍仍按三手柄走 ⇒ 同一个症状。`DEFAULT` 车底同理（`DefaultDriveController`
   读的正是 `throttleNotch`，而被 `!DEFAULT` 排除在单手柄之外 ⇒ 那些车底也永远是 0）。

修法三条：
- `isSingleHandle()` 改成 **`!"THREE_HANDLE".equals(activeMode)`**（除三手柄之外一切，含"还不知道"）。
  选这个方向是因为**猜错的不对称**：猜成单手柄而车其实是三手柄 ⇒ 三手柄控制器不看 `throttleNotch`
  ⇒ 车不动（按 D 仍在制动侧，无害）；猜成三手柄而车其实是单手柄 ⇒ 按键**完全没反应**（就是这次的现场）；
- 控制方式**按车记住**（`modeByVehicle`：vehicleId → `mmtrMode`），换车时用的是**这辆车自己**的记忆，
  不再沿用上一辆；
- 真正第一次上车、镜像也没到的那几拍，**说一句**（动作栏："先按单手柄走…镜像一到自动切回"）。

## 5. 实机验收清单（需要人）

1. **L 循环**：坐进 SAF420 的驾驶室，按 L —— 动作栏依次是 `尾灯 → 日间 → 夜间 → 尾灯`（三档）；
   坐进 BR101 的驾驶室（车底 `lightSwitch=LOCO`），依次是 `关闭 → 尾灯 → 日间 → 夜间 → 关闭`（四档）。
2. **哪一端亮**：停在车外看两端 —— 驾驶室那一端白、另一端红；换端（走到另一端坐下）后**反过来**
   （靠"换端也算刚坐下"这条：`MmtrDriveInput` 会在 `cabSpec` 变化时重新认开关）。
3. **换向器 N**：换向器打到 N ⇒ 两端都变红（哪怕开关在"夜间"）；回前进/后退 ⇒ 恢复按档位。
4. **日 / 夜亮度差**：夜间明显更亮（默认日间 = 夜间的 45%）；
   `run/mmtr-lightfield.properties` 里改 `headlightDayRatio` 2 秒生效。
5. **尾灯不照世界**：夜间档把车头对着地面 —— 白灯在地上留光斑；把同一端切到"尾灯" ⇒ 地面不再有光斑
   （只有车尾附近一圈红晕）。
6. **关闭档（机车）**：BR101 切到"关闭" ⇒ 该端全灭；切到 N ⇒ **仍然灭**（关闭压过 N）。
7. **无人车默认红**：把开关拨到"夜间"后直接下车走开 ⇒ 该端白灯在占用锁释放后落回尾灯。
8. **按键解耦**：驾驶室里按 A / D ⇒ 人不平移、只动油门；按 Q ⇒ 手里的东西不掉；
   按 F ⇒ 主副手不交换；**下车后** A/D/Q/F 立刻恢复原版行为。
9. **打字不误触**：在驾驶室里打开聊天框打 `a d r f q j l k g b y u n h` ⇒ 手柄、雨刷、灯光、
   车门、连挂全都不动；驾驶输入每拍补发照旧（HUD 上速度/手柄不抖）。
10. **HUD**：右上角出现 `灯光 本端 … · 对端 …`，换向 N 时带 `（换向N）`。

## 8. 现场事故：重启之后服务端/客户端都起不来（不是代码，是代理）

**症状**（用户 2026-09-29 23:3x）：
```
A problem occurred evaluating project ':fabric'.
> Not a JSON Array: {}
   at fabric/build.gradle:51  (mappings "net.fabricmc:yarn:${buildTools.getYarnVersion()}:v2")
BUILD FAILED in 5s
```

**根因链条**（每一环都有实测）：

| 环节 | 证据 |
| --- | --- |
| `getYarnVersion()` 走网络 | `BuildTools` 直接 `HttpURLConnection` 拉 `https://meta.fabricmc.net/v2/versions/yarn/1.20.4`（**不是** Gradle 依赖解析，所以 `--offline` 与 Gradle 缓存都救不了它） |
| 上游拿不到时它返回 `{}` | `getJson` 5 次重试后 `return new JsonObject();` ⇒ 上层 `getAsJsonArray()` 抛 `Not a JSON Array: {}` |
| 为什么拿不到 | `mmtr/game/gradle.properties` 把构建 JVM 指向**本地代理** `127.0.0.1:7890`，而 `meta.fabricmc.net` **不在** `nonProxyHosts` 里；此刻 **7890 上没有任何进程在监听**（`Get-NetTCPConnection -LocalPort 7890` 为空）⇒ 每次 ~2 s 连接被拒 ⇒ 5 次全失败（所以 `BUILD FAILED in 5s`，而不是超时几分钟） |
| 直连其实是通的 | `curl --noproxy '*' https://meta.fabricmc.net/v2/versions/loader/1.20.4` → **200**（yarn 2.2 s / loader 5.8 s，走 **IPv6**；同一条 URL 走 IPv4 是 `000` 超时）。`maven.fabricmc.net` 与 `api.modrinth.com` 直连 200 / 1.8 s（这两个本来就在排除表里） |

**修法**（一行，`mmtr/game/gradle.properties`）：把 `meta.fabricmc.net` 加进 `systemProp.http.nonProxyHosts`。
> ⚠️ 这一条与文件里 2026-09-24 那条注释（"meta.fabricmc.net 直连完全读不到，必须走代理"）**方向相反** ——
> 两条都是真的，只是**网络状态变了**：09-24 直连超时、代理通；今天直连通、代理没跑。
> 所以两边都留了当时的实测数字与"改回去"的方法，下次谁不通就换另一条路。

**验证**：`gradlew :fabric:help` → BUILD SUCCESSFUL（配置阶段过了）；随后 `run-server.bat` → `Done (4.326s)!`，
`[MMTR-DRV] 车底解析：… → saf420_motor/NOTCHED`（顺带确认 SAF420 就是**单手柄**车底）。

**教训**：这个仓的"起不来"有一类与代码无关 —— **构建的配置阶段依赖两个外网**（meta.fabricmc.net / api.modrinth.com），
而它们走不走代理是 `gradle.properties` 决定的。下次看到 `A problem occurred evaluating project ':fabric'`
就先去查**代理在不在跑**与**那个域名在不在 nonProxyHosts 里**，别去翻自己刚改的代码。

### 8.1 另一类"起不来"：Fabric 重映射缓存不可写（2026-10-01）

**症状**（客户端已经在跑的时候去起服务端）：
```
net.fabricmc.loader.impl.FormattedException: java.io.IOException: the jar file
  ...\run\.fabric\processedMods\worldedit-7.3.0+6678-55745ad-64b5720b4b825f21.jar can't be written
   at RuntimeModRemapper.remap(RuntimeModRemapper.java:161)
```
`worldedit` 是 `-Dfabric.addMods` 挂进来的**服务端专有** mod，Fabric 启动时把它重映射进
`<gameDir>/.fabric/processedMods/`；而**客户端与服务端共用同一个 `run/`**。失败的直接原因是那份
6.3 MB 的 jar **当时不可写**（`OutputConsumerPath` 的判据就是"文件在、但写不进去"）——
上一次服务端是被**强杀**的（job 包装取消后进程才死），留下的句柄/属性让新进程写不进去；
杀软扫刚生成的大 jar 也会造成同样的瞬时锁。

**实测与处置**：
- 目录本身可写、那个文件名可建可删（`Set-Content` / `Remove-Item` 都成功）⇒ **不是权限/ACL 问题**；
- 隔几分钟**重试就过了**：11:35:26 Fabric 重新写出那份 jar，11:35:39 `Done (2.531s)!`、RCON 25575、`list` 正常；
- 再遇到：**在没有任何 dev 进程占用时**删掉 `run\.fabric\processedMods\*.jar` 再重试；
- 经验顺序：**先起服务端、再起客户端**（这次失败正是"客户端已在跑"的时候去起服务端）。

## 10. 后续（2026-10-01，见 notes/353）——本轮的两个判据都还没成立

实机当场暴露两件事，都记在 **notes/353**：

1. **解耦一次都没跑过**：判据缓存的哨兵 `Long.MIN_VALUE` 参与了减法（`now - cachedAtMillis` 溢出成负数
   ⇒ "缓存还新鲜"永远成立）⇒ `compute()` 从没被调用。日志侧证据：所有客户端日志里**一行 `[MMTR-KEY]` 都没有**。
   现修成纯函数 `MmtrDecoupleCache.fresh`（哨兵只参与等式）+ 可执行的离线用例。
2. **"按 L 弹进度页面"不是解耦漏了 L，而是反过来的**：原版 `KeyBinding.KEY_TO_BINDINGS` 一个物理键只让
   **一个**绑定收到键盘事件（赢家由 HashMap 顺序决定），L 的赢家是原版的进度页 ⇒ **我们的灯光键当时根本收不到按键**；
   同理 A 的赢家是 MMTR ⇒ 原版"向左走"在车外也失效（用户现场："只有 A 走不动，D/W/S/空格正常"）。
   现由 `MmtrKeyEventFanout` 在 `setKeyPressed` 上把事件补发给全部同键绑定。

⇒ 本文档 §5 的实机验收清单**要按 notes/353 §7 重跑一遍**（尤其"按 L 只换灯不弹进度页"与"车外 A 能走路"）。
