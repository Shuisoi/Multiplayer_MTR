# 262 — "AFB 一会 160 一会 220"：客户端的手柄规格只在坐上司机位那一拍读过一次

用户口径（2026-09-23）：

> 我有个问题，到底进没进新动力模型？怎么 afb 一会是 160，一会是 220？

## 1. 先回答"进没进"：进了（三条硬证据）

1. **部署的 jar 里有新代码**：`mmtr/game/libs/Transport-Simulation-Core-0.0.1.jar`（18:42:55）里
   `ThreeHandleDriveController.class` 的常量池含 `isAfbUsesHandleAsCap` / `afbDemand` / `handleTraction`；
   控制器的 AFB 分支就是 `min(手柄, AFB)`（notes/256）。
2. **在跑的服务端加载的是它**：服务端 18:59:10 启动（晚于 jar）；客户端 18:59:53 上车。
3. **现场日志就是新模型**（`run/dev-server.out.log`）：

```
[MMTR-CONSIST] 车=5077314884639396326 手柄=97  定速=160 控制器=ThreeHandleDriveController 牵引比=100%/电阻0%  AFB=true 电机= 300kN
[MMTR-CONSIST] 车=5077314884639396326 手柄=-97 定速=160 控制器=ThreeHandleDriveController 牵引比=0%/电阻100% AFB=true 电机=-150kN
[MMTR-CONSIST] 车=5077314884639396326 手柄=0   定速=160 控制器=ThreeHandleDriveController 牵引比=0%/电阻0%   AFB=true 电机=   0kN
```

电阻 100% 给 **-150 kN** —— 只有配置里的 `rheostaticBrakeForceN: 150000` 会给出这个数
（出厂规格是 54 kN）。⇒ 服务端用的是 `mmtr-consist-types.json` 里那份 BR101 规格。

## 2. 那 160/220 是什么：**客户端这一侧的规格是"出厂规格"**

客户端没有 `consist-types.json`，手柄规格（定速量程 / 制动档位 / 比例表）只能从**快照镜像**的
`mmtrHandleSpec` 字符串解出来。老实现是：

```java
// 只在"坐上的那一拍"读一次
if (controlledVehicleId != vehicleId) { activeSpec = specOf(vehicle); }
specOf(...) = decode(镜像) == null ? ThreeHandleSpec.defaults() : decode(镜像)
```

而**坐上那一拍镜像往往是空的**（车对象刚建、快照还没到）⇒ 退回 `defaults()`。两者的差别正好是用户看到的数：

| 字段 | 出厂 `defaults()` | 配置 `br101_three_handle` |
| --- | --- | --- |
| `cruiseMaxKmh` | **160** | **220** |
| `rheostaticBrakeForceN` | 54 kN | 150 kN |
| `rheostaticFadeKmh` | 10 | 15 |

证据（客户端日志，上车那一拍）：

```
[MMTR-DRV] client seated at 1A (vehicle 5077314884639396326
            spec=TH;0.02;96;54000;10;160;5;1;1;...;0.5;0.05;100)
```

`54000 / 10 / 160` 三个字段与出厂规格**逐字节相同** ⇒ 这一份是 `defaults()`，不是配置。

于是：**同一根杆压到底（X≈0.999）**，用出厂规格算 = 160 km/h，用配置规格算 = 220 km/h
（`MmtrHidMapping.cruiseKmhFromAxis(X, cruiseMaxKmh, 5, …)`）。手柄是绝对量，量程换了读数就换 ——
"一会 160 一会 220"就是这么来的。**与力模型无关**：力在服务端由配置规格算，一直是 300 kN / 6.4 MW 那套。

## 3. 修法（已实现）

`MmtrDriveInput`（fabric + forge 各一份）：

- 新增 `activeSpecRaw`（已认下的规格串原文）+ `adoptSpec(vehicle)`：
  **每拍比一次字符串**，变了才 `decode` 并采用；
- 镜像还没到（`decode == null`）时**什么都不做** —— 沿用上一份规格，**绝不退回出厂值**；
- 采用新规格后把手中的杆位重新钳一次（新规格可能更窄）；日志打
  `[MMTR-DRV] handle spec adopted: TH;…;220;5;…`（`-Dmmtr.trace=true` 可见）；
- 上车那一行的日志补上"镜像规格=还没到 / 已到"，下次一眼能看出是不是踩到了空镜像。

修好之后：杆压到底 = **220**（与 BR101 铭牌一致），且不会再在两次上车之间摇摆。

## 4. 遗留

`defaults()` 仍然留在 `activeSpec` 的初值上（镜像到之前的 bootstrap）。真要让"第一拍"也准，
得让服务端在车对象建立时就把 `mmtrHandleSpec` 放进**首个快照**（现在靠 `mmtrMarkSyncDirty()`，
补丁白名单里有它，但客户端对象重建后要等下一拍）—— 这条与 notes/251 的镜像重建问题同源。
