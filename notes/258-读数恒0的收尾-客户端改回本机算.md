# 258 — 读数恒 0 的收尾：客户端改回**本机算**（同步链路只做兜底）

用户口径（2026-09-23，notes/257 之后）：

> 现在屏幕 UI 就没有牵引力提示了，右上角显示 0

## 1. 为什么 257 之后变成恒 0

notes/257 把 `mmtrMotorForceN` 挂到**稀疏补丁**上、并**去掉**了"力变了就强制整份快照"。但补丁这条路要三件事同时成立才通：

1. 字段在 `VehicleSyncPatch.DYNAMIC_KEYS` 白名单里（257 加了 ✓）；
2. 服务端这一拍真的走补丁（`needsUpdate=false`）而不是整份；
3. 客户端 `VehicleExtension.updateData(patch)` → `vehicleExtraData.updateData(...)` 认得这个字段（schema 生成 ✓）。

实际表现是恒 0 ⇒ 这条路在实机上没有把值送到（整份快照现在几乎不发 —— 那正是 257 的目的，代价就是
**读数完全依赖补丁，而补丁这条链在实机上没能把这一格带过来**）。

## 2. 改回本机算（根治，不再依赖同步时机）

notes/250 最初就是本机算，当时**乱跳**的原因是"镜像对象每包重建 ⇒ 控制器累积状态被清零"。
而那个重建正是被我 257 去掉的"整份快照"逼出来的：

- 257 之前：力一变 → 标脏 → 整份快照 → 镜像重建 → 本机控制器清零 ⇒ 乱跳；
- 257 之后：力走补丁、不再标脏 ⇒ **镜像不再重建** ⇒ 本机控制器状态留得住 ⇒ **本机算既稳定又每 tick 都新**。

所以现在：

```java
public double getMmtrMotorForceN() {
    if (isClientside && (mmtrConsistType == null || mmtrDriveController == null)) {
        return vehicleExtraData.getMmtrMotorForceN();   // 刚上车那一两拍的兜底
    }
    return mmtrLiveMotorForceN();                       // 其余一律本机算（每 tick，20 Hz）
}
```

- **实时**：HUD 每帧调它，值每客户端 tick 更新一次，不经网络；
- **稳定**：没有镜像重建，控制器的建力延迟/联锁状态都在；
- **同源**：客户端跑的就是服务端那一套 `ConsistDynamics + 控制器`（notes/235 的镜像架构），
  而且它本来就每 tick 在跑（客户端自己积分走行）；
- 服务端那份快照值仍然写着（`updateMmtrSyncFields`）并留在补丁白名单里 —— 当"本机还没准备好"的兜底，
  也给将来的旁观者视图留一条路。

另外把 257 加的 1 s 刷新率诊断删掉了（它存在的唯一目的就是判定"调用/变化"两个数；
问题已定性为同步链路，不再需要现场采集）。

## 3. 这一串问题的完整因果（免得下次再走一遍）

| 现象 | 真因 | 记录 |
| --- | --- | --- |
| 数字超高速乱跳 | 镜像对象每包重建 ⇒ 本机控制器状态清零（当时还在本机算） | notes/251 |
| 恒定 300 kN | 改成读快照 + **只写不标脏** ⇒ 只在"别的字段顺带推送"时刷新 | notes/252 |
| 50% 手柄也满力 | AFB 盖掉手柄（`afbUsesHandleAsCap=false`） | notes/253 |
| 读数不实时 | 新字段不在补丁白名单 ⇒ 只在整份快照（≈30 s 兜底）时更新 | notes/257 |
| 读数恒 0 | 去掉标脏后完全依赖补丁，而补丁没把这一格带过来 | notes/258 |

**净结论**：读数走本机算（不依赖同步链路），服务端快照只当兜底。
