## 1. 为什么先做引擎侧

设计 §9 写明"编排器 = 引擎 Web 服务层的模块，浏览器只是客户端"。而上一轮现场已经暴露一件事实：
**网页要的几样东西引擎端不出来** ——

| 页面 | 要什么 | 本轮之前的状态 |
| --- | --- | --- |
| ① 线路 | 选站、选站台（站序 / 停站 / 终点处理 / 环线） | ❌ **现场没有任何接口列出"站台 id"** |
| ② 密度 | 分段表 + 趟次（时间轴） | ❌ 没有趟次表接口（设计 §9 的 `service-plan`） |
| ③ 车底 | 车辆数 / 替补 / 出库提前量 + "所需 N vs 实际" | 🟡 一半（`mmtr-plan` 有车底，N 在 diagrams 里） |
| ④ 事件 | 规则 + 生效中事件条（理由 + 剩余） | ✅ 已有 |
| ⑤ 交路 | 每辆车一行：**计划 vs 实际** | ❌ 只有"已派步数/正在等谁"，没有条目级时间轴 |
| ⑥ 指派 | 选中车辆 → 指定任务 | ✅ 已有（`assign` / `takeover`） |

于是本轮做三件事：**趟次表**、**交路时间轴**、**现场可选项**，外加一个"重新排班"入口。

## 2. 交付物

`MmtrPlanFeed`（`org.mtr.core.mmtr.plan`，**全是纯函数，不认识世界**）：

| 方法 | 给哪个页面 | 关键字段 |
| --- | --- | --- |
| `servicePlan(line, pattern, times)` | ②（也服务乘客视角） | `outbound/inbound[]`（**两个方向**）、每趟 `departureMillis`/`terminalDoneMillis`/`stops[]{stationId, platformId, arrivalMillis, dwellMillis}` |
| `timeline(working, state, dayTime)` | ⑤ | `entries[]`（条目窗口 + `phase: PAST/NOW/FUTURE`）、`steps[]`（`dispatched` / `awaiting`）、`stepCount`/`dispatchedSteps`/`awaitingTaskId` |
| `world(stations, depots)` | ①③ | 站→站台（含 `dwellMillis`）、车辆段→股道（含车辆数、轨长）；**id 一律十进制字符串**，hex 只作标签 |

接口（都在 `/mtr/api/map/` 下，与既有 `mmtr-plan*` 同一风格）：

```
GET  mmtr-plan-service-plan   趟次表（两个方向；含 ring / 高峰间隔 / 问题数）
GET  mmtr-plan-world          现场可选项（站+站台、车辆段+股道）
POST mmtr-plan-replan         强制滚动重算（网页上的"重新排班"按钮）
GET  mmtr-plan-diagrams       ← 每个 working 现在多带一条 timeline（计划 vs 实际一行）
```

`timeline` 的三态与派发器的判据**是同一个数**（`dayTime` 与条目窗口的关系）：网页上的"灰/亮/浅"
和引擎里的"该跳/该派"是同一件事的两种呈现 —— 不另立一套口径。

## 3. 顺手抓到的一条真缺陷：冻结快照**永远是空的**（P5 验收 ⑤ 等于没接）

读 `Simulator.mmtrRefreshPlanDispatchers()` 时发现：

```java
mmtrPlanDispatchers.clear();                                    // ← 先清空
final Map<String, Long> frozen = new HashMap<>();
mmtrPlanDispatchers.values().forEach(d -> frozen.putAll(d.frozenUntilByConsist()));   // ← 再取，已经空了
```

于是"在途车的当前任务不被重算改动"这条**一次都没生效**：改一次密度、来一个事件，
在途的车会被当成新班重新派。修法两层：

1. 取快照独立成 `MmtrPlanAdjustments.frozenSnapshot(dispatchers)`（可取、可测）；
2. 重建改成"**建到局部表 rebuilt，最后整体换掉**" —— 顺序不再依赖读代码时的注意力（结构上写不反）。

同一轮还补了 `Simulator.mmtrForceReplan()`（清签名再重建）给网页的按钮用。

## 6. 现场顺手发现的：**日钟基准会平移**

配置时 `dayTimeMs` 读到 **00:10**，几分钟后同一条线路的"现在"变成 **00:02** ——
锚点优先取作业单调度器的（`mmtrJobScheduler.getAnchor()`），它**晚一步**才发布锚点时，
计划先用自己定的锚点算"现在"，等调度器的锚点一到，"现在"整体平移 7.5 分钟。
时刻表本身没变（"07:00 发车"还是 07:00），但操作者会看到"过点了车怎么还没动"。

本轮**只让它可见**：基准变了就打一行 `[MMTR-PLAN] 日钟基准变了：现在从 … 变成 …`。
如实记一句：重跑那次我先等了 20 秒让作业单锚点先落地，所以**没有再平移、那行日志也没出现** ——
它的触发条件是"先算过一天、锚点再变"。要不要把基准并进计划签名（基准一变就重排）
留给下一轮判断。
