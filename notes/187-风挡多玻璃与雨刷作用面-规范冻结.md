# 187 - 风挡多玻璃与雨刷作用面：规范冻结（实现未做）

## 起因

用户："挡风玻璃面同理也可能是曲面" → 深入后给出真实需求：
一个驾驶室有**多块玻璃**；**雨刷是实体建模的**；因此要引入**雨刷作用面**（一个扇形）来定义它刮哪儿；
雨滴与雨刮动画都按作用面同步。

## 已定（用户拍板）

| 项 | 决定 |
| --- | --- |
| 命名形态 | **玻璃只有一种 kind** + 单独的**作用面锚点**；"有作用面锚点"就等于"这块玻璃有雨刷"，不在名字里重复编码 |
| 玻璃 | `mmtr_windshield_<驾驶室>[_<玻璃>]` |
| 作用面 | `mmtr_wipersweep_<驾驶室>_<玻璃>`，**建模成三角扇网格**，打包器**拟合**出支点/半径/起止角 |
| 实体雨刷 | 模型里名为 `wiper_<驾驶室>_<玻璃>` 的对象 |
| 玻璃编号 | **主档永远 = 1**，侧窗等依次递增 |

拼写：用户写的是 "windsheld"，但这**不是英语单词** —— 标准英语是 **windshield**（wind + shield）。
仓库现有 `windshield` **175 处 / 16 个文件**、`windsheld` **0 处**，已建模的 SAF101v2 里就是
`o mmtr_windshield_1` / `_2`。所以一律沿用 `windshield`；用户若坚持要另一个拼写，说一声再改。
（这条要留记录：把拼写错误固化进"以后不好改"的命名规范，代价是全部代码+文档+已有模型+已发资源包。）

## 规范全文

写在 `mmtr/docs/02-运行与作业/MMTR-OBJ车辆资源包-标准化工作流.md` **§1.4**（新增）+
§1.1 锚点表 + §3.1 命名约定表。要点：

1. **索引规则（向后兼容的关键）**：一个索引 = **驾驶室号**（玻璃默认 1）；两个索引 = 驾驶室号 + 玻璃号。
   于是 `mmtr_windshield_1` = 驾驶室 1 主档、`mmtr_windshield_2` = **驾驶室 2** 主档（老模型照旧），
   `mmtr_windshield_1_2` = 驾驶室 1 的第 2 块玻璃。
   **若把单个索引当成"玻璃号"，SAF101v2 的两块玻璃就会从"两个驾驶室各一块"变成"驾驶室 1 的两块" —— 静默错位。**
2. **作用面扇形**：三角扇，**所有三角形共享的那个顶点 = 支点**。打包器拟合：
   支点 → `pivotU/pivotV`（左/下起算的比例）、最远顶点 → `armM`、两条边界边 → `parkAngleDeg`/`sweepDeg`
   （从面的**右**边量起、+ 朝上）、方向 → `sweepSign`。
   **这些就是现有 `windshield` 配置块里的字段** —— 所以"把参数用几何画出来"= 产出同一组数据，
   **客户端这套雨刷/擦拭逻辑几乎不用改**（`WindshieldConfig.get(vehicleId, anchorName)` 本来就是按锚点名读的）。
3. **曲面**：玻璃折面/曲面 → N 个共边四边形放进**同一个** Object，走 186 那套**沿折痕展开**；
   雨滴/湿度/雨刷在**展开域**里模拟（弧长保真，不被弦长压缩），雨层与刀片**逐面**渲染、刀片按面裁剪。
   扇形顶点沿同一套展开落进同一个域 → **作用面自动跟着曲面走**。
4. **实体雨刷**：角度与玻璃刮拭**共用同一份动画状态**（就是现在驱动画刀片的 `wiperAngleDeg`），
   所以两者天然同步，不存在两套时间。

## 现状核查（做之前查过代码，不是猜的）

- **多块玻璃本来就能跑**：`findWindshields(anchors, car)`（`MmtrVehicleAnchors:233`）返回该车**所有**风挡锚点；
  `MmtrWindshield:288` 给每个锚点建独立 `State`（各自雨滴数组/湿度网格/画布/贴图，key = `windshield:<name>:<car>`）；
  配置按锚点名读。**不需要新架构**。
- **卡在两处**：打包器 `wsm=/^windshield(?:_(\d+))?$/` 只允许一个索引且当驾驶室用；
  `findWindshield(anchors, car, cab)` 只返回该驾驶室的**第一块** → 雨刷档/司机在车上/面板指示灯会**拿错玻璃**。
- **实体雨刷要动引擎**：OBJ 部件的每帧变换目前只有**平移 + 0/π 的 Y 旋转**
  （`ModelPropertiesPart` 的 `partDetails.modelParts...render(g, x, y, z, flipped ? PI : 0, ...)` 与
  `addObjModelPosition` → `addTransformation(shaderType, x, y, z, flipped)`）。
  绕支点连续转需要在 `OptimizedRendererWrapper.queue(...)` 外面 push / 平移到支点 / 旋转 / 平移回来，
  并**量 optimized 缓存失效的代价**。

## 用户答案引出的两个打包器坑（当前**未修**，实现 W1 时一并处理）

`wiper_<cab>_<pane>` **没有 `mmtr_` 前缀**，所以：

1. `roleOf()` 匹配不上 → `currentRole = null` → 那些面**不写 `g` 行却仍会写出去**
   （`if(currentRole!=='anchor') out.push(remapFace(t))` 对 `null` 也成立）→ **静默粘到前一个组**。
   必须给 `groupMap` 加角色（如 `"wiper": ["wiper"]`）。
2. 光加角色还不够：非门角色的组名会被**统一改写成角色名**（`out.push('g '+cn)`），
   于是**所有雨刷并成一个部件**、无法各自独立旋转。门叶有特殊处理（保留各自组名），
   **雨刷需要同样的处理**。

## W1 已实现（打包器 + 离线校验）

### 命名

`pack_vehicle.js`：`wsm=/^windshield(?:_(\d+))?(?:_(\d+))?$/` + `swm=/^wipersweep(?:_(\d+))?(?:_(\d+))?$/`。
**单索引 = 驾驶室，双索引 = 驾驶室 + 玻璃**。锚点 JSON 里 `pane` **只在 ≠1 时写**，
所以单玻璃模型的老锚点条目**逐字节不变**。

### 扇形拟合

`fitWipersweep(group, domain)`：

- **支点 = 每个面都出现的那个顶点**（三角扇的扇心）。**两个三角形时这条会给出两个候选**
  （两个三角形共享一条边，几何上就是个四边形，哪个角是支点**根本不在网格里**）→ 退而用
  "每个面的第一个顶点"并打 NOTE。以后建模请用 **≥3 个三角形**。
- 起始角用**最大角度空隙**定位（排序后找最宽的空隙，扇形就是它的补集）—— 不需要"哪端是停放位"的约定，
  过 ±180° 也不会搞反。
- 映射到**现有**字段 `pivotU/pivotV/armM/parkAngleDeg/sweepDeg/sweepSign`，所以**客户端零改动**。
- 拒绝时全部打 WARNING 并说明原因（扇心不唯一 / 跨度<5° / 支点远在玻璃之外）——
  静默忽略的扇形 = 一个永远不刮的雨刷，在游戏里几乎无法诊断。

### 实体雨刷部件与 `drawBlade`

`wiper_<cab>_<pane>` 按名字约定**直接识别为独立可见部件**（无需 `groupMap` 条目，每个雨刷一件）。
顺手堵掉两个坑：没有 `mmtr_` 前缀的组若不识别，面会**不写 `g` 行却仍写出去**（静默粘到前一组）；
而通用 `"wiper"` 角色会把所有雨刷并成一个部件、还会在 `mmtr_wipersweep_*` 里抢名字
（5 字符 "wiper" 与 5 字符 "mmtr_" **打平**，胜负由对象键顺序决定 —— 所以还加了
`RESERVED_ANCHOR_KINDS` 白名单：`hud/seat/cabdoor/ack/windshield/wipersweep` 开头的名字**永远是锚点**。
**故意不含 `door`**：HST_B 与 p1 的客车门就叫 `mmtr_door_l_1`，靠更长的 `door_l` 模式赢过 `mmtr_`）。

## 追加：雨刷机构统一模型（用户："大部分雨刷是平行连杆结构或单轴汽车结构"）

两族不是参数差别而是**机理**差别：单轴 = 刀片随臂**转**；平行连杆 = 刀片**只平移不转**。
统一成"刀片两端各绕自己的支点转同一个角"：

```
A(theta) = P1 + R(theta)*(A0 - P1)      B(theta) = P2 + R(theta)*(B0 - P2)
```

- `P1 = P2` ⇒ 刚性转动（单轴）
- 连杆向量相等 ⇒ `B - A` 恒定 ⇒ 纯平移（平行连杆）。代入即可证，**不需要分支**

**各部件独立命名**（用户定的）：`wiper_` 刀片 / `wiperrod_` 拉杆 / `wiperarm_` 臂。
打包器按名字认、各自成件，并拟合 A0 B0（主轴 PCA —— **不能**用"最远两点"：盒子的最远两点是对角线，
会把刀片算长）、P2（拉杆贴住刀片的那端是接头，另一端是支点），并交叉校验臂的远端落在刀片**线段**上
（第一版要求它落在 A0 上，结果把真车全判错：**臂是拧在刀片中间的**，不是端头）。

**擦拭区域按几何分流**：一个支点用**扇形**（精确），两个支点用两次位置的**四边形 band**。
这是被离线断言逼出来的：先写成"有建模刀片就用 band"，单轴那块的断言挂了 4 个点 ——
四边形是直边，切掉了转动真正扫过的**弧**（矢高 ≈ R(1−cos)）。平移用四边形精确，转动不精确。

### ⚠️ 顺手发现的两个既有缺陷（**本次刻意没改**，因为无法在游戏里验证）

`driverOnBoard()` 现在是 false ⇒ 雨刷不运行 ⇒ **改刮拭几何无法验收**。所以下面两条只记录、不动手：

1. **刮拭区域的坐标系与雨滴是镜像的。** 证据链：
   - 雨滴 `drop.y` 是 **y 向上**：`advanceDrop` 里 `stepY = -down[1]*climbSpeed`，静止时
     `surfaceSpeedClimb = -gravityDown < 0`，而 `down[1] <= 0`（下坡）⇒ `stepY <= 0` ⇒ 下落时 `drop.y` **减小**。
   - `rebuildCanvas` 把 `dropY = drop.y * heightM`（y 向上）直接喂给 `wipeFactor`，而 `wipeFactor` 是
     **y 向下**的口径：`atan2(-deltaY, deltaX)` + `pivotY = (1 - pivotV) * heightM`（pivotV 是从**下**边量，
     所以 `(1-pivotV)` 只有在 y 向下时才是"下边"）。两者内部自洽，但**和雨滴差了 180°**。
   - `drawWiperFilm` 又把 y 向下的 `pivotY` 传给 `canvas.fillSector`，而 `fillSector` 要的是 y 向上
     （`py(m) = (heightM - m) * scaleY`）—— 第三处口径不一致。
   修法：在 `rebuildCanvas` 边界一次性换算（`(1 - drop.y) * heightM` 给刮拭/湿度，`drop.y * heightM` 给绘制），
   并把 `fillSector` 的 y 翻回来。**等 B2 让雨刷能跑起来再改，那时才验收得了。**
2. **`wipe < 0` 会连绘制一起跳过。** `wipeFactor` 对"超出臂长"的点返回 −1（文档写的是"让调用方跳过它"），
   而调用方 `if (wipe < 0) continue;` 把 `drawDrop` 也跳过了 ⇒ **雨刷一动，臂长之外的雨滴就消失**。
   新加的 band 路径从不返回 −1（没擦到的返回 0），所以新机构不受影响；老路径跟上面一起改。
