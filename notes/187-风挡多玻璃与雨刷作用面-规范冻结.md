# 187 - 风挡多玻璃与雨刷作用面：规范冻结（实现未做）

## 起因

用户："挡风玻璃面同理也可能是曲面" → 深入后给出真实需求：
一个驾驶室有**多块玻璃**；**雨刷是实体建模的**；因此要引入**雨刷作用面**（一个扇形）来定义它刮哪儿；
雨滴与雨刮动画都按作用面同步。

## 已定（用户拍板）

| 项 | 决定 |
| --- | --- |
| 命名形态 | **玻璃只有一种 kind** + 单独的**作用面锚点**；"有作用面锚点"就等于"这块玻璃有雨刷"，不在名字里重复编码 |
| 玻璃 | `mmtr_windshield_<驾驶室>[_<玻璃>]` |
| 作用面 | `mmtr_wipersweep_<驾驶室>_<玻璃>`，**建模成三角扇网格**，打包器**拟合**出支点/半径/起止角 |
| 实体雨刷 | 模型里名为 `wiper_<驾驶室>_<玻璃>` 的对象 |
| 玻璃编号 | **主档永远 = 1**，侧窗等依次递增 |

拼写：用户写的是 "windsheld"，但这**不是英语单词** —— 标准英语是 **windshield**（wind + shield）。
仓库现有 `windshield` **175 处 / 16 个文件**、`windsheld` **0 处**，已建模的 SAF101v2 里就是
`o mmtr_windshield_1` / `_2`。所以一律沿用 `windshield`；用户若坚持要另一个拼写，说一声再改。
（这条要留记录：把拼写错误固化进"以后不好改"的命名规范，代价是全部代码+文档+已有模型+已发资源包。）

## 规范全文

写在 `mmtr/docs/02-运行与作业/MMTR-OBJ车辆资源包-标准化工作流.md` **§1.4**（新增）+
§1.1 锚点表 + §3.1 命名约定表。要点：

1. **索引规则（向后兼容的关键）**：一个索引 = **驾驶室号**（玻璃默认 1）；两个索引 = 驾驶室号 + 玻璃号。
   于是 `mmtr_windshield_1` = 驾驶室 1 主档、`mmtr_windshield_2` = **驾驶室 2** 主档（老模型照旧），
   `mmtr_windshield_1_2` = 驾驶室 1 的第 2 块玻璃。
   **若把单个索引当成"玻璃号"，SAF101v2 的两块玻璃就会从"两个驾驶室各一块"变成"驾驶室 1 的两块" —— 静默错位。**
2. **作用面扇形**：三角扇，**所有三角形共享的那个顶点 = 支点**。打包器拟合：
   支点 → `pivotU/pivotV`（左/下起算的比例）、最远顶点 → `armM`、两条边界边 → `parkAngleDeg`/`sweepDeg`
   （从面的**右**边量起、+ 朝上）、方向 → `sweepSign`。
   **这些就是现有 `windshield` 配置块里的字段** —— 所以"把参数用几何画出来"= 产出同一组数据，
   **客户端这套雨刷/擦拭逻辑几乎不用改**（`WindshieldConfig.get(vehicleId, anchorName)` 本来就是按锚点名读的）。
3. **曲面**：玻璃折面/曲面 → N 个共边四边形放进**同一个** Object，走 186 那套**沿折痕展开**；
   雨滴/湿度/雨刷在**展开域**里模拟（弧长保真，不被弦长压缩），雨层与刀片**逐面**渲染、刀片按面裁剪。
   扇形顶点沿同一套展开落进同一个域 → **作用面自动跟着曲面走**。
4. **实体雨刷**：角度与玻璃刮拭**共用同一份动画状态**（就是现在驱动画刀片的 `wiperAngleDeg`），
   所以两者天然同步，不存在两套时间。

## 现状核查（做之前查过代码，不是猜的）

- **多块玻璃本来就能跑**：`findWindshields(anchors, car)`（`MmtrVehicleAnchors:233`）返回该车**所有**风挡锚点；
  `MmtrWindshield:288` 给每个锚点建独立 `State`（各自雨滴数组/湿度网格/画布/贴图，key = `windshield:<name>:<car>`）；
  配置按锚点名读。**不需要新架构**。
- **卡在两处**：打包器 `wsm=/^windshield(?:_(\d+))?$/` 只允许一个索引且当驾驶室用；
  `findWindshield(anchors, car, cab)` 只返回该驾驶室的**第一块** → 雨刷档/司机在车上/面板指示灯会**拿错玻璃**。
- **实体雨刷要动引擎**：OBJ 部件的每帧变换目前只有**平移 + 0/π 的 Y 旋转**
  （`ModelPropertiesPart` 的 `partDetails.modelParts...render(g, x, y, z, flipped ? PI : 0, ...)` 与
  `addObjModelPosition` → `addTransformation(shaderType, x, y, z, flipped)`）。
  绕支点连续转需要在 `OptimizedRendererWrapper.queue(...)` 外面 push / 平移到支点 / 旋转 / 平移回来，
  并**量 optimized 缓存失效的代价**。

## 用户答案引出的两个打包器坑（当前**未修**，实现 W1 时一并处理）

`wiper_<cab>_<pane>` **没有 `mmtr_` 前缀**，所以：

1. `roleOf()` 匹配不上 → `currentRole = null` → 那些面**不写 `g` 行却仍会写出去**
   （`if(currentRole!=='anchor') out.push(remapFace(t))` 对 `null` 也成立）→ **静默粘到前一个组**。
   必须给 `groupMap` 加角色（如 `"wiper": ["wiper"]`）。
2. 光加角色还不够：非门角色的组名会被**统一改写成角色名**（`out.push('g '+cn)`），
   于是**所有雨刷并成一个部件**、无法各自独立旋转。门叶有特殊处理（保留各自组名），
   **雨刷需要同样的处理**。

## 离线验证打算怎么做

- 扇形拟合：合成 fixture（一块玻璃 + 一个三角扇），断言拟合出的
  `pivotU/pivotV/armM/parkAngleDeg/sweepDeg` 与手算一致；扇心不唯一/非共面/角跨 360° 都要报错。
- 命名与配对：`windshield_1` vs `windshield_1_2` vs `windshield_2` 的解析断言（**这条直接防上面那个静默错位**）；
  有 sweep 无玻璃、有玻璃无 sweep 的配对检查。
- 向后兼容：`git show HEAD:` 的旧打包器 vs 新打包器跑同一源文件（hst_h / saf101 / saf101v2），锚点 JSON 必须逐字节相同。
- 曲面：扩 `mmtr/tools/wiper-preview`，加"域内 1 m = 曲面 1 m"的弧长断言与刀片逐面贴合断言。
