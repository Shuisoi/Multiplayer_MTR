## 2. 场地是**量**出来的，不是猜的

新增 `sandbox/scan_surface_area.py`：直接读 region 文件里的 `Heightmaps.WORLD_SURFACE`，
一次扫描给出整个矩形的地表高度分布 / 最平窗口 / ASCII 高度图（512×512 只要 ~1.8 秒）。

**两个必须记住的数据口径**：

1. **heightmap 的值是"相对维度最低建筑高度"的，不是绝对 y。** `Heightmap.getFirstAvailable`
   会把 `chunk.getMinBuildHeight()` 加回去；主世界 minY = -64，所以
   `绝对首个空气 y = 存的值 - 64`、`地表顶格 = 存的值 - 65`。
   实测对照：`(200,200)` 存的值 130，真实是 y=64 草方块 + y=65 矮草（首个空气 66 = 130-64）。
   **按绝对值读会让每一列都高 64 格** —— 第一版就是这么错的（扫出来地表 122..136）。
2. 结果：默认扫描区 70.8% 的列地表恰为 y=62（就是海面），
   最大一块 80×224 全平窗口是 `x=-144..-65 / z=-155..68`，**17920/17920 列起伏 0 格**。
   陆地只在地图东北角（地表 y=63..71，有起伏）。

施工前抽样复核（`read_block.py` 直读存档）：`(-144,63,-155)`/`(-104,63,-43)`/`(-65,63,68)` 全是空气、
y=62 全是水 ⇒ "铺三层就把水面盖住、轨道落在干面上"成立。

## 5. ⚠️ 节点朝向：`rail add` 的方位必须按 **mod 180** 比（用户当场发现）

**现象**（用户 2026-09-25）：16 条侧线**z=67 那端的节点整个横了 90°**，要转 90° 才对。
存档取证：z=-153 的 16 个节点一律 `facing=false`，z=67 的 16 个一律 `facing=true` ——
**一根直轨的两端本来就该是同一个朝向**，所以是远端错了。

**根因**：`BlockNode.getAngle` 的取值只有 `0 / 22.5 / … / 157.5`。
看 `assets/mtr/blockstates/rail.json` 就明白：节点只有 8 个分支 = 4 个模型
（`rail_node` / `_22_5` / `_45` / `_67_5`）各配 `facing` 的 0°/90° 两种 y 旋转，**不存在 180° 以上的值**。
⇒ 节点的朝向空间本身是 **mod 180** 的。
而 `MmtrCommandExecutor.resolveNodeState` 拿 `0..360` 的几何方位去比，于是"远端"出错：
沿 Z 的轨起点方位 90° 命中 90°（对），终点方位 270° 在可达集合里的最近值是 **0°**（差 90°）而不是 90°。

补充：这也解释了为什么**轨的几何长度恰好是 220 m** —— `Rail.getAngles` 把终点的 0° 折成了 180°（-X），
两条切线交于 `(-142, 67)`，正好落在弦上，二次贝塞尔退化成直线。**所以错的只是显示朝向，不是走行几何。**

**处置一（当场生效，不重启）**：`/setblock` 把 16 个 z=67 节点改成
`mtr:rail[facing=false,is_22_5=false,is_45=false,is_connected=true,waterlogged=false]`，
与 z=-153 端一致。方块状态纯显示，不触发 `onBreak2`，**引擎侧一点没动**（改完复查仍是 16 条 × 220 m）。

**处置二（改源码，下次重启生效）**：`MmtrCommandExecutor.resolveNodeState` 把目标方位与候选角度
**都折到 mod 180** 再取最小夹角：

```java
final double targetBearing = ((Math.toDegrees(Math.atan2(dz, dx)) % 180) + 180) % 180;
final double actual = org.mtr.mod.block.BlockNode.getAngle(candidate) % 180;
final double raw = ((actual - targetBearing) % 180 + 180) % 180;
final double difference = Math.min(raw, 180 - raw);
```

离线复算（0..359 逐个方位）：**每个方位与它的反向方位现在得到同一个状态，全 360 个都对得上**；
沿 Z 两端都落在 `(facing=false, F, F)`，与现场手改的结果一致。最大残差 11°（22.5° 量化的固有误差）。

> 教训：原注释里"两个口径一起错反而仍然自洽"这句话是**错的** —— 它只对了"口径相同"，
> 漏了"**取值范围也得相同**"。一个 0..360 对一个 0..157.5，必然有一半方位是错的。

## 6. Depot：留给用户在游戏里画（本轮不动引擎）

查过：引擎指令面里 **没有"建车辆段"这个词** —— `rail / signal / point / vehicle / manifest / job / query / server`
都有，唯独 depot 只能由玩家在游戏里的 MTR 仪表盘画（`DashboardScreen.buttonAddDepot` → 点两个角 →
`PacketUpdateData.addDepot`）。用户选择**自己在游戏里画**，因此本轮不改引擎、不重启。

**给用户的两点**：

- 仪表盘 → 车辆段 → 添加车辆段 → 点平台的**对角**（x/z 那两角即可）。
  MTR 的选区只取 x/z：`DashboardScreen` 里是
  `setCorners(new Position(x1, Long.MIN_VALUE, z1), new Position(x2, Long.MAX_VALUE, z2))`
  —— **y 是无界的**，所以不存在"点低了导致股道收不进去"这个坑。
- 16 条股道的中点都在 `(x, 65, -43)`，只要选区在 x=-142..-67 / z=-155..68 之内就全能收编。
- 收编走的是 `UpdateDataRequest.update() → data.sync() → mapAreasAndSavedRails`（按几何判定），
  与玩家放轨同一条路；之后任何一次 `rail add` 也会顺手重算归属。
