## 0. 一页速览

```text
             ┌──────────────── 输入层（唯一落盘的东西）────────────────┐
             │ MmtrPlanInputs = 线路 MmtrLine + 密度表 MmtrPattern     │   mmtr-plan.json
             │                + 车底 MmtrFleet                        │
             └───────────────────────────┬────────────────────────────┘
                                         │ 纯函数（可重放，不落盘）
                    ① 趟次表 MmtrServicePlan.generate(line, pattern, times)
                       └ 发车槽位(密度段左闭右开) → 每趟逐站到发 + 终点处理
                    ② 交路   MmtrDiagram：i mod N 套班（N=ceil(ring/高峰间隔)）
                       └ 每车：出库 → 往 → 返 → … → 回库；替补不占趟次
                    ③ 事件/人工 MmtrPlanAdjustments.recompute(...) → 调整后的交路 + notes
                    ④ 任务序列 MmtrPlanTasks.expand(line, working)  ← 交路展开成"一步一个任务"
                                         │
             ┌───────────────────────────▼────────────────────────────┐
             │ 派发（运行时，每 tick）                                  │
             │ MmtrPlanDispatcher.tick(dayTime, world)                 │
             │   分车 → 等上一步 → 等到点 → 出库闸门 → 迟到跳过 → 派下一步 │
             │ MmtrPlanWorld.dispatchTask → new MmtrMission + attachTask│
             └───────────────────────────┬────────────────────────────┘
                                         │ 挂到车上（mission = 运行时容器）
             ┌───────────────────────────▼────────────────────────────┐
             │ 执行（车辆侧，每 tick）：Vehicle.mmtrMissionTick()        │
             │   自臂规划 → 申请进路/道岔 → 走行 → 到位 → 停站/换端      │
             │   → 状态机推进 → 终态清理（放道岔/关自动/关门）           │
             └────────────────────────────────────────────────────────┘
```

**四句话**：

1. **三层概念**：**任务定义**（`MmtrTask`，纯值对象，9 种）→ **任务实例**（`MmtrMission`，挂在车上，
   带状态机与执行者）→ **执行**（`Vehicle.mmtrMissionTick()`，真正动手的人）。
2. **两条编排路径并存**：**时刻表派发**（P4，`MmtrPlanDispatcher`）与**作业单**（`MmtrJobScheduler`），
   外加**手工指令**（`MmtrMissionControl`）与**连挂手术**（`MmtrCoupleSurgery`）——
   全世界一共 **4 处** `setMmtrMission`。旧的那条（`MmtrPeriodicTaskSource`）是**空壳**。
3. **生成器是纯函数**：输入 → 趟次表 → 交路 → 任务序列，只依赖"走行时间"这一个世界侧接口；
   **只落盘输入**，计划本身每次重放（可重放、改一行就整条重算）。
4. **计划不知道现实**：走行时间 = 里程 ÷ 编组速度（恒速，没有加减速、没有信号/道岔等待），
   终点处理固定 3 分钟 —— 现实里的等待全靠执行期兜，兜不住就靠"迟到 10 分钟宽限 + 跳过"。

## 1. 时刻表生成器（✅ 我逐段读过）

### 1.1 输入（唯一落盘的那一层）

| 输入 | 类 | 关键字段 | 校验 |
| --- | --- | --- | --- |
| 线路 | `MmtrLine`(216 行) | `lineId` / `stops[]`（站 id、去程台、**回程台** `returnPlatformId`、`dwellMillis`）/ `yardSidingId` / `leadTimeMillis` / `terminalTreatment`(CHANGE_ENDS\|TURNBACK\|STABLE) / `loop` | `line.validate()`：没出库股道等 → 进 `errors` |
| 密度表 | `MmtrPattern`(196 行) | `segments[]` = `[fromMillis, toMillis)` + `headwayMillis` | 段重叠/坏段 → `errors` |
| 车底 | `MmtrFleet`(207 行) | `consists[]`（`consistId` + `maxSpeedKmh` + 车卡）/ `spares[]` | 容量校验 `validateCapacity(ring, headway)` |

- 落盘：`run/world/mtr/<dim>/mmtr-plan.json`（`lines` / `patterns` / `fleet`）✅
- **坏配置的后果**：`errors` 非空 ⇒ **不排班**（不新排、旧班也清），并把派出去的任务收回 ✅

### 1.2 趟次表 `MmtrServicePlan`（285 行，纯函数）

- `departureSlots(pattern)`：按密度段**左闭右开**展开发车时刻（`from ≤ t < to`，步长 headway）✅
- `generate(line, pattern, times, OUT)`：每趟 `buildTrip` —— 逐站累加 `legMillis`，到站记 `arrival`，
  停站时长**记在到达上**（起点站不停），末站 + `terminalMillis(处理方式)` = `terminalDoneMillis` ✅
- **回程（BACK）不是另一份时刻表**：发车时刻 = 对应往程趟的 `terminalDoneMillis`（镜像）✅
- 回程走**另一侧站台**（`stop.returnPlatformId`，notes/154）✅
- `ringMillis` = 往程 + 返程 + **两次**终点处理（与设计字面公式的偏离写在注释里）✅

### 1.3 交路 `MmtrDiagram`（321 行）

- 套班：`N = ceil(ring / 高峰最小间隔)`，第 i 个发车槽位 → 第 `i mod N` 辆车，且这辆车同时承担**同一槽位的返程** ✅
- 每条 `Entry`：`DEPART_YARD`（出库到首发台）/ `TRIP`（往或返，带完整到发）/ `STABLE_YARD`（回库）✅
- 替补（`fleet.spares`）**一个趟次都不占**，只在顶替时上场 ✅

### 1.4 走行时间（世界侧唯一接口）

- 接口 `MmtrTravelTimes`（56 行）：`legMillis(from,to)` + `terminalMillis(treatment)`；用例用 `uniform()` 假世界 ✅
- 真实实现 `MmtrRailTravelTimes`（105 行）：
  - 速度取**编组 `maxSpeedKmh`**（不是轨道限速；缺省 80）✅
  - 站间里程 = `MmtrRailDistance.between(...)`（沿轨 Dijkstra，只算**相邻**站）✅
  - 走不到 → `-1` → **0 分钟**（"看得见的错"而不是编个假数字），并有 `describeMissingLegs()` ✅
  - `millisForDistance` = 里程 ÷ 速度，**恒速**：没有加减速、没有信号/道岔等待、没有限速 min 链 ✅
  - 终点处理 = 固定 `DEFAULT_TERMINAL_MILLIS = 3 分钟`（换端/掉头/回库同一个数）✅

### 1.5 事件与人工调整 `MmtrPlanAdjustments`（341 行）

- 三条冻结节律（注释里写死）：**过去不可改** / **在途不打断**（`frozenUntil`）/ **重算不抢在途车已持有的道岔** ✅
- 事件模型 `MmtrEvent`：4 类（`PEAK_SURGE` 动计划层 / `DELAY` 动运用层 / `FAULT` 故障 / `SPEED_RESTRICTION` 降速），
  目标 LINE/STATION/SECTION(一组轨)/CONSIST；`state` 由时钟算（不存）；**事件不落盘** ✅
- `recompute(...)` 只产出"调整后的输入"再调一次同一组纯函数 → **没有第二套排班逻辑** ✅

### 1.6 任务序列 `MmtrPlanTasks`（147 行）

- 交路 → 有序任务表：出库=DRIVE_TO_PLATFORM；每站=DRIVE_TO_PLATFORM(+STATION_SERVICE，`dwell>0` 才加)；
  终点处理三态 = CHANGE_ENDS / DRIVE_TURNBACK / DRIVE_TO_SIDING；末段回库 = DRIVE_TO_SIDING（去重）✅
- 任务 id 形如 `L1/C1/035`；计划时刻 `earliestMs = dueMs = 该步计划时刻`（`note = "时刻表 07:05"`）✅
- 站台作业的计划时刻取**到站**而不是发车（notes/155 §8：否则每站白等一个停留）✅

## 2. 派发器（✅ 读过 tick 与状态字段）

`MmtrPlanDispatcher.tick(dayTime, world)`（401-482）：对每条交路（`WorkingState`）按固定顺序判：

| 顺序 | 判据 | 行为 |
| --- | --- | --- |
| 1 | `isComplete()` | 跳过 |
| 2 | 玩家接管（`playerDriven`） | 跳过（设计：接管只换执行者） |
| 3 | `vehicleId == 0` | `acquire`：本线路车场里**空闲且没被别的交路占用**的车；拿不到**原地等**（不跳步） |
| 4 | 手上有活（`awaitingTaskId`） | ①还在跑 → 等；②车空了 → 派下一步；③车忙别的 → **解绑重找车** |
| 5 | 未到点（`dayTime < earliestMs`） | 等 |
| 6 | **出库闸门**（第一步） | 距上次出库不足 `YARD_DEPARTURE_GAP_MILLIS = 4 分钟` → 等（咽喉只有一组道岔） |
| 7 | 迟到超 `LATE_GRACE_MILLIS = 10 分钟` **且整趟窗口已过** | **跳过**（记 `skippedIndexes`，不补跑） |
| 8 | 派 | `dispatchTask` → 成功则 `dispatchedSteps++`、`awaitingTaskId=taskId`；第一步成功时记出库时刻 |

- 计数器：`dispatchedTotal` / `retryCount` / `skippedSteps` ✅
- `WorkingState.dispatchedSteps` **把"跳过"和"派出"都算**，所以另设 `skippedIndexes` 供"这趟是否已在跑"判断 ✅

**挂到车上**（`Simulator.MmtrPlanWorld.dispatchTask`，1059-1093 ✅）：`dispatchable()` 检查 →
原地动作取"车此刻所在轨"当目的轨 → mission kind = 目标是站台 ? PASSENGER : MANEUVER →
`new MmtrMission(...).attachTask(task)` → `vehicle.setMmtrMission` → 非 motion 车 `engageMissionAutopilot()`。

**收回**（✅）：`releaseTask` 只在"车上跑的正是这一步"时 `setMmtrMission(null)`；
`mmtrWithdrawPlanTask` 遇**车还在动**只记账（`MmtrPendingPlanReleases`），等停稳再收（notes/153）。

## 3. 重建与交接（改配置/加事件之后）

- **输入签名** `mmtrPlanSignature()`：线路（id、**站数**、出库股道、提前量、loop）+ 密度表（各段）
  + 车底（数量）+ **轨数** + 手工指派 + 事件（id/类型/起止/目标/严重度/参数）✅
- 重建顺序（注释里被现场教训固定下来）：**先取冻结快照** → 逐线重建（事件重算 → 手工指派 → 换代交接）
  → 消失的线路收回任务 → 换掉整张表 ✅
- 换代交接 `adoptFrom`：把上代"谁在跑、跑到第几步、在等哪一步"接到新代；**孤儿**（车没了/不是那一步/目标变了）
  交给调用方收回 ✅
- **出库闸门要接手** `adoptYardDepartureGate`（否则重建后几台车同一个 tick 一起出库、互锁咽喉，notes/155 §17）✅

## 4. 任务系统（✅ 与并行调研逐条对齐过）

### 4.1 三层与 9 种任务

| 层 | 类 | 说明 |
| --- | --- | --- |
| 定义 | `MmtrTask`(92) + 9 个实现 | **纯值对象**：`taskId / targetRef / targetKind / earliestMs / dueMs / note`；行为只有 `kind() / describe() / validate() / inPlace() / dispatchable()`。**没有状态字段** |
| 实例 | `MmtrMission`(151) | 挂在车上的运行时容器：`Kind`(PASSENGER/FREIGHT/MANEUVER)、`State`、`Executor`(AUTOPILOT/PLAYER/AI)、`failureReason`、`task` |
| 执行 | `Vehicle.mmtrMissionTick()` | 真正动手的人（见 4.3） |

9 种任务（`MmtrTaskKind`）与**谁在用**：

| kind | 含义 | 生成者 | 现状 |
| --- | --- | --- | --- |
| `DRIVE_TO_PLATFORM` | 开到站台停稳 | 计划（出库/中间站） | ✅ 在用 |
| `STATION_SERVICE` | 站台开关门停站 | 计划（`dwell>0`） | ✅ 在用（`inPlace()=true`，且要求车真在该台轨上） |
| `DRIVE_TO_SIDING` | 开往股道 | 计划（回库/终点 STABLE） | ✅ 在用 |
| `CHANGE_ENDS` | 原地换端 | 计划（终点 CHANGE_ENDS）/ 作业单 | ✅ 在用（**没有目标**，靠 `inPlace()` 才派得出去，notes/150） |
| `DRIVE_TURNBACK` | 经折返轨掉头 | 计划（终点 TURNBACK） | ✅ 在用（作业单侧产不出它） |
| `COUPLE` / `UNCOUPLE` | 连挂/解挂 | **只有 `MmtrTaskFactory` 两条分支** | ⚠️ **实际不可达**（见 §6.1），真连挂走 `MmtrCoupleSurgery` |
| `DRIVE_TO_CONSIST` | 连挂走行 | 无 | ⚠️ 主代码**从不构造**（只测试用），`approachSpeedKmh` 只写不读 |
| `FREIGHT_WORK` | 货运装卸 | 无 | ⚠️ 主代码**从不构造**，`workMs` 只在 `describe()` 里读 |

### 4.2 mission 状态机与执行者

```text
ASSIGNED ──► DISPATCHED ──► AT_TARGET ──► COMPLETE
   │             │              │
   └─────────────┴──────────────┴──► FAILED / CANCELED
```

- 迁移表在 `MmtrMission.transition()`：终态不可再迁移 ✅
- **谁推进**：`Vehicle.mmtrMissionTick()`（`ASSIGNED→DISPATCHED` 看 `isMoving()`；`DISPATCHED→AT_TARGET` 看停稳到位；
  `AT_TARGET→COMPLETE` 按**任务给的停留**计时，站台作业按计划 dwell、其余任务到站即完成 —— notes/155）✅
- **终态清理**（`isTerminal()` 时一次性放掉外面的一切）：放道岔申请、关自动走行、清停车目标、
  清玩家进路闩、**关门** ✅
- ⚠️ `CANCELED` 在 main 代码里**不可达**（`cancel()` 只被测试调用）；`Executor.AI` 在 main 里**从不赋值** ✅

### 4.3 `Vehicle.mmtrMissionTick()` 每 tick 的固定顺序（✅ 读过 520-648）

1. **自臂**：motion 车的任务由自己解析目标台/股道 → `MmtrRunPlanner.planToRail` → 规划不可行先**反向一次**
   （`mmtrMissionFlippedForTarget` 防 A/B/A 循环）→ 仍不行 `mission.fail`；`needsShuntAuthority` 时给**整条进路**发调车授权
2. **停着不动却按着道岔 → 让位**（`mmtrYieldTurnoutsWhenStuck`）
3. **被岔挡住时自己补一条申请**（`mmtrRequestPointWhenHeldAtFork`）
4. **原地任务动作**：站台作业开关门、换端（`mmtrRunInPlaceTaskAction`）
5. **状态机推进**（见 4.2）
6. **终态清理**
7. **续申请道岔**（窗口内新进岔口，`replenishForkRequests` + 原子申请）
8. **刷新进路状态**（`MmtrRouteRegistry.refresh`）

### 4.4 任务与联锁/道岔的耦合面只有两处（✅ 复核）

- 进路类型：`MmtrRoute.Kind` = mission 是 MANEUVER 或持有调车授权 ? `SHUNT` : `MAIN`
- 进路优先级：`task.earliestMs`（缺则 `dueMs`）→ 计划早的先走（`MmtrRouteRegistry.outranks` / `hasLivePlan`）
- **任务自己不申请任何东西**：申请由 `Vehicle.armMmtrPointRun` 做（持有者身份 `"v"+vehicleId`）

### 4.5 收回路径（4 条入口 → 1 个执行体）

| 入口 | 触发 |
| --- | --- |
| `adoptFrom` 的孤儿 | 重建后：编组没了 / 车没了 / 不是那一步 / 目标变了 |
| `mmtrReleasePlanMissions` | 整条线路消失（删线路、车底清空、输入坏掉） |
| `mmtrReleaseUnclaimedPlanTasks` | 扫世界：跑着"这套计划的任务"而新代没认领 |
| `mmtrWithdrawPlanTask` | 上面三者的公共执行体：**在动就记账、停稳再收** |

**两套编排的隔离机制（🤖 补遗二：靠 taskId 的字符串形状实现）**：

- plan 侧任务 id = `{lineId}/{consistId}/{seq}`（形如 `L1/C1/007`，**含 `/`**，`MmtrPlanTasks:126-129`）；
  job 侧任务 id **直接搬作业单步骤的 `stepId`**（操作者自由命名，实测 `s01..s10`，**不含 `/`**，`MmtrTaskFactory:35-48`）。
- `mmtrReleaseUnclaimedPlanTasks` 的判据就写死在这上面：`slash = taskId.indexOf('/'); if (slash <= 0) return;`
  （javadoc 原话："**作业单（job）的任务不满足这个形状，不会被碰**"）；
  `mmtrReleasePlanMissions` 同样用前缀 `lineId + "/" + consistId + "/"` 收窄（javadoc："**作业单（job）、玩家自己开的车都不动**"）。
- ⇒ 这是**有意为之的窄判据**（"收错车的代价比漏收大得多"），代价见 §6.3：**作业单被删时同样没有任何地方收回它的任务**。

| 🤖9 | 计划包里一批**只写不读/无调用**：`MmtrPlanAdjustments.trimAfter`、`MmtrEventRegistry.pruneEnded`（事件永不清理 ⇒ Delay/Fault 的 `endMillis=-1` 使其永远 ACTIVE）、`MmtrRailDistance.pathLength` / `railOfSiding`、`MmtrTravelTimes.stopAt`、`MmtrServicePlan.lastTripDoneMillis`、`MmtrDiagram.Working.totalWaitMillis` / `idleConsistIds` / `spareConsistIds`、`Entry.describeWithNote`（feed 也不输出 note）、`MmtrEvent.targetsLine` | 深度调研逐个核过调用点 |
| 🤖10 | **注释与代码不一致**：`MmtrPlanTasks` 写"earliestMs 留 0"实际 `= dueMs`；`MmtrRailDistance` 写"同一条轨不许走第二遍"实际只挡原路折返；`MmtrPlanInputs` 说事件规则/货运队列"预留了位置"（plan 包里不存在） | 同上 |
| 🤖11 | **两道故障可能分到同一个替补** | `applyDiagramEvents` 的 `used` 取自**原始** `diagram.workings`，两处各自 `firstSpare` 会拿到同一个 |

### 6.2 计划层的语义空洞（可能被误用）——🤖 深度调研（生成器专线）逐条核实

| # | 空洞 | 证据 |
| --- | --- | --- |
| 1 | **"车底够不够跑"在生产里从不拦** | `validate()` 不做容量（自认要 ring）；`validateCapacity` 只被测试调用；生产里容量只落到 `MmtrDiagram` 的 `capacityProblem` 一句话，而 `Simulator` 建派发器时**不检查它** ⇒ 不够也照排照派 |
| 2 | **"保表"（Delay + KEEP_TIMETABLE）实际什么都没搬** | `MmtrPlanAdjustments` 里那条分支只调 `handOff()`（只挑一个编组名，不改 receiver、不从 source 删趟次）+ `shifted(...,0)` 原样复制 ⇒ 只有一句日志 |
| 3 | **事件"到点生效"不触发重算** | 签名只含事件自身字段、**不含 `dayTime`**；重建只看签名 ⇒ 预登记的高峰到点不会自动生效（要人工"重新排班"或别的输入变化） |
| 4 | **事件没有线路过滤** | `Simulator` 把 `mmtrPlanEvents.all()` 传给**每条线路**；`applyPatternEvents` 不看目标；`MmtrEvent.targetsLine` **零调用点** ⇒ 一个车站目标的高峰会压到所有线路 |
| 5 | **区段故障与降速事件对计划无效** | 只实现了 `Fault.vehicleDown` 分支；`Fault(section)` 与 `SPEED_RESTRICTION` 全无消费者（只进签名 → 触发一次无效果的重算）。`MmtrEvent` 注释自称"计划期速度取 min(编组速度, 事件限速)"**未落地** |
| 6 | **任务没有自己的时间窗** | 计划路径把 `earliestMs` 与 `dueMs` 设成同一个值 ⇒ 窗口宽度恒为 0；派发只按"到点没有"判，跳过只按"迟到 10 分钟且整趟窗口已过"判 ✅ |
| 7 | **计划路径从不调 `task.validate()`** | 唯一调用点在作业单侧 ⇒ `targetKind` 自检对 P4 任务不起作用 ✅ |
| 8 | **走行时间是理想值** | 恒速（无加减速/无信号道岔等待/无限速链）+ 固定 3 分钟终点处理；速度只取 `fleet.consists.get(0).maxSpeedKmh`（**其余编组与替补的速度不参与**）⇒ 计划与现实的时间差全靠 10 分钟宽限 + 跳过兜 ✅🤖 |
| 9 | **套班的 N 是"全天唯一值"** | `peakHeadway` 取**所有段里最小的 headway**，`requiredConsists` 与 `i mod N` 都用它 ⇒ 任意一分钟的高峰把全天的间隔定死 |
| 10 | **网页趟次表与车实际跑的班不是同一份** | `/mmtr-plan-service-plan` 用**原始** density（未套事件）重算；派发器用的是事件调整后的 pattern ⇒ 事件期间两边不一致 |
| 11 | **手工指派空 `fromTripId` 会把源车的"出库"一起搬走** | 接手车于是有**两条出库条目**，而 `MmtrPlanTasks.expand` 对 `DEPART_YARD` **没做去重**（回库那条有）⇒ 同一辆车可能被派两次出库 |

### 6.3 状态可能悬挂 / 边界情形

| # | 情形 | 证据 |
| --- | --- | --- |
| 1 | **作业单被删/改，车上的 mission 不收回** | `deleteMmtrJob` → 重建 scheduler；无收回路径；`mmtrReleaseUnclaimedPlanTasks` 认 taskId 形状（要含 `/`），而作业单任务是 `step.stepId` |
| 2 | `claimReleasable` **先摘账再核对**：核对不通过时该笔被静默丢弃（该收没收） | `MmtrPendingPlanReleases` + `Simulator:836` |
| 3 | 收回依赖 **taskId 形状**（`indexOf('/')` 切 lineId） | `Simulator:777-781` |
| 4 | **玩家接管期间**：派发器 `continue`，既不推进也不收回；重建时 `adoptFrom` 只按 taskId 认 | `MmtrPlanDispatcher:407-409`；`Simulator:708-722` |
| 5 | **跑完的 state 永远不清 `awaitingTaskId`** | `tick` 开头 `isComplete()` 直接 `continue`（本轮已派完时刚设上 `awaitingTaskId`）⇒ 该车永久停在"等最后一步"，`frozenUntilByConsist` 也永久给它边界；"车交回段里没有"这件事**没有状态** |
| 6 | **出库闸门跨天不清零** | `lastYardDepartureMillis` 只升不降 + 比较用减法，而 `dayTime = floorMod(..., 24h)` ⇒ 连续运行跨天后 `dayTime` 回绕，闸门会判 false（负差值），新一天首发被卡到时刻重新超过"昨天最后一次出库 + 4 分钟" |
| 7 | **跨线路的车辆认领没有全局账** | `isVehicleTakenByAnotherWorking` 只看**本派发器**；世界侧 `idleVehiclesForYard` 给的是**整个车辆段的全部股道**（找不到指定股道时退化成全部）⇒ 两条线路共用一个段时可能各自绑同一辆车（后到的会在 `isVehicleIdle` 处解绑自愈，但产生 churn） |
| 8 | **一个坏配置停掉全部线路** | `mmtrPlanErrors` 非空 ⇒ `mmtrPlanDispatchers.clear()`，不区分是哪条线路坏了 |
| 9 | **输入文件解析失败只有 `log.warn`**（日志不进服务端控制台） | ⇒ `mmtr-plan.json` 写坏 = 静默回到"未配置" |
| 10 | `lastAttemptMillis` 只用于诊断（没有"派不出去就报警/降级"的机制） | 字段声明与唯一写点 |

### 6.4 计划输入的签名没覆盖的字段（⚠️ 我读出来的；🤖 深度调研确认并扩大）

`mmtrPlanSignature()` 里：线路只贡献 **id / 站数 / 出库股道 / 提前量 / loop**；车底只贡献 **数量**；
世界只贡献 **轨数**。**没进签名的**：

- 每站的 `dwellMillis`、`stationId/platformId`、`returnPlatformId`
- 线路的 `terminalTreatment`（换端/掉头/回库三态）
- 车底的 `maxSpeedKmh`（**它决定走行时间**）与 `vehicleCount`
- 线路几何（只要轨数不变）

后果：只改"停站时长 / 回程站台 / 终点处理方式 / 编组速度"时**签名不变 ⇒ 不重排**，
计划还按老参数跑（要等别的字段变化或手工"重新排班"）。这几类恰好都是控制台能编辑的字段。

### 8.1 生成器专线补齐的细节（已并入上文，这里只留索引）

- 输入校验的**逐条判据**（线路：≥2 站、站台 id 非 0、dwell 非负、相邻站不同、首尾相同必须标环线、环线站序要闭合、
  提前量非负；密度：段非空 / `to>from` / `headway>0` / 段之间**不许重叠也不许有空档**；车底：编组码唯一非空、
  每编组有车、`maxSpeedKmh` 非负、`vehicleCount` 够装 consists+spares）✅🤖
- 趟次 id：`L1-001` / `L1-B001`（每方向各自从 1 编号）🤖
- **容量**：`requiredConsists = max(1, ceil(ring / peakHeadway))`，`peakHeadway` = 全天最小 headway；比对结果
  只写进 `capacityProblem`，**不拦排班**（见 §6.2 #1）🤖
- **走行时间**：`MmtrRailDistance.between` = 以轨为边、`Position` 为节点的 **Dijkstra**（从 from 的两端起算、
  走到 to 的任一端），权重是轨长；逐段只算**相邻站**且两端都用**去程站台**；走不到 = -1 → 0 ms 🤖
- **事件逐类行为**：`PeakSurge` 把高峰窗内的密度段切开换更小 headway（只看未来）；`Fault(vehicleDown)` →
  `MmtrSubstitution` 找替补并交接（冻结期留给故障车、接续点要够 `leadTimeMillis`、来不及的趟取消并产出
  "已取消"事件）；`Delay` → 保表（**实为空操作**，见 §6.2 #2）或整体平移 🤖
- **冻结边界的确切用法**：`frozenUntil = 在途车当前交路条目的 endMillis`；重算里
  `future = startMillis >= max(dayTime, frozenUntil)`；`handOver` 的接续点同样取这个 max 🤖
- **派发器的世界接口**：`idleVehiclesForYard` 给的是**该车场所在车辆段的全部股道**上的空闲车；
  `isVehicleIdle` = 车存在 + `getIsManualAllowed()` + 任务为空或已终态（"在进路上 ≠ 忙"是修出来的）🤖
- **`mmtr-plan.json` 落盘时机**：只在 line/pattern/fleet 的 upsert/delete 时写（事件的 upsert/delete 也会写一次
  —— 那只是"重写同一份输入 + 清签名触发重算"）🤖
- **启动播种**：文件在就读；派发器**懒建**（第一次 tick）；日钟锚点 = 作业单调度器的锚点优先，否则"第一次用到的此刻"
  ⇒ **开机时 dayTime 从 00:00 开始**，锚点切换会让"现在"整体平移（注释记着这次现场）🤖

### 8.3 控制台（`PlanView.vue`，六页）

- **六页 = 线路 / 密度 / 车底 / 事件 / 交路 / 指派**，只覆盖 **plan 面**；进页 `Promise.all` 五个只读接口，写操作后统一 `refresh()`。
- **能改的**：线路（含站序、回程站台、停留、终点处理、环线、出库股道、提前量）、密度分段、车底、事件（四类）、接管按钮、手工指派、强制重排。

### 8.4 游戏端（🤖 结论很干脆；本节已并入游戏端专项调查的更正与补强）

- `game/fabric` 里 **plan / mission / task / job 四个词一次都没出现**（全目录 grep 零命中）⇒ **计划与任务是纯服务端概念**。
- **最硬的一条（生成侧缺席）**：`engine/buildSrc/src/main/resources/schema/**`（**生成线上包载荷 JSON 字段名的源头**）里搜
  `mission|task|job|plan|dispatch` → **零命中** ⇒ 这些概念**连包载荷的字段定义都不存在**，不只是"游戏端没有界面"。
- **第二强的一条**：`mmtrMission` 是 `Vehicle` 的**私有字段**（不在 `VehicleExtraData` 里），而客户端同步只走
  `VehicleExtraData` 的 `mmtr*`（只有门与路径）⇒ **mission/task 连车辆同步包都进不去**。
- 引擎 → 游戏端只有三条通道：**进路镜像**（`nextRails` / `pendingEntries` / `restrictedNodes` / 灯色 `lamps` / 守轨 `lampRails`；
  发送方是 `org.mtr.mod.mmtr.MmtrRouteMirror`，**变化才推**）、**驾驶室操作**、**连挂解挂**。
  另有 `org.mtr.mod.mmtr` 这个游戏端 MMTR 专用包（6 个文件：指令执行 / 进路镜像 / 信号链 / 玩家会话 / 区块跟踪 / 信号块），
  注册点在 `org/mtr/init/MTR.java` —— **全部与计划/任务/作业无关**。
- **指令通道是两段的（更正）**：`POST mmtr-command` 的 `train <verb>`（doors/changeends/cab/shunt/interlock/trace）会被引擎
  **翻译后 push 进队列**，由 Fabric 服务端每 tick 轮询执行（`MmtrTrainCommands` → `simulator.mmtrPushCommand` → 游戏端
  `simulator.mmtrPollCommand()`）；理由写在回复里："这条动的是世界里的实体，只有游戏端能做"。
  **但这条队列上与计划/任务/作业相关的字面量一个都没有**（游戏端支持的动词见 `MmtrCommandExecutor` 的帮助行）。
- HUD 只画驾驶台（限速、LZB、AWS、门、调车授权、驾驶室名）；世界内贴图仪表盘（`render/panel/MmtrCabDashboard`）
  **只画速度与限速两个活值**；按键只有驾驶相关；游戏内指令只有 `mtr restoreWorld`。
- **⚠️ 别误读**：游戏里**确实有一套"时刻表"界面** —— 但那是 **MTR 原版**的（`EditDepotScreen` 的 depot 频率/实时发车、
  `PlatformScreen` 停留、`SidingScreen`），与 MMTR 的 `mmtr-plan*` / `mmtr-jobs*` **没有任何代码关系**。
- ⇒ **"只有网页有、游戏里没有"**：线路/密度/车底/事件编辑、趟次表、交路与"计划 vs 实际"、接管、指派、重排 —— 全在网页；
  游戏端只有**驾驶**与**进路/信号显示**。

### 8.5 作业系统（`mmtr/job/`，与 plan 并行的第二套编排）

- **是什么**：`MmtrConsistJob` = **车底作业单**（一车一天、按时间顺序的步骤，到点在股道生成编组、逐步推进、超时判 FAILED）；步骤五类 `MOVE_TO / SERVE / COUPLE / UNCOUPLE / CHANGE_ENDS`。
- **两种驱动语义**：MANUAL 股道 = 每步挂一条无头 mission 跑到该步结束；AUTO 股道 = 到点排一条**真发车**（`addDeparture` + `startUp`）。
- **谁创建**：只有接口 / 手改 `mmtr-jobs.json` / 脚本（`scripts/demo-timetable-upsert.ps1`）/ 模板展开；**引擎内部没有任何地方自己造作业单**。
- **谁推进**：`Simulator.tick` 里紧跟派发器之后 `mmtrJobScheduler.tick(...)`，且仅当 `mmtrAiJobStepsEnabled`（一旦有作业单就**永久置真**，没有置回的地方）。
- **与 plan 的关系**：**两套并行、互不调用、没有互斥**；**唯一硬接线是共用时间锚点**，而且这是**刻意设计**（`notes/140`
  原文：P4「**优先共用作业单调度器的锚点**（`MmtrJobScheduler.getAnchor()`，本轮新加的只读出口）：**两套编排的小时数必须是
  同一个意思**，否则运营台上"作业单 08:00"与"线路 08:00"会差出一段，谁也说不清哪个对」）；出口都汇到
  `Vehicle.setMmtrMission`（独占）。
- **死面**：`Simulator.mmtrJobsMode` **只写从不读**（注释还写着"禁掉老 depot 时刻表"，实际无消费者）——
  更精确地说：**它本该承担的那件事，现在实际是靠 `Siding.mmtrManualSpawn` + `mmtrSessionSpawned` 那套"手动刷车"标记做的**，
  `mmtrJobsMode` 本身全仓零读取点；`MmtrTimetableSource` 生产零调用；`mmtr-schedule` 无消费者。
- **测试很浅**：只有序列化/注册表/一条"整趟连挂到 DONE"；**没有 `MmtrJobSchedulerTests`**。
