# 172 · 信号灯登记表的自动刷新（+ 手动刷新按钮、道岔诊断日志节流）

> 现场：`world/mtr`（2026-09-16 夜）。用户口径（本轮的原话）：
> ①「灯确实敲掉了、但登记表没跟上啊」；②「你直接删了有什么用，肯定是需要进行手动刷新的构建啊」；③「还有自动刷新」。
> 交付：登记表 ↔ 世界 的核对**同一份实现**跑在三条路径上（区块加载 / 敲灯事件 / 每秒轮转），外加指令栏的
> 「刷新信号灯登记表」按钮。顺带修掉一处**把 tick 刷死**的诊断日志（这是本轮现场"指令通道超时"的真凶）。

## 1 问题到底是什么

登记表（`mmtr-signals.json`）是引擎侧的数据，而"世界里到底还有没有这盏灯"**只有游戏端答得出来** ——
只有游戏端能枚举区块里的方块实体。所以核对只有游戏端能做，而它原来**只有一个入口**：
操作员在中控敲一句 `world scan-signals`。

于是：

- 灯被敲掉之后，登记表里那一条会一直留着 ⇒ 地图上永远画着一盏**已经不存在的灯**；
- 而没有任何东西会告诉用户"你需要去敲那句指令"。**"世界改了登记表就跟着改"不能靠人记得**。

先澄清一个我自己造成的误会：扫描代码本身**早就是对的** —— 它只删"所在区块已加载、但区块里没有它"的条目
（`scannedChunks.contains(...)`），未加载区块的条目一律留着。我一度把扫完之后的灯数读错、以为它清了远处，
那是我读数的问题，不是代码的问题。手动扫描要保留（全量、可解释、可审计），这一轮补的是**自动**那三条路径。

## 2 自动刷新：三条路径，各管一段

新增 `game/fabric/.../mmtr/MmtrSignalSync.java`，`MTR.onInitialize` 里注册。

| 路径 | 钩子 | 管什么 |
| --- | --- | --- |
| 区块加载 | `ServerChunkEvents.CHUNK_LOAD` | 新区块进内存就核对一次（**只入队**，量在 tick 里按预算放） |
| 灯被敲掉 | `PlayerBlockBreakEvents.AFTER` | 敲掉的那一格（及上下相邻格）有条目就**立刻删**，不用等轮转扫到 |
| 常态轮转 | 每秒挑几个已加载区块 | **兜底**：爆炸/活塞/别的模组动的世界、以及"放灯"（放灯没有事件钩子） |

预算：排队的区块每 tick 最多 2 个（队列超过 64 说明在批量加载，放宽到 12 个）；轮转按"**一分钟走完一圈**"
摊（`SWEEP_TARGET_SECONDS = 60`，每轮 4～128 个区块）。单块开销 = 遍历该块的方块实体（个位数）+ 扫一遍登记表
（百来条），与世界规模无关。

### 2.1 删除的安全边界没有放宽
只能删**所在区块已加载、但区块里找不到它**的条目。玩家走远区块卸载之后，"找不到"只说明没加载 ——
所以同步**永远按区块做**，绝不"全表对全世界"。敲灯那条路查 `y-1 .. y+2` 四格（一盏灯两格高、登记可能在
上面那格也可能在下面那格；把灯脚下垫的块敲了灯会掉），判断错了有轮转扫描兜回来 —— 这一层兜底正是敢在那里放宽的原因。

### 2.2 手动扫描与自动刷新共用一份实现
`MmtrCommandExecutor.scanSignals` 现在只剩一个循环，逐区块的核对整体搬进 `MmtrSignalSync.syncChunk`。
两条路各写一份的后果是"手动扫一遍修好了、自动跑一轮又改回去"，而且用户没法用手动扫描的结果去解释自动刷新做了什么。

## 3 顺手修掉的坑：`set` 会抹掉人工绑定

`Simulator.mmtrSignalOp(..., "set", "")` 走的是 `MmtrSignalRegistry.put`，那里面是 `new SignalEntry(...)` **整体替换**
—— `mode` / `target` / `rails` 三个字段会被一起冲掉。手动扫描偶尔跑一次还看不出问题（BOUND 条目被 `continue` 跳过），
但**自动刷新是每秒都在跑的**：一盏 AUTO 灯只要被扫到一次，人工点选绑定就被抹一次，抹掉之后再也回不来。

所以另开了一条 `Simulator.mmtrSignalRefresh(x,y,z,angle,aspects)`：**只改世界告诉我们的那两个值**（朝向、灯位数），
`mode`/`target`/`rails` 一律不动；返回"是否新增"，新增才落盘（否则 `mmtr-signals.json` 会变成每秒一写的热文件；
朝向本来每次启动都会重新读一遍世界，不落盘不丢信息）。

## 4 手动刷新：指令 + 按钮

- 指令（本来就有，现在归到同一份实现）：`world scan-signals`（游戏端执行）。回一行
  `[signals] 扫描完成: 找到 N 个信号灯, 新增 A 个 AUTO 条目, 保留人工绑定 B 个（只刷新朝向，不动绑定）, 清理已拆掉的 C 个`
- 网页指令栏新增直接执行按钮「**刷新信号灯登记表**」（`CommandConsole.vue` → `scanSignals()`）与常用指令
  `world scan-signals`。为什么按钮必须存在：自动刷新是**按区块**收敛的（看不到的区块不敢删），
  所以"我确定这一片现在没有灯了"需要一个一次把全部已加载区块核一遍的入口。

## 5 现场事故：诊断日志把 tick 刷死（本轮真凶）

排查上面那件事时，`mmtr-command` 请求**超时 8 秒不应答**（`server stop` 也发不进去）—— 看起来像"引擎卡死"。
数了一下服务端日志的前缀频次：

```
3351  [MMTR-PT] req v-4738…@-170,-60,-161 via … leg 0 -> QUEUED
  78  按计划补申请：车 … 被 … 挡住，申请第 0 条腿 → QUEUED
```

`Simulator.mmtrPointRequest` 里那句诊断是**无条件**打的，而一处卡死的道岔会让车辆**每 tick** 重发同一个申请
（"按计划补申请"那条自救路就是这么写的）⇒ 每秒 20 行、每行 200+ 字符，而控制台 I/O 与 tick 同线程。
诊断本身要留着（卡死时正是靠这几行定位的），但**同一个结论不需要每秒说 20 遍**。

改法：`MmtrPointAuthority.shouldLogDiagnostic(key, outcome)` —— 第一次一定打、结果变了马上打
（QUEUED → GRANTED 这种跃迁不能等）、其余每 10 s 最多一条，且**按"车@节点"分别算**（一辆车刷屏不吞别的车的话）。
`req` 与 `rel` 两处都接上了。

## 6 验证

- 引擎全量测试 **726 通过 / 0 失败 / 5 跳过**（含 `MmtrSignalAspectTests` / `MmtrSectionServiceTests` 等信号面全套）；
  网页端 `npm test` 5 通过、`npm run build`（vue-tsc + vite）通过。
- 现场（部署后待核）：① 敲掉一盏灯 → 日志出现 `[MMTR-SIG] 自动刷新：灯被敲掉，删除登记 x,y,z`（立刻）；
  ② 把一条**世界里不存在的**登记用 `signal set` 造出来，区块已加载 ⇒ 一分钟内日志出现
  `[MMTR-SIG] 自动刷新：轮转核对 清理 1 盏`（这条是自动删除路径的端到端证明，和敲灯走的是同一段代码）；
  ③ `world scan-signals` 的手动报告与上面两条不冲突。
