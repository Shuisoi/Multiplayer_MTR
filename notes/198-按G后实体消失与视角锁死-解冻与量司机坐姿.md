## 1. "视角被锁死"是我的 bug：上车锁跟了本地请求，而不是引擎判定

`VehicleRidingMovement.movePlayer` 里那一行是驾驶室锁：

```java
final float speedMultiplier = mmtrIsInCab() ? 0 : ...;
```

而 `mmtrIsInCab()` 在 **`mmtrEnterCab` 里就被置真**了 —— 也就是**按下的那一瞬间，不等引擎回答**。
于是只要引擎**拒绝**（不停稳 / 驾驶室被占 / 不是编组体车），玩家已经"在驾驶室里"了：
**走不动、只能原地站着**，视觉上就是"视角被扭到一个固定位置"。
等骑乘计时器超时 `leaveRide` 才解开 —— 而那时玩家已经被锁了一段时间。

**修法（也是用户"不要设权限限制"的直接落实）**：把**上车**和**持钥匙**拆开。

| 概念 | 由谁决定 | 效果 |
| --- | --- | --- |
| 上了车（骑乘 + 站在驾驶室座位点） | **本地**，按下即成立 | 永远能上车，不看任何权限 |
| 司机锁（不能走动） | **引擎镜像**（`getMmtrActiveCabFromSync()` 非空 且 钥匙持有人含 `crew`） | 引擎没认，就只是乘客，可以自由走动 |
| 发给服务端的 `isDriver` | **同上**，随确认变化才推 | 不会出现"没有钥匙却告诉服务端我是司机" |

新增 `mmtrIsDriverLocked()` / `mmtrSetCabConfirmed()` / `mmtrIsCabConfirmed()`；
`MmtrCabInteraction.refreshConfirmation()` 每 tick 把镜像结果推给骑乘层。

## 2. 此前"失败"没有任何痕迹 —— 现在有

上车反馈只走**聊天栏**（`player.sendMessage`），**不写日志**。所以"按了没反应"在日志里查不到，
"被拒绝"和"引擎压根没收到"完全无法区分。现在：

- `[MMTR-CAB] 请求上车：车=… 车节=… 驾驶室=…（1A）模型=… 座位点=(…) 车体朝向=… 玩家朝向=… 掉宝=…`
- `[MMTR-CAB] 上车结果：… | 驾驶室=…·钥匙=…·速度=…km/h | 仍在车上=… 驾驶室已确认=…`
- `[MMTR-RIDE] 结束骑乘（<原因>）车=… 车节=… 驾驶室=… 已确认=…`

`leaveRide()` 现在**必须带原因**，三处调用点分别写明：
`计时器：movePlayer 没再推动玩家`、`四个角都没有地板（点 z=… x=…）`、`贯通道数据没了`。
（只在**真的有事可结束**时才打，否则 `tick()` 每帧都会打一行 —— 这条我特意处理了。）

→ 下一次按 G，日志能直接回答"请求到了没 / 引擎认了没 / 骑乘是被谁结束的"。

## 3. 量具一：座位点在不在**地板盒**上？（会决定"第 1 帧就被踢下车"）

`movePlayer` 每帧用 `clampPosition` 找地板盒；找不到就 `leaveRide`。所以座位点必须在地板上。
`sandbox/cab_floor_check.js` 直接从打包好的 OBJ 取 `floor` 组包围盒，跟座位锚点比：

```
floor 组：riding space x[-2.100,2.100] y[2.300,2.320] z[-15.886,15.886]
seat_1 riding=(-0.982, 12.529)  中心在地板上=true  四角在地板上=4/4  OK
seat_2 riding=( 0.982,-12.529)  中心在地板上=true  四角在地板上=4/4  OK
PASS
```

顺带确认：`cabView` 给的入场 Y = 门坎 + 0.05 = **2.3203**，正好等于地板盒顶面 2.320 ✓。
**所以"上不去"不是地板钳制引起的。**

## 4. 量具二：司机**实际**看得见仪表吗？（量出一个真问题）

MC 的相机在**脚底 + 1.62 m**，而 MTR 的地板钳制每帧把脚底按到地板上 ——
所以**相机高度是被地板钉死的**，模型里 `mmtr_seat` 写的**眼高用不上**
（`cabView` 有意丢掉它的 Y，注释里写了原因：写成眼高会让乘务员掉出车外）。
`sandbox/cab_view_check.js` 用**相机点**（不是座位点）向司机朝向打一条射线，量最近命中：

```
seat_1: 脚底 y=2.320  相机 y=3.940  模型眼位 y=4.750  → 相机比模型眼位低 0.810 m
        视线第一个命中：body @ 2.861 m（车头端墙，视线没被挡住）
seat_2: 同上
```

**结论：视线没被挡住（不是"什么都看不见"），但相机比模型设计的眼位低 0.81 m。**
而 101 的台面在 y≈**4.09**、仪表面中心在 y≈**4.36** —— 相机在 3.94，
**正好在台面下方**：坐着看是"台面挡在眼前、仪表在上方"，得抬头才看得全。

根因不是代码：**101 的驾驶台是按真车高度建的（地板 2.26 → 台面 4.09，高 1.83 m）**，
而 MC 的眼高固定 1.62 m —— 真车眼高约 2.5 m 才配这个台面。
MTR 官方车之所以没这个问题，是因为它们的台面按 MC 眼高（地板+1.62）做的。

**可选修法（等用户定）**：
- (a) 把台面/仪表整体**下移约 0.5~0.8 m**（改模型 `interior`，脚本可做）；
- (b) 把 `mmtr_seat` 的眼位改成"地板 + 1.62"让锚点不再说谎（视觉不变，只是不再误导）；
- (c) 先不动，进车看实际观感再决定。

## 6. 真因（19:59 用户实测的日志 + 堆栈）：**雨刷层的一行诊断把整条渲染循环打断了**

用户按 G 后日志给出三段决定性证据：

```
[MMTR-CAB] 请求上车：车=-8960752472062424013 车节=0 驾驶室=2（1B）模型=br101 座位点=(0.98, 2.32, -12.53) …
[MMTR-CAB] 上车结果：进入驾驶室 1B | 驾驶室=CAB_B·钥匙=CREW·速度=0km/h | 仍在车上=false 驾驶室已确认=false
[MMTR-RIDE] 结束骑乘（计时器：movePlayer 没再推动玩家）车=… 车节=0 驾驶室=2 已确认=false
```

**引擎是答应的**（`CAB_B` + `CREW` + 0 km/h）—— 所以"权限"从头到尾都不是问题。
但 **`仍在车上=false`**，而且 `[MMTR-RIDE]` 说明骑乘**建立过又被计时器拆掉**，
PERF 里 **`车内定位=0`** —— **`movePlayer` 一次都没跑到**。

同一秒的渲染线程堆栈（72 行 NPE，全部同一个位置）：

```
java.lang.NullPointerException: Cannot invoke "Vector3d.getZMapped()" because the return value of
  "ObjectObjectImmutablePair.left()" is null
    at MmtrWindshield.logGate(MmtrWindshield.java:524)
    at MmtrWindshield.render(MmtrWindshield.java:304)
    at RenderVehicles.lambda$render$15(RenderVehicles.java:272)      <-- 雨刷渲染
    at RenderVehicles.iterateWithIndex(RenderVehicles.java:645)      <-- 这个循环被异常打断
    at RenderVehicles.render(RenderVehicles.java:66)
```

**闭环解释一切**：

1. 上车后 `ridingVehicleId != 0`，但 `ridingPositionCacheOld`（相机用的车体局部偏移）
   **要等 `movePlayer` 至少跑过一轮才非空** —— 这是**必然存在**的窗口；
2. `logGate`（**一行诊断日志**）在 524 行**无条件解引用**它 → NPE；
3. NPE 从 `MmtrWindshield.render` 抛穿 `iterateWithIndex` 的 lambda →
   **`RenderVehicles:387` 那个 `movePlayer` 调用在 272 行之后，永远轮不到**；
4. 于是偏移永远算不出来 → 下一帧再 NPE → **死循环**；
5. 同时 `tick()` 的骑乘计时器超时 → `leaveRide` → **玩家永远上不去**；
6. 而 NPE 是从 `WorldRenderer.renderEntity` 抛出去的 → **整批实体渲染被打断** →
   **"所有实体瞬间消失又突然出现"**；玩家还被旧的本地锁钉住 → **"视角被扭到一个固定位置"**。

三处症状，一个根因。而且它**不是只在驾驶室门口才会发生**：任何让 `ridingVehicleId != 0`
而偏移还没算出来的时刻都会命中 —— 也就是说 **这行诊断很可能把所有火车上车都弄坏了**，
只是此前没人再上过车（PERF 里 `骑乘` 长期为 0）。

### 修法

1. `MmtrWindshield.logGate`：把偏移取出来**判空**（诊断绝不允许抛异常打断渲染）；
2. `MmtrWindshield.driverOnBoard`（**同一处解引用，只是在 304 之后**）：同样判空 →
   未知偏移时答"司机不在车上"（对雨刷而言既正确又无害）——
   这一处如果不修，修完 ① 下一个 NPE 就是它；
3. 顺带确认了全部 36 条堆栈**只有 `logGate` 一个位置**，没有第三处。

> 教训：**诊断代码写在渲染热路径上时，它必须比被诊断的代码更不可能失败。**
> 一行 `[MMTR-DBG]` 让"能不能上车"这件事整个失效，而且症状（闪烁 + 卡住 + 上不去）
> 与它毫无表面关联。

## 8. 第二轮实测：NPE 没了，暴露出下一层——地板钳制把人踢下车

修完 §6 之后重测（21:52-21:53）：

```
[MMTR-CAB] 上车结果：进入驾驶室 1B | 驾驶室=CAB_B·钥匙=CREW·速度=0km/h | 仍在车上=false
[MMTR-RIDE] 结束骑乘（四个角都没有地板（点 z=-12.53 x=0.98 不在任何地板盒上））车=… 车节=0 驾驶室=2
NPE = 0
```

✅ **NPE 归零**，而且 `movePlayer` **这次真的跑了**（能走到 `clampPosition` 的失败分支，
说明"渲染循环被打断"这一层已经通了）。

❌ 但骑乘仍然被 `clampPosition` 判成"四个角都没地板"而结束 —— 注意这次是**点位明确**的失败：
`(x=0.98, z=-12.53)` = `seat_2`（驾驶室 2）的骑乘空间坐标。

理论上它应该在地板上：打包 OBJ 的 `floor` 组在骑乘空间是 `x[-2.100,2.100] z[-15.886,15.886]`
（`cab_floor_check.js` 量过，四角都在）。所以问题只可能在 **Y**：
`clampPosition` 的主判据要求**盒子在 Y 上包住骑手**，而模型的地板是一层**只有 2 cm 厚**的板
（`y[2.300,2.320]`），入场 Y = 门坎 + 0.05 = **2.32026** —— 比地板顶面高 **0.00026 m**。

`bestPosition` 本来有兜底（`|盒顶 − 骑手Y| ≤ 1` 时按 X/Z 距离取最近盒），所以要么兜底也没命中，
要么**盒子的 Y 空间与我以为的不是同一个**（`MmtrVehicleAnchors` 的注释说地板盒在 `(x,y,-z)`；
如果实际是渲染空间 `(x,-y,-z)`，Y 会差 4.6 m —— 那就会两个判据全灭）。

**不再猜了**：`describeBoxes()` 已加进失败消息，会直接打印
**这次拿到几个盒 / 其中几个是地板 / 所有盒的 Y 范围**。下一次按 G 就能一次定案
（"一个盒都没有" = 车型/车节问题；"Y 范围是负的" = 空间不一致；"Y 范围含 2.32" = 浮点边界）。
