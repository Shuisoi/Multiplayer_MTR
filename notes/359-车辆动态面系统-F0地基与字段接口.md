# 359 · 车辆动态面系统 · F0 地基：数据接口 / 逻辑层 / 面文档 / 绘制运行时

> 日期：2026-10-02 · 口径来源：用户「我们不能想的太简单了，动态的东西会很多，我们需要构建一个子系统用来专门处理这些动态面的显示，以及绘制器，否则其他构建者或者车体作者难以制作车辆资源包」+「先拿个方案出来」+「选你推荐的 A 开始吧」
> 方案 A 的边界：**资源包 = 声明式数据（不可执行代码）；代码级扩展 = Java SPI（附属模组）**。

## 0. 为什么要有这一层（一句话）

水牌那一轮（notes/356/357/358）把"一块牌子写什么字"做完了，但**每来一个新需求就要改一次客户端**：
版式写死在 Java 里、条件只能写"有值就画"、动画完全没有。车体作者要的不是"再多一个字段"，
而是**一套能自己拼的东西**：数据接口 + 逻辑 + 绘制 + 一个能看见效果的工具。

## 2. L0 · 数据接口：字段表是**给外人看的接口**，所以它有漂移守卫

`MmtrFaceFields` 里一行一个字段（52 行），**四处**必须始终对得上，对不上就红：

| # | 核对 | 谁核对 | 漏了会怎样 |
| --- | --- | --- | --- |
| 1 | 登记表 ↔ 取值口 `MmtrVehicleFaceSource` 的 `case` | `MmtrFaceFieldsTests#valueSourceCoversExactlyTheRawFields` | 作者写了字段却永远空着 / 取值口里有没人能用的死字段 |
| 2 | 登记表的 `sync` ↔ 引擎白名单 `VehicleSyncPatch.DYNAMIC_KEYS` | `#syncFlagMatchesTheEngineWhitelist` | "读数不实时"（notes/257 那个经典病） |
| 3 | 登记表 ↔ 导出的 `tools/face-studio/fields.json` | `#exportedFieldsFileMatchesTheRegistry` | 工作室的自动补全与游戏不一致 |
| 4 | 名字唯一 + 每行都有说明 | `#fieldNamesAreUniqueAndDocumented` | 作者只能靠猜 |

**加一个新量 = 四步曲**（写进 `MmtrFaceFields` 类注释，也就是作者看得到的地方）：
① 引擎侧算出来 + 进镜像（`schema/data/vehicle.json`、标脏、必要时进 `DYNAMIC_KEYS`）
→ ② `MmtrVehicleFaceSource` 加 `case` → ③ 登记表加一行 → ④ 重生成 `fields.json`（用例会写出 `.actual`，拷过去即可）。

两条口径（都有用例）：
- **取不到 = 不放进去**：`var` 得 null、`missing` 认它缺、模板渲染成空串 —— 三种用法对"没有这个量"的理解一致；
- **空串也算没有**：引擎里"未知"常常就是 `""`（回库趟的终点），当"有值"会让 `when` 写不下去。

## 3. L2 · 逻辑层：用**现成的 JSONLogic 规范**，但只实现子集

- 支持：`var / if / and / or / ! / !! / == != === !== / < <= > >= / + - * / % / min max / cat / substr / in / missing / missing_some / ?: / some / all / none / filter / map` + `fn:*` 自定义（SPI 口已留）。
- 明确口径（都在共享向量里钉着）：真值 = `null`/false/0/空串/空数组为假（**`"0"`、`"false"` 是真**，与 JS 一致、与直觉相反）；比较时两边可数字化就按数字比，**有一边 null ⇒ `<` 一律假**（不把缺数据当 0）；类型不匹配的算术 ⇒ null（不抛、不静默当 0）。
- **预算**：一次求值 ≤512 节点、≤24 层，超了抛 —— 资源包不可信，一个刻意写深的表达式不能把客户端拖死。
- **共享测试向量** `tools/face-studio/conformance/logic.json`（68 条）：Java 端两种数据形态（Gson 树 / 普通 Map）各跑一遍，**F2 的 JS 端要跑同一份文件** —— "在浏览器里试出来的条件，进游戏还是那个结果"这句话从此是可证伪的。

## 4. L1 · 面文档：旧段是"糖"，新段是"面"

```json
"faces": {
  "pid_1": {
    "background": "#FF101418", "textColor": "#FFF2F4F6", "pxPerMetre": 512, "side": "normal",
    "require": {"!=": [{"var": "pid.service"}, ""]},
    "vars": {"arriving": {"and": [{">": [{"var": "lzb.targetM"}, 0]}, {"<": [{"var": "lzb.targetM"}, 200]}]}},
    "elements": [
      {"type": "text", "text": "{pid.service}", "x": 0.03, "y": 0.5, "size": 0.46, "align": "left"},
      {"type": "text", "text": "开往 {pid.terminus}", "x": 0.97, "y": 0.5, "size": 0.62, "align": "right",
       "when": {"!=": [{"var": "pid.terminus"}, ""]}}
    ]
  }
}
```

- **面名 = 锚点名**（本片最关键的一条约定）：模型里那个锚点叫什么，文档就写在 `faces.<锚点名>` 下 ⇒ 再加一块牌**不用改客户端**，只要打包器给一个锚点 + JSON 里写一段文档。
- 旧 `pid`/`next` 段由 `MmtrFaceDocument.builtinPid` **翻译成**面文档：一行 → 一个 `text` 元素，位置/字号/对齐/前后缀逐字照搬，`prefix` 的"只在有值时写出来"翻成等价的 `when`；新面缺省底色是**透明**（牌底交给模型），旧段缺省仍是那层不透明深色。
- 顺带的欠账：锚点 JSON 现在被读了**四次**（anchors / hud / pid / faces），各读各的缓存。本片先不动它（避免碰正在跑的水牌路径），记在这里。

## 5. L3 · 绘制运行时

- 元素注册表 `MmtrFaceElements`（7 种，F0），**一个元素画坏了只跳过它**并记一次日志 —— 资源包是不可信内容，一块牌里写坏一行不该让整列车的水牌全黑。
- `MmtrFaceRuntime`：**每帧每台车一份数据快照**（`MainRenderer` 每帧调 `tick()` 清）⇒ 同一帧里这台车的十几块面读到同一份数据，不会一块写海山一块写鸥湾；贴图只在"文档身份 + 数据 + 牌面尺寸 + 像素密度"签名变化时重画。
- `MmtrPanelQuad.drawSide(...)`：画在哪一侧由文档说（默认 `normal` = 朝读它的人 —— 水牌就是这条；`driver` = 仪表面板口径）。notes/357 那个"背面剔除让整块牌看不见"的坑，从此是**数据可配**的，不是靠猜法线。
- **切换是纯数据动作**：`MmtrPidBoard` 会跳过"有面文档的锚点"（`MmtrFaceRegistry.hasDocument`），所以 F1 把水牌换成面文档只改资源包。

## 7. 踩坑（都是当场修掉的）

1. **`JsonArray` 忘 import**：主源码编译失败（"找不到符号 JsonArray"×4）。Gson 的重定位前缀 `org.mtr.libraries.` 容易漏。
2. **`missing_some` 的参数形态**：JSONLogic 第二个参数是**一个数组**，而 `args()` 会把数组求值成 `List`；第一版把它当成"键表的一层包装"，于是 `["pid.terminus"]` 被当成一个键名 → 结果恒为"缺"。修法：`values.get(1)` 本身就是键表。
3. **`filter`/`map` 的元素求值**：`map` 必须返回**谓词的结果**而不是原元素；且谓词只应对元素求值，不能先对外层数据算一遍（白吃节点预算、还可能提前抛错）。
4. **测试的相对路径**：用例的工作目录是 `mmtr/game/fabric`（`run-fabric-tests-offline.ps1` 的 `Push-Location`）。`MmtrFaceFields.EXPORT_PATH` 是**工作区相对**的，所以要在测试里 `Path.of("..","..","..").resolve(...)`；写成 `Path.of("..","..", EXPORT_PATH)` 会变成 `mmtr/mmtr/...`（第一版就是这么错的，报"连 .actual 都写不出来"）。
5. **`run-fabric-tests-offline.ps1 -Tests a,b,c` 不生效**：`-File` 传参不做数组绑定，逗号整个变成一个类名 ⇒ `ClassNotFoundException: org...Tests,org...Tests`。要么不带 `-Tests` 跑全套，要么用 `-Command` 传 `@(...)`。
6. **日志没有 provider**：离线 runner 里 `Log4j API could not find a logging provider` —— 只是警告被丢掉，`Init.LOGGER` 本身可用（所以"只提示一次"的日志路径不会在用例里炸）。
7. **★ 门不能用 `{"!=": [{"var":"x"}, ""]}` 写**：快照里"取不到"是**不放进去**，于是 `var` 得 `null`，而 `null != ""` 是**真** —— 结果是"不在作业单上的车也挂牌"。改用 `{"!!": [{"var":"x"}]}`（null 与空串都是假）。**这条只有真值表用例才抓得住**（画面上是"该空的车挂了块牌"，不看实物根本发现不了）。
8. **"没有 when" ≠ "条件不成立"**：`resolveText` 第一版写成 `truthy(eval(when, data))`，`when == null` 时求值得 null ⇒ 假 ⇒ **所有没写 when 的元素都不画**（用例里表现为"第一段文字凭空消失"）。

## 9. 用户自己验收时的三步（本片交出去时的状态）

1. **看牌**：找一列**在作业单上**的 SAF420（派一趟 00109 之类），看车顶前方那块目的地牌。
   判据两条：① 牌面**上沿有一条琥珀色细线**（老渲染器画不出它 ⇒ 这条线在，就是面文档在画）；
   ② 文字与改之前**一模一样**（班次号靠左、`开往 终点` 靠右）；回库趟只写班次号，**不许**挂一个孤零零的"开往"。
2. **看铁证**：`mmtr/game/fabric/run/mmtr-panel-debug/` 下新出现的 `<车辆id>_0_pid_1.png` ——
   那是**游戏里真正上传的那张贴图**（`MmtrPanelTexture` 的首次绘制 dump）。有琥珀线就是新路径。
3. **想退回去**：删掉 `consist/saf420.json` 里那两个 `faces` 段重新打包，或把 `run/options.txt` 换回
   `SAF420_v35.zip`（备份 `options.txt.bak-359`）—— 两条路都不需要动代码。

> 交出去时的现场状态：服务端在跑（RCON 活着），客户端**已用新类 + v36 起过**（玩家在原线上，
> 曾 `tp` 到 1253.63 / 69.56 / 1806.5 试图抓过路车）；`build/classes/java/main` 里铺的是离线编出来的
> 726 个类（离线脚本与 gradle 同一份 javac 与 classpath）。
>
> ⚠ **手工起 dev 客户端的坑（本片踩了一次）**：`Start-Process java @<loom runClient argfile>` 的
> **工作目录必须是 `mmtr\game\fabric\run`**（= 服务端与 gradle runClient 用的那个游戏目录），
> 不是 `mmtr\game\fabric`。给错了的现场表现是「**设置全没了、一个资源包都没有**」——
> MC 把 cwd 当游戏目录，于是**在模块根目录新建了一整套** `config/ logs/ options.txt/ saves/ …`，
> 而真正的 `run/options.txt`（4 个包 + v36）根本没被读。修法：删掉那套新建的目录/文件、用
> `-WorkingDirectory <工作区>\mmtr\game\fabric\run` 重启；判据是"模块根不再冒出 `options.txt`"
> 且 `run\logs\latest.log` 在写。
