## 1 先排除、后来又证伪的一条岔路（两次都要记）

第一轮我把嫌疑放在 `wipeFactorBand()` 的四边形顶点数组上：

```java
final double[] ax = {from[0][0], from[0][1], to[0][0], to[0][1]};   // A0.x, A0.y, A1.x, A1.y
final double[] ay = {from[1][0], from[1][1], to[1][0], to[1][1]};   // B0.x, B0.y, B1.x, B1.y
```

正确应当是 A0 → B0 → B1 → A1（沿刀 → 跨到新位置 → 沿刀回来）。上面这四行把**不同顶点的 x 和 y
混在一起**，构成的根本不是四边形，而是一条**斜穿玻璃的细条**。

**但我在一个中刀时刻取样，测出 `client 3 beads, 0 false positives`，于是把它排除了。**
这个排除是错的：细条在任一时刻都只含极少的珠子，所以逐帧看它人畜无害；**它是随刀的每个角度重建的**，
扫过整程后的**并集**才是一片宽走廊。§2 的整程覆盖探针一量就出来了。

**教训（写进本仓的横向规律）**：一个"随时在变、每帧重建"的判据，**不能用一个瞬间的样本来洗清**；
要量它在整程上的**并集/覆盖率**。

## 2 真因：整程 15% 的玻璃被虚拟成"在刀下"

新增探针 `bandCoverageProbe()`：80×80 网格（每格 1.9 cm²，共 6400 格）覆盖整块玻璃，
沿一次完整外行程取 400 个刀位，逐格分别问
① 客户端 `wipeFactorBand()` 用的那对数组，② 独立参照（射线法点在显式四角多边形内）。

**修复前**：

```
client claims            0.614 m²
reference claims         0.748 m²
client-only              0.181 m² = 玻璃（1.2207 m²）的 15%，948 / 6400 格
最远的虚报点距刀          1103 mm（几乎等于整个玻璃宽度）
```

**修复后（四角改成循环序 A0→B0→B1→A1）**：

```
client 0.748 m²，reference 0.737 m²
disagree on 1.4% of the union（client-only 0.010 m²，最远 9 mm = 边缘膨胀带）
```

落在那条假走廊里的珠子会被 `wipe > 0` → 进入 `applyWipe` 的分支 → `aheadAfterM >= -mergeDistanceM`
→ **被捡进水浪、跟着刀一路走到行程末端**。这就是「带整片玻璃的雨滴往右移动」：
不是整片，但是一条斜穿玻璃的宽带，而且**与刀的实际位置无关**（最远 1.1 m）。

修法是两处：客户端 `wipeFactorBand()` 与夹具的同名函数，四角都改成正序。
夹具里加了 `bandXs()/bandYs()` 单一来源 + 射线法独立参照，防止顶点顺序再次被写错。

## 3 收集区：已实现，但实测是次要的

按用户要求加了 `collectZoneM`（默认 0.15 m，打包器白名单同步加上，否则静默丢弃）：

- **每个行程末端一个收集区** = 刀刃前缘线**之外**（沿刚才的行进方向）深 `collectZoneM` 的一条带，
  也就是刀行程末端贴着玻璃边的那一块；
- **折返时（`reversed`）**把水浪里的每颗珠子放进该端收集区：深度**逐颗随机**（0.15~0.85 区宽），
  乘上"这颗珠子在出玻璃之前还剩多少余量"的上限 —— 不这么做，越出玻璃的珠子会立刻 `respawn`，
  水正好在司机看着它的时候消失；
- 落区的珠子 `inCollectZone = true`，**此后的行程不再捡它**（`else` 分支开头直接 `continue`），
  它照样受密度模型驱动往下流、流出玻璃后 `respawn` 变回普通雨水（`respawn` 里清标记）。

实测（三次完整往返，同一块玻璃，与"关掉收集区"的对照并排）：

```
cycle 1: 有收集区 碰到 22 颗，平均位移 355.3 mm，11 颗落区（累计 11）
         无收集区 碰到 19 颗，平均位移 352.0 mm
cycle 2: 有收集区 碰到  9 颗，平均位移 245.2 mm， 0 颗落区（累计 11）
         无收集区 碰到 13 颗，平均位移 233.8 mm
cycle 3: 有收集区 碰到 16 颗，平均位移 266.2 mm， 3 颗落区（累计 14）
         无收集区 碰到 13 颗，平均位移 246.6 mm
```

读法要诚实：**停放数是 11/11/14，基本不累积**（落区的珠子会往下流走、出玻璃后变回新雨），
所以收集区**没有**把"反复带水"关掉，第二趟仍然碰到 9~16 颗。它带来的可见差别是
**玻璃两端会出现一条停在那里的水带**（真实雨刷刮到行程末端本来就会留下这一条），
这条水带是设计意图，值得留；但**它治不了"整片玻璃跟着动"，治那个的是 §2 的四边形**。

## 4 顺手纠正夹具自己的两处量具缺陷

1. **分解轴取错**：`bulkShiftProbe` 一开始用夹具里合成的 `strokeDirection()`（-0.77, 0.64）当
   "沿行程"轴，而刀真正的推力是**实测**的 (-0.92, 0.01)。两者在这个连杆上不是同一个向量，
   于是整个重力/下流分量被算进"跨行程"里，读出一个**并不存在**的横向错动 220 mm。
   改成用实测推力当轴后：沿行程 172 mm、垂直 142 mm，而垂直那 142 mm 是**向下**的
   —— 正是"水收成堆 → 堆够密 → 开始下流"那一段设计好的因果。
2. **`thirds()` 用 `lastPushX/lastPushY` 选分档轴**，而"刀没动"的调用会把这两个值清成 0，
   → 分档从 X 轴**悄悄切到 Y 轴**。改成行程开始时固定 `strokeAxisX/Y`。

"整片玻璃"这件事的**诚实结论**：没有横向错动。用实测轴分解，**没被刀碰到的珠子沿行程方向最多只动了 2.3 mm**；
会动的只有刀真的扫到的那些，而刀刃 0.706 m × 行程 1.123 m 的走廊本来就占玻璃的约 65%，
所以"看起来大半块玻璃在动"是犁水的固有量级（沿行程均值 172 mm），不是额外的 bug。

## 5 note 206 §4 的中雨数字被这个 bug 灌过水（向下修正）

`wipeFactorBand` 的假走廊会把**与刀无关**的珠子喂进"水带"样本集（`pushedThisStroke`），
于是 note 206 §4 记的"中雨时水带 0.116 m/s、1 s 走 118.2 mm、比周围快 2.2 倍"里，
有一部分是这些珠子贡献的。修正后：

| 量（intensity 0.60，一次行程后停放 1 s） | 206 记录（含 bug） | 修正后 |
|---|---|---|
| 水带密度 | 123 /m² | **238 /m²** |
| 1 s 走的距离 | 118.2 mm | **94.5 mm** |
| 没被刮到的玻璃走多远 | — | **64.8 mm** |
| 倍数 | 2.2× | **1.46×** |

所以"雨刷是中雨里让水流起来的原因"这条因果**仍然成立但幅度小得多**（1.46×）。
断言相应改成设计本意：**水带 1 s 必须走 ≥ 50 mm 且快于没被刮到的玻璃（≥ 1.3×）**，
并在注释里写明旧数字的来源；**满强度下的强版本（2.9×）仍在 §3 断言**。
如果希望中雨时水带流得更明显，旋钮是 `runoffMps` / `densityThresholdPerM2`（未动）。

## 9 后续：本轮的"诚实值"又被修正了一次

用户在 v36 上继续复测，报了「整片玻璃上的部分小水珠跟着走」，查出**第二个独立真因**：
`advanceDrops()` 不区分"是否正被刀按住"，被携带的水一边被推一边自由下淌，从刀前缘线里漏出去。
修好后"水收成堆就会流"**变强**（满强度 3.5×、中雨 **2.15×**），所以 §5 那次向下修正被**部分收回**。
详见 **note 209**（含那 258.6 mm → 0.0 mm 的测量与证明）。
