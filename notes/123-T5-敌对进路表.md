# 123 - T5（一）：敌对进路表 —— "什么算冲突"

> 对应设计：`docs/01-设计/行车控制-任务联锁与行车许可-设计.md` §A-6（敌对进路表）/ §6（T5 前置）。
> 前置：notes/116–122。触发：用户 2026-09-14「一路把T做完吧」。

## 1. 为什么先做成一张"表"，而不是直接接进 SET 判定

设计把敌对进路表列在 T1b 里，我当时推迟了。理由写在 notes/117 §5：把"共用轨段"直接做成 SET 判据，
会让**当前能 SET 的进路变成 PENDING**（例如两列车先后去同一个站台），有回归已验收行为的风险。

本片把它落成 `MmtrEnemyRoutes.conflicts(simulator)`：**只回答"这两条进路敌对吗、因为什么"，
不改变任何状态**。好处立刻体现在测试上 —— 它只需要轨图 + 进路登记，**不需要车、不需要授权、不需要 tick**，
所以 5 条用例都是纯的、快的、好读的。要不要接进 SET、以及怎么接（得等时刻表来裁决先后），是下一步的事。

## 2. 实现的两条判据

| 判据 | 内容 | 为什么这条 |
| --- | --- | --- |
| `TURNOUT` | 同一处道岔，两条进路要求的**位置**不同 | T1 的物理层已经在**权限**上挡住了（互斥需求在道岔上排队）；这里只是把它**报出来**，让运营台与诊断看见"为什么不能同时成立" |
| `OPPOSING` | 共用一根轨且**方向相反** | 对向 movement 是真正的敌对 |

**同向跟随不报**（判据②的反例是本类最重要的一条用例）：notes/82 已定它是闭塞（S1）按间隔解决的事。
把跟随也报成敌对，这张表就会把每一次"两列车在同一条线上"都变成冲突 —— **噪声表等于没有表**。

方向用**进路序列里这根轨的前后邻居**判定，**不用几何角度**：进路序列是走行的**因果顺序**，
比拿坐标算朝向可靠（曲线轨、反向铺设的轨都能坑到几何算法）。

**宁可漏报，不可误报**：取不到邻居（这根轨是进路端点）时不报。这张表是给人看的。

## 3. 没有实现的第三条：侧面防护区重叠（以及为什么）

"两条进路从同一处岔口的不同股道**同时**穿过"确实敌对（现实里要防侧面冲突），
但它**离开时间就判不出来**：同一个岔口一分钟内被两列车先后穿过是正常运营，同时穿过才是冲突。
而"同时"需要位置/时刻，**不是光看两条进路的轨集合能决定的**。

硬按几何判的后果很具体：会把每一次"两列车都要过这个咽喉"都报成敌对 —— 又是假阳性泛滥。
所以：

- 运行时的侧面防护由 **S1 规则 (4)**（岔区清限 `MMTR_JUNCTION_CLEARANCE_M = 10 m`）在**位置上**已经执行；
- 本表等**时刻表（P 系列）**能给出时间窗之后，再按"时间窗重叠 + 岔口不同股道"补这一条。

## 4. 出口（顺带交付 ⑥ 的一半）

`SystemMapServlet` 顶层新增 `conflicts[]`：`{vehicleA, vehicleB, kind, bothSet, detail}`。
`bothSet` 标出**两边都已经 SET** 的那种 —— 那才是"联锁在说谎"，最该被看见的一种。
运营台据此可以先看见冲突，不必等它接进判定。

## 5. 验收

- 新增 5 例（`MmtrEnemyRoutesTests`）：
  - `twoRoutesWantingDifferentTurnoutPositionsAreReported`（判据①，含理由点名坐标与两位）
  - `twoRoutesWantingTheSameTurnoutPositionAreNotEnemies`（① 的反例：同位不算争用）
  - `opposingMovementsOverTheSameRailAreReported`（判据②）
  - **`followingMovementsOverTheSameRailAreNotEnemies`**（② 的反例：跟随不算敌对）
  - `anIdleNetworkHasNoConflicts`（空表不抛异常）
- 全量引擎：**570 通过 / 0 失败 / 4 跳过**（T4 二 后 565 + 本片 5 例，**零新增失败**）。

## 6. T5 剩下的（以及它真正的卡点）

| 内容 | 状态 |
| --- | --- |
| 敌对表的**定义与观测** | ✅ 本片 |
| 把敌对表接进 **SET 判定** | ❌ 未做 —— 需要"按什么裁决先后"，而那要时刻表 |
| **时刻表预排进路**（方案 B 主体：计划时刻裁决 / 预约槽 / 晚点重排） | ❌ 未做 |

**T5 真正的卡点不是算法，是输入**：它的输入（趟次表 = 计划时刻）来自**另一份设计文档的 P 系列**
（`任务系统-线路派生与车底交路-设计.md` 的 P1–P4：输入模型 → 服务计划 → 车底运用 → 派发器）。
机制那一半已经就位并测过：`requestAtomically(..., priorityMillis)` 的裁决链（notes/118）
随时可以接收计划时刻 —— **只差有人填值**。

因此在 P 系列造出趟次表之前，T5 能推进的只剩"敌对表接进 SET"这一件，
而它恰恰需要一个先后裁决依据（否则就是"谁先来谁赢"换个说法）。建议的下一步是 **P1**（输入模型 + 校验）：
它完全不碰联锁、风险最低，而且是 T5 的前置。
