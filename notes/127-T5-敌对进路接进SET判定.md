# 127 - T5（二）：敌对进路接进 SET 判定 —— 以及一个被用例逼出来的洞

> 对应设计：`docs/01-设计/行车控制-任务联锁与行车许可-设计.md` §A-6 / §6（T5 的"冲突裁决"）。

## 1. 交付：敌对表从"只看不改"变成**载重**

`MmtrRouteRegistry.refresh` 新增第 ③ 条件（**排在原来那两个早退之前**）：

```
SET ⟺ ① 每个未越过的岔都授权给我
     ∧ ② 每个未越过的岔的物理位置就是我要的那一位   （T1）
     ∧ ③ 不存在一条比我优先的敌对进路                （T5，本片）
```

**③ 必须排在"无岔的进路直接 SET"那个早退之前**：一条直通走廊上的两条对向进路**都没有道岔**，
而它们正是最典型的敌对情形（单线对开）。放在早退之后，它们会双双 SET。

顺便把 `MmtrEnemyRoutes` 里的"只看轨序"那一半抽成 `opposingConflicts(routes)` ——
**它不需要几何**，所以 `refresh`（手里只有登记表、没有 Simulator）能直接调它。

**裁决用到达序**（`requestedMillis`，同刻按 vehicleId），也就是 T1b 裁决链的兜底那一档；
第一档"计划时刻"要等 P 系列（notes/118 已把入口 `requestAtomically(..., priorityMillis)` 留好）。

## 2. 被用例逼出来的洞（本片最值钱的部分）

第一版写的是"**只在对方已经 SET 时才压我**"，当时觉得这样更保守。写完加了一条用例
`arrivalOrderDecidesNotVehicleId`，它**红了**，而红的原因不是那条用例写错了：

```
refresh(v1) 先跑：此时 v2 还没 refresh 过（established=false）
                ⇒ v1 不受压 → SET
refresh(v2) 再跑：看到 v1 已 SET，但**排名上 v2 更优先**
                ⇒ v2 也不受压 → 两条都 SET
```

也就是说"**谁先被 refresh**"会决定结果 —— 而"两条敌对进路都 SET"正是这条规则要消灭的东西。
我那条"更保守"的写法，等于把判定交给了遍历顺序。

修法：**判据只看排名，不看对方当前是不是 SET**。于是结果与刷新顺序无关 ——
一条进路被压住，当且仅当存在一条排名更高的敌对进路。"最优先的那条 SET、其余 PENDING"成为唯一解，
且必然收敛（对手退场后后到的那条立刻能 SET，有用例钉住）。

> 这已经是本系列**第四次**"验证改写了结论"：notes/124（先核实是不是洞）、
> 125（先定口径）、126（把规则关掉再跑）、127（这条用例红得对）。四次里没有一次是多余的。

## 3. 诚实边界：这是**优先级反转**，不是死锁

排名更高的那条若长时间上不去（它自己的道岔被第三条进路占着），我就会被一直压着。
- **不是死锁**：我什么都没持有，构不成循环等待（T1b 的原子获取已经消灭了部分持有）；
- **有兜底**：对方一旦不再需要这条进路（任务终态 / 删车），`Vehicle` 会 release 掉它，压制随之消失；
- **真正的治法**是时刻表：按**计划时刻**而不是到达序裁决（那时"谁该先走"不再取决于谁先申请）。

## 4. 验收

- 新增 2 例：`opposingRoutesCannotBothBeSet`（后到者 PENDING + 理由点名敌对种类与对手 + 对手退场后可 SET）、
  `arrivalOrderDecidesNotVehicleId`（**这条就是抓出 §2 那个洞的用例**）。
- 全量引擎：**575 通过 / 0 失败 / 4 跳过**（573 + 2 例，**零新增失败**）。
- **零回归这件事本身也是一条信息**：加上这条规则之后没有一条既有用例变红，
  说明此前没有一个测试构造过"两条对向进路都 SET"的局面 —— 也就是说**这个洞此前从未被测到过**。
