# 112 - S5 实测：搬一盏灯验证轨中段切分（三条验收全部达成）

> 承接 notes/104–111（v2 全部代码片）。本片做 **S5 的实机验证**：在不依赖用户手动搬灯的情况下，
> 用 RCON 把一盏灯放到某根轨的**中段**，验证"灯切分轨"这一条真的工作。

## 1. 做法（以及我为什么能自己做）

- 该 dev 世界里 `z=-122` 有 **4 盏灯保护同一根 43 m 存车线**（notes/105 §3.1），四者信息等价；
- 引擎的 `signals scan` / 绑定工具**只读**，不能在虚拟世界凭空造灯，所以我把其中一盏
  `-168,-60,-122` **搬到该轨中段** `-168,-60,-100`（x 不变、z 从 -122 移到 -100，正好在该轨
  弧长 0.5 m→22 m 处）。
- 方式：MTR 方块 `mtr:signal_light_4_aspect_2` 用 **RCON** `setblock` 放到目标位置，再发
  `signals scan` 让引擎登记它（`mmtrSignals.put` 的坐标就是方块坐标，v2 的投影自动算出弧长）。

> ⚠ **这是对世界状态的改动**：新增了 1 个方块 + 1 条灯登记。撤销方式：
> RCON `setblock -168 -60 -100 air`，再发一次 `signals scan`（或用 `mmtr-signal-op` 的 `remove`）。

## 3. 实测顺带发现的三件事（都要用户决定）

### 3.1 `signals scan` 补登记了 24 架此前未登记的灯（世界比登记表多）

```
[signals] 扫描完成: 找到 31 个信号灯, 新增 24 个 AUTO 条目, 跳过 BOUND 1 个
```

也就是说：**这个世界实际有 31 架信号灯，而登记表里原本只有 8 架**（此前只扫描过部分区块）。
补登记后 `blocks-v2` 从 8 条区间涨到 **32 条**，覆盖轨从 35 根涨到 **59 根**。
这是**既有的**登记缺口（不是我引入的模型问题），但它意味着：**此前所有灯显/闭塞结论都只基于 8 架灯**。

### 3.2 多腿走行会把"兄弟分支的 span"混进同一个区间的 span 列表（v2 实现缺口）

证据：`blocks-v2 区间 -145,-60,-204 → 尽头 跨 3 根轨` 却是
`FFFFFF57 / FFFFFF6D[0.0,22.0) / FFFFFF6D[0.0,22.0)` —— **同一根轨出现两次**，
且该灯的 `fail` 分支本应终止在 `-145,-60,-169`。

原因（代码级）：`walk` 用**共享的 `section.spans`** 做多腿递归 —— 一条分支若终止在**灯**上，
会**提前 return**，于是**不把它已经 push 进 spans 的那一段算作"有分支继续"**；
兄弟分支随后继续 push，最终 spans 里混入了不属于同一路径的段，`exitSignalKey` 也被先到的
终止灯覆盖。单个分支看是对的，**跨分支的 span 列表不可靠**。

影响面：**只影响 `blocks-v2` 的 span 列表展示与 `section.lengthM()`**（诊断/长度）；
占用投影 `isOccupied` 逐 span 求交，多算的段会让区间偏保守（更容易被判被占）；
链深走的是 `following`（由终止灯推导），**不受影响**。
处置：记为 **v2 后续片（S6）**，修法是让每条分支携带自己的 span 列表、最后合并（或按路径去重）。
**本轮不改**：它不影响已验收的三条，且改动面在走行核心，应当单独一片 + 单独回归。

### 3.3 新增登记里出现同坐标的 AUTO 与 BOUND 两条

`-157,-59,-189` 是 BOUND，而 `-157,-60,-189` 是扫描新增的 AUTO（**y 差 1**）——
同一个信号方块位置被登记了两次（一次是旧的绑定、一次是扫描按方块坐标登记的）。
`mmtrBlocks.resolveRail` 对 BOUND 优先用 target，所以哑绑定那条仍然"未生效"（离轨 >8 m）。
处置：需要用户在游戏内**重新绑定**（notes/111 已让绑定工具与区间模型同源，但模型优先显式 target，
不会自动纠正）。**注意：`signals scan` 会按方块坐标再登记一条，所以重绑之后旧的那条仍需清理**。
