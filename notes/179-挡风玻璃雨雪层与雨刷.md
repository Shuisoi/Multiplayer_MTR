# 179 · 挡风玻璃：雨雪层 + 雨刷

> **修订（本轮）**：`mmtr_windshield_<n>` 的语义改了 —— 用户指出"靠打包器挑边来定上/停放方向不直观"，
> 所以改成**每个锚点 = 一根雨刷的专用平面**，由几何显式给出枢轴与停放方向。见文末 §7「语义修订」。

> 用户拍板：**不做受电弓**（世界观非电气化）、**雨刷用平面**、"暂时仅需针对驾驶室可观进行优化"。
> 本轮交付雨刷与雨雪效果的第一版：锚点命名、打包器配置、客户端渲染器。
> 验证：`fabric:compileJava` BUILD SUCCESSFUL；打包器产出 `windshield` 块；路径守卫 exit 0。

## 1. 命名与模型契约（给建模端）

### 命名
```
mmtr_windshield       一辆车一块挡风玻璃（单块）
mmtr_windshield_1     前风挡
mmtr_windshield_2     后风挡（或第二块）
```
**为什么 `_1`/`_2` 不能复用 hud 的正则**：`mmtr_hud_2` 的 `2` 是**驾驶室号**，而 `mmtr_windshield_2` 的 `2` 是**玻璃序号**。
两者语义冲突，所以打包器给了它**独立的 `^windshield(_(\d+))?$` 正则**，把序号写进锚点的 `door` 槽
（`pack_vehicle.js` 里 `const wsm=...` 那一段）。这是本轮唯一容易埋雷的地方。

> ⚠️ 上面这段的**语义已被 §7 修订**：现在 `_n` 是**雨刷序号**，每个锚点自带枢轴与停放方向。

### 几何（一个独立四边形 Object，与 `mmtr_hud` 完全同构）
| 项 | 规则 |
|---|---|
| 形状 | 一个四边形，面中心 = 玻璃中心 |
| 法线 | 朝**车外**（雨来的方向）。反了就加 `"flipAnchorNormalByGroup": ["mmtr_windshield"]` |
| 尺寸 | 自动量取 → `widthM` × `heightM`，**不用你写** |
| 局部坐标 | **与世界 +Y 最贴合的边 = "上"**，另一边 = "右"（沿用 `mmtr_hud` 约定） |

> **"上"这条为什么关键**：雨点是**沿重力在玻璃平面内的投影**流的，雨刷停放角是相对玻璃"右"轴量的。
> 如果"上"边选错了，雨会横着流、雨刷会斜停。把四边形的一个边尽量贴着竖直方向画就行。

- 玻璃面是**纯数据**：几何会被打包器剥掉（和 `mmtr_hud`/`mmtr_seat` 一样），你画的四边形本身不渲染。
  玻璃本体按你自己的美术做，`mmtr_windshield` 只是给它贴雨/雨刷的**定位面**。
- `mmtr_cabdoor_*` 那种"既是锚点又是可见部件"的特例**不适用**于挡风玻璃。

## 2. 雨刷：**不需要你画贴图**

这是本轮做了简化后的结论 —— 雨刷是**代码生成的实体几何**，不是贴图：

- 画法：从枢轴出发的**两根扁平四边形**（刀刃 + 略细略亮的摆臂），在玻璃平面内绕枢轴按角度旋转
- 材质：纯色（`colour` / `armColour`），复用 MC 自带的 `minecraft:textures/misc/white.png`
- 长度/宽度/角度全部由配置给数值 → **你只需要在模型里定出玻璃面，雨刷形状用参数调**

预览图（按默认参数画的几何形状，可直接打开看比例）：
`logs/2026-09/wiper-preview.png` —— 512×256，玻璃按 2.4 m 宽，画了 6° / 50° / 94° 三个角度，
枢轴在左下、臂长 0.60 m、刀宽 0.035 m。**这就是代码会画出来的东西的比例。**

> 如果你更想要贴图版雨刷（比如带橡胶纹理），说一声，我把 `drawWiperBar` 换成"贴一张 authored PNG、
> 用 UV 旋转"的版本；接口留好了位置，不用动别的地方。

## 3. 配置（`mmtr_anchors_<id>.json` → `windshield` 块，打包器自动生成）

打包器会在锚点 JSON 里多写一个 `windshield` 块，**有挡风玻璃的型号自动列出来**（没有则为空对象），
所以文件本身告诉你该调哪些键：

```jsonc
"windshield": {
  "windshield_1": {            // 键 = 锚点名
    "raindrops": 90,           // 并发雨点/雪点数 0..400
    "fallMps": 0.55,           // 沿玻璃下流速度 (m/s)
    "maxStreakM": 0.10,        // 拖尾最长 (m)
    "wiperCount": 1,           // 1 或 2（2 = 关于玻璃竖直中线镜像）
    "armM": 0.60,              // 臂长 (m) —— 建议 ≈ 玻璃高度，别超过
    "parkAngleDeg": 6,         // 停放角（0 = 贴着玻璃"右"轴水平停放）
    "sweepDeg": 88,            // 单程扫掠角
    "periodS": 1.6,            // 小雨时一个来回的秒数（雨越大越快，自动）
    "pivotU": 0.5,             // 枢轴在玻璃宽度上的比例 0..1
    "pivotV": 0.03,            // 枢轴在玻璃高度上的比例（0 = 下沿）
    "bladeWidthM": 0.035,      // 刀刃宽 (m)
    "colour": "#FF14181C",     // 刀刃色
    "armColour": "#FF3A4148"   // 摆臂色
  }
}
```

**雨刷速度是自动的**：`periodS` 是**小雨**时的周期，实际周期按雨量线性缩短到 `0.7 × periodS`（`1.45 - 0.75 × 雨量`）。
雨量取的是**原版自己的 `getRainGradient`**，所以和你看到的雨势一致。

**雨/雪自动判定**：按原版同一套规则 —— 取世界出生点生物群系的温度，`< 0.15` 判为雪。
雪会变慢（`×0.35`）、不留拖尾、画成白色圆点。

## 4. 代码结构

| 文件 | 改动 |
|---|---|
| `client/MmtrVehicleAnchors.java` | `Kind` 加 `WINDSHIELD`；`parseKind` 加 `case "windshield"`；新增 `findWindshields(anchors, modelCar)` |
| `render/panel/MmtrPanelCanvas.java` | 新增 `createPixels(widthM, heightM, widthPx)`：按**像素**建画布（雨层是整面图，要可预测的像素数）。为此把 `image/graphics/scaleX/scaleY` 从 final 改成可重设，并抽出 `replaceImage` |
| `render/panel/MmtrWindshield.java` | **新文件**，~660 行。状态机 + 降雨模拟 + 画布重绘 + 擦水 + 雨刷几何 |
| `render/RenderVehicles.java` | 逐车循环里、紧挨仪表板调用点之后加一行 `MmtrWindshield.render(...)` |
| `client/CustomResourceLoader.java` | 资源重载时 `MmtrWindshield.clear()` |
| `tools/obj-mtr-packager/pack_vehicle.js` | 独立 windshield 正则；`buildWindshieldConfig()`；写进锚点 JSON 的 `windshield` 块 |

### 渲染层的选择（这里有坑）
- 雨层 → `QueuedRenderLayer.EXTERIOR_TRANSLUCENT`（`getEntityTranslucentCull`：混合、**不写深度**、无 alpha 裁剪）
- 雨刷 → `QueuedRenderLayer.LIGHT_2`（`RenderLayer.getText`：**写深度**、有 alpha 裁剪）

枚举序 `EXTERIOR_TRANSLUCENT`(idx 5) < `LIGHT_2`(idx 6)，所以雨刷在**后一趟**画 → 必然盖住水。
**并且**雨刷离玻璃更远一点（`WIPER_OFFSET_M` 0.045 > `WATER_OFFSET_M` 0.030），让深度与层序一致而不是打架。

> 一开始我把雨层放进 `LIGHT_TRANSLUCENT`，后来发现两个问题：①它用 `getBeaconBeam`，是光束层，语义不对；
> ②`getText` 那句会把雨层按 alpha 阈值裁掉并写深度，软性水膜会变成硬边。所以改成现在的组合。

### 擦水怎么实现（用户设想的"雨雪层逻辑生成雨点用于提供挂水/雪效果"）
**不用遮罩、不用 shader**。画布每 ~90 ms 整张重绘一次，重绘时：
1. 铺一层极淡的湿膜色（让玻璃一直是"湿的"）
2. 逐雨点：**若它落在"上一次重绘到这一次之间雨刷扫过的扇区"内，就跳过它（并清掉它的拖尾）** —— 这就是被刮掉的效果
3. 否则画拖尾（沿重力投影方向）+ 雨点

扇区判定 = 到枢轴距离 ≤ `armM` 且极角介于「上一帧角」与「当前帧角」之间（带 `WIPE_PADDING_DEG = 7` 余量）。
角度先归一化到 [0,360) 再比大小，避免 `atan2` 的符号把扇区判反。

## 5. 已知限制（**未做**，按需再补）

| # | 限制 | 说明 |
|---|---|---|
| 1 | **没有玻璃遮罩** | 雨刷臂在大角度时会伸出玻璃轮廓（真实雨刷有遮罩，臂不会出框）。朴素做法是长度取 ≈ 玻璃高度、枢轴略低于玻璃下沿，观感可接受。要真遮罩就得在画布上按角度重绘雨刷层 |
| 2 | 雨点不"溅射" | 没有雨滴砸在玻璃上的飞溅粒子 |
| 3 | 刮过不留水膜 | 刮过的区域是干净的，没有半干水痕 |
| 4 | 不随车速变斜 | 雨点下落方向只取重力投影，没有叠加车速带来的向后斜（`vehicleSpeedMetersPerMs` 已传进 `advance()`，位置留好了） |
| 5 | 只有 1~2 块玻璃 | `wiperCount` 上限 2；多块玻璃请用多个 `mmtr_windshield_<n>` |
| 6 | 每块玻璃每 90 ms 一次整张上传 | 128 px 宽的 ARGB 图；1~2 块玻璃在雨天可接受，但这是纯 CPU 光栅 |

## 7. 语义修订：每个锚点 = 一根雨刷的专用平面

**起因（用户原话）**："不直观，这样，我专门设计一个面用来放置雨刷"。

原设计把 `mmtr_windshield_<n>` 当"整块玻璃"：枢轴靠 `pivotU`/`pivotV` 比例给，停放方向靠打包器
**挑一条与 +Y 最贴合的边**当"上"来推。两个问题：① 斜面上两条边一样斜时，打包器挑哪条**不可控**；
② `pivotU`/`pivotV` 还要再猜对应哪根轴。**两处都是"推"出来的，不是"画"出来的。**

### 新语义（已实现，`fabric:compileJava` BUILD SUCCESSFUL）

| 项 | 由什么决定 |
|---|---|
| **枢轴** | **面中心**（= 物体原点）—— 不再有 `pivotU`/`pivotV` |
| **停放方向** | **面的"右"边方向** —— 把四边形画成"其右边指向停放时雨刷该躺的方向" |
| **扫掠** | 从"右"方向起算，在面内**逆时针**扫 `sweepDeg` |
| **臂长** | **默认自动 = 四边形短边的一半**（正好是能塞进所画平面里的最大臂长）→ 尺寸正确的面**不用给 `armM`** |
| **擦水范围** | 以枢轴为心、`armM` 为半径的扇形；落在扇区内的雨点被擦掉 |

于是"枢轴在哪、停放朝哪、能扫多大"**全部由几何显式给出**，没有一处需要猜。
一锚点一雨刷：**两根雨刷 = 两个 `mmtr_windshield_<n>` 四边形**，各自画自己的枢轴与停向（不再有镜像规则）。

### 参数变化

| 参数 | 变化 |
|---|---|
| `pivotU` / `pivotV` | **删除**（枢轴 = 面中心） |
| `wiperCount` | **删除**。新增 `wiper`（bool，默认 `true`），后窗只做雨不做刷时设 `false` |
| `armM` | 默认 `0.60` → **`0` = 自动取短边一半** |
| `parkAngleDeg` | 默认 `6` → **`0`**（停放方向已由几何给出） |
| `sweepSign` | **新增**，`-1` 反转扫掠方向（不想翻面法线时用它） |

### 建模侧只剩三件事

1. 画一个**四边形**，命名 `mmtr_windshield_<n>`
2. **中心放在雨刷枢轴位置**
3. **让它的"右"边指向停放时的雨刷方向**

> "上"（= 与 +Y 最贴合的边）**仍然被算**，但只用于**雨点流向**（`panelDown()` 取重力在面内的投影），
> **不再影响雨刷** —— 所以本次改动后，就算"上"挑错了也只是雨斜点，雨刷照常。

### 已知取舍

臂长默认取短边一半、枢轴在面中心，于是**雨刷扫的是一个以面中心为心的扇形**。
如果平面画得比"实际擦得到的玻璃区域"大，雨刷臂就够不到四周。
想要精确控制就把四边形**画成紧贴擦刷区域**，或用 `armM` 显式给一个更大的值（臂伸出平面是允许的）。

### 双面画 + 法线朝向约定（用户拍板）

**用户的约定（照此建模）**：把四边形做成**法线指向车内**。在 Blender 的 Face Orientation 叠加里就是
**红色面朝车外、蓝色面朝车内**（蓝 = 面朝你，红 = 面背你）。

| 用途 | 需要哪个方向 | 该约定下 |
|---|---|---|
| 雨点画在哪侧 | **两侧都画**（见下） | 不依赖法线 |
| 雨刷沿法线抬起 | 朝车内抬 | ✅ 正好符合 |
| 雨点流向 | 只取世界重力在面内的投影 | 不依赖法线 |

**雨层改为双面画**（默认 `twoSided = true`）。这不只是"好看"，而是**必须**：

> 原来单面判定用的是 `facingSide()` —— "法线是否指向车体原点"。这对**仪表板**是对的，
> 对**挡风玻璃是错的**（司机和雨在玻璃的**两侧**），对**侧窗则完全退化**
> （法线朝外时 `horizontal` 分量 ≈ 0，判不出来）。双面画直接绕开这个问题，
> **也正是玩家从车外看玻璃时应该看到的**（外面玻璃上也有水）。

因为该层是 `EXTERIOR_TRANSLUCENT`（混合），**同一像素画两次会双重混合、看起来浓一倍**，
所以**两份各用一半 alpha**（`0x80FFFFFF`），两张叠加的覆盖率等于原来一张全不透明。

第二面不移动四边形，而是**把角点顺序倒过来**（`左下→左上→右上→右下`），用相反绕序让同一个矩形
在背面剔除下也能看到；同时**镜像 U**，使图像从背面看仍然正立。

关掉双面：配置里 `"twoSided": false`（此时恢复单面全 alpha）。

## 8. 命名语义再修订：`_n` = **驾驶室号**（覆盖 §7 里"雨刷序号"的写法）

> 用户原话："那不对了，设置 1、2 就是为了区别是驾驶室 1 还是驾驶室 2 的。"

**`<n>` = 驾驶室号**，与 `mmtr_hud_<驾驶室>` / `mmtr_cabdoor_<驾驶室>_<n>` / `mmtr_seat_<驾驶室>`
**完全一致**；不带编号按驾驶室 1 处理。

这一致性比"雨刷序号"重要得多：**双端机车必须能说清哪块玻璃属于哪个驾驶室**，否则代码区分不出
"该在哪一端画雨刷"。中途我一度把 `_n` 当雨刷序号、写进锚点的 `door` 槽，**是错的，已改回 `cab` 槽**
（`pack_vehicle.js:149-154` 与 `:215`）。

### 场景 → 锚点 映射

| 场景 | 怎么建 | 配置 |
|---|---|---|
| 单驾驶室 + 单雨刷 | 一个 `mmtr_windshield`（等价 `_1`） | 默认 |
| 双端机车，每端一块玻璃 + 各一根雨刷 | `mmtr_windshield_1` + `mmtr_windshield_2`，**各画各的枢轴（面中心）与停向（"右"边）** | 默认 |
| 一个驾驶室两把刷共用一个枢轴区（大片风挡） | 一块平面 + `dualWiper: true`，在面中心镜像生成第二把反向扫的刀 | `"dualWiper": true` |

> `dualWiper` 的**枢轴仍在面中心**，两把刀共用它、各向一侧扫。
> 若要"两把各有自己的枢轴"，就用**两个锚点**（`_1`/`_2`）而不是 `dualWiper`。

### 新增参数

| 参数 | 说明 |
|---|---|
| `dualWiper` | bool，默认 `false`。在面中心再镜像生一把反向扫的刀 |
| `wiper` | bool，默认 `true`。后窗只做雨不做刷时设 `false`（取代原 `wiperCount`） |
| `twoSided` | bool，默认 `true`。雨层双面画（见 §7） |
| `sweepSign` | `-1` 反转扫掠方向 |

### 客户端新增工具方法

`MmtrVehicleAnchors.findWindshield(anchors, modelCar, cab)` —— 取**指定驾驶室**那块玻璃，
给将来"只让在岗驾驶室的雨刷动"这类**按驾驶室**的判定用；渲染主循环仍用
`findWindshields(...)`（画该节车的全部玻璃）。

### 9.2 旋转映射（**实测**，别推）

打包器 `rotationDegY: -90` 的实际映射（用最小 OBJ 跑出来的）：

```
源 (x, y, z)  →  输出 (−z, y, −x)      即  源 Z → 输出 −X，源 X → 输出 +Z
源 X ±8（车长）  →  输出 Z ±8
源 Z ±2.5（车宽） →  输出 X ±2.5
```

**关键**：`mmtr_anchors_*.json` 里的 `x/y/z/normal/up/right` 是在**源模型坐标**里算的（`buildAnchors` 在旋转那一步之前），
所以看锚点数据时要拿源坐标比 —— `windshield_1.normal = (−1,0,0)` 意味着"朝源 −X"，而驾驶室在源 +X 一侧，所以是**朝车内** ✅。

### 9.3 挡风玻璃 `right` = 该驾驶室驾驶员的右侧

| | 该端朝向 | 输出坐标系里的右侧 | 锚点 `right`（源） | 映射到输出 |
|---|---|---|---|---|
| `windshield_1`（车头输出 +Z） | −Z | −X | (−1,0,0) | **+X** ✅ |
| `windshield_2`（车头输出 −Z） | +Z | +X | (+1,0,0) | **−X** ✅ |

用户口径"驾驶员在每头的右侧、**雨刷向左停放**"与数据完全一致：
`right` 指向的是**驾驶员的左边**（因为他坐右侧），所以 `parkAngleDeg = 0` 就是"停放在左"。
开启时向上扫的旋向由 `sweepSign` 控制。

> ⚠️ 上面这段里 `right` 的方向是拿**源坐标**读的，和客户端算出来的**不完全一样**：客户端在
> `Plane.of()` 里做 `toModelSpace(up)` 后按 `right = up × normal` 重算 right，实测
> `windshield_1.normal=(0,−0.283,−0.959)  up=(0,0.959,−0.283)  right=(−1,0,0)`
> （模型空间，`up` 仍是朝上的，符号都没翻）。**别按源坐标的表推客户端行为**。
>
> `sweepSign` 最终由用户拍板 = **`+1`**（`newstock.json` 里两个玻璃都是 `1`）。

### 9.5 两条模型侧经验

## 10. 雨层"垂直于风挡"的真凶：**复用驾驶台面板的欧拉解**（第六个静默失败）

### 10.1 症状与判据

实机：雨层不是贴在玻璃上，而是**竖着横切风挡**（用户的原话："垂直于 windshield 面"、"以车厢从左到右为轴，
旋转 90 度就是正常角度"）。这就是**绕着车的左右轴差了 90°** —— 一个纯粹的朝向错误。

### 10.2 根因

`MmtrPanelQuad` 的朝向是用一组欧拉角反解出来的：

```
pitch = asin(clamp(−up.y()))
yaw   = atan2(normal.x(), normal.z())
roll  = atan2(up.x(), up.y())
```

这套解是给**竖直朝前的仪表台面板**写的，而且它在结构上**解不出"绕着车的横轴转过 90°"这一档**：
它假设 `up` 的水平分量可以忽略（面板正对玩家），于是把 `up` 的竖直分量当成 pitch 的全部信息。

风挡不是这个姿态吗？对，但**风挡的 `up` 恰好让这套解退化**：实测 `windshield_1.up = (0, 0.959, −0.283)`，
`up.x() = 0` ⇒ `roll = 0`；`up.y() = 0.959` ⇒ `pitch = −73.6°`；再乘上 `yaw`。
合起来得到的矩阵把面板的"局部 Y（上）"映射到了**玻璃平面的法线方向附近**，
于是本来该铺在玻璃里的四边形被立了起来 —— 差的正是那 90°。

**判别方法（可复用）**：拿 `normal / up / right` 三个向量两两点乘。
风挡的实测值是**正交的**（`right.up = 0`、`up.normal = 0`），
所以**问题不在锚点数据，在代码怎么用这三个向量**。锚点数据是对的，不要去改模型。

### 10.3 修法：**不再用欧拉角，直接用基向量摆点**

新增 `MmtrWindshield.quadCorners(Plane plane, double widthM, double heightM, double liftM)`：

```java
centre + right·a + up·b + normal·lift      // a ∈ ±width/2, b ∈ ±height/2
```

点由**面自身的基向量**直接给出，所以四边形**按构造就在玻璃平面内**，
不管模型给的是哪种缠绕方向、也不管 `up` 的竖直分量是多少。
`Plane.pointAt(a, b)` 已经做了这件事，`quadCorners` 只是在外面加了一层 `normal * liftM`。

`drawRain` 相应改成：拿到 4 个角 → **只用 `carTransform`** 画（不再套局部旋转）。

> **一句话原则**：**锚点已经给了完整的正交基，就永远不要反解欧拉角。**
> 只要能拿到 `right/up/normal`，任何朝向问题都可以用基向量摆点绕过去。
> 反过来，任何"角度看着差 90°"的怪象，第一嫌疑都是欧拉反解退化了。

### 10.4 这一轮同时修掉的三个坐标错误（都在"贴图局部坐标"里）

雨点/雨刷都画在一张**贴图**上（`MmtrPanelCanvas`），贴图坐标和面坐标**不是同一个坐标系**，
这里有三个独立的坑，全部单独修过一遍：

| # | 错在哪 | 症状 | 修法 |
|---|---|---|---|
| 1 | 雨刷擦水扇区以**画布中心**为轴（`widthM/2, heightM/2`），而几何里的轴在**下沿** | 玻璃中间被擦出一个圆洞，刀刃却在底部扫 —— 两者对不上 | 擦水轴改用 `config.pivotU/pivotV`，与几何**同一个**轴 |
| 2 | 画布 `v` **向下**增长，面坐标 `up` **向上**增长 | 雨点往上"爬"、拖尾长在珠子**前面** | 擦水那边把 `deltaY` 取负换回面坐标；拖尾改成从珠子朝**下落反方向**延伸 |
| 3 | 拖尾长度按米算，但 `x`/`y` 两轴每格对应的米数不同（宽 3 m、高 1.56 m） | 宽风挡上拖尾**斜着飘** | 方向先按 `(down.x*widthM, down.y*heightM)` 归一，再乘 `trail` |

**约定（写进代码注释里了）**：`pivotV` 用**面坐标**（0 = 底沿），
`rebuildCanvas` 里 `pivotY = (1 − pivotV) · heightM` 是**唯一**一处做 v 镜像的地方。
