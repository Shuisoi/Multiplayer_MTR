| 件 | 内容 |

## 2. 规则（两端一致，写死在对应用例里）

1. 深度按**区间**计数：区间 1 = 灯保护的那个区间被占 → 红；2 = 它之后的下一个区间（同轨跨灯，或下一根轨的入口区间）→ 单黄；3 → 双黄；0 → 绿。
2. 区间占用只看**该区间颜色**；同一根轨的另一个区间被占不影响本区间。
3. 若轨上有**不属于任何区间**的被占颜色（老式 MTR 闭塞、人工封锁）→ 保守视为整轨关闭（与 B3b 前完全一致）。
4. 未切分的轨（区间 0 的色 = 轨色）行为与 B3b 前**逐位一致**。

## 3. 用例

- 引擎 `MmtrBlockServiceTests.everySectionCarriesItsOwnReservedSignalColor`：区间 0 = 轨色、区间 1 另色、跨实例稳定。
- 引擎 `MmtrSignalAspectTests.theChainCountsSectionsOnASplitRail`：未切分轨被占 → 红（改前读法）；切分后**只有远区间被占 → 单黄**，近区间被占 → 红。
- 引擎 `MmtrBlockSectionStopTests.aTrainInTheFarSectionDoesNotCloseTheNearSectionColor`：车列停在远区间时**只持有该区间颜色**，近区间颜色保持空闲（改前的整轨持有会把它关掉）；该用例顺带把测试的每 tick 顺序改成与 `Simulator.tick` 一致（先 roll 信号块快照再模拟），否则颜色持有会在 tick 间累积。
- 客户端 `MmtrSignalChainTests.aSplitRailIsCountedInSections`：远区间被占 → 2；近区间被占 → 1；外来颜色 → 1（保守整轨）。

## 5. 实机核查与注意

- 当前世界 8 架灯全在节点旁 → `splitRails()` 为空 → 镜像**不额外发送任何数据**，客户端行为与 B3 时完全一致（这是设计期望：B3b 是"真出现中段灯时"的能力）。
- **实机实证（运行中 dev 服务端，2026-09-10）**：把一架 BOUND 灯临时绑到真实世界最长那根 **187 m 轨**（`-220,-60,-125 → -220,-60,62`）的中段（`-220,-60,-32`），`blocks all` 立刻变成
  `轨道 134 根 / 区间 135 个 / 被灯切分的轨 1 根`、该灯 `弧=93.0 切分该轨`、`灯共 9 架：贴节点 7 / 切分轨 1 / 未生效 1`；
  `blocks <railHex>` 给出 `边界: NODE@0.0 SIGNAL@93.0(-220,-60,-32) NODE@187.0`、`区间 [0.0, 93.0)` 与 `区间 [93.0, 187.0)`。
  随后 `op=remove` 复原，世界回到 `134 轨 / 134 区间 / 0 切分轨 / 8 架灯`——证明 B1→B3b 的切分链路在真实轨图上可跑通且可回退。
- 客户端镜像格式变了（`sections` 字段），**服务端与客户端都要用新 jar/新构建**才能互通（旧客户端忽略未知字段即可，新客户端没有 `sections` 时退化为整轨规则）。
