## 1. 冲突与判据（结论先写）

两条规则原来都在比"**这一步的时刻**晚了多久"，于是打架：

| 规则 | 说的是 |
| --- | --- |
| 迟到不补跑（P4 / §7「过去不可改」） | 错过的班次不该补跑（半路开机不要重演上午） |
| 接管续行（P6 / §8.2） | 玩家把车还回来，AI 从**那一点**继续 |

**判据改对了以后是**：迟到只对"**这一趟的窗口已经过完**"的步生效，不看单步的时刻。

```
这一步所属的那个交路条目（按计划时刻落在哪个条目的时间窗里）
    ├─ 窗口已过（now > entry.endMillis）→ 跳（P4：错过的整趟不补跑）
    └─ 窗口还在 / 还没到              → 照派（P6：同一趟的下一步，跳了就等于这趟车不停那一站）
```

一句话：**错过的是"这一趟的窗口"，不是"某一步的时刻"。**
（查不到交路 / 查不到条目 ⇒ 退回老语义"迟到就跳"，宁可少跑也不凭空补。）

## 2. 第一版判据是错的，而且是测试抓出来的

第一版我写成"**这一步是不是一趟的发车**"（是发车才允许跳，中趟的步永不跳）——
听着对，实际把"整天都错过了"的班次**照跑一遍**：

- 用例 `staleStepsAreSkippedInsteadOfReplayed`（P4 装机前推演出来的那条）**红了**：
  09:00 开机时 `dispatchedTotal` 从 0 变成 **25** —— 上午那几趟的**中趟步**全被派了出去。
- 原因很清楚：中趟的步"永不跳"这条，**默认了这一趟已经在跑**。半路开机时它根本没开始过，
  于是派发器开始给一个不存在的班次补派"到第二站"。

改成"看条目窗口"以后，同一个用例回到 0（跳过 total 步），接管那条仍然绿。
**两条用例一起才把这条规则钉死**：少任何一条，都会往一边倒。

## 5. 现场顺手抓到的两条（都不改，记账）

1. **出库时刻被钳在 00:00**：`MmtrDiagram` 里 `Math.max(0, 首趟发车 - leadTime)`。计划里没有"昨天"，
   所以"首趟发车早于午夜+前置量"时出库被钳到 00:00 —— 于是那个条目的窗口会退化成
   `[0, 负数]`（start > end），本轮判据把它当"过完"跳过。**这是刻意钳位，不是缺陷**，
   但它让"半路开机"的第一个出库步容易落进宽限内被派出去 —— 要不要给首趟也做钳位/顺延，留给下轮判断。
2. **执行期的失败派发器看不见**：本轮验证线用的是**站 id 当台 id**（现场没有列出站台的接口），
   世界把 mission 判成 `FAILED：target siding … has no graph rail`，而派发器这边已经算
   "派出去了"（`dispatchedTotal=4`）。也就是说"世界接受了任务"与"任务真的跑起来了"之间有个缝。
   —— 因此本轮现场读数证明的是**派发器的判据**（该派/该跳），不是"车真的开到了站台"；
   走行时间也不是真值（ring 3960s ≈ 纯停站 + 两端终点处理，腿长 0）。
