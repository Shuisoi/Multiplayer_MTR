> 用户要求：给 `987654` 车场的 6 台车配一份时刻表 —— 站名 1→10 顺序走；10 站端经道岔
> (-155,-60,-189) 越过 (-147,-60,-169) 后换端；10→1 开回；回到 1 站后经 (-176,-60,-253)、
> 在 (-176,-60,-222) 前停车换端，再从 (-170,-60,-289) 进 1 站，**重复一次** 1→10、10→1，最后全部回库。

> 引擎 **670 通过 / 0 失败 / 4 跳过**；停机部署（22:14:29 的 jar）后现场验证。

## 1. 时刻表（配置与账）

现场读出来的东西：10 个站（站名就是 `1`…`10`，每站 2 个站台，默认停站 10 s）、
`987654` 车场 6 条股道各 1 台车。线路按站名顺序配，用**真站台 id**（十进制字符串）。

```
线路 L1「1-10 线」：10 站（1→10），停站 30 s，终点处理 CHANGE_ENDS，出库前置 5 分钟，
                     出库股道 = 987654 的 1 道；车底 = C1..C6（6 个编组，正好对上库里 6 台车）
真轨图算出来的：周转 ring = 17.47 分钟（单程 8.73 分钟；站间 2s~55s + 每站停 30s）
密度表：12 班 × 3 分钟 ⇒ N = ceil(17.47/3) = 6 ✔（正好 6 个编组）
```

**"两次往返"是这么落的**：12 个发车槽位按轮转分给 6 个编组 ⇒ 每个编组拿到**两对**去/回趟次：

```
C1: L1-001@00:18 → L1-B001@00:26 → L1-007@00:36 → L1-B007@00:44 → 回库
C2: L1-002@00:21 → L1-B002@00:29 → L1-008@00:39 → L1-B008@00:47 → 回库
…  C6: L1-006@00:33 → L1-B006@00:41 → L1-012@00:51 → L1-B012@00:59 → 回库
```

每个编组 78 步（出库 + 10 站到站/停站 × 4 趟 + 换端 + 回库）；第一趟与第二趟之间正好隔一个周转
（18 分钟 ≈ ring 17.47），所以第二次往返接得很紧、最后回库 ✓。这份配置已存成可复现的
`mmtr/config-example/plan-L1-1to10.json`（线路 + 密度 + 车底三段，直接 post 就能复现）。

**还没做的（下一轮）**：用户点名的那两处**折返走法**（10 站端"越过两个道岔再换端"、1 站端
"越过分岔、在指定点前停车换端、再从另一个节点进站"）。计划层现在只有三种终点处理
（`CHANGE_ENDS` 就地换端 / `TURNBACK` 开回车场折返 / `STABLE` 停车留驻），**没有"开到某个节点再换端"**
这种走法；要按用户说的走，得给线路加一条"折返目标"（股道或节点）并让交路多出
"到折返点 → 换端 → 回站台"这三步。这一轮先把车开出去，下一轮做这条。

## 2. 现场第一手：车为什么开不出去

**不是"车完全不动"，也不是 H 提示卡住**（这两条都验过了）：

| 观察 | 数据 |
| --- | --- |
| 用户看到"应答信号（按 H）" | 六台车的 `manualOverride=False`、`awsWarning=False`；AWS 那套**只在手动驾驶时才会响**（`mmtrManualOverride` 为真时状态机才跑），而且引擎的自动驾驶判据要求 `!mmtrManualOverride`。所以 H 提示不是这六台车的刹车 |
| 车往前挪了一点、车头停在节点上 | `motionAuto=True` 的那台确实动了（-184.5,-121.5），其余五台 `motionAuto=False`：它们的**进路自臂从来没成功过** |
| 进路为什么自臂不了 | 引擎原话（本轮为它加的诊断）：`道岔位置给不了（物理层/净空闸）：point -170,-60,-186 wantLeg=0 needPos=0｜lock=false holder=- queue=v-733…@0 phys=v-810… 现位=1` |

**读法**：要出库的那台车需要 (-170,-60,-186) 扳到**位置 0**，而它现在是**位置 1**；
没有任何人工锁、没有任何进向持有者 —— **但物理层的"位置"被另一台车（`v-810…`）按着**。
那台车自己正停在发车进路上（`route=PENDING`、`moving=False`），却继续把这条道岔的位置钉在 1，
于是要 0 的那台永远等不到，两台互相卡住 ⇒ 库里六台车一台都出不去。

这就是"一处道岔只有一个位置"（T1）与"多台车同时要出库"撞在一起时的**活锁**：
钉住位置的那台车**自己也没有进展**，而释放**只发生在它过岔/换路的时候** —— 它不动，就永远不会释放。

**下一轮的修法（已有判据）**：物理位置的使用期不该长过"持有者真的需要它"。判据可以用引擎已有的
那条净空判定（`MmtrJunctionState.blockedThrowReasonExcept`：谁真的压在这处岔区里）——
**持有者自己既不在岔区里、又停着不动时，它的位置钉必须被收掉**，让等着的那台能拿到位置。
修之前先写一条"两台车抢一处道岔、先到的那台停着不动"的用例，**证明会红**（这是本轮学到的教训：
没有会红的用例，这种活锁修了也不知道修对没有）。

## 3. 本轮修掉的真缺陷：重算把在途车丢了（幽灵车堵死车场咽喉）

现象（本轮实测）：改一次密度表 / 计划重算 ⇒ 重建派发器 ⇒ **世界里那台车还在跑上一代派给它的那一步**，
新派发器不认识它，于是去牵另一台；被忘掉的那台永远停在原地，还继续按 FIFO 占着道岔 ——
本轮现场两台这样的车（`-153,-121` 与 `-211,-158`）把咽喉堵死，六台车一步都出不去。

修法（`MmtrPlanDispatcher.adoptFrom(previous, check)` + `Simulator` 的两遍清理）：

1. **换代交接**：按任务 id（`线路/编组/序号`，跨次重算稳定）把"谁在跑、跑到第几步、正在等哪一步"
   接到新一代上；**并且问世界一句**"这台车还在、还在跑这一步吗" —— 只照记忆交接会接一台已经不存在的车
   （本轮第二轮现场就是这样：车场重建后车列 id 全变了，交接照记忆走 ⇒ 一台车都不动，比不交接更糟）。
2. **收回没被认领的任务**：重建之后扫一遍世界，凡是跑着"这套计划的任务"而新一代没有认领的车，
   把任务收回来（任务 id 形状 `线路/编组/序号`，作业单的任务不满足这个形状，不会被碰）；
   整条线路被删、输入坏掉（`mmtr-plan.json` 改坏）时同样收 —— 这些车以前会一直开下去。

测试：`MmtrPlanDispatcherTests` 新增 3 例（交接不重复派发 / 接不到活车就不接 / 编组在新计划里没了要交回），
**红证**：把 `adoptFrom` 那一步停掉 ⇒ 正好这两条新用例红（`15 tests completed, 2 failed`），恢复后全绿。
全量 663 → **670**。

## 4. 顺手补的诊断（"看不见的状态修不好"）

这一轮为了回答"车为什么不动"，补了三处**只读出口**（都不改行为）：

1. `mmtr-trains` 每台车多四个字段：`manualOverride`（手动接管）、`motionAuto`（自动驾驶接上没有）、
   `stoppedAtTarget`、`awsWarning`（AWS 点式警告未确认）—— 用户问的"H 提示"就是最后这个；
2. 等道岔的日志从"`lock=false holder=-`"（看着像无缘无故）升级成**引擎自己说清哪一处、哪一道门、
   谁按着哪个位**：`道岔位置给不了（物理层/净空闸）：point … needPos=… phys=… 现位=…`；
   加 `MmtrPointAuthority.lastWaitReason(owner)`：请求集是**原子**的，只报"第一处没持有的道岔"
   往往是红鲱鱼，真正的拦路者可能在同一组的后面 —— 现在由权限层直接记下那句话。

```
车：  五台 motionAuto=False（进路 PENDING，等 -170,-186 的位置）／一台 motionAuto=True 已挪到咽喉
```

**结论：时刻表本身是对的（趟次、分车、两次往返、回库都对上了），卡住它的是第 2 节那条活锁。**
