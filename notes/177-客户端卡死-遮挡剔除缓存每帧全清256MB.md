# 177 = 客户端"卡死"：遮挡剔除缓存每帧全清 256 MB（+ 三行现场取证）

> 触发（2026-09-16，用户）：**「首次进入游戏后正常移动，然后在两帧之间卡住来回抽搐，游戏里的车正常」**

> 状态：**根因已用 jstack 钉死，修复已实施、用例已过**；实机复验待用户重启客户端。

## 1. 先排掉的三个方向（都不是原因）

| 方向 | 怎么排掉的 |
|---|---|
| 服务端在拽人（位置校正） | 全窗口 `外部最大挪动=0.000 格（0 次）`、`反向=0 次`；且全 mod **没有任何**服务端 `teleport/requestTeleport` 调用，客户端写玩家坐标的地方只有 `VehicleRidingMovement.movePlayer` 一处（`车内定位=0`，从没跑过） |
| 客户端 tick 被卡 | `[MMTR-PERF] tick=100/101` 每 5 秒窗口 = 稳定 20 TPS，整段会话只有 5 次 >150 ms |
| 渲染线程死了 | `[MMTR-DBG] world render running` 每 2 秒一条，19:57→21:04 一条不断档 |

**真正的现场是"tick 还在跑、画面不出帧"** —— 这两条线必须分开量，tick 率看不出来（这就是本轮加 `帧=` 的原因）。

同一时刻渲染线程 `cpu=67015.62ms/elapsed=77.90s`（**86%**），C2 编译线程 23%，进程总计约 2.6 个核
⇒ 整个客户端被这一个数组清空拖住，画面几乎不出帧。

## 3. 根因：缓存大小是 reach 的**立方**

`com.logisticscraft:occlusionculling` 的 `ArrayOcclusionCache`：

```java
this.cache = new byte[(reachX2 * reachX2 * reachX2) / 4];   // reachX2 = reach * 2
public void resetCache() { Arrays.fill(cache, (byte) 0); }
```

MTR 传进去的 reach 是 `Math.min(渲染距离, 32) * 16`（`WorkerThread.updateInstance`）：

| 渲染距离 | reach | 缓存数组 | 一次 `Arrays.fill` |
|---|---|---|---|
| 8 区块 | 128 | 4.2 MB | ~0.15 ms |
| 16 区块 | 256 | 33.5 MB | ~1 ms |
| **32 区块（本机 options.txt 实测 `renderDistance:32`）** | **512** | **268,435,456 B = 256 MB** | **~7 ms** |

而 `WorkerThread.runTick()` 原来的循环是"**先睡 10 ms** → 队列非空就 `resetCache()` + 每个队列只跑**一个**任务"：

- 产出端：每帧各一个任务（`RenderVehicles`/`RenderRails`/`RenderLifts` 的无阴影分支）⇒ 120 FPS 时 240 个/秒；
- 消费端：10 ms 一轮、每轮每队列一个 ⇒ **上限 100 个/秒** ⇒ 队列（每队列上限 `MAX_QUEUE_SIZE=2`）**长期是满的**；
- 于是 `resetCache()` 每秒跑约 100 次：**≈ 700 ms/秒、≈ 25 GB/s 的纯内存写**，同时把 CPU 缓存和内存带宽占干净。

**两个后果一起发生**：① 73% 的一个核白烧，渲染线程掉帧（用户看到"卡死"）；② 队列常满 ⇒ 调度方
`scheduler` 在 `size() < MAX_QUEUE_SIZE` 为假时**把任务丢掉** ⇒ 花了 73% 的核却几乎没做遮挡剔除。

## 4. 修法（两处，都在 mod 侧，不改库）

### 4.1 `MmtrSparseOcclusionCache`：清空的代价从 reach³ 降到"碰过的格子数"

库允许注入自定义缓存（`OcclusionCullingInstance(int, DataProvider, OcclusionCache, double)`），
所以换掉那份实现即可：

- 语义与 `ArrayOcclusionCache` **逐位一致**（2 bit 一格、4 格一字节、`key = x + y*rx2 + z*rx2²`、
  `getState` 返回 `(byte >> offset) & 3`，`visible=1 / hidden=2`）——用例拿库自己那份当对照跑了 2 万步读写；
- 多一份"本帧写过的**字节**下标表"：`resetCache()` 只把这些字节清零（几百个）再清表，而不是 fill 2.68 亿字节；
- 去重判据：**字节为 0 ⇒ 本帧还没写过**（写过的字节在 reset 前必非零），所以同一字节最多记一次；
- 读数路径没有任何变化（仍是直接下标寻址），射线步进的性能不受影响；
- 兜底：记录表到 400 万条就退回一次全量 fill 并清表（那时只是那一帧按老代价付费）。

### 4.2 `WorkerThread.runTick`：有活一口气干完，没活才睡

```java
if (hasOcclusionTasks) {
    updateInstance();
    occlusionCullingInstance.resetCache();
    while (run(vehicle) | run(lift) | run(rail) | run(misc)) { }   // 队列清空为止（用 | 不短路）
} else {
    Thread.sleep(10);
}
```

这样既不再"每轮一个任务"地积压（任务不再被丢），也不再"闲着也每秒清 100 次缓存"。

## 5. 用例（`mmtr/game/fabric/src/test/.../MmtrSparseOcclusionCacheTests.java`，4/4 过）

| 用例 | 钉住的东西 |
|---|---|
| `everyReadAndWriteMatchesTheLibraryCache` | 与库实现**逐位一致**（2 万步随机读写，含 `setLastVisible/setLastHidden`）——位序错了不会崩、只会让剔除偶尔判反，所以必须对照 |
| `twoCellsInsideTheSameByteKeepTheirOwnBits` | 同字节 4 格互不串位，且**同字节只记一次** |
| `resetCacheForgetsEverythingAndKeepsWorkingAfterwards` | 清空后旧格子回到"未判定"、记录表也空、之后仍可写可读 |
| `theResetCostFollowsTouchedCellsNotTheArraySize` | 清空代价 = 写过的**字节**数（100 格 → 30 字节），远小于整个缓存 |
