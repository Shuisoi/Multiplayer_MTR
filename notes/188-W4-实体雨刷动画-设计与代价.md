# 188 - W4 实体雨刷动画：设计与代价（含一个必须先修的销点缺陷）

用户要求把**两种可动雨刷**（单轴 / 平行双连杆）的实体部件都做成会动。这一篇是动手前的测量与设计，
因为前面承诺过"先量 optimized 缓存的代价，再动 MTR 渲染管线"。

## 一、代价测量：结论是"几乎为零"

渲染路径（读代码得到的链路）：

```
ModelPropertiesPart.render(...)                      每部件、每帧
  └─ OptimizedModelWrapper.ObjModelWrapper            addTransformation(shaderType, x, y, z, flipped)
      └─ OptimizedModel.ObjModel.addTransformation   烘焙进 VBO 的**只有平移 + 180° 翻转**
  └─ OptimizedRendererWrapper.queue(model, graphicsHolder, light)
      └─ OptimizedRenderer.queue(...)                吃的是 **graphicsHolder 当前的矩阵栈**
```

MTR 自己的写法（`ModelPropertiesPart` 优化路径）：

```java
graphicsHolder.push();
graphicsHolder.translate(x / 16, y / 16, z / 16);
if (partDetails.flipped) graphicsHolder.rotateYDegrees(180);
CUSTOM_RESOURCE_LOADER.OPTIMIZED_RENDERER_WRAPPER.queue(partDetails.optimizedModelDoor, graphicsHolder, light);
graphicsHolder.pop();
```

**关键结论**：旋转是**矩阵栈上的一层**，烘焙进 VBO 的模型完全没被改动，所以

- **不会**让 optimized 缓存失效（不需要为每个角度重新烘焙）；
- 代价 = 每个雨刷部件每帧一次 `push` + 一次旋转 + 一次 `pop`（一块玻璃最多 3 个部件）；
- 而且这个写法和 MTR 现成的 180° 翻转**结构完全一样** —— 不是新机制，只是把固定的 180° 换成任意角。

**所以 W4 不需要新的渲染机制，也不需要量什么缓存命中率。** 这是我之前把它当作主要风险，
现在证据表明风险在别处（见第二节）。

## 二、真正的拦路石：销点（必须先修）

真车的**臂销在刀片中间**（推力均匀），**拉杆销在刀片端部或刷架上**。而现阶段实现用的是**刀片的两端**
当两个"被驱动的点"：

```
现在：  A(θ) = P1 + R(θ)·(A0 − P1)      A0 = 刀片靠主轴的那一端
```

- **单轴不受影响**：整条刀片刚性绕主轴转，用刀片上哪个点都等价 ✓
- **平行双连杆受影响** ✗：刀片的**平移量**由臂的真实销点决定（`M0 − P1`），而现在用的是 `A0 − P1`。
  两者不等时平移量算错，且"平行四边形残差"会**误判**（真平行四边形被判成非平行，或反过来）。

**修法**：改用**销点**——臂的远端 `M0`、拉杆的远端 `B0` 作为被驱动的两点，刀片作为**过这两销的刚体**去推：

```
M(θ) = P1 + R(θ)·(M0 − P1)          臂的销（主动）
B(θ) = P2 + R(θ)·(B0 − P2)          拉杆的销（从动）
刀片 = 刚体：M0 → M(θ) 且 B0 → B(θ)   → 两端 A、B 由刚体推出
```

两个销的坐标**打包器已经拟合出来了**（`armTip` 与拉杆贴刀片的那端），目前只用于交叉校验、没进运动学。
这也**很可能就是上一轮四杆环闭合失败的根因**：当时喂给它的输入是刀片两端，而不是销点。

fixture 之所以没抓到：生成器里**臂正好销在刀片端部**，恰好绕过了这个假设。要补一个"臂销在中间"的用例。

## 三、W4 设计（两族各自的变换）

| 部件 | 单轴（P1 = P2） | 平行双连杆 |
| --- | --- | --- |
| `wiperarm_` | 绕 **P1** 转 θ | 绕 **P1** 转 θ |
| `wiperrod_` | （没有） | 绕 **P2** 转 θ |
| `wiper_` | 绕 **P1** 转 θ | **刚体变换**：`M0→M(θ)`、`B0→B(θ)`（理想平行四边形下就是纯平移） |

- **挂载点**：`ModelPropertiesPart.render(...)` —— 它**自己知道 `names`**（构造时 `this.names.addAll(names)`），
  而且**已经收到 `vehicle` 与 `carNumber`**，所以可以在那里按部件名判断"这是不是雨刷部件、
  属于哪个（驾驶室, 玻璃）"，再问 `MmtrWindshield` 要当前的 θ。

  只需暴露一个"按 (vehicleId, car, cab, pane) 取 θ"的查询，**没有第二套时间**（雨滴被刮掉与刀片摆动天然同步）。
- **施加方式**：在部件的绘制外包一层
  `push(); translate(枢轴); rotate(玻璃法线, θ); translate(−枢轴); …绘制…; pop();`
  —— 与 MTR 现成的翻转写法同构。

  这一点要写进注释（曲面玻璃本身还没做，见 W3）。
- **单轴可以立刻做**：它只需要 `pivotU/V` + `parkAngleDeg`/`sweepDeg`，这些**已经在配置里**，
  不依赖销点修复。**平行双连杆必须等销点修好**，否则刀片平移错量。

## 六、实测：销点形式**不能**先于环闭合 —— 顺序反了（2026-09-18）

按"先修销点、再做 W4"的顺序，把打包器的解算切到销点形式（`M(θ)=P1+R(θ)(M0−P1)`、
`Br(θ)=P2+R(θ)(Br0−P2)`，取过这两点的刚体变换 T 推刀片两端），结果：

| | 结果 |
| --- | --- |
| 单轴那块（pane 1） | 60.00 度、刀片贴边 **0.0 mm** ✓（也对：单轴下 T 退化为绕主轴刚性旋转） |
| 连杆那块（pane 3） | **49.75 度、4.5 mm 残差** ✗（改前是 50.00 度 / 0.0 mm） |

而 pane 3 的**两个销与刀片两端完全重合**（实测 gap = 0.00000），所以残差不可能是"销点取错"。

**根因**：T 由"两个销各自绕自己的枢轴转同一个 φ"构造，但

- 两个销走的是**两条不同的圆弧**，所以它们之间的距离 `|Br(θ)−M(θ)|` **不守恒**；
- 而两个销都在**同一块刚性刀片**上，距离**必须守恒**。

只有 `|M0−P1| = |Br0−P2|` 且两连杆平行（**严格平行四边形**）时两者才一致。
本 fixture 是"微扇"（连杆向量差 0.015 m），于是销点形式**自相矛盾**，矛盾量就是那 4.5 mm。

**结论（重要，且改变了顺序）**：

1. **从动杆的角度必须由四杆环闭合解出**（`θ₂ ≠ θ₁`），不能假定与曲柄相等。
2. 因此**一般四杆的环闭合是销点形式的前提，不是它的后续**。之前"四杆失败"和这次"销点失败"
   是**同一个根因**：都假定了两端同步转。
3. 单轴雨刷（`P1 = P2`）两种形式都对，因为那时"两端同转"恰好是刚体旋转。

**已回退**打包器的这次切换（回到刀片两端直接旋转），离线恢复全绿：
`60.00 度 / 50.00 度`、刀片贴边 **0.0 mm**、verify PASS、注入故障 19/19。
销点数据（`pinAU/AV`、`pinBU/BV`）、作用面放宽为任意多边形、以及销点运动学的离线判据
（`checkPinKinematics`，含 11 mm 误差的量化）都保留。

**修正后的顺序**：
1. **四杆环闭合**（先做，用销点做输入：曲柄角 → 从动杆角 → 两个销 → 刀片刚体）；
2. 销点形式的运动学（`T` 由**环闭合算出的**两个销构造，此时距离守恒，T 自洽）；
3. fixture 补"中间销 + 连杆"用例；4. 最后才是 W4 引擎挂钩。

## 七、环闭合落地（三处一起改）—— 成功判据达成

第六节说"环闭合是销点形式的前提"。本轮把它落地，并且**生成器 / 打包器 / 校验器三处同时改** ——
上一轮只改一处导致夹具与被测对象建立在不同假设上，测不出问题。

### 实现

```
M(phi)  = P1 + R(phi)(M0 − P1)                              曲柄（主动、刚体）
Br(phi) = 圆(P2, |Br0−P2|) ∩ 圆(M(phi), |Br0−M0|)            从动杆（**解出**，不再假定与曲柄同角）
刀片     = 把停放位的销对映到当前销对的刚体变换 T 作用在刀片两端
```

**成功判据（目标里写的）达成**：

```
wiper linkage: windshield_1_3 pin span 0.3150 m conserved to 0.000 um over a full revolution
wiper mechanism: windshield_1_3 stroke solved as 50.00 deg from the fan edge at 93.95 deg (blade on it to within 0.0 mm)
wiper mechanism: windshield_1_3 parallel linkage, blade turns 3.95 deg over the 50.00 deg stroke -> slight fan
```

即：**销距在整个行程守恒到 0.000 µm**（刀片刚性所要求），行程被**精确**解出（50.00°，刀片贴边 0.0 mm），
刀片自转 3.95° 就是真实连杆的"微微的扇"。

### 这一轮踩的三个坑（都有诊断数据）

1. **圆-圆求交的半径顺序写反**：`radiusA` 属于**第一个点**所在的圆。传成 `(followerM, spanM)`
   会返回"另一对圆"的两个交点 —— 看着合理，实际差几米。修正后单轴那块恢复 60.00°/0.0 mm。
2. **夹具自己按错误假设生成**：`sweptRegionFan` 把拉杆端**独立**绕 P2 转。夹具与被测对象同错 ⇒ 测不出来。
3. **装配支链每帧重选**（最隐蔽）：生成器原本每个角度都取"离停放销最近的那个交点"，
   而两支链会在 toggle 位置交叉 ⇒ 中途翻到镜像支链。**打包器是"停放位定一次、全程沿用"**（它自己的注释
   就警告过这件事），于是两边分叉 —— 实测：生成器给 (0.5170,0.3314)，打包器给 (0.2078,0.7744)。
   改成"停放位定一次"后两边逐位一致。

### 另一个口径修正

`bladeTurnDeg` 原来用旧的 `directionAt`（两端同转）算，与真实机构不符：**3.95° vs 2.13°**。
改成用 `bladeAt`（过环闭合）计算后，打包器与校验器的报告一致（3.95°）。

### 现状

离线全绿：verify PASS、注入故障 19/19、三个真车锚点**逐字节不变**。
目标剩余：销点运动学（客户端）、中间销/四边形带 fixture 用例、W4 引擎挂钩。

## 八、客户端运动学切到环闭合（第 4 步）

`MmtrWindshield.bladeSegmentM` 现在与打包器/校验器**同一套数学**：

- 配置新增 `pinAU/AV`、`pinBU/BV`（**缺省回退到刀片两端** —— 老包与"销在端部"的机构因此照旧正确）
- `followMode` 改为按**停放位**定一次装配支链（并修好了它与 `followerEnd` 的半径顺序）
- `followerEnd` 的参数改名 `radiusAboutA` / `radiusAboutPivot`，并把"第一个半径属于第一个点"
  写进注释 —— 这个顺序错了会返回**另一对圆**的交点，看着合理却差几米
- 单轴（`P1 = P2`）直接走刚性旋转：环闭合在共轴时就是这个结果，不需要特判也能退化，但显式写出来更快也更清楚
- 刀片两端由"把停放销对映到当前销对的刚体变换"推出

编译通过。**注意**：这一步**进游戏验收仍不可行**（`driverOnBoard()` 还是 false），它的正确性来自
"与已验证的打包器/校验器同一套数学" + 离线断言，而不是来自实机。

## 九、W4 引擎挂钩（第 6 步）

`ModelPropertiesPart.renderNormal` 现在在画每个部件前问一次 `MmtrWindshield.pushPartTransform(...)`，
它按部件名识别雨刷部件并**压入一层刚体变换**（调用方在 true 时 `pop`）：

| 部件 | 变换 |
| --- | --- |
| `wiperarm_` | 绕**主轴 P1** 转 θ |
| `wiperrod_` | 绕**第二支点 P2** 转 θ |
| `wiper_` | 绕**停放位的臂销 m0** 转"销对转过的角"，再把该销平移到当前位置 —— 单轴退化为绕主轴旋转、平行连杆退化为纯平移 |

- **旋转轴 = 玻璃法线**：MTR 的 `GraphicsHolder` 只有 X/Y/Z 旋转，所以用与 `MmtrPanelQuad` 同一套
  帧解（`rotateY(yaw)·rotateX(pitch)·rotateZ(roll)`）把局部 +Z 对到法线上，绕 Z 转，再逆回去。
- **挂载点**：`ModelPropertiesPart` 自己知道 `names`；车辆标识用的是**模型资源 id**
  （`vehicle.getVehicleCarsAndPositions().get(carNumber).left().getVehicleId()`）——
  `vehicle.getId()` 是**数字** id，而锚点与雨刷状态是按**资源 id** 索引的，这个区别踩过一次。
- θ 直接取 `MmtrWindshield` 已有的 `wiperAngleDeg`，**没有第二套时间**。
- 为把 `carNumber` 传进 `renderNormal` 给它加了一个参数（两处调用点同步）。

**编译通过。** 与第二节的代价分析一致：旋转只是矩阵栈上的一层，烘焙几何与 optimized 缓存都没动。

### ⚠️ 验收状态的诚实说明

**这一步无法在游戏里验收**：`driverOnBoard()` 仍是硬编码 false（上下车重构期间），雨刷不运行，
所以实体部件永远停在停放位。它的正确性来自：

- 与**已验证**的打包器/校验器同一套数学（环闭合 + 销点 + 停放位定支链）；
- 离线判据全绿（verify PASS、注入故障 19/19、三个真车锚点逐字节不变）；
- 变换的**结构**与 MTR 自己的 `if (flipped) rotateYDegrees(180)` 同构。

真正的实机验收要等 B2 恢复"司机在哪个驾驶室"。**在此之前不应把 W4 说成"已完成"。**

## 十、第 (3) 步：中间销用例 —— 找到新缺陷，已回退

给 fixture 加了一块 **`windshield_1_4`：臂销在刀片中间**（真实机车的做法），并把 `sweptRegionFan`
改成用**销点**（而不是刀片两端）推刀片的两端位置。进展与结果：

**成功的部分**
- 联动机构可装配，且**销距守恒到 0.000 µm** —— 环闭合在"销≠端"的几何上同样成立；
- 打包器正确识别为 parallel linkage，并算出 `arm pin 0.583 m from the spindle`、`rod pin 0.583 m`。

**新缺陷（本轮回退的原因）**
平行四边形的行程**解不出来**，夹具的扇形被去重成**只剩两条边界线**：

```
[dbg] windshield_1_4 edge 90.00   phi 0.00  onEdge 0.00000   <- 停放位刀片，正确
[dbg] windshield_1_4 edge 140.96  phi 30.00 onEdge 0.44647   <- 远端刀片，差 0.45 m
```

即 `bladeAt(40)` **没有**落在夹具用 `carried()` 生成的远端边界上。两边的销点、销距、
从动杆长都核对过一致（0.30 / 0.583），装配支链也都按"停放位定一次"，
所以差异出在**刀片随销对的刚体变换**这一环，或者扇形本身在这种情况下退化（apex 落在 rim 顶点上，
使若干 rim 边长度为零而被跳过，于是只剩两条线）。

**下一步**：先把"`bladeAt(θ)` 与夹具有没有逐位一致"用一个独立探针钉住（打印两者的四个端点），
再决定是修正 `bladeAt` 还是修正 `sweptRegionFan` 的 apex 选取。**在那之前不保留这块 pane** ——
否则 `verify_windshield` 会红。

**已回退**：`make_wipefix.js` / `wipefix.obj` 恢复，离线全绿（60.00 / 50.00 度、销距守恒 0.000 µm、
verify PASS、注入故障 19/19、三个真车锚点逐字节不变）。
