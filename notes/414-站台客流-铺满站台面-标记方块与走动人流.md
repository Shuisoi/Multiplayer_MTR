# 414 站台客流：从「站台边那一排」铺到整个站台面（标记方块 + 走动人流）

日期：2026-10-10 ｜ 涉及：`engine/.../crowd/MmtrCrowd.java`、`engine/.../command/MmtrPlatformCommands.java`、
`game/.../mmtr/crowd/*`、`game/.../block/BlockCrowdMarker.java`、`game/.../render/RenderCrowdMarker.java`、
`mmtr/tools/crowd-marker/gen_crowd_marker_assets.py` ｜ 设计文档：`docs/01-设计/站台客流-村民实体与客量属性-设计.md`

## 起因（用户口径的两次修正）

1. 「村民只会在那一条站台方块上生成，但实际上是需要在那整个站台生成的」——
   旧实现把站台方块那一排当成人站的地方，**错**。
2. 「站台方块本身不能站人，所以外扩二格即可」+「分 2 级……1 级方块朝站台方向排队，未满时比例为 7：3；
   100% 时无论几级全站满」+「真的走来走去」+「透明方块（手持现形）……放在站台方块上以确认归属站台的方块」。

## 现场量的站台剖面（新工具 `sandbox/tmp/_platform_section.py`）

RCON 逐格问 `execute if block <x> <y> <z> minecraft:air`，把一条站台的横断面画成 ASCII。
上水村 x=900（东西向站台，所以剖面沿 z）：

```
     4567890123456789012      ← z 的末位（1794..1812）
  66 ...................
  65 SSSSP.........PSSSS     ← S 平滑石台面  P MTR 站台方块
  64 SSSSSSSSSSSSSSSSSSS
```

读数（**这一条量出来定死了整块几何口径**）：

- 两条轨在 z=1800 / 1806；**站台方块在 z=1798 / 1808**（离轨 2 格，靠站台那一侧）；
- 人站的那层地面在站台方块**后面**（z≤1797 / z≥1809），与站台方块同一高度（y=65 顶面）；
- 两条站台之间（z=1799..1807）在 y=65 是**空的**（轨道层），这正是"往轨道那侧扫要能停住"的物理依据。

## 做了什么

| 件 | 内容 |
|---|---|
| 自动区 | 站台方块**后面**第 1..`autoRows`（默认 2）格；每格要求"脚下同层实心地面 + 这一格没有碰撞箱" |
| 四种标记方块 | 一级 `crowd_mark_1` / 二级 `crowd_mark_2` / 流动 `crowd_flow` / 归属锚 `crowd_anchor`（一个方块实体类型，种类从方块状态反推） |
| 手持现形 | 方块 `getRenderType2 = ENTITYBLOCK_ANIMATED` + blockstate 空模型 ⇒ 平时看不见；拿着任意标记物时 `RenderCrowdMarker` 画贴地色块 + 矮柱 |
| 分配 | 未满 7:3；100% 两级全满；流动 = 客量% × 走道格；**上限截断时二级与流动各保底 2** |
| 走动人流 | `MmtrCrowdWalkers` 每 tick 驱动 `setPosition`，走道尽头掉头；走道按 (x,z) 两列索引 |
| 闸门 | 新增 `platform rows <0-8>`（自动区宽度）与 `platform force <on\|off>`（勘测模式：忽略玩家半径） |

## 四个坑（都实测踩过，别再踩）

### 1. 枚举"区块里的方块实体"扫不到任何标记

第一版标记扫描走的是"遍历站台周围已加载区块 → `WorldChunk.getBlockEntities()` → `instanceof BlockCrowdMarker`"。
**结果一个标记都没扫到**：`platform scan` 的"标记："那一行根本不出现（`markers.isEmpty()` 直接 return），
而被扫的方块实体确实存在（RCON `data get block 900 66 1795` 回 `{id: "mtr:crowd_marker"}`）。

没有再去追这条路的根因（映射层/加载器组合下的行为差异不值得为它花时间），改成**沿轨扫方块状态**：

- 与自动区**共用同一趟法线**：从站台方块往站台里数 1..12 格，每列看 3 层（`platformY..platformY+2`）；
- 地面高度一变就 `break` —— 往轨道那侧扫会自然停在轨道层，不会抢邻台的人流区（实测「抢格 0 次」）；
- 成本：220 格 × 12 列 × 3 层 ≈ 8 千次读方块，一个加载着的站台约 1 ms；而且**归属是确定的**
  （谁扫到归谁，记着离站台边几格），不再需要"最近站台方块"的距离启发式。

教训：**能用已经在用的读法（读方块状态）就用它**；为了省几次读方块去碰一个没验证过的 API，
代价是"功能完全不工作而日志里什么都没有"。

### 2. 走动人流一步都不走

`MmtrCrowdWalkers.reconcile` 第一版把「走道」设成了**这一拍选中的落点格**（受客量与上限裁剪过的）。
`cap=12` 时流动只有 2 个落点、彼此不相邻 ⇒ 每 tick 都判"下一格不在走道上"⇒ 掉头 ⇒ 原地不动。
RCON 连查 3 次位置一模一样（`2309.5, 76.0, 1812.5`）才抓到。

修法：**走道 = 整条流动标记铺出来的格**（不受裁剪），落点只决定"这一拍有几个人"。
`Selection` 因此同时带 `flowCorridor`（全走道）与 `flowTargets`（这一拍的人）。

附带一个同源坑：走道原来按**三维格**索引 —— 半砖/内缩站台上人会被重力放到格心下方一点，
`floor(y)` 与格坐标差 1 ⇒ 每 tick 都判"人不在走道上"⇒ 拽回格心 ⇒ 抽搐。改成按 **(x,z) 两列**索引。

### 3. 上限截断把二级与流动整类砍光

`cap=12`、候选 460 一级 + 20 二级 + 10 流动、客量 100% 时：按"先砍二级→再砍流动→最后砍一级"，
二级与流动被砍成 0 ⇒ 站台上只剩贴边那一排，**分级与流动全看不见**（而用户要的正是分级与流动）。

修法：**二级与流动各保底 `min(目标, 2)`**，缺口全从一级出（一级格最多，砍它损失最小）。
实测 `cap=12` 时读数变成 `应有 一级=8 二级=2 流动=2`，正好 12。

### 4. 阈值筛的人数不是"上限"，是二项分布

旧写法 `hash01(平台id, 格) < fraction`，`fraction = min(客量%, 上限/候选数)`：
220 格、上限 12 时实测铺出 **18** 个（均值 12、σ≈3.4，+1.7σ 很正常）。
上限是**客户端帧率的闸门**，必须硬。

修法：**按位置哈希排序取前 N 个** —— 既保持"挑哪几格由哈希决定"的随机散列外观，人数又精确等于目标。

1. **两轮几何都读错过**：第一轮把"内间距 5 格"读成"每门洞 7 格"（3+4），铺完用户才纠正"内间距 4 格、两红之间 2 格"

## 续：客量口径修正 + 走路速度 + 报告不再撒谎（用户 2026-10-10「村民数量没有增多」）

用户把 TEST 两条站台调成 **客量 50%** 之后说"村民数量没有增多"。读数印证了：
`platform scan` 报 `客量=50% ｜ 应有 一级=8 二级=2 流动=2`，与 100% 时**一字不差**。

根因不是客量没生效，是**口径把客量吃掉了**：旧代码算的是 `客量 × 全站候选格数`
（一级 300 + 二级 460 + 流动 180 = 940），50% = 470 人，而"单站台上限"当时是 12 ——
上限一咬住，客量 10% 与 100% 铺出来完全一样。上限是防客户端卡顿的闸门（用户口径，不能拿掉），
所以改的是**口径**：`人数 = 满员 × 客量%`，满员 = `platform cap`。

三处改动（都在 game 侧；服务端重启即生效，**客户端不用重开**）：

1. `MmtrCrowdModule.select`：新口径；走动人流份额 `FLOW_SHARE = 20%`（最小 2 只）；
   旧的"截断时二级/流动各保底 2 个"整段删掉（它只为旧口径服务）。
2. `MmtrCrowdWalkers.STEP`：0.045 → **0.09 格/tick**（1.8 格/秒）。原版腿摆幅是
   `min(4 × 每 tick 位移, 1)`：0.045 只给 0.18，正常走路是 ~0.4 —— 慢到那个程度
   FA 的走路动画几乎不摆腿，人看着像**滑行**而不是走。
3. `MmtrCrowdModule.report` 的"实有 流动"改成 `MmtrCrowdWalkers.summary().walkers()`：
   它原来读 `flowActual`，而那个 Map 存的是 `flowTargets.size()`（= **应有**）——
   一只走动村民都没登记上时，报告照样写"实有 流动=2"，排查"村民不动"时会把方向带偏。

闸门文件 `world/mtr/mmtr-crowd.properties`：`maxPerPlatform` 12 → **220**
（= 平台口径"每格一人 × 220 格"，与 `platform list` 自己报的"≈110人"同一个满员基准）。

实测（服务端重启后 ｜ cap 220 ｜ 客量 50%）：

| 项 | TEST 1 | TEST 2 |
|---|---|---|
| 应有 / 实有 | 一级 62 ｜ 二级 26 ｜ 流动 22 = **110** | 同左（逐位一致） |
| 走动 | 登记 22 只（落点 22）｜ 22 只合计位移 382 格 ⇒ **1.8 格/秒** ✓ | 同左 |
| 现场实体 | `@e[tag=mmtr_crowd]` = 220（176 站定 + 44 走动） | — |

**教训**：闸门（上限/半径）与"客量"同时存在时，读数必须能自答"改了客量，人数为什么不变" ——
现在那句自答就是报告末尾的"（满员 = 单站台上限 N 人）"。

## 续 2：只认标记 —— "村民乱站，在无标记位置也站"（用户 2026-10-10）

用户看着 50% 的站台，指出村民**站在没有标记的格子上**。

根因：候选格是 **自动区 ∪ 标记**（同一格标记优先），而自动区是"站台方块后面那 2 排"沿轨连续取的，
它把标记**没画到**的格子也补成了候选（算一级）。对着 TEST 站台的账逐项验：

| | 值 |
|---|---|
| 标记画的一级 | 180 格（30 个门洞 × (z0 与 z0+3) × 3 排） |
| 自动区补的无标记一级 | **120 格** = 30 个门洞 × 门洞内 2 格 × 自动区 2 排 |
| 报告里的"候选 一级" | 300 = 180 + 120 ✓ 逐项对得上 |

也就是说：**门洞内那两格**（两片门叶之间，标记没铺）被自动区当成了人流区，人站在那里看着就是"乱站"。

修法（`Plan.candidates()`）：**这条站台只要有标记，就只认标记** ——
候选 = 标记格，自动区整段不参与；一个标记都没有时才退回自动区（`platform rows`，0 = 彻底不自动铺）。

- 改前：`候选 一级=300`；
- 改后：`候选 一级=**180**`（= 标记数），`实有 = 应有 = 62/26/22`、`多出 = 0`、`漂移 = 0` ⇒ 全部人都在标记格上。

副作用（写进设计文档了）：**一格遗留标记就会让整条站台变成"只认标记"**。上水村 1/2 站台上有早期试验留下的
20 个二级 + 10 个流动标记，于是它们的候选只剩那 30 格（客量 100% 也只站 30 人）。
要么把那些格子敲掉回到自动区，要么就给它们正经铺一遍标记。

顺带这一次也把"自动区"恢复成默认 `platform rows 2`（有标记的站台不再受它影响）。



## 续 3：削成"没有碰撞箱的人形贴片"

用户口径："**村民导致帧数暴跌，我们也不需要这个村民有什么碰撞箱，能不能简化一下**"。

先量了一下（同一机位、TEST 两条站台、F3 读数）：

| 状态 | fps | GPU |
|---|---|---|
| 0 只 | 113–118 | — |
| 220 只 | 68–83 | 61% |
| 220 只但全部 Invisible:1b | 72–77 | **14%** |

**隐身不掉帧**、GPU 反而空下来了 ⇒ 瓶颈不是"画模型"，是**每只实体的固定开销**（几百只挤在一起，
原版每只每 tick 都要跟周围上百只做两两碰撞求解，每次还要新建候选列表）。所以这一版砍的就是这条：

- MmtrCrowdVillagers#simplify：NoAI / Silent / Invulnerable / PersistenceRequired / 速度清零 /
  名字设成不显示的 mmtr_crowd（客户端认身份用 —— 命令 tag 不同步给客户端）；
- MmtrCrowdEntityMixin（Entity#isCollidable）+ MmtrCrowdLivingEntityMixin（LivingEntity#canHit、#isPushable）
  一律返回 false，挂在 mtr.mixins.json 的 **mixins** 段（两侧都装）；
- **故意不用 
oClip = true**：它把方块碰撞也关掉，人会被重力穿过站台面掉下去（"站在地板上"要靠它）。

验证：:fabric:compileJava 通过（refmap 解析到 Entity.method_30948 / LivingEntity.method_5863 / method_5810）；
服务端重启后实查 NBT：CustomName = "mmtr_crowd"、NoAI = 1b、Silent = 1b；
crowd scan 仍是 应有 = 实有 = 62/26/22（每条站台 110 只），走动 22 只照走（5038 tick / 453 格）。

⚠ **客户端要重开一次**：碰撞箱这件事有一半在客户端（客户端本地算"我能不能穿过他"），
不重开客户端就只有服务端那一半生效。


## 续 4：帧率真的怎么救 —— 逐格人流半径 + EMF 的 LOD 三键

用户口径（2026-10-10）："帧数 50，不行，正常帧数 100 多" → "有一定提升，但还需要更加激烈"。

### 先量清楚钱花在哪

同一机位测过三组：客流 0 只 = 113–118fps ｜ 220 只 = 68–83fps ｜ **220 只全设 Invisible:1b = 72–77fps**
（GPU 从 61% 掉到 14%）。第二、三组几乎一样 ⇒ **贵的不是"画模型"**；
而按"进入视锥的实体数"算，每多一只 ≈ **0.06–0.1 ms/帧** —— EMF 要为每只村民做一整套自定义模型 +
动画处理（FA 的 optifine/cem/villager.jem + illager_animations.jpm，包里确实有），
这笔钱按"进渲染循环的实体数"付，跟最后画不画无关。

### 三档手段（按"掉不掉观感"排序）

1. **EMF 的动画 LOD 三键**（掉细节不掉模型，观感基本无损）：
   nimationLODDistance: 20 → 6（**每 N 格开始跳帧，越小越省**，tooltip 原文）； 
   
etainDetailOnLowFps: true → false（这项**开着**时低于 60fps 会**撤掉降级保细节** —— 越卡越保，
   正好把人锁在 50fps）；
etainDetailOnLargerMobs: true → false（同上，按体型再撤一次）。
2. **逐格人流半径**（掉的是"远处有人"，观感正常）：platform radius 从"整条站台"口径改成**逐格**，
   platform radius 32 ⇒ 只有玩家周围 32 格内有实体。这是数量级的那一刀（176 只 → 几十只）。
   实现见 MmtrCrowdModule#select：populate 之后对三个候选表 
emoveIf(!hasPlayerNear(...))。
3. **让村民整个不吃 EMF/FA**（掉的是村民自己的 FA 细节 —— 但**必须模型+纹理一起关**）：
   EMF modelsNamesDisabled: ["villager","villager2"] **只关模型**会让 FA 的 illager.png
   按旧 UV 画 → **村民没眼睛**（用户当场："这帮村民都没眼睛，十分恐怖"）。真要关，还得同时关纹理：
   ETF propertiesDisabled: ["villager"]，这样村民是**原版**样子（有眼睛、有群系配色，只是没有 FA 细节）。

目前的组合：**1 + 2**（FR 模型保留、modelsNamesDisabled: []），第 3 档留作最后手段。


## 续 5：定案 —— 110+ fps，且**人数与视距一个都没砍**

用户口径（2026-10-10）："**不要对视距以及村民数量进行限制，站台上该多少就多少**" → 于是逐格半径那条撤回
（platform radius 512 = 闸门等于关，恢复"整条站台该多少就多少"），改从**单只成本**下手。

### 最终配方（实测 50 → **110+ fps**，客流 176 只全在）

| # | 位置 | 设置 | 为什么 |
|---|---|---|---|
| 1 | EMF 配置 | modelsNamesDisabled: ["villager","villager2"] | 村民**不再走** FA 的自定义模型+动画管线（那才是贵的那笔：每只进视锥的村民约 0.06–0.1 ms/帧） |
| 2 | 自建资源包 |

| 3 | ETF 配置 | propertiesDisabled: ["villager","cem/villager"] | 不再吃 FA 的 illager.properties（随机纹理/眨眼那套） |
