## 1. 方案 B 是什么，为什么不能是方案 A

区间是"**某一行车方向**下的一段路"，所以双向线路上同一根轨的南行与北行**各有一个区间**，
两者在空间上**重叠**（现场实测：被区间覆盖的 96 根轨里 **62 根属于 2 个以上区间**，最多 5 个）。
把它们画在同一条线上根本分不开，所以：

**把同一个方向的所有区间沿轨的**法向**偏移一段固定距离** —— 两个方向自然成两条并排的带，
每条带再被**它自己方向的灯**切成一段一段。这正是现实里双向区间的样子（分界点两架背靠背的灯，各管一个方向）。

**偏移量按"方向"定，不按"第几条"定**（这一条是本轮的关键决定）：
按出现顺序编号（第一条 +5、第二条 −5）会把**同方向的多个区间**分到两条带上，
看图的人会误以为它们是两个方向。按方向定则天然自洽：南行永远在法向一侧、北行永远在另一侧，
重叠的区间落回同一条带并**叠色**，一眼看出"这里区间重叠"。

## 3. 顺手修掉的一处**正在发生的破损**

控制台一直在读 `node.block`（"这个节点所属的那个区间"）。引擎刚把那个字段**删掉**（notes/157），
所以旧代码拿到的是 `undefined` → 文案显示错、`isUnguardedBlock` 判错。

改法：节点的区间**由 spans 推**（不是引擎发），判据与引擎"灯贴着节点就算守这个节点"同一条口径 ——
**空间容差**（3 m，引擎是 4 m 减去端点取整余量），因为网页拿不到轨的弧长（`Rail` 只给两端坐标与采样点）。
于是节点文案变成"**N 个区间：…**"，多值本来就是双向线路的常态。

## 4. 那两条纯函数为什么要单独测

方案 B 的整个"两个方向各占一条带"就靠 `sideOfDirection` 与 `offsetPath`，而它们在组件里**渲染不了也断言不了**。
所以抽成纯函数（`domain/sectionBands.ts`），用项目既有的 `node --test` 链路测 5 条：

| 用例 | 钉住的判据 |
| --- | --- |
| 相对的方向落在相反的侧 | 南(0)/北(180) 必须不同侧；东(270)/西(90) 必须不同侧 —— 否则两条带重叠 |
| 同一方向（含浮点误差与非正方向）落在同一侧 | 0.0001 / 179.9 / 359 / −90 / 450 全部归位正确 |
| 偏移是法向的 | 水平折线偏移后 x 不动、y 整体平移（否则带子会斜着离轨，看起来像另一条线路） |
| 偏移量与方向成比例 | +5 与 −5 分居两侧、是两条不同的线 |
| 退化输入不产生垃圾路径 | 空折线/单点返回空串；**重复点不产生 NaN**（零长度段的除零） |

`npm test` 现在跑两条链（`test:plan` + `test:bands`）。

### 5.1 一个必须说明的部署顺序风险（本轮已经处理）

**`dist` 是由引擎直接从磁盘发的**（`MMTR_WEB_ROOT`），所以"**换网页不需要重启引擎**"。
这意味着刚才构建完的那一刻，网页已经是新版、而引擎还是 16:22 那版 **没有 `direction` 字段**。
如果网页直接去读 `section.direction.angle`，渲染里会抛异常 → **整张地图白掉**。

所以加了 `hasDirection()` 守卫：区间没有方向就**不画这一层**（跳过），别的图层照常。
上面那条"[通过] 旧引擎下区间层被跳过"就是这条守卫的实测证据。

**部署顺序因此自由了**：可以先上网页（区间层空着、其余照常），再停机换引擎（区间层自己出现）。
但**不能反过来长期停留**在"引擎新、网页旧"：旧网页读不到 `blocks` 字段，区间图层会空。

### 5.2 踩到的一个坑（记下来，免得下次又花时间）

无头 CDP 检查里**不要 `Page.enable`**。开了之后 CDP 会把事件（`frameNavigated` / `loadEventFired`…）
与命令响应混在同一条 WebSocket 上，而"一问一收"的简化客户端会把**事件当成响应**读走 ——
症状是后续 `Runtime.evaluate` **全部返回空值**，看起来像"页面没渲染"，其实是读错了消息。
本轮为此白跑了几轮定位。现在这个脚本只用 `Runtime.evaluate`（一问一收，干净）。
