# 224 右下角速度读数栅格化 —— 「绘图也太粗糙了吧」，顺带逮到两个真缺陷

承接 notes/223（右下角速度读数）。用户看完离线出图后一句 **「绘图也太粗糙了吧」**。
这一轮表面上只是"把图画好看"，实际做下来发现粗糙只是第一层，下面还压着两个**功能缺陷**。

---

## 1. 粗糙的根因：拿 MC 的矩形原语拼图

第一版的实现是纯 MC 原语：

| 元素 | 第一版画法 | 问题 |
| --- | --- | --- |
| 圆（限速牌、AWS 灯） | 逐行矩形条拼 | 边缘全是台阶，**零抗锯齿** |
| 楔形（背景） | 逐列矩形条拼 | 同上，斜边是锯齿 |
| 数字 | MC 字形放大 4 倍 | 字体图集是 1× 烘的，放大就糊 |

所以"粗糙"不是画得不够小心，而是**这条链根本没有抗锯齿**。改法不是继续修像素，而是换链：
仪表面板（BR101 `mmtr_hud_*`）早就在用 Java2D 栅格化（`MmtrPanelCanvas`），把它拿来画整幅即可。

改动：

- `MmtrSpeedHud.paint(canvas, speed, limit, aws, screenWidth, warnColour)`：整幅只碰
  `MmtrPanelCanvas`，**不碰任何 MC 类型** ⇒ 离线探针可以直接调它出 PNG。
- `MmtrPanelCanvas` 新增：`createExactPixels`（按设备像素建画布）、
  `textItalic(text,x,y,heightM,shear,colour,hAlign,vAlign)`（绕**各自墨迹中心**错切，
  这样"逐位中点固定"在斜体下依然成立）、`textWidth(text,heightM)`。
- `render()` 按**签名**缓存（速度/限速/AWS 状态/闪烁相位/尺寸/缩放率），只在变化时重绘，
  每帧只画一个 quad —— 与驾驶室仪表盘同一套路。

证据（同一段代码离线出图，624×312）：

| | 半透明像素（抗锯齿） | sha256（前 12 位） |
| --- | --- | --- |
| 第一版（矩形拼） | **0** | — |
| 这一版 | **85845** | `f5caa70c9ee1`（无告警那张；告警那张含闪烁相位，哈希每次不同） |

## 2. 真缺陷 A：限速牌的数字撑出白面

限速牌是红圈 + 白面 + 黑字。第一版给数字一个**固定**墨迹高（14），三位数（"100"/"120"/"160"）
量出来 33 宽，而白面可用宽只有 `2 × (13 − 3) × 0.92 = 18.40` ⇒ 数字直接压在红圈上。

第一版修法是"量一次、按宽度等比缩一次"。**这不够**：宽度对字号并不严格线性（AWT 会把字体尺寸取整、
字距也按像素取整），实测 100/120/160 缩到 8.69 号后真实宽度 **18.73**，仍然 > 18.40 ——
也就是说"用户看到的数字压圈"其实**没被修掉**。

改成**反复量-缩**（`fittedInkHeight(maxInk, boxWidth, widthAtInk)`，签名从"一个宽度数"改成
"量宽度的函数"）：每轮量真实宽度、按比例缩，最多 8 轮，单轮收缩 <0.1 或触到保底字号 6 就停手。
同一批限速值现在是：

```
限速  60：字号 12.87 → 墨迹宽 18.28 / 可用 18.40
限速 160：字号  8.33 → 墨迹宽 16.56 / 可用 18.40   ← 第一版是 8.69 号 / 18.73（溢出）
```

## 3. 真缺陷 B：斜边把数字"切"了一道

楔形是按用户口径画的：直角在屏幕右下角、底边 = 屏宽 20%、斜边与底边夹角 30°。
问题是**算术上就不存在**能装下 208×104 横长条读数的 30° 楔形：要让数字块左上角（x≈83，y≈44）
落在斜边内侧，底边得长约 209 单位 ≈ 整个画布宽，那时楔形已经退化成矩形。

实测（854 宽）就是：速度的 **"0" 上半截落在斜边外 ⇒ 白字压透明白底，字被切掉一截**。

修法：背景取 **楔形 ∪ 读数底板**（底板 = 内容包围盒 + 6 单位留白，右/下顶到画布边）。
两个形状都是半透明的 `0xB8101418`，**分两次画会在重叠处叠深、沿斜边露出一道可见的接缝**，
所以并集算成**一个多边形、一次填充**（`backgroundOutline`，`fillPolygon` 走 `Path2D` 非零环绕填充，
非凸多边形也正确）。四个分支就是两个形状互相包含的全部情况：

| 条件 | 背景轮廓 |
| --- | --- |
| `plateLeft ≤ x0` 且 `W ≤ plateTop` | 纯矩形（楔形整块在底板里） |
| `plateLeft ≤ x0` 且 `W > plateTop` | 底板 + 右上角斜边冒出来的那块 |
| `plateLeft > x0` 且 `yAtPlateLeft ≥ plateTop` | **纯楔形**（底板整块落在楔形里，形状没被改） |
| `plateLeft > x0` 且 `yAtPlateLeft < plateTop` | 底板 + 左下角楔形的尖（+ 右上角那块） |

## 4. 过程教训：上一轮"改完出图没变化"是幻觉

上一轮我改完限速字号后重新出图，**PNG 的哈希和像素统计与改动前一模一样**，一度怀疑逻辑没生效。
真因是**类路径上有旧类**（`sandbox/javac-out` 里上一次编译的 `MmtrSpeedHud.class` 排在前面）。
这一轮把这件事做成机制，不再靠猜：

1. 探针开头打印 `MmtrSpeedHud` 的加载来源：完整的 class 文件路径 + 修改时间 + 字节数。
2. 每张 PNG 打印 sha256。
3. 离线跑法固化成脚本 `sandbox/run-speed-hud-probe.ps1`（先全量 `javac` 到 `sandbox/javac-out`，
   再编译探针到 `sandbox/probe-out`，探针输出用 UTF-8 免乱码）。
4. 用例也离线跑：`sandbox/RunJUnit.java` 用 `junit-platform-launcher` 手写入口，
   jar 从 Gradle 缓存里取（**必须排掉 `*-sources.jar`** —— 上一版 `Select-Object -Last 1`
   正好挑中 launcher 的 sources jar，javac 去编译它的源码、报了一屏 `org.jspecify` 找不到）。
   这样**不用 Gradle、不用关游戏**也能拿到 JUnit 结论。

## 5. 回归：第一次真的贴图，就把 `drawTexture` 的参数写错了

改成贴图那一天，用户立刻反馈 **「UI 不在右下角了」**。

真因：`GuiDrawing.drawTexture(double×4, float×4)` 的四个 `double` 是**两个角**
`(x1, y1, x2, y2)`，**不是** `(x, y, w, h)`。我按"位置 + 尺寸"填了后两个槽位：

```java
// ✗ 写错（这一版）：四边形从 (854−208, 480−104) 一路拉到 (208, 104)
guiDrawing.drawTexture(width - HUD_WIDTH, height - HUD_HEIGHT, HUD_WIDTH, HUD_HEIGHT, 0, 0, 1, 1);
// ✓ 写对：两个角
guiDrawing.drawTexture(width - HUD_WIDTH, height - HUD_HEIGHT, width, height, 0, 0, 1, 1);
```

于是整块 HUD 被摊成 438×272 的反向四边形、斜着铺到屏幕中上部。

**为什么编译期抓不到**：8 个参数全是 `double`，尺寸和坐标同一类型，写错只是数字。
**为什么这一轮的验证没抓到**：探针验的是"画布里的内容长什么样"（栅格化、字号、暗底），
**没有验"这张贴图贴到屏幕的哪里"** —— 前者在离线可测，后者只有进游戏才看得见。
（顺带一句：上一版的 HUD 是用 MC 图元直接画在屏幕坐标上的，根本没有贴图，所以这个错是新引入的。）

**怎么定位的**：`javap -c` 反编译 mapping 层的 `GuiDrawing.drawTexture`，
四个顶点是 `(x1,y1) (x1,y2) (x2,y2) (x2,y1)`，**中间没有任何减法** ⇒ 四个 double 就是两个角；
上游调用点也印证（`RailwaySignScreen`：`drawTexture(x, y, x + size, y + size, …)`）。

**修法与判据**：贴图矩形抽成纯函数 `screenQuad(screenWidth, screenHeight)`，
用例 `theHudQuadIsPinnedToTheBottomRightCorner` 钉住"尺寸 = 画布尺寸 / 右·下边缘齐屏 / x1<x2、y1<y2"。
red-proof：把旧写法塞回去，用例当场失败（`屏 320：宽度必须是 208 ==> expected: <208.0> but was: <96.0>`）。

## 6. 验收

```
格心检查    368 项，违规 0    （格心与数字无关、步长 = 格宽、整块宽恒定）
限速牌检查   26 项，违规 0    （含"台阶模型"：一次估算缩不够、迭代后真实宽 18.00 ≤ 18.40）
楔形检查     20 项，违规 0    （底边 20%、夹角 30°、竖边装得下、随屏宽单调）
版面检查     23 项，违规 0    （真实字体：数字/单位不重叠、7 个限速值的墨迹都塞进白面）
暗底覆盖    2×7 点，缺底 0    （像素级：底板四角 / 数字块角 / 图标行角都压在背景上）
MmtrSpeedHudTests：8/8 通过（含 backgroundOutline 四分支 + 贴图四边形钉在右下角）
客户端编译：437 源 / 643 类 OK
```

`暗底覆盖` 这条是这一轮新加的**像素级**判据：它不看几何函数、直接在出图后的画布上采样，
所以"斜边切字"这类"几何算得对、画出来不对"的缺陷会被它挡住。
但**贴图落在屏幕哪里**仍属于"只有进游戏才看得见"的一类 —— 只能靠 `screenQuad` 这样的
纯函数 + 用例把坐标算对，不能靠离线出图。

## 7. 留待用户定的审美项（都不影响正确性）

- 底板左上角是直角、左下角带楔形的尖，看上去像"带斜尾的面板"；也可以换成四角都切角。
- 底板/楔形的透明度（现在 0xB8 ≈ 72%）与是否要描边。
- AWS 灯现在是"深色环 + 实心圆"，真实机车是分格向日葵盘。
- 速度数字要不要做阻尼/平滑（现在直接跟 `vehicle.getSpeed()`）。
