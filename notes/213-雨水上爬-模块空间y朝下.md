# 213 · 「雨滴还是往上掉落」的真因：这个模块的 +y 是朝下的

日期：2026-09-21 · 车辆：BR101 V25（v54 包）/ saf101（MMTR_NewStock_v1）· 结论：**`panelDown()` 的"世界 y 为负 = 下坡"整个反了；正确值是 `(right.y, up.y)`**

## 1. 症状与它为什么拖了三轮

用户三次报同一件事：「雨还是从下往上的」→「雨滴在往上反重力运动」→「**雨滴还是在往上掉落**」。
中间我做了一次"修正"（去掉 `flip`，并加了一句"下落方向的世界 y 必须为负"），**那次修正让情况更糟**：
它把 cab 1 从"向下"改成"向上"，而 cab 2 本来就是向上。所以"还是"是真的。

前两轮之所以没找到，是因为我一直在**同一个未验证的前提**上推理：以为 `panelDown()` 用的那个 `.y()` 是世界意义的"上"。
它确实不是 —— 而这个工作区里没有任何一处代码/注释把这件事写下来过。

## 2. 真因（一句话）

**锚点 JSON 是模建者按 y 朝上写的；`Plane.of` 用 `toModelSpace(x,-y,-z)` 把 y 镜像了一次；
所以这个模块工作的空间里 +y 指向地面。** 于是"下坡 = 世界 y 为负"应该读作"下坡 = 此空间 y 为正"。

## 3. 证据（都是文件里手写的事实，不是推断）

| 量 | 值 | 含义 |
|---|---|---|
| `seat_1.up`（BR101，存储空间） | `[0, 1, 0]` | 座椅的"上"是 +y ⇒ **存储空间 y 朝上** |
| `hud_1.y` vs `windshield_1_1.y`（BR101） | `2.661 < 3.020` | 仪錶台在玻璃中心**下面** ⇒ 存储空间 y 朝上 |
| `hud_1.y` vs `windshield_1.y`（saf101） | `2.764 < 3.762` | 同上，第二辆车独立复现 |
| 客户端日志 `plane.position` | `(0.606, -3.02, 8.986)` | `= toModelSpace(存储值)` ⇒ **模块空间 y 与存储空间相反** |

另外两条旁证：水层/雨刷**落点是对的**（说明 (right, up) 基与渲染空间一致，只是 y 轴方向相反），
以及 `seat_1.up=[0,1,0]` 在模块空间变成 `[0,-1,0]`（玩家不可能倒着坐）。

**判据用仪錶台，不用座椅**：saf101 的 `seat_*.up = [0,-1,0]`（作者写反了），而它的 hud 在玻璃下方。
位置关系是物理事实，手写的 `up` 可以写错 —— 所以 `verify_plane_frame.js` 的新检查以 **hud 在玻璃下方** 为权威判据，
座椅只作辅助。

## 4. 量出来的方向（`sandbox/_down_direction_check.js`，真实锚点）

| 雨水面 | 锚点 `up` 实际指向 | 旧 `flip` 版 | **212 的"修正"版（实机在跑）** | 修正后 `(right.y, up.y)` |
|---|---|---|---|---|
| windshield_1_1 / 1_2 | 真·上 | 下 ✓ | **上 ✗** | 下 ✓ |
| windshield_2_1 / 2_2 | 真·下（绕线翻转） | **上 ✗** | **上 ✗** | 下 ✓ |
| saf101 windshield_1 / 2 | 真·上 | 下 ✓ | **上 ✗** | 下 ✓ |

`verify_plane_frame.js` 现在每块都打印实测值：BR101 real-vertical **−0.651**、saf101 **−0.959**（负 = 下坡）。

**为什么这条公式能同时喂饱绕线相反的两块玻璃**：`(right.y, up.y)` 是"真实下落向量"在该玻璃平面
**自身基底**下的投影系数，投影与基向量的正负号无关（平面没变）。旧 `flip` 是"把结果锁死在画布 −y"的
180° 旋转，只在"锚点 up 恰好指向真实上方"时碰巧对 —— BR101 正好只有 cab 1 是这样的。

## 5. 那条"守卫"为什么是假的

```java
final double worldY = alongRight * plane.right.y() + alongUp * plane.up.y();  // = -(right.y² + up.y²)
final double sign = worldY < 0 ? 1 : -1;                                      // 恒为 +1
```

把 `alongRight/alongUp` 本身又代回去，得到的永远是一个负数平方和 —— **它证明不了任何事，也永远不会翻转**。
这和同轮删掉的 `fallWorldY`（`-(right.y²+up.y²)/mag`）是同一种错：**用待验证的量去"验证"自己**。
（教训写进本笔记：判据必须是**独立的**物理事实，比如仪錶台在玻璃下面。）

## 6. 改动与门禁

- `MmtrWindshield.java` `panelDown()`：`(-right.y, -up.y)` → **`(right.y, up.y)`**；注释里写出上面两张表的证明。
- `verify_plane_frame.js`：必需模式改为 `alongUp = plane.up.y();`；**禁止**旧的镜像投影 `alongUp = -plane.up.y();`
  与旧的 `flip`；新增 `checkRainDirection()`：以仪錶台/座椅锚点判定"哪边是上"，再逐块断言落地方向**不得朝上**。
- `selftest.js`：**新增两条注入**（镜像投影回来、旧 flip 回来），证明守卫有牙。
- 结果：`verify_plane_frame` BR101/saf101 全 PASS（方向全为负）；**`selftest 34/34`**；
  `check-java-compile` OK（432 源 / 633 类）；`:fabric:classes` OK。
- **纯客户端**：包不用重打（`options.txt` 仍指 `BR101_v54.zip`），但**要重启客户端**才生效。

## 7. 横向教训

1. **坐标系的 y 方向必须先量出来再用**，不要从"这是渲染空间所以 y 朝上"推。一行锚点数据就能定它。
2. **判据要独立**：拿 `down` 自己算出来的量去校验 `down`，只会得到一个永远成立的句子（本例两次）。
3. 一处符号错可以被另一处符号错"部分抵消"（旧 `flip` 在 cab 1 上碰巧对），于是症状看起来时好时坏 ——
   遇到"还是"这种复现，先怀疑**上次的修正本身**。
