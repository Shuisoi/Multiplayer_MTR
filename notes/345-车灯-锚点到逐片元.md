# 345 · 车灯：从 `mmtr_light_*` 锚点到逐片元光源（实现记录）

日期：2026-09-28 · 承接 notes/338（渲染管线）→ 339（别人怎么做）→ 340~344（光场 + AO）

用户诉求两句话：**"MTR 原版的车灯不能真的照明"**、**"不能重烘（粒度为格，视觉体验大打折扣）"**。

结论：车灯做成 **逐片元的光源**（现代引擎的做法），不做任何"往世界里放光"的事。
见 §1 的四条候选与为什么只剩这条。

## 1. 为什么不是"重烘"（四条候选的裁决）

| 做法 | 粒度 | 代价 | 裁决 |
|---|---|---|---|
| 往世界放隐形的 `minecraft:light` 方块 | **一格**（16 级整数场，锥边方块状） | 每次移动重烘区块网格 | ❌ 用户否决：不平滑 |
| OptiFine / LambDynamicLights 式"改建网格时的光值" | 同上（还是烘进几何） | 同上 | ❌ 同一族 |
| 动原版光照贴图 `Sampler2` | — | — | ❌ **物理上不可能**：光照贴图只是"光级→颜色"的一维渐变表，16×16 里没有空间信息，同光级的表面共享同一个纹素 |
| **片元里按世界坐标现算** | 连续（锥形 smoothstep + 距离衰减 + N·L） | 纯 ALU，零 draw、零重烘、零世界数据 | ✅ **选它** |

**关键一句**：平滑不来自"采样更细"，来自**把光变成函数而不是数据**。
车厢那一半 notes/344 已经做过了（光场：逐片元、按世界坐标取光、draw call 不变）；这一篇做的是车灯。

> 顺带记：地形（道床/隧道壁/站台）走原版 `rendertype_solid` 那一族，**本次不覆盖**。方案见 §6。

## 2. 契约：`mmtr_light_<驾驶室>_<第几盏>`

| 几何量 | 语义 |
|---|---|
| 面中心 | 灯罩中心（车体局部坐标） |
| **面法线**（顶点绕序决定） | **光射出的方向** |
| 面尺寸 `widthM/heightM` | 灯罩大小 |
| 第 3 个数字 `<n>` | 这一端的**第几盏**（纯序号，不决定强弱 —— 见下） |
| 驾驶室编号 | **1 = A 端 = −Z**（与 `mmtr_hud_1` / `mmtr_windshield_1_1` 同一约定，实测三者都在 z≈−9.7） |

**实测（2026-09-28，`saf420cab.obj`）**：车头是**左右两盏一模一样的方块灯罩**，
每盏 0.26 × 0.26 m，中心 `x=±1.020, y=1.580`，外表面 `z=−9.780`（法线 `(0,0,−1)`，朝 −Z）。
⇒ 这一条**推翻了我最初拟的"n=1 主灯、n≥2 弱标志灯"约定**：两盏一样的灯按那个规则会变成一亮一暗。

**所以强度按灯罩面积算**（基准 = 上面那 0.26 m 灯罩 = 0.0676 m²，夹在 0.35~1.8 倍之间）：
面积是**模型自己带的意图**，将来加一颗小标志灯不用改命名规则就自动更弱。
`index` 只用于日志与将来逐灯控制。

- 锚点面**会被打包器剥掉**（纯数据，不进渲染几何），只进 `mmtr_anchors_<id>.json`。
- **可见的灯罩**照旧是普通 MTR 部件（`headlights` 组 + `renderStage: ALWAYS_ON_LIGHT`）——
  一个组只能有一个 renderStage，所以"发光"与"照明"是两件独立的事，两者都要有。
- 打包器侧只改了三处：`ANCHOR_KINDS`/`RESERVED_ANCHOR_KINDS` 加 `light`、结构化命名正则加 `light`、
  导出 `"index": n`。客户端 `MmtrVehicleAnchors` 加 `Kind.LIGHT` + `Anchor.index` + `findLights()`。

### 2.1 ★ 陷阱一：法线朝里（hud/windshield 的绕序不能照抄）

实测 SAF420 的现役锚点：
```
hud_1            normal [0, 0.5, 0.866]      ← 朝司机（+Z，指向车尾）
windshield_1_1   normal [0, 0, 1]            ← 也是 +Z
seat_1           normal [0, 0, -1]
```
hud / windshield 的法线**朝车内**是**故意的**（面板、雨层都画在朝司机那一面）。
灯锚点要是照抄这个绕序，光就射进车厢、车头前面一点不亮 —— 而**打包、进游戏、日志全都正常**。

所以判据不能写死 `-Z`：`verify_lights.js` 的 L2 用**"法线必须背离车心"**（`dot(normal, 径向) ≥ 0.2`），
两个端通用。反了就在配置里加 `flipAnchorNormalByGroup: ["mmtr_light_1_1", ...]`，或回 Blender 改绕序。

### 2.2 ★ 陷阱二：A/B 端串号（头尾车是同一个 OBJ 打两遍）

10 节编组的头尾控制车**不是两个模型**，而是同一个 `saf420cab.obj` 打两遍：
- `saf420cab_a`：`rotationDegY: 0`，锚点按作者命名（`_1`）
- `saf420cab_b`：`rotationDegY: 180`（几何烘到另一端）+ **`groupRename` 把 `_1` 改写成 `_2`**

漏掉灯的改名，B 车就会带着"自称 cab1、却长在 z=+7.99"的灯锚点：几何没错、光也照出去了、
**打包器与所有现役校验都报 PASS**，只有驾驶室编号是错的（见 §4 的实测对照）。

**做法**：给 `groupRename` 加了**通配符**支持 —— `"mmtr_light_1_*": "mmtr_light_2_*"` 一条覆盖任意数量的灯
（`renameGroup()`：精确优先，其次通配符按"更具体的先匹配"，值里的 `*` 用键里 `*` 匹配到的内容替换）。
理由：显式表会在"下次再加一盏灯"时静默漏掉，而这正是最贵的一类错。

**mod 侧其实不依赖这个编号**：前照灯/尾灯是按**几何**判的（`dot(灯朝向, 行进方向)`），
所以反着挂的车也自动朝对方向。编号是为了"这条规则只写一处"（`nearestCab`、驾驶室进入、日志）不漂。

## 3. 实现：一帧里发生了什么

```
RenderVehicles.render（每个会被画的车节）
  └─ MmtrHeadlights.requestCar(vehicle, carNumber, absoluteCarPositionAndRotation)
       ├─ 惰性开帧：帧号取 MmtrLightField.frameId()；**在收集的那一刻读真相机**
       │    （不能放进光场的 beginFrame —— 那个钩子在 MainRenderer 的最后，比收集晚一整段）
       ├─ 锚点 → 世界：position = carPosRot.transformForwards(anchor.position, rotX, rotY, add)
       │                direction = anchor.normal.rotateX(pitch).rotateY(yaw)
       ├─ 端：engineEndOfSeat(anchor.position.z())（车体局部 +Z = 引擎的 B 端）
       ├─ 档位：镜像的 mmtrLightA / mmtrLightB + 换向器 ⇒ MmtrLightSwitch.lampState
       │    （**这一段 2026-09-29 换了判据**：原来按"逐帧位置增量"猜行进方向，停着不动只能含糊；
       │      现在是用户口径的"每个驾驶室一个开关 + 换向器 N 固定红"，见 notes/352）
       └─ 只留"射程+64 格"内的，按离相机距离排序取前 8 盏
每帧的 draw（VertexAttributeState.apply() → MmtrLightField.onDrawState）
  └─ MmtrHeadlights.uploadForCurrentProgram()   ← program 已绑定；每个 (帧, program) 只传一次
       uniforms: mmtrHeadlightCount / Pos[8](xyz+1/射程) / Dir[8](xyz+cos外锥) / Color[8](rgb+cos内锥)
       （**地形那一侧上传时跳过尾灯候选**，2026-09-29，notes/352）
片元（mmtr_vehicle_light.fsh）
  └─ color.rgb += mmtrHeadlightTerm(mmtrRelWorld, mmtrWorldNormal, albedo)
```

- **覆盖范围**：只加在**我们自己的 program** 里 ⇒ 它画什么就照亮什么 = **车厢 + 3D 钢轨**。
  车灯照亮车头前方的钢轨，正是"隧道里看得见"的那一半。
  **世界方块（道床/隧道壁/站台/草/水）当时不在范围内 —— 2026-09-29 已补上，见 §7.20。**
- **反照率取在乘光照贴图之前**（`mmtrAlbedo`）：灯照亮的是车漆本身；乘过光贴图再乘就是自乘，暗部永远提不亮。
- **加法而不是替换**：光场那条路取不到数据时会退回 per-draw 光，车灯照旧生效。
- **遮挡**：本版**没有**。灯不会被车体/墙挡住（世界方块遮挡要另接 §6 的实心位图 ray march）。
  射程默认 40 m 把"穿到后面几节车"压到可接受；这是已知边界，不是疏忽。
- **阴影 pass**：`RenderVehicles` 在阴影 pass 里也会收集，但那份列表只影响颜色，对深度没有影响。

### 3.1 开关（`run/mmtr-lightfield.properties`，改一行 2 秒生效、不用重启）

```properties
headlights=true            # 车灯总开关
headlightMode=auto         # auto=按灯光开关档位 | all=全当白前照灯 | off=全灭（后两个是诊断档）
headlightLux=1.0           # **夜间**档的白灯强度（日间 = 它 × headlightDayRatio）
headlightDayRatio=0.45     # 日间档相对夜间档的强度比（notes/352 新增）
headlightRangeM=40         # 主灯射程（米）
headlightConeDeg=14        # 主锥半角（这里是满强度）
headlightPenumbraDeg=26    # 外锥半角（半影到 0）；比主锥窄会被自动纠正
headlightTailLux=0.22      # 尾灯强度（尾灯**不进地形那一侧**，只在车厢附近）
# headlightAmbiguous      # 已废弃（notes/352）：判据换成"开关档位 + 端 + 换向器"，写了会点名一次
```
`lightfield.enabled=false` 会**连车灯一起**关掉（同一个 program），这是设计使然。

### 3.2 诊断（每 5 秒一行）

```
[MMTR-LIGHT] 车灯：画到的车=2 锚点=4 候选=4 上传=4/8 灯光=A端=夜间 B端=尾灯 | saf420cab_a#0 mmtr_light_1_1 端=B 档=夜间 世界=(...) → 夜间 lux=1.00 射程=40
```
**"灯不亮"这行里一眼可拆**：是开关在关闭 / 是这一端没设 / 还是 program 没注入（`光影车灯=…`、`地形=…` 在同一行）。
模型有锚点但一盏灯都没有时也会说一次。

1. **遮挡**：灯不被车体或墙挡住。要接的话，用**已经在 GPU 上的实心位图**（notes/344 §14.1 的 `solidTex`，

## 6. 让地形也吃车灯（**已实现** —— 见 §7.20）

> ⚠️ 下面这份是**动手前的方案**，其中"覆盖原版 `rendertype_solid` 一族"那一半**已被实测推翻**：
> dev 客户端装着 Sodium 0.5.8，区块整体走 **Sodium 自己的** program，原版那一族根本没被用到。
> 保留原文是为了记录当时的推理链；**以 §7.20 为准**。

地形走原版 `rendertype_solid` 一族，要单独覆盖一份 program。已核实的三个事实（都在 1.20.4 字节码里）：

1. **世界坐标是白送的**：`rendertype_solid.vsh` 里 `vec3 pos = Position + ChunkOffset;`，而
   `WorldRenderer.renderChunkLayer` 每个 chunk 每次 draw 前算的是
   `chunkOffset.set((float)(origin.getX()-camX), ...)` ⇒ **`Position + ChunkOffset` 就是相机相对世界坐标**。
   `ModelViewMat` 在这条路上是纯视图旋转。⇒ notes/344 §8~§10 在 MTR 那条路上踩的 `ModelMat`/`IViewRotMat`
   三个坑，**这条路上一个都不适用**。
2. **`in vec3 Normal` 本身就是世界法线**（ChunkOffset 只是平移，几何不带旋转）。
3. 光照贴图 `Sampler2` 只能给出"光级→颜色"，**表达不了"哪里被车灯照到"** —— 所以地形也必须走片元现算。

落地要点：把 `assets/minecraft/shaders/core/rendertype_solid.{json,vsh,fsh}` 复制进 mod 资源、
加两个 varying + 同一份 `mmtrHeadlightTerm`、JSON 里补 Sampler3/4/5（光场的 LUT/图集/实心位图）、
并在绑定这个 program 时上传同一组车灯 uniform（本版的上传点在 MTR 的 draw 上，地形要另挂一个）。
**风险面比 MTR 那份大**（全世界的方块都走它），且要实测 Sodium 是否用同一批 program ⇒ 单独一轮，单独一篇笔记。

## 7. 实机落地：Blender → OBJ → 包（2026-09-28 完成）

### 7.1 在用户**开着的会话里**做（不跑无头）

本会话的工具列表里没有 Blender MCP 工具，但插件本身就是个**空字节分隔 JSON** 的本地 TCP 服务，
所以桥可以直接用：`sandbox/blender_call.ps1` 把 `{"type":"execute","code":<python>,"strict_json":true}`
发到 `127.0.0.1:9876`，代码在 Blender 主线程执行。用户明确要求"不要无头"，这条路正好满足：
**改的是他屏幕上的场景，不是磁盘上的副本**。

> 桥的实现：`%APPDATA%\Blender Foundation\Blender\5.2\scripts\addons\mcp\mcp_to_blender_server.py`
> （模块 docstring 就是协议说明）。**`strict_json` 是必需字段**，漏了会报
> "sent a request without the required 'strict_json' boolean key"。

做法（`sandbox/br_make_lights.py`）：**复制灯罩的"射出面"当锚点** —— 遍历 `headlights` 里法线朝 −Z 的面，
按 X 正负分左右各取面积最大的一个，把它的**顶点坐标连绕序一起**拷进新对象。
这样"法线朝外"不是靠我摆对，而是**继承自模型自己那一面**；再整体前移 5 mm 免得视口 z-fighting。

- **左右顺序**：`_1 = +X`、`_2 = −X` —— 与本模型既有的 `mmtr_cabdoor_1_1`(x=+1.356)、
  `mmtr_wipersweep_1_1`(+X 侧) 同一个约定。
- **`headlights` 可见组原封不动**（16 顶点 / 12 面，两个 0.26 m 方块灯）：发光是它，照明是锚点。
- 独立回读验证（`sandbox/br_verify_lights.py`，另一条读路径）：13 项全 PASS。

### 7.2 导出：必须**原地导出**

`wm.obj_export` 的 `path_mode='AUTO'` 只在**导到模型自己目录**时才把贴图写成相对的 `map_Kd saf420.png`；
先导到 `sandbox/` 试的那一份写成了 `C:/Users/.../saf420.png` —— 仓库禁止字面路径，贴图解析也会坏。
轴向取 `forward_axis='Y', up_axis='Z'`（= notes/192 的恒等口径）。

**覆盖正式 OBJ 之前逐组对账**（`sandbox/compare_obj_groups.js`，用 `lib.js` 同一个解析器）：

```
顶点总数: 旧 11807 -> 新 11815          （+8 = 两个四边形）
只在旧里有的组: （无）
只在新里有的组: mmtr_light_1_1, mmtr_light_1_2
共有组的包围盒差异（超过 1 mm 才报）: （无：所有共有组的面数与包围盒逐位一致）
```
⇒ 这次导出相对旧 OBJ **只多了那两个锚点**。备份：`saf420cab.obj.bak-before-lights` /
`saf420cab.mtl.bak-before-lights` / `saf420.png.bak-before-lights2`。

### 7.3 ★ 顺带修掉一个**一直误判**的校验（`mmtr/scripts/pack-vehicle.ps1`）

那一步 zip 校验原来写死要求 `assets/mtr/<id>/<id>.obj` 与 `<id>.mtl`。**但打包器写的是
`assets/mtr/<id>/<源文件名>.obj`** —— 实测现役的 `SAF420_v4.zip` 里就是
`assets/mtr/saf420cab_a/saf420cab.obj`，而 `mtr_custom_resources.json` 声明的也正是
`modelResource = "mtr:saf420cab_a/saf420cab.obj"`。所以 `vehicle.saf420cab_a.json` 这条**一直报
"PACK FAILED: zip validation failed"**（只有源文件名恰好等于 id 时才碰巧通过 —— 早先的合成夹具就是
这样，所以它掩盖了这个缺陷）。

改成**真正的判据**：读回包里的 `mtr_custom_resources.json`，逐条核对声明的
`modelResource / textureResource / modelPropertiesResource / positionDefinitionsResource` 是否真的在 zip 里
（`minecraft:` 开头的原版贴图跳过），外加"id 目录下至少有一份 OBJ / MTL / PNG"的形状检查。
名字怎么起都不再影响判定，而"游戏找不到资源"这一类仍然会被拦住。

### 7.5 ★★ 实机翻车一次：A/B 端**镜像**，而我的判据跟着一起错

用户进游戏换包后的反馈：**"头尾两节 CAB 的朝向错了，但灯是亮的"**。

**症状与数据**（用现役 v4 当裁判，v4 是游戏里朝向对的那份）：

| | v4（对） | v8（错） |
|---|---|---|
| `saf420cab_a` `hud_1` / `seat_1` | 文件 z = **+9.312 / +8.172** | z = −9.340 / −8.200 |
| `saf420cab_b` `hud_2` / `seat_2` | 文件 z = **−9.312 / −8.172** | z = +9.340 / +8.200 |

**逐项镜像** ⇒ 整列车的车头车尾反过来。

**根因链**（三条都对上，缺一条都推不出来）：

1. 锚点 JSON 里的 x/y/z 是**文件空间**；客户端用 `MmtrVehicleAnchors.toRidingSpace` 转成**骑乘空间**：
   `(x, y, z) → (−x, y, −z)`（**z 取负**）。
2. "这是哪一端"由 `engineEndOfSeat(seatZ)` 按**骑乘空间** z 判：骑乘 z > 0 = 引擎 B 端 = 驾驶室 2。
3. ⇒ 换到文件空间：**cab 1 ⇒ 文件 z > 0**，cab 2 ⇒ 文件 z < 0。
   而作者空间的约定是"驾驶室1 在 −Z"，所以 **A 端车必须 `rotationDegY: 180`**（把作者空间的 −Z 烘到 +Z），
   **B 端车 `rotationDegY: 0` + `_1→_2` 改名**。这正是 v4 的组合；v8 把两者对调了（而 v8 从没打出过包，
   所以这个错一直没被看见）。
4. **`verify_lights.js` 的 L4 我写成了"cab1 ⇒ 文件 z < 0"** —— 漏了第 1 条那个取负。更糟的是我的合成夹具
   也是照这条错规则造的，于是**判据与夹具同错、互相印证、给我自己那份镜像的包放行**。
   这与 notes/344 §9.1 的教训同型：**判据的覆盖范围 = 它验证的东西**；夹具必须来自"已知对的现役数据"，
   不能来自我对规则的记忆。

**修法**：`consist/saf420.json` 与 `example/vehicle.saf420cab_a.json` 的 `rotationDegY` 改回
{A 端车 180 / B 端车 0 / 拖车 180}（并在配置里写了 `_orientationNote`，免得下次又被"顺手翻正"），
L4 规则改成"cab1 ⇒ 文件 z > 0"并写清推导与 v4 证据，重打为 **`SAF420_v9.zip`**。

**验收判据**（比"看着对"硬）：把 v9 的锚点与 v4 **逐项对账** ⇒ 两节 CAB 的
`cabdoor/hud/seat/windshield/wipersweep` **朝向不一致项 = 0**（法线 z 完全相同），
位置有 **+0.028 m 的统一偏移** —— 那正是 v8 把 `recenter` 从 `true` 改成 `false` 的已知差异（见 `_recenterNote`），
不是朝向问题。灯锚点：A 车 `light_1_*` cab1、骑乘 z=−9.785（引擎 A 端）；
B 车 `light_2_*` cab2、骑乘 z=+9.785（引擎 B 端）；两端法线都朝车外。

**顺带一条结论**：车灯**不需要跟着改** —— 前照灯/尾灯是按"灯朝向 · 行进方向"的**几何**判的，
不认驾驶室编号，所以镜像的包里头灯照样亮（用户的"灯是亮的"正好是这个设计的实测证据）。

### 7.6 换成 v9 后"前挡风玻璃不透明了" —— 是**贴图 alpha 没被任何面采到**，不是包的问题

排查顺序（全部是测量，没有一步靠看）：properties 逐行对账 → MTL 对账 → 包内 OBJ 的几何规模
→ 贴图 alpha → 玻璃面实际采到的纹素。

| 测的东西 | 结果 |
|---|---|
| `properties_saf420cab_a.json`：v4 vs v9 | **逐行一致**，只多一条 `headlights`（ALWAYS_ON_LIGHT）⇒ 不是 renderStage |
| MTL：v4 vs v9 | 一致（`saf420_mat` + `map_Kd saf420.png`，另有空壳 `door_mat`） |
| 包内 OBJ 顶点数 | v4 **32019** / v9 **33241** ⇒ v4 是 9/24 的老模型，两边本来不是同一个几何（别用几何对账当判据） |
| `saf420.png`（当前） | 2048²，**只有 9216 个像素非全不透明**（0.22%），且**全部 alpha=40**，集中在 u 0.5000..0.5464 / v 0.3442..0.3906（96×96） |
| 旧 `.bak-before-uv` 贴图 | 128²，**25% 全透明**（一整块透明象限） |
| 玻璃面采到的 alpha | `interior` 车头面 **258/258 个角全是 255**；`cab_body` 车头面 5032/5032 也是 255 |
| 谁采了那块 alpha=40 的区 | **没有任何面**（唯一"无 UV"的是两个新灯锚点，而它们的面会被剥掉） |

**机制**（两条路都堵上了）：

1. 旧的 128² 贴图有一整块**全透明**象限，而当时模型**没有 UV** ⇒ 打包器的 `untexturedUv`
   （v4 是 `(0.125,0.5)`，正好落在那块透明区）让玻璃角采到 alpha=0 ⇒ **玻璃是透的**（不是因为 UV 对）。
2. 现在模型做了 UV，车头 `interior` 面被 UV 在 **u 0.000–0.250 / vt.y 0.188–0.261**（贴图左下角，全 alpha=255）；
   而那只有 96×96 的 alpha=40 玻璃区**没有任何面指向它** ⇒ 玻璃按不透明画。
   配置里的 `untexturedUv` 现在是**无关项**（可见面全都有 UV）。

**要做的（建模/UV 收尾，不是我这一侧的改动）**：把前挡风那批面 UV 到那块 alpha 区里。

⚠️ **判据的符号踩过一次坑（2026-09-28 当天就修）**：采样公式是 `像素行 = (1 − vt.y) · H`，
所以"要落进像素行 1248..1343"对应的 OBJ 值是 **`vt.y` 0.3442..0.3906**。
我第一版给的"`vt.y` = 1 − v = 0.6094..0.6558"是**它的补数** —— 那会把玻璃导到贴图另一半。
同一个坑在"谁采了这块区"的扫描里又犯了一次（把 `1 − vt.y` 与 v 区间比），结论一度是错的
（"没有任何面采到"）。**修正后的结论才有了解释力**：

| | 采到的 alpha | 结果 |
|---|---|---|
| **40 个 `interior` 面**：x ±1.45、y 1.85..2.85、z −9.3..**+8.1**（贯通全车的**侧窗**） | 40（落在玻璃区） | **透明 ✓**（与"别的玻璃是透明的"完全吻合） |
| **车头 63 个面**（含前挡风）：UV 在 u **0.0000..0.2495**、vt.y 0.1880..0.3809 | 255 | **不透明 ✗** —— `u` 落在了错误的**列**（玻璃区在 u 0.50..0.55） |

⇒ 所以修法很具体：**把前挡风那批面搬到 u 0.50..0.55 那一列**（vt.y 0.3442..0.3906 内），
侧窗已经在里面了，说明用户本来就是这么用的。判断"哪些面是玻璃"的现成依据：
`mmtr_windshield_1_1` 锚点的矩形 = x ±1.275、y 2.05..3.25、z −9.725。
（B 端车是同一个模型，同样要修。）

**教训**（与 §7.5 同型，一天里第二次）：**凡是"v 翻转"这类跨口径的判据，写完必须拿一个"已知结果正确"的
现成数据去校准**（这里就是"侧窗透明、前挡风不透明"这一对事实）——否则判据与自己造的夹具会互相印证，
而这个错误在数字上看起来永远是对的。

### 7.6.1 修好了（2026-09-28）：一个面的 UV，改到与其它窗同一个纹素

**最终机制**（在**打包后**的 OBJ 上才看清）：这个模型的玻璃不是"靠 alpha 区铺满"，而是
**所有窗子都塌到同一个纹素点 `(0.52319, 0.36743)`**（那块 alpha=40 区里），
而**前挡风是唯一一个还留在 u 0.00–0.25 那一列（不透明）的面**。

- 起因：v4 时代模型**没有 UV**，打包器把"无 UV 的角"指向 `untexturedUv`，
  而当时那张 128² 贴图有一整块**全透明象限**，(0.125,0.5) 正好落在里面 ⇒ 看起来是透的。
  换成 2048² 的新贴图后 `untexturedUv = (0.5,0.5)` 采到不透明纹素 ⇒ 症状出现。
- 修法（`mmtr_light_1_1/_1_2` 那次同一套桥手法）：在用户开着的 Blender 里，把
  `interior` 的 **poly 211**（前挡风，x ±1.273、y 2.052..3.249、z=−9.675）那 4 个 loop 的 UV
  设成**从"已经透明的那批面"里读出来的同一个点**（不硬编码 ⇒ 不会自己发明约定）。
- 守卫（全过）：全部 UV 取指纹 → 改 → 再取，**实际只动了 4 个 loop**；玻璃区面数 40 → 41；
  Blender 里直接按游戏口径采贴图，前挡风 4 个角 = **RGBA(0.7686, 0.8314, 0.8784, 0.1569)**，
  与侧窗参照**逐位相同**（alpha 0.1569 = 40/255）；导出后逐面比对：顶点数不变、组不变、
  包围盒逐位一致、**UV 变化的恰好 1 个面**；包内复检：前挡风位置 12 个三角面里
  **面 11/12 = 玻璃点**；v10 与 v9 的锚点 JSON **逐字节相同**（只动了 UV）。

**又一条判据教训**：我先前在**源 OBJ** 上扫"谁采到玻璃区"，只数到 40 个面，于是错误地得出
"没有任何面采它"。在**打包后**的 OBJ 上一数：**4686 个角**都在那个玻璃点上（= 全车其它窗子）。
**判据要在游戏真正消费的那份数据上数**（打包器会去焊接、三角化、并且用 `untexturedUv` 顶替无 UV 的角）；
在作者文件上数，覆盖范围可能完全不同。

最终包：**`SAF420_v10.zip`**（`consist/saf420.json` 的 `packName`）。

### 7.7 玻璃独立材质（2026-09-28，用户定的方向：以后要有独立玻璃逻辑）

**做法**：玻璃不再靠车体图集里那一小块 alpha 区，而是**自带材质 + 自带贴图**。

- 玻璃面 = UV 落在玻璃区的面（用户既有约定，也等价于"采样 alpha<255 的面"）：实测**只有 `interior` 的 41 个面**
  （40 个侧窗 + 前挡风那 1 个；其中有 n 边形窗，41 个面共 1644 个 loop）。
- 新材质名 **`interior_translucent`**：MTR 的 OBJ 路径靠 **MTL 材质名**决定 shader 类型（notes/338 §5.3），
  这个名字 → `TRANSLUCENT_BRIGHT`，与它原先挂在 `interior` 部件下拿到的语义一致，但**贴图与车体图集解耦**。
- 新贴图 **`saf420_glass.png`**：64×64 均匀色块，字节 = 旧图玻璃区的字节 **(196,212,224,40)**
  ⇒ 换材质后**视觉零变化**，但以后改玻璃只需要动这一张小图。
- 41 个面的 UV 指向新图中心；导出后 MTL 里是两个材质（`interior_translucent→saf420_glass.png`、
  `saf420_mat→saf420.png`），包内 OBJ 里 `usemtl interior_translucent` 保留 ✓，v11 与 v10 的锚点逐字节相同 ✓。

**这一步里我犯的两个错（都靠"另找一个独立判据"抓回来）**：

1. **色彩空间做了两次转换**：我把 Blender `image.pixels` 读出的 (0.7686,0.8314,0.8784) 当成了**线性值**，
   又转了一次 sRGB 写成 (227,235,241)。它其实就是 `196/255, 212/255, 224/255` = **旧图玻璃区的 sRGB 字节**。
   校准判据：**用 PIL 直读旧图那 96×96 的原始字节**（游戏吃的就是字节），一比就露。教训与 §7.5/§7.6 同型：
   **判据必须有一个本体系之外的来源**（这里是 PIL 直读像素，而不是 Blender 的浮点像素数组）。
2. **导出静默丢了整个车壳**：OBJ 导出**只写可见对象**，而用户当时为了看内饰把 `cab_body` 隐藏了 ⇒
   那一次导出 v 11815→4975、34 组→33 组、1.37 MB→0.49 MB，而"导出成功"照样报。
   （所以包里会是**一辆没有外壳的车** —— 又一个"操作成功 ≠ 结果正确"。）
   修法：`sandbox/br_export_real_safe.py` —— 导出前记录并**临时取消隐藏**、导出后**原样还原**，
   并在导出后**校验组数 = 34 且 cab_body 在**。这一条对所有"从活动会话导出"的场合都适用。

**顺带观察**（不是本次改动）：MTL 里还有一个**没有 `map_Kd` 的空壳材质 `door_mat`**（15 个 `usemtl`），
即客车门那批面没有自己的贴图。

（从而能有自己的 renderStage / condition，例如雨刷只作用于前挡风、开门时窗玻璃跟着动），
还需要在 Blender 里把玻璃拆成**独立对象**（如 `glass`），并在配置里给一条 `groupMap` + `partSpecs`。

### 7.8 "从外向内不行、挡风玻璃不透明" —— 前挡风**缺了朝外的那个面**

用户反馈：**"从内向外没问题，但从外向内不行"**、**"挡风玻璃不透明"**、**"有破面"**。
（我第一反应是"单向面被剔除"，用户回"不是，是材质不对" ⇒ 于是把三条都拿数据验一遍。）

**先排除两条**：

| 假设 | 判据 | 结果 |
|---|---|---|
| 非平面多边形在 ear-clip 三角化时"破面" | 逐面算到最佳拟合平面的最大偏离 | `interior` 46 个 n-gon **全部 < 2 mm**、`cab_body` 也 0 ⇒ **不是** |
| 我换的材质名改变了混合方式 | notes/338 §5.3 的反汇编结论：**优先级 = `properties.json` 的 renderStage > MTL 材质名 > CUTOUT** | 玻璃面仍属 `interior`（INTERIOR_TRANSLUCENT）⇒ **材质名不改变混合**；贴图又与旧图那块**逐字节相同** ⇒ 这一步不可能造成"从外看不透" |

**测出来的真因**（41 个玻璃面的位置/法线逐面列表）：

- 40 个**侧窗面是成对的**：同一扇窗有 `x=1.400` 法线朝内 + `x=1.450` 法线朝外两个面 ⇒ 内外都看得见。
- **前挡风只有 1 个面**（四边形，法线 **+Z 朝内**）⇒ 从外面被背面剔除，你看到的是"洞 + 驾驶室里同样被剔除的内饰"，
  又暗又像破面。**40 个成对 vs 1 个单面**，这就是"从内向外没事、从外向内不行"的全部差别。

**修法**（照模型自己的约定补齐）：复制前挡风那一个四边形 → **反绕序** → 同材质、同 UV。
改动量：`interior` 面数 **1072 → 1073**、玻璃面 **41 → 42**，新面法线 `(0,0,1) → (0,0,-1)`；
导出后逐组对账：**只有 `interior` 面数 +1**（顶点 +4），所有组包围盒逐位一致、锚点逐字节不变。
包内复检：玻璃材质 **782 朝内 / 782 朝外**，前挡风位置 **2 个 (0,0,−1) + 2 个 (0,0,+1)** ✓。

**仍然开放**：用户截图里那串**镜像的 "SAF 420"**（内壁采到外皮涂装）属于 §7.6 那条 UV 问题 ——
车壳内外两面共用同一套 UV。修法是给**内表面**单独一块 UV 岛（素色或内装区），与本次玻璃改动无关。

### 7.9 ★ 反面结论：**不要在同一个部件内部拆材质**

用户反馈：**"在车外往内看看不到 `interior` 物体"**（从里面正常，从外面整个内装看不见）。

这正是 §7.7 那一步（把 41 个玻璃面在 `interior` **内部**换成第二个材质 `interior_translucent`）造成的。
机制：§5.3 已经写明一个 OBJ 部件在引擎里是 **`MaterialGroup(shaderType, texture)`** 组织的 ——
**一个部件基本就是一套材质/贴图**。在同组里混进第二个材质，贴图解析就落到整个部件上

- `interior` 材质槽 `saf420_mat | interior_translucent` → **`saf420_mat`**；42 个玻璃面 material_index 退回 0，
  1648 个 loop 的 UV 回到车体图集里的玻璃点 `(0.52319, 0.36743)`；空槽 pop 掉。
- 与 **v10 状态**（`.bak-before-glassmat`）逐组对账：顶点 +4、**只有 `interior` 面数 1072→1073**（就是那个朝外面）、
  所有组包围盒逐位一致；`usemtl` 只剩 `27× saf420_mat`；锚点与 v12 逐字节相同。

**想要"独立玻璃逻辑"的正确路线**（下次做）：**拆成独立对象**（= 独立部件），而不是同组换材质 ——

### 7.13 ★★ 实测推翻 §7.2 的一半：**这个 MTR 版本一个模型只吃一张贴图**

> **⚠ 本节结论已被 §7.14 部分推翻**：真正的原因是"**车辆优化路径只做 cutout（实心/丢弃），半透明混合没生效**"，
> 而**不是**"一个模型只吃一张贴图"。玻璃其实一直在用自己那张贴图（"淡蓝色" =(196,212,224) 就是它自己的颜色）。
> 那两次洋红测试之所以"没变洋红"，是**测试本身失效**（切换时模型/ModMenu 开关状态没跟上）——
> 教训升级：**一次测试只能证明"在它当时那个状态下"的事，切换类测试必须先确认状态真的换了**。

**症状**：前挡风从外看不透明、"玻璃和 interior 一个颜色"，而且 v11～v16 关于玻璃的改动**全都"一样没区别"**。

**一锤定音的测试**（不再靠读代码推）：把 `saf420_glass.png` 临时换成**不透明洋红**（v17；并留 `saf420_glass.png.good`），
包内核对确为洋红 ⇒ **车窗与前挡风仍是原来的暗色，没有变洋红**。

⇒ 玻璃面**没有采它自己那张贴图**，而是在采 **OBJ 旁边那张 `saf420.png`**（= 一个模型一张贴图）；
MTL 里第二个材质的 `map_Kd` 被忽略。而玻璃的 UV 是 `(0.5,0.5)` ⇒ 在车体图集上正好是**深灰 (70,74,80)**
⇒ 于是"前挡风不透明"、"和内装深色部分同色"、"怎么改都没变化"三件事一次讲通。

**结论（作为坑记下）**：
- notes/338 §7.2 的"**一个模型可以有多种材质 → 多张贴图**"**在本版本实测不成立**；
  但材质的**名字**仍然有用（§5.3：MTL 名 → ShaderType），所以第二个材质不必删。
- **判据要能一锤定音**：想知道"到底在采哪张贴图"，就把那张贴图换成**不可能认错的颜色**；
  从 MTL 反推（我前面 v11～v16 就是这么推的）会一路错下去。

**修法（v19）**：玻璃 UV 退回**车体图集那块透明玻璃区** `vt (0.52319, 0.36743)`（v9/v10 实测透明可用），
**但保留独立 `glass` 部件**（独立 renderStage/部件逻辑仍在，只是共用图集）。
守卫：逐组对账面数与包围盒逐位不变、UV diff **恰好 `glass` 42 面**、`body/interior/glass/headlights` 四个部件
的 renderStage 都在、雨刷恢复 `wiper=true`、`anchors/hud/rider` 与 v16 逐节相同 ✓。

`LIGHT_2` 层双面绘制，但**只有正在刮或正在下雨时才会画**（连续干燥后会清空水滴）；
用 v18（洋红玻璃 + 关掉两个雨刷）实测，前挡风**依然暗** ⇒ 不是叠加层，就是上面那条贴图问题 ✓。
（v18 的锚点 JSON 只改了 `windshield.*.wipers[*].wiper`，`anchors`/`hud`/`rider` 逐节对账相同 ✓。）

### 7.14 ★★★ 真相：车辆优化路径是**"实心或丢弃"**，半透明混合没生效

用户的两个关键观察把机制钉死了（都在**只有玻璃贴图 alpha 不同**、其余完全一致的两版之间对比）：

| 玻璃贴图 | 结果 | 读法 |
|---|---|---|
| α = 40/255 = 0.157 | 玻璃**不透明**（淡蓝实心；ModMenu 的 `hideTranslucentParts` 开或关都一样） | 被当 **cutout** 画：α > 0.1 阈值 ⇒ 直接写实心 |
| α = 0 | 玻璃**消失**（窗户成洞），并且**在车内隔着窗户能看见动物**（开关开或关都一样） | α < 0.1 ⇒ 被 **discard** ⇒ 洞 |

⇒ **`TRANSLUCENT_BRIGHT` 那档在这条路径上没有给出 alpha 混合**（若是混合，α=40 应半透、动物应一直可见）；
实际表现完全是 cutout。这与 MTR 官方车"窗户什么都不放"的设计互相印证。

**由此得到的可用做法**（v21，`SAF420_v21_glassalpha0`）：
玻璃贴图 **α=0**（颜色保留 (196,212,224) 作参考）⇒ 玻璃=洞 ⇒ 车内能看见外面（含动物）✓、
车外能看见内装 ✓。**独立 `glass` 部件仍然保留**（自己的材质/贴图/部件都在，将来要真玻璃只需改这一张图或走 mod 侧）。

**关键坑（本轮踩到）**：**配置层删不掉几何** —— 把 `glass` 从 `groupMap`/`partSpecs` 里删掉之后，
包内 `properties_*.json` 里确实没有 `glass` 部件了，但**游戏里玻璃照画**（回落成默认档 = EXTERIOR/不透明）。
原因：**MTR 会给 OBJ 里每一个组都建部件，`properties.json` 只是覆盖它列出的那些名字**。
⇒ 想"移除"某个组只能**从模型里删几何**，或在**贴图上让它被 discard**（本轮用的正是后者 ✓）。

**关于"在车内看不到外面的动物"**：相机在车内时，玻璃（cutout 实心）把后面画的实体一起挡了；
地形之所以看得见，是因为地形在车辆**之前**就画完了。α=0 之后动物恢复可见 ✓
（第三人称相机在车外时本来就不隔着玻璃 ⇒ 一直能看见 ✓，这也正是当初排除"实体程序 ModelMat"错判的那条观察）。

### 7.15 ★ 真半透明玻璃：**Blender 建锚点 + mod 画混合层**（分工不变）

**结论（回答"能不能在 Blender 里画半透明玻璃纹理"）**：
- **能画**：alpha 通道、渐变、污渍都能画，贴图也会被正确打包 ✓
- **但拿不到混合**：OBJ 优化路径是 cutout ⇒ α>0.1 实心、α<0.1 丢弃（§7.14 实测）✗
- ⇒ 半透明必须来自**另一条绘制通道**，而这条通道 mod 侧已经有了 ✓

**实现（第一版：前挡风）**：
- 新增 `render/glass/MmtrGlass.java`：读 `run/mmtr-lightfield.properties` 的
  `glass` / `glassArgb`(AARRGGBB，默认 `0x28C8E0F0` ≈ 16%) / `glassOffsetM`，**2 秒热重载**（与光场同一套节流写法）。
- `MmtrWindshield.drawGlassTint(...)`：在**挡风锚点**上画一个覆盖整块面板的四边形，
  走 `QueuedRenderLayer.EXTERIOR_TRANSLUCENT_DOUBLE`
  ⇒ 底层 `MoreRenderLayers.getExteriorTranslucentDoubleSided` = `RenderLayer.getEntityTranslucent`
  = **半透明 + 无背面剔除**（源码注释就写着 "one quad is visible from both sides" ✓）。
  **第一版我用了 `LIGHT_TRANSLUCENT`（= `getBeaconBeam(tex, true)`）—— 那一层有背面剔除**，
  实测症状：**只有车内能看到玻璃颜色，车外看不到** ✗（四边形朝向驾驶室，车外那一面被剔除）。
  教训：**画双面面板要选"无剔除"的层**，别照抄相邻功能（水膜用 DOUBLE 层正是因为要双面 ✓）。
- **必须画在天气状态机之前**：`MmtrWindshield.render` 里在"干燥且雨刷归位"时会 `continue`
  （`DRY_FORGET_MILLIS` 那一段）⇒ 挂在雨刷里的话，天一晴玻璃就消失 ✓
- **图层顺序天然正确**：枚举里 `LIGHT_TRANSLUCENT` 排在 `EXTERIOR_TRANSLUCENT_DOUBLE`（水膜/雨滴）之前
  ⇒ 玻璃先画、水膜后叠 ✓

**分工**：面板的**位置/尺寸/朝向**来自 Blender 里建的锚点（`mmtr_windshield_*`，无需新增 ✓），
**颜色/不透明度**由 mod 画 ⇒ "建模在 Blender、混合在 mod" ✓。

**下一步（侧窗）**：侧窗现在还是"α=0 的洞"（官方车风格 ✓）。要同样给侧窗真玻璃，需要
Blender 里加 `mmtr_glass_<cab>_<n>` 锚点（每个窗格一个四边形），客户端补
`Kind.GLASS` + `findGlass(...)`，再复用同一套 `drawGlassTint` 逻辑（锚点数量多，建议先做前挡风验证观感）。

**更新命令备忘**：改 Java 后 —— `mmtr/scripts/check-java-compile.ps1`（编译到 `sandbox/javac-out`）
→ 把 `sandbox/javac-out/*` 拷进 `mmtr/game/fabric/build/classes/java/main`（游戏读的是这个目录）
→ **重启客户端**（Java 不能热重载）；之后调颜色/透明度只需改属性文件（2 秒生效）✓

### 7.16 ★★ 前挡风之谜的真正收尾：`interior` 里那块**不透明的挡风板**

用户发现（关键）：**`interior` 里有一块挡风玻璃，`glass` 里也有一块**。量出来是这样：

```
interior  顶点=4  法线z=-1.00  x -1.274..1.274  y 2.051..3.248  z -9.725..-9.725  u 0.0152..0.2343 v 0.2107..0.2354
glass     顶点=4  法线z=+1.00 / -1.00（内外两面）            z -9.675..-9.675  u/v = 玻璃点
```

- 那块面在 **z=−9.725（车头最外皮那一层）**、**法线朝车外**、采样图集里的深色区 —— 它**压在玻璃前面**。
- 从**车外**：它是最先命中的面 ⇒ 前挡风是**一块不透明深色板**（这正是用户最早那句"挡风玻璃不透明"）。
- 从**车内**：它朝 −Z、背对驾驶员 ⇒ 被剔除、完全看不见 ⇒ **"从内向外没问题"**。
- 也解释了**洋红测试为什么无效**：洋红玻璃在它**后面**，永远露不出来。

**它是怎么漏过我前面的筛面的**：它紧挨着我修过 UV 的那块（**poly 210 = 它，poly 211 = 内面**），
而我当初是按"**UV = 玻璃点**"筛面的 ⇒ 只带走了 211，210 用的是**我修 UV 之前的老 UV**，所以留在 `interior` ✓。
⇒ 教训：**按 UV 筛面会把同一位置、不同 UV 的"兄弟面"漏掉**；筛完必须再按**几何位置**复核一遍
（本轮就是这么复核出来的：`sandbox/windscreen_leftover_probe.py` 按矩形 + 法线列面 ✓）。

**修法**：在 Blender 里删掉它（判据：4 顶点、整幅宽 |x| 跨度 ≥ 2.0、y 2.0..3.3、|z| ≥ 9.70、|法线 z| ≥ 0.9）
—— 边框条（法线 z≈0）保留 ✓。守卫：报告逐个待删面（对象/顶点数/包围盒/法线）、删后 **`interior` 1031→1030**
（只 −1）、逐组对账其余组**逐位不变** ✓、一步可撤 ✓。（作者模型只有一个驾驶室，B 端由打包时旋转同一份几何得到
⇒ 只需删一处 ✓。）

**侧窗**目前仍是"α=0 的洞"。若要同样给侧窗真玻璃，需在 Blender 里加 `mmtr_glass_<cab>_<n>` 锚点（每窗格一个四边形），
客户端补 `Kind.GLASS` + `findGlass(...)`，复用 `drawGlassTint` 同一套画法（见 §7.15）。

### 7.17 ★★ 玻璃的最终形态：**完全由 Blender 导出的 OBJ + 那张贴图决定**

用户定的方向（§7.15 之后）："需要在 Blender 中建模透明玻璃以及半透明材质，实在不行修改 MTE 渲染器"、
"需要完全由 Blender 导出的 obj 和其贴图文件决定"、"给窗户加一圈贴近现实的黑边"、"我没在 Blender 画，你来画然后导出"。

**链路（三层，各自只做一件事）**：

1. **Blender（作者/我）**：`glass` 对象 = 玻璃几何；它的 **UV 展开到整张贴图 (0,0)-(1,1)**；
   贴图 `assets/models/blender/saf420cab/saf420_glass.png`（**256×256**）：
   外圈 **10 px 近黑 (16,16,18,255)** ⇒ 窗框、再 **3 px (60,62,66,255)** ⇒ 边框过渡、内部 **(196,212,224,40)** ⇒ 半透明玻璃。
2. **打包器**（`tools/obj-mtr-packager/pack_vehicle.js` 的 `buildGlassPanes()`）：读**暂存 OBJ**（去焊接 + 三角化后那份），
   只取 `glass` 组的三角形，**两两配成四边形**（要求 4 个不同顶点、四角 UV 构成轴对齐矩形），
   把玻璃材质的 `map_Kd` 复制成 `assets/mtr/textures/vehicle/<id>_glass.png`，
   产出锚点文件的 `glass` 段：`{texture, flipTextureV, quadCount, skippedTriangles, quads[]}`。
3. **客户端**：`MmtrVehicleAnchors.parseGlass`（锚点文件是**文件空间**，x/z 取负换成骑乘空间）、
   `MmtrGlass.draw` 逐四边形 `IDrawing.drawTexture` 画（`EXTERIOR_TRANSLUCENT_DOUBLE`）⇒ 颜色/透明度/图案**就是贴图的样子**，mod 侧零颜色配置 ✓

**★ 本轮修掉的真根因（用户一句"Blender 中的模型也没有黑边"点破）**：
这 42 个面的 UV **此前全都挤在同一个纹素上**（当初为了"留洞/取单色"设的）⇒ Blender 视口和游戏里每块玻璃只采样**一个像素**，
贴图上的黑边当然永远看不见。**展开后立刻就好了**（42 面 / 1648 顶点 UV 全部落在 (0,0)-(1,1)，
第一块面的 UV 实测 `(0,1) (0,0) (1,0) (1,1)`；导出对账：**只有 glass 的 42 个面变了 UV，其余组逐位不变**）。

**数字**：`glass` 42 面 / 1648 顶点；打包后 mod 端 `quadCount=2`（前挡风内外两块）、
`skippedTriangles=800`（41 边圆角侧窗展开后 UV 不再是轴对齐矩形 ⇒ 被配对规则跳过）。
**侧窗的窗框照样显示** —— 由**模型自己的面**画（它们现在是整张贴图 + 混合路径），只是不走 mod 那条通道。
**已知副作用**：前挡风的框被画两遍（模型自己的面 + mod 的四边形）⇒ 比侧窗略深。

### 7.18 ★★★ "透过玻璃看不到猪牛羊/其他材质" —— 玻璃**写了深度缓冲**（本轮修的）

**症状（用户）**：透明材质的模型，透过去看 ⇒ **实体（猪牛羊）不渲染，其他材质也不渲染**。

**测量**（`javap -p -c` 读 1.20.4 yarn 客户端里 `net.minecraft.client.render.RenderLayer` 的字节码，
落在 `sandbox/renderlayer-probe/`）：

| 事实 | 证据 |
| --- | --- |
| 写掩码**默认是 ALL_MASK**（颜色 **+ 深度**） | `MultiPhaseParameters$Builder.<init>`：`getstatic RenderPhase.ALL_MASK; putfield writeMaskState` |
| `entity_translucent`（`getEntityTranslucent`，我们原来用的）**写深度** | 它的构建链里**从头到尾没有 `writeMaskState(...)`** ⇒ 落回默认 ALL_MASK；参数 = `ENTITY_TRANSLUCENT_PROGRAM` + `TRANSLUCENT_TRANSPARENCY` + `DISABLE_CULLING` + lightmap + overlay |
| `entity_translucent_cull`（`INTERIOR/EXTERIOR_TRANSLUCENT` 原来用的）**也写深度** | 同上，另外带剔除 |
| **不写深度**（`COLOR_MASK`）的实体图层只有：`entity_alpha`、`entity_shadow`、**`entity_no_outline`**、`entity_translucent_emissive`、glint/eyes/text 系列 | 逐个方法里 `writeMaskState(COLOR_MASK)` 的位置 |
| 其中**只有 `entity_no_outline`** 同时满足"同顶点格式 + 真混合 + 不剔背面 + 用光照贴图" | `of("entity_no_outline", POSITION_COLOR_TEXTURE_OVERLAY_LIGHT_NORMAL, QUADS, 1536, false, true, …)` |

**机制**：车厢玻璃与**所有实体/方块实体**进的是**同一个** `VertexConsumerProvider$Immediate` 延迟缓冲
（`GraphicsHolder.createVertexConsumer` 的字节码就是 `vertexConsumerProvider.getBuffer(layer_v)`），
最后**按图层**统一 flush。玻璃写深度 ⇒ 在它**之后** flush、且更远的几何被深度测试整体剔掉
⇒ 动物 / 水面 / 方块实体"透过玻璃看就消失"。谁先 flush 由图层顺序决定，**不由我们决定**
⇒ 只要玻璃写深度，必然有一类东西被它挡掉。

**修法**：`MoreRenderLayers` 的三条半透明层（`INTERIOR_TRANSLUCENT` / `EXTERIOR_TRANSLUCENT` /
`EXTERIOR_TRANSLUCENT_DOUBLE`）改走 `RenderLayer.getEntityNoOutline`（原版就有，映射层 `getEntityNoOutline` 现成）。

**开关**（`run/mmtr-lightfield.properties`，**2 秒热重载、不用重启**）：
`translucentLayer=nooutline`（默认，= 上面的修法）/ `double`（**改之前的行为**，用来复现对照）/ `cull`（写深度 + 剔背面）。
切模式会清掉三条半透明缓存（否则还捧着旧图层的 RenderLayer）。

**可预期的外观差异**：`rendertype_entity_no_outline.fsh` = `texture * vertexColor * ColorModulator`，
而它的 vsh 已把 lightmap 乘进顶点色 ⇒ 与 `rendertype_entity_translucent.fsh` 的
`texture * vertexColor * lightMapColor` **等价**；真正的差别只有两点：① **不再有 `if (color.a < 0.1) discard;`**
（对玻璃更合适）；② 不再混 overlayColor（受伤闪红，车厢用不到）。

**部署**：`mmtr/scripts/check-java-compile.ps1 -Files <改的文件>` → 拷 `sandbox/javac-out/*` 进
`mmtr/game/fabric/build/classes/java/main` → **重启客户端**（`MoreRenderLayers` 每帧都在用，已加载的类不会重读）。

**★ 实测结果：这条修法无效（下一轮证伪）**。客户端 01:16 重启、日志确认 `半透明件图层=nooutline`，
"挡风有黑框（玻璃画出来了）、站在车外看猪正常、从车内看向猪就消失" **三条现象一条没变** —— 真根因见 §7.19。

### 7.19 ★★★ 真根因：**优化渲染器那条路的半透明材质写了深度**（车厢车窗根本不走 §7.18 的图层）

**为什么 §7.18 打偏了**：默认 `OptimizedRenderer.hasOptimizedRendering() == true` 时，整个车厢（含车窗）
是 `OPTIMIZED_RENDERER_WRAPPER.queue(...)` 进 MTR 的 `BatchManager`、由 `ShaderManager.setupShaderBatchState(materialProperties)` 画的；
`ModelPropertiesPart.renderNormal` 只在"门开着"时才画 `optimizedModelDoor`，静态件**什么都不画**
（源码注释：主模型已经含关着的门）。**那条路的深度写入由 `MaterialProperties.writeDepthBuf` 决定，与 mod 选哪个原版 RenderLayer 毫无关系。**
mod 自己那个四边形确实走 `MoreRenderLayers` ⇒ 所以"黑框看得见"，它掩盖了"真凶是模型自己的玻璃"。

**字节码证据**（`javap -p -c` 读 `mmtr/game/libs/Minecraft-Mappings-fabric-1.20.4-0.0.1-dev.jar`）：

| 事实 | 证据 |
| --- | --- |
| RenderStage → ShaderType | `RenderStage.INTERIOR_TRANSLUCENT(OptimizedModel.ShaderType.TRANSLUCENT_BRIGHT)`（车窗那一档） |
| 每档的材质属性 | `MaterialProperties.<init>` 的 switch（`MaterialProperties$1` 映射：TRANSLUCENT→1、CUTOUT_BRIGHT→2、TRANSLUCENT_BRIGHT→3、CUTOUT_GLOWING→4、TRANSLUCENT_GLOWING→5）：<br>1=半透明+**写深度** ／ 2=不透明+写深度(光=0xF000F0) ／ **3=半透明+写深度**(光=0xF000F0) ／ 4=不透明+写深度+cutoutHack ／ **5=半透明+不写深度** |
| 唯一"不写深度"的半透明档 | case 5 = `TRANSLUCENT_GLOWING` = `RenderStage.ALWAYS_ON_LIGHT` ⇒ 走 beacon_beam ⇒ **自发光的挡风**（夜里发亮 ✗ 不能用它当修法） |
| 那个 GL 调用 | `MaterialProperties.setupCompositeState()` 末尾：`getfield writeDepthBuf; RenderSystem.depthMask(Z)`（字节码偏移 88/92） |
| 谁调用它 | `ShaderManager.setupShaderBatchState` → `setupCompositeState()`（`sandbox/renderlayer-probe/ShaderManager.txt` 第 99 行） |

**机制（把每条现象都对上）**：① 车厢/玻璃是**当场**画的（BatchManager 直接 GL draw）；
② 猪牛羊、方块实体、水面进的是原版 `VertexConsumerProvider$Immediate` 的**延迟缓冲**，到这一帧末才 flush；
③ 玻璃先 `depthMask(true)` 把深度写进去 ⇒ 之后 flush 的、更远的几何被 `GL_LEQUAL`（depthFunc 515）整片剔掉；
④ 地形在玻璃之前画 ⇒ 地形还在；水/方块实体也是延迟的 ⇒ "其他材质也不渲染"；站在车外不隔玻璃 ⇒ 一切正常。

**修法**：新增 mixin `org/mtr/mixin/MaterialPropertiesMixin.java` —— 在 `setupCompositeState()` 的 RETURN 处，
若 `translucent && !MoreRenderLayers.allowTranslucentDepthWrite()` 就再压一次 `RenderSystem.depthMask(false)`。
不透明车体照旧写深度（车体挡住身后东西是对的 ✓），混合函数与光照贴图一个字不动。

**开关**（`run/mmtr-lightfield.properties`，**2 秒热重载、不用重启**）：
`translucentDepthWrite=false`（默认 = 本修法）/ `true`（**改之前的行为**，用来复现对照）。

**部署**（Java **和** mixin 配置都变了）：编译 → 拷 `sandbox/javac-out/*` 进 `build/classes/java/main`
**以及** `src/main/resources/mtr.mixins.json` 拷进 `build/resources/main/` → **重启客户端**（mixin 只在启动时织入）。

**待实机确认**：重启后从车内看向猪牛羊/水面应当都能看见；把 `translucentDepthWrite` 切 `true` 应当**立刻复现**消失，
切回 `false` 立刻恢复 —— 这一对 A/B 就是因果证据。

### 7.20 ★ 让灯真的能照明：世界方块那一侧（2026-09-29，§6 的落地）

**诉求**：车厢那条 program 只覆盖 MTR 自己画的东西 —— **车厢 + 3D 钢轨**。道床/隧道壁/站台/草/水走的是
区块渲染器，跟 MTR 一点关系都没有 ⇒ 观感就是"车灯照亮了车厢，眼前的地面还是黑的"。§6 定的方案就是补这一环。

**动手前先测了五个事实（其中两个把 §6 的方案推翻了一半）**：

| 问题 | 实测 | 证据 |
| --- | --- | --- |
| 地形到底走谁的 program | dev 客户端装着 **Sodium 0.5.8**，区块整体走它自己的 `sodium:blocks/block_layer_opaque.vsh/.fsh`；原版 `rendertype_solid` 一族**根本没被用到** | Sodium jar 里的 `assets/sodium/shaders/**`；`ShaderChunkRenderer.compileProgram` 常量 `blocks/block_layer_opaque` |
| 能不能用"资源包放同名文件"覆盖 | **不能**。`ShaderLoader.getShaderSource` = `ShaderLoader.class.getResourceAsStream("/assets/<ns>/shaders/<path>")` ⇒ 走 **classpath**、不走资源包栈（谁在 classpath 前面谁赢，而 Sodium 的 jar 一定在里面） | `javap -c` 读 `ShaderLoader` |
| 世界坐标从哪来 | Sodium 的 `position = _vert_position + u_RegionOffset + 16*chunkCoord` **就是相机相对世界坐标**：`u_RegionOffset = 区块原点 − 相机位置`；fog 的 `getFragDistance` 也按它算 ⇒ 与 `MmtrHeadlights` 上传的灯位**同一个空间**，一个字都不用换算 | `DefaultChunkRenderer.setModelMatrixUniforms` → `getCameraTranslation(origin, camInt, camFrac) = (origin − camInt) − camFrac`；`include/fog.glsl` |
| 地形顶点有法线吗 | **没有**。Sodium 的地形顶点格式只有 position / texcoord / lightcoord / color（方向性明暗早就烘进顶点色） | `sodium:include/chunk_vertex.glsl` |
| 反照率能用顶点色吗 | **不能**。fsh 里 `v_Color = _vert_color * lightmap`，隧道里它是全黑 ⇒ 拿它当反照率，灯永远是黑的 | `block_layer_opaque.vsh` 第 53 行 |

**做法**（三件事，缺一不可）：

1. **换源码**：新增 mixin `SodiumShaderLoaderMixin`，在 `ShaderLoader.getShaderSource` 的 **RETURN** 处整体替换三个标识符 ——
   `sodium:blocks/block_layer_opaque.vsh` / `.fsh` → 我们的副本（`assets/mtr/shaders/sodium/mmtr_terrain_headlight.*`），
   `sodium:include/mmtr_headlight.glsl` → **共享 include 的内容**（Sodium 的 jar 里当然没这个文件，它由我们供给）。
   `@Mixin(targets = "字符串")` 而不是类字面量：Sodium 只是**运行时**依赖（不在编译期 classpath），而且不带 Sodium 跑时
   字符串形式只会"这个 mixin 不生效"，不会崩。`remap = false`：`getShaderSource` 是 Sodium 自己的方法名，不参与原版混淆映射。
2. **一份数学**：把 `mmtrHeadlightTerm` 从 `mmtr_lightfield_mtr.glsl` 搬进
   `assets/minecraft/shaders/include/mmtr_headlight.glsl`；车厢那条路 `#moj_import` 它，地形那条路
   `#import <sodium:include/mmtr_headlight.glsl>` → **两条路共用同一份实现**，观感不会各自漂。
3. **上传灯表**：新增 mixin `SodiumGlProgramMixin`，挂 Sodium `GlProgram.bind()` 的 RETURN
   （`ShaderChunkRenderer.begin()` 里"选程序 + bind + 传自己的 uniform"的必经之路），
   调 `MmtrHeadlights.uploadForTerrainProgram()`（惰性：每个 (帧, program) 只传一次，且只对认识
   `mmtrHeadlightCount` 的程序生效；不认识就静默跳过，所以挂宽一点不花代价、却不会漏）。

**两个不显然但必须处理的点**：

- **地形画在实体之前** ⇒ 地形那次上传用的是**上一帧**收集的灯表。灯在世界里没动、动的是相机，
  所以上传时按"收集时的相机 → 现在的相机"**整体平移**一次（8 盏灯同一个位移）⇒ 滞后被消掉，而不是忍着。
- **顶点格式没有法线** ⇒ 片元里用**屏幕空间导数重建面法线**（体素地形全是平面四边形，重建出来就是真法线）。
  符号**不靠 `gl_FrontFacing`**（依赖 GL 的手性/绕序约定），而是"翻到朝着相机那一侧"（相机在这个空间的原点，没有歧义）。

**开关**（`run/mmtr-lightfield.properties`，**2 秒生效、不用重启、也不用重载资源** —— 着色器永远只有一份，开关走 uniform）：

```properties
terrainHeadlights=true    # 地形吃不吃车灯（false = 上传时把 mmtrTerrainLuxScale 压成 0）
terrainLuxScale=1.5       # 地形这一侧的强度（与车厢分开调）。默认比车厢的 1.0 高：地面离灯远、
                          # 灯又几乎平射 ⇒ 兰伯特只有 0.2 上下，1.0 会偏暗
terrainNormal=derivative  # derivative=导数重建法线 | flat=不做兰伯特（各向同性，兜底档）
terrainDebug=false        # 假色：被车灯照到的地形画成**品红**、其余全黑
                          # （2026-09-29 首次交付时**先设成 true**：地形全黑 + 灯扫过处品红
                          #   = "补丁真的生效了"的判据；画面跟平常一样 = 着色器**没换上**）
```

> 为什么开关不放在"换不换着色器"上：Sodium 的 program **一辈子只编译一次**（`ShaderChunkRenderer.programs` 缓存），
> 按开关决定换不换就等于让开关变成"要重启"。所以源码永远换，`terrainHeadlights=false` 只是把系数压成 0。
> 另外 GL 的 uniform 默认值就是 0 ⇒ 即使一次上传都没发生，地形也不会凭空亮。

（`-Dmmtr.imports=sodium=<解出来的目录>`）与 `-Dmmtr.defines`。**踩到一脚**：defines 必须写成

（报错行号落在**使用处**而不是定义处，很容易看错方向）。实测值：`VERT_POS_SCALE=4.8828125E-4`、`VERT_POS_OFFSET=-8.0`、`VERT_TEX_SCALE=3.0517578E-5`。

**探针抓到的真问题（已修）**：共享 include 的**注释里**提到了 `#moj_import`/`#version` 这两个词，
