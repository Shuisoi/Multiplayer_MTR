# 83 - 实机验收（服务端侧）：连挂手术后进路孤儿修复

> 触发：2026-09-09 21:26 用**新 jar 重启 dev 服务端**做 A2/S5 服务端侧实机验收。
> 首次查询 `mmtr-trains` feed 就发现异常：`routes[]` 里有一条 `state:"SET"` 的 **SHUNT 进路**，
> 而它所属列车的 mission 已经是 **COMPLETE**。

## 1. 实机证据

```
GET /mtr/api/map/mmtr-trains?dimension=0
routes[0] = { vehicleId: -3848089928124968983, kind: SHUNT, state: SET,
              entryRail: …3D, targetRail: …3E, railCount: 6, forkCount: 2,
              requestedMillis: 1788959499337 }     ← 21:11 时刻
trains[0].mission = { kind: MANEUVER, state: COMPLETE, targetSidingId: -3054567530540565369 }
```

服务端日志（21:26:02，新进程重放错过的时间段）里这条进路的完整生命周期都在：
`调车授权 → planned via 牵出—推进 setback @138m → self-armed → 连挂完成（3 节）→ COUPLE done`。
也就是说：**连挂成功后，进路没有随任务终结而释放**。

## 2. 根因

`MmtrCoupleSurgery` 合并编组时会**新建一个 Vehicle 对象**（`new Vehicle(mergedData, …)`），
而进路当时挂在 Vehicle 的**对象字段** `mmtrRoute` 上：

- 旧对象的字段随对象一起消失；
- 新对象（同一 vehicle id）的字段是 null，于是它跑到终态清理时 `if (mmtrRoute != null)` 不成立，
  **按 id 释放进路的那一步被跳过** → 登记表里留下一条永远 SET 的孤儿进路。
- 被吸收的那节车（rake）的 id 更是彻底消失，若它也有进路/道岔持有，同样无人释放。

## 3. 修复（登记表是唯一真源）

| 件 | 改动 |
| --- | --- |
| `Vehicle.getMmtrRoute()` | 改为**按 id 从 `Simulator.mmtrRoutes` 读**（不再信任对象字段）——手术重建对象后仍能读到本车的进路 |
| `Vehicle.releaseMmtrPointRequests()` | 终态清理**无条件按 id 释放**进路（去掉 `mmtrRoute != null` 闸门） |
| `Vehicle.mmtrMissionTick()` | 每 tick 的 `refresh` 也改为按 id（无进路时是 no-op） |
| `MmtrCoupleSurgery` | 被吸收车的进路 + 道岔持有立即释放；当合并已使继承的 mission 终结（任务驱动调车的常态）时，合并车 id 的进路也一并释放 |
