# 09 客户端/服务端分离：职责与链路审计（round23）

## 部署形态（用户选定 A）
MC 专用服务器（或单机集成服务器）= 权威引擎；客户端只负责输入/渲染/镜像，绝不运行 Simulator。

## 现状审计（结论：逻辑分离已大体成立，入口校验是本轮补强点）
- 引擎实例化只在服务器侧：Init.registerServerStarted -> new Main(...)（Simulator 仅在服务器进程）。
- 逻辑客户端不建 Simulator：MinecraftClientData extends ClientData + VehicleExtension，
  由服务器 DataRequest/VehicleUpdate 填充（轨道图+车辆快照）。
- mmtr 输入链（已是 C->S->engine）：客户端 VehicleRidingMovement.tick 采键盘/HID notch
  -> 变化时 PacketDriveControl(vehicleId, T/B/R/E)
  -> runServer -> Init.sendMessageC2S(MMTR_DRIVE, MmtrDriveControl(vehicleId,state,playerUuid))
  -> 引擎 OperationProcessor -> Vehicle#applyMmtrControl。
- 占用锁（服务端权威）：MmtrDriveAccess.canControl / shouldAutoRelease + canTakeMmtrControl
  （只认当前坐在驾驶位的玩家 uuid；下车/换车/断线自动释放）。存在 MmtrDriveAccessTests。
- 客户端镜像只读：Vehicle#isClientside（!data instanceof Simulator），mmtr 快照字段从服务器
  VehicleUpdate 来，dirty 驱动；客户端用同一控制器/种子做本地镜像，不改权威态。
- 任务/调度（mission/dispatch/periodic source）全部只在 Simulator 侧，客户端不跑。
- Dashboard 是独立 Web（SystemMapServlet），不是 MC 客户端。

## 本轮补强：服务端入口合法化（防御恶意/异常客户端）
- MmtrDriveAccess.sanitize(ControlState)：notch [0..16]、reverser [-1..1]、axes [-1..1] 硬钳制，
  在 Vehicle#applyMmtrControl 存储/镜像前统一执行（控制器内部再按 ConsistType 档位二次钳制）。
- 测试 MmtrDriveSanitizeTests：越界输入被钳、合法输入不动、emergency 原样。
- 说明：mmtr_dispatch（Web/op）与 mmtr_drive 都经由引擎 OperationProcessor 在服务端处理，
  天然只服务端可执行；Web action 未做鉴权（开发入口，多人服需加 operator 白名单 - TODO）。

## 职责矩阵（契约）
| 能力 | 归属 | 客户端可见 |
| 仿真（物理/任务/时刻表/占用锁/保护） | 服务端 Simulator | 只读快照+镜像 |
| 输入采集（键盘/HID notch 上升沿） | 客户端 VehicleRidingMovement | 本地 |
| 输入生效 | 服务端 PacketDriveControl->MMTR_DRIVE | 无（HUD 读镜像） |
| 任务派发/周期源 | 服务端 op/Simulator | 面板读 feed |
| 渲染/地图/面板 | 客户端(MC) + Web | 本地 |

## 缺口/TODO（下一步候选）
1. Web 派车/操作鉴权（32 人服不能开放匿名 dispatch/改配置）。
2. 客户端 notch 状态与服务器权威值不一致时以快照回写纠正（目前只发不读回）。
3. 纯客户端（连专服）应彻底不加载引擎 Simulator 代码路径（单 jar 发行没问题，但可再加
   ClassLoader/懒加载约束）；单机仍用集成服务器合法。
4. 频率限制/过期输入：packet 仅变化发送，缺最后保持状态的心跳语义（可加 250ms 心跳）。
