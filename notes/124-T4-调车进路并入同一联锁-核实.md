# 124 - T4（三）：调车进路并入同一联锁 —— **核实结论是"结构上已经满足"**

> 对应设计：`docs/01-设计/行车控制-任务联锁与行车许可-设计.md` §A-5（⑤）/ §6（T4）。
> 前置：notes/121/122。触发：用户 2026-09-14「一路把T做完吧」。

## 1. 设计把它列为待办，但核实下来**不是缺口**

设计 §A-5 的 ⑤ 写的是：

> **`MmtrShuntAuthority` 并入同一联锁**：SHUNT 进路同样要过物理道岔预约与 A-2 的 SET 判定，
> 区别只在"灯显走副显示、可越过闭塞占用"。现在它是**绕过 S1 占用的第二套授权**，
> 与主进路并行。

"绕过"这个词让这一条读起来像个洞。**先核实，再动手** —— 结论是它**结构上已经满足**，
证据两条（都是一行就能看出来的事实，不需要跑起来才知道）：

| 证据 | 位置 |
| --- | --- |
| 道岔申请**与 kind 无关**：`armMmtrPointRun` 对两类进路一视同仁（它压根不问 kind 就申请 pending forks） | `Vehicle.armMmtrPointRun` |
| SET 判据**没有 kind 过滤**：授权条件与 T1 的物理位置条件对 MAIN / SHUNT 同等适用 | `MmtrRouteRegistry.refresh` |

也就是说，"第二套授权"实际管的只有两件事：**副显示的灯显** 与 **S1 占用豁免**。
而这两件正是设计**要**的（调车本来就可以进占用区段、由副显示授权）——
它不是绕过联锁，它是**联锁之外的那一层玩法语义**。设计那句话里"绕过 S1 占用"是对的，
"与主进路并行"读起来像并行**两套联锁**，实际只有一套联锁 + 一套占用豁免。

## 2. 交付：把它钉住（而不是"修"它）

既然是"已经满足"，本片的交付就是**用例 + 结论**，防止日后有人改出这个洞：

`aShuntRouteCannotBypassTheTurnoutReservation` 的断言链：

1. 另一列车（`vOther`）先把这处道岔按在**正线贯通**（它要去站台）—— 物理位置被别人占了；
2. 调车进路手里**确实握着 C3a 的副显示授权**（断言 `active(shuntId) != null`，否则这条用例就没意义）；
3. 它申请道岔 → **`QUEUED`**（同一套物理预约，互斥就是排队）；
4. `refresh` → 进路**必须 PENDING**，且理由点名"物理道岔…两条进路互斥"；
5. 前车越岔让位 → 调车进路这才 **SET**（与列车进路**同一套判据**，没有第二条路）。

## 4. 一条方法论上的备注

这一片值得单独记一笔：设计文档里"待办"的措辞（"绕过…第二套…并行"）会让人直接去改代码。

风险与收益完全不成比例。
