## 1. 交付

| 件 | 内容 |
| --- | --- |
| `MmtrDirectionalBlockService.hasSection` / `railsWithSections` / `railsWithSectionsCount` | "v2 在这根轨上是否说了算"的快速判据（`railsWithSections` 由原来的计数方法改名，避免同名歧义） |
| `MmtrSignalAspect.chainDepth` | 有 v2 区间时先走 **v2 链深**（单位 = 灯到灯区间）；**结果为 0 时回退 v1 走行** |
| `MmtrSignalAspect.v1ChainDepth` | 原来的按轨走行，原样保留（无区间轨走它；有区间轨在 v2 无结论时也走它） |
| 受限节点缓存 | `restrictedNodeKeys()`：v2 每步都要问"这个节点是否未清"，按占用树签名缓存，避免逐步重算全图 |
| **走行补缺：轨中段的灯** | `nearestLampOnSpan` / `MidRailLamp`：走行经过一根轨时，若该轨**中段**站着灯（投影不在端点上），就在那里**截断区间**并把该灯记为终止灯 |

### 1.1 为什么"取更保守的那个"

v2 读**共享占用树**，v1 还认**每区间保留信号色**。两条通道可能不一致（历史 MTR 块、人工块，
或只预留了颜色却没写 footprint 的调用）。所以接线写成：

- v2 有结论（>0）→ 用它；
- v2 无结论（0）→ **交给 v1 走行**，两者取更严的。

信号绝不能因为"两条占用通道不一致"而放行 —— 这是安全方向。

### 1.2 补掉的走行缺口

S1 走行只认**节点上的灯**，于是"灯站在一根轨的**中段**"时不会被当作边界：
探针实测（notes 记录于本片）显示，200 m 轨上两盏灯（一个在起点节点、一个在中段）会得到
**两段互相重叠**的区间（第一盏覆盖 0..200，第二盏覆盖 100..200），`aspectFrom` 于是给出红而不是黄。
修正后两段正确分为 `0..100` 与 `100..200`。
设计文档 §5 早就写了"几何投影是节点绑定的超集"，这是把它真正实现。

## 2. 期望值变化（逐条说明，门禁要求）

**只有 1 个既有用例变化**，已重写并改名为 `theChainCountsBlocksBetweenLamps`（原
`theChainCountsSectionsOnASplitRail`）：

| 原写法 | 现在 | 原因 |
| --- | --- | --- |
| 用一盏"轨中段、朝南（angle=0）"的灯把东西向长轨切成两段，占**远端**期望单黄 | 用**两盏朝东的灯**（起点节点 + 中段）造出两个区间，占远端期望单黄、占近端期望红 | v1 的 aspect **按轨**、不看向；v2 **看向**。原场景里那盏灯与轨**垂直（dot=0）**，在 v2 下不属于"照这条轨朝东"的方向，方向判定退化成反向，区间方向就错了。v2 里"同一根轨上的两个闭塞"由**两盏灯**表达，这也正是真实布置的样子 |
| — | 该用例不再依赖 v1 的"无灯整根轨"那半段（删掉） | 那半段在 v2 走行里读的是占用树，与 v1 读保留色的依据不同，属于 v1 语义，另有用例覆盖 |

另外新增 1 例 `aReservedColourOnlyHoldStillShowsDangerOnAV2Rail`：**只有 v1 保留色、占用树为空**时，
信号仍然保持危险（§1.1 的安全网）。

## 4. 下一步（S4 真正的最后一小块 + S5）

### 4.1 客户端镜像（唯一剩余代码工作）

`MmtrSignalAspect` 已按 v2 出结论，但**客户端渲染器是按轨取色**的，而 v2 的区间是**按方向**的 ——
一个轨的显示色在 v2 下应当来自"**照它的那盏灯**"。所以需要给镜像加一层：

- 引擎：`PacketMmtrRoutes` 增加"灯 → 显示"（灯 key + v2 色/链深），或直接推
  `describeLampAspects` 的等价结构；
- 客户端：`MmtrSignalChain` 按**灯**而不是按轨取数（渲染器已经知道自己在哪盏灯上，
  它调用 `getAspectState` 时手里有 `blockPos`）。
