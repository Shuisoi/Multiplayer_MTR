# 328 · 作业单仿真器 P0 闸门：一天跑不跑得动（实测数字 + 两处卡死）

> 目的：作业单仿真器（独立程序，只按作业单编排，控制台不参与）立项前，先回答一个只能用数字回答的问题 ——
> **在副本世界上用真引擎跑完一天，要多少墙钟？** 顺带在真负载下把"全天作业单到底立不立得住"先撞一遍。
>
> 现场：当前 dev 测试图（2026-09-26 环线 + 车厂）。世界**只读副本**，线上存档一个字节没动。

## 1. 一行结论

**吞吐够用，编排不够用**：16 编组跑一天约 **46 min**（31× 实时），可接受（GUI 走"录一遍再回放/分析"）；
但**当前地图上 4 列车就会集体卡死**，全天作业单在修掉那两处之前根本跑不完。

## 3. 实测数字（本机，单进程，未开 Jetty）

| 窗口 | 4 编组 | 16 编组 |
| --- | --- | --- |
| **活跃**（`step()` 的 1 s 步长，车在走） | 27.4 ms/仿真秒 → 一天 **40 min** | 32.1 ms/仿真秒 → 一天 **46 min** |
| **静置**（车都卡住不动） | 1.06 ms/仿真秒 → 2 min | 48.7 ms/仿真秒 → 70 min（车没走，但都在抢岔/重试） |
| **生产节拍**（10 ms 步长，每秒 100 tick） | 92.8 ms/仿真秒 → 134 min | 3034 ms/仿真秒 → **4370 min（73 h）** |

两条读法：

1. **规模不敏感**（4 → 16 编组只涨 17%）：每 tick 的固定开销（162 轨、信号链、派发器、道岔表）是主项，
   不是车辆数。⇒ 多开车不会让仿真变慢，**这对"全天所有列车一起仿"是决定性的好消息**。
2. **节拍决定一切**：同样一天，1 s 步长 46 min、生产节拍 73 h —— **差 95 倍**。
   ⇒ 仿真器必须用 `Simulator.step()`（内部按 1 s 切片，注释自述就是给"future headless task servers"留的），
   **不能**照生产那样 10 ms 一 tick。

> 第一版测量把控制台日志算进去了（引擎每 tick 都 `System.out.println`），量出 8.87 ms/仿真秒 ——
> 那个数里绝大部分是管道 I/O。上表是**把 `System.out` 换掉之后**量的（`measure()` 里做的事）。

## 4. 撞出来的两处卡死（这才是仿真器该产出的东西）

### 4.1 西行回程永久停在出发信号前：信号要 `leg 1`、授予的是 `leg 0`

单列车路线（出库 → 上水村1 → 莫氏岛1 → 叶楼村1 → 换端 → 西行）前 6 步全绿（含站台开门/停站 20 s/换端 CAB_B），
第 7 步（西行去 莫氏岛 2 台）在里程 10187 m 处停住：

```
[MMTR-SIG] motion stopped at block stop 10186.81m（进路未设好，停在出发信号前：
           组合不存在（positionForLeg 判死）：point 0,65,1800 wantLeg=1 | lock=false holder=- phys=- 现位=无主, waiting）
[MMTR-PT]  req v…@100,65,1800 leg 0 -> GRANTED      ← 补申请授予的是 leg 0
[MMTR-PT]  按计划补申请：车 … 被 100,65,1800 挡住，申请第 0 条腿 → 已授予
```

之后 **660 s 里程 0 m**。判据很清楚：**信号链算出来的腿（leg 1）与规划器申请到的腿（leg 0）不是同一条**，
两边各等各的 ⇒ 永久停住。这不是"慢"，是死锁。

### 4.2 车场咽喉：16 编组里 8 列停在 100 m 根本没出库

| 编组 | 现象 |
| --- | --- |
| 4 编组 | 活跃窗后**全部**停住（100 m / 2771 m / 4272 m / 7767 m） |
| 16 编组 | 8 列停在**同一位置 100.0 m**（排队），4 列 `步=0`（任务派出去了但从没推进），4 列还 `PENDING` |

`100.0 m` 是车场牵出线上的同一个点 ⇒ 咽喉一次只放一列，后面的全部排队。
作业单路径**没有出库闸门**（notes/152 那道 4 min 闸门是给时刻表派发器的，作业单侧没有对应物），
所以 N 份作业单只要发车时刻挨得近，就会一起挤咽喉。

## 5. 两个操作坑（省下一次重新踩）

1. **`gradlew.bat` 不能接 `-Dp0.consists=4`**：PowerShell 调批处理时它被拆成两个参数，Gradle 拿 `.consists=4`
   当任务名报 `Task '.consists=4' not found`。⇒ 测试参数改读**环境变量**。
2. **改了环境变量 Gradle 不会重跑测试**（env 不是任务输入，判 UP-TO-DATE）⇒ 必须加 `--rerun`。

## 6. 对方案的四条影响

1. **节拍**：仿真会话一律走 `Simulator.step()`（1 s 切片）。生产节拍（10 ms）在仿真里是 95 倍成本，不可用。
   ⇒ 需要一条**保真度核对**：同一场景 1 s 与 10 ms 两种步长的结果（停车点、序、时间）差多少，写进报告。
2. **GUI 形态**：46 min 跑一天 ⇒ 「**跑一遍 → 落轨迹 → 回放/分析/拖时间轴**」是主流程，
   不是"实时跟着看"（31× 实时的直播只是附带能力）。这条与既定架构一致，但与"打开就能看车实时跑"的直觉不同。
3. **作业单生成器必须带"错开发车 + 咽喉容量"**：4.2 那处是**生成器**该避免的（不是引擎缺陷）——
   一份全天的作业单需要把 N 份发车时刻按咽喉能力摊开，并在体检里报"这份作业单需要的咽喉时间 > 可用时间"。
4. **4.1 那处是真缺陷**，得先修（信号链的腿 vs 规划器的腿不一致）：不修，任何"出去再回来"的全天作业单
   都会在回程第一步永久停住。**这正是仿真器存在的理由** —— 它把一个"跑一天才知道"的问题变成了"跑 20 分钟就看见"。

### 8.1 判据：授予的是 leg、信号链要的是位

```
[MMTR-PT]  req v…@-280,65,1800 via …-0708-…-0708 leg 1 -> GRANTED
[MMTR-SIG] motion stopped at block stop 2158.53m（进路未设好，停在出发信号前：…
           point -280,65,1800 … v… 现位 1，可开通，但本进路需要位 0，走不通该进路, waiting）
[MMTR-SIG] motion stopped at block stop 2659.23m (block ahead ends at an unset turnout, waiting)
[MMTR-PT]  req v…@-200,65,1800 via …-0708-…-0708 leg 0 -> GRANTED
```

`-280,65,1800` 是**下水站台东端的岔口**（下水台轨 = `(-500,65,1800)→(-280,65,1800)`）。
规划器申请并拿到的是 **leg 1**（正是车当前所在的位），而信号链算出来"本进路需要**位 0**" ——
⇒ **授予了也不放行**，车永久停在出发信号前；没有第二个人会去扳这个岔（无主），于是死锁。

与 §4.1 是同一族（那边是 `positionForLeg 判死` + 授予 `leg 0`，这边是 `现位 1 / 需要位 0` + 授予 `leg 1`）：
**规划器/道岔授予的 "leg" 与信号链要求的 "位" 不是同一套编号**（0/1 基或映射方向不一致）。
修法在引擎侧：把 `MmtrPointAuthority` 的授予与信号链的 `positionForLeg` 收敛到同一个映射。

### 8.2 连带后果（为什么"一个卡点 = 全车场堵死"）

`DAY-LOOP-01` 停在 `-280,65,1800`（站台东端）之后，其余 15 份作业单**一个也出不了库**
（全部停在 `m0y`，各自从发车时刻起就没动过）。出库通道与这条主线上行闭塞是同一段 ——
所以修 8.1 之前，"全天作业单"的仿真结果**只反映这一个缺陷**，量不出别的。

## 9. 追加：§8 的判据是错的 —— 真根因是「① 长区块」把扣住它的那处道岔漏出申请集（已修）

**一句话**：卡死与"腿号/岔位编号不一致"无关。作业单（同一份 `day-loop.json`）、引擎代码、世界副本
三者都不动时，**单列车能连跑两圈**；16 份一起跑 900 仿真秒里 5 列车全在走、`DAY-LOOP-01` 跑完一整圈
（圈=1），日志里 `unset turnout` / `让位` / `进路未设好` **一行都没有**。

§8 那两行读错了：`[MMTR-PT] req …@-280,65,1800 … leg 1 -> GRANTED` 后面那行不是"放掉持有"，而是
**补申请日志**（`按计划补申请：车 … 被 -280,65,1800 挡住，申请第 1 条腿 → 已授予`）；而
`motion stopped at block stop 2158.53m（进路未设好…）` 是**另一列车**（J02）的读数，不是 J01 的。

### 9.1 复现：世界状态一变，同一份作业单就卡死

22:59 那次与 23:05 之后**唯一变过的是世界的 `mmtr-points.json`**：`-200,65,1806` 由 0 变成 1
（`positions` 那一列）。把当前副本里的这处道岔用引擎自己的接口扳回 0 ⇒ **那次卡死逐行复现**：

```
[MMTR-SIG] motion stopped at block stop 2659.23m (block ahead ends at an unset turnout at -200,65,1806, waiting)
[MMTR-SIG] motion stopped at block stop 2158.53m（进路未设好，停在出发信号前：物理道岔 -280,65,1800 被 v… 按在
           位置 1（岔股开放），本车需要位置 0（正线贯通）—— 两条进路互斥, waiting）
```

2659.23 / 2158.53 两个数与 incident 完全一致（复现脚本：`TempSimStuckProbeTests#dayLoopTwoThroatSwitchThrownAgainstTheRoute`）。

### 9.2 机制：咽喉两处道岔互锁（`throatMap` 实测的几何）

| 节点 | 根部 | 正线远端 | 岔股 | 位置 0 / 位置 1 |
|---|---|---|---|---|
| `-280,65,1800`（下水1台东端） | `(-500,1800)` 站台轨 220 m | `(-200,1800)` | `(-200,1806)` 斜渡线 C（80 m） | 0 = 站台↔正线；1 = 站台↔C |
| `-200,65,1806`（C 的出口） | `(-100,1806)` 正线 | `(-280,1806)` 下水2台轨 | C（80 m） | 0 = 正线↔下水2台；**1 = 正线↔C** |

作业单"下水1台 → 上水村2台"（去 z=1806 那一侧）要的正是 `-280=1` 与 `-200,1806=1`。
`-200,65,1806` 停在 0 ⇒ **从 C 这条进路根本开不出去**（`continuationFrom(C, 0) = null`，而
`MmtrForkElection.elect` 在"进向不在当前岔位开通的那一对里"时**直接返回 null、连按意图扳岔那条路都不走**）：

1. ①（"要进的区块出口是选不出腿的道岔"）把车扣在站台轨末端的信号前 —— 判据就是"进了 C、到它的远端 F2 会被挡"；
2. 而 `replenishForkRequests` 在 ① 成立时**加进最近一处道岔就 `break`**（`just the next fork ahead`），
   扣住本车的 F2 **一次申请也发不出去** —— 计划里 F2 距车只有 **80 m**，本来就在 120 m 接近锁闭窗口内，
   纯粹被那个 `break` 丢掉的；
3. 车不动 ⇒ F2 更走不进窗口（自锁）；同时它的车头正压在 `-280` 节点 10 m 净空区内 ⇒ 后车连"扳 `-280`"
   都被净空闸拒绝（现场原话：`净空闸=岔区净空被占：轨 … 靠这个节点的 10.0 m 内有车足迹 —— 不许把道岔
   从车下抽走`）⇒ 咽喉两处岔互锁，**一天里 15 份作业单一份也没出库**。

### 9.3 修法（两处，都在 `engine/.../data/Vehicle.java`）

1. `nextSectionAuthorityStopM` 把"扣住本车的那一处道岔"写成节点键
   （新字段 `mmtrSectionAuthorityHoldNodeKey`），阻塞理由也带上它
   （日志由 `block ahead ends at an unset turnout` 变成 `… at -200,65,1806` —— 只说"道岔没设好"
   时，排查的人无法知道是哪一处、该看谁的持有，这一轮就是为此多花了一轮）；
2. `replenishForkRequests` 在 ① 成立时**把那处道岔一起申请**（原子组），不再"只申请最近一处"。
   窗口外、又不是扣住本车的那几处**照旧不申请** —— 接近锁闭的本意不变（§2 的注释本来就写着
   "车可能离它整整一个区块"，这里只是把它落成代码）。

### 9.6 修好之后才看得见的东西：**"塞死"与并发数不成正比 —— 是一处相位相关的互锁**（9.6b 已修正）

> ⚠️ **本节初版的结论（"这张图只撑得住 1 列并发"）是错的**，见 §9.6b。初版的表保留在这里，作为
> "只看单次跑的结果就下结论"的反面教材。

初版：同一份作业单、同一份世界，只改发车错开（16 份那版文件，`capacity*` 用例），得：

| 编组 × 错开 | 并发（≈ 一圈 900 s / 错开） | 一小时结果 |
|---|---|---|
| 4 × 900 s | ≈ 1 | 3600 s 全程无卡死 |
| 8 × 450 s | ≈ 2 | t≈3300 s 全网静止 |
| 16 × 300 s | ≈ 3 | t≈1067 s 全网静止 |
| 16 × 180 s | ≈ 5 | t≈1935 s 全网静止 |

当时读成"容量 ≈1 列并发"。**这个读法站不住**：4 × 900 s 与 16 × 180 s 的"并发"根本不在一个量级上，
而前者干净只是因为**车少、相遇相位也少**。

| **180 s（文件现在就是它）** | ≈ 4 | **3600 s 零卡死；每列车跑完 4~5 圈**（43~53 km），4 列车全程 RUNNING |
| 450 s | ≈ 2 | 3600 s 零卡死 |
| 900 s | ≈ 1 | 3600 s 零卡死 |
| 300 s | ≈ 3 | **t≈1067 s 全网静止**（与 16 份那版同一时刻、同一形态） |

⇒ 三件事：

1. **"并发越多越容易死"不成立**：4 列车按 180 s 发车（并发最高的一档）反而跑得最好，
   而 300 s 那一档（并发更低）死在**和 16 份那版一模一样的 t≈1067 s** —— 这是**相位**问题：
   某两列车以某个相对位置在咽喉/站台相遇时构成循环等待。t≈1067 s 这个数在两版文件里重合，
   说明那是**同一次相遇**（列车从同一股道、同一时刻出发，轨迹可复现）。
2. 所以这不是"作业单排不进这张图"，而是**一处与相遇相位相关的互锁**（还没有定性到最后一层）。
   P3 的"作业单体检"要报的是"这份作业单里有会互锁的相遇相位"，而不是"密度超了"。
3. 用户口径的 **4 辆**（180 s）当前**跑得通**：一天一小时 4~5 圈/列，这就是"全天可仿真"的基线。


### 9.7 两个工具教训（本轮踩的）

1. **"车不动"不是卡死判据**：站停 20 s + 圈间静置 5 s + 下一圈站停 20 s = 一列车合法地静止 45 s 以上，
   第一版"45 s 零位移"判据就是这么误报的（把一次正常的循环折返当成了死锁）。现在的判据是
   "**里程 + 步号/圈号 + 调度状态 + 子任务 revision** 连续 N 秒全都不变"。
2. **同一份输入要多跑几遍再下结论**，而且**不要拿"并发数"当唯一自变量**：16 × 180 s 复现的是 t≈1935 s，
   16 × 300 s 是 t≈1067 s，4 × 180 s 干净、4 × 300 s 又死在 t≈1067 s —— 顺序/相位不同，冲突展开的路径
   就不同（§9.6b）。判"能不能跑"要按**相位/发车时刻**扫，别按单次跑的结果说"容量是多少"。

### 9.8 两条现场教训（写给下一轮）

1. **世界的 `mmtr-points.json` 是仿真输入的一部分**。同一份作业单，道岔初始位置不同就是"跑得通/整天
   卡死"两种结论。Studio 的"一天"要可复现，就该在录制前把道岔状态**显式定义**（复位到默认位，
   或明确声明"沿用现场存档"），不能默认继承线上服务器随手留下的那几行 —— 这次的 A/B 就是它造成的。
2. **默认行会折算成位置**：新表型出来的道岔，`mmtrEnsurePointDefaults` 会给**每个进向**写一行 `leg 0`
   （老的"每进向各 0/1"习惯），而"从岔股那一行看 leg 0"恰恰等于"岔股开放"⇒ `mmtrTurnoutPosition`
   的"行折成位置"那一步会把新道岔从 0 折成 1。现象与 notes/117 同族，本轮没动它（本次卡死不需要），
   但凡是"新世界/新道岔跑出来位置不对"的现场，先看这里。

## 10. 追加：运营日（07:00 出库 → 23:00 回库完毕）怎么表达与怎么录

用户 2026-09-27 口径：**跑一个早 7:00 出库、23:00 回库完毕的**。引擎的作业单格式里没有"跑到某个
时刻就收车"这种东西（`loop` 是无限循环），所以运营日由**生成器**展开成显式步骤：

| 元素 | 写法 |
|---|---|
| 出库 | 第一圈的第一步 `MOVE_TO 下水1台`（厂内股道 → 站台），07:00 首发、180 s 一份（07:00/03/06/09） |
| 客运圈 | 路线原样重复 N 次（每圈 16 步：MOVE_TO+SERVE ×7 站 + 叶楼村 `CHANGE_ENDS`） |
| 圈数 N | `N = floor((回库截止 − 首发 − 回库预算 600 s) / 单圈估时 643 s)`；07:00→23:00 得 **88 圈**（第 4 列 87 圈） |
| **回库** | **最后一步 `MOVE_TO 本务股道`** —— 调度器本来就认这一步（"退库：车已回到本务股道"），不需要新步骤类型 |
| 收车 | `loop=false`：回库步做完作业单即 `DONE`，不再起新圈（车留在库里） |
| 时刻约束 | 所有步骤 `dueTimeOfDayMs = 23:00` ⇒ 任何一步晚于 23:00 完成就判失败（这就是"23:00 回库完毕"的判据） |

工具侧两处配套（都在 `mmtr-studio`，控制台一行没动）：

1. `StudioJobs` 新增运营日模式：`--startMs/--untilMs/--cycleMs/--cycles`；`--cycles` 用来做短验证；
2. `StudioRecorder` 新增 `--dayOffsetMs`：先把仿真空推到起始时刻再开始录 —— 否则"07:00 出库"要先把
   00:00–07:00 这 25 200 个空转 tick 也录进去（车都停在库里，没内容）；页面的日钟也跟着从那儿起算。
3. `studio.ps1` 一条命令：`.\mmtr-studio\studio.ps1 -Action all -StartTime 07:00 -EndTime 23:00`
   （生成运营日作业单 → 从 06:50 录到 23:05）。

**短验证（先跑 2 圈 + 回库，确认这条链通）**：4 份全部在 07:25–07:36 走到 `DONE`，日志里最后一次
`motion arrived at stop target …` 落在各自股道的远端（车真的开进库了），32.55 ms/仿真秒。

## 11. 硬规矩：仿真必须与**服务端行为完全一致**（用户 2026-09-27 口径）

原话："主要是要和服务端行为完全一致，不需要取巧。" 这条把"优化"的边界钉死了：

**必须一致的三件事**

1. **同一份引擎构件**（Studio 只依赖 `engine.jar`，不 fork 一套仿真）；
2. **同一段代码路径**（不许为了快而绕过某些层，例如不申请道岔、不重建区间）；
3. **同一节拍**：服务端 `Main.MILLISECONDS_PER_TICK = 10` ⇒ 每 10 ms 一次 `tick()`。
   而 `Simulator.step(ms)` 内部**按 1 s 切片**（`Math.min(millisElapsed, MILLIS_PER_SECOND)`），
   所以 `--tickMillis 1000` 的录制**不是**服务端行为：同一个 `tick(delta)`，delta 差 100 倍，
   凡是按 delta 累计的量（制动、停留计时、道岔申请窗口、扳岔时序）都可能不同。

⇒ 录制器已加 `--tickMillis`，**默认 10 ms（保真）**；粗节拍必须显式写 `--tickMillis 1000`，
且**报数字时必须标注节拍**（§9.6/§9.6b/§10 那些结论都是粗节拍，属"筛查"，不是服务端口径）。

**"不取巧"下的优化规则**

| | |
|---|---|
| **允许** | **逐位相同的**（bit-identical）改动：纯函数结果记忆化、同一 tick 内的重复计算合并、把纯查找换成等价索引 |
| **不允许** | 改采样步长 / 换近似算法 / 跳过计算 / 改节拍 —— 这些都会改结果 |
| **验收** | **golden trace 对拍**（同输入两次跑 → 轨迹逐字段相同）+ JFR 前后对比 |

**账要算清**（P0 实测，4 编组）：保真节拍 = **92.77 ms/仿真秒** ⇒ 16 h 运营日 ≈ **89 min**，
24 h ≈ **2 h 13 min**；粗节拍是 27 ms/仿真秒（≈3.4× 便宜，但结果不可当服务端）。
所以**保真模式要能日常用，必须先把 §12 那处合规的重复计算去掉**。
