## 1 今天"权威"是怎么定的（以及为什么它必须变成显式的）

答案在 `mmtr/game/fabric/src/main/java/org/mtr/mod/client/MmtrVehicleMotionClient.java:333`
的 `mmtrDisplayTick`：**每 tick 现算一次**——

```java
final double projected = sample.railProgress() + sample.speedMilliBlocksPerMs() * (now - sample.millis());
final double error = projected - vehicle.getRailProgress();
if (MmtrDriveInput.isLocallyDriving(vehicle.getId())) {      // ← 权威判据：一个**时间窗**谓词
    if (Math.abs(error) <= LOCAL_CORRECT_BASE_M + LOCAL_CORRECT_SECONDS * Math.abs(vehicle.getSpeed())) {
        return;                                              // 本地权威：下载只当对账
    }
    localCorrections++;
}
// 否则按 DISPLAY_TAU_MS 连续吸收，超过 DISPLAY_HARD_SNAP_M 就硬对齐
```

而 `isLocallyDriving`（`MmtrDriveInput.java:702`）= 坐在那辆车的司机位上 **且** `ownsCab`
**且** 距上次本地写的毫秒数 ≤ `LOCAL_HOLD_MILLIS(600)` **且** 没被解除。

**这个形状的问题**（也就是用户说的"需要一个明确的渲染交接"）：

1. **权威不是一个状态，是一个每 tick 重算的谓词**。于是"谁在开"这件事在任何时刻都**说不出来** ——
   日志里、HUD 上、别的子系统里都没有一个地方写"这辆车现在是本地权威"。
   它只在 600 ms 的窗口里成立，窗口一过期就**静默**回到服务端权威（没有任何一行日志）。
2. **交接点不可观测**：乘客看到的是"车忽然被拽了一下"，而日志里什么都没有。
3. **上行没有落脚点**：上行要回答"我什么时候开始上传"（= 权威在我），而一个时间窗谓词答不了
   —— 窗口每 600 ms 都可能闪断，上行就会跟着闪断。

所以第一步不是加协议，而是**把权威变成一个显式的、带理由的、有日志的状态**（§2、§3）。

## 2 权威状态机（显式两态 + 一个"正在交接"的过渡，本片落地）

**按车**一条记录（客户端侧；服务端侧将来用同一套词，见 §5）：

| 状态 | 含义 | 渲染读谁 |
| --- | --- | --- |
| `SERVER` | 服务端权威：下载的位置就是要显示的位置 | 下载（吸收/硬对齐，即今天那条路） |
| `CLIENT` | **本地权威**：我自己的物理是要显示的位置，下载降级为**对账信号** | 本地积分（下载只用于纠偏） |
| `HANDOVER_OUT` | **正在交还**（过渡态）：条件已经不成立，但还没确认服务端那一帧 | 下载（立刻回到吸收，但**不硬对齐**，避免交接瞬间被拽一下） |

### 迁移条件（**每一条都必须写得出理由，并且落一行日志**）

| 迁移 | 条件 | 理由（日志里照这句写） |
| --- | --- | --- |
| `SERVER → HANDOVER_OUT` | **交接那一刻**：`holdsCabOf`（我坐在那间驾驶室 + 钥匙是我的 + 本地闭环没被解除）**连续 2 tick** 成立 | "本地闭环条件成立（坐在驾驶室、钥匙在我手里）：开始交接，下载准备降级为对账" |
| `HANDOVER_OUT → CLIENT` | 连续 2 tick 里误差**收回到纠偏阈值以内**（`基准 + 系数 × 速度`） | "对账两拍无硬失配：本地权威生效，下载只用于纠偏" |
| `HANDOVER_OUT → SERVER` | `holdsCabOf` 不再成立，或出现**硬失配**（\|误差\| > `DISPLAY_HARD_SNAP_M`） | "交接未确认（对账硬失配 X m）：放弃本地权威，回到服务端" |
| `CLIENT → HANDOVER_OUT` | **任一**：① `holdsCabOf` 不再成立（离开驾驶室 / 钥匙不是我的 / 被解除）；② 对账误差 > 纠偏阈值 | "对账超阈值（X m > Y m）：交回服务端" |

三条设计意图，写下来免得以后被改掉：

1. **过渡态是必要的**：直接 `SERVER → CLIENT` 会让"本地物理"在某几拍里与服务端那一帧硬碰
   （本地刚起步、下载还在上一个位置），那时若按 `CLIENT` 去容忍，误差会一直挂着；
   若按 `SERVER` 去吸收，又会在交接瞬间拽一下。两拍的确认窗口把这两种都避掉。
2. **`CLIENT → SERVER` 必须能由"对账超阈值"触发**：那是唯一能自动发现"我这边算飞了/引擎拒绝了我的输入"
   的通路。上行落地之后，这一条同时是**上行不可信时把权威交回服务端**的入口（§4.4）。
3. **每次迁移只记一次**：不允许每 tick 重复记（notes/408 踩过这个坑 —— 到站通知 14 秒刷了 262 条）。

### 2.1 ★ 进入条件是"交接那一刻"，**不是**那个 600 ms 手柄窗口（实现时改对了）

第一版实现把"进入本地权威"的前提写成了 `MmtrDriveInput.isLocallyDriving` —— 那个谓词含一个
**600 ms 的手柄窗口**，于是语义变成"**先动手柄才旁路**"。这与用户口径相反：

> "在停站符合交接条件后，**明确赋予玩家驾驶的权利**并使玩家与列车之间绑定，此时玩家客户端下载
> 当前列车位置路径需要旁路至对账纠正路径"

所以实现里进入与待在是**同一个**条件：`MmtrDriveInput.holdsCabOf(vehicleId)`
（= 我坐在这辆车的司机位上 + 钥匙是我的或还无人持有 + 本地闭环没被解除），**不含任何时间窗口**。
那条窗口原来的职责（"证明引擎确实在收我这份值"）由两处更强的机制承担：
`noteEcho` 的**解除**（回声连续对不上就停用本地闭环，notes/407 那个 SYSTEM 钥匙的洞就是它抓的）
与 §2 的"对账超阈值退回"。`isLocallyDriving` 仍然存在，但它现在只服务于 `noteEcho` 那一支，
不再是权威判据。

## 3 渲染交接：渲染只读一处

- `mmtrDisplayTick` 的判据从 `MmtrDriveInput.isLocallyDriving(...)` 换成
  `MmtrAuthority.source(vehicleId) == CLIENT` —— **一处状态、一处判断**。
- `SERVER` 态：保持今天那条路（`DISPLAY_TAU_MS` 连续吸收，> `DISPLAY_HARD_SNAP_M` 硬对齐）。
- `CLIENT` 态：保持 notes/407 那条路（阈值内**一个字都不写**位置，超阈值才纠偏并计数）。
- `HANDOVER_OUT` 态：**吸收但放宽**（只吸收误差的一部分、不做硬对齐）—— 交接瞬间不许拽。
- 指示：`[MMTR-MOTION]` 那一行加 `权威=本地N/服务端M/交接中K` 三个计数（**可从日志证伪**）。

## 4 上行协议（客户端上传位置）—— 下一轮落地，契约先定

### 4.1 传什么、多久一次

| 字段 | 说明 |
| --- | --- |
| `vehicleId` | 哪辆车 |
| `railProgressM` | **我这边算出来的累计里程**（与引擎 `Vehicle.railProgress` 同一坐标系） |
| `speedMilli` | 我这边算出来的速度（m/ms，与 ① 同一口径） |
| `sequence` | 单调递增序号（丢包/乱序的判据，服务端只接受更大的） |

**频率 10 Hz**（与 ① 的 `MOTION` 同频，便于直接对照"上行领先了多少"）。

### 4.2 服务端做什么

1. **认人**：发件人必须是这辆车当前的**驾驶权持有人**（`mmtrDuties` 的 `DRIVING` 且 uuid 是它，
   或 `Vehicle.getMmtrCrewUuid()` 是它）——否则丢弃并记一笔（这是"谁能上传"的唯一判据）。
2. **认序号**：`sequence` 必须大于上一条（否则丢弃、不报错）。
3. **认合理性**（三条，任一不过就丢弃这条并**把权威交回服务端**，见 §4.4）：
   - 位移：`|railProgressM − 服务端当前值|` ≤ `最大可能位移(Δt) + 余量`（最大可能位移按该车动力学的
     最大加速度反推，余量取 5 m）；
   - 单调：不允许倒退超过 `1 m`（倒退是换端/连挂的信号，那两种情形本来就不该在本地权威下发生）；
   - 在轨：上传的位置必须落在**该车腿表覆盖的里程范围**内（走出阴影 = 不知道自己在哪根轨上）。
4. **写进权威**：`vehicle.mmtrApplyUploadedMotion(railProgressM, speedMilli)`（服务端侧），
   并且**这一拍跳过它自己的位置积分**（否则两个积分器会互相拉）。
5. **不新开广播**：① `MmtrVehicleMotionSync` 本来就是每 tick 读**权威车辆**的
   `railProgress` 打包发出去的 ⇒ 观察者拿到的是**上传后的位置**，不需要第二条中继通路。
   这条是本文最重要的省事结论：**上行只改"权威从哪来"，不改"怎么发出去"**。

### 4.3 谁写哪些字段（与 notes/369 的 ①② 所有权表衔接）

| 字段 | `SERVER` 权威 | `CLIENT` 权威 |
| --- | --- | --- |
| `railProgress` / `speed` | 引擎自己的积分（今天） | **上传**（引擎跳过自己的积分） |
| 手柄六件套 | C2S `PacketDriveControl`（今天） | 仍然 C2S（手柄本来就是我发的，upload 只补位置） |
| 门 / 旗标 / 灯光 / 钥匙 / 夹紧量 | 引擎（今天） | **不变**（notes/369 的 ② 继续拥有） |

### 4.4 上行不可信 → 权威交回服务端（必须有）

上行一旦通过，服务端就**部分让出了权威**；所以必须有一条**自动夺回**的路：
§4.2 第 3 条任一不过 ⇒ 丢弃该条 + 该车权威交回 `SERVER` + 记 `[MMTR-AUTH] … 上行不可信（<哪条>）：
权威交回服务端`。客户端下一次收到 ① 的硬对齐自然会跟着走（那条路今天就有）。

### 4.5 开关

`-Dmmtr.upload=false`（**默认 false**）：关掉时上行包一条都不发、服务端一条都不收，行为与今天
**逐位一致**。默认值在实测出 §4.2 第 3 条的三个界（尤其是"最大可能位移"）之后才改成 true。

两端各自读同一个属性名（`Vehicle.mmtrUploadEnabled()` 与 `MmtrVehicleMotionClient.UPLOAD_ENABLED`），
所以**必须两端都打开**这条路才成立；只开一端时另一端的日志会直接说出来（服务端侧：
`[MMTR-UP] 丢弃（…）` / `[MMTR-AUTH] …`；客户端侧：上行计数一直是 0）。

实机打开方式（**不改任何仓库文件** —— 属性跟着 JVM 环境走，`runClient` / `runServer` 两个 fork 出来的
JVM 都会继承它）：

```powershell
# 两端都开（当前会话内）
$env:JAVA_TOOL_OPTIONS = '-Dmmtr.upload=true'
# 服务端：pwsh -File mmtr\scripts\dev-server.ps1
# 客户端：Set-Location mmtr\game; .\gradlew.bat -I ..\..\sandbox\dev-run\pathcache-ab.gradle :fabric:runClient
```

`dev-server.ps1` 自己会把 `-Djava.io.tmpdir=…` **前置**拼进同一个变量（它保留已有的值），所以上面这句
不会把它的临时目录设置顶掉。

### 4.6 实现记录：落地时才暴露的几件事（每条都写了理由）

1. **"跳过自己的积分"落地为"算出来但不采纳"**，不是"连算都不算"。
   - 理由：这一拍引擎还要用它自己的动力学产出 **HUD / 气压读数**（`mmtrPublishAirReadings`）与保护判定的
     输入；连算都不算会让司机面板上的管压/缸压**冻住**，那比多算一遍更糟。
   - 落点：`Vehicle.mmtrApplyUploadAuthorityToTick(ownDistance, now, engineGrip)` 插在那一串闸门
     **之后**、停点夹紧**之前** —— 引擎算出来的 `integratedDistance` 被换成"上传驱动的位移"，而停点
     收口、走行器前进、腿表延长、到站判定（`mmtrMotionArriveAtStopTarget`）全部照旧。
   - 到站这一条特意核对过：客户端在站台停稳时上传的位移是 0，那一拍走的是 `integratedDistance == 0`
     的"已经停在有效停车点上"那一支（`Vehicle` 里 `speed == 0 && brakeTargetActive && …`），
     它同样会登记到站 —— 所以"授权在客户端"不会把到站/交接条件吃掉。

2. **两次上传之间按上传速度推算**：位置 = 上传位置 + 上传速度 × 距那一帧的时间。
   - 理由：① 是 10 Hz 而引擎 tick 是 20 Hz。若"两次上传之间不动"，每隔一拍就会出现"速度 ≠ 0 而
     位移 = 0"（HUD 与诊断读数自相矛盾），腿表也跟着一格格跳。按上传速度推算与客户端自己那一份
     **同一口径**，不引入第二个积分器（引擎自己的动力学仍然不采纳）。
   - 不影响"领先"：下一帧到达时的残余是 `½·a·(0.1 s)²` ≈ 0.5 cm 量级，而且**不累积**（每帧重新锚定）。

3. **引擎的否决优先于上传**：钉住（位置锁死）、闭塞停车（前方区间被占）、制动包线已经咬住的停车
   （授权接近车钩间隙）—— 这三种"这一拍不准动"照旧由引擎说了算；这种时候**只按住、不交回**
   （闭塞与包线都是暂时的，交回会把一次正常等待变成一次权威切换）。

4. **交回之后有 3 秒隔离期**（`-Dmmtr.upload.quarantineMillis`）。
   - 理由：没有它，"交回 → 下一帧又接管"会每帧来回刷（尤其保护制动那一支），日志与车辆状态都失去意义。
   - 代价两条，都认：保护制动结束后最多 3 秒才可能重新交出权威；保护制动**期间**根本收新帧
     （`mmtrProtection` 那条闸门），所以不会出现"引擎刚刹住又被上传开走"。

5. **"认人"由值守状态机判，不由引擎侧那段校验判**。
   - `PacketMmtrUploadMotion.runServer` 问一次 `simulator.mmtrDuties.of(玩家)`（`DRIVING` 且车辆是本车），
     把结果当 `holder` 传进引擎 —— 判据只有一处（notes/408 §2.4：值守状态机是"这辆车归谁"的真源），
     引擎侧那一段就能在单测里把其余几层（开关 / 序号 / 合理性 / 隔离期）各演一遍。
   - 连带一条口径：**不是持有人时"只丢帧、不交回"**（本来就没在手）。并且**每种丢弃都有一行
     `[MMTR-UP]`**（1 秒最多一行）—— "上行一条都没生效"如果是静默的，这条路第一个坑就会变成谜。

6. **客户端只在"权威 = 本地"时才发**（`MmtrAuthority.isClient(vehicleId)`），10 Hz；序号
   **跨交接不重置**（服务端第一帧不看序号，只在同一个连续窗口里比大小 —— 拿旧司机的大序号去卡新司机
   会把交接卡死）。

7. **驾驶权交接/归还立刻夺回**：`Simulator.mmtrJobTakeover` 成功后调
   `mmtrRecallUploadAuthorityForNewHolder(driver, …)`（**同一个人重复接管不动他的上行**），
   `mmtrJobRelease` 调 `mmtrRecallUploadAuthority(…)`。加上 §4.4 的走廊看门狗（500 ms 没有帧）与
   保护制动夺回，一共四条路能自动把权威拿回服务端。

8. **看门狗必须在 `simulateMmtrMotion` 的早退之前**：`mmtrMotionStoppedAtTarget` 那一支会直接
   `return`，看门狗放在它后面的话，"客户端停帧而车正好停在停车点上"会让"权威在客户端"永远挂着。

9. **上行与 `-Dmmtr.localdrive` 是串联的**（A/B 时要注意）：客户端的"要不要传"取决于
   {@code MmtrAuthority.isClient}，而它进入"本地"的条件是 {@code MmtrDriveInput.holdsCabOf}
   —— 那个谓词的第一项就是 `mmtr.localdrive`。于是：

   | 客户端开关 | 本地闭环 | 位置权威 | 上行 |
   | --- | --- | --- | --- |
   | `-Dmmtr.localdrive=true`（默认）+ `-Dmmtr.upload=true` | 有 | 可以到"本地" | **发** |
   | `-Dmmtr.localdrive=false`（notes/407 的对照趟） | 无 | 停在"服务端" | **不发**（没有本地权威可传） |

   这不是缺陷，是同一件事的两面：**没有本地闭环就没有可供上传的权威**。所以 notes/407 的对照趟
   与上行的实机验证要分两次跑，不要指望一趟里同时量到两边的数。

10. ★ **实机抓到的单位错（2026-10-09，用户报"经过一个节点速度就归 0"）**：
    纠偏阈值那一项本来是"**半秒的余量**"= `0.5 s × 速度(m/s)`，而 `Vehicle.getSpeed()` 返回的是
    **m/ms** —— 漏掉 ×1000 之后，120 km/h 只加 `0.017 m`，阈值事实上**恒为基准 8 m**。速度一起来，
    正常的上行提前量（`速度 × RTT`，90 km/h ≈ 4 m）加上 ① 帧龄造成的投影误差（客户端掉到 2~5 帧/s
    时帧龄 200~500 ms ⇒ 5~12 m）就每拍击穿 8 m ⇒ 权威在"本地 ↔ 交接中"之间翻转。实机读数：

    ```
    [19:06:37] [MMTR-AUTH] 车 -710282462574849916：本地 → 交接中（对账超阈值（9 m > 8 m）：交回服务端）
    [19:06:37] [MMTR-AUTH] 车 -710282462574849916：交接中 → 本地（对账两拍无硬失配：本地权威生效…）
    ```

    修法：`× INTERNAL_SPEED_TO_SI(1000)`（阈值在 90 km/h 变成 8+12.5=20.5 m、120 km/h 变成 24.7 m，
    与 notes/407 的原意一致）。**这一条同时是"三个界"之外的第四个界**：它是**显示侧**的门，
    前三个是**引擎侧**的门，两边都要量。

11. ★ **本地权威期间不许用 ① 覆盖本地速度**（同一个实机现场的另一半）。位置早就不写了，速度却一直
    被 ① 无脑覆盖，而引擎那一拍**自己**算出来的速度在"被权威扣住 / 到点夹紧 / 换端 / 无任务"这些拍上
    是 0 ⇒ 本地物理被按停 —— 那正是"速度归 0"这四个字。改成：`MmtrAuthority.isClient(车)` 为真时
    只记账（这一帧仍进显示模型的误差缓冲），不写速度；权威一交回服务端立刻恢复写。
    口径与位置完全一致：**本地权威 ⇒ 下载降级为对账，只记账不接管**。

12. ★ **本地权威期间跳过"腿表阴影末端夹紧"**（同一个实机现场的第三条；也是唯一一条**没取到读数**的改动）。
    引擎 `simulate()` 里有一条"车头走到腿表总长就夹停"的兜底（`mmtrRunTotalDistance`）。客户端镜像的腿表
    是**向前伸**的（§6.2/§6.3 实测表末端在引擎位置之前 100–124 m），但那个末端只有在**服务端把腿表延长**
    之后才会跟着前移 —— 而位置权威在客户端时，**服务端延长腿表靠的正是客户端的上行**（先有位置、后有腿）。
    于是可能出现"客户端被自己镜像的旧表末端夹停、服务端等不到新位置、腿也不延长"的死锁。
    改成：`mmtrLocalAuthority` 为真时**只记账不夹停**
    （`mmtrNoteSkippedShadowClamp` → `[MMTR-CLAMP] 车 X：本地权威 —— 腿表末端夹紧已跳过（车头超出阴影 N m）`）。
    - **读数：`[MMTR-CLAMP]` 计数 = 0**（`clamp-client.out.log`，19:20–19:34 全程 200 MB 日志）。
      所以这一条**既没被证实也没被证伪** —— 本次驾驶里那个夹紧点根本没走到。它是**防死锁的保险**，
      要判它有用得专门造一次"客户端跑到表末端而服务端还没延长"的场面。**留着，但不算"已实测"。**

13. ★★ **收尾对账时抓到的真缺口（本轮唯一没完全达成 brief 的一处）：客户端"本地权威"的进入条件

14. ★★ **没有驾驶权的人不许把引擎的 AI 挤下车**（`PacketDriveControl`，用户报"车不加速不正常运营"的根因）。

    就足以让一列正在自动运行的车把 AI 让出去 —— 而这个人如果还没拿到驾驶权（值守 `ABOARD`），
    他也开不动（引擎只认驾驶权持有人）⇒ **谁都不能开车，车停在半路**。实机（车 3210607068659547126）：

    19:46–19:52  每 2 s：[MMTR-DRV] 收到操纵：车=3210607068659547126 油门=0 制动=0 换向=1 司机=aeaca7ad-…

## 5 服务端侧的同一套词（本轮落地）

服务端也需要知道"这辆车的权威在哪"，理由：它要决定**跳过不跳过自己的积分**（§4.2 第 4 条）。
口径与客户端**同一套三态**（`SERVER / CLIENT / HANDOVER_OUT`），由 `mmtrDuties` 的
`DRIVING` + 钥匙持有人推出，**不新开一张表** —— 值守状态机已经是"这辆车归谁"的真源
（notes/408 §2.4），权威只是它的一个**函数**。

落地形状（`Vehicle`）：`mmtrUploadAuthority`（布尔 = 权威在客户端）+ 最后一条被接受的帧
（位置/速度/序号/时刻/发件人）。日志用**与客户端同一套词**、同一个前缀：

```
[MMTR-AUTH] 车 -6785950461307398693：服务端 → 本地（接受上行第一帧：阿甲，序号 1，与引擎当前差 10 m）
[MMTR-AUTH] 车 -6785950461307398693：本地 → 服务端（上行不可信（位移 400 m > 这一拍的最大可能位移 5 m…）；3000 ms 内不接受新的第一帧）
```

于是**一次驾驶的两端日志可以逐行对照**：客户端说"服务端 → 本地"（交接那一刻），服务端也说
"服务端 → 本地"（接受上行第一帧）—— 两条之间的时间差就是"客户端先动手、服务端多久认账"。

### 7.1 落地时抓到的一个真 bug：**负的车辆 id 被当成了"同名多辆"的哨兵**（2026-10-09）

`findVehicleIdByJobId` 原来是"返回 long，{@code 0} = 没有，{@code -1} = 同名多辆"。而**车辆 id 是随机
的有符号 long**（现场随手就是 `-6810673503153593564`、`-8180550217393323477`）—— 于是派车指令
`assign` 里那句 `if (vehicleId < 0)` 会把**一个合法的负 id** 读成"场上有多辆车挂着同一个车次"，
现场报错"场上有**多辆**车都挂着车次 D-020"，而场上明明只有一辆。

- 为什么它会**时红时绿**：单测每次 spawn 的 id 都是随机的 ⇒ 约 50% 概率落到负数 ⇒ 同一份代码
  跑两遍结论不同。这正是"哨兵值不许与值域重叠"最典型的翻车形状。
- 修法：值域里有负数的东西**不许用负数当哨兵**。新增
  {@code MmtrDutyRegistry.findVehicleIdsByJobId(String)} 返回**全部匹配的车辆 id**（去重），
  `assign` 改成看 `size()`（0 = 没有，>1 = 多辆，1 = 唯一）；
  旧的 `findVehicleIdByJobId` 保留成"唯一匹配才给 id，否则 0"的便利口，**不再有 -1 这个约定**。
- 单测当场就抓到了它（`assignResolvesTheJobIdAndKeepsTheGivenCabSpec` 在两个连续 run 里一次绿一次红），
  所以这条记在这里而不是当"偶发"丢掉。

## 8 风险

1. **两拍确认窗口**会把交接推迟 ≥100 ms。可接受（那两拍本来就在"刚坐进驾驶室"的窗口里），
   但如果实测发现在起步瞬间仍被拽，就把它缩到 1 拍并把阈值调宽。
2. ~~**`isLocallyDriving` 的 600 ms 窗口**是这一切的地基~~ —— **已解决，见 §2.1**：
   权威的进入/待在条件都不再用那个窗口（改用 `holdsCabOf`），所以 AFB 巡航（手柄几分钟不动）
   不会让权威掉回服务端，也就不会"每 600 ms 交接一次"。`isLocallyDriving` 只剩 `noteEcho` 那一支在用。
3. 上行一旦开着，**服务端派生的所有东西**（占用/信号/S1 闭塞停点/LZB/AWS/SPAD/到站判定）

   （§4.2 第 3 条），且必须留 §4.4 的夺回路径。

### 10.2 ①② 已修（2026-10-09 21:0x，同一轮）

**① 引擎侧 `Vehicle.mmtrAcceptUploadedMotion` 两处**（正是上面那两条读数的来源）：

1. **位移基准改成"上一条被接受的帧"**：持有权威期间 `deltaM = railProgressM − mmtrUploadProgressM`
   （而不是 `− mmtrMotionWalker.distanceM()`）。理由与"倒退比的是上一条被接受的帧"完全同源
   （那一条本来就写着长注释）：引擎按住车时不采纳上传位移 ⇒ 引擎位置一直落在客户端后面 ⇒
   拿它当基准会把界里那 5 m 余量耗光 ⇒ 实机 `位移 5 m > 界 5 m` 每 3 秒收一次权。
   第一帧仍然跟引擎当前值比（它必须落在 30 m 交接窗口里）。
   ⇒ 连带的口径变化：`[MMTR-UP]` 记账里的"位移最大 Xm"从此是**每帧位移**（与它被比较的那条界同口径），
   不再是"客户端与引擎的累计差"。
2. **倒退界看司机意图**：`mmtrActiveControl.getReverser() < 0`（司机挂了反方向）时倒退允许量取
   `maxMoveM`（与前进同一条界），否则仍是 1 m；被拒时的理由里会写明"司机已挂反方向"。

**② 客户端侧 `MmtrAuthority` 上闩（不加协议）**：`CLIENT → HANDOVER_OUT` 若由**对账超阈值**触发，
则**上闩**：误差必须**连续**收在纠偏阈值以内 `RECONCILE_LATCH_MILLIS = 1500 ms` 才解闩、才允许再进
本地权威。引擎真的在按住我时误差收不住（下载那份不动、本地一直推），于是闩一直挂着 ——
本地权威不再"退回去 → 2 拍后又进来推车"，`交回 67 次` 那种风暴不会再出现。闩上/解闩各一行
`[MMTR-AUTH]`（`noteReconcileLatch`，理由只在变化时记）。

★ **② 是"权宜但正确"的一半，真正的那一半还没做**：客户端手里**已经有**引擎的灯色
（`PacketMmtrRoutes` 的 `lampAspects` / `lampRails`，见 `MmtrClientRoutes.lampAspect/lampRails`），
所以正确形状是"**守着我这条轨的灯是红 ⇒ 不进本地权威**"（把 `refusal` 拼成
"引擎给这条进路红灯"）—— 缺的只是一段"车头在哪根轨 → 那根轨归哪盏灯"的取数。②落地后
司机会在红灯前**推不动**（而不是穿过红灯），但**不会被来回拽**。

#### 为什么引擎放它过去了（三条叠在一起）

1. **00101 当时在"上行权威"里**：`[MMTR-AUTH] 21:02:29 … 服务端 → 本地（接受上行第一帧：Shuisoi，序号 1，差 0 m）`，

   `driverMayOverrun=true` 把 `mmtrBlockedWaiting` 那一支**显式豁免**了（"司机优先"）。

   而上传帧带的速度是 **0**（客户端"停着"时也在传位置），`DynamicsEnvelope.requiresBraking(0, …)` 永远为假
   ⇒ 位置被一帧一帧"传送"过界限，保护无从咬合。

#### 修 A（本轮落地）：**占用/几何类硬界限**（`Vehicle.mmtrOccupancyStopM`，§4.6 第 16 条）

- `computeMmtrBlockStopM` 里把**规则 ①（同轨占用面/编组体）②（前方区间被占）④（岔区清限）**的 min 单独留一份
  ⇒ `mmtrOccupancyStopM`。规则 ③（进路没设好）与 ⑤（红灯）**不进**这一份：它们仍可按响应键闯（真车 SCR 口径）。

  1 s 一条 `[MMTR-SIG] 硬界限夹住上行权威：…（客户端看不见前方那列车，引擎不许跟过去）`。

- 例外：手上有**调车授权**（副显示/呼唤显示）时不设硬界限 —— 连挂本来就要贴到车钩间隙
  （规则 ① 已把间隙换成 `MMTR_COUPLER_GAP_M`）；少了这个例外连挂永远贴不上。

**测试守护**：`MmtrMotionBlockingTests#anUploadedFrameMayNotCarryTheTrainPastAnOccupancyFace`
