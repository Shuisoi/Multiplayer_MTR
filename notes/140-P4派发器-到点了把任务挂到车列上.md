## 1. 派发器长什么样

```
交路（P3）→ 任务序列（MmtrPlanTasks，一步一个任务）→ 派发器按计划时刻挂到具体车列（MmtrPlanDispatcher）
```

`MmtrPlanDispatcher` 是一个**纯状态机**，与世界的接口只有三件事（`World`）：

```java
long[] idleVehiclesForYard(long yardSidingId);   // 这个车场里谁空着
boolean isVehicleIdle(long vehicleId);           // 它还空着吗
boolean dispatchTask(long vehicleId, MmtrTask task);  // 挂这一步
```

于是"一整天几百步"可以在用例里毫秒级跑完（假世界），而适配层（`Simulator` 内部类
`MmtrPlanWorld`）只管把这三件事接到股道/车辆/任务上。**这也是这份设计反复强调的分界**：
生成与编排是纯函数，世界只在边界上出现。

四条验收逐条有断言（`MmtrPlanDispatcherTests` 9 例）：

| 验收 | 怎么钉的 |
| --- | --- |
| ① 一趟完整服务：出库 → 各站（到站+停站）→ 终点处理 → 回程 → 回库 | 用例推进一整天，断言**派发顺序**逐条对（`DRIVE_TO_PLATFORM→2001`、`→2002`、`STATION_SERVICE→2002`、…、`CHANGE_ENDS`、`→2002`（回程）、`DRIVE_TO_SIDING→42`） |
| ② 跨 tick 不重复派发 | 同一时刻连 tick 5 次，`dispatchedTotal` 不变；没到点不派；到点只派一步 |
| ③ 任务类型与 `MmtrTaskKind` 对应正确 | `MmtrPlanTasks.terminalTaskKind` 三态 + 环线不处理；全序列只出现四种既有类型（**没有新词汇**，设计 §1.1） |
| ④ 车列被占用时重试而不丢趟 | 没车 → 原地等（不计跳过）；挂不上 → 同一步重试（`retryCount` 计数）；车中途被开走 → 解绑重找，已派步数不变 |

**"派出去才前进"这条不变量是本片的命根子**：注掉它（`if (true) state.dispatchedSteps++`）→
8 例里 **5 例立刻红**。这就是"用例有没有牙齿"的证据。

## 2. 任务展开（设计 §3 / §5.2）

| 交路里的那一条 | 展开成 |
| --- | --- |
| 出库 | `DRIVE_TO_PLATFORM`（车场 → 首发站台），计划时刻 = 首发时刻 |
| 一趟车的中间站 | `DRIVE_TO_PLATFORM`（到站）+ `STATION_SERVICE`（开门—停站—关门） |
| 一趟车的终点站 | 同上 + **终点处理**：`CHANGE_ENDS` / `DRIVE_TURNBACK` / `DRIVE_TO_SIDING` |
| 环线 | 不处理终点（继续跑） |
| 回库 | `DRIVE_TO_SIDING`（末站台 → 车场股道） |

两条细节写进了实现：**一趟车的起点站不停站**（车本来就在那儿），以及**"回库"不会连着来两次**
（终点处理本身就是回库时，末端那条不再重复）—— 后者是"让车白跑一趟"的经典写法。

## 3. 真实走行时间（把 P1 那条边界接上）

`MmtrRailTravelTimes`：站间里程从**轨图**算（`MmtrRailDistance`，轨为边、节点为位置的 Dijkstra），
除以编组速度得时间。两条判断值得记下来：

- **站台就是一段被标记的轨**（`SavedRailBase.mmtrGraphRail()`，与 `MmtrRunPlanner` 解析站台目标同一条路），
  所以"站台 → 轨"不需要另做匹配；
- **两站之间要有一根连接轨**才测得出里程：两个相邻站台若直接共用端点，它们之间的里程就是 0。
  第一版夹具就是这么搭的，于是断言拿到 0 而不是 20 m —— **夹具比实现更早暴露了模型的语义**
  （测的是"两站之间的轨"，不是"站台那根轨的长度"）。

走不到时（站序与轨图对不上）**不给数字**：里程标 `-1`、时间 0、`describeMissingLegs()` 点出是哪一段 ——
宁可让计划里那一段显示成 0 分钟（看得出来的错），也不编一个假数字。

## 4. 装机前推演不出来的两件事（都是现场/推演逼出来的）

### 4.1 单位错：纪元毫秒 vs 当日毫秒

派发器第一版拿 `currentMillis`（纪元毫秒，1.7×10¹²）去比 `task.earliestMs`（当日毫秒，`07:00 = 25_200_000`）
—— **"到点没有"永远成立**，所有步会一起涌出去。作业单调度器的口径是
`dayTime = (t - anchor) mod DAY`，所以派发器也照这个来，并且**优先共用作业单调度器的锚点**
（`MmtrJobScheduler.getAnchor()`，本轮新加的只读出口）：两套编排的小时数必须是同一个意思，
否则运营台上"作业单 08:00"与"线路 08:00"会差出一段，谁也说不清哪个对。

### 4.2 迟到的步不许补跑

`dayTime >= earliestMs` 这个判据本身还意味着：中午开机时"早上 07:00 的出库"会在 19:00 被执行。
设计 §7 的口径是**过去不可改**（已完成的趟次是事实，也是"实际到发"的数据源），
所以加一条宽限：迟到超过 `LATE_GRACE_MILLIS = 10 min` 的步**跳过并计数**（`skippedSteps`），
不补跑。用例 `staleStepsAreSkippedInsteadOfReplayed`：09:00 才开机 → 整天的短交路逐步跳过、
一步都不派、也不会卡住。

**旧的空壳还留着（`MmtrPeriodicTaskSource` 没删）**，但它的位置已经被真正的派发器接管 ——
删掉那个类是收尾（等确认没有任何脚本/文档还在引用它）。

## 5b. 装机现场（真世界：真站台/真股道/真车）

配一条真线路（3 个真站台 + 全天 10 min 密度 + 1 组车底 + 车场 987654 的真股道），现场读数：

```
[MMTR-PLAN] 交路 L1：N=1（ring 493s / 高峰间隔 600s），1 辆车 288 趟（走行时间按轨图算）
[MMTR-PLAN] 派车 开往站台 #-16333677002112739 到站停稳 → 车 -7657540310698289811（L1/C1/001）
[MMTR-DRV]  motion auto run enabled
[MMTR-MSG]  motion mission PASSENGER self-armed to rail … stop @453m
mmtr-plan-diagrams → dispatchedTotal=1 retryCount=0 vehicle=-7657540310698289811
                      steps=1442（一整天）next=DRIVE_TO_PLATFORM→9181441402015485493
```

也就是：**ring 是真实轨图算出来的**（三站 493 s）、**N=1**、**分到了真车**、
任务类型正确（`PASSENGER`）、目标正确、**同一辆车**跑（`retryCount=0`）、
派完一步就等它跑完再派下一步（25 秒后仍停在第一步，因为车还在开）。

### 装机抓出的第三个缺陷：**"忙"不等于"被抢"**

第一版现场是**五条派车日志、五个不同的车辆 id** —— 一趟车的每一步都换一辆车。
根因：派发器分不清"车正忙着我派的那一步"与"车被别人占了"，于是每次派完就解绑、下一 tick 重新找车。
修法：`World` 多一条 `isVehicleRunningTask(vehicleId, taskId)`（任务挂在 mission 上，按 id 认领），
状态机于是有三种情形：还在跑我的活（等）/ 空了（我的活跑完，继续）/ 忙别的（解绑重找）。
用例 `oneWorkingKeepsTheSameVehicleForTheWholeTrip`（两辆车可用、活不自动完成、断言全程只用第一辆）。

> 三条现场缺陷（单位错、迟到补跑、忙≠被抢）**没有一条是靠读代码找出来的**，都是"跑起来看读数"。
