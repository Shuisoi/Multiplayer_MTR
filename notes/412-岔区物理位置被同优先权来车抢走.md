# 412 岔区：同优先权来车靠 owner id 抢走已按住的物理位置（+ expirePhysical 的 null 拆箱 NPE）

## 1 症状（引擎用例 `MmtrRouteConflictTests` 时红时绿）

`engine :test --tests "*Mmtr*"` 里只剩这一处红，而且**两条用例轮流红**：

| 轮次 | conflict 用例 | follow 用例 |
|---|---|---|
| 1 | FAIL（等待理由点名的是 `0,0,0` 而不是 `-20,0,0`） | FAIL（后车第 1 tick 就 armed） |
| 2 | ok | FAIL |
| 3 | ok | ok |
| 4 | FAIL | FAIL |
| 5 | FAIL | FAIL |
| 6 | FAIL | ok |

同一份代码、同一个顺序，结果随机 ⇒ 一定有"随机输入"进了判定。

## 2 读数（诊断埋点，6 轮）

在 `conflictingRoutesQueueAtTheThroatAndTheSecondSetsAfterTheFirstClears()` 里打印两层持有表，
`v1` = 前车（从直股 y1 进咽喉）、`v2` = 后车（从岔股 y2 进咽喉）：

```
失败轮（round 1）：
 刚派车 v2：  N(-20,0,0) phys=v1/0  legViaY1=v1  legViaY2=null   reason2=物理道岔 -20,0,0 被 v1 按在位置 0 …
 v2 派车后 1 tick：N(-20,0,0) phys=v2/1  legViaY1=v1  legViaY2=v2    reason2=物理道岔 0,0,0 被 v1 按在位置 0 …

通过轮（round 2）：
 刚派车 v2：  N(-20,0,0) phys=v1/0  legViaY1=v1  legViaY2=null
 v2 派车后 1 tick：N(-20,0,0) phys=v1/0  legViaY1=v1  legViaY2=null   reason2=物理道岔 -20,0,0 被 v1 按在位置 0 …
```

也就是说：**后车在 1 tick 之内把咽喉道岔的位置从 0 扳成 1 并拿走**（`phys` 从 v1 变成 v2），于是它
的进路在 N 处不再被挡，一路走到下一处岔口 `0,0,0` 才排队 —— 用例的"等待理由必须点名 `-20,0,0`"
与"后车在咽喉外等"两条判据同时落空。

引擎日志里那一行把原因写得很直白（`confdiag-1.log`）：

```
[MMTR-PT] 优先权：把道岔 -20,0,0 的位置从 v1913021474444274896（无计划） 交给更该先走的 v1549095188365414779（无计划）
```

**"（无计划）交给（无计划）"** —— 两边服务等级、车号、计划时刻**全都一样**，根本谈不上优先级。

## 3 根因

`MmtrPointAuthority.request()` 的"优先权收位"分支用 `outranks(...)` 判断来车是不是更该先走：

```java
// outranks：服务等级/车号 → 计划时刻 → owner id
if (otherPriority != minePriority) {
    return otherPriority < minePriority;
}
return otherOwner.compareTo(mineOwner) < 0;   // ← 最后一档
```

最后一档的输入是 `owner = "v" + vehicleId`，而**车辆 id 是随机的**。它的本意是给"让位"判断一个
**不对称**的口径（两边同时让位 = 回到振荡，见 notes/149/155），但同一个函数被**收位**（把别人已经
按住的物理位置拿走）借用了 ⇒ 随机 id 决定了"谁的道岔被抢走"。

- 抢位这一档的其它闸门都拦不住它：净空闸过（前车还在自己股道上，没压住岔区）、前车不在岔轨上；
- 两车走的是**不同 via**（y1 / y2），所以逐进向那一层（`requestPerApproach`）也不会替物理层拦；
- 现场后果不是测试洁癖：**已经按住的岔位会没理由地易主**，前车进路变 PENDING 重算、后车冲进咽喉
  才被下一处岔口拦下。真实比例 ≈ 一半（取决于两个随机 id 的字符串序）。

## 4 修法（动一处）

```java
// 抢位只认"真档位"：等级/车号严格更优，或计划时刻严格更早
if (outranksStrictly(priorityMillis, owner, holder.priorityMillis, holder.owner)
    && positionChangeBlockedReason(...) == null
    && !holderStillOnNodeRails(nk, holder)) { ... }
```

新增 `outranksStrictly(...)`：与 `outranks(...)` 同前两档，**去掉 `owner.compareTo` 兜底**（同优先权 ⇒ 不收位，
后车排队）。`outranks` 本身不动 —— 让位判断仍然需要那个不对称口径。

## 5 判据（确定性守卫）

`MmtrPointAuthorityTests#anEqualPriorityNewcomerCannotStealAHeldPhysicalPosition()`（新）：

- 自建咽喉：`y1`（直股，从 `-40,0,0` 来）、`y2`（岔股，从 `-40,0,10` 来）、`throat`（通向 `0,0,0`），
  用真 `Simulator` 的 `mmtrPointAuthority`（真道岔/净空/占用查询）；
- 前车 owner 取 **`"vB"`**、后车取 **`"vA"`** —— 故意让 `owner.compareTo` 指向"该抢"的方向，
  所以**修前这条是确定性的红**（不是靠运气复现）；
- 断言：前车 `GRANTED` 且 `physicalHolder=vB / position=0`；后车 `QUEUED` 且**位置还是 vB/0**；
- 第二节：真优先级更高（计划时刻严格更早）的来车**仍然收得走位置** —— 修的是"同优先权靠 id 抢"，
  不是取消优先权（否则就把 notes/151 的功能删了）。

## 6 顺带逮到的第二个 bug：`expirePhysical` 的 null 拆箱 NPE

写守卫用例时第一版直接 NPE：

```
java.lang.NullPointerException: Cannot invoke "java.lang.Boolean.booleanValue()" because the return value of
  "MmtrPointAuthority$HolderOccupancy.ownerIsOnNodeRails(long,long,long,String)" is null
    at MmtrPointAuthority.expirePhysical(MmtrPointAuthority.java:1310)
    at MmtrPointAuthority.physicalHolder(MmtrPointAuthority.java:1149)
```

`HolderOccupancy` 的返回是**三态**（`TRUE` 在岔轨上 / `FALSE` 不在 / `null` 查不出来，接口注释写得很清楚：
放位按"不在"、续期按"在"），但这一行是裸调用 + 自动拆箱 —— **null 直接抛异常**。
而"查不出来"在生产里是常态之一（owner 是 `"v"+车辆id`，车辆被移除、或存档恢复出一个不在车辆表里的
owner，占用查询就答 null）。权限层在 tick 里抛异常 ⇒ 那一拍的联锁判定整条断掉。

修法：`!Boolean.FALSE.equals(holderOccupancy.ownerIsOnNodeRails(...))` —— 与接口注释同一条口径
（查不出来按"在"处理，宁可不放位），也与同文件里 `holderKnownAwayFromNodeRails` 的写法一致。
