# 234 · 删除轨道：数据是按 hex 分片的文件，删完必须重启

> 用户口径（2026-09-24）：「把 4000 那边站台后面的轨道删除」——
> 即删掉末站（站台段 z=3982..4082）之后的那段延伸轨（z=4082..4222，含一组剪刀渡线）。

## 1. 为什么不能像 `rail add` 那样热删

指令面只有 `rail add` / `rail list`（`MmtrRailCommands`），**没有 remove**；
HTTP 面上也没有 `delete_data` / `DeleteDataRequest` 的入口（`SystemMapServlet` 的 case 列表里没有）。
所以删轨只有一条路：**停服 → 删数据文件 → 起服**（跑着删会被引擎的下一次存档写回来）。

## 2. 数据在哪、怎么分片

```
world/mtr/minecraft/overworld/rails/<XX>/<完整hex>
```

`<XX>` 是**末端那两个 hex 字符**（不是首两个）。实测：末端 `102E`(z=4142) 在 `rails/2E/`，
`1056`(4182) 在 `rails/56/`，`107E`(4222) 在 `rails/7E/`，`0FF2`(4082) 在 `rails/F2/`。
**文件名就是整条 hex**，所以按精确名字匹配删除是安全做法（不要按分片目录整个删）。

## 3. 已执行

1. 世界里轨道自己的方块：`fill -5 64 4083 10 64 4222 minecraft:air replace`
   （y=64 那一层；路基 y=62..63 保持不动）；
2. 停服 → 备份并删除 **8 条**轨文件 → 起服。备份：
   `sandbox/rails-removed-20260922-161229/`（8 个文件，名字就是 hex，可原样放回 `rails/<XX>/`）；
3. 复查：轨条数 **99 → 88**，最大 z **4222 → 4082**（末站站台轨 `x=0 z=3982..4082` 完好，
   站台记录 `站台@站 z=3982..4082` 也完好 ✓）。

## 4. ⚠️ 顺带暴露的一件事：**有 3 条轨从来没落盘**

删之前 `rails/` 目录里只有 **96** 个文件，而引擎内存里有 **99** 条轨 —— 差 3 条是"运行时加的、
还没存档"的。重启把它们一起带走了（**不是**这次删除删的：磁盘上从来没有对应的文件，
备份里也只有我点名的那 8 个）。丢的是：

* `x=5` 那条轨在末站的那 100 米（约 z=3982..4082）；
* 两截 1 米长的接缝轨（x=0 与 x=5 在 z=4081..4082）。

**后果**：现在第二条轨（x=5）在 z=3982 就断了，没有和末站站台并排。
要补回来的话一条命令：

```
rail add 5 64 3982 5 64 4082 --speed=160      # 不要加 --platform：站台记录已经挂在 x=0 那条上了
```

**教训**：`rail add` 之后**至少让它存一次档**（或记住"这次加的还没落盘"），
否则任何一次重启都会静默丢轨 —— 这次是因为我要删轨才重启，纯属撞上。
