# 106 - 闭塞区间 v2 · S3：S1 停车改读有向区间

> 承接 notes/104（S1 数据）、105（S2 占用/查询/报告）。设计：
> `docs/01-设计/闭塞区间-灯到灯跨轨有向模型-设计.md`。
> 本片把 **S1 的停车判定**从"按轨"改成"按有向区间"。

## 1. 交付

| 件 | 内容 |
| --- | --- |
| `Simulator.mmtrDirectionalBlocks` | v2 服务挂到 Simulator（懒构建 + 双签名缓存） |
| `MmtrDirectionalBlockService.sectionBoundaryAheadM(...)` | **规则**：沿本区间逐 span 走 —— 本 span 前方被占 → 停在该占用面前；**下一段 span 被占 → 停在本段末端（两段之间的灯/节点边界）**；都不占 → 无限制 |
| `isSpanOccupied` / `distanceToOccupancyM` | 单段占用查询与"到占用面距离"（按行进方向取值） |
| `Vehicle.directionalSectionStopM(...)` | 把上面的规则翻译成 walker 空间的停点（与既有 `MMTR_BLOCK_NODE_EPS_M` 同一口径） |
| `Vehicle.nextSectionStopM(...)` | **先问 v2**；v2 答"与我无关"（该轨没有区间）时**回退 v1 的按轨规则** |

**回退是刻意的**：真实世界里 134 根轨只有 35 根属于某个区间，直接替换会让其余 99 根轨**完全失去占用停车**。
所以"有灯区段走区间语义、无灯区段逐位保持 v2 之前的行为"是本片的硬要求，也是零回归的原因。

## 2. 实现中修掉的三个自己的错

1. **第一条规则写反了**：初版是"本区间被占 → 停在自己区间的边界"。正确规则是 v1 的结构 ——
   **"将要进入的那一段被占 → 停在它前面"**。前者会让列车在自己区间空、前方区间被占时**反而获准进入**
   （`if (occupied) hold` 反了）。
2. **忽略了调用方传入的占用树**：`directionalSectionStopM` 一开始去读 `Simulator.mmtrOccupancyTrees()`，
   而 `computeMmtrBlockStopM(vehiclePositions)` 的 `vehiclePositions` 才是**本次判定该用的那份**。
   真实服务端里两者恰好一致（所以看不出来），但**所有 71 处既有测试都传自建 trees**，于是规则在测试里永远"看不见"占用。
3. **方向向量读取**：用 `RailMath.getPosition(arc ± 0.05)` 采样得到行进方向（与 `MmtrDirectionalBlockService`
   内部同一手法），而不是依赖 `ReversePositions` 标志推断。

## 3. 用例

`MmtrDirectionalBlockingTests`（2 例，`org.mtr.core.data`）：

| 用例 | 钉住的行为 |
| --- | --- |
| `theSectionSpansTheWholeCorridorAndTheRailsInsideItAreNotBoundaries` | 走廊入口一盏灯 → 区间跨 **RA/RB/RC 三根轨**（72 m），`sectionAt` 在 RA、RB 上都命中同一条区间；反向无区间 |
| `aTrainIsHeldAtTheLampWhenTheOccupiedStretchIsTwoRailsAhead` | 占用放在**第三根轨**（RC）、RA/RB 全空时，列车停在**自己区间内**那个占用面前（12 m），不放行进入被占段 |

测试基建上记两条（都是踩过的坑）：
- `Simulator.tick()` **不能用**于这类测试：它按墙钟差推进，紧循环里列车几乎不动。既有测试统一用
  `siding.simulateVehicles(1000, trees)`，本片沿用。
- 占用必须注入**判定所读的那份 trees**（本片 = 传给 `simulateVehicles` 的列表的 `get(1)`），
  并**每 tick 重新注入**：`simulateVehicles` 会 `removeFirst()` + `add(new)`，注入的树会被轮转并丢弃。

## 4. 验证

- 新增 2 例绿；**引擎全量 508/0/2**（S2 后 506，+2 例，**零新增失败**）。
- 既有 `MmtrMotionBlockingTests`（B2 的按轨规则全套）**全绿且零期望值改动** —— 即无灯区段逐位未变。
- 走行/停车侧没有任何被修改的既有用例，说明回退路径确实生效。

## 5. 诚实结论：本片在**当前世界**下的可观测差异是有限的

必须写清楚，避免误以为"改了 S1 就立刻不一样了"：

1. **灯位重复（notes/105 §3.1）让每条区间都只有一根轨** —— 在 dev 世界里，v2 的区间边界恰好都落在轨的端点上。
   于是在"占用在下一根轨"这种最常见场景里，v2 的"停在区间边界"和 v1 的"停在轨端"**落在同一位置**。
2. v2 真正不同的场景是：
   - **占用在区间内更远处**（本片用例即是）—— v1 只看下一根轨，下一根空就放行；v2 会因为区间内更远处被占而扣住；
   - 一盏灯**切在一根轨中段**时（v2 边界在区间中间，v1 表达不了）；
   - 区间跨多根轨且**中间没有灯**时，v2 的边界意义是"那盏灯"，而不是"最近的一个节点"。
3. 因此 §验收里"dev 世界被灯切分的轨不再是 0"这一条，**取决于灯位整理（S5）**：
   现在 8 盏灯 7 盏贴节点、4 盏重复，v2 已经把这件事**量化暴露**出来，但不会自己消失。
