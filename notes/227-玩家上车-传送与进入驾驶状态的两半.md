# 227 把某位玩家传送到车上并进入驾驶状态 —— 以及这件事为什么必须分成两半

用户口径：**「把某玩家传送至车上并进入驾驶状态」**（"玩家与作业表相连"的第一步：
人得先在车里、在司机位上，才谈得上认领作业、手动开车完成任务）。

## 1. 先看清这件事的边界：MTR 的"乘车"是客户端权威的

这是整轮的关键事实，决定了实现形状：

| 事实 | 出处 |
| --- | --- |
| 骑乘状态（`ridingVehicleId` / 车体局部坐标 / 驾驶室号）**只存在于客户端**的一个静态类里 | `VehicleRidingMovement`（类注释写明"本类是骑乘坐标的唯一写者"） |
| 只有**客户端的** `RenderVehicles → VehicleRidingMovement.movePlayer` 每帧把玩家钉在车上、并推进骑乘会话 | `RenderVehicles:247`；`VehicleRidingMovement.tick()` 在"没有任何东西推动玩家"时结束骑乘 |
| 服务端对骑乘玩家做的事是"放行"而不是"搬运"：`noGravity` + `noClip` + `inTeleportationState` | `Init.updateRidingEntity` / `updatePlayer`（`PlayerTeleportationStateAccessor`）、`Init:246` 每 tick 重放 |
| 玩家位置由客户端上报（每秒一次 `PacketUpdateVehicleRidingEntities`），服务端只记录 | `VehicleRidingMovement.sendUpdate` |

所以**服务端把玩家实体挪到座位坐标上是不够的**：客户端不会因此认为自己在车上，车一开人就被落下。
"传送上车"与"进入驾驶状态"必须由两侧分工完成，这就是本轮的形状。

## 2. 交付（服务端一半 + 客户端一半）

```
/mtr mmtrboard <vehicleId> [<车节><A|B>] [玩家名]          ← 游戏内 OP 指令（pm 2）
  或 引擎指令栏：train board <vehicleId> [<车节><A|B>] [玩家名]   ← 引擎只转交
        │
        ▼  服务端（MmtrBoardPlayer.board）
   ① 找到车所在的那个维度与它的**真实世界坐标**（取该节车第一个转向架的位置 = 车正下方的钢轨上，+1 m）
   ② ServerPlayerEntity#teleport 过去（这一步不只是"省得走路"：**车辆的客户端镜像按玩家位置同步**，
      人在几百格外时那辆车根本不在 MinecraftClientData.vehicles 里，客户端也就无从算座位点）
   ③ 给**那个玩家**发 PacketMmtrBoardPlayer {vehicleId, cab}
        │
        ▼  客户端（PacketMmtrBoardPlayer → MmtrBoardRequest → MmtrCabInteraction.enterCab）
   ④ 每客户端 tick 重试，直到车出现在镜像里（最长 5 s，超时如实报错）
   ⑤ 按 (车节, 端) 挑驾驶室 → MmtrVehicleAnchors.cabView 取座位点 → VehicleRidingMovement.mmtrEnterCab
   ⑥ 顺带发 PacketMmtrCabOp(ENTER)：向引擎申领这个驾驶室（与按 G 同一条路）
```

新增/改动的文件：

| 文件 | 角色 |
| --- | --- |
| `packet/PacketMmtrBoardPlayer.java`（新） | 服务端 → 客户端的"进这辆车的驾驶室"，载荷 `{vehicleId, cab}` |
| `client/MmtrBoardRequest.java`（新） | 客户端落地：等镜像 + 挑驾驶室 + 调进舱；**只登记意图**，真正的执行在主线程 tick 里 |
| `mmtr/MmtrBoardPlayer.java`（新） | 服务端一半：算落点、传送、发包；另有 `findPlayer(名字)` |
| `render/MmtrInteractPrompt.java` | 新增 `cabTargetsOf(vehicleId)`（**不依赖准星/距离**的全部驾驶室）与 `isVehicleMirrored(id)` |
| `client/MmtrCabInteraction.java` | `enterCab` 改 `public` —— "按 G"与"被传送"共用同一段进舱代码 |
| `render/MainRenderer.java` | 每拍 `MmtrBoardRequest.tick()` |
| `Init.java` | 注册包 + `/mtr mmtrboard` 指令（`mmtrBoard` 解析参数并把失败原因说清楚） |
| `mmtr/MmtrCommandExecutor.java` | 新增 `board` 动词（引擎指令栏那条路到游戏端的落点） |
| `engine/.../MmtrTrainCommands.java` | `train board …` 转交游戏端（引擎侧只加了一个 case 与一行用法） |

## 3. 三个刻意的取舍

1. **不自己算座位点（服务端）**：座位点在**车型资源包**里（`mmtr_cabdoor` 锚点），客户端那份才与它
   自己加载的模型一致。服务端只把人放到那节车的真实位置上，差的一两米由客户端进舱时一次抹平。
   两个入口各推一遍"哪个端算驾驶室"必然分叉（notes/163 的教训）。
2. **进舱代码只有一份**：`MmtrCabInteraction.enterCab` 被"按 G"和"被传送"共用。所以传送进去与走过去
   按 G 的结果**逐字节一致**（同样的座位朝向、同样的驾驶室申领、同样的骑乘上报）。
3. **不点名玩家时只在场上恰好一人时猜**：多于一人就要求点名 —— 猜错等于把别人瞬移走。

## 4. 失败模式与判据（都有日志，别只看"没成功"）

| 现象 | 日志 | 真因 |
| --- | --- | --- |
| 指令回"找不到车辆" | —— | id 不对（`vehicle list` 看看场上有哪些车） |
| 指令回"场上有 N 名玩家" | —— | 没点名且不止一人 |
| 人到了、但没进驾驶室 | `[MMTR-BOARD] … 还没进客户端镜像，重试中…` → 5 s 后 `放弃上车` | 服务端落点没生效（维度/坐标），或车已不存在 |
| 同上，但日志是 | `[MMTR-BOARD] 车 … 在镜像里但一个驾驶室锚点都没有` | 车型缺 `mmtr_cabdoor` 锚点（等多久都不会好） |
| 进了驾驶室但引擎不认 | `[MMTR-CAB] 上车结果：… 钥匙=…` | 引擎那三关：车没停稳 / 该驾驶室被别人拿着 / 这列不是编组体车（第三种不写日志，spawn 静默退化成遗留整车） |

## 5. 验收

- **离线**：`scripts/check-java-compile.ps1` → **443 源 / 650 类 OK**；引擎 `gradlew compileJava` OK；
  `scripts/check-paths.ps1` → 无机器相关绝对路径。
- **实机（待做，需要重启 dev 服务端才会带上新代码）**：
  1. 指令栏/聊天敲 `/mtr mmtrboard <车id>`（或 `train board <车id>`）→ 人出现在车上、右上角 HUD 出现；
  2. 游戏日志出现 `[MMTR-BOARD] <玩家> → 车 … 已发出上车请求` 与 `[MMTR-CAB] 请求上车…`；
  3. 引擎侧 `interlock <车id>` / `mmtr-trains` 的 `mmtrActiveCab` / `mmtrCabKeyHolder` 反映该玩家；
  4. 按油门能开动（这一条在"无任务不得操纵"（`mmtrRequireTaskToDrive`）打开时会**不成立** ——
     那正是下一片"玩家与作业表相连"要接的闸门）。
