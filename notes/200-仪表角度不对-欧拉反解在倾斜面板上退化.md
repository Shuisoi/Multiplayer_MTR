# 200 · 仪表角度不对：**欧拉反解在倾斜面板上退化** —— 实测偏 68°

> 用户："仪表角度不对，这也是个老问题。"
> **确实是老问题**：notes/179 §10 已经为**风挡**诊断并修掉了同一个根因（那时差 **90°**），
> 但**仪表面板（`MmtrPanelQuad`）一直还在用那套欧拉反解**。本篇按同一个修法把它也换掉。

---

## 1. 根因（notes/179 §10 已定案，这里只是它第二次咬人）

`MmtrPanelQuad.drawFrame` 原本把锚点的正交基**反解成三个欧拉角**：

```java
pitch = asin(clamp(-up.y()));
yaw   = atan2(sideNormal.x(), sideNormal.z());
roll  = atan2(up.x(), up.y());
// 然后 rotateYDegrees(yaw) · rotateXDegrees(pitch) · rotateZDegrees(roll)
```

这套解是给**竖直朝前的仪表台**写的：**它把 `up` 的竖直分量当成 pitch 的全部信息**，
即隐含假设"`up` 的水平分量可以忽略（面板正对玩家）"。于是**只要模型给的
`up` 有一部分是沿着面本身走的**（倾斜的仪表台、风挡），这一档姿态就**解不出来**，
结果面板被绕车的横轴转掉一大截。

notes/179 的判别方法（可复用）：**把 `normal / up / right` 两两点乘** ——
实测是正交的，所以**问题在代码怎么用这三个向量，不在锚点数据**。

---

## 2. 量化：101 的仪表面板偏了多少

`sandbox/panel_euler_error.js` 对每个 hud 面算"欧拉解出来的局部轴"与"锚点真实基"的夹角：

```
hud_1 facet0:  yaw=157.1 pitch=78.7 roll=180.0
               local+X 偏 4.38°   local+Y 偏 68.32°   local+Z（面法线）偏 68.25°
hud_1 facet1:  local+X 偏 0.00°   local+Z 偏 67.38°
hud_1 facet2:  local+X 偏 4.38°   local+Z 偏 68.25°
hud_2 三个面同值（镜像）
=> 最差：面法线偏 68.25°，面内右向偏 4.38°
```

**面板平面本身偏了 68°** —— 这完全对得上用户"角度不对"的观感
（不是小歪斜，是几乎立起来；风挡那次的同款错误是 90°）。

> 口径说明：该脚本按标准右手 `Ry·Rx·Rz` 约定复算。**绝对角度依赖 MTR 的旋转约定**，
> 但两个结论不依赖它：① 这套解在结构上表达不了这类姿态（notes/179 已实机证实风挡差 90°）；
> ② **新写法完全不用欧拉角**，所以与约定无关。

---

## 3. 修法：**不再反解欧拉角，直接用锚点的基摆四个角**

```java
// centre + sideRight*a + up*b + sideNormal*lift      a ∈ ±w/2, b ∈ ±h/2
final Vector[] corners = { … };
MainRenderer.scheduleRender(texture, false, QueuedRenderLayer.LIGHT_2, (graphicsHolder, offset) -> {
    carTransform.transform(graphicsHolder, offset);     // 只套车体变换，没有局部旋转
    IDrawing.drawTexture(
        graphicsHolder,
        c0.x, c0.y, c0.z,  c1.x, c1.y, c1.z,  c2.x, c2.y, c2.z,  c3.x, c3.y, c3.z,
        uLeft, (float) v0, uRight, (float) v1,          // v1 = 上边缘（这条老约定不变）
        Direction.UP, IGui.ARGB_WHITE, GraphicsHolder.getDefaultLight());
    graphicsHolder.pop();                                // transform() 会 push
});
```

- 四个角**按构造就在模型面所在的平面里** —— 与缠绕方向、倾斜角、`up` 的朝向都无关；
- 顺序仍是**左下 → 右下 → 右上 → 左上**（与该面法线同侧的绕序，notes/193/195 的结论不变）；
- `panelFlipU`（`u → 1−u`）与"两面都画"的语义不变；
- **必须 `graphicsHolder.pop()`**：`carTransform.transform()` 会 push
  （风挡那条路径同样 pop；漏掉会破坏矩阵栈，正是"实体消失"那一类症状）。

> **一句话原则（notes/179 §10.3 原话）**：**锚点已经给了完整的正交基，就永远不要反解欧拉角。**
> 反过来，任何"角度看着差 90°（或 68°）"的怪象，第一嫌疑都是欧拉反解退化了。

## 5. 与 notes/195/199 的关系

- notes/195 修的是**画布内容**（折面绕序 → 跨折痕连续、不镜像）；
- notes/199 修的是**人能不能上车**（合成地板 Y）；
- **本篇修的是"贴上去的那块四边形在不在建模的面上"** —— 三者是三个不同层：
  画布 → 几何摆放 → 载具落位。前两层都对，面板仍可能因为欧拉反解而不在面上。
