# 122 - T4（二）：进路类型由任务类型决定

> 对应设计：`docs/01-设计/行车控制-任务联锁与行车许可-设计.md` §A-5（③）/ §6（T4）。
> 前置：notes/121（T4 一：玩家任务接入联锁 + 准入闸门）。触发：用户 2026-09-14「一路把T做完吧」。

## 1. 修的是什么：类型**不稳定**，而不是答错

`Vehicle.armMmtrPointRun` 原来这样定进路类型：

```java
simulator.mmtrShuntAuthorities.active(getId()) == null ? Kind.MAIN : Kind.SHUNT
```

即"从**此刻有没有调车授权**反推"。病根不是它答错，而是它**不稳定**：
授权一到/一走，同一条 movement 的类型就翻，而 `MmtrRouteRegistry.request` 靠
`sameMovement`（**含 kind**）判断"还是不是同一条进路" —— 于是每翻一次就换一个新对象，
把信号层与运营台手里持有的那个对象 churn 掉（notes/78 当初特意让"同 movement 重试保持同一对象"，
就是为了防这个）。

## 2. 交付

```java
static MmtrRoute.Kind mmtrRouteKindOf(@Nullable MmtrMission mission, boolean hasShuntAuthority) {
    if (mission != null && mission.getKind() == MANEUVER) return SHUNT;   // 作业类型是调车 ⇒ 调车进路
    return hasShuntAuthority ? SHUNT : MAIN;
}
```

先看**任务类型**，再看副显示授权。于是：

- **调车作业永远是调车进路**，与"此刻有没有授权"无关 → 类型不再翻，对象不再被 churn ✓
- 既有用例不受影响：`MmtrRouteVehicleTests.shuntMovementIsPublishedAsAShuntRoute` 用的是
  MANEUVER 作业 + 调车授权，**两条判据给出同一个答案**（SHUNT），所以它照旧绿。

## 3. 与设计文档字面的一处偏离（写清楚免得被当成漏做）

设计说"**不再反推**"（Kind 只由任务类型决定），本实现**保留了**"有调车授权 ⇒ 调车进路"这一条。

理由：`Kind.SHUNT` 的语义不是"这是一趟调车作业"，而是
**"这列车是由副显示授权的，主灯不许清"**（`MmtrRoute` 自己的类注释就是这么写的，C3a 的规则也建立在它上面）。
副显示授权**定义**了这类进路 —— 它不是旁证，是判据本身。所以：

| 作业 | 有副显示授权 | 结论 |
| --- | --- | --- |
| MANEUVER | 否 | SHUNT（本片新增：作业类型说了算） |
| MANEUVER | 是 | SHUNT |
| PASSENGER | 否 | MAIN |
| PASSENGER | 是 | **SHUNT**（安全侧：宁可不清主灯） |

如果只按作业类型，PASSENGER + 副显示授权会得到 MAIN —— 那意味着给一条"进入占用区段"的
movement 按列车进路处理、可能清主灯。这个方向不安全，所以不退。

## 6. T5 的前置：它真正缺的是输入

设计 §6/§7 把 T5 排成"**稳定后**"，并且它就是**方案 B（时刻表预排进路）**。仔细看它的内容：

- "冲突按**计划时刻**裁决" —— 需要**计划时刻**存在；
- "预约槽 / 晚点重排" —— 需要一张时刻表。

而**时刻表是另一份设计文档的产物**（`任务系统-线路派生与车底交路-设计.md` 的 P1–P4：
输入模型 → 服务计划（趟次表）→ 车底运用 → 派发器）。所以 T5 真正卡住的地方不是算法，
而是**它的输入还没被造出来**：现在填进 `requestAtomically(..., priorityMillis)` 的那个值**没有来源**
（T1b 二 已经把机制与时序做通并测过，只差有人填值）。

因此 T5 里**唯一不依赖 P 系列**的一块是：**敌对进路表的定义**（"什么算冲突"）——
设计把它放在 T1b，我按当时的判断推迟了（共用轨段/净空区重叠若直接做成 SET 判据，
会让当前能 SET 的进路变 PENDING，有回归已验收行为的风险）。它是下一步要做的第一件事，
而且必须先做成**可计算、可观测、可单测**的表，再谈要不要接进 SET 判定。
