## 1 先排除的那条：坐标系错位（**不成立**，但值得记下来）

`bladeSegmentM()` 用的是 `pivotU * widthM` 这类**角原点**（0..widthM）米坐标，而 `drawBeads()`
画珠子用的是 `(drop.x - 0.5) * widthM`，即 `Plane.pointAt()` 要的**中心原点**坐标。
两处不一致看起来正好能解释"水到不了尽头"（判定带被整体平移 0.58 m）。

**它不成立**：`applyWipe()` 里 `pointX = drop.x * anchor.widthM` 与 `bladeSegmentM()` **同是角原点**，
`wipeFactorBand()` / `aheadM` 两边一致；只有 `drawBeads()` 转中心原点，而它转得对。
记录下来是因为这条岔路很容易被当成真因（而且它确实是一处容易再次写错的地方：
**判据是"同一个量在两处的原点必须相同"，不是"看起来像个偏移"**）。

## 2 真因：`advance()` 每个**渲染通道**跑一次，而通道会落在同一毫秒

`MmtrWindshield` 的入口 `now = System.currentTimeMillis()`（`MmtrWindshield.java:360`），
然后对每个 pane 调一次 `state.advance(now, ...)`。**这个方法每个渲染通道都会被走到一次**
（车厢内外同时可见时就是两次），于是**第二遍拿到的时钟和第一遍一模一样**：

```
elapsed = min(250, max(0, now - lastAdvanceMillis)) = 0
→ advanceWiper(0) 不动臂 → wiperAngleDeg == previousWiperAngleDeg
→ bladeAdvanceM = 0 → bladeTravelling = false
```

而释放条件写的是：

```java
if (!bladeTravelling || wiperTravelDirection != drop.carriedDirection) {
    drop.carriedByBlade = false;   // 原地放下
```

**「这一帧刀没动」被读成了「刀折返了」**，于是整个水浪被当场倒在地上。
下一帧真实步进只能把刀口附近的几颗重新捡起来，所以净位移永远只有一点点。

### 2.1 游戏内证据（`mmtr/game/fabric/run/logs/latest.log`，windshield_2_1）

| 量 | 实测 |
|---|---|
| `wipe` 诊断行总数 | 2172 |
| `span=0.0deg`（刀**完全没动**的调用） | **561 次（25.8%）** |
| 其中 `released>0`（水浪被倒掉） | **501 次** |
| 这些次被倒掉的雨滴合计 | **2031 颗（平均 4.05 颗/次）** |
| 真折返释放（`span>0` 且 `released>0`） | **仅 11 次** |
| `released>0` 里属于重复通道的比例 | **97.8%** |

而且这些 `span=0.0` 的调用**角度散布在 94°/106°/135°/143°/151°/168° 整个行程上**
（不是只在折返点附近），这就是"同一时刻被看了两遍"而不是"折返"的铁证。

**为什么时好时坏**：两遍是否落在同一毫秒，取决于渲染线程的亚毫秒时序。落在同一毫秒 →
`elapsed=0` → 水浪被倒掉；跨过毫秒边界 → `elapsed=1 ms` → 刀动了极小一点，`bladeTravelling`
为真 → 不释放。这解释了为什么现象是"有时候推一点，有时候完全不动"，而不是稳定的一半。

## 3 离线复现：把游戏的真实调用序列搬进夹具

`DropletFlow` §8 新增探针：同一块玻璃、同一次行程，跑三遍 ——
① 单通道（客户端正常路径）；② 加重复通道 + **旧规则**（`Glass.releaseOnStall`，逐字还原被替换的判据）；
③ 加重复通道 + **本次修复**。

```
one pass only:            carried 597.9 mm each over 1123 mm of blade travel (53%); wave peak 23; released 0 (0 mid-stroke)
+ duplicate, OLD rule:    carried   0.0 mm each (0%);  wave peak  0; released 141 (126 mid-stroke)
+ duplicate, THIS fix:    carried 597.9 mm each (53%); wave peak 24; released 0 (0 mid-stroke)

刮之前就在玻璃上的珠子，按三档（刀去的一侧 / 中段 / 起始侧）：
  before                  49 / 40 / 48
  one pass                52 / 11 / 21     ← 中段被清空，水堆到一侧
  old rule + duplicate    41 / 33 / 37     ← 中段几乎没动，水留在原地  = 用户看到的"留在中间"
  fix    + duplicate      52 / 11 / 21     ← 与单通道逐档相同
```

**三档计数是"按世代追踪的珠子个数"**，不是任何可以造假的位移指标：它就是"刮之前在那儿的
水，刮完到哪儿去了"。旧规则 + 重复通道下中段 40→33（几乎不动），与用户描述完全一致。

### 3.1 这一步差点被度量假象骗过去（记录一次）

第一次跑出来 `fix+duplicate` 是 `44/21/19`，与单通道 `52/11/21` 不同。差点据此认为
"重复通道还有副作用"。逐项排查后是**夹具自己的度量缺陷**：

- 第一次差异来自 `advanceDrops(dt=0)` 仍然从共享 RNG 取数 → 生成序列分叉（已改成重复通道只跑 `applyWipe`）；
- 第二次仍有差异，真因是 **`thirds()` 用 `lastPushX/lastPushY` 决定分档轴**，而重复通道
  `push = {0,0}` 把这两个值清成 0 → 分档**从 X 轴悄悄切到 Y 轴**。

修法：行程轴在行程开始时固定（`strokeAxisX/Y`），不再读"最后一次 applyWipe 恰好推的方向"。
修完 `fix+duplicate` 与单通道**逐档完全相同**，这才叫空操作。
（这与本仓 `MMTR-OBJ车辆-故障谱系与离线判据.md` 的横向教训同源：**先证明量具，再相信数字**。）

## 4 修法（两处，互为纵深）

### 4.1 根因：零时间的调用直接返回

```java
if (now == lastAdvanceMillis) {
    return;   // 同一时刻被看了第二遍
}
```

这一并修掉了**整个场步骤**被跑两遍的问题（雨滴推进 `dt=0` 本是无操作，但 `mergeDrops()`、
窗口计数 `windowFramesAdvancing`、`[MMTR-WSHLD] wipe` 的节流计数都在重复累加）。
`draw()` 在 `advance()` 之外照旧每通道调用，所以第二遍照常画，只是不再推进物理。

### 4.2 纵深：释放判据不再把"没动"当折返

```java
final boolean reversed = bladeTravelling && wiperTravelDirection != drop.carriedDirection;
if (!bladeMoving || reversed) { drop.carriedByBlade = false; ... }
```

- **折返** = 真的动了、而且方向相反（比旧规则晚一步，不是判错一步）；
- **停机** = `bladeMoving == false`，即雨刷关掉或在停放位驻留 —— 这时水必须留在刀停下的地方
  （这是诚实的行为：司机中途关雨刷，水就停在刀口）；
- **重复通道**（`bladeMoving` 仍为 true、方向未变）→ 不释放，`carriedM = 0`，什么也不发生。

即使 4.1 将来被某条新路径绕过，4.2 也能挡住同一种伤害。

## 6 遗留与风险

1. **`carriedM = min(bladeAdvanceM, progressBladeM - wavePickedProgressM)` 里的投影量依赖坐标系原点**
   （`progressBladeM = toMidX*push[0] + toMidY*push[1]`，`toMid` 是角原点）。因为拾取时用的是
   `push_pickup`、现在是 `push_now`，原点的常量项只在 `push` 转动时**不完全抵消**（这一行程机构
   转动约 15°，量级 ~0.2 m）。它只会**减少**携带（`min` 的第二项），正常情况下不生效，
   所以本次没动它；要彻底消除就改成沿路径累加（`Drop.carriedPathM` 那种写法）。
   **→ 已处理，见 note 209 §3**：连同 `Drop.wavePickedProgressM` 一起删掉了
   （携带只需要刀自己的位移；删掉后"相对刀中点的偏移增长 258.6 mm → **0.0 mm**"可证）。
   但 note 209 也写明：**它不是"水浪散开"的主因**（去掉钳位后仍是 73 mm）。
2. **`densityCellM` 的中雨死区**（intensity 0.60 时 `flowing == 0`）未处理，旋钮是 `0.05 → 0.08`。
3. **`fallMps = 0.75` 与注释里按 0.55 推的 30 km/h 交叉点**仍不一致（note 206 §7.2）。
4. **`WiperPreview.java` 仍是 STALE**（还在 ink 模型上）。
5. **`wipersweep` 仍是 98 点条带**，打包器扇形拟合读 `293.764°`，靠机构求解救回 80.00°。
6. **重复渲染通道本身没有根治**：现在只是让它无害。真正的省法是在 `MmtrWindshield.render` 入口
   按 `vehicleId+carNumber` 缓存"这一毫秒已经推进过"，从源头少跑一遍（收益是每帧省一次
   全场 O(n) 的 `advanceDrops` + `measureDensity`）。未做，因为先要把正确性钉住。
