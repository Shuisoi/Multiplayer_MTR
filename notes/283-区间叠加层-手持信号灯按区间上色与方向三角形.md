# 283 · 区间叠加层：手持信号灯时按区间上色 + 方向三角形

> 用户提问（2026-09-25）：「目前游戏内建造轨道时，区间难以辨认，能不能复用当前的叠加层，用三角形表示方向，
> 用不同颜色来代表不同区间，仅需相连颜色不同即可，连续轨道可以有相同颜色。**在手持信号灯时不显示轨道类型而显示区间**」
>
> 用户当场拍板本轮的两个分岔：① **只在手持信号灯时**顶掉"轨道类型"配色（连接器/节点/刷子等其余铁轨工具不动）；
> ② 同一根轨上的多段按**方向分左右两条带**（与网页方案 B 同一口径，notes/158）。

---

## 1. 这一层只回答两件事

| 要回答的 | 怎么做 | 不是什么 |
| --- | --- | --- |
| **边界在哪** | 相邻两段（相接的、同轨叠着的）**必须异色**；颜色 = **区间身份** | 不是状态：占用/灯位归信号层（轨上原有的信号色条、单向箭头都不动） |
| **往哪走** | 沿带每隔 5 m 一个**白色三角形**，尖指行车方向（复用 `one_way_rail_arrow.png` 那张三角贴图） | 不是"该不该走"：那是 aspect |

颜色是身份而不是状态，正是"边界看得见"的前提：状态色（全绿/全红）看完还是分不出哪到哪。

## 2. 数据链路：引擎给结论，客户端只显示

```
MmtrSectionService#sectionOverlay()        每条区间一行：色号 + 行车方向 + 各段弧窗
  └ MmtrSectionOverlay#colorize()          贪心上色（对称闭包 + 按 id 排序后取"邻居没用过的最小色号"）
      └ MmtrRouteMirror#sectionBandWire()  拍成扁平字符串：轨hex / 区间id / 色号 / 方向x‰ / 方向z‰ / 弧起cm / 弧止cm
          └ PacketMmtrRoutes "sectionBands"（步长 7）
              └ MmtrClientRoutes.sectionBands(轨hex)   按**规范 hex** 入索引
                  └ MmtrSectionBands.render(轨)        沿弧窗画带 + 三角形
```

数值一律走**整数**（千分位方向 / 厘米弧长）：区域设置若用逗号作小数点，客户端的 `Double.parseDouble`
会静默失败，而弧长算错的表现是"带子画到别的轨上"——那种错查起来极贵。

为什么要引擎算（而不是客户端按 spans 自己推一遍）：**"哪两段算相连"本身就是结论**，客户端推一遍必然分叉，
而分叉的表现是"看着是两段、其实是一段"。这与 S4（灯显）是同一条规矩（notes/110）。

## 3. 相连的两条判据

| 判据 | 来源 | 为什么算相连 |
| --- | --- | --- |
| 链上的下一段 | `followingBySection` | 灯到灯相接 —— 这就是"边界"，边界处必须跳色 |
| 同轨且弧窗重叠 | `sectionsByRail` | 它们画在**同一条带**上（同向叠着），撞色就看不出切点 |

**相对方向不要求异色**：两条带沿轨法向分居两侧（网页方案 B），本来就不在同一条带上看。

## 4. 颜色为什么必须"引擎算 + 稳定"

贪心按 **id 排序**后访问 ⇒ 世界不变时颜色逐段不变。不排序的话哈希序一变整张图就换色，
而"颜色一闪"会让人以为区间真的变了（比撞色更坏）。用尽的兜底：色号回绕（撞色好过不画），
调色板 `MmtrSectionOverlay.COLOR_COUNT = 12`，现场实测最多只用到 6 个。

## 5. 量出来的三个数（不猜）

写这一层有三处"猜错也看不出来"的地方，所以都实测过：

| 数 | 怎么量的 | 值 |
| --- | --- | --- |
| 轨面有多宽 | `railMath.render(cb, 1, -1, 1)` 的四角离中心线的距离（`sandbox/_band_probe/BandProbe.java`） | **±1.0 格** ⇒ "半个轨宽"= 0.5 格、带宽取 0.8 格 |
| 三角贴图尖朝哪 | 把 `one_way_rail_arrow.png` 逐像素解出来（Python + zlib） | 底边在 **v=13/32**、尖在 **v=19/32**，x∈[10,22) |
| 四角与 uv 的对应 | 从 mapping jar 的字节码里读 `drawTextureInWorld` | ⚠️ **这一格当时读错了**：实际是 corner1/2 → **v2**、corner3/4 → **v1**。更正与逐条证据见 [`notes/285`](285-方向三角形反指-uv是反着贴的.md)（实机症状：箭头全部反指） |

三条合起来才得出"尖落在弧大的那一端（v2 侧）"，于是 `tipAtFarEnd` 一处的开关就能决定整条带的方向。
猜错的症状是"三角形全部反着指"或"带子跑到对面那条带上"，两种都不像 bug、像自己拿错了工具。

## 6. 途中被用例抓到的一个坑：邻居表必须做对称闭包

第一版只从"我"记到"我的下一段"，于是：访问 A 时 B 还没颜色、轮到 B 时它自己的邻居表里又没有 A
⇒ **相接的两段拿到同一个色号**，边界正好看不见。被 `twoSectionsThatMeetAtALampGetDifferentColours` 抓住。
修法：`colorize` 里先做对称闭包（"相连"本来就是双向关系），并留一条专门的纯用例
（`anEdgeStoredInOneDirectionStillForbidsTheSameColour`）。

## 8. 本轮新增的两个工具（都进仓库了）

dev 会话活着时，`gradlew :fabric:compileJava` / `:fabric:test` 都不能跑（会把新类写进活进程的
classpath，notes/195/281），而"客户端代码用了引擎新 API"又必须能查 —— 于是：

| 脚本 | 做什么 |
| --- | --- |
| `mmtr/scripts/check-java-compile-newengine.ps1` | 与既有 `check-java-compile.ps1` 同一套做法，但把 `engine/build/libs` 里**最新**的 shadow jar 顶到 classpath 最前（**必须用 shadow jar，不能用 classes 目录**：后者里是未重定位的 fastutil，会凭空造出 119 条假类型错误） |
| `mmtr/scripts/run-fabric-tests-offline.ps1` + `scripts/lib/FabricTestRunner.java` | 在 `sandbox/` 里编译 fabric 主源码与用例，用 JUnit 的 Launcher API 直接跑（工作目录切到 `game/fabric`，否则有两条按相对路径读资源的用例会假红） |

## 9. 还没做（需要一个停机窗口）

1. **同步引擎**：区间带的数据由引擎发，不同步就是空的 —— 客户端会**安静地什么都不画**（不报错）。
   要 `scripts/sync-engine.ps1`（需停机）+ 重启服务端。
2. **实机目视**（同步后）：拿信号灯看 ① 双向走廊是否真有两条并排的带 ② 咽喉那根 5 条带 ③ 三角形是否
   与行车方向一致 ④ 边界处颜色是否跳变。
3. **若三角形整体反指**：只改 `MmtrSectionBands.renderTriangles` 里的 `tipAtFarEnd` 一处，别动别的地方。
4. **已知代价**：镜像每 tick 重建一次载荷（0.14 ms + 约 20 KB 签名串），与既有的 `lampRails` 同一做法。
   世界再大一个量级时，值得按"拓扑签名"缓存这份载荷（本轮不做：现在的量级不值得引入第二份签名）。
