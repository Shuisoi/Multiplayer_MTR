## 2 现行加载管线的时机与代价（读代码得到的结构问题）

```
InitClient（客户端 tick）
  registerChunkLoad → lastUpdatePacketMillis = now + 500ms        ← 触发源：区块加载
  到点 → DataRequest(uuid, 相机方块, 渲染距离 × 16) → PacketRequestData
服务端 PacketRequestRequestBase.runServerOutbound → OperationProcessor.GET_DATA
  → DataRequest.getData(simulator)：按半径收集 车站/站台/侧线/车辆段/轨/… ，
    已存在的只回 id（writeExistingIds ⇒ 增量）
客户端 PacketRequestData.runClientInbound
  → new DataResponse(jsonReader, MinecraftClientData).write()
      rails.removeIf(!keep) / addAll(new) / … → data.sync()
```

三件事决定了单 tick 的峰值：

| 环节 | 今天的样子 | 问题 |
|---|---|---|
| **触发时机** | 区块加载（`registerChunkLoad`）+500 ms，然后拉一次 | **"车到了才要"**：区块进内存那一刻才发请求，一个来回之后落地，正好和该 tick 的区块落地撞在一起 |
| **载荷** | 半径 = `渲染距离 × 16` 米（视距 12 区块 ≈ 192 m） | 节点/咽喉/站场是**轨最密**的地方 ⇒ 一次回来的新轨最多 |
| **落地** | 客户端主线程：`parseJson(content)` + `DataResponse.write()` → `ClientData.sync()` → `Data.sync()` **全量重建** `positionsToRail`、各 id 映射、`mapAreasAndSavedRails`（O(站台×车站)）、`depot.writePathCache()`；`MinecraftClientData.sync()` 再 `checkAndRemoveFromMap`（AVL 树 O(N log N)）+ 每根新轨 `new RailWrapper` | 与"这次来了多少"无关的**基数成本**（客户端手上所有轨）也在这一 tick 上 |

`PacketRequestResponseBase.runClient()` 里 `Utilities.parseJson(content)` 与 `runClientInbound` 都在客户端主线程上，
且**没有任何计时**（本轮补上，见 §4）。

## 3 三个动态项各自今天的加载方式

| 动态项 | 权威状态在哪 | 怎么到客户端 | 距离/时机闸门 | 依赖区块？ |
|---|---|---|---|---|
| **钢轨/节点/站台** | 引擎 `Simulator` | `DataRequest`（相机、渲染距离半径、增量） | 相机 + 渲染距离；**触发**是区块加载事件 | 数据驱动（渲染不吃区块），但**请求时机**被区块事件绑住 |
| **信号灯/道岔的状态**（红黄绿、岔位、守轨） | 引擎 `MmtrSignalRegistry` / 区间服务 | `PacketMmtrRoutes`（**变化时**发、**全世界一份**镜像、客户端整份替换） | **无距离闸门** | 否 |
| **信号灯/道岔的可见方块** | 世界方块 / 方块实体 | 区块（MTR 的方块实体渲染器） | 客户端视距 | **是** |
| **站台客流** | 引擎 `Platform.crowdLevel` | 服务端 `MmtrCrowdVillagers` 生成**真村民实体** | `platform radius`（默认 96 格，**圆心是玩家**）+ `platform cap`（默认 48） | 是（实体随区块跟踪） |

⇒ **空缺清单**（用户说的"没有专用管线"确有其事）：
1. 钢轨数据的**时机**没有前视——只有"区块到了再要"；
2. 信号灯/道岔**状态**完全没有距离概念（全世界一份，变化才发）；
3. 站台客流的闸门圆心是**玩家**，不是**车**；车快速进站时客流是"车到了才开始生成"。

## 4 本轮已落（客户端半边）

### 4.1 `[MMTR-LOAD]` 探针 —— 先把"这一拍被谁花掉"量出来

`mmtr/game/fabric/src/main/java/org/mtr/mod/mmtr/MmtrLoadProbe.java`（新）

- **长 tick 归因**（≥100 ms 的 tick 各一行，每窗口最多 12 行）。
  **格式**（数字是排版示例，实机读数待值班）：`长 tick 314ms：区块载入=7 ｜ 包 2 次 96ms（PacketRequestData=1×80ms(max 80, 解析 24, 48.3KB) …）其余≈218ms`
- **5 秒汇总**：`tick` 最长/超 100 ms 个数、区块载入总数与"最长一 tick 几个"、包落地的次数/累计/最长/字节/解析、每个包类名的明细、前视拉取的次数与平均前视距离、本窗口最长的那个 tick。
- 挂点：`InitClient` 的 `registerStartClientTick`/`registerEndClientTick` + 新增 `registerChunkLoad`；
  `PacketRequestResponseBase.runClient()` 里**解析与落地分开计时**。
- 开关 `-Dmmtr.load=0`；关掉后每次调用只剩一次 boolean 读。

**为什么要分开解析/落地**：这两段在今天这条路上各占多少决定了该修哪一段。只记一个总数会让我们改错地方
（这个仓在 notes/401 已经吃过一次"猜错了"的亏）。

### 4.2 前视拉取 —— 管线的第一段

`mmtr/game/fabric/src/main/java/org/mtr/mod/mmtr/MmtrDynamicLoad.java`（新），由 `InitClient` 每 tick 调一次：

| 参数 | 默认 | 含义 |
|---|---|---|
| `-Dmmtr.dynload` | `1` | 整条管线开关（`0` = 回到"只在区块加载后拉一次"的老路） |
| `-Dmmtr.dynload.lead` | `192` | **前视距离**（米）：请求中心在相机运动方向上的提前量 |
| `-Dmmtr.dynload.radius` | `128` | 单次请求半径（米）＝**切片**大小 |
| `-Dmmtr.dynload.step` | `32` | 前视点每走这么多米才发下一次 |
| `-Dmmtr.dynload.period` | `250` | 两次请求的最小间隔（毫秒） |

- **方向**取自相机自身位移（EMA 平滑，`SMOOTHING = 0.25`），速度 < 1 m/s 时**不发**（站着不动由老路 + 重拉键负责）；
- 请求形状与 `InitClient` 里那次**同一个包**（不引入第二条数据通道），差别只有三处：
  圆心在前视点上、半径是切片大小、由"前视点走了多远"驱动；
- 仍然 `writeExistingIds`（**增量**）：没有新东西时 `DataResponse.write()` 直接空转，所以"多发几次小的"比"少发一次大的"便宜；
- **老路一条不删**：区块加载触发的那次拉取照旧（它是"新区块出现后收敛"和 notes/某 重拉键的保障），
  前视拉取只负责让**车前方**的东西提前落地 —— 到达时就没什么可落地的了。

## 5 怎么读（判据）

1. `[MMTR-LOAD]` 每 5 秒一行。先看 `超100ms=n` 与 `区块载入（最长一 tick 几个）`：
   如果长 tick 与"一 tick 进来 ≥4 个区块"同拍，那引信可能是 vanilla 的区块落地；
2. 长 tick 行里 **三块占比**：
   - `包 …ms` 占大头 ⇒ 修**数据落地**（下一步：服务端按更小半径多次发 / 客户端分期 apply）；
   - `区块载入=a` 大而 `其余>` 大 ⇒ 修**区块/实体到达**（服务端前视 chunk ticket、客流圆心挪到车前）；
   - `其余≈整拍` ⇒ 时间在没埋点的 vanilla 代码/GC/别的线程上，探针要换方向（那时才该 F3+L / jstack）；
3. `[MMTR-LAG]` 的条数与 `[MMTR-FRAME] 最慢` 是**验收口径**：A/B 两轮同一条线路同一段车速，比这两项。

```
第二轮：客户端加 -Dmmtr.dynload=0   → 同上
判据：长 tick 条数、超 100ms 个数、[MMTR-FRAME] 最慢、[MMTR-LAG] 条数
```

## 6 待办（本轮**未**覆盖的两层）

1. **信号灯/道岔状态按前视窗口裁剪**：`PacketMmtrRoutes` 今天全世界一份、变化才发。要做到"固定距离加载"，
   得让引擎按**每个客户端的前视窗口**投影一份（引擎已经有 `Client.setPositionAndUpdateRadius` 这套 AOI，
   可以复用），客户端镜子里就只留车前那一窗。
2. **站台客流圆心从"玩家"挪到"最近列车的前视点"**：`MmtrCrowdModule` 的闸门与 `MmtrCommandDispatcher`
   的 `platform radius/cap` 都是按玩家半径算的；车快速进站时客流来不及生成，到站那一刻才批量生成 ⇒ 与
   "站台客流也应该提前固定距离加载"是同一条要求。
3. **若读数是包落地占大头**：把 `DataResponse` 的落地**切片**（服务端一次只发一小片 + 客户端分期 apply），
   或者把 `Data.sync()` 的重建从"全量"改成"增量"（`positionsToRail` 增量维护）。
4. **若读数是"其余"占大头**：说明在 vanilla 区块落地/实体生成/GC 上，管线要往服务端挪
   （前视 chunk ticket：让车前方固定距离的区块在车到达之前就已经在客户端）。
