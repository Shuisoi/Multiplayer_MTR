## 2 现行加载管线的时机与代价（读代码得到的结构问题）

```
InitClient（客户端 tick）
  registerChunkLoad → lastUpdatePacketMillis = now + 500ms        ← 触发源：区块加载
  到点 → DataRequest(uuid, 相机方块, 渲染距离 × 16) → PacketRequestData
服务端 PacketRequestRequestBase.runServerOutbound → OperationProcessor.GET_DATA
  → DataRequest.getData(simulator)：按半径收集 车站/站台/侧线/车辆段/轨/… ，
    已存在的只回 id（writeExistingIds ⇒ 增量）
客户端 PacketRequestData.runClientInbound
  → new DataResponse(jsonReader, MinecraftClientData).write()
      rails.removeIf(!keep) / addAll(new) / … → data.sync()
```

三件事决定了单 tick 的峰值：

| 环节 | 今天的样子 | 问题 |
|---|---|---|
| **触发时机** | 区块加载（`registerChunkLoad`）+500 ms，然后拉一次 | **"车到了才要"**：区块进内存那一刻才发请求，一个来回之后落地，正好和该 tick 的区块落地撞在一起 |
| **载荷** | 半径 = `渲染距离 × 16` 米（视距 12 区块 ≈ 192 m） | 节点/咽喉/站场是**轨最密**的地方 ⇒ 一次回来的新轨最多 |
| **落地** | 客户端主线程：`parseJson(content)` + `DataResponse.write()` → `ClientData.sync()` → `Data.sync()` **全量重建** `positionsToRail`、各 id 映射、`mapAreasAndSavedRails`（O(站台×车站)）、`depot.writePathCache()`；`MinecraftClientData.sync()` 再 `checkAndRemoveFromMap`（AVL 树 O(N log N)）+ 每根新轨 `new RailWrapper` | 与"这次来了多少"无关的**基数成本**（客户端手上所有轨）也在这一 tick 上 |

`PacketRequestResponseBase.runClient()` 里 `Utilities.parseJson(content)` 与 `runClientInbound` 都在客户端主线程上，
且**没有任何计时**（本轮补上，见 §4）。

## 3 三个动态项各自今天的加载方式

| 动态项 | 权威状态在哪 | 怎么到客户端 | 距离/时机闸门 | 依赖区块？ |
|---|---|---|---|---|
| **钢轨/节点/站台** | 引擎 `Simulator` | `DataRequest`（相机、渲染距离半径、增量） | 相机 + 渲染距离；**触发**是区块加载事件 | 数据驱动（渲染不吃区块），但**请求时机**被区块事件绑住 |
| **信号灯/道岔的状态**（红黄绿、岔位、守轨） | 引擎 `MmtrSignalRegistry` / 区间服务 | `PacketMmtrRoutes`（**变化时**发、**全世界一份**镜像、客户端整份替换） | **无距离闸门** | 否 |
| **信号灯/道岔的可见方块** | 世界方块 / 方块实体 | 区块（MTR 的方块实体渲染器） | 客户端视距 | **是** |
| **站台客流** | 引擎 `Platform.crowdLevel` | 服务端 `MmtrCrowdVillagers` 生成**真村民实体** | `platform radius`（默认 96 格，**圆心是玩家**）+ `platform cap`（默认 48） | 是（实体随区块跟踪） |

⇒ **空缺清单**（用户说的"没有专用管线"确有其事）：
1. 钢轨数据的**时机**没有前视——只有"区块到了再要"；
2. 信号灯/道岔**状态**完全没有距离概念（全世界一份，变化才发）；
3. 站台客流的闸门圆心是**玩家**，不是**车**；车快速进站时客流是"车到了才开始生成"。

### 4.2 前视拉取 —— 管线的第一段

`mmtr/game/fabric/src/main/java/org/mtr/mod/mmtr/MmtrDynamicLoad.java`（新），由 `InitClient` 每 tick 调一次：

| 参数 | 默认 | 含义 |
|---|---|---|
| `-Dmmtr.dynload` | `1` | 整条管线开关（`0` = 回到"只在区块加载后拉一次"的老路） |
| `-Dmmtr.dynload.lead` | `192` | **前方覆盖**（米）：请求窗口要在相机前方至少盖到这么远 |
| `-Dmmtr.dynload.radius` | `128` | 前视之外再留的余量（米） |
| `-Dmmtr.dynload.step` | `32` | 相机每走这么多米才发下一次 |
| `-Dmmtr.dynload.period` | `250` | 两次请求的最小间隔（毫秒） |

- **请求窗口 = 以相机为圆心、半径 `max(渲染距离 × 16, lead + radius)`（默认 320 米）**。
  **圆心必须在相机上** —— 第一版把它放到车前方 192 米，把玩家身后的轨删了，见 §9；
- **方向**取自相机自身位移（EMA 平滑，`SMOOTHING = 0.25`），速度 < 1 m/s 时**不发**（站着不动由老路 + 重拉键负责）；
- 请求形状与 `InitClient` 里那次**同一个包**（不引入第二条数据通道），差别只有两处：
  半径不小于例行窗口且保证前方够远、由"相机走了多远"驱动；
- 仍然 `writeExistingIds`（**增量**）：没有新东西时 `DataResponse.write()` 直接空转，所以"多发几次小的"比"少发一次大的"便宜；
- **老路一条不删**：区块加载触发的那次拉取照旧（它是"新区块出现后收敛"和 notes/某 重拉键的保障），
  前视拉取只负责让**相机前方**的东西提前落地 —— 到达时就没什么可落地的了。

## 9 事故：前视窗口把玩家身后的轨删掉了（2026-10-09 实机）

### 9.1 现场

用户报（原话）："现在铁轨，列车等实体会不规律消失和显示，好像和移动有关，比如当我移动到节点左侧
就显示节点左侧的轨道，右侧则显示右侧的，列车也一样，是不是渲染被你改坏了"。

### 9.2 根因（一条链，全部可读代码/可测）

1. `PacketRequestData` 的响应是 `DataResponse`，它的 `write()` **不是合并、是"按窗口替换"**
   （`engine/.../operation/DataResponse.java:53-73`）：

   ```java
   if (data instanceof ClientData && (… !rails.isEmpty() …)) {   // ← 只有"有新区块/新轨"那一次才进来
       data.rails.removeIf(rail -> !railsToKeep.contains(rail.getHexId()));   // 窗口外的轨全删
       data.rails.addAll(rails);
       … data.sync();
   }
   ```

2. `railsToKeep` 只装**这一次请求半径内**的轨（`DataRequest.getData()` → `rail.closeTo(clientPosition, requestRadius)`）；
3. 第一版的请求圆心在**相机前方 192 米**、半径 128 米 ⇒ 每次响应都把相机**身后与两侧**的轨删掉；
4. 客户端 `MinecraftClientData.sync()` 用 `checkAndRemoveFromMap(railWrapperList, rails, …)` 跟着删，
   于是 `RenderRails` 连"这一根轨"都不再遍历 —— **不是画不出来，是数据里没有了**（列车同理：
   车底那根轨被删掉，车也没法定位/画出来）；
5. `DataResponse.write()` 的删除分支**只在这一次响应里有新内容时**才跑 ⇒ 症状"不规律"：
   只有**移动进新区域、有新东西到达的那一次**才发作 —— 站着不动时一次都不会掉。

### 9.3 判据（引擎侧事实，已落用例）

`mmtr/engine/src/test/java/org/mtr/core/operation/MmtrDataWindowPruneTests.java`（新，5 条，全绿）。
实测输出（同一条 20 米轨、同一份客户端数据）：

```
圆心 x=0   半径 250 ⇒ 客户端轨 0, 200          （相机窗口：身后的轨在）
圆心 x=192 半径 128 ⇒ 客户端轨 200, 300        （★ 前视窗口：身后的轨 x=0 被删掉）
圆心 x=0   半径 320 ⇒ 客户端轨 0, 200, 300     （修好后的形状：一条不少）
同一窗口再来一次（无新内容）⇒ 一条不删          （解释"不规律"）
```

### 9.4 修法

`MmtrDynamicLoad`：**圆心改回相机所在方块**，半径 `max(渲染距离 × 16, lead + radius)`（`requestRadius()`），
不再把圆心往前挪。前视的效果由"半径足以含住前方 + 相机一移动就再拉一次"给出。
类注释里把"圆心为什么必须是相机"写成硬规矩（那条 `max` 就是闸）。

### 9.5 读数（新增，实机唯一直接判据）

`[MMTR-LOAD]` 汇总行新增一行：

```
｜ 客户端轨数 512→512（本窗口跌 0 次，最多 没掉）
```

口径：`PacketRequestResponseBase.runClient()` 落地一包前后各量一次 `MinecraftClientData.rails.size()`。
**修前**（前视窗口）这个数每次移动都会掉几十条；**修后**应当是"跌 0 次"。这就是"轨有没有被删"的直接读数，
不用靠眼睛。

### 9.6 与渲染线的边界（诚实）

同一时段内**另有两件与本事故无关**的事，都**不是本轮改出来的**，本轮不改：

1. `[MMTR-RAILBAKE] 缓存 61/96 项` 的 61/96 是**缓存容量占用**（`MAX_ENTRIES = 96`），不是"96 根轨只烘了 61 根"；
   `get()` 返回 null 时调用方逐实例回退（`RenderRails.java:341-360`），并有异常兜底（`MmtrRailMeshCache.java:343-358`）；
2. 客户端日志里 `########## GL ERROR ########## / 65544: Win32: Failed to create interface` 的洪水
   （实测：collision-client 978,064 行、run2 360,752 行、run4 324,576 行，**早于本次改动**，且成片出现）。
   它会不会造成"图形资源建不出来 ⇒ 东西不画"，是**另一条线**，需要单独量（见 §10）。

## 10 另一条线：GL 错误洪水（本轮不动，留给下一轮）

`########## GL ERROR ##########` 与 `65544: Win32: Failed to create interface` 在**最近三次**客户端日志里
都是成片出现（见 §9.6 的数量），而且**与本次前视窗口事故无关**（它在 10-05 那次渲染改动之后就一直有）。
要判定它是否也在制造"东西不画"，需要一次**只切一个量**的对照：

| 轮次 | 客户端参数 | 看什么 |
|---|---|---|
| 1 | 照常 | `########## GL ERROR` 条数/分钟、`[MMTR-RAILBAKE]` 的"新建烘焙/upload"次数、帧率 |
| 2 | 加 `-Dmmtr.railbake=false` | 同上。若 GL 洪水随之消失 ⇒ 洪水来自烘焙/上传那一支，且"轨不画"与它同源 |
| 3 | 加 `-Dmmtr.load=0`（只留渲染） | 排除探针本身；探针只读计数，理论上为零成本 |

判据：**A/B 两轮的 `GL ERROR` 条数**与**`客户端轨数` 是否掉**。若第 1 轮"客户端轨数跌 0 次"而 GL 洪水照旧，
则本事故已修死，洪水的锅单独背。
