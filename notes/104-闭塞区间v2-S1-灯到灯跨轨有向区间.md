# 104 - 闭塞区间 v2 · S1：灯到灯的跨轨有向区间（纯数据）

> 承接 2026-09-10 用户判断「区间还是没有正确的划分出来」，设计见
> `docs/01-设计/闭塞区间-灯到灯跨轨有向模型-设计.md`。本片只做数据层，**未接任何消费方**。

## 1. 用户看到的现象与代码级根因

`POST /mtr/api/map/mmtr-command {"command":"blocks all"}`（运行中 dev 世界）：

```
轨道 134 根 / 区间 134 个 / 被灯切分的轨 0 根（灯都贴在节点旁：每根轨 = 一个区间）
灯共 8 架：贴节点 7 / 切分轨 0 / 未生效 1
```

v1 `MmtrBlockService` 的边界生成里有一条守卫：

```java
if (arc <= NODE_SNAP_M || arc >= length - NODE_SNAP_M) {
    continue; // sitting at an end node: the node is already a boundary
}
```

本世界 **8 盏灯的投影弧长全是 0.0**（灯立在轨端节点旁），**全部命中 `continue`** →
`signalBoundaries` 为空 → 边界只剩每根轨的两个 `NODE` → **区间退化成"一根轨"**，灯完全没参与。

删掉守卫也修不好：v1 的 `Block` 是 `railHex + arcFrom + arcTo`，**单轨内的弧长区间**，
而灯贴节点时在自己那根轨上切不出任何东西；且 `buildRail` 无条件把两端节点当边界。

## 2. 本片交付

新增 `mmtr/signal/MmtrDirectionalBlockService.java`（纯数据，未接线）：

| 件 | 内容 |
| --- | --- |
| `headingOf(angle)` | **MTR 灯朝向 → 行进方向向量**。`BlockSignalBase.getAngle` = `FACING.asRotation()`（+22.5/45），`Direction.asRotation()` 是 MC 约定 **南=0 / 西=90 / 北=180 / 东=270**，故方向 = `(-sin, -cos)`。单测用 `SOUTH/WEST/NORTH/EAST` 常量锁死这条约定 |
| `resolveProtectedRail(entry)` | 灯 → (保护轨, 方向)。**BOUND 的 `target` 优先**；否则**按方向**选：灯正下方**轨中段**内的轨优先；灯站在节点上时，选**沿朝向离开该节点**的那根轨（绝不选"在节点结束"的那根 —— 那是灯已经走过的区间）。这修掉了 v1"纯最近轨"会把灯绑到身后轨的缺陷 |
| `Section` / `RailSpan` | 区间 = **有序的 `(railHex, arcFrom, arcTo, heading)` 列表**（跨轨、带方向）；`id` = 起始灯 key；`exitSignalKey` = 终止灯（无则视为走到尽头） |
| `buildSection(...)` / `walk(...)` | 从灯沿朝向走：**只有灯产生边界**，走到下一盏灯所在的节点即终止；节点处选**最直的一条续轨**（最大点积，不跟回头轨）；轨数/长度上限防环 |
| 查询 | `sectionOfSignal` / `sectionsOfRail` / `sectionAt(railHex, arc, headingX, headingZ)`（**按方向过滤** —— 同一弧长在两个方向上属于不同区间）；双签名缓存（rails + signals，含 angle/target） |

## 3. 用例（7 例，`MmtrDirectionalBlockServiceTests`）

| 用例 | 钉住的行为 |
| --- | --- |
| `oneLampOnALongRailMakesTheWholeRailOneSection` | 300 m 长轨 + 端点上 1 盏灯 → 整根轨 1 个区间（v1 会丢弃这盏灯） |
| `aSectionRunsAcrossRailBoundariesUntilTheNextLamp` | **3 根 100 m 轨串成一条走廊，只在头部有 1 盏灯 → 1 个区间 = 3 个 span、300 m**（这就是 v1 表达不了的"跨轨"） |
| `theNextLampFacingTheSameWayEndsTheSection` | 第三根轨头上再放 1 盏灯 → 第一段区间 = 2 个 span、`exitSignalKey` 指向第二盏灯 |
| `aLampStartsAtTheNodeItStandsOnEvenWhenAHeadRailEndsThere` | 灯站在"前一根轨结束"的共享节点上：必须绑到**离开该节点**的那根轨，而不是绑到身后的轨（否则区间长度为 0 —— 实现首版就是这个 bug） |
| `sectionsAreDirectional` | 同一根轨上、东西两端各 1 盏灯：两条区间**都覆盖整根轨**，但 `sectionAt` 按行进方向只返回对应那一条 |
| `aLampFacingAwayFromARailDoesNotBindToIt` | 灯在轨旁但朝向横穿该轨 → 不绑定（v1 的纯最近轨会误绑） |
| `anExplicitTargetWinsOverGeometricInference` | BOUND 的 `target` 覆盖几何推断 |

## 4. 验证

- 新增单测 7/7 绿；**引擎全量 502/0/2**（上一轮 495/0/2，+7 例，**零新增失败**）。
- 本片**未改任何既有文件**，`MmtrBlockService`（v1）与所有消费方原样保留 → 全量数字只增不减可佐证。
- 已知取舍（写进设计文档，待 S4 处理）：区间走行遇到道岔时**只跟最直的一条腿**。理由是"一盏道旁灯授权的是它照的那条腿，
  不是整个岔群"；这与现状"每个分支都算"的保守链不同，S4 需要在此基础上叠加**进路收窄**再比对显示。
