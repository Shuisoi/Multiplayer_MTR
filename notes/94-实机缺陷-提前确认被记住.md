# 94 - 实机缺陷：提前按下的确认被记住，AWS 窗口形同虚设

> 触发：用户实机反馈「没有 `[MMTR-AWS] unacknowledged warning - SPAD emergency engaged`」。
> 日志里其实**响了警告**，但下一 tick 就被"已确认"吃掉了。

## 1. 实机证据（23:30:02，dev 服务端）

```
[MMTR-AWS] warning on …FE39 at 398.5m - signal RED on …FE4E in 20.5m, boundary at 398.9m
[MMTR-SIG] motion stopped at occupancy block 398.93m (rail ahead occupied, waiting)
[MMTR-AWS] acknowledged          ← 紧接着，同秒
[MMTR-AWS] warning cleared (restriction gone)
```

用户当时按过 H（新加的键）——但**不是在警告响的时候**按的。

## 2. 根因

`Vehicle.applyMmtrControl` 收到 `acknowledge` 就无条件入队：

```java
if (mmtrActiveControl.isAcknowledge()) { mmtrAwsAckQueued = true; ... }
```

而 `tickMmtrAwsWarning` 在"当前无受限边界"的早退分支里，**只在状态非 NONE 时**才清这个队列：

```java
if (!restricted) { if (mmtrAwsState != MMTR_AWS_NONE) { ... mmtrAwsAckQueued = false; } return; }
```

于是**没有警告时按的确认会一直挂着**；等下一次警告响起，第一 tick 置 WARN 并 return，
**第二 tick 就消费掉那个陈旧确认** → 状态直接 ACKED → 2.5 s 窗口从未计时 → 永不 SPAD。

## 3. 修复

| 位置 | 改动 |
| --- | --- |
| `applyMmtrControl` | 只有 `mmtrAwsState == MMTR_AWS_WARN`（警告正在显示）时才入队；其余情况丢弃（并照旧清掉控制状态里的标记） |
| `tickMmtrAwsWarning` | 进入 WARN 时清空队列；无受限边界时**无条件**清空队列 |

语义变成："确认 = 对**正在显示的那次警告**的一次点按"，与真实 AWS 的取消按钮一致。

## 4. 用例与验证

- 新增 `MmtrAwsWarningTests.anAcknowledgePressedBeforeTheWarningDoesNotCancelIt`：
  先在不受限时发一次 `setAcknowledge(true)`，再照常驶向被占轨 → 警告仍要响、且**未再确认时必须 SPAD**（修复前必失败）。
- `MmtrAwsWarningTests` **6/0**；全量引擎 **474/0/2**（上一轮 473/0/2）。

## 5. 另一个观察（不是缺陷，但影响你复现）

日志里那次警告时，列车已经**停在占用块前 0.4 m**（`boundary at 398.9m`，车在 398.5m）。
SPAD 的前提是**仍在行驶**（`mmtrManualOverride && speed > 0`）——"已安全停稳不惩罚"是设计语义。
所以要看 SPAD，必须**在滚动中**接近非绿信号、且窗口内不按 H；若车先被占用块拦停，就不会 SPAD。
