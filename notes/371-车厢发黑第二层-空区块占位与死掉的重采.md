# 371 · 车厢发黑（第二层）：**空区块占位**也被当成"区块到手了"，而且 `markChunkDirty` 从来没有调用点

日期：2026-10-03 · 承接：**notes/367**（第一层：光场采到了客户端没有的区块）· 相关代码：`render/light/MmtrLightField.java`

**用户口径（原话）**：「现在能开了，但是我当前所在位置列车发黑，光照问题仍未解决」。
（"能开了"= notes/370 的编组尾车驾驶室修复：`saf420` 10B 现在真的能开。）

**一句话结论**：367 把判据放在"客户端有没有这块数据"上，方向是对的，但那道闸门
（`ClientWorld.isChunkLoaded`）**对客户端自己放的"空区块占位"返回 true** —— 传送落地那一瞬，
`getBlockState` 全是空气、`getLightLevel` 全是 0，于是照样采出"合法但全 0"的一节并被发布；
再叠上第二个独立缺陷：**`markChunkDirty()` 全仓没有调用点**（367 §4 改动 4 从未接线），
"光照变了就重采"整条不存在 ⇒ 那一节永远黑着，`实心 0.0% + 全 0` 于是"仍未解决"。

---

## 1. 复现证据（本轮日志，已经是 notes/367 之后的代码）

367 §5 给的验收判据是"`sky 0..0 avg 0.00` 只剩真地下（不会 `实心 0.0% + 全 0`）"。实测**不成立**：

```
[11:28:55] slots=24/256 … 未加载跳过(车次)=0 | section(-108,4,86) slot=13 block 0..0 avg 0.00 / sky 0..0 avg 0.00 / 实心 0.0%
[11:29:50] slots=15/256 … 未加载跳过(车次)=0 | section( -92,4,86) slot=4  block 0..0 avg 0.00 / sky 0..0 avg 0.00 / 实心 0.0%
```

* `未加载跳过(车次)=0` ⇒ **367 那道闸门说"区块到手了"**；
* `实心 0.0%` ⇒ 那一节**连一个实心方块都没有** ⇒ 客户端手上其实是空区块占位（列车停在道床上方，
  真实的一节不可能 100% 空气且天空光 0）；
* 两个时刻都紧跟一次 `train board` 的**传送**（11:28:23 落在 (-1911, 76, 1388)，11:29:4x 落在 (-1662, 76, 1388)）。

同一现象在上一场（03:10）也在，且有一个**更硬的旁证**：同一个世界点 `(-1795, 74, 1387.5)`，
在**传送落地那一场**（11:32）客户端读到的真实光照是 `0/0`，而在**区块真到手之后**（11:40）同一点是 `6/15`
—— 也就是说，"客户端手上是空区块占位"这件事连**世界读数**都看得见，不只是光场的问题。

> ⚠️ 订正一处早先记错的证据：诊断行里的 `车心光场采样=0/0 真实光照=6/15` **本身不是**"光场数据错"的证明 ——
> 那两行当时读的是**相邻两格**（光场按 `floor(世界坐标 − 0.5)` 取，基准按 `floor(世界坐标)` 取）。
> 本条已一并修掉（见 §3 改动 5）。真正可靠的证据是"采到 `实心 0.0% + 全 0` 的 section 被发布"这一条。

## 2. 两个独立缺陷

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | `isChunkLoaded` 对**空区块占位**为真 ⇒ 采集读到"空气 + 零光" | 上面两条 `实心 0.0% + 全 0`，且 `未加载跳过=0` |
| 2 | `markChunkDirty(int chunkX, int chunkZ)` **全仓只有声明、没有调用点** ⇒ 采过就永远不刷新 | `grep -rn "markChunkDirty" src/` 只有 `MmtrLightField.java:609` 自己 |

缺陷 2 的后果正是用户口径里的"**仍未解决**"：即使某一节采歪了，也没有任何机制把它改回来。

## 3. 修法（都在 `MmtrLightField.java`）

| # | 改动 | 为什么 |
|---|---|---|
| 1 | `summarizeSection()` 改成**返回**"这一节是不是纯空气 + 零光"（`blockMax==0 && skyMax==0 && solidCount==0`）；是 ⇒ **不发布**：`slotReady` 清位、`clearAtlasTile`/`clearSolidRow`、`lutDirty=true`（LUT 那一格变 0 ⇒ 着色器**退回 MTR 的 per-draw 光**，可预测、不黑），并按 **1 s → 8 s 退避**重采 | 判据放在"数据可不可信"这一层当**兜底**：367 的能力闸门抓不到空区块占位，这一条抓得到。真地下的一节不会是"纯空气 + 零光"（一定有实心方块或非零方块光），所以误杀面极小 |
| 2 | `ensureSlot()` 里加**滚动重采**：跟踪中且有车经过的 section，采满后每 **3 s** 重采一次（零光的那一节按 1..8 s 退避） | 这就是 `markChunkDirty` 那条死掉的意图的落点：光场是"世界的光"的快照，区块后到手、点灯、日夜、进隧道都会变。范围只有"有车经过的 section"（`ensureSlot` 只被 `requestCar` 调到），代价封在既有采集预算里（每帧 4 层 × 16×16，队列按离相机远近排序） |
| 3 | 新读数：slots 行加 `零光重采=N`；拒绝时摘要前加 `【未发布·零光，等真区块】` | 现场一眼分清"这一节是没采到"还是"采到了真数据"。否则诊断行里看到的仍是一节全零的 section，像是没修 |
| 4 | LUT 诊断行的"最近登记车"改成**离相机最近**的那辆车 | 原来取"最后登记的那辆"，而 MTR 优化渲染器不做距离剔除、一帧登记几十辆车 ⇒ 探针落在 460 格外（`最近登记车=(-1262.88, …)` 而相机在 -1720），眼前那节车一行读数都没有。顺带修掉"清零时机放在 beginFrame 开头 ⇒ 打印时是 (NaN, NaN, NaN)"这个自作自受 |
| 5 | `worldLightAt()`（诊断基准）改用**与光场同一格**：`floor(世界坐标 − 0.5)` | 原来用 `floor(世界坐标)` = **隔壁那一格**。车厢贴着站台/道床时，两格的差别正好是"空气（天空光 15）"与"实心（0/0）"，于是诊断行显示成"光场 `0/0` 而真实光照 `6/15`"，看起来像数据错了 —— 其实旁边那行 `车心 AO=0.60（格点实心=是）` 早就说明采样点埋在实心方块里。这条**不修画面，只修诊断的可信度** |
| 6 | **着色器兜底**（`mmtr_lightfield_mtr.glsl`）：光场采到"两个分量都 0"时，与 MTR 自己给的 per-draw 光取 `max()` | 光场只许把车厢**照亮**，不许凭一个"落在几何里面"的采样点把它压黑。真正的暗处（隧道/夜里）MTR 的 per-draw 光本来就是暗的，`max()` 不会提亮它；而"数据还没到手 / 采样点埋进方块"这两种情形下，结果都不会比"光场不介入"更黑 |

## 4. 实机验收（2026-10-03 11:37 重启客户端后）

修复前（同一段日志）：`section(-96,4,86) slot=13 block 0..0 / sky 0..0 / 实心 0.0%` 被**当作数据发布**。

修复后：

```
[11:37:55] 零光 section ⇒ 不发布、等真区块（第 1 次重采）：section(-96,4,86) slot=13 block 0..0 avg 0.00 / sky 0..0 avg 0.00 / 实心 0.0%
[11:38:27] slots=21/256 … 零光重采=2 | section(-96,4,86) slot=13 block 0..0 avg 0.00 / sky 0..15 avg 13.16 / 实心 8.2%
```

**同一个 section**：被拒时全 0，两轮重采之后 `sky 0..15 avg 13.16`、`实心 8.2%` —— 真数据回来了、发布了。

最终构建（含着色器兜底与诊断修正）另一次重启后的同一段：

```
[11:42:52] LUT: cells=2  tracked=38 | 最近登记车=(-1766.62, 74.00, 1387.50) 车心光场采样=0/0 真实光照=0/0
[11:42:57] LUT: cells=36 tracked=38 | 最近登记车=(-1764.04, 74.00, 1387.50) 车心光场采样=0/0 真实光照=0/0
[11:42:57] slots=38/256 … 零光重采=6 | 【未发布·零光，等真区块】section(-123,4,86) slot=38 block 0..0 / sky 0..0 / 实心 0.0%
[11:43:07] slots=38/256 … 零光重采=1 | section(-113,4,86) slot=10 block 0..15 avg 2.77 / sky 0..15 avg 5.58 / 实心 57.9%
[11:43:02] AO 探针：车心 AO=0.60（格点实心=是）
```

两个读数都自证了：

* `cells=2 → 36`：刚落地时几乎全部 section 都被判"零光、不发布"（正是空区块占位），
  几秒内真区块到手，逐个转成已发布 —— **这就是"传送落点附近的车厢发黑"的现场**；
* `车心光场采样=0/0` 与 `真实光照=0/0` **一致**，且 `格点实心=是` ⇒ 这一格的 0/0 是**真的**
  （采样点埋在站台里），不是数据缺 —— 修好诊断之后，"光场与真实不一致"这种可疑读数不再出现。
* 客户端日志里**没有着色器编译错误**（两条 `could not find sampler named Sampler2` 是每一场都有的
  MTR 原生警告，`dev-client-*.log` 场场各 2 条，与本次改动无关）。
其余窗口的摘要也都是真值（`block 0..15 avg 2.75 / sky 0..15 avg 9.23 / 实心 26.7%`、`sky avg 5.58`…），
`未加载跳过(车次)=0`。

## 5. 现场怎么判"还黑不黑"（不用猜）

1. `零光重采=` 在传送刚落地时**非零是正常的**（那正是空区块占位被挡下来的次数）；
   它应当在几秒内回落到 0。
2. **绝不该再看到**"没有 `【未发布·零光…】` 标记、却又是 `实心 0.0% + 全 0`"的摘要 ——
   那种组合现在只以"未发布"的形态出现。
3. 眼前那节车的读数看 LUT 行的 `最近登记车`（现在真的是离相机最近的车）：
   `车心光场采样` 要么是真值，要么是 `无数据`（= 该节未发布 ⇒ 走 per-draw 光）；
   **不该再出现"`0/0` 而 `真实光照` 非 0"**。

## 6. 诚实的代价（取舍写在明处）

* 真的"完全封闭 + 一点光都没有 + 全是空气"的一节（少见）现在**永远不进光场** ⇒ 那种地方的车厢走
  MTR 的 per-draw 光。这与着色器里"宁可少黑也不要因为缺数据凭空变黑"是同一条口径。
* 滚动重采让"跟踪中的 section"每 3 s 重采一次：`slots` 上限 256、采集预算每帧 4 层，
  实测 `零光重采` 与 `collected` 都正常（见 §4）。若将来槽位数大幅上升，先看
  `collecting=` 是否长期非零 —— 那是"采集跟不上"的信号。

## 7. 教训

1. **"客户端有没有这块数据"不能只用一句 `isChunkLoaded`**：客户端在传送后会放**空区块占位**，
   它对"在不在"回答 true、对"内容"回答"空气"。所以能力闸门要有**兜底的结果判据**，
   两条一起用（一条防漏、一条防误）。
2. **写了"什么时候重采"的函数，要 grep 一遍调用点**：`markChunkDirty` 从写下那天起就没有调用点，
   367 的 §4 把它记成"已修"，实际那条链整条是死的 —— 症状就是用户说的"仍未解决"。
3. **诊断探针要钉在用户看的东西上**："最后登记的那辆车"在离相机几百格处毫无意义；
   一行读数必须落在"眼前这节车"上，否则修好了也证明不了。
