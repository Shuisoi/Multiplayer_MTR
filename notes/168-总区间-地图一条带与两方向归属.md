## 1. 问题是真的：L2 是**有方向**的，两条带会叠在一根轨上

灯是**错开**布置的（上行灯与下行灯不站在同一处），所以：

- 上行区间 = 从某架朝上的灯走到下一架朝上的灯；
- 下行区间 = 从某架朝下的灯走到下一架朝下的灯；
- 两个方向的边界**不重合** ⇒ 一辆车夹在中间时，**同时**落在"上行某段"和"下行某段"里。

现场实测（notes/166 期间）：140 根轨里 **62 根属于 2 个以上 L2 区间、最多 5 个** —— 按 L2 画就是
**多条带压在同一根轨上**，既重叠、又说不清"这一段现在归谁"。用户要的正是"地图上每个位置只画一条带"。

## 2. 结论：它是 **L1 的那一段**，不是第三层划分（证明必须写死）

1. 两个方向的行车区间**各自**都是"若干 L1 段的并"（L2 的边界必是灯位 = L1 的切点，notes/166）；
2. 所以它们的**交、并、按"覆盖配对"分组**，结果**都还是 L1 段的并**；
3. 而**相邻两个 L1 段之间必有一盏灯** —— 是上行灯就会换掉上行区间、是下行灯就会换掉下行区间 ——
   于是"覆盖配对相同"的最大连段**恰好就是 L1 段本身**；
4. 想更粗（把错开"抹平"成一条对齐的带）就只能**放弃某一个方向的灯当界**，
   那与裁定 2「切点只由灯产生」直接冲突。

⇒ 总区间的**几何 = L1**（同一批 id、同一批 span），它多出来的只有**归属**这一半：
"这一处由哪几个方向的哪几段覆盖、那些段现在什么显示、占不占"。

**因此它不是"新的切法"，而是"L1 ＋ 两方向的覆盖关系"** —— 也正因为如此，它必须放在**服务端**：
几何是引擎的结论，归属（覆盖关系、显示、占用）也只有引擎算得对。网页自己求交必然与引擎的容差漂移
（notes/113 的 web 侧划分出过 137 片 / 64 处重叠；notes/158 记过 3 m 与 4 m 容差不一致）。
HUD 与网页都读同一份结论。

## 3. 对外形态

`GET /mtr/api/map/mmtr-total-sections`（`SystemMapServlet.getMmtrTotalSections`）：

```json
{
  "totalSections": [{
    "id": "T12",                    // 就是那一段 L1（与 /mmtr-track-sections 同一批 id）
    "length": 100.0,
    "occupied": true,               // L1 那唯一一条判据的答案
    "directions": 2,                // 覆盖它的行车方向数（2 = 上下行都照到这一处）
    "staggered": true,              // 错开：两个方向都照到，但不是同一段路
    "covers": [
      {"section": "50,0,0", "entrySignal": "50,0,0", "exitSignal": "", "next": "150,0,0",
       "aspect": "RED", "occupied": true, "uncovered": false, "length": 150.0,
       "direction": {"angle": 270, "label": "东", "dx": 1, "dz": 0}},
      {"section": "150,0,0", "entrySignal": "150,0,0", "exitSignal": "", "next": "",
       "aspect": "GREEN", "occupied": true, "uncovered": false, "length": 150.0,
       "direction": {"angle": 90, "label": "西", "dx": -1, "dz": 0}}
    ],
    "spans": [{"hex": "…", "from": 50, "to": 150, "points": [x, z, …]}]
  }],
  "count": 3, "busyCount": 1, "staggeredCount": 1
}
```

引擎侧：`MmtrSectionService.TotalSection`（几何 ＋ 原始 cover 表）、
`TotalView`（几何 ＋ `SectionView` 覆盖表 ＋ `occupied`）、`totalSections()` / `totalSectionViews(trees, restricted)`。
指令：`totals`（一行一条带，下面挂各方向 cover —— 与 `tracks` / `lamps` 同一套口径）。

## 4. 语义细节（每条都有用例）

1. **一处一条带**：`everyPlaceHasOneTotalSectionWhoseGeometryIsTheTrackSection` 钉住
   `总区间数 == 轨道区间数`、`id` 相同、span 相同 —— 防止以后有人按"上下行都照到"再划一遍。
2. **"既在上行、也在下行"是可查的**：错开处车压在同一根轨上，`covers[].occupied` **两条都报 true**
   （`aCarOnAStaggeredStretchSitsInBothDirectionalSectionsAtOnce`）。这是用户那句话在数据里的形状。
3. **"同一段路"按集合比，不按顺序比**：上行段从西往东数、下行段从东往西数，同一段路的 span 表
   顺序正好相反；按顺序比会把**成对布置**的灯误判成错开（`lampsPairedAtTheTwoEndsAreNotStaggered`）。
4. **`staggered` 只在两个方向都照到时才有意义**：一处若只有单侧有灯（或另一侧是无灯大区间），
   报 `directions=1` —— 那是"半边无灯"，与"错开"是两件事（`aStretchOnlyOneDirectionReachesReportsASingleCover`）。
5. **占用仍然只有一条判据**：`occupied` 就是 `isOccupied(L1)`；它不是"各 cover 的或"
   —— 两者恒等只是因为 L2 的占用本来就来自 L1（notes/166 裁定 4）。

## 5. 顺带修掉的缺陷

`sectionViews(...)` 过去**不含无灯大区间**（它们没有入口灯可作键，从没进过 `sectionsBySignal`），
于是 `/mmtr-block-sections` 的 `uncovered` 字段永远是 false、无灯的世界在网页上"一段区间也没有"。
详见 notes/167 §5。修完后无灯处也有 cover（两条，`entrySignal` 空、`aspect` 空）。

### 6.1 这一轮现场抓到的事故：**半个 jar**（jar 在服务端运行时被换掉）

`deploy-engine.ps1` 头里早就写下过这条事故的症状清单，这次**原样复现**：

- 服务端 tick 里持续抛 `java.util.zip.ZipException: invalid LOC header (bad signature)` /
  `EOFException: Unexpected end of ZLIB input stream`（日志里 13:17–13:18 那批，785 条）；
- `[MMTR-HLTH] vehicles=0`（车全没了）；
- **指令通道完全不应答**：`mmtr-command` 执行任何一条指令都挂到超时（实测 `vehicle list` / `point list` /
  连只有一句用法文字的 `server` 都超时），而**地图接口照常回 200** —— 看起来像"引擎卡死"。

原因：Fabric 的类加载器**按需**从 `game/libs/Transport-Simulation-Core-0.0.1.jar` 里读 class，
在它还活着的时候覆盖这个 jar，等于把正在读的 zip 换掉一半。

恢复：**一键重启**（`server restart`）。但注意顺序上的两难 —— 优雅停机本身要靠指令通道，而通道正好死了，
所以这一轮只能"写重启标记 + 杀 JVM"让启动器接力；起来之后：

- 指令通道 `query totals` 从**超时**回到 **116 ms**；
- 换新 jar 的时机放在**没有服务端 JVM 的那几十秒**（杀掉/停掉之后、启动器拉起新 JVM 之前），
  这次是：14:12:51 受理重启 → 14:12:55 JVM 已停、顺手换 jar → 14:13:24 新 JVM → 14:13:41 接口应答。
- 新一圈的日志里 **Zip 错误 0 条**。

⇒ **纪律（写死）**：换 `game/libs` 里的 jar 只允许两种时机 —— 服务端没在跑（`deploy-engine.ps1` 默认拦的就是这个），
或者**换完立刻 `server restart`**；"换完让它继续跑"必然走到上面那三个症状。

## 7. 不做 / 留给下一轮

- **不用它替代 L2 做授权**：总区间只解决"怎么画"，授权仍然必须看方向（它只是 L1 ＋ 覆盖关系）；
- **画法的主角是谁还没定**（用户可一句话改）：现在是"正中一条 0.1 格的带（嵌在 L2 两条方向带之间的
  空档里，横截面互补不重叠）"；若要让总区间当主角，就把它改成 0.6 格宽带、
  把 `BlockSectionsLayer` 改成 0.2 格 / 偏 0.4 格（0.2+0.6+0.2 = 1 格，同样互补）；
- **显示档位是否按灯头数收口**（`SignalEntry.aspects`）仍未定 —— 用户问过"正常吗"，等裁定；
- **L2 唯一归属**（按"最近上游灯优先"让每一米在同一方向上恰好属于一段）**没做**：
  咽喉处多腿重叠是刻意的（"一盏灯守整个咽喉"），要收口必须先有裁定。
- **浏览器实测还没做**：本轮的验证是引擎侧探针（真实世界 113 段）+ 前端纯函数用例（10 条）+
  `vue-tsc`/`vite build`；页面上的逐条比对（像 §六 那几条 `sandbox/*.mjs` 探针）等下一轮。

## 8. 用户裁定（2026-09-16，本轮）：**总区间当主角** —— 1 格宽、画在中心线上；L2 方向带从页面撤下

> 原话：「现在服务端新增了叫总区间的逻辑用于绘图，但是那边不小心应用在地图上了，
> 现在按当前的风格重新绘图，**区间线宽和点相同**。」

§7 的第一条（"画法的主角是谁还没定"）就此落定，而且比原先设想的 0.6 格更彻底：

1. **总区间的带 = 1 格宽**（`TotalSectionsLayer.BAND_WIDTH = UNITS_PER_BLOCK`），画在**轨道中心线上、
   不让开**。1 格 = 与区间切点、轨道线同一个数，所以它**正好盖住整根轨**：这一页看得见的"轨"
   就是这条带。几何仍是 span 采样点**原样**投影（与 L1 同一批点，实测 160/160 逐点命中）。
2. **L2 方向带从页面撤下**（`BlockSectionsLayer.vue` 与它的画法说明都留着）：它 0.4 格、偏 ±0.25 格，
   会被 1 格宽的带整条盖住；方向归属（哪几个方向、各自什么显示、错开没有）改从**悬浮提示**读
   （`TotalSectionsLayer` 每条的 `<title>`）。实测这一页 `polyline.band` = 0、`polyline.total-band` = 160。
3. **道岔淡出改挂在带上**：轨被盖住之后轨的 `stroke-opacity` 就看不见了，所以"道岔没指向的那根出口"
   改成**它所在的那条带**淡到 0.5 —— 判据还是引擎在 `mmtr-points` 每行给的 `prohibited`，
   用的还是同一个 `prohibitedRailHexes()`（两页同源，网页不自己算几何）。实测 **27 根 / 27 条带**。
   代价（写在图层文件头，等用户一句话）：黑底上 50% 透明度 = 颜色变暗（黄 `#d8b81c` → 暗橄榄
   `#6c5c0e`），于是"被切掉的黄"与"淡黄 `#e3dc9c`"观感接近。

### 8.1 顺带抓到的坑：**轨 hex 的写法跟着行车方向走**（不规范化就漏一根）

span 里的 `hex` 按**行车方向**写，`mmtr-topology` / `mmtr-points` 按另一种顺序写 —— 实测 159 根里
**10 根**倒过来（例：`(1,64)→(-19,51)` 写成 `(-19,51)→(1,64)`）。第一版按字符串比对，于是
**27 根禁止轨只淡了 26 根**，肉眼看不出（少淡一条而已），是探针逐条比对才现形的。
修法：`domain/MapNode.ts` 新增 `railHexKey()`（两端坐标三元组排序），跨来源比对前先过它。
轨道层那两处是 `mmtr-points` ↔ `mmtr-topology`，实测两边写法一致（27/27 原样命中），不受影响。

### 8.3 端点放大一倍（同日，用户：「将行车区间的端点变为原来的2倍」）

这一页看得见的"端点"就是**区间端点**（`SectionCutPointsLayer` 的那些点）：L1 的切点，也就是
**行车区间的端点所在处** —— L2 是"灯到灯"，而切点只由灯产生（notes/166 裁定 2），两个方向的区间
都在这批点上断开。原来是 1 格（与「地图」页的节点圆点同口径），现在：

- **连描边 2 格**：`CUT_POINT_DIAMETER = UNITS_PER_BLOCK * 2`，边框按同一比例（直径的 10% ⇒ 0.2 格）
  一起放大 ⇒ r = 1.8、描边 0.4、外径 4.00 画布单位 —— 观感还是"白心 + 灰边"，只是整体大了一倍；
- **实测**（`section-track-probe` 6/6 + `total-sections-raster` 第 ⑤ 条）：
  r = 1.8 + 描边 0.4 ⇒ 外径 **2.000 格**（默认取景 3.24 px）；像素扫描有覆盖的跨度
  **4.0 画布单位 = 2.00 格**，中心白 `rgb(255,255,255)`、边缘灰 `rgb(132,132,132)`；
- **没黏成一团**：端点之间的最近距离中位数 **8.94 格**（最小 5.10 格），间距 < 2 格（会互相盖住）的
  **0 个** —— 所以这次放大不会把密集区糊成一片。
- 注意**它现在比带宽（1 格）还大**：点是画在最上层的，所以每个断点处会看到一颗 2 格的点压在 1 格宽的
  带上面（这也正是"看得出区间在哪儿断开"的本意）。

### 8.4 点的样式与「地图」页相同（同日，用户：「点的样式也和地图相同」）

尺寸 2 倍之后用户紧接着要的是**样式**与「地图」页的节点圆点一致。这一页原来只有"白心 + 灰边"，
所以补上的是那一套**渐变黑色外阴影**（`RailNodesLayer` 的写法逐条照抄，id 另取 `#mmtr-cut-point-shadow`）：

- 半径 = 点外半径 **×2.5**（同一个倍数），径向渐变 `0% 全黑 → 40% 全黑 → 100% 透明`
  （40% = 点边缘，`100 / 2.5`，在这之前全黑反正被点盖住）；
- **阴影画在点和带/线之间**（与「地图」页同一个理由：它落在穿过端点的总区间带与轨上，黑圈才看得见；
  画在线下面等于白画）；
- 边框仍然占直径 10%（0.4 画布单位）—— 与「地图」页 0.2/2.00 同比例。

验证：新探针 `sandbox/point-style-probe.mjs`（**6/6**）**依次切到两个页签**把两页的计算样式逐条对起来 ——
颜色、边框占直径 10%、阴影半径 ÷ 外半径 = 2.5、渐变停点 `0%/40%/100%`、叠放（阴影在点下、点压在轨与带上）
**五条全同**，唯一的差别是尺寸（1.00 格 vs 2.00 格 = 2×）。
`section-track-probe` 也加了一条同样的样式检查（7/7），`total-sections-raster` 的端点那一条多了
"点外那圈是不透明的黑"（|dx| 2.4–3.0 处 alpha 166–208 —— 这也顺带回答了 §五 那个"黑底上阴影看不见"
的老问题：在**带**上面它是看得见的）。

### 8.5 信号灯也画进区间地图（同日，用户：「然后信号灯也一起显示在里面」）

做法是**直接复用「地图」页那一个图层** —— `SectionMapView.vue` 里加一行 `<SignalLayer/>`（压在最后）。
它能直接复用是因为这一层**自给自足**：自己 `fetchMapNodes()` 取灯与节点、自己按方位槽摆位，
只依赖框架的 `project()`；而这一页的锚点由 `SectionTrackLayer` 用**同一个算法**（节点云中心）报到，
所以两页的投影完全一致、灯的位置逐盏相同。

- 灯的尺寸与颜色**照「地图」页的原样**（灯点连描边 1 格、`^` 高 0.6 格张角 90°、离节点 2 格；
  绿 `#22c55e` / 红 `#ef4444` / 单黄 `#c8920c` / 双黄 `#ffd400`）—— 这一页没有把灯跟着端点一起放大，
  用户原话只是"一起显示在里面"；要放大是一句话的事。
- 叠放变成四层：**轨 → 总区间的带 → 区间端点 → 信号灯**（灯压在最上面，与「地图」页的
  "轨 → 阴影 → 节点 → 灯"同一个相对次序）。
- **一个值得知道的位置差（当场就修了）**：灯原本锚在**拓扑节点**旁（方块角），而这一页的端点在
  **方块中心**，两者相差半个方块 ⇒ 用户当场看出来「**灯左右分布不均匀**」（实测：右边的灯离点
  **1.58 格**、左边的 **2.55 格**；48 盏 2.55 + 43 盏 1.58）。修法：给 `SignalLayer` 加一个
  `anchor-frame` 属性，这一页传 `"rail-sample"` —— 锚点整体搬**量出来的**采样偏移
  （`domain/Rail.ts` 的 `railSampleShift()`，众数，实测 (0.5, 0.5) 格；与"轨端点 → 最近的 span
  采样点"量出来的完全一致，318 个轨端点都是这个偏移）。修完 **94/94 盏正好 2.000 格**，
  左 45 盏、右 45 盏的中位数都是 2.000 格 ⇒ 左右对称。「地图」页默认 `"node"`、偏移恒为 (0, 0)，
  一字未变（`signal-layer-probe` 14/14 仍是"离最近节点 2 格"）。
- **这不是"图像偏移"**：区间图的轨/带/点**都在同一套写法里**（方块中心），实测 155/156 个端点都落在
  "最近的拓扑节点 + (0.5, 0.5) 格"上、317/318 个轨端点与最近的 span 采样点也差 (0.5, 0.5) 格 ——
  全图层一致，没有"向右偏"这回事；偏的只有灯那一层（它是唯一按节点坐标摆的）。

验证：新探针 `sandbox/signal-on-section-probe.mjs`（**7/7**）依次切两个页签，逐盏比对
rotate / 灯点 r、描边、颜色 / `^` 的路径、描边、颜色、不填充，并验"translate 只差量出来的采样偏移"、
叠放、"灯的左右对称"（两侧中位数都 2.000 格）与"灯心像素 = 状态色"。同时把 `total-sections-probe`
的叠放断言（尾节点从端点变成灯）与 `section-track-probe` 的圆点计数（只数 viewport 的**直接子**圆点，
灯点是嵌在 `g.signal` 里的）跟着改准；`node-ui-probe` 的剪贴板桩改成**只包一层**
（同一个页面重复跑时不再把每笔记两次 —— 实测踩过）。

实测读数（2026-09-16，活页面同一时刻）：94 盏，颜色 绿 61 / 红 19 / 单黄 9 / 双黄 5，
旋转角 0°×45、180°×45、90°×2、270°×2；两页 94 盏的 `transform` **逐字符相同**。
