# 205 · 雨滴「车内看不见、车外可见」：车的网格先画、雨层是排队后画

> 用户实测：**雨滴车内不可见，车外可见**；且**没有明显的物理雨滴、只是不动**。
> 前一半（车内不可见/车外可见）在代码里是**确定的**，见 §1；后一半见 §5（两条都要先确认「世界里正在下雨」）。

---

## 1 真因：同一个座位，玻璃的**深度写入**把雨层挡掉了

雨层是一张四边形，沿玻璃锚点法线抬起 `WATER_OFFSET_M = 0.030 m`（正值 = 朝车外）。

而**车体自己的网格和雨层的提交时机不同**：

```
RenderVehicles.java:272   MmtrWindshield.render(...)   -> 只是 MainRenderer.scheduleRender（排队）
RenderVehicles.java:274-275   model.render(...)        -> 车体 + interior_glass 立刻提交
RenderVehicles.java:179   CustomResourceLoader.OPTIMIZED_RENDERER_WRAPPER.render(...)  -> 整包最后
MainRenderer.java:134-177 才把排队的层倒出来画（EXTERIOR_TRANSLUCENT_DOUBLE 是枚举最后一个）
```

于是**玻璃先被光栅化并写入深度**，排队里那些**比它离相机更远**的像素随后被深度测试丢掉：

| 视角 | 相机在哪侧 | 先被击中的面 | 结果 |
|---|---|---|---|
| 车外 | 玻璃**外侧** | 雨层（+0.030 在玻璃之外） | **雨可见** ✅ |
| 车内（司机位） | 玻璃**内侧** | **玻璃内表面** | 雨层在它后面 → **被挡掉** ❌ |

这正好解释「车外可见、车内不可见」这种**单侧**症状——不是朝向问题，是**深度遮挡**。

### 实测玻璃面在哪（`sandbox/_q_glass_offset.py`）

以锚点平面为 0、法线朝车外为正，实测 `interior_glass` 的顶点分布：

```
glass_offset_min = -0.0115 m   （玻璃内表面，朝司机一侧）
glass_offset_max = +0.0115 m   （玻璃外表面）
```

也就是**玻璃厚度约 0.023 m，锚点平面基本在玻璃中面**。原来的 `+0.030` 落在玻璃外表面之外
约 20 mm —— 司机从里往外看，视线先撞内表面，雨层在 42 mm 之外，**必然被深度测试丢掉**。

---

## 2 修法：把雨层放到**司机这一侧**，并做成逐玻璃可配的字段

新增配置字段 **`waterOffsetM`**（默认 `+0.030`，可负）：

| 位置 | 改动 |
|---|---|
| 客户端 | `MmtrWindshield.WindshieldConfig` 新增 `waterOffsetM`（钳在 ±0.5 m），`drawRain` / `logPlaneOnce` 改用它，不再读常量 |
| 打包器 | `pack_vehicle.js` 的 `WINDSHIELD_FIELDS` 加 `waterOffsetM`（不加 = 写进锚点 JSON 却被静默丢掉，就是 notes/179 §9.4 #3 那个坑） |
| 车配置 | `example/vehicle.br101.json` 的 `windshield` 块：四个面都 `"waterOffsetM": -0.03` |

`-0.03` 落在玻璃内表面（实测 −0.0115）**里侧约 18 mm**，所以：

- **车内**：雨层比玻璃更靠近司机 → 深度测试通过 → **看得见** ✅
- **车外**：玻璃仍挡在相机与雨层之间 → 车外那一侧**失去**雨层

> ⚠️ **这是一个权衡，不是无损修复**：雨层是**一张**四边形，只能待在玻璃的一侧。
> 这次选了「司机看得见」，因为用户看的是驾驶室。要两侧都保住，就得画**两张**（各带自己的偏移），
> 代价是多一次混合绘制 —— 留作后继项（§6）。
>
> 日志里 `[MMTR-WSHLD] ... all out-of-plane must be -0.03` 会直接把选的那一侧打印出来，
> 不用猜。

## 3 「雨滴不动」怎么读

`sandbox/bl.py` + `tools/wiper-preview` 的离线证据（24 项断言全过）说明**模型本身会动**：

```
[ok] 静止时雨珠向下流（平均方向朝下）              meanDirY=-1.00
[ok] 静止时雨珠下落速度 0.15~0.80 m/s               movingSpeed=0.7016
[calib] 20s pinned=0.58 running=0.42               ← 58% 钉住、42% 在流
[calib] 60s pinned=0.62 wetness coverage=0.817
```

- **58%~62% 的雨珠是「钉住不动」的**——这是**设计**（表面张力），不是静止 bug。
  只看一眼确实像"一堆不动的点"；要判断它在不在流，看**有没有水痕在变长**。
- **车速越高越不动**：气流项与车速平方成正比，约 **22 m/s（80 km/h）**处与重力平衡，
  再快就**缓缓向上爬**。所以「跑起来雨点几乎不动」是**预期**的（1.5 m 长风挡、0.09 m/s 上爬）。
- 走路/停车时应该是明显下流的。

### 但有一个前提必须先满足：**世界里得正在下雨**

`snow` 层只在 `rainGradient > 0.02` 时才画：

```java
final float rainGradient = clientWorld != null && clientWorld.isRaining() ? clientWorld.getRainGradient(1) : 0;
final boolean precipitating = rainGradient > 0.02F;
```

若上一次实测是在**没下雨**的时候，那么雨层根本不存在——这与"不动"是无法区分的。
**判据**：开 `[MMTR-WSHLD]` 日志，看有没有 `wiper gate ... panes=4`（有）以及雨层是否重建；
也可在游戏里 `/weather rain` 强制下雨再进驾驶室。

### 3.1 「不动」的四种成因分不开：加了一条量「场自己动了多少」的日志

屏幕上「雨滴不动」至少有四种完全不同的成因，而它们**看起来一模一样**：

| # | 成因 | 现场表现 |
|---|---|---|
| 1 | 世界没下雨 → 雨层根本没画 | 玻璃上什么都没有，或只有上一次留下的残影 |
| 2 | 雨珠**全部**被表面张力钉住（阈值/生长率不匹配） | 有斑点、全静止、**没有水痕** |
| 3 | 场在动但**图没重建**（签名/上传出问题） | 有斑点、静止、`rebuilds` 不增长 |
| 4 | 场在动但**看不出来**（车速高 → 几乎所有雨珠被气流顶住） | 有斑点、几乎不动、**车速一降就动** |

所以新加一行（**每 300 帧、每个玻璃一条，不需要开关**，dry 也打——dry 正是最该看到的那种）：

```
[MMTR-WSHLD] motion windshield_1_1 prev=<正在下雨?> intensity=<> snow=<> speedMps=<>
             down=(<x>, <y>) alive=<> pastPin=<> meanSurfaceSpeed=<> maxStep/frame=<>
             spread=(<x>, <y>) offGlass=<> rebuilds=<> mode=<> angle=<>
```

读法：

- `prev=false` / `alive=0` → **成因 1**（没下雨）。`/weather rain` 再测。
- `alive` 有几百但 `pastPin` ≈ 0 且 `maxStep/frame` ≈ 0 → **成因 2**（钉死）。
- `maxStep/frame > 0` 但 `rebuilds` 不涨 → **成因 3**（画不出来）。
- `maxStep/frame > 0`、`rebuilds` 在涨、`meanSurfaceSpeed` 却很小 → **成因 4**（被气流顶住，看 `speedMps`）。

`maxStep/frame` 是**场自己走了多远**（上一帧到这一帧、所有雨珠里的最大位移），是唯一能把
"动了但你没注意" 和 "真的冻住" 分开的量。

## 3.2 读出来了：`down=(0.0, 1.0)` —— **下落方向反了**

v14 的实机读数（用户提供，节选）：

```
[MMTR-WSHLD] motion windshield_1_2 prev=true intensity=1.0 snow=false speedMps=0.0
             down=(0.0, 1.0) alive=84 pastPin=26 meanSurfaceSpeed=0.225
             maxStep/frame=0.0 spread=(0.97, 1.098) offGlass=4 rebuilds=272 mode=SLOW angle=91.056
```

**`down` 是单位向量、它的「上」分量必须为负**（雨珠往坡下走）。这里是 `+1`，
也就是**雨珠被推向玻璃上沿**：走到边界 → 被 `respawn()` 拉回随机位置 → 再被推上去。
所以玻璃上**有斑点（`alive=84`）、钉扎/生长正常（`pastPin=26`）、表面速度也不小（0.225 m/s）**，
但看起来完全不动 —— `maxStep/frame=0.0` 正是这个。

### 根因：`panelDown()` 盲目对锚点的 `up` 取负

```java
final double alongRight = -plane.right.y();
final double alongUp    = -plane.up.y();     // ← 假设锚点的 up 已经指向"上"
```

这个假设对 BR101 的斜风挡**不成立**：锚点的 `up` 经 `toModelSpace()` 后是
`(0, -0.763, -0.646)` ——**指向下方**。取负自然得到 `+1`。

### 修法：以**锚点作者的口径**为基准，而不是假设

锚点契约是「`up` = 指向车顶」（notes/179 §1 冻结的）。所以**唯一的判据是它的 Y 分量**，
低于地平线时把整个基翻转，再从世界的"下"做投影：

```java
final double flip = plane.up.y() < 0 ? -1 : 1;
final double alongRight = -plane.right.y() * flip;
final double alongUp    = -plane.up.y() * flip;
```

### 为什么这个 bug 能活这么久

- 离线夹具 `tools/wiper-preview` 用的是 `down = (0,-1)` **写死**，绕过这条投影 —— 24 项断言全绿，
  却完全测不到它（夹具的"上"是对的，客户端的不是）。
- 现场表现（"雨滴不动"）与另外三种成因（没下雨 / 全钉住 / 图没重建）**一模一样**。
- 它不会报错、不会掉帧、`pastPin`/`meanSurfaceSpeed` 这些中间量看起来全都正常。

**一条量具解决**：把方向本身打出来（`down=(x, y)`）。中间量正常不足以证明结果正常 ——
必须量**最终那一步的输入**。

## 5 为什么改的是「偏移」而不是「渲染层」

试过的另一个方向是换渲染层让它排在玻璃之后。**不行**：`EXTERIOR_TRANSLUCENT_DOUBLE` 已经是
枚举里**最后**一层（`QueuedRenderLayer` 末尾），而且 `MainRenderer:179` 的
`OPTIMIZED_RENDERER_WRAPPER.render()` 在**所有排队层之后**——车体（含玻璃）永远是最后画的。
所以排队层排序**再怎么调也追不上**车体，只能靠**几何在哪一侧**来决定谁被深度测试留下。
这也就是为什么把偏移做成**逐玻璃配置**：它本质上是**这块玻璃的可见性属性**，不是全局常量。

## 6 遗留

1. **只保住了一侧**（现在=司机侧）。两侧都要就要画两张四边形：内偏移 = `waterOffsetM`、
   外偏移 = `waterOffsetMOutsideM`，两张同层（`total` 混合会把两层叠起来，需要各用一半 alpha，
   见 notes/179 §7 的双面做法）。
2. 雨刷本体（`WIPER_OFFSET_M = +0.045`）在**玻璃外侧**：司机看自己的刀片可能同样被玻璃挡掉。
   本次未验证（用户报的是雨滴）。若实机确认刀片在车内看不见，同一套办法处理（臂/刀片偏移也可配）。
3. 雨滴不随车速横抽、曲玻璃展开（W3）——与本次无关。
