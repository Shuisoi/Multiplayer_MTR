# 269 — HUD「制动力」只显示电制动：整列气制动力必须由引擎算好镜像下来

用户口径（2026-09-25）：**「制动力 xx kN 只显示电制动的」**。

## 1. 现场证据（服务端日志）

```
[MMTR-CONSIST] 手柄=0 制动=4 牵引比=0%/电阻36% 速度=0.0366(内部) 缸压=0.0 管压=0.779 电机=-54kN
```

- 管压 0.779 × 5.2 = **4.05 bar** = 3 档目标 ✓（管压/分配阀都对）；
- **机车缸压 = 0**：电空混合（notes/267）把**机车自己**那份机械制动（≈53 kN）交给电制动削掉了；
- **拖车仍在气制动**：两节 p1 各 ≈22 kN ⇒ 整列气制动力 ≈ **44.6 kN**；
- 电制动 54 kN ⇒ `电阻=36%` 是"混合吃进去的那份 / 可用 150 kN"。

## 2. 根因：HUD 用**车头那一节**的缸压反算整列气制动力

`Vehicle.getMmtrPneumaticBrakeForceN()` 原来拿镜像回来的 `mmtrBrakeCylinderPressure`（**车头/机车**的缸压）
乘制动锚折算。单车时代这是对的；**逐车管压（notes/268）＋电空混合（notes/267）之后就不成立了** ——
机车缸压被削到 0，而拖车还在刹，于是"气"那一份被整段丢掉，HUD 只剩"电"。

另外 `brakeForceText` 当时把量级 <0.5 kN 的一份**省略不显示**，于是连"气 0"都看不到，只看到"（电）"。

## 3. 修法（与"电机出力"同一套路）

1. **新增镜像字段 `mmtrPneumaticBrakeForceN`**（notes/250/257/259 的口径：力的读数一律服务端算、客户端读）：
   - `schema/data/vehicleExtraData.json` + 生成类 `VehicleExtraDataSchema.java`（字段/反序列化/序列化/toString/方法）；
   - `Vehicle.getMmtrPneumaticBrakeForceN()`：**客户端读镜像**；服务端取
     `ThreeHandleDriveController.getLastPneumaticBrakeForceN()`（逐车求和的那份），legacy 控制器退回缸压比例；
   - `VehicleSyncPatch.DYNAMIC_KEYS` 加上它（**漏了白名单 = 只在整份快照时才更新**，notes/257 的老坑）；
   - 控制器在服务/紧急两条支路都记下这一拍的整列气制动力。
2. **HUD 永远显示两份**：`制动力 45 kN（气 45 · 电 0）` —— 一边是 0 本身是信息
   （"电全吃下了"与"气没建起来"是两件事），不再按量级省略。
3. `[MMTR-CONSIST]` 日志行加 `气制动=NNkN`，现场可直接对账。

## 4. 验证

新增用例 `thePneumaticBrakeForceIsTheWholeTrainNotTheHeadCar`——**把现场那一拍原样复现**：

```
[TEST] 现场场景（3 档 @132 km/h）：机车缸压 0.000 bar、拖车 2.407 bar ⇒ 整列气制动力 44.6 kN
```

断言：机车缸压 = 0（混合削掉）、拖车缸压 ≈ 2.41 bar（分配阀那一档）、整列气制动力落在 35–55 kN、
电制动比例 >0.3。修前这条"整列气制动力"根本不存在（客户端只能算出 0）。

全量：**838 条，失败 3 条**（仍是那 3 条预先存在的世界存档漂移）。

## 5. 教训（写下来）

**"逐车化"之后，所有"用一节车的读数代表整列"的反算都要重新审一遍** —— 这一轮已经踩了两次：
① 缸压（HUD 的"缸压"行现在明确是**车头**读数，驾驶室表看的就是它，见 notes/268）；
② 气制动力（整列的数，必须由引擎算好镜像下来）。
这与 notes/250/257/259 是同一根纪律：**HUD 上的每一个力/压力，都该是引擎算好的那一份，不是客户端拿别的读数
凑出来的**。
