## 1 怎么找的

notes/404 §8 把"改完之后还剩什么"列了出来：`getVehicleCarsAndPositions` 仍在渲染线程采样里占
7–9%。它本身是纯查询，所以问题不在它内部，而在**谁在问**：

> 一份 JFR 里，把栈上出现 `Vehicle.getVehicleCarsAndPositions()` 的采样按"它的上一层"归类。

归类结果一眼就能看出：`modelCarIndex`(54) + 各种 `xxxIdFor`(16) 一共 70/79，
而它们要的只是 `cars.get(i).left().getVehicleId()` —— **车节顺序与模型 id**。

而 `getVehicleCarsAndPositions()` 的实现（`Vehicle.java`）是：

```java
for (int i = 0; i < vehicleExtraData.immutableVehicleCars.size(); i++) {
    final VehicleCar vehicleCar = vehicleExtraData.immutableVehicleCars.get(i);
    ...  carNumber → railProgress → getBogiePositions() → PathData.getPositionAndTiltAngle() ...
}
```

**它就是按 `immutableVehicleCars` 的顺序配位置的** ⇒ 只要 id 的调用者可以直接读那份列表，
结果完全相同（同一个 `VehicleCar` 对象、同一个顺序）。

## 2 改了什么

### 2.1 引擎：一个共享 helper + 一个计数器（`Vehicle.java`）

```java
/** 第 carNumber 节车的模型资源 id；越界返回 null。只读 immutableVehicleCars，不算位置。 */
@Nullable
public String mmtrCarResourceId(int carNumber) {
    return carNumber < 0 || carNumber >= vehicleExtraData.immutableVehicleCars.size()
        ? null : vehicleExtraData.immutableVehicleCars.get(carNumber).getVehicleId();
}
```

五个调用点（`MmtrVehicleAnchors.modelCarIndex`、`ModelPropertiesPart.vehicleIdFor`、
`MmtrWindshield.resourceIdFor`、`MmtrDriverSeat.modelIdFor`、`MmtrCabInteraction.modelIdFor`）
全部改成读它。**这几处是纯替换：输出逐位相同**（越界返回 null 的语义也一致），所以没有开关
—— 开关在这一类改动上没有意义（"回退"就是 git diff）。

`modelCarIndex` 还顺手少了一次 `size()` 边界判断的重复（原来是 `carNumber >= cars.size()`）。

### 2.2 车钩提示的粗筛（`MmtrCoupleInteraction.anyTrainNearby`）

它每帧对**客户端知道的每一列车**调 `carCentres(vehicle)`（= 整列车每节车的两个转向架位置），
只为判"有没有车在提示半径 25 m 内"。而一列车的每一节都在**车头往后 `totalLength` 之内**
⇒ 车头到眼睛的距离 > `HINT_RANGE + totalLength + 余量(8 m)` 时，整列车都不可能命中：

```java
final Vehicle.PositionAndTiltAngle head = MMTR_COUPLE_HINT_FILTER ? vehicle.getHeadPositionAndTiltAngle() : null;
if (head != null) { ...距离 > reach ⇒ continue... }
```

被判为"可能近"的列车仍然走**原来那套逐节判定**，所以结论不变（这是保守界：余量给宽了只是多算，
给窄了才会漏，8 m 覆盖了瞄准高度与朝向带来的差）。

开关：`-Dmmtr.couplehintfilter=false` 回到"每列车都算整列位置"。

### 2.3 试过又撤掉的：门洞检查按区块取方块（`RenderVehicleHelper.canOpenDoors`）

`canOpenDoors` 会把门洞框出的立方体逐格扫一遍（`getBlockState` × ~60 格/次）。
试过"按 (chunkX, chunkZ) 各取一次 `BlockView` 再逐格问它"（语义等价：`getChunkAsView` 就是
`getBlockState` 内部那条 `getChunk(x, z, FULL, false)`，未加载区块同样当空气）。

**实测没测出收益，已回退**（读数见 §4）。原因也在读数里：这一段的叶子**两次都是
`net.minecraft.world.chunk.PalettedContainer.get`**（≈ 每条路径都要付的"读调色板"那一步），
而 4 月那次现场里占 70% 的 `World.getChunk` 叶子，在这次 run 里没有复现 —— 叶子归属会被 JIT 内联
改变，**跨 run 比叶子不可靠**。省下的那些区块查询按理论值只有 ~1% 量级，测不出来就不该留在代码里。

## 4 新增的那一格读数（与场景无关）

`[MMTR-FRAME]` 的窗口行现在多一行（**一直在数**，不需要开关 —— 它只在
`getVehicleCarsAndPositions()` 里加一次 `AtomicLong.incrementAndGet()`，稳态几十~几百次/帧）：

```text
  ｜ 车辆位置查询：12614 次（Vehicle.getVehicleCarsAndPositions）
```

它的用法：**它是"还剩几个调用点真的需要位置"的唯一直接指标**。id-only 那几处摘掉之后，
它应当只随"视野里的列车数 × 真的需要位置的调用点（车灯 2 处、平滑位置、车钩粗筛未命中的那部分）"增长；
若哪天它突然涨回去，说明又有人从"只要 id"的路走了位置查询。

## 6 下次从这里开始（交接单）

改后同一份 JFR 里剩下的大头（渲染线程采样，1,189 条）：`RenderVehicles` 14.47%、
`MmtrCabDashboard|panel.` 4.88%、`canOpenDoors` 4.63%、`MmtrFaceRuntime` 1.68%、
`MmtrHeadlights` 1.26%、`getVehicleCarsAndPositions` 0.76%。

### 6.1 门洞检查：省**调用次数**（唯一还没试的方向）

`RenderVehicleHelper.canOpenDoors` 是**每个门洞每 pass 一次**（开光影 pass=2），每次扫一门洞立方体
（~60 格 `getBlockState`）。改后它占 4.63%，其中 ~60% 是 `PalettedContainer.get` —— 那是"读方块状态"
本身，**把每次查询做快救不了它**（§2.3 已实测：按区块取 `BlockView` 测不出差别，已回退）。

唯一有效的方向是**少扫几次**：一次视觉帧内世界不会变（两 pass 之间不发生 tick）
⇒ 在同一帧内跨 pass 复用"这个车这扇门的结论"是**无陈旧风险**的。做法要点：

1. 需要一个**帧号**（`MainRenderer.render` 每视觉帧 +1，或复用现成的帧计数器）；
2. 缓存键：`(车 id, 节号, 门洞 index, 帧号)`；值：`(能否开门, 被挡量, 记下的 PSD/APG 位置表)`；
3. **副作用必须重放**：`canOpenDoors` 里会给未锁的 PSD/APG 推 `setDoorValue(doorValue)`，
   门被玩家挡住时还会 `VehicleRidingMovement.overrideDoors()` —— 命中缓存时按记住的那张小表重放，
   用**本次**的 `doorValue`，这样语义与逐次调用一致；
4. 开关 `-Dmmtr.doorcache=false`，判据：`canOpenDoors` 的渲染采样占比应当约**减半**（4.63% → ~2.3%），
   而 `[MMTR-VDRAW] 门开=…` 的帧数、`[MMTR-DOORBATCH] 门合并：…` 两行必须与改前逐字相同
   （开门态的脸/门数不能变）。

上限就在那儿：约 2.3% —— 如果嫌小，就跳过它去做 6.2。

### 6.2 面板与动态面（改后 4.88% + 1.68%）

它们现在的大头已经**不是**几何/绘制（`MmtrFaceRuntime` 有签名跳过重绘，见 notes/396），
而是**每帧的锚点与布局计算**（`MmtrVehicleAnchors` + `MmtrFrameProbe` 里的 `panel.*` 段）。
继续之前先量：把 `[MMTR-FRAME]` 的 `main.cabdash` / `panel.*` 段拉出来，确认是"算"还是"画"，
再决定是缓存锚点变换还是跳过重算。

### 6.3 还剩下的"真的需要位置"的调用点

`MmtrHeadlights.requestCar/lampColor`（要灯的位置）、`VehicleExtension.getSmoothedVehicleCarsAndPositions`
（平滑位置本体）、车钩粗筛未命中的那部分。它们要的是位置，不是 id，所以本条的手法用不上。
若要再压，唯一的路是**按视觉帧缓存一次 `getVehicleCarsAndPositions()` 的结果**并让这几处共用
—— 注意两个前提：① 缓存必须绑**帧号**（不能只绑 `railProgress`：客户端"刚学会这条真轨"时，
同一 `railProgress` 的位置会变，绑它会把近似曲线冻住 ⇒ 改画面）；② 网络线程可能在渲染中改车辆状态，
所以缓存只在同一帧内有效、不跨帧。

### 6.4 复现这一节所有读数的命令

```powershell
# 进世界后抓 JFR（不要用默认 stack-depth：默认只打 5 层，看不到调用者）
& $jcmd <pid> JFR.start name=x settings=profile maxsize=64m
& $jcmd <pid> JFR.dump "name=x" "filename=`"<绝对路径>.jfr`""
& $jcmd <pid> JFR.stop name=x
& $jfr print --stack-depth 64 --events jdk.ExecutionSample <file>.jfr > s.txt
```

归类脚本要点（本条的判据就是它）：在 `s.txt` 里按 `sampledThread = "Render thread"` 取块，
统计"栈上出现过某函数"的**占比**；以及把"`Vehicle.getVehicleCarsAndPositions` 的上一层"归类成调用者清单。
