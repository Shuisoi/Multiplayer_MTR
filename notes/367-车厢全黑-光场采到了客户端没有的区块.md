# 367 · 偶发"整节车厢全黑"：光场采到了**客户端手上根本没有的区块**

日期：2026-10-03 · 承接：notes/344（光场实现）→ 345（车灯）→ 351（光影包注入）· 相关代码：`render/light/MmtrLightField.java`

**用户报的症状（原话）**：「是光照方面的，偶发的有些区块渲染全黑」→ 追问后确认是**列车车厢**（不是地形），
「不定，没规律」「难以复现」。

**一句话结论**：光场把"客户端根本没拿到的区块"采成了**合法但全 0** 的一节
（方块光 0 + 天空光 0），又把它当"有数据"发布进 LUT；着色器于是认为"那一节的光就是 0"，
`mmtrFieldColor((0,0))` 正好是原版光照贴图最暗那一格 ⇒ **整节车厢画成纯黑**。

这不是"某个参数漂了"，是**光场的覆盖范围（相机 ±192 格）比客户端真正到手的区块（本服 160 格）大**，
中间那条 **160~192 格的窄带**就是病灶；再叠上两个同族缺陷（见 §4）。

---

## 1. 症状与判据（先分清"车厢黑"还是"地形黑"）

| 症状 | 结论 |
|---|---|
| **地形方块**成块变黑 | **与光场无关**。地形那条路（notes/345 §6）只做**加性**车灯，数学上不可能把方块压黑 —— 已把我们的副本与 Sodium 0.5.8 的 `block_layer_opaque.vsh/.fsh` 逐行 diff 过，MMTR 只多了"加一项"（§3.5） |
| **车厢 / 3D 钢轨**成块变黑 | **光场**。车厢走 `mtr:shaders/core/mmtr_vehicle_light`（notes/344 §8），光照整段由光场替换 |

用户确认是**车厢** ⇒ 查光场这条链。

---

## 2. 决定性证据：同一个 section，存档说"亮"，光场说"全黑"

### 2.1 光场自己记下来的那一批（`run/logs/latest.log`，5 秒一次诊断行）

```
[00:20:30] [MMTR-LIGHT] slots=0/256 collecting=0 collected=0 tiles=0 frames=591 cam=(-4014.0, 73.7, 1394.1)
           | section(-263,4,86) slot=9  block 0..0 avg 0.00 / sky 0..0 avg 0.00 / 实心 0.0%
```

同一形态在整份日志里出现 **78 次**（`sky 0..0 avg 0.00`）。`summarizeSection` 是"这一节真的采到了什么"的
硬证据 —— 它读的就是 `atlasCpu` 里那一格。

### 2.2 同一个 section 在**存档**里长什么样（`sandbox/light_scan.py` 直读 region/NBT）

```
--- chunk(-263,86) section Y=4  (blocks x=-4208..-4193 z=1376..1391, y=64..79)
    block palette (3 entries): ['minecraft:air', 'minecraft:smooth_stone', 'mtr:rail']
    SkyLight: present   BlockLight: ABSENT
    Y=4  sky[n=4096 15s=3424 0s=336 max=15]     ← 天光几乎全亮
```

| 来源 | 方块 | 天光 | 结论 |
|---|---|---|---|
| 存档 `r.-9.2.mca` | 调色板含 **`mtr:rail` + `smooth_stone`**（有轨道、有道床） | **3424/4096 格 = 15**，`isLightOn=1`、`Status=full` | 这一节是有东西的、且是亮的 |
| 光场采集（诊断行） | `实心 0.0%`（4096 格一个不透明整方块都没有） | `sky 0..0 avg 0.00` | 客户端**当时读到的是空气 + 0** |

`isOpaqueFullCube` 对 `smooth_stone` 必然为真 ⇒ 采集时**客户端手上没有这个区块**
（`World.getBlockState` 对没有的区块返回空气、`getLightLevel` 返回 0）。
⇒ **不是"那里真的黑"，是"数据根本不在客户端手上"。**

### 2.3 距离算术：那条窄带有多宽

| 量 | 值 | 出处 |
|---|---|---|
| 相机位置 | `(-4014.0, 73.7, 1394.1)` | 同一行诊断 |
| 病灶 section | X=-263 ⇒ 方块 **x=-4208..-4193** | — |
| 到相机距离 | **179 ~ 194 格** | 减法 |
| 光场网格 | 25×8×25、OFFSET=12 ⇒ 相机 section **±12 = ±192 格** | `MmtrLightField.GRID_*` |
| 客户端真正到手的区块 | 服务端 `server.properties: view-distance=10` ⇒ **160 格**（客户端 `options.txt: renderDistance=32` 被服务端压住） | 两个配置文件 |

⇒ 存在的区间：**160~192 格**（两个 16 格区块宽）。这段里 MTR **照样画车厢**
（优化渲染器不做距离剔除，这是 notes/344 里就记过的性质），但区块没到手。

**为什么"只有车厢黑、地形看着正常"**：那条带里客户端没有区块 ⇒ 本来就没有地形可画；
而车厢是 MTR 自己画的，照画 ⇒ 于是看见的是"一个飘在远处、纯黑的车厢"。

## 3. 代码路径（三条，逐条可对照）

### 3.1 登记：只判"在不在网格里"，不判"区块到手没有"

`MmtrLightField.requestCar()` → `isSectionInsideGrid()` **只看 ±12 section**，没有任何"区块已加载"判据。

### 3.2 采集：直接把"没有"读成 0

```java
final int block = currentWorld.getLightLevel(LightType.BLOCK, cursor);
final int sky   = currentWorld.getLightLevel(LightType.SKY, cursor);
atlasCpu.put(base + u + v * TILE, (byte) ((block & 15) | ((sky & 15) << 4)));
```
区块不在手上时这两句都返回 **0**（而不是"失败"）⇒ 图块被写成一整片 0。

### 3.3 发布：LUT 里"槽位 ≠ 0"= 着色器眼里的"这一节有数据"

```glsl
// mmtr_lightfield.glsl
uint slot = mmtrLightSlot((blockPos >> 4) - gridOrigin);
if (slot == 0u) return vec3(0.0, 0.0, -1.0);      // 没数据 ⇒ 调用方退回 per-draw 光
...
// mmtr_lightfield_mtr.glsl
if (!field.valid) return fallback;                 // ← 只要槽位在，这条就不走
return vec4(mmtrFieldColor(field.light) * field.ao, 1.0);   // light=(0,0) ⇒ 最暗那一格 ⇒ 纯黑
```

⇒ **`slotReady` 没有概念**：槽位一分配就进 LUT，于是"还没采到 / 采到的是空气"这两种情况
和"那里真的很黑"在着色器里**完全无法区分**。

### 3.4 `markChunkDirty` 的判据多除了一个 16（**第二个真缺陷**）

```java
if ((keyX(key) >> 4) == chunkX && (keyZ(key) >> 4) == chunkZ)   // ← 错
```

`keyX(key)` **已经是 section X**（`sectionKey` 的入参来自 `floorToSection = floor(coord) >> 4`），
而 section 本来就是 chunk 对齐的 16³ ⇒ 判据应当是 `keyX(key) == chunkX`。
多除一次 16 的效果：**只有 |sectionX| < 16 的那一小圈（世界原点附近）才会命中** ⇒
"服务端光照更新到了 → 那一列重采"这条**整条是死的**（`ClientPlayNetworkHandlerLightMixin` 白挂）。
影响：光场里的光会**停在采集那一刻**（灯开/关、隧道口、门开合都不同步）。

**线程安全（修之前必须确认）**：这条钩子以前"从不命中"，所以"在网络线程上遍历 `sectionToSlot`"
这个隐患一直没暴露。改之前先读字节码确认了它跑在**主线程**上：

```
public void onLightUpdate(LightUpdateS2CPacket);
     0: aload_1 ... invokestatic NetworkThreadUtils.forceMainThread:(...)V     ← 先强制回主线程
    25: getfield world ... invokedynamic run:(...)      // LightData 的应用体
    39: invokevirtual ClientWorld.enqueueChunkUpdate:(Ljava/lang/Runnable;)V    ← 再排队到主线程
    42: return
```

⇒ 方法体（含我们的 `@At("TAIL")`）在主线程；而且 `markChunkDirty` 只是"下一帧重采"，
光照数据本身也是排进主线程队列之后才落地的 —— 顺序天然正确。整份日志里也没有任何
`ConcurrentModificationException`。

### 3.5 顺手排除：地形那条路不可能把方块压黑

把我们的两份 Sodium 副本与 `sodium-mc1.20.4-0.5.8.jar` 里的原版逐行 diff：
`block_layer_opaque.vsh/.fsh` **只多了** `mmtrRelWorld` / `mmtrTerrainShade` 两个 varying、
三个 `mmtrTerrain*` uniform 与 `diffuseColor.rgb += mmtrLight;`（**加性**）。
⇒ 地形变黑的成因不在这一侧（这条结论以后可以省一轮）。

## 4. 修法：**宁可不发布，也不要发布不可信的数据**

三处改动都在 `render/light/MmtrLightField.java`，方向一致：把判据放在**能力边界**上
（"客户端有没有这块数据"），而不是放在结果上（"采出来是不是 0"）。

| # | 改动 | 为什么 |
|---|---|---|
| 1 | `requestCar()` 里加 `isSectionLoaded(sx, sz)`（**chunk 坐标 = section X/Z**，不用再除 16）；没到手就不登记，并计入新诊断读数 `未加载跳过(车次)=` | 根因：没到手就不该进光场。不登记 ⇒ 该格 LUT=0 ⇒ 着色器退回 per-draw 光 |
| 2 | `collectSlice()` 采之前再判一次：没到手就**丢掉任务、保留槽位**；`ensureSlot()` 对"没采满"的槽位重新入队 | 兜底：判据 1 若有漏网（例如登记与采集之间区块被卸载），也不会把空气采成光；区块到手后自动补采 |
| 3 | 新增 `slotReady` 位：**只有采满整整一节才准进 LUT**；`ensureSlot/releaseSlot/reset` 清位；分槽时 `clearAtlasTile()`（4096 B memset） | 同族缺陷一次关掉：①"已分配未采集"的 1..N 帧；②槽位复用时图块还留着**上一节的光**（"凭空的别处光照"）。代价只是那一节头几帧走 per-draw 光 |
| 4 | `markChunkDirty()` 判据改成 `keyX(key) == chunkX` | 让"光照更新 → 重采"这条真的活过来 |

**判不出来时一律当作已加载**（`isSectionLoaded` 里的 catch）：宁可维持现状，
也不要在某台机器上把整条光场凭空关掉。

**语义边界（诚实写清）**：带外（>160 格、服务端没发）的车厢现在退回 MTR 的 **per-draw 光**
（"整段一个光值"）—— 那是光场介入**之前**的样子，不是新的缺陷。
想让那条带也有逐片元光，只有两条路：把服务端 `view-distance` 提到 **13** 以上（208 格 > 192），
或者把网格缩到 view-distance 以内（会牺牲"远处车厢也有世界光"）。

## 5. 怎么确认修好了（现场三条，都不用猜）

1. 诊断行里 `未加载跳过=0`（服务端 view-distance ≥ 13 时应当恒为 0），
   且 `section(...) block 0..0 avg 0.00 / sky 0..0 avg 0.00` 这种摘要**只剩真正的地下 section**
   （真正的黑暗节一定同时有 `实心` 比例或非零方块光，不会"实心 0.0% + 全 0"）。
2. 站在能看到 160~192 格处一列车的机位：车厢应当是**正常亮度**（按 MTR 的 per-draw 光，
   "整段一个光值"），不是纯黑。
3. A/B：`run/mmtr-lightfield.properties` 的 `enabled=false`（2 秒生效、不用重启）
   本来就能把整车切到 per-draw 光 —— 修复**后**带内车厢的画面应当与 `enabled=false` 时**一致**；
   修复**前**它是纯黑。这一条不需要等重现。

## 7. 三条可复用的教训

1. **"采集读到的 0" 必须先证明"那个世界真的是 0"**。这次是靠**第二个来源**（存档 region/NBT）
   把"读数为 0"分成两种：世界真的黑（地下、隧道）vs 数据不在客户端手上。没有这一步，
   `实心 0.0%` 只会被当成"一节空气"，方向全错。
2. **判据要放在能力边界上，不要放在结果上**。"采出来是不是 0"这个判据是错的
   （黑暗节也是 0）；"客户端有没有这块数据"才是对的。
3. **凡是有两个子系统对同一件事各自取数（这里：网格 ±192 格 vs 服务端 view-distance 160 格），
   两者之差的**那条带**就是缺陷的温床** —— 光场、车灯、剔除、AO 都会在那里出问题。
   以后凡是"我们的覆盖范围"与"游戏给我们的数据范围"不一致，先把差值算出来。
