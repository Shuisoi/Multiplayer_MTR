# 134 · 解锁道岔必须落盘：为什么"解了又回来"

现场（2026-09-14）：用户决定"全部解开"那 6 个节点的人工锁。网页/feed 上确实清了 ——
`locked=true` 从 10 行变 0 行。但翻存档时发现 `mmtr-points.json` 里**还躺着 20 条锁**，
而且其中有些是界面上根本没有对应按钮的进向。结论：**这一次"解锁"只在当前进程里成立，
重启后锁会原样回来**。这是引擎缺陷，已修。

---

## 1. 现场事实（先后两次读盘，中间隔了一次"逐行解锁"）

```
第一次：feed 里 locked=true 的 10 行（6 个节点）→ 逐行 point unlock → feed 里 locked=true 的 0 行
       存档 mmtr-points.json: locks = 20 条（7 个节点）
```

同一批节点，两个数字对不上（0 行 vs 20 条）。差的那些键是**界面上表达不出来**的进向：

- 人工搬岔一次锁的是这处道岔的**三条进向**（`stem` / `far` / `branch`，
  见 `mmtrOperatorSetTurnoutPosition` 里那个 for 循环）；
- 而 `mmtr-points` 是**按进向行**给的，一行道岔派生出来的三行里，
  网页只画得出有按钮的那一条（单开道岔只留根部那一行来画，见 `TopologyPanel` 的 `displayPoints`）。

所以"逐个点解锁"永远有死角：看不到的键没有按钮可点。而 `-147,-60,-169` 那两条更是
**旧世界遗留**（我早前用 `point unlock` 解过它，界面早就显示未锁，文件里却还在）。

## 2. 根因：`mmtrPointUnlock` 只改内存，不落盘

```java
// 修之前
public void mmtrPointUnlock(long x, long y, long z, String viaRailHex) {
    mmtrPointAuthority.unlock(x, y, z, via);   // ← 只动内存
    System.out.println("[MMTR-PT] unlock …");
}
```

对比一下同族的另一条路：`mmtrOperatorSetTurnoutPosition`（`point set` 走的就是它）
第 985 行是 `persistMmtrPointBranches()` —— **加锁落盘、解琐不落盘**，方向正好反了。

后果是双向的：

1. 解锁是假的：重启后锁回来（用户看到"我明明解开了"）；
2. 更隐蔽的一层：锁还在内存里时，**别处任何一次落盘**（`point set`、轨集合变化触发的那次
   persist）都会把内存里的旧锁**写回文件** —— 于是"文件干净了"这件事也保不住。

而设计上锁是明确的"永久"语义（用户 2026-09-14 的选择："人工搬岔同时把道岔锁住，
**永久生效直到解锁**"），永久生效的东西解锁不落盘，等于没解。

## 3. 修了什么

| 位置 | 改动 |
| --- | --- |
| `Simulator.mmtrPointUnlock` | 解锁后 `persistMmtrPointBranches()` |
| `Simulator.mmtrPointLock` | 加锁后同样落盘（同一族，别只修一半） |
| `Simulator.mmtrUnlockAllPoints()`（新） | 按**引擎自己持有的键**全清（含界面表达不出来的），返回清掉几把，并落盘 |
| `MmtrPointAuthority.clearLocks()`（新） | 逐个 `remove` + `promote`（排队的自动申请立刻接手，不等到下一 tick），返回清掉的把数 |
| `point unlock --all`（新） | 指令入口；`point unlock` 还支持原来的逐进向写法 |
| `point locks`（新） | **问引擎到底锁了哪些**（逐进向列出）。这个现场问题的排查入口：界面上看到的锁闭是"有行的那些"，看不见的只能问引擎 |

`point why` / `point list` 之外的这两个动词是这次现场逼出来的：**只按界面能表达的范围做指令，
就永远修不好"界面上看不见的状态"**。

## 4. 现场已经处理到什么程度（以及为什么还要重启一次）

- **内存**：按存档里那 20 个键逐个 `point unlock` → 引擎手里一把锁都不剩（feed 0 行）。
- **存档**：`mmtrPointUnlock` 不落盘，所以文件还是 20 条。用
  `sandbox/clear-stale-locks-in-save.ps1` 只把 `locks` 这一个数组清成 `[]`（正则只替换这一个数组；
  改完自己核一遍：仍是合法 JSON、`locks=0`、`positions` 22 条与 `switches` 52 条**逐条相同**），
  备份留在 `logs/2026-09/mmtr-points-before-lockclear-*.json`。
  这一步是安全的，因为**内存已经是干净的**：此后任何一次落盘写回来的都是"没有锁"。
- **代码**：上面那几处修好了，但引擎跑在 Fabric 服务端进程里（8888 端口就是那个进程），
  换 jar 要停服。所以**下一次重启服务端时**这套修复才生效 —— 在那之前，如果又有新的人工搬岔，
  它的加锁照样会落盘（老代码有落盘），而解锁又只落在内存里，就还是老问题。
  重启的收益：以后 `point unlock` / `point unlock --all` 立刻就是永久的。

## 5. 测试：两条，各钉一半

`MmtrPointAuthorityE2ETests` 里：

- `aLockSurvivesARestartAndAnUnlockSurvivesItToo`
  人工搬岔 → "重启"（同一存档目录再起一个 `Simulator`）→ 锁还在；解一条进向 → **这处道岔仍算锁着**
  （一处道岔三条进向，任一锁着就不许自动扳）；`mmtrUnlockAllPoints()` → 一把不剩 → 再"重启" → 不锁了。
- `unlockAllAlsoClearsLocksThatNoApproachRowCouldShow`
  造一条**界面上不可能点到**的键（坐标上根本没这个进向）→ 它照样落盘、重启后还在 →
  `mmtrUnlockAllPoints()` 清掉 → 重启后依然是空的。

**测过它们真的能红**：把 `mmtrUnlockAllPoints()` 里那行 `persistMmtrPointBranches()` 注掉再跑，
两条都红（线 310 / 338）；恢复后全绿。也就是说这两条测的是"落盘"这条规则本身，
不是顺手通过的。
（第一版 `unlockAllAlsoClears…` 是**假通过**：那条锁是我直接 `authority.lock(...)` 塞进内存的，
从来没落过盘，所以"重启后为空"是理所当然 —— 已改成走 `mmtrPointLock` 先落盘再验。）
