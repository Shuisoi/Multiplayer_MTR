## 1. 架构决定：合成放离线，游戏端只挑档 + 变调

Minecraft 的音效接口只给「SoundEvent + pitch + volume」（`SoundInstance`），**没有自定义合成器**，
所以游戏里不可能跑那个加法正弦 bank。但调研给了一条恰好成立的关系：

> 同一个分周档内，载波与基波**严格成正比**（`f_c = 分周数 × f₁`）

所以"预烘焙每档一条循环 + 按 speed 变调播放"**在数学上是精确的**。分工于是变成：

| 谁 | 干什么 | 代价 |
|---|---|---|
| `bake.mjs`（离线，JS） | 沿 f₁ 细扫 → 找出模式切换点 → 按变调预算细分 → 合成 → 编码 ogg + 清单 | 跑一次几秒 |
| `MmtrVehicleSound`（在线，Java） | 由速度+电机出力算 f₁ → 挑 f₁ 最近的一档 → 变调 | 每帧几个乘法 |

**附带的最大好处**：调制状态机只活在 JS 一侧，Java 侧**不需要移植它**，
于是不存在"两份实现各说各话"（那是本仓最恨的一类现场）。

## 2. 无缝循环：先做到数学无缝，再发现过不了编解码

### 2.1 数学上怎么做到
设循环时长 `L = N/f₁`（`N` 为整数）。只要**每个分音的频率都是 f₁ 的整数倍**，
每个分音在 `L` 内就恰好跑完整数个周期 ⇒ 首尾样本天然接续，**零代价无缝**（"整周期条件"）。

模型里基波簇是 `n·f₁`，天然满足；但**载波簇不是** —— 异步段的载波是独立设定的（如恒 1045 Hz），
一般不是 f₁ 的整数倍。所以合成前做一步 **snap：把每个分音频率吸附到最近的 f₁ 整数倍**。
误差 ≤ f₁/2（f₁ = 10 Hz 时对 1045 Hz 只偏 0.5%），听不出来，换来严格无缝。
吸附后的频率**逐条写进清单**，保证"烘焙出来的 = 清单里写的"。

### 2.2 然后实测打脸
用 `sandbox/sound-probe/verify_baked.py` 量"声明长度 vs 解码长度"：

```
entry                        应有     实际  delta     seam   step95  ratio
traction_async_00049.ogg    45176   45176     +0  0.00727  0.01765    0.4   好
traction_async_00110.ogg    44101   43973   -128  0.37572  0.03025   12.4   会咔
traction_async_00129.ogg    44302   44174   -128  0.61021  0.03630   16.8   会咔
```

**Vorbis 编解码会吞吐样本**（多数文件解出来比喂进去少 **128**，但**因文件而异**：
有的 delta = 0，还有一个 +906）。长度一偏，MC 循环回起点就落在错误相位上 ⇒ 咔。

试过"循环回绕地前置 128 样本"（等价于把周期信号旋转一下，旋转不破坏无缝）：
**只在一部分文件上成立**，其余反而更糟（delta 反成 +128）。既然补样长度不可控，
就只能用不依赖它的手段。

### 2.3 最终办法：首尾淡化兜底
首尾各 8 ms 升余弦淡到 0。淡到 0 之后，无论解码器怎么偏相位，接缝处的跳变都被乘成接近 0。

| 配置 | 最差接缝比 | 说明 |
|---|---|---|
| 1 s + 前置 128 样本 | 20.6 | 只在一部分文件上成立 |
| 1 s + 4 ms 淡化 | 10.1 | 仍会咔 |
| 1 s + 8 ms 淡化 | 3.7 | 可用 |
| **2 s + 8 ms 淡化** | **0.5** | **采用** |

代价是每循环一圈有一次极轻的幅度凹陷：2 s 循环 ⇒ 0.5 Hz、占空比 0.4%。
比"每 2 秒咔一下"好得多，也比现有 OpenBVE 素材（最差 9.7）干净。

## 3. 档位铺设与变调预算（这条路成立的前提）

沿 f₁ 细扫（0.05 km/h 步长）找出模式分段，再按"相邻档 f₁ 比值 ≤ `--maxstep`"细分。

通用通勤型（2 电平 IGBT，载波 250→1045 Hz）扫到 220 km/h：

| 分段 | 速度区间 | 模式 |
|---|---|---|
| 1 | 0.0–87.2 km/h | async |
| 2 | 87.3–113.2 | 7-pulse |
| 3 | 113.2–159.9 | 5-pulse |
| 4 | 160.0–220.0 | 3-pulse |

细分后 **27 档**，2 s 循环，共 **249 KB**。

**烘焙器自己验这条不变量**（不等到 Java 测试或进游戏才发现）：
```
变调自检：最差 rate = 1.0877 @ 牵引 62.25 km/h（f₁=84.11 → 档 77.32）
（预算 ±15%；Minecraft 的 pitch 硬范围是 [0.5, 2.0]）
✓ 全速度域都在变调预算内
```
最差 8.8%，离 MC 的 `[0.5, 2.0]` 硬夹取还有很大余量。破了直接 `exit 1`，不产出不能用的清单。

> 注意 async 段内**载波恒定而基波在变**，所以一条 async 循环变调播放会让载波跟着动 —— 这是错的。
> 解法就是多铺几档 async（本次铺了 20 档），每档只用很小的变调量。

## 4. Java 侧：模型零依赖、清单即契约

| 文件 | 作用 |
|---|---|
| `sound/MmtrTractionSoundModel.java` | **纯模型**：`rotorHzPerKmh` / `rotorHz` / `fundamentalHz`（含滑差与再生切除）/ `loadAxis` / `select`（挑最近的档 + 夹进 pitch 范围）。**不引 Gson、不引 MC、不引引擎 core** —— 只有 `java.*` |
| `sound/MmtrTractionSoundSet.java` | 读 `mmtr_traction.json`（Gson + `ResourceManagerHelper`），把每条 entry 变成 `SoundEvent` |
| `sound/MmtrVehicleSound.java` | 播放器：每帧挑档、变调到 f₁、换档时等功率交叉淡化（60 fps 下 6 帧） |
| `sound/VehicleSoundBase.feedDemand(double)` | **新增的默许空实现**，见 §5 |
| `data/PersistentVehicleData.feedDemand(...)` + `data/VehicleExtension` | 转发 |
| `resource/VehicleResource.createVehicleSoundBaseInitializer()` | 第三条分支：清单在 ⇒ MMTR 引擎 |

**模型零依赖是刻意的**：于是它能被 `javac` 裸编译、被命令行直接跑，
"模型算得对不对"与"资源包读得对不对"两件事互不牵连。

**事件 id 写进清单**（`entry.eventId`）而不是让两边按命名规则各自拼：
命名规则一改，忘记同步的那一侧会**静默无声**（notes/178 记过：MC 在 id 未注册时只打一行日志然后 return）。

**"清单在 ⇒ 用 MMTR 引擎"是显式的**：`mmtr_traction.json` 与 BVE 的 `sound.cfg` 是**同一层级**的东西
（音效集自带的配置），所以"文件在不在"就是声明本身，不是额外的隐藏开关位。
清单在但解析坏了会写 error 日志并退回 BVE/legacy —— 不静默。

## 5. 为什么加 `feedDemand` 而不是改 `playMotorSound` 的签名

MTR 的签名 `playMotorSound(blockPos, speed, speedChange, acceleration, isOnRoute)` **不带电机出力**，
而"惰行"与"起步（速度为 0 但电机在出力）"这两种情形**用速度/加速度差分不出来**：
惰行时阻力让车减速，会被误判成再生制动。

改签名会牵动两个加载器 + 所有现存音效类，所以改成**加一个默许空实现的方法**：

```java
public void feedDemand(double motorForceN) { }   // VehicleSoundBase，默认什么也不做
```

现存的 BVE / legacy 音效类**一行都不用改**（默认空实现），只有 MMTR 牵引音覆盖它。
喂进来的是 `VehicleExtraData.getMmtrMotorForceN()` —— 引擎快照每 tick 下发的**权威**读数
（notes/257/259），然后 `powerW = force × speed × 1000`（`speed` 是 MTR 的 m/ms 口径）。

## 6. 本轮抓到的两个真问题（都是测试抓的，不是先验设计）

### 6.1 再生制动的**切除速度**（模型缺了一个物理量）
Java 用例扫全速度域时报：`最差变调 0.5（再生 3.75 km/h）` —— 被夹到 pitch 下限了。

真因：模型给再生段算的是 `f₁ = max(0, 转频 − 滑差)`，在 3.75 km/h 时只有 0.3 Hz，
而最低那一档是 4.88 Hz ⇒ 变调 0.06 ⇒ 被硬夹到 0.5，音高完全走样。

物理上：**再生制动在某个速度以下是根本不投入的**（BVE `sound.cfg` 的 `RegenerationLimit`，
仓库里 saf101 那套是 7.5 m/s = 27 km/h；与本仓电制动三段式的"低速淡出"同源）。
所以给 spec 加了 `regenCutoffKmh`，JS 与 Java 两侧同步实现，并各加了一条用例。

### 6.2 静止 + 再生的 f₁ = 0 是**对的**，不是漏档
同一条用例一开始还报了 `速度 0.0 应当能选中一档` —— 那也是我的预期写错：
静止时转频为 0，"转频 − 滑差"被夹到 0 ⇒ **没有牵引音是对的**（车靠气制动/闸瓦）。
改成显式断言"只有再生允许 f₁ = 0"。

## 12. 第三轮补充：forge **不必**镜像（我先做了又回退）、拖车静音、清单解析用例

### 12.1 forge 不需要镜像 —— 它是 `setupFiles` 从 fabric **生成**的副本（我先做了、又回退了）
一开始我按 notes/178「两个加载器都改了」的先例，把三个新文件复制到 forge、四处改动也照着改了。
**这个动作是错的**，本轮已全部回退 —— 四个文件的行数与字节数都回到改动前的原值
（`VehicleSoundBase` 23 行/710 B、`PersistentVehicleData` 193/8218、`VehicleExtension` 403/20922、
`VehicleResource` 613/25484，与原值逐一相同）。

证据链：
1. `game/.gitignore:38-43` 把 forge 的 `org/mtr/core`、`org/mtr/legacy`、`org/mtr/mod`、
   `resources/assets`、`resources/data` **整片忽略** —— 这些目录不是手写的。
2. `game/forge/build.gradle` 的 `setupFiles` 任务写得很直白：
   ```
   delete fileTree("src/main/java/org/mtr/mod")
   copy { from "../fabric/src/main/java/org/mtr/mod" into "src/main/java/org/mtr/mod" }
   ```
   ⇒ forge 那棵树是 **fabric 的副本**；手改它，下一次 `setupFiles` 就 `delete` 掉（静默消失）。
3. `game/settings.gradle:17-32`（notes/220）：forge 是**可选**子工程、默认不 include，
   fabric 才是本仓的开发目标。而且 forge 树下 `org/mtr/mod/mmtr/**` 是按 Yarn 写的，
   在 forge 映射下**编不过** —— 真要构建 forge 得 `gradlew -Pmmtr.forge=true :forge:build`
   并先把那份源码对齐到 forge 映射。
4. 旁证：forge 那份 `org/mtr/mod` 是**旧副本**（`LegacyVehicleSound.java` 已与 fabric 不同），
   而 `BveVehicleSound.java` 与 fabric 逐字相同 —— 典型的"某个时间点复制过一次、之后只在 fabric 上演进"。

**结论与做法**：fabric 是唯一事实来源；forge 由 `setupFiles` 生成，**不要手改**。
真要出 forge 包时跑一次生成，本轮改动会一并带过去。
这同时解释了为什么仓库的两个类型检查脚本与离线用例 runner 都是 fabric-only —— 那是刻意的。

> 绕的这个弯子值得记下来：**动手镜像之前先找一遍"这棵树是谁生成的"**。
> 光看"两侧同名文件大部分逐字相同"，很容易误判成"人工维护的双份"。

### 12.2 拖车静音：判据必须是**三态**
引擎快照里的电机出力是**整列**口径（`getMmtrMotorPowerW` 是整列的电机做功），
而音效是**每节车**一个实例（`PersistentVehicleData` 按 `carNumber`）⇒ 拖车那一份会跟着动车响。

修法是在 `VehicleExtension.playMotorSound` 里把挂车的出力喂成 0。但判据**不能**写成 `!powered`：
引擎里"这节车有没有动力"是三态的（notes/271 片 1）——
**写了** `mmtrPowered:false` 的才是被牵引的挂车，**根本没写**这个键的车（例如没配车底清单的 BR101）
读出来同样是 `false`，而它其实有动力。把"没声明"当"无动力"会把整批老车静音，
现场只会表现为"没声音"，极难查。

所以口径是 **`poweredDeclared && !powered`**（只有显式声明无动力才静音），
落在 `MmtrTractionSoundModel.shouldMuteMotorSound(declared, powered)` 里，**四条分支都有用例**。

### 12.3 清单解析：拆出纯函数 + 两条读清单的路交叉验证
原 `parse` 会顺手建 `SoundEvent`（MC 类型），于是"清单解析对不对"在没有 Minecraft 的环境里测不了。
拆成：

```
static ParsedManifest parseManifest(baseName, text)   // 纯：Gson 解析 → 模型 + 事件 id 列表，零 MC 类型
public static MmtrTractionSoundSet load(String)        // 建 SoundEvent（只在游戏里跑）
```

用例里加了两条：
- `manifestParserReadsTheContractFields`：内联一份最小清单，验 spec 字段 / 档序 / `eventId` / 解析出来的模型能直接 `select`。**工作区里没有烘焙产物时这条也一直在守契约。**
- `bothManifestReadersAgreeOnTheRealBakedFile`：拿**真实清单**把生产路径（Gson）与用例里的正则扫描**逐条对齐**（档数 / 文件名 / f₁ / 模式），再验事件 id 由档名收尾。两条路一旦分叉，就是"模型算得对、进游戏却没声音"这类最难查的现场。

清单查找改成**优先找真正打进资源包的那一份**（`sandbox/sound-studio/baked/saf420/`），
因为 `final2s/` 那份是自检用的、没带 `--base`（事件 id 前缀不同，第一版用例就栽在这上面）。

### 13.1 `check-pack.ps1`：资源包对账（12 项）
资源包是"我这边"与"游戏那边"**唯一的接口**。打包器说 `sound events: 27` 只证明它**登记**了 27 条，

- 车配置里的 `soundDir` 指的是**这份**清单（指错了 ⇒ 包里是旧的，怎么改模型都不生效）。

对账内容：包里清单与源目录**长度一致**、27 档 ogg 一档不缺、事件登记双向一致（不漏不多）、

| 故意造坏 | 结果 |

### 13.2 `verify_loops.py`：循环接缝（把能力边界量清楚了）
第 2 轮那个"数学无缝过不了 Vorbis 编解码"的结论，当时是拿 `sandbox/` 里的临时探针量的。
本轮把它提成正式工具，并且**用对照实验把它的能力边界一条条量出来**：

| 输入 | 接缝比 | 判定 | 说明 |
|---|---|---|---|
| 真集（2 s + 8 ms 淡化） | 最差 **1.6** | 好 ✓ | 淡到 0 之后接缝≈0 |
| 440.3 Hz 正弦 / 1.3 s（572.39 周期，相位差 0.39 周期） | **10.8** | **会咔** ✓ | 音调型抓得到 |
| 粉噪（长度也不对） | **1.6** | 好 ✗ | **抓不到** |
| 523.7 Hz 正弦 + 粉噪混合（相位差 0.6 周期） | **1.6** | 好 ✗ | **也抓不到** |

⇒ **这个指标只适合给"我们自己烘的音调型循环"把关**，不能拿去认证采样的宽带素材。
**顺带纠正第 1 轮一个偏乐观的结论**：当时说"现有 OpenBVE 素材最差 9.7、多数 ≤3，所以循环安全"——
对 `run.ogg` / `motor0.ogg` 那类宽频文件，这个指标**看不见**接缝，所以那句话对它们不成立。
（基准也从"全局步进"改成"接缝附近的局部步进"，能救"音调为主、少量噪声"的情形。）
另外工具自己踩了个坑：Windows 控制台是 GBK，脚本里的 `⇒` 直接抛 `UnicodeEncodeError`
—— 那是"工具崩了"而不是"音频有问题"，最容易被误读，已加 stdout 重编码。

### 13.3 `verify_spectrum.py`：**烘焙音频 = 清单声明的分音**（以前只靠眼看）
清单把每一档的分音逐条写了下来（`partials: [{hz, amp, cluster}]`），声称"烘焙出来的 = 清单里写的"。
第 2 轮这条是**拿眼睛看两行数**确认的（模型算 124/247/…/1360 Hz，探针打出的峰里有这些数）——
抽查一两档还行，换个模型参数就得重看一遍，守不住。现在自动对账三条：

1. 清单里幅度 ≥ 声明峰值 30% 的每个分音，都要在实测频谱里找到对应峰（容差 max(2 Hz, 2%)）；
2. 清单里最强的那个，必须落进实测前 3 峰；
3. 实测里幅度 ≥ 实测峰值 30% 的每个峰，都要能被清单里的某个分音解释（⇒ 音频里没有"清单没声明的东西"）。

**真集：27/27 全对得上，最强峰频率最大偏差 0.01 Hz。**
**对照实验**：同名文件、把清单里的分音频率整体 ×1.2（音频不动）⇒ **27/27 全失败**，
诊断指出"凭空主音 239.2/244.0/248.9/…Hz"与"声明最强 298.7 Hz 不在实测前 3 峰里"，exit 1。

> 这个工具第一版**27 档全部误报**：③ 我写成了"不许有比**声明最强分音**还强的峰"，
> 于是拿**清单里的 amp**（烘焙时的相对幅度）去比 **FFT 幅度**（取决于窗与点数）—— 两者单位不同。
> 改成"各自域内取相对"才对。**又一个"检查本身写错"的例子，与 §12.6 同源。**

### 13.4 让"进游戏那一步"可诊断
进游戏后"没声音"有三种完全不同的原因，而且在日志里长得一模一样：
① 清单没读到（音效集根本没被认成 MMTR 集，静默退回 BVE/legacy）；
② 清单读到了但没有档（永远挑不中）；
③ 引擎接管了、但选档/音量算出来是 0（惰行、未励磁、拖车被静音）。

所以加了两处**有上限**的日志：
- `MmtrTractionSoundSet.load` 成功时也打一行：`[MMTR-SND] 音效集 saf420 已被 MMTR 牵引音接管：27 档，
  事件前缀 mtr:sounds/saf420`（档数为 0 时改成 warn）—— 抬头一行就能分掉 ① 与 ②；
- `MmtrVehicleSound` **换档时**打一行（含 f₁ 与变调比例）。它天然有上限（最多 = 档数，一趟车只经过 5~8 档），
  而且让"进游戏听"变成**可对账**的：日志里的档序应当与 §10 那张表一致（0 km/h 起 async、90 km/h 起 7-pulse…）。

配套：`Selection` 现在把**当时用的 f₁** 一并带出来（`Selection.f1Hz`），
播放器不再自己重算一遍 —— 否则又成了"两处各算一套"，而日志与听感会对不上。
用例 `selectionCarriesTheFundamentalItUsed` 守住这一点（落在档上 / 落在两档之间 / 被夹取时都照带）。

## 14. 第五轮补充：**离线预演**——在重编译之前先听到"这趟车会是什么声音"

### 14.2 `verify_preview.py`：核对音频里真的是计划里那些频率

要核的等式只有一条：

> **实测分音频率 = 清单声明的分音频率 × 变调比**

它成立，"离线预演代表得了进游戏听到的东西"这句话才站得住 —— 而那条等式正是游戏端唯一做的事。
关键点：它**从磁盘上重新解码音频、重新读计划**，与本进程里那份计划数组不共享任何状态。

## 15. 第六轮补充：补上**齿轮啮合层**（第二层，独立变调基准）

本轮动因：查出模型里算了齿轮簇、**烘焙器却完全没烘** —— 所以出货的 27 条循环里根本没有齿轮啸叫。
调研早就写明这一层**必须合成**（它严格随机械转频成比例，采样做不出无缝变速），而真车的齿轮啸叫
在车内是"细而持续"的一层，缺了它声音就只剩载波嗡鸣。

### 15.1 为什么它必须是**独立一层**（而不是并进那 27 条循环）

| | 牵引层 | 齿轮层 |
|---|---|---|
| 唱什么 | 定子基波 `f₁ = 转频 ± 滑差` | **机械转频**（不含滑差） |
| 变调基准 | `f₁ / 该档的 f₁Hz` （围绕 1 上下浮动） | `速度 / 参考速度`（**严格线性**） |

两者**差一个滑差**（本 spec 是 4.5 Hz）⇒ 变调比例不可能同时满足两层。
一条循环只能有一个变调基准，所以齿轮层必须有自己的循环、自己的播放器。
这条"差一个滑差"被**直接测出来**了 —— 它才是"独立成层"的理由，不是随手加的断言：

- JS 自检 `齿轮层与牵引层的基准不同（差一个滑差）`：断言 `f₁ − 转频 == slipHz`；
  以及 `齿轮层频率与速度成正比（可用独立 rate 播）`（60 km/h 时恰好 ×60）；
- Java `gearRateIsStrictlyProportionalToSpeed`、`gearLayerGoesSilentRatherThanPlayingAWrongPitch`。

### 15.2 参考速度为什么取 100 km/h

因为转频与速度成正比 ⇒ `playbackRate = 速度 / 100` **恰好等于机械转频之比**，
这一层的变调在物理上严格线性（牵引层做不到这一点，它每档的 rate 是围绕 1 浮动的）。

无缝原理与牵引层相同：`f_mesh = 齿数/(极数/2) × 转频 = 8 × 转频`，谐波是 8/16/24 倍，
循环长度取 `N/转频` ⇒ 每个分音都跑完整数个周期。实测分音 **1023.1 / 2046.1 / 3069.2 Hz**，
正好是转频（127.8817 Hz）的 8/16/24 倍。

变调可用区间 = rate 落在 Minecraft 的 `[0.5, 2.0]` ⇒ **50~200 km/h**。
出区间时**静音而不是夹取**：音高错的齿轮音比没有更难听，而且夹取会让音高与实际转频脱节
（听起来像另一个转速）。用例 `gearLayerGoesSilentRatherThanPlayingAWrongPitch` 守这条。

### 15.3 一个**会静默失败**的坑，专门加了用例守
清单里有 `gear` 段、但对应事件没登记进 `sounds.json` 时：
`MmtrTractionSoundSet.load` 建齿轮 `SoundEvent` 会抛异常 → 被 catch 抓住 → 写一条 error 日志 →
**整个音效集退回 BVE/legacy**。现场表现只是"没声音"，而清单看起来完全正常。

所以 `realBakedGearLayerIsRegisteredAsASoundEvent` 把**真实清单里的齿轮事件 id** 与
**真实 `mmtr_traction.sounds.json`** 对一遍（还核了 `baseDir + 文件名` 这条路径）。
`sounds.json` 里现在 28 个事件（27 档 + 齿轮）。

### 15.4 顺带修掉的一处用例缺陷
`bothManifestReadersAgreeOnTheRealBakedFile` 里那个"刻意不引 Gson"的正则扫描器是**全篇扫 `"file"`** 的。
清单多了 `gear` 段之后它也带一个 `"file"`，于是扫描器读出 **28**、Gson 读出 **27** ——
这条用例立刻抓到了自己的扫描范围错误（这正是它存在的意义）。

2. 有接管行、但**没有换档行** → 挑档恒为静音：查 `feedDemand` 有没有喂到出力（拖车静音判据）；
3. 有换档行、**听不到** → 音量/衰减问题（`MASTER_VOLUME`、`attenuation_distance: 32`）。

## 17. 第七轮：给合成音加**壳子**（传导 → 失真 → 弱化）

### 17.1 问题定性与一个**参照系错误**
你说"电机音本身没问题，缺的是壳子"——对。我先把它量化了，三条指标（`compare_texture.py`）：

| 指标 | 合成（干信号） | 真实录音 |
|---|---|---|
| 短时 RMS 起伏 | 0.010 ~ 0.014 | 0.12 ~ 0.33 |
| 能量 <500 Hz 占比 | 8% ~ 19% | 43% ~ 99% |
| 谱平坦度 | 0.0000 | 0.0018 ~ 0.0028 |

**★ 参照系一开始配错了**：我拿"电机循环"去比别人的 `run.ogg`（**走行音**），
于是以为低频要 75%~98% —— 那 75~98% 是**滚动噪声**的特征。
正确的配对是 `br_423/motor0~3.ogg`（**牵引音**）：
`low = 98.7% / 43.0% / 59.3% / 95.3%`，`tvar = 0.296 / 0.255 / 0.334 / 0.187`。
**参照物选错，后面所有判断都会歪**，这条比任何参数都重要。

### 17.2 调研：别人是怎么在**没有录音**的情况下做的
| 来源 | 做法 | 对我们要紧的地方 |
|---|---|---|
| [VvvfGeeks/VVVF-Simulator](https://github.com/VvvfGeeks/VVVF-Simulator) | **把逆变器的 PWM 开关波形直接当音频播**（不是采样）；可设 PWM 电平数、脉冲模式（Async/Sync/CHM/SHE/HO）、调制指数 | **Carrier Frequency 里有 "Random Modulation (Range / Interval)"**（如 700 Hz ±50，隔几秒变一次）——真实逆变器用随机/扩频 PWM 摊开开关噪声。**这是"非平稳"的物理出处**，我把它做进了壳子 |
| [Audiokinetic：在 Wwise 中结合使用样本和粒子合成技术构建发动机声音模型](https://www.audiokinetic.com/zh/community/blog/engine-sound-modeling-from-sampling-to-granular-synthesis-in-wwise/) | 行业做法是"参数化模型 + 少量素材 + 粒子合成"，而不是全靠素材 | 说明"纯合成"在业界是成立的路线，不是我们一家在硬扛 |
| [MTRBBS：如何自定义列车走行音](https://www.mtrbbs.top/thread-1623-1-5.html) | 社区标准答案：**复用模组自带的录音**（`speed_sound_base_id` 指别的车） | 反证了你的判断：这个圈子默认吃录音，拿不到录音就得自己造 |
| [OpenBVE MotorSound.cs](https://github.com/leezer3/OpenBVE/blob/fc619de44250639927b3a5760a98dd7989eda052/source/TrainManager/Motor/BVE5/MotorSound.cs) | 表驱动：速度 → 若干**录音元素**的交叉淡化 | 它是"有录音"前提下的最优解，帮不了我们 |

结论：**没有录音时，可行路线是"物理参数化合成 + 一条把信号变脏变弱的链路"**，
而我们缺的正是后一条 —— 就是你说的壳子。

### 17.3 壳子：[`shell.mjs`](../tools/sound-studio/shell.mjs)，五级串联
```
源 ──▶ ① 传导滤波 ──▶ ② 底噪床(叠加) ──▶ ③ 非平稳调制 ──▶ ④ 非线性失真 ──▶ ⑤ 弱化归一
        结构传声+空气吸收    轮轨/风/辅机      载波随机调制等       饱和/互调       整体衰减
```
**顺序本身有物理含义**：③ 在 ④ 之前（调制是"源"层面的，先调制再饱和，互调产物才真实）；
② 在 ④ 之前（底噪与音调一起穿过同一条链路）；⑤ 必须在最后（否则饱和量一变响度就变，没法比）。

三套 voicing：`interior`（客室内）/ `cab`（司机室）/ `exterior`（车外轨旁）。
**只有 interior 是被测量验证过的**；cab/exterior 手上没有匹配的参照，
它们只是"方向合理"（离声源更近、没有车体空腔 ⇒ 不该那么闷），**没有假装验证过**。

### 17.4 这一轮踩的坑（每条都有可辨识的症状，值得留档）
| # | 错在哪 | 症状 | 修法 |
|---|---|---|---|
| 1 | 用"少数频点抽样的 DFT"算频带占比 | 低频占比系统性偏高（JS 23.2% vs Python 8.0%、61.8% vs 18.6%）——高频分音（齿轮 2046/3069 Hz）落在抽样点之间，那带能量整个没算进分母 | 换成完整 FFT + Hann 窗，定义与 `compare_texture.py` 逐字对齐（现已**逐条精确一致**） |
| 2 | 把 44100 个样本直接喂 radix-2 FFT | 44100 **不是 2 的幂** ⇒ 谱是垃圾：1 秒的 100 Hz 纯音算出"低频占比 **0.0%**"。而真实文件 88282 样本恰好被截到 65536 才没暴露 | 先取 ≤上限的**最大 2 的幂**。（另：不能用"不断右移直到成为 2 的幂"，44100 会被移到 172） |
| 3 | "循环滤波"每遍都把滤波器状态清零 | 那等于**把同一个滤波器串联两级**（频响平方），完全没做成周期。症状很隐蔽：**循环滤波后接缝比反而比因果滤波更差**（0.44 vs 0.14），因为两级串联本身是合法滤波，只是不是要的那个 | 状态**跨遍保留**：第一遍暖机，第二遍从该状态开始并留用 |
| 4 | 噪声床是"时域造噪 + 滤波"，不是周期的 | 干信号接缝比 0.01，加壳后 **0.44→8.62** —— 前三轮把接缝从 20.6 压到 0.5 的努力被一次还回去 | 先试"频域周期构造"（失败：逆 FFT 要 2 的幂，而循环长度 88282 放不下整数个周期 ⇒ 8.62），改成**首尾交叉淡化** ⇒ 0.33 |
| 5 | 非平稳调制的速率是任意值 | 调制不是 `t` 的周期函数（`mod(0) ≠ mod(T)`），回绕点幅度直接跳 ⇒ 整链接缝 **4.74** | 所有调制速率**吸附到"循环基频（1/循环长度）"的整数倍**；2 秒循环本来就只能表示 0.5 Hz 整数倍的起伏，这不是妥协而是诚实 |
| 6 | 用例里拿"能量占比"判"低通把高频压下去了" | 永远判不出来：3 kHz 被压小之后剩下的能量**仍在 3 kHz**，"高频占比"还是 100% | 改判**绝对量**（RMS 比，实测 65.6 倍） |
| 7 | 用例里拿**纯 3 kHz 音**判"低频变主导" | 低通**不可能造出**低频，判据永不成立 | 改用 100 Hz + 3 kHz **等幅双音**（50% → 100%） |

**接缝的最终保证不靠滤波器，靠"淡化放在最后"**：
烘焙链顺序定为 **合成 → 归一 → 壳子 → 首尾淡化 → 落盘**。
实测加壳成品 `verify_loops`：最差接缝比 **2.4**，0 个超阈值 ✓。

## 18. 第八轮：**"起步太尖锐"的定量诊断**，以及把电气规格换成 E235 口径

### 18.1 症状

用户（听完 `preview-v4/AB-trip.ogg`）：

> 起步时的声音过于尖锐了，**从 4 秒到 10 秒听感还不错**，这样看看日本的 E235 系是什么样的电机，改成那样的 VVVF。

关键词是"**局部**"：不是整段不对，是**开头那几秒**不对。整段平均的 `band_profile.py` 看不见这种事
（它会把起步那 3 秒摊平进 100 秒里），所以先补了一个按时间出表的工具。

### 18.2 新工具：`timeline_bands.py`（按时间片看频带）

```
python mmtr/tools/sound-studio/timeline_bands.py <音频> [--from 0] [--seconds 12] [--slice 0.5]
```

每片输出 **RMS / 谱心 / >1.5 kHz 占比 / 音调性 / 主要三个频带**。
其中"音调性"= 100 Hz~6 kHz 内 **最强 bin / 中位 bin** 的 dB 值。

**这个量的标定（对照实验，实测值）**：

| 信号 | 音调性 |
|---|---|
| 500 Hz 纯正弦（1 s 窗，float64） | **230.8 dB** |
| 粉红噪声 | **22.7 dB** |
| `br_423/motor0-3.ogg`（**真实**牵引录音） | **51.4 / 67.6 / 67.3 / 57.4 dB**（逐条最大 68.1） |
| 本次的起步段（`preview-v4/trip-interior`） | 60.1 ~ 67.4 dB |

★ **注意最后两行：我们的起步段落在真实录音的区间里** ——
所以"音调性高"**本身不能**证明起步是错的（真实 VVVF 本来就有很强的音调成分）。
真正能定性的是下面三条：**单带占比 97%**（真实最大 86%）、
**比巡航段高 20 dB**、以及**载波在滑音**（真实载波是定的或跳档的，不是 glissando）。

加音调性这一列的原因：三分之一倍频程带太宽（±12%），
一条被抹开成 ±10% 的谱线和一根纯正弦落在同一个带里占比几乎一样，
**频带占比看不见"线 vs 带"**，这个能看见。

### 18.3 诊断结果：起步那 3.5 秒是**一根上滑的纯音**

`preview-v4/trip-interior.wav`：

| 时间 | RMS dBFS | >1.5k | 音调 dB | 主要频带 |
|---|---|---|---|---|
| 0.00~0.50 | −18.9 | 0.0% | **67.4** | **250:74%** 315:24% |
| 0.50~1.00 | −15.2 | 0.1% | 62.2 | **400:90%** |
| 1.00~1.50 | −11.0 | 0.2% | 60.1 | **500:94%** |
| 1.50~2.00 | −16.5 | 0.1% | 61.2 | **630:97%** |
| 2.00~2.50 | −23.7 | 1.1% | 55.4 | **800:85%** |
| 3.50~4.00 | −31.8 | 0.1% | 51.9 | 63:41% 500:7% |

- **单带占比 74→97%**（真实录音的最大单带占比是 86%）⇒ 那几秒里**基本只有一根谱线**，
  频率从 250 Hz 一路滑到 800 Hz。
- 电平从 −18.9 爬到 **−11.0**，然后一路掉到 −31.8 ⇒ **起步那 2 秒比巡航段高 20 dB**。
- 音调性 60~67 dB —— **这一条不算证据**（真实录音也是 51~68 dB，见 §18.2 标定表）。

**这不是"壳子没调好"，是三条原因叠出来的，全部可查：**

1. **载波是"上滑"的**：`carrierHzPerHz: 40` + `carrierMaxHz: 1045` ⇒ 异步段载波 = 40·f₁，
   而 40·f₁ 从 250 爬到 1045 只覆盖 **0~20 km/h**（约前 3.5 秒）—— 那条滑音正好全落在起步段。
2. **同步分周阶梯在正常运用里根本用不上**：`f1Sync = carrierMaxHz / pMax = 1045 / 9 = 116 Hz`，
   对应 **87 km/h**。也就是说 0~87 km/h 全程都是"一根上滑载波"，
   真车那个"一档一档往下掉"的分周换档**在这台车上永远不会出现**。
3. **壳子里那个 630 Hz 共振峰被滑音扫过**：interior 传导链有
   `peak 630 Hz Q0.9 +9 dB` + `lowpass 1100` + `lowpass 650`。
   同一个载波，在 630 Hz 处被抬 **+9 dB**，在 1045 Hz 处被压约 **−11 dB** ——
   **差值正好 20 dB**，与上表量到的 20 dB 起步凸起逐位对得上。
   ⇒ 那 20 dB 不是电机变响了，是**拟合出来的共振峰被一根滑音扫过去了**。

补充一条：`voiceRecipe` 里 `p.hz < 20` 的分音会被丢掉，而起步时 f₁ = 4.5 Hz ⇒
基波簇的 8 根谐波（4.5~36 Hz）**全在这条线以下**，所以起步段**除了载波真的什么都没有**。

f₁(0 km/h) = slipHz，取 4.5 能过 `minFundamentalHz`、取 0.56 直接静音
（起步只剩载波）。**这条要不要改，本质上是"起步该不该有电机音"这个听感判断。**

**这条 spec 的意义不只是"照抄 E235"**：本仓 SAF420 的**车体与力学口径本来就取自 E235-0**
（山手线 11 节 6M5T，见 `notes/279` §9），而电气规格一直用的是西门子论文里的"通用通勤型"
（齿轮比 **5.93**、载波 40·f₁ 上滑）。**同一节车不可能既是 E235 又是论文样例** ——
这一轮把电气侧也对齐，三处出处（车体 / 力学 / 音效）第一次统一。

**★ 但"0 番台不是清一色三菱"这条修正很重要**：量産先行車（01 編成）是
**三菱 SC104 フル SiC + 東芝 SC105 ハイブリッド SiC 混装**，量産車才全三菱。
⇒ 如果以后要复刻"某一列"的音色，得先确认编成号。合成层目前表达的只是"2 电平 SiC"，
**フル SiC 与ハイブリッド SiC 的区别在合成里没有可分辨的对应量**，所以没建这个维度。

### 18.5 新增 spec 与新增开关

- `SPEC_E235_SIC`（`e235`）：齿轮比 **7.07**、`carrierMode: 'fixed'`、异步段开关频率 **1.5 kHz**、
  阶梯 `[27,21,15,11,9,7,5,3,1]`、`regenCutoffKmh: 7`。
  换档点（烘焙自检输出）：**0~33.5 km/h 异步（恒 1.5 kHz）→ 21 → 15 → 11 → 9 → 7 → 5 → 3 分周**。
  取 1.5 kHz 的理由**不是**"E235 是 1.5 kHz"（那是未知量），而是它让 27/21 分周真的落在
  正常运用速度区间里 —— 比原来的 250→1045 Hz 上滑更接近"恒定开关频率"这个 SiC 的**定性**事实。
- `model.mjs` 新增可选字段 **`asyncFixedHz`**：原来 `carrierMaxHz` 一个字段兼着两个角色
  （"定载波模式的载波值" 与 "同步段 p·f₁ 的上限"）。E235 这两者必须取不同的值，所以拆开。
  **缺省退回 `carrierMaxHz` ⇒ 老 spec（E231 / 209 / N1000）行为逐字不变。**
- `bake.mjs` 新增 **`--carrierhz <Hz>`**：把载波钉成定值以覆盖 spec 设定。
  存在的理由：**"载波是上滑还是恒定"和"恒定在多少 Hz"是两个独立问题**，
  混在一次改动里就分不清是哪一条让听感变了。
- ★ **`regenCutoffKmh` 从 27 改成 7 是"实现约束"不是实车数据**：`notes/379` 按全电气制动取 5，
  但 `bake.mjs` 的分档表是沿**牵引**扫描出来的（0 km/h ⇒ f₁ = slipHz = 4.5），最低一档在 f₁≈4.9；
  而再生段 f₁ = rotor − slip 可以低到 0。切除点低于"f₁=4.9 对应的 6.2 km/h"时在线挑档挑不到档，
  实测变调量掉到 **0.66**（预算 ±15%，`bake.mjs` 直接 exit 1）。所以取 7 km/h（该点 f₁≈6.2）。

### 18.10 ★★ 出 preview 时抓到一个**安静的严重 bug**：①.5 扩散从头到尾是个空操作

**起因**：渲染 `preview-e235` 时看了一眼壳子的逐级 RMS，发现 `smear` 一级
`source RMS 0.1354 → smear RMS 0.0339`，**正好是 0.25 倍**，而 `interior` 的
`smear.amount = 0.75` ⇒ `out = x·(1−a) + wet·a = 0.25x + 0.75·wet`。
0.25 倍意味着 **`wet ≡ 0`**。

**确认**：对 1 kHz 纯音跑一轮，`max |smear(x) − 0.25·x| = 7.1e−13`；
再对 200/400/630/1000/1500/2000/3000/5000 Hz **每一个频率都是恰好 −12.04 dB**
—— 随机脉冲响应不可能对所有频率给出同一个常数目，这只能是"输出 = 干信号项"。

**根因**（`shell.mjs` 的 `circularConvolve` 最后一行）：

```js
out[i] = -ai[i] / n;   // ✗ 取虚部
out[i] =  ar[i] / n;   // ✓ 取实部
```

第三次 fft 之后，**虚部本来就应该是 0，实部才是 `n·(x⊛ir)`**。
拿虚部当结果，等价于断言"卷积恒等于 0"。

**判据不靠推导，靠暴力循环卷积** —— 新增 [`diag-convolve.mjs`](../tools/sound-studio/diag-convolve.mjs)，
自带一份 fft 与两版实现，与 O(n·L) 暴力解逐样本比：

| 版本 | 随机用例（n=64，IR=9）与暴力解最大误差 | delta 脉冲响应 |
|---|---|---|
| A 现有（取 −imag/n） | **4.707e−1**（量级就是答案本身） | **不是恒等**（误差 4.96e−1） |
| B 改为（取 real/n） | **4.441e−16** | 6.66e−16 ✓ |

**为什么这么久没被发现（三件事叠在一起）**：

1. **`selftest.mjs` 里根本没有扩散这一级的断言** —— 传导 / 底噪 / 非平稳 / 失真 / 弱化都有，
   只有它没有。**这次补了两条**（见下）。
2. **那 −12 dB 是"安静"的**：它把进 `saturate` 的电平压小 4 倍 ⇒ 饱和变弱 ⇒ 谐波变少，
   于是 1 kHz 带占比正好从 2.56% 掉到 0.59%、2~5 kHz 从 0.49% 掉到 0.10%。
   **我当时把这次"变干净"记成了"扩散生效"，那个结论是错的。**
   用户后来仍说"电机声还是太 raw"—— **因为他要的那一级从来没运行过。**
3. 断言写法本身也踩过坑（两版都写错过，都记在 `selftest.mjs` 注释里）：
   - 用**单根纯音**测"输出 ≠ 输入×常数"是**恒不成立**的（稳态正弦是卷积的特征函数，
     卷积只给它乘一个常数）—— 必须用**多根分音**；
   - 判"响度不变"也是**错的**：干湿两项去相关 ⇒ 期望响度 `10·log10((1−a)²+a²)`，
     `a=0.75` 时是 **−2.04 dB**（实测逐位吻合）。第一版把判据写成 `|Δ| ≤ 1.5 dB`，
     于是**正确的实现被判成失败**——判据错，不是代码错。

**修好之后必须重估的东西**（这轮已重做）：

| 量 | bug 版（=纯 −12 dB） | 修好版 |
|---|---|---|
| 壳子逐级 RMS（E235，interior） | source 0.1354 → smear 0.0339 → output 0.1048 | source 0.1354 → smear **0.0883** → output **0.1717** |
| `saturate` 入口 RMS | 0.0929 | **0.2429**（饱和强得多） |
| E235 起步 0~0.5 s | −42.3 dBFS，`63:6%`（只剩底噪） | **−38.9 dBFS，`500:26% 630:14% 800:5%`**（谱丰富了） |
| 加壳集接缝 | 最差 6.3、0 问题 | **最差 6.3、最低边界窗电平 0.52、0 问题**（循环卷积保周期，没退化） |

**新增的两条断言**（`selftest.mjs`，且都做了"把 bug 放回去必须失败"的控制实验）：

| 断言 | 修好版 | 放回 bug |
|---|---|---|
| ①.5扩散：真的在卷积（输出不是输入的纯缩放） | k=0.6905，残差 **62.6%** | **FAIL** k=0.2500，残差 **0.0%** |
| ①.5扩散：宽带响度变化 = 干湿功率和的解析式（±1 dB） | 实测 −2.04 vs 解析 −2.04 | **FAIL** −12.04 dB |

自检从 101 条升到 **103 条，0 失败**。

**顺带纠正一条物理说法**：35 ms 的脉冲响应**不能把一根稳态谱线"抹成一条窄带"**
（稳态正弦是卷积的特征函数）。它对**周期性信号**真正做的是：按 ≈29 Hz 的分辨率
给相邻分音各乘一个随机增益与相位，把"严格幂律、相位无关"的加法合成**去相关**。
机理已按这个改写进 `shell.mjs` 的注释。

### 18.11 同一次排查里发现的第二个"安静的工具 bug"：`band_profile.py` 只量了开头 1.49 秒

修扩散的过程中跑 `band_profile.py` 同时喂了两份 100 秒的 preview，得到
**「1 kHz 带占 42.47%、是真实的 76 倍」**。这个数字看着像"载波炸了"，
但 `timeline_bands.py` 逐 5 秒扫一遍，**整段最大单带占比是 500 带的 22~76%，1 kHz 从没上过台面**。

原因：`band_profile.py` 原实现是

```python
n = 2 ** int(np.floor(np.log2(min(x.size, 1 << 16))))   # 长文件 ⇒ 65536 样本 = 1.49 s
spec = np.abs(np.fft.rfft(x[:n] * w)) ** 2               # 只对开头 1.49 秒做一次 FFT
```

**它只量开头 1.49 秒，而且不告诉任何人**。再叠加 `main()` 会把多个输入**按文件平均**，
于是那 42% 其实几乎全部来自两份文件里"起步时载波被钉在 1045 Hz"的那一份。
⇒ **两份工具给出矛盾结论时，先怀疑工具，别先怀疑信号。**

已改：改成 65536 点、50% 重叠**滑窗平铺取平均**，并把"实际量了多少秒"打出来。
重测单份 `trip-e235-interior.ogg`（103.7 s）得到的是另一幅图 —— 而这幅图才是可用的：

| 带 | 我的 | 真实 | 差 |
|---|---|---|---|
| 100 | 3.36% | 19.26% | 0.17（偏少） |
| 500 | **51.30%** | 8.04% | **6.38（过突出）** |
| 630 | 16.01% | 40.35% | 0.40（偏少） |
| 1000 | 1.10% | 0.43% | 2.55 |
| **2~5 kHz** | **0.09%** | **0.14%** | ✓ 不刺 |

⇒ 修好扩散之后，**"刺耳段"（2~5 kHz）是达标的（0.09% vs 0.14%）**，
剩下的失衡是 **500 Hz 过突出（6.4 倍）+ 630/100 Hz 偏薄** ——
和 §18.6b 指出的那个 `peak 630 Hz` 拟合产物是同一根线，
再次印证"该重做的是壳子的频率形状，不是载波"。

## 19. 第九轮：**底噪压低**，并把**驾驶室**定为主目标

### 19.1 用户口径（两条，都是范围性的决定）

> 感觉实际列车的声音底噪没有那么明显，**并且我们主要需要制作驾驶室内音效**。

- 第一条是**混音平衡**问题：底噪床太显眼。
- 第二条是**项目范围**问题：`cab` 从"顺便做的第二个 voicing"升为**主目标**，
  `interior` / `exterior` 降为参考。§18.8 里"预设用哪个"这一问到此为止。

### 19.2 先给底噪一个可以单独试听的开关：`--bedgain`

`preview.mjs --bedgain <倍数>`（默认 1，`0` = 完全不放底噪）。
理由与 `--carrierhz` 相同：**"底噪是不是太响"和"底噪该是什么频谱"是两个独立问题**，
不拆开就只能靠猜。同时在报告里加了一行**分层占比**：

```
分层占比：牵引层（含齿轮）RMS 0.0935 · 底噪层 RMS 0.0312 ⇒ 底噪按能量占 10.0%
```

**控制实验（证明这个开关与那条自检都还活着）**：`--bedgain 0` 会让
`preview.mjs` 原有的"惰行仍有滚动噪声（速度驱动）"这条自检 **✗ 失败**
—— 正是应该的：底噪归零之后惰行就没东西了。

### 19.3 底噪实测：原来占**三成能量**，现在约**一成**

| | 底噪层 RMS | 牵引层 RMS | 底噪按**能量**占比 |
|---|---|---|---|
| 改前（cab，E235 整趟） | 0.0608 | 0.0935 | **29.7%** |
| 改后（cab，E235 整趟） | 0.0312 | 0.0935 | **10.0%** |
| `--bedgain 0.5` | 0.0156 | 0.0935 | 2.7% |
| `--bedgain 0.25` | 0.0078 | 0.0935 | 0.7% |

三套预设的 `bed` 参数（都**降电平并变暗**，不是单纯调音量）：

| 预设 | 改前 | 改后 | 底噪频谱变化（实测） |
|---|---|---|---|
| `interior` | `-9 dB / lp 2200 / tilt 320+8` | `-15 dB / lp **1500** / tilt 280+7` | —— |
| **`cab`（主目标）** | `-10 dB / lp 2600 / tilt 380+7` | **`-16 dB / lp 1400 / tilt 300+7`** | 低(<500) 80.1→**86.4%**、中(500~2k) 18.6→**13.2%**、高(>2k) 1.2→**0.2%** |
| `exterior` | `-9 dB / lp 3600 / tilt 520+5` | `-13 dB / lp 2600 / tilt 400+4` | —— |

**为什么不能只降电平**：底噪是**没有结构的噪声**，它"显眼"主要来自
500~2000 Hz（人耳最敏感、而牵引谐波在那里最薄）。所以电平降 6 dB 的同时把
低通从 2.6 kHz 收到 1.4 kHz —— "嘶"的成分往下压，"轰"的成分留下。

### 19.4 ★ 换到驾驶室之后发现的**结构性事实：起步段就是载波本身**

在 `cab` 下扫载波（同一趟、同一 E235 规格、只换 `--carrierhz`），取 0~1 s：

| 载波 | RMS | 谱心 | >1.5 kHz | 主要频带 |
|---|---|---|---|---|
| **700 Hz** | **−9.9** | 724 | 0.6% | `630:52% 800:39%` |
| 1045 Hz | −13.0 | 1046 | 1.6% | `1000:93%` |
| 1500 Hz | −14.0 | 1582 | **82.0%** | `1600:93%` |
| 2200 Hz | −20.5 | 2152 | **95.8%** | `2000:67% 2500:31%` |

**四个载波下起步段都是 91~99% 集中在那一根上。** 这不是参数没调好，是模型的**结构性**结果：
起步时 f₁ = slipHz = 4.5 Hz，基波簇 8 根谐波（4.5~36 Hz）**全部落在 `voiceRecipe`
的 `p.hz < 20` 截断线以下**，于是除了载波**真的什么都不发**（§18.3 已指出，这里是四载波重复验证）。

⇒ 起步段能调的只有**两件事**：载波**定在多少 Hz**、载波**多响**
（`carrierAmplitude` / 低速段是否整体淡出）。频率越高越"嘶"（2200 Hz 时 96% 能量在 1.5 kHz 以上）。

**这里有个诚实的矛盾**：SiC 的真实开关频率几乎肯定是 **kHz 量级**，
但在本模型 `cab` 传导链下（低通 3000/2200 ⇒ 1.5 kHz 几乎不衰减），
1.5 kHz 以上会变成一根**压过一切**的亮啸叫。
**这个矛盾不是靠调载波能解决的** —— 它就是 §18.6b 那条结论的另一面：
壳子的高频形状是拟合产物，它决定了答案。
所以第 3 步（重做壳子频率形状）从"可选项"变成**驾驶室音效的前置条件**。

### 20.6 剩下三处差距，以及哪些是**不该追**的

1. **400 Hz 0.04× / 1~1.6 kHz 10~17×：这是 E235 与京急的电气差异本身，不该追。**

2. **125 Hz 2.37× 偏厚**：还没调掉。来源是起步早期 n=2,3 落在 125 Hz 一带；
   `humFundamentalGain` 从 0.15 压到 0.08 只动了 0.1 个百分点 ⇒ 说明它不是 n=1 造成的。
   **待办**。
3. **2~5 kHz 我们 0.20% vs 实录 1.27% —— 这一条我倾向"不该追"。**
   那一段是 iPhone 自己的本底噪声 + 风噪；要把混音的 2~5 kHz 抬到 1.27%，
   底噪床得有 7~22% 的能量在 2 kHz 以上，那就又变成"嘶嘶响"（正是 §19 用户否掉的东西）。

### 20.7 ★ 一条物理上限：我们的电机转得比京急快 39%

E235 齿轮比 **7.07**，京急 2100 约 **5.33**（且轮径 0.82 vs 0.86）。同一速度下
**电机转频高约 1.39 倍**（85 km/h：我们 f₁ ≈ 135 Hz，对方 ≈ 97 Hz）。
⇒ **"频带分布逐格对上"在保留 E235 传动比的前提下做不到。**
能对上的是两条：**能量重心落在 100~400 Hz**、**载波不再压过一切**。两条都已达到。

### 20.10 第 21 轮：用户「**电机高频有些刺耳，声音也略大了**」

#### ★ 试了又撤掉的两条路（记下来免得再走）

1. **"整备运转底噪地板"**（`bedGainForSpeed` 给一个与速度无关的地板，取 0.20）。
   动机是一手实录：**停车时车内就有 −25.5 dBFS 的底噪**，起步最初 4 s 只比它高 1.3 dB。
   **实测毫无效果**：2~4 s 的频带占比与改前**逐格相同**。算得出原因 ——
   底噪层全速域平均 RMS 只有 **0.031**（−30 dBFS），乘 0.20 = −44 dBFS，
   而那一瞬牵引层是 −15.8 dBFS ⇒ **差 28 dB**。同时让两条语义正确的断言（`停车为 0`、
   `负速度按 0 处理`）失败。**已撤。**
2. **`partialAudibility`：把 `p.hz < 20` 的硬截断换成 12→24 Hz 平滑渐入**。
   动机是"权重最大的 2f₁ 在 f₁≈9→10.6 Hz 时越过 20 Hz，整根突然出现 ⇒ 阶跃"。
   **也毫无效果** ——因为 `saturate` 级自带一个 **20 Hz 高通**（去直流用），
   12~20 Hz 的内容在下游照样被拿掉。同时它把"分音必须落在 [20, 8000] Hz"这条**契约断言**打破了。
   **已撤**（撤干净：重新烘焙出的清单除 `generatedAt` 外与 v21 **逐字节一致**）。

#### ★ 顺带发现一条**验证方法**上的坑：`.ogg` 的字节不可复现

撤掉改动后重新烘焙，`v23` 与 `v21` 的 **32/32 个 ogg 文件字节都不同**、清单也不同 ——
但**解码成 f32 之后逐字节完全相同**（362400 字节，0 处不同）；清单的差异只是 `generatedAt`。
⇒ **以后不能拿 `.ogg` 的哈希做回归判据**（编码器不保证可复现），要比就比**解码后的样本**。

#### 仍然开着的口子：起步 2~4 s 有一个 +7 dB 的单带台阶

| 我们 0~8 s | RMS | 主要频带 |
|---|---|---|
| 0~2 s | −22.8 | `63:17% 80:13% 100:10%`（三带分摊，正常） |
| **2~4 s** | **−15.8** | **`63:73%`**（单带、音调性 67 dB，**跳 7 dB**） |

| 6~8 s | −17.7 | `125:94%` |

- **不是齿轮层**：`--gearvol 0` 时逐格相同（`63:73%`、−15.9 vs −15.8）。

n=2（2f₁=21.2 Hz）幅度 **0.261**，而其余分音都 ≤0.039 —— **一根顶 6.7 倍**。
这是 `magnetostrictionBoost 1.0` 与 `humDecay 1.0` 组合出来的，是**下一步**要解决的

### 20.11 第 22 轮：用户「**电机音的遮盖效果不够，音量也较大**」

#### ★★ 先说这一轮最重要的东西：**不是调参，是两个"第二份定义"的 bug**

改完参数重烘、重渲染，**起步电平一点没变**。查下去发现 spec 被**手抄了两遍**：

| 位置 | 症状 |
|---|---|
| `bake.mjs` 写清单时 | `spec: { id, name, poleCount, … }` **逐字段手抄白名单** ⇒ 新字段（如 `startupFullSpeedMps`）**被静默丢掉** |
| `preview.mjs` 读清单时 | `const spec = { … }` **又抄一遍白名单**，还硬编码 `loadBlendSpeedMps: 8` ⇒ 就算清单里有也进不来 |

两处一叠加，`SPEC_*` 里新加的字段**永远到不了预览端**（`preview.mjs` 用 `loadAxis` 算每一帧音量，
所以"音量"相关的字段全都受影响）。这与 `humWeight`（§20.8）是**同一类坑**：
**同一条规则写在两个地方，改一处就有一半不生效。**

已修：`bake.mjs` 改成 `spec: { ...spec, rotorHzPerKmh, breakpointKmh }`（全量 + 覆盖派生量），
`preview.mjs` 改成 `const spec = { ...manifest.spec }`。修完清单里 **44 个字段**全部到位
（实测 `startupFullSpeedMps = 1.5`、`humLowpassHz`、`humAmplitude`、`carrierAmplitude` 都能读到）。

> **教训**：以后凡是"新加一个 spec 字段"，必须验证**它有没有走到预览/游戏端**，
> 不能只看 `model.mjs` 里写了。

#### "遮盖效果不够"是怎么量的、结论是什么

**量的是"底噪有多少能量落在电机盖不住的频段"**。电机（E235）的基波簇在 160~400 Hz，
**800 Hz 以上它盖不住任何东西**。新增 [`diag-bed-lowpass.mjs`](../tools/sound-studio/diag-bed-lowpass.mjs) 量出来：

| cab 底噪低通 | <500 | 500~2k | >2k | **800 Hz 以上占比** |
|---|---|---|---|---|
| 原 3600 | 83.1% | 15.2% | 1.49% | **7.74%** ← 这部分会从电机上面"探出来" |
| 2000 | 84.7% | 14.6% | 0.50% | 6.09% |
| **1200（改用）** | **87.4%** | **12.3%** | 0.09% | **3.68%** |
| 800 | 91.0% | 8.8% | 0.02% | 1.63% |

取 **1200**：探出来的部分减半（7.74% → 3.68%），而且**底噪自己的频带切分变成 87.4% / 12.3%**
——与实录的 **87.7% / 11.9%** 几乎相同（一个独立的旁证）。

#### 试过但**放弃**的方案：把梳齿调密（"遮盖"的直觉解）

直觉上"密梳齿遮盖更好"，实测也对：

| | 顶带占比 @2~4 s | 起伏 | <500 Hz |
|---|---|---|---|
| 稀疏（现状） | **73%**（一根顶住） | 0.392 | **88.3%** |
| 密集（`humshape 0.08,0.35,0.45,0.55`） | **42%** | **0.449** | **36.9%** |

密集版把**音调性、起伏、遮盖**三项全部修好（起伏 0.449 vs 实录 0.450），
但**能量被推到 500~1000 Hz**，<500 Hz 掉到 36.9%。

**试过用"绝对频率包络"（`humLowpassHz`）把密集梳齿压回 160~400 Hz** ——
新增了 `humBandGain`/`humAmp`（`model.mjs` 与 `bake.mjs` **共用一份**实现），
烘了 `humLowpassHz` = 500、组合密集梳齿：<500 Hz 只回到 **67.0%**，仍明显不如稀疏版。

**为什么这一条是死路（记下来）**：实录那条"400 Hz 22% → 500 Hz 2.4%"的断崖，
**不是滤波器斜率**，而是**它的主导成分本来就是一根离散的载波线**
（低载波 GTO 的音阶顶音正好 400 Hz）。要复刻那个断崖，就得让我们的主导成分**也是一根线**
—— 那就回到了"稀疏、遮盖差"。**"频带分布像这段实录"与"遮盖好"在物理上是互斥的**，
因为这段实录本身就是一个稀疏、音调性强的声音。所以这一轮取了"保频带分布 + 用底噪变暗来改善遮盖"。

得你定，我没有替你改。

### 20.12 第 23 轮：用户质疑「**是不是咱们参数错了，E235 走行音好像不这样**」⇒ 做参数溯源

#### ★ 结论：**有一个参数可以证明是错的**，而且它正好在最听得见的地方

**错的是"载波恒定 1.5 kHz"**（`carrierMaxHz` / `asyncFixedHz` 都取 1500）。

推导很简单：唯一有出处的分周事实是
「**高速域のスイッチングを従来の1パルスから27パルスへ変更**」。
27 分周 ⇒ `f_c = 27·f₁`；E235 在 120 km/h 时 f₁ ≈ **187 Hz**
（齿轮比 7.07 + 极数 4 + 轮径 0.82 —— 这组数已用 MT79 官方额定点验过）
⇒ **开关频率必须能到 27 × 187 ≈ 5.06 kHz**。

反过来：**若天花板只有 1.5 kHz，`27·f₁ ≤ 1500` 仅在 `f₁ ≤ 55.6 Hz`（≈33 km/h）成立**
⇒ "27 分周"在 33 km/h 以上**自行失效**，而那条事实说的恰恰是**高速域**。自相矛盾。

**而且我得承认这个数是怎么来的**：当初是**反推**的 ——
"我想让分周换档落在 33 km/h（正常运用区间内），所以把天花板取 1500"。
**这是把结论当参数用**，属于本仓最不能接受的一类错误。

#### 参数溯源表（回答"是不是参数错了"）

| 参数 | 值 | 性质 |
|---|---|---|
| SiC、**2 レベル**電圧形 PWM-VVVF | — | **官方**（電気設備学会誌 2015-08、日文维基） |
| 主电动机 MT79 / 140 kW / 全閉式外扇形 | — | **官方**（同上） |
| 极数 **4** | — | **推导**：官方 80 Hz ↔ 2380 rpm；且与齿轮比+轮径在额定点自洽（2378.5 vs 2380 rpm，差 0.06%） |
| 齿轮比 **7.07** | — | **官方** |
| **27 パルス（高速域）** | — | **官方** |
| 1C4M、0 番台三菱+东芝混装 / 量産車全三菱 | — | **官方** |
| **载波时序** | ~~恒定 1.5 kHz~~ | ★★ **错**（见上，与"27 分周"矛盾） |
| 分周阶梯 27→21→15→11→9→7→5→3→1 | — | ★ 只有 **27** 有出处，其余是按 2 电平惯例补齐的 |
| `slipHz` 4.5 Hz | — | ★ 取自日立 **1979** 论文（另一台电机）；MT79 官方 すべり 0.7% ⇒ **0.56 Hz** |
| 车轮径 0.82 m / 电机侧齿数 16 | — | ★ 未找到官方值 |
| `carrierAmplitude` / `humAmplitude` / `humLowpassHz` / 各簇权重 | — | ★ **全部是声学拟合量，无任何一手依据** |

#### 按有出处的事实重做的时序：`SPEC_E235_27PULSE`

异步到 f₁ = 40 Hz（≈25 km/h，载波 **1080 Hz**），此后**一律 27 分周**
（`modeTable: [[40, 0], [1e9, 27]]`）⇒ 载波随速度线性上升：

| km/h | 5 | 20 | 30 | 40 | 60 | 80 | 100 | 120 |
|---|---|---|---|---|---|---|---|---|
| **恒定 1.5 kHz（错）** | 1500 | 1500 | 1500 | 1375 | 1440 | 1391 | 1413 | 1312 |
| **27 分周保持（有出处）** | 1080 | 1080 | **1356** | 1768 | 2591 | 3415 | 4238 | **5061** |

（★ `asyncFixedHz = 1080` 是取"让异步与同步在 f₁=40 Hz 处连续"，不是独立测量的数；真实换档点仍未知。）

两者是**完全不同的听感**：一个是**恒定的高频哨音**，另一个是**一条上滑的高频啸叫**。

#### ★ 这一比又暴露第二个错：`cab` 传导链的高频滚降也是凑出来的

把两条时序放在**同一载波幅度 0.05** 下对照（单变量）：

| | >1.5 kHz 能量占比 |
|---|---|
| ① 恒定 1.5 kHz | **0.7 ~ 5.0%** |
| ② 27 分周上升 | **0.1 ~ 0.9%** |

② 的载波**爬出了 `cab` 链的通带**（那条链在 5 kHz 处衰减 **22 dB**，是我上一轮为了拟合
三分之一倍频程凑的）。但真实 E235 的 SiC 啸叫**在司机室里是听得见的** ⇒
**`cab` 的双低通（3000/2200）同样是错的**，而且它和载波时序的错误**互相掩盖**：

### 22.1 用户口径，以及它推翻了什么

|---|---|---|

### 22.2 ★★ 先修 bug：`filterChain` 的 circular 模式把每一级**串了两遍**

**症状**是从"整链台阶比"这条断言亮起来的（1.40，干信号 0.968）。定位过程：

1. [`diag-art-seam.mjs`](../tools/sound-studio/diag-art-seam.mjs)：把 ⑥ 的三级**各自单独**量
   ⇒ 暖化 1.337、去刺 0.970、空间 0.985 ⇒ 嫌疑落在暖化；
2. 再拆暖化：它是"滤波 + 无记忆 tanh"，于是分别量**移位可交换性**
   （对周期信号，`F(shift x) = shift F(x)` ⟺ 输出以循环为周期）
   ⇒ 暖化 **6.5e-2**、走**循环卷积**的 ①.5 扩散 **7.6e-13**、`conduct`（走 `filterChain`）**3.9e-1**；
3. [`diag-circular-filter.mjs`](../tools/sound-studio/diag-circular-filter.mjs) 把误差**分块**打出来
   ⇒ 误差只在**开头约 4000 个样本**（块 1 之后是 1e-10 量级）= 一个**启动瞬态**；
4. [`diag-filter-cascade.mjs`](../tools/sound-studio/diag-filter-cascade.mjs) 给出决定性判据 ——
   **单根纯音的增益**：

| 预设 | 实测增益 | 应 |
|---|---|---|
| `{peak 120 Hz Q1 **+6 dB**}` | **+11.97 dB** | +6.00 dB |

**根因**：`filterChain` 里"跑两遍"写成了 `const src = pass`（上一遍的**输出**），
而不是 `const src = y`（同一条输入）。于是"第二遍"变成**把同一级滤波器再串一级**：

* **频响被平方** —— `interior` 的 630 Hz +9 dB 实际是 **+18 dB**，两级 lowpass 实际是 **−24 dB/oct × 2**；
* 第二遍的 `x1/x2` 里存的是**原信号**的历史、而输入是滤波后的信号 ⇒ 状态不匹配 ⇒
  输出**开头**一个与信号同量级的启动瞬态 —— 而开头正是**循环的回绕点**。

**为什么它能活这么久（这条最值得记）**：**这种错误会被"调参数"完整吸收。**
每一轮试听之后我们都去改 `SHELL_PRESETS` 里的数字直到听着对为止 ——
改的其实是"预设 × 2"这条曲线。所以**耳朵发现不了它**，只有**解析判据**能：
"一级 +6 dB 的 peak 必须正好是 +6.00 dB"。

修完之后（`src = y`）：+6.00 dB ✔、移位可交换性 **0.000e+0** ✔、整链台阶比 1.402 → **0.976** ✔。

**影响面**：
* `baked/saf420`（**出货的那个包**）是 `--shell off` 烘的 ⇒ **不受影响**，`SAF420_v41.zip` 一个字节没动；
* 所有 shell 试听产物（interior / cab / exterior 的历史版本）都是在"频响平方"下听的，**作废重听**；
* 游戏端 Java **没有**壳子实现（只按 volume/rate 播烘好的循环），所以不需要改 Java。

### 22.3 ⑥ 艺术化加工：三级

作用位置：**还原链之后、峰值归一之前**（`saturate` → ⑥ → `weaken`）。三级各自的机制必须写清楚，
因为它们都必须**保持循环无缝**，而"无缝"是前几轮花最大力气换来的：

| 级 | 做什么 | 怎么保证循环安全 |
|---|---|---|
| ⑥a 暖化 | 并联一路**带偏置的偶次谐波**（2 次为主），输入只取 150~520 Hz 的"机体带" | 无记忆 + 循环滤波 ⇒ 严格周期 |
| ⑥b 去刺 | **STFT 域动态频带压缩**：2~5 kHz 静态 1.5 dB + 动态最多 4 dB | 帧索引模 N 回绕、重叠相加按窗能量归一 |
| ⑥c 空间 | 与 62 ms **司机室脉冲响应**做循环卷积，按 `mix` **相加** | 循环卷积（数学上严格保持周期） |

**⑥a 为什么是"带偏置"**：没有偏置的对称饱和只产生**奇次**谐波（五度/三度，听感"硬"）；
加直流偏置后 `2 次项` 系数 `tanh''(bias)/2 ≠ 0` ⇒ **偶次（八度）出现**。
再除以原点斜率 `g0 = a·sech²(bias)`，小信号处单位增益 ⇒ `amount` 才有确定含义。
实测：2 次 9.13e-3 vs 3 次 9.36e-4（**偶次为主，比 9.8**），4 kHz 处几乎不被动到（4.2e-4）。

**⑥b 为什么必须进 STFT**（这一条是本轮第二个"实测推翻直觉"）：
时域谱减法 `y = x − (1−g)·H·x` 的实际衰减是 `|1 − (1−g)·H(f)|`，**同时依赖 `H` 的幅度与相位** ⇒
3.4 kHz 处设定 −3 dB 只做到 **−2.16 dB**；而在滤波器拐点上那一项是**正交相加** ⇒ **变成提升**。
去刺的级在某个频率上把刺抬起来是不能接受的 ⇒ 信号路径改到 STFT（增益逐 bin 是实数，相位不动）。
STFT 往返在"增益 = 1"时的重建误差实测 **−81 dB**。

**⑥b 的检测器必须与信号路径分开**：进 STFT 之后第一版拿"帧内带内 RMS"当包络，
结果**稳态正弦与同有效值的脉冲串帧有效值一样** ⇒ 动态那一份完全不动作（实测两者都是 0.00 dB）
—— "动态"名存实亡，退化成一个静态 EQ。去刺要反应的是**峰值因数**，所以检测器改成
**峰值包络**（快起慢落）、阈值取这一带的**长期有效值**：稳态正弦的 `峰值/有效值 = +3 dB`，
于是 `overDb: 3` 恰好让稳态落在阈值上、而高峰值因数的瞬态越界。
实测：同有效值下，稳态正弦 **−0.01 dB**、高峰值因数脉冲串 **−4.27 dB**。

**⑥c 为什么用"加"而不是"干湿混合"**：`(1−a)·干 + a·湿` 在两项去相关时响度按
`10·log10((1−a)²+a²)` **下降**（`a = 0.7` 时 −2.0 dB，`smear` 那一级吃过这个亏）。
混响在物理上是**叠加**在上面的 ⇒ 用加法，宽带电平上升 ≈ `10·log10(1+mix²)`
（实测 1.26 dB vs 解析 0.37 dB，±1 dB 内）。**车外预设刻意不给 room** —— 轨旁是自由场，
加混响就是错的。

## 23. 第 26 轮：**距离与墙**（不是音量）＋ **电子清爽感**（谱对比度）

### 23.1 用户口径

> 「cab 声音还需要一定的**距离和墙阻隔衰减**，**不能单纯降低音量**。
>   其次电机声依旧很 **raw**，没有真车的**电子清爽感**」

两条都不是"再调一个数"，各自需要一级新的 DSP：**⓪ 传播**、**⑥d 清爽**。

### 23.2 ⓪ 传播：原来的"距离"其实是个音量旋钮

原来那段代码在 `conduct()` 里：

```js
const airHz = Math.max(600, 9000 / (1 + α·d·0.06));
y = filterChain(y, [{ lowpass, airHz }]);
y *= 1 / (1 + d·α·4);
```

代入 cab 的旧值（`α = 0.002`、`d = 5`）：**`airHz = 8995 Hz`（等于什么都没做）、增益 0.96（−0.3 dB）**；
车外（`α = 0.02`、`d = 25`）只相当于一个 **−9.5 dB 的音量**。用户那句"不能单纯降低音量"说的正是它。

**距离与墙在听感上是三件事，没有一件是音量**：

| # | 机制 | 量 |
|---|---|---|
| ① | **传播延迟** `d/343` | 8 m ⇒ **23.3 ms**（实测 1029 样本）。这是距离最主要的线索 |
| ② | **空气吸收** `α(f) = 1.55e-7·f^1.6` dB/m（ISO 9613-1 量级，20 °C/50 %RH） | 8 m：8 kHz 只有 **2.2 dB** ⇒ **司机室的高频损失不是空气给的**；25 m 才 6.8 dB |
| ③ | **墙的隔声**：质量律 + 吻合谷 + 结构声旁路 + 侧向传声上限 | 见 23.3 |

实现上：延迟用**循环移位**、空气与墙用**幅度谱**（`applyMagnitudeResponse`，零相位）——
两者都**严格保周期**（实测移位可交换误差 3.2e-13），接缝一个字节都没动。
**不做球面扩散的增益**：整条链最后按峰值归一，绝对电平没有意义，
而"距离 = 变小"正是用户否掉的那个理解；距离改的是**延迟、音色、直达/混响比**。

### 23.3 墙：迭代三次，拐点必须落在 1~2 kHz

| 版本 | 实测结果 |
|---|---|
| 16 dB @250 Hz、6 dB/oct、无上限 | 整条谱压到 100~400 Hz；2~5 kHz **0.04%**；630~1600 Hz 掉到 1/5 |
| 12 dB @800 Hz、4 dB/oct、上限 20 | 630~1600 Hz 掉到 **1/3**（低频占 98.8%） |
| **4 dB @2 kHz、4 dB/oct、上限 10、地板 3** | 见 23.6 |

⇒ **拐点必须落在 1~2 kHz**：低中频是**结构声**主导（转向架→车体→地板，墙几乎不额外衰减），
空气声到高频才接管。这正是"结构声 ↔ 空气声交叉"的物理图像，
也恰好是靶子的形状（§21.10 修正后的 E235：200~1600 Hz 的总倾斜只有 ~3 dB）。
`tlMaxDb: 10` 是**侧向传声/漏声**（车窗、线束穿孔、门缝）——真实构件达不到质量律外推值。

三条断言分别盯着三个物理事实：**低频几乎不隔**（100 Hz ≤ 4 dB）、
**衰减随频率上升**（1.5 k → 8 k 再涨约 7 dB）、**吻合频率处比附近传声更多**（4.2 kHz 的谷）。

### 23.4 ⑥d 清爽：谱对比度，包络必须**两级**

判据不是"高频多不多"，而是**音调性**（谱线上的能量 / 线之间的能量）。
真实 VVVF 是一组**很干净的谱线**，线之间是安静的；我们的线被
①.5 扩散的随机相位、底噪床、饱和的互调产物填满了线之间 ⇒ "一坨噪声里有点音调"。

做法（46 ms 窗 —— 必须比去刺那级的 12 ms 长得多，否则主瓣 344 Hz 比线间距 190 Hz 还宽）：

```
trend = 宽滑动平均(mag, ±10 bin ≈ 1/6 倍频程)      ← 吃掉"谐波随次数衰减"与共振形状
norm  = mag / trend
g     = clamp((norm / max(norm 邻域 ±4 bin))^p, floorGain, 1)   ← 只减不增
```

**★ 两级包络是踩了两次才定下来的**：

| 做法 | 实测 |
|---|---|
| 滑动**平均**包络 | 平坦的雾对自己没有对比度 ⇒ 只压 −0.6 dB；音调性 **50.6 → 50.9**（等于没做） |
| 直接在 `mag` 上取滑动**最大值** | 高次谐波衰减 ⇒ 局部最大值总取到邻近更强的那根 ⇒ **线自己也被压** ⇒ 整趟 630~1600 Hz 掉到 v31 的 **1/3** |
| **两级（trend → 归一化 → 最大值）** | 音调性 **50.6 → 56.4 dB**（+5.8）；**线** −0.5 dB、**线之间** **−6.0 dB** ✔ |

第三行那三组数就是它的契约：**只动线之间，不动线**。

### 23.5 顺带修掉的：混响的归一方式（暗中差 5.6 dB）

`roomIr` 原来是**能量归一**（`Σh² = 1`）。它保证的只是"**全带**平均 `|H(f)|² = 1`"，
而我们的信号是**带限**的（100~6000 Hz，占 0~22 kHz 的 ~27 %），IR 又是**暗**的
⇒ 在信号所占的那一段里平均 `|H|² ≈ 3.7` ⇒ **混响暗中比干信号响 5.6 dB**。
后果不止"响一点"：`room.mix` 的含义被偷偷放大 3.7 倍，"空间感"永远比设定的重。
改成**通带增益归一**后，`10·log10(1+mix²)` 这条解析式才成立（实测 **0.58 dB vs 解析 0.90 dB**）。

## 24. 第 27 轮：**换靶 —— 不按 E235 了，改按京急 2100 形**

### 24.1 用户口径与理由

> 「我们不如不按 E235 了吧，按京急的算了，**235 参考太少了**」

理由是**对的**，而且有一条很硬的事实支撑它：E235 那份只有一段 ATO 走行录音，且 §21.10 已经证明
它 2 kHz 以上全是录音笔本底；而京急那份是 **1072.7 s 的"前面展望"（相机架在司机室里）**，
素材量差两个数量级。

### 24.2 ★ 先按 §21.10 的规矩复验京急那份 —— 它**通过**了

`band_levels.py`（停车段 = 本底，运行段 = 信号；都是同一段录音里的片段）：

| 中心 Hz | 停车本底 | 120 km/h | 差 |
|---|---|---|---|
| 100 / 125 / 160 | −41.8 / −40.9 / −38.6 | −25.4 / −24.2 / −21.2 | **+16.4 / +16.6 / +17.4 ⇒ 可用** |
| 200 / 250 / 315 | −37.6 / −38.3 / −40.1 | −21.8 / −22.7 / −27.7 | **+15.8 / +15.6 / +12.4 ⇒ 可用** |
| **400** | −39.9 | −29.3 | **+10.6 ⇒ 可用**（这就是那个主导带） |
| 500 | −39.6 | −32.1 | +7.5 ⇒ 勉强 |
| **630** | −38.8 | −34.2 | **+4.6 ⇒ 就是噪声** |
| 800 | −41.8 | −31.5 | +10.2 ⇒ 可用 |
| 1000~1600 | −36± | −33± | **+2~5 ⇒ 就是噪声** |

⇒ **修正 §20 的两条结论**：那里说"1~1.6 kHz 几乎是空的（1.8%）"、
"2~5 kHz 有 1.27%" —— 按本底法复验，**630 Hz 以上基本是相机/编码器的本底**，
不是列车。京急这份**可用的只有 100~500 Hz 那一段（外加 800 Hz 一带有信号）**。

好消息是：**牵引能量正好就在那一段** ⇒ 作为司机室靶子，这份素材够用。

### 24.3 京急身份 = **GTO**（低载波 / 同步 PWM / 分周阶梯），不是 SiC

新增 [`harmonic_report.py`](../tools/sound-studio/harmonic_report.py)（逐片估 f₁ + 谐波阶梯，
带**连续性约束**）与 `peak_report.py` 的 `--sub`（逐 bin 减停车段功率）。

**实测（不依赖任何假设的那一条）**：加速段**最强移动谱线**从 **168 Hz 单调升到 423 Hz**（12 s），
到 120 km/h 巡航时 ≈ **400 Hz** —— 与 §20.2 独立读到的"30~36 s `400:41%`"一致。

**谐波阶梯**（设 4 极 + 齿轮 5.33 + 轮径 0.86 ⇒ `1.10 Hz/(km/h)` ⇒ 120 km/h 时 `f₁ ≈ 132 Hz`）：

| 时刻（源） | 最强线 | 主导次数 n |
|---|---|---|
| 23 s | 168 Hz | **8** |
| 25 | 192 | 8 |
| 27 | 252 | 7.5 |
| 29 | 272 | 6 |
| 33 | 367 | 5 |
| 36（≈120 km/h） | 400~420 | **3** |

⇒ 加速过程中**主导谐波次数从 8 递减到 3**，而绝对频率仍在上升 ——
这就是"分周阶梯"在频谱上的样子，也正是用户听到的那个**"ドレミファ"**印象的来源。
`400 Hz = 3·f₁` ⇒ 高速段是 **3 分周同步模式**（GTO 的典型终态）。

**与 E235 的差别（这才是换靶的实质）**：

| | E235（SiC） | 京急 2100（GTO） |
|---|---|---|
| 同一速度下的 f₁ | 1.53 Hz/(km/h) | **1.10 Hz/(km/h)（低 28%）** |
| 载波 | **27·f₁ = 1~6.7 kHz** | **3·f₁ ≈ 0.3~0.4 kHz** |
| 能量重心 | 0.16~1 kHz | **0.1~0.5 kHz** |

⇒ 京急比 E235 **整体低约两个八度**。§20.6 里那条"400 Hz 对不上、不该追"的矛盾
**自动消解** —— 因为它本来就是"我们按 E235、靶子是京急"造成的。

### 24.4 ★ 一条必须说清的限制：那份素材是 **128 kbps mp3**

相机/手机录的 mp3，MDCT 窗 ~26 ms ⇒ **频率分辨率 ~38 Hz**；而 f₁ 的谐波间距只有 20~90 Hz。
后果：**阶梯的细节只能当"指示值"**（单纯梳齿搜索会锁到 20~22 Hz 的录音链隆隆上，
实测整段加速量出来 f₁ 几乎不动；加了"f₁ 必须单调上升"的连续性约束才追出上面那条单调曲线）。
⇒ 要用它做**精细定标**（哪一档分周、切换点速度），最好拿到**原始视频/无损音轨**。

   **低载波 + 同步分周阶梯**（按 24.3 那组 n 标定），
   `carrierAmplitude` / `humAmplitude` 按"**400 Hz 主导**"重配（正是 §20.4 那套配平想要的目标）。
2. `cab` 预设的靶子换成**京急实测**（100~500 Hz 平台、400 Hz 主导、125 Hz 偏厚要压）。
3. 重烘 + 渲染 + A/B：**我们的京急 vs 实录京急**。
4. 「距离 / 墙 / 清爽」那套加工**全部保留**（与车型无关），不再动。
5. `SPEC_E235_SIC` / `SPEC_E235_27PULSE` **留在代码里不删**（它没错，只是不再是靶子）。

### 24.6 开工：`SPEC_KEIKYU_2100_GTO` + 第一版 A/B，以及一个**重要修正**

已按 §24.5 落地：`model.mjs` 新增 `SPEC_KEIKYU_2100_GTO`
（4 极 / 齿轮 5.93 / 轮径 0.86 / `table` 载波 175→400 九音 / `asyncEnabled: false` /
`carrierAmplitude 0.30` 让**载波簇当主体**），`bake.mjs` 注册为 `keikyu`。
首烘 `baked/kei1`（27 档，模式 5→3→1 分周），首渲染
`baked/preview-kei/trip-keikyu-v1.ogg`，对照 `baked/preview-kei/AB-keikyu-real-vs-ours.ogg`。

**第一轮三分之一倍频程对照**（我们整趟 vs 实录加速段 21~36 s）：

| Hz | 100 | 125 | 160 | 200 | 250 | 315 | **400** | **500** | 630 | 800 |
|---|---|---|---|---|---|---|---|---|---|---|
| 我们 v1 | 5.40 | 7.30 | 10.17 | 8.74 | 16.11 | **20.81** | 13.38 | **12.94** | 1.63 | 2.22 |
| 实录 | 6.68 | 5.76 | 13.30 | **15.10** | 11.11 | 8.59 | **28.99** | **2.37** | 2.38 | 4.17 |
| 倍 | 0.81 | 1.27 | 0.76 | 0.58 | 1.45 | **2.42** | **0.46** | **5.47** | 0.69 | 0.53 |

**★ 实录的形状不是"低频一片"，而是**：`200:15.1 → 250:11.1 → 315:8.6 → **400:29.0** → 500:2.4`
—— **400 Hz 一个窄带吃掉 29%，紧跟着 500 Hz 断崖（掉 12 倍）**。
这不是电机谱（电机谱是 `n·f₁` 的梳齿、随速度走），这是**车体/司机室的结构共振**：
400 Hz 处一个大峰 + 500 Hz 以上的隔声断崖。它也解释了 §20.2 那条"30~36 s `400:41%`"。

**⇒ 因此修正我在 §24.3 的一个读法**：加速段那条 `168 → 423 Hz` 的"最强移动线"
**不是**载波在爬音阶（那样它到 400 Hz 就该停住、而不是继续涨到 423），
而是**电机的谐波梳齿扫过那个 400 Hz 共振峰**；音阶（175/223/293/390 那几根**互不成整数比**的线）
只出现在**起步最初几秒** —— 也就是说社区那份表"9 个音压在 `f₁ = 0.5~6.5 Hz`"**可能本来就是对的**。
本 spec 里把它改成 `0.5~80 Hz` 的那次"重标"**先留着当实验**，A/B 里两版都要听。

**下一步（顺序已定）**：
1. `cab` 预设的 `conduct` 按实录重做：**+400 Hz 附近一个高 Q 峰**、**≥500 Hz 断崖** ——
   这是"路径"的属性，与车型无关；现在的 `peak 60 +3 dB + lowpass 3100` 完全没有这个形状。
2. 重渲染 + 三轮 A/B：**实录 / 我们的（9 音在起步）/ 我们的（9 音铺满加速）**。
3. 齿轮比 5.33（§20.7 旧估）vs 5.93（社区资料）**仍未定**，差 11% 会让所有频率整体挪。

### 24.7 第 28 轮：**电机必须弱于底噪**、**墙必须只加在电机上**、**起步励磁音**

用户口径（三条，一起给）：

> 「电机声音还是过于大而且直白了，**完全没有距离衰减和墙衰减**，样品中的录音质量还是比较高的。
>   明显速度起来后**电机音弱于底噪**，仅有些中高频电子音」
> 「启动时候细微的**高频励磁音**没了」

**（1）架构错了：底噪原来加在壳子之前** ⇒ 墙/距离**同时**作用在两层上 ⇒ 比例一点不变。
真车里滚动噪声从转向架直接传来、离人更近，电机声要穿地板与车体才到耳朵
⇒ **墙只能加在电机层上**。`preview.mjs` 已改：壳子 → 之后再加底噪 → 最后统一归一。
这一条同时让"底噪层"与"游戏端的独立底噪层"口径一致（§17.6）。

**（2）顺手抓到一个我自己的错**：`bake --shell cab` **烘进了壳子**，而 `preview --shell cab`
**又加了一遍** ⇒ 墙是 **2×18 dB**、静态去刺 **2×3.5 dB**。第一版京急的试听全中这一枪。
（E235 那批没问题：`e24f` 的清单里 `shell: null`。）**烘要干着烘，壳只在渲染/游戏端加一次。**

**（3）墙与距离按用户口径重定**：`distanceM 11`（延迟 **32 ms**）、
`tlDb 10 @ 300 Hz`、`5 dB/oct`、上限 **18 dB**、地板 5 dB；底噪 `levelDb −16 → −4`、低通 `1200 → 800`。

实测层占比：**底噪从 11% 升到 71.9%**（`牵引层 RMS 0.0691 · 底噪层 0.1105`）⇒
"速度起来后电机弱于底噪"这一条**在总能量上已经成立**。

**（4）★ 起步励磁音：实现了，但暴露了架构限制。**
实测（逐 bin 减停车段功率）它是一根 **2097 Hz 的固定线**（不随速度走），
**只存在于起步最初几秒**（f₁≈28 Hz 就没了）——异步 PWM 段的开关频率，
同时带 2 次谐波 4196 Hz（−7 dB）。已加进 spec（`startupExcite`）并**做成共享函数**
（`voiceRecipe` 与 `bake.mjs` 的 `synthesize` 同一份实现，避免"模型说一套、烘出来另一套"）。

生成是对的（烤好的循环里确认：f₁=7.27 Hz 那档，**2094 Hz、幅度 0.152**，是第二强的分音）。
**但它进了"循环"就被当成 f₁ 的谐波一起变调**：播放时随 rate 挪到 **2172 Hz**，
而且加速中 f₁ 每片都在变 ⇒ 这根线在一秒的窗里**扫开成一条 40~80 Hz 宽的带**，
听起来是"嘶"而不是"哨"。**而实录里它是固定频率、锐利的一根。**

⇒ **它不能是一个"循环层"**，必须像齿轮层那样**单独成层**：固定频率合成、
只按速度门控（`f₁ < 20 Hz`），不参与任何变调。
`preview.mjs` 里加一层即可；游戏端也已经有独立齿轮层的先例可循。
**这一条是本轮最明确的下一步**，我没有在这轮擅自动这一层（它是新增一层，要动渲染与游戏两端）。

产物：`baked/kei4`（**干烘**，27 档）、`baked/preview-kei/trip-keikyu-v6.ogg`、
`AB-startup-real-vs-v6.ogg`（起步：实录 ↔ 我们）、`AB-cruise-real-vs-v6.ogg`（巡航：实录 ↔ 我们）。
自检 139/0。

### 24.8 第 28 轮（续）：励磁音**不会消失**，以及**一层被漏掉的中高频**

用户两句：「正常起步励磁音是**连续**的，怎么这个很短促？」
「并且励磁高频**不会消失**，我认为是不是还有一些**中高频音我们没有考量到**？」

**（1）"短促"的根因是层的位置错了**：它原来被烘进**牵引循环**，而循环是要变调的 ——
2097 Hz 那根线于是被 playbackRate 挪到 2172 Hz，加速中 f₁ 一秒一变，
**扫开成 40~80 Hz 宽的带**，听起来是"嘶"不是"哨"。
⇒ 已改成**播放端单独一层**（`preview.mjs` 的起步励磁层）：固定频率、连续、不参与变调，
只按速度门控，且加在壳子之前（照常走墙/距离 —— 它也是从车外进来的）。
改完实测：`2097 Hz` 在 2.0~2.2 kHz 里是**最强**的一根，邻居低 **15.5 dB**（实录是 9 dB）✔ 锐利了。

**（2）★ 励磁音**不只在起步**——用户对，我上一轮的门控是错的。**
补测了录音的**巡航段**（源 150/300/450/600 s 各 20 s），逐 bin 减停车段功率：

| 源时间 | 800~6000 Hz 里最强的几根 |
|---|---|
| 150 s | 904 / 921 / 912、**1386 / 1394**、826 |
| 300 s | 813、**1386 / 1397 / 1435 / 1443**、1373 |
| **450 s** | 818 / 824、**2097（−13.7 dB）** ← 巡航段它**还在** |
| 600 s | 1903、937、1499、1117 / 1125、2492 / 2536 |
| 56 s | 802、918 / 907 / 929、1136、1459 / 1408 / 1351 |

⇒ 两件事：① 2097 Hz 是**持续**的（开关/纹波，只要励磁就在）⇒ 门控已去掉；
② 800~2500 Hz 有一整层**持续**的线 —— 这就是"没考量的中高频"。

**（3）模型里确实缺一整簇：`2f_c / 3f_c / 4f_c …`。**
`voiceRecipe` 从来只发 `f_c ± n·f₁`（载波两侧的边带），**从不发载波自己的高次谐波**。
已补 `carrierHarmonicPartials()`（**共享函数**，`voiceRecipe` 与 `synthesize` 同一份实现）
+ `carrierHarmonicCount: 6` / `carrierHarmonicDecay: 0.32`，并把边带数 `5 → 9`、衰减 `1.6 → 2.4`。

**（4）★ 但还是差 10~30 倍 —— 瓶颈已经不在模型，在"路径"。**
把 `trip-keikyu-v9` 与实录巡航段（源 300 s）逐带比：

| Hz | 250 | 315 | 400 | 500 | 630 | 800 | 1000 | **1250** | **1600** | **2000** | **2500** |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 我们 v9 | 15.30 | 12.85 | 8.35 | 5.66 | 2.81 | 1.48 | 0.60 | **0.21** | **0.06** | **0.05** | **0.01** |
| 实录 | 15.77 | 5.05 | 6.12 | 1.82 | 2.78 | 2.37 | 1.45 | **3.72** | **2.04** | **0.68** | **0.33** |
| 倍 | 0.97 | 2.55 | 1.36 | 3.12 | 1.01 | 0.63 | 0.41 | **0.06** | **0.03** | **0.08** | **0.02** |

⇒ **100~630 Hz 已经对得很齐**（0.97~1.36，除 315/500 偏厚），
但 **1.25~2.5 kHz 我们少 10~30 倍**，而实录在那里有 **≈7% 的能量**（一个宽驼峰，峰在 1.25 kHz）。
两个原因都得动：
1. **墙太狠**：现在 `10 dB @300 Hz / 5 dB/oct / 上限 18 dB`，到 1.25 kHz 已是 18 dB，
   再加去刺 3.5 dB ⇒ 整段中高频被压掉 21 dB。**而实录从 250 Hz 到 1250 Hz 只低约 6 dB。**
   本轮为了"电机必须弱于底噪"把它调狠了 —— 那件事**应该只由电平配比解决**（底噪 −4 dB 已经做到 69.5%），
   不该由墙的斜率去解决。**下一个动作就是把它放回来**（上限 ~10~12 dB、斜率 ~3.5）。
2. 模型里 `humLowpassHz: 900` 与各簇的衰减指数也把中高频削得快，要和墙一起重配。
