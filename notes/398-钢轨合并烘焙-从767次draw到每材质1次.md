# 398 钢轨合并烘焙 —— 从每帧 767 次 draw 到每个材质 1 次

> 用户口径（2026-10-05）：「我的想法是能不能使其和常规方块一样进行单次加载？并且在修改时更新渲染就行了」

前置：notes/397（逐实例视锥剔除）只拿到 10–17%，**远低于预估的 40–60%** —— 那条路的天花板就在那里：
draw 次数是**结构性**的，不管怎么剔，只要"一个实例一次 draw"，剩下的就全是白花。

本笔记记的是把那个结构换掉。

---

## 0 先回答用户的问题：能，而且不需要"一个实例一个方块"

用户问的是"能不能像常规方块一样**只加载一次**、只在改动时更新"。原版方块能那样，是因为它**建区块网格**：
上千个方块合成一个 VBO，一个 section 一个 draw，光照更新才重建。

MTR 对钢轨**从来没有这一步**：世界里只有 `BlockNode` 方块，钢轨本体是引擎里的
`Rail`（两个节点 + 两端朝向 + `Shape` + `RailMath` 曲线），客户端每帧沿曲线现算 200 个实例。
所以"像方块一样"不需要真的放方块 —— 需要的只是**补上"建网格"这一步**，而且钢轨天然满足它的前提：
**静止，只在玩家编辑线路时变**。

### 决定性的三件事（都是反汇编映射库确认的，不是推断）

1. **draw 次数 == queue 进去的 `VertexArray` 个数。**
   `BatchManager.queue(List<VertexArray>, state)` → `forEach` → 每个 `VertexArray` 一条 `RenderCall`；
   `RenderCall.draw()` → `vertexArray.bind(); state.apply(); materialProperties.vertexAttributeState.apply(); vertexArray.draw()`。
   而 `VertexArray.draw()` 是 **`glDrawElements`，非 instanced**（字节码确认）
   ⇒ **实例化这条路是堵死的，只有"合并成一个大网格"能减 draw。**
2. **`OptimizedModel` 的构造口是公有的。**
   `public OptimizedModel(List<VertexArray>)`、`public VertexArray(Mesh, VertexAttributeMapping)`、
   `public VertexAttributeMapping.Builder set(type, source)`、`RawMesh(MaterialProperties)` / `addVertex` / `applyMatrix` /
   `append`、`RawModel.append(RawMesh)` / `getRawMesh` / `upload(mapping)`、连 `Vertex(Vertex)` 和 `Face(Face)` 拷贝构造都有。
   **一行映射库代码都不用改、不用重编译那个预编译 jar。**
3. **光照可以逐顶点，而且本来就是。**
   `OptimizedModel.DEFAULT_MAPPING` 里 `UV_LIGHTMAP → GLOBAL`（每 draw 一个常量）—— 但那只是 MTR 的默认值，
   映射是我们自己造的。改成 `VERTEX_BUFFER` 后：
   - `VertexAttributeType.UV_LIGHTMAP` 是 **location 4、`GL_SHORT`×2、`iPointer=true`** —— 正是原版
     `rendertype_entity_*` 里 `in ivec2 UV2` 的槽位与类型；
   - `PatchingResourceProvider` 只给原版 entity 着色器打 `ModelMat` 补丁（插 `in mat4 ModelMat;`、
     把 `Position` 换成 `(MODELVIEWMAT * ModelMat * vec4(Position,1.0)).xyz`），**没动 `UV2`**；
   - `VertexAttributeState.apply()` 对光照用的是 **`glVertexAttribI2i`（整数属性）**，不是 `glVertexAttrib2f`
     —— 又一次证明着色器声明的是 `ivec2`。

   ⇒ 我上一轮（口头）判断的"最大的技术障碍"，**是错的**。不需要按光照值分组。

## 1 做法

```
取源几何（RawMesh）           ← StoredModelResourceBase.onObjModelsReady 交接点
  ↓ 沿曲线走一遍，把每个实例的变换烘进顶点（顶点存"本轨局部坐标"）
按材质合桶 → upload(VERTEX_BUFFER 光照映射) → 一个材质一个 VertexArray
  ↓ 缓存起来，每帧只 queue 一次：ModelMat = 纯平移(本轨原点 − 相机位置)
```

### 为什么顶点存"本轨局部坐标"

不能把世界坐标直接烘进 float 顶点：float 在 30000 附近的分辨率约 **0.002 m**，大世界里钢轨会抖。
所以顶点 = `世界 − 本轨 AABB 最小角`，每帧 `graphicsHolder.translate(origin - offset)`。
`origin - offset` 在 **double** 上算完才交给 `translate` ⇒ 精度与原版相机相对渲染同级。

### 为什么不能烘"视锥内的实例"

烘进去的是**整根轨的全部实例**。相机一动就重建等于白干。
粗一级剔除仍由 `railWrapper` 的整轨 AABB 承担（`occlusionCullingInstance`），细一级交给 GPU 裁剪。
代价是放弃了 notes/397 那 10–17% 的逐实例剔除 —— **用 10–17% 的几何换 99% 的 draw，值**。

### 失效只有两个来源

| 来源 | 判据 | 代价 |
|---|---|---|
| **几何** | 键 = `resource 身份 + rail.getHexId() + style + 本轨 AABB` | 节点被改 = 另一个键，天然失效 |
| **光照** | 每帧最多复检**一根**轨（轮转），比光照哈希 | 天空光/方块光是**离散档位**，实际重建次数远低于"每帧" |

配套：每个 pass 最多重建 2 根；标脏后**继续画旧的**（宁可光照过时一帧，也不要钢轨闪掉）；
缓存上限 96 项，超了按"最久没用"淘汰并**释放 GL 资源**。

## 2 几个必须记下来的坑

1. **`RawMesh.addVertex` 会每 4 个顶点自动补一个 Face。**
   克隆**不能**用它 —— 要直接 `clone.vertices.add(...)` / `clone.faces.add(...)`，
   再把整块交给 `RawModel.append(clone)`（它才会正确平移面索引）。用 `addVertex` 会在源网格不是纯四边形时静默出错。
2. **源网格要"存引用"而不是"立刻快照"。**
   `fromObjModels` 会对每个 `RawModel` 跑 `generateNormals()` + `distinct()`。
   在它之前快照，拿到的法线可能是**全零**，而 `RawMesh.upload` 会对法线做 `normalize()`
   ⇒ 零向量归一化 ⇒ 光照全坏。所以 `onObjModelsReady` 只存引用，真正读在烘焙时。
3. **`Vertex(Vertex)` 是深拷贝**（`Utilities.copy` 位置与法线）—— 已字节码确认，就地改源网格才是安全的反面。
4. **新烘出来的项必须立刻写 `lastUsedFrame`**，否则它以 0 排在 LRU 队首，可能下一帧就把一个**正在用**的模型淘汰掉。
5. **`OptimizedModel$ObjModel.rawModel` 是私有的、映射库没给 getter** —— 反射是唯一一条路。
   它必须**能失败**：拿不到就整条停用、回退逐实例渲染，绝不让钢轨消失。
   `-Dmmtr.railbake=false` 也能整条关掉。
6. **烘焙绝不能走 `beginReload()/finishReload()`** —— 那是 `ShaderManager.reloadShaders()`，
   正是现在 400 ms 级卡顿的元凶（模型 60 s 过期重建）。
   ⚠️ **但这半句话当初写的太满，实机第一次跑就翻车了 —— 见 §10。**

  ｜ 拆分：钢轨 draws=6.0(1.00批)  非钢轨 draws=284.0(11.00批)

| | 改前 | 改后 |
|---|---|---|

| 总 draws/pass | 949 | **290** |

`200 个实例 → 1 个材质` 正是 §8/§9 离线算出来的值（钢轨模型 `groups=[obj1]`、`mtl=0 chars` ⇒ 恰好一个材质）。

**错在哪：那 5.08 ms 的 submit 里本来就只有一部分是钢轨。** 实测（同一次会话、取"相机不动"的窗口）：

|---|---|---|---|

| `shadow.submit` | 2.00 | 1.19 | −0.81 |

⇒ **省下来的是 1.91 ms/帧，不是 5 ms。** 659 根钢轨 draw × ~2.9 µs ≈ 1.9 ms —— 与"每 draw 约 2.9 µs"吻合。
而改后 290 个 draw 里 **284 个是车辆**，所以 submit 还剩 2.72 ms。

### ⚠️ 那份 60 FPS vs 41 FPS 的对比**不成立**

两个窗口的相机不在同一个地方：

| | 相机 | `vehicles` |
|---|---|---|
| 改前 19:15:40 | `(879.8, 75.4, 1803.5)`（静止） | 0.04 ms/帧 |
| 改后 19:24:47 | `(943.2, 67.6, 1812.5)` → 之后一路移动 | 3.63 ms/帧 |

**同场景外推**：改前 15 ms（60 FPS）的帧里去掉 1.91 ms ⇒ 约 13.1 ms ⇒ **约 76 FPS**。
（这是外推，不是实测 —— 要坐实得让相机回到同一个位置各测一次。）

## 4 回退路径

| 情况 | 行为 |
|---|---|
| `-Dmmtr.railbake=false` | 全量回退逐实例渲染 |
| 反射拿不到 `rawModel` | 自动停用 + 记一条 WARN，全量回退 |
| 烘焙/解算**抛异常** | 当次退化成回退；连续 `MAX_BAKE_FAILURES=5` 次后自动停用整条（防止每帧刷日志 + 每帧白算） |
| 资源**暂时**取不到源几何 | 这一帧回退逐实例渲染；下一帧再试（**不留永久标记、不消耗预算**） |
| 本 pass 烘焙预算用完 | 当帧回退逐实例渲染（所以**钢轨永远不会不画**） |
| `OptimizedRenderer.hasOptimizedRendering() == false` | 直接返回 null ⇒ 回退路径会走 `dynamicVehicleModel`，与改前一致 |

逐实例路径**原样保留**在 `RenderRails.renderRailStandard` 里，不是删掉重写。

### ★ 为什么"异常必须兜住"是硬要求（notes/396 的教训）

`MmtrRailMeshCache.get()` 跑在**渲染线程的主链**上：

```text
MainRenderer.render → RenderRails.render → renderRailStandard → get → bake
                     ↓（异常穿出去的话，下面全都不跑）
                     RenderLifts / RenderRails 剩余部分 / 队列派发 / MmtrLightField.beginFrame / 批次提交
```

所以症状**不是"掉几帧"，而是"钢轨乃至更多东西整片消失"**。
2026-10-05 已经因为这个踩过一次：一个面板签名的 NPE（`MmtrFaceDocument.collectReferencedFields`
在 `pages == null` 时抛）正好撞在 `RenderVehicles` 里，结果 `RenderRails` 一次都没跑到 —— 现象就是"铁轨没了"。

因此 `get` 与 `bake` 各套了一层 try/catch，任何失败都退化成"返回 null / 返回旧的"，
**绝不向上抛**。停用后日志里会带状态后缀，一眼能看见。

## 6 离线等价性校验（**可复跑**，不依赖游戏）

「只改性能、不改画面」这句话必须能证。烘进顶点的是**矩阵**，所以判据就是：
烘焙路径算出来的顶点，和改前逐实例路径算出来的顶点，是不是同一个点。

工具：`sandbox/railbake-verify/VerifyRailBake.java`（工作区外，不入库）。跑法：

```powershell
$jdk  = "$env:USERPROFILE\.gradle\jdks\eclipse_adoptium-21-amd64-windows.2"
$joml = (Get-ChildItem "$env:USERPROFILE\.gradle\caches\modules-2\files-2.1\org.joml\joml\1.10.5" -Recurse -Filter "joml-1.10.5.jar" | Select-Object -First 1).FullName
$dir  = "sandbox\railbake-verify"
& "$jdk\bin\javac.exe" -cp $joml -d $dir "$dir\VerifyRailBake.java"
& "$jdk\bin\java.exe" -cp "$joml;$dir" VerifyRailBake
```

**结果（20 万随机实例，世界坐标 ±30000，相机 0–256 m）：**

| 量 | 结果 |
|---|---|
| 旋转部分 3×3 | **0.000e+00，逐位相同 200000/200000** |
| 法线 | **0.000e+00** |
| 相机相对顶点位置残差 | ≤ **0.0191 mm**（< 16 m 段 0.0181、16–64 m 段 0.0191） |

残差不为 0 是**故意的计量口径**：改前把 `mid − 相机` 一次成形，改后是
`float(顶点 = R·v + (mid − 原点))` 再 `translate(原点 − 相机)` —— 两次 double→float，比改前多一到两次舍入。
100 m 量级上 float 分辨率就是 7.6e-6 m，所以 1.9e-5 m 正是舍入量级。
钢轨截面约 60 mm ⇒ 0.019 mm 是它的 **0.03%**，任何视距下都看不出来。

### 校验过程中自己的两个错量法（记下来免得再犯）

1. **拿两个矩阵逐元素比。** 它们的平移列本来就差一个"本轨原点"（几万），比出来必然 3e4 —— 有意义的是旋转部分。
2. **把世界坐标算出来再相减。** 在 `|x|≈30000` 上用 float 累加，分辨率 0.0039，量到的是量化不是误差。
   **渲染器从不在那个量级上做 float**：两条路径都先在 double 上减掉相机位置。

## 7 顺带挖出来的**既有**渲染问题：近水平钢轨的 pitch 被量化掉了

这不是本次改动的产物，是**改前就存在**的 —— 但找等价性的时候撞上了，必须记下来，因为它是"看起来像 bug 的正常行为"。

Minecraft 的旋转链（反汇编 `net.minecraft.util.math.RotationAxis` 确认）：

```text
MatrixStack.multiply(Quaternionf)  →  Matrix4f.rotate(quaternion)
RotationAxis.POSITIVE_X.rotation(f)  →  new Quaternionf().rotationX(f)     ← 注意是 rotationX
RotationAxis.rotationDegrees(f)      →  rotation(f * 0.017453292f)
```

而 JOML 的轴专用四元数构造走 `cosFromSin`（`w = ±sqrt(1 − sin²)`）。钢轨的 X 角**恒为**
`ax = π − pitch`（轨道近水平，pitch 极小），于是 `sin(ax/2) → 1`、`1 − sin²` 落到 float 的
**非规格化尾巴**上：

| pitch (rad) | 解析 `m12 = −sin(ax)` | 实际（走四元数） |
|---|---|---|
| 0 | +8.74e-08 | **0**（被舍掉） |
| 4.88e-04 | −4.8819e-04 | **0（整个 pitch 没了）** |
| 2.00e-03 | −2.0000e-03 | −1.9531e-03（= 2⁻¹⁰，误差 2.3%） |
| 1.00e-02 | −9.9997e-03 | −1.00067e-02（误差 6.9e-06） |

⇒ **MTR 现在画的钢轨，在 pitch ≲ 5e-4 rad 的近水平段是完全没有俯仰的**，而且小 pitch 上有量化台阶。

**本次改动不动它。** 我一开始写的是 JOML 的 `rotateX/rotateY/rotateZ` 欧拉链，那样反而**更准**
（最多差 0.73 mm），但那就顺手改了画面 —— 违背"只改结构"的前提。
最终改成复刻 MC 的 `new Quaternionf().rotationX(...)` 调用，做到**逐位一致**（见 §6）。
要修 pitch 量化，**另开一片**，并且要知道它会改变现有观感。

## 8 合并本身的运行时校验（驱动**真实的**映射库类）

§6 证的是"顶点位置对不对"，这里证的是核心论断本身：
**N 个实例 × 1 个材质 ⇒ 恰好 1 个 VertexArray ⇒ 恰好 1 次 draw。**

字节码已经把这条链的每一环读死了（`RawModel.append` 按 `MaterialProperties` 合桶、
`RawModel.upload` 每个带面的 `RawMesh` 造一个 `VertexArray`、
`BatchManager.queue(List,…)` 每个 `VertexArray` 建一条 `RenderCall`、
`RenderCall.draw()` 一次 `glDrawElements`），但**跑一遍**才排除"我读漏了"。

工具：`sandbox/railbake-verify/VerifyMerge.java`。它驱动的是真类
（`RawMesh` / `RawModel` / `MaterialProperties` / `OptimizedModel$ShaderType`），只跳过最后的
`upload()` —— 那一步要建 GL buffer，离线跑不了；所以判定用 `upload()` 的同一个判据
（`hasFaces()` 的 mesh 数 = VertexArray 数 = draw 数）。

**难点是 classpath**：`MaterialProperties.<clinit>` 会牵出 MC 的 `Util`，逐个 jar 试是死路。

## 9 自造顶点映射的校验（驱动**真实的** `VertexAttributeMapping$Builder`）

"逐顶点光照"这条路 MTR 自己从没用过（它一直把 `UV_LIGHTMAP` 定成 `GLOBAL`），所以这是全片**唯一
无法靠"和 MTR 对比"来确认**的一环 —— 必须直接验这个映射本身。

工具：`sandbox/railbake-verify/VerifyMapping.java`（同一个 classpath 技巧）。

**① 与 `OptimizedModel.DEFAULT_MAPPING` 的差异只有一格**

```
差异项数 = 1        UV_LIGHTMAP  GLOBAL → VERTEX_BUFFER
```

**② 顶点缓冲布局自洽**

| 属性 | location | GL 类型 | 分量 | 偏移 | 字节 | iPointer |
|---|---|---|---|---|---|---|
| POSITION | 0 | `GL_FLOAT` | 3 | 0 | 12 | false |
| UV_TEXTURE | 2 | `GL_FLOAT` | 2 | 12 | 8 | false |
| **UV_LIGHTMAP** | **4** | **`GL_SHORT`** | **2** | **20** | **4** | **true** |
| NORMAL | 5 | `GL_BYTE` | 3 | 24 | 3 | false |

首尾相接、无空洞无重叠、`27 + padding(1) = stride 28`、**4 字节对齐** ✓

**③ 最关键的一条：预留的字节数 == 实际写入的字节数**

`RawMesh$lambda$upload$6` 对 `UV_LIGHTMAP` 写的是 `ByteBuffer.putInt(vertex.light)` = **4 字节**；
`UV_LIGHTMAP.byteSize` = `size(2) × GL_SHORT(2)` = **4 字节**。**一致** ⇒ 不会错位。
再加 `location=4` / `GL_SHORT` / `iPointer=true` / `normalized=false`，与着色器里的 `in ivec2 UV2` 完全同槽同格式。

### ⚠️ 这个测试纠正了我一个**错的假设**：顶点变宽了

我一开始断言"stride 应当和 `DEFAULT_MAPPING` 一样"。**错的。**
把光照放进顶点缓冲，顶点格式必然变宽：

```
每顶点 24 → 28 字节（+16.7%）    ← 逐顶点光照的固定代价
```

所以 §2/§5 里"每根轨常驻显存"的估算要跟着涨 ~17%（原估 100 根 × 200 段 ≈ 30 MB ⇒ 约 **35 MB**）。
`MAX_ENTRIES = 96` 的上限因此更重要，不能只想着 draw 数。

**判定：全部通过（exit 0）。**

## 10 实机第一次跑：**烘焙全部失败**，以及"建 GL 对象"真正需要什么

2026-10-05 19:10，客户端重启后第一次实机。日志：

```text
[19:10:15] [Render thread/WARN] [MMTR-RAILBAKE] 烘焙钢轨模型时抛异常（第 1 次，共 5 次后停用）
[19:10:27] [MMTR-RAILBAKE] 窗口 300 帧：新建烘焙 0 次 … ｜ 状态：烘焙连续失败 5 次，已自动停用（逐实例渲染）
```

堆栈（关键三行）：

```text
java.lang.IllegalStateException: GlStateTracker: Not protected
  at GlStateTracker.assertProtected(GlStateTracker.java:59)
  at VertexBuffer.bind(VertexBuffer.java:24)
  at VertexAttributeMapping.setupAttributesToVao(VertexAttributeMapping.java:58)
  at VertexArray.<init>(VertexArray.java:26)
  at RawModel$lambda$upload$0(RawModel.java:20)
  at RawModel.upload(RawModel.java:18)
  at MmtrRailMeshCache.bakeInner(MmtrRailMeshCache.java:438)
```

### 根因

**建 `VertexArray` 必须在 `GlStateTracker` 的"保护区"里。** 这不是可选优化，是硬前提：
`VertexBuffer.bind()` 第一件事就是 `assertProtected()`，不在保护区里直接抛。

`GlStateTracker` 保护的是 VAO / `GL_ARRAY_BUFFER` / `GL_ELEMENT_ARRAY_BUFFER` 三个绑定 + 当前 shader
（`capture()` 逐个 `glGetInteger` 存下来，`restore()` 还原并 `enableCull()` + `depthMask(true)`）。

**而 `OptimizedRenderer.beginReload()` = `reloadShaders()` + `capture()`** —— 我之前只盯着前一半，
把后一半当成"建 VBO 只是 glGenBuffers，不需要它"给否掉了。**那半句是错的。**

### 难处：不能直接用 `beginReload()`，也不能盲目 `capture()+restore()`

| 事实（都是字节码确认的） | 后果 |
|---|---|
| `ShaderManager.reloadShaders()` = 关掉旧 program → `clear()` → `loadShader` × 3 | 每次调用**重新编译 3 个着色器程序** ⇒ 绝不能按需调 `beginReload()` |
| `GlStateTracker.isStateProtected` 是**一个布尔量，不是嵌套计数** | `capture()` 已保护时**直接 return**（幂等）；`restore()` **无条件**清保护位 |
| ⇒ 盲目 `capture()+restore()` 会拆掉**外层**已有的保护区 | 害得 MTR 自己后面建 buffer 抛异常 —— 比不优化更糟 |

所以正确做法是**只拿 `beginReload()` 的后一半**，并且先问一句"已经受保护了吗"：

```java
final boolean alreadyProtected = isGlStateProtected();   // 反射读私有静态布尔
if (!alreadyProtected) {
    GlStateTracker.capture();
}
try {
    return action.get();        // merged.upload(MAPPING)
} finally {
    if (!alreadyProtected) {
        GlStateTracker.restore();   // 谁开的谁收，绝不越权
    }
}
```

反射拿不到 `isStateProtected` 时**直接把整条烘焙停用**，而不是"当作已保护"：
猜错的后果不对称 —— 当作 true 只是回到不优化，当作 false 会破坏别人的保护区。

### 这一轮真正救场的是**第 3 轮加的那两条 try/catch**

实机失败时**没有崩、钢轨也没有消失**：`钢轨 draws` 回到改前的 624–671，画面正常。
如果没有那两层兜底，异常会从 `RenderRails.render` 穿出去 —— `MainRenderer.render` 里
`RenderRails` 之后的队列派发 / 光场 / 批次提交全都不跑。**（`GraphicsHolder.createInstanceSafe`
会兜住不让游戏崩，但那意味着每帧的剩余渲染都被跳过。）**

⇒ "异常必须兜住"不是防御式编程的习惯，是这条链上**必须有的结构**。

### 复验：两处反射假设

`VerifyReflection.java`（只读静态字段、不碰 GL，可离线跑）：

| 断言 | 结果 |
|---|---|
| `OptimizedModel$ObjModel.rawModel`：private final、类型 `RawModel`、实例字段 | ✓ |
| `GlStateTracker.isStateProtected`：private static boolean、**初值 false** | ✓（正好印证"确实需要我们 capture"） |
| `capture()` / `restore()` / `assertProtected()` 都是 public | ✓ |

### 为什么"在帧中间 capture/restore"是安全的 —— MTR 自己每帧都在干

这条很关键，因为我们的调用点在 `RenderRails.render()`（帧中间），而 MTR 原来只在资源加载时用。
反汇编 `OptimizedRenderer.render(boolean)`：

```java
if (shaderManager.isReady()) {
    GlStateTracker.capture();
    batchManager.drawAll(shaderManager, renderTranslucent);
    GlStateTracker.restore();
}
```

**这就是 `MainRenderer.render()` 最后那一步 `OPTIMIZED_RENDERER_WRAPPER.render(...)`，每个视觉帧都跑。**
⇒ 结论有三条：

1. `capture()`/`restore()` **本来就是帧中间的常规操作**，不是只能用在资源加载；
2. `restore()` 的那几个副作用（`RenderSystem.setShader(...)`、`enableCull()`、`depthMask(true)`）
   **本来每帧就已经发生一次** ⇒ 我们多调一次不会引入新的状态风险；
3. MTR 的用法也是"capture → 干活 → restore"**不嵌套** —— 我们那个 `alreadyProtected` 判断
   正是为了守住同一条纪律（唯一区别：别人已经开着保护区时，我们什么都不碰）。

### 顺带修正一处细节

保护是给**建/绑**用的，不是给画用的：

| 调用 | 要不要保护 |
|---|---|
| `VertexArray.<init>` → `setupAttributesToVao` → `VertexBuffer.bind()` | **要**（`assertProtected`） |
| `VertexArray.bind()` / `VertexArray.unbind()` | **要**（`assertProtected`） |
| `VertexArray.draw()` → `glDrawElements` | **不要**（直接画） |
| `VertexArray.close()` → `glDeleteVertexArrays` | **不要**（只查是否在渲染线程） |

⇒ 我们的保护区**只需要罩住 `merged.upload(MAPPING)`**，画和淘汰都不用管。

## 11 第二个坑：`UNBAKEABLE` 哨兵会**永久毒住**懒加载还没到位的键

**发现方式：读数对不上。** 实机日志里

```text
[MMTR-RAILBAKE] 窗口 300 帧：新建烘焙 0 次 … ｜ 缓存 9/96 项 … ｜ 状态：烘焙连续失败 5 次，已自动停用
```

**缓存 9 项，却只报了 5 次失败。** 差的那 4 项一次异常都没抛过 —— 说明它们走的是
`sourceMeshesOf(...) == null` 那条**静默**分支（`bakeInner` 直接 `return previous`，不计数），
然后被我原来的代码记成了"这根轨这个样式永远烘不了"。

**但那 4 项并不是真的烘不了**：本机只有**一个**钢轨模型 `mtr:models/rail/rail.obj`
（日志 `loading model mtr:models/rail/rail.obj: obj=5110 chars, mtl=0 chars, groups=[obj1]`），
它是 OBJ、只有一个 group ⇒ 一个材质 ⇒ 完全可烘。

真正的原因是**源几何是懒加载的**：`RailResource.getBakeSourceObjModels()` 只有在
`load()` 跑过之后才有值，而 `load()` 是第一次真正用到这个资源时才触发的。
于是"第一帧跑到这里时还没 load 完"的那些键，**被一个永久标记钉死了**。

### 为什么这个 bug 值得单独记

它有两个后果，第二个比第一个严重得多：

1. **少烘几根轨**（这一帧本可以下一帧烘）；
2. **把烘焙预算吃光**。每 pass 只允许烘 `MAX_BAKES_PER_PASS = 2` 根，而
   `bakesThisPass++` 原来发生在"检查有没有源几何"**之前** ⇒
   每帧开头那几个"永远烘不了"的样式先把 2 个名额占掉，**同一帧里真正能烘的轨永远轮不到**。
   症状会是"优化时灵时不灵、看视角而定"，极难查。

### 改法

删掉 `UNBAKEABLE` 哨兵，改成**每帧一次廉价的空检查**，并且放在**消耗预算之前**：

```java
if (!hasBakeSource(railResource)) {
    return null;          // 这一帧回退逐实例渲染：不消耗预算、不留永久标记
}
if (bakesThisPass >= MAX_BAKES_PER_PASS) { ... }
bakesThisPass++;
```

`hasBakeSource` 只是两个空检查（外加一次反射字段读）—— 每帧做也不花钱。
**"便宜的判断可以每帧重做；只有贵的操作才需要缓存"** —— 这条比"缓存一切"更安全，
因为缓存一个可能过期的**否定**结论，代价是永久失效。

（这一次是**读数内部不自洽**抓出来的，不是靠看代码。所以那行 `缓存 N/96 项` 和
"失败次数"要并排看。）
