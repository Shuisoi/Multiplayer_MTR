## 1 结论

站定客流的"长什么样"不再由客户端在运行期派生，而是**离线烘一次**：

```
run/resourcepacks/HumanEra_Villagers.zip（输入，只读）
   ├─ assets/minecraft/optifine/cem/villager.jem       几何（32 盒，成年用 28）
   └─ .../textures/entity/villager/{,type/,profession/,profession_level/}  99 张贴图
        │  python mmtr/tools/crowd-bake/bake_crowd.py
        ▼
game/fabric/src/main/resources/assets/mtr/
   ├─ crowd/crowd_mesh.json        28 盒（脚 y=0、x/z 居中、含膨胀）+ 每面 uv 矩形
   ├─ crowd/crowd_tiles.json       图集尺寸 + 99 块落点 + 四个组别下标表
   └─ textures/crowd/crowd_atlas.png   1188×1452 图集（219 KB）
        ▼
运行期：MmtrCrowdStatues 载入这三份 → 扫附近的 crowd_seat_* 格 → 每帧按格子画人
```

**不写盘、不重载、不反射、不录渲染、不反推盒子**。整包资源 245 KB（旧派生包 11.58 MB）。

## 3 四个"照抄 vs 想当然"的地方（都实测钉死了）

1. **`sizeAdd` 必须加**（原版 `Cuboid` 的 Dilation，六面各外扩）：派生真值里每个盒子都比声明尺寸大
   `2×sizeAdd×0.9375`；衣服层正是靠这个膨胀避免共面闪烁。**uv 展开仍用声明尺寸**（膨胀不改 uv）。
   [check_dilation.py]
2. **`bone2` 的 `rotate: [90,0,0]` 必须做**：不做的话那块"帽子边"是竖着的板，整体高度 40 单位；
   做了之后是 y 向厚 1、xz 各 15 的横板，中心 (0,25.80,0) —— 与真值逐位吻合。
   语义 = **绕该部件自己的原点转，translate 不参与旋转**。
3. **成年只画 `head2` 支**：`head3`/`bone3` 是幼年"大头"，jem 的动画表用 `if(is_child, 0, 69420)`
   把它们移走（69420 单位 = 看不见）；硬塞进去会让脑袋整片 z-fighting。
4. **贴图层的正确集合是 `底皮 + type + profession + level`**（照抄实体渲染器的层）：
   实测底皮在外套区几乎全透明（`villager10.png` 11/384、`aaaaa.png` 0/384）——
   **只画底皮 = 裸体**。所以画四层（同一套四边形，各配自己的贴图块）。

## 8 回退「座位方块」，并把雕像看不见的根因修掉（2026-10-11）

### 8.1 口径回退：标记方块自己就是计划载体

用户口径（原话）："标记方块依旧需要原本的逻辑啊，我们只不过是查询标记方块并生成村民模型。"

于是**删掉"标记 ⇄ 座位"这条换方块的支路**：{@code crowd_seat_1/2} 不再由生成器写入，
"这一格站着人"写回**标记自己的 {@code occupied}**（{@link BlockCrowdMarker#OCCUPIED}，
2026-10-10 之前就是这个口径，那一版被"1024 个状态会把方块属性表撑爆"的顾虑带偏了 ——
实际撑不撑爆与"要不要人"无关：姿势/外观本来就该由格子坐标哈希算，不该进方块状态）。

| 件 | 现在 |
|---|---|
| 铺人 / 收人 | {@code world.setBlockState(cell, BlockCrowdMarker.withOccupied(state, true/false))} —— 方块种类与摆放朝向**不动** |
| 计划载体 | 标记方块（`crowd_mark_1/2`），服务端重启、区块重载都读得回来 |
| 客户端判定 | `BlockCrowdMarker.isOccupied(state)` 的格子 = 有一个人 |
| 手势现形 | `RenderCrowdMarker` 回到原样：手持任意一种标记方块 ⇒ 全部标记现形（贴地色块 + 十字矮柱） |

**过渡（本轮保留，下轮删）**：老存档里已经铺下去的座位格要能认出来并迁回标记 ——
`BlockCrowdMarker.isLegacySeat` / `kindOf`（座位也算标记）与 `BlockCrowdSeat` 三个类暂时留着，
`applySeatOp` 遇到座位格就写成"同种类的标记 + `occupied`"，世界扫干净后一起删
（`crowd dump` 的"雕像格台账"里不再有座位格时就是干净了）。
本轮没删的原因：那些格子里有用户手放的**几百个标记**，删了方块类它们会直接变成空气。

### 8.2 雕像一个都看不见的根因：图集 Identifier 少了前缀与后缀

客户端日志里一直是：

```
Failed to load texture: mtr:crowd/crowd_atlas
java.io.FileNotFoundException: mtr:crowd/crowd_atlas
    at net.minecraft.client.texture.ResourceTexture$TextureData.load(ResourceTexture.java:83)
```

`RenderLayer.getEntityCutoutNoCull(Identifier)` 要的是**完整贴图路径**：
`assets/<ns>/textures/crowd/crowd_atlas.png` ⇒ Identifier 必须写成
`mtr:textures/crowd/crowd_atlas.png`（本仓 `RenderCrowdMarker` 的 `textures/block/white.png` 就是这个写法）。

**排查代价**：那条 `Failed to load texture` 一直躺在日志里，而"本帧雕像 220/739 个 ｜ 147840 顶点"
说明顶点确实写下去了 —— 两条放在一起看，"写进去了但贴图没加载"就是唯一解释。
先前的怀疑方向（光照全黑、相机坐标系、矩阵栈、配额被远区块占满）都不成立：
用户当时说的"完全没有，不是全黑"就是这条日志的准确描述。

### 8.3 姿势与外观

| 量 | 现在怎么来 |
|---|---|
| 朝向 | 格子坐标哈希（`MmtrCrowdStatues.spot`，22.5° 一档 ×16，0 = 北、北→西→南→东） |
| 底皮 / 群系 / 职业 / 等级 | 同一个哈希的不同位段（与朝向用不同盐，免得绑在一起） |

方块状态里的 `head`/`variant` 因此**渲染器不读**（留着是为了 blockstate 文件不用重写；
真要清爽，下一轮把这两个属性与 `blockstates/crowd_mark_*.json` 一起收掉）。
`MmtrCrowdModule` 里的 `bodyStepOf`/`headStepOf`/`variantOf` 已删除。

## 9 实机那一轮踩到的两个坑（都是本轮修掉的）

### 9.1 `occupied` 不能直接 `get`：座位方块没有这个属性

`BlockCrowdMarker.isOccupied` 原来写的是 `state.data.get(OCCUPIED)` —— 过渡期的座位方块
（`crowd_seat_1/2`）**没有** `occupied`，于是：

* 服务端：`Exception ticking world` / `IllegalArgumentException: Cannot get property BooleanProperty{name=occupied…} as it does not exist in Block{mtr:crowd_seat_1}`；
* 客户端：同一个异常把渲染线程打掉（`Unreported exception thrown!`）。

两处修的写法：

| 位置 | 写法 |
|---|---|
| `BlockCrowdMarker.isOccupied` | `state.data.contains(OCCUPIED) && state.data.get(OCCUPIED)`（先问有没有） |
| `MmtrCrowdModule.hasStatue` | `!isLegacySeat(state) && isOccupied(state)`（先判座位） |
| `MmtrCrowdStatues` 扫描 | 同上：`!isLegacySeat(state) && !isOccupied(state)` |

### 9.2 迁移不能只覆盖"这一拍的目标格"

第一版迁移只对 target 里的格子生效 ⇒ 客量 50% 时**非目标的那一半座位格**永远不会被迁回
（它们既不在 target、也不在 `plan.seats` 台账里）—— 表现就是"人走了，标记也没了"。
现在 `enqueueDiff` 里多了一遍：**遍历 `plan.sweptMarkers`，凡是还铺着座位方块的就入队迁回**
（`spot = target.get(cell)`：该有人的迁成 `occupied=true`，不该有人的迁成 `occupied=false`）。
每格迁完就不再是座位，所以这一遍每格最多入队一次。

| `雕像资源已载入：28 盒 ｜ 图集 1188×1452` | ✓ | 网格/图集读进来了 |
| `Failed to load texture` 条数 | **0** | 图集 Identifier 修好了 |

## 10 渲染路径定论：走 MTR 的队列（2026-10-11 实机）

用户实测两条路径：

| 路径 | 结果 |
|---|---|
| 自己往实体批次写顶点（`getEntityVertexConsumers().getBuffer(...)` + `vertex(相机相对坐标)`，`AFTER_ENTITIES`） | **钉在屏幕上**（原话："村民会跟着视角动，在屏幕上固定"）—— 顶点进了实体批次，但批次 flush 的位置不在实体 pass 里，拿到的变换不对 |
| `MainRenderer.scheduleRender(...)` + `QueuedRenderLayer.EXTERIOR` + `IDrawing.drawTexture`（`BEFORE_ENTITIES` 里排队） | **位置正确**（原话："位置没问题了"）—— 与车厢/钢轨/标记现形同一条路：`MainRenderer.render` 本身就是实体渲染器，它在实体 pass **内部**绑定图层并立刻调用回调 |

两条实现细节值得钉住：

1. **角序要循环挪一格（c1,c2,c3,c0）**：`GraphicsHolder.drawTextureInWorld` 的字节码里，
   uv 的 (u1,v1) 挂在第 1 个角、(u2,v1) 挂第 2 个、(u2,v2) 挂第 3 个、(u1,v2) 挂第 4 个
   （2026-10-11 用 `javap -c` 逐条读过）。循环不翻绕序，所以背面剔除与原版一致；
   直接照抄原版角序会把 uv 转 90°/镜像。
2. **一个人只做一次矩阵平移**（`graphicsHolder.push/translate/pop`），别用
   `IDrawing.drawTexture(..., playerOffset, ...)` 那个重载 —— 它对**每个四边形**的 12 个坐标
   各调一次映射层 getter。

## 11 规模与代价（1075 格时实测）

| 读数 | 值 |
|---|---|
| 扫描半径 | 8 区块（17×17）⇒ 站台上 **1075–1187** 格真的站着人 |
| 每帧画一个雕像 | ≈ **60 µs**（672 个四边形 = 28 盒 × 6 面 × 4 层） |
| 自调上限 | 目标 `MMTR_STATUES_BUDGET_MS`（默认 8 ms）⇒ 约 **125 个/帧** |
| 全画 1075 个 | ≈ **64 ms/帧** ⇒ 这条路做不到"8 区块内全显示" |

**所以"8 区块内全部显示"要换载体**：把整片雕像烘进 MTR 优化渲染器的批次
（`RawMesh` + `new OptimizedModel(parts)` + `OptimizedRenderer.queue`，MMTR 的钢轨已经这么做，
见 `MmtrRailMeshCache`）—— 一次性上传、每帧几个 draw call，代价是显存（约 2.9M 顶点 ⇒ 几十 MB）
与"客流变了要重烘一次"的卡顿。这一步还没做（就是 `notes/398` 那条路）。

扫描那边**不贵**：先 `section.hasAny(...)` 问"这一段有没有客流标记"（只走调色板），
再逐格读 —— 半径从 4 提到 8 之后扫描仍然只是"段数"级别的开销。

## 12 第二刀：烘进 VBO 批次（2026-10-11 落地，8 区块内 1280 人全画）

用户口径："能缓存的一定就先缓存。" 于是把整片雕像烘进 **MTR 优化渲染器的 VBO 批次**（与钢轨同一条路）。

### 12.1 读数（实机，同一条站台）

| 指标 | 逐帧写顶点（旧） | 批次（现在） |
|---|---|---|
| 画的人数 | 8 ms 预算内 ~150 / 1180 | **1280 / 1280（全部）** |
| 每帧 CPU | 8 ms | **0.02–0.07 ms**（排队） |
| 优化渲染器 draw 数 | 0 | 14（+钢轨 15）｜ 1 个 batch |
| 建块（一次性 / 变化时） | — | 一块 35–94 ms，每帧最多一块 |

客户端 `[MMTR-LIGHT]` 的读数直接确认了它进了同一条批：`非钢轨 top4：mtr:textures/crowd/crowd_atlas.png=14.0(1.00批)`。

### 12.2 踩到的两个坑（都在映射库字节码里确认过）

1. **必须三角化**：`RawMesh.upload(Mesh, mapping)` 给索引缓冲只分配
   `faces.size() * 3 * 4` 字节（每面 3 个下标、每个下标 4 字节）——
   我们是**四边形**，直接上传就是 `BufferOverflowException`。
   解法：上传前 `RawModel.triangulate()`（一次）。
2. **失败后要清干净**：第一版 catch 里清了 `DIRTY_TILES`，而外层正在遍历它 ⇒ 后续 `remove()` 返回 null、
   一连串 NPE。现在改成迭代器 + `batchUnavailable` 立刻收手。

### 12.3 结构（`MmtrCrowdStatues`）

| 件 | 说明 |
|---|---|
| `TILE_SHIFT = 5`（32 格一块） | 玩家走一格只重烘"新进入视野的那几块"，走远了整块 `close()` 释放显存 |
| 每块签名 | 格坐标 + 朝向桶 + 四个外观下标混一遍；签名没变不重烘（扫描每 100 tick 算一次） |
| `MAX_TILE_BUILDS_PER_FRAME = 1` | 建 VAO 的几毫秒摊到多帧 |
| `MAX_VERTICES_PER_BATCH = 60000` | 一块里人多就切段（索引是 32 位，切段只是为了重建粒度/内存曲线） |
| `MAPPING` | 与 `MmtrRailMeshCache` 逐条一致的顶点映射（位置/uv/法线/光照逐顶点，颜色与 ModelMat 每 draw 常量） |
| 每块一个原点 | 顶点存"相对本块原点"的 float；每帧 `push/translate(原点−相机)/queue/pop`（照抄 `RenderRails`） |
| `MMTR_STATUES_WORLDLIGHT` | 2026-10-12 起**默认 on**：烘的时候按标记格坐标取世界光照打进顶点；`off` = 强制全亮（与 MTR 一致，截图/排查用）。光进顶点 ⇒ 世界光变了不刷新，是静态烘焙的既定代价（不加重建触发，见 notes/416 §6） |

### 12.4 还欠的

1. **建块 35–94 ms 依旧在渲染线程**：首次进站约 0.5 s 摊在 14 帧里。下一步把"顶点 → RawModel"
   挪到工作线程（钢轨的 `MmtrRailBakeJob` 就是这么做的），渲染线程只留 `upload()`；
2. **显存**：1280 人 ≈ 3.4M 顶点（几十 MB 级）。要压就在烘焙器里做**隐藏面剔除**
   （28 个盒子里被别的盒子完全盖住的面），预计能砍三成；
3. 逐帧写顶点那条路保留为回退（映射库私有字段取不到 / 批次建失败时用）。

## 13 切段时的一个真 bug（"只画出了一小部分人"）

第一版切段写反了顺序：

```java
if (顶点数超限) {
    upload(rawModel);      // ← 此时 mesh 还没 append 进 rawModel ⇒ 上传的是空模型
    mesh = newRawMesh();   // ← 攒了 22 个人的 mesh 被整段丢掉
}
...
rawModel.append(mesh);     // 只有最后一段走得到这里
```

于是**每块只画得出最后 ≤22 个人**，而计数报的是全量（计数数的是"块里有几格"，不是"烘进去几个顶点"）。

修法：切段时先 `rawModel.append(mesh)` 再 `upload(rawModel)`；同时把计数改成**真的烘进去的格数**
（`bakedSpots`）—— 这样这类 bug 在读数里立刻现形：现在进站时读数是
`128/640 → 256/640 → 724/1280 → 1280/1280`（逐块长满），不再是"一上来就 1280/1280"。

修复后实测：1280 人 / 14 块，`非钢轨 draws=53–57(1.00 批)`（= 我们的 58 段），每帧排队 **0.03 ms**。

**代价（下一步）**：一块 32 格（约 90 人）的建块 ≈ **200 ms，仍在渲染线程** —— 进站/走动/客量变化时
会出现 p95 100–300 ms 的卡顿（p50 仍是 14–28 ms）。要治就两步：把"顶点 → RawModel"挪到工作线程
（钢轨的 `MmtrRailBakeJob` 就是这么搬的）、以及在烘焙器里做隐藏面剔除压顶点数。

## 14 周期性卡顿的根因：签名被算了两个版本

用户报："原地不动也有周期性卡顿，好像与加载无关。"——正是下面这个：

```java
// prepareTiles()：签名 A（格坐标 + 朝向桶 + 四个外观下标）
// buildTile()   ：签名 B（Math.round(x*4)*31 + Math.round(z*4)）
BATCHES.put(key, new TileBatch(..., 签名B));
if (cached.signature != 签名A) DIRTY_TILES.put(...);   // ← 永远不等 ⇒ 每 5 秒全部重烘
```

每 100 tick 扫一次 ⇒ 每次扫描都把 12–14 块全部标脏 ⇒ 每块 ~200 ms、每帧烘一块
⇒ **每 5 秒一次 200 ms 级的卡顿**，与区块加载无关。

修法：签名只在 `prepareTiles()` 算一次，**原样**通过 `DirtyTile` 带进 `buildTile()` 存进 `TileBatch`。
另加一条读数（DEBUG）：`扫描耗时 X ms ｜ N 格 ｜ 待烘块 K ｜ 已烘块 M` —— 这类"每拍重烘"以后一眼可见。

### 实测（原地不动，976 人）

| 读数 | 修前 | 修后 |
|---|---|---|
| 帧间隔 p50 / p95 / 最慢 | 28 / 106–219 / 318 ms | **21–22 / 24–25 / 27–30 ms** |
| 待烘块（每次扫描） | 12–14（全部） | **0** |
| 扫描耗时 | 未测 | **1.9–2.1 ms**（所以扫描不是卡顿源） |
| 每帧排队 | — | 0.015 ms ｜ 47 个 crowd draw |

**还剩的卡顿窗口**：跨块走动 / 客量变化时新块要建（一块 ~200 ms，仍在渲染线程）。
下一步照 `MmtrRailBakeJob` 把"顶点 → RawModel"挪到工作线程，渲染线程只留 `upload()`。

## 15 流动人群口径 + "来回移动卡顿"两处放大机制（2026-10-11）

### 15.1 流动人群最多 = 流动格数的 1/10

用户口径："对于流动人群仅需要少量即可，最多为方块数量的 1/10"（这里按**流动格数**理解）。

`MmtrCrowdModule.select()`：

```java
final int flowCeiling = Math.min(flow.size() / 10, Math.max(2, (int) Math.round(capacity * FLOW_SHARE)));
targetFlow = Math.min(budget, level <= 0 ? 0 : Math.max(Math.min(2, flowCeiling), flowByLevel));
```

服务端读数（变的时候打一条）：

```
[MMTR-CROWD] 流动目标 = 18 只（走道 180 格 ｜ 1/10 顶 = 18 ｜ FLOW_SHARE 顶 = 400 ｜ 客量 100% ｜ 满员 2000）
```

—— 改之前客量 100% 时这条走道能要到 180 只（EMF 实测 0.06–0.1 ms/只 ⇒ 11–18 ms/帧）。

### 15.2 来回移动卡顿的两处放大机制（都修了）

| 机制 | 症状 | 修法 |
|---|---|---|
| 区块进出"已加载"集合 ⇒ 同一块的格数忽多忽少 ⇒ 签名每拍都变 ⇒ 反复重烘 | 走动时抖 | `tileChunksLoaded(key)`：**2×2 区块没全加载的块这一拍不动它**（既不算变化也不回收） |
| 块离开扫描半径就被立刻 `close()` ⇒ 走回去又重烘 | 来回走更抖 | **留 96 块的余量**（`MAX_KEPT_TILES`），且"连续两轮扫描没看见"才真释放 |

### 15.3 建块成本拆解（新读数，决定下一步优化谁）

```

```

**钱几乎全在 `upload()`**（`triangulate` + 逐顶点写 direct ByteBuffer + 建 VBO/VAO），
造顶点只占 ~7% ⇒ "把顶点搬去工作线程"收益很小，真正要治是**压顶点数**：
①烘焙器里做隐藏面剔除（28 盒里被完全盖住的面）；②把 群系/职业/等级 三层合成一张衣服图（490 块）。
