# 404 — 车辆位置查询每帧重建整条曲线：客户端渲染线程 24% 的真凶

> 2026-10-08。承接 notes/401（周期性卡顿的真凶是钢轨烘焙）。本条是**稳态每帧**的那一半，
> 与烘焙无关。一句话：`PathData.writePathCache` 在"查不到真轨"这一路**既不缓存也不延冷却**，
> 于是客户端每一次车辆位置查询都 `new Rail` → `RailMath` 沿曲线采样建表（实测 46–50 µs/次），
> 每帧被 7 个调用点放大到约 800 次/列 ⇒ **渲染线程 24.4% 的采样**、活跃窗口 **42.5–69.4% 的墙钟**。

## 1 怎么找到的：从"自检失效"到一条完整栈

`[MMTR-FRAME]` 自己带一条判据：**已量段合计 ÷ 帧间隔 p50 ≈ 1** ⇒ 帧时被表中那些段解释完了。
2026-10-08 的日志里这条判据**明显不成立**：

```text
[MMTR-FRAME] 5.0s 窗口：帧=172（34.4 FPS）帧间隔 p50=18ms p95=67ms 最慢=381ms ｜ 已量段合计=8.49ms/帧
  ｜ 分段（累计ms/次数 max=单次最坏ms，按累计耗时排序）—— main.tick=371ms/172 max=7.71 | shadow.vehicles=329ms/172 | main.vehicles=323ms/172 | …
  ｜ 兜底轨：现建 28827 次（1376.8ms，均 47.8us）｜ 复用 0 次（0.00%）｜ 查表 命中 2 / 未命中 28827 ｜ 缓存=关
```

注意这几件事同时成立：
`shadow.vehicles + main.vehicles` 只有 **3.8 ms/帧**，`已量段合计` 8.49 ms/帧，而 p50 是 18 ms；
同窗口里 `兜底轨` 却报了 **1376.8 ms / 172 帧 = 8.0 ms/帧**。
⇒ 有一件 8 ms/帧 的事**发生在被埋点的段之外**（§4 解释为什么）。

然后用 JFR 把它钉死。**`jfr print` 默认只打 5 层栈**（这次踩到了：不写 `--stack-depth` 会看到 `...`），
要看清调用者必须给足深度：

```powershell
& $jfr print --stack-depth 64 --events jdk.ExecutionSample sandbox/tmp/jfr-client2.jfr > sandbox/tmp/s2full.txt
```

归一化到**渲染线程**采样（改前那份录制里渲染线程占 4412 / 7509 条）：

| 栈上出现 | 条数 | 占渲染线程采样 |
| --- | --- | --- |
| `PathData.defaultRail` | **1076** | **24.39%** |
| `RailMath.<init>` | 1074 | 24.35% |
| 其中叶子 = `RailMath.lambda$new$0` | 619 | 14.03% |
| 其中叶子 = `RailMath.renderSegment` | 235 | 5.33% |
| 其中叶子 = `StrictMath.atan2` | 130 | 2.95% |
| `Vehicle.getVehicleCarsAndPositions` | 180 | 4.08% |
| `canOpenDoors`（另一件事，见 §8） | 348 | 7.89% |

即：**1074 / 1076 的叶子都在 `RailMath` 的构造里** ⇒ 这些采样不是在"用"曲线，是在**造**曲线。

## 2 源码：一个"只在命中分支续命"的缓存

```java
private void writePathCache(Data data) {
    final long currentMillis = System.currentTimeMillis();
    if (currentMillis > getRailCacheCooldown) {
        rail = Data.tryGet(data.positionsToRail, startPosition, endPosition);
        if (rail == null) {
            rail = defaultRail();                     // ← 每次调用都新建：Rail.newRail → new RailMath
        } else {
            getRailCacheCooldown = currentMillis + 1000 + RANDOM.nextInt(1000);  // ← 只有命中才延冷却
        }
    }
}
```

`rail` 这个字段本来是"上一次查到的那条轨"，但**未命中分支把它覆盖成一条刚造出来的近似轨，
而且不给冷却** ⇒ 下一次调用又进这个分支、又造一条。字段等于没用。

为什么客户端会一直未命中：客户端的 `positionsToRail` 只覆盖它加载到的那些轨，而
**车辆路径的轨大多不在里面**。探针把这件事量化了（改后仍在复用的那些窗口）：

```text
｜ 兜底轨：现建 0 次（0.0ms，均 -）｜ 复用 109236 次（100.00%）｜ 查表 命中 7 / 未命中 109236 ｜ 缓存=开
```

命中 3–17 次 / 未命中 5.6 万–35.7 万 —— **未命中是常态，不是边缘情况**。

代价不止 CPU：`RailMath` 的构造会按曲线采样建表并分配 `double[]`。改前每帧几百次
⇒ 每帧几百个采样表 + `double[]` 进垃圾堆（GC 最大停顿本身只有 39 ms，所以这条不是"GC 的锅"，
但它是实打实的分配churn）。

## 3 是谁在每帧要位置：7 个调用点

把 1076 条栈按 `Vehicle.getVehicleCarsAndPositions()` 的上一层归类：

| 调用者 | 采样 | 占比 | 性质 |
| --- | --- | --- | --- |
| `MmtrVehicleAnchors.modelCarIndex` | 480 | 44.6% | 锚点（车灯/面板/驾驶室都用它） |
| `VehicleExtension.getSmoothedVehicleCarsAndPositions` | 179 | 16.6% | 平滑位置（渲染用） |
| `MmtrCoupleInteraction.carCentres` | 153 | 14.2% | **车钩提示的"附近有没有车"每帧扫描** |
| `ModelPropertiesPart.vehicleIdFor` | 85 | 7.9% | 按车选模型 |
| `MmtrHeadlights.requestCar` | 74 | 6.9% | 车灯 |
| `MmtrHeadlights.lampColor` | 68 | 6.3% | 车灯 |
| `MmtrInteractPrompt.carTransforms` | 37 | 3.4% | 交互提示 |

七个调用点**各自**调一次 `getVehicleCarsAndPositions()`（里面每节车 × 每个转向架 × 2 个端点
都查一次位置），于是同一列车的同一段曲线在一帧里被重建几十次。所以修在
`PathData` 这一层（离数据最近、每个调用点都覆盖），而不是去给七个调用点各加一个缓存。

`MmtrCoupleInteraction.tick()` 的完整栈（`--stack-depth 64` 才看得见）：

```text

PathData.writePathCache(Data)
PathData.getPositionAndTiltAngle(Data, double)

Vehicle.getBogiePositions(double, DoubleArrayList)

MmtrCoupleInteraction.anyTrainNearby(ClientPlayerEntity)

```

## 4 为什么帧探针的段里看不见它（这条是本条的教训）

`MainRenderer.render` 上有一段**每帧钩子**（模拟 + `tick()` 那一半），它**不在**
`MmtrFrameProbe` 埋的 `main.*` / `shadow.*` 段里 —— 这一点 `MmtrFrameProbe` 的类注释本来就写着
（"`MainRenderer` 里的早期返回只挡掉了'模拟 + 每帧钩子'那一半"）。七個调用点里：

* `MmtrVehicleAnchors` / `MmtrHeadlights` / `MmtrFaceRuntime` 在 `RenderVehicles` 里 ⇒ **算在段内**；
* `MmtrCoupleInteraction.tick` / `VehicleExtension.getSmoothed…` / `ModelPropertiesPart` /
  `MmtrInteractPrompt` 在钩子/其它半边 ⇒ **段外**（≈42% 的采样）。

所以"已量段合计 ÷ p50 ≈ 1"这条自检一旦不成立，答案就在**没埋点的那半边** —— 它不是噪音，
它是线索。该去 JFR，而不是继续给渲染段加计时。

## 5 改法

`PathData` 里加一条**按对象**的兜底轨缓存：

* **缓存键 = `speedLimit`**。兜底轨只由 `(startPosition, startAngle, endPosition, endAngle, speedLimit)`
  决定，而前四个在 `PathDataSchema` 里是 **`final`**（构造后不可能变），只有 `speedLimit` 会被
  `writePathCache(ObjectList, Data, TransportMode)` 按区间重算 ⇒ 键只需它。
* **不去动查表节奏**。`Data.tryGet(...)` 仍然每次都调：命中分支的 1–2 s 冷却会推迟"客户端刚知道这条轨"
  的采纳时刻，那会**改画面**（车辆位置从近似曲线跳到真曲线）。`tryGet` 本身是一次两级 map 查询，
  实测不是成本（改后 1.34M 次查询的残余只占渲染线程 ~1.9%）。
* 兜底轨从不登记进 `data.positionsToRail`，也没有任何外部持有它（`Rail.newRail` 无副作用，已核对）
  ⇒ 复用同一个实例不改变任何调用方能观察到的东西。

### 5.1 等价自检（默认关，`-Dmmtr.pathdata.verify=true`）

头几次"复用"时**当场再建一条新的**，逐位比几何：曲线长度、形状、沿曲线 9 个等分点上的
位置与倾角，用 `Double.doubleToLongBits` **全等**比较（不给容差——输入相同就该逐位相同，
给容差只会让"几乎一样"掩盖真问题）。

```text
[MMTR-PATHCACHE] 兜底轨等价自检第 1 次（逐位相同）：复用 d17c2037bf434fbd 长=100.0000 端点=(-199.5000,65.0000,1806.5000,tilt=0.0000)(-99.5000,65.0000,1806.5000,tilt=0.0000) ｜ 现建 d17c2037bf434fbd … ｜ 限速=300
（第 1–5 次全部"逐位相同"，摘要值与端点完全一致）
```

## 7 开关 / 读数 / 复现

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| `-Dmmtr.pathdata.fallbackcache=false` | 开 | 回到"每次查询都重建"（改动前行为，A/B 用） |
| `-Dmmtr.pathdata.probe=true` | 关 | 计数：由 `[MMTR-FRAME]` 汇总行多打一行"兜底轨" |
| `-Dmmtr.pathdata.verify=true` | 关 | 头 5 次复用当场现建一条、逐位比几何（`[MMTR-PATHCACHE]`） |
| `-Dmmtr.pathdata.verifylimit=N` | 5 | 自检次数上限 |

探针行长相（每 5 s 一行，跟着 `[MMTR-FRAME]` 走）：

```text
  ｜ 兜底轨：现建 0 次（0.0ms，均 -）｜ 复用 109236 次（100.00%）｜ 查表 命中 7 / 未命中 109236 ｜ 缓存=开
```

便利脚本 `sandbox/dev-run/pathcache-ab.gradle`：`-PmmtrPathCache=on|off`、`-PmmtrPathProbe=true`、
`-PmmtrPathVerify=true`（带 `--quickPlayMultiplayer` 直连本机 dev 服务端）。

⚠️ 引擎在 `game/libs` 里是**副本 jar**：改了 `mmtr/engine` 必须
`mmtr/scripts/sync-engine.ps1`（**要先停 dev 会话**），否则客户端跑的还是旧引擎
