# 407 — 驾驶输入回路：把"我推了手柄"从网络来回里拿出来（本地闭环）

> 2026-10-09。承接 notes/369（运动流 ①）、notes/375（腿表唯一来源）。
> 用户口径（2026-10-09）：接管之后"玩家客户端下载当前列车位置路径需要旁路至对账纠正路径"，
> 目的是"防止客户端延迟导致列车操作、动画因网络原因卡顿"。
>
> 本条按 **A 方案**做：**本地立即生效 + 回声当纠正**（服务端权威不变），不做位置权威移交（那是 B 片）。
>
> 状态（2026-10-09）：代码已落、类型检查已过；**A/B 实测读数已补（见 §3）** ——
> 关（`localdrive=false`）78 样本 148.9 ms、开（默认）231 样本 27.2 ms。

## 1 病因（已确证，不是推测）

客户端**跑的就是同一套物理**，但它的输入严格只来自镜像 —— 而镜像的手柄值要走一个来回：

| 环节 | 代码 | 代价 |
| --- | --- | --- |
| 按键 → 上报 | `MmtrDriveInput.send`（`changedSinceLastSend()` 即刻发；1 s 那次只是心跳） | — |
| 服务端线程 → 引擎 C2S 队列 | `PacketDriveControl.runServer` → `Init.sendMessageC2S` | 引擎下一 tick ≤50 ms |
| 引擎算完 → ① 的 `CONTROL` | `MmtrVehicleMotionSync`（**边沿型**：变了才发） | ① 下一帧 ≤100 ms |
| 回程 → 客户端落镜像 | `MmtrVehicleMotionClient.apply(Control)` → `mmtrApplySyncControl` | 半个 RTT |
| 本地物理读它 | `Vehicle.simulateMoving` 的镜像分支：`createMirrorControlStateFromSync()` | — |

**合计 ≈ RTT + 150 ms**（局域网 ≈150 ms，远程 200–350 ms）。

两处代码把这件事钉死：

- `Vehicle.java`（`simulateMoving` 上方那段注释）：*"Mirrored client-side from the snapshot so every
  client simulates identical physics"* —— 同一个 `ConsistDynamics`、同一个控制器；
- `MmtrDriveInput.send(...)`：**只发包，一个字段都不写本地**。

于是症状精确到一句话：**动画不卡（位置是本地积分 + 160 ms 误差吸收），卡的是"我推了手柄、车没反应"**。
`MmtrVehicleMotionClient` 那套显示模型治不了它 —— 它平滑的是位置，不是控制回路。

## 2 改法（三处，都是加东西）

| # | 文件 | 改动 |
| --- | --- | --- |
| ① | 引擎 `Vehicle` | 新增 `mmtrApplyLocalDriveControl(...)`：写**与 `mmtrApplySyncControl` 完全相同的六个字段**（油门/制动/油门手柄/定速/换向/紧急）。① 的 `CONTROL` 里全部是司机自己的手柄（灯光档位不在 ① 里发），所以"本地写"与"回声写"是同一格，不存在两个所有者 |
| ② | 客户端 `MmtrDriveInput` | 折算只留**一处**（`controlOut()`）：`send` 与本地写用同一份值（免得两处各写一遍漏字段 —— notes/279 那个形状）。`send` 里顺手 `applyLocally`，并暴露 `isLocallyDriving(vehicleId)` |
| ③ | 客户端 `MmtrVehicleMotionClient` | 本地闭环期间：**不收** `CONTROL` 回声（那是同一批字段的稍旧值）；显示模型对**这一辆**改成"对账纠正" |

### 2.1 为什么显示模型也必须改（否则本地闭环白做）

`mmtrDisplayTick` 原来每帧把本地位置往服务端那一帧吸（160 ms 时间常数）。而本地闭环一开，
服务端那一帧按定义**落在我后面一个来回**（我本地已经用同样的手柄值推过了）——于是那套吸收
就变成"每帧把我往回拉"，手柄推下去车像被拽着。

改成：本地闭环期间误差不超过阈值就不动它，超过才硬对齐。阈值 =
`8 m + 0.5 s × 速度`（`-Dmmtr.localdrive.correctm` 调基数，0 = 关掉对账纠正）。
8 m 是原来的硬对齐线；半秒那一项盖住"网络来回的正常领先"（`speed × RTT`：60 km/h、150 ms ≈ 2.5 m；
120 km/h ≈ 5 m）。于是正常领先根本不动它，而**换轨 / 连挂 / 引擎拒绝了我的输入**那类真不同步仍会被抓住。

### 2.2 谁有资格本地生效（这一条决定它安不安全）

两个前置，都在 `applyLocally` 里判：

1. **我坐在那辆车的司机位上**（`MmtrDriverSeat.current()`，就是 `tick()` 本来就用的那个判据）；
2. **镜像里的 crew uuid 是我的，或者还空着**（`ownsCab`）。空 = 还没人持有 ⇒ 我这一动手柄引擎
   就会把它给我；**是别人 ⇒ 本地不许提前生效** —— 否则"别人正开着"时我会看到车在我手上动、
   而服务端根本不理我（那种分歧是**无界**的：我会一直握着那根杆）。

再加一条**时间闸门**：本地写进镜像之后 `LOCAL_HOLD_MILLIS`（默认 600 ms，`-Dmmtr.localdrive.hold`）
之内不收回声，**窗口只在"我真的改了手柄"时刷新**（每秒那次心跳补发不算，否则窗口永不过期）。
窗口一到回声重新成为权威 ⇒ "引擎钳位 / 拒绝 / 换端 / 钥匙被抢"最多错这么多毫秒。

## 3 验收判据（读数怎么量）

读数：**"我改了手柄" → "本地镜像的手柄值等于我这一份"** 过了多少毫秒（`[MMTR-LOCAL] 驾驶回路` 行）。

- **为什么这个数就是死时间**：本地物理的输入是 `createMirrorControlStateFromSync()`，也就是镜像 ——
  镜像什么时候变成我的值，车上就什么时候有反应。
- **为什么开/关可比**：两条路用**同一个**读数（不靠手感），而且它总是会触发（不必等到车真的动）。

| 开关 | 期望（机制推导） | 实测（2026-10-09，从各趟客户端日志的 `[MMTR-LOCAL]` 行聚合） |
| --- | --- | --- |
| `-Dmmtr.localdrive=false`（旁路关闭的行为） | RTT + ≤150 ms | **78 样本 · 加权均值 148.9 ms · 最大 236 ms**（`ctrl-client.out.log`，55 行**全部** `开关=关`） |
| 默认（本地闭环 = `-Dmmtr.localdrive=true`） | ≤1 个客户端 tick（0–50 ms，平均 ≈25 ms） | **231 样本 · 加权均值 27.2 ms · 最大 51 ms**（4 趟 `开关=开`：`on-client` 6/27.7/51、`verify-client` 9/29.8/50、`upload-client2` 44/26.9/43、`clamp-client` 172/27.2/330） |

**两条带都被实测证实**：关的那趟 148.9 ms 正好落在"RTT + ≤150 ms"（单机 RTT ≈ 0）；
开的那趟 27.2 ms 与推导的 25 ms 差 2 ms、最大 51 ms 也还在"≤1 tick"里 —— 这就是"本地立即生效"
该有的形状（它量的是本地写的时延，不是网络时延）。

两个必须一起读的口径：

1. **330 ms 那一个是长静置之后的第一笔**（`样本=1 时延均值=330ms`，整行只有一次手柄变化，
   它跨了一次区块/渲染卡顿）。它是**单点尖峰，不是稳态**（稳态最坏 51 ms）。聚合里我把它
   **算进最大值**而没有剔除 —— 宁可让读者看到那个尖峰。
2. **四趟 ON 不是同一趟**：`on / verify / upload-client2 / clamp` 是四次不同的启动，世界状态不同。
   逐趟均值 26.9–29.8 ms 彼此差 <3 ms，所以合成"231 个样本的一条读数"站得住；
   但它是**四次重测，不是一次受控 A/B**（受控对照只有 `ctrl-client` 那一趟的 OFF）。

配套读数（同一行）：`本地闭环=N 帧 跳回声=M 领先max=X m 对账=K`（在 `[MMTR-MOTION]` 那一行末尾）。
`对账` 持续增长 = 本地与服务端真的在分叉（阈值那一项该调）；`跳回声=0` 而本地闭环 >0 帧 = 回声本来就没来。

实测一行（2026-10-09 19:34，本地闭环开着、车静止）：

```
[MMTR-MOTION] … 最大误差=0.867m 硬对齐=0 … 权威=本地45/服务端0/交接中0 切换=本地0次·交回0次·否决0次
              本地闭环=45帧 跳回声=0 领先max=0.0m 对账=0 上行=9条（最后 10058.99m / 0.0km/h）
```

`本地闭环=45帧` 与 `权威=本地45` **同一个数**（修前只有前者、没有后者），`跳回声=0` 且 `对账=0`：
回声与对账都没在吵。★ 但这一行**只证明"显示回路闭合"**；"我发出去的上行服务端收没收"是另一件事 ——
本局正好抓到一个反例，见 notes/409 §4.6 第 13 条。

## 4 怎么跑（需要一次停机窗口）

引擎多了一个方法，而游戏编译/运行对的是 **`game/libs` 里那份引擎 jar 的副本**，
所以必须：

```powershell
# 1) 停掉 dev 服务端（deploy-engine.ps1 会拒绝在服务端运行时覆盖 jar，见该脚本顶部的事故记录）
# 2) 打包并部署
mmtr\scripts\deploy-engine.ps1 -Build
# 3) 起客户端（脚本见 dev-client.ps1 / 运行手册）
#    开关关闭那一趟：
#    -Dmmtr.localdrive=false
```

**注意**：在同步 jar 之前，`check-java-compile.ps1` 会对**旧引擎**做类型检查 ——
它会报 `找不到符号: mmtrApplyLocalDriveControl`。那不是代码坏了，是 jar 还没同步
（脚本自己那句警告说的就是这件事）。同步之后再跑就是绿的。

## 5 回退

| 开关 | 作用 |
| --- | --- |
| `-Dmmtr.localdrive=false` | 完全回到改前行为：手柄只在 ① 的回声里到本地，显示模型照旧每帧吸收 |
| `-Dmmtr.localdrive.hold=<ms>` | 不接受回声的窗口（默认 600） |
| `-Dmmtr.localdrive.correctm=<m>` | 对账纠正的阈值基数（默认 8，`0` = 本地闭环期间完全不纠正） |

开关关闭时是**逐位回退**：`isLocallyDriving` 恒为 false ⇒ 不写本地、不收不到回声、
`mmtrDisplayTick` 走原来那两支。多出来的只有计数器自增与一行日志（纯读）。

## 6 已知边界与风险（**没验证的也在这里**）

1. **服务端仍然落后一个来回。** 本地闭环只让"我这台机器上的车"立刻响应；服务端的停车点/信号/
   进近判据读的仍是它自己那份（落后的）位置。所以"我看到的停车距离"与"引擎算的停车距离"会差
   `speed × RTT`（60 km/h ≈ 2.5 m）。**这是设计内的**，不是缺陷 —— 但它意味着司机看到的到站提示
   比引擎的判据早一点点（B 片才会把这件事翻转过来）。
2. **本地领先会被"对账"收掉的那一部分没有量过。** §3 的 `领先max` 就是给它准备的读数。
3. **没有在实机上跑过**（本片交付时 dev 服务端在运行，jar 不能换）：手感、`推手柄→车动` 的观感、
   以及在**别人正开着**的车里就座时会不会有本地抖动，都还没看。
4. **多客户端没测**：两个客户端看同一列车时，司机那台本地闭环、旁观那台走原路 ——
   理论上各看各的误差，但没有实测。
5. **HID（真手柄/摇杆）那条路没单独测**：轴是绝对量，压在键盘之后（`applyHidAxes`），
   走的是同一份 `controlOut()`，所以应当同样受益；但"轴连续变化时窗口被反复刷新导致长时间不收回声"
   这一格需要实机确认（轴一直在动 = 窗口一直在刷新 = 回声被我压住 —— 这在`ownsCab` 成立时是对的，
   不成立时不会生效）。
6. **`emergency` 也在本地立即生效**（它是 ① CONTROL 的六个字段之一，本来就是司机请求）。
   如果将来保护/SPAD 也要抢这一格，得把它从"司机所有"里摘出来 —— 现在它不在 `STATE` 里，
   所以这一片没有动它。
