## 1. 事件抽象类（设计 §6.1）

> 用户原话："事件类型及其多，但无非就是恶劣天气降速、故障、卧轨、某站客流激增临时高峰期等，
> 说白了就是现实里那点事" —— 所以**抽象在前、细分在后**。

`MmtrEvent`（抽象）：类型 / 目标（线路·车站·区段·车列）/ `startMillis` / `endMillis`（-1 = 未知）/
`reason`（**给人看的理由文案 = 前台展示的契约**）/ 严重度；**状态由时钟算**（未生效/生效中/已结束），
不自己存 —— 存了就会和时钟不一致。

四类细分（§6.2）：`PeakSurge`（临时高峰，动**计划层**）、`Delay`（延误，动**运用层**，
两种策略）、`Fault`（故障，车列下线 / 区段不可用）、`SpeedRestriction`（降速 = **动态约束**，
进 min 链 —— 与姊妹文档的唯一接合点，接线留到那一层就绪，本片先做"存在且可见"+计划期参考速度）。

`MmtrEventRegistry`：只给前台两条带（生效中 + 即将生效），带剩余时长文案（"预计 20 分钟后恢复"）；
**不落盘** —— 配置里那份是规则，事件实例是"这次运营里发生了什么事"，重启即清空是对的。

## 2. 事件怎么改计划（设计 §6.2 + §7）

`MmtrPlanAdjustments.recompute(...)`：**不另写一套排班**，只产出"调整后的输入"再跑一次 P2/P3 的纯函数 ——
于是重算永远与首次生成走同一条路（这条纪律是这份设计最值钱的地方）。

| 事件 | 改什么 | 落到代码 |
| --- | --- | --- |
| `PeakSurge` | 未来趟次**加密**：把高峰窗那一段密度表切开、换成更小的间隔（**已过的那一截一行不改**） | `applyPatternEvents` |
| `Delay` 保表 | 该车未来趟次**转给别的编组**，时刻表一行不动 | `applyDiagramEvents` |
| `Delay` 保车 | 车不变，它未来条目**整体平移**（`Trip.shiftedBy`） | 同上 |
| `Fault` | 未来趟次**取消**并写清为什么（替补顶替是 P6） | 同上 |

三条冻结规矩（§7）逐条落到代码：**过去不可改**（`dayTime` 之前的不动）、
**在途不打断**（每辆车 `frozenUntil` 之前的条目原样保留）、
**不抢在途车已持有的道岔**（重算只改"未来谁跑哪一趟"，在途那趟逐字段不变）。

`frozenUntil` 从哪来：**派发器自己就知道**（谁在跑哪一步、跑的是哪条交路条目）——
`MmtrPlanDispatcher.frozenUntilByConsist()` 把"当前任务 → 所属条目 → 条目结束时刻"折出来。
这与设计 §7 的"授权持有 = 在途的物理表达，不必另建状态"是同一个意思。

## 3. 测试账（P5 验收六条逐条对上，7 例）

| 验收 | 用例 |
| --- | --- |
| ① 四类细分各一例 | `theFourEventKindsEachAnswerWhatWhenAndWhy`（类型/目标/状态由时钟算/理由/剩余时长）+ `theRegistryFeedsActiveAndUpcomingOnly`（前台两条带、覆盖、终止） |
| ② 未来加密、已过一行不改 | `aPeakSurgeDensifiesOnlyTheFuture`：已过的发车时刻**列表逐条相等**；基础密度表本身未被改动 |
| ③ 两种策略 | `aDelayCanKeepTheVehicleAndShiftItsFutureTrips`（每条要么没动要么正好 +15 min，且只有未来的动）+ `aDelayCanKeepTheTimetableAndHandTripsOver`（时刻逐条不变） |
| ④ 车列下线 | `aFaultTakesTheConsistOutOfServiceButNeverTouchesAnInFlightTrip` |
| ⑤ 冻结边界 | 同上用例的后半：冻结期内的趟次**必须原样在**，保留下来的只能是冻结期内的 |
| ⑥ 不抢在途车的道岔 | `recomputeNeverReassignsTheTripAnInFlightVehicleIsRunning`：重算后在途那趟**逐字段一样**（车次 id / 发车 / 终到 / 方向 / 每站到点与站台） |

> 写 ⑥ 时把第一版断言写成"必须是**同一个对象**"，红了一次：重算是"重新生成 + 只调未来"，
> 对象当然是新的 —— 要钉的是**内容不变**（派发器按任务 id 跟踪，id 稳定就够）。
> 记在这里，免得下次又去要一个不该要的不变量。

## 4. 接口

```
GET  mmtr-plan-events          → { dayTimeMs, feed[生效中/即将生效的文案], events[逐条字段] }
POST mmtr-plan-event-upsert    ← { eventId, kind, ... , reason }（四类按 kind 分派）
POST mmtr-plan-event-delete    ← { eventId, end? }（end=true 是"终结"而不是删掉）
```

事件进了派发器的输入签名（`mmtrPlanSignature`）—— 否则"加了事件、计划却看着没动"（那是这类系统最经典的假象）。

## 5. 装机现场（真世界）

```
GET mmtr-plan-events （空表） → {"dayTimeMs":314193,"feed":[],"events":[]}
配线路（2 个真站台）+ 全天 20 min 密度 + 1 组车底
  → [MMTR-PLAN] 交路 L1：N=1（ring 432s / 高峰间隔 1200s），1 辆车 144 趟（走行时间按轨图算）
POST mmtr-plan-event-upsert {kind:PEAK_SURGE, stationId:5, start:now, end:now+1h, headway:5min, reason:"站台客流激增（验证）"}
  → feed: 生效：临时高峰（车站 5）生效中：预计 1 小时 0 分钟后恢复 —— 站台客流激增（验证）
  → [MMTR-PLAN] 交路 L1：N=2（ring 432s / 高峰间隔 300s），1 辆车 164 趟；车底不够跑：运营需要 N=2 个编组（周转 7 min / 高峰间隔 5 min），现在只配了 1 个（缺 1 个）
```

**事件确实改了计划**：趟次 144 → **164**（高峰窗内加密）、N 1 → **2**，
并且 P1 那条"车底不够跑"的账**穿过事件路径照常报出来**（缺 1 个）——这是三片串起来的证据。

⚠️ **一处待查**：`[MMTR-PLAN] 事件改计划：…` 那行没出现在服务端日志里，而计划明明被改了
（说明 `notes` 有内容却没打出来，或者那次重建走了别的路径）。功能是对的、说明文案的出口要复核
（下一轮第一件事：本地跑一次带事件的 `mmtrRefreshPlanDispatchers` 看 notes 是否为空）。
