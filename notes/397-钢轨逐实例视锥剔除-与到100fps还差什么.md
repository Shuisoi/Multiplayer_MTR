# 397 钢轨逐实例视锥剔除 —— 以及"到 100 FPS"到底还差什么

> 用户口径（2026-10-05）：「现在 fps 在 60，我们基准无轨面是 100，40 帧的渲染这也很抽象了，铁轨这方面还是优化不够」。

前置：notes/396（面板每帧重画）已修完，`main.faces` 从 7.70 ms/帧降到 0.4，FPS 25–35 → 55–63。

## 0 帧预算（60 FPS = 16.7 ms/帧，`renderDistance=10`）

| 项 | 值 | 说明 |
|---|---|---|
| `main.submit` | **2.89 ms/帧** | 主 pass 的 draw 提交 |
| `shadow.submit` | **2.19 ms/帧** | 阴影 pass 把同一批**再画一遍** |
| `draws/frame` | **767**，`batches/frame=1.00` | 一个钢轨材质批次装 767 个 draw |
| 其余已量段 | ~1.0 ms | queue / rails Java / lightfield / vehicles |
| **未量到** | **~10.6 ms** | 地形 + 呈现（探针量不到）= 那 100 FPS 的基准 |

⇒ **要到 100 FPS，得把那 6.7 ms 的 MTR 开销几乎全部消掉**，其中 **5.08 ms 是 draw 提交**。

## 1 为什么是 767 个（两处真浪费）

`RenderRails` 沿轨道**每 `repeatInterval` 米**排一个实例，一个实例 = 一次 `glDrawElements`。
剔除是两级的，**两级都有洞**：

| 级别 | 现状 | 洞 |
|---|---|---|
| **整根轨一个 AABB**（异步 worker，`railWrapper.startVector→endVector`） | 一根轨最长 **100 m**（节点段）⇒ 一个巨大的盒子 | 只要一角落在视锥里，**整根轨的约 200 个实例全画**。767 ≈ **4 根长轨全画** |
| 逐实例 | `<32 格`：**完全不剔除**；`32 格~视距`：只判 `z > 0` | 近处**背后的也画**；远处**只判前后、不判左右** |

## 2 本轮改动：逐实例视锥剔除

`RenderRails`：

- 新增 `frameProjectionScale`，在 `render()` 开头取一次（每 pass 一次）：
  `MmtrInteractPrompt.projectionScale(minecraftClient)` —— **复用仓里已有的正确做法**。
  它的注释记着上一次"手推 FOV 语义"造成的 bug，所以**不手推**，直接读游戏真正在用的
  `GameRenderer.getBasicProjectionMatrix(fov)` 的对角（`m00 = m11/aspect`、`m11 = 1/tan(fov/2)`）。
  `MmtrInteractPrompt.projectionScale` 由 `private` 改为**包内可见**（同类同包），并加注：
  **改它的语义会同时影响交互提示与钢轨剔除**。
- 新增 `insideViewFrustum(offset)`：相机空间判据 `|x|·m00 ≤ z` 且 `|y|·m11 ≤ z`。
- **两带用同一套判据**，原来那个 `<32 格不剔除` 的分支取消。

**两处刻意的宽容**（防"画面边缘钢轨闪掉"）：

| 常量 | 值 | 理由 |
|---|---|---|
| `CULL_MARGIN` | 1.3 | 视锥放宽 30% |
| `CULL_BEHIND_METRES` | 2.0 | 相机平面之后 2 m 内仍照画 —— 取点只是实例的一个角（实例约 0.5 m 长） |
| `CULL_NEAR_DEPTH` | 1.0 | 贴近相机时视锥退化成一条线，用深度下限保证近处照画 |

**取不到投影矩阵时**退化成"只剔背后的"——比改前更保守也更正确（改前近处背后是照画的）。

## 3 诚实的收益上限（别指望这一步就到 100）

- 逐实例视锥剔除：估计把 767 砍掉 **40–60%** ⇒ submit 5.08 → ~2.0–3.0 ms ⇒ **60 → ~70–78 FPS**。
- **零代码、更大的一笔**：`disableShadowsForShaders`（MMTR 配置界面已有按钮）跳过 MTR 内容在阴影 pass 的绘制
  ⇒ 去掉 `shadow.submit` 2.19 ms 与整个阴影 pass（`阴影pass avg=2.71 ms`）⇒ **再 +2 ms 左右**。
  钢轨是薄片、在阴影贴图里几乎看不出来，这笔买卖划算。
- **模型重建修复**（notes/396 §3 第 2 条，未做）：不改稳态 FPS，但去掉 **100–600 ms** 的停顿
  （实测重启后 2 分钟内 `ShaderManager.reloadShaders` 17 次、`loading model` 5 次）。

**结构性的天花板**：实例之间只差一个 ModelMat，本来正是 `glDrawElementsInstanced` 的场景；
但 MTR 的 `BatchManager` 按 `VertexAttributeState`（含 ModelMat）切 `RenderCall`，
**合并在预编译的映射库里**，不动那个 jar 就到不了"一个批次一次 draw"。
所以 60 → ~80 可以靠剔除与阴影开关拿到，**再往上要靠改 MTR 的批次层**（另一个量级的工程）。

## 4 验收

**看 `draws/frame` 掉了多少**（现成的读数，不用加探针）：

```powershell
Select-String -Path "mmtr\game\fabric\run\logs\latest.log" -Pattern "optimizer draws/frame" |
  Select-Object -Last 3 | ForEach-Object { $_.Line }
```

改前基线：`draws/frame=767 batches/frame=1.00`。

**同时必须看画面**：转动视角时**画面边缘的钢轨不能闪掉**。若出现闪掉 ⇒ 把 `CULL_MARGIN` 从 1.3 加大
（或 `CULL_BEHIND_METRES` 加大），这是唯一有视觉风险的旋钮。

相关：`notes/396`（面板重画）、运行手册 §8.2 D10（draw 数才是帧率的相关量）。
