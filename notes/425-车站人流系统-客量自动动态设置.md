# 425 车站人流系统：客量自动动态设置（2026-10-13/14）

> 用户原话（2026-10-13）：**「然后是车站人流系统，这个需要一个系统进行自动动态设置」**。
> 在这一条之前，站台客量只能靠 `platform set/station/all <0-100>` 一个个手填 —— 那是布景参数，
> 不是运营：真实车站会跟着**一天里的节律**、**这个站实际有多忙**、**此刻有没有车进站**自己起伏。
>
> 交付：引擎侧 `MmtrCrowdSystem`（算式 + 观察 + 平滑量化 + 落盘）、指令名词 `crowd …`、
> 只读出口 `/mtr/api/map/mmtr-crowd-system`、15 条单测；设计见
> [01-设计/车站人流系统-自动动态客量-设计.md](../docs/01-设计/车站人流系统-自动动态客量-设计.md)。
> 相关：notes/416（跨端只有 `crowdLevel` 一个数值）、上位设计（`docs/01-设计/站台客流-…`）、
> 台账 §1.4（`docs/02-运行与作业/测试地图-站名与坐标.md`）。

## 1 一套式子

```
目标% = clamp( round( 曲线[小时] × (基准%/100) × 班次因子 × 事件乘法 + 事件加法 + 停站冲量 ), 0, 100 )
输出% = quantize( 当前% + (目标% − 当前%) × min(1, dt/τ), step )        step 默认 2%
```

四个输入各管一件事，任何一项都能在 `crowd status` 里单独看到：

| 输入 | 来源 | 默认 |
|---|---|---|
| 曲线[0..23] | 预设（通勤/全天/夜间/空）或 `crowd curve` 手改 | 通勤：早 8 点 95%、晚 18 点 95%、后半夜 1–2% |
| 基准% | `crowd base`（站台 > 车站 > 全局） | 100% |
| 班次因子 | **实测**到站次数（10 分钟半衰）+ 按最忙站归一 | boost 0.35（最忙 1.00、没车 0.65） |
| 停站冲量 | **实测**"车正停在这条站台上" | +45% |
| 事件 | `crowd event add +40 10 --station=<站>` | 无 |

## 2 三条设计决定（都不是随手写的）

### 2.1 写 `crowdLevel` **本身**，不用 `setModulator` 钩子

`Platform.getEffectiveCrowdLevel()` 那个调制器（`Platform.java:81`，2026-10 留的接口）**不跨端**：
游戏侧每 tick 比对并推送的是 `getCrowdLevel()`，`effectiveCrowdLevel` 只出现在读数里
（notes/416 的取证结论：静态数据对已下发对象不回字段，必须服务端主动推 `crowdLevel`）。
所以动态值只有写进**字段**才走得到画面；走调制器 = "改了个没人推的数"，画面上一个人都不会变。
`crowd status` 两个都报，是为了读数不撒谎。

### 2.2 默认**关着**

一个新系统悄悄接管所有站台的客量，会把用户上一轮手填的 100%（上水村 / TEST / 莫氏岛）抹掉 ——
实机第一次 `crowd status` 就特意验证了这一点：**关着时那三条站台字段仍是 100%**。
`crowd on` 才接管；系统开着时 `platform set/station/all` **改的是系统的基准**（不跟系统抢字段）。

### 2.3 三个"不写"

写字段会 `bumpRevision()` → 推客户端 → 重铺方块。所以：**关着不写**、**量化后才写**（默认 2% 一档）、
**平滑**（τ=90 s）。另外第一次见到一条站台时直接落到目标（否则"打开了没反应"会被当成没生效）。

## 3 实机里改掉的一件事：冲量的"上冲"必须更快

第一版只有一条 τ=90 s。实机第一次抓到真实停站（水牌 00101 进 鸥湾，站停 25 s）时读数长这样：

```
目标 = 83~100（冲量 45 已计入），字段 22 → 32 → 41 …      ← 站台上"人聚得不够"
```

站停只有二十几秒，τ=90 s 在那个窗口里只走 **1/5** —— 于是加了第二条时间常数：
**冲量上冲用 `surgeTau`（默认 20 s），回落仍用 `tau`（90 s）**。改完实测同一条站台：

```
00:11:20  冲量=45  目标=83  字段=50
00:11:25  冲量=45  目标=83  字段=58     ← 每 5 秒 +6~8（上冲）
00:11:30  冲量=45  目标=83  字段=64
00:11:35  冲量=45  目标=79  字段=68
00:11:40  冲量= 0  目标=34  字段=66     ← 车走了：冲量归零
00:11:50  冲量= 0  目标=34  字段=62     ← 人慢慢散（回落）
00:12:00  冲量= 0  目标=34  字段=60
```

**这就是"车进站人聚、车出站人散"的全过程**，也是这套系统唯一一处"看数据才改对"的地方。

## 4 班次因子：不用配置就会分化

到站次数是**实测**的（车在这个站台上"进站已确认 / 出站未确认"的上升沿记一次，10 分钟半衰），
再按**最忙的那个站**归一。实机读数（重启后约 15 分钟，期间真作业单在跑）：

| 车站 | 计数 | 因子 | 目标（曲线 32 时） |
|---|---|---|---|
| 下水 | 4.94 | 1.00 | 35 |
| 鸥湾 | 3.46 | 0.89 | 31 |
| 内湾 | 1.96 | 0.79 | 50（当时有车停站） |
| 朗源 | 1.76 | 0.77 | 27 |
| 其余 6 座（还没跑过车） | 0 | 0.65 | 23 |

**没有一个数字是人填的**：谁忙谁不忙由车自己跑出来。

## 5 指令面

```
crowd status [--detail] | crowd why <站台hex>       # 读数（算式逐项）
crowd on | off | toggle | crowd now | crowd snap
crowd clock world|real | crowd profile 通勤|全天|夜间|空
crowd curve [show|<小时> <0-100>|<24 个数>]
crowd base <车站|站台hex|all> <0-100|default>
crowd tune [--period=秒 --tau=秒 --surge-tau=秒 --step=% --service=0-1 --surge=%]
crowd event add <+n|-n|x倍> <分钟|forever> [--station=<车站|all>] | crowd event list | crowd event clear [id|all]
```

`crowd status` 的那张三栏读数是现场判"生效没有"的唯一入口：
`目标`（算式结果）/ `字段`（写进 `crowdLevel` 的值）/ `平滑中`（还没写下去的那个值）。

### 6.2 实机（真 dev 服，真作业单在跑）

1. **关着不接管**：上水村 / TEST / 莫氏岛 仍是手填的 100%，其余 0；
2. `crowd on` → 下水 32%（曲线 32 × 因子 1.00）、其余 22%；服务端日志
   `[MMTR-CROWD] 客量已推送到客户端：22 条站台 ｜ …=30%（原 28%）…`（**跨端那一段真的在动**）；
3. RCON `time set 1000` → 小时档 **14 → 7**、曲线 **32 → 65**、目标立刻 65/42，字段按 τ 爬（时钟驱动成立）；
4. 真车停站 → 冲量 45、计数 +1、目标 83~100，上冲/回落曲线见 §3；
5. `crowd base 叶楼村 30` → 目标 ≈19，`crowd why` 里看到三级基准的解析；`default` 撤销后爬回 23；
6. `crowd event add +40 5 --station=岩壁` → 只作用于该站，5 分钟后**自动过期**；
7. **第二次换 jar 重启后配置整个活下来**：`enabled=true`、`profile=通勤`、`surgeTau=20`、叶楼村基准；
8. 存档直读：`mmtr-crowd-system.json`（411 B）＋ `platforms/<hex>` 里的 `crowdLevel` 与系统报的字段一致。

### 6.3 留下的状态

- 系统**开着**（`enabled=true`，随存档持久）——用户要的就是"自动动态"，要手填先 `crowd off`；
- 实机验证期间设的 `叶楼村 base 30` 与那条事件**都已撤销/过期**，没有给用户留奇怪的车站设置。

## 7 三条纪律（下次别再踩）

1. **"留了接口" ≠ "接口能到画面"**：`setModulator` 只改有效值，而有效值不跨端（notes/416 早就写过），
   所以做"自动动态"之前必须先回答"这个值走哪条路到客户端"；
2. **实体/平滑参数要在真的时间尺度上对**：站停 25 s vs τ=90 s 是 1:3.6 —— 离线怎么算都"对"，
   只有真车停一次才看得出"人聚不起来"；
3. **换 `game/libs` 的引擎 jar 之前，客户端也要退**（notes/216 那个坑在客户端那一侧一模一样）：
   本轮我先停服务端、换 jar、重启、装好新引擎，但用户的 `runClient`（22:43 起就在跑）没退 ——
   它的类加载器按**旧文件偏移**去读那个被替换的 jar，于是 `PacketUpdateData.update` 每 5 秒抛一次
   `Failed to load class file for 'org.mtr.core.operation.UpdateDataResponse'!` /
   `Caused by: ZipException: ZipFile invalid LOC header (bad signature)`，最后客户端退出（00:18:31）。
   **jar 本身没坏**（事后直读 `UpdateDataResponse.class` 正常、前 4 字节 `CA FE BA BE`），
   坏的是"运行中的那个 JVM 眼里的那一份"。修法 = **重开客户端**：重开后类加载错误 **0 条**，
   客流推送立刻生效（客量 16→24% 跟着 `crowd event` 走）。判据：
   **换 jar 之后，任何还活着的 JVM（服务端 + 客户端）都必须重启**，一个都不能漏。
