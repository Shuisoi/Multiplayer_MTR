# 115 - 道岔 × 信号：**一处道岔只有一个位置**

> 用户 2026-09-13 的规格（原话）：
> 「道岔为 0 时，逻辑上相当于 `-67, -60, -167` 节点与之相连，为 1 时，`-35, -60, -157` 与之相连，
> 同时这二者是互斥的会引发列车脱轨。所以在为 0 时，`-67, -60, -139` 到 `-35, -60, -157` 这段路
> 就应该以**禁止通行**为其属性，另一侧同理。同时信号灯的作用节点也不同，针对信号灯 `-64 -59 -139`，
> 若状态为 0，则保护北向轨道，若为 1，则保护南向轨道。完成这个道岔-信号逻辑重写」
>
> 两个当场定下的决策：
> **(a)** 背向（从被切断那一侧）开车 = **禁止** —— 车停在岔前，等道岔扳过来；
> **(b)** 所有道岔**不存在未知态**，只有 0 或 1，默认 0。

## 1. 改前的模型错在哪

引擎原来把道岔记成 **“每个进向各一份 0/1”**（`BranchStore` 键 = 节点 + 进向轨）。
那是**方向视图**，不是物理事实：一处道岔只有一个可动件、一个位置。三份视图各说各话的后果实测到了 ——
dev 世界 `-67,-60,-139` 的三行**全都是 0**，而其中“从侧线进来”那一行的 0 表示“侧线通往北轨”，
与“0 = 正线贯通”直接矛盾；更糟的是**从岔股开往正线远端**这种物理上不存在的组合会被放行，
现实里就是列车在尖轨处脱轨。

## 2. 新模型：一处道岔 = 一个位置 + 两根互斥的进路

`org.mtr.core.mmtr.point.MmtrTurnout`（纯几何推导，不依赖任何人工声明）：

```
        远端 far ────┐
                     ├── 根部 stem（两个位置都连通的那一侧）
        岔股 branch ─┘
```

- **位置 0（正线贯通）**：`stem ↔ far` 通，**branch 禁止通行**；
- **位置 1（岔股开放）**：`stem ↔ branch` 通，**far 禁止通行**；
- 从**岔股**出发永远只能回根部（且必须位置 1）；从远端出发只能回根部（且必须位置 0）。

`continuationFrom(viaRailHex, position)` 就是这个规则的唯一出口：返回“允许去的那根轨”，
禁止通行/无续行返回 `null`。`prohibitedRailHex(position)` = 用户要的“这段路以禁止通行为其属性”。

**怎么从几何认出这三条**（`MmtrTurnout.resolve`，只用度 3 节点 + 有序腿）：

1. **直股对**：互为“最直续行”的那两根轨 = `stem`/`far`；
2. **岔股** = 剩下那根；
3. **根部** = 从它看岔股 `cos > 0` 的那一侧（迎着开过去看得见它分出去）；
4. `|cos| <= 0.1` → 直角三岔口（TEE），**不认**（现实里那是两组道岔背靠背），退回原几何规则。

## 3. 三个接缝

| 接缝 | 文件 | 行为 |
| --- | --- | --- |
| **走行**（闸门） | `MmtrForkElection` | 位置由“行视图 + 本次授权”折出（`turnoutPositionFromGrant` 用的是**调用方给的那份授权表**）；`continuationFrom == null` → 返回 `null` = **车停在岔前**（决策 a）。取值顺序（人工位→授权→目标→唯一续行）不变，只加过滤 |
| **联锁扳动** | `Simulator.mmtrSyncTurnoutPositionToGrant`（每 tick）+ `mmtrSyncTurnoutPositionsToGrants`（全量） | 授权/进路要哪条腿，道岔就扳到哪个位置；授权释放后位置留在原地（人工位/默认位，人工随时可再扳） |
| **信号灯** | `MmtrDirectionalBlockService.applyTurnoutPosition` | **禁行的腿从这盏灯的视野里消失**；若它守的那条**正线**正好被切断，则退守**根部**；一条都不剩时保持原样（不当死灯） |

### 实测（dev 世界 `-67,-60,-139`，度 3）

南 `(-67,-139)→(-67,-103)` 36 m、北 `(-67,-167)→(-67,-139)` 28 m、岔股曲线 `(-67,-139)→(-35,-157)` 42 m。
解出 **stem = 南 / far = 北 / branch = 曲线**：

- **位置 0**：禁止通行 = 岔股；灯 `-64,-139`（面朝北）守 **28 m、航向 (0,-1) = 北** ✅ 与用户“为 0 保护北向”一致；
- **位置 1**：禁止通行 = 北；同一盏灯退守 **36 m、航向 (0,1) = 南（根部）** ✅ 与“为 1 保护南向”一致。

dev 世界共认出 **8 处**单开道岔：`-147,-169`、`-170,-161`、`-185,-135`、`-67,-139`、`-82,67`、`-96,76`、`1,-48`、`1,64`。

## 4. 行视图 = 派生，不是权威

一个位置，**三行派生**（`normalizeTurnoutRows`）：能走的进向写“该去第几条腿”，禁行那一侧写 `-1`
（行也要消失，否则“这一侧有续行”会骗到走行与显示层）。写入路径反过来折成位置
（`mmtrTurnoutPosition` / `MmtrTurnout.positionFromRows`），所以网页、指令、手改 `mmtr-points.json`
最终都落到同一个物理位置，不可能再互相矛盾。

- 老存档升级：没有节点级位置的，从行视图反推（`inferPositionFromRows`，任何进向选岔股 → 1），默认 0（决策 b）；
- `point set … -1`（清人工位）→ 回到 **0**，不再是“未知态停车”；
- web `mmtr-points` 每个点新增 `position`/`prohibited`/`stem`，每条腿新增 `prohibited`。

## 5. 本轮被**测试**逼出来的两个真 bug

1. **“从岔股回根部”被当成“不表态”**（`positionForLeg` / `mmtrTurnoutPositionForLeg`）。
   车尾在岔股上时，“我要回根部”恰恰就是“把岔股扳通”（位置 1）；旧实现返回“保持当前位置”，
   于是道岔扳不动、禁行闸门把车永远挡在岔前 —— `MmtrRouteConflictTests` 的 S5 排队场景实测到
   （侧线 2 的车请求出库，停在库门口 23.18 m 处“awaiting operator/task”）。
   现在 `positionForLeg` 按**进向**回答：`via == branch && leg == stemLeg → REVERSE`、
   `via == far && leg == stemLeg → NORMAL`、`via == stem` 才是不表态。
2. **`MmtrDirectionalBlockService` 只看“最直的那条腿”**：岔股被丢掉后灯会漏掉整个咽喉
   （`theThroatReadsThroughEveryBranchNotOnlyTheStraightestOne`）。

## 6. 用户当场问的那盏红灯：`-64,-59,-139` 为什么红

两个原因叠在一起，都在这一轮修掉了：

**6.1 显示层的假警报（单开道岔被判"岔口没人决定"）**

`MmtrJunctionState` 有两条"岔口清不掉"的规则 —— ①**岔区净空被占**（车压在这个节点 10 m 净空区里）、
②**岔口没人决定**（某个进向有 ≥2 条腿，既没有人工位也没有授权）。规则 ② 是"道岔未定 ⇒ 危险"时代的产物，
与决策 (b)「一处道岔只有一个位置、只有 0/1、默认 0，不存在未知态」直接冲突：**道岔位置本身就是决定**。
于是这处单开道岔被判"没人决定"，深度被钉在本层 → 守住它的**每一盏**灯都被压红。

修法：`MmtrJunctionState.reason(...)` 里，识别为单开道岔的节点直接跳过规则 ②（规则 ①照旧）。
顺带把**为什么清不掉**做成可打印的：`signal why` 现在在每个受限节点后面追一行
`原因 …：岔区净空被占：轨 FFFFFF… 靠这个节点的 10.0 m 内有车足迹` / `岔口没人决定：进向 … 有 2 条腿…`。
（"灯为什么红"必须一条指令读出来 —— 这一轮被"只报占用、不报受限原因"绕进去过三次。）

**6.2 真原因：那时灯被"退守"到了南向轨，而南向轨上停着车**

修掉 6.1 之后灯色仍会随道岔位置变：当时的实现是"位置 0 守北向 28 m、位置 1 **退守根部**南向 36 m"，
而南向那根轨正是车辆段 `test1` 的股道（那里停着一列车，足迹占弧 `10..26 m`）→ 位置 1 时它守的区间被占
→ `②占用=是 → depth=1 → RED`。当时 `signal why` 写的就是：`① 保护的轨 …（长 36 m）… ②[1] … 占用=**是** … ③ 深度 1 → RED`。

**用户随后否掉了这条规则**（见第 7 节）：现在这盏灯不再看道岔位置，也不再守南向那根轨。

用例：`MmtrSignalAspectTests` 里原 `anUndecidedForkAndAFouledJunctionRestrictTheSignal` 的夹具
（45° 岔口）其实**就是一处单开道岔**，它的"没人决定 ⇒ 红"在新模型下已作废；改成
`aTurnoutPositionDecidesTheJunctionAndAnUndecidedWyeStillHoldsDanger`：45° 道岔 → 绿（默认 0 即已定），
另加一个 **120° 三岔口（三角线：几何上不是单开道岔）** → 仍旧"没人决定 ⇒ 红"，人工位一设即绿。

## 7. 灯的保护范围：**不随道岔位置改变**（用户最终裁定）

原话："这个灯的灯光向南，保护向北的**所有**股道，那就是到 `-67,-60,-167` 和 `-35,-60,-157` 的。"
以及："现在不能手动设置某盏灯守某个道了。"

`MmtrDirectionalBlockService.applyTurnoutPosition(...)`（我按早先"0 守北 / 1 守南"那句话加的）做了两件事：
把**禁行那条腿从灯的视野里删掉**，并在它守的正线被切断时**退守根部**。后果是两个真问题：

- 灯守的轨随扳道岔**跳来跳去**（同一盏灯一会儿守 28 m 北轨、一会儿守 36 m 南轨）；
- **人工点选绑定被静默改掉** —— 绑到"当前被禁行那一侧"的灯，绑定看着生效、实际被覆盖
  （用户报的"不能手动设置某盏灯守某个道了"就是它）。

修法：**删掉这一层收窄**。灯永远守**它自己 FACING 那一侧的整组腿**（几何选腿 + 人工绑定），
道岔扳到哪一位都不变；道岔的禁行由走行侧的闸门负责（车停在岔前），不需要灯替它表达。
连带把上一轮加的"道岔位置要进区间缓存签名"补丁**回退**：区间视图现在根本不看道岔位置，不需要它失效。

部署后实测（dev 服务端，同一个节点、两个位置各读一遍）：

| 道岔位置 | `-64,-59,-139` 守的轨 | 灯色 |
| --- | --- | --- |
| 0 正线贯通 | `(-35,-157)→(-67,-139)`、`(-67,-167)→(-67,-139)` | GREEN |
| 1 岔股开放 | 同上**两条**（完全不随位置变） | GREEN |

候选轨一共三条（还含南向 `(-67,-139)→(-67,-103)`），它只守向北那两条 —— 与用户原话逐字一致。
人工绑定也实测过：`signal bind -64 -59 -139 --rail=<岔股那条>` → `boundExplicit=True`、只守 1 条，
**扳道岔到 1 之后仍然只守那 1 条**（修前会被改掉）；`--clear` 回到自动的两条。

用例：`MmtrDirectionalBlockServiceTests.theLampKeepsItsOwnLegsWhenThePointsMove`
（扳道岔前后守的腿集合必须相同，且不会把根部那条塞给这盏灯）。

## 8. 网页上的物理道岔操作（用户问"能不能正常设"）

能，而且这一轮把"看不懂"的部分补掉了。原来网页把**三行**当三个道岔画在同一个节点上，
菱形里的数字是**逐行腿号**：位置 1 时"正线远端"那一行的腿号是 -1，于是显示成"未设定（按 0 直通）"
—— 把"这一侧禁止通行"说成了"默认直通"。

现在：

- `mmtr-points` 每条目多给 `far` / `branch`（连同原有的 `position` / `prohibited` / `stem`），
  网页不必从"当前禁行哪一条"去反推另一条；
- **菱形里的数字 = 道岔位置 0/1**（物理道岔），逐行腿号退回卡片里当细节；
- 卡片多一块「物理道岔」：`位置 N（正线贯通/岔股开放）` + `禁行：正线远端/岔股（轨 …）`，
  根部那一行给**两个按钮**「0 正线贯通 / 1 岔股开放」（点它就是 `point set --via=根部 --branch=该位置的腿`，
  腿号按**轨**认，不按序号猜）；其它进向那一行只读，写明"位置由道岔决定，X 现在禁止通行"；
- 禁止通行的腿按钮划掉标红；扳不动的组合（例如从岔股写"去正线远端"）引擎会拒绝，提示改成"两条进路互斥，物理上不存在这个组合"。

端到端验证工具：`mmtr/tools/check-web-turnout.ps1`（单开道岔：**只画 1 个标记** → 面板 ↔ 引擎位置 →
点「位置 N」→ 引擎真的翻 → 禁行侧跟着换 → 地图点亮的轨跟着换 → **视图不回中** → 扳回原状），
与验老式岔口的 `check-web-points.ps1` 分工。它们 + `check-web-bind.ps1`（点选绑定）
+ `check-web-signals.ps1`（73 盏灯页面/引擎比对）本轮全部通过。

### 附：操作道岔时地图回中（用户报的另一个现象）

`MapCanvas` 的取景 watcher 原来是"**任何数据变化**就 `resetTouched()` + `fit()`"。可面板上每个操作
（扳道岔、看某盏灯为什么这个色、扫信号灯）都会走一遍 `load()` 重取数据 —— 几何一模一样，视图却每次回中、
缩放也退回 1×；更糟的是它先把"用户动过视图"的标记清掉，连"我已经平移过、别动我"这层保护也失效。

改法：比一份**几何签名**（节点/轨的条数 + 排序后的首末项）。签名没变 = 这是"状态刷新"（扳道岔、灯色、进路），
视图一动不动；签名变了 = 世界改画了，才重新取景。断言落在 DOM 上：扳动前后比较两盏灯标记的
`translate(...)` 与 HUD 的缩放读数，必须完全一致（实测 `745.611px, 618.549px | 719.823px, 612.962px | 1.00×` 前后不变）。

## 9. 用户现场校形：**正线 / 岔股到底是什么，网页为什么看起来像两个道岔**

用户 2026-09-13 看到网页后指出两件事，都对：

1. "这个道岔不是 `-67,-60,-103` 到 `-67,-60,-167` 是正线、到 `-35,-60,-157` 叉出去的吗？
   怎么 WEB 显示的是 `-67,-60,-139`→`-67,-60,-103` 是两个岔道不同去向？"
   —— 网页把引擎的**三行（每个进向一行）**当三个道岔画在同一个节点上，看起来就像"同处有三个道岔、去向各不同"。
2. "实际铁路不可能从 `-35,-60,-157` 直接开到 `-67,-60,-167` 啊。"
   —— 完全正确。可那一行（从岔股进来那一行）的腿列表里**确实列着正线远端**那条腿，因为接口给的是
   **几何腿号**："从岔股看正线远端"在几何上是一条腿。更糟的是老 `positionForLeg` 把它翻译成位置 0
   并**受理**了（实测：指令回"道岔已设定 … → 第 0 条腿"，位置真的变成 0）—— 等于在界面上承认了一条
   现实里不存在的进路。

三处修法：

- **网页：一处物理道岔只画一个标记**（`TopologyView.displayPoints` 按节点合并，留根部那一行）。
  卡片上不再列逐进向的腿，只给两个位置，并且**用坐标**写出这一位接通哪两条轨：
  `0 正线贯通 (-67, -103) ↔ (-67, -167)` / `1 岔股开放 (-67, -103) ↔ (-35, -157)`，
  外加一行 `禁行 正线远端 (-67, -167)`。不可能的组合**根本点不到**。
- **引擎：任何位置都不相连的组合一律拒绝**（`MmtrTurnout.positionForLeg`）：
  `岔股 → 正线远端` 与 `正线远端 → 岔股` 都返回 `MIN_VALUE`，`mmtrSetPoint` 不受理。
- **指令回复点名原因**（`MmtrPointCommands`）：实测现在是
  `设定失败：从岔股去正线远端这两条进路**互斥**（道岔只有位置 0/1），物理上不存在这个组合`，
  而不是笼统的"节点/轨不匹配"。

用例：`MmtrPointDefaultZeroTests.impossibleCombinationsAreRejected`（两个不可能组合都拒绝、
两个合法位置仍可用、被拒绝的请求不改动位置）。

## 10. 进路被道岔切断的灯必须是**红**（用户第四问）

用户 2026-09-13 指着 `-70,-59,-167` 问：「这个灯为什么是黄的，正常不应该是红的吗」。

**这盏灯**：立在正线北端、朝南 —— 管的是 28 m 那段正线，列车朝岔口开。道岔设 1 时北侧正线被切断，
车即使被放行也只能开到岔前停住 ⇒ 这条进路**根本走不出去**。原实现看不到这一层：它只在闭塞链上
往下找，看到"岔口另一侧那段（停在 test1 里的那列车）有车"，于是给**单黄** —— 语义上说的是
"前方有车"，而实情是"这条路不存在"。用户的判词对。

三处修法：

1. **走到头撞在道岔禁行侧 ⇒ 没有进路 ⇒ 红**：`walk(...)` 到节点时若"进来的那条轨"正是道岔当前位置
   禁行的那一侧，就把这一段标成 `blockedAtArrival`（`endReason` 写明"撞在道岔 … 的禁行侧"），
   `depthAt` 在这一层就命中（红），`followings(...)` 也不再往后连 —— 车永远不会进入岔口另一侧那一段。
2. **起点就被切断的腿不算进路**：`blockedAtDeparture`（灯就在岔口节点上、这条腿正是禁行侧）。
   它**不参与灯色计算**，但**仍旧是这盏灯守的轨**（用户要的"保护向北的所有股道"）——
   节点灯朝北时：正线那腿被切、岔股那腿开着 ⇒ 按岔股给颜色（绿），而不是因为被切的那条腿变红。
   一条能走的进路都没有时才给红。
3. **道岔位置重新进区间缓存签名**：走行到哪里为止、哪一段"撞在禁行侧"都取决于道岔位置。
   注意这与"灯守哪几条轨"无关 —— 守的轨不随位置变（§7），变的是**这些轨上的进路通不通**。

另外把 `signal why` 的深度复算**改成与显示层同源**（`aspectDepthFor`）：它原来自己重写了一份、
只沿单条链走（岔口另一支看不到），73 盏里有 6 盏自相矛盾（接口/网页读单黄、诊断说绿）——
诊断输出骗人比没有诊断更坏。

部署后实测（dev 服务端，同一个节点、两个位置各读一遍）：

| 道岔位置 | `-70,-59,-167`（朝岔口开） | `-64,-59,-139`（节点灯，守向北两条） |
| --- | --- | --- |
| 1 岔股开放（北侧正线被切断） | **RED** —— 诊断：`撞在道岔 -67,-60,-139 的**禁行侧**（道岔位置 1：这条轨禁止通行）→ 这条进路走不出去，按红显示` | GREEN（能走的进路是岔股那条） |
| 0 正线贯通 | SINGLE_YELLOW（贯通正线，下一段是停着车的 test1 股道） | GREEN |

全盘灯色由 50 绿 / 8 红 / 10 单黄 / 5 双黄 变成 **46 绿 / 13 红 / 8 单黄 / 6 双黄** ——
多出来的红灯都是"进路被道岔切断"（dev 世界里 `-147,-60,-169`、`-185,-60,-135` 也在位置 1，同理）。
接口 73 盏与 `signal why` 复算现在**逐个一致（0 处不一致）**。

用例：`MmtrDirectionalBlockServiceTests.aRouteCutByThePointsReadsRedNotCaution`
（位置 0 绿 / 位置 1 红 + `blockedAtArrival` 标志）。
注意道岔位置是**落盘**的，用例开头要显式归零、结尾扳回，否则第二跑会带着上一跑的位置（实测踩过）。

## 11. 用户第五问：道岔扳回 0 后那盏灯还是双黄（**区间 id 撞车**）

现象（用户实测，我照原样复现了）：道岔设 1 时 `-64,-59,-139` 正确变**双黄**（岔股那条链在第三段看到
test2 里新生成的 SAF101），手动扳回 0 之后它**还是双黄** —— 应该变**绿**。

根因不在规则，在**标识符**：一灯多腿时每段的 id 原来是

```java
key + "#" + shortHex(protectedRail.rail.getHexId())   // shortHex = 前 6 位
```

而 dev 世界的轨 hex 前十几位几乎全是 {@code F}（坐标都是负数）⇒ 同一条灯的两段腿都叫
`-64,-59,-139#FFFFFF` ⇒ {@code followingBySection} 这个**按 id 索引**的表把两条链并成一条：
朝正线那条腿于是继承了岔股那条腿的后续（第三段上停着车）⇒ 链深 3 ⇒ 双黄。

修法：id 后缀改成**腿序号**（`#1` / `#2`）—— 既唯一，又与"第几条腿"一一对应，比截 hex 可靠。
实测（同一个节点，扳来扳去）：

| 道岔位置 | 灯 `-64,-59,-139` | 逐腿明细 |
| --- | --- | --- |
| 1 岔股开放 | DOUBLE_YELLOW | 岔股腿 42 m 链深 3（第三段是 test2 里那辆 SAF101）；正线腿 … |
| **0 正线贯通** | **GREEN** | 岔股腿被标成"**道岔禁行侧**：不是进路，不参与灯色"；正线腿 28 m 链深 0 |

顺带把两件事一起收敛了：

- `blockedAtDeparture`（起点侧被道岔切断的腿）现在**在 `buildSection` 里统一判定**，不再散落在各个
  选腿分支里 —— 只在其中一条分支标过，另一条走的就是"被切断的腿照样算进路"，现象同样是灯色不对。
- `signal why` 的 ③ 结论改成与显示层**同一套规则**（跳过被切断的腿、一条不剩才给红），
  并在逐腿明细里点名"这一条是道岔禁行侧，不参与灯色"。诊断输出骗人比没有诊断更坏 —— 这已经是第三次。

影响面：dev 世界有 **3 盏**多腿灯（`-145,-169`、`-157,-189`、`-64,-139`）都在这条撞车路径上，全部一起修好。
全盘灯色随之变成 45 绿 / 14 红 / 9 单黄 / 5 双黄；四个网页端到端脚本（灯色比对 / 老式岔口 / 单开道岔 / 点选绑定）全过。
