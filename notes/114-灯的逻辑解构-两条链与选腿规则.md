# 114 - 灯的逻辑解构：两条链 · 一个选腿规则

> 用户 2026-09-13：「先把灯的逻辑解构一下吧，目前完全乱套了」，并要求以
> **`-70,-59,-139` 这盏灯（角 0，对着 north 亮，显示 depot 区间状态）为基准**把服务端与 web 的数据捋明白。
> 本笔记是那次解构的结论 + 当轮修掉的两个真 bug。

## 1. 先说结论：存在**两条互不相干**的链，必须分开看

"灯显示什么颜色"这个问题在这个工程里有**两个**答案，它们的数据源、单位、判据都不一样。
把两者混着看，就是"乱套"的来源。

| | **链 A：闭塞区间 v2（权威）** | **链 B：逐轨链（遗留，仍在跑）** |
| --- | --- | --- |
| 单位 | **灯到灯的区间**（可跨多根轨） | **单根轨** |
| 谁算 | 引擎 `MmtrDirectionalBlockService` | 客户端 `MmtrSignalChain`（纯函数，有单测） |
| 判据 | 区间的有向跨度 + 占用足迹重叠 | 沿轨链往上数最多 3 根轨 |
| 出口 | `lampAspectNames(...)` | `RenderSignalBase.mmtrChainDepth(...)` |
| 谁在读 | 游戏渲染器（经镜像）· web 信号层（`mmtr-signals` 的 `aspect`）· `signal why` ③ | 游戏渲染器**兜底**（链 A 没给这盏灯答案时） |

**渲染色取自哪一条**（`RenderSignalBase.mmtrEngineAspect`，第 135 行）：

1. 先查镜像缓存 `MmtrClientRoutes.lampAspect(x,y,z)`（内容 = 链 A 的结论，由服务端 `MmtrRouteMirror`
   每 tick 在有变化时下发，包体 `PacketMmtrRoutes`）；
2. 查得到 → **用链 A**；
3. 查不到 → 退回 `localDepth` = **链 B**。

**web 上的灯色取自链 A**（`SystemMapServlet.getMmtrSignals` → `lampAspectNames`）。

所以"web 与游戏对不上"只有三种可能，查的时候按这个顺序：
(a) 镜像还没下发（刚进世界/刚重启），游戏那一瞬在读链 B；
(b) **链 A 自己算错了**（本轮修的就是这个）；
(c) web 页面没刷新。

> 另有一份**逐轨**的颜色 `MmtrSignalAspect.aspectsForAllRails()`（`mmtr-rails`/`aspects`），
> 它是链 B 口径的对外投影，**不是**灯显。两个都叫"aspect"，看接口名区分。

## 2. 链 A 内部的分工（这是"守哪条腿"真正决定的地方）

```
灯（注册表：坐标 + 角度 + 面数 + 模式）
  └─ ① 选腿   resolveLegByPointState(...)      ← 本轮改成"半平面全收"
       └─ ② 建区间 buildSection(每条腿各一段)   ← 一段 = 从灯走到下一盏灯
            └─ ③ 连链 following(...)            ← 段尾节点上找"起步的段"
                 └─ ④ 深度 depthAt(...)         ← 本级占用=红；下一段=单黄；再下一段=双黄；否则绿
                      └─ ⑤ 显示 lampAspectNames(...)  ← **多腿取最不利的一条**
```

**①②③④⑤ 每一层都已经支持"一灯多腿"**（`sectionsBySignal` 是 `key → List<Section>`，
区间 id 在多腿时带 `#轨hex` 后缀）。本轮之前唯一不支持的是 **①**：它只留**一条**腿。
于是下游那套多腿支持一直是空转的。

### ① 选腿：用户的规则（2026-09-13 拍板，两问确认）

> **基准点**（用户原话）：「{@code -70,-59,-139} 这盏灯它发光面是**朝北**的，它接管的是
> {@code -67,-139} 到 {@code -67,-103} 这段」
> **方向**（用户原话）：「车**从北边**（z 更小）开过来」
> **两盏灯**（用户确认）：「-70 管南段、-64 管北段」

翻成代码（`resolveLegByPointState`）：

1. 取最近的节点（`NODE_BIND_RADIUS_M = 4.0`；灯方块两格高，实测常离节点 3.16 格）；
2. 对节点上的**每一条腿**，算它**从节点朝外**的方向（`awayFromNode`）；
3. **与灯朝向点积 `< -0.1` 的腿全部留下** —— 即 **灯管它面朝方向的"对面"那一半**；
4. 一条都没有时退回全部腿（不让灯变成"不参与闭塞"）；
5. 顺序按"朝外长度降序"定死（区间的头一条是入口轨，不能让遍历顺序决定它）。

**为什么是这个方向**：司机在**被守护的那段**上、**迎着灯面**开过来 —— 过灯之后才进入下一段。
锚点的车正是从北边开来、看着朝北的灯面，过灯后进入的是南段，而灯管的正是南段。铁路惯例一致。

> **这一条翻转是本轮最关键的改动。** 原来的实现是"同向才算它守的腿"（点积 `> 0.1`），
> 恰好相反 —— 于是朝北的灯去守北边那条空线，车停在南边那条上：**游戏里红、web 上绿**。

### 被删掉的三个"判据"

（同前，略）—— 它们都曾经参与选腿，逐个都有实测反例，删掉是为了让规则只剩一句话。

### 跨度方向：必须用"腿的外向"，不能用"灯的朝向"

`ProtectedRail` 现在存**两个方向**：`headingX/Z` 是**区间走行方向**（= 腿从节点朝外的方向），
`lampX/Z` 是**灯面朝向**（= 走行的反面）。

以前只存一个、且填的是**灯朝向**，于是朝北的灯去建"往北"的跨度 —— 而它守的那条腿是往南的，
`buildSection` 按灯朝向选方向，把跨度建到了**对面那条轨**上。实测诊断串：

```
[占用诊断] span=000000 弧0.0..30.0 railByHex=有 树层数=1 端点=(0,0,-30)→(0,0,0) 层0:足迹=取不到
```

灯守着 40 m 的南腿，建出来的 span 却是北边那条 30 m 的轨 —— 于是它自己的区间永远读不到停在
南腿上的车，灯永远绿。**方向翻对之后锚灯立刻变红（实测 `③ 结论：深度 1 → RED`）。**


| 删掉的 | 为什么是错的 |
| --- | --- |
| **"前方余长"按行向算**（`leg.forward` 决定 `弧长-节点弧` 还是 `节点弧`） | 进库 stub `(-67,-139)→(-67,-103)` 的弧增方向指向节点，于是"前方余长"算出 **0**，整条腿被当"前方无轨"丢掉。行向说的是"列车沿这根轨往哪边走"，与"灯面前有没有路"无关。现在用 `away·长度`。 |
| **端点距离**（灯的投影离节点多近） | 它算的是 `节点→灯` 的模，**对所有腿都是同一个数**，从来没在腿之间分过胜负，只是日志里看着像判据。 |
| **`朝灯 > 0` 就排除** | 前提是"灯立在节点旁、腿朝灯伸过来"。锚点的进库 stub 与 `节点→灯` **垂直**（点积 0），这条判据对它无效，却把环线判走了。 |

## 3. 本轮修掉的两个真 bug

### bug 1：选腿只留一条 → 库里的车看不见（用户："游戏里红、web 上绿"）

锚点 `-70,-59,-139`（角 0 = 朝北）在节点 `(-67,-139)` 上，北侧有**两条**腿：
进库 stub `(-67,-139)→(-67,-103)`（36 m）与东北环线 `(-67,-139)→(-35,-157)`（42.3 m）。
旧实现按点积只留环线那条，而车停在 **stub** 上（`testX = -66.5, Z = -128.5`）——
于是灯守着一根空轨，永远绿。

修后明细自己说话：
`[选腿] ... 指向=(0.87,-0.49) 与朝向点积=0.49 | 指向=(0.0,-1.0) 点积=1.0 | 指向=(0.0,1.0) 点积=-1.0（灯朝的那个半平面里有 2 条腿，都要守）`
`②[多腿] 这盏灯守 2 条腿 ... · id=…#42m 占用=否 · id=…#52m 占用=否`

### bug 2：节点的游戏内朝向，引擎根本拿不到

引擎的拓扑里节点**只有坐标**。而节点朝向（`BlockNode.getAngle`：`FACING`/`IS_22_5`/`IS_45` 三个方块属性，
放置时由玩家朝向定）是原版渲染 `RenderSignalBase.getAspectState` 用的那个值。
现在由 `signals scan` 采集上报（`Simulator.mmtrNodeAngles`），并在 `mmtr-topology` 的节点上多出 `angle` 字段。

**两个坑（都踩过）**：
- 节点**不是方块实体**：第一版把节点判定写在 `chunk.getBlockEntities()` 的循环里，一个都没采到
  （实测：137 个节点，带 angle 的 0 个）。现在改成"只去引擎已知的节点坐标查方块状态"，
  按区块分组、只查登记过节点的那些格。
- **节点角与灯的角不在一个体系**：实测 137 个节点里 119 个是 90、15 个是 0（还有 1 个 112.5），
  而灯的角全是 0/180。同一个节点上两盏朝向相反的灯共用同一个节点角 ——
  所以"灯的朝向换算"推不出节点角，两者要分别采集。

> 用户对节点角的定义：「节点 0 就是上下的，90 就是左右的」= **这组轨的直通方向**。
> 注意它**不是**"灯守哪条腿"的判据（同一节点两盏反向的灯，节点角是同一个）；
> 它是"哪两条腿是一对贯通轨"的判据，留给道岔/进路那一层用。

## 4. `signal why` 的口径（本轮补齐）

- ① 走的是 `describeProtectedRailCandidates`，为了和主路径同口径，结论行已改成**列出全部守轨**；
- ② **新增 `②[多腿]` 一节**：逐条腿列出 `id / 长 / 占用 / 段数 / 链深`，并把每条腿的 span 展开
  （hex 打**全**，不再截断 —— 截断过的 hex 认不出是哪根轨，实测绕过好几轮）；
- ③ 仍与显示层同规则复算。

## 5. bug 3（本轮真正的那一刀）：占用树**取错了键**

锚点守的腿对了（3 条都收），区间也建对了，可库里那辆车就是读不到。加了一条 `query occupancy`
把占用树里**真正记着的轨**打出来，一眼定案：

```
占用树 2 层，共 16 条轨上有足迹：
  (-67,-139)→(-67,-103)  车=[-4282003469230822656]  足迹=[10..26]     ← 车就在进库 stub 上
  ...
```

车在（足迹 10..26 正对车头 z=-128.5），可区间报 `占用者=无`。原因是**取值用的端点对顺序**
和树里存的是反的：占用树是两级映射（轨的一端 → 另一端 → 足迹），轨是无向的，两个端点谁在前
都应当等价，而 `rail.mmtrOrderedPositions()` 的顺序来自轨的声明顺序，与车辆写入时用的顺序**可以相反**。

修法：新增 `MmtrDirectionalBlockService.footprintOn(tree, ordered)` —— 正反两对键都试一遍，
并把**全部 8 处**同一口径的取值都换过去（`isOccupied` 两处、`boundaryNodeKeys`、区间视图、
`MmtrJunctionState.unclearedNodeKeys`、`signal why` 的 `ownersOn` 等）。

> **为什么 526 条用例一条都没抓到**：测试夹具 `occupancy(rail, from, to)` 用的键顺序与产品代码
> 完全一致，于是"反向的那一半"从来没被测过。补了
> `theOccupancyTreeIsReadWhenItsKeyOrderIsReversed`（把夹具的键**反过来**放），全量 **528 / 0 / 2**。
> 教训：**夹具与实现共用同一个"约定"时，这个约定本身就没有被测试。**

## 6. 部署事故（工具化，避免重犯）

在服务端**还活着**的时候覆盖 `game/libs/Transport-Simulation-Core-0.0.1.jar`，等于把 Fabric
类加载器正在读的 zip 换掉一半：

```
Caused by: java.io.EOFException: Unexpected end of ZLIB input stream
  at net.fabricmc.loader.impl.launch.knot.KnotClassDelegate.getRawClassByteArray
```

症状不是"崩了"，而是更坏的一种：服务端 tick 持续抛异常、**车辆全部消失**（`MMTR-HLTH vehicles=8 → 0`）、
`mmtr-command` 完全不应答（请求超时），而地图接口照样回 200 —— 看起来像"引擎卡死"。
恢复只能杀掉这一轮让它用完整 jar 重启。

新增 `scripts/deploy-engine.ps1`：**判据用"进程还在不在"**（半个 jar 的状态下 8888 照样应答），
进程在就拒绝拷贝并提示先停；`-Build` 先打包，`-Force` 才允许强拷。

## 7. 验证

- 引擎全量 **528 / 0 / 2**。既有用例**零期望值改动**（除了锚点那条测试改成断言"守 2 条腿"）——
  说明"一灯多腿"在下游早已就位，本轮只是让 ① 真的产出多条腿 + 让 ④ 真的读到占用。
- 锚点实测：`②[多腿]` 两条腿各成一段；三条 span 解出来是
  东北环线 `(-67,-139)→(-35,-157)` 42 m、向南主线 `(-67,-167)→(-67,-139)` 28 m、
  **向北 stub `(-67,-103)→(-67,-167)` 0..24**——也就是灯朝向的那个半平面上的腿全在。

## 8. 未结

- 客户端链 B（`MmtrSignalChain`）与链 A 仍可能给不同答案；镜像下发前的那一瞬间就是"web 与游戏对不上"的
  一类现象。长期看应当让链 B 退成"仅用于没有 v2 区间的轨"，而不是一盏灯的兜底。
- `signal why` ① 与选腿新规则现在同口径（列出全部守轨），但 `describeProtectedRailCandidates` 内部
  仍在用"6 格内最近投影"那一套打分来列候选 —— 只用于展示，若以后要拿它当判据需先统一。
