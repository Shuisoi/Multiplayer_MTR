# 324 - 轨道沉进地基 + 连接线没有节点：QUADRATIC 的纵向是抛物线

> 用户口径（2026-09-26，接 notes/323 的首次实跑）：
> 「轨道略微有问题，一方面是没有节点没法放信号灯，另一方面是部分轨道沉到了地基以下。」
> → 追问后选择「现在就回滚重建」。

**两个现象是同一个根因。** 修完已重打，四层验收 + 专项扫描全绿。

---

## 1. 根因：`Shape.QUADRATIC` 的纵向剖面是**抛物线**，不是直线坡

`rail add` 建轨固定用 `Rail.newRail(..., Rail.Shape.QUADRATIC, 0, ...)`。
而 `RailMath.getPositionY`（`mmtr/engine/.../data/RailMath.java:537`）的默认分支是：

```java
final double intercept = length / 2;
...
return yChange * offsetValue * offsetValue / (intercept * intercept) + yInitial;
```

**y 是 `value²` 的二次式** ⇒ 前段比两端连线高、后段比连线低，
最大偏差 `|Δy| / 8`（两端 `yStart/yEnd`，中点是准确的中值）。

notes/323 那条连接线：**一根 1521 m 的单轨从 75 降到 71**，Δy = 4 ⇒ 偏差 **±0.5 格**。
而我的路基是按"直线坡"算的（顶 = `round(py) - 1`）⇒ 后段路基顶压到轨面以上，
**轨道看起来沉进了地基**。

顺带同一个根因给出第二个现象：**整条连接线只有两个端点、没有中间节点**
（`rail add` 一条命令 = 一条轨），所以**没法摆信号灯**。

> ⚠ 别再相信"坡就是直线连"：Δy 越大越明显。Δy=1 时偏差 0.125 格（不可见），
> 这也是既有爬坡段（每段 1 格）一直没暴露这个问题的原因。

---

## 2. 既有线早就有正确的做法，我没照做

`gen_line_climb.py`（爬坡段生成器）里有两条关键约定：

```python
deck_top = min(ya, yb) - 1        # 路基做成**平顶**，取该段**低端**轨面
nodes = 每 100 m 一个 + 端点       # 直线段切成节点
y = round(线性插值)                # 每段最多升降 1 格
```

⇒ **每段 Δy ≤ 1 格 ⇒ 抛物线偏差 ≤ 0.125 格（不可见）**，而且节点每 100 m 一个。

---

## 3. 改法（`route_geom.py` 重写几何部分）

| 规则 | 内容 |
| --- | --- |
| **弧一律水平** | 弧的两端等高 ⇒ `getPositionY` 直接返回常数（`yStart == yEnd` 那一支），**零偏差** |
| **坡度只走带节点的直线段** | 每 100 m 一个节点、`y = round(线性插值)`、每段 Δy ≤ 1 |
| **路基逐段平顶** | `top = min(该段两端轨面) - 1`（照 `gen_line_climb.py`） |
| **曲线段也要有直线垫** | `shift` 模式：S 弯（水平）+ 弯后直线；`turn` 模式：直线 + 弧 + 直线 |

新的 `shift` 几何（同一个 `--to 4031 2312`）：

```
2520 ──[S 弯 745 m 纵向，R=400，**水平 y=75**]──> 3265
3265 ──[直线 656 m，节点每 100 m，轨面 75→74→73→72→71]──> 3921 ──[新站 220 m]──> 4141
```

S 弯的纵向长度由半径决定：`L_s = sqrt(4·|o|·R − o²)`（`o` = 横向错开量）。
`R` 太小（`< |o|/4`）或**弯后剩不下直线**都会直接报错，不再"先铺了再说"。

## 4. 顺手修掉的两个同源小 bug

| 现象 | 真因 | 修法 |
| --- | --- | --- |
| 斜段路基边缘离轨最多 4 m | 每个路基方块在**沿线路方向各撑了 5 米**，而斜段中心线在这 5 米里已经横移了 ~4 m | 方块只在自己的 1 米上取值（不再外撑），横向另给余量 |
| 靠后的清障把靠前的路基删掉 | 路基方块互相重叠，而**清障（air replace）按段顺序在后**，会把前一段已经铺好的平顶削掉 | 不再外撑 ⇒ 段间不再重叠，问题自然消失 |

## 5. 新增专项检查：`sandbox/check_rail_above_deck.py`

**这类错引擎一个字都不会报**（`rail list` 正常、指令回 ok），所以必须读存档自己比：

```
用 route_geom 把同一套参数重算一遍（纯算术）→ 拿到"哪一段轨面是多少"
→ 去存档里读该处两条轨位置上的方块，从轨面上方往下扫
→ 判据：路基顶 <= 该段低端轨面 - 1
```

⚠ 扫描时**必须跳过 `mtr:` 那一族** —— 节点方块本身就在轨面上，
不跳过会把"轨"当成"路基"，整条线全是假警报（第一版就是这么错的，当场修掉）。

实测（重打之后）：

```

抽查 338 处（两条轨都查）
最高的一处：路基顶 y=74，该段低端轨面 75，应到 74 ⇒ 高出 0 格
✔ 没有一处路基顶高过「该段低端轨面 - 1」
```

## 7. 教训（已写进 skill）

1. **`rail add` 能画曲线，但"曲线 + 坡度"要分开**：弧水平，坡度走直线。
2. **一条轨就是一个节点对**：要节点就得切段；而**曲线不能切段**
   （分成子弧会得到 `R = min(along, lateral)` 的错半径）⇒ **曲线段天生没有节点**，
   摆灯只能靠它前后的直线段。
3. **凡"引擎不报错但结果不对"的，都要有独立检查器**：这次的
   `check_rail_above_deck.py` 就是这类。光靠 `rail list` 永远发现不了。
