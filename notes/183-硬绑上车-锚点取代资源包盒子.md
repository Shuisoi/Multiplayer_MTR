# 183 · 硬绑上车（锚点取代资源包盒子）

> 用户实机反馈："上不了车了哎" → 提供关键线索："**有一个改动是列车高度**，可能是这个原因，
> 所以能不能直接**死绑视角和玩家位置到车上**？"

这条线索是对的，而且指向的是一整类问题，不是一个 bug。

---

## 1. 为什么"上不了车"最可能是几何对不上

MTR 判定玩家能不能上车，问的是**玩家世界坐标是否落在资源包声明的盒子里**
（`floors` / `doorways`），即 `RenderVehicleHelper.boxContains`：

```java
// RenderVehicles
openDoorways.forEach(openDoorway -> {
    if (MmtrCabPermissions.canBoard(clientPlayerEntity, vehicle.getId())) {
        openFloorsAndDoorways.add(openDoorway.left());   // ← 只有这个列表里的门洞能上人
    }
});
...
VehicleRidingMovement.startRiding(openFloorsAndDoorways, ...);   // 里面才是 boxContains
```

盒子与模型对齐时这套完全正确。**一旦两者不一致，失败是彻底且静默的**：
玩家可以站在门口、看得见车、准星对着车，就是上不去 —— 因为判定用的盒子在别处。

**改变列车高度就足以触发**（整体抬高、改地板高度、重导模型都会）。
而且这类问题**没有好症状**：

| 症状 | 同一个根因 |
|---|---|
| 门开着但上不去 | 盒子不在玩家脚下 |
| 走进去被弹出来 | 盒子在玩家身体里，每帧把他推出去 |
| 这个站台上得去、那个上不去 | 站台高度不同，只有一处盒子碰巧对上 |

三种都要花一整轮进游戏复现。

## 2. 出路：用**锚点**代替盒子

模型**已经**声明了门在哪里 —— `mmtr_cabdoor_<cab>_<n>` 锚点，`MmtrVehicleAnchors` 已经能读出来。
**锚点是车体自身坐标系里的一个点**，所以它天然跟着模型走，没有东西需要对齐。

于是判定从"世界空间盒子包含"换成：

1. 玩家挨着哪节车（水平距离最近的车中心）？
2. 那节车有没有门的锚点在 `REACH_M` 以内？
3. 有 → **把玩家绑到那节车的那个锚点上**。

这就是用户要的"死绑视角和玩家位置到车上"。**没有盒子可以歪**，所以抬高模型、改地板高度、
改门洞几何都不可能再让上车失效。

## 3. 实现（`MmtrBoarding`）

新增 `game/fabric/.../client/MmtrBoarding.java`，由 `MmtrCabInteraction.tick()` 每 tick 调用一次
（就放在驾驶室按键处理**之前**，这样刚绑上去就能按 G 进驾驶室）。

```java
// 每 tick：找最近的可上车的车 + 最近的门锚点
for (VehicleExtension vehicle : MinecraftClientData.getInstance().vehicles) {
    if (VehicleRidingMovement.isRiding(vehicle.getId()) || Math.abs(vehicle.getSpeed()) > MAX_BOARDING_SPEED) continue;
    for (每节车) for (每个 mmtr_cabdoor 锚点) {
        Vector world = car.transformForwards(anchor.position, rotateX, rotateY, add);   // 与驾驶室代码同一条路
        if (|Δy| > REACH_Y_M) continue;
        if (Δx² + Δz² < best) best = ...;
    }
}
// 绑上去
VehicleRidingMovement.mmtrPlaceRiding(depotId, sidingId, vehicleId, carNumber,
        door.position.x(), floorY, door.position.z() + 向内 0.55, carYaw, 朝车内 yaw);
VehicleRidingMovement.mmtrSetCabLock(false);   // 乘客仍可走动
```

### 关键参数与理由

| 常量 | 值 | 为什么 |
|---|---|---|
| `REACH_M` | 2.0 | **水平**判定。刻意收窄：这是"站在门口"，不是"在站台上"。 |
| `REACH_Y_M` | 2.5 | **垂直**容差，比水平宽得多 —— **抬高/降低的模型正是这个功能存在的理由**，一辆抬到站台高度的车很容易比玩家高一个半方块。 |
| `STEP_IN_M` | 0.55 | 绑进门内一点，不站在门框里。 |
| `MAX_BOARDING_SPEED_M_PER_MS` | 1e-4 | 走不上正在动的车。 |

**垂直方向只做门限、不参与"选哪个门"的排序**：这是刻意的。否则一辆被抬高的车会因为垂直距离大
而选不中任何门 —— 那正是我们要绕开的那类失败。

### 蹲下 = 明确拒绝

```java
if (((net.minecraft.entity.player.PlayerEntity) player.data).isSneaking()) return;
```

没有这个开关，近距离自动绑定会变成**牵引光束**：想沿着站台走过去都不行。蹲下是玩家说
"我就站这儿"的唯一手段。

### 已绑上就不再动

`boardNearestTrain` 一开始就 `if (VehicleRidingMovement.isRiding(vehicle.getId())) continue;`，
所以它**从不和 `VehicleRidingMovement.movePlayer` 抢人** —— 绑上去之后怎么走，还是原来那套逻辑。
这是避免 notes/177 那个"两帧之间来回抽搐"的关键：**绑一次，不是每帧按**。

## 4. 没被替换的东西（重要）

| 仍然走盒子 | 为什么 |
|---|---|
| 门的**位置**、门扇滑动 | 美术问题，盒子对不上是资源包的事，不该由代码兜 |
| 廊道（gangway） | 同上 |
| **已经在车上之后的走动** | `movePlayer` 每 tick 仍然用盒子判定玩家在车内能站哪。**只换了"上车那一下"的判定** |

也就是说：硬绑解决的是**入口**，不是车内几何。如果模型抬高之后**车内走动**也不对，
那是另一个问题（盒子/地板需要跟着模型改），本轮没动。

## 5. 第二轮：视角必须落在 `mmtr_seat` 上

用户实机反馈："上车是上车了，**但视角没有在 `mmtr_seat` 上**"。

### 5.1 我第一版错在哪

第一版绑的是**门锚点**：

```java
final double localX = door.position.x();
final double localZ = door.position.z() + towardCentre * STEP_IN_M;   // ← 门在车侧
```

门锚点在**车的侧面**，座位在**台子前面**。saf101 的实测量级：

| 锚点 | ride-space |
|---|---|
| `cabdoor_1_1` | (2.406, 3.0, 3.993) |
| `seat_1` | (0.75, 3.5, 4.993) |

X 差 **1.66 m** —— 所以人进得去，但相机站在门口，不是坐在驾驶位。

### 5.2 现在的解析顺序

用**和按 G 进驾驶室完全同一条路**（`MmtrVehicleAnchors.cabView`），保证"上车"和"坐下"落在同一点：

```
X/Z  ← cabView.x / cabView.z
       （内部：显式 mmtr_seat 锚点优先，否则由 mmtr_hud 的法线往后退 EYE_BACK_M 推导；
         单端车模型 cab 2 会镜像到 cab 1）
Y    ← mmtr_seat.position().y − 1.62   （+ `movePlayer` 的地板钳制兜底）
Yaw  ← 座位锚点的水平法线 → 车体局部方向 → 世界朝向
```

**为什么 Y 要减 1.62**：`mmtr_seat_<cab>` 是**按司机眼睛位置**画的（saf101 实测 `normal=[0,0,1]`，
座位在地板 **+1.03 m**，正是坐姿眼高）。而 riding 状态里的 Y 是**脚的位置** —— 相机在它上面 1.62。
不减就直接高一个头。

### 5.3 读了 `movePlayer` 才知道的关键事实

相机**不是**跟着玩家实体走的。`RenderVehicles` 第 85 行：

```java
offsetVector = getRidingVehicleCarNumberAndOffset(...).right().left();   // = ridingPositionCacheOld
```

即**相机的车体局部位移来自 riding 状态**。而 `VehicleRidingMovement.movePlayer` 每 tick：

```java
ridingVehicleX += movementX + clampX;   // ← X 保留（可走动）
ridingVehicleY = maxY;                  // ← ★ Y 被地板钳制覆盖
ridingVehicleZ += movementZ + clampZ;
if (offsets.isEmpty()) { /* 没有地板 → 直接下车 */ }
```

所以：

- **X/Z 由座位锚点说了算** → 这就是"视角在不在 `mmtr_seat` 上"的判据；
- **Y 由车内地板说了算**，而且**离地板超过一个方块会被直接丢下车**；
- 因此把 Y 写成"座位 Y"是错的（会浮空 + 可能掉下去），写成"座位 Y − 1.62"是正确的 ——
  它决定**第一帧**，之后地板接管。

> 这也解释了为什么"改列车高度"能同时影响上车和视角：**地板钳制用的是资源包的地板盒**。
> 模型抬高而地板盒没跟着抬，Y 就落在旧高度上，相机也跟着错。

### 5.5 第三轮：Y 必须**锁存**，否则被地板钳制吃掉（"视角过于低"）

用户反馈："**视角过于低了，不在 `mmtr_seat` 的中心**"。

上一版把 Y 写成 `座位眼高 − 1.62` 是**对的算法、错的位置** —— 它只活了**一帧**。
§5.3 那条 `ridingVehicleY = maxY` 每 tick 把 Y 换成**资源包地板盒**给出的值，
所以相机最终 = 地板盒 + 1.62，而不是座位锚点。地板盒偏低（模型抬高后尤其明显）→ 视角偏低。

**这次真的修了**：新增锁存 `mmtrLockedSeatFootY`。

```java
// movePlayer 里
ridingVehicleY = Double.isNaN(mmtrLockedSeatFootY)
        ? maxY                    // ← 站立乘客：Y 由地板盒决定（"在不在车上"也靠它）
        : mmtrLockedSeatFootY;    // ← 坐在座位上的：Y 来自 mmtr_seat 锚点
```

**为什么这个值真的能驱动相机**（先验证过再改）：`movePlayer` 最后是

```java
clientPlayerEntity.updatePosition(x, y, z);   // 把玩家实体瞬移到车体坐标算出的世界位置
InitClient.scheduleMovePlayer(runnable);      // 客户端 tick 末尾再来一次，避免橡皮筋
```

而 `RenderVehicles` 取相机偏移量就是 `ridingPositionCacheOld`（= riding 状态）。
所以**改 riding Y 就是改相机**，这条路是对的 —— 上一轮纯粹是实现顺序写错了。

| 决定 | 理由 |
|---|---|
| X/Z 钳制**照旧**，`offsets.isEmpty()` 的**下车**判定照旧 | 只换 Y。地板盒仍然是"人在不在车上"的权威 |
| **只对钉住的座位**生效，站立乘客不享受 | 乘客的 Y **应该**来自地板 —— 那正是"站在车上"和"走出车外就下车"的机制 |
| 两条入口都钉：按 G 进驾驶室（`MmtrCabInteraction.placeAtCabView`）与硬绑（`MmtrBoarding`） | 两条路会遇到同一个"偏低" |
| `mmtrSetCabLock(false)` / 下车 / 掉出车外 都会清掉锁存 | 否则残值会钉死**下一次**乘车的 Y |

### 5.5.1 第三轮还是没生效：我把两个概念揉在一起了（"地板依旧在限制"）

用户反馈："**地板依旧在限制，依旧很低**"。这次是实现错误，而且很典型：

```java
// ❌ 第一版：条件恒为假
ridingVehicleY = mmtrCabLocked && !Double.isNaN(mmtrLockedSeatFootY) ? ... : maxY;
```

`mmtrSetCabLock(false)` 会**清掉**锁存，而硬绑路径为了让人能走动必须调它。
于是 `mmtrCabLocked == false` ⇒ 整个条件恒假 ⇒ **锁存永远不可能生效**。我自己把唯一入口焊死了。

**根因是把两件独立的事绑到了一起**：

| 概念 | 含义 |
|---|---|
| **锁存（pin）** | "这个人的眼高来自模型的座位锚点" |
| **锁定（lock）** | "这个人不许在车里走动" |

硬绑上来的人要 **pin 但不要 lock**；按 G 拿到钥匙的司机**两个都要**。修法是拆开并给出成对 API：

```java
mmtrPinSeatFootY(double footY)      // pin + 解锁（硬绑用）
mmtrLockSeatAndPin(double footY)    // pin + 锁定（驾驶室用）
```

成对 API 的意义在于**顺序不可能写错**：`(pin, lock(false))` 这种顺序会把 pin 悄悄抹掉，
而 `mmtrLockSeatAndPin` 内部只有一个顺序。

> **教训**：**"我设了位置"和"位置留在那儿"是两件事。**
> 凡是每帧被别处重算的量（Y、朝向、车厢号），设一次没有用 —— 要么找到那个重算点让它让路，
> 要么把值**锁存**成这一个座位的权威值。
> 而如果"锁存"的开关又受另一个状态门控，**先确认那个门控在调用点上真的为真**，
> 否则错误的形式是"条件恒假" —— 表现和"没写"完全一样，看代码却像是写了。

### 5.5.3 第四轮："刚上车可以，然后又掉到下面"

这条时序描述信息量很大，它把范围缩到**一个形状**：

> pin **确实被设上了**（所以刚上车对），然后在**一两拍之内被清掉**，地板钳制接管。

所以问题不是"条件写错"（那是第三轮），而是**有东西在清 pin**。清点只有四处：

| # | 清点 | 什么时候发生 |
|---|---|---|
| 1 | `mmtrSetCabLock(false)` | 离开驾驶室 / 硬绑上车路径 |
| 2 | `tick()` 顶部"无车更新位置→自动下车" | 连续若干拍没有车更新玩家位置 |
| 3 | `movePlayer` 里"脚下无地板→下车" | `offsets.isEmpty()` |
| 4 | `mmtrPlaceRiding` 之后被再次调用 | 换了另一台车 |

**不再靠猜**：所有写入都走 `setSeatFootY(footY, source)`，只在**值真的变化**时打印一次：

```
[MMTR-RIDE] 座位锁存 无 → 1.88 （来源 硬绑上车 mmtrPinSeatFootY）
[MMTR-RIDE] 座位锁存 1.88 → 无 （来源 ???）          ← 下一轮就靠这一行定位
```

这样一遍游戏就能定位，不用每次改一版猜一次。

**另一个已排除的可能**（顺手查过）：`clampPosition` → `bestPosition` 的兜底分支用
`Math.abs(floor.getMaxYMapped() - ridingVehicleY) <= 1` **按当前 Y 挑地板**，理论上"pin 高了就挑不到地板"。
但 `bestPosition` 返回 null 时 `offsets` 为空 → 走的是**下车**（清点 #3），不是压低。
所以"掉到下面"不可能由 `bestPosition` 造成 —— 它只可能是 pin 被清掉。这两条互斥，省掉一轮猜测。

### 5.5.5 第五轮：日志定位到真凶 —— **地板探测用的是被钉高的 Y**（"刚上车可以，然后又掉下去"）

用户给出的日志（关键四行，其余省略）：

```
[MMTR] cab 2 of car 1 (vehicle …, model saf101): seat car-local (-0.75, 2.0456, 5.09636) mirrored=false
[MMTR-RIDE] 座位锁存 无 → 1.88 （来源 进驾驶室 mmtrLockSeatAndPin）
[MMTR-RIDE] 座位锁存 1.88 → 无 （来源 脚下无地板→下车）        ← ★
[MMTR-BOARD] door=cabdoor_2_2 → mmtr_seat ride-space=(-0.75, 3.5, 5.1)  [cabView x/z=(-0.75, 5.1) 户内地板 y=2.05]
[MMTR-RIDE] 地板盒想要 y=1.0 实际用 y=1.88 座位锁存=1.88 驾驶位锁=false local=(-0.75, 1.88, 5.096)
[MMTR-LAG] tick 之间被外部挪动 9.676 格（服务端校正 / 车内定位在拍间落地）  ← ★ "掉到下面"
```

**先确认 pin 其实是对的**：`cab 2 ... seat car-local (-0.75, 2.0456, 5.096)`
—— `2.0456 = 1.88 + 1.62`，**正好是"riding Y + 眼高"**。所以相机确实坐在座位锚点上，
X/Z 也和 `mmtr_seat` 一致（-0.75 / 5.096）。**视角那部分一直是好的。**

**真凶在 `[MMTR-RIDE] 地板盒想要 y=1.0`**：资源包的地板盒在 **1.0**，而被钉高的 Y 是 **1.88**。
而 `clampPosition` → `bestPosition` 是这样找地板的：

```java
.filter(box -> RenderVehicleHelper.boxContains(box, x, ridingVehicleY, z))          // ← 玩家的 Y
.orElse(... filter(box -> |box.getMaxY() - ridingVehicleY| <= 1) ...)               // ← 玩家的 Y
```

两个分支都拿**玩家的 Y** 去问"这里有没有地板"。我把 Y 钉到 1.88（在盒子顶之上），于是
**每一个地板都判定为不存在** → `offsets` 为空 → `offsets.isEmpty()` → **下车** →
玩家掉回地面 → 服务端把人拽走 **9.676 格**。这就是"掉到下面"。

**根因是一句话**：我把"相机多高"和"地板在哪"当成了同一个量。它们是两个问题，
却共用了一个变量 `ridingVehicleY`。

**修法**：把两个问题分开。

| 问题 | 用什么回答 |
|---|---|
| 玩家**在不在**车上（有没有地板） | `mmtrFloorProbeY` = **地板自己的 Y**（新增，静态） |
| 相机**多高** | `mmtrLockedSeatFootY` = 座位锚点 |

```java
// movePlayer：探测用 floorProbeY（内部已改），最后再套上 pin
mmtrFloorProbeY = maxY;
ridingVehicleY = Double.isNaN(mmtrLockedSeatFootY) ? maxY : mmtrLockedSeatFootY;
```

`bestPosition` / `clampPosition` 里的两处 `ridingVehicleY` 都换成了 `mmtrFloorProbeY`。

**而且 probe 必须在第一拍就对**：我一开始想用"上一拍钳制出的 maxY"来自学，但**硬绑那一刻还没有上一拍**，
首拍仍会下车。所以 probe 作为参数一起传进来 —— 两条入口各自都有这个数：

```java
mmtrPinSeatFootY(localY, floorY);          // floorY = cabView.y（模型地板）
mmtrLockSeatAndPin(seatFootY, view.y);     // 同上
```

**这一轮的教训**（比前几轮都值钱）：

> 当一个变量同时承担两个职责时，**修改它会静默破坏另一个职责**，而且症状出现在离修改点很远的地方
> （我改的是"相机高度"，炸的是"地板探测"，表现为"人被弹飞 9.6 格"）。
> 加日志把**两个职责各自的值**分别打出来，是唯一能一眼看穿的办法 —— 我前面三轮都在猜，
> 这一轮把值摆出来，一行就定位了。
>
> 另外：**断言要在打印的值上兑现，不能在脑中兑现**。我此前在注释里写过
> "地板盒仍然是'人在不在车上'的权威"——写的时候以为安全，实际正是这句话掩盖了 bug。

### 5.5.7 第六轮：**任何由 Y 猜的探测都会失败** —— 让盒子自己回答

用户日志（`座位锁存 无 → 1.88` / `1.88 → 无（脚下无地板→下车）` 每 tick 循环）说明：
即使把 `mmtrFloorProbeY` 设成**模型地板**（`cabView.y = 2.52`），**仍然找不到地板**。

**为什么**：模型地板在 **2.47**，而资源包地板盒在 **1.0** —— 差了 **1.47 m**。
所以"模型地板"和"盒子在哪"是**两个不同的高度**，用一个去探另一个必然失败。
（这正是用户说的"改过列车高度"：模型抬高了，资源包的地板/门洞盒没跟着抬。）

**根因是方法论错误**：我在用**一个算出来的 Y** 去问盒子"你在不在这个高度"。
只要算出来的 Y 和盒子不一致就会失败，而**没有人能提前知道盒子的高度**。

**修法：让盒子自己回答。**

```java
// 第一遍：用 mmtrFloorProbeY 探（有缓存时为 O(1) 命中）
// 第二遍（新增）：把每个盒子拿到"它自己的顶面"去问
for (entry : floorsOrDoorways) {
    if (boxContains(box, x, box.getMaxYMapped(), z))   // ← 用盒子自己的 maxY
        best = 最高的那个;
}
if (best != null) mmtrFloorProbeY = best.getMaxYMapped();   // 采纳它的高度，下一拍回到第一遍
```

这一步去掉了"必须有人提前算对 Y"这个假设：**盒子是权威，探测值向它收敛**，
而不是让 `caller` 猜一个 Y 去碰运气。同时 `clampPosition` 里判定"人是否在门洞盒内"也改用
`mmtrFloorProbeY`（原来用 `ridingVehicleY`，被钉高后同样恒假）。

| 同族问题（同一个错法） | 修法 |
|---|---|
| `bestPosition` 用 `ridingVehicleY` 找地板 | 改用 `mmtrFloorProbeY`（§5.5.5） |
| `mmtrFloorProbeY` 用**模型**地板（仍可能错 1.47 m） | 加**第二遍自探**，并采纳盒子自己的高度（§5.5.7） |
| `clampPosition` 用 `ridingVehicleY` 判定门洞包含 | 改用 `mmtrFloorProbeY`（§5.5.7） |

> **教训**（接 §5.5.5）：**不要用推算出来的值去查询权威数据源。**
> 第一次是"用相机的 Y 查地板"，第二次是"用模型地板的 Y 查资源包盒子"——
> 同一个错误换了个更可信的输入而已。正确的形状是**反过来**：
> 遍历权威数据（盒子），用每个候选自己的坐标去匹配。

**并且这次把"为什么找不到"也打出来了**（`recordFloorMiss` / `logFloorMissOnce`），
内容是探测点 + 全部候选盒子的范围：

```
[MMTR-RIDE] 找不到地板 → 下车：probe=(0.75, 2.52, 5.096) 瞄准锁存=1.88 盒子 3 个:
   [地板 x -1.50..1.50 y 1.00..1.05 z -8.00..8.00] [门洞 x 2.10..2.60 y 2.00..4.00 z 3.50..4.50] …
```

下一次如果还失败，这一行会直接说明是**探测点不在盒子的水平范围内**（位置问题）
还是**一个盒子都没有**（资源包问题）——而不是再来一轮猜。

### 5.5.9 第七轮：pin 必须是**自愈**的，不能只在门口设一次

用户日志的关键一行：

```
[MMTR-RIDE] 地板盒在 y=1.0 钳制想要 y=1.0 实际用 y=1.0 座位锁存=无 驾驶位锁=false local=(0.75, 1.0, -4.993)
```

注意 **`座位锁存=无`**，而 `local` 的 X/Z 正是座位锚点（`seat_1` = `(0.75, 3.5, -4.993)`）。
所以：**位置对了、地板找到了、pin 没了。**

**根因**：`boardNearestTrain` 第一句就是

```java
if (VehicleRidingMovement.isRiding(vehicle.getId()) || ...) continue;   // 已经在车上 → 跳过
```

这个跳过是**必须**的（否则每 tick 都会跟走动逻辑打架），但它意味着
**`placeOnCar` 一生只执行一次** —— 只在门口那一刻。而 pin 会被两处清掉：

| 清 pin 的地方 | 什么时候 |
|---|---|
| `mmtrSetCabLock(false)` | 任何重置驾驶位锁的路径 |
| `movePlayer` 的"脚下无地板→下车" | 地板探测失败那几拍（§5.5.5–5.5.7 修的就是它） |

清掉之后**再没有任何东西会把它设回来**，于是表现为
"刚上车可以（第一帧 pin 生效），然后掉到地板盒高度（pin 被清、地板接管）"。

**修法：把 pin 变成自愈的。** 存一份"钉在哪里"的描述符，`tick()` 里**每帧重新断言**：

```java
private static long pinnedVehicleId;          // 钉在哪台车
private static double pinnedX, pinnedFootY, pinnedZ, pinnedFloorY;

tick():
    reassertPin();            // ← 先自愈
    ... 接近检测 ...

reassertPin():
    if (pinnedVehicleId == 0) return;
    if (!isRiding(pinnedVehicleId)) { pinnedVehicleId = 0; return; }   // 下车就忘掉
    mmtrPinSeatFootY(pinnedFootY, pinnedFloorY);                       // 只补 pin，不再 mmtrPlaceRiding
```

**不调 `mmtrPlaceRiding`**：位置本来就是对的，重新 place 会每 tick 发一个 riding-entity 包。
只补那个可能被清掉的 Y。

> **教训**（本轮第三次同族错误）：**"设一次"只对不可变的状态成立。**
> 一个会被别的路径清掉、且自己不会重生的状态，本质上是**每帧都要维护的不变量**，
> 而不是一次性初始化。判据很直接：
> **如果这个值有一条"清空"路径，就必须有一条"重建"路径，而且重建的触发频率不能低于清空的频率。**

### 5.5.10 第八轮：pin 的生命周期**不能挂在驾驶位锁上**（真凶：`mmtrSetCabLock(false)`）

自愈上线后日志变成了这样：

```
[MMTR-RIDE] 地板盒在 y=1.0 钳制想要 y=1.0 实际用 y=1.88 座位锁存=1.88 驾驶位锁=true local=(0.75, 1.88, -4.993)  ← 自愈生效
[MMTR-LAG] tick 之间被外部挪动 6.051 格（服务端校正）… 车内定位累计=2
[MMTR-RIDE] 座位锁存 1.88 → 无 （来源 mmtrSetCabLock(false)）       ← ★ 真凶
[MMTR-RIDE] 地板盒在 y=1.0 … 实际用 y=1.0 座位锁存=无 …
```

**自愈确实生效了**（`实际用 y=1.88`），但 `MmtrCabInteraction` 的**钥匙对账**判定
"驾驶室不属于你"→ `forget()` → `mmtrSetCabLock(false)` → **顺手把 pin 也清了** →
下一拍相机掉回地板。于是 1.88 / 1.0 交替、每拍服务端校正 —— 用户看到的抽搐正是这个。

**根因**：我把 pin 的生命周期挂在了驾驶位锁的置位/清除上（上一轮那行 `if (!locked) clear()`）。
但"能不能走动"和"相机多高"是两件独立的事，而且**钥匙对账会反复释放锁** ——
对账失败 ≠ 人不在座位上。

**修法**：pin 有自己的生命周期，**只在真正离开列车时清**。

```java
mmtrSetCabLock(boolean)   // 只改锁，不碰 pin
markLeftTrain()           // 唯一的清除点：下车 / 廊道脱落 / 无车更新
```

并把各处清 pin 的地方统一换成 `markLeftTrain()`。

> **教训（第四次同族错误，这次是"生命周期归属"而非"查询方向"）**：
> **一个状态量应该只被它的所有者清除。**
> pin 的所有者是**"这一段乘车"**，不是"驾驶位锁"、不是"某一帧的地板搜索结果"、不是"钥匙对账结果"。
> 每多挂一个清除点，就多一条会被无关逻辑误触的路径 ——
> 本轮先后挂掉了：地板搜索失败、调用顺序、无车更新、驾驶位锁，**四个都不该由它们清**。
>
> 判断归属的简单问法：**"这个值该活多久？"**
> 答案是一个区间（"从上车到下车"），那么**进区间的点只能有一个、出区间的点也只能有一个**。

`movePlayer` 每 0.5 s 打一行：

```
[MMTR-RIDE] 地板盒在 y=1.0 钳制想要 y=1.0 实际用 y=1.88 座位锁存=1.88 驾驶位锁=false local=(-0.75, 1.88, 5.096)
```

### 5.5.13 第九轮：**两个入口在抢同一个座位**（"上车一会就被判定为下车，但还在车中"）

用户反馈："上车一会就被判定为下车了，但还在车中"。

日志里两个线索直接对上了：

```
[MMTR]      cab 1 … seat car-local ( 0.75, 2.0456, -4.99298)   ← 按 G 落在 cab 1
[MMTR-RIDE] … 座位锁存=1.88 local=(-0.75, 1.88,  5.096)         ← 硬绑把它钉到车体另一端
[MMTR-LAG]  tick 之间被外部挪动 10.200 格
```

**`2 × 5.096 = 10.19 ≈ 10.200`** —— 那个"大跳"正是两端座位锚点之间的距离。
也就是说**硬绑把已经坐好的司机瞬移到了另一端**，对账再纠正回来，来回几次就被判成"下车"。

**根因：同一个座位有两条进入路径，各自独立解析座位点，且都自认为权威。**

| 入口 | 触发 | 解析出的座位 |
|---|---|---|
| `MmtrCabInteraction` | 按 G 认领驾驶室 | 它指名的那间（`cab 1` → `(0.75, …, -4.993)`） |
| `MmtrBoarding` | 走到门口就近上车 | 它选中的那个门 → 那个驾驶室（`(-0.75, …, 5.096)`） |

两者都调 `mmtrPlaceRiding` / `mmtrPinSeatFootY`，于是**每帧互相覆盖**。

**修法：显式认领优先。** 硬绑让位给"按 G 拿到钥匙"：

```java
if (VehicleRidingMovement.mmtrHasCabLock()) {   // 有驾驶位锁 = 按 G 坐进来的
    pinnedVehicleId = 0;                        // 放弃硬绑的钉扎，让驾驶室说了算
    return;
}
```

顺带修掉**同一个错误的第二个实例**：
`reassertPin` 每帧调 `mmtrPinSeatFootY`，而它**原来会 `mmtrCabLocked = false`** ——
于是每帧把驾驶位锁清掉 → `mmtrCabDriver` 恒假 → 客户端不再向服务端报告"我持钥匙" →
**服务端收回驾驶室** → 被判定为下车（人还在车里）。
现在 `mmtrPinSeatFootY` **只动 pin**，不碰任何其他状态。

> **教训**：**一个目标状态只能有一个权威。**
> 当同一件事有两个入口，"谁说了算"必须**在代码里写死**，否则表现是两者按帧交替覆盖 ——
> 而症状（瞬移、被判定下车、抖动）看起来完全不像"两套逻辑在打架"。
> 判断方法：**同一个目标状态有几条写入路径？如果 >1，就要有一条明确的优先级规则。**

### 5.5.15 第十轮：**钥匙被"镜像还没追上"丢掉**（"在驾驶位上按 J 提示需要坐在驾驶座上"）

用户反馈："现在在驾驶位上按 J 提示需要坐在驾驶座上"。

J 是雨刷键，它的守卫是 `MmtrCabInteraction.holdsAnyCab()` —— 为假说明**本地钥匙已经没了**，
而人还坐在驾驶座上。丢钥匙有两条路径，都太急：

| 路径 | 原来的判据 | 问题 |
|---|---|---|
| `tick()` 里 `!isRiding(heldVehicleId) → forget()` | 只看 riding 状态 | riding 状态会被"地板探测失败""车辆流卡顿"清掉（§5.5.9），人没动钥匙就没了 |
| `reconcile()` 里"镜像对不上 → forget()" | 要求镜像**完全一致** | 认领还在收敛、编组换端、补丁在途时镜像都**不一致**，于是刚认领就被撤回 |

**修法：区分"确凿被抢"和"还没追上"。**

```java
// 1. 钥匙只随「真正离开列车」消失（驾驶位锁还在 = 人还在座位上）
if (heldVehicleId != 0 && !isRiding(heldVehicleId) && !mmtrHasCabLock()) forget(...);

// 2. 对账：只有「别的船员确凿持有」才算被抢
if ("CREW".equals(holder) && !crew.isEmpty() && !crew.equals(localUuid)) forget(...);   // 决定性
else reclaim();   // 其余一律当"还没追上" → 每 2 s 重发一次认领，而不是放弃
```

> **教训**：**"不一致"不等于"被拒绝"。**
> 与权威源对账时，必须把**负向的确定证据**（"别人拿着"）和**信息缺失/滞后**（"还没同步到"）分开处理。
> 前者才允许放弃本地状态；后者应该**重试**。
> 把两者都当成"失败"就得到本轮的症状：玩家坐在座位上，系统却说他没有钥匙 ——
> 因为这个判断被一个**暂时的、会自愈的**状态差异驱动了。
>
> 这和 §5.5.10 是同一个家族：**用瞬时观测去驱动持久状态的转移**。
> 持久状态（钥匙归属）的转移，只能是持久事件（真的下车 / 真的被抢）。

### 5.5.16 一次性诊断（配合 §5.5.3 / §5.5.5 / §5.5.7 一起看）

`movePlayer` 每 0.5 s 打一行：

```
[MMTR-RIDE] 地板盒在 y=1.0 钳制想要 y=1.0 实际用 y=1.88 座位锁存=1.88 驾驶位锁=false local=(0.75, 1.88, -4.993)
```

| 现象 | 结论 |
|---|---|
| `座位锁存=无`（且正在车上） | pin 被清掉且没有重建 → §5.5.9 自愈 |
| `座位锁存=1.88` 但**紧接着** `→ 无（来源 离开列车）` | 真的被判定下车 → 查 §5.5.13 的两个入口互抢 |
| `实际用 y` ≠ `座位锁存` | 调用顺序问题（有东西把 pin 抹了） |
| `local` 在两端锚点之间来回跳 | 两个入口在抢座位 → §5.5.13 |
| `座位锁存=1.88` 但按 J 说"需要坐在驾驶座上" | 本地钥匙被丢 → §5.5.15（看有没有 `离开列车（…）` 或 `重新认领驾驶室`） |
| 全都对但仍偏低 | 1.88 本身不对，比 §5.6 的表 |

> **saf101 的实测落差**（日志与锚点数据一致）：模型地板 `cabView.y = 2.52`，
> 而资源包**地板盒顶面在 1.0** —— 差 **1.5 m**，因为模型被抬高过而资源包没跟着改。
> 硬绑的 pin 让**相机**不再受这个落差影响，但**地板探测**必须让盒子自己回答（§5.5.7）。

## 6. 顺手发现的**另一个**真问题（未修，已取证）：门的同步到不了客户端

实机验证时发现：**门的同步到不了客户端**。

我通过本地引擎 web API 直接下命令（这是实测，不是推断）：

```
POST /mtr/api/map/mmtr-command  {"command":"train doors 7732985433690931942 open --side=both"}
→ ok=True  "已转交游戏端执行"

引擎命令日志：[doors] 7732985433690931942 开门 both (L=true R=true 手动=true)
```

**引擎账上两侧门都是开的、人工标记也是真的**。但同一个客户端的渲染循环持续输出：

```
[MMTR-DBG] vehicle queue: 0/10 part conditions have optimized geometry, doorsClosed=true, model=saf101
```

`doorsClosed=true` 意味着客户端的 `openDoorways` 是空的 —— 客户端**没有**接受那份门状态。
我又 toggle 了一次（`L=false R=false`），客户端依旧 `doorsClosed=true`，所以不是"开/关方向"的问题，
是**这条状态根本没生效**。

已排除的：
- 引擎 shadowJar **确实**含 `mmtrDoorManual` / `mmtrDoorLeft` / `mmtrDoorRight`（我开 jar 逐个查过）；
- 三个字段都在 `VehicleSyncPatch.DYNAMIC_KEYS` 白名单里；
- 命令确实执行了（引擎回显带真实字段值）。

所以嫌疑落在**客户端侧的应用**：`VehicleExtension` 合并补丁、或
`vehicleExtraData.isMmtrDoorManual()` 在客户端为 false 导致走了站台邻近分支
（`RenderVehicles` 第 204 行的 `canOpenDoors`）。**下一轮从这里查**。

> 注意：这条 bug 与"上不了车"是**两个独立问题**。硬绑绕过了几何问题，但**门自己不开**仍然是 bug：
> 门不开 → 车门渲染不动 → 从站台上看起来还是关门。硬绑让玩家能上去，但外观仍然是错的。

## 7. 实机验证清单

需要**重启客户端**（只改了 game 侧，引擎不用动；也不需要重打包资源包）。

1. 走到车门口（2 格内）→ 动作条出现 `已上车（按锚点硬绑）/ on board`；
2. **视角应落在 `mmtr_seat` 上**（和按 G 进驾驶室是同一个点），朝向车头；
3. 上车后可以正常走动；车门外观是否跟随（见 §6）；
4. **蹲下**在车旁走动 → 不应该被吸上去；
5. 上车日志 `[MMTR-BOARD]` 与 `[MMTR-RIDE]`：
   - `mmtr_seat ride-space=(…)` 与 `绑定 local=(…)` 的 **X/Z 必须相等**；
   - `[MMTR-RIDE]` 里 `实际用 y` 应等于 `座位锁存`，且 `差值` 不为 0（说明确实压过了地板盒）；
     若 `座位锁存=无` → 锁存没设上；若两者不等 → 又是调用顺序问题（见 §5.5.1）；
