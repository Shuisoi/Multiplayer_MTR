# 384 — 起步高频族：三个 250 Hz「鼓包」是假象，两个门控真 bug，和一条一直没归属的下行射线

对象：京急 2100 形司机室。源录音仍是 `【4K前面展望】…京急線 横浜→品川…`（128 kbps / 48 kHz）。
本文所有绝对时间都指该录音；我们渲染的 `t=0` ↔ 录音 **16.5 s**（起步瞬间）。

---

## 1. 先推翻一整个待办：**2075 / 3075 / 4075 三个 250 Hz 宽「鼓包」不存在**

之前记的是「三条 250 Hz 宽的隆起，我们模型里没有，要新建一族」。第 38 轮复量，**这是分窗口径造成的假象**。

把 16~32 s 分成子窗、用细谱（nfft 32768 ⇒ 0.73 Hz）找局部峰，超过 +6 dB 的只有：

| 窗 | 1800~4400 Hz 上的局部峰 |
|---|---|
| 16~20 s | **2097.7 (+13.4)**　4195.3 (+12.4) —— **只有两根** |
| 20~24 s | 2097.7 (+13.7)　4195.3 (+12.8)　3022.0 (+7.0) |
| 24~26 s | 2097.7 / 4195.3 + 2996…3299 一串（速度扫过的那族进来了） |
| 26~32 s | **（无）** |
| 32~42 s | **（无）** |

平均到 16~32 s 之所以看起来像"三条宽台"，是因为每根线带一个 **±100 Hz 的宽肩**：

```
实录 20-24 s 平滑谱（±50 Hz），相对本窗 1.2~4.4k 中位
2100 +20.8   2000 +9.3   2200 +9.7   1900 +2.7   2300 -0.1
             ↑ 距中心 ±100 Hz 只掉 11 dB
```

**1 kHz 梳齿假设也否掉了**：残差谱自相关 ac(1000 Hz) = **+0.058**（= 0）。
§3 里那些"2.5 k / 3.5 k 掉 12~18 dB"不是梳齿凹陷 —— 是拿**不同速度**的窗当参考造成的底噪高度差，
同一窗内的平滑谱没有交替结构。

> ⇒ **「新建 2075/3075/4075 一族」这项工作取消。**

## 2. 但换出来三件真东西

### 2.1 门控量漏了滑差 4.5 Hz

`untilF1` 比的是 `f₁`，而 `f₁ = 转频 + 滑差 4.5 Hz`（`fundamentalHz`）。
所以"门关在 25.4 km/h"对应的不是 31 Hz，而是 `1.2193 × 25.4 + 4.5 = 35.5` ⇒ 取 **36**。
写成 32 时渲染实测门在 **6.8 s** 就关，比实录早 1 s。

**自证**（0.5 s 步长探针，2097 突出度）：

| t (s) | … | 6.5 | 7.0 | 7.5 | 8.0 |
|---|---|---|---|---|---|
| `untilF1 = 32` | … | 12.5 | **4.5** | 5.4 | 5.6 |
| `untilF1 = 36` | … | 12.5 | 12.1 | 12.5 | **5.3** |

### 2.2 谐波形状：**几何 decay 表达不了，必须用显式幅度表**

用**绝对电平**（相对同窗 2097 峰，不再用"突出度"）：

| 窗 | 2097 | 4195 | 6294 | 8392 |
|---|---|---|---|---|
| 实录 17~19 s | 0 | **−10.9** | −9.3 | **−5.6** |
| 实录 19~21 s | 0 | −10.4 | −11.5 | −9.9 |
| 我们（旧 `count 3 / decay 0.70`） | 0 | **−6.9** | −12.2 | **无（−54）** |

三处都错：

1. 2 次比实录**响 4 dB**；
2. 4 次（8388 Hz）**整根缺失** —— `count` 只有 3，而且基类 `maxPartialHz: 8000` 会把它切掉；
3. 形状**非单调**（6 次比 4 次高），任何 `decay^k` 都给不出来。

⚠ **根因是口径**：旧的 `decay 0.70` 是用**突出度**定的，而突出度 = 线 − 局部包络；
4~8 kHz 的底比 2 kHz 低二十几 dB ⇒ **同一根线在高频天然显得更突出**。
**以后定谐波形状一律用绝对电平。**

改动：`fixedTonePartials` 增加可选 `partials: [相对幅度…]`（给了就完全接管 count/decay）；
本 spec `maxPartialHz: 8000 → 9000`；起步族改为 `partials: [1, 0.295, 0.302, 0.407]`。

### 2.3 那条「3 kHz 附近往下走的射线」找到了

`notes` 里挂了好几轮、一直"归属未定"的下行射线，用 0.5 s 探针一量，**是一根很干净的线性下滑音**，
而且和 2097 族**同开同关**：

| 绝对时间 | 16.5 | 18.0 | 20.0 | 22.0 | 24.0 | 25.0 |
|---|---|---|---|---|---|---|
| 实录峰频 (Hz) | **3146** | 3120 | 3108 | 3085 | 3056 | 3050（已进底噪） |

线性拟合 **−12.0 Hz/s**（预测 3104/3080/3056，实测 3108/3085/3056）。
起步段 `df₁/dt = 1.2193 × 3.3 = 4.02 Hz/s` ⇒ 斜率 = **−3.0 Hz per Hz of f₁**。

`fixedTonePartials` 因此增加 `hzPerF1`（并按次数等比缩放）。
`hz` 写 **3159.5**（= 3146 + 3.0 × 4.5）以补偿静止时 f₁ 已经是 4.5 Hz 这件事 ——
不补的话渲染出来是 3129 Hz，比实录低 17 Hz。

**自证**：改后渲染 3k 峰 `3144 → 3135 → … → 3053`（t = 0…7.5 s），斜率 **−12.1 Hz/s**。

⚠ **诚实说明**：这段录音加速度是常量 ⇒「随时间线性下滑」与「随 f₁ 线性下滑」**无法区分**。
按 f₁ 写是因为它不需要绝对时间原点、换加速度曲线仍成立。若将来发现它是"某台机器按自己的时间表减速"，
这个字段就是错的，要换成时间斜率。

## 3. 顺带修掉的两个**真 bug**（比上面三件都严重）

`preview.mjs` 里固定音的门控原来写成了**跨所有分音的 OR**：

```js
const speedOk = parts.some((p, k) => it.f1 < until[k]);        // ①
const dutyOk  = duty.some((d) => d.on > 0 && dutyGate(...));   // ②
```

1. 只要有一条 `untilF1 = Infinity`（常驻音），**速度门永远为真** ⇒
   起步高频族的 `untilF1` **完全失效**；
2. 只要有一条带占空比，它一断就把**所有**固定音一起掐掉 ——
   包括本该**常驻**的 354.5 Hz 族。

**实测症状（v53）**：2097 在 `t = 7.0 s`（占空比 7 on / 14 off 的关点）**整族掉 7 dB**，
而实录同时刻是平的：

| t (s) | 6.0 | 6.5 | **7.0** | 7.5 |
|---|---|---|---|---|
| v53（改前）2097 突出度 | 12.2 | 12.6 | **10.6** | **5.3** |
| v56（改后） | 12.1 | 12.5 | **12.1** | 12.5 |

改成**逐分音**门控（各自的攻击/释放包络、各自的通断状态）后两个问题一起消失。

## 4. 撞上一面墙：**我们的司机室壳子在 8.4 kHz 砍得比真实司机室多 17.5 dB**

dry（不加壳）渲染的谐波比例是 `0 / −9.6 / −10.7 / −7.0`，和我设的 partials 基本一致 ⇒ **合成端没错**。
但加上 `--shell cab` 之后变成 `0 / −13.6 / −16.2 / −24.5`（实录是 `0 / −10.9 / −9.3 / −5.6`）。

壳子的传导链里有一条 **`lowpass 3100 Hz`（q 0.7，二阶 ⇒ −12 dB/oct）**，
是第 27 轮为了压 E235 的 3.3 kHz SiC 载波"刺耳"故意设的。它在 8.4 kHz 处正好给出约 −17 dB。

试了一下用现成的 `--condlp 6500` 替换：

| | 2097 | 4195 | 6294 | 8392 |
|---|---|---|---|---|
| 实录 | 0 | −10.9 | −9.3 | −5.6 |
| v56（`--condlp` 不给 ⇒ 3100） | 0 | −13.6 | −16.2 | **−24.5** |
| v57（`--condlp 6500`） | 0 | −8.5 | −6.2 | **−12.3** |

6500 之后 2/3 次反而偏响 2~3 dB、4 次仍差 6.7 dB ⇒ 真实链路不是一条 6500 Hz 二阶低通。

**没有动壳子**：它同时塑造**所有**层（底噪、齿轮、载波），而且被耳朵调过两轮。
用"源端预加重"去抵消它也不可取 —— 要抵消 8392 那 18.8 dB，
4 次的幅度得设到基音的 **3.5 倍**，那是荒谬的，只说明壳子在这一带不对，而不是源不对。

**这是一个需要耳朵裁决的岔路**，A/B 已生成：`AB-hf-comb.ogg`
（前 12 s = A：现行 3100 低通；后 12 s = B：`--condlp 6500`）。

## 5. 一个测量口径上的事故（记下来免得再犯）

1. **preview 输出的 wav 是 44100 Hz**，而参考录音是 **48000 Hz**。
   会话里早先几个 `ours-*.f32` 是按 48 k 解码 44.1 k 文件的 ⇒ 频率读数**偏 8.8%**
   （实测 2097 的线落在 2282 Hz 就是证据）。第 38 轮起统一用 FFT 带限重采样到 48 k 再比。
2. 我把旧文件 `sandbox/tmp/ours-v53.f32` **覆盖掉**了（同名写入 44.1 k 版本）。
   内容可从 `trip-keikyu-v53.wav` 重建，但这一步是本轮的操作失误。
3. `np.fft.irfft` 返回 **float64**，直接 `tofile` 会写出双精度、按 `<f4` 读回去全是 NaN。
   已改为显式 `.astype('<f4')`。
4. **改 `model.mjs` 里的 spec 之后必须重新 `bake`** ——
   `preview.mjs` 用的是 bake 出来的 `mmtr_traction.json` 里的 `manifest.spec`，
   不是直接读 `model.mjs`。本轮 v55 与 v54 逐字节相同就是这个原因。

## 8. 追加：频带占比重测 —— 真错是 **300~3000 Hz 整段缺 10 dB**，不是"低频不够厚"

### 8.1 先修一个**测量脚本的 bug**（否则本节全部结论都是错的）

`bands_of.py` 的 `fractions()` 原来写的是 `n = 1 << 16; x = x[:n]` ——
那**只取开头 1.37 秒**（48 kHz × 65536），所谓"整段占比"其实是"头 1.4 秒占比"，
而头 1.4 秒恰好是低频最集中的地方 ⇒ 结论被整体带偏（一度算出"我们 73.8% 挤在 20~50 Hz"）。
改成对整段做 Welch 平均（nfft 65536、50% 重叠）之后，数字变了：

| 带 | 实录 16.5~32 s | 我们 0~15.5 s（改前口径） | 我们（Welch 整段） |
|---|---|---|---|
| <500 Hz | 89.1% | 99.8% | 99.0% |
| 20~50 | 4.5% | 56.5% | 8.9% |
| 50~100 | 13.5% | 36.4% | **33.8%** |
| 100~300 | 55.6% | 6.1% | 50.1% |
| 300~500 | 15.4% | 0.7% | 6.2% |
| 500~1100 | 9.7% | 0.2% | **0.9%** |
| 1100~3000 | 1.0% | 0.0% | 0.1% |

**结论**：不是"低频不够厚"（旧笔记里的 17.2% 那一条也是这个 bug 的产物，且方向相反），
而是 **300~3000 Hz 整段缺约 5.6 dB（按占比）/ 500~1100 缺 10 dB**。
实录在这一段是**宽带**（线状度 +5.8 dB、"线占带内 0.0%"）⇒ 属于**环境/走行底**，不是牵引分音。

### 8.2 分层量

| 层 | RMS | <500 Hz | 300~500 | 500~1100 | 1100~3000 |
|---|---|---|---|---|---|
| 牵引层（壳内） | −19.6 | 99.2% | 5.7% | 0.7% | 0.0% |
| 底噪层（差值法隔离） | **−29.6** | 97.3% | 8.5% | 2.0% | 0.5% |
| 合计 | −20.9 | 99.0% | 6.2% | 0.9% | 0.0% |

⇒ **两层都过分偏低频**。底噪比牵引低 **10 dB**（约 9% 能量，与 `shell.mjs` 注释里的 9~10% 相符
—— preview 日志里那句"底噪按能量占 49.0%"量的是**壳子之前**的量，不能拿来判最终平衡）。

### 8.3 离线搜索：底噪要抬 ~14 dB + 一条 700 Hz 平台

`输出 = 牵引层 + α · EQ(底噪)`，扫 (α, 中频峰增益, 峰中心)，用 300 Hz 以上的占比距离选优：

| 带 | 实录 | 现行 | **α=5（+14 dB）+ 700 Hz/+6 dB/Q0.7** |
|---|---|---|---|
| 20~50 | 4.5 | 8.9 | 3.6 |
| 50~100 | 13.5 | 33.8 | 13.1 |
| 100~300 | 55.6 | 50.1 | 58.8 |
| 300~500 | 15.4 | 6.2 | 16.1 |
| 500~1100 | 9.7 | 0.9 | 7.0 |
| 1100~3000 | 1.0 | 0.1 | 1.2 |
| 3000~8000 | 0.2 | 0.0 | 0.0 |

⚠ **与第 29 轮的用户口径直接冲突**：那一轮用户说「底噪中，风噪占比大了点」「底噪又过于明显刺耳」，
于是把底噪从 29.7% 压到 9~10%。而现在实录指向的平衡是底噪**远高于**牵引。

**不冲突的读法**：第 29 轮投诉的是 **>2 kHz 的嘶声**（"风噪/刺耳"），
而缺的是 **400~2500 Hz 的平台**（我们 3000~8000 只有 0.0%、实录 0.2% —— 高频两边都很少）。
所以正确的做法是加**带限平台**（`midPeakHz/midPeakDb`，cab 的 bed 目前**没设**这两个字段），
不是加宽高频。搜索的最优解也正是"抬电平 + 只加一条 700 Hz 平台"。

**没有动壳子** —— 电平抬高 14 dB 是听感上的大改，且与用户上一轮的口径相反。
三档 A/B/C 已生成：`ABC-bed-level.ogg`（A 现行 / B 底噪×3 / C 底噪×5，各 16 s）。
若要落地，改动是 cab 的 `bed`：`levelDb −4 → +10`，并加 `midPeakHz: 700, midPeakDb: 6, midPeakQ: 0.7`。

### 8.5 ★ 裁决（用户，第 38 轮末）：**选 A —— 保持现行**

`ABC-bed-level.ogg` 三档（A 现行 / B 底噪×3 / C 底噪×5）与 `AB-hf-comb.ogg` 两档
（A 现行 3100 Hz 低通 / B `--condlp 6500`）—— **两处的 A 都是"现行"，用户都选 A。**

⇒ **壳子的底噪电平与 HF 低通都保持不动。** 具体含义：

1. **§8.3 那张"最优配比"表不作为目标。** 它是从**手机录音**反推的，
   而手机的小振膜麦克风本身就压低频、抬中高频 —— 实录那 26% 的 300~3000 Hz 里
   有多少是车厢、多少是麦克风，本项目**分不出来**。耳朵已经否掉了这个目标。
2. 也就是说：**"我们比实录暗"是被有意识接受的**，不是待修的缺陷。
   以后不要再用"实录 300~3000 Hz 占比 26%"去驱动壳子改动 —— 那条路已经走到头并被否决。
3. 但 §8.1 那个**测量 bug 的修复**是独立成立的，与偏好无关：
   任何频带占比都必须对整段做 Welch，不许 `x = x[:n]`。
   同理"§7 低频厚度 17.2% vs 23.8~55.7%"那条旧记录**作废**（它就是那个 bug 的产物）。

§8.2 的分层事实（牵引层 99.2% <500 Hz、底噪层比牵引低 10 dB）仍然有效，
只是**不再当作要消除的误差**。


### 8.6 这次踩到的另一个坑

`shares()` 一类的脚本**一律要对整段做 Welch**，不要 `x = x[:n]`。
另外 `preview.mjs` 的分层 RMS 是**壳子之前**的量，`shell.mjs` 注释里的百分比也是；
判"最终平衡"必须用**渲染出来的 wav**去量。
