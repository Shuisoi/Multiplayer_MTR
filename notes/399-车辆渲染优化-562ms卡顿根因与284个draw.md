## 1 卡顿：(1) 现象与日志证据

```text
[19:27:40] [MMTR-LIGHT] ShaderManager.reloadShaders()
[19:27:41] [MMTR-DBG] loading model mtr:saf420cab_b/saf420cab.obj: …     ← 连 OBJ 都重新解析
[19:27:41] [MMTR-LAG] 帧间隔 562ms（渲染线程被卡住：掉帧）
[19:27:41] [MMTR-LIGHT] ShaderManager.reloadShaders()   ×4（同一毫秒）
[19:27:49] 同样一组 5 次，换 cab_a
```

**一次重建 = 5 次 `reloadShaders()`**，每次关掉并**重新编译 3 个着色器程序**（字节码确认：
`shaders.values().forEach(close)` → `clear()` → `loadShader` × 3）⇒ 15 次编译，卡 562 ms。

### 5 次从哪来（与代码结构一一对应）

| # | 调用点 |
|---|---|
| ①②③④ | `VehicleResource.writeToOptimizedModels`（:570）—— 被调 **4** 次（:478-481：本体 / 关门 / 转向架1 / 转向架2），各自一个 `CachedResource` |
| ⑤ | `VehicleModel.createModel`（:116） |
| （另一条） | `StoredModelResourceBase.load`（:21） |

它们由 `CachedResource.tick()`（`InitClient:411`，20 Hz）触发：一起过期就一起重建。

## 2 根因：MTR 把"重编译着色器"绑在了每一次模型构建上

`OptimizedRenderer.beginReload()` = `ShaderManager.reloadShaders()` + `GlStateTracker.capture()`。
**建 VBO 只需要后一半**（notes/398 §10 已经查清这一点：`VertexArray` 构造要保护区，不要新着色器）。

所以修法是**把两半拆开**：

| 时机 | 该做什么 |
|---|---|
| **建模型（每次、每部件）** | 只 `capture()` / `restore()` |
| **着色器真的该换了（资源重载）** | `reloadShaders()`，**一次** |

### 落地（fix A）

| 文件 | 改动 |
|---|---|
| `render/MmtrGlStateGuard.java` | **新增**：共享的保护区助手。含"已经受保护就别动"的判据 —— `GlStateTracker` 是**一个布尔量不是嵌套计数**，盲目 `capture+restore` 会拆掉外层的保护区 |
| `resource/OptimizedRendererWrapper.java` | `beginReload/finishReload` 只在 `shadersDirty` 时真重载；否则只 `capture/restore`。**加了嵌套深度计数**（建模型这条路会嵌套，只有最外层能碰 GL 状态） |
| `client/CustomResourceLoader.java` | `reload()` 里 `markShadersDirty()` —— **着色器重编译的唯一时机** |

**为什么不用"距上次若干毫秒内去重"**：时间窗猜错会漏掉一次真正的重载（资源包换了还在用旧 program），
那是"画面不对"级别的问题。显式标记不会。

**为什么 `shadersDirty` 初值是 `true`**：保证开机第一次建模型一定编译着色器。若初值为 false
且 `CustomResourceLoader.reload()` 没跑过，就会一个 program 都没有 ⇒ **整片不渲染**。这条是刻意兜的。

**预期**：一次重建的 `reloadShaders()` 从 5 → 1，562 ms 按比例降到 ~110 ms。

### ✅ 实测确认（2026-10-05 23:53 起的新会话，PID 18696）

| | 旧会话 | 新会话 |
|---|---|---|
| 一次模型重建的 `reloadShaders()` | **5 次** | **1 次** |
| 同一波的 `loading model` | 5 | 3 |
| 异常 / `Not protected` / 着色器报错 | — | **无** |
| 稳态 | 34–41 FPS（当时场景） | **93.8 FPS，帧间隔 p50=10ms** |

```text
reloadShaders 时刻分布：… 19:38:45 x5 ｜ 23:54:52 x1     ← 整个新会话只 1 次
loading model：        23:54:53 ×2、23:54:54 ×1          ← 3 个模型，只重编译 1 次
```

**着色器那一半治好了，而且没有副作用** —— 这是我最担心的风险面（搞错就是"整片不渲染"）。

### ⚠️ 但卡顿没消失：代价只降了约 2 倍

```text
[23:54:53] loading model …（3 个）        ← 这一波只有 1 次 reloadShaders
[23:54:54] [MMTR-LAG] 帧间隔 455ms
```

旧会话同样的重建是 562 ms，新会话是 **284 + 455 ms**。⇒ **着色器编译本来只占一部分**，
剩下的大头是**在渲染线程上解析 4.5 MB 的 OBJ + 建 VBO**。

**这是 (1) 的残余，切分点很干净**：`OBJ 文本 → RawMesh` 是纯 CPU（可以上 `MainRenderer.WORKER_THREAD`），
只有 `upload()` 建 VAO/VBO 必须在渲染线程 —— 与钢轨那套（CPU 克隆 + 渲染线程 upload）同形。

**但它的优先级比看上去低**：本会话里模型加载**只发生了一波**（不是每隔几分钟一次），
所以这是"每个模型每会话一次"的代价，不是持续开销。这也是为什么我把它排在 B 后面。

### C 的前提在新会话里**没有复现**

整个新会话 `reloadShaders` 只有 1 次、`loading model` 只有一波 —— **没有"每隔几分钟重建"**。
与 §3 的判断一致：19:27 那次是 `CustomResourceLoader.reload()`（资源重载，紧挨 `webBuilds=1`），
不是 60 s 过期。⇒ **C 不该基于"过期"这个理由去做。**

### 顺带补掉一个**配对**漏洞

`beginReload()/finishReload()` 必须成对。查了三处调用点：

| 调用点 | 有没有 try/finally |
|---|---|
| `VehicleModel.createModel`（:116/:148） | **有** ✓ |
| `StoredModelResourceBase.load`（:21/:77） | 里面的分支各自有 try/catch ⇒ 基本能跑到 ✓ |
| `VehicleResource.writeToOptimizedModels`（:570/:584） | **没有** ✗ ← 补上了 |

没有 try/finally 的后果是**静默**的：循环里一抛异常，`finishReload()` 永不执行 ⇒
`GlStateTracker` 的保护位（一个布尔量）**永久留着**，GL 状态再也回不到调用前的绑定。
而且在我的深度计数下还会更隐蔽 —— 之后每次 `beginReload()` 都以为自己在保护区里，
**既不再重编译着色器、也不再 capture**。

两手都做了：① 给那一处补 try/finally（治源头）；② `OptimizedRendererWrapper.resetProtectionState()`
在 `CustomResourceLoader.reload()` 里清零账本（兜底，下一次真正该重载时会
`capture()` 再 `restore()`，顺手把漏掉的那层一起收掉）。

## 3 C（改 `CachedResource` 续期）**暂缓** —— 前提被证据推翻

目标里写的触发条件是「`MODEL_LIFESPAN=60000` 过期」，但实测不符：

| 证据 | 含义 |
|---|---|
| `cab_b`/`cab_a` 在 19:24 已加载，19:27 又**连 OBJ 都重新解析** | 整份重新加载，不是"优化模型过期重建" |
| 19:24:21 → 19:27:41 = **200 s**，不是 60 s | 不符合 60 s 寿命 |
| `[MMTR-HLTH] … webBuilds=1` 紧挨在卡顿之前 | 资源包创作工具的 web 构建 ⇒ 触发 `CustomResourceLoader.reload()` |

⇒ 改"过期续期"治不了"资源重载"。而 `CachedResource` 是车辆/钢轨/物件/电梯/标志**共用**的，
blast radius 很大 —— **证据不足时不动它**。（待确认：用户 19:27 前后是否点过资源包构建。）

## 4 draw 数：284 从哪来（B，尚未动工）

### 机制

每个 **(车, 部件, 材质)** 一个 `OptimizedModelWrapper`，渲染时各走一次
`StoredModelResourceBase.render` → `MainRenderer.scheduleRender` → `queue(...)`。
而映射库的 `BatchManager.queue(List<VertexArray>, state)` 给**每一个** `VertexArray` 建一条 `RenderCall`，
`RenderCall.draw()` 就是一次 `glDrawElements`，**非 instanced**（notes/398 已字节码确认）。

⇒ **一个部件一次 draw，批次数只有 11-12 个（材质数），但 draw 数是部件数。**

### 数字对得上

`mtr:saf420car/saf420.obj` 的 group 列表约 **50 个**
（`body, door_l_1..6, door_l_*_glass, door_r_*, doorway_*, floor, glass, interior`）；
2 辆车 ⇒ `saf420.png` 112 + `saf420_glass.png` 104 ≈ 216，与实测 284 同量级。

### 设计（比钢轨**简单**，因为不需要世界坐标烘焙）

车辆部件本来就活在**车体局部坐标系**里，每个部件有自己的局部变换。所以：

> 把同一辆车、同一材质、**当前动态状态下变换相同/静态**的部件，在**局部空间**里合成一个网格；
> 每帧的 ModelMat 仍然是这辆车的矩阵 —— 不用改。

比钢轨少两个麻烦：**没有世界坐标精度问题**（都是小量），**不用管光照重采样**（车辆光源另有体系）。

要分开保留的（会动）：车门/门玻璃（开关）、雨刷（角度）、转向架（已单独成 wrapper）。
合并的失效键：**模型身份 + 影响部件变换的动态状态**（各门开度、雨刷角等）。

**预计**：216 → 个位数（每材质 1-2 个）。

### 4.1 真正的机制（2026-10-05 读 `ModelPropertiesPart` 后定下来）

`ModelPropertiesPart.writeCache` 里有两套东西，**位置其实已经合过了**：

- `addObjModelPosition(objModels, objModelsForPartConditionAndRenderStage, x, y, z, flipped, modelYOffset)`
  —— 把该部件的**每一个摆放位置**都烘进**同一个** `RawModel`。所以一个部件（= 一个 OBJ group）
  无论放几处，产出的都是**一个** `OptimizedModelWrapper` ⇒ 那些位置已经是 1 次 draw。
- `partDetailsList` 每条持 `optimizedModelDoor.get()` —— 那是**门/机构**那一路（会动），
  普通静态部件在这里是 `null`，走车体级批次模型。

⇒ **draw 数 = 部件（OBJ group）数，不是位置数。** 这解释了 `saf420.png` 的 84 个 draw
（该车 `saf420car.obj` 的 group 列表约 50 个）。

**那为什么合不了？** 卡在最后一步：`OptimizedModelWrapper(m1, m2)` 的构造是

```java
optimizedModel = new OptimizedModel(optimizedModel1.optimizedModel, optimizedModel2.optimizedModel);
```

而 `OptimizedModel(OptimizedModel...)` 只是把各自的 `uploadedParts` **首尾相接**（字节码：新建 ArrayList →
逐个 `addAll`）—— **它不会按材质合桶**。所以每个部件保住自己的 `VertexArray`，各占一次 `RenderCall`。

### 4.2 落点：在 `VehicleResource.writeToOptimizedModels` 里**按材质合并后再 upload**

那里已经在遍历 `PartCondition.values()`，并且手上就是 `ObjectArrayList<ObjModelWrapper>`
（`.objModel` 里就是 `RawModel` —— **私有字段，但 `MmtrRailMeshCache` 已经有一条验证过的反射路**）。

改法（形状与钢轨那套**完全同构**，可复用已验证的机器）：

```
对每个 (PartCondition, MaterialProperties)：
    把各部件该材质的 RawMesh append 进一个 RawModel      ← RawModel.append(RawMesh)，会按材质合桶并平移面索引
    一次 rawModel.upload(DEFAULT_MAPPING)               ← 一个材质一个 VertexArray
    → 一个 OptimizedModel
```

**不参与合并的（必须保留动态）**：

| 类别 | 为什么 |
|---|---|
| 门 / 门玻璃 | 逐扇门独立开关，走 `optimizedModelDoor` |
| **机构件（雨刷）** | **`ModelPropertiesPart:203-212` 的注释已经把坑写清楚了**：雨刷若进批次模型，就会在"关门"那份静态拷贝里**冻住一份**，雨刷一动就"长出一根第二雨刷"。所以 `isMechanism()` 的部件**刻意不进批次** |

⇒ 合并只针对**已经在批次里的**静态部件，门的动态逻辑与雨刷的排除规则**一个字都不动**。
这也顺便说明了为什么 B 的风险其实比看上去低：**边界已经由现有代码划好了**。

**车辆这边不需要逐顶点光照** ⇒ 直接用 `DEFAULT_MAPPING`，比钢轨简单一层
（钢轨那张 `UV_LIGHTMAP → VERTEX_BUFFER` 的自造映射这里不用碰）。

### 4.3 ⚠️ 开工前必须先搞清的三个问题（**别照 §4.2 直接开工**）

读完 `renderNormal`（`ModelPropertiesPart:404-460`）之后发现 §4.2 的落点**不完整**。
这个方法是三分支的，而**只有其中一条**能做合并：

```java
if (OptimizedRenderer.hasOptimizedRendering() && !isWiperPart) {
    if (!openDoorways.isEmpty() && partDetails.optimizedModelDoor != null) {
        …translate(x/16,y/16,z/16)…  queue(partDetails.optimizedModelDoor, …)   // ← 门：**逐位置**一次 draw
    }
    // 关门时这里**什么都不画** —— 关门后的门已经在车体批次模型里了
} else {
    …pushPartTransform(雨刷运动学)…
    partDetails.modelParts.forEach(...)
    if (partDetails.modelParts.isEmpty() && partDetails.optimizedModelDoor != null) {
        …translate(x/16,y/16,z/16)…  queue(partDetails.optimizedModelDoor, …)   // ← 雨刷：在旋转的 push/pop **里面**
    }
}
```

⇒ **`optimizedModelDoor` 绝不能合进批次**：它是**逐位置**排队的（每次都带一个 `translate`），
雨刷那次还夹在 `pushPartTransform` 的旋转里。合掉它 = 门/雨刷全废。

**所以 B 只能合并两个 bundle**：`VehicleResource` 里的 `optimizedModels`
（开门用的非门部件）与 `optimizedModelsDoorsClosed`（关门用的车体+关门后的门）。
实测那 196 个 draw 是**关门状态**的，也就是这两个 bundle 的部件数 —— 与"门开着时才有额外 draw"一致。

**三个必须先回答的问题**（都是"读代码就能答"，但不能猜）：

1. **`addObjModelPosition(firstArg, target, …)` 是不是两个 map 都填？**
   调用点看起来第一个参数总是那个 scratch `objModels`（:220 :223 :225），
   而 `optimizedModelDoor` 的 lambda 就是从这个 scratch 建的（:214）。
   若两个都填，那么**关门时**的门的几何也在 `optimizedModelDoor` 里 ——
   那开门时排队画出来的到底是什么？必须读 `addObjModelPosition` 的实现才能定。
2. **`PartDetails.optimizedModelDoor` 与车体批次模型是否有重叠**？
   若关门时两者都含门，合并批次时就得排除前者，否则门会被画两遍（而 §4.1 提到的
   "雨刷第二根"注释（:203-212）说明**这类双画已经踩过一次**）。
3. **`PartCondition` 的取值与 render stage 的组合**会不会让同一个部件出现在多个 bundle 里？
   若会，合并的键必须是 `(PartCondition, RenderStage, MaterialProperties)` 三元组，不能是二元组。

**在回答这三条之前不要动 B。** 破坏面正好是目标里写死的"车门/雨刷不得改变"，
而 :203-212 与 :404-415 那两段注释说明这类双画/不动的问题**已经各踩过一次**。

### 4.4 ✅ 三问已答（2026-10-05，读 `addObjModelPosition:624-635` 与 `isDoor/isMechanism`）

**① `addObjModelPosition(firstArg, target, …)` 里 firstArg 是"源"，不是 scratch。**
实现是（:629-634）：

```java
objModels.forEach(objModel -> Data.put(target, condition, renderStage, oldValue -> {
    objModel.addTransformation(renderStage.shaderType, (x + doorAnimX)/16, y/16 - modelYOffset, (z + doorAnimZ)/16, flipped);
    newObjModels.add(objModel);        // 同一个对象进批次
}));
```

`:210` 那句 "does both" 指的是「**把位置烘进 ObjModel** + 加进批次 map」，
**不是**"填两个 map"。⇒ `optimizedModelDoor`（从**源**列表建）与批次 map **持有同一批 ObjModel 对象**。

**② 重叠是存在的，但被状态互斥掉了 —— 所以不是 bug，也所以不能乱合。**

| 部件 | 进哪个批次 | `optimizedModelDoor` 里有吗 | 何时画 |
|---|---|---|---|
| 非门非机构 | `…AndRenderStage`（开门用） | **没有**（`isDoor() \|\| mechanism` 才建） | 开门时 |
| 门（`isDoor()`） | 只进 `…DoorsClosed`（:222 的 `if (!isDoor())` 挡住了另一个） | **有** | **关门**时走批次；**开门**时走 `optimizedModelDoor`（:420） |
| 机构（雨刷） | **不进任何批次**（:220 传的是个丢弃的 map） | **有** | 永远走 `optimizedModelDoor`（:448），且夹在 `pushPartTransform` 旋转里 |

⇒ 关门态：批次画门、`:420` 因 `openDoorways.isEmpty()` 不排队 ⇒ **不双画** ✓
⇒ 开门态：走开门批次、`:420` 排队门 ⇒ **不双画** ✓

**③ 合并键：`MaterialProperties` 就够，因为 RenderStage 已经烘进材质里了。**
`addTransformation(renderStage.shaderType, …)` 把 shaderType 写进每个 `RawMesh` 的 `MaterialProperties`；
而 `DynamicVehicleModel.writeFloorsAndDoorways`（:110）在交给 `writeToOptimizedModels` **之前**
已经把 RenderStage 那一层 `flattenCollection` 掉了。
而 `RawModel.append(RawMesh)` 正是**按 `MaterialProperties` 合桶**（notes/398 §8 已验证）
⇒ **用 `MaterialProperties` 当键，RenderStage/translucent/cutout 的区分自动保住。**

### 4.5 于是 B 的落点定了（且**碰不到**门与雨刷）

在 `VehicleResource.writeToOptimizedModels` 里，对每个 `PartCondition`：

```
现在：OptimizedModelWrapper.fromObjModels(objModels)      // 每个 ObjModel 各自 upload ⇒ 各自一个 VertexArray ⇒ 每个部件一次 draw
改成：把各 ObjModel 的 RawMesh 收进一个 RawModel → append → 一次 upload(DEFAULT_MAPPING)
```

`optimizedModelDoor` **根本不在这些 bundle 里**（它是 `ModelPropertiesPart` 从**源**列表自己建的），
所以**门与雨刷的代码一行都不用碰** —— 合并动不到它们。

**但有一个顺序陷阱必须处理**：`fromObjModels` 会对每个 `RawModel` 跑
`generateNormals() + distinct()`（**就地修改**），而批次 map 与 `optimizedModelDoor`
**共享同一批 ObjModel** ⇒ 如果我在它归一化**之前**去克隆 RawMesh，拿到的法线可能是全零
（`RawMesh.upload` 会 `normalize()` 零向量 ⇒ 光照全坏）。这与 notes/398 §2 踩的是同一个坑。

⇒ **规矩：先从 `RawModel` 克隆（`new Vertex(v)` / `new Face(f)` 都是深拷贝），只读不改；
且必须在 `fromObjModels` 跑过之后读，或自己先跑一次 `generateNormals() + distinct()`。**
`isDoor()` / `isMechanism()` 的实现（:336 / :345）要在写代码前顺手确认一遍判据字符串。

> 判据已确认（2026-10-05）：`isDoor()` = `doorXMultiplier != 0 || doorZMultiplier != 0`；
> `isMechanism()` = 组名以 `wiper` 开头。**分类发生在上游 `ModelPropertiesPart`**，
> `writeToOptimizedModels` 收到的 bundle 里只有该进去的部件。

## 5 B 到底值多少钱 —— 先算天花板，再决定要不要冒破坏车辆的风险

用已实测的两个数（notes/398 那次对照）反推单价：

| 量 | 值 | 来源 |
|---|---|---|
| 每 draw 的提交成本 | **≈ 2.9 µs** | 659 根钢轨 draw 被消掉后 submit 降了 1.91 ms ⇒ 1.91 ms ÷ 659 |
| 车辆 draw（重场景） | 284/pass | `非钢轨 draws=284` |
| 车辆 draw（本次轻场景） | 196/pass | `非钢轨 draws=196` |

⇒ **B 的天花板 ≈ 196–284 × 2.9 µs × 2 pass ≈ 1.1–1.6 ms/帧。**

| 场景 | 帧时 | B 的占比 |
|---|---|---|
| 轻（93.8 FPS） | 10 ms | ~11% |
| 重（41 FPS） | 24 ms | ~5% |

**对比一下同期账上的其它项**（重场景实测）：`submit` 合计 2.72 ms、
`vehicles` Java 侧 3.63 ms（尖峰 52.68 ms）、**未量到（地形+呈现）≈ 16 ms**。

⇒ **B 是 ~1.1–1.6 ms，排在"未量到的 16 ms"和"车辆的 Java 侧 3.63 ms"之后。**
而它的风险面是**车辆外观 / 车门 / 车灯 / 雨刷**（目标里写死不许变的四项），
这段代码已经因为"多画一份/不动"各踩过一次（:203-212、:404-415）。

**所以我的建议改一下**：B **不该**是下一个动的东西。下一个该问的是
**"那 16 ms 未量到的到底是什么"** —— 它比 B 大 10 倍，而且至今没有埋点。
（可参照 notes/395 的教训：`draws/frame` 与帧率相关，但**不是唯一杠杆**；
钢轨那一轮就是"把 5 ms 的 submit 当成全部差距"，结果只兑现了 1.9 ms。）

如果仍要做 B，工程上应当**默认关闭 + 系统属性开关**（照抄钢轨那套纪律）：

```
-Dmmtr.vehiclemerge=true     # 默认 false ⇒ 行为与现在**逐位相同**
```

这样风险面被压到"只有主动开开关才会变"，而且能**同机同事位 A/B**（钢轨那次就是因为
两次会话站位不同，对比一度不成立 —— 见 notes/398 §3 的教训）。

### 5.1 已实现（默认关闭）

| 文件 | 内容 |
|---|---|
| `resource/MmtrVehicleMeshMerger.java` | **新增**：把一批部件的 `RawMesh` 收进一个 `RawModel`（`append` 按材质合桶 + 平移面索引）→ 一次 `upload(DEFAULT_MAPPING)` → 一个 `OptimizedModel`。带 `-Dmmtr.vehiclemerge`（默认 `false`）；任何失败都回退 `fromObjModels`，不向上抛；并打一行 `[MMTR-VEHMERGE] 合并 N 个部件 → M 个材质（= M 次 draw）` |
| `resource/VehicleResource.java` | `writeToOptimizedModels` 里按开关二选一；**只碰那两个 bundle** |

**顺序陷阱已按 §4.5 落实**：先对源 `RawModel` 跑 `generateNormals() + distinct()`，**再** `append`。
反过来会拿到全零法线，而 `upload` 会对法线 `normalize()` ⇒ 光照全坏（notes/398 §2 踩过）。

**默认关闭 ⇒ 本次改动对现有画面的行为逐位相同。** 要验证才加 `-Dmmtr.vehiclemerge=true`。

**为什么没到"每材质 1 次"**：合并的粒度是**每个 `PartCondition` 一次**

那会改变可见性语义，**不做**。

**为什么 −86% 的 draw 只换来 −1.68 ms**：与 notes/399 §5 的预估（1.1–1.6 ms）吻合 ——
单价就是 ~2.9 µs/draw。这也再次说明：**draw 数已经不是主要矛盾了**
（改后 `非钢轨 40 + 钢轨 6 = 46`，而同期 `vehicles` Java 侧 3.18 ms、未量到的仍有 ~10 ms）。
