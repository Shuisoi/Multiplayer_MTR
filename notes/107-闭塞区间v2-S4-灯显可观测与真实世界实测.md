## 1. 交付

| 件 | 内容 |
| --- | --- |
| `MmtrDirectionalBlockService.sectionProtecting(railHex, entryNode)` | 从**进入节点**侧找到保护这根轨的那条有向区间（进入节点必须匹配区间首段的起点 —— 同一根轨从另一端进入属于反方向的另一条区间，不能混报） |
| `MmtrDirectionalBlockService.chainDepth(railHex, entryNode, trees, restrictedNodes, maxDepth)` | v2 版链深：**单位是灯到灯的区间**，1 = 本区间被占（红）/ 2 = 下一区间（单黄）/ 3 = 再下一区间（双黄）/ 0 = 绿。没有区间的轨返回 0，调用方回退 v1 |
| `boundaryNodeKeys(section)` | 区间进/出边界节点的 `x,y,z` 键（供 ④ 的"节点未清"判据复用同一套键） |
| `describeLampAspects(...)` + 指令 `lamps-v2` | 逐灯报告"按 v2 该显示什么"（含区间段数/长度/后继灯），用于**接线前**在真实世界对照 |

## 4. 实测暴露的设计缺口（必须拍板，故本片不接线）

**"只跟最直的一条腿"在车场咽喉出口处会让一盏灯只保护一股道。**

证据：这 6 列车停在 `z=-122..-79` 的 6 条**平行**股道上（x=-154…-193），
而 `z=-122` 那 4 盏灯的区间**只覆盖 x=-170 那一条**（43 m，1 段）。
也就是说，这是一个"车场出口咽喉 + 多条平行股道"的地形，而当前走行规则每到一个节点只挑**最直的一腿**，
所以一盏灯只能照到它正对的那一股道。

两条路线：

| 路线 | 做法 | 后果 |
| --- | --- | --- |
| **A. 保持单腿**（现状） | 咽喉出口要为**每条股道各放一盏灯** | 与真实联锁不一致（现实里出口信号保护整个咽喉区）；车场要放很多灯 |
| **B. 多腿收窄**（更贴现实） | 走行在岔口**跟着节点走**（把该节点所有前向腿都当**同一区间**，或按当前道岔位置/进路收窄到一条） | 与 `MmtrSignalAspect` 现有"无进路时每个分支都算"的保守链一致；但会改变区间长度与链深分布，需要在 S4 后半一并回归 |

**建议 B**（并在有进路时用进路收窄到一条腿，无进路时保守全算）—— 理由是与既有 A2 显示语义一致，
且 v1 本来就是这个口径；A 会让灯位数量爆炸且与现实不符。**但这条要用户拍板**，因为它改变
"区间有多长、哪些轨属于同一个闭塞"这一最基础的定义。
