# 241 · 定速第四次修订：AFB 能"加"牵引 + 客户端→服务端三段链路日志

日期：2026-09-23 · 现场第四轮，用户两句话把问题定死了：

> **「现在的逻辑就是有问题。定速的设置无法增加牵引力，只能减少牵引力。」**
> **「外加应该从操作是否从客户端来到服务端来检查。」**

---

## 1. 修法一：AFB 能加也能减（`afbUsesHandleAsCap` 缺省 false）

前几版无论怎么调，牵引力都被"手柄位置"夹住 —— 手柄给 30%，AFB 最多也只能给 30%，所以从司机座位上看
**"定速只会削、不会加"**。现在缺省 `afbUsesHandleAsCap = false`：

```
error > 门限  →  牵引 = clamp(afbGainPerMps × error, 0, 1)      ← 不受手柄限制，**能加**
error < −门限 →  电阻制动出 min(需要, 可用)，缺口由 AFB **补气**（与气制动手柄取大耦合）
带内          →  惰行
```

- 手柄的**电阻制动侧**仍是司机的手动干预（它一有诉求就走制动支，牵引被压住）；
- 气制动手柄一离开"运行"位、或缸压没排空 ⇒ 牵引联锁为 0（司机拉闸优先）；
- 想完全手动开车：把定速关到 0（这才是"动力手柄决定输出力"的场景）。

## 2. 修法二：三段链路日志（客户端发 → 服务端收 → 控制器算）

一次操纵要经过三段，任何一段断了，在 HUD 上看起来都是"按了没用"。现在三段都留着痕：

| 段 | 日志（前缀） | 触发 |
| --- | --- | --- |
| ① 客户端**发出** | `[MMTR-DRV] client sent vehicle=… 油门/制动/定速/换向` | `MmtrDriveInput` 每秒补发时（限频 2 s），需 `-Dmmtr.trace=true` |
| ② 服务端**收到** | `[MMTR-DRV] 收到操纵：车=… 油门=… 制动=… 定速=… 换向=… 司机=…` | `Vehicle.applyMmtrControl`（限频 2 s） |
| ③ 控制器**算出来的** | `[MMTR-CONSIST] …手柄=… 制动=… 换向=… 定速=… 牵引比=x%/电阻y% AFB=true/false 速度=…` | `simulateMmtrMotion` 每 2 s（手柄非零时） |

被拒的操纵另有既有的 `[MMTR-DRV] 操纵被拒：理由=…`（三种拒绝：不在司机位 / 无身份 / 保护）。

## 3. 测试（世界里那台 BR101 的参数）

```
[AFB5] 手柄关闭、定速 100：200 s 后 99.77 km/h        ← 手柄不给力也能到
[AFB]  手柄 97、定速 100：峰值 99.77、稳态 99.77      ← 不超调、差 0.23 km/h
[AFB3] 从 120 起、定速 100：60 s 后 99.77，最低 99.77 ← 反向收得回、不下冲
[AFB4] 从 60 起、定速 20：最大缸压 1.000，90 s 后 19.83 ← 补气真的上
新增：afbCanAddTractionBeyondTheHandlePosition       ← 手柄 5% 时牵引比 > 5%（"只能减"的反面判据）
```

引擎全量 **784 条，失败 3 条**（仍是那 3 条世界存档漂移）；客户端类型检查 OK（并新增了
"jar 比引擎 classes 旧就点名警告"这条，notes/237 §5）。

## 4. 附：客户端镜像被**每秒重建约 17 次**

开着 `-Dmmtr.trace` 跑了 80 s，`[MMTR-CL] mirror created` 打了 **1383 行**（15:10:21 → 15:11:41），
而且 `progress` 每次只前进 1–1.5 m —— 也就是**每个客户端 tick 都在 new 一个 `VehicleExtension`**
（`VehicleExtension` 构造函数里那行日志）。这解释了"客户端看到的和引擎算的不一致"为什么总是难以复现：
镜像对象的本地积分每 tick 都被重建一次。**这是下一个要查的目标**（MTR 客户端车辆更新路径，
很可能在 `MinecraftClientData.updateVehicles` / `ClientVehicleSync` 里无条件重建）。
