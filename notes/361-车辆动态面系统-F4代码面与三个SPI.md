## 0. 一句话

作者侧仍然只写 JSON；**代码级的扩展住在模组里**，由 `MmtrFaceExtension` 一个接口进，
能加**元素画法 / 算子 / 过滤器 / 字段**四样东西 —— 加完就出现在面文档里，引擎源码一个字不用动。

## 1. 四类注册

| 给什么 | 登记口 | 落在哪 | 作者侧长这样 |
|---|---|---|---|
| 元素画法 | `registrar.element("vendor:bar", renderer, "value")` | `MmtrFaceElements.register`（`render.panel`：画布在这一层） | `{"type": "vendor:bar", "x":0.1, "w":0.8, "value": 0.62}` |
| 算子 | `registrar.function("vendor:percent", (args, data) -> …)` | `MmtrFaceLogic.register`（F0 就有了，F4 才把命名规矩与装载补上） | `{"vendor:percent": [{"var":"a"}, {"var":"b"}]}` |
| 过滤器 | `registrar.filter("vendor:kmh", (value, parameter) -> …)` | `MmtrFaceText.registerFilter` | `{speedKmh\|vendor:kmh}` |
| 字段 | `registrar.field(new MmtrFaceField(){ … })` | `MmtrFaceField.Registry`（**从快照算**，见下） | `{vendor:traction}` / `{"var":"vendor:traction"}` |

发现方式是最标准的 `ServiceLoader`：模组里放一份
`META-INF/services/org.mtr.mod.mmtr.face.MmtrFaceExtension`，客户端启动扫一次、**每次资源重载再扫一次**
（`CustomResourceLoader`），所以"装了/卸了模组"重载后立刻生效，不会留一半旧注册。

## 2. 命名规矩：必须带命名空间

元素类型 / 算子 / 过滤器 / 字段一律要写成 `厂家:名字`（`vendor:bar`）。不带的**拒绝注册**并记一条账。三条理由：

1. **不撞内置**：`text`/`rect`/… 与 32 个算子、8 个过滤器是"随包发行的最小集"，扩展不该能悄悄把它换掉 ——
   否则同一份文档在不同客户端上画出不同的东西；
2. **能解释"我这里为什么没有"**：自检报 P4"不认识的元素类型"时，作者一眼知道"这是某个模组提供的，我没装"；
3. **能解释"我这里为什么不一样"**：文档里的键本身就能自证来自哪个扩展。

配套的是**两份清单**，别混：

| 清单 | 含义 | 谁用 |
|---|---|---|
| `operators()` / `filters()` / `schema.json` / `ELEMENT_TYPES` | **随包发行的最小集**（32 / 8 / 9 种） | 工具一致性用例、工作室面板、`verify_face.js` —— 扩展**不进**这几份 |
| `allOperators()` / `allFilters()` / `MmtrFaceElements.types()` | **这台客户端现在认得什么** | 日志、调试、扩展自查 |

## 3. 字段：为什么是"从快照算"而不是"向引擎要"

字段值只有两条来路：

* **引擎镜像**（`MmtrFaceFields` 那 53 行）：值来自权威模拟器，走稀疏补丁同步。要加一个得动引擎
  （字段表 + 同步键 + 提供者），**不是**附属模组该做的事 —— 这条仍然走"加字段四步曲"；
* **客户端算**（`MmtrFaceField.value(快照)`，F4 新增）：拿**已经收集好的那份快照**算一个新量。
  例：由 `motor.forceN` 与 `speedKmh` 算"牵引/惰行/制动"。

第二条刻意**只能读快照、读不到游戏世界**：于是扩展字段与内置字段在面文档里行为完全一样
（一样进重画签名、一样能离线出图、一样碰不到"权威数据"那条线，见 notes/259 的老毛病）。

## 4. 判据：第三方代码真的生效（149 / 149）

`MmtrFaceExtensionTests` 做的事就是"一个附属模组作者会做的事"，四步都真跑：

1. 用 JDK 自带的编译器 API **真的编译** `sandbox/face-addon/src`（不是"假设它能编译"）；
2. 把编译产物（含 `META-INF/services`）用 `URLClassLoader` 装进来；
3. 交给 `MmtrFaceExtensions.load(classLoader)` —— 与客户端启动**同一条路**（ServiceLoader）；
4. 断言四件事：`vendor:bar` **画出了红色像素**（出图再读回像素）、`vendor:percent` 算得出 `25.0` 与除零的 `null`、
   `{v|vendor:kmh:mph}` 得到 `12 mph`、`MmtrFaceData` 里出现 `vendor:traction`（且取不到电机出力时**不放进去**）。

外加一条反例：不带命名空间的四类注册**全部被拒绝**、四类各记一条账、内置清单不受影响。

## 5. 踩坑（都是当场修掉的）

1. **`%TEMP%` 不可写**：用例最初用 `Files.createTempDirectory` ⇒ `AccessDeniedException`（这台机器上 java 进程的临时目录不可写）
   ⇒ 编译产物改落 `sandbox/face-addon/out`。同一个毛病在离线出图里表现成"ImageIO 一张图都读不出"
   （notes/360 §5），是**同一个环境事实**的第二次现形。
2. **`operators()` 该不该包含扩展**：一开始用 `operators()` 断言扩展算子，红了 —— 它必须保持
   "随包发行的 32 个"（工具一致性用例拿它与 `verify_face.js` 逐项比对）。于是补 `allOperators()`/`allFilters()`，
   把"最小集"与"这台客户端认得的集"分开。**这不是绕开判据，而是判据本身要求两份清单**。
3. **过滤器名自带冒号 ⇒ 参数不能用"第一个冒号"切**：`{v|vendor:kmh:mph}` 按第一个冒号切会解析成
   名字 `vendor`、参数 `kmh:mph`。改成**最长匹配已注册的名字**，参数取它之后那一段（用例钉着 `12 mph`）。
4. **扩展的键要报上来**：不报的话，`vendor:bar` 上写的每个键都会被"未知键"守卫记一条账（那是给拼错用的提示）——
   合法扩展会天天刷假警告。于是 `element(type, renderer, keys…)` 有可变参数，声明的键进
   `MmtrFaceSchema.registerExtensionKeys`（只影响拼写守卫，**不进** `schema.json`）。
5. **`Op` 是两个参数**（`(List<Object> args, Object data)`），不是只有一个 —— 参考扩展第一版写成单参 lambda 编译不过；
   好在这里的编译错误信息会**带出 javac 的原文**（用例把诊断流收进断言消息里），一眼就看到。

## 6. 用户自己验收时的三步

F4 的判据本来就在**离线**（设计文档 §9 那一行写的就是"在 `sandbox/` 写一个第三方风格的自定义元素，
不碰引擎/模组源码即生效"），所以三步都是本地命令、不需要进游戏：

1. **看它真的编译了第三方代码**：
   `pwsh -File mmtr\scripts\run-fabric-tests-offline.ps1`
   —— 里面 `MmtrFaceExtensionTests` 会用 JDK 编译器编译 `sandbox/face-addon/src`、
   用 ServiceLoader 装进来、**出一张图再读回像素**（产物在 `sandbox/face-addon/out`、`out-bar.png`）。
2. **看那一张图**：`sandbox\face-addon\out-bar.png` 里应当有一段**红色横条，正好占框宽的一半**
   （`value: 0.5`；这张图是"第三方画法真的上屏了"的唯一直接证据）。
3. **想真在游戏里看到**：把参考扩展做成一个带 `fabric.mod.json`（`"depends": {"mmtr": ">=4.0.5"}`）的小模组丢进
   `mmtr\game\fabric\run\mods\`，面文档里写 `{"type": "vendor:bar", …}` —— 这一轮没做（见 §7 欠账 6）。

## 7. 欠账（诚实清单）

1. （已随扩展路径撤销）**SPI 没有版本号/能力协商**：将来若改 `MmtrFaceElementRenderer` 的签名，已编译的扩展会 `NoSuchMethodError`。
   现阶段的规矩是"只加不改"；真要改就在服务声明里带上版本（还没做）。
2. （已随扩展路径撤销）**扩展键不进 `schema.json`**：所以工作室的属性面板不会显示扩展类型的专属键、`verify_face.js` 会把它们报成
   P4/P9 —— 目前的解法是作者侧用 `--allow-type` / `--extra-fields` 放行（见作者指南），
   要让工具**自动**知道，得让扩展随包带一份字段/键声明文件（还没做）。
3. （已随扩展路径撤销）元素画法**要不要允许扩展画到"折叠面（facets）"上**：目前 facets 仍然整块不走面系统，扩展也画不到。
4. （已随扩展路径撤销）`MmtrFaceExtension` 只扫 `ServiceLoader`；模组热重载（如果有）不会重新扫，只有资源重载会。
5. （已随扩展路径撤销）**画法上下文的类型名不好看**：扩展写 lambda（`(canvas, document, element, paint) -> …`）时不用提它，但若要显式声明方法，参数类型现在是 `MmtrFaceElements.Paint`（一个嵌在画法注册表里的 record）。它该叫 `MmtrFacePaint` 独立成文件 —— 等有第二个扩展真的要显式声明时再改（现在改只是搬名字，价值不大）。
6. （已随扩展路径撤销）**实机验证 SPI 要打一个真的附属模组**：离线判据（编译第三方源码 + ServiceLoader 装载 + 出图读像素）已经闭环，但要**在游戏里**看到 `vendor:bar`，得做一个带 `fabric.mod.json` 的小模组丢进 `run/mods/` —— 这一轮没做（本轮判据本来就是离线的，见 §4）。
