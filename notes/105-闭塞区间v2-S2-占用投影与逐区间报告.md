## 1. 交付

| 件 | 内容 |
| --- | --- |
| `isOccupied(section, trees)` | 占用投影：区间的每个 span 是**同一根轨上、与占用树同弧长空间**的窗口，所以逐 span 与共享占用树求交即可；跨多根轨的区间**任一段命中即算被占**。写入端零改动（沿用既有"只换读取端粒度"原则） |
| `sectionEndAheadM(railHex, arc, heading)` | 本区间还剩多长（S3 的 S1 停车要用）；不在任何区间时返回 `Double.MAX_VALUE` = 无灯区段没有该停的边界 |
| `sectionAhead(railHex, arc, heading, trees)` | 本车"下一个必须清空才可进入"的区间：本区间空则就是本区间，本区间被占则取其后续区间 |
| `following(section)` | 区间链：某区间终止于某盏灯 → 后续区间 = 那盏灯开启的区间 |
| `MmtrDirectionalBlockReport` + 指令 `blocks-v2 [all\|<railHex>]` | 逐**区间**报告（起灯 → 止灯、跨几根轨、总长、每根轨的弧长窗口），与 v1 的 `blocks` 并存对照 |

`blocks-v2` 由 game 侧 `MmtrCommandExecutor` 执行（与 `interlock` / `blocks` 同一条 web 指令通道）。

## 3. 实测暴露的两个真问题（都不是 v2 走行的错）

### 3.1 灯位重复 —— 4 盏灯定出**同一个**区间

`-152 / -160 / -168 / -175, z=-122` 四盏灯全部绑到同一根 43 m 轨（`FFFFFFB1`）并朝同一方向，
于是四条区间**完全相同**。也就是说 **z=-122 那 4 盏灯里只有 1 盏有意义**；
`-149/z=-169` 与 `-157/-163/z=-189` 三盏灯又一起走进同一条 15 根轨的走廊、彼此重复。

这是**布置问题**（灯挤在同一节点群 / 绑到同一根轨），不是区间模型的问题 —— 但它正好解释了
用户看到的"区间没划分出来"：**灯虽然多，却没有一盏把线路切成不同的段**。处置建议：
把冗余灯移到线路中段（或至少移到不同节点），一个方向一条走廊只留一盏。属 §7 S5 的布置侧收尾。

### 3.2 走行以"尽头"结束，且最后一次终止在**道岔节点**

8 条区间**全部**以"尽头"结束（`exitSignalKey` 为空），而不是终止在下一盏灯。多数是合理的
（该方向确实没有下一盏灯了）。但 `-157` 与 `-163` 两条在**同一个节点**上以不同的弧长收尾
（26.99 m 与 13.42 m，都在轨道末段），这个节点有 ≥3 条邻轨 —— 说明**在岔口选不出腿**时走行就停了。

- 当前实现的选择规则是"最大点积（最直的一腿），且 dot > 0.1"。在岔口如果所有续轨都与来向
  接近垂直/折返，就会停下。对"照一条腿"的语义这是可接受的，但**咽喉/渡线上的一盏灯会因此
  只覆盖很短一段**。
- 处置：**记为 S4 的开放问题**（设计文档 §6 风险表已列"走行在复杂咽喉/渡线上叉开或打环"）。
  在接显示之前必须先定：岔口是"选最直一腿"（现状）还是"跟当前道岔位置/进路"（更贴现实，但要在
  S4 与进路收窄一起做）。
