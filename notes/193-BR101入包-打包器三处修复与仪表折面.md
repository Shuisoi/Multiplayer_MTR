## 2. 打包器缺陷（3 处，都会静默出错）

### 2.1 参考法线取了"组质心三点叉积"——折面仪表因此拿不到 facet 数据

`buildAnchors` 里锚点的法线原本是 `cross(v1-c, v2-c)`，`c` 是**整组所有顶点的质心**。
组是平的时它恰好等于参考面的法线；**组一折，质心就离开了参考面**，这个叉积指向别处。
BR101 的仪表板实测**偏 49.3°**，于是连锁三件事一起坏（全部静默）：

1. 锚点自己写出去的 `normal`/`up`/`right` 是错的 —— `up` 是对 `normal` 正交化的，
   49° 的误差把 `up` 从 `(0, 0.98, -0.20)` 拖成 `(-0.22, 0.50, -0.84)`；
2. `buildFacets` 的绕序守卫拿"参考面法线"和它比，差的超过 0.9 → 直接放弃，
   **折面仪表一块 facet 数据都没有**，退回"一块错位的大平板"（docs §1.3⑨ 说的那个失败）；
3. 每块风挡的 2D 域也建在这个歪法线上（BR101 实测偏 **5.83°**），
   于是打包器自己的雨刷拟合与独立校验器**差 3–27 mm**。

**修法**：锚点法线改成**参考面自己的 Newell 法线**（docs §1.3⑨ 本来就写着"法线只取面积最大那个面"）。
平的组方向不变（HST_H 只差 5.4°→0°，见 §5），折的组一次修好三件事。

### 2.2 行程求解分不清"停放边"和"远端边"——四块玻璃里错两块

`fitWiperMechanism` 原本的规则是"排除 |phi| < 0.2 的候选，取残差全局最小"。
真实机车的平行连杆**两条边近乎平行**，刀片到远端盖与停放盖的距离只差几毫米
（BR101 实测 **4.85 mm vs 6.64 mm**），而离散化会让停放边的最佳 phi 落在 **0.30°** 上——
**刚好越过 0.2° 的过滤器**。于是只要两个实现各自 PCA 出的刀片端点差几毫米，
全局最小就会选中**停放边**，写出 `sweepDeg = 0.30`。

实测后果（cab 2 的两块）：`298.956°` 与 `0.30°` —— **四块雨刷里两块等于不刮**。
（cab 1 两块只是"刚好"赢了 1.8 mm。）

**修法**：**先按位置认停放边**（最佳 |phi| 最小的那条，且必须 < 8°），把它摘掉，
再在剩下的边里取全局最小，并要求行程 > 8°。phi 上"0 附近"与"行程角"相差一个数量级，
所以这个判据不受毫米级差异影响。修后四块**全部解出 92.60°**，且四块互为精确镜像
（`pivot u` 0.6936/0.3064 对称、`armM` 全为 1.6038、`park` 89.13/90.87）。

### 2.3 ★ `foldAboutUp` 分支把 v 矩形也建在折向坐标上（折面图会散架）

`buildFacets` 的两个分支里，折痕**竖向**（fold about `up`）那支：

```js
const uA=(sharedMin2-sharedMin)/sharedSpan, uB=...;   // 跨折痕（shared 坐标）
const sA=(sMin-foldMin)/foldSpan, sB=...;             // 沿折痕（fold 坐标）
const vA=1-sB, vB=1-sA;
const face = foldAboutRight ? {u0:uA,u1:uB,v0:vA,v1:vB}
                            : {u0:sA,u1:sB,v0:vA,v1:vB};   // ✗ v 又用了一次 fold 坐标
```

`foldAboutUp` 时 v 应该用 **shared 坐标**（沿折痕那条），却用了 fold 坐标——
于是每块面的 `v1-v0` 恰好等于 `u1-u0`，三块板被**沿图像竖向叠起来**，
而它们本该共享一条竖折痕。`verify_facets` 当场报 12 条
（`rectangle area != face area` + `the image would break at the crease`）。

**为什么一直没被发现**：`fixture/foldfix.obj` 折痕是**横向**的，走的是另一支；
这一支从来没被跑过。修后 BR101 的仪表板 facet 校验通过。

顺带在打包器里加了一条**自检**（每条 facet 的矩形尺寸必须等于该面的真实尺寸，
不符就打 WARNING 并给出两个数）——这类缺陷此前只有人手动去跑 `verify_facets` 才看得见。

## 3. 校验器缺陷（2 处，会造成"假 FAIL"）

### 3.1 M2 / band 测试没有乘 `sweepSign`

客户端扫的是 `park → park + sweepDeg·sweepSign`。校验器的两处（刀片自转角、band 覆盖）
都写成 `+sweepDeg`，于是 **`sweepSign = -1` 的玻璃被反向走了一遍连杆行程**——
在那段区间机构根本装不起来，于是：

```
FAIL: wipersweep_1_2: the blade turns 89.36 deg over a 92.60 deg stroke, i.e. it is not
      a linkage at all  ← 一个被证明是"理想平行四边形"（刀片自转 0.11°）的模型
```

**修法**：两处都乘上**写进配置的那个** `sweepSign`（本节校验的就是客户端要读的那份配置）。

### 3.2 band 测试要求"弦 = 弧"，正确模型差 3.8 mm 过不去

四边形 band 是刀片轨迹的**弦**，而真实轨迹是**弧**：刀片由半径 R 的曲柄驱动，
一步 dθ 内偏离弦 `R(1-cos(dθ/2))`。BR101 实测 R=1.17 m、dθ=9.26° → **3.79 mm**，
而固定膨胀量是 3 mm —— 一个明显正确的雨刷就卡在这 0.79 mm 上。

**修法**：按几何算膨胀量（`R(1-cos(dθ/2))`，取与常量的较大者）。
判据的牙没掉：`selftest` 注入的故障是 50/100 mm 与 10° 量级，**21/21 仍全部抓到**。

## 4. 模型侧：仪表板两侧板是"错切的平行四边形"（用户选择修）

实测 `mmtr_hud_1`：中间板是标准矩形（相邻边 **90.0°**），
左右两块却是 **85.70° / 94.31°** —— 宽边在 XZ 平面里转了 22.5°，
而上边（折痕方向 `(0, 0.45, -0.09)`）**没有跟着转**。后果：面板是平行四边形，
而客户端每个折面画一个**矩形**，矩形比面板高约 0.1 m（0.556 vs 0.459），
`verify_facets` 报 4 条 `rectangle area != face area`。

**修法**（`sandbox/br101_r50_hud_fold_fix.py`，只碰 `mmtr_hud_1/2` 的外边两个顶点/块）：

```
外边 = 折痕端点 + R(u, θ) · flat方向 · L
```

`u` = 折痕方向，`flat方向` = 中间板的宽度方向（指向该侧），
`θ` = **从几何量出来的当前折角**（≈22.5°，不写死），`L` = 当前板长（不变）。
即：保持折痕边、板长、折角，只把宽边摆正到与折痕垂直。

| 项 | 结果 |
|---|---|
| 四角 | **全部 90.0°**（此前 85.70/90.0/94.31） |
| 共面性 | ≤ 4.7e-7 |
| 外边位移 | 左板 **+97 mm（升）**、右板 **+57 mm**（左右对称；即"折一块前倾的板，翼尖会抬起来"） |
| 折角 | 折面图实测 **45.0°**（= 2 × 22.5） |
| 网格 | 8 顶点 / 3 面（不变），折痕顶点没动 → 仍然焊接 |
| 幂等 | 再跑一次位移 = 0.000 |

前后对照图：`sandbox/vox_preview/hud_cab_view.png`（司机后方俯视，
车体外壳临时隐藏、仪表涂品红）。**脚本可反复跑**（第二次位移为 0）。

## 7. 遗留（诚实说明）

1. **世界里的 br101 车辆尺寸是 MTR 默认值**，不是这辆车的：
   `world/mtr/minecraft/overworld/mmtr-rolling-stock.json` 里两处 br101 都是
   `length 16.0 / bogie1 −5.333 / bogie2 +5.333`（= MTR 给"长度 16 的车"的默认值），
   而模型是 **32.3729 / ±9.2797**。后果：这辆车在**世界里**的占用与连挂间距按 16 格算，
   而客户端按 32.37 格画——会与邻车重叠、进出岔区的占位也不对。
   **本轮没动**（那是存档侧数据，且服务端在跑、内存态会覆盖文件）。
   修法二选一：① 停服改 `mmtr-rolling-stock.json` 再起服；② 游戏内用 MTR Creator/车场界面按正确尺寸重放这辆车。
2. **雨刷停放位**：note 190 记录用户原话是"静止位置应该在 +46 度处"，而 `r48` 导出在 `phi=-46°`（另一端）。
   本轮**按用户 2026-09-19 的选择保留 −46°**，因为两者只差"刀片静止时倒向哪边"，
   刮拭范围/角度完全一致（`sweepSign` 会跟着拟合出来）。要换只改 `r48` 的 `POSE_DEG` 后重导出重打包。
3. **`mmtr_hud_1/2` 的绕序朝车头**（法线 `z` 为负），与"法线朝司机"的字面约定相反。
   客户端是**按"法线指向原点的那一侧"自动选边**（docs §1.3⑤），所以画面不受影响；
   本轮没翻绕序（翻了 `right` 会一起翻，虽然按 §1.3⑤ 又会抵消，但没必要动）。
4. **W4（实体雨刷绕支点转）仍未做**，`driverOnBoard` 已在 notes/189 实装 →
   进游戏可以验"按 J 档位 → 刀片扫"这条链路了。
