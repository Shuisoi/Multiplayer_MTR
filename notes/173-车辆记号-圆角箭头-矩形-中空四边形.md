## 2. 引擎侧：逐节位置怎么来的

`mmtr-trains` 的每辆车上新增 `cars[]`（`SystemMapServlet.mmtrCarJson()`）：

```json
"cars": [
  {"index": 0, "railHex": "…", "railArcM": 15.2, "railArcLengthM": 25.0, "forward": false,
   "lengthM": 16.0, "stockId": "saf101", "powered": true, "capacity": 0}, …
]
```

三个关键点（都是查出来的，不是猜的）：

1. **编组从哪来**：`Vehicle.getVehicleCarsAndPositions()` 的**顺序就是编组顺序**（A 端在前）；
   每一节再由 `MmtrConsistWalker` 给出它落在**哪条腿**（`SpineLeg(railHex, entryNode, exitNode, lengthM)`）上。
2. **弧长仍然落在与车头同一套弧空间里**（沿用 notes/170 §2 的结论）：编组体给的是"车心沿**主轴**
   （一串轨腿）从 A 端量的弧"：`body.carCenterArcM(i)` → `body.legAtArcM(arc)` 得到**哪条腿** →
   `body.legOffsetM(arc)` 得到**腿内偏移**。而**弧空间与拓扑发 `path` 的空间可以差一个整长**
   （`path` 从"位置图先遇到的端点"开始走），所以最后一步按**同一个判据**翻：
   `railIndex.firstEnd(legHex).equals(leg.entryNode())` 为真就是"腿的入口就是折线首端"，
   否则整条按 `lengthM − offset` 倒着量。车头那一节用的是另一条实现（`mmtrArcOfPoint()` 投影），
   但两者比的是**同一件事** —— 拓扑收集 `ends[0]` 的顺序（`MmtrRailIndex` 建索引时也是照那个顺序 `putIfAbsent`）。
3. **每节车的朝向**：`forward = (towardB == legForward)`，其中 `legForward = firstEnd.equals(leg.entryNode())`。
   为什么不能整车共用一个方向：**列车在折返/调车时前后两节可能分别朝着两条腿的相反方向**
   （同一 `railHex` 的两个方向是两份数据）。

顺带把 `SavedRailBase.mmtrOrderedPositions()` 抽出来，让"这条轨的位置按折线顺序"只有一个实现。

### 2.1 引擎侧的用例：`MmtrTrainCarsJsonTests`（一节与八节看起来一样，所以必须自己造编组）

活页面上**验不了**这件事：dev 世界里 7 辆车全是同一车型的**单节**编组（`cars.length = 1`），
"逐节"与"整车"画出来一模一样。所以用例自己在长股道上摆一列 **8 节编组**
（`hst_h` 15 m + 6 × `hst_b` 17 m + `hst_h_rev` 15 m = 132 m，与 `MmtrConsistMultiCarPlacementTests` 同一套），
再**直接构建 `mmtr-trains` 的那份 JSON**（`SystemMapServlet.FEEDS.get("mmtr-trains").builder()` ——
与线上同一份 builder），逐条查：

- 每节的 `lengthM / powered / capacity / stockId` 与 `VehicleCar` 清单**逐位**相符
  （`powered` 就是前端画"圆角箭头 / 矩形"的判据）；
- 每节的 `railHex` 是规范形式、**世界里真有这根轨**，且 `railArcLengthM` ≈ 那根轨的几何长度（±0.1 m）；
- `0 ≤ railArcM ≤ railArcLengthM`；
- **链**：相邻两节的世界距离 ≈ 两节车长之半的和（编组背靠背连着）。弧空间没翻对的那一节会整整偏**一个轨长**
  （17–43 m），这条立刻红 —— 与 notes/170 逮到那三个坑的是同一类"另一条判据"；
- **头**：接口自己的 `headX/headZ`（那个字段已被 notes/170 独立验过）必须落在**某一节车的车身里**。

世界坐标是拿 `rail.railMath.getPosition(arc)` **反算**的：与引擎报的弧长同一套几何，但**没有复用
`mmtrCarJson` 的任何一行代码**。实测输出：

```
[CARS] 8 节编组：总长 132.0 m；头在车 0 里（7.50 m）；
       相邻中心距 16.00(≈16.00) 17.00(≈17.00) 17.00(≈17.00) 17.00(≈17.00) 17.00(≈17.00) 17.00(≈17.00) 16.00(≈16.00)
```

`7.50 m` 正好是第一节车长的一半（15 / 2）—— 头在该车正中偏前，合理；七个间距**逐位**等于理论值，
说明整列车的弧长跨了多根轨也是对的（那列编组有 132 m，比单根轨长得多）。
跑法：`.\gradlew.bat test --tests 'org.mtr.core.servlet.*'`（**已通过**，整包 BUILD SUCCESSFUL）。

## 3. 前端：形状只有一个真源（`vehicleMarkerShapes.ts`）

```ts
carMarkerKind(train, car) → "arrow" | "rectangle" | "hollow"
markerPath(kind, lengthUnits, widthUnits) → 一条 <path> 的 d
markerFilled(kind) → boolean
markerKindLabel(kind) → "动车" / "无动力车厢" / "货车"（悬浮提示里用）
```

判定规则**只有两条**，因为引擎里"是不是货车"只有**任务级**判据（`MmtrMission.Kind = PASSENGER / FREIGHT / MANEUVER`，
车本身不带货运标记）：

1. **有动力 ⇒ 圆角箭头** —— 动车、**机车**（用户追加裁定"只有无动力挂车中空、机车画箭头"：
   机车在数据上就是"有动力的那节"，所以货运任务的机车也是箭头）；
2. **没有动力 ⇒** 看任务：**货运 ⇒ 中空四边形**（挂车 / 货车），**其它 ⇒ 矩形**（无动力客车 / 回送车）。

也就是说**动力是第一判据、"货运"只在无动力时才参与** —— 这样不需要引擎新增"车级货运标记"，
用户要的观感（机车箭头、挂车中空）就有了。

### 三种形状（局部坐标：中心在原点、车头朝 +x）

| 种类 | 路径特征 | 为什么这样 |
| --- | --- | --- |
| `arrow` | 8 段、含 `Q`：车尾两角圆角 + 车头两条二次曲线收成圆润的鼻子 | 用户要"圆角箭头"；纯三角形太尖、和道岔图标混 |
| `rectangle` | 4 段直线、四角见棱 | 用户要"矩形"，与圆角箭头**一眼分得开** |
| `hollow` | 4 个点、后端满宽、前端收窄到 72%、不填充 | "中空"要能同时与**填色的矩形**和**箭头**区分；前端收窄是第二条区分通道 |

### 两个尺寸决定（都写进注释与用例了）

1. **宽固定 1.2 格，长按真车长**（`lengthM` 米 → 画布单位，1 格 = 1 米）：真车 5 米宽会盖住 5 根轨，
   那是"按比例画车"而不是"地图记号"；**长度却必须是真的** —— 一列车占住轨的哪一段是调度要看的，
   7 节 × 16 米 = 112 格，在图上就是一条能看出长度的车。
2. **车头收尖段至少占车长的 30%**：只按半宽算的话（半径 = 1.2 画布单位），16 米的车长宽比 13:1，
   画出来是"一根棍子前面削了个尖"。用例 `收尖段不能只有半宽那么长` 把这条钉住了。
   （第一版就是按半宽收尖的 —— 是**用例**而不是肉眼发现的。）

### 样式钩子

模板上是 `class="vehicle"` + `:class="vehicle-${item.kind}"`，`fill` 走 CSS：
`.vehicle { fill: var(--accent); stroke: var(--bg) }`、`.vehicle-hollow { fill: none; stroke: var(--accent) }`
（两条规则**权重相同**，靠"后写的赢"覆盖 —— 中空形状上底色描边没有意义，边线直接用强调色）。

### 老引擎的退路

`cars` 缺失（老 jar / 没有编组体）⇒ 退回"车头一节"，按**动车**画一个箭头，长度用 `FALLBACK_CAR_LENGTH_M = 16`。
这条不是摆设：**现在活页面上跑的就是这一支**（见 §5）。

## 4. 用例：10 条（`scripts/vehicle-shapes.test.ts`，`npm run test:vehicle-shapes`）

形状这种"错了也画得出来"的东西只能靠用例钉：判定三种组合、箭头**必须有曲线**、车尾两角是圆的
（`|y| = 半宽` 的点不许落在 `x = −半长` 上）、车头只有一个点且 `y = 0`、矩形四角**正好**在包围盒角上、
中空四边形只有四个点且前端比后端窄、三种形状互不相同、只有中空不填充、短车（车长 < 记号线宽）不出负长度、
浮点尾巴按 0.01 修约、`describeCar()` 把"第几节/什么车/多长/有没有动力"写进提示。

**为什么必须有用例**：活世界里现在**没有无动力车厢、也没有货运任务**（7 辆车全是 16 米动车、任务全是 `PASSENGER`），
所以矩形与中空四边形**在页面上根本画不出来** —— 探针只能证明"页面画的就是形状模块算的那一份"，
"形状本身对不对"只有用例能守。

### 顺手修掉的三条**探针自己**的问题

1. **"停着的车必须精确"曾经假失败**：图层每 2 秒才重取一次，读到 DOM 时它可能是 2 秒前的世界
   （实测差 1.44 画布单位 = 0.72 格，正好是"这一拍里挪了半步"）。现在读**两轮**（隔一个节拍），
   只对**两轮之间弧长没变**的车要求精确 —— 弧长没变就说明它真的没动，DOM 无论哪一轮画的都必须一模一样。
2. **`live-refresh-probe.mjs` 不再写死 500 ms**：节拍在"实时性 vs 吃掉多少 tick"之间来回调过
   （500 → 2000，notes/172 §5 还留着一个"把 `FEED_LIVE_MAX_AGE_MILLIS` 调到 2000"的旋钮），
   写死一个数只会让探针在别人调参之后开始假失败。现在它**从 `mapContext.ts` 读** `LIVE_REFRESH_MILLIS`，
   读数的窗口与等待也都按这个数算（隔一个完整节拍再比两次读数）。
   同一招也用在了 `node-ui-probe.mjs`（扳岔后要**等一个节拍**再读 DOM，否则"图上 27 根 vs 引擎 26 根"）。
3. **"半个方块"那条判据改了写法**：部署后它立刻假失败（7 列车的"落点 vs headX/headZ 投影"都是 15.03 画布单位）。
   原因不是画错了，而是判据本身过时了 —— 记号现在画在**车心**，而 `headX/headZ` 是**车头**，两者本来就差半个车长。
   正确写法是**把坐标差拆成沿轨 / 跨轨两半**：跨轨那半才是"半个方块"（实测正好 0.500 格），
   沿轨那半是"记号在车心"（实测 7.50 格）。**判据跟着功能一起演进**，否则它会从"守门"变成"噪声"。

## 6. 部署：趁启动器的 3 秒窗口把 jar 换掉

用户裁定"现在部署"。规矩是**服务端停着才能覆盖 `game/libs` 里的 jar**（半个 jar 事故，见 `deploy-engine.ps1` 头部），
所以过程写清楚，下次照做：

1. `POST /mtr/api/map/mmtr-command {"command":"server restart --delay=3"}` —— 优雅停机，并**写下重启标记**；
2. 轮询"命令行里有 `fabric.dli.env=server` 的 java 进程"，等它消失（实测 3 秒就退了）；
3. 立刻 `scripts\deploy-engine.ps1`（它自己会再确认一次服务端停着，所以窗口内安全）——
   **用启动器的 3 秒窗口**（`dev-server.ps1` 第 146 行：读到重启标记后 `Start-Sleep -Seconds 3` 再拉起）；
4. 校验 `build/libs` 与 `game/libs` 的 **SHA256 一致**（实测 `EA8D2394B114…`）；
5. 启动器自己把服务端拉回来（**不用我接管**，还是原来那个会话的启动器循环），新 JVM 起于 18:27:27
   —— **晚于** 18:26:45 的拷贝，所以它读到的就是新 jar。

为什么不用 `server stop`：那会让启动器**退出**，我还得自己起一个（多一个所有者）；而 `restart` 是"优雅停机 + 接力"，
窗口也够（35 MB 本地拷贝 < 1 秒）。实测整个过程服务端只断了约 45 秒。

## 7. 留给下一轮

- **无动力车厢的宽度**：现在所有记号同宽（1.2 格）；真车拖车与动车宽度差不多，没理由分开。
- **区间地图要不要也画车**：那一页画的是**引擎原始形状**（不对齐端点），要用 `VehiclesLayer` 就得把
  `railAlignment` 换成"不对齐"那一档（notes/170 §6 已记，本轮没做）。
- **真正的无动力 / 货运车**：现在世界里 8 节车**全是动车**（`powered=true`），所以矩形与中空四边形
  在活页面上仍然画不出来（只有用例守着）。等用户造出无动力或货运编组，形状就自动出来了 —— 不需要改代码。
- **`headX/headZ` 到底指哪里**：实测它比车心靠前 **7.5 m**（16 米车，半个车长是 8 m），
  而引擎侧的 8 节编组里它正好在第一节车心前 7.50 m（15 米车的一半 = 7.5）—— 两处都指向"它不是车头前脸，
  而是某个 0.5 m 缩进的基准点"。目前只用在"车头必须落在某节车身内"这条判据上，够用；要精确就得查
  `MmtrMotionSnapshot.frontX/frontZ` 的定义。
