## 1 为什么今天看不出"等待态 / 驾驶态"

不是"忘了加显示"，是**根本没有这台状态机**。今天"谁在开"散在三个各管一段的地方：

| 记录 | 位置 | 它管的那一段 | 它答不了的 |
| --- | --- | --- | --- |
| 作业单的司机绑定 | `MmtrJobScheduler.humanHold` / `driverUuid` | 这条**作业单**有没有绑定司机 | 没绑司机的车；"人已在驾驶室但还没交给他" |
| 驾驶室钥匙 | `Vehicle` 的 `mmtrCabKey` / `getMmtrCrewUuid()` | 这辆**车**的钥匙在谁手里 | **钥匙在我手里 ≠ 驾驶权在我手里**（notes/407 那个洞就是它） |
| 任务执行者 | `MmtrMission.executor` | 这**一步**是 `AUTOPILOT` 还是 `PLAYER` | 作业单里没有 mission 的那几步（换端 / 连挂 / 空作业）什么都不说 |

而且界面上唯一那行**被删掉了**：`game/fabric/.../render/MmtrTaskHud.java:542` 的注释写着 ——
原来有一行 `司机` / `自动`，**2026-09-25 用户口径「把司机删除」**，理由是"人坐在司机位上才看得见这块卡片，
所以它是冗余的"。删掉之后，"这台车现在归谁"就再没有一处回答了。

已经能自己敲的两件事：

- `/mtr mmtrboard <车id> [<车节><A|B>] [玩家名]`（`Init.java:144`，OP 2）—— 送到车上并进驾驶室；
- 坐在司机位上**按 B** 接管 / 归还（`MmtrTaskInteraction.java:92` → `PacketMmtrCabOp.TASK_TAKE/TASK_RELEASE`）。

缺的是三件：**`B` 是盲的**（按下去前后界面都不说现在归谁）、**引擎那几条指令只能在 HTTP 指令栏里发**
（`job take` / `job release` / 派车 —— 所以一直是替用户发的，这就是"需要我自己能够输入命令"）、
**没有任何一处记得"我认领了某趟车、正在站台上等它"**。

## 2 状态机

### 2.1 玩家侧值守（真源 = 引擎）

一个玩家同一时刻**至多一个**值守（一条 `Duty` 记录）。六个状态：

| 状态（界面词） | 枚举 | 含义 | 进入条件（**证据事件**） | 离开条件 |
| --- | --- | --- | --- | --- |
| 空闲 | `IDLE` | 没有值守 | 初始 / 退出后离开驾驶室 / 车没了 | 认领某趟车 |
| 等待接站 | `WAITING` | 已认领该车次，**人在下一停站站台**等（不在车上） | PDA「站台接站」（或指令） | 车到该站**停稳** → 送到车上 → `ABOARD` |
| 已上车·未获驾驶权 | `ABOARD` | 人在该车驾驶室，**油门还不归他** | 「直接上车」落位；或接站到位 | 停稳且交接条件成立 → `DRIVING` |
| 运转中 | `DRIVING` | 油门在他手里 | 引擎 `mmtrJobTakeover` 成功（`Simulator:1400`） | 退出（立刻 / 下一站）/ 离开驾驶室 |
| 运转中·下一站退出 | `DRIVING_EXIT_ARMED` | 已挂"下一站退出" | TAB 面板「下一站退出」 | 到站**停稳** → 交还自动 → `RELEASED`；接站的人此时接手 |
| 已退出 | `RELEASED` | 已交还自动，人可能还在车上 | 「马上退出」/ 下一站退出到点 | 下车 / 再接管 / 该车被删 |

**为什么"下一站退出"是独立状态而不是一个布尔**：它同时改变三件事的行为 ——
① 车次列表里这趟车对别人**只允许接站**（用户口径）；② 到站时引擎必须**自动交还**；
③ 接站的人到站时**有权直接接手**（不用再等一次静止闸门）。一个布尔会让这三条各处自己判，
而它们必须是同一个判断。

### 2.2 车次侧（PDA 列表每行）

每行要能回答"我能不能上它"，所以每行带四个字段（前三个已经在同步里，第四个是本片新增）：

| 字段 | 来源 | 今天有没有 |
| --- | --- | --- |
| 车次号（作业单名，如 `00104`） | `jobIdOfVehicle` → 镜像 `mmtrJobId` | ✅ |
| 当前这一步 / 下一步的人话 | 镜像 `mmtrTaskNote` | ✅ |
| 速度 / 到停车点距离 | 镜像 `speed` / `mmtrDistanceToStopTargetM` | ✅ |
| **值守占用**：无人 / 有玩家（运转中）/ 有玩家·下一站退出 | 本片新增，随车同步 | ❌ |

于是"两条路"的可用性是**读出来的**，不是客户端自己猜的：

| 这趟车的值守占用 | 直接上车 | 站台接站 |
| --- | --- | --- |
| 无人（`IDLE` 或没人认领） | ✅ | ✅ |
| 有玩家·运转中 | ❌（有人在开） | ❌ |
| 有玩家·**下一站退出** | ❌（到站才有位置） | ✅ |
| 有玩家·等待接站/已上车未获权（同一人） | 该人自己能"取消/接管" | — |

### 2.3 迁移图（一条线，没有旁路）

```
        ┌──────────────── 认领（等待接站） ────────────────┐
        │                                                  ▼
     IDLE ──认领（直接上车）──► ABOARD ──停稳+交接条件──► DRIVING ──「下一站退出」──► DRIVING_EXIT_ARMED
        ▲                        ▲                          │                              │
        │                        └── 接站到位（车到站） ◄────┘                              │
        │                                     ▲  到站停稳自动交还 ◄─────────────────────────┘
        └──────── 下车 / 离开驾驶室 ──── RELEASED ◄──「马上退出」──────────────────────────┘
```

三条铁律：

1. **`DRIVING` 只能由"引擎的接管成功"进入**，不许客户端自己认为在开车（notes/215 的教训：
   客户端复刻一遍引擎的判据，迟早当着司机的面互相矛盾）。
2. **交接只在停稳时发生**（`Simulator:1408` 已有闸门：`speed > 1e-9 || isMoving()` 就拒）。
   `ABOARD` 之所以存在，就是"人到了、车还在动"这个真实且常见的窗口。
3. **每个迁移必须落一条日志**（`[MMTR-DUTY] …`），带"谁 / 哪趟车 / 从哪个态到哪个态 / 为什么"。
   界面上的字与日志必须是**同一份编码**，否则"指示"就只是另一个人写的故事。

### 2.4 与既有三处记录的关系（谁继续说话）

- `MmtrJobScheduler.driverUuid`：**继续是**"这条作业单的司机"，由值守状态机在进入 `DRIVING` 时写；
  不再有别的入口写它（今天 `job take` 是唯一的写入口，S1 之后它成为更低层的原语）。
- `Vehicle.mmtrCabKey`：**继续是**"谁在驾驶室"。它是 `ABOARD` 的入口证据，不是驾驶权的证据。
- `MmtrMission.executor`：**继续是**"这一步谁执行"，`DRIVING` 时必须是 `PLAYER` + 同一个 uuid；
  这两者不一致时以值守记录为准并**报冲突**（这种不一致正是 notes/407 那个洞的形状）。
- P6 ③ 的 `Simulator.mmtrPlanPlayerDriven`（计划层的"编组由玩家开"）：值守进入 `DRIVING` 时顺带置位，
  退出时清掉 —— 否则"计划层以为 AI 在跑、实例层以为人在跑"，两套派发会互相踩。

## 3 PDA 面板规格

### 3.1 列表页（拿起 PDA 右键 / 打开界面）

一页一张表：**每行一个车次**。

```
车次   状态              这一步                        速度    到停车点
00104  有玩家·下一站退出  开到 鸥湾1台                  42 km/h  380 m    [接站]
00107  无人              TT-LOOP-1 3/14 站台作业        0 km/h   0 m      [直接上车] [站台接站]
```

行尾按钮**按 §2.2 那张可用性表出**（不可用的按钮不出，而不是出了再拒 —— 用户口径是"仅可以选择接站"）。

### 3.2 两条路

| 按钮 | 做什么 | 落到哪个状态 |
| --- | --- | --- |
| 直接上车 | 传送到**这趟车**上并进驾驶室 | `ABOARD`（车在动就停在这儿，停稳后自动 → `DRIVING`） |
| 站台接站 | 传送到**这趟车下一停站的站台**，在那儿等 | `WAITING`（车到站停稳 → 送上驾驶室 → `DRIVING`） |

### 3.3 驾驶中按 TAB

同一块面板，换成"我正在开的这趟车"：车次 / 这一步 / 时刻表（本趟剩余步骤）/ 速度 /
到停车点距离 / 两个按钮：**马上退出**、**下一站退出**。
（`马上退出` = 立刻交还自动；`下一站退出` = 挂上 `DRIVING_EXIT_ARMED`，到站自动交还。）

### 3.4 指示（同一份编码，三处一致）

1. **驾驶室 HUD 卡片**：恢复一行值守状态（`运转中·00104` / `已上车·未获驾驶权（车还在动）`），
   即 2026-09-25 删掉的那一行的**接任者**，但词表换成 §2.1 那六个；
2. **TAB 面板**：同一句话，加上可点的按钮；
3. **动作栏播报**：每次迁移给**那个玩家**播一条（"你现在是 等待接站 —— 00104 下一站 鸥湾1台"）。

## 8 下车（S3）落地记录 + 现场查出来的三条既有缺陷

对着门按 G 下车已经落地（`game/fabric` 四个文件）：`VehicleRidingMovement.mmtrAlight()` 是
**唯一**的"结束骑乘"入口（只是把既有的 `leaveRide` 起了一个 public 名字，**没有**复制一份清状态逻辑）；
`MmtrCabInteraction` 在"握着驾驶室"那一支按"准星有没有能下车的那扇门"分流：有 → 下车（**车没停稳就拒绝**），
没有 → **原样保留**今天的行为（只拔钥匙、人留在车上）。提示行同时改成按玩家状态说真话。

### 8.1 坐着时那句"按 G 下车"为什么画不出来（已修）

`MmtrInteractPrompt` 的判据是"6 m 内 **且** 视线夹角 50° 内"，而**司机门在坐着的人的视野背后**
（座位 `|z|=8.2`、司机门 `7.502`、风挡 `9.725`，司机朝风挡）。所以那条提示在驾驶状态永远不成立 ——
功能等于不存在。修法是**只放宽角度、不放宽距离**：对"我正坐着的那间驾驶室的司机门"跳过 50° 锥，
`REACH_M = 6 m` 照旧。

几何可达性用资源包锚点实测（不是推断）：座位 → 本端最近司机门 = SAF420cab 0.72 m、BR101 1.49 m、
SAF101 2.01 m、HST_H 1.91 m —— 6 m 判据都很宽松。

### 8.2 「我坐在这间驾驶室里」是**两级**判据（必须有第二级）

第一级是 `MmtrDriverSeat.current()`（位置判据，与司机 HUD / 手柄 / isDriver 上报同源）。
但 **SAF101 的资源包里一个 `mmtr_windshield` 都没有**，而 `current()` 靠"最近的风挡"定位 ⇒
**在 SAF101 上它永远是 null**。只靠第一级的话，"对着门按 G 下车"在那辆车上完全不可达，
而且没有任何线索说明为什么。第二级退回本地骑乘状态（`mmtrCabVehicleId/CarNumber/Number`，
进舱时写入、`leaveRide` 清空 —— 同一帧里就是同一个事实）。两级都要求驾驶室编号相等，
所以同一列车另一端的驾驶室门不会被误认。

### 8.3 ★ 顺手修掉的真 bug：离车不清引擎钥匙

任何"结束骑乘"（潜行 30 拍、下車、被服务端移出）都**不发** `PacketMmtrCabOp`，
于是引擎侧 `mmtrCabKeyHolder=CREW` + `mmtrCabCrew=<旧 uuid>` **永远留着**，
而 `MmtrCabState.insertKey` 会因此拒绝**别的**乘务员进这间驾驶室 —— 现场表现是
"这间驾驶室再也没人能进"，只有本人再按一次 G 或操作员敲 `cab <id> out` 才解得开。
现在 `leaveRide` 在清 `mmtrCab*` **之前**按本地状态补发 `Op.LEAVE`（单发，单向包，
**拔钥匙失败不影响下车成功** —— 两件事刻意解耦）。

### 8.4 查出来但**没有**修的（留给下一轮，都记在这里免得丢）

1. **SAF101 没有风挡锚点 ⇒ `MmtrDriverSeat.current()` 恒为 null**。这不只影响下车：
   `isAtControls()` 为假 ⇒ 司机 HUD、速度 HUD、任务提示音、**输入解耦**在 SAF101 上全都不生效，
   而且 `refreshDriverFlag()` 会因此**不上报 isDriver**。修在锚点侧（补 `mmtr_windshield`）
   或把 `nearestCab` 的判据从"风挡"改成"座位/仪表"。
2. `MmtrInteractPrompt` 与 `MmtrCabInteraction` 各有一份完全相同的私有 `vehicleById` / `modelIdFor`。
3. 提示行在"没有目标"时不画，而上车那一支只回一句"把准星对准司机门再按 G" —— 约 10 条不可达路径
   玩家看不到任何"为什么"。与 §8.1 是同一类毛病（提示与状态不一致），只是方向相反。

### 9.3 实机查出来的两个缺陷（一个已修，一个待修）

   `refreshPassiveFields`，扩散面大）。`direct=true`（传送）那条有同一个形状的风险。

   改成：切换按钮挪到顶部右侧、驾驶页按钮从第 7 行下面起、按钮文案跟当前页走

## 4 下车（对着门按 G）

今天 G 是 `MMTR_CAB_INTERACT`（上车/进驾驶室）。要加的是**反向那一半**：
在车上 / 驾驶状态下，准星对着门按 G → 离开驾驶室并下车。

判据要分清（否则"上车"与"下车"会互相抢同一个按键）：

- 没在车上 + 对着门 → **上车**（今天的行为，不变）；
- 在车上（或钥匙在我手里）+ 对着门 → **下车**：`DRIVING` 时先交还自动（或拒一次并提示
  "还在运转中，先按 TAB 退出" —— 两种口径要选一种，见 §6 待定 ③）。

## 6 待定与风险

1. **"下一站"到底是不是引擎知道的**：引擎有 mission 的目标（`targetId` / `targetRailHex`），
   但它不一定是**站台**（可能是股道 / 轨目标）。站台接站要求"下一站是站台"才成立 ——
   非站台的目标（回库、折返）必须**拒绝接站**并说明原因，不能送到一个没有人能上车的股道。
   **待核实**：`MmtrMission` 里暴露目标站台 id 的取数口叫什么。
2. **「马上退出」不判车是否在动**（**用户口径，2026-10-09 定**）：

   > "马上退出无需判断车是否正在运行，因为都马上退出了，肯定是开一半不开了啊"

   代码本来就是这么写的（`exitNow` → `handBackToAutopilot` → `Simulator.mmtrJobRelease`，
   一路没有速度判据；所有"停稳"字样都属于**反方向** —— 进 `DRIVING` 必须停稳、"下一站退出"在到站时触发）。
   归还之后**由 AI 从行进中接手**：这正是 `Simulator.mmtrJobRelease` 里
   `vehicle.mmtrArmActiveMissionNow(this)` 那一行要做的事（旧代码手动
   `setMmtrMotionAuto(true)` 反而把自臂门关死 ⇒ 车停着不动，见 §9.3 与那一段的长注释）。

   ⚠️ **仍然待实机确认的风险**：`mmtrJobTakeover` 在交接时调过 `mmtrResetTravelDirectionForDriver()`
   （把朝向翻成"司机坐在车头"），而**换向器在这个引擎里有一条红线：只在停稳时可动**。
   于是"行进中归还"要盯的是：自臂重算进路时会不会需要翻换向器、那条红线会不会把它拒掉
   （若被拒，现象是"归还了、车却朝反方向或干脆不动"）。**这条只有实机能证伪** ——
   判别场景 = 开着一趟车在区间里停住 → 按「马上退出」→ 看车速是否自己升起来（§9.2 那次的对照读数
   是修复前 20 秒速度一直 0）。

3. **「下车」与「退出」的次序**：驾驶中按 G 下车，是自动交还自动，还是必须先退出驾驶态？
   我倾向**先交还再下车**（人走了车不能没人管），但这条要用户拍一下。
4. **`ABOARD` 自动转 `DRIVING` 的时机**：车到站停稳后是"自动接管"还是"再按一下确认"？
   用户口径（"在停站符合交接条件后，明确赋予玩家驾驶的权利"）读起来是**自动**给的。
5. **PDA 物品的获得方式**：给所有人默认一个（进服即发），还是合成/指令拿？影响的是"谁都能开"还是"发了才有"。
6. **面板里的"时刻表"**（**已定，不是待定**）：查过镜像字段了，**不用新开同步**。
   引擎已经在发 `mmtrTaskStep` / `mmtrTaskSteps`（第几步/共几步）、`mmtrTaskNote`（这一步的人话）、
   `mmtrSubTasks` / `mmtrSubTaskHint`（站台作业的四条子任务与"现在该做哪条"）、`mmtrJobId` ——
   于是 TAB 面板的"时刻表"就是这些既有字段的排版：**本趟第几步/共几步 + 当前这一步 + 子任务清单 +
   现在该做什么**。真实剩余步骤表（调度器里的 `stepIndex` 之后那些）**仍然看不到**，这一条要如实写在
   面板上（"只显示当前这一步，后续步骤引擎不发"），不许拿别的东西充当。
   真要做完整趟次表，那是一条**按车次**（不是按车）的新同步，单独估。

### 7.1 开发环：引擎测试不必停服务端（本轮实测更正）

`notes/407` §4 把"引擎多了一个方法"写成"需要一次停机窗口"，那是**对停机范围的高估**。
`mmtr/engine` 是**独立的 gradle 工程**（自己的 `settings.gradle.kts` / `gradlew.bat`），
与 `mmtr/game` 的 `:fabric:runServer` **不是同一把锁**。实测（dev 服务端正在跑）：

```powershell
. .\env\workspace.env.ps1        # ★ 必须：用户级 JAVA_HOME 指向 JRE 8（`C:\Program Files\Java\jre1.8.0_431`），
                                 #   不 dot-source 直接死在 "JAVA_HOME is set to an invalid directory"（退出码 3）
Set-Location mmtr\engine
& .\gradlew.bat test --tests "*MmtrMissionTests*" --console=plain     # → BUILD SUCCESSFUL in 18s
```

所以真正**只**需要停机的只有一件事：**往 `mmtr/game/libs/` 拷 jar**（`deploy-engine.ps1`
第一段拦的就是它 —— 半覆盖 jar 会让正在跑的类加载器抛 `EOFException: Unexpected end of ZLIB input stream`，
现象是"车辆全部消失、指令通道不应答"，见该脚本顶部的事故记录）。编译、跑测试、`shadowJar` 都不用停。

另外 `deploy-engine.ps1 -Build` **只跑 `shadowJar`、不跑测试** —— 别把它当成验收。
