# 365 · 水牌只在车头车尾：锚点的"车型内第几节"与一条回退规则

2026-10-03。用户口径：「PID 只有前后面 2 个车厢有，后面没有，是什么原因」。
结论：**不是牌画错了，是中间 7 节车一个锚点都查不到** —— 这是共享查找逻辑的缺陷，一处修好全列车。

## 1. 症状与判据

游戏里 10 节编组（`saf420cab_a ×1 + saf420car ×8 + saf420cab_b ×1`）只有两端的控制车有牌。
客户端 `run/logs/debug.log` 里那一句就是**直接证据**：

```
[23:53:38] [Render thread/INFO] [MMTR] 车型 saf420car 没有任何 mmtr_pid_* / mmtr_next_* 锚点，这节车不挂水牌
```

注意它说的是"**车型** saf420car 没有任何锚点" —— 而 v39 的 `mmtr_anchors_saf420car.json` 里明明有 4 个
`pid` 锚点。日志撒谎的原因见下。

## 2. 链条（每一环都有据）

| 环 | 事实 | 出处 |
| --- | --- | --- |
| 1 | 编组里 **8 节车用同一个模型 id** `saf420car` | `_write_formation.py` 的 6M4T 表；世界 manifest 实测 10 条股道全是这一组 |
| 2 | 锚点是**按模型 id 一份**（`mmtr_anchors_<id>.json`），`Anchor.car` = "这个模型里的第几节车" | `MmtrVehicleAnchors.get/read`；`Anchor.car` 的注释 |
| 3 | 每节车查锚点时用的序号是 **`modelCarIndex()`**（同车型的第几节，0 起） | `MmtrFaceRuntime:87`、`MmtrPidBoard:82`、`MmtrVehicleAnchors.modelCarIndex` |
| 4 | 过滤条件是 `anchor.car == modelCar` | `ofCar` / `findOfKind` / `findLights` / `findHuds` / `findWindshields` |
| 5 | **所有包里的锚点都只声明了 `car: 0`**（SAF420 三份、HST、BR101、saf101 实测全是 `car=[0]`） | 从 `run/resourcepacks` 里逐个解包统计 |
| 6 | ⇒ 8 节 `saf420car` 的序号是 0..7，**只有第 0 节匹配**；其余 7 节查出来是空表 | 就是第 1 节那条日志 |

两节控制车各自是**唯一**使用自己模型 id 的车 ⇒ 序号恒为 0 ⇒ 正常。**"只有前后面两节有"就是这么来的。**

## 3. 同病的还有谁（同一处缺陷的四个出口）

1. **水牌 / 动态面**（`findPidBoards` / `findNextBoards` / `ofCar`）—— 用户看到的那个；
2. **仪表**（`findHuds`）：同车型多节的列车，只有第 0 节有仪表锚点；
3. **车灯**（`findLights`）：同上，灯锚点只在第 0 节；
4. **风挡**（`findWindshields`）：更糟 —— `RenderVehicles` 传进去的是**编组序号**而不是模型内序号
   （`MmtrWindshield.render(..., carNumber, ...)`），于是 B 端驾驶室（编组第 10 节 = 序号 9）连自己那块
   玻璃的锚点都查不到：**B 端的雨与水刷从来没数据**。同一条链上 `pushPartTransform` 也一样。

## 4. 修法（一条规则，一处实现）

`MmtrVehicleAnchors` 加一个 `effectiveCar(anchors, modelCar)`：

> **精确声明了就按精确的来；没声明就回退到第 0 节那一份。**

即"一个模型只声明了一套锚点 ⇒ 它的每一节都用这一套"。所有 `find*`（`ofCar` / `findOfKind` /
`findLights` / `findHuds` / `findWindshields` ×2 / `findWindshield` / `findHud`）都改走它，
所以四个出口一次修好。将来真有包按节声明（`car: 1`…），精确匹配优先，回退不会抢。

配套两件：

1. **风挡口径归一**：`MmtrWindshield.render` 与 `pushPartTransform` 都多收一个 `modelCar` 参数
   （调用方 `RenderVehicles` / `ModelPropertiesPart` 用 `modelCarIndex` 算），
   `carNumber` 只留作身份（缓存键、日志、"司机在哪节车"）——两者不能混。
2. **日志措辞**：改成"车型 X 的**第 N 节**（模型内序号 M）没有对应锚点"，免得下次再被它带偏。

## 5. 波及面（诚实清单）

- **今天的现场零副作用**：世界里只有 SAF420 这一种编组，而 8 节拖车**只有 pid 锚点**
  （没有 hud/light/seat/风挡/cabdoor）⇒ 回退只让它们多拿到那 4 块侧牌。
- **将来**：如果 HST（`hst_h` 声明了 cabdoor/hud/seat）或 saf101 用同一个模型 id 拼多节，
  那几节的仪表/座椅/驾驶室门锚点也会跟着出现 —— 这在"同一个模型挂 N 次"的语义下是**一致的**
  （模型里有的几何，每一节都有）。要"只有某一节有"，就在包里给那一节声明 `car` 索引。
- 没有改 `car` 字段的语义、没有改打包器、没有动任何资源包。

## 6. 判据（全部实跑）

| 判据 | 结果 |
| --- | --- |
| 新增 `MmtrVehicleAnchorsTests`（4 条：一个模型挂 8 节每节都拿到 / 精确声明优先 / 四个族同一条规则 / 第 0 节不变） | 通过 |
| 全量离线用例 | **150 / 150**（原 146 + 新增 4） |
| 现场 | 待用户重起客户端后目视：10 节车每节都应有 4 块侧牌（v39），两端控制车另有车头正脸那块 |

## 7. 还没做的一件事

**客户端要重起**才拿到新类（锚点查找是客户端 Java 代码，资源重载不会换类）。
服务端不用动（这条逻辑纯客户端）。

## 8. 顺带发现（v39 侧牌）

用户 2026-10-02 新打的 SAF420_v38 里新增了 12 块侧牌，v39 给它们写了面文档（上下两排：班次号 + 开往终点）。
**因为本条缺陷，那 12 块牌在修好之前只可能在 3 节车上出现**；修好后会一次出现在全部 10 节车上。
