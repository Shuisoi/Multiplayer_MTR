# 十站环线（001 线，10 车 2 圈）：优先级系统 + 三处闭塞/净空缺陷

场次：2026-09-27。作业单 `mmtr-studio/jobs/line001-c2.json`（7 往西 / 3 往东，120 s 间隔，2 圈后收车），
世界 = `mmtr/game/fabric/run/world/mtr` 的副本（10 站 / 22 站台 / 295 轨 / 46 股道 / 1 车辆段），
引擎 = `mmtr/engine` 当日工作树。

**结论：10 列车全部 DONE（2 圈跑完 + 各自回本务股道收车）** ——
西半场 00101-00107 各 94 步，东半场 00108-00110 各 86 步。

## 1 用户口径：抢同一处道岔时按等级 + 车号裁决

> 「如果同时抢一个道岔，那就得设计个优先级系统了，同级（通勤）谁车号小谁先走，
> 不同级（如区域，高铁）则按级别踩头」

新增 `MmtrTrainPriority`（服务等级 + 车号），钉进**三条既有裁决链的最前面**（计划时刻退到它后面）：

| 位置 | 用途 |
| --- | --- |
| `MmtrPointAuthority#pickNext` / `#pickNextPhysical` | 道岔队列挑头（谁先拿位置） |
| `MmtrPointAuthority#outranks` | 让位 / 收回别人按着的位置（`someoneHasPriorityOver` 与物理位置抢占共用） |
| `MmtrRouteRegistry#outranks` | 敌对进路谁 SET（进路层同一条链） |

- 等级：`通勤 / 区域 / 城际 / 高铁`（也认数字，数字原样保留）；认不出的名字按通勤（老作业单不因拼错被抬高）。
- 车号：作业单号**末两位**（`00101` → 1 号车、`00110` → 10 号车）；没有数字尾巴 ⇒ 有等级、无车号。
- 有作业单的车排在"问不出优先级"的车（玩家车 / 无单调车）前面。
- **问不出优先级时逐位退回老口径**（计划时刻 → 入队序/owner id），所以基线与既有测试一动不动。
- 作业单新增 `serviceClass` 字段（`MmtrConsistJob` → `MmtrMission` → `Vehicle` 发布进路时带上），
  studio 生成器新增 `--serviceClass`（默认"通勤"，即线路 001 的档）。
- 诊断：`MmtrInterlockReport` 多一行 `优先级: 00101（通勤 车号 1）`。
- `MmtrTrainPriorityTests`（6 条）钉住：同级车号小者先、不同级踩头（车号更大也先）、判断不对称、
  无优先级时老口径逐位不变。

**实测：单靠这一档不改变本场次的结局**（要如实记下）。120 s 间隔下改前 3 车到家 / 7 车卡 `ret`，
只加优先级后同样 3 / 7；240 s 间隔下改前改后都整线冻住。原因：车号顺序恰好等于出库顺序，
且计划时刻全部**已漂移**（`计划/实际: 计划 86399000 | 实际申请 1790535667635（已漂移：计划槽早于申请，
裁决退回到达序）`）⇒ 裁决退化成到达序，与改前同序。真正卡住车的是下面三处闭塞/净空缺陷。
这条规则的价值在"等级不同 / 车号乱序"时才兑现（用例覆盖）。

## 2 三处引擎缺陷（都已修，signal/point/route 三包测试全绿）

### 2.1 意图扳岔的净空闸没有排除请求方自己（`Simulator#mmtrThrowTurnoutForIntent`）

原来走的是**不带请求方**的 `blockedThrowReason` —— 而车开到岔前时车头本来就进了 10 m 净空区
⇒ 判定永远"岔区净空被占" ⇒ 意图扳岔永远失败。同一处另外两条路（`mmtrSyncTurnoutPositionsToGrants`
的两支）2026-09-16 已按"排除请求方"修过；诊断里那句 `（改位置的请求方 ）` 是空的就是这条路留下的痕迹。
现改为 `blockedThrowReasonExcept(..., vehicleIdOfOwner(requesterOwner))`。

### 2.2 已经在区间里的车，被同一区间里**跟在它后面**的车扣成红灯（`MmtrSectionService#mmtrChainDepth`）

判定原来对"进向节点所在的这一段"做**整段占用**。实测两处（同一根因）：

```
东行 S 弯   段 2519,77,1808 -> 3835,72,2317 spans=6 len=1451.18  被占=true
            00103 已在段内（x=3218），00108 跟在后（x=2606）也在这一段里
入库引入线  段 500,66,1798 -> 99,66,1502 spans=13 len=1250.45  被占=true
            00109 已进段（咽喉 x≈106..200），00110 跟在后（x=500..600）也在这一段里
```

两处的进向节点（`3218,73,2060` / `106,64,1718`）**都不是这一段的边界** ⇒ 车是从区间中间进去的。
区间内部没有信号机，它前方第一架灯在**下一段的入口**，所以链要从下一段开始数。
现改为 `alreadyInsideSection(...)`：进向节点与这一段两端边界节点都不重合时跳过本段、从它的后继开始。
后车不许进同一段由**它自己**那条链负责（它的进向节点就是段边界，整段占用照旧判红）。

### 2.3 前方闭塞按进路判，而不是按岔口**所有分支**判（`MmtrSectionService#chainDepth` 新增 `allowedRails`）

**这条是最后解开收车自锁的那一条**，也是"信号灯摆放没问题、缺的是引擎口径"的答案：

```
00109 要进 x=-97 那条股道（收车目标），链深=1
  +1  -102,70,68 -> DEAD_END spans=2 len=221.0 被占=true
      span (-102,65,-153)..(-102,65,67) [0..220]   ← 就是一整条 220 m 股道
      coversRail=false  在进路表=false              ← 00109 根本不走这一支
      占它的是已经收车停好的 00108（x=-102 那条股道）
```

区间链历来"跨所有分支走"（notes/166 R4：防哈希顺序只跟第一条），于是**任何一条股道里停着车，
整个引入区间的灯就是红的** —— 车场只能进第一台车，之后 5 台自锁。
灯本身没问题（每条股道一段区间是对的）；错的是"这一趟要不要管那条分支"。

现改为：`MmtrMovementAuthority` 在**进路已 SET** 时把本车进路的轨表交给链（`route::coversRail`），
链只走这一趟真的会走的分支；没有进路的自由驾驶（`allowedRails == null`）仍按所有分支保守判。
灯显/镜面那条路不传（它没有"谁的进路"这个信息），于是仍是岔区级的保守显示 ——
**这一处不对称是刻意的：灯守岔区，行车许可按进路**，已在代码注释里写明。

## 6. 真因定位与修复（2026-09-27 晚，`notes/338` 本节）

### 6.1 先把"多车互锁"排掉：**只装一份作业单，一列 6 节照样出不去**

`DepotProbe`（`.tmp-studio/dump/DepotProbe.java`）只留 1 份作业单（`--consists 1`），世界里没有第二台车：

| 编组 | 07:00 发车后 10 s | 结论 |
| --- | --- | --- |
| 1 节 SAF420 | 偏移 90.9 m → 171.2 m，累计里程 9.35 m，速度 +4.67 m/s | 正常出库 |
| 6 节 SAF420 | 偏移 48.87 m **不变**，累计里程 **0.0 m**，速度 **−0.04 m/s** | 卡死（且每 15 s 更负：−0.18 → −0.40 → −0.83） |

⇒ 与道岔、闭塞、优先级、多车互锁**全都无关**：一台车、一条股道、进路 `established=true`、
`不动理由=（空）`、`被权威扣=false`，它就是不动。

### 6.2 真因：**整列牵引 = 0**（借牵引的车底借给了头车，而头车是显式无动力的控制车）

链条（全部可复现）：

1. 世界目录里**没有** `mmtr-consist-types.json`（引擎找的是 `<dimension>/mmtr-consist-types.json`；
   `mmtr/game/fabric/run/world/mtr/minecraft/overworld/` 下只有 `mmtr-points.json` + `mmtr-signals.json`）
   ⇒ `Simulator.mmtrConsistTypes == null`（`DepotProbe` 打印 `车底注册表=null 缺省=null` 实测）。
2. `MmtrCarTypeResolver.explicitTypeIdOf` 在 `registry == null` 时对**每一节**都返回 null
   ⇒ 作业单里逐车写好的 `consistTypeId`（`saf420_trailer` / `saf420_motor`）**一节都用不上**。
3. `MmtrComposition.fromVehicleCars`：`anyExplicit=false` ⇒ 走"整列借缺省车底"的老兜底
   "**只有第一节**借牵引，其余按拖车"。修前那一节是**写死的 index 0**。
4. 而这个编组的第 0 节是**显式无动力的控制车**（作业单 `powered=false`，T–M–M–T…）
   ⇒ 它借来的那份车底在 `toConsistType` 求和时被 `unit.isPowered()` 挡掉 ⇒ **ΣF = 0**。
5. 自动巡航那一支的加速度是"净加速度"（`TrainPhysics.tractionAccelerationMps2` = 牵引−阻力，
   已除质量）：零牵引 ⇒ `a = −阻力/m < 0`，而那一支写作 `speed = min(cruiseCap, speed + a·dt)`
   **没有下限** ⇒ 速度一直往负方向涨；`integratedDistance = speed·dt < 0`
   ⇒ 下面 `if (integratedDistance > 0)` 永不成立 ⇒ 走行体一步都不前进，`累计里程` 恒 0.0 m。
6. 所有闸门（进路/闭塞/停车点/权威）都"没拦它"，所以 `不动理由` 是空的 ——
   这就是"车不动、还看不出是谁的锅"的标准形状。

### 6.3 修复（两处，都在引擎）

| 位置 | 改动 |
| --- | --- |
| `MmtrComposition.fromVehicleCars` | "借牵引的那一节"从**写死 index 0** 改成 **第一节能出力的车**（`cars.get(i).getMmtrPowered()`，都没有动力时才退回 0）。`anyExplicit=true` 的分支逐位不变（有配置时仍按 notes/247：借来的车一律不给牵引）。 |
| `Vehicle`（自动巡航支） | 负速度按 0 处理（车**站住**，不再"倒着加速"），并**只报一次** `[MMTR-DRV] 车=… **整列零牵引**（车节 N 节 [T,M,…]…）`，把"谁的锅"直接说出来。 |

零回归：老现场（世界里全车 `powered` 缺省=真）第一节本来就是 index 0 ⇒ 逐位不变；
有配置（`anyExplicit=true`）时那一整支不参与。

**遗留的一处不对称（已知、本次不动）**：准入层的 `MmtrCarTypeResolver.anyCarCanPull` 在
"注册表在、但**一节车都没解析出车底**、且全都显式写了 powered"时仍按 `i == 0` 借牵引 ⇒ 它会答
"整列不能出力"，而物理层（本轮之后）答"能"。唯一后果是这种车列**没有任务时会被钉住**（停放语义），
有任务时两层结论都不影响出车；而且注册表为 null 的现场那两处调用点本来就短路成"按老口径"。
要一并改的话，是 `anyCarCanPull` 里那句 `!anyExplicitType && i == 0`，须连同
`MmtrCarTypeResolverTests` / `MmtrConsistTractionMappingTests` 的真值表一起动。

### 6.5 那条"驾驶室 2 进不去、UI 不显示"的线索 = **同一族问题的另一面**（已一并修掉）

线索是对的，但**不是**这次卡库的原因（自动驾驶走系统钥匙，不依赖模型锚点）。查清如下：

**在用的资源包（`SAF420_v4.zip`，`options.txt` 里已启用）三节车都齐** ——

| 车辆 id | 长度 | 锚点（`mmtr_anchors_*.json`） |
| --- | --- | --- |
| `saf420cab_a` | 19.5 m | `cab:1, car:0`：`cabdoor_1_*` / `seat_1` / `windshield_1_1` / `hud_1` |
| `saf420cab_b` | 19.5 m | `cab:2, car:0`：`cabdoor_2_*` / `seat_2` / `windshield_2_1` / `hud_2`（打包器 180° 旋转 + `groupRename`） |
| `saf420car` | 16.95 m | （拖车，无驾驶室锚点） |

坏的是**编组形状**：作业单生成器（studio）以前把**每一节**都写成同一个车辆 id `saf420cab_a`。
客户端给第 N 节车找仪表锚点用的是 `MmtrCabDashboard.modelCarIndex` = "**同车型里的第几节**"：

- 10 节同 id ⇒ 尾车查到 index **9**，而锚点表里只有 `car:0` ⇒ `findHuds(anchors, 9)` 为空
  ⇒ 尾车驾驶室**没有面板（UI 不显示）**；
- `MmtrVehicleAnchors.cabView(anchors, 2)` 找不到 `cab=2` 的锚点时**镜像 cab 1**，
  而 cab 1 的锚点在 `car:0` ⇒ 座位算在**第 0 节**车里 ⇒ "进驾驶室 2 没法操作"；
- 客户端把 `车号+端`（引擎给的 `mmtrPreferredCabSpec()` 例如 `10B`）落不到实处时悄悄退回第一个驾驶室
  （`MmtrBoardRequest.pick` 的告警"没有驾驶室 10B，改用第一个"）。

**修法**（已改 `mmtr-studio/src/StudioJobs.java` 的 `cars()`）：按真车列出编
`saf420cab_a + 8×saf420car + saf420cab_b`（Tc–M×6–T×2–Tc，总车体 174.6 m）——
每节车在**自己**的车型里都是第 0 节，两端的驾驶室锚点都查得到。
这也正是打包器 `tools/obj-mtr-packager/consist/saf420.json` 一直定义的那三节车
（B 端就是那份 `groupRename` 出来的）。

### 6.6 部署缺口：`apply-consist-config.ps1` 永远补不上"缺文件"的世界

该脚本用 `Get-ChildItem -Recurse -Filter 'mmtr-consist-types.json'` **找到才处理**，
里面那句 `if (-not (Test-Path ...)) { Copy-Item }` 是**死代码**（能找到就说明文件存在）
⇒ `run/world`（loom runServer 真正在用的世界）从来没有这份文件时，脚本什么都不会做，
服务端就一直按"没有车底配置"的缺省物理跑（这也是为什么 1 节车能跑、多节车卡：
单节不走"按车求和"那条路，缺配置对它是无害的）。

⇒ 两件事是分开的：**引擎那两处修的是"缺配置时多节编组会静默零牵引"这个故障**；
**这份配置文件缺不缺**是部署问题 —— 缺它的时候整队车（含 BR101）跑的都是通用车力学
（60 t / 100 kN / 600 kW / 40 km/h），SAF420 那 6M4T 的口径根本没生效。
装它是一条命令（`mmtr\scripts\apply-consist-config.ps1`，但先看上一段那个死分支），
**要不要装是用户的决定**：装了以后服务端与仿真台一起换成真车力学。

## 7. 部署（2026-09-27 晚，用户口径："把刚仿真的部署了"）

用户要的是**把这套仿真装进服务端跑起来**，不是只部署引擎。四件事，缺一件现场都看不出来：

| # | 落点 | 内容 | 校验 |
| --- | --- | --- | --- |
| 1 | `game/libs/Transport-Simulation-Core-0.0.1.jar` | 引擎构件（本轮的优先级 + 三处车场自锁 + 本文两处多节编组修复） | 与 `engine/build/libs/…-1.0.0.jar` **SHA256 逐位相同**；loom 的 `argFiles/runServer` 里就是这份 |
| 2 | `<world>/minecraft/{overworld,the_nether,the_end}/mmtr-consist-types.json` | 车底策略（`config-example` 那份；`apply-consist-config.ps1` 那个死分支已修，现在是它自己装上的） | 与 `config-example` / `saves\新的世界` 那份 SHA256 相同 |
| 3 | `<world>/minecraft/overworld/mmtr-rolling-stock.json` | **车底生成表**：zero 段 10 条股道各一列 10 节真 SAF420（Tc–6M–2T–Tc，逐车 `consistTypeId`） | 开机立刻 `trains=10`、10 条股道 `vehiclesParked=1`、全部速度 0 里程 0 |
| 4 | `<world>/minecraft/overworld/mmtr-jobs.json` | 十站环线作业单（10 班、每班 244 步 = 6 圈 + 回库、`repeatDaily=true`），发车时刻改成**锚点后 1:00 起每 2 分钟一班** | 到点后日志是 `manual step 01m -> … vehicle=<车底表那台>`，**没有** `placed N car(s)` |

**为什么必须有第 3 件**（用户现场口径 2026-09-27："车需要预先停好啊，不能有任务了才刷出来"）：
作业单原来靠 `placeCars()` 在**发车那一刻**才把车刷卡进股道（`[MMTR-JOB] placed 10 car(s) from job …`）——
服务端里就是"到点凭空刷出一列车"。车底表把这一步前移到**开机**：`Simulator` 载入表后
`mmtrResetAndApplyRollingStock()`（**清空全部车 → 按表逐条 `vehicle spawn`**）把 10 列停好，
作业单到点走 `findFreeParkedVehicle()` **取用**已停好的那列。两条路各有日志，互不混淆：

```
[MMTR-MFST] rolling-stock reset applied: 10 siding(s) staged for spawn on minecraft/overworld
[MMTR-JOB] manual step 01m -> PASSENGER target … vehicle=7150947890869271452   ← 车底表那台
```

**时间锚点**：`dayTime = (t - anchor) mod DAY`，`anchor` = 调度器**第一拍**（`MmtrJobScheduler` 342），
而**每次重启归零** —— 所以作业单里的 `startTimeOfDayMs` 是"重启后多久"，不是墙钟。
（这也是 studio 那份 07:00 起班不能直接照搬的原因：它配的是录像器的 `--dayOffsetMs` 口径。）

**改动/重置的口径**（都在中控指令里，不必手改文件）：
`manifest list / add <depotId> <sidingId> <车型…> / remove … / reload / replay`、
`mmtr-jobs-upsert` / `mmtr-jobs-delete`（POST 单个作业）、`server restart`（= 优雅停机 + 启动器接力）。
`manifest` 是**权威**的：开机先清空所有车再按表生成，所以表里没有的车重启就没了。
`manifest add` 只吃**车型 id**（逐车 `consistTypeId` 会丢）⇒ SAF420 这种"6 动 4 拖"要保牵引力，
要么用带 `--consist-type=` 的 `vehicle spawn`，要么把车底表的 `cars` 写全（本次就是这么写的）。
