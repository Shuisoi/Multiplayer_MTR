# 230 · 主任务 = 模板 + 目标：把任务拆成基础操作

> 用户口径（2026-09-21，本轮全部依据）：
>
> > 「我认为任务系统应该将主任务和子任务分离，并且将任务目标分离。例如主任务应该是以下几个因素组装：
> > 主任务：停站乘降 —3站1台；子任务：1.停在3站1台 2.开门 3.等待上下客 4.关门。
> > 其中 3站1台则为变量，任务为一对象。同理主任务 开往——车厂987654股道1；子任务：1.停在车厂987654股道1。
> > 这样拆一个任务到基础的操作以简化逻辑判定。」

这一轮不是"再加一层抽象"，而是**修当天上午那个 bug 的根因**：notes/229 把"到站"拆成了子任务，
但只给**站台作业**（SERVE）那条路拆了；"开往站台"（MOVE_TO）那条路没有清单，于是它掉回
"精确停车点"判据 —— 而玩家任务没有停车点 ⇒ 那一步永远到不了站 ⇒ 下一步的开门提示永远不来
（用户实机报的正是这一条）。用户提的结构把这一类漏洞**在结构上**消掉了：
每个主任务都展开成同一套基础操作，判定只有一处。

---

## 1. 三件东西，各有各的家

| 概念 | 类 | 谁写它 | 它回答什么 |
| --- | --- | --- | --- |
| **主任务模板** | `MmtrTaskTemplate`（`DRIVE_TO` / `STOP_AND_SERVE` / `NONE`） | 引擎（从步骤类型翻译） | 这件事由**哪几件基础操作**组成 |
| **任务目标**（变量） | `MmtrTaskTarget`（`PLATFORM`/`SIDING`/`STATION`/`RAIL`/`NONE`） | 引擎（从 `targetId`/`targetRailHex` 解析，**含人话名字**） | **停在哪儿 / 开往哪儿** |
| **基础操作清单** | `MmtrSubTask`（`STOP_AT_TARGET`/`OPEN_DOORS`/`WAIT_PASSENGERS`/`CLOSE_DOORS`） | 由"模板 × 目标"展开 | 这一步**现在该做什么**、做到哪了 |

展开就是一句话：

```java
DRIVE_TO        → [停在<目标>]
STOP_AND_SERVE  → [停在<目标>, 开门, 等待上下客 <dwell>, 关门]
```

`MmtrTaskTemplate.ofStepType()` 是"作业单作者写的东西"（`MOVE_TO`/`SERVE`）与"引擎要做的基础操作"
之间**唯一的翻译点** —— 以后加一种步骤类型，只改这一处，不再需要记得"这条路也要接判据"。

## 2. 目标名从对象现算，不抄作业单的 note

用户举的两个例子在引擎里都能**算**出来，这正是"目标为变量"的好处：

* 站台：`车站名 + "站" + 站台名 + "台"`（实机数据 `stationName=2, platformName=1` ⇒ **2站1台**）
* 股道：`车辆段名 + "股道" + 股道名`（实机 `depotName=987654, sidingName=1` ⇒ **987654股道1**）
* 轨：`"轨 " + hex 前 8 位 + " 尽头/起点/百分比"`（折返那类）
* 原地动作：`（原地）`

于是司机看到的是「**停在 2站1台**」「**停在 987654股道1**」，而不是笼统的"到站停稳"；
站台改名、股道改名，提示跟着改，**零成本**（抄 note 就会过时 —— 作业单里的"去程到 1 站 1 台"
是作者手写的另一份真源，scheduler 的 note 仍作为作业步骤的人话保留在 HUD 的"任务"行）。

## 3. "宣布到站"与"记录停在目标"是两件事（这一轮真正的技术点）

重构第一版把两件事合成一句，立刻被两个既有用例打红：
**原地动作那条捷径**（车已经站在目标轨上 ⇒ 直接把状态推到 AT_TARGET）不经过停车点，
于是自动车的"精确停车点"判据永远不为真、门永远不开。分开之后各归其位：

```java
// 状态机：该不该宣布到站（时机）
private boolean mmtrArrivedAtMissionTarget(mission, motionMission)
    → 玩家 ? mmtrObservedAtTarget()          // 观测
           : isMmtrMotionStoppedAtTarget();  // 引擎自己按包线刹的停车点

// 子任务 STOP_AT_TARGET：车确实停在目标上吗（事实，执行者无关）
private boolean mmtrObservedAtTarget()
    → 停稳 && (目标轨上有车 || 车头已在目标轨上)
```

一句话：**状态机管"什么时候算到"，子任务管"记下到没到"**。共用同一个观测，但"谁说了算"分开 ——
自动车没到停车点不许宣布到站（即使已被信号按在站台轨上），而一旦宣布，子任务记的就是可观测的事实。

## 4. 顺带清掉的分叉

* `mmtrArrivalIsLoose` 从 `executor == PLAYER && 有子任务链` 变成 **`executor == PLAYER`**
  （表格化静态方法，单测直接钉真值表，与 `mmtrRouteKindOf` 同一手法）；
* AT_TARGET 分支里"有链走链、没链按老口径算停留"的分叉没了 —— **每个主任务都有清单**，
  完成判据只剩"清单全达成"（真的没有清单可拆的临时任务才走默认停留）；
* `MmtrSubTask` 的人话在**展开时**就生成（带目标名），线上编码因此变成
  `KIND:STATE:ACK:人话`；实时进度（"还差 5s"）只出现在 hint 里，链上的文案保持稳定
  （不然每一秒都在推全量字符串）。客户端仍然只画不算。

## 6. 实机（2 节编组 br101+p1）

服务端已带本轮引擎；作业 `TT-LOOP-1-3` 自动跑循环时，日志逐条变成基础操作的口径：

```
[MMTR-SUB] 进站确认：车 … 已到 2站1台（任务 STOP_AND_SERVE，执行者 AUTOPILOT，停稳，占用车节在目标轨上=true）
[MMTR-SUB] ▶ 基础操作开始：STOP_AT_TARGET（…✔停在 2站1台 ·开门 ·等待上下客 20s ·关门）
[MMTR-SUB] ✔ 基础操作完成：STOP_AT_TARGET —— 已停在 2站1台（… 2/4 …）
```

**玩家那一半（开门/关门提示）本轮修好了但还没被实机走到**：
现场卡在"去程到 2 站 1 台"那一步的根因就是本轮修的判据，重开服务端后
（车停在站台上即可）那一步会当 tick 到站、下一步的"开门：请按开门键"就会出现在 HUD 与动作栏。
`[MMTR-SUB]` 整条链、`job status <车辆id>` 的"基础操作 n/N / 现在该做 / 进站= 出站="三处读数同源。

## 7. 还没拆的

* `CHANGE_ENDS` / `COUPLE` / `UNCOUPLE` 仍是 `NONE`（不假装有链，走各自原有的动作路径）。
  按这套结构它们也该有清单（换端 = [停稳, 换端完成]；连挂 = [靠近车钩距离, 连挂完成]），
  但那是下一轮：**先把主干道（开往 / 停站乘降）统一**，再逐个搬 —— 搬一个删一处特判。
* 目标的"人话"目前只用于文案；将来信号/进路若也要报"去哪"，应当**读同一个 `MmtrTaskTarget`**，
  别再各自拼字符串。
