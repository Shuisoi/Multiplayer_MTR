# 293 · 牵出线地基往 +Z 再铺 320 格（到 z=640）

> 用户口径（2026-09-25）：**「地基再往+Z铺一点」**。问了一轮距离，选 **再铺 320 格（到 z=640）**。
> 宽度沿用现在的 **16 格（`x=-112..-97`）**、三层 `y=62..64`、`minecraft:stone_bricks`。

## 1. 做了什么

| 项 | 值 |
| --- | --- |
| 范围 | `x=-112..-97`，`z=321..640`（320 格） |
| 方块 | **15,360 格** `minecraft:stone_bricks`（16 × 3 × 320，一条 `/fill` 就够，离 32768 上限很远） |
| 接缝 | 与旧段严丝合缝：`(-104,64,320)` 与 `(-104,64,321)` 都是石砖 |
| 生成器 | `gen_yard_throat.py` 里 `LEAD_Z` 由 `(281, 320)` 改成 `(281, 640)`，**命令文件与事实保持一致** |

`build_throat_deck.txt` 现在是 3 条 fill：咽喉两段 + 牵出线段 `fill -112 62 281 -97 64 640`。
（重跑整个文件是幂等的：已铺的两段只会回 "No blocks were filled"。）

## 2. 新事实：那一片**根本没生成过**

z=320 以南不是"要清障的地形"，而是**世界还没生成到那儿**（第一次扫出来 0 列）。
`/forceload add` 会触发区块生成 —— 标了 `[-8,20]..[-6,40]` 共 63 个区块，
生成完再 `save-all flush`，就能读了。

**生成后的地形**（牵出线走廊 `x=-112..-97`，`z=321..660`）：

```
已读 5440/5440 列，最高 y=62，>=66 的列 = 0     ⇒ 全平海面，不用清障
```

所以这段只需要铺，不需要像咽喉区那样先 `air replace` 削岛。

## 3. ⚠️ 排查时踩的坑：`build_grid` 的 `size` 是**正方形边长**，不是走廊长度

第一次"确认生成进度"时写的是 `build_grid(region, -112, 321, 16)` —— 想的是"16 格宽"，
实际 `size` 是**正方形的边**，于是只扫了 `x=-112..-97 / z=321..336` 一个区块行，
读数**永远卡在 256 列**，看上去像"生成停住了"（还白等了 6 分钟轮询 12 次）。

**正确姿势**：这种窄长走廊不要用正方形扫描器，直接按**区块**枚举
（`x=-112..-97` 全在 chunk x = -7，`z=321..660` 是 chunk z 20..41，共 22 个区块），
用 `chunk_surface` 逐个读 —— 22 次读 vs 方圆 340 格。
