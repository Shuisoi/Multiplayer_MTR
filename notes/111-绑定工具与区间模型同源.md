# 111 - 绑定工具与区间模型同源（S5 准备）

> 承接 notes/105 §3.1（`-163,-60,-189` 哑绑定）与 notes/110（S4 收尾）。
> 本片不新增功能，而是**消除第二份方向真源**，并修掉一个我自己引入的递归陷阱。

## 1. 发现：绑定工具有自己一套方向算法

`Simulator.mmtrSignalBindAtNode(...)`（游戏侧绑定工具/扫描上行用的）**没有用区间模型的解析**，
而是自己重算了一遍"灯朝向哪根轨"：

```java
final double want = Math.toRadians(angle + 90.0);   // 注释：the renderer applies a 90 degree offset
... bearing = atan2(far.z - node.z, far.x - node.x) ...
```

而区间模型（v2）用的是 `headingOf(angle) = (-sin, -cos)` → 方位角 = `angle + 90`。

**这两者在"90 度"这一点上其实一致**（我先误判为差 90°，已核对 `heading` 的方位角：朝向角 θ 的方位角就是 θ+90；
`angle=270` → heading `(1,0)` → 方位 0 → 与 `atan2` 的 0 对上）。

但**算法仍然不同**：绑定工具只在"被点击的那个节点的邻轨"里挑（永远能挑出最近的一条，哪怕那条是横穿灯朝向的），
而区间模型是"灯正下方/朝向的轨，方向必须与朝向一致，否则不绑定"。
**第二个真源就算今天结果相同，明天也会分叉** —— 而"绑到横穿的轨"正是哑绑定的形态（notes/105 §3.1）。

## 2. 交付

`mmtrSignalBindAtNode` 改为**先问区间模型**：

```java
final ProtectedRail resolved = mmtrDirectionalBlocks.resolveProtectedRail(probe);
if (resolved != null) {
    return mmtrSignalOp(x, y, z, angle, aspects, "set", resolved.rail.getHexId());
}
// 模型答不出来（灯离任何轨都超容差）时，才退回原来的"节点最近朝向"搜索
```

外加两个**真实缺陷**的修复：

1. **`resolveProtectedRail` 之前不 `refresh()`** —— 它读的是可能陈旧/为空的 `railByHex`。
   游戏侧绑定工具正好是"在任何区间查询之前就调用它"的那类调用方，于是拿到空索引 → 解析失败。
   现在拆成 `resolveProtectedRail`（公共，先 refresh）+ `resolveProtectedRailInternal`（`rebuild()` 内部用，
   **不**再 refresh —— 否则 `rebuild → resolve → refresh → rebuild` 递归，实测直接把 8 个用例打红，见 §3）。
2. 公共方法的注释写清了"为什么必须 public 且先 refresh"。

## 3. 踩坑记录（自己引入、自己修掉）

- 把 `refresh()` 直接加在 `resolveProtectedRail` 上 → `rebuild()` 内部调用它 → **递归重入**，
  `MmtrDirectionalBlockServiceTests` 8 个用例同时变红。拆内部/外部方法解决。
- 绑定工具的返回值 `mmtrSignalOp` 是"**注册表是否发生变化**"（`changed`），不是"是否成功"：
  同一个 key 已存在时它会返回 false。用例因此改为断言解析结果（`target` / `mode`），而不是布尔值 ——
  这个语义值得记住，它是"看起来失败其实成功"的陷阱。

## 4. 验证

- 新增用例 `theBindToolChoosesTheRailTheSectionModelWouldProtect`（15/15 绿）：
  节点上朝东的灯绑**东向轨**、朝西的灯绑**西向轨**，且 `mode=BOUND`。
- 引擎全量 **513/0/2**（S4 收尾后 512，+1 例，零新增失败）。

## 5. 对 S5 的意义

绑定工具与区间模型同源之后，**用户重新绑定那盏哑灯时会得到与模型一致的结果** —— 这正是 S5 第 ② 条
（`-163,-60,-189` 哑绑定）能一次做对的前提。**但它必须重新绑一次**：旧的 `target` 仍指向横穿的那根轨
（模型优先用显式 target），不会自动纠正。
