## 1. 引擎侧：没有写死，模型是对的

`point why -176 -60 -253` 原话：

```
结论：认成 1 处单开道岔 —— 根部 (-176,-222) / 正线远端 (-176,-289) / 岔股 (-170,-289)
      （位置 0 = 根部↔正线远端，位置 1 = 根部↔岔股）
岔尖候选（从它开进去，另外两根都在前方 = cos > 0.1）：
  (-176,-289)：(-176,-222) cos 1.0（只有一根在前方）
  (-176,-222)：(-176,-289) cos 1.0、(-170,-289) cos 0.99
```

对外那一行（`/mmtr-points`，hex 解成坐标）：`via=stem=(-176,-253)→(-176,-222)`、
`far=(-176,-289)→(-176,-253)`、`branch=(-176,-253)→(-170,-289)`，现位 1，禁止通行 = 正线远端。

⇒ **两个位置切换的确实是 `(-176,-289)` 与 `(-170,-289)`** —— 正是用户说的"应该是"。
`(-176,-222)` 是**根部**（列车开来的那一侧），它两个位置都通、**永远不参与切换**。

系统里"写死"的东西只有两处，都不是本次原因：`mmtr-points.json` 里的**人工位置与人工锁**
（按设计持久化），以及**岔口腿表**（`/mmtr-junction-legs` 实测 **0 条**，空的；它只影响走行能不能
选某条腿，不影响道岔被认成哪两路）。

## 2. web 端：两处显示把这件事说糊了（这才是真问题）

### 2.1 淡出是一张**全局**的"哪根轨被切"表，不说是谁切的

用户看的那片咽喉里，**同时有三根轨在淡出，分属三处不同的道岔**（逐个查证过）：

| 被淡出的轨 | 是谁切的 |
| --- | --- |
| `(-176,-289)↔(-176,-253)` | **`(-176,-60,-253)` / 位置 1** ← 他问的这处 |
| `(-176,-253)↔(-170,-289)`（斜轨） | `(-170,-60,-289)` / 位置 0 ← **渡线的另一头** |
| `(-176,-222)↔(-170,-199)` | `(-170,-60,-199)` / 位置 0 ← **另一处道岔** |

于是：**扳这处道岔时，只有 `(-176,-289)` 那根会明暗变化**；斜轨因为另一头也切着，**始终是暗的**；
而 `(-176,-222)` 那根（另一处切着）也始终是暗的。图上看起来就像"在这两根之间切"。

**教训**：`prohibitedRailHexes()` 返回的是一张扁平集合，图层只说"这根淡"，**没有"谁切的"**
这半个信息。这是**已知取舍**（写在 `MapNode.ts` 的注释里），但这次它直接导致了误读。

### 2.2 卡片根本没写"两个位置各接哪两根轨"

卡片只有 `位置 0（正线贯通）/ 位置 1（岔股开放）` 这种术语；而本该说清这件事的
`Point.turnoutPositionText()` / `prohibitedText()` 是**死代码**（没有任何地方调用），
而且用的是 `hex.slice(0, 8)` —— hex 前 8 个字符是**所有负坐标轨共有的** `FFFFFFFF`，等于没说。
（同一类问题用户 2026-09-14 就报过一次：`SystemMapServlet` 那段注释里记着
"卡片里'接哪两条轨（坐标）'退化成 hex 前缀"。）

## 3. 修法（web 端，不动模型）

1. **`railEndpointsText(hex)`**（`domain/Point.ts`）：hex 六段就是 `x1-y1-z1-x2-y2-z2`（64 位补码），
   直接解出 `(-176,-253)↔(-176,-289)` —— 不必回拓扑查一遍；段数/十六进制不对时**原样返回**，
   不抛异常（宁可丑，不能让整张卡片消失）。
2. **卡片写全三件事**（`Point.turnoutPositionText`）：**根部**（不参与切换）、这个位置**接**的那根、
   以及**被切**的那根。真机实测输出：

```
位置 0 : 位置 0（正线贯通）：根部 (-176,-253)↔(-176,-222) 接正线远端 (-176,-289)↔(-176,-253)；岔股 (-176,-253)↔(-170,-289) 禁止通行
位置 1 : 位置 1（岔股开放）：根部 (-176,-253)↔(-176,-222) 接岔股 (-176,-253)↔(-170,-289)；正线远端 (-176,-289)↔(-176,-253) 禁止通行
现在切掉: 正线远端 (-176,-289)↔(-176,-253)
```

3. **菜单**（`NodeMenu.vue`）：多一行"根部 …（列车开来的一侧，两个位置都通）/ 现在切掉 …"；
   每个按钮第二行写"接 `<坐标>`"；按钮 `title` 是整句。没有物理模型的岔口那几条动作
   也从 `hex.slice(0,8)` 改成坐标。
4. **`TurnoutAction.position`**：菜单需要"这个动作是哪个位置"才能去问那两根轨（非物理岔口给 null）。

## 3.5 "两处道岔抢着管同一根轨"的提示：**做过又按用户要求撤回**（2026-09-16）

用户指出那根斜轨 `(-176,-253)↔(-170,-289)`"是虚线，因为 `(-170,-60,-289)` 也是道岔"，
并要"想个办法进行提示"。查证与结论（**这些事实仍然有效，记下来免得下次重查**）：

**① 它不是虚线。** 这一页虚线只有一个含义：**无信号区段**（两侧都没有灯）。接口给的 25 条无信号带
坐标全列过 —— **没有一条在这片咽喉里**。那根斜轨是**被切**的暗红（`stroke-opacity 0.5`；
实测渲染元素 `class="total-band" stroke="#d98080" stroke-opacity="0.5"`）。

**② 用户的归因是对的**：那根轨**同时是两处道岔的岔股**，所以它的明暗由**另一端**决定；人点着这一处、
看着那根轨变暗，就会以为是这一处切的。

**③ 当时做的提示（已全部撤回）**：两端都是道岔的轨加一条 0.3 格细亮线 + 悬浮提示写清两端是谁；
道岔卡片加"另一端也是道岔（谁、现位、切没切）"；每条带的提示附上道岔归属。
判据是 `railClaimsByHex()`（按"节点 + 身份"去重 —— 同一处道岔在接口里可能是多行，不去重会把一处数成三处；
去重后这张世界 **155 节点 / 13 根**轨是"两端各有一处道岔"的）。

**撤回范围**（用户 2026-09-16："删了上一轮的改进吧，这个到时候再说吧"）：细亮线、卡片那行、
带提示里的道岔归属、`railClaimsByHex` 那一族函数、`nodeInteraction.allNodes`、3 条用例 —— 全删，
`Point.ts` / `TotalSectionsLayer.vue` / `NodeMenu.vue` 回到上一轮之前的样子。
**保留**的是上一轮（§3）那个卡片修复：位置 0/1 接哪两根轨、根部单独一行、被切的那根带坐标。
**没有保留的教训**：`<title>` 是纯文本，文案里不要写 Markdown 记号（当时实测星号会原样显示）。

> 待办（用户："到时候再说"）：这种情况下图上到底怎么提示 —— 细线 / 引线 / 打开菜单时只高亮这一处的切口，
> 都还没定；**根因**是"淡出没有'谁切的'这半个信息"（§2.1）。
