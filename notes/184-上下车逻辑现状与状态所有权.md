# 184 · 上下车逻辑：现状全貌与状态所有权（重构前的家底清点）

> 起因：用户判断"需要完全重构机车动车上下车这个问题，就是车内外切换的逻辑，先搞清楚现有的逻辑是怎么样的"。
> 本文**只描述现状**，不改代码。§7 才谈重构方案。
>
> 为什么值得单独写一份：本轮为了修"视角不在座位上"连续改了 10 版，每一版都在
> `VehicleRidingMovement` / `MmtrCabInteraction` / `MmtrBoarding` 之间挪一个状态量，
> 说明**这个子系统没有单一真相源**，靠读局部代码是推不出行为的。

## 1. 涉及的文件（4 个客户端 + 2 个服务端 + 1 个包）

| 文件 | 职责 | 触发时机 |
|---|---|---|
| `render/RenderVehicles.java` | **决定"这一帧玩家能不能上车"** + 驱动 `movePlayer` | 世界渲染，每帧，按车按车厢 |
| `client/VehicleRidingMovement.java` | **riding 状态机本体**（唯一的 riding 状态所在） | `tick()` 每客户端 tick + `movePlayer` 每帧按车厢 |
| `client/MmtrCabInteraction.java` | **驾驶室钥匙**（G 键）：认领/释放/对账 | 每客户端 tick |
| `client/MmtrBoarding.java` | **硬绑上车**（锚点半径内自动上） | 每客户端 tick（被上一个调用） |
| `packet/PacketUpdateVehicleRidingEntities.java` | 客户端 → 服务端的 riding 上报 | 状态变化时 |
| `engine/.../data/Vehicle.java#updateRidingEntities` | 服务端权威：谁真的在车上、谁是司机 | 收到包时 |
| `engine/.../data/VehicleExtraData.java` | `ridingEntities` 集合 + 门目标 | — |

**关键结构事实**：`VehicleRidingMovement` 的所有状态都是 **`private static`** ——
全客户端只有一份，不区分车辆/车厢。这就是"两个入口互相覆盖"能发生的土壤。

## 2. 状态清单与**所有权**（现状）

### 2.1 riding 状态（`VehicleRidingMovement`）

| 变量 | 含义 | 谁写 | 写入时机 |
|---|---|---|---|
| `ridingVehicleId` | 正在乘的车（0 = 没乘） | `startRiding` / `mmtrPlaceRiding` | 上车；**下车有 3 处**：tick 顶部 / 廊道脱落 / 脚下无地板 |
| `ridingVehicleCarNumber` | 车厢序号 | 同上 + **廊道跨车 `++`** | 上车 / 走进廊道 |
| `ridingVehicleX/Y/Z` | **车体坐标**里的位置 | `startRiding` / `mmtrPlaceRiding` / `movePlayer` 每帧 | 上车；之后每帧被 `movePlayer` 重算 |
| `isOnGangway` | 是否在廊道上（此时 X/Z 是**百分比**不是坐标） | `movePlayer` | 走进/走出廊道 |
| `ridingVehicleCooldown` | 连续多少帧有车在更新我（<5 判定脱车） | `tick` ++ / `movePlayer` 归零 | 每帧 |
| `shiftHoldingTicks` | 潜行按住的累计帧时长（>=30 下车） | `tick` | 每帧 |
| `ridingPositionCache` / `Old` | 上帧车体坐标（**相机的来源**） | `tick` / `startRiding` / `mmtrPlaceRiding` | 每帧 |
| `ridingYawDifference` | 转向差值（相机随车转） | `tick` | 每帧 |

**相机怎么来的**（这条以前搞错过）：`RenderVehicles` 第 85 行取
`getRidingVehicleCarNumberAndOffset()` → `ridingPositionCacheOld` → 作为 `offsetVector` 渲染整列车。
**所以相机的车体坐标就是 `ridingVehicleX/Y/Z`。**

### 2.2 MMTR 追加的状态（同一个文件里）

| 变量 | 含义 | 谁写 | 谁清 |
|---|---|---|---|
| `mmtrCabLocked` | 坐在驾驶位（= 不能走动 + 算司机） | `mmtrLockSeatAndPin`(true) | `mmtrSetCabLock(false)` / **`markLeftTrain()`** |
| `mmtrLockedSeatFootY` | **相机 Y 的钉扎值**（座位眼高 − 1.62） | `mmtrPinSeatFootY` / `mmtrLockSeatAndPin` | **只由 `markLeftTrain()`** |
| `mmtrFloorProbeY` | 探测地板盒用的 Y（可能 ≠ 模型地板） | 同上 + `bestPosition` 自探修正 | `markLeftTrain()` |
| `mmtrDriverSynced` | 是否已把"我是司机"告诉服务端 | `tick` | `markLeftTrain()` |

### 2.3 驾驶室钥匙（`MmtrCabInteraction`）

| 变量 | 含义 | 谁写 |
|---|---|---|
| `heldVehicleId` | 本地认为持着哪台车的钥匙 | `enterCab` / `reclaim` |
| `heldCab` / `heldCarNumber` | 哪一端 / 哪节 | `enterCab` |
| `claimMillis` | 认领时刻（1.5 s 宽限） | `enterCab` / `reclaim` |
| `lastReclaimMillis` | 上次重发认领 | `reclaim` |

### 2.4 硬绑（`MmtrBoarding`）

| 变量 | 含义 |
|---|---|
| `pinnedVehicleId` / `pinnedX/Y/Z` / `pinnedFloorY` | 硬绑钉在哪（用于每帧自愈） |

## 3. 流程 A：**上车**（有三条并行路径）

### A1. 走近门洞（MTR 原生路径）

```
RenderVehicles.render() 每帧、每车厢：
  canRide = !isSpectator
  ① 算 openDoorways：
       人工门（mmtrDoorManual）→ 按 mmtrDoorLeft/Right 旗标 + clipToOpenSide 裁半车宽
       资源包编辑器      → 全部门洞
       车在动            → 空
       否则（原生）      → 站台邻近检查 canOpenDoors() + 玩家挡门
  ② openFloorsAndDoorways = []
       floors   → **只进 floorsAndDoorways（走动用），不进上车列表**
       doorways → 若 canBoard(player, vehicleId) 才进 openFloorsAndDoorways
  ③ 挂载检查：startRiding(openFloorsAndDoorways, ...)
       条件 ridingVehicleId == 0 || isRiding(vehicleId)
       逐个 boxContains(箱子, 玩家实际世界坐标) → 命中才骑上
  ④ movePlayer(...)  ← 每帧把玩家按到车体坐标
```

**要点**：
- **上车只认门洞，不认地板**（MMTR 故意改的：地板只给走动，"不被吸进车厢"）。
- **判定用"玩家世界坐标 vs 资源包盒子"**。模型与盒子不一致 ⇒ 彻底失效（notes/183 §1）。
- 上车位置 **就是玩家当时的实际位置**（`ridingVehicleX = x` 世界坐标 → 其实是绝对坐标，见 §6 不一致 #1）。

### A2. 按 G 进驾驶室（`MmtrCabInteraction`）

```
G 键边沿 → findAimTarget()（准星 40° 内、5 格内找 mmtr_cabdoor 锚点）
  → canBoard 检查
  → 发 PacketMmtrCabOp(ENTER, "<车号><A|B>")
  → 本地立刻：heldVehicleId/heldCab/heldCarNumber 置位
  → placeAtCabView()：
       anchors = MmtrVehicleAnchors.get(modelId)
       view    = cabView(anchors, end)      ← 显式 mmtr_seat 优先，否则 hud 法线后退 1.05
       mmtrPlaceRiding(depot, siding, vehicleId, carNumber, view.x, view.y, view.z, carYaw, yaw)
       mmtrLockSeatAndPin(seatAnchor.y - 1.62, view.y)   ← 钉相机 + 锁走动
```

### A3. 走近门口硬绑（`MmtrBoarding`，本轮新加）

```
tick() 每帧：
  reassertPin()                     ← 自愈：还在骑 + 没驾驶位锁 → 重钉
  蹲下? → return（明确拒绝）
  boardNearestTrain()：
     遍历所有车：跳过"已在骑的"和"在动的"
     遍历 mmtr_cabdoor 锚点：|Δy| ≤ 2.5、水平距离 < 2.0 → 取最近
     → placeOnCar()：cabView 解座位 → mmtrPlaceRiding + mmtrPinSeatFootY(眼高−1.62, floorY)
```

**A2 与 A3 解同一个座位**（`cabView`），且**都写 `ridingVehicle*`** —— 这就是抢座位的来源。

## 4. 流程 B：**车内走动**（`movePlayer`，每帧每车厢）

```
isRiding(vehicleId) && ridingVehicleCarNumber == carNumber ?
  ridingVehicleCooldown = 0
  speedMultiplier = mmtrCabLocked ? 0 : 帧时长 × 0.005 × (疾跑?2:1)   ← 驾驶位锁 = 不能走
  ① 廊道分支（isOnGangway）：X/Z 是百分比，可跨车 → ridingVehicleCarNumber++
  ② 普通分支：
       clampPosition × 4 个角 → offsets
       offsets 空  → **markLeftTrain() 下车**
       否则        → ridingVehicleX/Z += 移动 + clamp
                     ridingVehicleY = pin ?? 地板钳制的 maxY
  ③ ridingPositionCache = (X,Y,Z)
     newPlayerPosition = 车体→世界
     movePlayer(x,y,z) → updatePosition()（当场 + tick 末各一次）
```

### 地板判定的细节（本轮反复踩的地方）

```java
bestPosition(x, z):                       // 用 mmtrFloorProbeY 探
  第一遍：boxContains(box, x, probeY, z) → 取 maxY 最高
  第二遍：boxContains(box, x, box.maxY, z) → 取 maxY 最高，并采纳它的高度为 probeY
clampPosition(x, z):
  bestPosition == null      → 记 floorMiss，offsets 空 → 下车
  是地板  → offsets += (X/Z 夹回盒内, box.maxY, ...)
  是门洞  → 若 boxContains(box, x, probeY, z) 则 offsets += (0, box.maxY, 0)
```

**三种 Y 必须分清**（混用就是 bug）：
| 名字 | 是什么 |
|---|---|
| `ridingVehicleY` | 玩家**脚**的位置（相机 = 它 + 1.62） |
| `mmtrLockedSeatFootY` | 钉扎的脚位置（= 座位锚点 − 1.62） |
| `mmtrFloorProbeY` | 资源包**盒子**所在的 Y（可能差 1.5 m） |

## 5. 流程 C：**下车**（四条路径）

| # | 触发 | 代码 | 发下车包？ | 清钥匙？ |
|---|---|---|---|---|
| 1 | 潜行 ≥ 30 帧时长 **或** 连续 ≥5 帧没有车更新我 | `tick()` 顶部 | ✅ | 清 `mmtrCabLocked`/pin |
| 2 | 在廊道上但廊道位置数据缺失 | `movePlayer` | ✅ | 清 |
| 3 | **脚下无地板**（`offsets` 空） | `movePlayer` | ✅ | 清 |
| 4 | 离开骑乘的车（换车） | `mmtrPlaceRiding` | ✅ | — |

**包**：`PacketUpdateVehicleRidingEntities(sidingId, vehicleId, ridingCar = dismount ? -1 : carNumber, x, y, z, isOnGangway, isDriver, ...)`
→ 服务端 `Vehicle.updateRidingEntities()`：
`isOnVehicle()` 为真则 `vehicleRidingEntitiesToAdd + simulator.ride(uuid, id)`，否则 `stopRiding`。

**注意**：`sendUpdate(true)` 里 `if (ridingVehicleId != 0)` ——
**下车包只在 id 非 0 时发得出去**，所以"先清 id 再发"的调用点其实什么都没发。

## 6. 现状的不一致点（重构要解决的清单）

| # | 不一致 | 后果 |
|---|---|---|
| **1** | `startRiding` 把**世界坐标**写进 `ridingVehicleX/Y/Z`，而 `mmtrPlaceRiding` 写的是**车体坐标**；两者都调 `movePlayer` | 上车瞬间坐标语义不明；原生路径实际靠下一帧 `movePlayer` 重算覆盖 |
| **2** | **三条上车路径**（A1/A2/A3），A2 与 A3 解同一个座位、都写同一组静态变量 | 抢座位、瞬移 10.2 格（§5.5.13） |
| **3** | riding 状态是**每客户端单一**，但写入者分布在 3 个类、4 个时机 | 任何一方按自己的理解清/写都会覆盖别人 |
| **4** | `mmtrLockedSeatFootY` 的**清除点一度有 4 个**（地板失败/调用顺序/无车更新/驾驶位锁） | 相机反复掉回地板（§5.5.5–5.5.11） |
| **5** | "上车"判定用**资源包盒子**，而"座位"用**锚点**，两套几何 | 模型抬高 1.5 m 就彻底失效（§5.5.7） |
| **6** | 地板探测的 Y **必须靠猜或自探**，因为模型地板与盒子地板可以差 1.5 m | 逻辑绕（§5.5.7） |
| **7** | 下车是**四条独立路径**，其中两条（无地板/无车更新）会因瞬时异常触发 | 人被判定下车但还在车内 |
| **8** | 钥匙（`MmtrCabInteraction`）与骑乘（`VehicleRidingMovement`）**各有一套状态**，靠"对账"维持一致 | 对账一失败就丢钥匙（§5.5.15） |
| **9** | 服务端权威状态（`ridingEntities` / `mmtrActiveCab` / 钥匙持有者）与客户端本地状态**没有单一同步点** | 两边各自为政，靠宽限+重试兜 |
| **10** | 门（`mmtrDoorManual` 旗标）与"能否上车"耦合：门关了就不能上 | 侧线/非站台处把自己锁在外面 |

## 7. 重构方向的候选（待用户拍板，先不动手）

### 核心思路：**一个车辆乘坐会话（Session），单一所有者**

现状的病根是**状态分散 + 多写者**。重构的目标是把"我在车里"变成**一个对象**，它拥有：

```
RideSession {
    vehicleId, carNumber, carLocalX/Y/Z, yaw, isOnGangway
    phase: OUTSIDE | BOARDING | INSIDE | CAB | LEAVING
    cabClaim: NONE | LOCAL | SERVER_CONFIRMED   ← 钥匙归属
    seatAnchor: 可选（坐驾驶位时）
}
```

**规则**：
1. **只有 Session 能写 riding 状态**，其他类**发意图**（`requestBoard` / `requestCab` / `requestLeave`）。
2. **几何只用一套**：锚点。资源包盒子**只用于走动碰撞**（车内走动仍需要），
   **不再参与"能否上车"** —— 彻底删掉 §6 #5。
3. **地板/座位只有一个 Y**：由 Session 在进入时解析一次（锚点优先，盒子兜底），
   之后每帧只维护它，不再有"钉扎/探测"两个变量。
4. **下车只有一个出口**（`Session.requestLeave(reason)`），
   瞬时异常（一帧没地板、几帧没车更新）**只降级不结束**（宽限 N 帧）。
5. **钥匙归属并入 Session**：`cabClaim` 只有一个写者 = 服务端镜像；本地认领只是"待确认"，
   不会被本地逻辑清掉（§5.5.15）。

### 可以拆成三步走（每步都能单独验收）

| 步骤 | 内容 | 验收 |
|---|---|---|
| **R1** | 抽出 `MmtrRideSession`，把 `VehicleRidingMovement` 的 riding 字段收进去，**其他类只读 + 发意图**（行为不变） | 上下车、走动、视角与现在一致 |
| **R2** | 几何统一：上车判定改用锚点；盒子只留作走动；Y 只解析一次 | 抬高模型 / 改地板盒都不影响上下车 |
| **R3** | 钥匙并入 Session，对账改为"服务端镜像单向覆盖 + 本地待确认" | 驾驶位按 J 稳定可用；不再出现"坐在座位上却被告知没钥匙" |

> **建议**：R1 是纯搬家（行为不变、最容易验证），R2/R3 才改行为。
> 如果直接上 R2/R3，出了问题无法区分"搬家搬错了"还是"新行为不对"。
