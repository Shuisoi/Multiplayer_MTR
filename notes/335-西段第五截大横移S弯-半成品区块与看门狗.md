## 2. ★ 新缺陷：**半成品区块会被 flush 落盘，之后服务器才补 feature**

第一次跑（1277 条命令、**0 拒**）之后，`check_rail_above_deck.py` 的**净空**那一遍报红：

```
(-5739,1642) 路基顶 68 > 应有 67（轨面 68）    x 范围 -5758 .. -5734
```

现场直读：`(-5739,67..68,1642) = minecraft:gravel` ——**一小块天然砂砾压在轨面上**。
可产品文件里那条清障**明确覆盖了它**（`fill -5744 67 1642 -5734 74 1642 … air replace`），
执行日志也回 **`Successfully filled 88 block(s)`**。

**真因**：`wait_for_generation` 只看"高度图在不在"，而**半成品区块也有高度图** ——
`save-all flush` 会把 `minecraft:carvers` 这类中间态落盘（本轮**实测抓到**该状态的区块），
等服务器把它跑完时才补上 feature（砂砾/树/矿），**清障已经跑过了**。

**修法**：
* `scan_surface_area.chunk_status()` —— 读区块 NBT 的 `Status`；
* `gen_p2p.wait_for_full_chunks()` —— ⑥ 步在 `wait_for_generation` 之后**再等到全部 `minecraft:full`**
  （flush + 轮询；超时只告警不中止，但收工必须看净空那一遍）；
* 重跑后旧报红点 `(-5739,67..68,1642)` 三格**全变 air** ✓。

> 同源上一个坑（notes/332）：**同一批区块的高度图也可能是中间态**（山头读到 79、真实 119）。
> 两条合起来一句话：**新生成区块的"落盘 ≠ 生成完"**。

## 4. ★★ 事故：施工把服务端逼到**看门狗**（引擎侧性能问题，未修）

`15:59:36` 服务端被杀，`crash-2026-09-27_15.59.36-server.txt`：

```
java.lang.Error: Watchdog
  at MmtrSectionGeometry.project(:53) ← projectArc(:72)
  at MmtrSectionService.resolveProtectedRailInternal(:3872) ← resolveProtectedRailsInternal(:3271)
  at MmtrSectionService.protectedRailsOf(:933)
  at MmtrRouteMirror.lambda$tick$0(MmtrRouteMirror.java:64)   ← 服务端每 tick
```

**根因**：`MmtrRouteMirror.tick` 挂在 `END_SERVER_TICK` 上、**每 tick 全量重算**：
对**每一盏灯 × 每一根候选轨**做 0.25 m 步长的弧投影（232 灯 × 280 轨 ≈ 6.5 万次投影；
`MmtrSectionGeometry.ProjectionCache` 是 2026-09-27 才加的**冷启动**优化，
`MAX_ENTRIES = 200_000` 一被撑爆就 `clear()` ⇒ 周期性回到全冷算），
再叠加施工期 1108 条逐米 fill —— 单 tick 超过 60 s ⇒ 看门狗。

拉起来之后**并没有好**：`dev-server.out.log` 里周期性刷
`Can't keep up! Running 29197ms / 583 ticks behind`、`19697ms / 393 ticks behind`
（约每 30~60 s 一记，20~29 s 的卡顿），`vehicles=0`（没有车、没有 web 构建）——
即**地图规模（280 轨 / 232 灯 / ~200 区间）已经把这条每-tick 全量重算压垮了**。

⇒ **下一步应单独修引擎/模组这一处**（候选：给 mirror 加节流/脏标记；把
`protectedRailsOf` 的结果按"轨几何版本 + 灯集合"缓存；或把 `ProjectionCache` 的上限做成自适应
而不是整体 `clear()`），改完要 `compileJava` + `sync-engine` + 重启服务端（客户端需重进）。
