# 251 — "电机做功"数字乱跳的真因：客户端镜像每帧重建

用户口径（2026-09-23，notes/250 刚上线）：

> 显示抽风，数字超高速乱跳

## 1. 真因（先量再改）

在游戏里数了一下客户端日志：

```
grep 'MMTR-CL] mirror created' run/logs/latest.log   → 1803 条 / 107 s = 16.9 次/秒
```

**客户端那台 `VehicleExtension` 镜像对象每秒重建约 17 次**（MTR 每收到一次车辆更新包就新建一个）。
后果：**凡是"对象里攒出来的状态"，客户端都留不住** —— 控制器实例、它的实际牵引比、
气制动缸压、我上一轮加的 `mmtrLastDriveAccelerationMps2`，每次重建全部清零。

于是 notes/250 那行读数（读控制器累积状态）在客户端就变成锯齿：0 → 涨一点 → 被重建清零 → 再涨。
20 TPS 的更新率摊到 80 FPS 的屏幕上，就是"数字超高速乱跳 / 抽风"。

> 这也解释了为什么这一条与物理无关：车跑得好好的（速度来自快照），只有"自算的读数"在跳。

## 2. 修法：读数走**镜像字段**，不在客户端自算

| 处 | 改动 |
| --- | --- |
| schema `data/vehicleExtraData.json` | 新增 `"mmtrMotorForceN": { "type": "number" }`（**故意不写 `minimum: 0`** —— 出力带符号，电阻制动是负的） |
| 生成类 | `generateSchemaClasses` 重新生成：`protected double mmtrMotorForceN` + `unpackDouble/serializeMmtrMotorForceN` |
| `VehicleExtraData` | 新增 `setMmtrMotorForceN(double)`（服务端写）与 `public getMmtrMotorForceN()`（客户端读） |
| `Vehicle.updateMmtrSyncFields()` | 每 tick 把**服务端算出来的**出力写进镜像（紧挨既有的 `setMmtrAccelerationSi/DecelerationSi`） |
| `Vehicle.getMmtrMotorForceN()` | **客户端读快照值**；服务端仍按控制器实际比例活算（三手柄：`tractiveEffortN(实际比例,v) − 电阻制动力`；其它模式：净加速度 × λm） |

`getMmtrMotorPowerW()` 不变（= 出力 × 速度，速度本来就走快照），HUD 一行代码没改 —— 只是它现在
读到的是**逐帧稳定**的值。

**判据**：读数与车辆物理仍然是同一份数（服务端在积分之后写、客户端只读），只是把"谁算"从
每帧都会被清零的客户端对象挪到了权威侧。

## 3. 遗留（真问题还在）

镜像每帧重建这件事本身没修，它不只影响这一行读数：

- 客户端控制器的**建力延迟/气制动状态**每次重建都从头来（气路状态靠 `mmtrAirState` 快照回灌才没露馅）；
- 之前记过的"客户端与服务端感知漂移"很可能同源。

要根治得让 `VehicleExtension` **复用**同一台车而不是每包新建（MTR 的 `VehicleUpdate` 路径），
但那会动到 MTR 的客户端实体生命周期 —— 单独一片做，别和读数混在一起。

- `generateSchemaClasses` + `compileJava` ✓（生成类里已有 `mmtrMotorForceN` 的 field/unpack/serialize）；
- 全量：**801 条，失败 3 条**、跳过 6 条（仍是那 3 条世界存档漂移）；
