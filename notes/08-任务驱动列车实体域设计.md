# 08 任务驱动的列车实体域设计（多人基础架构）

## 为什么改
MTR 现状：车辆由“Depot→路线→时刻表”生命周期生成（Siding 模板 + departures）。
多人/货运/连挂/玩家调度需要一个**与时刻表解耦、以任务约束玩家**的实体域：
列车是持久对象，玩家行为由 Task 约束，道岔/信号/调度由系统依据（列车位置 + 任务意图）驱动。

## 分层
1. **Train 实体域（实体层）**
   - Train：世界持久；formation = VehicleCars + 每节 ConsistType/powered/mass（映射自 MmtrComposition）；
     一个 Vehicle 沿 railProgress 运行（MTR 单刚体不变）；state ∈ {PARKED, DISPATCHED, DRIVING, TASK, COUPLED}；
     location = 占用 siding 槽位；不绑定 departureIndex。
   - 能力：mmtr_spawn(formation, siding) → 停场车；mmtr_retire；mmtr_dispatch；mmtr_couple/uncouple（执行器落这里）。
2. **Mission/Task（约束层，第一公民）**
   - 任务状态机：ASSIGNED → (玩家认领/司机) → INBOUND → DRIVING → AT_TARGET → COMPLETE/FAILED/CANCELED。
   - Task 决定“这列车被允许做什么”：
     * 司机驾驶 = 执行任务的人（占用锁/角色校验——已有 MmtrDriveAccess/占用机制接这里）；
     * 货运任务 = 起点股道 → 中途挂/摘单元 → 终点；
     * 调度任务 = 给某车排路/让行/扣停。
   - 权限：任务下发/认领在服务端，玩家只能对“派给自己的任务车”操作。
3. **基础设施反应层（自动道岔/信号/调度）**
   - 输入：当前各 Train 的（位置、速度、任务意图=下一目标点/目标股道）。
   - 输出：道岔目标位置、信号开放/扣停、进路锁闭——不再依赖“时刻表预排”，而是**按任务实时求值 + 冲突仲裁**。
   - 引擎内实现为每 tick 的 Router/Discipliner：对所有 DISPATCHED/DRIVING 车求“期望进路”，
     冲突时按优先级/任务类型仲裁（谁先到、谁主行）。
4. **旧调度器 = 适配器**
   - 旧 depot 频率发车翻译为“周期 spawn+dispatch 的 AI 任务”；老存档/老内容不改也能跑，多人服可关 AI。

## 与已有代码的接缝
- VehicleExtraData/Vehicle：已是“路径+车厢+控制器”自洽对象（M1 已证可直接构造/显式启动）。
- Depot 寻路管线复用：任意“股道→站台/股道”的 PathData 可由现有 SidingPathFinder 产出，Task 只指定端点。
- 物理/镜像/保护/占用锁（已建）全部按 Vehicle 实体工作，实体域在其上叠生命周期即可。
- mmtr_couple/mmtr_uncouple op seam + MmtrCoupling 核心 → 迁移到 Train 域执行器。

## 切片路线（建议）
- S1 任务-发车竖切（也解开 M2）：mmtr_dispatch op：给合成线停场车下发“A→B”任务，
  系统按任务取寻路 PathData 并驱动列车沿线路运行 → railProgress 前进断言（M2 达标 + 架构验证）。
- S2 Train 注册表 + PARKED/RETIRE：mmtr_spawn(任意 formation)/retire，股道槽位占用，持久化。
- S3 基础设施反应层 v1：自动道岔 + 信号开放/扣停，按 (车位置+任务意图) 求值 + 冲突仲裁。
- S4 货运任务链：起点→摘挂单元→终点（复用 MmtrComposition/stepAir/连挂核心）。
- S5 多人接入：任务认领/司机权（占用锁）→ HUD/交互。

## 关键取舍
- 保留 MTR“单 Vehicle 多车厢刚体 + PathData”为运动模型（低开销），**不加车厢级多体力学**。
- 任务驱动的“路径/进路”由系统从任务端点现算，而不是预先全部排好。
- 玩家自由度被任务约束，但不被“时刻表/股道模板”约束。
