# 08 任务驱动的列车实体域设计（多人基础架构）

## 为什么改
MTR 现状：车辆由“Depot→路线→时刻表”生命周期生成（Siding 模板 + departures）。
多人/货运/连挂/玩家调度需要一个**与时刻表解耦、以任务约束玩家**的实体域：
列车是持久对象，玩家行为由 Task 约束，道岔/信号/调度由系统依据（列车位置 + 任务意图）驱动。


## 任务的宿主 = Train；玩家/AI 只是执行者（读取者）
- **Mission 附着在 Train 上**（一个编组同一时刻一条活动任务），不是附着在玩家/角色上。
- 例子：客运线路 = “周期任务源”（TimetableAdapter）：按时刻表周期性对某个车底
  spawn/dispatch 一个“A→B 客运交路”任务；无需任何玩家/AI 在场也能跑（自动驾驶）。
- 玩家/AI 的角色 = **可选的 TaskExecutor**：认领某车的任务后成为司机（权限+占用锁校验），
  读取该任务得到交路/停站/目标，输入驾驶；不认领时系统按任务自动驾驶该车。
- 同一条任务可以被不同执行者驱动同一语义：AI 自动驾驶 / 玩家手动驾驶(读取同一任务做辅助/联控)。
- 玩家“读取”自己的已认领任务；服务端始终是任务权威（下发/认领/撤销）。

### 数据流（更新版）
TimetableAdapter/任务源 --(挂任务)--> Train.activeMission --> [Router/Discipliner(自动道岔/信号)
按 位置+意图 实时求值] + [可选 Executor(玩家/AI) 或 Autopilot 驱动车辆]

## 分层（修订）
1. **Train 实体域（实体层）**
   - Train：世界持久；formation = VehicleCars + 每节 ConsistType/powered/mass（映射自 MmtrComposition）；
     一个 Vehicle 沿 railProgress 运行（MTR 单刚体不变）；state ∈ {PARKED, DISPATCHED, DRIVING, TASK, COUPLED}；
     location = 占用 siding 槽位；不绑定 departureIndex。
   - 能力：mmtr_spawn(formation, siding) → 停场车；mmtr_retire；mmtr_dispatch；mmtr_couple/uncouple（执行器落这里）。
2. **Mission/Task（第一公民，宿主=Train）**
   - 状态机：IDLE → ASSIGNED(周期源下发) → (可选 Executor 认领) → DISPATCHED/DRIVING → AT_TARGET → COMPLETE/FAILED/CANCELED。
   - 任务种类：客运交路（周期源）、货运任务（起点→摘挂→终点）、调度/让行/扣停（其他车引发）。
   - 权威：服务端 Train.activeMission；玩家/AI 仅按角色执行/读取。
3. **基础设施反应层（自动道岔/信号/调度）**
   - 输入：当前各 Train 的（位置、速度、任务意图=下一目标点/目标股道）。
   - 输出：道岔目标位置、信号开放/扣停、进路锁闭——不再依赖“时刻表预排”，而是**按任务实时求值 + 冲突仲裁**。
   - 引擎内实现为每 tick 的 Router/Discipliner：对所有 DISPATCHED/DRIVING 车求“期望进路”，
     冲突时按优先级/任务类型仲裁（谁先到、谁主行）。
4. **旧调度器 = 适配器**
   - 旧 depot 频率发车翻译为“周期 spawn+dispatch 的 AI 任务”；老存档/老内容不改也能跑，多人服可关 AI。

## 与已有代码的接缝
- VehicleExtraData/Vehicle：已是“路径+车厢+控制器”自洽对象（M1 已证可直接构造/显式启动）。
- Depot 寻路管线复用：任意“股道→站台/股道”的 PathData 可由现有 SidingPathFinder 产出，Task 只指定端点。
- 物理/镜像/保护/占用锁（已建）全部按 Vehicle 实体工作，实体域在其上叠生命周期即可。
- mmtr_couple/mmtr_uncouple op seam + MmtrCoupling 核心 → 迁移到 Train 域执行器。

## 切片路线（建议）
- S1 任务-发车竖切（也解开 M2）：Mission 引擎核心 + TimetableAdapter 周期下发：给合成线一列停场车
  按“每 N 分钟一班”下发 “A→B” 任务（无玩家/AI 也自动驾驶），同时可让玩家认领同一任务手动开；
  railProgress 前进断言（M2 达标 + “任务绑车、执行者可选”验证）。
- S2 Train 注册表 + PARKED/RETIRE：mmtr_spawn(任意 formation)/retire，股道槽位占用，持久化。
- S3 基础设施反应层 v1：自动道岔 + 信号开放/扣停，按 (车位置+任务意图) 求值 + 冲突仲裁。
- S4 货运任务链：起点→摘挂单元→终点（复用 MmtrComposition/stepAir/连挂核心）。
- S5 多人接入：任务认领/司机权（占用锁）→ HUD/交互。

## 关键取舍
- 保留 MTR“单 Vehicle 多车厢刚体 + PathData”为运动模型（低开销），**不加车厢级多体力学**。
- 任务驱动的“路径/进路”由系统从任务端点现算，而不是预先全部排好。
- 玩家自由度被任务约束，但不被“时刻表/股道模板”约束。

## round15-16：M2 确定性达成（墙钟依赖移除）
- 根因：Simulator.tick() 是墙钟追赶（totalDifference=now-simNow），headless 紧循环里大量 tick 的
  millisElapsed=0 → 物理冻结（dev 世界“59m 但每次不同”即此）。合成线诊断显示 power=7/manual=true/
  onRoute=true/stop=120 却只前进 0.000087 m。
- 修复：Simulator 增加公共确定性入口 step(long millisElapsed)（内部按 1000ms 切片调私有 tick），
  测试/无头任务服务器用它精确推进。
- MiniWorldDeterministicDriveTests：合成单线（股道→A→B）手动 autopilot 启动后 step(1000) 遍历，
  maxTravel>5.0 断言通过（BUILD SUCCESSFUL）。data 包全套绿。
