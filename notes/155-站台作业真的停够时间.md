# 155 · 站台作业真的停够时间（以及"停车点要锚在站台上"）

> 用户现场（2026-09-15）第一轮："发现 1 个问题，车只停第一站和第二站，别的站不停。"
> 第二轮："现在还是没停站，一般发生在 3 站和以后。"
> 引擎 **686 通过 / 0 失败 / 4 跳过**（680 → 686，六条新用例，逐条红证过）；控制台已重建；已停机部署。

| --- | --- | --- |
| 一 | 车到站不停（`dwellMs` 没人读） | 站台作业没人执行动作 + 任务当成"有目的地"的任务被当 tick 完成 |
| 二 | 站 2 停得准（306 m = 306 m）、站 3 停在 1114.8（目标 1131）、站 4 停在 **1374.96**（目标 1298） | **停车点是"沿计划进路的累计里程"，进路一变就漂** —— 站 4 直接冲过站台 77 m 才开门 |

## 1. 症状与第一层：计划里的"停留 30s"全引擎没人读

线路配置每一站都写了 `dwellMillis: 30000`，服务计划里每一站也确实算出了
`arrivalMillis / departureMillis`（相隔 30 秒）。但引擎里**没有任何地方读 `dwellMs`**：
`StationServiceTask.dwellMs` 只被写、被打进日志，任务执行器（notes/150）当时只认换端。

所以"停 30 秒"这件事从来没发生过 —— 现场看到的"停一下"是**进站那一步**到点停稳。

## 2. 第二层（真正的元凶）：站台作业走的是"有目的地"那条路，命中"已经在那儿了"的捷径

`MmtrTask.inPlace()` 默认 `false`，站台作业没覆盖它 —— 于是它被当成"要去某个站台"的任务，
目标 = 站台。而自臂那条路上有一条**捷径**（本来就是给"跨轨调车已经把目标轨占住了"写的）：

```
目标轨 hex == 脚下这条轨  ⇒  dispatch → atTarget → complete（当 tick）
```

车刚在"开往站台"那一步停稳，站台作业一挂上就**当 tick 完成**：既没有停留，也没有门。
十站里"看着像停过"的两站，其实只是进站那一步到点的那一瞬。

**修法**：`StationServiceTask.inPlace()` 返回 `true`（它本来就该是原地动作：车就在站台上，
要做的只是"开门、停够、关门"）；同时在自臂的原地分支上加一条**前提判据**：

```
原地动作里唯一有前提的一种：车得真的停在这个站台上（mmtrStandsOnRail）
不在 ⇒ 落到正常规划路，照常开一趟过去（到了还是这个任务的停留）
```

没有这条判据，"原地"会退化成"在哪儿都开门"：上一步进站被撤活、车卡在半路时，
站台作业会在半路开门、停够 30 秒、报"本站服务完成" —— 比不停更坏（时刻表看着对，车没进过站）。

## 3. 第三层：进站那一步白停 5 秒（每站都多，一趟就是 50 秒）

`AT_TARGET` 的完成判据原来一律用引擎默认 `MMTR_MISSION_DWELL_MILLIS`（5 秒）。
而 `DRIVE_TO_PLATFORM` 的语义就是"**到站停稳**"（见它的类注释），停留是**下一步**的活。
于是每一站都白停 5 秒：十站一趟 50 秒，越跑越晚，计划里的到达/发车时刻系统性推后。

**修法**：到站不动后要停多久，按任务类型定 ——
`StationServiceTask` 取"计划给的"与"引擎默认"的大者；**没有任务的旧任务单路径**照旧 5 秒；
**带任务但不是站台作业**的（进站/进段/连挂…）到站即完成。

## 4. 第四层：关门那条分支是死代码（读代码的人会被骗）

任务执行器第一版把"动作做过了没有"的闩放在**方法入口**：

```java
if (... || mmtrTaskActionDone) return;      // ← 入口闩
...
case STATION_SERVICE -> {
    if (!mmtrTaskActionDone) { 开门; 闩=true; }
    else if (停够) { 关门; }               // ← 永远到不了
}
```

开门那一 tick 把闩置上，之后每 tick 都在入口返回。**现场效果恰好一样**（任务到点完成时
tick 里还有一次关门的兜底），但"关门"那行是死的。现在闩的语义收紧为
"**这个任务的动作已经完成**"，挡在动作开始之后；站台作业另用一个
`mmtrStationServiceAnnounced` 只负责"开门停站"这条日志打一次（门可能是进站时就已经开着的）。

## 5. 第二轮：停车点锚在站台上（不信"累计里程"）

### 5.1 缺陷

停车点原来是 **`MmtrRunPlanner.planToRailForward` 算出来的一个累计里程**：

```java
plan.stopCumulativeM = walker.distanceM() + plannedM - (1 - stopFraction) * target.railMath.getLength();
```

`plannedM` 是"这次规划出来的那条进路"的长度。于是：

- **同一次进路**里它是自洽的（既有用例都过）；
- 但**换一条进路**（让位后重规划、岔位换了、多绕一根轨）它整体平移 —— 站 3 的 1131→1115 就是一根轨（16 m），
  站 4 的 1298→1375 是绕了 77 m。车按这个数字停，就停到了站台外。

### 5.2 修法：给自臂再加一个"锚点"

```
Plan:
  stopCumulativeM   累计里程（降级为"刹车的粗略目标"）
  stopRailHex       停车点所在的那根轨            ← 新增
  stopFraction      它在轨内的比例（0 = 本方向轨起点，1 = 远端）← 新增
```

`Vehicle` 侧的用法（三句话）：

1. **到位判据**：`railProgress ≥ 累计里程` **或** `车头在锚点轨上、轨内偏移 ≥ 比例×轨长`；
2. **本 tick 的剩余里程**：车头已经在锚点轨上时取 `比例×轨长 − 当前偏移`（量出来的，不是估的）—— 越过锚点的硬夹紧；
3. **锚点校正**：车头一进锚点轨，就把累计目标改写成"本轨起点累计里程 + 比例×轨长"，
   于是 **刹车曲线也变精确**（不再靠估算），日志里能看到 `停车点按锚点校正 1298.36m → 1298.36m`。

还有一条**防死锁**：估算偏短时车会提前停死在半路（累计里程"到了"、锚点却没到）——
这时放掉停车目标与 auto，让任务下一 tick 用当前位置重新自臂（`停车里程估短了…放掉目标重新规划`），
而不是让车在站台外干等。

### 5.3 测试

`MmtrMotionStopTargetTests.thePlatformAnchorWinsOverACumulativeEstimateThatRunsLong`：
自臂时故意把累计里程说成 **+40 m**（现场那种"重规划后漂到站台外"），锚点给站台轨内 18 m 处 ⇒
车必须**停在 18 m 那个锚点上**（`progress = 50.0`），而不是估算的 90.0。
红证：把锚点参数整个无视掉 ⇒ `expected: <50.0> but was: <90.0>`（正是现场的错法）。

## 7. 顺带修掉的两处（都是这次踩出来的）

1. **`deploy-engine.ps1` 把客户端当成服务端**：判据只匹配 `fabric.dli.config`，
   而客户端和服务端**命令行里都有**它，只有 `fabric.dli.env` 分得开（`client` / `server`）。
   于是"玩家开着客户端"= 部署被无理由拒绝（现场退出码 2）。判据改成 `dli.env=server`。
2. **`Vehicle` 里一段孤立的 javadoc**（两个 `/** */` 连着写，"停着不动就让位"的注释挂在了
   下一个方法头上）—— 移到它真正描述的 `mmtrYieldTurnoutsWhenStuck` 上。

## 8. 现场诊断记录（"车停着不动"的这次原因，与代码无关）

停机部署前先看了现场，结论是**配置的时间基准**问题，不是引擎不动：

```
计划输入的密度窗口： 3960000 ~ 6000000（当日 01:06 ~ 01:40）
派发现场的当日时刻：    293512（00:04:53）
图解：workings=6（六台车都分好了）dispatchedTotal=0   ← 一辆都没派，因为"还没到点"
```

`mmtrPlanDayTime()` 的锚点是**引擎启动那一刻**（`mmtrPlanAnchor` 在第一次用时置为当前时刻；
作业单调度器有锚点时优先用它）。于是**每次重启，当日时刻都从 0 重新开始**，
而配置里写的是绝对时刻 —— 重启前配的"01:06 首发"，重启后要等一小时。

本次验证的处置：把落盘的 `world/mtr/minecraft/overworld/mmtr-plan.json` 里的密度窗口
改成 `360000 ~ 2400000`（00:06 ~ 00:40，首发前 5 分钟出库 ⇒ 引擎起来约 1 分钟后第一台出库）。

**未修（记在这里）**：锚点应当持久化（或密度窗口改成相对口径），否则"改完配置重启一次，
列车就不动了"这件事会一直复发。这是一条**产品级缺陷**，不是现场操作问题。

## 12. 幽灵持有者：车主没了、位置还按着（本轮另一条现场缺陷）

清车重铺之后，六台新车的出发信号**全红**、理由是同一条：

```
point -170,-60,-161 wantLeg=0 needPos=0 | lock=false holder=- queue=v-4921669961753386885@0 v-9025879055767916345@0 phys=v-1408677344944419170 现位=1
```

`phys=v-1408677344944419170` 是**道岔物理位置的持有者**，而那个 id 的车**早已不在世界里**
（`clear-all` 清掉了）。进路、道岔位置/排队、调车授权都是**按持有者 id 跨 tick 存活**的，
可 `Siding#clearVehicles()` 原来只有一行 `vehicleIdMap.clear()` —— 车没了，痕迹全留着：
幽灵按着道岔位置、它不会动也不会让位，于是整条咽喉谁也拿不到（六台车全卡在库里，重试数一直涨）。

修法：`Simulator#mmtrReleaseVehicleClaims(vehicleId)` 一处放干净（进路 + 道岔 + 调车授权），
**所有"车离开世界"的路**都走它：删除（原有）、`Siding#clearVehicles`（清车/重铺）、
`Siding#simulateVehicles` 的淘汰分支（同轨重复车被剔除）。

测试：`MmtrMotionMissionTests.clearingTheFleetReleasesTheTurnoutHoldsOfEveryVehicle`
（自臂拿到道岔 ⇒ `physicalHoldNodesOf("v"+id)` 非空 ⇒ 清车 ⇒ 必须空）。
红证：把 `Siding#clearVehicles` 里的放行去掉 ⇒ `车没了 ⇒ 位置不能还被它按着` 红。

## 13. 仍未解决：咽喉活锁（下一轮）

幽灵修掉之后车能出库了（C1 走到 1 站台 199.67 m 并开门），但**多车仍在咽喉里互相让位**：

```
[14:49:21] [MMTR-PT] 让位（停着不动）：车 -91885876 放掉自己在道岔层的持有与排队，20 秒后重新规划并申请
[14:49:41] [MMTR-PT] 让位：车 -91885876 等道岔超过 20 秒，放掉自己在道岔层的持有与排队，让别的车先走
```

下一步的想法（有依据再动手）：**让位要认优先权** —— 联锁层已经有"计划早的先走"（{@code priorityMillis}），
而 {@code mmtrYieldTurnoutsWhenStuck} 现在是"停着 + 手里有东西 + 等够 20 秒"就无条件全放，
于是**领先车也可能把自己刚拿到的位置放掉**，后车再去拿、它再申请 —— 来回振荡。
判据应改成"**只有别人比我优先时才让**"，让位才是在解环，而不是在制造环。

## 14. 上一轮"四台车全停"的现场记录（同一片区域，留作对照）

四台车同时在线时的读数（服务端日志 + `mmtr-plan-diagrams`）：

```
已派 15  跳过 0  在途 4
  C1 1682m 停车 红灯 每 20 秒"让位"一次（在 -176 轨上，等 -176→-170 渡线的道岔位置）
  C2 1069m 停车 红灯（"停在这架信号前 0 m"）
  C3  230m 停车 红灯（刚出库、停在 1 站台）
  C4  207m 停车 红灯（刚出库）
  C5/C6 库里
```

`mmtr-sections` 里最关键的一条：`-145,-60,-169#2` —— **562 m、24 段轨**，走行顺序是
"沿 x=-155 那条轨一路向下 → 尽头 U 弯 → 沿 x=-170 那条轨一路向上"，也就是**两条平行轨被并成一个区间**；
C1 当次进路 13 段里有 12 段落在这个区间内。

同时记一个**读数陷阱**（本轮已修）：`mmtr-trains` 的 `nextSection` 原来取 `sectionsOfRail(rail).get(0)`
（**不分方向**），而真正的授权链走的是 `sectionAt(rail, arc, heading)` / `sectionBoundaryAheadM(..., heading...)`
（分方向）。所以"六台车的 `nextSection` 是同一个"**未必**等于"它们的授权都由那一个大区间决定"——
现在报的是**按本车行进方向匹配**的那一个区间（`SystemMapServlet#sectionMatchingTravel`），
读数与授权链同口径，下一轮判断锁死时不会再被这个假象带偏。
