# 49 - 实机缺陷：驾驶室进不去 / 乘客门开不了（钥匙归属）

> 用户实机反馈（8 编组 HST 在铁路上正常显示、门与钥匙修好之后）：① 乘客门还是开不了；
> ② 驾驶室也进不去了（网页指令返回 `[cab] <id> 无法进入（需停稳且该驾驶室空闲）`）。
> 两个现象是**同一个根因**：从滚动清单出库的编组被引擎自己插了一把"系统钥匙"占着驾驶室。

## 根因链

| 层 | 事实 |
| --- | --- |
| 出库路径 | `Siding.spawnMmtrConsistVehicle(walker, Cab.CAB_A)` → `engageMmtrConsistMotion` → `walker.insertKey(cab, true, true)` |
| 目的 | 编组体靠"哪个驾驶室有人"决定**哪一端是头**（§3.2）；无人车也得有方向，所以引擎代插一把钥匙 |
| 缺陷 | 这把系统钥匙与司机钥匙**不可区分**：`MmtrCabState.insertKey` 的前置是 `!isManned()` |
| 后果 | 玩家把自己刚刷出来的车锁在门外：网页 `cab-enter` 返回"无法进入"；游戏里对着司机门按 F 也进不去 |
| 连带 | 客户端 `MmtrCabInteraction.enterCab` 是**乐观**的（先本地认领 + 传送视角，服务端结果不回传），于是客户端以为"我在开车"，服务端根本没给 |
| 门 | 对着司机门按 F 时 `findAimTarget()` 命中司机门锚点 → 按键走"进驾驶室"分支而不是"开门"分支 → 门也开不了 |
| 另一个真 bug | `VehicleRidingMovement.tick()`：`isHoldingDriverKeyNew && driverKey.canOpenDoors`——坐在驾驶室但**手里没钥匙**时 `driverKey == null` → 每 tick NPE |

## 修复（引擎：钥匙归属）

`MmtrCabState` 增加 `KeyHolder {NONE, SYSTEM, CREW}` + `crewUuid`：

| 动作 | 新语义 |
| --- | --- |
| `insertSystemKey(cab, stopped)` | 引擎占位钥匙；任何钥匙已在车上即拒绝（**在岗司机永远优先**） |
| `insertKey(cab, stopped, atCab, crewUuid)` | 司机插钥匙：可顶掉 `SYSTEM`，不可顶掉另一名司机；记 `crewUuid` |
| `removeKey(crewUuid)` | 司机只能拔自己的（也拔不动系统钥匙）；`null` = OP 指令，可拔任意 |
| `isHeldBy(uuid)` | `SYSTEM` 对任何玩家都为假——**系统钥匙不授予操纵权** |

`Vehicle`：

- `engageMmtrConsistMotion` 改用 `insertSystemKey`（出库仍是"有方向"的）；
- `enterMmtrCab(cab, uuid)`：顶掉系统钥匙时同时**解除已武装的自动运行**（`mmtrMotionAuto`/停点/岔权请求）——
  现在是人工驾驶，与换端同样的清理；
- `canTakeMmtrControl(uuid)`：编组体车上额外要求 `holdsMmtrCabKey(uuid)`——客户端自称"坐在司机席"
  不再够用，**钥匙在谁手里谁才能开车**（服务端权威）；
- `shouldAutoRelease` 同样要求持有钥匙 → **运行中拔钥匙，下一 tick 撤销 override**，牵引归零、服务制动停稳
  （§3.3 的"运行时拔钥匙 = 失去牵引"这才真正生效）。

## 修复（客户端：诚实认领）

- `MmtrCabInteraction.reconcile()`：每 tick 用镜像回来的 `mmtrActiveCab` / `mmtrCabKeyHolder` / `mmtrCabCrew`
  核对本地认领，不一致就**放手**并提示原因（"钥匙在 <uuid>"/"无人持钥匙"/"已换到 CAB_B"），
  不再出现"客户端以为在开车、服务端不给"的错位；`holdsCab(vehicleId)` 供骑乘层查询。
- `VehicleRidingMovement`：`mmtrCabDriver` 追加 `MmtrCabInteraction.holdsCab(ridingVehicleId)`；
  同时修掉 `driverKey == null` 的 NPE（`driverKey != null && isHoldingDriverKeyNew && driverKey.canOpenDoors || ...`）。
- `PacketMmtrCabOp` 把玩家 uuid 带进指令 `cab <id> <cab> <uuid>`；`MmtrCommandExecutor` 解析后传给引擎，
  并在结果里回报钥匙归属。

## 镜像与运营可见

- `vehicle.json` 新增 `mmtrActiveCab` / `mmtrCabKeyHolder` / `mmtrCabCrew`（非必填、带默认值，旧存档/旧客户端安全）；
- `MmtrMotionSnapshot` 新增 `cabKeyHolder` / `cabCrew`；`mmtr-trains` 每列车新增同名字段。

## 门开不了的实机链路（复述，避免再次误判）

站台上"开乘客门"用的是同一个 F 键，**只在没瞄准司机门时才走开门分支**。所以进不了驾驶室时，
玩家站在司机门附近按 F 只会反复触发被拒绝的进舱请求。驾驶室能进之后，两条路都通：
对准司机门按 F 进舱 → 舱内门键；或站在车厢旁（不瞄司机门）按 F 开/关乘客门。

## 验证

- 引擎全量 **394/0/2**（387 → +7，零新增失败）：新增 `MmtrCabStateTests` 5 例（系统钥匙可被顶掉、
  引擎不抢司机的钥匙、一车一钥匙、司机拔不动系统钥匙、`isHeldBy`），`MmtrConsistVehicleMotionTests` 2 例
  （司机接管出库车并独占操纵权、拔钥匙掉牵引；接管同时解除自动运行）。
- `MmtrManifestMotionSpawnTests` 改为**先接管驾驶室再开车**——这正是新的实机流程。
- 引擎 shadowJar 已重建并同步到 `game/libs`（33.7 MB，12:51）；`:fabric:compileJava` 通过。
- **两个进程都要重启**（客户端与服务端是独立进程，引擎改动只对重启的那个生效）。

实机确认清单：

1. 出库的 8 编组 HST：对准司机门按 F → 进入驾驶室（不再"无法进入"），HUD 亮；
2. 舱内门键 / 站台旁按 F → 乘客门开合；
3. 不拿钥匙推油门 → 能动（钥匙归属 CREW 为该玩家）；
4. 运行中再按 F 拔钥匙 → 牵引归零、服务制动停稳；
5. 网页 `mmtr-trains` 的 `cabKeyHolder` 在 1–4 过程中从 `SYSTEM` → `CREW` → `NONE`。
