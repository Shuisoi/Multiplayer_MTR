# 411 车队停摆：到站"自动交还"之后编组没有驾驶室钥匙

> 现场 2026-10-09 22:36（服务端 + 引擎在线读数，未改动任何代码/世界）
> 用户问："为什么 00101 停止了、00106 也停了，很多车都停了"。

## 1 结论（一句话）

**不是信号灯/道岔坏了。** 是 **00101 与 00106 这两个编组没有驾驶室钥匙**（`activeCab=NONE`），
而在这套走行器里"没有钥匙"的定义就是"**没有车头，也给不出当前轨**" ⇒ 自动任务既开不动、
又规划不出一根轨 ⇒ 任务被判 **FAILED** ⇒ **不可自愈**。
后面所有红灯都是"前方真的有车"的**正确排队**（`signal why` 能逐字点出占用者）。

也就是说：**自动车本该拿着引擎的占位钥匙跑，这两列把钥匙丢了。**

## 3 根因链（逐环带代码位置）

### 环 1 钥匙是怎么丢的：`handBackToAutopilot` 只收不还

`duty status` 写明这次退出是"**到站停稳，自动交还**"，它走的是

`MmtrDutyRegistry.handBackAtStop` → `handBackToAutopilot`（[MmtrDutyRegistry.java:1241](mmtr/engine/src/main/java/org/mtr/core/mmtr/duty/MmtrDutyRegistry.java#L1241)），
而这个方法只做四件事：`simulator.mmtrJobRelease(...)`、把值守记录置 `RELEASED`、`releasePlanPlayerDriven(...)`、`pushDutySync(...)`
—— **没有把引擎的占位钥匙插回去**（唯一入口是 `MmtrCabState.insertSystemKey`，[:162](mmtr/engine/src/main/java/org/mtr/core/mmtr/consist/MmtrCabState.java#L162)）。

于是钥匙停在 `activeCab=NONE / keyHolder=NONE`。

**这个坑代码里认识**，其它路上都补了钥匙，唯独"交还给自动"这条路没补：

| 路径 | 补钥匙的地方 |
| --- | --- |
| 连挂手术 | [MmtrCoupleSurgery.java:226](mmtr/engine/src/main/java/org/mtr/core/data/MmtrCoupleSurgery.java#L226) `insertSystemKey(stagedCab, true)` |
| 车场刷车 / 换端 | [Vehicle.java:4728](mmtr/engine/src/main/java/org/mtr/core/data/Vehicle.java#L4728) |
| 司机在无人编组上动车 | [Vehicle.java:3680](mmtr/engine/src/main/java/org/mtr/core/data/Vehicle.java#L3680) `mmtrAdoptUnmannedConsistForDriver` |
| **到站自动交还** | **（没有）** |

连挂那一段的注释逐字写着这个失败模式：

> The merged train must stay DISPATCHABLE. The task layer plans from a manned leading end
> (`MmtrConsistWalker.railHex()/offsetM()` are null/0 while no cab is manned), so a merge …
> used to leave the merged consist unmanned — and it could never be given another mission
> (**实机 2026-09-09: "walker has no current rail / ahead node"**).

### 环 2 "没有钥匙" = "没有当前轨"（走行器的定义）

```java
// MmtrConsistWalker.java:347
public @Nullable String leadingRailHex() {
    return cabs.isManned() ? leadingLeg().railHex() : null;   // 无人 ⇒ null
}
// MmtrConsistWalker.java:214
public @Nullable Rail peekNextRail() {
    if (!cabs.isManned()) { return null; }
    ...
}
```

`MmtrMovementAuthority.forVehicle`（[:101](mmtr/engine/src/main/java/org/mtr/core/mmtr/signal/MmtrMovementAuthority.java#L101)）取
`nextRail == null ? walker.railHex() : …` ⇒ 两个都 null ⇒
`forApproach` 直接返回 **`GREEN` + `"轨位置解不出来"`**（[:142](mmtr/engine/src/main/java/org/mtr/core/mmtr/signal/MmtrMovementAuthority.java#L142)）。

### 环 3 这句话被当成"位置丢了"，任务随即判死

**位置其实没丢**：`railProgressM=10924 / 8535.8`、`railArcLengthM=220 / 81` 都在，
占用树里也有它的足迹（`query occupancy`：

```
(-6401,63,1938)→(-6181,63,1938)  车=[8823215764811329617]  足迹=[33..217]
```

即 00101 的车体正压着 00102 要进的那个区间）。

但规划器把"没有当前轨/前方节点"当成不可恢复，直接写失败：
`plan.reason = "walker has no current rail / ahead node"`（[MmtrRunPlanner.java:321](mmtr/engine/src/main/java/org/mtr/core/mmtr/plan/../MmtrRunPlanner.java#L321)、[:730](mmtr/engine/src/main/java/org/mtr/core/mmtr/MmtrRunPlanner.java#L730)），
它随后成为 `mission.failureReason`，任务变 **FAILED** ⇒ 再没有任何东西会去插钥匙。

### 环 4 第二层"关门"：`mmtrMotionAuto` 已为真时自臂也被挡住

- 00101：`motionAuto=False`（自臂没武装，但因为没钥匙，规划不出来 —— 失败）；
- 00106：`motionAuto=True` 且 `activeCab=NONE` —— 它连"重新规划"都被门挡住。

这道门是 2026-10-09 那次修正留下的（`Simulator.mmtrJobRelease` 的注释：`mmtrMotionAuto` 在这个库里
**不是"允许自动开"，而是"自动步进已经武装好了"**，自臂的门要求 `!mmtrMotionAuto && 停车点 < 0`；
原来归还时手动置真 ⇒ 执行者已是 AUTOPILOT 却没有任何目的地 ⇒ 死锁。现在改成
`vehicle.mmtrArmActiveMissionNow(this)`）。

⇒ 两列车刚好落在"两把锁"的各一边：**一个卡在没钥匙，一个卡在没钥匙 + 自臂门**。

## 4 为什么"很多车都停了"（都是正确的排队）

沿 00101 停在的那条单线往外排：

```
咽喉 -7174,65,1661 ── 00104（车头 -7173.5,1661.5，压在岔上、按着位置 1）
                       └ 00105 排队等位置 0            （point why：物理位置=1 持有者=00104 队列=[00105@0]）
  → 00103（-6789.5,1802.5，红灯）
  → 00102（-6459.5,1938.5，红灯；signal why -6638 65 1906 逐字列出前方区间占用者 = 00101）
  → 00101 / 00106（无人驾驶室，0 km/h，永远不动）
```

`point why` / `query occupancy` / `signal why` 三份读数互相印证：
**咽喉那一幕是"前面堵住"的下游表象**（00104 走不了 → 它按着的岔位放不掉 → 00105 拿不到），
不是道岔自身故障；`signal why` 显示的所有"占用/受限"都是真实车体。

## 5 已落地的修（三层，2026-10-09 22:58 部署）

### 5.1 第一层：归还给自动时就把钥匙插回去（根因）

`MmtrDutyRegistry.handBackToAutopilot`（[:1241](mmtr/engine/src/main/java/org/mtr/core/mmtr/duty/MmtrDutyRegistry.java#L1241)）
在 `mmtrJobRelease` 之后调 `vehicle.mmtrEnsureSystemKeyForAuto()`，并登记一条兜底
（此刻司机可能**还坐在驾驶室里**，钥匙在他手上 ⇒ 这次插不进去，得等他离开驾驶室那一刻）。

### 5.2 第二层："无人"不再被当成"位置解不出来"，任务不进终态

- `MmtrRunPlanner.Plan` 多一格 {@code unmannedConsist}：规划失败时先判"是不是无人编组"
  （`walker instanceof MmtrConsistWalker && !cabs().isManned()`）；
- `Vehicle.mmtrMotionSelfArmMission` 在 `!plan.feasible` 那一支里：**无人 ⇒ 补钥匙 + 下一拍重试，
  绝不 `mission.fail`**（旧行为是把 `walker has no current rail / ahead node` 写进
  `mission.failureReason` 并进终态，那正是整队停摆不可自愈的原因）；
- C10 反向行驶那一步也跳过无人编组（无人时翻方向毫无意义）。

### 5.3 第三层：**事件登记 + 有界重试**的钥匙兜底网（用户口径）

用户当场质疑得对：**"每 tick 的兜底不占用资源么，不应该做判断重试吗"** —— 全车队每 tick 扫一遍是
稳态固定成本，而这个失败是低频事件。所以这一层按事件驱动做：

| | |
| --- | --- |
| 登记 | `Vehicle.leaveMmtrCab`（钥匙真的从车上出去那一刻）与 `handBackToAutopilot` 各登记一次；**只登记"还挂着在跑自动任务"的车**（一个 long 进小表） |
| 判断/重试 | `MmtrAutoKeyWatch` 每 **5 tick（250 ms）** 才看一眼表；表空则连取模都不做（稳态成本 = 一次自增 + 一次取模 + 一次 `isEmpty`） |
| 补 | 到点且"停稳 + 非终态 AUTOPILOT 任务 + 无人" ⇒ `insertSystemKey(CAB_A)`；司机拔钥匙时车可能还在滚，那就**继续等它停稳** |
| 有界 | 表上限 64；每列车最多重试 40 次（10 s）后记一条放弃日志，绝不无限刷屏；出表条件 = 车没了 / 任务终态或换玩家 / 钥匙回来了 |
| 范围 | **玩家执行的任务一概不碰**（司机可能正走向驾驶室，引擎不许抢） |

第二层与第三层缺一不可，实机把这一点抓出来了：**只加第二层不够** —— 自臂入口有
`!mmtrMotionAuto && 停车点 < 0` 的门，"已经武装起来、随后钥匙被拔掉"这一支根本走不到规划那一步
（旧构建 42 秒无自愈就是这一支，新构建的那条 `[MMTR-KEY]` 来自兜底网）。

### 5.5 本轮**未**做（留给下一轮）

1. `到站自动交还`本身仍可能留一拍 `activeCab == NONE`（司机离开驾驶室那一刻）—— 兜底网补上了，
   但"收旧钥匙 → 写新钥匙连在一起"这条纪律在那条路上仍然只靠兜底；
2. `mission.failureReason` 里那句 `walker has no current rail / ahead node` 仍会把"没人值班"说成"没有轨"，
   本轮只在**不再走到这一步**上做了修，消息本身没改（它是既有测试没断言的自由文本，但值得下一轮分开）；
3. 终态 `FAILED` 的任务仍需人工重新派车 —— 兜底网只救"非终态"的（有意如此：终态可能是真的失败）。

## 6 复现（下次要现场抓这个形状）

```powershell
# 1) 让一趟自动车（或玩家车）到站停稳，触发"到站停稳，自动交还"
# 2) 立刻读：
Invoke-RestMethod -Uri 'http://127.0.0.1:8888/mtr/api/map/mmtr-trains' | % data | % trains |
  ? { $_.cabManned -eq $false } | select vehicleId,railHex,cabKeyHolder,activeCab
# 3) 判据：cabManned=false 且 railHex 空 ⇒ 环 2 成立；再去 server log 找
#    "归还给自动：车 <id>" 与随后的 "walker has no current rail / ahead node"
```
