# 396 列车动态面每帧重画：签名用了整张字段登记表

> 用户口径（2026-10-05）：「AB都做」（A = 查 `main.faces` 为什么 1.13 ms/次；B = 查 `RenderVehicles` 为什么 8.93 ms/帧 + 百毫秒尖峰）。

两份只读调查（子代理 A/B）与我自己读代码**三路独立收敛到同一个根因**。本篇记根因、因果链、
以及两条我读错的纠正。探针口径见运行手册 §8.2 D7/D10、§8.8。

## 0 结论速查

| 症状 | 真因 | 位置 |
|---|---|---|
| `main.faces` **0.07 ↔ 1.37 ms/次**双峰（车停着 ↔ 车在跑） | 重画签名 `data.describe()` 用了**整张字段登记表**，而 `speed` 等量每帧在变 ⇒ **车一动，同一节车上每一块面都被打脏**，包括只读 `pid.terminus` 的纯静态水牌 | `MmtrFaceRuntime.java:189-201` + `MmtrFaceData.java:36-49, 80-103` |

## 1 因果链（带量）

1. 客户端每帧本地积分速度：`MainRenderer` → `vehicle.simulate(millisElapsed)` → 引擎 `Vehicle.simulate` 里大量 `speed = …`。
2. `MmtrFaceData.of()` **遍历 `MmtrFaceFields.specs()` 整张登记表**（不是文档引用到的字段），把 `speed`（全精度 `double`）、`cab.arcM`、`lzb.targetM`、`shunt.remainingS`、`motor.forceN`、`brake.pneumaticForceN`… 全装进快照。
3. `MmtrFaceRuntime.signature()` = `document.id() | data.describe() | 时间桶` ⇒ 车一动，**每块面的签名每帧都变**。
4. `slot.needsRedraw(signature)` 为真 ⇒ 整幅重画：`new BufferedImage` + Java2D 光栅 + `writeInto`（**逐像素 `setPixelColor()`，9.4 万像素 ≈ 461×204**）+ `glTexSubImage2D` ≈ **1–2 ms/块面**。
5. 每节车 6.8 次面调用/帧 ⇒ `main.faces` ≈ **7.7 ms/帧 = `main.vehicles` 的 86%**。

**日志相关性**（474 个窗口，按 `[MMTR-MOTION] 记录/s` 分桶）：`<8`（停着）102 窗，`faces` 中位 **0.07 ms/次**；
`≥12`（在跑）355 窗，中位 **1.37 ms/次**，中间无过渡。⇒ 双峰由"车是否在动"完全解释。

> **同一个仓里已经有正确写法**：`MmtrCabDashboard.signature` 用 `(int)Math.round(speed*3600)`（量化）。
> 面系统没照抄。这是最小改法的现成模板。

## 2 两条我读错的（会误导下一步）

**(a) 两张表来自两个不同窗口。** `main.vehicles=1607/180/max29.11`（+`shadow max 6.99`）是 **14:14:50**；
`shadow.vehicles max=79.71` 与 `136/115/113/100/93 ms` 五行最坏帧是 6 秒后的 **14:14:56**，
那里主 pass 的最坏也到 **66.50 ms**。⇒ **尖峰不是阴影 pass 独有。**

**(b) 最坏帧榜结构上报不出 `main.*`（探针 bug，已修）。** `frameBoundary()` 在主 pass 入口读段账，
而 `passBegin` 每次都把它清零 ⇒ 那一刻只剩**本帧阴影 pass** 的段。已把该数组改成**按视觉帧**累计
（只在 `frameBoundary` 清），于是"最重段"覆盖的区间与 `帧间隔` 量的区间**自洽**（主 pass N + 阴影 pass N+1）。
附带修掉：`passBegin` 原本在 simulate/tick 探针**之后** ⇒ `shadow.simulate`/`shadow.tick` 报的其实是**主 pass** 的值
（实证：某窗口只有 4 个主 pass，却出现 `shadow.simulate=136ms/4`）。

## 3 改法（按收益排序）

| # | 改法 | 预期 |
|---|---|---|
| **1** | **面签名去噪**：`signature()` 只收**文档真正引用到的字段**（`MmtrFaceDocument` 已有表达式树，加一个字段收集口）；或先照抄 `MmtrCabDashboard` 对数值量化 | **主收益**。昂贵相 → 便宜相：14:14:50 窗口 27 ms → ~19.5 ms，**35 → ~51 FPS** |
| **2** | **模型重建挪出渲染线程**，并把 `beginReload()/finishReload()` 从模型构建路径**摘掉**（重建模型不需要重编译全部 shader —— 那是 100 ms 级的那一笔） | 干掉 **488–604 ms** 级尖峰与 615 ms 帧间隔 |
| 3 | `MmtrPanelCanvas.writeInto` 逐像素 `setPixelColor()` 改批量拷贝（画布直接建 `TYPE_4BYTE_ABGR`，一次取整幅） | 单次重画 1–2 ms → 期望 0.2–0.4 ms |
| 4 | `MmtrFaceData` 缓存 `describe()`（它不可变） | 消掉"同车 N 块面 × 2 pass"的重复拼串；便宜相 ~0.5 ms/帧 归零 |
| 5 | `getVehicleCarsAndPositions()` 每节车每 pass 被整份调 8 次（O(车数²)），把已知的 `vehicleId/modelCar` 沿链传下去 | 实测值 1.2–1.9 ms/pass，最大分配源 |
| 6 | 探针：`passBegin` 移到 simulate/tick 之前；最重段按整帧合计 | **已完成**（本轮） |

## 5 测量污染（必须知道）

## 6 已实现（第 1+4 条；编译 504 源文件 / 761 类，exit 0）

| 文件 | 改动 |
|---|---|
| `MmtrFaceData.java` | ① `describe()` 加缓存（不可变对象，而同一份快照每帧被要"面数 × pass 数"遍）；② 新增 `describeOnly(Set<String>)` —— 只拍选中字段（含子树），遍历顺序与 `describe()` 一致，`null` = 全量 |
| `MmtrFaceDocument.java` | 新增 `referencedFields()` —— 扫 `require`/`vars`/`pageExpr`/每元素的 `when`+`raw`+`text` 模板+子元素，收集全部 `{"var": …}` 路径与 `{字段}` 标识符；**带缓存**（文档不可变） |
| `MmtrFaceRuntime.signature()` | `data.describe()` → `data.describeOnly(document.referencedFields())` |

**保守回落（故意的失败方向）**：`referencedFields()` 在这些情况返回 `null` ⇒ `describeOnly(null)` = 全量
⇒ 行为与改前**逐字相同**：有 `anim`、有 `forEach`、有 `drum`、`{"var": ""}`（要整份数据）、
或 `{"var": …}` 的路径不是字符串字面量。**宁可多画几次，也绝不能出现"牌子该变却没变"。**

### 6.1 为什么这条正好打中要害（查过实际资源包）

实际打包的 `mmtr_anchors_saf420cab_a.json` **没有 `faces` 段** —— 只有旧段 `anchors/hud/windshield/pid/glass/rider`，
而旧段由 `builtinPid` **在代码里**翻译成面文档（`defaultElements`）：

```java
elements.add(defaultElement("{pid.service}",  0.21, LEGACY_SUB_SIZE));
elements.add(defaultElement("{pid.terminus}", 0.65, LEGACY_MAIN_SIZE));
// 门 gateFor() = {"!!": [{"var": "pid.service"}]}
```

⇒ **线上 pid 牌只引用 `pid.service` / `pid.terminus` / `pid.next`，全是"到站才变"的字段，没有一个每帧变。**
按 `defaultElement` 造出的元素逐步走过收集器：`anim=null` 不触发回落、`text` 抽到 `pid.terminus`、
`require` 树抽到 `pid.service`、`raw`/`children` 干净 ⇒ **返回真实集合**（不是 `null`）。

### 6.2 验收口径

**必须让车在跑**（`[MMTR-MOTION] 记录/s ≥ 12` 那个工况；停着的工况改前改后都是 0.07 ms/次，看不出差别）：

| 读数 | 改前（车在跑） | 期望 |
|---|---|---|
| `main.faces` 每次调用 | 1.1 – 2.7 ms | **~0.1 ms** |
| `main.faces` 每帧 | 7.7 ms | **~0.5 ms** |
| `main.vehicles` 每帧 | 8.9 ms | **~2 ms** |
| `optimizer draws/frame` | — | **必须不变**（改的是重画次数，不是 draw） |

画面必须确认：pid 牌的**到站/终点站名照旧会变**（若不变 ⇒ 收集器漏了字段，是 bug）。

### 6.3 残余风险（写在明处）

1. **收集器漏字段 ⇒ 牌子不刷新**（"该变却没变"）。兜底只覆盖了**已知**的动态构造
   （anim / forEach / drum / 非字面量 var）；**将来新增的元素类型若从别处读数据，不会自动触发回落**。
   `MmtrFaceDocument` 的"四步曲"若加取值口，必须同步检查这里。
2. **引用了易变字段的文档仍会每帧重画** —— 这是**正确的**，它真的依赖那个值。
   若重画率仍高，下一步应把签名从"输入值"换成**"求值后的结果"**（指纹 `plan()` 出的可绘制项：
   类型 + 几何 + 已解析文本），那样 `{"var": "lzb.targetM"}` 只在**条件结果真的翻转**时才重画。
   **本轮没做这一步。**
3. 本轮**没有**加"重画次数"探针；验收看现成的 `main.faces` ms/次就够。

## 7 ⚠️ 上线即崩：`pages` 为 null ⇒ 铁轨全没了（已修）

第 6 条的收集器**没有做空保护**，第一次进服务器就炸：

```
[Render thread/ERROR] java.lang.NullPointerException:
    Cannot invoke "java.util.List.iterator()" because "this.pages" is null
	at MmtrFaceDocument.collectReferencedFields(MmtrFaceDocument.java:379)
	at MmtrFaceDocument.referencedFields(...)  →  MmtrFaceRuntime.signature:200
	→  MmtrFaceRuntime.drawFace:141  →  MmtrFaceRuntime.render:113
	→  RenderVehicles.lambda$render$15:290  →  RenderVehicles.render:64
	→  MainRenderer.render:184
```

**症状不是"某块牌子画不出来"，而是「铁轨全没了」。** 因果链：
`RenderVehicles` 抛异常 ⇒ 异常从 `MainRenderer.render` 里穿出去 ⇒ 同一次调用里**排在后面的
`RenderLifts` 与 `RenderRails` 整段不执行** ⇒ 钢轨一个都不画。日志里 20640 条 `exception chain`。

**根因**：`MmtrFaceDocument` 的构造函数接受 null 的 `pages` —— `builtinPid` 那条路（3 个调用点）
就是传 `null`。字段是 `final List<Page>` 但**可以是 null**，我在新代码里直接 `for (… : pages)` 了。
`allPages()` 那套老代码是处理过 null 的，我新写的那条路没有。

**改法**：四处遍历全部兜空 —— `pages`、`elements`、`page.elements()`、`element.children()`
（`require`/`vars`/`pageExpr`/`when`/`raw` 本来就走 `collectFromJson` 的 null 分支）。

### 7.1 两条教训（比这个 bug 本身值钱）

1. **`final List<X>` ≠ 非空。** 这个类有 4 个构造点，其中 3 个传 null。**新写遍历之前先看构造点**，
   不要从字段类型推。
2. **`编译通过` 与 `check-paths` 都抓不到这一类错；而这个错误的爆炸半径远超它所在的模块**
   （一块面板的 NPE 让整个世界的钢轨消失）。`RenderVehicles → RenderLifts → RenderRails` 是顺序调用，
   **前面抛异常 = 后面的全丢**。⇒ 面系统（以及任何在渲染循环里跑的按车代码）值得一个
   "单个面出错不影响别的面、更不影响别的渲染器"的兜底；本轮**没有加**，因为先要把正确性修对。
