## 3. 本轮修掉的四个工具缺陷（**都是"回话 ok 但世界是错的"**）

### 3.1 ★ `route_geom.build_plan` **只允许降坡**，升坡会把落差全压在一根轨上

```python
y_next = max(min(y_next, y_prev), y_prev - 1)     # ✗ 只降不升、每段最多 1 格
```

升坡时 `min(y_next, y_prev)` 恒等于 `y_prev` ⇒ **每段都被夹回原高**，最后 `pieces[-1]["y1"] = rail_y`
把 9 格一口气塞进最后一根 90 m 的轨（`Shape.QUADRATIC` 偏差 `|Δy|/8 = 1.125 格` ⇒
notes/324「轨道沉进地基」的同款成因）。**东段那单是降坡（75→71），所以从没暴露**。

**修法**（`route_geom.py`）：

1. 升/降各夹各的：`dy_total >= 0` 时 `min(max(y_next, y_prev), y_prev + 1)`；
2. 自动选弧步数时**不只看"直线放得下"，还要看"坡度摊得下"**
   （`_piece_count() >= |落差|`）—— 于是本单自动档从 **m=2（7 段，摊不下 9 格）** 变成
   **m=3（12 段）**，R 从 705 m 变 335 m；
3. 显式 `--curve-steps` 给得太小 ⇒ **直接报错**（"每段 Δy ≤ 1 格摊不下，加大 --curve-steps"），
   不再静默产出陡轨；
4. `leg_run` 加了同口径的告警（直线/转弯腿的段数 < 落差时 `plan.warnings` 里点名）。

自检新增 **G 组**：升坡 65→74 断言"每根轨 |Δy| ≤ 1、末段正好 74、段数 ≥ 落差"，外加一条反例
（`--curve-steps 2` 必须报错）。`--self-test` 全绿。

### 3.2 ★ `connection_nodes` 是**局部系** ⇒ 区间灯坐标整体取反（14 盏全被拒）

`gen_p2p.line_signals` 把 `pt[0] + side*nrm[0]` 当**世界系**折 `rg.world()`，而
`route_geom` 交出来的 `connection_nodes` 用的是 **U/V 局部系**（`sgn_a`/`sgn_c` 已折过一次）。
`sgn_a = sgn_c = -1`（往西/往北接）时坐标**整体取反**：

```
setblock 500 70 -1808 …      ← 实际（应为 -500 … 1808）
→ FAIL "That position is not loaded" ×28
```

东段那单 `sgn_a = sgn_c = +1`，两次折符号互相抵消 ⇒ **一路顺跑，从没暴露**。

**修法**：`route_geom` 里 `connection_nodes` **一律 `to_real()`**（点与法线都算，与 `plan.path`
同一个世界系），`gen_p2p` 那边只保留 `rg.world()` 的**轴交换**；自检加两条断言
（首点 = 两条轨起点中点、法线是单位向量）——**这两条本来就能拦住它**。

⚠ 因为 forceload 在 `gen_p2p` 收尾（⑪）已经被清空，**补灯必须先重新 forceload 走廊**，
否则又是一片 `not loaded`。新增脚本 **`sandbox/_p2p_lamps_only.py`** 专门干这件事：

```powershell
python sandbox\_p2p_lamps_only.py --from 下水 --to -1800 1390 --rail-y 74 --mode shift \
    --src-center 1803 --src-rail-y 65 --src-along-lo -500 --src-along-hi -280          # 只看
python sandbox\_p2p_lamps_only.py … --push        # forceload 走廊 → 摆灯 → scan-signals → 清 forceload
```

> **为什么不能直接重跑 `gen_p2p` 补灯**：它会重放整条**清障 fill**，把已铺好的
> `mtr:rail` 节点方块删掉（notes/304 的幽灵轨）。

### 3.3 两个检查器的**判据假设**（假警报，都修了）

| 检查器 | 假警报 | 真因 | 修法 |
| --- | --- | --- | --- |
| `check_rail_above_deck.py` | 14 处"路基顶高 1 格"（全在节点上、差值恰好 1） | 拿 `seg.ylow`（**整段低端**轨面）当全段基准，可爬坡段高端那些点上轨面本来就高一格 | 改成该采样点的**真实轨面**（QUADRATIC `y(t)=y0+Δy·t²` ⇒ `ceil(y)-1`，与 notes/327 §3.3 同一条口径） |
| `verify_p2p_build.py` | 接头/连接轨/路基 4 项全打在**错的一端** | 写死"接头 = 站台 z0 端"（东段恰好如此）。本单源站在 +along 侧 ⇒ 接头在 **z1** | 接头端由 `--conn-start` 判方向（`junction`/`far`/`outward`） |
| 同上 | "连接线路基顶 = 轨面-1" 判 air | 有坡度的连接线在接头外侧已降 1 格（本段平顶 72） | 判据改成"**轨下最近实体是 `smooth_stone`**" |

### 3.4 ⚠ 读存档核对前**必须 `save-all flush`**（本轮又踩一次）

施工刚结束时读 `(-1404,72,1393)`、`(-1690,74,1387/1393)` 都是 `minecraft:air`，
差点判成"节点方块缺失"；`save-all flush` + 停 3 s 后再读**全是 `mtr:rail`**。
**世界还在内存里没落盘**（notes/327 §3.3 同款）。同理，`gen_p2p` 收尾报的
"游戏端回报已铺 0 条"也不能当结论 —— 引擎 26/26 + 存档直读 12 个节点都对，
说明服务端**确实**写了方块，是读日志那条路没读到。
