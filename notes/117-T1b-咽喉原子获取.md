## 1. 这一半修的是**永久死锁**

`MmtrRunPlanner.requestForkOps` 逐个岔申请，失败的**只置标志、不回滚**：

```java
for (final String[] op : forkOps) {
    if (authority.request(...) != Result.GRANTED) {
        all = false;          // ← 已经批下来的留在手里
    }
}
```

配合两件事，后果是**永久**的：
- `Vehicle.armMmtrPointRun` 把接近窗口（120 m）内的岔**一次申请**（会拿到一部分）；
- armed 的任务**每 tick 续期**（`untilMillis = now + 10 min`），所以授权**永不超时**。

于是 A 车进路要 `[P, Q]`、B 车进路要 `[Q, P]` ⇒ **A 持 P 等 Q、B 持 Q 等 P，两列车永久卡死**。
这比"两条互斥进路同时报 SET"（T1 修的那个）严重得多：那是状态说谎，这是系统停摆。

## 2. 交付

| 件 | 内容 |
| --- | --- |
| `MmtrPointAuthority.requestAtomically(ops, owner, untilMillis)` | **一组要么全拿、要么全不拿** |
| `Vehicle.requestPendingForksAtomically(...)` | 两处申请点（self-arm 与每 tick 续期）都改走原子申请 |
| 只读判据 | `perApproachGrantableTo` / `physicallyGrantableTo`（无锁、无他人持有、或位置相容） |
| `releaseSet` | 失败时把本 owner 在这组里持有的**一切**让出去（**含它上一 tick 就有的**） |
| `queueSet` | 等待时在**整组每一处**排队（保住 FIFO 位置），`enqueueIdempotent` 刷新窗口不重复入队 |

**做法是"干跑再落地"**：先只读地判断整组能不能成立，成立才真正申请（此时每一条都会成功）；
不成立就整组让出 + 整组排队。中途万一有一条没成功（单线程内不该发生），保守地把本次拿到的全部退回 ——
这段防御性回滚的存在，是为了让不变量在这条推理被破坏时**依然成立**。

### "咽喉"的操作化定义

设计文档说的是"咽喉区（度 ≥ 3 节点的净空区及其中间的道岔）"。实现把它落成
**"这列车此刻正在接近的那一组"（接近窗口 120 m ≈ 一处咽喉的尺度）**：

- 需要的性质是"**不提前占远端岔**"——窗口外的岔仍然不申请，这条一字未改；
- 变的只是**获取的粒度**：从"逐岔"变成"整组"；
- 好处是不需要新增几何聚类（也就不会引入"两处岔算不算同一咽喉"的判据风险）。
  真要按几何收缩成字面咽喉，留给 T5（那时有整张计划，可以一次算准）。

## 3. 诚实的边界：逐进向递补仍是**按单点**发生的

`promote`（队列递补）是按**单点**触发的，所以前车只让出一处时，等待者可能被临时提上来拿到那一处。
这不是永久的：armed 的任务每 tick 重试，**一问整组拿不到就把已有的让出去**，所以部分持有被限制在
**一个 tick 之内**，"永久循环等待"不成立。

本片把这个不变量钉进了用例（`anAtomicWaiterNeverKeepsAHalfSetAcrossItsOwnRetry`）：
**重试之后整组要么全有、要么全无**。

> 若日后实测发现这一 tick 的抖动造成咽喉吞吐损失，做法是把原子组的键集合挂在队列条目上、
> 让 `promote` 只在整组同时可授时才交出去。这一片**没有做**：它需要给 `Req` 加组引用并重写
> `promote`/`promotePhysical` 的交出路径，属于"用更大的改动换更小的抖动"，先记在这里。

## 4. 验收

- 新增 3 例（`MmtrPointAuthorityTests`，那里不接物理层，测的就是逐进向的原子性）：
  - `atomicAcquisitionLeavesNoPartialHoldingSoACircularWaitCannotForm`（① 循环等待：一列全拿到、一列一处都没有）
  - `atomicFailureGivesUpAMemberThisOwnerAlreadyHeld`（"全无"包括让出已有的那一处）
  - `anAtomicWaiterNeverKeepsAHalfSetAcrossItsOwnRetry`（跨重试的不变量）
- 全量引擎：**550 通过 / 0 失败 / 4 跳过**（T1 后基线 547 + 本片 3 例，**零新增失败**）。

## 5. 未结（本片有意不做）

1. **敌对进路表（共用轨段 / 侧面防护区重叠）推迟到 T5**。理由：
   - "同岔不同位"这一条已经由 T1 的物理唯一持有者解决；
   - "同向跟随"由闭塞（S1）解决，notes/82 已定为**不算敌对**；
   - 剩下的"共用轨段/净空区重叠"如果现在就做成 SET 判据，会让**当前能 SET 的进路变成 PENDING**
     （例如两列车先后去同一个站台），有回归已验收行为的风险；而 T5 的时刻表预排会在计划阶段
     就把这些冲突消掉，运行时的敌对表价值大幅下降。
2. **计划时刻优先**随 T5 一起（它需要时刻表作为输入）。目前裁决仍是**到达序（FIFO）**。
3. **防饿死**（等待超时提升优先级）尚未做 —— 它是 T1b 的后半，另起一片。
4. **人工锁 TTL**尚未做（设计 §5.2 的建议项）。
5. `releaseAll` 里"删一个元素就丢掉整个队列条目"的旧写法仍在（notes/116 §6.3 已记）。
