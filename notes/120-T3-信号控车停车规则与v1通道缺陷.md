## 2. 本片最重要的发现：**v1 逐轨回退链不能用来停车**

规则 (5) 一接上，**五条既有用例立刻红**（`MmtrAwsWarningTests`、`MmtrJunctionClearanceTests`、
`MmtrRouteConflictTests`、`MmtrSectionAuthorityStopTests` ×2），症状一律是"列车到不了目的地 —— 被扣住了"。

根因在 `MmtrSignalAspect.chainDepth(hex, entryPos, excludeVehicleId)`：

```java
if (directional.hasSection(hex)) {
    final int d = directional.chainDepth(..., excludeVehicleId);
    if (d > 0) return d;
    return v1ChainDepth(hex, entryPos);   // ← 不带 exclude
}
return v1ChainDepth(hex, entryPos);       // ← 不带 exclude
```

v1 走的是**预留信号色**通道（`rail.mmtrIsSignalColorBlocked(section.signalColor)`），
那个通道**认不出这团影子是不是问话的这列车自己**。所以车会把自己的车身读成"前方占用" → 红灯。

- 作为**显示**：只是保守一点（这正是 notes/112 §4 那个"一给油就告警"的来源，当时给 AWS 加了
  `excludeVehicleId`，但**只有 v2 那条路用得上它**）；
- 作为**停车规则**：列车被**自己的影子**永久扣住 —— 这是死锁，不是保守。

**修法（本片采用）**：**停车只认 v2 的结论**。`forApproach` 里加一道闸：

```java
if (aspect == RED && !simulator.mmtrDirectionalBlocks.hasSection(signalRailHex)) {
    // v1 回退链的红灯不作为停车依据；没有 v2 区块的轨段本条不作声，
    // 交给原有规则 (2)(3)(4) 照旧扣车（行为与修前一致）。
}
```

v2（灯到灯有向区间）带 `excludeVehicleId`，排除得了自身。加上这道闸之后 **559/0/4 全绿**。

> 这一条同时解释了为什么"把灯色接进停车"以前没人敢做：**灯色的一个来源根本不能用作行车依据**，
> 而它在显示上与另一个来源混在一起、看不出来。notes/114 定的"链 A 权威 / 链 B 兜底"在这里第一次
> 有了**安全含义**，不只是显示口径。

## 3. 验收

- **全量 559 通过 / 0 失败 / 4 跳过**（与 T2 后完全一致，**零新增失败**）。
- 五条既有用例的**行为被修好**而不是被改期望值：接规则前后它们从"绿 → 红 → 绿"，
  中间那次红正是 v1 自身影子造成的死锁。也就是说这一片顺带**暴露并绕开**了一个既有缺陷。
- 新增用例：**待补**（见 §4）。本片目前靠"五条既有用例的行为 + 全量零新增失败"支撑，
  还没有 T3 自己的端到端停车断言 —— 这一点如实记在这里，不当成已完成。

## 4. 验收用例：做了哪几条，哪些还没做

设计 §6 给 T3 列的五条断言，现状如实记账：

| # | 断言 | 状态 |
| --- | --- | --- |
| ② | 进路 PENDING ⇒ 停在**进路入口信号前**（而不是开到岔前） | ✅ `aTrainWhoseRouteIsNotSetIsHeldAtItsDepartureSignal` |
| ③ | 红 → 绿自动续行 | ✅ `settingTheRouteLetsTheHeldTrainGo` |
| ⑤ | 停车理由可读 | ✅ 上述两条都断言了理由串（"进路未设好" + 进路自己的等待原因） |
| ① | 红灯前精确停住、不冒进 | ❌ 未做 |
| ④ | 黄灯确认后正常通过（未确认仍走既有 AWS SPAD） | ❌ 未做 |

**为什么先做 ②③ 而不是 ①**：① 与 ④ 都要用**占用**把灯压红，而占用造成的停车**规则 (2) 本来就会做**
—— 修前就有，所以那两条**测不出规则 (5) 的增量**（去掉规则 (5) 它们照样绿）。
真正能隔离规则 (5) 的通道就是"进路 PENDING"：它在修前**完全不产生任何停车**。
要做 ①/④ 得有"真灯 + 真占用 + 真车"的夹具（现有两套各有一半：`MmtrDirectionalBlockServiceTests`
有灯没车，`MmtrRouteConflictTests` 有车没灯），那是下一步的正经工作量。

新增夹具 `MmtrSignalAuthorityStopTests.ForkNet` 踩过一个坑，记下来免得重蹈：
岔股的几何**不能从岔口平着出去**（`Angle.fromAngle(0)` 会让它看起来与正线共线，
`MmtrTurnout.resolve` 于是找不到干净的直股对 → 返回 null → "夹具的岔口是一处单开道岔"直接红）。
照抄 `MmtrPointDefaultZeroTests.forkNet` 的轨形（起点角 0、终点角 180 的 QUADRATIC）即可。

## 5. 留给用户拍板的一件事

v1 通道"认不出自己"这个缺陷，有两种处理：

- **(a) 本片采用的闸**：停车只认 v2。改动小、不动显示、既有行为逐位不变；
- **(b) 根治 v1**：让 v1 那条链也带 `excludeVehicleId`。但那要改"预留信号色"通道的数据结构
  （颜色目前不记是谁预留的），会动到**灯显**本身 —— 而灯显是用户花了好几轮才调准的
  （notes/114/115），风险与收益要用户权衡。

在 (b) 落地之前，**同一盏灯在 v2 与 v1 两条路上仍可能给出不同的结论**，
这正是 notes/114 §8 一直挂着的未结项；本片给它补上了一条新的、更硬的理由。
