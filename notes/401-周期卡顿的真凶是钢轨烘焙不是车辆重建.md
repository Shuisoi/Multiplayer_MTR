# 401 周期卡顿的真凶是**钢轨烘焙**，不是车辆模型重建（2026-10-08，活体客户端 JFR）

## 0 为什么开这一枪

notes/400 §8 收尾时把"还剩什么"排成：① 车辆 `建 VBO`（`new DynamicVehicleModel` = `writeCache` +
`addTransformation`）76–111 ms；② GL `upload()` 20–34 ms；③ `地面/门洞/mapDoors` 25 ms。
按这个排序，"下一项"自然是那 76–111 ms。

**先量了再动，结果把这条排序推翻了**：那一波重建（20:11:51，JIT 已热）的 `[MMTR-LAG]` 是**零条** ——
`建 VBO 72 ms` + 6 份 `upload 20–30 ms` 分散在不同 tick 里，**没有任何一帧超过 `[MMTR-LAG]` 的门限**。
而同一份日志里 300–660 ms 的帧另有其人。

本节把"另有其人"钉死。**结论：是钢轨烘焙（{@code MmtrRailMeshCache}），不是车辆。**
证据全部来自**活着的客户端**（不用重启、不用改代码）：`jcmd JFR.start` + `jfr view` / `jfr print`。

## 1 三件常见的嫌疑，全部否定

## 2 形状：帧 300–660 ms，而"已量段合计"只有 0.78 ms/帧

`[MMTR-FRAME]` 自己在说明里写死了这个判据：

> 已量段合计 ÷ 帧间隔 p50 ≈ 1 ⇒ 帧时基本被表中的段解释完了；明显偏小 ⇒ 时间在没埋点的代码、
> 别的线程（区块构建/遮挡剔除）或 GC/呈现上。

现场就是"明显偏小"：`[19:49:00] 帧=336（67.2 FPS）最慢=659ms ｜ 已量段合计=0.78ms/帧`。

**为什么小得这么离谱 —— 一个一直被忽略的事实**：Minecraft 的 `Render thread` **同时也是客户端 tick 线程**。
实体 tick、方块/区块查询、网络包处理都在它上面跑；而 `[MMTR-FRAME]` 的段只在 `MainRenderer.render`
里打点。所以 **`帧间隔` = tick + 渲染**，tick 那一半根本没进表。

JFR 采样落在那一帧里的栈（`sampledThread = "Render thread"`，20:11:31.103 起）五花八门：

## 4 为什么一次烘焙就是 200+ ms

`MmtrRailMeshCache` 已经有预算：

```java
private static final int MAX_BAKES_PER_PASS = 2;   // ← 限的是「次数」
```

限的是**次数**，不是**时长**。一次烘焙 = `walk()`（枚举 440 个实例）→ 合桶 → `generateNormals()` +
`distinct()` → `merged.upload(MAPPING)`，**全部在渲染线程上**（`bakeInner` 行 477）。
两次就是 200–400 ms —— 正好是 `shadow.rails max=255 ms` 那个数量级。

**它和车辆几何是同一个形状**：一大段纯 CPU 的"合并 + 归一化"，紧跟一段**必须留在渲染线程**的
`upload()`。notes/400 §8 刚为车辆做的那套两段式（`bake` 在 `MMTR-ModelParse` 上、`upload` 在渲染线程、
失败回退同步、`-D` 开关）可以**原样照搬**。

## 5 结论与下一步（按收益排序）

1. **把钢轨烘焙的"合并 + 归一化"搬到工作线程**，渲染线程只留 `upload()`。
   预计把 200–400 ms 的单帧压到 upload 那一档（车辆那份实测 52–93 → 20–34 ms）。
2. **一行就能见效的止血**：`MAX_BAKES_PER_PASS` 2 → 1（代价：缓存更慢热、覆盖范围涨得慢）。
3. 车辆的 `建 VBO`（`writeCache`/`addTransformation`）72–111 ms —— notes/400 §8.6 的第一项，
   仍然成立，但按本节的数据它**不是**用户感觉到的那一下。

## 6 动手之前的最后一个量：一次烘焙内部怎么分

在 `MmtrRailMeshCache.bakeInner` 里加了 `[MMTR-RAILBAKE] 烘焙分段`（只打 ≥ 12 ms 的，总数封顶 80 条），
把三段分开量。**改之前的实机读数**（2026-10-08 20:31，进世界那一波）：

```text
[MMTR-RAILBAKE] 烘焙分段 160 个实例 39 ms ｜ 走曲线+取光 22 ms（其中取光 0 ms）｜ 矩阵+克隆+合桶 13 ms ｜ upload 16 ms
[MMTR-RAILBAKE] 烘焙分段 440 个实例 63 ms ｜ 走曲线+取光  5 ms（其中取光 0 ms）｜ 矩阵+克隆+合桶  5 ms ｜ upload 57 ms
[MMTR-RAILBAKE] 烘焙分段 440 个实例 31 ms ｜ 走曲线+取光  8 ms（其中取光 0 ms）｜ 矩阵+克隆+合桶  8 ms ｜ upload 23 ms
```

两条结论都不在预期里：

1. **取光（`clientWorld.getLightLevel`）是 0 ms** —— 它是三段里唯一有线程安全问题的一段，
   而它根本不值钱 ⇒ **留在渲染线程，不要去动它**（原计划里"要不要跟着搬"到此为止：不搬）。
2. **`upload()` 才是大头（16–57 ms）**，而"纯 CPU、可搬"的那一半只有 10–35 ms。
   ⇒ 这次改造能省的是 10–35 ms／根，不是"把 200 ms 变成 0"。

## 7 改法：四段状态机（走曲线 → 取光 → 合桶 → upload）

新增 `MmtrRailBakeJob`（`org.mtr.mod.render`）：

```text
① 工作线程 MMTR-RailBake   RailMath.render 走一遍 → 每个实例 10 个坐标（x1,z1,x2,z2,x3,z3,x4,z4,y1,y2）
② 渲染线程                逐实例取世界光照 + 光照哈希（老路里这一段在 walk 的回调里，值一模一样）
③ 工作线程                 逐实例：矩阵 → 逐顶点深拷贝 → RawModel.append 合桶
④ 渲染线程                 merged.upload(MAPPING)（进 GlStateTracker 保护区）
```

* ①③ 是把原来的代码**逐字搬过去**（四个矩阵步骤、四元数写法、`(x1*z1)%10` 那个 z 旋转、
  逐顶点深拷贝 + `copy.light` 的顺序都没动），只换了"在哪里跑"。
* **为什么敢在工作线程读 `Rail.railMath`**：`railMath` 是 `public final`，`RailMath` 的字段**全是 final**
  ⇒ 渲染线程取一次引用当快照，工作线程读的是不可变对象。世界数据一个都不碰（光照留在渲染线程）。
* 复用 `MmtrAsyncModelParse`，但给它加了一个**专用线程池**：车辆那条（解析 + 几何烘焙）一次能占住
  `MMTR-ModelParse` 几百毫秒，而钢轨烘焙是**突发**的（进世界 42 次）。共用一条会让钢轨排在车辆后面，
  而排队期间那些轨只能逐实例画（draw 数暴涨）—— 那比"慢一点烘好"更糟。所以新开了 `MMTR-RailBake`。
* 预算换了位置：老路"每 pass 最多烘 N 根"限的是整次烘焙；现在后台可以多跑几份（`MAX_PENDING_JOBS = 3`，
  每份在 build 阶段持有一份 4–5 MB 的 RawModel），但**一个 pass 只允许 N 次 upload**
  —— 贵的本来就是 upload。作业超时（120 帧没人问）会被丢掉，不会变成泄漏。
* 失败：任何一段抛异常 ⇒ 这一份作废、打一条 warn，并把整条切回渲染线程上同步烘
  （`asyncUnavailable`，与 `sourceUnavailable` 同一套纪律：绝不静默、绝不半成品、绝不每帧重试）。
* 开关：`-Dmmtr.railbake.async=false` 回老路；`-Dmmtr.railbake.verify=true` 开自检。

## 8 等价性自检：3/3 逐字节一致

光"看起来一样"不够 —— 这是逐实例矩阵 + 逐顶点拷贝，差 1e-6 肉眼看不出来。所以加了一次性自检
（`-Dmmtr.railbake.verify=true`）：头 3 次烘焙**同时**在老路上再算一遍几何（不上传），
把两份 `RawModel` 的材质桶顺序、每个顶点（位置/法线/uv）、每条面的索引摘要比一遍。

```text
[MMTR-RAILBAKE] 等价性自检 1/3 default_3d@…F510…: 两份模型摘要逐字节一致 ✓（后台版可以继续用）
[MMTR-RAILBAKE] 等价性自检 2/3 default_3d@…F4AC…: 两份模型摘要逐字节一致 ✓
[MMTR-RAILBAKE] 等价性自检 3/3 default_3d@…F510…: 两份模型摘要逐字节一致 ✓
```

> 摘要**故意不含 color / light**：后台那条路的光照是在"走完曲线的那一帧"取的，自检那条是当下取的，
> 同一根轨通常一样、但"通常"不能当判据。要证的是几何（矩阵/克隆/合桶）逐字节对；光照本来就是
> 同一段代码、同一个线程（渲染线程），只是换了个 for 循环。

## 10 第 2 项（`MAX_BAKES_PER_PASS` 2→1）被读数**否掉了**

试过默认改成 1，读数是这么说的：

* 改后每烘一根渲染线程只剩 `upload 13–35 ms` ⇒ "每 pass 2 根"的上界只有 **26–70 ms**，不大；
* 而**真正贵的是"还没烘好的轨走逐实例渲染"**：进世界那一瞬实测
  `[MMTR-LIGHT] 钢轨 draws=293.7(0.62 批)`（0.62 批 = 几乎全是逐实例）与 `shadow.rails max=386 ms`
  —— 那是**冷缓存**的代价，与烘焙本身无关；
* 把额度降到 1 只会让缓存热得更慢：2 根/pass = 一帧 4 根，42 根约 11 帧热完；降到 1 要 ~21 帧，
  逐实例那一段**拖得更久**。

⇒ **默认保持 2**，但把它做成系统属性 `-Dmmtr.railbake.perpass=1`（要压单帧尖峰就用它，代价写在上面）。

**同时更正 §3/§5 里我自己的一句过头话**：那时把 `[MMTR-FRAME] shadow.rails max=418.93 ms`（同步烘焙）
与 `max=60.15 ms`（后台烘焙）摆在一起说成"7 倍改善"——那两段窗口只有 5–7 帧、还盖着进世界的
资源加载，**不可比**。可比的只有"每烘一根"的分段读数（上表）。

## 11 第 3 项：车辆"建 VBO"那 100 ms 花在哪

```text
[MMTR-VEHCTOR] mtr:properties_saf420cab_a.json 97 ms ｜ 部件 49 ｜ writeCache 94

[MMTR-MODEL]  mtr:saf420cab_a/saf420cab.obj 这一轮重建 137 ms ｜ 读 32 ms ｜ 解析 已在后台完成 ｜ 建 VBO 100 ms（本线程 CPU 62 ms）
```

拆开看：

| 段 | 值 | 性质 |
| --- | --- | --- |
| `writeCache` 合计 | **94 ms** | 构造的全部几乎都在这里 |
| ├ `addTransformation`（逐位置烘几何） | 17 ms / 40 次 | 纯 CPU，**可搬** |
| ├ `optimizedModelDoor.get()`（门/雨刷各自的模型） | **36 ms / 28 次** | 每次都要 `generateNormals + distinct + upload`，**主要是 GL（建 VBO）** |
| └ 其余（PartDetails / Box / 两张 bundle 表的 Data.put / supplier 构造） | ~41 ms | 纯 CPU，**大部分可搬** |
| `testDoors` | 2 ms | 纯 CPU，可搬 |
| 调试日志 | 0 ms | — |
| **CPU 62 ms vs 墙钟 100 ms** | 差 38 ms | **不是算出来的**：GC 停顿 / 被别的线程抢核 —— 这部分**搬线程也没用** |

### 11.1 门模型那 36 ms 只在**开门**时才用得到

`optimizedModelDoor` 的两处使用：

* 门（24 组）：`renderNormal` 行 572 —— 条件里带 `!openDoorways.isEmpty()`，**只有开门态才画**；
  合并那条路（`MmtrDoorBatch`）用的是 `doorBatchGeometry()`（源 `ObjModel`），**不用**这个包装。
* 雨刷（4 组）：`isWiperPart` ⇒ 走 else 分支，行 601 **每帧都画**。

⇒ 24 组门的那 24 次建 VBO（约 31 ms）在**关门态（常见情形）完全是白做的**。

### 11.2 第 3 项的计划（当时的排序；实际落地见 §11.3）

1. **门那 24 个模型改成"第一次真要用时才建"**（开门态 / 或第一次被画）。
   省的是每次重建 ~31 ms；代价是把它挪到"开门的第一帧"—— 而那一帧本来就在建门批次
   （`[MMTR-DOORBATCH] 门合并`），所以是**并到一处**，不是新增一处。
   注意：`upload` 需要 GL 状态保护区，得走 `beginReload/finishReload` 或 `withProtectedGlState`。
2. **把 `writeCache` 里纯 CPU 的那一半（17 + 41 + 2 ≈ 60 ms）搬到工作线程**，
   渲染线程只留门/雨刷的 upload 与登记。这是 notes/400 §8 那套两段式的第三次应用，
   但它要重构 `writeCache`（bundle 表 / PartDetails 都是渲染线程马上要用的），改动面最大。
3. **不要**只搬 `addTransformation`（17 ms）：收益最小、还要动同一段代码。
4. **38 ms 的 CPU/墙钟差值是搬不走的**（GC/抢核）—— 与 §1 的结论一致
   （JFR 里 young GC 只有 3–5 ms，但那是"停顿"的时长；这 38 ms 是"没在算"的时长，
   含被抢核与 GC 之外的等待）。所以**上限**是"100 ms 里最多省掉 ~60 ms"。

### 11.3 落地：门那 24 个模型改成"第一次真要用时才建"

代码在 `ModelPropertiesPart.PartDetails`：`optimizedModelDoor` 从"构造时算好的值"变成
"`Supplier` + 第一次 `doorModel()` 时才算"，两个渲染分支改成先问 `hasDoorModel()`（**不触发**创建）再取。
雨刷（mechanism）**照旧现建**（它每帧都画，推迟没有收益）。惰性那次创建外面套
`beginReload/finishReload` —— 与渲染中途建门批次的 `MmtrDoorBatch.build` 是同一把锁的用法
（那个包装器按嵌套层数记账，只有最外层碰 GL 状态）。

```text
改前 [MMTR-VEHCTOR] 97 ms ｜ 部件 49 ｜ writeCache 94（addTransformation 17 / 40 次、门模型 36 / 28 次）｜ testDoors 2 ms
改后 [MMTR-VEHCTOR] 81 ms ｜ 部件 49 ｜ writeCache 76（addTransformation 16 / 40 次、现建门/雨刷模型 28 / 4 次）｜ testDoors 4 ms
     [MMTR-MODEL]   121 ms ｜ 读 19 ms ｜ 解析 已在后台完成 ｜ 建 VBO 87 ms（本线程 CPU 46 ms）
```

* **现建模型次数 28 → 4**（只剩 4 组雨刷）—— 改动生效。
* **但冷启动那一节只省了 16 ms（97 → 81）**：原来那 36 ms 里相当一部分是 `fromObjModels`
  那条路的 **JIT / 首次初始化**（旧：36/28 = 1.3 ms 一个；新：4 个雨刷就要 28 ms = 7 ms 一个）——
  JIT 的钱只是换了个人付，**没有省掉**。这条教训值得记：**别拿冷启动的分段读数给优化记功**。
* 真正省下的是**稳态**那一档（那才是每 ~100 s 重复发生的那一次）：阈值从 40 ms 降到 20 ms 后
  才看得见，读数见 §11.4。
* 推迟到哪去了：`[MMTR-LAZYDOOR] 惰性建门/雨刷模型 N ms ｜ M 次 draw` —— 只在**开门态第一次**
  真画门时出现（默认 `MmtrDoorBatch` 接管了门类，所以多数情况下连这一笔也不会有）。

### 11.4 稳态那一档：构造那 100 ms 其实是**争用时的数字**

把阈值从 40/50 ms 降到 20 ms 重跑，同一会话（21:06 连接）里同一条 cab_a 的重建：

```text
21:09:27 [MMTR-MODEL] cab_a 这一轮重建 20 ms ｜ 读 24 ms ｜ 解析 已在后台完成 ｜ 建 VBO 17 ms（本线程 CPU 15 ms）
21:11:00 [MMTR-MODEL] cab_a 这一轮重建 41 ms ｜ 读  5 ms ｜ 解析 已在后台完成 ｜ 建 VBO 41 ms（本线程 CPU 31 ms）
```

⇒ **安静的稳态下这个构造只要 17–41 ms**，而 72–111 ms 那几笔全部是在"进世界 / 一波三辆车同时重建"
的时刻量的（那时 JIT 冷、区块/贴图/着色器都在加载、工作线程也在忙）。所以第 3 项的正确读法是：

| 情形 | 构造 |
| --- | --- |
| 进世界那一波（JIT 冷 + 一切都在加载） | 81–100 ms（就是当初那 72–111 ms 的来源） |
| 稳态单独一次重建（JIT 热、世界安静） | **17–41 ms** |

**这条更正很重要**：notes/400 §8.6 把"建 VBO 76–111 ms"排成第一项，那是拿争用态当稳态了。

### 11.5 开门态**真的验到了**（顺手把前几轮一直挂着的那个缺口补上）

这一局客户端里门开态出现了（不是特意造的，列车在站台停了）：

```text
[MMTR-VDRAW]   5.0s 窗口：车·帧=4578（门关=3346 门开=1232）
[MMTR-DOORBATCH] 门合并：4 个动画类、24 组门 → 8 次 draw/pass（-Dmmtr.doorbatch=false 可回退）
[MMTR-LAZYDOOR]  惰性建门模型 0 ms ｜ 1 次 draw ｜ 累计第 N 次
```

* **`4 个动画类、24 组门 → 8 次 draw/pass` 与改前（notes/400 §6.6）逐位相同** ⇒ 门批次的行为没有被
  钢轨/车辆这两轮改动碰到；`每次排队 draw 数 avg=1.1 max=4` 也照旧。
* **惰性门模型真的被建出来并画上了**（`1 次 draw`，每次 0 ms）—— 也就是 §11.3 那条新路在开门态下
  确实工作，而且它推迟的那一笔几乎不要钱（这也反过来说明：当初那 36 ms 主要是 JIT，不是门 VBO）。
* 同时看到安全阀按设计工作：`类 0.0|14.0|STANDARD|false|NORMAL|3（6 组门）这一帧不合并：
  [door_r_2] 与 [door_r_2_glass] 的位移不同：1.9040 vs 1.9600` —— 那个类这一帧退回逐组画
  （门位移动画是同帧按毫秒插值的，差 0.056 超过了 `DOOR_OFFSET_TOLERANCE=0.05`）。
  **这是既有安全阀的既有行为**（notes/400 §6.3/§6.4），与本轮改动无关，画面一致、只是那个类多几次 draw。

#### 11.5.1 再把"惰性那条路"单独压一遍：`-Dmmtr.doorbatch=false`

默认挡位下 `MmtrDoorBatch` 接管了门类（`skipOptimizedDoor=true`）⇒ 惰性模型只在"被拒合并的那个类"
才用得到。为了**单独验**它，再跑一局 `-Dmmtr.doorbatch=false`（这时 24 组门全走逐部件那条路）：

```text
[init] runClient 已注入 -Dmmtr.doorbatch=false（门合并回退到逐部件组）
[MMTR-VDRAW]  车·帧=27090（门关=22450 门开=4640）
[MMTR-LAZYDOOR] 惰性建门模型 0 ms ｜ 1 次 draw ｜ 累计第 N 次      ← 这一局共 41 次，每次都是真模型
[MMTR-VDRAW]  门/雨刷逐位置排队=118056 次 draw avg=1.0 max=1 ｜ 门·类合并=0 次 draw
[MMTR-LIGHT]  钢轨 draws=5.6–8.0(1.00 批) ｜ 非钢轨 draws=284.5–317.9(11.00 批)
```

判据：

| 看什么 | 期望 | 实测 |
| --- | --- | --- |
| 门批次有没有插进来 | 没有（已关） | `[MMTR-DOORBATCH]` **一条都没有** ✓ |
| 逐部件那条路在画门 | `门/雨刷逐位置排队` 的 `avg=1.0 max=1`（一组一次 draw，就是改动前的形状） | `avg=1.0 max=1`，累计 11.8 万次 ✓ |
| 惰性模型真的建出来了 | 每次 `1 次 draw`（不是 null、不是 0） | 41 次全部 `1 次 draw`、每次 0 ms ✓ |
| 钢轨仍是烘焙路 | `1.00 批` | `5.6–8.0(1.00 批)` ✓ |
| 失败 | 一条都没有 | 空 ✓ |

⇒ **开门态 + 逐部件路（惰性模型唯一真正吃重的那条路）验过了**；而默认挡位下门批次与改前
`4 个动画类、24 组门 → 8 次 draw/pass` 逐位相同。门这一侧两挡都干净。

### 11.6 第 3 项的结论

* **落地**：门那 24 个模型的惰性化（`现建门/雨刷模型 28 → 4 次`）。
* **不再往下做 `writeCache` 的 CPU 半边重构**，理由是 11.4 的读数：稳态构造只有 17–41 ms，
  里面 `addTransformation` 16 ms、`testDoors` 2–4 ms，而 CPU/墙钟差值是搬不走的；
  为剩下那十几毫秒去重构 `writeCache`（bundle 表 / PartDetails 都是渲染线程马上要用的）不划算。
* 冷启动那一档（81–100 ms）的大头是 JIT + 争用，**搬线程救不了**（§11.4 的教训：别拿争用态的分段读数记功）。

## 12 复跑（这套手法值得留着：**不用重启客户端**）

```powershell
# ① 在活着的客户端上开录制
$pid0 = (Get-CimInstance Win32_Process -Filter "Name='java.exe'" |
         Where-Object { $_.CommandLine -like '*dli.env=client*' }).ProcessId
$jh = "$env:USERPROFILE\.gradle\jdks\eclipse_adoptium-21-amd64-windows.2"
& "$jh\bin\jcmd.exe" $pid0 JFR.start name=mmtr settings=profile maxsize=64m
# ② 抓到你关心的那一下之后导出（路径带空格 ⇒ filename 的值必须自己加引号，否则 jcmd 报
#    Unknown argument 'DEV\MC\...'）
& "$jh\bin\jcmd.exe" $pid0 JFR.dump name=mmtr "filename=`"<工作区>\sandbox\tmp\jfr-client.jfr`""
# ③ 看（**选项必须写在 view 名之前**，写成 `jfr view hot-methods --width 140 f.jfr` 会报 unknown option）
& "$jh\bin\jfr.exe" view --width 150 hot-methods     sandbox\tmp\jfr-client.jfr
& "$jh\bin\jfr.exe" view --width 150 native-methods  sandbox\tmp\jfr-client.jfr
& "$jh\bin\jfr.exe" view --width 130 latencies-by-type sandbox\tmp\jfr-client.jfr
& "$jh\bin\jfr.exe" print --events jdk.GCPhasePause            sandbox\tmp\jfr-client.jfr
& "$jh\bin\jfr.exe" print --events jdk.ExecutionSample --stack-depth 8 sandbox\tmp\jfr-client.jfr > samples.txt
& "$jh\bin\jcmd.exe" $pid0 JFR.stop name=mmtr
```

* **别用 `jfr print --json` 看 ExecutionSample**：3 分钟的录制吐了 **330 MB**，整份读不动。
  纯文本只有 4.5 MB，够用。
* 文本里线程字段叫 **`sampledThread`**（不是 `eventThread`）。
* 判定速查：栈里全是同一段代码 ⇒ 单一热点；栈五花八门 + 段合计远小于帧间隔 ⇒ **这一帧是 tick 侧
  （实体/区块/网络）或别的线程**，不是渲染。
