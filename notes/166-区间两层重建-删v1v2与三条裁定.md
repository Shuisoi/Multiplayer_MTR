## 2. 目标模型

```text
Level 0  弧长 (railHex, arc)                      —— 与占用树同一 ordered-position-1 空间
Level 1  TrackSection 轨道区间（无方向、双向共用）
           切点 = 灯在轨上的投影点（只由灯）
           段沿"唯一续轨"的链推进；遇 ①灯投影点 ②分叉/合流节点 ③线路尽头 收口
           （②③ 不是新增的切点来源，而是"段不能分叉/不能无限长"的推论）
           不变量：每一点**恰好**属于一个轨道区间（真正的唯一划分）
           占用只在这一层判定 —— **占用无方向**
Level 2  BlockSection 行车区间（有方向）
           对每个方向 D：从一架朝 D 的灯起，沿 D 走到下一架朝 D 的灯（不含）
           = 连续若干 TrackSection 的并（L2 边界一定是 L1 边界）
           无任何信号灯的连通块：整块作为一个**大区间**（用户裁定 3）
           占用 = 它的成员 TrackSection 任一被占
```

**为什么这样分**：占用是物理事实（谁压在这段轨上），与方向无关；授权是行车方向的事（谁能进哪一段）。现状把两者压成 v1/v2 两套"切法"，于是同一个词指了两种东西（见 §4）。

## 3. 必须有用例钉住的不变量

1. **L1 唯一划分**：每一点恰好一个轨道区间（`owners == 1`，既有用例只钉了 `<= 1`，天窗抓不到）。
2. **L2 ⊆ L1 的并**：任一行车区间 = 整数个连续轨道区间，边界必是灯位；不得出现"半截轨道区间"。
3. **按方向的干净划分**：同一方向上每一点恰好属于一个行车区间（L2 含无灯大区间，所以这次真的成立）。
4. **灯到灯 / 节点不切分 / 出口灯不含**（沿用 v2 已钉住的语义）。
5. **走行不许掉头**（`MMTR_REVERSAL_DOT`，只对唯一续段生效）。
6. **一灯多腿 ⇒ 多段行车区间**（现状零断言，本轮补上）。
7. **占用只有一个判据**（重叠量纲一处实现，v2 的三份实现合一）。
8. **`reachable` 只影响"占用"，不影响"守卫"**（现状测试文案与代码相反，本轮钉死）。
9. **无灯连通块 = 一块大区间**（反转 notes/157；两种方向都走它）。

#### R2 抓到的两个真漏洞（写下来，别再犯）

1. **灯站在节点上时，切的是"节点"而不是"轨内一点"**。第一版把"投影落在弧 0 / 轨长"当成
   "轨端、不产生内部切点"，于是度 = 2 的接头照样把两侧接起来 —— **那盏灯等于白站**
   （它划的分界在数据里根本不存在）。修法：这类投影记进 `cutNodeKeys`，合并时该节点不许接。
   实机上这是**常态**：dev 世界 73 盏灯没有一盏落在节点格里，投影都在 0 / 轨长附近。
2. **`NODE_CUT_TOLERANCE_M = 1.0`（一格）**：MTR 的灯方块中心 = 方块坐标 + 0.5，所以一盏明明
   立在接头上的灯投影落在弧 **0.5** 处。按 `MIN_BLOCK_PIECE_M = 0.05` 判，会在接头旁切出一段
   0.5 m 的碎片 —— 现场"没人守的碎片"正是这么来的。取 1 格判为节点切点；3 m 开外已经是
   "轨中段的灯"（`NODE_BIND_RADIUS_M` 那条实测：灯立在节点旁 3.16 格）。

#### 另两条已落实的规则

- **段不能分叉**：度 ≠ 2 的节点一律收口（道岔处**即使没有灯**也切）。这不是新增的切点来源，
  而是"段是线性的"的推论，现实依据同构（道岔区段自成一段，绝缘节在警冲标外方）。
- **占用判据收成一份**：`overlapsEnough(vp, from, to, exclude)` 的弧窗版本，L1 与 L2 共用
  （原先三份：本类两份 + `MmtrJunctionState.foulsZone` 里硬编码同一个 1.0 —— 第三份待收编，记在 R3）。

#### R3 必须处理的一个语义开口（别丢）

**"守卫多值"与"归属唯一"要分开**：咽喉多腿时一盏灯守多条腿，多盏灯的守卫范围会**重叠**
（用户 2026-09-10「一盏灯守整个咽喉」要的就是它，且是现场必需：岔股上可能停着扳岔前就进来的车）。
但"同一方向上每一米恰好属于一个行车区间"要求归属**唯一**。所以 L2 需要两条不同的读法：
`guardingSectionsOf(rail, arc)`（多值，守备用）与 `ownerOf(rail, arc, heading)`（唯一，= **最近上游灯优先**，
那条规则正是被删的水闸层用过的，但**只用于归属、不用于守卫**）。R3 落地，R8 补用例。

#### R3 实施记录（L2 补齐）

- **链序**：L1 成段时一并记下"谁和谁在哪个节点接上"（`joins` + `orderChain`），组内 span 按链序排。
  为什么必须要它：给无灯大区间算**方向**（`RailSpan.headingX/Z`）只能沿链算 —— "从哪一端进、往哪一端出"

  id 为 `无灯#<L1 id>` / `无灯#<L1 id>·逆`。补完 L2 是**全网络覆盖**的：每个方向上每一点恰好一个行车区间。
- 新增用例 2 例（`aStretchNoLampReachesBecomesOneBigSectionInBothDirections`、
  `aLampLitStretchIsNotDuplicatedByAnUncoveredSection`），该文件共 8 例全绿。

## 6. 取舍与已知后果（写下来免得以后当 bug 报）

1. **裸删期间仓库不可运行**：这是用户选定的顺序（「先把 v1/v2 删掉，新层随后长回来」）。R4/R5 之间引擎不编译属预期。
2. **"段不能分叉" ⇒ 道岔节点必然收口**：用户裁定切点"只由灯"，但 L1 段是线性物，度 ≥ 3 的节点处必须收口。这不是新增切点来源，是"段"这个概念本身的推论（现实里也如此：道岔区段自成一段，绝缘节在警冲标外方）。
3. **无灯连通块 = 一块大区间**（裁定 3）**反转 notes/157** 的"无灯轨不属于任何区间"。后果：长走廊会被整块锁（一列车在里面，同方向后车就停在块外）。用户明确要求"不按当前世界来看"，所以**不为 dev 世界的 44 根无灯轨做特例**。
4. **占用不再借 MTR 的每轨信号色通道**：旧的 B3b"每区间一个保留色"随之取消。网页与游戏端都改读 L1/L2 的占用结论；客户端不再自己算区间。
5. **灯 → (保护轨, 方向) 的解析与走行算法是保留资产**，不是"两套模型"的一部分（现场实测修出来的东西：掉头判据、多腿、禁入侧、键序、中段灯）。删的是两套模型的**身份**与 v1 的逐轨语义。
