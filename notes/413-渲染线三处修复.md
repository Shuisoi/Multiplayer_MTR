# 413 渲染线三处：烘焙作业被 LRU 秒删、逐实例剔除用了查不到约定的旋转、异步收尾会把在用的模型关掉

用户 2026-10-09 报（原话）："现在铁轨，列车等实体会不规律消失和显示，好像和移动有关，比如当我移动到
节点左侧就显示节点左侧的轨道，右侧则显示右侧的，列车也一样，是不是渲染被你改坏了"。

同一晚的只读审计（另一路，未改文件）把这条症状拆成**四件互不相同的事**。其中"以节点为界按左右分侧"
这一形状，全仓只有**数据裁剪**能产生（`DataRequest.rail.closeTo` + `DataResponse.write()` 的窗口替换），
已在 [notes/410 §9](410-动态项前视加载管线.md) 修掉并落用例；本笔记记渲染线那三处。

## 1 烘焙作业在新建的下一帧就被 LRU 删掉（已修）

### 机制

| 环节 | 读数 |
|---|---|
| 新建后台作业 | [MmtrRailMeshCache.java:412-423](../game/fabric/src/main/java/org/mtr/mod/render/MmtrRailMeshCache.java#L412-L423)：`new MmtrRailBakeJob(...)` → `PENDING.put(key, job)` → `return cached`，**没有 `markUsed`** |
| 作业的"最近使用帧" | [MmtrRailBakeJob.java:151](../game/fabric/src/main/java/org/mtr/mod/render/MmtrRailBakeJob.java#L151) `private long lastUsedFrame;` —— **无初值 = 0** |
| 超时淘汰 | [MmtrRailMeshCache.java:921](../game/fabric/src/main/java/org/mtr/mod/render/MmtrRailMeshCache.java#L921) `frame - lastUsedFrame > 120`（PENDING_JOB_TIMEOUT_FRAMES，:117） |
| frame | [MmtrRailMeshCache.java:318](../game/fabric/src/main/java/org/mtr/mod/render/MmtrRailMeshCache.java#L318) 只在**主 pass** 递增；阴影 pass 提前 return |

⇒ 只要 `frame > 120`（进世界一两秒后），**新建作业在下一个 `beginPass` 就被删**，
而删发生在任何一次 `resolve()` 之前 ⇒ `advance()` 永远轮不到它，作业永远走不到 `合桶`/`upload`。

### 实机判据（这份日志里有完美相关）

`[MMTR-RAILBAKE] 窗口 300 帧` 汇总行共 **342** 条，与同期的 `[MMTR-FRAME] 通行=` 交叉：

```
 92 条  通行=1.00（只有一个主 pass）：新建=0 upload=0 在飞=2 缓存=61  ← 一次都没烘完，恒卡 2 个在飞
所有 upload>0 的窗口 100% 是 通行=2.00（阴影+主两个 pass）         ← 作业靠"不淘汰的阴影 pass"续命
后台线程：18656 条「走曲线」 vs 只有 195 条「合桶」                  ← 99% 的作业死在 advance() 之前
```

### 后果与用户症状的关系

`ENTRIES` 冻结在"开光影那段时间攒下的 61 根"（`MAX_ENTRIES=96` 不会淘汰它们）。之后玩家遇到的、
**不在这 61 根里**的轨永远烘不出来 ⇒ 永远走 [RenderRails.java:341-360](../game/fabric/src/main/java/org/mtr/mod/render/RenderRails.java#L341-L360) 的**逐实例回退**；
而回退那条路里跑着第 2 条那个剔除，已经烘好的 61 根**完全不跑** ⇒ 画面里同时存在两套可见性规则。

> 重要否定结论（审计给的口径）：烘焙未就绪时调用方是**逐实例回退、不是跳过** —— 所以"烘不出来"
> 本身不会让钢轨消失，消失来自"两条路的剔除规则不一样"。

### 修法

`PENDING.put` 之后立刻 `job.markUsed(frame)`（[同处](../game/fabric/src/main/java/org/mtr/mod/render/MmtrRailMeshCache.java#L424)）。
同一文件里 `recordRebuild` 早就为**已完成的项**踩过同一个坑（"新烘出来的项必须立刻打上本帧刚用过，
否则它会以 lastUsedFrame=0 排在 LRU 队首"）—— 这次补上的是**在飞的作业**那一半。

## 2 逐实例视锥剔除用了一个"约定查不到"的旋转（已修）

### 机制

原来的写法（[RenderRails.java:449-450](../game/fabric/src/main/java/org/mtr/mod/render/RenderRails.java#L449-L450) 附近）：

```java
final Vector3d rotatedVector = new Vector3d(x1, y1, z1).subtract(cameraPosition)
        .rotateY((float) Math.toRadians(camera.getYaw()))
        .rotateX((float) Math.toRadians(camera.getPitch()));
```

`com.logisticscraft.occlusionculling.util.Vec3d` 的旋转约定在本仓里**无从查证**（该类不在工作区源码里，
也不在能扫到的依赖 jar 里）。按标准右乘约定把它展开，深度项会多出 `2·dy·sin(pitch)`：

> 相机俯角 30°、目标在视线正前方 10 m（dy = −5, dz = 8.66）时，这段算出的相机空间是
> `z = 5.0`、`|y| = 8.66` —— 判据 `|y| ≤ z/m11·1.3`（≈4.55）不成立 ⇒ **正中央的目标被判到画面外**。

也就是说：**抬头/低头时，走逐实例回退的那些轨会成片消失**（已烘好的 61 根不跑这个剔除，所以"有些轨
一低头就没了、有些轨不闪"）。它解释不了"左右分侧"，但与第 1 条叠在一起就是"不规律消失"的完整故事。

### 修法：换成同仓已被单测钉死的基底

本仓 `MmtrInteractPrompt` 里有一套**被 `mmtr/tools/projection-check` 的算术单测钉死**的相机基底
（forward / right / up，三个符号选择每一个都曾经错着上过线），并且把 `projectionScale()`（投影矩阵对角
`m00/m11`）的语义写得明明白白是"逐实例剔除也要用"。

所以：

1. 把基底提取成 `MmtrInteractPrompt.cameraBasis(camera)`（返回
   `{forwardX, forwardY, forwardZ, rightX, rightZ, upX, upY, upZ}`，正上/正下返回 `null`），
   `project()` 改为调它 —— **算术逐字不变**；
2. `RenderRails` 的逐实例剔除改用同一套基底的**点乘**：`depth = d·forward`、
   `cameraX = d·right`、`cameraY = d·up`，判据仍是 `|cameraX| · m00 ≤ depth`、`|cameraY| · m11 ≤ depth`
   （`CULL_MARGIN`、`CULL_BEHIND_METRES`、`CULL_NEAR_DEPTH` 都不动）；
3. 取不到基底（正上/正下）时**不剔**（照画），保守优先。

离线自检：`& "$env:JAVA_HOME\bin\java.exe" mmtr\tools\projection-check\ProjectionCheck.java`
（提取前后的算术对比）。

## 3 后台收尾会把刚登记进缓存的模型关掉（已修）

- `upload()` 在"合并产出 0 个材质"时返回 `previous`（[MmtrRailMeshCache.java:534-536](../game/fabric/src/main/java/org/mtr/mod/render/MmtrRailMeshCache.java#L534-L536)）；
- 同步老路挡住了这一情形（`:500-504` `if (rebuilt == cached) { cached.lightDirty = false; return cached; }`）；
- **后台路没有**：它直接 `recordRebuild(key, rebuilt, cached)`，而 `recordRebuild` 会
  `ENTRIES.put(key, rebuilt)` 之后 `cached.model.close()` —— 也就是**把刚登记进去的那个模型的 GL 资源释放掉**。
  之后 `get()` 仍返回这个非 null 的 `Baked`，`RenderRails` 走烘焙分支、压掉逐实例回退 ⇒
  **这一根轨永久不画**（直到键变化）。
- 修法：后台路补上与同步路同样的判断（这一次也不记 `reportBakeSegmentsAsync` —— 没产出分段可报）。

审计口径：这条**未在日志里观测到**（没有 `[MMTR-RAILBAKE]` 失败 WARN）。它是"防永久消失"的护栏，
不是复现出来的症状。

## 4 排除掉的（不要再来这两条）

1. **GL ERROR 洪水不是原因**：`########## GL ERROR ##########` / `65544: Win32: Failed to create interface`
   的字面量只存在于**原版 `Window` 类**（GLFW 错误回调，`@ Render` 段）。`65544 = 0x10008 = GLFW_PLATFORM_ERROR`，
   **不是 GL 错误码**（GL 错误码是 0x0500–0x0506），也不指示 VAO/VBO 创建失败。整份日志 324,576 块，
   23:10:06 起、约 23:14:43 止。
2. **"以节点为界左右分侧"不是渲染**：渲染/烘焙的粒度都是**整根轨**，剔除对 x/y 取绝对值（对称）。
   唯一对得上的形状是逐根轨 AABB 的**数据裁剪** —— 即 notes/410 §9 那条，已修。

## 5 验收读数（实机）

| 读数 | 修前 | 期望（修后） |
|---|---|---|
| `[MMTR-RAILBAKE]` 的 `新建烘焙` | 单 pass 窗口恒 0 | **> 0**（走动时），`在飞` 不再恒 2 |
| 同行的 `缓存 N/96` | 冻结在 61 | 随走动**增长**（上限 96 后 LRU 正常换） |
| `通行=1.00` 的窗口里 `upload` | 恒 0 | 与 `通行=2.00` 一样会有 upload |
| `[MMTR-LOAD]` 的 `客户端轨数 …（跌 n 次）` | 每次移动掉几十条（notes/410 §9） | **跌 0 次** |
| 抬头/低头走动 | 成片钢轨消失 | 不消失 |

判别性 A/B（同一份构建，只切一个 `-D`）：

- `-Dmmtr.railbake=false`：整条烘焙关掉 ⇒ **所有**轨都走逐实例回退（剔除那条路）。若症状反而消失，
  说明问题在"两条路混用"（第 1 条）；若症状照旧，就是第 2 条那条剔除本身。
- `-Dmmtr.railbake.async=false`：走同步老路 ⇒ 若 `新建烘焙` 立刻非 0、`在飞` 恒 0，就单独证出第 1 条。

## 6 未修、留给下一轮（审计给的候选，量级未证实）

1. **遮挡剔除任务被丢**：`RenderRails.java:99-107` / `RenderVehicles.java:103-117` 把逐轨/逐车的
   `shouldRender` / `rayTracing` 交给 `MainRenderer.WORKER_THREAD` 异步算，下一帧才落地；
   `WorkerThread` 的 `MAX_QUEUE_SIZE=2` 满了就**直接丢任务** ⇒ 相机快速移动时布尔值停在旧值。
   这是**轨与车共用的唯一机制**（也是"两者一起闪"最贴合的一条），但 `WorkerThread.java` 不在本次提交的
   改动清单里 ⇒ 属于既有的东西。判别性测量：把 `RenderRails.java:101`、`RenderVehicles.java:105` 的
   `isAABBVisible(...)` 临时改成恒 `true`，若轨和车都立刻不闪，就是它。
2. **车辆侧新增的"整节车厢不排队"窗口**：`VehicleResource` 的后台烘焙未就绪时 supplier 返回 null ⇒
   `RenderVehicles` 整节跳过（`:275-277`），而 `MODEL_LIFESPAN = 60000` ⇒ 每 60 秒过期一次。
   日志量级无法确证。判别：`-Dmmtr.meshbakeasync=false`。
3. `[MMTR-VDRAW]` 里 `totalCars=1` 的车 `draw avg=0.0 max=0` ⇒ 那节车**每帧什么都不画**
   （`OptimizedModelWrapper.optimizedModel == null` 时 `queue()` 是空操作）。更像资源/模型数据对不上，
