# 354 打包闸门与两个静默回归：锚点被"隐藏"即丢 · 门滑向的空间（★ 实机纠正版）

> 本轮任务：把 10 编组（6M4T）的 SAF420 打成资源包（本轮从 v30 起，最终交付 **`SAF420_v33.zip`**）。
> 结论：**包已出，但先修掉了两个"不报错、进游戏才发现"的真缺陷**，并把 consist 打包做成有闸门的入口。
> 本文只记**判据与证据**，不重述设计。

## 1. 缺陷一：视图层"隐藏"的物体不进 OBJ ⇒ 雨刷锚点静默消失

**症状（差一步就发出去）**：车头 `.blend` 里 47 个 mesh，入库的 `saf420cab.obj` 只有 **44** 个 `o` 组 ——
少的正好是 `mmtr_windshield_1_1` / `mmtr_wipersweep_1_1` / `mmtr_wipersweep_1_1_2`。
这三组是**打包器算风挡锚点与雨刷扫掠扇形的唯一来源** ⇒ 打出来的包会没有风挡/雨刷锚点，
游戏里雨刷失效，而**导出、打包、`check_pack.py` 全部报 PASS**。

**取证**（都在库里，可复跑）：

| 判据 | 命令/文件 | 结果 |
| --- | --- | --- |
| 旧 OBJ 到底有没有这三组 | `Select-String -Path saf420cab.obj* -Pattern "^o mmtr_windshield_1_1"` | 9/24–9/29 00:46 的**每一份**备份都有；9/29 22:50 那份**没有** |
| 这三个物体是不是被隐藏了 | 独立后台 Blender 打开 `.blend`，逐物体读 `visible_get()` | 三个都 **`False`**，而 `hide_viewport`/`hide_render` 都是 `False`、集合也没 exclude ⇒ 是**视图层里的 H 隐藏**（只有 `visible_get()` 看得出来） |
| 导出器只导可见物体 | 同上：47 mesh 里 44 个可见 = OBJ 里 44 组 | 一一对应 |

**修法（两层，都在库里）**：

1. **工具层**：`sandbox/saf420_export.py` 导出前**解除全部视图层隐藏**（跑完按原样还原，不动用户屏幕上的可见性），
   导出后**断言** OBJ 的 `o` 组集合 == `.blend` 里全部 mesh 物体名集合，差一个就 `RuntimeError`（不许拿去打包）。
2. **数据层**：独立后台进程重导出并**存回** `.blend`（备份 `saf420cab.blend.bak-before-anchorfix`）。
   判据（`sandbox/saf420_export_bg.py` 自证）：公共组逐组坐标哈希**完全一致**、只多出那三组、组集合与 `.blend` 一致。

> 后台重导出用 `D:\SteamLibrary\steamapps\common\Blender\blender.exe --background --factory-startup`，
> **不占用用户屏幕上那个会话**（当时开着的是拖车）。同一版 Blender（5.2.2）＋同样的导出参数 ⇒ 与桥接导出逐字节可比。

## 2. 缺陷二（★ 我第一版判反了，2026-10-01 实机纠正）：门叶滑向的空间 = **OBJ 空间 = 文件空间 z 取反**

**最终口径（实机为准）**：文件空间里位于 **+Z 侧**的叶取 **−**、**−Z 侧**取 **+**。

| 证据 | 位置 | 含义 |
| --- | --- | --- |
| MTR 对 **OBJ 模型**的 doorZMultiplier **取反** | `LegacyVehicleResource.java:398`<br>`partsObject.addProperty("doorZMultiplier", (isObj ? -1 : 1) * doorZMultiplier);` | OBJ 那一套的 z 与 cube 模型相反 |
| 同一处 OBJ 部件的包围盒**三个轴全取反** | `ModelPropertiesPart.java:191`<br>`new Box(-objModel.getMinX(), -objModel.getMinY(), -objModel.getMinZ(), …)` | 同一个事实的第二处痕迹 |
| **实机**（决定性） | 用户 2026-10-01：`SAF420_v32`「开门还是反的」（客户端只启用了 v32 —— `run/options.txt` 查过） | 按"文件空间远离门洞中心"写的 v30–v32 是**反的** |
| 旁证 | 用户在 v28 时代**看过门开**（他报的是"门玻璃不跟着动"），当时没报门向反 | v9–v28 那套符号在实机是对的 |

**产物级扫描**（`python sandbox\saf420_pack_door_check.py`，按修正后的判据逐片叶判）：

```
v1 v2 v3 v4 v8                36 片反向   ← 老车型 rotation 还是 0 时定的符号（当时没人看门）
v9 … v19 v20 v21 v22 v23 v24 v25 v26 v27 v28 v29   36/36 正确   ← 9/28 换 rotation 后**恰好**对了
v30 v31 v32                   36 片反向   ← 我按"文件空间远离门洞中心"改的，实机证明是反的
v33                           36/36 正确   ← 改回
```

**我第一版错在哪**：我按"offset 与几何落在同一个空间"去读 `ModelPropertiesPart:399`
（`partDetails.z + offset`，而我们的 `definition` 位置全为 0、几何自带绝对坐标）⇒ 得出"打包空间远离门洞中心"。
**这个前提是错的**：OBJ 模型的门偏移走的是被取反的那一套 z（上面两条 MTR 自己的代码就是证据）。
中间还试过一版"把坐标转回模型空间再判"的判据 —— 那是把两套空间混起来，会让**任何**一版都报 PASS，已删。

**修法**（v33）：

1. `consist/saf420.json` 三车 `doorSlideByGroup` 回到 **v9–v28 那一套数值**（A 端车/拖车 `−14,+14,…`，B 端车 `+14,−14,…`），
   并把"OBJ 运行期空间 = 文件空间 z 取反"的口径与证据写进各自的 `_doorSlideNote`。
2. `verify_doors.js` 的 D3 期望值改成"文件空间 +Z 侧取 −"（并在文件头写明三条证据）；
   `sandbox/saf420_pack_door_check.py`（产物级）同步。
3. **闸门仍然拦得住**：把 v33 的符号整组取反跑 `pack-consist.ps1` ⇒ 12 条 D3 FAIL、exit 1、不出包。
4. 单车型夹具 `example/vehicle.saf420cab_a.json` 同步改并重刷 staging，`selftest.js` 的期望串回到 `must be 14` ⇒ **40/40**。

## 3. 雨刷拟合 FAIL 的真因：**导出的是动画中间帧的姿态**（模型没坏，也没人动雨刷）

症状（v29/v30）：`verify_windshield.js` 两个车头各 4 条 FAIL：

```
! sweep wipersweep_1_1: no fan boundary edge is a blade position (the fan must be the region the blade sweeps)
! sweep wipersweep_1_1: single-axis (one pivot) but the blade direction drifts 86.772 deg over a 287.608 deg stroke
! （wipersweep_1_1_2 同样两条：89.502 deg over 298.340 deg stroke）
```

打包器于是把扫掠角算成 **287.6°/298.3°**，而客户端就是按
`state.angleDeg = parkAngleDeg + phase * sweepDeg`（`MmtrWindshield.java:1295`）转叶片 ⇒ 实机会**转近一圈**。

**真因（后台独立 Blender 量的，三份文件对照）**：

| 判据 | 结果 |
| --- | --- |
| 这 4 个雨刷件的 action | `wiper_1_1_sweep` / `wiper_1_2_sweep` / `wiperarm_1_1_sweep` / `wiperarm_1_2_sweep`，`rotation_euler[2]` 关键帧 **1→25→49 = 0 → −90° → 0** |
| 场景当前帧 | **37**（1 与 49 都是停位）⇒ 求值出 **−45.000001°** |
| 19:45 快照 | 动画**已经在**，但帧是 **1** ⇒ 位姿 0°、一切正常 |
| 22:50/22:59 的 .blend 与入库 OBJ | 帧 **37** ⇒ 叶片被烘成 −45° |
| `saf420cab.obj.bak-before-glassuv-unwrap`（0:46）vs 现在 | `mmtr_windshield_1_1` / `mmtr_wipersweep_*` **逐顶点一致**；4 个雨刷件的差值 = **精确定点旋转 45°**（Δz = 0，质心 Δ(0.466, 0.532)） |

⇒ **顶点从来没被编辑过**。"OBJ 导出会把当前帧的姿态烘进顶点"，而打包器的判据是
"扇形盖边 = 停位叶片" ⇒ 差 13.6 mm 就认不出来，退回"以全体顶点平均当枢轴读扇形"。

**修法（两层）**：

1. 导出前把帧放回**起始帧**（= 停位帧）：`scene.frame_set(scene.frame_start)`，并把帧存回 `.blend`。
   重导出后那 4 组与 0:46 那份**坐标哈希逐字节相同** ✓。
2. **护栏**（关键的一条）：`sandbox/saf420_export.py` / `sandbox/saf420_export_bg.py` 在导出前找出
   "带 location/rotation/scale 动画的 mesh 物体"，**当前帧 ≠ 起始帧就拒导**并点名物体
   （`--park` 自动回起始帧）。实测拦下的原话：
   `当前帧 37 ≠ 起始帧 1 —— 导出会把第 37 帧的姿态烘进 OBJ：wiper_1_1, wiperarm_1_1, wiper_1_1_2, wiperarm_1_1_2`。
   这类错**导出 / 打包 / `check_pack.py` 全都不报**，只有 `verify_windshield.js` 事后看得出来。

**修后**：`verify_windshield.js` 两个车头 **PASS**（`park 179.98 deg, stroke 88.80 deg` —— 与 v28 当时的值**逐字段相同**，
`v28 → v31` 对照里 `windshield 块: 变化 无`），`verify_plane_frame.js` 的 2 条 FAIL 也一起消失
（它就是同一件事的另一面：转轴与扫描角）。

> **走过的一段弯路（留着免得再走）**：我先把这 4 组的坐标差误判成"有人把叶片挪了 / 扇形没重建"，
> 写了个"把物体旋转清零"的还原脚本 —— **它没用**：物体带 action 时 `rotation_euler` 只是**求值结果**，
> 清零后存盘、重开文件又被关键帧覆盖（实测 `saved: true`，文件里仍是 −45°）。脚本已删。
> 正确做法只有一个：**改帧**（或用 `--park`）。

**另外两处判据失败的归属**（别当成新问题查）：

* `verify_plane_frame.js` 的 2 条 FAIL **就是同一件事**（见上，修后消失）。
* `verify_facets.js` 对 cab_b 报的 `no matching mmtr_hud_2 object in the source OBJ` 是**工具缺陷**：
  反向车是"**同一个 OBJ + 打包时 `groupRename`**"（`mmtr_hud_1` → `mmtr_hud_2`），源 OBJ 里当然没有
  `mmtr_hud_2`。已修（`verify_facets.js` 先按 `groupRename` 反查源组名，支持 `*` 通配符）⇒ 两个车头现在都 PASS。

## 5. 夹具联动：改了 `example/vehicle.saf420cab_a.json` 必须重刷它的 staging

`notes/279 §10` 建的单车型夹具 `mmtr/tools/obj-mtr-packager/example/vehicle.saf420cab_a.json`
（rotation 180 + **稳定 staging 目录** `.pack_stage_saf420cab_a`，离线判据与 `selftest` 都对着它跑）
里存的是**同一套旧符号** ⇒ 本轮一起改成 `+14,-14,…`，并且：

```powershell
node mmtr\tools\obj-mtr-packager\pack_vehicle.js mmtr\tools\obj-mtr-packager\example\vehicle.saf420cab_a.json   # 重刷 stage（否则 selftest 的 baseline 读的是旧产物，报 "BASELINE FAILS"）
```

`selftest.js` 里那条注入用例的期望串也跟着改（`door_r_2` 的正确符号由 `+14` 变 `-14` ⇒ `expect: 'must be -14'`）。
**教训**：判据工具的"基准（baseline）"是从**入库产物**读的 ⇒ 改了夹具配置却忘了重刷 stage，整轮自检会以
"BASELINE FAILS" 的形式喊停（这是它该做的事，别去改判据）。
