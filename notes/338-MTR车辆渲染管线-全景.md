# 338 · MTR 车辆渲染管线全景（含 MMTR 已经改过的地方）

日期：2026-09-28 · 目的：为"**结合 Blender 与 mod 进一步美化车体**"打地基。
本轮只做一件事：**把 MTR 到底怎么把一辆车画到屏幕上搞清楚**，做成可检索的事实表。

> 全部结论来自本仓库的源码、反汇编与本工作区实测；每条都带证据（`文件:行`）。
> **推断**的地方单独标注。凡是"游戏里看起来怎样"的判断，都以"能在离线复算出来的量"为准。

## 0. 一句话

MTR **不用 Minecraft 的方块/实体模型系统**画火车。它的做法是：

1. 在客户端**凭空造一个不可见的假实体** `mtr:rendering`，每帧把它**钉在相机位置上**；
2. 借原版"渲染实体"这条通道，在**世界坐标**里自绘**整列车的几何**（车体、转向架、内装、门、显示器、雨刷、升降机、轨道）；
3. 几何来自资源包的 **OBJ / bbmodel / MQO**，按 **组名 → 部件(part) → 渲染阶段(renderStage)** 分类；
4. 每个部件不立刻画，而是**按渲染层攒进队列**，一帧末了**按固定层序统一倒出**（可选的批处理优化器在最后面）。

所以"MTR 的渲染"= **自己的变换栈 + 自己的队列 + 自己的层序**，只在最外面借了原版一层皮。

## 1. 入口链（假实体 + mixin）

| 步 | 事实 | 证据 |
|---|---|---|
| ① | 客户端每 tick 保证世界里存在一个 `EntityRendering`（`mtr:rendering`），**服务端不许存在**（存在就 `kill`） | `InitClient.java:414-425`；`entity/EntityRendering.java:26-33` |
| ② | 这个实体每帧被**挪到相机位置**（距离 >1 格或暂停时才写，避免抖动） | `entity/EntityRendering.java:39-44` |
| ③ | mixin 把它**塞进 `ClientWorld.getEntities()`**，于是原版实体渲染循环就会带上它 | `mixin/ClientWorldRenderingMixin.java:19-28` |
| ④ | 它注册的渲染器是 `MainRenderer extends EntityRenderer<EntityRendering>` | `render/MainRenderer.java:30`；`MainRenderer.java:63-65` |
| ⑤ | 因为实体钉在相机上，原版那步 `translate(entity - camera)` 约等于 0 —— **MTR 拿到的矩阵栈近似单位阵，几何全部用世界坐标自己减相机** | 见 §3 |

**这条链的含义**：MTR 拿到了"每帧一次、在世界坐标系里、可以用任意 RenderLayer"的绘制机会。
代价是它**不在原版的区块/实体排序体系里**——遮挡、透明排序、光影兼容都要自己处理（见 §6 的 MMTR 教训）。

## 2. 一帧里发生什么（`MainRenderer.render`）

```java
MainRenderer.render(graphicsHolder, offset)          // MainRenderer.java:78-192
├─ millisElapsed 与各 tick（仅在非阴影 pass）        // :87-131
├─ RenderVehicles.render(millisElapsed, cameraShake) // :134
├─ RenderLifts.render(...)  RenderRails.render()     // :135-136
├─ 双缓冲交换：RENDERS ←→ CURRENT_RENDERS            // :138-144
├─ 按 (优先级 2 档) × (QueuedRenderLayer 10 层) 倒出 // :146-189
└─ OPTIMIZED_RENDERER_WRAPPER.render(renderTranslucent) // :191  ← 永远在最后
```

- 队列结构：`RENDERS[priority][QueuedRenderLayer][textureIdentifier] -> List<BiConsumer<GraphicsHolder, Vector3d>>`
  （`MainRenderer.java:39-56`）——**两层索引是"优先级"和"层"**，第三层是贴图（同层同贴图合批）。
- 入队 API：`MainRenderer.scheduleRender([texture,] priority, layer, callback)`（`:194-202`）。
- **两阶段**：本帧 `RenderVehicles` 里 `scheduleRender` 进 `RENDERS`；交换后 `CURRENT_RENDERS` 是"上一帧/本帧早段排好的"，
  `RENDERS` 清空留给下一帧。这就是"这一帧画的东西可能是上一帧排的队"的来源（notes/207 那类"水浪被同一毫秒第二通道丢掉"的舞台）。
- **阴影 pass 会跳过整个收集**（`OptimizedRenderer.renderingShadows()`，`:88`、`RenderVehicles.java:403`），
  除非配置 `disableShadowsForShaders`（`config/Client.java:51-52`）。

### 队列层序（`render/QueuedRenderLayer.java:14`，声明序 = 绘制序）

```
LIGHT → INTERIOR → EXTERIOR → LIGHT_TRANSLUCENT → INTERIOR_TRANSLUCENT
      → EXTERIOR_TRANSLUCENT → LIGHT_2 → LINES → TEXT → EXTERIOR_TRANSLUCENT_DOUBLE
```

每层到 MC RenderLayer 的映射在 `MainRenderer.java:150-182` → `render/MoreRenderLayers.java`：

| QueuedRenderLayer | MC RenderLayer | 性质 |
|---|---|---|
| `LIGHT` | `RenderLayer.getBeaconBeam(tex,false)` | **自发光**（信标光柱层，不吃光照） |
| `LIGHT_TRANSLUCENT` | `getBeaconBeam(tex,true)` | 自发光 + 半透明 |
| `LIGHT_2` | `RenderLayer.getText(tex)` | 自发光、无剔除（LED/七段码/线路色用） |
| `INTERIOR` | `getEntityCutout` | 内装，全亮 |
| `INTERIOR_TRANSLUCENT` | `getEntityTranslucentCull` | 内装玻璃（**有背面剔除**） |
| `EXTERIOR` | `getEntityCutout` | 外皮，吃世界光照 |
| `EXTERIOR_TRANSLUCENT` | `getEntityTranslucentCull` | 外皮半透明（有背面剔除） |
| `EXTERIOR_TRANSLUCENT_DOUBLE` | `getEntityTranslucent` | **无剔除**，一片两面可见 —— MMTR 为挡风玻璃加水层新加的 |
| `LINES` | `RenderLayer.getLines()` | 调试线框 |
| `TEXT` | `null`（**不建 vertex consumer**） | 见 §5：优化器打开时所有 NORMAL 部件都排在这一层 |

> `EXTERIOR_TRANSLUCENT_DOUBLE` 是 MMTR 追加的，注释写在 `QueuedRenderLayer.java:3-12`：
> `EXTERIOR_TRANSLUCENT` 走 `getEntityTranslucentCull`，**画两遍不等于双面**，所以另开一层。

## 3. 每辆车 → 每节车 → 变换链

```
MinecraftClientData.vehicles                     // 客户端已知的所有车
└─ vehicle.getSmoothedVehicleCarsAndPositions(millisElapsed)   // RenderVehicles.java:73
   └─ 每节车 PositionAndRotation（由两个转向架位置平均+yaw+pitch 反推）  // render/PositionAndRotation.java:28-60
      ├─ 每个转向架：queueBogie / iterateBogieModels            // :130-138
      └─ 车体：storedMatrixTransformations → model.render(...)  // :261-275
```

变换在 `render/StoredMatrixTransformations.java`：

```java
transform(graphicsHolder, offset):                       // :46-52
  push()
  if (useDefaultOffset) translate(x - offset.x, y - offset.y, z - offset.z)   // ★ 世界坐标 − 相机
  ...stored transforms...
```

再叠一个**固定的 180° 翻转**（`RenderVehicles.java:466-470`）：

```java
rotateYRadians(yaw + π)
rotateXRadians(pitch + π)
rotateZDegrees(oscillationAmount)      // 车体摇摆
```

- `Ry(yaw+π)·Rx(pitch+π) ≡ Rz(π)`，即 `(x,y,z) → (−x, −y, z)`：**绕 Z 翻 180°**。
- **推断（两侧独立证据）**：引擎内部的模型/模块空间是 **y 朝下、z 反序**（= 建模空间的 `(x, −y, −z)`），
  所以世界侧要再翻一次把它掰正。
  - 证据 A：`notes/213` 实测 —— 锚点 JSON 里 `seat.up=[0,1,0]` 是"上"，而模块空间读到 `[0,-1,0]`；
    `Plane.of` 用 `toModelSpace(x,-y,-z)`；日志里 `plane.position = (0.606, −3.02, 8.986)` 与存储值反号。
  - 证据 B：本文件的 `Rz(π)`（源码直读）。
  - **对建模者的结论**：不要试图在 Blender 里"预先翻过来"。按 §4 的实测口径建，剩下的由引擎负责。

### 骑乘时的抖动抑制

乘车时车辆位置与玩家位置不同步 → 抖动。MTR 用 `getRenderPositionAndRotation()`（`RenderVehicles.java:422-446`）
把整列车改成**相对被乘那节车**渲染，并叠 `cameraShakeOffset`。这是"能不能骑"与"渲染像不像"的分界点。

## 4. 模型空间的实测口径（建模者唯一要知道的事）

实测两辆**游戏内显示正常**的车（直接解析源 OBJ 的 `v` 行）：

| 模型 | X（宽） | Y（高） | Z（长） |
|---|---|---|---|
| `saf420cab.obj` | −1.475 .. 1.475（**2.950**） | **0.000 .. 3.800** | −9.806 .. 9.750（19.556） |
| `saf420car.obj` | −1.475 .. 1.475（**2.950**） | **0.000 .. 3.800** | −8.475 .. 8.475（16.950） |
| 对应 `mtr_custom_resources.json` | `width: 2.95` | — | `length: 19.5 / 16.95`（含缓冲） |

⇒ **MTR 的 OBJ 口径（已实测，不是猜）**：

- **1 单位 = 1 格 = 1 米**（资源包 JSON 里的 `length`/`width` 就是同一把尺子）；
- **X = 车宽（±半宽居中）**；
- **Y = 高度，`y = 0` 在轨面**（不是车底！车底起于某个正 y）；
- **Z = 车长，绕 0 居中**（±半长）；
- **车头永远朝 −Z**；导出轴向按 `notes/192` 的口径（Blender 自身口径 `forward_axis="Y", up_axis="Z"` = 恒等转换）。

对照 `notes/192`：BR101 当年"看不见"就是因为它是"长度沿 Y、高度沿 Z"（在 Blender 里立着），
绝对数值完全正确、关系完全错 —— 所以**判据是包围盒的三个区间，不是"模型加载成功"**。

## 5. 部件（part）：组名 → 渲染阶段 → 画法

### 5.1 组名就是 API

OBJ 的 `g <name>` / bbmodel 的分组名 → `nameToObjModels: Map<String, ObjModel>`（`resource/ModelPropertiesPart.java`、`render/DynamicVehicleModel.java:72-83`）。
`properties_<id>.json` 的 `parts[].names[]` 把组名**逐字**认领；没被任何 part 认领的组**不会被画**。
（`ModelProperties.addPartsIfEmpty`：`parts` 为空时才给每个组自动补一条。）

BR101 / SAF420 的现役 properties（实测导出）长这样：

```
body        EXTERIOR                interior        INTERIOR_TRANSLUCENT
door_l_1..6 / door_r_1..6  EXTERIOR   floor / doorway_*  （TYPE，不是 stage）
wiper_1_1 / wiperarm_1_1 / wiperrod_*   EXTERIOR
```

### 5.2 `renderStage` 的**全部**取值与它们的真实语义

`resource/RenderStage.java:5-16` —— 枚举本身只有 5 个值，各带一个 `OptimizedModel.ShaderType`：

| renderStage | ShaderType | 直绘时的层（on route） | 光照 | 备注 |
|---|---|---|---|---|
| `EXTERIOR` | `CUTOUT` | `EXTERIOR` | 世界光照 | 默认 |
| `LIGHT` | `CUTOUT_GLOWING` | `LIGHT` | **恒亮** | **只在 `vehicle.getIsOnRoute()` 时生效** |
| `ALWAYS_ON_LIGHT` | `TRANSLUCENT_GLOWING` | `LIGHT_2` | **恒亮** | **不受 on-route 影响**，永远亮 |
| `INTERIOR` | `CUTOUT_BRIGHT` | `INTERIOR` | 全亮（MAX_LIGHT_INTERIOR） | 只在 on route 时 |
| `INTERIOR_TRANSLUCENT` | `TRANSLUCENT_BRIGHT` | on route → `INTERIOR_TRANSLUCENT`；**不在线上 → `EXTERIOR_TRANSLUCENT` + 世界光照** | 全亮 / 世界光 | 见 `ModelPropertiesPart.java:711-732` |

★★ **`ModelPropertiesPart.getRenderProperties()` 是这块的权威**（`:711-732`）：

```java
if (renderStage == ALWAYS_ON_LIGHT) → (LIGHT_2, 恒亮)
else if (vehicle != null) {
    if (vehicle.getIsOnRoute()) {
        LIGHT                 → (LIGHT, 恒亮)
        INTERIOR              → (INTERIOR, 全亮)
        INTERIOR_TRANSLUCENT  → (INTERIOR_TRANSLUCENT, 全亮)
    } else {
        INTERIOR_TRANSLUCENT  → (EXTERIOR_TRANSLUCENT, 世界光照)
    }
}
→ 其余全部 (EXTERIOR, 世界光照)
```

**非显然的后果**：车停在**车场/没在交路上**时，`LIGHT` / `INTERIOR` 全部**降级成普通外皮**——
"车灯只有跑起来才亮"。想让灯永远亮，必须用 `ALWAYS_ON_LIGHT`。

### 5.3 ★ 第二条通道：**MTL 材质名**也能定渲染阶段（反汇编得到）

`org.mtr.mapping.render.obj.ObjModelLoader.legacyMapping(String)`（mappings jar 反汇编）
把 **`.mtl` 里的材质名**（小写后精确匹配）映射成 ShaderType：

| MTL `newmtl` 名 | ShaderType |
|---|---|
| `light` | `CUTOUT_GLOWING`（= LIGHT） |
| `always_on_light` | `TRANSLUCENT_GLOWING`（= ALWAYS_ON_LIGHT） |
| `lighttranslucent` | `TRANSLUCENT_GLOWING` |
| `interior` | `CUTOUT_BRIGHT`（= INTERIOR） |
| `interior_translucent` / `interiortranslucent` | `TRANSLUCENT_BRIGHT`（= INTERIOR_TRANSLUCENT） |
| `exteriortranslucent` | `TRANSLUCENT` |
| 其他任何名字 | `CUTOUT`（= EXTERIOR） |

而 `properties.json` 的 `renderStage` 在建模入缓存时会**覆盖**它：
`ModelPropertiesPart.addObjModelPosition()` → `objModel.addTransformation(renderStage.shaderType, …)`（`:616-627`），
`ObjModel.addTransformation` 的实现是**克隆 RawMesh 并换成传入的 ShaderType**（反汇编 `OptimizedModel$ObjModel.lambda$addTransformation$4`）。

⇒ **优先级：`properties.json` 的 `renderStage` > MTL 材质名 > CUTOUT。**
⇒ 反过来也用得上：**没写进 properties 的组不会显示**，但如果哪天要临时试效果，改 MTL 名字比改 JSON 快。

### 5.4 部件类型 `type`

`resource/PartType.java`：`NORMAL / DISPLAY / FLOOR / DOORWAY / SEAT`。

- `NORMAL`：走 §5.2 的渲染阶段；
- `DISPLAY`：**不画模型**，改画 MTR 自己生成的显示屏（`ModelPropertiesPart.render` `case DISPLAY`，`:242-256`）——
  线路色块 / 七段码 / 滚动文字 / 静态文字，全部走 `LIGHT_2`（自发光）；
- `FLOOR` / `DOORWAY`：**不是"画什么"而是"玩家能站哪儿/从哪儿上车"**，MTR 按门叶包围盒与下沿**自动生成**，不要手工建模
  （`notes/199`：MTR 给 OBJ 车不建地板盒，所以上下车靠这两样）；
- `SEAT`：座位眼位。

### 5.5 条件 `condition` 与门动画

- `PartCondition`（`resource/PartCondition.java`）**全部 10 个值**：
  `NORMAL, AT_DEPOT, ON_ROUTE_FORWARDS, ON_ROUTE_BACKWARDS, DOORS_CLOSED, DOORS_OPENED, CHRISTMAS_LIGHT_RED/YELLOW/GREEN/BLUE`。
  判定入口 `VehicleResource.matchesCondition(vehicle, condition, doorsClosed)`（`ModelPropertiesPart.java:232`）。
- **车门**：`isDoor()` 的判据是 `doorXMultiplier != 0 || doorZMultiplier != 0`（`:334-336`），
  动画类型 `doorAnimationType`（`STANDARD/PLUG/...`）；门叶**按 part 独立移动**。
- **隐藏一个 part 的手法很土**：把它的 y（或 x/z）写成 `Integer.MAX_VALUE` 把它推到天边（`renderNormal` `:363`、`:398-399`）。
  所以"某个部件莫名其妙不见了"要往这里找。
- 还有 `flashOnTime/flashOffTime`（闪烁，用于圣诞灯之类）。

### 5.6 单位：part 的位置是"像素"（1 格 = 16）

`addCube` / `addObjModelPosition` 里 **`x/16, y/16, z/16`**（`:611`、`:623`），
`modelYOffset` 是以**格**为单位、在 y 上被减掉。这与 Blockbench 的 1/16 网格一致。

### 5.7 一个组 = 多个实例：`positionDefinitions`

`definition_<id>.json` 声明若干 `positionDefinitions`（现役车都只有一条 `p0`，内容为空 `{}`）：

```json
{ "positionDefinitions": [ { "name": "p0", "positions": [ {} ], "positionsFlipped": [] } ] }
```

每条 definition 是一串 `positions` + `positionsFlipped`；part 用 `positionDefinitions: ["p0"]` 引用它。
`iteratePositions()`（`ModelPropertiesPart.java:741-744`）会把 `positionsFlipped` 的 x **取负**
并置 `flipped`，然后**给每个位置各生成一份几何拷贝**（`addObjModelPosition` → `ObjModel.addTransformation`）。

⇒ **同一段几何可以复用到多个位置（含镜像）而不用在 Blender 里复制**——这是"6 扇门只建 1 扇"的正规做法，
代价是包内几何按份数膨胀（BR101/SAF420 的包内 OBJ 都比源大 3 倍左右）。

### 5.8 bbmodel 才有的东西：组的 pivots

`resource/GroupTransformations.java` 把 bbmodel 的**组原点与组旋转**（`origin`/`rotation`，见 `:19-25`）
变成矩阵栈上的多层 `translate + rotateZ → rotateY → rotateX`（`:51-65`）。
**OBJ 没有组层级 ⇒ 这条路对 OBJ 车不成立**（OBJ 的组是平的，没有 pivot）。

### 5.9 JSON 里**没有**"随时间的动画"

翻遍 `properties` / `definition` 的字段，能产生"随时间变化"的只有三样：
**门动画**（`doorXMultiplier/doorZMultiplier/doorAnimationType`）、
**闪烁**（`flashOnTime/flashOffTime`，`:360`）、
**显示屏文字/滚动**（`DisplayType` + `DisplayOption`）。
其余（受电弓、风扇、踏板、雨刷…）**必须写代码**——见 §10 的 E3/E4。

## 6. 两条渲染路径：优化器（默认开）与直绘

`OptimizedRenderer.hasOptimizedRendering()`（客户端设置）决定走哪条：

```java
// ModelPropertiesPart.render()  :231-241
final renderProperties = getRenderProperties(renderStage, light, vehicle);
if (hasOptimizedRendering()) {
    scheduleRender(QueuedRenderLayer.TEXT, () -> renderNormal(..., renderProperties, ...));  // ★ TEXT 层，不建 consumer
} else {
    scheduleRender(texture, false, renderProperties.left(), () -> renderNormal(...));         // 直绘到你该在的层
}
```

- **优化器打开（默认）**：`NORMAL` 部件全部排进 `TEXT` 层（该层在 `MainRenderer` 的 switch 里**没有对应 RenderLayer**，见 `:179-182`），
  回调里再 `CustomResourceLoader.OPTIMIZED_RENDERER_WRAPPER.queue(...)` 塞进批处理；
  **整批在 `MainRenderer.render` 的最后一行才倒出**（`:191`）。
  ⇒ **一旦开了优化器，§2 那张层序表对 `NORMAL` 部件就失效了**，实际绘制顺序由优化器内部按 ShaderType 决定。
- **优化器关闭**：部件真的画在它自己的层上，层序完全按 §2。
- **优化器不能吃的部件**（必须排除，否则静默不画）：
  - 会动的部件。MMTR 的实证：`ModelPropertiesPart.java:402-415`
    > "机制件（wiper_ / wiperarm_ / wiperrod_）由自己的运动学逐件移动，**不能**被优化分支接管：
    > 那一支只会重画 `optimizedModelDoor`，对一个非门部件就是**什么都不画**。"
  - 关闭路径下 geometry 从 `partDetails.modelParts`（bbmodel）或 `optimizedModelDoor`（OBJ）取；

★★ **关键推论：OBJ 车实际上被锁死在优化器上**（读代码得出，与谱系的"横向教训：'优化渲染开着'是默认前提"一致）：

- OBJ 路径的 `partDetails.modelParts` **永远是空的**（`ModelPropertiesPart.java:225` 写死 `new ObjectArrayList<>()`）；
- 它的几何只在 `optimizedModelDoor` 里，而 `OptimizedModelWrapper.fromObjModels()` 在
  `!hasOptimizedRendering()` 时返回**内层为 null 的壳**（`OptimizedModelWrapper.java:28-30`），
  `OPTIMIZED_RENDERER_WRAPPER.queue()` 又判 `optimizedModel != null`（`OptimizedRendererWrapper.java:30-34`）；
- ⇒ **关掉优化渲染，OBJ 车一节都画不出来**（门和机制件也一样）。

所以：**`getRenderProperties()` 那张"renderStage → QueuedRenderLayer"的表主要服务于 bbmodel/直绘路径；
OBJ 车的明暗与发光是靠建缓存时就烘进网格的 `ShaderType` 实现的**（见 §5.3）。
两套东西同名不同路，别混着推理。

- 优化器的纹理走 **`AtlasManager`**（`OptimizedModel` 静态字段 `ATLAS_MANAGER`，反汇编），
  所以**贴图会被拼进图集**——这与"`upload()` 是 `glTexSubImage2D`，不能改尺寸"（工作流 §1.3②）是同一条约束的两面。

## 7. 模型加载与 OBJ 的两条硬假设

### 7.1 支持格式与入口

`ModelResourceLoader.isSupportedModelResource()`：`.obj` / `.mqo` / `.mqoz`（MQO 先转 OBJ，`MqoModelConverter`）。
另有 bbmodel / Minecraft json 走 `DynamicVehicleModel` 的另一条构造器。**MMTR 的火车全部走 OBJ。**

### 7.2 贴图从 `.mtl` 来，不从 JSON 来（这条很容易搞错）

`ModelResourceLoader.loadModel()`（`:37-53`）把两个 resolver 交给 `ObjModel.loadModel`：

```java
mtlString     -> 读同目录同名 .mtl                                     // :43-47
textureString -> 空 ? WHITE_TEXTURE
               : "default.png" ? vehicleJson.textureResource
               : 同目录同名 .png    (CustomResourceTools.getResourceFromSamePath)  // :48
```

⇒ **OBJ 车的贴图由 MTL 的 `map_Kd` 决定**；`mtr_custom_resources.json` 里的 `textureResource`
**只在 MTL 写 `default.png` 时才用得上**。打包器把它硬编码成 `minecraft:textures/misc/white.png`
（`mmtr/tools/obj-mtr-packager/pack_vehicle.js:1771`）是**无害的**，真正生效的是 MTL。
⇒ 反过来说：**一个模型可以有多种材质 → 多张贴图**（`OptimizedModel.MaterialGroup(shaderType, texture)`，
`resource/OptimizedModelWrapper.java:54-70`），这是"分区贴图"的正规入口。

### 7.3 ObjModelLoader 的两条硬假设（`notes/194` 反汇编，仍然是当前最大的静默坑）

| # | MTR 的读法 | Blender 的默认导出 | 后果 |
|---|---|---|---|
| ① | **第 i 个顶点配第 i 个 `vt` / 第 i 个 `vn`**（面里的 `v/vt/vn` 三元组**从来不读**） | 顶点共享、`vt`/`vn` 各自独立索引空间 | 第 `#vt` 号之后的顶点 UV 全变 `(0,0)`；之前的拿到别人的 UV |
| ② | **每个面只读前 3 个角** | 四边形/多边形原样保留 | 四边形丢第 4 角，n 边形变乱三角 |

⇒ 打包器的 `toMtrObj()` 负责"去焊接 + 耳切三角化"，产出 `#v == #vt == #vn`、全 `f i/i/i`、全三角形；
`verify_mtr_obj.js` 是唯一的离线判据（L1 布局 / L2 配对 / L3 面积 / L4 包围盒）。
**实测 SAF420 与 BR101 的包内 OBJ 都满足**（例：BR101 v=vt=vn=36105，f=19500 全三角）。

### 7.4 另外三个静默开关

- `flipTextureV`：MTR 公式 `v = flip ? 1 - vt.y : vt.y`。Blender 导出 v 向上、MC 贴图 v 向下
  ⇒ **Blender 模型必须 `true`**（`notes/194` §2.3）。
- `untexturedUv`：MTR **永远**给每个顶点取一个 UV，"没有 UV"不存在。没 UV 的角默认采 **(0,0)**，
  打包器用这个字段把它们指到指定纹素（`vehicle.br101.json:19-22`）。
- **文件名全小写**：MTR 路径整体转小写，找不到就静默读空串（`obj=0 chars`）。

### 7.5 图集（AtlasManager）什么时候才参与

`OptimizedModel` 持有静态 `ATLAS_MANAGER`（反汇编）；`AtlasManager` 的 API 是
`load(Identifier)` / `applyToMesh(RawMesh)` / `clear()`，内部有 `sprites` 与 **`noAtlasList`** 两张表，
`load` 走 Gson 读 JSON —— 这是一套**"引用 Minecraft 方块贴图 / 精灵图"时才用的图集**机制。
**资源包自带的车辆 PNG 不进图集、按原分辨率直接用**（实测 `saf420.png` 128×128 就是这么用的）。
⇒ 换涂装贴图时尺寸可以自由选（128/256/512 都行），只要 UV 匹配；
真正不能改尺寸的是**运行时生成的那些面板贴图**（`MmtrPanelTexture`，工作流 §1.3②）。

## 9. 现状：车体"素"在哪里（美化空间在哪）

实测现役两包（`mmtr/game/fabric/run/resourcepacks/SAF420_v4.zip`、`BR101_v54.zip`）。
**下面是量出来的数，不是印象**：

| 项 | 实测 | 含义 |
|---|---|---|
| `saf420.png` | 128×128，**419 B**，内容=**4 条纯色竖条**（米白 / 深灰 / 浅灰 / 白） | 这是一张**色板**，不是涂装图 |
| 源 `saf420cab.obj` | `v=11278` 但 **`vt=22`（只有 4 个不同纹素）**、`vn=2756`、`f=12965`、组名用 **`o`** 不是 `g` | 整车**只采 5 个点** ⇒ 视觉上就是 5 块平色 |
| 包内 `saf420cab.obj`（打包器处理后） | `v=vt=vn=32019`、`f i/i/i` 全三角、**distinct vt = 5** | 布局已合规（§7.3），**但仍是 5 个平色** |
| MTL | `newmtl saf420_mat`（`map_Kd saf420.png`）+ `newmtl door_mat`（**没有任何 `map_Kd`**） | `saf420_mat` 是唯一被 `usemtl` 引用的材质；`door_mat` 是空壳 |
| renderStage 使用 | 只有 `EXTERIOR` 与 `INTERIOR_TRANSLUCENT` | **没有任何车灯 / 内装亮面 / 显示屏** |
| 动态件 | 只有雨刷（`wiper*`，走 MMTR 的自绘通道） | |
| 细节表达 | 全靠**几何**（门缝、窗框、把手都做成真凹凸），贴图不承担任何细节 | 所以远景/近景都"塑料感" |

> BR101 侧同理：`br101.png` 是 256×256 色板条（左上角还留着 "SAF" 字样），模型 UV 的 v 只落在 `0.546875..1`。
> **两辆车都是"几何很讲究、涂装几乎是空的"。**

⇒ 可美化的方向（按"投入产出比"排）：

1. **真贴图 + 真 UV**（零几何风险，收益最大）：`map_Kd` 换成真正的涂装图 —— 分色腰线、车窗黑边、
   门缝阴影、雨渍、车顶设备、铭牌字号；配合 **AO 烘焙**（把环境遮蔽烘进贴图）能立刻消掉"塑料感"。
   注意 `flipTextureV: true`、`untexturedUv`、以及 §7.3 的 v/vt/vn 配对。
2. **分区材质**：按 MTL 多材质 + properties 的 `renderStage` 把玻璃、灯罩、金属件分开 ⇒ 真正的透明玻璃与**自发光的车灯**
   （`ALWAYS_ON_LIGHT` 保证停车也亮）。
3. **显示屏**（`type: DISPLAY`）：目的地牌 / 车次 / 七段码，MTR 自己会画，零建模。
4. **条件件**（`condition`）：`AT_DEPOT` / `DOORS_OPENED` / 圣诞灯 —— 免费的"分状态外观"。
5. **mod 侧自绘**（`mmtr_*` 锚点 + `scheduleRender`）：动态面（雨、雪、刹车屑）、随速度变化的受电弓/风挡、
   自定义发光 bloom 近似等。**成本最高、但天花板也最高**；先照抄 `MmtrWindshield` 的骨架。
