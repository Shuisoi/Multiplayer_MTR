# 375 · 换端之后"车不动、过一会儿瞬移" —— 腿表没有唯一来源（增量表达不了"整表反序"）

日期：2026-10-03 · 承接：**notes/369**（运动流 ① 与腿阴影增量 S3b）· 代码：
`MmtrMotionFrame.java`、`MmtrVehicleMotionSync.java`、`MmtrVehicleMotionClient.java`、`MmtrLegAppender.java`、
`VehicleExtraData.java`、`VehicleExtension.java`、`Client.java`、`Vehicle.java`、`MmtrMotionPosition.java`、
`MmtrConsistWalker.java`

**用户口径（原话）**：

> 「目前客户端内显示**其他列车**的行为不对，例如当前**岩壁站换端从另一边出发，直接不动并瞬移**，
> 我认为是**缺少唯一来源并加了一些判断**导致的」

**一句话结论**：客户端手上的**腿表**（摆车用的几何：车尾 → 车头的轨序列 + 累计里程）与**位置**
（`railProgress`）走了两条独立的路 —— 位置每 100 ms 由 ① 送来、只增不减；而几何只在"服务端新踏上一根轨"
时以**增量**形式来。换端是"同一批轨、相反顺序"，**增量协议在数学上表达不了它**，而 ② 那条唯一能整表重建
的路对"已经持有镜像的客户端"**一个字节都不发**（见 §2.4）。于是几何停在旧坐标系、位置继续往前跑，
渲染侧（`VehicleExtension#getSmoothedVehicleCarsAndPositions`）每帧把车**夹回阴影末端** ⇒ 画面上的车
**不动**；直到镜像被删掉再重建（几十秒后）才**瞬移**到位。

## 1. 现场与证据（修前，15:50–16:24 那一场）

客户端 `[MMTR-MOTION]` 那行里的 `阴影越界=N次/Xm` 是这一层的温度计（"车头走到了阴影（上一次刷新时车头位置）
之外多少"）。把 981 个 5 秒窗口按"越界是否 > 0"分段：

| 状态 | 时间 | 长度 | 窗口内最大越界 |
|---|---|---|---|
| 正常 | 15:51:34 → 15:52:58 | 77 窗 | 0 |
| **越界** | 16:18:36 → 16:19:35 | 43 窗 | **824.67 m** |
| 正常 | 16:19:36 → 16:20:36 | 55 窗 | 0 |
| **越界** | 16:20:37 → 16:21:35 | 42 窗 | **824.22 m** |
| 正常 | 16:21:36 → 16:22:36 | 55 窗 | 0 |
| **越界** | 16:22:37 → 16:23:21 | 43 窗 | **824.53 m** |

（合计 218/981 个窗口越界。824 m ≈ 23 m/s × 36 s —— 也就是"从发车起一直被夹着"。）

四条互相咬合的证据：

1. **每段都从"换端后自臂发车"那一刻开始**：段首的 `[MMTR-DRV]` 是
   `motion auto run enabled` + `motion mission PASSENGER self-armed to rail … stop @44187m`，
   而前一段是"到站停稳"。用户报的"岩壁站换端从另一边出发"正是这个时刻。
2. **段内腿记录几乎全是拒绝**：`腿记录=1（接=0 丢=0 … 整表=1 接不上=0）`、`（接=0 … 接不上=1）`
   —— 成功接上的次数（`接=`）在整段里是 0。阴影一次都没延长。
3. **② 全程没有整份快照**：`[MMTR-CL] 车辆包：整份=0 补丁=1 … 字节=485`，每秒钟一行，
   50 秒里 `整份` 一直是 0。唯一能"重建镜像 = 重建腿表"的路没走。
4. **修好的那一刻正是镜像被删掉再回来**：段末 `[MMTR-DBG] world render running, client vehicles=0`
   （这一拍它不在任何一张表里 ⇒ 客户端删镜像），随后 `整份=1` 重建 ⇒ `阴影越界=0`。
   用户看到的"停住 → 突然出现在远处"就是这两拍。

## 2. 五个具体的坑（都能从代码/字节码读出来，不是猜）

### 2.1 增量判定比的是**规范化 hex**，而 hex 里没有方向

`MmtrMotionFrame.legDelta(previous, current)` 的判据是"旧表的**后缀** == 新表的**前缀**"。而 v1 线上传的
是**规范化** hex（两端按坐标排序，因为那是客户端 `railIdMap` 的键）—— 同一根轨的两个方向**长得一模一样**。

换端时表反序：旧 `[r1→, r2→, r3→]`、新 `[r3←, r2←, r1←]`。按 hex 比：`keep=1`（旧后缀 `[r3]` == 新前缀 `[r3]`）
⇒ 算出"**丢 2 根、车头再接 2 根**"，客户端于是按增量接出一张**方向错的表**。（修前的日志里，
`接不上` 与 `整表` 两个计数交替出现，正是"有时丢成功、有时丢不动"的两种落地形态。）

### 2.2 落地不是原子的：先丢后接

`MmtrLegAppender.apply` 原来是"先把车尾端该丢的丢了，再试着往车头接"，接不上时**已经丢掉了**。
换端那一拍丢得动、一根都接不上 ⇒ 手上剩下一张**残表**（极端时只剩车头那一根）。
残表的末端里程远在车后面 ⇒ 渲染侧每帧夹车 ⇒ **车不动**。

### 2.3 v1 的 SLOT 首帧把**整张表**当"增量"发

`writeVehicle` 的建槽那一支发的是 `writer.legs(slot, 0, 整张表)`。客户端的增量判据要求"新腿接在现有表的
**末端**"，而整张表的**第一根**是车尾那根 ⇒ 接入端永远对不上 ⇒ 镜像刚建起来的第一拍就被拒
（修前 15:51:01 那一行 `腿记录=1 … 接不上=1` 就是它）。于是从会话一开始，腿表就再也没能靠 ① 延长过。

### 2.4 ② 的 `patch == null` 被静默吞掉（唯一能整表重建的路）

`VehicleSyncPatch#patchOf` 的契约是：**`null` = 这一份与上次差的不只是动态字段**（换交路、改编组、
**path 换了**）或"到了 30 秒强制兜底"，两种都要求客户端**重建镜像**。而 `Client#update` 原来只在
"客户端还没有这辆车"时才走整份：

```java
if (patch != null && patch.size() > 0 && clientAlreadyHasIt) { …补丁… }
else if (!clientAlreadyHasIt) { …整份… }
else { /* 标脏了但一份都不差 ⇒ 保活 */ }   // ← patch == null 也会掉到这里
```

于是"客户端已持有 + 静态字段变了" ⇒ **一个字节都不发**，连那句"每 30 秒强制整份"的兜底也一起失效。
现场表现就是 §1 第 3 条：50 秒里 `整份=0`。

### 2.5 丢腿判定喂的是客户端**自己的** `railProgress`

`mmtrApplyLegDeltaFromSync` 把 `getRailProgress() - 车长` 当 `tailDistanceM` 交给原子性检查。
位置一旦跑飞（阴影没延长 ⇒ 位置超出去），这个数就跟着跑飞，于是"这根腿还在车身底下、不许丢"
的保护**反过来失效**：该留的留不住、该丢的丢不成 —— 一个自持的正反馈。

### 2.6 ② 重建镜像之后 ① 还按旧基准发增量（"两条腿各记一本账"）

客户端的腿表有两个来源：② 的整份快照（重建镜像时）与 ① 的 {@code LEGS}。而 ① 的"上次发出去的
腿表"记在**服务端自己的** {@code SentState.legs} 里。只要 ② 在中间重建过一次镜像，两本账就可能不同源
（② 那一份是序列化那一刻的表，① 那本账是它上一次发出去的表）—— 之后每一个增量都在客户端"接不上"，
被原子地拒绝 ⇒ 几何又停在旧值上，只能等下一次整表（20 秒兜底或表形一变）。

修后第一次实测（17:03–17:06）就抓到了这一支：`接不上=1` 每隔一分钟上下出现一次。

### 2.7 ★ ② 把运动车的**腿表**当"静态字段"（修 §2.4 之后才炸出来的那个）

走行体每"踏上一根新轨 / 掉一根尾轨"就重写 `vehicleExtraData.path`（`refreshMmtrMotionLegs`），
而 `path` **不在** `VehicleSyncPatch.DYNAMIC_KEYS` 里 ⇒ 那一拍被判成"**静态字段变了**"：

* 修 §2.4 之前：这些整份对"已经持有镜像的客户端"根本没发出去 —— 这正是 §1 第 3 条
  （50 秒里 `整份=0`）的**机制**，也是"换端后车不动"的另一半原因；
* 修 §2.4 之后（17:0x 实测）：它们**真的发出去了** —— 客户端日志里
  `车辆包：整份=1 补丁=0 … 字节=7616` 每 1.5–6 秒一次（每次新踏上一根腿）：
  一列 7.6 KB 的整份快照，而它带的九成是与 ① 重复的腿表。8 辆车在场时 ≈ **30 KB/s** 白花，
  并且每次重建镜像都会让 ① 再补一张整表（实测 `腿记录=17（整表=17）`/秒）。

这条是**读数抓出来的**：如果只看"车不动"有没有好（`阴影越界=0`），它会被当成修好了。

## 3. 修法：腿表只有一个来源 —— 服务端那张表 + 它的锚点 + 逐腿方向

### 3.1 线格式 v2（`MmtrMotionFrame.VERSION = 2`）

```
kind 0x08 LEGS   slot(u16) droppedFromTrainTail(u16) anchorM(f32) count(u8)
                 [hexLength(u8) hexBytes]×count          ← 规范化 hex（查轨表用）
                 [entryIsOrdered1 位, ceil(count/8) B]   ← 方向位（v1 缺的那一半）
```

* `droppedFromTrainTail = 0xFFFF`（`LEGS_FULL_REPLACE`）= **整表替换**，不是"丢 65535 根"。
* `anchorM` = 这张表在**镜像里程坐标系**里的起点（= 第一根腿的 `startDistance`，引擎那边就是
  `MmtrConsistWalker.mirrorPathAnchorM() = distanceM - mirrorHeadArcM()`）。**整表重建全靠它** ——
  少了它，客户端重建出来的表与镜像 `railProgress` 差一个常量，那正是"车停在阴影末端不动"。
* 方向位 = `!PathData.reversePositions`：规范化顺序的第一端就是接入端。客户端于是**照抄**接入端，
  不再"拿上一根腿的末端去猜"。
* 代价：一条腿 101 + 1 + 1/8 ≈ **108 字节**（原来 107）；整表 6 根腿 ≈ 660 B，只在**表形变了**与
  **20 秒兜底**时发 ⇒ 约 33 B/s/车。

### 3.2 判定改成方向敏感 ⇒ 换端必然走整表

`legDelta` 现在比的是 `Leg(hexId, entryIsOrdered1)` —— "同一根轨、相反方向"是**不同的腿**。
换端时 `keep=0` ⇒ `replacesWholeTable()` ⇒ 服务端发**整表 + 锚点**（`MmtrVehicleMotionSync`）。
`MmtrMotionFrameTests#changeEndsIsAFullReplaceNotAnAppend` 把这条钉死。

### 3.3 客户端：整表按锚点重建，增量**先验证后落表**

* `MmtrLegAppender.replaceWholeTable`：逐腿按方向位构造 `(entry, exit)`，要求相邻两腿首尾相接
  （断链 ⇒ 整张表原样不动），里程用 `generatePathDataDistances(rebuilt, anchorM)` ⇒ 与服务端逐字段一致。
* 增量：**先在临时表里把整段新腿接完**，一根接不上就 `DISCONTINUOUS`/`UNKNOWN_RAIL` 返回、
  **连该丢的尾巴也不丢**（原子）。车头那一根永远留着（它是"车头在哪根轨上"的唯一判据）。
* 空表（`EMPTY_TABLE`）不动旧表：清空 = 每节车都找不到落点。
* **不再从"要丢的比手上还多"这种数上猜整表**：那只说明"手上这张表与服务的不同源"，
  而那时服务端给的只是它那张表的**后半段**，配上整张表的锚点会整体偏掉。这种情形一律拒绝＋等整表。

### 3.4 首帧也发整表

建槽那一支改发 `LEGS_FULL_REPLACE`（§2.3）。镜像是后建的也没关系 —— 下一拍那张整表 / 20 秒兜底会补上。

### 3.5 ② 的契约修回来

`Client#update` 现在第一支就是 `patch == null ⇒ 排队一份整份快照`（`ClientVehicleSyncTests` 里新增用例钉住：
"已持有 + 静态变了"必须发整份）。空补丁（`size() == 0`）仍然是"没东西要发"。

### 3.6 读数（这次真正缺的东西）

* 客户端 5 秒行：`腿记录=N（接= 丢= 整表= 无基准= 空表= 缺轨= 接不上=）` ——
  `整表` 是"整表重建成功"的次数（换端就靠它），另外四类拒绝任何一个持续增长都是一个红证。
  注意 `接/丢` 只统计**增量**（整表替换的数量级完全不同，混在一起那对数就没意义了）。
* 服务端 5 秒行：`腿整表=N（形状变了/定时兜底）`。
* **客户端会自己喊"腿表跟不上"**（`MmtrVehicleMotionClient#noteShadowOverrun`）：连续越界超过 5 秒，
  每 5 秒一行 warning，带车辆 id 与最大越界量；恢复时一行 info"腿表已跟上"。
  这一条就是"车不动"再也不会只留下一堆计数的那道保险。

### 3.7 谁让客户端的镜像重建，谁就让 ① 重新对齐（§2.6 的修法）

`Client` 记下"上一拍整份快照发出去的那些车"（`lastFullUpdateVehicleIds`，在 `processVehicles` 里
从 `vehicleUpdates` 取），暴露 `tookFullVehicleUpdate(vehicleId)`；① 每秒 10 次地问这一句，
是的话**立刻发整表 + 锚点**（把 ① 的账本重新锚到客户端手上那张表上）。

顺序上这是严丝合缝的：② 在模拟线程里发整份 → ① 跑在 `END_SERVER_TICK`（同一 tick、在它之后），
两条包在同一条连接上**有序** ⇒ 客户端先重建镜像、再收到那张整表。

### 3.8 渲染夹紧的容差 0.75 m → 2.0 m（把"正常瞬态"和"真病"分开）

腿表是 10 Hz + 单程延迟，车头压过一根轨的接头时"新腿那一拍"最多晚 ~100 ms ⇒ 60 km/h 下约 **1.1 m**。
0.75 m 的容差把这种**正常瞬态**也夹住（画面上是接头处那一小下，而且它会让 `阴影越界` 这个读数
永远不是 0，把它当红证用就不灵了）。2.0 m 让它自然外推过去；而它要防的那种病（阴影几十秒不更新）
是**几米到几十米**（实测 824 m）量级，那道闸一点没松。

### 3.9 运动车的腿表**不进 ②**（§2.7 的修法：几何只有一个来源）

`Vehicle#mmtrBuildSyncPayload` 对走行体把 `path` 从 `data` 段里**摘掉**（连"上一次发出去的基准"
一起摘，所以它不再参与静态/动态的判定）。于是：

* 每踏上一根腿不再触发一份 7.6 KB 整份；
* 客户端的几何**只剩 ① 一个来源** —— 镜像刚建起来那一拍，① 在**同一个 tick**
  （`END_SERVER_TICK`，包排在 ② 之后）就把整表送来（靠 §3.7 的 `tookFullVehicleUpdate`），
  所以 ② 一个字节的 path 都不必带；
* 遗留（烘焙路径）的车辆照旧：它们的 path 是静态数据，靠整份快照送。

### 3.10 客户端被拒的腿表**本地重试**（`缺轨` 不用等 20 秒）

被拒的原因里只有 `缺轨`（本地轨表还没收到那根轨）是**等一等就会自愈**的。客户端把最新那条
被拒记录留 ≤1.2 秒，每收到一帧（10 Hz）重试一次，最多 12 次；成功即落地，超时即放弃。
**过期的表绝不用来重建**：整表带的锚点是"那一刻的里程"，隔久了重建出来的是一张落后的几何 ——
那正好会制造阴影越界。这样"缺轨"的代价从"最长 20 秒被夹"降到"≤0.1 秒"，而且不花一个字节。

### 3.11 定时兜底 20 s → 60 s（可调）

`-Dmmtr.motion.legs.fullSeconds=`（默认 60，0 = 关）：一张表 ~660 B ⇒ 约 11 B/s/车。
`缺轨` 已被 §3.10 治掉、② 重建已被 §3.7 治掉，剩下的只有"没想到的不同源"，60 秒足够把它拉回来。

第四轮是**用户在游戏里自己看着确认的**（原话「OK了 我游戏里看着差不多了」）：站台上有车进站、
换端、再开出去，画面里没有"停住再瞬移"，读数也一次夹车都没有。这一列就是"修好了"的样子：
**一次夹车都没有、几乎没有拒绝、② 不再按根腿发整份、① 的带宽回到修前水平**。
第一轮里 `整表=1` 明确出现在 5 秒行里（`腿记录=1（接=0 丢=0 整表=1 …）`），
说明换端那一支真的走到了"整表 + 锚点重建"。

**没有做的**：没有**人为**触发换端（`train changeends` 会打乱 AI 的作业状态，没动）——
"换端那一拍"的读数是 AI 车自己在终点换端时自然产生的；前几轮观察窗的长度取决于 AI 车
什么时候路过玩家所在的车站（第三轮只有 54 秒有车）。

## 6. 遗留

* **客户端被拒的记录最长只重试 1.2 秒**（§3.10）：超过就放弃、等下一次整表。`缺轨` 之外的原因
  （基准不同源）重试没有意义，只能靠"形状变了"或定时兜底重新对齐 —— 那种情况现在应该已经不存在了
  （§3.7 + §3.9），但真发生了也只有 ≤60 秒的窗口。
* 遗留单点走行器（非编组体）的 `mirrorPathAnchorM()` 恒为 0，与它自己的 `buildLegs()`（也从 0 起算）一致；
  它的镜像里程本来就与 `distanceM()` 不同源，这一轮没动。
* 回退开关：`-Dmmtr.motion.legs=false`（关掉整条腿表通道，回到"车头走到阴影末端就停住"的旧行为）、
  `-Dmmtr.motion.legs.fullSeconds=0`（只关定时兜底）、`-Dmmtr.motion.stream=false`（关掉 ① 整条通道）。
* 引擎用例里有 4 支**与本次改动无关的红灯**（`MmtrConsistMultiCarPlacementTests` ×2、
  `MmtrTrainCarsJsonTests`、`MmtrRouteConflictTests`）：前两支与第三支依赖**开发存档里已经不存在的**
  股道（`assertNotNull(siding, "the long … siding must exist")`，存档数据变了），第四支的断言字符串
  来自本次改动之外的未提交 WIP（道岔等待理由）。本次改动的用例（线格式/腿表/客户端同步）全绿。
