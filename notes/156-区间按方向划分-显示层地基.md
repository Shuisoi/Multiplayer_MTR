# 156 · 区间按方向划分：显示层的地基（批次 1）

> 用户提问（2026-09-15）："需要在 web 构建一个以轨道为基础的区间显示。首先对于区间的概念我们不能单单
> 从轨道节点进行划分，毕竟涉及到双向，我们如何设计比较好？"
> 用户后续裁定：**① 只有灯产生边界（节点永不切分）；② Web 用方案 B（方向带）；③ 旧的单值节点归属直接删除。**
> 本轮 = 批次 1（引擎加字段，判定逻辑零改动）。引擎 **691 通过 / 0 失败 / 4 跳过**（689 → 691，两条新用例）。

---

## 1. 先说结论：模型层早就是对的，缺的是把"方向"报出来

现场核对（2026-09-15，运行中的 dev 世界：140 轨 / 73 灯 / 77 区间）：

| 事实 | 数据 |
| --- | --- |
| 区间总数 | 77 |
| 被区间覆盖的轨 | 96（另外 44 根不在任何区间里） |
| **1 根轨只属于 1 个区间** | **34 根** |
| **1 根轨属于 2 个以上区间** | **62 根** |
| 最多的那根 | **属于 5 个区间** |
| 长度分布 | 70 个 < 50 m，3 个是 628.7 / 584.6 / 289.6 m（见 §5） |

所以"一个点/一个节点 → 一个区间"这种**单值**模型在这个世界上不是不优雅，是**必然出错**：
96 根被覆盖的轨里 62 根有多个归属。

而引擎里其实**已经**按方向建区间了：`RailSpan` 带 `headingX/headingZ`，`matchesHeading()` 做方向过滤，
`sectionAt(轨, 弧, 方向)` 的注释就写着"同一个点属于两个方向各一个区间"。
缺的只是**接口没把方向发出来** —— `SectionView` 只有 `id/exitSignal/aspect/occupied/length/spans`，
网页只能靠区间 id 的字符串去猜方向。这是显示层做不出双向的**唯一**根因。

## 2. 概念定义（本轮定案）

**区间 = 某一行车方向下的一段路**，不是"一段轨"，节点根本不在定义里：

```
Section = {
  entrySignal   开本区间的那盏灯（它把守入口）
  direction     本区间的行车方向（单位向量 + 角度 + 中文名）★
  spans[]       [(railHex, arcFrom, arcTo, heading)] 有序；每段就是列车实际走过的弧窗
  exitSignal    出口灯（或 END）
  occupied      占用
  next          下游区间（按出口灯连）
}
```

**切分规则**：区间从一盏灯开始，走到**下一盏面朝同一方向的灯**为止；
**节点不产生边界**（只有站在节点上、面朝本方向的那盏灯才产生边界）；
走不到的岔腿**守着但不判断路**（沿用 notes/132 §5）。

推论（用户提的那件事）：**"节点归属"在双向线路上必然是多值的**。所以归属表的类型从

```
(节点)            → 区间id           ← 单值，双向必错（旧 GateBlock 层就是这样）
```
改成
```
(轨hex, 弧, 方向) → SectionId         ← 多值索引（sectionAt 已经是这个形状）
(轨hex, 弧)       → {(方向, 区间)…}    ← 给显示层的"成员集合"（本轮新增 byRail）
```

## 3. 本轮改了什么（纯增量，判定逻辑一行未改）

### 3.1 `MmtrDirectionalBlockService`

- 新增 `Direction{angle, dx, dz, label()}`：`label()` 给中文方向名（南/北/东/西行）。
- 新增 **`angleOfHeading(headingX, headingZ)`**：把行进向量换回 MTR 的 Facing 角，与读灯的
  `headingOf(a) = (-sin a, cos a)` **严格互逆**（`a = atan2(-dx, dz)`，归一化到 `[0,360)`）。
  为什么必须互逆：灯的角与区间的方向角**必须是同一套数**，否则网页画的箭头会整体转 90°
  而数字看着全都"挺合理"——这是最难查的一类错。现场实测两者逐盏对得上（0 = 南行、180 = 北行）。
- `SectionView` 补 `entrySignalKey` 与 `direction`；新增私有 `directionOf(Section)`
  取**第一段**的行进朝向（区间内所有 span 必须同向——那是"走行不许掉头"的要求，见 §5）。
  入口灯单列一份的理由：区间 id 在"一灯多腿"时带 `#n` 后缀，前端不该拆字符串去还原它。

### 3.2 `SystemMapServlet#getMmtrSections`

每个区间新增：

```jsonc
"entrySignal": "-145,-60,-169",
"direction": { "angle": 180, "label": "北行", "dx": 0, "dz": -1 },
"spans": [ { ..., "dirOfTravel": true } ]      // 本段是沿弧增还是沿弧减走过
```

新增顶层 **`byRail[]`**（方案 B 的地基）——"一个点属于哪几个区间"：

```jsonc
{ "hex": "...", "from": 0, "to": 28,
  "members": [ { "section": "-157,-60,-419", "angle": 0, "label": "南行", "aspect": "RED", "occupied": false },
               { "section": "-145,-60,-169#2", "angle": 180, "label": "北行", "aspect": "GREEN", "occupied": false } ],
  "memberCount": 2, "directionCount": 2, "bidirectional": true }
```

粒度 = "轨 hex + 弧窗"：一根多归属的轨会展开成几条记录，**前端直接画、不自己求交、不自己算弧长**
（这与既有 `points` 采样的原则一致：引擎是唯一几何真源）。

## 5. 顺带查清的两件事（记在这里，不在本轮修）

1. **628 m 巨块的成因**（用户问的双向显示问题的另一面）：
   区间 `-145,-60,-169#2` 长 628.7 m / 26 段轨，**入口灯角 = 180（北行）**，
   走行顺序是"沿 x=-155 向南 → 穿过内圈 U 弯（-161,-60,-486）→ 沿 x=-170 向北"。
   也就是**走行在 U 弯处跟着钢轨的物理连接转过头了**，从南行走廊走进了北行走廊，
   最后撞上 `x=-170` 上第一盏朝北的灯才停。它中途路过 15 盏朝南的灯没停，是因为
   既有判据（背向的灯不算边界，`aLampGuardingTheOppositeDirectionDoesNotEndTheSection` 钉的）
   在起作用——**那条判据本身是对的**（现实里分界点两架背靠背、背向那架管反方向），
   缺的是**"走行必须始终待在同一个行车方向里"这条不变量**。
   这也是"三片未交付"里 `Section.direction` 必须取第一段朝向的原因：区间内不许掉头。
   → 列为**批次 4**（单独一轮，它会改少数区间边界，必须逐条红证）。
2. **一根轨属于 5 个区间**的那根在咽喉（`-160/-168/-172/-191` 走廊的交汇处），
   属于层叠区间。方案 B 的 UI 必须能表达"同段弧同时属于多个区间"（用层叠 + 冗余度徽标），
   这正是"方案 A（交替上色）"做不到、必须选 B 的理由。
