## 1. 按现实做法（§8.1 的口径逐条落进代码）

```
故障 / 晚点超阈值
  → 该车的**后续趟次**转给替补车          （MmtrServicePlan 一行不改）
  → 接续点 = "后续某站的某一趟次"，不是凭空开始：
      替补车需要一条"从停放位置开到接续站"的前置任务   ← 本类的全部要点
  → 若替补来不及（前置任务时长 > 可用窗口）→ 取消该趟 + 发出**带理由**的事件
```

`MmtrSubstitution.handOver(...)` 的三步：

1. **冻结期内的条目原样留给故障车**（在途不打断：它得先把手上的活跑完）；
2. **接续点**：从第一趟"替补来得及开到接续站"的趟次开始 —— 判据就是现实里那一条：
   前置任务时长（车场 → 接续站，用线路输入的 `leadTimeMillis`）必须塞得进"现在到那趟发车"的窗口。
   塞不进的趟**取消**（不能让它凭空出现在接续站），一路往后找；
3. **替补的交路** = 一条 `DEPART_YARD` 前置任务（目标 = 接续站的站台，计划开始 = 接续趟发车 − 前移量）
   + 接手的那些趟（**原样搬过来，时刻表一个字不改**）。

结果里带三样给人看的东西：`cancelledTripIds`（取消了哪几趟）、`notes`（一句句人话）、
`event`（要对外发的事件，**理由在 `reason` 里**，前台直接显示）。

## 2. 接进了既有的事件路径（所以能现场验证）

P5 的 `Fault`（车列下线）原来只是"取消未来趟次"；现在**先找替补**：

```
Fault（车列下线）→ 有替补：后续趟次交给它（时刻表不动）+ 前置任务；来不及的趟取消并记进 notes
                 → 没有替补：全部取消（原来的行为），事件理由写"没有替补编组可用"
```

于是这条能力**不需要新接口**：`POST mmtr-plan-event-upsert {kind:"FAULT", consistId:"C1", vehicleDown:true}`
就能在现场看到"计划里换了一辆车"。
