# 370 · 编组尾车驾驶室（saf420 的 10B）坐进去就被请出车外 —— 骑乘看门狗把"这一节车还在加载"判成了"人走出了车外"

日期：2026-10-03 · 承接：notes/199（OBJ 车地板盒是合成的）、227（上车是客户端权威）、198（结束骑乘的三条理由）
· 相关代码：`client/VehicleRidingMovement.java`

**用户口径（原话）**：「下一步是编组相关，saf420 的驾驶室 2 无法控制列车」。

**一句话结论**：人**进得去**（引擎也把钥匙给了他：`CAB_B·钥匙=CREW`），但 `movePlayer` 那一帧拿到的
地板/门洞盒列表是**空的** —— 因为**这一节车的模型还在加载**（`VehicleResource.getCachedVehicleResource`
在"模型没到手"时返回 null）—— `clampPosition` 找不到任何盒子 ⇒ `leaveRide`。
头车永远先被画到（所以 1A 一直没事），**尾车的模型只有在人坐进去那一刻才开始加载**，
于是"驾驶室 2 永远进得去、待不住、开不了"。

`engineEndOfSeat` = 2 = B，与 `10B` 一致。）

## 2. 定案：给骑乘那条链加上"为什么没推动"的留痕

`VehicleRidingMovement` 里 `tick()` 的看门狗只在"连续 5 拍没人推动玩家"时结束骑乘，
而"没被推动"有四种成因，现场长得一模一样。加了三行诊断（同一理由 1 s 一行）：

```
[MMTR-RIDE] 进舱：车=… 车节=9 驾驶室=2 座位=(-0.7, 0.88, 8.2) 镜像车数=10
[MMTR-RIDE] 骑手停滞：车节不匹配：手上=9 走到的是=0（… 车节缓存=0 … 冷却=0/5）
[MMTR-RIDE] 骑手停滞：不是骑乘的那辆车：走到的是=-6662411583594295190（…）
[MMTR-RIDE] 骑手停滞：这一节车的模型/地板盒还没来 ⇒ 先挂在车上等（不再立刻请人下车）
[MMTR-RIDE] 结束骑乘（四个角都没有地板（点 x=-0.7 z=8.2 y=0.88；这次一个盒都没有（车型没有 FLOOR 部件？或车节对不上）））车=… 车节=9 驾驶室=2
```

两次实机（`train board <停稳的车> 10B`，2026-10-03 11:25 与 11:28）都在**第一次尝试**上复现。
`这次一个盒都没有` 是关键：不是"点没落在地板上"，是**这一帧根本没有盒子**。

## 3. 真因链（逐环有代码位置）

1. `RenderVehicles` 每节车去取这一节的资源缓存：`vehicleResource.getCachedVehicleResource(carNumber, totalCars, false)`；
2. 这一节的**模型还在加载**时它返回 **null**（`VehicleResource:423-428`：只要有一个
   `vehicleModel.cachedModel.getData()` 为 null 就返回 null）⇒ `floorsAndDoorways` 空表；
3. `movePlayer` 拿着空表去 `clampPosition` ⇒ `offsets.isEmpty()` ⇒ `leaveRide("四个角都没有地板")`；
4. 头车 `saf420cab_a` 每帧都在画 ⇒ 早已加载完；**尾车 `saf420cab_b`（3.8 MB OBJ）只有人坐进去才第一次被请求**
   ⇒ 它永远是"加载中的那一节"。

`saf420` 的包本身没问题：`mmtr_anchors_saf420cab_b.json` 锚点齐全（cabdoor_2_x / seat_2 / windshield_2_1 /
hud_2 / light_2_x），`mtr_custom_resources.json` 里两头控制车都是 `legacyRiderOffset=-0.12`（合成地板 y=0.88，
与座位点 y=1.39 差 0.51 m，在 1 m 容差内）。

## 4. 修法（`VehicleRidingMovement.java`，客户端）

| 处 | 改动 |
|---|---|
| `movePlayer` 的 `offsets.isEmpty()` 分支 | **"一个盒都没有"不再立即下车**：那是"模型还没加载"的中间状态。宽限 `FLOORS_NOT_READY_GRACE_MILLIS = 15 s` 内保留骑乘；且**刻意不 return**，照常走方法尾部的定位 —— 车在动时人仍然被钉在这一节车上。只有"盒子在、点/Y 够不着"才是真的掉出车外，照旧下车 |
| `movePlayer` 开头 | 记下"这一节的地板盒从什么时候开始缺"（有盒子就清零），并打一次 `骑手停滞：这一节车的模型/地板盒还没来` |
| 早退留痕 | `ridingVehicleCarNumber != carNumber` 只在**走到驾驶室所在那一节**时留痕（遍历别的车节对不上号是正常的，原来会每秒刷一行） |
| `mmtrRideDiag` / `进舱` / `上车覆盖车节` | 新诊断：骑乘状态、车节缓存、驾驶室车节、镜像车数、冷却计数；`startRiding` 若在握着驾驶室时改掉"我在第几节"必须留痕 |

## 7. 教训

1. **"进得去"与"待得住"是两件事**：进舱那一步只写骑乘坐标与申领钥匙，真正把人钉在车上的是
   每帧的 `movePlayer`；中间任何一环拿到空数据，症状都是"坐进去几秒后被请出去"，而日志只写着
   "四个角都没有地板"，看起来像模型问题。
2. **空列表要分两种**："一个盒都没有"（数据没到）与"盒子在但够不着"（真的掉出去）。
   前者该等，后者才该下车 —— 这次就是把这两件事分开。
3. **诊断要看门狗自己的状态**，不要只看结果：`tick()` 的冷却计数、手上的车节、镜像车数这三样
   一摆出来，四种成因立刻分开。
