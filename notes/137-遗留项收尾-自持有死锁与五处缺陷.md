## 1. 一辆车被**自己的持有**卡死（notes/136 §3，清单第 1 项）

### 1.1 现场形状（原文照抄自 notes/136）

```
车 8431887902004786548（调车任务 MANEUVER）停在出发信号前，进路 PENDING：
  "物理道岔 -212,-60,-159 被 v8431887902004786548 按在位置 1（岔股开放），
   本车需要位置 0（正线贯通）—— 两条进路互斥"
point why -212 -60 -159 → 物理位置 = 1，物理持有者 = v8431887902004786548
```

**持有者就是它自己**，于是两个判据互相咬死：进路因为"物理位置 ≠ 本车要的位"判 PENDING，
而意图扳岔的第一道闸门是"有人物理持有就不扳"——**没有"持有者就是我"这条豁免**。谁也解不开。

### 1.2 为什么单靠"豁免"不够：位置由**持有者**决定

T1（notes/116）之后，`mmtrTurnoutPosition` 与 `mmtrSyncTurnoutPositionToGrant` 都是**先读物理持有者**：

```java
final int physical = mmtrPointAuthority.physicalPosition(x, y, z);
if (physical != NO_PHYSICAL_HOLDER) { return physical; }   // ← 持有者说了算，行视图写了也没用
```

所以"把行视图/道岔行写过去"**根本不会改位置**。豁免的写法必须同时**改它自己的需求**，
否则症状会变成"日志说扳过去了、车还是不动"。故本轮三处一起改：

| 层 | 改动 | 作用 |
| --- | --- | --- |
| 权限层 | `MmtrPointAuthority.repointPhysicalHold(x,y,z,owner,position)`（持有关系与窗口不变，只换它要的位） | 让"持有者改自己的位"成为一次真实的状态变更 |
| 意图扳岔 | `Simulator.mmtrThrowTurnoutForIntent(..., requesterOwner)`：**别人持有**才拒；持有者本人**豁免**，并调 `repointPhysicalHold` | 解开死锁的**即时**路径：车在岔前就能自己把位换过来 |
| 重新规划 | `Simulator.mmtrReleaseStalePhysicalHolds(owner, wanted)` + `Vehicle.mmtrReleaseStaleHoldsForPlan` 在 `armMmtrPointRun` 里**先放旧的、再申请新的** | 不留垃圾：旧计划按下的位在新计划不要它时立刻让位（队列头接手） |

`MmtrForkElection.elect` 把 `pointAuthorityOwner` 一起传下去（生产里就是 `"v"+车辆id`）。

### 1.3 安全性没有被放松

豁免只对**持有者本人**成立，而且**第三道闸门照旧**：
`MmtrJunctionState.blockedThrowReason`（车压在岔区上不扳）是独立的一条，豁免第 1006 行不会把道岔
从车底下抽走（本轮还给**自动**那条路也补上了同一道闸，见 §3）。释放侧同样带净空校验：
**车还压在岔区上就不放**（它一走，下一次重新规划再放）。

### 1.4 用例（`MmtrTurnoutAuthorityTests`，6 → 9 例）

- `onlyTheHolderItselfMayRepointATurnoutItPins`：别人要求扳 → 拒且位置不动；**它自己**要求 → 扳成，
  且 `physicalPosition` 与 `physicalHolder` 一起对得上（证明改的是持有者的需求，不是只写行视图）。
- `aReplanGivesUpThePositionTheOldPlanPinnedButKeepsTheOneItStillWants`：新计划要**同一位** → 一处不放
  （等联锁时每 tick 重来，不能churn、不能丢队列位置）；要**另一位** → 放掉且幂等。
- `aRouteBlockedOnlyByTheVehiclesOwnStaleHoldBecomesSetOnceItIsDropped`：整条链的端到端 ——
  进路 PENDING 且理由点名"持有者是本车" → 按修好的顺序自救（先放旧的、再原子申请）→ **SET**。

## 2. `vehicle remove --depot=<车辆段>` 只清一条股道（清单第 2 项）

`--depot` 原来走 `resolveSiding`，而那个方法给 `--depot` 的语义是**"这个段里的第 index 条股道"**
（那是给 `vehicle spawn` 用的：一条股道同时只停一组车）。于是"按车辆段删"实际只清一条，
而用法文字与结果行都让人以为删干净了（现场：`aassdd` 两辆车只删掉一辆）。

现在 `--depot` **遍历该车辆段的全部股道**，并把过程说清楚：

```
车辆段「aassdd」共 3 条股道，扫到 2 辆车
股道 -5385228036074278397 上有 1 辆车
股道 -3054567530540565369 上有 1 辆车
已删除车辆 …
按股道清理完成：扫 3 条股道，删掉 2 辆车
```

`--siding` 仍是"只清这一条股道"（语义没被带偏）。

**顺手修掉一个真缺陷（用例抓出来的）**：找不到目标时，代码先往 `result` 里写一句话、再
`return new Result(false, …)` —— 那句话永远到不了用户（新对象是空的），失败只剩一句"命令失败了"。
`--siding` 与 `--depot` 两条失败路径都改成**先建失败的 Result 再写行**。

用例：`MmtrVehicleCommandTests`（新文件，4 例）—— 两条股道各一辆，一次 `--depot` 之后**两条都空**；
空车辆段不算失败且有可读回话；`--siding` 只动点名的股道；找不到车辆段要说清楚且什么都不删。

## 3. 自动扳岔补净空闸（清单第 3 项，notes/130 §8 第 2 条）

人工扳岔（`point set`）与意图扳岔早就有"车压在岔上不许扳"，只有**跟着授权自动扳**那条路没有。
本轮补上，而且补的是**两条**路 —— 现场读数说明"只补每 tick 的同步"是不够的：

| 路径 | 什么时候改位置 | 本轮处置 |
| --- | --- | --- |
| `mmtrSyncTurnoutPositionsToGrants`（每 tick 跟着授权折位置） | 没有物理持有者时 | 直接加 `MmtrJunctionState.blockedThrowReason` 闸（与人工/意图同一条判定） |
| **`MmtrPointAuthority.request(...)`（授权申请本身）** | T1 之后**位置由持有者决定**，所以新持有者在**申请那一步**就把位置改掉了 | 新增 `PositionChangeGuard` 注入（`Simulator::mmtrPositionChangeBlockedReason`），申请要被拒时**收回刚发出的逐进向授权、改为在道岔上排队**（不留半个持有，T1b 不变量） |

**为什么不动单车那条 `mmtrSyncTurnoutPositionToGrant`**：它是**列车自己**走到岔前、按自己的授权就位用的
（`MmtrForkElection` 在选举之前调它）。车到岔前时车头本来就进了净空区，给它加闸等于
"车到了、道岔却永远不同步"——那是**新的死锁**。每 tick 的**全局**同步才是"别人的道岔"该被拦的地方。

**排除请求方自己**：`MmtrJunctionState.blockedThrowReasonExcept(..., excludeVehicleId)` ——
净空被**别人**占住才拦。请求方自己压在岔上不算：它按着自己的位（T1），本来就该能改自己的需要
（换端/折返），否则会把自己锁死；"从自己车下抽走"这件事由走行侧与人工侧的闸门各自兜住。

用例：`MmtrJunctionClearanceTests.theAutomaticGrantPathsAreRefusedWhileAConsistFoulsTheJunction` ——
先断言显示层说"岔区净空被占"，再断言 ① 申请被排队（**修前这里直接 GRANTED 并改位置**）且不留半个持有、
② 每 tick 同步不扳、③ 请求方自己不算被挡、④ 车出清后自动同步照常扳到位。

> 这一项是 notes/130 §8.2 里"本次没做，因为可能改变既有进路测试的时序语义，需要单独一批验收"的那条。
> **验收结论：全量零新增失败**（606 通过，route/conflict 那一批一条没动）。

## 4. 区间占用收敛到**走得到的 span**（清单第 4 项，notes/132 §5）

notes/132 收尾时留了一条保守项：区间的 **span 照旧覆盖走不到的腿**（守住整个咽喉），
而占用判定是"本段任意 span 有车" —— 于是"某列车在道岔扳动之前进了岔股、之后一直停在走不到的
那条腿上"会让这盏灯**永远红**。

本轮把"**守卫范围**"与"**占用范围**"分开：

- `RailSpan.reachable`（走行时算出来，就是 notes/132 已经用来决定"出口灯/结束节点"的那个 `reachable`）；
- `isOccupied(Section…)` **跳过 `reachable == false` 的 span**；
- `signal why` 的区间描述里走不到的段会带 `(走不到)` 后缀，便于对照。

守卫照旧（`blockedAtDeparture`、灯守的轨、`blocks` 图层都不变）；**只在"这条路走不走得进去"
这一件事上收敛**。全量零新增失败。

## 5. 存档 hex 键**载入归一化**（清单第 5 项，notes/130 §6b 的遗留）

同一条实体轨有两种写法（互为逆序）。对外一律发规范写法（`canonicalHex`），而
`mmtr-points.json` 的行（`switches[].via`）与人工锁（`locks[].via`）存的是**引擎内部写法**。
同一份存档里读回来一致，所以今天不出错；但**世界改画**（某根轨反向重画）之后旧键就是孤儿键 ——
**锁还在文件里，却静默锁不住任何东西**。

修法：在 `refreshMmtrTurnouts` 的"轨图签名变了"那一刻跑 `normalizeMmtrPersistedRailHexes()`
（载入时轨图还没建好，做不了），用 `mmtrResolveRailHex`（两种写法都认）把行与锁的 `via` 翻成
引擎内部写法；`BranchStore.rekey` / `MmtrPointAuthority.rekeyLock` 负责换键。有变化才落盘，幂等。

用例：`MmtrPointPersistenceTests`（新文件，5 例）—— 锁/行两种写法被归一化且**旧键不再留着**、
归一化让锁**真的锁得住**（修前 `isTurnoutLocked` 为 false，这是"孤儿键"的现场）、幂等、
垃圾键与别的节点原样不动、`rekey` 的 no-op 语义。

> 写这组用例时踩到一次**夹具污染**：夹具目录复用，上一次跑落盘的 `mmtr-points.json` 会被载入，
> 于是"归一化之前"的前提不成立（第一次全量跑就红了）。夹具现在先删那份文件 —— 教训与
> notes/130 §5.2 的"测试夹具会互相污染"是同一条。

## 6. 两个度 4 共用节点（清单第 6 项）：**需要改图，不是代码**

用户 2026-09-14 的裁定：**"一个节点只能有一个道岔，那里是历史遗留问题"** —— 引擎保持
"一个节点 = 一个可动件"，这两个节点继续不建模（`point why` 会说明"相邻轨 4 根"）。
要统一就得**改图**。本轮把现场几何读清楚了，下面是可直接照着做的清单。

### 6.1 现场读数（`mmtr-topology` + `point why`，2026-09-14 实测）

**节点 `-219,-60,67`**（degree 4，四条腿的远端）：

| 远端 | 方位 | 说明 |
| --- | --- | --- |
| `-242,-60,67` | 正西 | 与东侧那根**精确共线**（一条正线） |
| `-170,-60,67` | 正东 | 同上 |
| `-242,-60,76` | 西北 | 浅斜线（约 0.06 斜率） |
| `-202,-60,74` | 东北 | 浅斜线（约 0.08 斜率） |

**结论**：一条沿 x 的正线 + 西北/东北两条浅斜线**汇在同一个节点**上 = 两处道岔背靠背
（现实里也是两组可动件）。

**节点 `1,-60,38`**（degree 4）：`1,-60,6`（正南）/ `1,-60,64`（正北）为一条正线，
`-4,-60,7`（西南斜）/ `-19,-60,51`（西北斜）两条斜线汇在同一节点上 —— 后者正是 notes/130
里的**对称人字岔**那根轨。

### 6.2 改图步骤（在游戏内做，MTR 铁轨工具）

以 `-219,-60,67` 为例（另一处同理）：

1. **先把正线断开成一个新节点**：在正线上插入一根 3 格短轨：
   `-219,-60,67 ↔ -216,-60,67`（两段正线：`-242,67 ↔ -219,67`、`-216,67 ↔ -170,67`）。
   ⚠ 断点要选在**两条斜线各自的汇入点之间**，否则一处道岔仍会与另一处共节点。
2. **把东北那条浅斜线挪到新节点上**：删掉 `-219,-60,67 ↔ -202,-60,74`，在
   `-216,-60,67 ↔ -202,-60,74` 重画（几何几乎不变，只差 3 格起点）。
3. 于是两个节点各 3 条腿：`-219,-60,67` = 正线西 + 正线东 + **西北斜**；
   `-216,-60,67` = 正线西 + 正线东 + **东北斜**。

**注意**：`1,-60,38` 的断点最好与 `-19,-60,51` 那处人字岔的几何对齐（斜线斜率较大，
断 3–4 格即可），并**避开**站台/道床的既有方块。

### 6.3 改完怎么验（照着跑，不需要读代码）

```
point why -219 -60 67        # 期望：认成 1 处单开道岔（三条腿），不再说"相邻轨 4 根"
point why -216 -60 67        # 期望：同样是一处单开道岔
point list                   # 度 4 的 legacy 行应消失
blocks all                   # 这两个节点的闭塞归属随之重算，不应再有"同向重叠"
```

改图**只能解决"引擎不建模"这一件事**；这两处道岔在改图之前一直是**没有任何物理互斥保护**的
（`point why` 会这么说），所以改图前的现场作业要当"这里有盲区"来对待。
