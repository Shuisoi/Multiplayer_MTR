# 231 · 客户端"连不上服务器"的真因：类初始化里那次没有超时的黑名单抓取

> 用户报（2026-09-21 21:14）：「双端又连不上了」。这是 notes/228 里那个"卡在正在连接服务器"的**第二次**，
> 但根因与上一次（`enforce-secure-profile` + Mojang 公钥超时）**不是同一处**。

---

## 1. 先排除掉的东西（都不是原因）

| 检查 | 结果 |
| --- | --- |
| 服务端进程 / 25565 监听 / 8888 应答 | 都在（PID 47660，`::` 监听 25565 与 8888，引擎 200） |
| `server.properties` | `online-mode=false`、`enforce-secure-profile=false`、`server-ip=` 空 |
| 从本机 TCP 连 `127.0.0.1:25565` / `[::1]:25565` | **都连得上**（服务端是双栈 socket，IPv4 走 `::ffff:127.0.0.1`） |
| 实机日志 | `Connecting to 127.0.0.1, 25565` 之后再无**任何**输出；服务端侧连登录行都没有 |

也就是：**不是端口、不是防火墙、不是 online-mode、不是服务端**。

## 2. 真因（线程转储一眼看出）

```
"Server Connector #1" ... waiting on the Class initialization monitor for
    net.minecraft.client.network.AllowedAddressResolver
  at com.mojang.patchy.MojangBlockListSupplier.createBlockList(MojangBlockListSupplier.java:23)
  at net.minecraft.client.network.BlockListChecker$$Lambda.apply
  at net.minecraft.client.network.BlockListChecker.create(BlockListChecker.java:20)
      ↓
  at sun.security.ssl.SSLSocketImpl.startHandshake(...)   ← 卡在 TLS 握手读
```

链条：{@code ConnectScreen} 要用 `AllowedAddressResolver` → 它的**静态初始化**建 `BlockListChecker`
→ patchy 去抓 `https://sessionserver.mojang.com/blockedservers`（javap 确认：URL 硬编码、
`openConnection().getInputStream()`，**没有读超时**）→ 本机到 Mojang 的 TLS 握手不返回
→ **类初始化永远不完成** → 所有等这个类的线程（渲染、登录、Server Connector）全部挂住
→ 界面上就是"正在连接服务器"永远转圈，**而且不会有超时**。

现场证据：客户端进程挂着 3 条到 `150.171.110.133:443`（Microsoft 边缘）的 ESTABLISHED 连接，
没有任何一条到 25565 的连接（连接还没开始）；4 个线程等在同一个类初始化锁上。

**为什么这是结构问题、不是抖动**：那次网络调用没有超时，且长在**类初始化**里 ——
只要这条路由不通，客户端就必然挂在同一个地方。上次修好的那条（`enforce-secure-profile`）
管不了它：这是**客户端**在连出去，与服务端配置无关。

## 3. 修法：客户端加一个 mixin 守卫（`MojangBlockListSupplierMixin`）

```java
@Mixin(MojangBlockListSupplier.class)
public abstract class MojangBlockListSupplierMixin {
    @Inject(method = "createBlockList()Ljava/util/function/Predicate;", at = @At("HEAD"), cancellable = true)
    private void mmtrSkipBlockListFetch(CallbackInfoReturnable<Predicate<String>> callbackInfo) {
        if (Boolean.getBoolean("mmtr.blocklistFetch")) return;   // 想照原版抓就加这个 JVM 参数
        callbackInfo.setReturnValue(serverAddress -> false);     // 空黑名单：不抓、不卡
    }
}
```

* 挂在 `mtr.mixins.json` 的 **client** 段（服务端根本不需要它）；
* 开发/离线环境里"封禁服务器名单"本来没有意义，直接不抓；想恢复原版行为用
  `-Dmmtr.blocklistFetch=true`（一个开关，不用改代码重编）；
* **离线核对过**：`sandbox/run-mixin-probe.ps1` 报
  `OK MojangBlockListSupplierMixin.java → com.mojang.patchy.MojangBlockListSupplier（方法 1 个）`，
  含描述符精确匹配 —— 这正是 notes/226 立那条纪律的原因：`method = "…"` 写错编译不报，启动才炸。

## 4. 顺手记下的两件事

1. **卡死的客户端必须强杀**：渲染线程也等在同一个锁上，窗口点不动 ——
   本轮是我用 `Stop-Process -Force` 结束它（PID 4272）的。下次遇到同样症状直接杀进程，别等它超时（没有超时）。
2. **客户端是 IDEA 起的**（`idea64.exe → java(gradle daemon) → java(runClient)`），
   不是 `scripts\dev-client.ps1`。所以"重启客户端"这件事只能由用户在 IDEA 里按 Run ——
   我这边的脚本重启的是**服务端**，别把两者搞混。

## 5. 与本次部署无关的一处现场（下一轮要看）

重启后的作业跑到第 9/16 步「回程到 3 站 2 台」时**卡住不动**，日志每 5 秒一条：

```
[MMTR-PT] 按计划补申请：车 -6532065768603640975 被 -170,-60,-511 挡住，但计划要的腿不在岔口腿表里 —— 需要重规划

           turnout at node requires a branch outside the walker's branch0/1 choice
```

即：**道岔的腿号超出了走行器 branch0/branch1 的二选一表达能力**（"牵出—推进"这种
setback 进路需要的腿不在腿表里），于是"补申请"与"重规划"互相推着转，谁也不动。
这与本轮（模板/子任务、Mixin 守卫）无关，是**进路与道岔腿表**那一层的老问题；
本轮作业在第 3/4/6 步（开往 + 停站乘降两条模板）都正常跑过，所以模板化本身没有回归。
