# 373 · 车灯（四）：**车灯照不亮自己的灯罩** —— 尾灯的"染红"与自发光那一半

日期：2026-10-03 · 承接：**notes/372**（AI 驾驶员拨灯：车头白、车尾红）· 代码：`MmtrHeadlights.java`、
`mmtr_headlight.glsl`（+ `assets/sodium/...` 的那份副本）、`mmtr_vehicle_light.fsh`、
`mmtr_lightfield_pack_headlight.glsl`、`MmtrLightField.java`

**用户口径（原话）**：「车尾需要使灯变红阿」。

**一句话结论**：372 把**状态**修对了（AI 车尾的开关确实是"尾灯"），但**灯罩本身根本吃不到那一盏灯** ——
车灯的加性项是 `锥形 × 兰伯特` 的，而灯罩自己两条都不满足（① 在锥顶之外、② 法线背对灯心），
**任一为 0 ⇒ 这一盏灯对自己的灯罩贡献为零**；尾灯又因为"尾灯不照世界"（notes/352）在地形那条路上被整个跳过
⇒ 车尾没有任何地方是红的。而且这**不是调大强度能解决的**：加法做不到把白灯罩染红
（`白(1,1,1) + 红(0.16,0.02,0.01)` 还是白）。所以尾灯必须另走一条"**自发光染色**"的路。

---

## 1. 根因链（每条都能在代码里指到行）

| # | 事实 | 位置 |
|---|---|---|
| 1 | 加性项 = `color * (cone * attenuation * lambert)`，返回 `albedo * sum` | `mmtr_headlight.glsl` 的 `mmtrHeadlightTerm` |
| 2 | **灯罩在锥顶之外**：灯罩片元到灯心的方向几乎垂直于灯的朝向 ⇒ `dot(toLight, -dir) ≈ 0` ⇒ `cone = 0` | 同上第 63 行（`smoothstep(cosOuter, cosInner, dot(...))`） |
| 3 | **灯罩法线背对灯心**：灯罩朝外，灯心在它后面/平面上 ⇒ `dot(normal, toLight) ≤ 0` ⇒ `lambert = 0` | 同上第 73 行 |
| 4 | 尾灯在**地形**那条路上被整个跳过（"尾灯不照世界"）⇒ 连"照到地面上的那点红"也没有 | `MmtrHeadlights.upload` 的 `terrainProgram && candidate.tail` |
| 5 | 尾灯的颜色本身也偏暗：`headlightTailLux` 出厂 **0.22** × 灯罩面积系数 0.74 ⇒ 0.16 | `MmtrLightField` / `MmtrHeadlights.requestCar` |

⇒ 现场："AI 开着车，车尾一点红都没有"。372 的实机日志也确实只证明了**状态**（`B端 尾灯`），
没有任何一行能证明**那盏灯在画面上是红的** —— 这正是本轮要补的读数。

## 2. 修法：标志灯另走一条"自发光染色"

| # | 改动 | 为什么 |
|---|---|---|
| 1 | 上传时把 `Pos.w` 写成**负数**表示"标志灯"（正 = 前照灯） | 零成本的一位信息：不新增 uniform 数组、不多一个字节。着色器里唯一用到 `Pos.w` 的地方加 `abs()` |
| 2 | 新函数 `mmtrMarkerGlow(relativeWorld, lampSurface)` → `vec4(rgb=灯色, a=权重)`：**只对"灯罩自己的几何"生效**（见 §8），**全向**（标志灯本来就是全向的）、到灯心 0.24 m 内权重 1（**平台**：灯罩有尺寸 ⇒ 实测角点离灯心 0.19 m，平台必须盖过它）、到 0.40 m 平滑落到 0、**不乘反照率**（红玻璃罩自己发光） | 这才是"红玻璃罩"的正确语义。**位置/半径分不开灯罩与车体**（灯嵌在平的车头面上，距离一样），所以"是不是灯罩"必须由几何判据给（§8） |
| 3 | 调用处用 **`mix` 而不是加法**：`color.rgb = mix(color.rgb, glow.rgb, glow.a)` | **加法做不到替换**：白灯罩 + 红还是白。两个调用处都改了：车厢（`mmtr_vehicle_light.fsh`）与光影包注入（`mmtr_lightfield_pack_headlight.glsl`） |
| 4 | 新 uniform `mmtrMarkerGlowM`（properties: `headlightMarkerGlowM`，默认 **0.40 m**；0 = 关掉这一项回到旧行为） | 半径要在**不重启**的前提下调（notes/345 的既有口径）。默认值是按灯罩尺寸量的：0.40 × 0.6 = 0.24 m 平台 &gt; 罩子角点的 0.19 m |
| 5 | `headlightTailLux` 出厂值 0.22 → **1.2** | 它现在同时是**染色的目标色**：1.2 × `TAILLIGHT_RGB(1.0,0.12,0.06)` × 面积系数 0.74 ≈ `(0.89, 0.11, 0.05)` = 饱和红（实机日志 `尾灯 lux=0.89`） |
| 6 | 地形那条路**不接**这一条（它永远收不到标志灯 —— 第 4 条跳过），在注释里写明 | 免得下次有人以为漏了 |
| 7 | `assets/sodium/shaders/include/mmtr_headlight.glsl` 与 `assets/minecraft/...` 那份**逐字同步**（本轮才发现仓库里有两份同名副本） | `MmtrSodiumTerrain` 供出去的是 minecraft 那份，而 Sodium 的 `#import` 真去查资源时用的是 sodium 那份（notes/350：找不到会当场抛异常）。**两份不一致 = 数学会漂**，两边都加了"改一处要 `Copy-Item`"的告示 |
| 8 | 诊断：**第一次认出我们的 program** 时报一行"灯表 uniform 齐了（标志灯自发光 uniform=有/没有）"；5 秒行加 `标志灯自发光=0.85m` | 这一轮真正花时间的不是着色器数学，而是"**跑的到底是不是新着色器**"：实测撞上 `compileJava/processResources` 双双假 `UP-TO-DATE`（notes/281 的同一族），build 里的着色器还是旧的 |

> ⚠️ 顺手修掉一个**哨兵坑**（`MmtrHeadlights.Locations` 的构造函数）：字段默认 0，
> 而 `refresh()` 里 `wasOurs = countLocation >= 0` 把 0 读成"上一次就有" ⇒ 第一次 refresh 被当成复核，
> **"uniform 齐了"永远不报**，且"从有变无 / 位置搬了"两条警告建在错误的基准上。
> 现在构造时先全部置 −1（"还没查过"）。这与存储槽位那条哨兵是同一个坑：**0 必须是"没有"，不能兼作"还没查"**。

## 4. 两个现场可调旋钮（改一行 2 秒生效，**不用重启**）

`mmtr/game/fabric/run/mmtr-lightfield.properties`：

| 键 | 默认 | 作用 |
|---|---|---|
| `headlightMarkerGlowM` | 0.85 | 标志灯自发光的半径（m）：0.34 m 内全染红，到 0.85 m 渐隐。嫌红圈小就加到 1.2，嫌糊就减到 0.5；**0 = 关掉这一项**（回到旧行为） |

## 5. 边界（诚实的）

| 项 | 说明 |
|---|---|
| 头灯**没有**自发光灯罩 | 本轮只给标志灯加了染色。头灯看不到这个缺陷（灯前的地面/车头有溢光），但严格说头灯的灯罩也是"不亮"的 —— 想给头灯也加一个白灯盘的话，是同一个函数加一个分支（用户没要求，没做） |
| 距离剔除（既有，本轮没动） | 候选灯的闸门是 `cameraDistance > range + 64`：尾灯射程 12 m ⇒ **76 m** 之外不进候选（近处看车尾完全没问题；远处那两盏灯在屏幕上只有两三个像素） |
| 染色会影响灯心附近的**车体** | **不会**（§8）：染色由几何判据限定在"常亮部件"= 灯罩那组面上，车体上一点红晕都没有（用户口径就是这条） |
| 光影包那条路 | 注入片段（`mmtr_lightfield_pack_headlight.glsl`）用的是同一份数学与同一个 `mix`，但**本机没有包在跑**，那条路只有代码与离线判据，没有实机画面证据 |
| 地形 | 收不到标志灯（notes/352 的"尾灯不照世界"），所以世界方块上不会有红灯斑 —— 这是**口径**，不是漏做 |

## 6. 已知瑕疵（留给下一个碰这里的人）

1. `uniform 齐了` 那一行对**地形 program** 会报"标志灯自发光 uniform=**没有**（这一份是旧着色器 ⇒ 尾灯不会变红）"，
   读起来像故障。判据应该加上"这个 program 有 `mmtrTerrainLuxScale`（= 地形）⇒ 不需要那个 uniform"。
   本轮没改（改它要再重启一次客户端，而它只影响日志措辞）。
2. `上传=N/8` 这个计数是**窗口里最后一次上传**写的，而地形那一趟会把尾灯跳掉 ⇒ 只画尾灯的窗口里
   会显示 `上传=0/8`（看起来像"一盏都没传"）。要分清得把"车厢上传"与"地形上传"分成两个计数。
3. 本轮又踩了一次 notes/281 的 `UP-TO-DATE 假绿`：`compileJava` 与 `processResources` 双双报 UP-TO-DATE，
   而 `build/classes`、`build/resources` 是旧的 ⇒ 客户端跑的是**旧着色器**。修法还是那一条：
   `Remove-Item -Recurse -Force fabric\build\classes\java\main` 之后重编（本轮连 `build/resources/main` 一起删才干净）。
   **判据：去 `build/resources/main/assets/...` 里 `Select-String mmtrMarkerGlow`，别信 Gradle 的话。**

## 7. 实机验收（需要人）

1. 站在一列车**车尾**那一端看：两盏灯应当是**红玻璃罩**（整块罩子红、**周围车体没有红晕**），不是白/不亮。
2. 站远一点（>80 m）：尾灯不再上传（亚像素），画面与旧行为一致。
3. 嫌红的范围/浓淡不合适：改 `run/mmtr-lightfield.properties` 的 `headlightMarkerGlowM`（默认 0.40）/
   `headlightTailLux`（默认 1.2），2 秒生效、不用重启。
4. 车头照旧：白（日间档暗、夜间档亮），且 18:00 自动翻档（notes/372 §3）。

## 8. 修正（同日，用户口径）：「玻璃罩为白色，其实仅需要红色玻璃罩就行了。不需要红晕」

第一版按"离灯心 0.85 m 内都染"来做，于是灯罩周围的**车体**也红了一圈（红晕）。
用户明确指出：玻璃罩（灯罩）本身在贴图里就是白的，**只要把这块罩子染红**即可，不要红晕。

**为什么半径解决不了**：先量了模型 —— `headlights` 组 = 两个 **0.3465 × 0.1449 × 0.035 m** 的小盒子
（24 个三角面，x 跨 2.5 m 说明是两个灯各一个盒子），而车灯是嵌在**平的车头面**上的：
罩子周围就是车体，距离与罩子几乎一样 ⇒ 任何"按半径染"的做法都必然把车体一起染。

**判据换成几何**：这个灯罩组在车底 properties 里是

```json
{"names":["headlights"], "renderStage":"ALWAYS_ON_LIGHT", "condition":"ON_ROUTE_FORWARDS"}
```

—— `RenderStage.ALWAYS_ON_LIGHT` 正是 MTR 用 `GraphicsHolder.getDefaultLight()`（UV2 = `0xF000F0`
= `(240,240)`）画的那一批"常亮部件"（`ModelTrainBase:94`）。而车厢那条 program 的片元着色器**本来就知道**
这件事（`flat in ivec2 mmtrLightUv` + 既有的 `mmtrForcedBrightUv2`）。所以新增一个更窄的判据
`mmtrAlwaysOnLightUv2(uv2)`（只要 `(240,240)`，**不含**车内照明那个 `(176,240)`），把它当
`lampSurface` 传给 `mmtrMarkerGlow`：**只有灯罩那几片几何会被染红**，车体一个像素都不沾 ✓。

半径同时收到 **0.40 m**（平台 0.24 m，刚好盖住罩子角点的 0.19 m）—— 半径现在只负责"盖住整块罩子"，
"染谁"由几何决定。

**顺带发现的一处资源包口径（没改，留问题给用户）**：`saf420cab_a` 与 `saf420cab_b` 两个车底的
`headlights` 组都写着 `condition: ON_ROUTE_FORWARDS`，而判据是
`vehicle.getIsOnRoute() && !vehicle.getReversed()`（`VehicleResource.matchesCondition`）
⇒ **这列车一旦被判成 `reversed`（人工 REV，或 AI 规划不出来时翻一次方向），两端的灯罩几何整个都不会被画**
（既没有白车头也没有红车尾）。上游 MTR 车底是 head_1/head_2 两个相反条件配对的，这里两端同一个条件。
要"灯罩常画、颜色全由灯光状态决定"的话，把那两处 `condition` 去掉即可（改的是资源包 properties，
不是渲染器）。

## 9. 用户实机反馈把它坐实了：「并不是红色的，灯消失了」 —— 就是 §8 最后那条

**用户口径**：「并不是红色的，灯消失了」。

**不是染色的问题**：染色只能改**已经画出来的**几何的颜色；几何根本没画，就什么也染不了 ——
而"灯罩消失"的原因正是 §8 末尾点出的那条资源包条件：

```
headlights 组：renderStage = ALWAYS_ON_LIGHT, condition = ON_ROUTE_FORWARDS
```

三条链一接就成立（都是读代码读出来的，不是猜）：

| # | 事实 | 出处 |
|---|---|---|
| 1 | `ON_ROUTE_FORWARDS` 判据 = `vehicle.getIsOnRoute() && !vehicle.getReversed()` | `VehicleResource.matchesCondition` |
| 2 | 编组车的 `reversed` = `consistWalker.mirrorReversed()`，而它 `return towardB()` = **"这趟车正朝 B 端跑"** | `Vehicle.syncMmtrConsistMirror()` / `MmtrConsistWalker:598` |
| 3 | 两个控制车（A 端、B 端）的 `headlights` **用的是同一个条件** | 在用包 `SAF420_v39.zip` 里两份 properties（本轮从 zip 里抽出来核过） |

⇒ **只要这列车朝 B 端跑，两端的灯罩几何一起不画**（既没白车头也没红车尾）。
现场日志正好撞在这个状态上（13:13:49）：`灯光=A端=尾灯 B端=日间` = 车头在 B 端 = 正在朝 B 端跑
= 旧包下**整列车一个灯罩都没有** ✓ 与用户看到的一模一样。

**修法（资源包侧，不是渲染器）**：`mmtr/tools/obj-mtr-packager/consist/saf420.json` 里两处
`partSpecs.headlights` 的 `condition` 从 `ON_ROUTE_FORWARDS` 改成 **`NORMAL`**
（= packager 的缺省；判据走 `matchesCondition` 的 default → `getChristmasLightState(NORMAL)` → **true** = 常画）。
重新打包为 **`SAF420_v40.zip`**（2026-10-03 13:10，`pack-consist.ps1 … -Version 40`），
`run/options.txt` 的 `resourcePacks` 换成 v40 ⇒ 客户端重启后生效（日志里 `Reloading ResourceManager: … file/SAF420_v40.zip`）。

**为什么这是"正确的口径"而不是绕过**：MMTR 的灯光是**状态驱动**的（notes/352：每个驾驶室一个三档开关，
同一块灯罩既当前照灯也当尾灯，颜色由引擎的档位 + 换向器决定）⇒ 灯罩**必须永远在**，
"亮不亮、白还是红"全归 `MmtrHeadlights` 那条路。上游 MTR 的 `head_1`/`head_2` 相反条件配对是
"只画前车灯的罩子"那套老逻辑（本包当年也据此删掉了 `tail_lights` 组），与我们的口径相反。

**顺带核过**：`BR101_v54.zip` 里**没有**任何 `ALWAYS_ON_LIGHT` 部件 ⇒ 不受这条影响（它的灯不是这么画的）。
